# 1. 为什么 Agent 需要记忆

**结论先行**：Agent 的智能不仅来自模型参数，更来自"记住什么"。没有记忆，每次请求都是一次无状态（Stateless）的函数调用；有记忆，才能形成连续、个性化、可积累的协作体验。

## 1.1 无记忆与有记忆的对比

### 1.1.1 无记忆的表现

无记忆意味着模型把每次请求当作孤立事件处理，前后请求之间没有任何状态传递。

```text
无记忆（Stateless）：
  请求1：你好           → "你好"
  请求2：我叫张三       → "很高兴认识你"
  请求3：我叫什么？     → "我不知道你的名字"   ← 信息丢失
```

### 1.1.2 有记忆的价值

有记忆（Stateful）意味着系统在请求之间保存状态，并在下一次请求时把相关状态注入上下文（Context）。

```text
有记忆（Stateful）：
  请求1：你好           → "你好"
  请求2：我叫张三       → "你好，张三"          ← 写入记忆
  请求3：我叫什么？     → "你叫张三"            ← 读取记忆
```

## 1.2 记忆驱动的能力矩阵

记忆不是单一功能，而是多项能力的共同底座。

| 能力 | 依赖的记忆类型 | 典型场景 |
|------|----------------|----------|
| 多轮对话 | 会话记忆 | 客服、助手 |
| 个性化 | 用户画像 | 推荐、写作风格 |
| 长期协作 | 跨会话记忆 | 项目管理、代码助手 |
| 经验积累 | 程序性记忆 | 工具使用模式 |

## 1.3 记忆缺失的代价

- **上下文断裂**：用户必须反复重复相同信息，体验割裂。
- **无法个性化**：每次都要重新说明偏好、角色、约束。
- **经验无法复用**：同类问题每次都从零推理。
- **难以长期协作**：跨天、跨周的任务无法接续。

**边界与坑**：记忆并非越多越好。无差别记忆会引入噪声、放大 Token 成本，并可能把过时或错误信息带入后续推理。

## 1.4 生产建议

- 明确区分"必须记住"和"可以遗忘"的信息类别。
- 记忆写入应可追溯（记录来源、时间、置信度）。
- 默认按用户与租户隔离，避免跨用户污染。

# 2. 记忆的层次

**结论先行**：记忆按生命周期与作用范围分为三层——上下文（Context）、短期记忆（Short-term）、长期记忆（Long-term）；长期记忆又细分为情景、语义、程序性三类。

## 2.1 三层记忆模型

```text
┌──────────────────────────────────────────────┐
│  ① 上下文（Context）                          │  本次请求带给模型的内容
├──────────────────────────────────────────────┤
│  ② 短期记忆（Short-term）                     │  当前会话的消息历史
├──────────────────────────────────────────────┤
│  ③ 长期记忆（Long-term）                      │  跨会话持久化
│     ├── 情景记忆（Episodic）  发生过什么        │
│     ├── 语义记忆（Semantic）  知道什么          │
│     └── 程序性记忆（Procedural）怎么做          │
└──────────────────────────────────────────────┘
```

### 2.1.1 上下文（Context）

上下文是单次请求实际发送给模型的全部 Token，包括系统提示、工具定义、记忆、检索片段、当前问题与输出预留。它的容量上限就是模型的上下文窗口（Context Window）。

### 2.1.2 短期记忆（Short-term）

短期记忆是当前会话（Session）内按时间累积的消息序列，通常以 Redis 或数据库存储，带 TTL（Time To Live，存活时间）。

### 2.1.3 长期记忆（Long-term）

长期记忆跨会话持久化，容量大、生命周期长，通常落在关系库、向量库或图数据库中。

## 2.2 长期记忆的三个子类型

| 子类型 | 回答的问题 | 示例 | 常用存储 |
|--------|------------|------|----------|
| 情景记忆 | 发生过什么 | 上次我们改了登录逻辑 | 事件表/时序库 |
| 语义记忆 | 知道什么 | 用户偏好简洁回答 | 向量库/键值库 |
| 程序性记忆 | 怎么做 | 部署流程、工具调用链 | 规则库/图 |

## 2.3 层次对比

| 层次 | 生命周期 | 存储 | 容量 | 访问方式 |
|------|----------|------|------|----------|
| 上下文 | 单次请求 | 内存 | 上下文窗口 | 直接拼接 |
| 短期 | 单次会话 | Redis/DB | 有限 | 顺序/窗口 |
| 长期 | 永久 | DB/向量库 | 大 | 语义检索 |

**边界与坑**：三层之间不是简单叠加，而是竞争同一份上下文预算。长期记忆召回过多会挤压短期记忆与输出空间。

## 2.4 生产建议

- 短期记忆负责"连续性"，长期记忆负责"积累性"，职责不要混淆。
- 长期记忆写入应有明确触发条件（如用户明确陈述偏好）。
- 每层都要有独立的容量与淘汰策略。

# 3. 记忆与 RAG 的区别

**结论先行**：记忆与 RAG（Retrieval-Augmented Generation，检索增强生成）都往上下文注入内容，但来源、时效与目的不同；二者互补，生产系统常同时使用。

## 3.1 本质区别

记忆来自**交互过程本身**，随使用动态增长；RAG 来自**外部文档**，相对静态，通过导入更新。

## 3.2 对比表

| 维度 | 记忆 | RAG |
|------|------|-----|
| 内容 | 对话历史、用户偏好 | 外部知识 |
| 来源 | 交互产生 | 文档导入 |
| 时效 | 动态增长 | 相对静态 |
| 检索 | 顺序/语义 | 语义 |
| 目的 | 连续性、个性化 | 知识补充 |
| 更新频率 | 高 | 低 |
| 一致性要求 | 中等 | 高 |

## 3.3 协同模式

> 两者常同时使用：RAG 提供知识，记忆提供连续性。检索时先由记忆召回用户画像与会话摘要，再由 RAG 召回文档片段，二者统一排序后进入上下文组装。

## 3.4 边界与生产建议

- 不要把用户隐私写进 RAG 知识库，也不要把公共知识塞进用户记忆。
- 记忆与 RAG 的检索结果需统一排序（Rerank，重排序）后再入上下文。
- 明确二者的失败降级：RAG 失败可回退纯模型回答，记忆失败不应导致对话中断。

# 4. 记忆的读写流程

**结论先行**：记忆系统本质是一对读写循环——读时按需检索并组装进上下文，写时提取值得保留的信息并去重更新。

## 4.1 读路径

```text
读：
  用户提问
     │
     ▼
  从记忆中检索相关内容（按会话/相关性）
     │
     ▼
  组装进上下文（受 Token 预算限制）
     │
     ▼
  模型生成
```

## 4.2 写路径

```text
写：
  交互结束
     │
     ▼
  提取值得记住的信息
     │
     ▼
  写入记忆存储（去重、摘要、更新）
```

### 4.2.1 信息提取

从对话中抽取偏好、事实、约束、决策等结构化信息。可用规则（关键词、正则）或模型抽取。

### 4.2.2 去重与更新

同一事实多次出现时应合并，而非追加；新事实与旧事实冲突时应按时间或置信度覆盖。

## 4.3 完整 Java 示例

以下为 Spring AI / LangChain4j 风格的服务骨架（部分 API 为示意，具体以所用版本为准）。

```java
public interface MemoryStore {
    List<MemoryItem> retrieve(MemoryQuery query);
    void write(MemoryItem item);
    void update(String id, MemoryItem item);
    void delete(String id);
}

public record MemoryQuery(
        String userId,
        String sessionId,
        String queryText,
        int topK,
        Set<MemoryType> types) {}

@Service
@RequiredArgsConstructor
public class MemoryService {

    private final MemoryStore store;
    private final MemoryExtractor extractor;
    private final EmbeddingModel embeddingModel;

    public List<MemoryItem> read(String userId, String sessionId, String question) {
        MemoryQuery query = new MemoryQuery(
                userId, sessionId, question, 5, Set.of(MemoryType.SEMANTIC));
        return store.retrieve(query);
    }

    public void write(String userId, String sessionId, String userText, String aiText) {
        List<MemoryCandidate> candidates = extractor.extract(userText, aiText);
        for (MemoryCandidate candidate : candidates) {
            if (candidate.importance() < IMPORTANCE_THRESHOLD) {
                continue;
            }
            MemoryItem existing = store.findSimilar(userId, candidate.content());
            if (existing != null) {
                store.update(existing.id(), existing.merge(candidate));
            } else {
                store.write(candidate.toItem(userId, sessionId, embeddingModel));
            }
        }
    }
}
```

## 4.4 边界与生产建议

- 写路径应异步化，避免阻塞主响应链路。
- 抽取失败时不应丢弃原始消息，至少保留在短期记忆中。
- 对写入设置速率限制，防止恶意用户刷爆记忆库。

# 5. 记忆的核心挑战

**结论先行**：记忆系统的难点不在"存"，而在"选、合、忘、护"——相关性、一致性、成本、隐私与隔离共同构成核心挑战。

## 5.1 挑战总览

| 挑战 | 说明 |
|------|------|
| 容量 | 上下文窗口有限 |
| 相关性 | 记住什么、忘记什么 |
| 一致性 | 记忆冲突时以谁为准 |
| 时效 | 旧信息可能已过时 |
| 成本 | 记忆越多，Token 越多 |
| 隐私 | 记忆含敏感信息 |
| 隔离 | 多用户/多租户隔离 |

## 5.2 容量与相关性

### 5.2.1 容量约束

上下文窗口是硬上限，记忆不能无限注入。需要预算化（Budgeting）与优先级裁剪。

### 5.2.2 相关性判断

判断"什么值得记"依赖重要性评分与语义相似度；判断"什么该召回"依赖检索质量。二者都易受噪声影响。综合打分常采用"相似度 + 时效 + 重要性"的加权形式。

## 5.3 一致性与时效

- **一致性**：用户先说"喜欢咖啡"，后说"戒咖啡了"。系统需按时间戳或显式纠错覆盖。
- **时效**：三年前的地址可能已失效，记忆应带过期时间或衰减因子。

## 5.4 成本、隐私与隔离

- **成本**：记忆检索、嵌入（Embedding）与注入都会增加 Token 与算力开销。
- **隐私**：手机号、身份证、健康信息等需脱敏或加密后存储。
- **隔离**：多租户系统必须保证 A 用户记忆绝不出现在 B 用户上下文。

## 5.5 生产建议

- 为每条记忆打上来源、时间、置信度、重要性四个元数据。
- 冲突解决定义明确规则：时间优先 / 显式纠错优先 / 置信度优先。
- 隐私字段做脱敏后再嵌入，避免敏感信息进入向量空间。

# 6. 记忆策略

**结论先行**：五种基础策略从"全量"到"分层"逐步演进，生产环境推荐分层（短期 + 长期）并配合遗忘机制。

## 6.1 五种基础策略

| 策略 | 说明 | 适用 |
|------|------|------|
| 全量 | 保留所有历史 | 短对话 |
| 窗口 | 保留最近 N 条 | 通用 |
| 摘要 | 压缩早期内容 | 长对话 |
| 向量 | 按相关性召回 | 长历史 |
| 分层 | 短期 + 长期 | 生产推荐 |

## 6.2 策略对比

| 策略 | Token 成本 | 信息完整度 | 实现复杂度 | 连续性 |
|------|------------|------------|------------|--------|
| 全量 | 高 | 高 | 低 | 强 |
| 窗口 | 中 | 中 | 低 | 中 |
| 摘要 | 低 | 中 | 中 | 中 |
| 向量 | 低 | 取决于检索 | 高 | 中 |
| 分层 | 可控 | 高 | 高 | 强 |

## 6.3 策略选择决策

```text
会话长度短？ ──是──▶ 全量
     │否
     ▼
需要精确近期上下文？ ──是──▶ 窗口
     │否
     ▼
历史很长且成本敏感？ ──是──▶ 摘要 + 向量
     │否
     ▼
生产级需求 ──▶ 分层（短期 + 长期 + 遗忘）
```

## 6.4 边界与生产建议

- 摘要策略会损失细节，关键事实应同时保留原始条目。
- 向量召回可能"答非所问"，需设置相似度阈值。
- 分层架构要防止重复注入（同一信息既在摘要又在窗口）。

# 7. 生产推荐架构

**结论先行**：生产架构以"上下文组装器"为核心，向下连接会话记忆与长期记忆两类存储，向上产出受预算约束的最终提示。

## 7.1 分层架构图

```text
┌─────────────────────────────────────────────┐
│  上下文组装（受 Token 预算）                  │
│  ├── System 提示                             │
│  ├── 长期记忆（用户画像，按需）               │
│  ├── 摘要记忆（会话摘要）                     │
│  ├── 近期消息（窗口）                         │
│  └── 当前问题                                 │
└─────────────────────────────────────────────┘
         ▲                    ▲
         │                    │
   ┌─────┴─────┐      ┌──────┴──────┐
   │ 会话记忆   │      │ 长期记忆     │
   │ Redis/DB  │      │ 向量库/图    │
   └───────────┘      └─────────────┘
```

## 7.2 组件职责

| 组件 | 职责 | 典型实现 |
|------|------|----------|
| 上下文组装器 | 按预算拼接各部分 | 自研 |
| 会话记忆 | 存消息历史 | Redis/Postgres |
| 长期记忆 | 存跨会话知识 | 向量库/图库 |
| 摘要器 | 压缩早期对话 | 模型调用 |
| 遗忘调度器 | 执行 TTL/淘汰 | 定时任务 |

- 组装器应输出被引用的记忆 ID，便于审计与反馈。
- 存储层应支持按租户分片，避免热点与越权。

# 8. 记忆写入的内容

**结论先行**：写入内容需结构化，并以重要性评分过滤，只保留真正有价值的信息。

## 8.1 数据结构

```java
public record MemoryItem(
        String id,
        String userId,
        String sessionId,
        MemoryType type,          // EPISODIC / SEMANTIC / PROCEDURAL
        String content,
        Map<String, Object> metadata,
        Instant createdAt,
        Instant expiresAt,
        float importance           // 重要性评分
) {}
```

## 8.2 值得记住 vs 不值得记住

| 值得记住 | 不值得记住 |
|----------|------------|
| 用户偏好、身份信息 | 寒暄、无关内容 |
| 重要决策与结论 | 临时中间结果 |
| 关键事实与约束 | 重复信息 |
| 反馈与纠正 | 已过期信息 |

## 8.3 重要性评分

重要性可由多因子加权得到：

```text
importance = w1 * 显式程度      // 用户是否明确陈述
           + w2 * 复现次数      // 是否多次出现
           + w3 * 影响范围      // 是否影响后续决策
           + w4 * 时效性        // 是否长期有效
           - w5 * 噪声惩罚
```

## 8.4 边界与生产建议

- 评分阈值应可配置，不同业务差异大。
- 写入前做敏感信息检测，命中则脱敏或拒绝。
- 保留原始消息与抽取结果的双向引用，便于纠错。

# 9. 记忆的遗忘

**结论先行**：遗忘不是缺陷而是设计，通过 TTL、衰减、容量淘汰与冲突替换四种机制控制记忆质量与成本。

## 9.1 遗忘的必要性

```text
记忆不是越多越好，需要遗忘机制：
① 时间过期（TTL）
② 重要性衰减（久未访问则降权）
③ 容量淘汰（超出上限淘汰最不重要的）
④ 冲突替换（新信息覆盖旧信息）
```

## 9.2 四种遗忘机制

### 9.2.1 时间过期（TTL）

每条记忆带过期时间，到期自动删除。适合时效性强的信息（如临时偏好、会话上下文）。

### 9.2.2 重要性衰减

久未被访问的记忆逐步降低权重，检索时排序靠后，最终被淘汰。

### 9.2.3 容量淘汰

为每个用户设置记忆上限，超出时按重要性或最近访问时间淘汰。

### 9.2.4 冲突替换

新信息与旧信息冲突时，按规则覆盖，保证一致性。

## 9.3 Java 实现

```java
public class ForgettingPolicy {

    private final float decayRate = 0.98f;
    private final Duration maxAge = Duration.ofDays(180);

    public boolean shouldForget(MemoryItem item, Instant now) {
        if (item.expiresAt() != null && now.isAfter(item.expiresAt())) {
            return true;
        }
        if (Duration.between(item.createdAt(), now).compareTo(maxAge) > 0
                && item.importance() < LOW_IMPORTANCE) {
            return true;
        }
        return false;
    }

    public float decayedImportance(MemoryItem item, Instant lastAccess) {
        long days = Duration.between(lastAccess, Instant.now()).toDays();
        return item.importance() * (float) Math.pow(decayRate, days);
    }
}
```

定时任务负责周期性执行遗忘扫描与容量淘汰，通常按用户维度统计条目数并淘汰最低分项。

## 9.4 边界与生产建议

- 衰减参数需按业务调优，避免误删重要长期偏好。
- 淘汰前可先归档到冷存储，保留可恢复性。
- 冲突替换要记录历史版本，支持回溯。

# 10. 生产注意事项

**结论先行**：生产环境的记忆系统需要同时满足功能、成本、安全与可观测四方面要求。

## 10.1 风险清单

| 风险 | 建议 |
|------|------|
| 无记忆 | 无法多轮/个性化 |
| 记忆无限增长 | 窗口 + TTL + 摘要 |
| 记忆不隔离 | 按用户/租户隔离 |
| 敏感信息入库 | 脱敏/加密 |
| 无遗忘机制 | TTL + 淘汰策略 |
| 记忆冲突 | 定义优先级 |
| 无监控 | 监控记忆大小与命中 |

## 10.2 监控指标

| 指标 | 含义 | 告警建议 |
|------|------|----------|
| memory.items.count | 记忆条目总数 | 异常增长告警 |
| memory.retrieve.latency | 检索延迟 | P99 超阈值告警 |
| memory.hit.rate | 召回命中率 | 过低说明质量差 |
| memory.write.rate | 写入速率 | 突增可能被刷 |

## 10.3 实施清单

- 定义记忆类型与写入规则。
- 建立隔离与脱敏机制。
- 配置预算、TTL 与淘汰策略。
- 接入监控与审计。

# 11. 小结

## 11.1 核心结论

- 记忆分三层：上下文、短期、长期。
- 长期记忆分情景、语义、程序性。
- 记忆与 RAG 互补，常同时使用。
- 核心挑战：容量、相关性、一致性、成本、隐私。

## 11.2 实践要点

- 生产用"短期 + 长期"分层架构，并配备遗忘机制。
- 写入要结构化、评分化、可追溯。
- 遗忘是设计的一部分，而非缺陷。
