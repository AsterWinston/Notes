# 1. 概述与动机

结论先行：长对话的消息会不断累积，最终突破上下文窗口（Context Window）上限；记忆压缩（Memory Compression）把早期内容浓缩为摘要与结构化状态，在有限窗口内保留关键信息并控制成本。

## 1.1 为什么需要压缩

### 1.1.1 长对话的 Token 困境

```
长对话：消息不断累积 → Token 超限 → 要么截断（丢信息）要么报错
压缩：把早期内容浓缩为摘要，保留关键信息
```

每多一轮对话，输入 Token 就增长一次；若每轮都把全部历史喂给模型，成本随轮次近似线性上升，且迟早触顶。

### 1.1.2 压缩的价值

| 不压缩 | 压缩 |
|--------|------|
| 超限后截断 | 保留关键信息 |
| 早期信息全丢 | 早期信息浓缩保留 |
| 成本随轮次线性增长 | 成本趋于稳定 |
| 行为不可预期 | 窗口使用可控 |

## 1.2 压缩的边界

### 1.2.1 压缩不是无损

任何压缩都会丢失部分信息。目标不是"零损失"，而是"关键信息不丢、次要信息可弃"。因此必须先定义"关键信息"的范围（身份、偏好、约束、决策、变量）。

### 1.2.2 何时不该压缩

- 对话很短且远未触顶：压缩只会徒增一次 LLM 调用。
- 信息高度依赖原始措辞（如法律条款、代码片段）：摘要会引入歧义。
- 需要精确审计的场景：应保留原文并另存，而非覆盖。

## 1.3 本文范围

本文覆盖压缩策略、滚动摘要、分层摘要、关键信息抽取、工具结果压缩、压缩时机、代价与优化、效果验证及生产实践。

# 2. 三种压缩策略

结论先行：按信息损失从高到低，压缩策略依次为滑动窗口、滚动摘要、分层摘要；实际系统常组合使用，而非二选一。

## 2.1 策略对比

### 2.1.1 对比表

| 策略 | 说明 | 信息损失 |
|------|------|:--------:|
| 滑动窗口（Sliding Window） | 丢弃早期消息 | 高 |
| 滚动摘要（Rolling Summary） | 早期内容转摘要 | 中 |
| 分层摘要（Hierarchical Summary） | 多级摘要 | 低 |

### 2.1.2 选型建议

| 场景 | 推荐策略 |
|------|----------|
| 短任务、无关历史 | 滑动窗口 |
| 常规多轮对话 | 滚动摘要 |
| 长周期助理 | 分层摘要 |

## 2.2 滑动窗口

只保留最近 N 条消息，实现最简单、零额外成本，但早期信息全部丢失。适合"历史与当前无关"的任务型对话。

## 2.3 滚动摘要

保留最近若干条原文，把更早的内容压成一段摘要，置于系统消息（System Message）中。兼顾成本与信息保留，是最常用的默认策略。

## 2.4 分层摘要

对时间跨度更大的历史，按时间粒度逐级压缩（分钟级 → 小时级 → 天级），既保留远期要点，又避免摘要过长。

## 2.5 边界与坑

- 滑动窗口在"用户早就说过偏好"的场景会反复追问，体验差。
- 滚动摘要在阈值附近反复触发，可能造成摘要抖动。

# 3. 滚动摘要实现

结论先行：滚动摘要的核心是"保留近端原文 + 压缩远端历史"，触发点由 Token 阈值决定，摘要由一次独立的 LLM 调用完成。

## 3.1 压缩主流程

### 3.1.1 代码

```java
public List<Message> compressWithSummary(List<Message> messages,
                                         int keepRecent) {
    if (messages.size() <= keepRecent + THRESHOLD) {
        return messages;                      // 未超阈值，不压缩
    }

    int splitPoint = messages.size() - keepRecent;
    List<Message> old = messages.subList(0, splitPoint);
    List<Message> recent = messages.subList(splitPoint, messages.size());

    // 把早期消息压缩为摘要
    String summary = summarizer.summarize(old);

    List<Message> result = new ArrayList<>();
    result.add(SystemMessage.from("""
            以下是之前对话的摘要：
            %s
            """.formatted(summary)));
    result.addAll(recent);
    return result;
}
```

### 3.1.2 阈值设计

- `keepRecent`：保留多少条原文，通常 6～12 条，覆盖最近几轮。
- `THRESHOLD`：留出的缓冲，避免每次都在窗口边缘触发。
- 触发量应基于 Token 估算，而非消息条数。

## 3.2 摘要器

### 3.2.1 Summarizer 接口

```java
interface Summarizer {

    @UserMessage("""
            把下面的对话压缩为简洁摘要，保留：
            - 用户的关键信息（身份、偏好、约束）
            - 已达成的结论与决策
            - 未解决的问题

            对话：
            {{conversation}}

            摘要（不超过 300 字）：
            """)
    String summarize(String conversation);
}
```

### 3.2.2 提示词要点

- 明确列出"必须保留"的类别，而非笼统说"总结"。
- 限定字数，防止摘要本身过长而失去压缩意义。
- 要求保留专有名词与数值，避免改写。

## 3.3 边界与坑

- 把摘要塞进系统消息会削弱其权威性，建议加明确前缀（如"历史摘要"）。
- 若 `old` 为空仍调用摘要器，会浪费一次调用。
- 摘要失败（超时/限流）时应回退为滑动窗口，而非直接报错。

## 3.4 生产建议

- 摘要器使用便宜的小模型，主对话使用强模型。
- 摘要结果缓存，同一段历史不重复摘要。
- 对摘要做长度校验，超长则二次压缩或截断。

# 4. 分层摘要实现

结论先行：分层摘要把历史按"近、中、远"三段分别处理，近端保原文、中端做一级摘要、远端做二级摘要，从而在固定窗口内表达更长时间跨度。

## 4.1 多级摘要模型

```
原始消息 ──▶ 一级摘要 ──▶ 二级摘要 ──▶ 三级摘要
（近期）      （分钟级）    （小时级）    （天级）
```

### 4.1.1 层级划分

| 层级 | 覆盖范围 | 形式 |
|------|----------|------|
| L0 | 最近 N 条 | 原文 |
| L1 | 次近 M 条 | 一级摘要 |
| L2 | 更早历史 | 二级摘要 |

## 4.2 实现

### 4.2.1 代码

```java
public class HierarchicalSummarizer {

    public List<Message> compress(List<Message> messages) {
        // ① 最近 10 条：保留原文
        List<Message> recent = last(messages, 10);

        // ② 10~50 条：一级摘要
        String level1 = summarize(messages.subList(
                Math.max(0, messages.size() - 50),
                Math.max(0, messages.size() - 10)));

        // ③ 更早：二级摘要（已有摘要基础上再压缩）
        String level2 = existingSummary != null
                ? summarize(existingSummary + "\n" + earlierMessages)
                : "";

        return List.of(
                SystemMessage.from("早期摘要：\n" + level2),
                SystemMessage.from("近期摘要：\n" + level1),
                UserMessage.from(...));
    }
}
```

### 4.2.2 层级合并时机

当一级摘要积累到一定长度或时间跨度时，才合并进二级摘要，避免频繁重写远端摘要。

## 4.3 边界与坑

- 逐级摘要会放大"摘要漂移"，越远越失真。
- 各层边界必须不重不漏，否则会丢消息或重复计入。
- 二级摘要若每次都用"摘要的摘要"，数轮后可能面目全非。

## 4.4 生产建议

- 远端摘要定期用"原始消息 + 现摘要"重生成，抵消漂移。
- 为每层摘要记录覆盖的消息区间，便于审计。
- 层级数量一般不超过 3，过多收益递减。

# 5. 关键信息抽取

结论先行：摘要可能丢失关键细节，需用结构化抽取（Structured Extraction）把事实、决策、约束、未决问题与关键变量单独保存，比纯文本摘要更可靠。

## 5.1 结构化状态

### 5.1.1 模型

```java
public record ConversationState(
        List<String> facts,           // 已确认的事实
        List<String> decisions,       // 已达成的决策
        List<String> constraints,     // 约束条件
        List<String> openQuestions,   // 未解决问题
        Map<String, String> variables // 关键变量（如订单号）
) {}
```

### 5.1.2 抽取器

```java
interface StateExtractor {

    @UserMessage("""
            从对话中抽取结构化状态：

            对话：
            {{conversation}}

            输出 JSON：
            {
              "facts": [],
              "decisions": [],
              "constraints": [],
              "openQuestions": [],
              "variables": {}
            }
            """)
    ConversationState extract(String conversation);
}
```

## 5.2 摘要与抽取结合

推荐"双轨"：摘要保留叙述连贯性，结构化状态兜住关键事实与变量。注入上下文时，先给结构化状态，再给摘要。

## 5.3 边界与坑

- 结构化抽取同样依赖模型，可能漏项或幻觉，需做字段级校验。
- 变量名（如"订单号"）应预定义，避免模型每次起不同名字。
- 状态合并时新值应覆盖旧值，但需保留变更历史。

## 5.4 生产建议

> 结构化状态比纯文本摘要更可靠，不会"漏掉订单号"这类关键信息。

- 对 `variables` 做正则校验（订单号、日期格式）。
- 抽取失败时保留上一版状态，而非清空。
- 关键字段变更可触发人工确认（如金额、地址）。

# 6. 工具结果的压缩

结论先行：工具（Tool）返回的原始结果往往冗长，需在入上下文前精简；JSON 类结果按关键字段提取，文本类结果做摘要或截断。

## 6.1 压缩策略

### 6.1.1 代码

```java
public String compressToolResult(String rawResult, int maxTokens) {
    if (estimateTokens(rawResult) <= maxTokens) {
        return rawResult;
    }

    // 结构化结果：只保留关键字段
    if (isJson(rawResult)) {
        return extractKeyFields(rawResult);
    }

    // 文本结果：摘要或截断
    return summarize(rawResult);
}
```

### 6.1.2 关键字段提取

```java
// 例：订单查询只保留关键字段
private String extractKeyFields(String json) {
    JsonNode node = objectMapper.readTree(json);
    return """
            {"orderId":"%s","status":"%s","amount":"%s"}
            """.formatted(
            node.get("orderId").asText(),
            node.get("status").asText(),
            node.get("amount").asText());
}
```

### 6.1.3 截断的取舍

文本类结果优先"首尾保留"（保留开头摘要与结尾结论），比单纯截断开头更不易丢关键信息。

## 6.2 边界与坑

- 关键字段提取前必须确认字段存在，否则 `get(...)` 返回 null 导致 NPE。
- 摘要工具结果会丢失列表项，分页类结果应保留总数与页码。
- 压缩后若模型仍需完整数据，应支持"按需重新调用工具"。

## 6.3 生产建议

- 为每类工具定义关键字段白名单，集中维护。
- 记录原始结果与压缩结果的 Token 比，评估收益。
- 压缩失败时降级为截断，保证不阻塞主流程。

# 7. 压缩时机与调度

结论先行：压缩不应每轮都做，而应在"Token 超阈值"或"会话空闲/结束"时触发；在线请求路径上的压缩必须异步化，以免增加延迟。

## 7.1 三种时机

### 7.1.1 对比

| 时机 | 说明 | 特点 |
|------|------|------|
| 每轮检查 | Token 超阈值时压缩 | 及时，可能阻塞 |
| 会话空闲 | 后台异步压缩 | 不阻塞，需调度 |
| 会话结束 | 生成最终摘要 | 成本低，粒度粗 |

### 7.1.2 异步压缩

```java
public void maybeCompress(String sessionId) {
    int tokens = estimateSessionTokens(sessionId);

    if (tokens > COMPRESS_THRESHOLD) {
        compressAsync(sessionId);            // 异步压缩，不阻塞请求
    }
}
```

## 7.2 阈值与触发

- 阈值取窗口上限的 70%～80%，留出生成空间。
- 异步压缩需加锁，防止同一会话并发压缩。
- 压缩期间的新消息应继续追加，不能丢。

## 7.3 边界与坑

- 无锁并发压缩会让摘要互相覆盖。
- 阈值设得过高，压缩来不及完成就已超限。
- 会话结束后才压缩，长会话中途仍会触顶。

## 7.4 生产建议

- 压缩任务进队列，带会话 ID 做幂等键。
- 监控压缩频率，异常升高往往意味着阈值不合理。
- 为压缩设置超时与重试，失败则跳过本轮。

# 8. 压缩的代价与优化

结论先行：压缩不是免费的，它带来额外 LLM 调用、信息损失、延迟与摘要漂移；优化方向是异步、用便宜模型、结构化抽取、避免多次叠加。

## 8.1 代价

| 代价 | 说明 |
|------|------|
| 额外 LLM 调用 | 摘要需调用模型 |
| 信息损失 | 摘要不可避免丢信息 |
| 延迟 | 同步压缩会增延迟 |
| 摘要漂移 | 多次摘要后失真 |

## 8.2 优化手段

### 8.2.1 四条优化

```java
// ① 异步压缩，不阻塞请求
// ② 用便宜的小模型做摘要
// ③ 关键信息用结构化抽取而非摘要
// ④ 避免多次摘要叠加（保留原始 + 摘要）
```

### 8.2.2 摘要缓存

对同一段历史只摘要一次，用内容哈希做缓存键，重复触发时直接命中。

## 8.3 边界与坑

- 用强模型做摘要会显著抬高成本，收益却有限。
- 只保留摘要而丢弃原文，事后无法重新抽取。
- 缓存键若只用会话 ID，历史变化后缓存会失效错乱。

## 8.4 生产建议

- 原文落库长期保存，摘要只是派生视图。
- 定期统计摘要 Token 与原文 Token 的压缩比。
- 漂移严重的会话，定期用原文重生成摘要。

# 9. 压缩效果验证

结论先行：压缩必须验证"关键信息是否保留"，方法是对压缩前后分别抽取结构化状态并比对，同时校验 Token 是否显著下降。

## 9.1 验证思路

用同一抽取器分别处理压缩前与压缩后的消息，比较 `facts`、`variables` 等字段；字段一致说明关键信息未丢。

## 9.2 测试代码

### 9.2.1 关键信息保持

```java
@Test
void compression_preserves_key_info() {
    List<Message> messages = loadLongConversation();
    ConversationState before = extractState(messages);

    List<Message> compressed = compressor.compress(messages);
    ConversationState after = extractState(compressed);

    // 关键事实不能丢
    assertEquals(before.facts(), after.facts());
    // 关键变量不能丢
    assertEquals(before.variables(), after.variables());
    // Token 显著减少
    assertTrue(estimateTokens(compressed) < estimateTokens(messages) * 0.5);
}
```

### 9.2.2 补充指标

| 指标 | 含义 |
|------|------|
| 压缩比 | 压缩后 Token / 压缩前 Token |
| 关键信息保持率 | 未丢失字段数 / 总字段数 |
| 摘要漂移度 | 多轮压缩后的语义偏移 |

## 9.3 边界与坑

- 抽取器本身有噪声，比对需容忍小差异。
- 仅比较 Token 下降而不比较信息，会掩盖信息丢失。
- 测试数据需覆盖"含关键变量"的长对话，否则测不出问题。

## 9.4 生产建议

- 把关键信息保持率纳入上线门禁。
- 线上抽样对比，持续监控漂移。
- 保留失败样本，用于迭代摘要提示词。

# 10. 生产注意事项

结论先行：压缩的生产风险集中在"丢关键信息、增延迟、成本、漂移、无阈值、不验证"六类，逐项均有对应工程手段。

## 10.1 风险与对策

| 风险 | 建议 |
|------|------|
| 摘要丢关键信息 | 结构化抽取 + 校验 |
| 同步压缩增延迟 | 异步压缩 |
| 摘要成本高 | 小模型 + 缓存 |
| 多次摘要失真 | 保留原始 + 摘要 |
| 无阈值 | 超阈值才压缩 |
| 不验证 | 压缩后校验关键信息 |

## 10.2 监控指标

| 指标 | 含义 |
|------|------|
| 压缩触发次数 | 频率是否异常 |
| 平均压缩比 | 压缩效率 |
| 压缩耗时 P99 | 异步任务健康度 |
| 摘要失败率 | 链路稳定性 |

## 10.3 边界与坑

- 只监控 Token 不监控信息质量，问题会长期潜伏。
- 压缩与业务写入不在同一事务，可能读到中间态。

## 10.4 生产建议

- 压缩状态持久化，进程重启后不丢。
- 提供手动"重建摘要"入口，便于应急。
- 对超长会话设硬上限，兜底防止无限增长。

# 11. 小结

结论先行：记忆压缩是长对话可持续运行的基础设施，关键在选对策略、抽准信息、异步执行并持续验证。

## 11.1 要点回顾

- 压缩让长对话在有限窗口内持续。
- 三种策略：滑动窗口、滚动摘要、分层摘要。
- 关键信息用结构化抽取，比纯摘要可靠。
- 压缩要异步、用便宜模型、避免多次叠加。
- 压缩后必须验证关键信息未丢失。

## 11.2 落地清单

- 定义关键信息范围与抽取 Schema。
- 实现滚动摘要为默认策略，分层摘要按需启用。
- 工具结果按类型压缩，保留关键字段。
- 压缩走异步队列，带幂等与超时。
- 建立压缩比与信息保持率监控。
