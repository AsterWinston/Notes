# 1. 发布什么

LLM（大语言模型，Large Language Model）应用的"发布"对象远多于传统应用：除了代码与镜像，还包括配置、Prompt（提示词）、向量索引与 Agent（智能体）定义。任何一项变更都会改变线上行为，因此都算一次发布，都必须可灰度、可回滚。

## 1.1 发布对象清单

```
① 代码（业务逻辑）
② 镜像（应用）
③ 配置（模型、阈值）
④ Prompt（模板版本）
⑤ 索引（向量库）
⑥ Agent 定义（工具集、权限）
```

### 1.1.1 代码与镜像

代码决定控制流、工具编排与错误处理；镜像封装运行时与依赖。二者通常一起发布，但镜像 tag 与代码 commit 必须可对应。

### 1.1.2 配置与 Prompt

配置包含模型名、温度、`top-k`、超时、阈值等；Prompt 决定指令与格式。它们改动最频繁，却常被当作"随手改"，必须纳入版本管理与灰度。

### 1.1.3 索引与 Agent 定义

索引是向量库中的嵌入数据，换嵌入模型或改分块策略都需重建；Agent 定义包含可用工具集、权限边界与系统提示，属于行为契约的一部分。

> **任何一项变更都算一次发布**，都需要可灰度、可回滚。

## 1.2 为什么"任意一项都算发布"

- 改 Prompt 可能让格式解析失败，等价于代码 bug。
- 换嵌入模型后旧查询向量与新文档向量不在同一空间，检索直接失效。
- 缩小 Agent 工具权限可能让多轮任务中途失败。
- 改温度会显著改变输出分布与成本。

## 1.3 边界与坑

- 只对代码做灰度，忽略 Prompt/索引，是常见误区。
- 多处变更混在一起发布，出问题无法归因。
- 索引重建耗时可能数小时，需提前规划窗口。
- Agent 定义若无版本化，回滚时无从下手。

# 2. 发布策略对比

不同策略在回滚速度、资源开销与验证充分度之间权衡。LLM 应用首选金丝雀：可用真实流量验证效果与成本。

## 2.1 四种策略

| 策略 | 说明 | 回滚速度 | 资源 |
|------|------|:--------:|:----:|
| 滚动更新 | 逐步替换实例 | 中 | 低 |
| 蓝绿 | 新旧两套，切流量 | 快 | 高（双倍） |
| 金丝雀 | 小比例放量 | 快 | 低 |
| 影子 | 新版本接收流量但不返回 | 不影响 | 中 |

### 2.1.1 滚动更新

按批次替换 Pod，容量平稳但新旧版本短暂共存，回滚需再次滚动，速度中等。

### 2.1.2 蓝绿

维护两套完整环境，通过切换流量入口瞬间切换。回滚极快，但资源翻倍且数据迁移复杂。

### 2.1.3 金丝雀

先放小比例流量，逐步扩大。可结合真实流量指标自动决策，资源开销低。

### 2.1.4 影子

新版本接收真实流量的副本但结果只记录不返回，零用户风险，但成本翻倍且不能用于有副作用的写操作。

> **金丝雀是 LLM 应用的首选**：可用真实流量验证效果。

## 2.2 选择建议

| 场景 | 推荐策略 |
|------|----------|
| 常规迭代 | 金丝雀 |
| 重大重构、需秒级回滚 | 蓝绿 |
| 只读链路效果验证 | 影子 |
| 无状态小服务 | 滚动更新 |

## 2.3 边界与坑

- 蓝绿要求数据库兼容新旧两个版本，否则无法同时运行。
- 影子会重复调用模型，成本翻倍，需评估预算。
- 金丝雀样本量太小则指标不可信。
- 滚动更新期间新旧版本共存，接口需向后兼容。

# 3. 金丝雀发布

金丝雀发布按流量比例逐步放量，每一步都观察指标，异常则暂停或回滚。

## 3.1 放量阶段

```
阶段1：1% 流量 → 观察 30 分钟
阶段2：10% 流量 → 观察 1 小时
阶段3：50% 流量 → 观察 2 小时
阶段4：100% 流量
```

观察时长应覆盖业务峰谷，避免只在高流量或只低流量时段验证。

## 3.2 流量切分

### 3.2.1 基于 Header

内部测试或灰度用户带特定请求头进入金丝雀，便于定向验证。

### 3.2.2 基于权重

按百分比随机分流，用于统计意义上的效果对比。

```yaml
apiVersion: networking.istio.io/v1beta1
kind: VirtualService
metadata:
  name: ai-app
spec:
  hosts: [ai-app]
  http:
    - match:
        - headers:
            x-canary:
              exact: "true"
      route:
        - destination: { host: ai-app-canary }
    - route:
        - destination: { host: ai-app-stable }
          weight: 90
        - destination: { host: ai-app-canary }
          weight: 10
```

## 3.3 金丝雀验证指标

### 3.3.1 指标定义

| 指标 | 阈值 |
|------|------|
| 错误率 | ≤ 稳定版 |
| P99 延迟 | ≤ 稳定版 × 1.2 |
| 单次成本 | ≤ 稳定版 × 1.1 |
| 用户反馈 | 无显著恶化 |
| 评测分数 | ≥ 稳定版 |

### 3.3.2 自动决策

```java
@Component
public class CanaryAnalyzer {

    public CanaryDecision evaluate() {
        double stableErrorRate = metrics.errorRate("stable");
        double canaryErrorRate = metrics.errorRate("canary");

        if (canaryErrorRate > stableErrorRate * 1.5) {
            return CanaryDecision.ROLLBACK;
        }
        if (metrics.p99("canary") > metrics.p99("stable") * 1.2) {
            return CanaryDecision.PAUSE;
        }
        return CanaryDecision.PROMOTE;
    }
}
```

决策三态：`PROMOTE`（放量）、`PAUSE`（暂停观察）、`ROLLBACK`（回滚）。

## 3.4 边界与坑

- 低流量时段金丝雀样本不足，指标噪声大。
- 只比平均值不比 P99，会漏掉长尾劣化。
- 灰度用户与普通用户分布不同（如内部用户），结论可能失真。
- 未固定对照版本，稳定版本身也在变，比较无基准。

# 4. 蓝绿发布

蓝绿发布同时维护两套环境，靠切换流量入口实现瞬时切换与秒级回滚。

## 4.1 原理

- 蓝环境：当前生产。
- 绿环境：新版本，部署并验证完毕后切流量。

```yaml
# 蓝环境（当前生产）
apiVersion: v1
kind: Service
metadata:
  name: ai-app
spec:
  selector:
    app: ai-app
    version: blue          # ← 切换这里即可切流量
```

## 4.2 操作步骤

```bash
# 部署绿环境
kubectl apply -f deployment-green.yaml

# 验证绿环境
./scripts/verify.sh green

# 切流量
kubectl patch service ai-app -p '{"spec":{"selector":{"version":"green"}}}'

# 观察后清理蓝环境
kubectl delete -f deployment-blue.yaml
```

## 4.3 优缺点

| 优点 | 缺点 |
|------|------|
| 回滚极快（切回 selector） | 双倍资源 |
| 验证充分 | 数据迁移复杂 |

## 4.4 边界与坑

- 数据库 schema 必须新旧兼容，否则两套环境无法共存。
- 长连接需在切换时优雅断开，否则客户端卡住。
- 双倍资源对 LLM 服务（高内存）成本压力大。
- 清理旧环境前需确认无残留流量。

# 5. 影子发布

影子发布让新版本接收真实流量的副本，但结果只记录不返回给用户，实现零风险验证。

## 5.1 原理

```
真实请求 ──┬──▶ 稳定版 ──▶ 返回用户
           │
           └──▶ 影子版 ──▶ 只记录结果（不返回）
```

优点：零风险验证；缺点：双倍成本，且有副作用的操作不能影子执行。

## 5.2 适用与不适用

| 适用 | 不适用 |
|------|--------|
| RAG 检索 | 下单/支付 |
| 文本生成 | 发送通知 |
| 意图识别 | 写数据库 |
| 重排 | 扣减库存 |

> 影子模式只适合**只读链路**（如 RAG 检索、生成），不能用于下单等写操作。

## 5.3 边界与坑

- 副作用操作必须屏蔽，否则会重复执行。
- 双倍成本需提前评估，必要时只影子采样流量。
- 影子结果与线上结果需可关联（同一 traceId）才能对比。
- 影子流量不应计入真实业务指标。
- 影子版本读取真实数据但不得写回，需在代码层强制只读。
- 采样率需可配置，便于在成本与置信度间权衡。

# 6. Prompt 灰度

Prompt 变更不需要重新部署应用，可在运行时按用户分流，逐步放量。

## 6.1 按用户分流

### 6.1.1 哈希分流

用用户 ID 哈希取模，保证同一用户稳定命中同一版本，避免体验跳变。

```java
public String resolvePromptVersion(UserContext user) {
    FeatureConfig config = configStore.get("prompt-version");
    if (config == null) return "v1";

    int hash = Math.abs((user.userId() + "prompt").hashCode());
    return (hash % 100) < config.rolloutPercentage() ? "v2" : "v1";
}
```

### 6.1.2 一致性要求

同一会话内应固定版本，避免多轮对话中 Prompt 漂移导致上下文不连贯。

## 6.2 放量阶段

| 阶段 | v2 比例 |
|------|:-------:|
| 1 | 5% |
| 2 | 20% |
| 3 | 50% |
| 4 | 100% |

## 6.3 边界与坑

- 用随机数而非哈希会导致同一用户反复切换版本。
- 分流键加入时间戳会破坏一致性。
- Prompt 版本必须与评测结果绑定，放量前跑对应评测。
- 配置中心不可用时的默认版本要安全（通常回退 v1）。

# 7. 索引发布

向量索引变更（换嵌入模型、改分块策略）无法原地更新，必须重建并按"新索引 + 别名切换"发布。

## 7.1 为什么不能删旧建新

删除期间检索会失败，用户请求直接报错；重建耗时可能数小时，服务不可用窗口无法接受。

```
① 用新配置构建新索引（新表/新集合）
② 双写：新数据同时写入新旧索引
③ 灰度：部分流量走新索引
④ 验证：对比召回率与效果
⑤ 全量切换：别名指向新索引
⑥ 清理旧索引
```

## 7.2 六步流程拆解

### 7.2.1 构建与双写

新索引用新配置构建，同时业务写入需双写到新旧索引，保证增量数据不丢。

### 7.2.2 灰度与切换

部分查询走新索引，对比召回率与答案质量；达标后用别名原子切换，最后清理旧索引。

## 7.3 别名切换实现

```java
// 用别名切换，避免服务中断
vectorStore.switchAlias("knowledge", "knowledge_v2");
```

> **绝不能"删旧建新"**：删除期间检索会失败。

## 7.4 边界与坑

- 新旧索引嵌入维度不同，查询时需匹配对应嵌入模型。
- 双写期间一致性需校验，避免漏写。
- 别名切换需原子操作，部分向量库需手动维护双别名。
- 旧索引清理要留观察期，便于快速切回。

# 8. 回滚

回滚是把所有发布对象恢复到上一稳定状态。覆盖越全、恢复越快，事故影响越小。

## 8.1 应用回滚

```bash
# 应用回滚
kubectl rollout undo deployment/ai-app

# 或指定版本
kubectl rollout undo deployment/ai-app --to-revision=3
```

## 8.2 全对象回滚清单

回滚清单：

| 对象 | 回滚方式 |
|------|----------|
| 应用 | `kubectl rollout undo` / 切 selector |
| 配置 | 配置中心历史版本 |
| Prompt | 切回旧版本 |
| 索引 | 别名切回 |
| Agent 定义 | 激活旧版本 |

### 8.2.1 配置与 Prompt 回滚

配置中心（如 Nacos/Apollo）保留历史版本，回滚即激活上一版本；Prompt 同理，切回旧模板并重新加载缓存。索引回滚靠别名切回，Agent 定义回滚靠激活旧版本快照。四者都应提供一键操作，避免人工改文件。

```java
// 配置中心保留历史版本，回滚即激活上一版本
configCenter.rollback("ai-app", "prompt-version", previousRevision);
```

## 8.3 边界与坑

- `rollout undo` 依赖 ReplicaSet 历史，`revisionHistoryLimit` 太小会丢失版本。
- 已写入新索引的数据无法自动回退，需兼容或补偿。
- 配置/Prompt 回滚若不与代码版本联动，可能出现不兼容组合。
- 回滚后必须重新验证，确认指标恢复。

# 9. 回滚演练

```
定期演练：
- 模拟故障 → 执行回滚 → 记录耗时
- 目标：5 分钟内完成回滚
```

> **没演练过的回滚 = 不存在的回滚。**

## 9.1 演练流程

1. 在预发或生产低峰模拟故障。
2. 由值班人员执行回滚。
3. 记录从决策到恢复的耗时与卡点。
4. 复盘并修复自动化缺口。

## 9.2 度量与目标

| 指标 | 目标 |
|------|------|
| 决策耗时 | ≤ 1 分钟 |
| 执行耗时 | ≤ 3 分钟 |
| 恢复验证 | ≤ 1 分钟 |
| 端到端 | ≤ 5 分钟 |

## 9.3 边界与坑

- 演练只走"顺利路径"，未覆盖权限缺失、配置错误等异常。
- 演练在低峰进行，与高峰回滚行为不同。
- 未记录耗时，无法发现退化。
- 演练后未更新手册，人员轮换后失效。
- 演练应覆盖"回滚失败后的人工兜底"路径。

# 10. 生产注意事项

## 10.1 风险清单

| 风险 | 建议 |
|------|------|
| 无灰度 | 金丝雀放量 |
| 回滚慢 | 配置化 + 别名切换 |
| 索引删旧建新 | 新索引 + 别名切换 |
| 无验证指标 | 定义金丝雀指标 |
| 未演练 | 定期回滚演练 |
| 多处变更混发 | 一次只改一个变量 |

## 10.2 检查清单

- [ ] 六类发布对象均有版本与灰度方案。
- [ ] 金丝雀指标含错误率、P99、成本、评测分。
- [ ] 索引发布走新索引 + 双写 + 别名切换。
- [ ] 回滚覆盖应用、配置、Prompt、索引、Agent 定义。
- [ ] 回滚流程已演练且端到端 ≤ 5 分钟。
- [ ] 一次发布只改一个变量。

# 11. 小结

- 发布对象包括代码、镜像、配置、Prompt、索引、Agent 定义。
- 金丝雀是 LLM 应用首选，可用真实流量验证。
- 索引发布用"新索引 + 别名切换"，绝不删旧建新。
- 回滚要覆盖所有发布对象，且必须定期演练。
- 一次只改一个变量，便于归因。
