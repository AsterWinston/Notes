# 1. 选型维度

> 结论先行：模型选型是七个维度的多目标权衡——能力、成本、延迟、上下文、合规、生态、稳定性。正确做法是先用硬约束（合规、上下文）缩小范围，再按加权评分排序。

## 1.1 七维模型

```
① 能力：任务需求匹配
② 成本：单价 + 用量
③ 延迟：TTFT + TPS
④ 上下文：窗口大小
⑤ 合规：数据出境、备案
⑥ 生态：工具、框架支持
⑦ 稳定性：可用性、限流
```

| 维度 | 关键指标 | 常见硬约束 |
|------|----------|:----------:|
| 能力 | 任务准确率 | 否 |
| 成本 | 每千 token 单价 | 否 |
| 延迟 | TTFT、TPS | 是（实时场景） |
| 上下文 | 最大 token 数 | 是（长文档） |
| 合规 | 备案、出境 | 是 |
| 生态 | SDK、框架支持 | 否 |
| 稳定性 | SLA、限流 | 是（生产） |

### 1.1.1 维度定义与度量

- 能力：以任务准确率或人工评分为度量。
- 成本：以每千 token 单价 × 预估用量为度量。
- 延迟：以 TTFT 与 TPS 为度量，需区分 P50 与 P99。
- 上下文：以最大支持 token 数为度量，注意有效上下文。
- 合规：以是否满足出境与备案要求为度量，属一票否决。
- 生态：以官方 SDK、框架与社区支持为度量。
- 稳定性：以 SLA、限流策略与历史可用性为度量。

## 1.2 维度优先级

### 1.2.1 硬约束与软约束

硬约束是一票否决项：数据不出境、窗口必须够长、必须已备案。软约束是可权衡项：成本、延迟、生态。先用硬约束筛选，避免在不可行方案上浪费时间。

### 1.2.2 加权评分

```
总分 = Σ (维度权重 × 维度得分)
```

权重应由业务方共同确定，例如实时客服重延迟，离线批处理重成本。

## 1.3 边界与坑

- 坑一：把软约束当硬约束，导致候选集过小。
- 坑二：权重拍脑袋，结果与实际业务目标脱节。
- 坑三：忽略稳定性，上线后频繁限流。

## 1.4 生产建议

- 先列硬约束清单，逐条验证候选模型。
- 用评分卡量化软约束，保留计算过程可追溯。
- 每季度复评权重与得分，价格与能力都在变。

# 2. 能力匹配

> 结论先行：能力匹配的核心是"任务需求"而非"模型总分"。分类抽取用小模型即可，复杂推理才需要大模型或推理模型。

## 2.1 任务到能力映射

| 任务 | 能力需求 | 建议 |
|------|----------|------|
| 分类/抽取 | 低 | 小模型 |
| 通用问答 | 中 | 中模型 |
| RAG 生成 | 中高 | 中/大模型 |
| 复杂推理 | 高 | 大/推理模型 |
| 代码生成 | 高 | 代码专长模型 |
| 多语言 | 中高 | 多语言模型 |

## 2.2 能力评估方法

### 2.2.1 公开榜单

| 榜单 | 侧重点 | 局限 |
|------|--------|------|
| MMLU | 通识知识 | 趋于饱和 |
| GPQA | 科学推理 | 题目少 |
| HumanEval | 代码生成 | 函数级 |
| SWE-bench | 真实工程 | 成本高 |
| Arena | 人类偏好 | 主观 |

### 2.2.2 自有评测集

构建步骤：

```
① 从真实业务日志抽样 200~500 条
② 人工标注标准答案
③ 定义评分规则（准确/部分/失败）
④ 批量跑候选模型
⑤ 统计准确率与成本
```

## 2.3 边界与坑

- 公开榜单存在数据污染，分数虚高。
- 自有评测集样本少，结论置信度有限。
- 离线评测与线上表现可能不一致（分布漂移）。

## 2.4 生产建议

- 公开榜单用于初筛，自有评测集用于终选。
- 评测集持续扩充，覆盖边界与对抗样本。
- 上线后做 A/B 测试，用线上指标校准。

# 3. 成本考量

> 结论先行：成本由输入与输出 token 单价共同决定，输出通常更贵。控制成本最有效的手段是分层路由，其次才是选更便宜的模型。

## 3.1 成本公式

```
成本 = 输入 token × 输入单价 + 输出 token × 输出单价
```

| 项 | 说明 |
|----|------|
| 输入 token | 提示词、上下文、历史 |
| 输出 token | 生成内容 |
| 缓存折扣 | 命中提示缓存可降价 |
| 批处理折扣 | 离线批量可降价 |

## 3.2 模型相对成本

| 模型 | 相对成本 | 适用 |
|------|:--------:|------|
| 小模型 | 1x | 分类、抽取 |
| 中模型 | 5~10x | 通用问答 |
| 大模型 | 20~50x | 复杂任务 |
| 推理模型 | 50~200x | 数学、难题 |

## 3.3 成本优化

### 3.3.1 分层路由

```
简单请求 -> 小模型
复杂请求 -> 大模型
```

按复杂度分流，可显著降低平均成本。

### 3.3.2 缓存与批处理

- 提示缓存：重复前缀命中缓存，降低输入成本。
- 结果缓存：相同问题直接返回历史结果。
- 批处理：离线任务走批处理接口，享折扣。

## 3.4 边界与坑

- 坑一：只看单价，忽略输出长度与重试成本。
- 坑二：缓存命中率低时收益有限。
- 坑三：推理模型 token 消耗大，难题才划算。

**生产建议**：监控每请求平均成本，设置预算告警与自动降级。

# 4. 延迟考量

> 结论先行：延迟分两段——首 token 延迟（TTFT）决定"多久有反应"，每秒 token 数（TPS）决定"多快看完"。实时对话重 TTFT，长文生成重 TPS。

## 4.1 延迟指标

### 4.1.1 TTFT

TTFT（Time To First Token，首 token 延迟）是从发送请求到收到第一个 token 的时间，受模型大小、排队与网络影响。

### 4.1.2 TPS

TPS（Tokens Per Second，每秒 token 数）是生成速度，决定长回答的总时长。

```
总时长 ≈ TTFT + 输出 token 数 / TPS
```

## 4.2 场景匹配

| 模型 | TTFT | TPS |
|------|:----:|:---:|
| 小模型 | 快 | 快 |
| 大模型 | 慢 | 慢 |
| 推理模型 | 慢 | 很慢（思考） |

```
延迟敏感场景（实时对话）-> 小/中模型
延迟不敏感（异步任务）-> 大/推理模型
```

### 4.2.1 交互式与批处理

| 类型 | 延迟要求 | 选型倾向 |
|------|:--------:|----------|
| 交互式对话 | 高 | 小/中模型 + 流式 |
| 在线生成 | 中 | 中模型 |
| 异步批处理 | 低 | 大/推理模型 + 批处理接口 |

区分两类流量并隔离队列，避免批处理任务挤占交互式请求的资源。

## 4.3 优化手段

| 手段 | 效果 |
|------|------|
| 流式输出 | 降低感知延迟 |
| 提示缓存 | 降低 TTFT |
| 小模型分流 | 降低整体延迟 |
| 就近部署 | 降低网络延迟 |

## 4.4 生产建议

- 为实时场景设定 TTFT 与 TPS 的 SLO。
- 用流式输出改善感知体验，即使总时长不变。
- 异步任务与实时请求隔离队列，避免相互影响。

# 5. 上下文窗口

> 结论先行：窗口大小决定能塞多少内容，但"窗口大不等于有效"——长上下文中间的信息可能被忽略，且成本与延迟随长度上升。

## 5.1 窗口分级

| 窗口 | 适用 |
|------|------|
| 4K~8K | 常规对话 |
| 32K~128K | 长文档、RAG |
| 200K~1M+ | 超长文档、代码库 |

## 5.2 有效上下文

"迷失在中间"（lost in the middle）现象：模型对上下文开头与结尾的信息更敏感，中间内容召回率下降。因此长窗口需要配合检索与重排。

```
位置:  开头    中间    结尾
召回:  高      低      高
```

## 5.3 成本与延迟影响

- 成本随输入 token 线性上升。
- KV Cache 随长度增长，占用显存。
- 长输入使 TTFT 上升。

## 5.4 生产建议

- 长文档优先用 RAG 检索相关片段，而非全量塞入。
- 关键信息放在上下文开头或结尾。
- 用滑动窗口或摘要压缩历史对话。

# 6. 合规考量

> 结论先行：合规是硬约束，不满足则一票否决。核心关注数据出境、服务备案、行业监管与开源许可。

## 6.1 合规要求

| 要求 | 影响 |
|------|------|
| 数据不出境 | 用国产/本地模型 |
| 服务备案 | 用已备案厂商 |
| 行业监管 | 金融/医疗特殊要求 |
| 开源许可 | 审查商用条款 |

## 6.2 行业差异

| 行业 | 敏感度 | 典型要求 |
|------|:------:|----------|
| 互联网 | 低 | 基本合规 |
| 金融 | 高 | 数据本地、审计 |
| 政务 | 高 | 私有化、备案 |
| 医疗 | 高 | 隐私保护 |
| 教育 | 中 | 内容安全 |

## 6.3 边界与坑

- 坑一：默认厂商已合规，未核实出境路径。
- 坑二：忽略开源许可证的商用门槛。
- 坑三：上线后才补备案，导致停服。

## 6.4 生产建议

- 选型初期即引入法务与安全评审。
- 明确数据分类分级与出境清单。
- 保留合规文档与审计日志。

# 7. 选型决策流程

> 结论先行：选型是工程流程而非直觉判断——明确需求、列候选、评测、比成本、查合规、试点、灰度。

## 7.1 七步流程

```
① 明确任务类型与能力需求
② 列出候选模型（3~5 个）
③ 用自有评测集测试能力
④ 对比成本与延迟
⑤ 检查合规与生态
⑥ 小规模试点
⑦ 灰度上线
```

## 7.2 Java 实现示例

```java
import java.util.Comparator;
import java.util.List;

public final class ModelSelector {

    public record TaskProfile(double minQuality, double maxCost) {}

    public record ModelScore(String name, double quality, double cost, double latency) {}

    public record ModelRecommendation(String name, ModelScore score) {}

    public ModelRecommendation recommend(TaskProfile task, List<ModelScore> candidates) {
        return candidates.stream()
                .filter(s -> s.quality() >= task.minQuality())
                .filter(s -> s.cost() <= task.maxCost())
                .min(Comparator.comparingDouble(ModelScore::cost))
                .map(s -> new ModelRecommendation(s.name(), s))
                .orElseThrow(() -> new IllegalStateException("无满足条件的模型"));
    }
}
```

## 7.3 边界与坑

- 坑一：候选太少，可能错过更优解。
- 坑二：评测集不具代表性，结论失真。
- 坑三：跳过试点直接全量，风险高。

## 7.4 生产建议

- 流程固化为可复用的选型模板。
- 每次选型产出文档：需求、评测、结论、理由。
- 试点设定明确指标与回滚条件。

# 8. 常见选型结论

> 结论先行：多数场景有成熟答案——原型用便宜模型，生产用均衡模型，难题用推理模型，中文用国产模型。

## 8.1 场景推荐表

| 场景 | 推荐 |
|------|------|
| 快速原型 | GPT-4o-mini / Qwen-turbo |
| 通用生产 | GPT-4o / Qwen-plus / DeepSeek-V3 |
| 复杂推理 | o1/o3 / DeepSeek-R1 |
| 代码 | Claude / DeepSeek-Coder |
| 中文场景 | Qwen / DeepSeek / GLM |
| 本地部署 | Llama 3 / Qwen2.5 |
| 极致省钱 | Qwen2.5-7B + 量化 |

## 8.2 决策树

```
需要复杂推理？
  是 -> 推理模型
  否 -> 需要代码？
          是 -> 代码专长模型
          否 -> 延迟敏感？
                  是 -> 小/中模型
                  否 -> 大模型（能力优先）
```

## 8.3 反例

- 反例一：用推理模型做分类，成本高且更慢。
- 反例二：用 7B 小模型做复杂推理，准确率不达标。
- 反例三：为省钱选便宜模型，重试成本反而更高。

## 8.4 生产建议

- 结论是起点而非终点，仍需自有评测验证。
- 同一场景准备主选与备选两个模型。
- 模型价格与能力变化快，结论需定期刷新。

# 9. 多模型策略

> 结论先行：不要绑定单一模型。用"主模型 + 备用模型 + 分层路由"提升稳定性并优化成本。

## 9.1 角色划分

```
不要绑定单一模型：
  主模型 + 备用模型 + 分层路由
```

| 角色 | 说明 |
|------|------|
| 主模型 | 默认使用 |
| 备用模型 | 主模型故障时降级 |
| 小模型 | 简单任务 |
| 大模型 | 复杂任务 |

## 9.2 路由与降级

### 9.2.1 主备切换

主模型超时或报错时自动切到备用模型，保证可用性。

### 9.2.2 分层路由

按复杂度与敏感度分流，兼顾成本与质量。

### 9.2.3 熔断降级

当主模型错误率或延迟超过阈值时，自动熔断并切到备用模型；同时降低输出质量档位，保证服务不中断。

## 9.3 边界与坑

- 坑一：多模型导致提示词与评测维护成本上升。
- 坑二：备用模型能力差异大，降级后质量骤降。
- 坑三：路由规则复杂，难以调试。

## 9.4 生产建议

- 统一抽象接口，路由与业务解耦。
- 备用模型定期演练切换，确保可用。
- 为每条路由独立监控质量与成本。

# 10. 生产注意事项

> 结论先行：选型落地靠治理——用自有数据评测、用兼容协议防锁定、用分层路由控成本、用灰度控风险。

## 10.1 风险清单

| 风险 | 建议 |
|------|------|
| 只看榜单 | 用自有数据评测 |
| 绑定单一厂商 | 用兼容协议 |
| 忽视成本 | 分层路由 |
| 忽视延迟 | 按场景选型 |
| 合规遗漏 | 提前评估 |
| 一步到位 | 小规模试点 |

## 10.2 评测与灰度

| 阶段 | 动作 |
|------|------|
| 评测 | 自有评测集 + 公开榜单 |
| 试点 | 小流量真实用户 |
| 灰度 | 按比例放量 |
| 全量 | 持续监控 |

## 10.3 监控与治理

- 监控：质量、成本、延迟、错误率、限流。
- 治理：预算告警、熔断降级、版本锁定。
- 复评：季度评估模型能力与价格变化。

# 11. 小结

- 选型维度：能力、成本、延迟、上下文、合规、生态、稳定性。
- 用自有评测集测试，而非只看榜单。
- 能力匹配任务，而非追求总分最高。
- 延迟看 TTFT 与 TPS，按场景选型。
- 窗口大不等于有效，长文档优先 RAG。
- 合规是硬约束，提前评估。
- 不要绑定单一模型，用分层路由 + 备用。
- 中文场景优先国产模型。
- 小规模试点再灰度上线。
