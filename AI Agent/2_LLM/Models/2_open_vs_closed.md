# 1. 核心差异

> 结论先行：开源与闭源的根本区别只有一条——模型权重（weight）是否公开。权重公开意味着可以下载、本地部署、微调与量化；权重不公开则只能通过 API 调用。其余差异（成本、合规、定制）都是这一条的推论。

## 1.1 开源与闭源的定义

### 1.1.1 权重公开的含义

```
开源：模型权重公开，可下载部署
闭源：仅提供 API，权重不公开
```

权重是模型的参数文件（数十 GB 级）。公开权重后，用户可在自己的硬件上完成推理，数据无需离开内网。

### 1.1.2 开放权重的层次

| 层次 | 公开内容 | 能否复现训练 |
|------|----------|:------------:|
| 完全开源 | 权重 + 数据 + 训练代码 | 可 |
| 开放权重 | 仅权重 | 否 |
| 开放 API | 无 | 否 |

现实中绝大多数所谓"开源模型"属于"开放权重"，训练数据与配方并不公开。

### 1.1.3 开放程度的连续谱

开放程度不是二值，而是一条连续谱。

| 程度 | 权重 | 训练代码 | 数据 | 商用 |
|------|:----:|:--------:|:----:|:----:|
| 完全开源 | 是 | 是 | 是 | 通常可 |
| 开放权重 | 是 | 否 | 否 | 视许可 |
| 开放微调 | 否 | 否 | 否 | 视条款 |
| 纯 API | 否 | 否 | 否 | 按协议 |

选型时应确认自己需要的是"可部署"还是"可复现"，两者要求完全不同。

## 1.2 对比矩阵

| 维度 | 开源 | 闭源 |
|------|------|------|
| 权重 | 公开 | 不公开 |
| 部署 | 可本地 | 仅云端 |
| 数据 | 不出内网 | 需评估 |
| 成本 | 硬件 + 运维 | 按量计费 |
| 定制 | 可微调/改架构 | 有限 |
| 效果 | 接近顶级 | 通常最强 |
| 迭代 | 自主可控 | 跟随厂商 |
| 支持 | 社区 | 官方 SLA |

## 1.3 常见误解与边界

- 误解一："开源 = 免费"。硬件、电力、运维都是成本。
- 误解二："开源 = 能力弱"。头部开源模型已接近顶级闭源。
- 误解三："闭源 = 不安全"。厂商通常有更强的安全与合规投入。
- 边界：开放权重不等于可随意商用，需逐条审查许可证。

## 1.4 生产建议

- 把"权重是否公开"作为第一筛选项，它决定后续所有选项。
- 若数据敏感或需深度定制，直接进入开源路线评估。
- 若追求能力上限且数据可出网，优先闭源 API。

# 2. 成本对比

> 结论先行：成本没有绝对赢家，关键看用量与周期。低用量、快验证选闭源 API；高用量、稳定需求选自建。盈亏平衡点由"自建固定成本 ÷ 单位 token 节省额"决定。

## 2.1 成本结构拆解

### 2.1.1 闭源 API 成本

```
闭源 API：
  成本 = token 数 × 单价
  优势：无前期投入，按量付费
  劣势：用量大时成本高
```

成本项包括输入 token、输出 token（通常更贵）、以及缓存与批处理的折扣。

### 2.1.2 开源自建成本

```
开源自建：
  成本 = GPU 硬件 + 运维 + 电费
  优势：用量大时边际成本低
  劣势：前期投入大，需运维能力
```

- 固定成本：GPU 采购或租用、机房、网络。
- 变动成本：电力、运维人力、备件。
- 隐性成本：利用率不足导致的资源浪费。

### 2.1.3 混合与溢出成本

当本地容量不足以覆盖峰值时，可把溢出流量导向 API：

```
基线负载 -> 本地自建（成本固定）
峰值溢出 -> 云端 API（按量付费）
```

优点：无需按峰值配置硬件，避免长期闲置。缺点：需处理两套调用的结果一致性与监控。

## 2.2 盈亏平衡点估算

```
自建月成本 ≈ GPU 租金 + 运维
API 月成本 ≈ token 数 × 单价

当 API 月成本 > 自建月成本时，自建更划算
```

伪代码估算：

```java
public boolean preferSelfHost(double monthlyTokens,
                              double pricePerToken,
                              double gpuRent,
                              double opsCost) {
    double apiCost = monthlyTokens * pricePerToken;
    double selfCost = gpuRent + opsCost;
    return apiCost > selfCost;
}
```

## 2.3 成本对比表

| 场景 | 更优 | 原因 |
|------|------|------|
| 低用量、快速验证 | 闭源 API | 无前期投入 |
| 高用量、稳定需求 | 开源自建 | 边际成本低 |
| 敏感数据 | 开源自建 | 数据不出网 |
| 需要最新能力 | 闭源 API | 迭代领先 |
| 波峰波谷明显 | 混合 | 峰值溢出到 API |

## 2.4 边界与坑

- 坑一：只算 GPU 不算运维，低估自建成本 30% 以上。
- 坑二：只看单价不看"一次成功率"，重试会放大成本。
- 坑三：忽略缓存与批处理折扣，闭源实际成本可能更低。
- 边界：自建利用率低于约 30% 时，通常不如 API 划算。

**生产建议**：按季度核算实际 token 与 GPU 利用率，动态调整分层比例。

# 3. 数据与合规

> 结论先行：数据是否离开内网，是开源与闭源最刚性的差异。金融、政务、医疗等敏感行业通常只能选开源自建或私有化部署。

## 3.1 数据流向

### 3.1.1 闭源数据链路

```
业务系统 -> 厂商 API -> 厂商服务器（可能跨境）
              |
        数据出网 + 可能出境
```

风险点：传输加密、厂商留存策略、跨境传输。

### 3.1.2 开源数据链路

```
业务系统 -> 内网推理服务 -> 本地 GPU
              |
        数据不出网
```

风险点：内网安全、模型文件来源可信度。

### 3.1.3 数据留存与训练使用

闭源 API 需确认三件事：请求数据是否被留存、留存多久、是否用于训练。多数厂商提供"不用于训练"的选项，但需在合同中明确。开源自建则完全由自己控制留存策略。

## 3.2 合规要求

| 关注点 | 开源 | 闭源 |
|--------|------|------|
| 数据出网 | 否 | 是 |
| 数据出境 | 无 | 需评估 |
| 备案 | 自建需备案 | 厂商已备案 |
| 审计 | 完全可控 | 依赖厂商 |

> 金融、政务、医疗等敏感行业**倾向开源自建**。

## 3.3 行业差异

| 行业 | 数据敏感度 | 推荐路线 |
|------|:----------:|----------|
| 互联网 | 中 | 混合 |
| 金融 | 高 | 开源自建 |
| 政务 | 高 | 私有化部署 |
| 医疗 | 高 | 开源自建 |
| 教育 | 低 | 闭源 API |

## 3.4 生产建议

- 上线前完成数据分类分级，明确哪些字段不得出网。
- 对敏感字段做脱敏或本地处理后再调用外部 API。
- 建立数据流向审计日志，满足合规留痕要求。

# 4. 定制能力

> 结论先行：开源模型可微调、可量化、可改架构，定制自由度最高；闭源模型通常只支持提示词工程与少量微调，无法触及权重。

## 4.1 定制手段

### 4.1.1 微调与 LoRA

- 全量微调：更新全部参数，成本高、效果上限高。
- LoRA（低秩适配，Low-Rank Adaptation）：只训练低秩矩阵，显存占用小。
- QLoRA：在 4bit 量化基座上做 LoRA，单卡可微调大模型。

### 4.1.2 量化与架构改造

- 量化：FP16 → INT8/INT4，降低显存与延迟。
- 蒸馏：用大模型教小模型，压缩能力。
- 改架构：调整层数、注意力、专家数，仅开源可行。

## 4.2 定制能力对比

| 能力 | 开源 | 闭源 |
|------|:----:|:----:|
| 微调 | 完全 | 有限（部分支持） |
| LoRA | 支持 | 部分厂商支持 |
| 改架构 | 支持 | 不支持 |
| 蒸馏 | 支持 | 需遵守条款 |
| 量化 | 支持 | 不支持 |
| 私有词表 | 支持 | 不支持 |

## 4.3 边界与坑

- 微调不是万能：数据质量差会放大幻觉。
- 微调可能损害通用能力（灾难性遗忘）。
- 闭源微调的数据可能被厂商留存，需评估。

## 4.4 生产建议

- 优先用提示词工程与 RAG，效果不足再考虑微调。
- 微调用 LoRA 起步，验证收益后再考虑全量。
- 微调数据需去重、脱敏、平衡，并留出评测集。

# 5. 开源模型的挑战

> 结论先行：开源的主要挑战在"用起来"而非"拿得到"——部署、运维、效果差距与许可证审查都需要专业能力。

## 5.1 部署与运维

| 挑战 | 说明 |
|------|------|
| 部署成本 | 需要 GPU |
| 运维 | 需专业团队 |
| 扩容 | 峰值需预留资源 |
| 高可用 | 自建需容灾 |

### 5.1.1 资源规划

按峰值并发与上下文长度估算显存，并预留 20%~30% 余量。需注意 KV Cache 随并发与序列长度线性增长。

### 5.1.2 高可用

自建需自行实现多副本、健康检查与故障转移；单机部署一旦宕机即整体不可用。

## 5.2 能力与迭代

| 挑战 | 说明 |
|------|------|
| 效果差距 | 与顶级闭源有差距 |
| 更新 | 需自行跟进 |
| 评测 | 需自建评测体系 |
| 调优 | 提示词与参数需自行摸索 |

## 5.3 许可与合规

| 挑战 | 说明 |
|------|------|
| 许可 | 商用条款需审查 |
| 备案 | 自建需完成备案 |
| 来源 | 模型文件需可信来源 |

## 5.4 生产建议

- 用 vLLM 等成熟框架，避免自研推理。
- 建立模型版本与评测的流水线，跟进更新。
- 法务提前审查许可证，特别是商用门槛条款。

# 6. 闭源模型的挑战

> 结论先行：闭源的主要挑战在"受制于人"——成本随用量上升、数据需评估、存在厂商锁定与变更风险。

## 6.1 成本与锁定

| 挑战 | 说明 |
|------|------|
| 成本 | 用量大时昂贵 |
| 锁定 | 切换成本 |
| 议价 | 缺乏议价能力 |

## 6.2 数据与限流

| 挑战 | 说明 |
|------|------|
| 数据 | 需评估出境与隐私 |
| 限流 | 受厂商配额限制 |
| 可用性 | 依赖厂商 SLA |

## 6.3 变更风险

| 挑战 | 说明 |
|------|------|
| 变更 | 模型更新可能影响效果 |
| 下线 | 旧模型可能被弃用 |
| 行为漂移 | 同一提示词输出变化 |

## 6.4 生产建议

- 用 OpenAI 兼容协议封装调用，降低切换成本。
- 对关键输出做回归测试，捕捉行为漂移。
- 与厂商确认配额与 SLA，设置熔断降级。

# 7. 混合策略

> 结论先行：混合策略是多数企业的选择——简单任务走本地小模型，复杂任务走云端大模型，敏感任务走本地方案。核心是分层路由。

## 7.1 分层路由

### 7.1.1 按敏感度

```
敏感任务 -> 开源自建（数据不出网）
非敏感任务 -> 云端 API（效果好）
```

### 7.1.2 按复杂度

```
简单任务 -> 开源小模型（本地，便宜）
复杂任务 -> 闭源大模型（API，效果好）
```

## 7.2 Java 实现示例

```java
public enum SensitivityLevel { LOW, MEDIUM, HIGH }

public final class ModelRouter {

    private final ChatModel localModel;
    private final ChatModel localSmallModel;
    private final ChatModel cloudModel;

    public ModelRouter(ChatModel localModel,
                       ChatModel localSmallModel,
                       ChatModel cloudModel) {
        this.localModel = localModel;
        this.localSmallModel = localSmallModel;
        this.cloudModel = cloudModel;
    }

    public String route(String question, SensitivityLevel sensitivity) {
        if (sensitivity == SensitivityLevel.HIGH) {
            return localModel.chat(question);
        }
        if (isSimple(question)) {
            return localSmallModel.chat(question);
        }
        return cloudModel.chat(question);
    }

    private boolean isSimple(String question) {
        return question.length() < 100;
    }
}
```

> **混合策略是多数企业的选择**。

## 7.3 边界与坑

- 路由规则过于简单会误判，需结合分类器。
- 多套模型意味着多套提示词与评测，维护成本上升。
- 本地与云端输出风格不一致，影响用户体验。

## 7.4 生产建议

- 用轻量分类器替代长度阈值做复杂度判断。
- 统一抽象接口，路由逻辑与业务解耦。
- 对每条路径独立监控质量、成本与延迟。

# 8. 选择建议

> 结论先行：没有普适答案，按场景查表并叠加硬约束。快速原型选闭源，敏感数据选开源，高并发选混合。

## 8.1 场景决策表

| 场景 | 推荐 |
|------|------|
| 快速原型 | 闭源 API |
| 高并发生产 | 混合（本地 + 云端） |
| 敏感数据 | 开源自建 |
| 需要微调 | 开源 |
| 追求最强能力 | 闭源 |
| 成本敏感 | 开源 + 量化 |

## 8.2 决策树

```
数据能否出网？
  否 -> 开源自建
  是 -> 需要最强能力？
          是 -> 闭源 API
          否 -> 用量是否大？
                  是 -> 开源自建 / 混合
                  否 -> 闭源 API
```

## 8.3 反例

- 反例一：为省成本自建，结果 GPU 利用率不足，比 API 更贵。
- 反例二：追求最强能力用闭源，却因数据合规无法上线。
- 反例三：绑定单一厂商，厂商涨价或下线时被动。

## 8.4 生产建议

- 先明确硬约束，再在可行集合内优化成本与延迟。
- 小规模试点验证，再灰度放量。
- 保留至少一条可切换的备用路径。

# 9. 生产注意事项

> 结论先行：开源与闭源之争最终落到工程治理——避免锁定、控制成本、保障合规、留好降级。

## 9.1 风险清单

| 风险 | 建议 |
|------|------|
| 锁定单一厂商 | 用兼容协议，便于切换 |
| 数据合规 | 评估出境与隐私 |
| 开源许可 | 审查商用条款 |
| 成本失控 | 监控 + 分层路由 |
| 运维能力不足 | 用托管服务 |

## 9.2 工程化建议

| 实践 | 说明 |
|------|------|
| 统一接口 | 屏蔽厂商差异 |
| 配置驱动 | 模型名与路由可配置 |
| 版本锁定 | 固定模型版本号 |
| 回归测试 | 捕捉行为漂移 |

## 9.3 监控与治理

- 监控维度：质量、成本、延迟、错误率、限流命中。
- 治理机制：预算告警、熔断降级、灰度发布。
- 定期复评：季度评估模型能力与价格变化。

# 10. 小结

- 开源可本地部署、可定制、数据可控。
- 闭源通常能力最强、免运维。
- 用量大、数据敏感时倾向开源。
- 混合策略是多数企业的选择。
- 用 OpenAI 兼容协议降低切换成本。
- 选型先看硬约束（数据、合规），再权衡成本与能力。
