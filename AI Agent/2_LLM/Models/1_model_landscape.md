# 1. 模型家族总览

> 结论先行：主流大模型可归为 GPT、Claude、Gemini、Llama、Qwen、DeepSeek 六大主家族，外加 Mistral、GLM、豆包、Kimi、文心、混元等。记住"闭源看 OpenAI、Anthropic、Google，开源看 Meta、阿里、深度求索"这条主线，即可覆盖绝大多数选型场景。

## 1.1 家族地图与代表模型

家族不是营销概念，而是技术路线、生态与许可证的集合体。同一家族内部通常共享分词器、训练配方与接口风格，因此"换型号不换家族"的迁移成本最低。

### 1.1.1 国际闭源家族

- GPT（OpenAI）：GPT-4o、GPT-4.1、o1/o3 系列。特点是通用能力全面、工具调用与结构化输出成熟、生态最广。
- Claude（Anthropic）：Claude 3.5/3.7、Claude 4。长上下文、代码生成与长文写作口碑好，安全对齐投入大。
- Gemini（Google）：Gemini 1.5/2.0/2.5。原生多模态（文本、图像、音频、视频），上下文窗口可达百万级。

### 1.1.2 开源与国产家族

- Llama（Meta）：Llama 3/3.1/4。开源生态的基准线，社区微调版本最多。
- Qwen（阿里）：Qwen2.5、Qwen3。中英双语强，尺寸覆盖 0.5B 到 235B，衍生模型极其丰富。
- DeepSeek（深度求索）：DeepSeek-V3、R1。推理与代码强，MoE 架构与开源权重是标志。
- Mistral（Mistral AI）：Mistral、Mixtral。欧洲代表，稀疏 MoE 路线较早。
- GLM（智谱）：GLM-4。通用能力均衡，国内政企场景常见。
- 豆包（字节）：Doubao。对话体验与工程化落地成熟。
- Kimi（月之暗面）：Kimi。以长上下文起家。
- 文心（百度）：中文语义与知识图谱结合。
- 混元（腾讯）：社交与内容生态内嵌。

## 1.2 命名规则解读

看懂型号名能避免"买错档位"。命名通常由"家族 + 版本 + 尺寸 + 变体"四段构成。

### 1.2.1 版本号与档位后缀

- 版本号：如 3.5、4、4o 中的数字表示代际，数字越大通常越新。
- 档位后缀：`mini`、`turbo`、`flash`、`haiku` 表示轻量低价；`pro`、`sonnet`、`opus` 表示中到高端。
- 特殊标记：`o1/o3`、`R1`、`thinking` 表示具备显式推理（测试时计算）能力。

### 1.2.2 尺寸与变体后缀

- 尺寸：`7B`、`14B`、`72B`、`235B` 表示参数量（B 为十亿参数，billion）。
- 变体：`Instruct`/`Chat` 为指令微调版，`Base` 为基座版，`Coder` 为代码专长，`VL` 为视觉语言版。
- 量化标记：`Q4`、`Q8`、`AWQ`、`GPTQ` 表示量化精度与算法。

| 后缀 | 含义 | 使用场景 |
|------|------|----------|
| base | 基座，未对齐 | 二次训练 |
| instruct / chat | 指令微调 | 对话与 Agent |
| coder | 代码专长 | 编程任务 |
| vl / vision | 视觉语言 | 图文理解 |
| mini / flash | 轻量低价 | 高并发简单任务 |
| pro / max | 高端 | 复杂任务 |

## 1.4 家族选择的生产建议

- 优先选同一家族内的多个档位做分层，迁移成本最低。
- 跨家族对比时，不要只看版本号，要落到具体评测与成本。
- 关注家族的接口兼容性，OpenAI 兼容协议是事实标准。
- 家族会迭代，选型要留出替换空间，避免硬编码模型名。

# 2. 能力梯队划分

> 结论先行：能力梯队是"相对排序"而非"绝对真理"，同一梯队内差异可能很小，跨梯队则通常有可感知的差距。梯队用于快速初筛，最终必须用自有评测集验证。

## 2.1 梯队划分标准

梯队划分综合静态榜单（benchmark）、人工盲测（arena）与真实任务表现。

### 2.1.1 静态榜单与动态评测

- 静态榜单：MMLU、GPQA、HumanEval、SWE-bench 等，可复现但易被针对性优化。
- 动态评测：LMSYS Chatbot Arena 采用匿名对战投票，Elo 分更贴近人类偏好。
- 真实任务：企业自有评测集最可信，但构建成本高。

### 2.1.2 梯队不是绝对

- 同一模型在不同维度上可能跨梯队：某模型通用第二梯队，但代码第一梯队。
- 版本更新会打乱梯队，榜单滞后数月很常见。
- 推理模型在难题上强，但简单任务性价比低。

## 2.2 四梯队模型清单

```
第一梯队（顶级）：
  GPT-4o / Claude 4 / Gemini 2.5 Pro

第二梯队（强）：
  Llama 3.1 405B / Qwen3-235B / DeepSeek-V3

第三梯队（性价比）：
  GPT-4o-mini / Claude Haiku / Qwen2.5-7B

第四梯队（小模型）：
  Llama 3.2 3B / Qwen2.5-1.5B
```

## 2.3 梯队与成本的关系

| 梯队 | 相对能力 | 相对成本 | 典型用途 |
|------|:--------:|:--------:|----------|
| 第一梯队 | 100% | 最高 | 复杂推理、旗舰产品 |
| 第二梯队 | 85%~95% | 中 | 通用生产 |
| 第三梯队 | 60%~80% | 低 | 高并发、分类抽取 |
| 第四梯队 | 40%~60% | 极低 | 边缘、离线 |

## 2.4 梯队评估的坑

- 榜单污染：训练数据可能包含测试集，分数虚高。
- 提示词差异：同一模型换提示词，排名可能变化。
- 长尾任务：梯队反映平均能力，特定任务可能反转。
- 成本错觉：第一梯队单位 token 贵，但若一次成功率高，总成本未必高。

**生产建议**：先用梯队缩小候选到 3~5 个，再用自有数据评测，最后按成本与延迟排序。

# 3. 开源与闭源谱系

> 结论先行：开源指权重可下载、可本地部署，闭源仅提供 API。开源胜在数据可控、可定制、边际成本低；闭源胜在能力上限、免运维、迭代快。多数企业最终走混合路线。

## 3.1 开源与闭源的定义边界

### 3.1.1 权重开放不等于完全开源

"开放权重"（open weights）只公开模型参数，未必公开训练数据与训练代码。因此严格意义上的"开源"很少，多数是"开放权重"。区别影响：能否复现训练、能否审计数据来源。

### 3.1.2 许可证差异

| 许可证 | 代表 | 商用 | 限制 |
|--------|------|:----:|------|
| Apache 2.0 | Qwen 部分 | 可 | 宽松 |
| MIT | 部分小模型 | 可 | 宽松 |
| Llama 社区许可 | Llama | 有条件 | 月活门槛、命名要求 |
| 自定义许可 | 部分国产 | 需审查 | 条款各异 |

## 3.2 对比矩阵

| 维度 | 开源 | 闭源 |
|------|------|------|
| 权重 | 公开 | 不公开 |
| 部署 | 可本地 | 仅 API |
| 数据 | 不出内网 | 需评估 |
| 成本 | 一次性硬件 | 按量计费 |
| 定制 | 可微调 | 有限 |
| 效果 | 接近顶级 | 通常最强 |
| 迭代 | 社区 + 官方 | 官方 |
| 支持 | 社区 | 官方 SLA |

## 3.3 开源谱系生态

开源模型的可用性很大程度取决于推理与服务生态。

| 工具 | 作用 |
|------|------|
| vLLM | 高吞吐推理服务 |
| SGLang | 结构化生成与高并发 |
| llama.cpp | CPU/边缘量化推理 |
| Ollama | 本地一键运行 |
| Transformers | 训练与微调基础库 |
| PEFT / LoRA | 参数高效微调 |

## 3.4 边界与反例

- 反例一：开源模型本地跑，若没有 GPU 与运维，成本可能高于 API。
- 反例二：闭源 API 也可能因数据合规无法用于敏感场景。
- 边界：开放权重不等于可随意商用，许可证必须逐条审查。

# 4. 模型规模分类

> 结论先行：参数量决定能力上限与硬件门槛，但真正决定推理成本的是"激活参数"与"量化精度"。MoE（混合专家，Mixture of Experts）让总参数大而激活小，是当前主流路线。

## 4.1 按参数量分级

| 规模 | 参数量 | 部署 | 代表 |
|------|--------|------|------|
| 微型 | < 3B | 手机/边缘 | Llama 3.2 3B |
| 小型 | 7~14B | 单卡 | Qwen2.5-7B |
| 中型 | 30~70B | 多卡 | Llama 3.1 70B |
| 大型 | 100B+ | 多机 | Llama 3.1 405B |
| MoE | 总参数大、激活小 | 多卡 | DeepSeek-V3 |

## 4.2 稠密与 MoE 架构

### 4.2.1 MoE 机制拆解

稠密模型每个 token 都经过全部参数；MoE 把前馈层拆成多个"专家"，每个 token 只路由到少数专家（如 Top-2）。

```
稠密模型：
  token -> [FFN 全部参数] -> 输出
  FLOPs 正比于总参数

MoE 模型：
  token -> Router -> Top-2 专家 -> 加权合并 -> 输出
  FLOPs 正比于激活参数（远小于总参数）
```

### 4.2.2 激活参数与显存

- 激活参数决定计算量，总参数决定显存占用（权重需全部驻留）。
- 例：总参数 671B、激活 37B，计算像 37B，显存像 671B。
- 因此 MoE 省算力不省显存，部署仍需大显存。

## 4.3 量化与显存估算

| 精度 | 每参数字节 | 70B 显存 | 说明 |
|------|:----------:|:--------:|------|
| FP16 | 2 | ~140GB | 基准 |
| INT8 | 1 | ~70GB | 轻微损失 |
| INT4 | 0.5 | ~35GB | 常用，需校准 |

估算公式（伪代码）：

```
显存 ≈ 参数量 × 每参数字节
       + KV Cache（随上下文与并发增长）
       + 运行时开销
```

## 4.4 规模选型的生产建议

- 单卡能跑就本地跑，超过单卡优先考虑 API 或 MoE。
- 量化到 INT4 是性价比拐点，再低精度损失明显。
- 上下文越长，KV Cache 越吃显存，需单独核算。

# 5. 模型能力维度

> 结论先行：模型能力不是一个分数，而是知识、推理、代码、多语言、长上下文、工具调用、多模态、指令遵循八个维度的组合。选型必须按任务匹配维度，而非看综合分。

## 5.1 八大能力维度

```
① 通用知识（MMLU）
② 推理（数学、逻辑）
③ 代码（HumanEval、SWE-bench）
④ 多语言
⑤ 长上下文
⑥ 工具调用
⑦ 多模态
⑧ 指令遵循
```

## 5.2 各维度的评测基准

### 5.2.1 知识类基准

- MMLU：多学科选择题，衡量通识。
- GPQA：研究生级科学问答，区分度高。
- C-Eval / CMMLU：中文知识与推理。

### 5.2.2 推理与代码基准

- GSM8K / MATH：小学数学到竞赛数学。
- HumanEval / MBPP：函数级代码生成。
- SWE-bench：真实仓库缺陷修复，贴近工程。

### 5.2.3 对齐与指令基准

- IFEval：指令遵循的格式约束。
- MT-Bench：多轮对话质量。
- 工具调用：BFCL 等函数调用基准。

## 5.3 基准的局限

| 局限 | 说明 |
|------|------|
| 数据污染 | 测试集可能进训练数据 |
| 饱和 | 分数接近满分失去区分度 |
| 形式化 | 选择题不等于真实任务 |
| 语言偏 | 英文基准不代表中文表现 |

## 5.4 维度匹配生产实践

| 任务 | 关键维度 | 建议 |
|------|----------|------|
| 知识问答 | 知识 + 指令 | 中/大模型 + RAG |
| 数学推理 | 推理 | 推理模型 |
| 代码 | 代码 + 工具 | 代码专长 |
| 文档分析 | 长上下文 | 长窗口模型 |
| Agent | 工具调用 | 函数调用强的模型 |

# 6. 版本演进趋势

> 结论先行：模型演进有六条主线——上下文变长、多模态、推理增强、MoE 普及、小模型变强、成本下降。理解趋势能帮助判断"现在该不该等下一代"。

## 6.1 六大趋势

| 趋势 | 说明 |
|------|------|
| 上下文变长 | 4K → 128K → 1M+ |
| 多模态 | 文本 → 图像/音频/视频 |
| 推理增强 | 引入思考过程 |
| MoE 普及 | 大容量低激活 |
| 小模型变强 | 蒸馏 + 过训练 |
| 成本下降 | 竞争 + 优化 |

## 6.2 上下文扩展机制

- 位置编码外推：RoPE（旋转位置编码）插值与缩放。
- 注意力优化：FlashAttention、稀疏注意力降低长序列开销。
- 训练策略：长文本继续预训练，逐步拉长序列长度。

## 6.3 推理增强（测试时计算）

推理模型在回答前生成"思维链"（Chain of Thought），用更多推理算力换准确率。

```
普通模型： 问题 -> 直接答案
推理模型： 问题 -> 思考(长) -> 答案
           延迟高、token 多、难题准确率高
```

## 6.4 趋势对选型的影响

- 长上下文与 MoE 会持续降价，非紧急需求可观望。
- 推理模型适合难题，不适合高频简单任务。
- 小模型每年能力提升，边缘场景可逐步下沉。

- 上线前确认备案与内容安全流程。

# 8. 模型选择的影响因素

> 结论先行：选型是"能力 + 成本 + 延迟 + 合规 + 生态"的多目标权衡，没有单一最优解。应先用硬约束（合规、上下文）筛除，再按加权评分排序。

## 8.1 五要素模型

```
能力 + 成本 + 延迟 + 合规 + 生态
```

| 因素 | 说明 |
|------|------|
| 能力 | 任务需求匹配 |
| 成本 | 按量 vs 自建 |
| 延迟 | 用户体验 |
| 合规 | 数据出境、备案 |
| 生态 | 工具、框架支持 |

## 8.2 多因素权衡

### 8.2.1 能力与成本

能力越强通常越贵，但"一次成功率"会改变总成本：高价模型若减少重试，总成本可能更低。

### 8.2.2 延迟与合规

延迟敏感场景优先小模型或本地部署；合规硬约束可能直接排除境外 API。

### 8.2.3 生态与稳定性

生态决定开发效率，稳定性（可用性、限流）决定生产可用性。

## 8.3 评分卡示例（Java）

```java
import java.util.Comparator;
import java.util.List;

public final class ModelScorer {

    public record Criterion(String name, double weight, double score) {}

    public record Candidate(String name, List<Criterion> criteria) {

        double weightedScore() {
            double totalWeight = criteria.stream()
                    .mapToDouble(Criterion::weight)
                    .sum();
            double sum = criteria.stream()
                    .mapToDouble(c -> c.weight() * c.score())
                    .sum();
            return totalWeight == 0 ? 0 : sum / totalWeight;
        }
    }

    public List<String> rank(List<Candidate> candidates) {
        return candidates.stream()
                .sorted(Comparator.comparingDouble(Candidate::weightedScore).reversed())
                .map(Candidate::name)
                .toList();
    }
}
```

## 8.4 生产注意事项

| 风险 | 建议 |
|------|------|
| 只看综合分 | 按任务维度评测 |
| 忽略硬约束 | 先用合规/上下文筛选 |
| 权重拍脑袋 | 与业务方共同定权重 |
| 一次定终身 | 定期复评并保留替换 |
