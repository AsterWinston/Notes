# 1. SFT 概述

结论先行：SFT（Supervised Fine-Tuning，监督微调）用"指令-回答"数据微调 Base Model，把它从"会补全文本"转变为"会遵循指令"。

## 1.1 定义与定位

### 1.1.1 从 Base Model 到 Instruct Model

**SFT（Supervised Fine-Tuning，监督微调）** = 用"指令-回答"数据微调 Base Model，让它学会遵循指令。

```
Base Model：会补全，但不会遵循指令
SFT 之后：  "请写一首诗" → 输出一首诗
```

Base Model 只学过"预测下一个 token"，它的行为是"续写"而不是"应答"。SFT 通过成对的指令-回答样本，把"应答"这种行为模式注入模型。

### 1.1.2 SFT 在训练流水线中的位置

现代大模型训练通常分三段：

```
预训练（Pre-training）
   │  海量无标注文本，学语言与世界知识
   ▼
SFT（监督微调）
   │  指令-回答数据，学"如何应答"
   ▼
对齐（Alignment：RLHF / DPO）
      偏好数据，学"哪种应答更好"
```

SFT 是承上启下的关键一步：没有 SFT，RLHF/DPO 无从谈起。

## 1.2 与其他训练阶段的关系

### 1.2.1 预训练 / SFT / 对齐

| 阶段 | 数据 | 目标 | 典型规模 |
|------|------|------|----------|
| 预训练 | 无标注文本 | 学语言与知识 | 万亿 token |
| SFT | 指令-回答 | 学遵循指令 | 万~百万条 |
| 对齐 | 偏好对 | 学好坏偏好 | 万~十万条 |

三者的数据量相差数个数量级，SFT 用极少量数据即可显著改变行为。

### 1.2.2 SFT 与 RLHF/DPO 的分工

SFT 回答"能不能按指令作答"，对齐回答"答得好不好"。SFT 只学模仿，无法表达"好"与"更好"的偏好差异，这正是 RLHF/DPO 的用武之地（详见 `4_rlhf.md`、`5_dpo_variants.md`）。

## 1.3 数学形式化

### 1.3.1 条件语言建模

SFT 本质是条件语言建模（Conditional Language Modeling）。给定指令 $x$ 与回答 $y=(y_1,\dots,y_T)$，模型建模：

$$
\pi_\theta(y \mid x) = \prod_{t=1}^{T} \pi_\theta(y_t \mid x, y_{<t})
$$

### 1.3.2 负对数似然损失

训练目标是最大化回答的对数似然，等价于最小化负对数似然（NLL）：

$$
\mathcal{L}_{\text{SFT}}(\theta) = - \sum_{t=1}^{T} \log \pi_\theta(y_t \mid x, y_{<t})
$$

直觉：对每一个真实回答 token，抬高模型给它分配的概率。这本质是最大似然估计（MLE）。

## 1.4 边界与坑

- 若把指令 $x$ 的 token 也算进损失，模型会同时学"如何提问"，稀释"如何回答"的学习信号。
- SFT 只会逼近数据分布，数据里没有的能力不会凭空出现。
- 损失下降不等于效果好，需以人工/自动评测为准。

# 2. 数据格式与模板

结论先行：SFT 数据必须结构化为"角色 + 内容"，并经过与训练时一致的对话模板（Chat Template）序列化。

## 2.1 对话数据格式

### 2.1.1 messages 结构

主流格式是消息列表：

```
{
  "messages": [
    {"role": "system", "content": "你是一个有用的助手。"},
    {"role": "user", "content": "写一首关于春天的诗"},
    {"role": "assistant", "content": "春风拂面花自开..."}
  ]
}
```

| 要素 | 说明 |
|------|------|
| system | 系统提示（可选） |
| user | 用户指令 |
| assistant | 期望的回答 |

### 2.1.2 单轮与多轮

单轮样本只有一对 user/assistant；多轮样本交替出现多对，共享同一段上下文。多轮数据能训练模型维持对话状态，但要注意掩码与截断。

## 2.2 Chat Template

### 2.2.1 特殊 token

序列化时用特殊 token 标记角色边界，例如：

```
<|system|>你是一个有用的助手。<|user|>写一首诗<|assistant|>春风...
```

不同模型的特殊 token 不同，必须使用与预训练/SFT 一致的模板。

### 2.2.2 模板一致性

训练与推理（Inference）必须使用完全相同的模板。模板不一致是"训练好好的，上线就崩"的常见原因。

## 2.3 数据校验

### 2.3.1 常见格式错误

| 错误 | 后果 |
|------|------|
| 角色名拼写错误 | token 被当普通文本 |
| assistant 内容为空 | 无效样本 |
| 缺失 assistant 结尾符 | 模型学不会停止 |
| 特殊字符未转义 | 模板解析错位 |

### 2.3.2 自动化校验

上线前应校验：角色合法、内容非空、模板可解析、token 长度在范围内。

## 2.4 边界与坑

- 不要在数据里手写特殊 token，应交给模板函数，避免转义问题。
- 截断长样本时若把 assistant 答案截掉，会得到"只学提问"的坏样本。
- 同一批数据混用不同模板会导致模型角色混乱。

## 2.5 生产建议

- 把模板封装为单一函数，训练、评测、推理共用。
- 数据入库前跑一遍 schema 校验与 token 长度统计。
- 保留原始 messages 与序列化后文本两份，便于排查。

# 3. 训练目标与损失掩码

结论先行：只在 assistant 部分计算损失，user/system 部分用 -100 忽略，是 SFT 的标准做法。

## 3.1 只在 assistant 计算损失

### 3.1.1 原理

```
只在 assistant 部分计算损失：
  user 部分的 token 不参与损失计算

原因：我们希望模型学会"如何回答"，
      而非"如何提问"
```

若对整段序列求损失，模型会花容量去建模用户措辞，学习信号被稀释。

### 3.1.2 实现

```python
    # 掩码：user 部分 loss 置为 -100（忽略）
labels = input_ids.clone()
labels[user_positions] = -100
loss = cross_entropy(logits, labels)
```

PyTorch 的 `cross_entropy` 默认 `ignore_index=-100`，被置为 -100 的位置不贡献梯度。

## 3.2 掩码的边界情况

### 3.2.1 system/user 处理

system 提示通常也忽略。但若希望模型学会"遵守 system 约束"，部分实现会保留 system 损失，需实验权衡。

### 3.2.2 多轮掩码

多轮样本中，每一轮 user 段忽略、assistant 段计算损失，逐段构造掩码。角色切换 token（如 `<|assistant|>`）的归属需与模板严格对应。

## 3.3 数学直觉

带掩码的损失可写成：

$$
\mathcal{L} = - \sum_{t \in \mathcal{A}} \log \pi_\theta(y_t \mid x, y_{<t})
$$

其中 $\mathcal{A}$ 是 assistant token 的位置集合。掩码只是把求和范围从全序列缩小到 $\mathcal{A}$。

## 3.4 Java 实现示例

### 3.4.1 掩码构建

```java
public static int[] buildLabels(int[] inputIds, boolean[] isAssistant) {
    int[] labels = new int[inputIds.length];
    for (int i = 0; i < inputIds.length; i++) {
        labels[i] = isAssistant[i] ? inputIds[i] : -100;
    }
    return labels;
}
```

### 3.4.2 损失计算

```java
public static double maskedCrossEntropy(double[][] logits,
                                        int[] labels) {
    double total = 0.0;
    int count = 0;
    for (int t = 0; t < labels.length; t++) {
        if (labels[t] == -100) {
            continue;
        }
        total += -Math.log(softmax(logits[t])[labels[t]]);
        count++;
    }
    return count == 0 ? 0.0 : total / count;
}
```

### 3.4.3 边界提醒

- 若某样本掩码后 `count == 0`，应跳过该样本而非产生 NaN。
- logits 与 labels 需做 shift：位置 `t` 的 logits 预测位置 `t+1` 的 token。

## 3.5 边界与坑

- 忘记 shift 会导致预测错位，损失居高不下。
- 全部 token 都被掩码的样本要过滤，否则除零。
- 不同框架对 ignore_index 默认值不同，需显式指定。

## 3.6 生产建议

- 训练前打印若干样本的掩码可视化，人工确认 assistant 段正确。
- 记录每个 batch 的有效 token 数，异常时及时告警。

# 4. 数据质量与构造

结论先行：SFT 效果主要由数据质量决定，少量高质量数据常胜过海量低质量数据。

## 4.1 质量维度

### 4.1.1 正确性与相关性

```
SFT 效果 = 数据质量 × 数量
质量远比数量重要
```

| 质量维度 | 说明 |
|----------|------|
| 正确性 | 答案正确 |
| 相关性 | 切题 |
| 格式规范 | 符合期望格式 |
| 多样性 | 覆盖多种任务 |
| 难度分布 | 从易到难 |

### 4.1.2 多样性与难度

多样性防止模型对单一任务过拟合；难度分布让模型既能处理简单请求，也能应对复杂推理。

> **1000 条高质量数据可能胜过 10 万条低质量数据**（如 LIMA 论文）。

## 4.2 数据来源

### 4.2.1 人工 / 真实 / 合成 / 开源

| 来源 | 说明 |
|------|------|
| 人工标注 | 质量最高，成本高 |
| 真实对话 | 贴近实际 |
| 强模型生成 | 成本低，需筛选 |
| 开源数据集 | 现成，需适配 |

### 4.2.2 蒸馏与 Self-Instruct

用强模型生成回答属于"知识蒸馏（Distillation）"；由少量种子样本让模型自举生成更多指令，是 Self-Instruct 思路。

```python
    # 用强模型生成 SFT 数据
def generate_sft_data(seed_examples, target_model):
    data = []
    for seed in seed_examples:
        # 让强模型生成高质量回答
        response = target_model.chat(seed["instruction"])
        data.append({
            "instruction": seed["instruction"],
            "output": response
        })
    return data
```

合成数据的风险：会继承强模型的错误与偏见，且分布可能过于单一，必须过滤与去重。

## 4.3 数据配比

### 4.3.1 典型配比

```
一个高质量 SFT 数据集应覆盖：
├── 通用对话（30%）
├── 推理与数学（20%）
├── 代码（15%）
├── 领域任务（25%）
└── 安全拒答（10%）
```

### 4.3.2 配比调整

配比影响模型的能力分布，需按目标调整。领域模型应提高领域任务占比，但不能完全挤掉通用能力，否则泛化骤降。

## 4.4 边界与反例

- 反例：100% 领域数据微调，模型在通用问题上严重退化。
- 反例：合成数据未去重，模型学会复读模板句式。
- 边界：安全拒答数据过少会导致越狱（Jailbreak）成功率上升。

## 4.5 生产建议

- 建立数据分级（金标/银标/合成），金标优先。
- 用去重（MinHash/SimHash）与质量分类器过滤合成数据。
- 定期抽样人工复核，跟踪配比漂移。

# 5. 训练超参数与微调方式

结论先行：SFT 用较小的学习率、1~3 轮训练，并优先考虑参数高效微调。

## 5.1 关键超参数

### 5.1.1 学习率 / 轮数 / 批大小

| 参数 | 典型值 |
|------|--------|
| 学习率 | 1e-5 ~ 2e-5 |
| 训练轮数 | 1~3 |
| 批大小 | 视显存 |
| 序列长度 | 2048~8192 |
| 微调方式 | LoRA / 全量 |

> SFT 通常只训练 1~3 轮，**过拟合会损害泛化**。

### 5.1.2 序列长度与调度

序列长度决定单样本覆盖的对话轮数；过长增加显存，过短会截断。学习率调度常用余弦退火加少量 warmup。

## 5.2 参数高效微调

### 5.2.1 LoRA

LoRA（Low-Rank Adaptation，低秩适配）冻结原权重 $W$，只训练低秩增量：

$$
W' = W + \frac{\alpha}{r} B A
$$

其中 $A \in \mathbb{R}^{r \times d}$、$B \in \mathbb{R}^{d \times r}$，$r \ll d$。可训练参数量大幅下降。

### 5.2.2 QLoRA

QLoRA 把基座权重量化到 4-bit，再在量化权重上做 LoRA，使单卡微调大模型成为可能。

| 方式 | 可训练参数 | 显存 | 效果 |
|------|-----------|------|------|
| 全量 | 全部 | 极高 | 最好 |
| LoRA | 少量 | 低 | 接近全量 |
| QLoRA | 少量 | 最低 | 略降 |

## 5.3 显存与并行

### 5.3.1 梯度累积

显存不足时用小批大小配梯度累积，模拟大批大小：

```python
for step, batch in enumerate(loader):
    loss = model(batch) / accum_steps
    loss.backward()
    if (step + 1) % accum_steps == 0:
        optimizer.step()
        optimizer.zero_grad()
```

### 5.3.2 ZeRO 与 FSDP

ZeRO/FSDP 把优化器状态、梯度、参数分片到多卡，降低单卡显存占用，是全量与大规模微调的常用手段。

## 5.4 边界与坑

- 学习率过大导致灾难性遗忘，过小则学不动。
- 梯度累积时忘记按累积步数缩放损失，等效学习率会偏大。
- LoRA 的 target module 选择不当会显著影响效果。

## 5.5 生产建议

- 先跑小规模消融，锁定学习率与轮数再放量。
- 记录 loss 曲线，出现震荡及时降学习率。
- 固定随机种子，保证可复现。

# 6. 灾难性遗忘与稳定训练

结论先行：微调可能让模型"忘记"预训练学到的能力，需通过低学习率、少轮数与数据混合缓解。

## 6.1 遗忘现象

### 6.1.1 成因

```
微调可能让模型"忘记"预训练学到的能力
```

在窄分布数据上持续更新参数，会使参数偏离预训练最优点，通用能力随之下降。

### 6.1.2 度量

用微调前后的通用基准（如常识、数学、代码）对比，量化遗忘程度。

## 6.2 缓解策略

### 6.2.1 数据混合与回放

在 SFT 数据中混入通用指令或预训练语料，是最直接有效的手段。

### 6.2.2 低学习率与正则

| 对策 | 说明 |
|------|------|
| 低学习率 | 减少参数漂移 |
| 少轮数 | 1~3 轮 |
| 数据混合 | 混入通用数据 |
| LoRA | 只训练部分参数 |

也可加入与初始权重的 L2 距离正则（类似 EWC 思想），抑制大幅漂移。

## 6.3 边界与反例

- 反例：只训领域数据且轮数过多，通用能力断崖式下跌。
- 边界：LoRA 并非绝对防遗忘，秩过大时同样会遗忘。

## 6.4 生产建议

- 上线前跑通用能力回归测试。
- 保留 SFT 前的基座，便于对比与回滚。
- 领域微调时监控通用指标的下降幅度。

# 7. SFT 的局限与演进

结论先行：SFT 只学"模仿"，无法表达偏好，这催生了 RLHF/DPO 等对齐方法。

## 7.1 局限

| 局限 | 说明 |
|------|------|
| 只学"模仿" | 学会格式，不保证质量最优 |
| 无法表达偏好 | 无法区分"好"与"更好" |
| 数据瓶颈 | 高质量数据有限 |

SFT 的目标是最大化示范回答的似然，它告诉模型"这样答"，但不告诉模型"这样比那样更好"。

## 7.2 演进方向

- 偏好对齐：RLHF、DPO 及其变体。
- 拒绝采样微调（RFT）：用模型自采样并筛选优质回答再 SFT。
- 可验证奖励：在数学、代码等可验证任务上做强化学习。

> SFT 只学模仿，偏好对齐需 RLHF/DPO，详见 `4_rlhf.md` 与 `5_dpo_variants.md`。

## 7.3 生产建议

- 把 SFT 视为对齐流水线的基座，不要指望它单独解决偏好问题。
- 在 SFT 后再接入 DPO 通常比单独 SFT 效果好。

# 8. 生产注意事项与评测

结论先行：SFT 落地的关键在于数据治理、防遗忘与系统性评测。

## 8.1 工程风险

| 风险 | 建议 |
|------|------|
| 数据质量差 | 严格筛选 |
| 训练轮数过多 | 1~3 轮 |
| 灾难性遗忘 | 低学习率 + 数据混合 |
| 只算全序列损失 | 只算 assistant 部分 |
| 无评测 | 微调后评测 |

## 8.2 评测体系

### 8.2.1 自动评测

用固定基准与 LLM-as-Judge 打分，覆盖指令遵循、事实性、安全性等维度。

### 8.2.2 人工评测

对关键场景做盲评与 A/B 对比，弥补自动评测的盲区。

## 8.3 生产建议

- 评测集与训练集严格隔离，防止数据泄漏。
- 建立上线门槛，未达标不放量。
- 灰度发布并持续监控线上指标。

# 9. 小结

## 9.1 核心结论

- SFT 用指令-回答数据让 Base Model 学会遵循指令。
- 数据格式为角色化 messages，序列化需与模板严格一致。
- 只在 assistant 部分计算损失，其余 token 用 -100 掩码。
- 数据质量远比数量重要，需关注配比、去重与来源。
- SFT 只学模仿，偏好对齐需 RLHF/DPO。

## 9.2 落地清单

- 学习率小、训练 1~3 轮，配合 LoRA/QLoRA 与数据混合防灾难性遗忘。
- 上线前必须做自动与人工评测，并隔离训练/评测数据。
- 保留基座与各阶段 checkpoint，支持回滚。
