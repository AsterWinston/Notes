# 1. 为什么需要分布式

分布式训练（Distributed Training）把模型与数据切分到多张 GPU 上协同计算。

**结论先行**：单卡显存装不下大模型的参数、梯度、优化器状态与激活值，必须把训练状态切分到多卡，而切分方式决定了通信量的大小。

## 1.1 显存账单

```
单卡显存有限（80GB）：
  70B 模型 FP16 需要 ~140GB → 装不下
  训练还需要优化器状态、梯度、激活 → 更多

必须把模型与数据切分到多卡
```

### 1.1.1 训练状态的显存构成

以参数量 P、精度 FP16（2 字节）为例：

| 组成 | 精度 | 显存 |
|------|------|------|
| 参数 | FP16 | 2P |
| 梯度 | FP16 | 2P |
| 优化器一阶动量 | FP32 | 4P |
| 优化器二阶动量 | FP32 | 4P |
| FP32 主权重 | FP32 | 4P |
| 合计 | — | ~16P 字节 |

### 1.1.2 激活值

激活值（Activation）随批次大小与序列长度增长，是显存的第二大来源。

```
激活显存 ≈ 层数 × 序列长度 × 隐藏维度 × 批次 × 常数
```

> 混合精度、梯度检查点（Gradient Checkpointing）可显著降低激活显存。

## 1.2 单卡放不下的两种表现

| 现象 | 原因 |
|------|------|
| OOM（显存不足） | 参数/优化器状态过大 |
| 无法增大批次 | 激活值过大 |

## 1.3 通信与扩展的权衡

切分越细，单卡负担越小，但卡间通信越多。分布式训练的核心矛盾就是"显存 vs 通信"。

```
切分粒度 ↑  →  单卡显存 ↓  →  通信量 ↑
切分粒度 ↓  →  单卡显存 ↑  →  通信量 ↓
```

# 2. 三种并行总览

**结论先行**：数据并行切数据、张量并行切层内参数、流水线并行切层间，三者通信量与适用场景各不相同。

## 2.1 切分维度

| 并行 | 切分对象 | 通信量 |
|------|----------|:------:|
| 数据并行（DP） | 数据 | 中 |
| 张量并行（TP） | 层内参数 | 高 |
| 流水线并行（PP） | 层间 | 低 |

```
数据并行：每卡一份完整模型，处理不同数据
张量并行：一层内的矩阵切到多卡
流水线并行：不同层放在不同卡
```

## 2.2 通信特性对比

| 并行 | 通信频率 | 通信内容 | 适合链路 |
|------|:--------:|----------|----------|
| DP | 每步一次 | 梯度 | 节点间也可 |
| TP | 每层多次 | 激活 | 节点内 NVLink |
| PP | 层边界 | 激活 | 节点间 |

## 2.3 组合思路

```
小模型、多数据     → 数据并行
单层放不下         → 张量并行
层数多、想省通信   → 流水线并行
超大规模           → 三者组合（3D 并行）
```

# 3. 数据并行

**结论先行**：数据并行每卡持有完整模型副本、处理不同数据，通过梯度 AllReduce 保持同步，实现简单但显存冗余。

## 3.1 原理

```
     完整模型      完整模型      完整模型
       GPU0         GPU1         GPU2
        │            │            │
     数据batch1   数据batch2   数据batch3
        │            │            │
        └────────────┼────────────┘
                     ▼
              梯度 AllReduce 同步
```

```python
# PyTorch DDP
model = DDP(model, device_ids=[rank])
output = model(batch)
loss.backward()          # 自动 AllReduce
optimizer.step()
```

## 3.2 梯度同步机制

### 3.2.1 Ring AllReduce

Ring AllReduce 把梯度分成 N 份，在环上做"分发-归约"与"全收集"，通信量与卡数近似无关。

```
步骤1  Reduce-Scatter：每卡归约一部分并传给下一卡
步骤2  All-Gather：把归约结果在环上广播

通信量 ≈ 2 × (N-1)/N × 参数量 ≈ 2 × 参数量
```

### 3.2.2 Java 模拟归约

```java
static double[] allReduceSum(double[] local, int rank, int world) {
    double[] global = new double[local.length];
    // 简化：模拟各卡求和后广播
    for (int i = 0; i < local.length; i++) global[i] = local[i] * world;
    return global;
}
```

## 3.3 优缺点与边界

| 优点 | 缺点 |
|------|------|
| 实现简单 | 每卡要装完整模型 |
| 扩展性好 | 通信量大 |
| 收敛等价单卡 | 显存无节省 |

> 数据并行不减少单卡模型显存，这是 ZeRO 出现的原因。

# 4. 张量并行

**结论先行**：张量并行把单层权重矩阵按行或列切到多卡，解决单层装不下的问题，但每层都需通信，对带宽要求极高。

## 4.1 列并行与行并行

### 4.1.1 列并行

把输出维度切分，每卡计算部分输出，最后拼接。

```
W = [W1]   →  GPU0 持有 W1
    [W2]      GPU1 持有 W2

Y = XW = [XW1 | XW2]  → 各卡算一段，AllGather 拼接
```

### 4.1.2 行并行

把输入维度切分，每卡得到部分和，最后求和。

```
W = [W1 W2]  →  GPU0 持有 W1，GPU1 持有 W2

Y = XW = X1W1 + X2W2  → 各卡算部分和，AllReduce 求和
```

## 4.2 在 MLP 中的组合

```
Y = GeLU(X A) B
  A 列并行（无需通信即可接 GeLU）
  B 行并行（用一次 AllReduce 合并）

每层 MLP 只需一次 AllReduce → 通信被摊薄
```

```python
# 列并行
class ColumnParallelLinear(nn.Module):
    def __init__(self, in_features, out_features, world_size):
        self.weight = nn.Parameter(
            torch.empty(out_features // world_size, in_features))

    def forward(self, x):
        # 每卡计算部分输出，再 AllGather
        ...
```

## 4.3 优缺点与边界

| 优点 | 缺点 |
|------|------|
| 解决单层装不下 | 通信频繁 |
| 计算可并行 | 适合高带宽（NVLink） |
| — | 跨节点性能骤降 |

> 生产上张量并行通常限制在单节点 8 卡以内。

# 5. 流水线并行

**结论先行**：流水线并行把不同层放到不同卡，通信量小，但存在流水空泡，需要靠微批与调度策略填补。

## 5.1 原理与微批

```
GPU0: [层1-4] → GPU1: [层5-8] → GPU2: [层9-12] → GPU3: [层13-16]
```

```
微批（Micro-batch）流水：
时间 →
GPU0: [B1][B2][B3][B4]
GPU1:    [B1][B2][B3][B4]
GPU2:       [B1][B2][B3][B4]
GPU3:          [B1][B2][B3][B4]
```

## 5.2 空泡与调度

### 5.2.1 GPipe

先全部前向、再全部反向，空泡最大但实现简单。

```
空泡比例 ≈ (P - 1) / (M + P - 1)
P = 流水段数，M = 微批数
```

### 5.2.2 1F1B 调度

一前一后交替执行，显著降低激活显存与空泡。

```
1F1B：每个卡前向一个微批后立即反向一个微批
稳态时所有卡都在工作，空泡仅出现在首尾
```

## 5.3 优缺点与边界

| 优点 | 缺点 |
|------|------|
| 通信量小 | 有空泡（bubble） |
| 易扩展 | 需微批填充 |
| 省激活显存（1F1B） | 负载需均衡 |

> 微批数 M 越大，空泡占比越小，但显存占用越高。

# 6. ZeRO 与显存优化

**结论先行**：ZeRO 通过切分优化器状态、梯度、参数，消除数据并行的显存冗余，是训练大模型的主流技术。

## 6.1 冗余来源

```
数据并行的冗余：每卡都存完整的优化器状态、梯度、参数

ZeRO 分三个阶段消除冗余：
  Stage 1：切分优化器状态
  Stage 2：切分梯度
  Stage 3：切分参数
```

## 6.2 三个阶段

### 6.2.1 切分对象与节省

| Stage | 切分 | 显存节省 |
|:-----:|------|:--------:|
| 1 | 优化器状态 | ~4x |
| 2 | + 梯度 | ~8x |
| 3 | + 参数 | ~64x |

### 6.2.2 CPU/NVMe offload

把切分后的状态卸载到 CPU 内存或 NVMe，进一步降低显存，代价是带宽受限。

```python
# DeepSpeed ZeRO-3
config = {
    "zero_optimization": {
        "stage": 3,
        "offload_optimizer": {"device": "cpu"},
        "offload_param": {"device": "cpu"}
    }
}
```

## 6.3 通信代价与边界

| 配置 | 通信量 | 适用 |
|------|:------:|------|
| ZeRO-1 | 与 DP 相同 | 显存紧张但带宽一般 |
| ZeRO-2 | 略增 | 常规大模型 |
| ZeRO-3 | 显著增加 | 极限压缩显存 |

> ZeRO 是训练大模型的主流技术（DeepSpeed、FSDP）。

# 7. 混合精度训练

**结论先行**：混合精度用低精度做计算、高精度存主权重，兼顾速度与稳定，BF16 因动态范围大而更稳。

## 7.1 数值格式

```
FP32：稳定但慢、显存大
FP16：快但易溢出
BF16：快且稳定（推荐）

混合精度：大部分计算用 BF16，关键部分用 FP32
```

| 精度 | 指数位 | 尾数位 | 动态范围 |
|------|:------:|:------:|:--------:|
| FP32 | 8 | 23 | 最大 |
| FP16 | 5 | 10 | 小 |
| BF16 | 8 | 7 | 大 |

## 7.2 损失缩放

### 7.2.1 FP16 溢出

FP16 动态范围小，梯度下溢为 0 或上溢为 inf，需用损失缩放（Loss Scaling）放大损失。

```
loss_scaled = loss × S
梯度 = 反传(loss_scaled) / S
```

### 7.2.2 动态 scaler

根据是否出现 inf/NaN 自动调整缩放因子。

```python
scaler = torch.cuda.amp.GradScaler()
with torch.cuda.amp.autocast(dtype=torch.bfloat16):
    loss = model(batch)
scaler.scale(loss).backward()
scaler.step(optimizer)
scaler.update()
```

## 7.3 边界与坑

| 精度 | 显存 | 速度 | 稳定 |
|------|:----:|:----:|:----:|
| FP32 | 100% | 1x | 最好 |
| FP16 | 50% | 2x | 需 scaler |
| BF16 | 50% | 2x | 好 |

- BF16 无需 scaler，但尾数位少，某些任务收敛略慢。
- 归约（AllReduce）若用 FP16 可能丢精度，建议用 BF16 或 FP32 累加。

# 8. 3D 并行与配置

**结论先行**：3D 并行把数据、张量、流水线并行组合，是大规模训练的标准配置，各维度的乘积等于总卡数。

## 8.1 组合公式

```
数据并行 × 张量并行 × 流水线并行
= 3D 并行（大规模训练的标准配置）
```

```
例：64 卡
  数据并行 4 × 张量并行 4 × 流水线并行 4 = 64
```

## 8.2 配置示例

```python
parallel = {
    "data_parallel_size": 4,    # 跨节点
    "tensor_parallel_size": 4,  # 节点内
    "pipeline_parallel_size": 4
}
assert (parallel["data_parallel_size"]
        * parallel["tensor_parallel_size"]
        * parallel["pipeline_parallel_size"]) == 64
```

## 8.3 实践建议

| 维度 | 放置位置 | 原因 |
|------|----------|------|
| 张量并行 | 节点内 | 通信最频繁 |
| 流水线并行 | 跨节点 | 通信最少 |
| 数据并行 | 最外层 | 通信可重叠 |

# 9. 通信优化

**结论先行**：通信优化从硬件链路、集合通信算法、计算通信重叠与梯度压缩四个层面展开。

## 9.1 硬件层面

| 技术 | 说明 |
|------|------|
| NVLink | 卡间高带宽 |
| InfiniBand | 节点间高带宽 |
| NVSwitch | 全互联交换 |

## 9.2 算法层面

| 技术 | 说明 |
|------|------|
| Ring AllReduce | 带宽最优 |
| Tree AllReduce | 延迟最优 |
| 分桶通信 | 小梯度合并发送 |

## 9.3 重叠与压缩

| 技术 | 说明 |
|------|------|
| 梯度压缩 | 减少通信量 |
| 通信与计算重叠 | 隐藏延迟 |
| 异步通信 | 牺牲一致性换速度 |

> 反向传播中梯度逐层产生，可与通信重叠，把通信时间藏进计算时间。

# 10. 容错与检查点

**结论先行**：大规模训练故障是常态，分片检查点与快速恢复是保证训练不中断的关键。

## 10.1 分片检查点

```
ZeRO-3 / FSDP 下参数是分片的
  → 检查点也应分片保存
  → 恢复时按相同并行配置加载
```

## 10.2 故障恢复

| 手段 | 说明 |
|------|------|
| 定期保存 | 按步数/时间 |
| 异步保存 | 不阻塞训练 |
| 弹性训练 | 卡数变化后重分片 |

## 10.3 边界

- 并行配置改变后，检查点需重分片，否则无法加载。
- 异步保存可能与训练竞争带宽，需控制频率。

# 11. 生产注意事项

**结论先行**：生产落地的核心是把显存、通信、精度三者的权衡配置好，并持续监控。

## 11.1 显存与通信

| 风险 | 建议 |
|------|------|
| 显存不足 | ZeRO-3 + offload |
| 通信瓶颈 | 张量并行限制在节点内 |
| 空泡 | 微批填充 |

## 11.2 精度与稳定性

| 风险 | 建议 |
|------|------|
| 精度问题 | 用 BF16 |
| 梯度爆炸 | 梯度裁剪 |
| 损失尖刺 | 回滚检查点 |

## 11.3 监控与调优

```
监控指标：显存占用、通信占比、MFU、损失曲线
调优顺序：先显存 → 再通信 → 后精度
```

| 风险 | 建议 |
|------|------|
| 检查点大 | 分片保存 |
| 卡数变更 | 弹性 + 重分片 |

# 12. 小结

## 12.1 核心结论

- 单卡显存不足是分布式的根本动因。
- 三种并行：数据、张量、流水线，通信量与适用场景各异。
- 数据并行简单但冗余，ZeRO 消除冗余（三阶段 + offload）。
- 张量并行解决单层装不下，通信频繁，限节点内。
- 流水线并行通信少但有空泡，靠微批与 1F1B 缓解。

## 12.2 实践要点

- 混合精度用 BF16 兼顾速度与稳定，FP16 需损失缩放。
- 3D 并行 + 通信优化 + 分片检查点是大规模训练标配。
