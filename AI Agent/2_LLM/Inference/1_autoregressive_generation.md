# 1. 什么是自回归生成

自回归生成（Autoregressive Generation）是当前大语言模型（LLM）逐 token 产出文本的基本方式。

**结论先行**：模型每一步只预测下一个 token，再把该 token 拼回输入，循环往复，直到命中停止条件。

## 1.1 定义与直觉

**自回归** = 逐 token 生成，每次把已生成的内容作为下一次的输入。

```
输入:  "今天天气"
  ↓ 前向
输出:  "真"
  ↓ 拼接到输入
输入:  "今天天气真"
  ↓ 前向
输出:  "好"
  ↓
...
直到 <EOS>
```

## 1.2 形式化

### 1.2.1 联合概率分解

序列的联合概率按链式法则分解为逐步条件概率：

```
P(x_1, ..., x_n) = Π_{t=1}^{n} P(x_t | x_1, ..., x_{t-1})
```

每一步模型输出词表上的概率分布：

```
P(x_t | x_<t) = softmax(W · h_t)
h_t = 第 t 步的隐状态
```

### 1.2.2 生成算法

```
1. 输入 prompt，前向得到第一个 token 分布
2. 采样/贪心选出 token
3. 拼接到序列末尾
4. 重复 2-3 直到停止
```

## 1.3 边界

| 边界 | 说明 |
|------|------|
| 误差累积 | 一步错可能引发后续偏移 |
| 无法回头 | 生成后不能修改历史 token |
| 长度上限 | 受上下文窗口限制 |

# 2. 两个阶段：Prefill 与 Decode

**结论先行**：推理分为 Prefill（一次处理整段输入）与 Decode（逐 token 生成）两阶段，前者算力密集、后者访存密集。

## 2.1 Prefill（预填充）

```
Prefill（预填充）：
  一次处理整个输入 prompt
  计算并缓存所有位置的 K、V
  → 计算密集（矩阵乘法）
```

### 2.1.1 计算特征

- 输入是完整的 prompt，长度 L。
- 所有位置可并行计算，GPU 算力被充分利用。
- 产出：所有层的 KV Cache 与首个 token 的 logits。

### 2.1.2 与序列长度的关系

```
Prefill 计算量 ∝ L²（注意力部分）
Prefill 访存量 ∝ 参数量 + L
长 prompt → 计算量随 L² 增长，成为主要开销
```

## 2.2 Decode（解码）

```
Decode（解码）：
  逐 token 生成
  每次只处理 1 个新 token
  → 显存带宽密集
```

### 2.2.1 串行特征

- 每步只处理一个 token，但需读取全部权重。
- 串行依赖，无法并行，延迟累积。

### 2.2.2 单步耗时

```
单步耗时 ≈ 模型参数量 / 显存带宽
与序列长度弱相关，与批次强相关
```

## 2.3 对比与瓶颈

```
时间 →
Prefill: [====输入====]  → 首个 token
Decode:  [t1][t2][t3][t4]...  → 后续 token
```

| 阶段 | 特点 | 瓶颈 |
|------|------|------|
| Prefill | 并行、计算密集 | GPU 算力 |
| Decode | 串行、访存密集 | 显存带宽 |

> 理解这两个阶段是推理优化的基础。

# 3. 延迟与吞吐指标

**结论先行**：TTFT 衡量首 token 快不快，TPS 衡量后续吐字快不快，总延迟是两者之和。

## 3.1 核心指标

| 指标 | 说明 | 受什么影响 |
|------|------|------------|
| TTFT | 首 Token 时间 | Prefill 速度 |
| TPS | 每秒生成 Token | Decode 速度 |
| 总延迟 | 全部生成完 | 两者之和 |

```
TTFT = Prefill 时间
总延迟 ≈ TTFT + (生成 token 数 - 1) / TPS
```

## 3.2 流式输出

```
流式输出改善的是"体感延迟"（TTFT）
实际总时长由 TPS 决定
```

流式（Streaming）让用户尽早看到第一个字，但不会缩短总生成时间。

## 3.3 指标关系

| 目标 | 优化点 |
|------|--------|
| 降低 TTFT | 加速 Prefill、前缀缓存 |
| 提高 TPS | 批处理、加速 Decode |
| 提高吞吐 | 连续批处理 |

# 4. 生成实现与 KV Cache

**结论先行**：KV Cache 缓存历史 token 的键值，避免每步重算，把单步复杂度从 O(L²) 降到 O(L)。

## 4.1 基础生成循环

```python
@torch.no_grad()
def generate(model, prompt, max_new_tokens=100):
    input_ids = tokenize(prompt)

    for _ in range(max_new_tokens):
        # 前向：只处理新 token（利用 KV Cache）
        logits = model(input_ids)          # 只取最后一个位置

        # 采样
        next_id = sample(logits[:, -1, :])

        # 拼接
        input_ids = torch.cat([input_ids, next_id], dim=-1)

        if next_id == EOS_ID:
            break

    return detokenize(input_ids)
```

## 4.2 KV Cache

### 4.2.1 原理

注意力中每个位置需要 Key 与 Value，历史位置的 K、V 不变，可缓存复用。

```
无缓存：每步重算全部位置的 K、V → O(L²)
有缓存：只算新 token 的 K、V，读取缓存 → O(L)
```

### 4.2.2 显存开销

```
KV Cache 大小 ≈ 2 × 层数 × 头数 × 头维度 × 序列长度 × 批次 × 字节
```

| 因素 | 影响 |
|------|------|
| 序列长度 | 线性增长 |
| 批次大小 | 线性增长 |
| 层数/头数 | 线性增长 |

## 4.3 复杂度对比

| 方案 | 单步计算 | 单步显存访问 |
|------|:--------:|:------------:|
| 无缓存 | O(L²) | O(L²) |
| 有缓存 | O(L) | O(L) |

> KV Cache 用显存换时间，是 Decode 提速的关键。

# 5. 为什么 Decode 慢

**结论先行**：Decode 每步只算一个 token，却要读取全部模型参数，算术强度低，瓶颈在显存带宽而非算力。

## 5.1 访存瓶颈

```
生成 N 个 token 需要 N 次前向

每次前向：
  读取模型全部参数（70B 模型 → 140GB）
  但只计算 1 个 token

→ 显存带宽成为瓶颈（算力利用率低）
```

## 5.2 算术强度

```
算术强度 = 计算量 / 访存量（FLOP/Byte）

Decode：计算量极小，访存量巨大 → 算术强度极低
Prefill：计算量与访存量都大 → 算术强度高
```

## 5.3 结论

| 阶段 | 算力利用率 | 原因 |
|------|:----------:|------|
| Prefill | 高 | 矩阵大，可并行 |
| Decode | 低 | 只算 1 token，受带宽限 |

> 这解释了为什么 Decode 阶段 GPU 利用率低。

# 6. 批处理与调度

**结论先行**：批处理把多个请求合并计算，摊薄权重读取成本，是提升吞吐的核心手段。

## 6.1 静态批处理

```
无批处理：一次只处理一个请求 → GPU 利用率低
有批处理：多个请求一起处理 → 提升吞吐
```

```
请求1: [t1][t2][t3][t4]
请求2: [t1][t2][t3][t4]     ← 并行
请求3: [t1][t2][t3][t4]
```

静态批处理需等待整批凑齐，长短请求互相拖累。

## 6.2 连续批处理

| 技术 | 说明 |
|------|------|
| 静态批处理 | 固定批次（需等待） |
| 连续批处理 | 动态加入/退出（vLLM） |

连续批处理（Continuous Batching）在每个解码步检查完成情况，完成后立即腾出槽位给新请求。

### 6.2.1 调度原理

每步迭代后重新组批，已完成请求立即退出，新请求立即加入，避免长短请求互相等待。

## 6.3 PagedAttention

```
KV Cache 按页（Block）管理，像操作系统分页
  → 消除碎片，提高显存利用率
  → 支持前缀共享
```

| 方案 | 显存碎片 | 吞吐 |
|------|:--------:|:----:|
| 连续分配 | 高 | 低 |
| 分页管理 | 低 | 高 |

# 7. 采样与贪心

**结论先行**：贪心确定但呆板，采样多样但需调参，温度、Top-k、Top-p 共同控制随机性。

## 7.1 贪心解码

```python
# 贪心：每次取概率最大的
next_id = logits.argmax(-1)
```

确定性输出，适合事实问答、代码补全。

## 7.2 采样

```python
# 采样：按概率分布随机
next_id = torch.multinomial(softmax(logits), 1)
```

### 7.2.1 温度、Top-k、Top-p

| 策略 | 作用 |
|------|------|
| 温度 T | 缩放分布，T 小更确定 |
| Top-k | 只在概率最高的 k 个中采样 |
| Top-p | 在累积概率达 p 的最小集合中采样 |

```
温度：softmax(z / T)
  T→0 趋近贪心，T=1 原分布，T>1 更随机
```

> 详见 `2_sampling_strategies.md`。

## 7.3 Java 示例

```java
static int greedy(double[] logits) {
    int best = 0;
    for (int i = 1; i < logits.length; i++) {
        if (logits[i] > logits[best]) best = i;
    }
    return best;
}

static int sample(double[] logits, double temperature, java.util.Random rnd) {
    double[] p = softmax(logits, temperature);
    double r = rnd.nextDouble();
    double acc = 0.0;
    for (int i = 0; i < p.length; i++) {
        acc += p[i];
        if (r <= acc) return i;
    }
    return p.length - 1;
}
```

# 8. 停止条件与生成控制

**结论先行**：生成需明确停止条件，否则会浪费算力或截断输出；约束解码可强制格式。

## 8.1 停止条件

| 条件 | 说明 |
|------|------|
| 生成 <EOS> | 模型自然结束 |
| 达到 max_tokens | 硬性上限 |
| 命中停止序列 | 自定义停止词 |

```python
if next_id == EOS_ID or len(generated) >= max_tokens:
    break
if any(generated.endswith(s) for s in stop_sequences):
    break
```

## 8.2 约束解码

```
约束解码（Constrained Decoding）：
  在每步把不满足语法/格式的 token 概率置零
  → 保证输出是合法 JSON、SQL 等
```

## 8.3 边界

- 停止序列可能被模型"绕过"（如输出变体），需配合后处理。
- max_tokens 过小会截断答案，过大会浪费算力。

# 9. 数值与边界问题

**结论先行**：自回归生成存在数值溢出、重复退化与上下文溢出三类典型问题，需分别应对。

## 9.1 数值溢出

```
logits 过大时 exp 溢出
  → 用 max 减去后再 exp（数值稳定 softmax）
```

### 9.1.1 稳定 softmax

```
m = max(logits)
softmax(z_i) = exp(z_i - m) / Σ_j exp(z_j - m)
```

## 9.2 重复与退化

| 问题 | 现象 | 缓解 |
|------|------|------|
| 重复 | 反复输出同一句 | 重复惩罚、Top-p |
| 退化 | 陷入无意义循环 | 温度调整、n-gram 屏蔽 |

## 9.3 上下文长度

```
上下文窗口 = 输入长度 + 生成长度
  超限 → 截断或滑动窗口
```

| 方案 | 说明 |
|------|------|
| 截断 | 丢弃最早内容 |
| 滑动窗口 | 保留最近 N 个 token |
| 外推 | RoPE 插值等 |

# 10. 生产注意事项

**结论先行**：生产部署要在延迟、吞吐、质量、成本之间做权衡，并按请求特征分别优化。

## 10.1 性能

| 风险 | 建议 |
|------|------|
| TTFT 高 | 前缀缓存、加速 Prefill |
| TPS 低 | 连续批处理、量化 |
| GPU 利用率低 | 增大批次 |

## 10.2 质量

| 风险 | 建议 |
|------|------|
| 重复退化 | 调采样参数 |
| 格式不符 | 约束解码 |
| 截断 | 合理设置 max_tokens |

## 10.3 成本

```
成本 ≈ (Prefill 计算 + Decode 步数 × 单步访存) × 单价
优化：缓存前缀、批处理、量化权重
```

| 项 | 优化 |
|----|------|
| 显存 | 量化 KV Cache |
| 吞吐 | 动态批处理 |
| 延迟 | 投机解码（Speculative Decoding） |

# 11. 小结

## 11.1 核心结论

- 自回归生成：逐 token，把已生成内容作为下次输入。
- 两阶段：Prefill（并行、算力密集）+ Decode（串行、访存密集）。
- TTFT 受 Prefill 影响，TPS 受 Decode 影响，流式只改善体感。
- KV Cache 把单步复杂度从 O(L²) 降到 O(L)，用显存换时间。
- Decode 慢的根因是算术强度低、受显存带宽限制。

## 11.2 实践要点

- 批处理（尤其连续批处理）是提升吞吐的核心。
- 采样策略、停止条件与数值稳定共同决定输出质量。
- 理解两阶段是推理优化的基础。
