# 1. 优化目标与指标体系

推理优化（Inference Optimization）的目标可以概括为一句话：在给定硬件预算下，让单位成本产出尽可能多的有效 token。

```
降低成本、提升吞吐、降低延迟
```

## 1.1 三大目标

### 1.1.1 目标的含义

| 目标 | 含义 | 主要手段 |
|------|------|----------|
| 降低成本 | 单位 token 的算力/显存花费更低 | 量化、批处理、小模型 |
| 提升吞吐 | 单位时间处理的 token/请求更多 | 连续批处理、PagedAttention |
| 降低延迟 | 单个请求更快返回 | 投机解码、前缀缓存 |

### 1.1.2 目标之间的权衡

吞吐与延迟往往相互冲突：把批（batch）开大能提升吞吐，却会让单个请求排队更久。

```
吞吐
 │                    ╱ 大 batch
 │              ╱────╯
 │        ╱────╯
 │  ─────╯
 └──────────────────────▶ 延迟
       ↑
   小 batch 低延迟
```

### 1.1.3 不同场景的优先级

| 场景 | 首要目标 | 次要目标 |
|------|----------|----------|
| 在线聊天 | 低延迟 | 吞吐 |
| 离线批量生成 | 高吞吐 | 延迟 |
| 高并发 API 服务 | 吞吐 + 成本 | 尾延迟 |

## 1.2 关键指标

### 1.2.1 指标定义

| 指标 | 全称 | 含义 |
|------|------|------|
| TTFT | Time To First Token | 首 Token 延迟 |
| TPOT | Time Per Output Token | 每输出 Token 耗时 |
| TPS | Tokens Per Second | 每秒生成 Token |
| 吞吐 | Throughput | 每秒处理的请求数或 token 数 |
| 显存利用率 | GPU Memory Utilization | 显存被有效使用的比例 |

### 1.2.2 指标之间的关系

单请求延迟可以近似拆分为：

```
总延迟 ≈ TTFT + TPOT × 输出 token 数
```

系统吞吐受批大小约束：

```
吞吐 ≈ batch_size × (1 / TPOT)
```

### 1.2.3 指标采集的边界

- TTFT 受 Prefill 长度影响，长 prompt 会显著抬高首 token 延迟。
- TPOT 在批增大时上升，因为每一步要处理的序列变多。
- 只盯平均 TPS 会掩盖排队延迟，必须同时观察 P99。

## 1.3 成本估算直觉

设显卡时租为 C，单步耗时 T，批大小为 B，则单位 token 成本近似正比于：

```
cost_per_token ≈ C × T / (B × tokens_per_step)
```

由公式可见：**降成本的核心是提高 B（批大小）与 tokens_per_step**，这正是后文连续批处理与投机解码的价值所在。

# 2. 连续批处理

## 2.1 静态批处理的问题

### 2.1.1 静态批处理时序

```
静态批处理：等一批请求凑齐才处理，短请求等长请求

静态：
  [长请求1][长请求2][短请求3        ]  ← 短请求等长请求
```

### 2.1.2 长尾浪费

静态批（Static Batching）中，整批必须等最慢的请求完成。若批内序列长度方差大，短请求的算力被浪费在"等待"上。

```
浪费比例 ≈ (max_len - avg_len) / max_len
```

## 2.2 连续批处理原理

### 2.2.1 迭代级调度

连续批处理（Continuous Batching）在**每个 decode 迭代**后检查：已完成的序列立即退出，排队的请求立即补位。

```
连续：
  时间 →
  [请求1][请求2][请求3][请求4]...
  完成即退出，新请求立即补位
```

### 2.2.2 吞吐提升的数学直觉

设批内序列长度独立同分布，静态批需等最长序列：

```
静态步数 ≈ max(len_1, ..., len_B) ≈ B / (B + 1) × L_max
连续步数 ≈ 总 token 数 / B
```

长度方差越大，连续批处理收益越高，实测吞吐可提升数倍。

### 2.2.3 与 PagedAttention 的协同

连续批处理会让批内序列长度不断变化，KV Cache 必须能动态伸缩。PagedAttention 的分页机制正好满足这一需求，二者是配套技术。

> 连续批处理是 **vLLM 等框架的核心优化**，吞吐提升数倍。

## 2.3 Java 视角：调度队列

下面用 Java 伪代码示意调度循环的核心结构（不含真实推理调用）。

```java
class ContinuousBatchScheduler {
    private final Deque<Request> waiting = new ArrayDeque<>();
    private final List<RunningSeq> running = new ArrayList<>();
    private final int maxBatchSize;

    void step() {
        while (running.size() < maxBatchSize && !waiting.isEmpty()) {
            running.add(waiting.pollFirst().admit());
        }
        for (RunningSeq seq : running) {
            Token t = seq.decodeOneToken();
            seq.append(t);
        }
        running.removeIf(RunningSeq::isFinished);
    }
}
```

## 2.4 边界与反例

- 若所有请求长度几乎相同，连续批处理收益有限。
- 调度过于激进会让大请求频繁抢占，导致小请求饥饿。
- 每步都要重建批的张量，CPU 侧调度开销不可忽略，需要 CUDA Graph 配合。

# 3. PagedAttention 与显存管理

## 3.1 KV Cache 的显存碎片

### 3.1.1 连续内存分配的浪费

传统做法为每条序列预留 `max_model_len` 大小的连续 KV 空间，但实际序列往往远短于上限。

```
预留 max_len=2048，实际只用了 300：
[■■■□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□]
  已用                 浪费（不可复用）
```

### 3.1.2 内存浪费估算

| 浪费类型 | 来源 |
|----------|------|
| 内部碎片 | 预留长度 > 实际长度 |
| 外部碎片 | 分配释放导致空洞 |
| 预留碎片 | 为未来 token 预留但未用 |

## 3.2 分页机制

### 3.2.1 逻辑块与物理块映射

PagedAttention 借鉴操作系统虚拟内存：把 KV Cache 切成固定大小的**块（block）**，逻辑块按需映射到非连续物理块。

```
逻辑序列:   [B0][B1][B2]
              │   │   │
物理显存:  [B0] ... [B2] [B1] ...
             非连续，通过块表翻译
```

### 3.2.2 块表与地址翻译

每条序列维护一张块表（Block Table），第 i 个逻辑块指向物理块号。注意力计算时通过块表寻址，几乎无额外开销。

### 3.2.3 显存利用率提升

```
利用率 ≈ 已用 token 数 / 分配块覆盖的 token 数
```

由于按块分配，最坏浪费不超过一个块，利用率可从 20%~40% 提升到 90% 以上。

## 3.3 前缀共享

多个请求若共享同一前缀（系统提示、few-shot 示例），其逻辑块可指向同一物理块，采用写时复制（Copy-on-Write）避免污染。

```
请求A: [系统提示块][A 的对话块]
请求B: [系统提示块][B 的对话块]
            └── 共享同一物理块
```

> 详见 `3_kv_cache.md`。

## 3.4 生产注意事项

| 风险 | 建议 |
|------|------|
| 块大小设置不当 | 块太小翻译开销大，块太大碎片多 |
| 未开启前缀缓存 | 多轮对话/固定 system 场景务必开启 |
| 显存打满 OOM | 预留 `gpu_memory_utilization` 余量 |

# 4. 投机解码

## 4.1 基本思想

### 4.1.1 草稿-验证流程

```
用一个小模型（草稿模型）快速生成多个候选 token
用大模型一次性验证
→ 大模型一次前向可确认多个 token
```

```
草稿模型: 生成 [t1 t2 t3 t4]
大模型:   一次前向验证 → 接受 [t1 t2 t3]，拒绝 t4
结果:     一次前向生成 3 个 token（加速）
```

### 4.1.2 为什么能加速

Decode 阶段是**访存瓶颈（memory-bound）**：每步只生成一个 token，却要读取全部权重。投机解码把"多次单 token 前向"合并为"一次多 token 前向"，提高了算力利用率。

## 4.2 正确性保证

### 4.2.1 拒绝采样

设草稿分布为 q，目标分布为 p。对候选 token x 以概率 `min(1, p(x)/q(x))` 接受；若拒绝，则从残差分布采样。

```
接受概率 = min(1, p(x) / q(x))
```

### 4.2.2 输出分布不变

可以证明：上述接受-拒绝机制采样出的分布恰好等于 p，因此投机解码**不改变输出质量**，只加速计算。

## 4.3 常见变体

| 方法 | 草稿来源 | 特点 |
|------|----------|------|
| 草稿模型 | 独立小模型 | 通用，需额外显存 |
| Medusa | 多头预测 | 免独立模型 |
| EAGLE | 特征级自回归 | 接受率高 |
| Lookahead | Jacobi 迭代 | 无需草稿 |

## 4.4 加速比与边界

| 优点 | 缺点 |
|------|------|
| 提速 1.5~3x | 需要草稿模型 |
| 输出质量不变 | 草稿质量影响加速比 |

边界：当目标模型本身已高度并行、或批很大（算力已饱和）时，投机解码收益下降。

# 5. 前缀缓存

## 5.1 原理

### 5.1.1 复用公共前缀的 KV

```
多请求共享相同前缀：
  系统提示、few-shot 示例、长文档
  → 只计算一次 KV，多请求复用
```

### 5.1.2 哈希匹配

系统对 token 前缀做哈希，命中缓存即直接复用 KV 块，跳过 Prefill。

## 5.2 应用场景

| 场景 | 前缀 | 收益 |
|------|------|------|
| 多轮对话 | system + 历史 | TTFT 大幅下降 |
| RAG | 固定长文档 | 省去重复 prefill |
| Agent | 工具定义 | 每轮复用 |

```python
# vLLM 自动启用
llm = LLM(model="...", enable_prefix_caching=True)
```

## 5.3 Java 示例：提升命中率

保持前缀稳定可提升缓存命中率。

```java
String stablePrefix = SYSTEM_PROMPT + "\n" + TOOL_SCHEMA;
String prompt = stablePrefix + "\n" + userInput;  // 动态部分放最后
```

## 5.4 边界与反例

- 前缀中插入时间戳/随机 ID 会导致缓存全失效。
- 前缀顺序不同（哪怕内容相同）也无法命中。
- 缓存块需要回收策略，否则显存被历史前缀占满。

# 6. 并行策略

## 6.1 张量并行

### 6.1.1 切分方式

张量并行（Tensor Parallelism, TP）把单层权重按列/行切分到多卡，单请求跨多卡计算。

```
权重 W 按列切分：
卡0: W[:, :d]      卡1: W[:, d:]
        └── all-reduce 合并结果
```

### 6.1.2 通信开销

每层都需 all-reduce，卡间带宽成为瓶颈，通常限制在单机 8 卡内。

## 6.2 流水线并行

流水线并行（Pipeline Parallelism, PP）按层切分，不同卡负责不同层，形成流水。需要处理气泡（bubble）问题。

```
卡0: 层1-8   卡1: 层9-16   卡2: 层17-24
     └── micro-batch 依次流过 ──▶
```

## 6.3 数据并行与专家并行

| 策略 | 说明 |
|------|------|
| 张量并行 | 单请求跨多卡 |
| 流水线并行 | 跨多卡按层切 |
| 数据并行 | 多副本处理不同请求 |
| 专家并行 | MoE 专家分布到不同卡 |

## 6.4 策略选择

```
单请求延迟优先 → 张量并行
吞吐优先 → 数据并行（多副本）
超大模型放不下 → TP + PP + EP 组合
```

# 7. 其他关键优化技术

## 7.1 计算与访存优化

### 7.1.1 CUDA Graph

把一串 kernel 启动录制为图，一次提交，减少 CPU 启动开销，对 decode 小 batch 尤其有效。

### 7.1.2 算子融合

把 LayerNorm、残差、激活等合并为一个 kernel，减少显存读写往返。

### 7.1.3 FlashAttention

分块计算注意力，避免实例化完整注意力矩阵，降低显存占用并提升速度。

## 7.2 量化

| 精度 | 显存 | 质量 | 备注 |
|------|------|------|------|
| FP16 | 1x | 基准 | 默认 |
| INT8 | 0.5x | 略降 | 常用 |
| INT4 | 0.25x | 有损 | 需校准 |

量化降低权重与 KV 的显存与带宽需求，是降成本最直接的手段。

## 7.3 分块预填充

长 prompt 一次性 prefill 会阻塞其他请求。分块预填充（Chunked Prefill）把长 prompt 切成若干块，与其他请求的 decode 交错执行，降低 TTFT 抖动。

## 7.4 技术对比

| 技术 | 说明 | 主要收益 |
|------|------|----------|
| CUDA Graph | 减少 kernel 启动开销 | 降延迟 |
| 融合算子 | 合并计算减少访存 | 降延迟 |
| FlashAttention | 高效注意力 | 降显存/延迟 |
| 量化 | 降低显存与带宽 | 降成本 |
| 分块预填充 | 长 prompt 分块处理 | 降 TTFT 抖动 |

## 8.2 vLLM 使用示例

### 8.2.1 Python API

```python

from vllm import LLM, SamplingParams

llm = LLM(
    model="Qwen/Qwen2.5-7B-Instruct",
    tensor_parallel_size=2,              # 2 卡张量并行
    enable_prefix_caching=True,
    max_model_len=8192)

outputs = llm.generate(prompts, SamplingParams(temperature=0.7, max_tokens=512))
```

### 8.2.2 关键参数

| 参数 | 作用 |
|------|------|

# 9. 性能调优实践

## 9.1 指标驱动调优

| 目标 | 手段 |
|------|------|
| 降 TTFT | 分块预填充、前缀缓存 |
| 提 TPS | 投机解码、量化 |
| 提吞吐 | 连续批处理、PagedAttention |
| 省显存 | 量化、GQA、KV 量化 |
| 降成本 | 量化 + 批处理 + 小模型 |

## 9.2 显存估算

### 9.2.1 权重显存

```
权重显存 ≈ 参数量 × 每参数字节数
例：7B × 2 字节（FP16） ≈ 14 GB
```

### 9.2.2 KV Cache 显存

```
KV 显存 ≈ 2 × 层数 × 头数 × 头维 × 序列长 × 批大小 × 字节数
```

GQA（分组查询注意力）通过减少 KV 头数直接压缩该项。

## 9.3 调优流程

1. 建立基线：记录 TTFT、TPOT、吞吐、显存。
2. 定位瓶颈：访存受限还是算力受限。
3. 单项优化：一次只改一个变量。
4. 回归验证：确认质量与稳定性未退化。

# 10. 生产注意事项

## 10.1 常见风险

| 风险 | 建议 |
|------|------|
| 只优化单指标 | 综合吞吐与延迟 |
| 显存估算不足 | 预留 KV Cache 空间 |
| 批太大延迟高 | 平衡批大小 |
| 无监控 | 监控 TTFT/TPS/利用率 |
| 框架版本不兼容 | 锁定版本 |

## 10.2 监控指标

- 请求级：TTFT、TPOT、端到端延迟的 P50/P95/P99。
- 系统级：GPU 利用率、显存占用、批大小分布、缓存命中率。

## 10.3 反模式清单

- 为省显存把 `gpu_memory_utilization` 设到 0.99，导致 OOM。
- 动态前缀破坏前缀缓存，却未察觉命中率骤降。
- 盲目叠加优化，未做消融，无法归因收益。

# 11. 小结

## 11.1 核心结论

- 连续批处理与 PagedAttention 是吞吐优化的核心。
- 投机解码用草稿模型加速，且不改变输出分布。
- 前缀缓存复用公共前缀，显著降低 TTFT。

## 11.2 实践要点

- 并行策略决定大模型能否跨卡部署。
- vLLM 是当前主流的高吞吐推理框架。
- 优化要综合吞吐、延迟与显存，并用指标驱动。
