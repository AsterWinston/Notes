# 1. 什么是推理模型

**推理模型** = 在回答前先进行长链思考的模型（如 OpenAI o1、DeepSeek-R1）。

```
普通模型：
  问题 → 直接给答案

推理模型：
  问题 → [长时间思考：探索、验证、回溯] → 答案
```

> 核心思想：**用推理时的计算量换取质量**。

## 1.1 定义与直觉

### 1.1.1 与普通模型的对比

普通模型在单次前向中"顺口"给出答案；推理模型先产出一段显式的思考轨迹（reasoning trace），再给出结论。

| 维度 | 普通模型 | 推理模型 |
|------|----------|----------|
| 生成方式 | 直接回答 | 先思考再回答 |
| 输出长度 | 短 | 长（含思考） |
| 训练重点 | 指令跟随 | 推理能力 |
| 典型场景 | 闲聊、抽取 | 数学、代码、规划 |

### 1.1.2 核心思想的类比

可以把推理模型理解为"允许打草稿的考试"：

```
普通模型：口算，一次报答案
推理模型：发一张草稿纸，允许演算、验算、划掉重写
```

### 1.1.3 为什么有效

思考过程把复杂问题分解为多个中间步骤，每一步的局部计算都更简单，从而绕开了"一步到位"的误差累积。

## 1.2 代表模型

| 模型 | 发布方 | 特点 |
|------|--------|------|
| o1 / o3 | OpenAI | 闭源，隐藏思考过程 |
| DeepSeek-R1 | DeepSeek | 开源权重，公开推理路径 |
| QwQ | 阿里 | 开源推理模型 |
| Gemini Thinking | Google | 可配置思考预算 |

## 1.3 常见误解

- 误解一：推理模型"更聪明"。其实它在简单任务上可能更慢更差。
- 误解二：思考越长越好。超过必要长度会出现"过思考"（overthinking）。
- 误解三：思考内容一定可靠。思考过程可能自洽但结论仍错。

## 1.4 适用边界

| 判断维度 | 倾向普通模型 | 倾向推理模型 |
|----------|--------------|--------------|
| 答案唯一性 | 低 | 高 |
| 步骤数 | 1~2 步 | 多步 |
| 延迟容忍 | 低 | 高 |
| 可验证性 | 弱 | 强 |

# 2. 测试时计算

## 2.1 两种缩放范式

### 2.1.1 训练时缩放

```
传统缩放：增大训练规模 → 提升能力
```

通过增加参数、数据、算力提升模型能力，成本在训练阶段一次性投入。

### 2.1.2 测试时缩放

```
测试时缩放：增加推理时计算 → 提升质量

推理时计算包括：
- 更长的思维链
- 多次采样 + 投票
- 搜索与回溯
- 自我验证
```

### 2.1.3 缩放曲线对比

```
质量
 │                    ╱ 测试时缩放
 │              ╱────╯
 │        ╱────╯
 │  ─────╯  训练时缩放
 └──────────────────────▶ 计算量
```

两条曲线形状相似，但测试时缩放按需付费，更灵活。

## 2.2 测试时计算的形式

### 2.2.1 长思维链

模型自动生成更长的中间推理步骤，相当于在"潜在搜索空间"中走更多步。

### 2.2.2 多采样投票

对同一问题采样多个回答，取多数一致的结果（self-consistency）。

```
采样 N 次 → 得到答案 A、A、B、A、C
→ 众数 A 作为最终答案
```

### 2.2.3 搜索与回溯

在思考中显式尝试不同路径，遇到矛盾时回退重试，类似树搜索。

## 2.3 缩放上限

测试时计算并非越多越好：当采样次数或思考长度超过临界点，质量收益递减甚至反转。

```
质量
 │        ╱───── 饱和
 │    ╱──╯
 │  ╱
 └──────────────▶ 计算量
```

# 3. 思维链内化

## 3.1 从提示到内化

### 3.1.1 普通 CoT

```
普通 CoT：提示里写"一步步思考"
```

思维链（Chain-of-Thought, CoT）依赖提示词触发，模型并不总会自发思考。

### 3.1.2 推理模型的内化

```
推理模型：思维链已内化到训练中，无需提示

模型自动生成：
  <thinking>
  让我分析这个问题...
  第一步...
  等等，这里可能有问题...
  重新考虑...
  </thinking>
  最终答案：...
```

### 3.1.3 内化带来的变化

| 对比 | 普通 CoT | 内化 CoT |
|------|----------|----------|
| 触发方式 | 需要提示 | 自动触发 |
| 稳定性 | 不稳定 | 稳定 |
| 长度 | 短 | 长且自适应 |

## 3.2 思考格式与解析

### 3.2.1 thinking 段

推理模型的输出通常分为思考段与答案段，思考段常被特殊标记包裹（如 `thinking` 标签）。

### 3.2.2 最终答案抽取

```
原始输出:
  <thinking>...</thinking>
  最终答案：42

抽取结果: 42
```

解析时必须只取答案段，避免把思考中的中间数字误当结论。

### 3.2.3 解析的工程实现

```java
static String extractAnswer(String raw) {
    int end = raw.lastIndexOf("</thinking>");
    String tail = (end >= 0) ? raw.substring(end) : raw;
    int idx = tail.indexOf("最终答案：");
    return (idx >= 0) ? tail.substring(idx + 5).trim() : tail.trim();
}
```

## 3.3 思维链蒸馏

可以用推理模型生成的思考轨迹去微调小模型，把推理能力"蒸馏"到更小、更便宜的模型上。

```
大推理模型 → 生成大量 CoT 数据 → 微调小模型
```

# 4. 训练方法

## 4.1 三阶段流程

### 4.1.1 冷启动 SFT

```
① 冷启动 SFT
   用高质量长思维链数据微调
```

先让模型学会"像样地思考"的格式与风格。

### 4.1.2 强化学习

```
② 强化学习（RL）
   用可验证的奖励（数学题对错、代码测试通过）
   让模型学会"思考-验证-修正"
```

### 4.1.3 拒绝采样

```
③ 拒绝采样
   保留正确的推理路径，继续训练
```

把 RL 过程中被验证正确的轨迹回收，作为新的 SFT 数据，形成正循环。

## 4.2 GRPO 与组内相对优势

### 4.2.1 数学直觉

GRPO（Group Relative Policy Optimization）对同一问题采样一组回答，用组内均值作为基线计算优势：

```
advantage_i = (reward_i - mean(rewards)) / std(rewards)
```

无需额外训练价值网络（critic），显存更省。

### 4.2.2 Java 伪代码

```java
double[] rewards = group.stream().mapToDouble(r -> reward(problem, r)).toArray();
double mean = Arrays.stream(rewards).average().orElse(0);
double std = stddev(rewards);
for (int i = 0; i < group.size(); i++) {
    double adv = (rewards[i] - mean) / (std + 1e-8);
    updatePolicy(group.get(i), adv);
}
```

## 4.3 奖励设计

| 奖励类型 | 说明 | 可靠性 |
|----------|------|--------|
| 结果奖励 | 只看最终答案对错 | 高 |
| 格式奖励 | 是否遵守思考/答案格式 | 中 |
| 过程奖励 | 对中间步骤打分 | 低（难标注） |

# 5. 可验证奖励

## 5.1 适用与不适用

```
推理模型训练的关键：有客观的验证方式

适用：
  数学（答案唯一）
  代码（测试通过）
  逻辑题（答案唯一）

不适用：
  开放写作（无客观标准）
  主观判断
```

> 这也是为什么推理模型在**数学、代码**上提升最明显。

## 5.2 奖励函数设计

### 5.2.1 数学

```python
# 用可验证奖励做 RL（GRPO 等）
def reward(problem, response):
    # 数学题：答案是否正确
    answer = extract_answer(response)
    return 1.0 if answer == problem.expected else 0.0

# 对同一问题生成多个回答，用组内相对优势更新
```

### 5.2.2 代码

代码任务可执行单元测试，通过率即为奖励信号。

```
reward = passed_tests / total_tests
```

## 5.3 奖励劫持与边界

- 模型可能学会"绕过验证"而非真正推理，如猜测答案格式。
- 奖励函数有漏洞时会被利用（reward hacking）。
- 只有结果奖励时，正确路径与侥幸路径难以区分。

# 6. 思维链长度与预算

## 6.1 长度与质量的关系

```
推理模型会"思考"很久：
  简单问题：几百 token
  复杂问题：几千到几万 token

思考越长，通常质量越高（但有上限）
```

## 6.2 控制参数

| 参数 | 说明 |
|------|------|
| `reasoning_effort` | 思考投入程度（low/medium/high） |
| `max_thinking_tokens` | 思考长度上限 |

### 6.2.1 按需调节

简单任务调低 effort，复杂任务调高，是最直接的省钱手段。

### 6.2.2 硬上限的作用

设置 `max_thinking_tokens` 可防止单请求无限思考，保护尾延迟与成本。

## 6.3 过思考问题

当模型对简单问题反复验算，会产生大量无用 token，既费钱又无质量收益，需要路由与预算双管齐下。

```
过思考典型表现：
  已经得出正确答案
  → 仍继续"再检查一次"
  → 换一种方法重算
  → 反复否定又肯定
```

缓解手段包括：降低 `reasoning_effort`、设置 `max_thinking_tokens`、在系统提示中要求"确定后立即给出答案"。

# 7. 成本与延迟

## 7.1 成本构成

```
推理模型的代价：
- 输出 token 大幅增加（思考过程）
- 延迟显著增加（几秒到几分钟）
- 成本上升
```

思考 token 通常按输出 token 计费，这是成本上升的主因。

## 7.2 对比表

| 对比 | 普通模型 | 推理模型 |
|------|:--------:|:--------:|
| 延迟 | 1~5s | 10s~数分钟 |
| 输出 token | 几百 | 几千~几万 |
| 成本 | 1x | 5~20x |
| 复杂任务质量 | 中 | 高 |

> **不是所有任务都需要推理模型**，简单任务用普通模型更快更省。

## 7.3 延迟优化

- 流式输出思考过程，让用户感知进度。
- 缓存思考结果，相同问题直接复用。
- 对简单请求做前置路由，跳过推理模型。

# 8. 何时使用

## 8.1 适合与不适合

| 适合 | 不适合 |
|------|--------|
| 数学推理 | 简单问答 |
| 复杂代码 | 格式转换 |
| 逻辑难题 | 闲聊 |
| 多步规划 | 延迟敏感 |
| 需要验证的任务 | 简单抽取 |

## 8.2 路由策略

### 8.2.1 复杂度判断

可用轻量分类器或规则先判断任务复杂度，再决定是否走推理模型。

```
简单 → 普通模型
复杂 → 推理模型
```

### 8.2.2 Java 路由示例

```java
Model route(String query) {
    if (isSimple(query)) {
        return Model.FAST;      // 普通模型
    }
    return Model.REASONING;     // 推理模型
}
```

## 8.3 混合策略

对同一请求先由普通模型尝试，置信度低时再升级到推理模型，兼顾成本与质量。

# 9. 与其他技术结合

## 9.1 推理模型与工具

```
推理模型 + 工具：
  思考 → 调用工具验证 → 继续思考 → 答案
```

工具（计算器、代码执行、检索）为思考提供外部事实校验，减少幻觉。

## 9.2 推理模型与多采样

```
推理模型 + 多采样：
  生成多个思考路径 → 投票选最优
```

多路径投票在数学与逻辑题上进一步提升准确率，代价是算力翻倍。

## 9.3 推理模型与检索

先检索再推理（RAG + reasoning），让思考建立在真实证据之上，适合需要引用的复杂问答。

# 10. 生产注意事项

## 10.1 风险清单

| 风险 | 建议 |
|------|------|
| 所有任务都用 | 按复杂度路由 |
| 延迟不可接受 | 设置 thinking 上限 |
| 成本失控 | 预算 + 路由 |
| 思考过程泄露 | 过滤 thinking 部分 |
| 无监控 | 监控思考 token 占比 |

## 10.2 监控指标

- 思考 token 占比 = 思考 token / 总输出 token。
- 单请求成本与 P99 延迟。
- 路由命中率：多少请求真的需要推理模型。

## 10.3 反模式

- 把思考过程直接展示给终端用户（可能含敏感或混乱内容）。
- 未设上限导致个别请求耗尽预算。
- 用推理模型做格式化等机械任务。

# 11. 小结

## 11.1 核心结论

- 推理模型在回答前进行长链思考。
- 核心思想：用测试时计算换质量。
- 训练靠可验证奖励的强化学习（如 GRPO）。

## 11.2 实践要点

- 在数学、代码等可验证任务上提升最明显。
- 成本与延迟高，需按任务路由并设置思考预算。
