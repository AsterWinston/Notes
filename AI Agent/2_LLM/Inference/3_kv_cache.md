# 1. 为什么需要 KV Cache

结论先行：KV Cache（键值缓存）是自回归推理的必备优化，它把每个 token 的重复计算消除掉，使生成复杂度从 O(n²) 降到 O(n)。

## 1.1 自回归推理的重复计算

Transformer（变换器）解码时逐 token 生成，每一步都要对"已生成的全部前缀"做注意力。若不缓存，历史 token 的 Key、Value 投影会被反复重算。

### 1.1.1 无缓存的过程

```
无缓存：
  生成 t1: 计算 [x1] 的 K,V
  生成 t2: 计算 [x1,x2] 的 K,V     ← x1 重复计算
  生成 t3: 计算 [x1,x2,x3] 的 K,V  ← x1,x2 重复
```

第 t 步要算 t 个 token 的投影，累计代价是 1+2+...+n = O(n²)。

### 1.1.2 有缓存的过程

```
有缓存：
  生成 t1: 计算 x1 → 缓存 K1,V1
  生成 t2: 用 K1,V1 + 计算 x2 → 缓存 K2,V2
  生成 t3: 用 K1,K2,V1,V2 + 计算 x3
```

每一步只算新 token 的投影，历史直接从缓存读取，累计代价降为 O(n)。

### 1.1.3 Prefill 与 Decode 两个阶段

推理其实分两个阶段，KV Cache 的角色不同：

- Prefill（预填充）：一次性处理整段 prompt，并行计算所有 token 的 K、V 并写入缓存，是计算密集型。
- Decode（解码）：逐 token 生成，每步只算一个新 token 的 K、V 并追加，是显存带宽密集型。

```
Prefill: [x1 x2 x3 ... xn] --> 一次前向 --> 写入全部 KV
Decode : xn+1 -> 读缓存 + 算一个 KV -> 输出 -> xn+2 -> ...
```

理解这两个阶段，才能解释为什么长 prompt 首字延迟高、而后续每 token 延迟低。

## 1.2 复杂度分析

### 1.2.1 计算复杂度

| 阶段 | 无缓存 | 有缓存 |
|------|:------:|:------:|
| 单步投影量 | O(t) | O(1) |
| 总投影量 | O(n²) | O(n) |
| 注意力量 | O(n²) | O(n²) |

注意：缓存消除的是投影的重复，但每步仍需让新 token 与全部历史做注意力，这部分仍是 O(n²)。所以"降到 O(n)"针对的是投影计算，整体注意力仍随长度增长。

### 1.2.2 省下的计算量

以 n=4096 为例，无缓存时投影次数约为 n(n+1)/2 ≈ 840 万次 token 投影；有缓存后仅需 n = 4096 次，减少约 2000 倍。这正是开启缓存后生成速度数倍提升的原因。实际加速比受注意力和访存影响，不会达到理论值，但数量级上的收益非常确定。

### 1.2.3 显存换时间

KV Cache 本质是用显存换计算：缓存占用随序列长度线性增长，换来生成速度大幅提升。这也是长上下文推理显存吃紧的根源。

| 维度 | 无缓存 | 有缓存 |
|------|:------:|:------:|
| 生成速度 | 慢 | 快 |
| 显存占用 | 低 | 高（随长度线性） |
| 实现复杂度 | 低 | 中 |
| 长上下文可行性 | 差 | 依赖显存 |

## 1.3 适用边界

- 训练时通常不用 KV Cache（要并行处理整条序列）。
- 推理时几乎必开；除非序列极短、显存极度受限。
- 批量推理时缓存按请求独立计算，显存随并发线性增长。
- 单次分类/打分、极短序列可不开缓存；长文本生成必开。

# 2. Attention 与 KV 的关系

结论先行：注意力里 Q 只与"当前 token"有关，K、V 与"全部历史 token"有关，所以只需缓存 K、V。

## 2.1 注意力公式回顾

### 2.1.1 QKV 投影

每个 token 的隐状态 h 经三组权重投影得到查询 Q、键 K、值 V：

```
Q = h W_q
K = h W_k
V = h W_v
```

### 2.1.2 注意力计算

```
Attention(Q, K, V) = softmax(Q K^T / sqrt(d_k)) V
```

在解码第 t 步，Q 只有一行（当前 token），K、V 是全部 t 个 token 的堆叠。当前 token 的 Q 只与历史 K 做点积，历史的 K、V 一旦算好便可反复复用。

## 2.2 为什么只缓存 K、V

- Q 是"查询"，每一步只对当前 token 求一次，用完即弃，无需缓存。
- K、V 是"被查询的对象"，历史 token 的 K、V 在后续每一步都会被再次使用，因此必须缓存。

```
第 t 步:
  Q_t  = 当前 token 的查询        (1 x d)
  K_1..t = 历史键拼接            (t x d)  <- 缓存
  V_1..t = 历史值拼接            (t x d)  <- 缓存
```

## 2.3 边界与坑

- 位置编码（如 RoPE，旋转位置编码）需在缓存时正确处理，否则位置会错位。
- 缓存的是投影后的 K、V，不是原始隐状态。
- 多头注意力下每头独立缓存，头数直接决定缓存大小。

### 2.3.1 位置编码与缓存的关系

RoPE 在计算注意力前对 Q、K 施加与位置相关的旋转。缓存时通常存"已旋转"的 K，因此每个新 token 的位置索引必须正确递增，否则旋转角会错乱、输出退化。这是手写推理循环时最常见的坑之一。

# 3. 显存占用

结论先行：KV Cache 显存与层数、KV 头数、头维度、序列长度、批大小全部成正比，任何一项翻倍都会使缓存翻倍。

## 3.1 计算公式

```
KV Cache 显存 ≈ 2 × L × n_kv_heads × head_dim × seq_len × batch × bytes

2：K 和 V
L：层数
n_kv_heads：KV 头数
head_dim：每头维度
seq_len：序列长度
batch：批大小
bytes：精度字节数（FP16=2）
```

### 3.1.1 逐项解释

| 符号 | 含义 | 影响 |
|------|------|------|
| 2 | K 与 V 两份 | 固定系数 |
| L | 层数 | 线性 |
| n_kv_heads | KV 头数 | 线性，GQA 的关键 |
| head_dim | 头维度 | 线性 |
| seq_len | 序列长度 | 线性 |
| batch | 并发数 | 线性 |
| bytes | 精度 | FP16=2，INT8=1 |

### 3.1.2 单位换算

把公式结果除以 1024³ 得 GB，除以 1024² 得 MB。估算时先算单序列、再乘并发，便于定位瓶颈。

## 3.2 代码估算

```python
def kv_cache_size(num_layers, num_kv_heads, head_dim,
                  seq_len, batch, dtype_bytes=2):
    return (2 * num_layers * num_kv_heads * head_dim
            * seq_len * batch * dtype_bytes)

# 例：LLaMA-7B (32 层, 32 头, 128 head_dim)
size = kv_cache_size(32, 32, 128, 4096, 1)
# ≈ 2 GB（单个序列）
```

```java
static long kvCacheBytes(int layers, int kvHeads, int headDim,
                         int seqLen, int batch, int dtypeBytes) {
    long v = 2L * layers * kvHeads * headDim * seqLen * batch * dtypeBytes;
    return v;
}

// LLaMA-7B: 32 层, 32 KV 头, head_dim=128, 序列 4096, 批 1, FP16
long bytes = kvCacheBytes(32, 32, 128, 4096, 1, 2);   // ≈ 2 GiB
```

## 3.3 边界与坑

- 估算时容易漏掉 batch 维度，实际服务并发下缓存可能暴涨。
- 除权重外还有激活、临时张量占用，需预留余量（常按 1.2~1.5 倍）。
- 框架可能有额外对齐或分页开销。

# 4. 显存估算示例

结论先行：GQA（分组查询注意力）通过减少 KV 头数，把 KV Cache 缩小数倍，是长上下文落地的关键。

## 4.1 不同模型对比

| 模型 | 序列长度 | KV Cache（FP16） |
|------|:--------:|:----------------:|
| 7B (MHA) | 4K | ~2 GB |
| 7B (GQA 8:1) | 4K | ~0.25 GB |
| 70B (GQA 8:1) | 8K | ~2.5 GB |
| 70B (MHA) | 8K | ~20 GB |

## 4.2 GQA 的影响

MHA（多头注意力）下每个查询头都有独立的 KV 头；GQA 让多个查询头共享一组 KV 头，比例 8:1 即 KV 头数降为 1/8，缓存同步降为 1/8。MQA（多查询注意力）更极端，所有查询头共享一组 KV。

```
MHA:  Q Q Q Q Q Q Q Q
      | | | | | | | |
      K V K V K V K V   (每头独立)

GQA:  Q Q Q Q | Q Q Q Q
      K V     | K V        (4 查询头共享 1 组 KV)

MQA:  Q Q Q Q Q Q Q Q
      K V                (全部共享 1 组 KV)
```

## 4.3 生产建议

- 长上下文部署优先选 GQA/MQA 模型。
- 显存预算 = 权重 + KV Cache + 激活，三者都要算。
- 用实测峰值而非纸面估算配置实例。

### 4.3.1 显存预算分解

| 组成 | 7B FP16 | 说明 |
|------|:-------:|------|
| 权重 | ~14 GB | 参数量 × 2 字节 |
| KV Cache | ~2 GB | 4K 序列单并发 |
| 激活/临时 | ~1~2 GB | 随批大小变化 |
| 合计 | ~17~18 GB | 单并发估算 |

若并发 8，KV Cache 部分变成约 16 GB，总需求逼近 34 GB，24 GB 显卡就会 OOM——这正是批大小受限的原因。

# 5. 优化手段总览

结论先行：KV Cache 优化分"少存""存得省""管得好"三类，实际部署常组合使用。

## 5.1 分类

| 手段 | 效果 |
|------|------|
| GQA/MQA | 减少 KV 头数 |
| KV 量化 | FP16 → INT8，省一半 |
| PagedAttention | 分页管理，减少碎片 |
| 滑动窗口 | 限制缓存长度 |
| 共享前缀 | 多请求共享公共前缀 |

## 5.2 组合策略

```
显存不足
   |
   +--> 先看能否换 GQA/MQA 模型（结构性收益）
   +--> 再开 KV 量化（省一半）
   +--> 启用 PagedAttention（减少碎片、提吞吐）
   +--> 最后用滑动窗口/前缀共享兜底
```

## 5.3 各项优化细看

### 5.3.1 KV 量化

把缓存的 K、V 从 FP16 降到 INT8，显存减半，代价是精度轻微下降。可只量化 V 或只量化 K，视敏感度而定。

### 5.3.2 滑动窗口

只保留最近 W 个 token 的 KV，显存上界从 O(n) 变为 O(W)，代价是丢失超窗上下文。适合长对话、流式生成。

### 5.3.3 前缀共享

相同前缀只算一次 KV，多请求复用。对固定系统提示的 Agent 场景收益极大。

## 5.4 生产建议

- 优先结构性优化（模型架构），再做工程优化（量化、分页）。
- 各项优化可能相互影响（如量化 + 分页），需整体压测。

# 6. PagedAttention

结论先行：PagedAttention 借鉴操作系统虚拟内存，把 KV Cache 切成固定大小的页，按需分配，大幅减少碎片并支持共享。

## 6.1 问题背景

### 6.1.1 碎片化

传统实现要求每个序列的 KV Cache 占用一段连续显存。序列长度不定，预留与释放之间会产生大量外部碎片，显存利用率低。

### 6.1.2 预留浪费

为应对最长可能输出，系统常按上限预留空间，而实际用不满，造成内部浪费。

```
问题：KV Cache 需要连续显存，容易碎片化
```

## 6.2 分页机制

```
PagedAttention：
  把 KV Cache 分成固定大小的块（page）
  像操作系统虚拟内存一样管理
  → 减少碎片、支持共享、提升吞吐
```

```
传统： [====请求1的KV====][====请求2的KV====]  （预留连续空间）

Paged: [page1][page3][page2][page5][page4]     （非连续，按需分配）
```

逻辑上每个序列看到连续的页序列，物理上页可以散落各处，用一张页表映射。

```
逻辑页表（请求1）:  [0] -> 物理页 3
                    [1] -> 物理页 1
                    [2] -> 物理页 5

物理显存:  [页0][页1][页2][页3][页4][页5]
                   ^         ^         ^
                   请求1     请求1     请求1
```

当序列需要增长时，只需再分配一个物理页并追加到页表，无需拷贝已有内容，这是它抗碎片的关键。

> PagedAttention 是 **vLLM 的核心技术**。

## 6.3 边界与坑

- 页大小需要权衡：太小则页表开销大，太大则浪费。
- 分页带来额外的索引与拷贝开销，短序列收益有限。
- 与自定义算子、量化格式的兼容性需验证。

### 6.3.1 页大小权衡

| 页大小 | 页表开销 | 内部浪费 | 适用 |
|:------:|:--------:|:--------:|------|
| 小 | 高 | 低 | 变长、短序列 |
| 大 | 低 | 高 | 定长、长序列 |

典型页大小为 16 个 token。选型需结合实际序列长度分布压测。

## 6.4 生产建议

- 高并发服务默认启用 PagedAttention。
- 页大小按典型序列长度调优并压测。
- 结合前缀共享可进一步放大收益。

# 7. 前缀缓存

结论先行：多个请求若共享相同前缀（如系统提示），只需计算一次该前缀的 KV 并复用，可显著提升吞吐。

## 7.1 原理

```
多个请求共享相同前缀（如系统提示）：
  只计算一次前缀的 KV，多个请求复用
```

```
请求1: [系统提示][问题1]
请求2: [系统提示][问题2]
        └─ 共享 KV ─┘
```

> 显著提升有长系统提示场景的吞吐。

## 7.2 命中条件

- 前缀必须逐 token 完全一致（含空格、换行）。
- 前缀越长、复用越多，收益越大。
- 缓存通常按前缀哈希索引，需处理淘汰。

### 7.2.1 命中与未命中对比

```
未命中: 请求A 计算 [系统提示+问题A] 全部 KV   (慢)
        请求B 计算 [系统提示+问题B] 全部 KV   (慢)

命中:   请求A 计算 [系统提示] KV + [问题A] KV
        请求B 复用 [系统提示] KV + 算 [问题B] KV   (快)
```

系统提示越长，复用的 KV 越多，节省的 prefill 计算越可观。

## 7.3 生产建议

- 把稳定的系统提示放在最前，动态内容放后面，最大化命中。
- 注意前缀缓存与用户隐私：跨用户共享需谨慎。
- 监控命中率，命中率低说明前缀设计不合理。

# 8. 缓存淘汰与压缩

结论先行：序列超长时无法保留全部 KV，需按策略淘汰，主流有滑动窗口、Attention Sink 与 H2O。

## 8.1 滑动窗口

```
序列太长时，需要淘汰部分 KV：
  滑动窗口：只保留最近 N 个
```

只保留最近 N 个 token 的 KV，丢弃更早的。实现简单，但会丢失早期上下文，适合局部依赖强的任务。

```
窗口 W=4，当前序列长度 7：

  保留:              [t4][t5][t6][t7]
  丢弃: [t1][t2][t3]

  显存上界 = O(W)，与总长度无关
```

滑动窗口常与"窗口外再保留少量 sink"结合使用，以缓解开头信息丢失。

## 8.2 Attention Sink / StreamingLLM

```
  StreamingLLM：保留开头的 attention sink
```

观察发现，序列开头的少数 token 会吸收大量注意力（attention sink，注意力汇）。StreamingLLM 保留开头若干 sink token 加最近窗口，即可支持超长流式生成。

```
保留: [sink1 sink2][ ... 最近窗口 ... ]
丢弃:           [ 中间被淘汰的 KV ]
```

## 8.3 H2O

```
  H2O：保留"重要"的 KV
```

按累计注意力得分识别"重击者"（heavy hitter）KV，保留高分、淘汰低分，在受限预算下尽量保住信息量。

```
重要性得分 ≈ 累计注意力权重
保留 top-B 个 KV（B 为预算）
其余丢弃
```

实践中为支持后续 token 的稳定，通常仍固定保留最近窗口与 sink token。

## 8.4 对比与建议

| 方法 | 说明 |
|------|------|
| 滑动窗口 | 简单，丢弃最旧 |
| Attention Sink | 保留开头几个 token |
| H2O | 按重要性保留 |

- 边界与坑：淘汰会损失长距离依赖，需按任务验证质量。
- 生产建议：优先滑动窗口 + sink 组合，复杂任务再上 H2O。

### 8.4.1 预算分配示意

```
总预算 B 个 KV 槽位：

  [ sink(4) ][ 重要 KV(按分保留) ][ 最近窗口 W ]
     固定          动态              固定
```

固定保留 sink 与最近窗口保证稳定性，剩余预算按重要性填充历史 KV，是当前较稳妥的工程方案。

# 9. 代码实践

结论先行：现代推理框架自动管理 KV Cache，理解手动流程有助于排查问题。

## 9.1 手动管理

```python
# 手动管理 KV Cache
past_kv = None
for step in range(max_tokens):
    logits, past_kv = model(
        input_ids[:, -1:],           # 只传新 token
        past_key_values=past_kv,      # 传入缓存
        use_cache=True)
    next_id = sample(logits)
    input_ids = torch.cat([input_ids, next_id], dim=-1)
```

```java
// 伪代码：缓存的逻辑结构
class KVCache {
    double[][][] keys;    // [layer][seq][head_dim]
    double[][][] values;
    int filled;           // 已填充长度

    void append(int layer, double[] k, double[] v) {
        keys[layer][filled] = k;
        values[layer][filled] = v;
        // filled 在最后一层更新
    }
}
```

> 现代推理框架自动管理，无需手动处理。

## 9.2 框架自动管理

- HuggingFace `use_cache=True` 自动返回并接收 `past_key_values`。
- vLLM 通过 PagedAttention 在底层统一管理。
- 注意首次 prefill（预填充）与后续 decode（解码）阶段的差异。

### 9.2.1 两阶段代码差异

```python
# Prefill：整段 prompt 一次前向，建立缓存
out = model(prompt_ids, use_cache=True)
past = out.past_key_values          # 缓存已就绪
next_id = sample(out.logits[:, -1:])

# Decode：每步只喂一个 token
while not done:
    out = model(next_id, past_key_values=past, use_cache=True)
    past = out.past_key_values
    next_id = sample(out.logits[:, -1:])
```

Prefill 是计算密集，Decode 是访存密集；优化手段（如连续批处理）主要针对 Decode 阶段的吞吐。

## 9.3 生产注意事项

| 风险 | 建议 |
|------|------|
| 长上下文 OOM | GQA + 量化 + 滑动窗口 |

# 10. 小结

## 10.1 核心结论

- KV Cache 缓存历史 K、V，避免重复计算。
- 显存占用随层数、头数、序列长度、批大小线性增长。
- GQA/MQA 大幅降低 KV Cache。

## 10.2 工程实践

- PagedAttention 用分页管理减少碎片、支持共享。
- 前缀缓存与滑动窗口是常用优化。
- 长上下文的核心矛盾是显存，需架构与工程双管齐下。
