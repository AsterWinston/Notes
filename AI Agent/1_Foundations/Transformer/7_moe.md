# 1. 核心思想

**结论先行**：混合专家（Mixture of Experts，MoE）用多个"专家"子网络替代单个前馈层，每个 Token 只被路由到其中少数几个专家。这样做的结果是**参数量可以远大于激活参数量**，从而在有限计算预算下扩大模型容量。

## 1.1 MoE 是什么

**MoE（Mixture of Experts）** = 用多个"专家"子网络，每次只激活其中几个。

```
标准 FFN：
  每个 token 都经过同一个 FFN（全部参数参与）

MoE FFN：
  每个 token 只经过 top-k 个专家
  参数量大，但激活参数少
```

**原理**：MoE 把原前馈网络（FFN）拆成 N 个并行的专家，再加一个路由器（Router）为每个 Token 选择 top-k 个专家，最后按权重把它们的输出加权求和。

### 1.1.1 专家是什么

**原理**：专家本身通常就是一个普通 FFN（或 SwiGLU 前馈块），结构完全相同，只是参数各自独立。所谓"专家"并不预先指定领域，而是在训练中自行分化。

### 1.1.2 稀疏性从何而来

```
稠密：每个 token 激活全部 N 个专家
稀疏：每个 token 只激活 top-k 个（k ≪ N）
```

## 1.2 整体结构图

```
            输入 token
                │
         ┌──────┴──────┐
         ▼             ▼
     路由器 Router（决定选哪些专家）
         │
    ┌────┼────┬────┬────┐
    ▼    ▼    ▼    ▼    ▼
  专家1 专家2 专家3 ... 专家N
    │         │
    └────┬────┘
         ▼
      加权求和
```

## 1.3 与稠密 FFN 的对比

| 项目 | 稠密 FFN | MoE FFN |
|------|----------|---------|
| 每个 Token | 全部参数 | top-k 专家 |
| 参数量 | = 激活量 | ≫ 激活量 |
| 计算量 | 固定 | 固定（由 k 决定） |
| 容量 | 受计算限制 | 可独立扩大 |
| 实现复杂度 | 低 | 高 |

**边界与坑**：MoE 只稀疏化前馈层，注意力层通常仍是稠密的；因此 MoE 的显存收益主要体现在前馈参数上，注意力部分的 KV Cache 并不因此减少。

**要点**：

- MoE 用多个专家替代单个 FFN。
- 每个 Token 只激活 top-k 个专家。
- 参数量与激活量解耦，容量可独立扩大。

# 2. 为什么有效

**结论先行**：MoE 的核心价值是"容量与计算解耦"：模型可以拥有海量参数（大容量），而每个 Token 只支付少量计算（低成本）。

## 2.1 容量与计算解耦

```
传统模型：参数量 = 激活参数量
MoE：    参数量 >> 激活参数量

例：8 个专家，top-2 激活
  总参数：8 × FFN 参数
  激活参数：2 × FFN 参数
  → 用 1/4 的计算量获得 4 倍的容量
```

> **在相同计算预算下，MoE 能显著扩大模型容量。**

**原理**：稠密模型若要扩大容量，必须同步扩大计算量；MoE 把"存了多少参数"与"用了多少参数"分开，从而打破这一绑定。

### 2.1.1 一个数量级直觉

```
稠密 7B：每 token 用 7B 参数
MoE 47B（激活 13B）：每 token 只用 13B 参数
  → 容量接近 47B，成本接近 13B
```

## 2.2 条件计算视角

**原理**：MoE 属于条件计算（Conditional Computation）：网络根据输入动态选择子网络，不同 Token 走不同路径，相当于在共享主干上挂载了许多可选的专用模块。

### 2.2.1 专家分化

**原理**：训练中不同专家会自然承担不同模式（如语法、事实、多语言），形成分工；这并非人为指派，而是路由与梯度共同作用的结果。

## 2.3 与集成学习的区别

| 项目 | 集成学习 | MoE |
|------|----------|-----|
| 参与推理 | 全部模型 | 少数专家 |
| 输出 | 平均/投票 | 加权求和 |
| 训练 | 可独立 | 端到端联合 |

**边界与坑**：MoE 并非"免费的容量"：总参数决定显存占用，专家越多显存压力越大；同时路由与负载均衡会引入训练难度。

**要点**：

- 容量与计算解耦是 MoE 的核心。
- 属于条件计算，按输入选择子网络。
- 与集成学习不同，推理只用少数专家。

# 3. 路由器

**结论先行**：路由器（Router）是一个小型线性层，为每个 Token 计算对各专家的偏好概率，再取 top-k 并归一化，最后据此加权聚合专家输出。

## 3.1 路由计算

```
Router 计算每个 token 对各专家的概率：
  logits = x · W_router
  probs = softmax(logits)
  选择 top-k 个专家
  加权求和输出
```

**公式**：

```
g = softmax(W_r · x)
top-k 索引 I = argtopk(g, k)
权重 w_i = g_i / Σ_{j∈I} g_j
y = Σ_{i∈I} w_i · Expert_i(x)
```

**原理**：softmax 把 logits 变成概率分布，top-k 选出最相关的专家，再在选中的专家上重新归一化，保证权重和为 1。

### 3.1.1 为什么重新归一化

**原理**：top-k 截断后原始概率之和小于 1，若不重新归一化，输出尺度会随被选专家的概率大小波动，重新归一化可稳定输出尺度。

### 3.1.2 top-1 与 top-k

```
top-1：每 token 只走一个专家，最省计算
top-2：每 token 走两个专家，质量更好
top-k：k 越大质量越高，计算越多
```

## 3.2 代码实现

```python
class MoELayer(nn.Module):
    def __init__(self, d_model, num_experts, top_k):
        super().__init__()
        self.num_experts = num_experts
        self.top_k = top_k
        self.router = nn.Linear(d_model, num_experts, bias=False)
        self.experts = nn.ModuleList([
            FeedForward(d_model) for _ in range(num_experts)])

    def forward(self, x):
        # ① 路由
        logits = self.router(x)
        probs = F.softmax(logits, dim=-1)
        top_probs, top_indices = probs.topk(self.top_k, dim=-1)

        # ② 归一化权重
        top_probs = top_probs / top_probs.sum(dim=-1, keepdim=True)

        # ③ 加权聚合专家输出
        output = torch.zeros_like(x)
        for k in range(self.top_k):
            idx = top_indices[..., k]
            for e in range(self.num_experts):
                mask = (idx == e)
                if mask.any():
                    output[mask] += top_probs[mask, k:k+1] * self.experts[e](x[mask])
        return output
```

## 3.3 路由的挑战

**原理**：路由是离散的 top-k 选择，本身不可微，实践中依赖"概率加权"这一可微近似回传梯度；这带来路由不稳定、专家坍塌等训练问题。

### 3.3.1 可微性问题

```
top-k 选择：离散、不可导
解决办法：用被选专家的 softmax 概率作为权重
  → 权重可导，梯度可回传
```

### 3.3.2 专家坍塌

**边界与坑**：若路由器过早偏好少数专家，其余专家得不到梯度，会形成"强者愈强"的坍塌，最终只有少数专家有效，容量优势荡然无存。

**要点**：

- 路由器是小型线性层，输出专家概率。
- top-k 后需重新归一化权重。
- 路由不可微，靠概率加权近似。
- 需警惕专家坍塌。

# 4. 负载均衡

**结论先行**：负载均衡（Load Balancing）通过辅助损失等手段，鼓励 Token 均匀分配到各专家，避免少数专家过载、其余专家闲置。

## 4.1 问题来源

```
问题：路由器可能偏好少数专家 → 其他专家训练不足

对策：负载均衡损失（Load Balancing Loss）
  鼓励 token 均匀分配到各专家
```

**原理**：路由目标是"选最合适的专家"，天然会导致选择集中；而系统效率要求"各专家负载相当"。两者冲突，需要用辅助损失把负载往均匀方向推。

## 4.2 负载均衡损失

```python
def load_balancing_loss(router_probs, expert_indices, num_experts):
    # 每个专家被选中的比例
    tokens_per_expert = F.one_hot(expert_indices, num_experts).float().mean(0)
    # 每个专家的平均路由概率
    router_prob_per_expert = router_probs.mean(0)
    # 两者点积（越均匀越小）
    return num_experts * (tokens_per_expert * router_prob_per_expert).sum()
```

**公式**：

```
L_balance = N · Σ_i (f_i · p_i)
f_i = 分配给专家 i 的 token 比例
p_i = 专家 i 的平均路由概率
```

**原理**：f_i 与 p_i 的点积在分布均匀时取最小值，因此最小化该项即推动负载均匀；乘 N 使完全均匀时损失为 1，便于跨配置比较。

### 4.2.1 为什么同时用 f 与 p

**原理**：f 基于硬选择、不可导，p 基于 softmax、可导；把二者相乘，既利用可导的 p 回传梯度，又用 f 反映真实负载。

### 4.2.2 损失权重

**边界与坑**：均衡损失权重过大，会压过语言建模损失，损害质量；过小则起不到均衡作用，通常取一个较小的系数（如 0.01 量级）并通过实验调节。

## 4.3 其他对策

| 问题 | 对策 |
|------|------|
| 专家负载不均 | 负载均衡损失 |
| 部分专家不训练 | 容量因子、强制均衡 |
| 路由不稳定 | 噪声路由（训练时加噪声） |

### 4.3.1 噪声路由

**原理**：训练时在路由 logits 上加入高斯噪声，使探索更充分，避免早期就锁定少数专家，属于一种随机探索机制。

## 4.4 容量因子

**原理**：容量因子（Capacity Factor）限制每个专家最多接收的 Token 数；超出容量的 Token 会被丢弃（直接走残差）。它把负载硬性截断，保证显存与计算可预测，但可能丢信息。

```
容量 = 容量因子 × (总 token 数 / 专家数)

容量因子 = 1.0：严格均分，丢弃多
容量因子 = 1.25：留有余量，丢弃少
```

**要点**：

- 负载均衡用辅助损失鼓励均匀分配。
- 均衡损失由硬比例 f 与软概率 p 构成。
- 噪声路由帮助探索，容量因子限制过载。
- 均衡与质量需权衡。

# 5. 常见 MoE 架构

**结论先行**：从 Switch Transformer 的 top-1 到 Mixtral 的 top-2，再到 DeepSeek-MoE 的细粒度与共享专家，MoE 架构沿"更细、更省、更稳"方向演进。

## 5.1 架构对比

| 模型 | 专家数 | 激活 | 特点 |
|------|:------:|:----:|------|
| Switch Transformer | 多 | top-1 | 最早的大规模 MoE |
| Mixtral 8x7B | 8 | top-2 | 开源代表 |
| DeepSeek-MoE | 多 | top-k | 细粒度专家 |
| Qwen-MoE | 多 | top-k | 中文友好 |

## 5.2 代表模型要点

### 5.2.1 Switch Transformer

**原理**：把 top-k 简化为 top-1，每 Token 只走一个专家，路由与计算最简；配合容量因子与均衡损失，证明 MoE 可扩展到超大参数。

### 5.2.2 Mixtral 8x7B

**原理**：每层 8 个专家、top-2 激活，总参数约 47B、激活约 13B，是开源社区广泛使用的稀疏模型，质量接近更大稠密模型而推理更省。

### 5.2.3 DeepSeek-MoE

**原理**：采用更细粒度的专家切分，并引入共享专家（Shared Expert）承担通用知识，让路由专家专注差异化知识，减少专家间冗余。

## 5.3 共享专家与细粒度

| 设计 | 目的 |
|------|------|
| 共享专家 | 承载通用知识，减少冗余 |
| 细粒度专家 | 切得更小，组合更灵活 |
| 分组路由 | 组内竞争，稳定负载 |

### 5.3.1 细粒度为何更优

**原理**：专家越小、数量越多，可能的组合数呈指数增长，模型能更精细地匹配不同 Token；代价是路由与调度的开销上升。

**边界与坑**：细粒度与共享专家都增加实现复杂度；不同模型的专家数、激活数、是否共享差异很大，横向比较参数时需区分"总参数"与"激活参数"。

**要点**：

- Switch 用 top-1 开创大规模 MoE。
- Mixtral 8x7B 是开源代表。
- DeepSeek-MoE 引入细粒度与共享专家。

# 6. 参数与成本

**结论先行**：MoE 的推理计算成本由激活参数决定，显存需求由总参数决定，能力上限由总参数决定；因此 MoE 本质上是"用显存换计算效率"。

## 6.1 参数构成

```
MoE 模型：
  总参数 = 专家数 × 单专家参数 + 共享参数
  激活参数 = top-k × 单专家参数 + 共享参数

推理成本取决于"激活参数"，而非总参数
显存需求取决于"总参数"
```

**公式**：

```
总参数   ≈ N × P_expert + P_shared
激活参数 ≈ k × P_expert + P_shared
```

## 6.2 成本归属

| 指标 | 取决于 |
|------|--------|
| 计算成本 | 激活参数 |
| 显存需求 | 总参数 |
| 能力上限 | 总参数 |

> MoE 的权衡：**用显存换计算效率**。

### 6.2.1 举例说明

```
8 专家、top-2、单专家 P：
  总参数   = 8P
  激活参数 = 2P
  → 显存按 8P 准备，计算按 2P 支付
```

## 6.3 训练与推理的差异

**原理**：训练时所有专家都会收到梯度（因为不同 Token 路由到不同专家），因此训练计算量接近"激活参数 × 数据量"；但显存仍需容纳全部专家参数与优化器状态。

### 6.3.1 分布式通信

**边界与坑**：分布式训练时专家分散在不同设备上，Token 需通过 All-to-All 通信发送到目标专家再取回，通信量随专家并行度上升，可能成为瓶颈。

**要点**：

- 总参数决定显存，激活参数决定计算。
- MoE 用显存换计算效率。
- 训练显存需容纳全部专家。
- 分布式下 All-to-All 是主要开销。

# 7. 优势与挑战

**结论先行**：MoE 以更高容量、更高计算效率见长，但代价是显存占用、路由稳定性与工程复杂度。

## 7.1 优势

| 优势 | 说明 |
|------|------|
| 计算效率高 | 同等计算下容量更大 |
| 容量大 | 总参数可远超稠密模型 |
| 可扩展 | 增专家即增容量 |
| 训练快 | 每 Token 计算量小 |
| 推理快 | 同等能力下更省算力 |

## 7.2 挑战

| 挑战 | 说明 |
|------|------|
| 显存占用大 | 需常驻全部专家参数 |
| 路由不稳定 | 离散选择难训练 |
| 负载均衡难 | 易发生专家坍塌 |
| 通信开销大 | 分布式需 All-to-All |
| 部署复杂 | 路由与调度工程量大 |

### 7.2.1 显存与计算的不对称

**原理**：MoE 的显存按总参数算、计算按激活参数算，导致"省算力但不省显存"，这在显存受限的单卡场景反而是劣势。

### 7.2.2 微调与部署

**边界与坑**：MoE 微调时若数据分布单一，可能只更新少数专家，破坏原有分工；部署时需专门的路由与批处理策略才能兑现效率优势。

**要点**：

- 优势在容量与计算效率。
- 挑战在显存、路由与工程复杂度。
- 显存与计算不对称是关键特征。

# 8. 稀疏激活

**结论先行**：稀疏激活（Sparse Activation）是 MoE 的本质特征：前向时只有部分参数参与计算，稀疏度即激活参数与总参数之比。

## 8.1 稀疏度定义

```
稠密模型：所有参数都参与计算
MoE：      只激活部分参数（稀疏）

稀疏度 = 激活参数 / 总参数
```

**原理**：稀疏度越小，说明用越少的计算撬动越多的参数，容量与效率的杠杆越大。

## 8.2 稀疏度对比

| 模型 | 稀疏度 |
|------|:------:|
| Mixtral 8x7B | 约 1/4 |
| DeepSeek-V3 | 约 1/20 |

### 8.2.1 稀疏度的上限

**边界与坑**：稀疏度并非越小越好，过度稀疏会让单个专家见过的样本不足，训练不充分；同时路由难度与负载不均风险上升。

## 8.3 训练与推理的稀疏性

| 阶段 | 稀疏表现 |
|------|----------|
| 训练 | 前向稀疏，反向只更新被选专家 |
| 推理 | 每 Token 只算 top-k 专家 |

**原理**：训练时虽只更新被选专家，但不同 Token 会覆盖不同专家，长期看所有专家都能获得梯度；推理时则严格按 top-k 计算。

**要点**：

- 稀疏度 = 激活参数 / 总参数。
- 越稀疏杠杆越大，但训练难度越高。
- 训练与前向均稀疏，梯度覆盖靠路由分布。

# 9. 常见误区

**结论先行**：关于 MoE 的误解多集中在"参数即成本""专家即领域"与"MoE 一定更快"上。

## 9.1 关于参数与成本

| 误区 | 澄清 |
|------|------|
| 总参数大所以很慢 | 计算只看激活参数 |
| MoE 一定省显存 | 显存按总参数算，通常更费 |
| 稀疏度越小越好 | 过度稀疏训练不充分 |

## 9.2 关于专家与路由

| 误区 | 澄清 |
|------|------|
| 每个专家对应一个领域 | 专家分工是训练自发形成的 |
| 路由总能选对专家 | 需均衡损失与噪声稳定 |
| MoE 无需额外训练技巧 | 均衡、容量、通信都需调 |

**边界与坑**：不同实现中"专家参数"是否包含共享层、路由器参数是否计入总参数，口径不一；比较模型规模时应明确统计范围。

**要点**：

- 计算看激活参数，显存看总参数。
- 专家分工是涌现的，非人工指派。
- MoE 需要一整套训练与部署技巧。

# 10. 小结

**结论先行**：MoE 通过路由器与多个专家实现稀疏激活，在相同计算预算下扩大模型容量，代价是显存、路由稳定性与工程复杂度。

## 10.1 核心要点

- MoE 用多个专家 + 路由器，每次只激活部分。
- 相同计算预算下可显著扩大模型容量。
- 路由器决定选哪些专家，需负载均衡。
- 推理成本看激活参数，显存看总参数。
- Mixtral、DeepSeek-MoE、Qwen-MoE 是代表。

## 10.2 记忆口诀

```
专家多而激活少，容量计算解耦了
路由 top-k 选专家，权重要做归一化
负载均衡防坍塌，容量因子控过载
计算看激活，显存看总量
```

**要点**：

- 一个本质：稀疏激活、容量与计算解耦。
- 一个关键：路由与负载均衡。
- 一组权衡：算力、显存、复杂度。
