# 1. 为什么需要分词

**结论先行**：神经网络只能处理数字，分词（Tokenization）是"文本 → token → ID"的桥梁，它决定了模型的输入形式、成本与上下文占用。

## 1.1 模型输入的本质

### 1.1.1 文本到 ID 的映射

```
模型只能处理数字，不能直接处理文本
分词 = 把文本切成 token，再映射为 ID
```

```
"我爱北京" → ["我", "爱", "北京"] → [1234, 5678, 9012]
```

整个过程分两步：

```
文本 --(分词器切分)--> token 序列 --(查词表)--> ID 序列 --> Embedding --> 模型
```

**要点**：分词是把连续符号离散化并与模型参数对齐的过程。

## 1.2 分词的目标

分词要在覆盖率（任意文本都能切分）、序列长度（越短越省）、语义完整性（token 尽量有意义）三者间平衡：

```
理想分词 = 常见词整体成 token + 罕见词拆成子词
```

**要点**：分词是"覆盖率、长度、语义"三者权衡的结果。

# 2. 三种粒度

**结论先行**：分词有字符级、词级、子词级三种粒度，现代 LLM 几乎都用子词级。

## 2.1 字符级

### 2.1.1 特点

```
每个字符一个 token
"我爱北京" → ["我","爱","北","京"]
```

### 2.1.2 优缺点

| 方面 | 说明 |
|------|------|
| 优点 | 词表极小、无未登录词、参数少 |
| 缺点 | 序列长、语义单位被打碎、模型难学长依赖 |

**边界与坑**：字符级对中文尚可，对英文会把单词切得很碎，序列显著变长。

## 2.2 词级

### 2.2.1 特点

```
每个词一个 token
"我爱北京" → ["我","爱","北京"]
```

### 2.2.2 优缺点

| 方面 | 说明 |
|------|------|
| 优点 | 序列短、语义完整 |
| 缺点 | 词表巨大、未登录词多、无法泛化 |

**边界与坑**：词级分词需要预先知道词边界，中文还需额外分词器。

## 2.3 子词级

### 2.3.1 特点

```
介于字符与词之间
"playing" → ["play", "ing"]
"我爱北京" → ["我","爱","北京"]
```

### 2.3.2 为什么胜出

| 优势 | 说明 |
|------|------|
| 词表可控 | 几千到几十万 |
| 无未登录词 | 罕见词由子词拼出 |
| 语义与长度平衡 | 常见词整体、罕见词拆分 |
| 跨语言 | 多语言共享子词 |

## 2.4 粒度对比

| 粒度 | 说明 | 词表 | 例子 |
|------|------|:----:|------|
| 字符级 | 每个字一个 token | 小 | ["我","爱","北","京"] |
| 词级 | 每个词一个 token | 大 | ["我","爱","北京"] |
| 子词级 | 介于两者之间 | 中 | ["我","爱","北京"] |

> 现代 LLM 几乎都用**子词级**。

# 3. 子词算法

**结论先行**：子词算法通过统计规律从数据中自动学习词表，主流有 BPE、WordPiece、SentencePiece、Unigram 及 Byte-level BPE。

## 3.1 BPE（Byte Pair Encoding）

### 3.1.1 算法流程

```
① 初始：每个字符一个 token
② 统计：找最频繁的相邻对
③ 合并：把该对合并为新 token
④ 重复直到达到词表大小
```

```
初始: l o w e r
合并: lo w e r → low e r → lower
```

### 3.1.2 训练与编码

```
训练：反复找最高频相邻对并合并，记录合并顺序
编码：按合并顺序对新词做贪心合并
解码：把 token 序列直接拼接还原文本
```

**用于**：GPT 系列、LLaMA。

## 3.2 WordPiece

### 3.2.1 与 BPE 的差异

```
类似 BPE，但用似然度（而非频率）选择合并
```

```
合并评分： score(a,b) = freq(ab) / (freq(a) · freq(b))
```

即优先合并"一起出现概率远高于独立出现"的对。

**用于**：BERT。

## 3.3 SentencePiece

### 3.3.1 设计动机

```
直接在原始文本上训练，不依赖预分词
支持多语言，无需空格分词
```

传统分词器需要先按空格预分词，对中日韩（无空格语言）不友好；SentencePiece 把空格也当普通字符处理。

### 3.3.2 两种模式

| 模式 | 说明 |
|------|------|
| BPE 模式 | 基于合并 |
| Unigram 模式 | 基于概率删减 |

```
空格用 "_" 表示：
"Hello world" → ["▁Hello", "▁world"]
```

**用于**：T5、LLaMA、Qwen。

## 3.4 Unigram

### 3.4.1 算法

```
从大词表开始，逐步删除影响小的 token
```

```
① 初始化一个很大的候选词表
② 用当前词表计算语料的似然
③ 删除使似然下降最小的 token
④ 重复直到达到目标词表大小
```

**用于**：部分多语言模型。

## 3.5 算法对比表

| 算法 | 方向 | 选择依据 | 代表模型 |
|------|------|----------|----------|
| BPE | 合并 | 频率 | GPT、LLaMA |
| WordPiece | 合并 | 似然 | BERT |
| Unigram | 删减 | 似然 | 多语言模型 |
| SentencePiece | 两者皆可 | - | T5、Qwen |
| Byte-level BPE | 合并 | 字节频率 | GPT-2/3/4 |

**要点**：算法差异在"合并依据"与"是否依赖预分词"，工程上更关心与模型的匹配。

# 4. 中文分词的特殊性

**结论先行**：中文没有天然词边界，传统分词依赖词典与统计，而现代 LLM 多按字符或子词处理，Token 数约等于字数。

## 4.1 无空格分词问题

### 4.1.1 分词歧义

```
中文没有空格分隔：
  "我爱北京天安门"

字符级：我/爱/北/京/天/安/门（7 个 token）
词级：  我/爱/北京/天安门（4 个 token）
```

```
歧义示例：
  "研究生命起源" → 研究/生命/起源 或 研究生/命/起源
  "南京市长江大桥" → 南京市/长江大桥 或 南京/市长/江大桥
```

### 4.1.2 未登录词

人名、地名、新词、专业术语常常不在词典中，会导致分词错误。

**边界与坑**：分词错误会向下游传播，影响检索与标注质量。

## 4.2 传统中文分词方法

### 4.2.1 基于词典

| 方法 | 说明 |
|------|------|
| 最大匹配 | 贪心取最长词，简单但易错 |
| 最短路径 | 结合词频求最优切分 |
| 双向匹配 | 正向与逆向取一致结果 |

### 4.2.2 基于统计与序列标注

```
把分词看作对每个字打 B/M/E/S 标签：
  B 词首、M 词中、E 词尾、S 单字
"我爱北京" → 我/S 爱/S 北/B 京/E
常用模型：HMM、CRF、BiLSTM-CRF
```

## 4.3 现代模型的做法

> 现代模型多按**字符或子词**处理中文，Token 数约等于字数。

| 做法 | 说明 |
|------|------|
| 字符级 | 每字一 token，简单稳定 |
| 子词级 | 高频词合并，低频字独立 |
| 不显式分词 | 让 BPE 自动学习边界 |

**要点**：中文没有空格，传统靠词典/统计，现代靠子词；中文 token 密度更高。

# 5. Token 与成本

**结论先行**：Token 数同时决定成本、延迟与上下文占用，是 LLM 应用最直接的资源度量。

## 5.1 成本构成

### 5.1.1 计费

```
Token 数决定：成本 + 延迟 + 上下文占用
```

```
费用 ≈ 输入 token 数 × 输入单价 + 输出 token 数 × 输出单价
```

### 5.1.2 延迟

| 因素 | 影响 |
|------|------|
| 输入长度 | 影响首 token 延迟 |
| 输出长度 | 影响总生成时间 |
| 上下文占用 | 影响可用窗口与缓存 |

## 5.2 语言比例

| 语言 | 大致比例 |
|------|----------|
| 英文 | 1 token ≈ 4 字符 ≈ 0.75 词 |
| 中文 | 1 token ≈ 1~1.5 字 |

```
经验值：一段 1000 字中文 ≈ 700~1000 token
```

## 5.3 计算方法

### 5.3.1 Python tiktoken

```python
# 用 tiktoken 计算
import tiktoken
enc = tiktoken.get_encoding("cl100k_base")
tokens = enc.encode("Hello, 世界!")
print(len(tokens))    # token 数
```

### 5.3.2 Java jtokkit

```java
// Java：jtokkit
Encoding encoding = Encodings.newDefaultEncodingRegistry()
        .getEncodingForModel("gpt-4o-mini");
int count = encoding.countTokens("Hello, 世界!");
```

## 5.4 边界与坑

```
误区：用字符数估 token → 中英文误差大
做法：始终用目标模型的 tokenizer 精确计数
```

**要点**：Token 是成本与延迟的一等公民，任何预算都要以 tokenizer 为准。

# 6. 特殊 Token

**结论先行**：特殊 token 是分词器保留的控制符号，用于标记序列边界与对话结构，需防止用户输入混入。

## 6.1 常见特殊 Token

| Token | 作用 |
|-------|------|
| `[BOS]` / `<s>` | 序列开始 |
| `[EOS]` / `</s>` | 序列结束 |
| `[PAD]` | 填充 |
| `[UNK]` | 未知词 |
| `<|im_start|>` | 对话角色标记（ChatML） |

### 6.1.1 序列控制

```
BOS：告诉模型"从这里开始"
EOS：告诉模型"到这里结束"
PAD：批量训练时对齐长度（不参与 loss）
```

### 6.1.2 结构标记

结构标记用于区分角色、工具调用、推理块等，由对话模板定义。

## 6.2 ChatML

### 6.2.1 格式

```
ChatML 格式：
<|im_start|>system
你是助手<|im_end|>
<|im_start|>user
你好<|im_end|>
<|im_start|>assistant
```

### 6.2.2 作用

| 作用 | 说明 |
|------|------|
| 区分角色 | system/user/assistant |
| 统一多轮 | 拼成单一序列 |
| 控制生成 | 模型在 assistant 后生成 |

## 6.3 安全风险

### 6.3.1 特殊 token 注入

```
用户输入若包含 "<|im_end|>" 等字样，
可能伪造角色边界，导致提示注入
```

| 风险 | 缓解 |
|------|------|
| 角色伪造 | 清洗/转义用户输入 |
| 指令覆盖 | 系统提示与用户输入隔离 |
| 工具滥用 | 权限最小化 + 审计 |

## 6.4 要点

**要点**：特殊 token 是协议而非普通文本，输入侧必须清洗。

# 7. 词表大小

**结论先行**：词表大小是"序列长度"与"参数规模"的权衡，主流模型在 5 万到 15 万之间。

## 7.1 主流模型词表

| 模型 | 词表大小 |
|------|:--------:|
| GPT-2 | 50,257 |
| GPT-4 (cl100k) | 100,256 |
| LLaMA 3 | 128,256 |
| Qwen | 151,936 |

## 7.2 大小权衡

| 影响 | 说明 |
|------|------|
| 词表大 | 序列短、embedding 参数多 |
| 词表小 | 序列长、计算多 |

### 7.2.1 词表大的代价

```
Embedding 参数量 = 词表大小 × 向量维度
例：150000 × 4096 ≈ 6.1 亿参数
→ 稀有 token 训练不足，占用显存
```

### 7.2.2 词表小的代价

```
序列变长 → 注意力计算与 KV 缓存变大
→ 长文本场景成本上升
```

## 7.3 要点

**要点**：词表大小不是越大越好，要与目标语言、领域和模型规模匹配。

# 8. 分词对检索的影响

**结论先行**：稀疏检索（BM25）严重依赖分词质量，分词错误会直接导致检索失败。

## 8.1 BM25 与分词

### 8.1.1 BM25 简介

```
BM25 基于词频与逆文档频率打分：
  score(q, d) = Σ IDF(t) · (tf · (k1+1)) / (tf + k1 · (1 - b + b · |d|/avgdl))
其中 t 为查询词，tf 为词在文档中的频率
```

### 8.1.2 分词质量的影响

```
BM25 依赖分词质量：
- 分词错误 → 检索失败
- 领域术语需加入自定义词典
```

```
"大模型" 被切成 "大" + "模型"
→ 查询"大模型"可能匹配到大量无关文档
```

## 8.2 自定义词典

### 8.2.1 jieba

```python
# jieba 自定义词典
import jieba
jieba.load_userdict("custom_dict.txt")   # 加入领域术语
```

词典格式（词、词频、词性）：

```
大语言模型 1000 n
向量数据库 800 n
```

### 8.2.2 维护策略

| 策略 | 说明 |
|------|------|
| 从日志挖掘 | 高频未登录词补充词典 |
| 人工审核 | 保证术语准确性 |
| 版本管理 | 词典随业务迭代更新 |

## 8.3 要点

**要点**：混合检索中，稀疏侧靠分词、稠密侧靠句向量，两者都需要与业务词典对齐。

# 9. 生产注意事项

**结论先行**：分词环节的常见风险都可归为"估算不准、边界不清、词表不匹配"三类。

## 9.1 常见风险

| 风险 | 建议 |
|------|------|
| 用字符数估 Token | 用 tokenizer 精确算 |
| 中文分词错误 | 加领域词典 |
| 特殊 token 混入用户输入 | 清洗 |
| 超长文本 | 按 token 截断 |
| 词表不匹配 | 用模型对应的 tokenizer |

## 9.2 建议清单

```
① 明确目标模型的 tokenizer，并固定版本
② 所有长度限制按 token 设定
③ 输入侧转义特殊 token
④ 检索侧维护领域词典
⑤ 监控实际 token 用量与费用
```

## 9.3 边界与坑

```
坑：同一段文本在不同模型下 token 数不同
坑：tokenizer 升级可能导致缓存失效
坑：截断时切断了关键信息（如代码、JSON）
```

**要点**：把 tokenizer 当作模型契约的一部分来管理。

# 10. 小结

- 分词把文本切成 token 再映射为 ID。
- 三种粒度中，现代 LLM 用子词级（BPE/WordPiece/SentencePiece/Unigram）。
- Byte-level BPE 用 UTF-8 字节消除未登录词。
- 中文没有空格，传统靠词典/统计，现代按字符或子词，Token 数约等于字数。
- Token 决定成本、延迟与上下文占用，必须用 tokenizer 精确计算。
- 特殊 token 是协议标记，用户输入需清洗防注入。
- 词表大小是序列长度与参数规模的权衡。
- BM25 检索依赖分词质量，领域词典很重要。
