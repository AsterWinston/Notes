# 1. 什么是句向量模型

## 1.1 结论先行

**句向量模型**（sentence embedding model）= 把整段文本编码为一个固定维度向量的模型，用于语义检索。它是把"文本"变成"可计算几何对象"的桥梁。

## 1.2 原理：从文本到向量

```
"如何报销差旅费" → [0.12, -0.34, ...]（1024 维）
```

编码后，语义相近的文本在向量空间中距离更近，于是"找相似"变成"找最近邻"。

## 1.3 公式/图示：编码与检索

```
编码：  text  ──encoder──▶  v ∈ R^d
检索：  query ──encoder──▶  q
        相似度： sim(q, v) = cos(q, v)
        返回 top-k 最大的 v
```

| 组件 | 作用 |
|------|------|
| 编码器（encoder） | 文本 → 向量 |
| 相似度函数 | 比较两个向量 |
| 近邻索引 | 快速取 top-k |

## 1.4 边界与坑

| 坑 | 说明 |
|----|------|
| 把向量当"可读摘要" | 单维无独立语义，只有整体几何有意义 |
| 用未微调模型 | 通用模型在垂直领域可能很弱 |
| 忽略归一化 | 余弦相似度需先做 L2 归一化 |

## 1.5 要点

- 句向量模型把文本编码为固定维度向量。
- 检索 = 编码 + 相似度 + 最近邻。
- 它是 RAG 的核心组件，直接决定检索质量。

# 2. 为什么需要专门的句向量模型

## 2.1 结论先行

直接用 BERT 的 `[CLS]` 向量做检索效果很差，必须用**对比学习**专门训练句向量模型。

## 2.2 原理：BERT 的 `[CLS]` 为什么不适用

```
用 BERT 的 [CLS] 向量直接做检索 → 效果差
原因：
- BERT 的预训练目标是 MLM，不是句相似度
- [CLS] 向量未针对相似度优化
```

BERT 的预训练任务是掩码语言模型（Masked Language Model, MLM），它优化的是"预测被遮住的词"，而不是"让相似句子靠近"。因此 `[CLS]` 向量里编码的是语言建模所需的特征，而非相似度所需的特征。

## 2.3 公式/图示：两种目标的差异

```
MLM 目标：  上下文 ──▶ 预测被遮词
            优化 token 级分布

句相似度：  句子   ──▶ 向量
            优化向量空间中的距离
```

解决：用**对比学习**专门训练句向量模型。

### 2.3.1 早期方案：SBERT

Sentence-BERT（SBERT）用孪生网络（Siamese network）对两个句子分别编码，再以相似度目标微调，使 `[CLS]`（或池化）向量具备相似度意义。

### 2.3.2 池化方式

| 池化 | 做法 | 说明 |
|------|------|------|
| CLS | 取 `[CLS]` | 简单，依赖训练 |
| Mean | 所有 token 取平均 | 常用且稳定 |
| Max | 逐维取最大 | 对显著特征敏感 |
| Last-token | 取末位 token | 生成式模型常用 |

无论用哪种池化，训练与推理必须严格一致。训练时用 mean 池化、推理时改用 CLS，是效果骤降的常见原因。

## 2.4 边界与坑

| 坑 | 说明 |
|----|------|
| 混用不同池化 | 训练与推理必须一致 |
| 忽略 `[CLS]` 训练方式 | 未训练的 `[CLS]` 无相似度语义 |
| 以为参数量越大越好 | 句向量效果取决于训练目标 |

## 2.5 要点

- BERT 的 `[CLS]` 未针对相似度优化。
- 必须用对比学习专门训练句向量模型。
- 池化方式要与训练时保持一致。

# 3. 对比学习训练

## 3.1 结论先行

对比学习（contrastive learning）的核心：把语义相近的正样本对拉近，把语义无关的负样本对推远。

## 3.2 原理：正负样本对

```
正样本对（语义相近）→ 拉近
负样本对（语义无关）→ 推远
```

```
       ▲
       │   ●查询  ○正样本（拉近）
       │
       │            △负样本（推远）
       └──────────────────────▶
```

常用损失：MultipleNegativesRankingLoss（批内负样本）。

## 3.3 公式/图示：InfoNCE 损失

```
L = -log  exp(sim(q, k+) / τ)
          ─────────────────────────────
          Σ_j exp(sim(q, k_j) / τ)
```

其中 `sim` 为余弦相似度，`k+` 为正样本，`k_j` 为批内所有样本（含负样本），`τ` 为温度系数（temperature）。

### 3.3.1 批内负样本

批内负样本（in-batch negatives）的巧思：一个批次里有 N 对正样本，则对每个查询而言，其余 N-1 个正样本天然构成负样本，无需额外采样，计算高效。

### 3.3.2 难负样本

难负样本（hard negatives）是"看起来相似但语义无关"的样本，能显著提升判别力，但过难会导致训练不稳定。常用策略：用当前模型检索出的高相似非相关文档作为难负样本。

### 3.3.3 温度系数的作用

温度系数 `τ` 控制 softmax 的"尖锐程度"：

| `τ` | 效果 |
|-----|------|
| 小 | 分布尖锐，强区分，但训练不稳 |
| 大 | 分布平滑，梯度柔和，区分度弱 |

实践中常用可学习温度或固定值（如 0.02–0.05），需结合批大小调参。

## 3.4 边界与坑

| 坑 | 说明 |
|----|------|
| 批太小 | 批内负样本不足，效果差 |
| 假负样本 | 批内恰好语义相关却被当负样本 |
| 温度不当 | 过小训练不稳，过大区分度弱 |
| 无难负样本 | 模型学不会细粒度区分 |

## 3.5 要点

- 对比学习 = 拉近正样本、推远负样本。
- InfoNCE 是对比学习的标准损失。
- 批内负样本高效，难负样本提效但要防不稳。

# 4. 主流模型

## 4.1 结论先行

选模型先看三件事：语言覆盖、维度、是否自带稀疏/多向量能力。没有"最好"，只有"最匹配场景"。

## 4.2 原理：模型族谱

| 模型 | 维度 | 语言 | 特点 |
|------|:----:|------|------|
| BGE-large-zh | 1024 | 中文 | 中文检索强 |
| BGE-m3 | 1024 | 多语言 | 稠密+稀疏+多向量 |
| E5-large | 1024 | 多语言 | 需加前缀 |
| GTE-large-zh | 1024 | 中文 | 阿里开源 |
| text-embedding-3-small | 1536 | 多语言 | OpenAI |
| text-embedding-3-large | 3072 | 多语言 | OpenAI，更强 |
| Jina-embeddings-v3 | 1024 | 多语言 | 长文本 |
| Cohere embed-v3 | 1024 | 多语言 | 商业 |

## 4.3 公式/图示：稠密/稀疏/多向量

```
稠密（dense）：  一个向量代表整段文本
稀疏（sparse）： 词权重向量，维度=词表大小
多向量（multi）：每个 token 一个向量，延迟交互
```

| 类型 | 代表 | 优势 |
|------|------|------|
| 稠密 | BGE、E5 | 语义泛化强 |
| 稀疏 | BM25、SPLADE | 关键词精确 |
| 多向量 | ColBERT | 细粒度匹配 |

## 4.4 边界与坑

| 坑 | 说明 |
|----|------|
| 中文任务用英文模型 | 中文效果显著下降 |
| 忽略许可 | 商用需确认许可证 |
| 维度不匹配索引 | 建库与查询必须同模型同维度 |

## 4.5 要点

- 中文优先 BGE/GTE，多语言选 BGE-m3/E5/Jina。
- BGE-m3 可同时产出稠密、稀疏、多向量。
- 模型选择要以自有数据评估为准。

# 5. 前缀要求

## 5.1 结论先行

不同模型对输入格式有要求，**不加前缀会显著降低效果**，甚至让查询与文档落到不同子空间。

## 5.2 原理：为什么需要前缀

有些模型在训练时对"查询"与"文档"使用不同模板，前缀相当于告诉模型"这是查询"或"这是文档"。若推理时不加，输入分布与训练分布不一致，向量就会偏。

## 5.3 公式/图示：前缀写法

```python
# BGE（中文）：查询加指令前缀
query = "为这个句子生成表示以用于检索相关文章：" + question
doc = document                      # 文档不加

# E5：query/passage 前缀
query = "query: " + question
doc = "passage: " + document
```

| 模型 | 查询前缀 | 文档前缀 |
|------|----------|----------|
| BGE-zh | 有指令 | 无 |
| E5 | `query:` | `passage:` |
| GTE | 无 | 无 |
| OpenAI | 无 | 无 |

### 5.3.1 如何验证前缀是否正确

取一个已知查询与其相关文档，分别编码后算余弦相似度。正确加前缀时，相关文档的相似度应明显高于不相关文档；若两者接近，说明前缀模板可能用错。

## 5.4 边界与坑

| 坑 | 说明 |
|----|------|
| 查询加了、文档没加 | 训练模板不一致，效果下降 |
| 前缀有细微差异 | 空格、冒号、标点都需与文档一致 |
| 全部模型都加前缀 | GTE/OpenAI 不需要，加了反而有害 |

## 5.5 要点

- 前缀是模型训练模板的一部分，不是可选装饰。
- 严格按模型卡（model card）要求加。
- 查询与文档的前缀规则不同，切勿混用。

# 6. 维度选择

## 6.1 结论先行

维度决定存储与计算成本，也影响效果上限。选择时要平衡"效果、成本、延迟"三者。

## 6.2 原理：存储估算

| 维度 | 存储（每百万向量） | 效果 |
|:----:|:------------------:|:----:|
| 384 | ~1.5 GB | 一般 |
| 768 | ~3 GB | 好 |
| 1024 | ~4 GB | 更好 |
| 1536 | ~6 GB | 好（OpenAI） |
| 3072 | ~12 GB | 最好 |

> 存储 = 维度 × 4 字节 × 向量数。

### 6.2.1 计算验证

每百万（1e6）向量、1024 维、float32：

```
1024 × 4 字节 × 1e6 = 4.096e9 字节 ≈ 4 GB
```

若改用 float16，存储可减半；若用量化（quantization）到 int8，可再降至约 1/4。

### 6.2.2 维度与效果并非线性

更高维度提供更强表达能力，但收益递减，且检索延迟与内存同步上升。部分模型支持"截断维度"（Matryoshka embedding），可动态取舍。

## 6.3 公式/图示：存储与延迟

```
存储  ∝ 维度 × 向量数
延迟  ∝ 维度 × 候选数（暴力检索）
```

| 优化 | 手段 | 代价 |
|------|------|------|
| 降维 | PCA / Matryoshka | 少量精度损失 |
| 量化 | float16 / int8 | 精度损失 |
| 近似索引 | HNSW / IVF | 召回损失 |

### 6.3.1 维度变更的连锁反应

维度不是孤立参数，它绑定编码器。更换编码器会改变维度与向量空间，旧向量全部失效，必须全量重编码并重建索引。因此维度决策应在上线前定好，避免后期迁移成本。

## 6.4 边界与坑

| 坑 | 说明 |
|----|------|
| 只按榜单选维度 | 忽略自身成本约束 |
| 忘记索引也占内存 | 近似索引额外开销 |
| 维度变更不重建 | 新旧向量不可比 |

## 6.5 要点

- 存储 = 维度 × 4 字节 × 向量数。
- 维度越高效果通常越好，但成本同步上升。
- 量化、降维、近似索引可换取成本。

# 7. 非对称检索

## 7.1 结论先行

RAG 是"非对称检索"（asymmetric retrieval）：查询短、文档长。模型必须在这种非对称场景下被训练与使用。

## 7.2 原理：非对称的含义

```
RAG 是"非对称检索"：
  查询短（几个词）
  文档长（几百字）

因此：
- 查询与文档用不同的处理（前缀）
- 模型需在非对称场景下训练
```

对称检索是"短对短"（如相似问题匹配），非对称检索是"短对长"（如问题找文档）。两者对模型的要求不同。

## 7.3 公式/图示：对称 vs 非对称

```
对称检索：   短查询 ──▶ 短查询
非对称检索： 短查询 ──▶ 长文档
```

| 场景 | 查询 | 文档 | 例子 |
|------|------|------|------|
| 对称 | 短 | 短 | 相似问题 |
| 非对称 | 短 | 长 | RAG 问答 |

### 7.3.1 分块长度与检索质量

文档分块过短会丢失上下文，过长会让向量被"平均"而失去焦点。常用折中：每块 200–500 token，块间保留 10%–20% 重叠。分块长度应与查询长度、模型最大长度共同考虑。

## 7.4 边界与坑

| 坑 | 说明 |
|----|------|
| 用对称模型做 RAG | 效果不佳 |
| 查询当文档编码 | 前缀/模板错位 |
| 文档过长不切分 | 语义被平均，检索变差 |

## 7.5 要点

- RAG 是非对称检索：短查询找长文档。
- 查询与文档需用各自模板处理。
- 长文档应分块后再编码。

# 8. 中文模型选择建议

## 8.1 结论先行

纯中文优先 BGE-large-zh；中英混合选 BGE-m3 或 GTE；无 GPU 用 OpenAI 托管模型。

## 8.2 原理：场景驱动选型

| 场景 | 推荐 |
|------|------|
| 纯中文、追求效果 | BGE-large-zh |
| 中英混合 | BGE-m3 / GTE |
| 需要稀疏检索 | BGE-m3（自带稀疏） |
| 无 GPU、追求简单 | OpenAI text-embedding-3 |
| 长文本 | Jina-v3 / BGE-m3 |

## 8.3 公式/图示：选型决策树

```
是否纯中文？
 ├─ 是 ─▶ 是否需要稀疏？─▶ BGE-m3
 │                        └─ 否 ─▶ BGE-large-zh
 └─ 否 ─▶ 是否有 GPU？
          ├─ 有 ─▶ BGE-m3 / E5 / Jina
          └─ 无 ─▶ OpenAI text-embedding-3
```

## 8.4 边界与坑

| 坑 | 说明 |
|----|------|
| 忽视领域词 | 通用中文模型对垂直术语弱 |
| 忽略延迟 | 大模型在线推理慢，需缓存/批处理 |
| 频繁换模型 | 每次换都要全量重建索引 |

## 8.5 要点

- 纯中文选 BGE-large-zh，多语言选 BGE-m3/E5/Jina。
- 需要稀疏能力优先 BGE-m3。
- 选型后要做自有数据评估。

# 9. 模型评估

## 9.1 结论先行

必须用自有数据评估，而非只看公开榜单。榜单与业务分布往往不一致。

## 9.2 原理：评估指标

```
用自有数据评估，而非只看榜单：
  准备查询-相关文档对
  计算 Recall@K / MRR / nDCG
```

| 指标 | 含义 | 关注点 |
|------|------|--------|
| Recall@K | 前 K 个中是否含相关 | 召回能力 |
| MRR | 第一个相关结果的倒数排名均值 | 排序质量 |
| nDCG | 折损累积增益 | 多级相关性 |

### 9.2.1 Recall@K

```
Recall@K = 命中的查询数 / 总查询数
```

### 9.2.2 MRR

```
MRR = (1/N) · Σ 1/rank_i
```

其中 `rank_i` 是第 `i` 个查询的第一个相关结果的排名。

### 9.2.3 nDCG

```
nDCG = DCG / IDCG
DCG  = Σ (2^rel_i - 1) / log2(i + 1)
```

nDCG 支持多级相关度，并对排名靠后的结果做折损（discount），是排序质量最全面的指标。

## 9.3 公式/图示：评估代码

```python
def evaluate_embedding(model, test_cases, k=5):
    hits = 0
    for query, relevant_ids in test_cases:
        results = search(model, query, k)
        if any(r in relevant_ids for r in results):
            hits += 1
    return hits / len(test_cases)
```

## 9.4 边界与坑

| 坑 | 说明 |
|----|------|
| 测试集太小 | 指标方差大，不可信 |
| 只测 Recall | 忽略排序质量 |
| 数据泄漏 | 测试样本出现在训练集 |
| 用榜单代替评估 | 与业务分布脱节 |

## 9.5 要点

- 用自有数据评估，而非只看榜单。
- 关注 Recall@K、MRR、nDCG。
- 评估集要足够大且无泄漏。

# 10. 生产注意事项

## 10.1 结论先行

生产环境的核心风险：模型/前缀/维度不一致、频繁换模型、无版本记录、单点故障。

## 10.2 原理：风险与建议

| 风险 | 建议 |
|------|------|
| 只看榜单 | 用自有数据评估 |
| 漏加前缀 | 按模型要求加 |
| 维度误解 | 按维度估算存储 |
| 频繁换模型 | 需全量重建 |
| 无版本记录 | 元数据记录模型版本 |
| 单点 | 独立服务 + 多副本 |

## 10.3 公式/图示：服务化架构

```
        ┌───────────────┐
查询 ──▶│ embedding 服务 │──▶ 向量
        └───────────────┘
              │
        ┌─────┴─────┐
        ▼           ▼
     副本 A      副本 B
        │           │
        └─────┬─────┘
              ▼
         向量索引库
```

## 10.4 边界与坑

| 坑 | 说明 |
|----|------|
| 索引与查询模型不同 | 向量不可比，检索失效 |
| 无批量编码 | 逐条推理延迟高 |
| 无缓存 | 重复查询重复计算 |
| 无降级 | 服务故障导致全站不可用 |

## 10.5 要点

- 索引与查询必须同模型、同维度、同版本。
- 换模型需全量重建索引。
- 服务化 + 多副本 + 缓存，保证可用与低延迟。

# 11. 小结

## 11.1 关键结论

- 句向量模型把文本编码为固定维度向量。
- 用对比学习训练，专门优化相似度。
- BGE/GTE 中文强，E5/Jina 多语言。
- 注意前缀要求（BGE 查询前缀、E5 query/passage）。
- 必须用自有数据评估，而非只看榜单。

## 11.2 一句话回顾

选模型看语言与维度，用前缀对齐训练模板，用自有数据验证效果。
