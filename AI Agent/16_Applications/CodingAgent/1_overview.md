# 1. 项目背景与定位

## 1.1 项目背景

### 1.1.1 业务痛点

结论先行：研发团队需要一个能理解代码库、修改代码、执行测试的编码 Agent（智能体），辅助日常开发，降低重复性的定位、修改与调试成本。

机制层面，团队在日常迭代中反复经历三类高耗时活动：

- 定位代码：面对陌生模块，需跨文件、跨目录检索才能找到入口与调用链。
- 联动修改：一次修复常牵动多个文件（实现、接口、测试、配置、文档）。
- 验证闭环：改完需运行测试、读取堆栈、再次修复，循环往复。

一个典型任务的原始工单可能长这样：

```
标题：登录接口在 token 过期时返回 500
现象：携带过期 token 调用 /api/user/profile 返回 500，期望 401
线索：认证过滤器、JWT 解析、全局异常处理
```

这些活动单靠"补全式"工具无法覆盖，必须引入具备"检索—修改—执行—修复"闭环能力的 Agent。

边界与坑：并非所有任务都适合 Agent。架构决策、模糊需求、强合规约束的改动仍应由人主导，Agent 只做候选方案。

生产建议：以"辅助"而非"替代"为定位，所有改动保留人工确认关口。

### 1.1.2 现有工具局限

结论先行：现有工具各解决一环，缺少"端到端闭环"。

| 工具类型 | 能力边界 | 缺失环节 |
|----------|----------|----------|
| 代码补全 | 行/函数级建议 | 无跨文件理解、无执行验证 |
| 聊天助手 | 解释、生成片段 | 无仓库读写、无测试闭环 |
| 静态分析 | 规则化告警 | 无自动修复、无语义理解 |
| 本编码 Agent | 检索 + 修改 + 执行 + 修复 | 需沙箱与审计兜底 |

能力分层可用下图表示：

```
补全工具      单文件  ─┐
聊天助手      单轮    ─┤ 无执行
静态分析      规则    ─┘
本 Agent      多文件 + 多轮 + 执行 + 审计   ← 目标能力
```

边界与坑：补全工具在"上下文已知"时体验极佳，但无法自主决定"改哪个文件"。

生产建议：把本 Agent 定位为补全工具之上的"任务级"能力，二者互补而非替代。

## 1.2 项目定位

### 1.2.1 与通用编程助手的区别

结论先行：本 Agent 的差异化在于"可读写仓库 + 可执行验证 + 可审计回滚"。

| 维度 | 通用编程助手 | 本编码 Agent |
|------|--------------|--------------|
| 上下文 | 当前文件/选区 | 全仓库检索结果 |
| 产出 | 文本片段 | 结构化补丁（patch） |
| 验证 | 无 | 沙箱执行测试 |
| 闭环 | 单轮 | Reflexion 多轮修复 |
| 安全 | 无状态 | Git 隔离 + 人工确认 |

边界与坑：能力越大风险越大，必须配套沙箱、审计与回滚。

### 1.2.2 价值主张

- 效率：把"读—改—跑—修"的机械循环交给 Agent。
- 质量：以测试通过为硬性完成条件，减少"看似改对"。
- 一致性：沿用仓库既有代码风格与依赖，降低引入新依赖的风险。
- 可追溯：每次改动留痕，可审计、可回滚。

### 1.2.3 能力边界声明

| 能做 | 不做（本期） |
|------|--------------|
| 检索、解释、修改、跑测试 | 自动提交、自动部署 |
| 生成测试用例 | 修改生产配置 |
| 生成变更说明 | 访问生产数据 |

生产建议：将"不做"清单写入系统提示词与工具白名单，双重约束。

## 1.3 术语与约定

| 术语 | 含义 |
|------|------|
| Agent | 具备工具调用与循环决策能力的智能体 |
| 工具（Tool） | Agent 可调用的受控函数，如 searchCode |
| 补丁（Patch） | 描述文件差异的结构化文本 |
| Reflexion | 基于执行反馈的多轮自我修复机制 |
| 沙箱（Sandbox） | 隔离的代码执行环境 |
| 检索增强（RAG） | 先检索相关代码再交给模型生成 |

编号约定：一级标题用 `# k.`，二级用 `## k.m`，三级用 `### k.m.j`，各级编号独立连续。

# 2. 目标用户与场景

## 2.1 用户画像

| 用户 | 场景 | 核心诉求 |
|------|------|----------|
| 开发者 | 修改 bug、添加功能 | 少写样板、快速定位、测试兜底 |
| 测试 | 生成测试用例 | 覆盖边界、可运行 |
| 新人 | 理解代码结构 | 快速建立模块心智模型 |

结论先行：三类用户共享同一套"检索 + 修改 + 执行"能力，只是入口与提示词不同。

| 用户 | 默认权限 | 默认模式 |
|------|----------|----------|
| 开发者 | 读写 | 任务模式 |
| 测试 | 写测试文件 | 生成模式 |
| 新人 | 只读 | 问答模式 |

## 2.2 典型场景

### 2.2.1 缺陷修复

输入自然语言缺陷描述，Agent 检索相关代码、定位根因、提交最小补丁并运行回归测试。

### 2.2.2 功能开发

按需求描述新增接口与实现，同时补齐单元测试，保证测试通过。

### 2.2.3 代码理解

只读模式：检索并解释调用链、数据结构与关键逻辑，不写文件。

## 2.3 用户旅程

```
用户提交任务 → 检索相关代码 → 生成方案(人工可预览)
   → 应用补丁 → 沙箱执行测试 → 失败则修复 → 通过
   → 生成变更说明 → 人工确认 → 提交
```

| 阶段 | 用户可见物 | 可干预点 |
|------|------------|----------|
| 检索 | 命中文件与片段 | 补充线索 |
| 方案 | 修改计划 | 修改/否决 |
| 执行 | 测试输出 | 中止 |
| 交付 | diff + 说明 | 确认/回滚 |

边界与坑：新人场景应默认关闭写权限，避免误改。

# 3. 功能范围

## 3.1 核心功能

### 3.1.1 代码检索与理解

以函数/类为切分单位，结合语义与关键词检索，返回带文件路径与行号的片段。

### 3.1.2 代码修改

支持多文件修改，产出结构化补丁，逐文件落盘并可生成 diff。

### 3.1.3 测试验证与修复

在沙箱内执行测试，读取错误输出，基于反馈循环修复，直至通过或达上限。

### 3.1.4 变更说明生成

汇总改动文件、改动意图、测试结果，生成可供评审的变更说明。

核心功能清单：

```
核心功能：
├── 代码检索与理解
├── 代码修改（多文件）
├── 执行测试验证
├── 读取错误并修复
└── 生成变更说明
```

## 3.2 非目标

```
非目标：
├── 自动提交代码（需人工确认）
├── 部署
```

结论先行：非目标是有意为之，用于划定安全边界。

边界与坑：非目标不等于"永不做"，而是"当前版本不自动化"，保留人工卡点。

## 3.3 功能优先级

| 优先级 | 功能 | 理由 |
|--------|------|------|
| P0 | 检索 + 单文件修改 | 最小可用闭环 |
| P1 | 多文件修改 | 覆盖真实修复 |
| P2 | 沙箱执行 + 测试 | 验证正确性 |
| P3 | 自动修复循环 | 提升一次成功率 |
| P4 | 评测 + 上线 | 量化与灰度 |

| 功能 | 验收项 |
|------|--------|
| 检索 | 能定位相关文件 |
| 修改 | 修改后测试通过 |
| 执行 | 沙箱隔离、限资源 |
| 修复 | 失败可自愈 |
| 审计 | 可回滚 |

# 4. 非功能需求

## 4.1 需求矩阵

| 维度 | 要求 | 度量方式 |

| 沙箱 | 代码执行必须隔离 | 无宿主机写权限 |
| 安全 | 禁止访问生产数据 | 沙箱无生产凭证 |
| 成功率 | 简单任务 > 70% | 评测集通过率 |
| 可审计 | 记录所有修改 | 变更日志完整率 100% |

## 4.2 安全与合规

### 4.2.1 沙箱隔离

容器隔离、禁网、限 CPU/内存/进程数/时长，禁止挂载宿主敏感目录。

### 4.2.2 数据隔离

仅挂载目标仓库副本，使用脱敏或模拟数据，禁止连接生产数据库。

## 4.3 性能与容量

| 指标 | 目标 |
|------|------|
| 单任务端到端时延 | P95 < 10 分钟 |
| 索引吞吐 | 10 万行/分钟 |
| 并发任务 | 单节点 8 路 |
| 单任务成本 | 可控于预算阈值 |

边界与坑：大仓库索引与长任务时延是主要瓶颈，需异步化与配额控制。

生产建议：以任务队列削峰，超时即中止并回收沙箱。

# 5. 验收标准

## 5.1 功能验收

- [ ] 能定位相关代码文件
- [ ] 修改后测试通过
- [ ] 生成可读的变更说明

## 5.2 质量与安全验收

- [ ] 沙箱隔离（无网络、限资源）
- [ ] 无越权访问
- [ ] 变更可审计、可回滚

## 5.3 评测方法

| 维度 | 方法 | 通过线 |
|------|------|--------|
| 定位准确 | 人工标注相关文件，算命中率 | > 80% |
| 修改正确 | 测试通过率 | 简单 > 70% |
| 安全 | 红队用例 | 0 高危 |
| 可回滚 | 随机抽样回滚 | 100% 成功 |

## 5.4 评测集示例

结论先行：评测集应包含任务、期望文件、判定方式三要素。

```java
public record EvalCase(
        String id,
        String task,
        List<String> expectedFiles,
        String testCommand) {}

public double evaluate(List<EvalCase> cases, CodingAgent agent) {
    long passed = cases.stream().filter(c -> {
        CodingResult r = agent.solve(c.task(), repoFor(c.id()));
        return r.testPassed() && hits(r.changedFiles(), c.expectedFiles());
    }).count();
    return (double) passed / cases.size();
}
```

边界与坑：测试通过不等于语义正确，需辅以人工抽检与评审。

## 5.5 验收流程

```
提交评测任务 → 自动跑评测集 → 汇总通过率与安全用例
   → 人工抽检 → 签署验收 → 进入灰度
```

## 5.6 验收责任矩阵

| 验收项 | 责任方 | 方式 |
|--------|--------|------|
| 功能验收 | 研发 | 评测集 + 演示 |
| 安全验收 | 安全 | 红队 + 渗透 |
| 性能验收 | 运维 | 压测 |
| 合规验收 | 合规 | 审计日志检查 |

结论先行：验收不是一次性的，应固化为上线前的门禁（gate）。

# 6. 技术选型

## 6.1 选型总览

| 组件 | 选择 |
|------|------|
| 框架 | Spring AI / LangChain4j |
| 模型 | 代码专长模型（Claude/DeepSeek） |
| 代码检索 | 混合检索（语义 + 关键词） |
| 执行 | Docker 沙箱 |
| 版本控制 | Git（只读 + 人工提交） |

## 6.2 关键组件对比

### 6.2.1 框架对比

| 框架 | 优势 | 权衡 |
|------|------|------|
| Spring AI | 与 Spring Boot 无缝、工具调用成熟 | 生态较新 |
| LangChain4j | 抽象丰富、工具/记忆齐全 | 依赖较多 |

### 6.2.2 模型对比

| 模型 | 代码能力 | 成本 | 适用 |
|------|----------|------|------|
| Claude 系 | 强 | 高 | 复杂修复 |
| DeepSeek 系 | 强、性价比高 | 中 | 常规任务 |
| 通用小模型 | 中 | 低 | 检索/分类 |

### 6.2.3 检索方案对比

| 方案 | 优点 | 缺点 |
|------|------|------|
| 纯向量 | 语义泛化好 | 标识符命中弱 |
| 纯关键词 | 精确匹配强 | 语义泛化弱 |
| 混合 | 兼顾两者 | 需调权重/融合 |

结论先行：代码场景标识符重要，混合检索优于任一单方案。

## 6.3 选型理由与替代

- 框架：优先与既有 Spring 技术栈一致，降低运维成本。
- 模型：按任务复杂度路由，复杂任务用强模型，常规任务用性价比模型。
- 检索：先落地混合检索，后续可引入重排（rerank）。
- 执行：Docker 起步，后续可演进到 gVisor/Kata 等更强隔离。

边界与坑：更换模型需重跑评测，避免回归。

## 6.4 选型决策树

```
需要与 Spring 集成?
├── 是 → Spring AI / LangChain4j
└── 否 → 直接调用厂商 SDK
任务复杂度?
├── 高 → 强模型 (Claude 系)
└── 常规 → 性价比模型 (DeepSeek 系)
检索?
└── 混合检索(向量 + BM25)，必要时加 rerank
隔离?
└── Docker 起步 → gVisor/Kata 演进
```

# 8. 风险与应对

## 8.1 风险登记

| 风险 | 应对 |
|------|------|
| 破坏代码 | Git 隔离 + 人工确认 |
| 沙箱逃逸 | 容器隔离 + 禁网 |
| 上下文超限 | 代码分块 + 检索 |
| 测试环境 | 独立沙箱 |

## 8.2 关键风险详析

### 8.2.1 代码破坏

机制：Agent 误改无关文件或引入破坏性变更。应对：Git 分支隔离、最小补丁、人工确认、可一键回滚。

### 8.2.2 沙箱逃逸

机制：恶意或失控代码尝试越界。应对：禁网、只读挂载非工作目录、限制系统调用与权限、定期更新基础镜像。

## 8.3 应急与回滚

- 回滚：基于 Git 分支与补丁，一键还原。
- 熔断：连续失败或超时即中止任务并释放资源。
- 审计：所有改动留痕，支持事后追责与复盘。

## 8.4 风险评分

| 风险 | 可能性 | 影响 | 等级 |
|------|--------|------|------|
| 破坏代码 | 中 | 高 | 高 |
| 沙箱逃逸 | 低 | 高 | 高 |
| 上下文超限 | 高 | 中 | 中 |
| 成本超支 | 中 | 中 | 中 |

## 8.5 熔断示例

```java
public CodingResult guardedSolve(String task, Path repoDir) {
    int failures = 0;
    for (int i = 0; i < MAX_ATTEMPTS; i++) {
        CodingResult r = solveOnce(task, repoDir);
        if (r.testPassed()) {
            return r;
        }
        if (++failures >= CIRCUIT_THRESHOLD) {
            return CodingResult.aborted("连续失败触发熔断");
        }
    }
    return CodingResult.failed("达到最大尝试次数");
}
```

# 9. 成本与效益

## 9.1 成本估算

| 项 | 说明 |
|----|------|
| 模型调用 | 按 token 计费，复杂任务更高 |
| 沙箱资源 | CPU/内存/时长占用 |
| 索引存储 | 向量库与元数据 |
| 运维 | 监控、告警、迭代 |

单任务成本可近似为：

```
cost ≈ tokens_in * price_in + tokens_out * price_out
      + sandbox_minutes * price_per_minute
```

## 9.2 效益指标

| 指标 | 目标 |
|------|------|
| 单任务节省工时 | > 30% |
| 一次修复成功率 | 持续提升 |
| 测试通过率 | 简单 > 70% |

## 9.3 上线策略

先内部灰度，限定仓库与用户，收集评测数据后逐步放量；高风险仓库保持只读。

## 9.4 投入产出

结论先行：当单任务平均节省工时大于其模型与资源成本时，项目具备正向 ROI。

边界与坑：忽略沙箱资源与人工确认成本会高估收益。

# 10. 小结

## 10.1 核心结论

- 目标是辅助开发的编码 Agent。
- 核心：检索、修改、执行、修复。
- 沙箱隔离与审计是硬要求。
- 用代码专长模型 + 混合检索。
- 修改需人工确认与可回滚。
- 分阶段推进：检索 → 多文件 → 沙箱 → 修复循环 → 评测上线。
