# 1. 背景

## 1.1 业务痛点

### 1.1.1 结论先行

数据分析 Agent 要解决的核心矛盾是：业务人员有数据需求却不懂 SQL，而数据团队被大量临时取数需求淹没。用自然语言替代 SQL，是唯一能同时缓解"需求排队"和"人力瓶颈"的路径。

### 1.1.2 痛点拆解

| 痛点 | 表现 | 影响 |
|------|------|------|
| 取数排队 | 临时需求排到数天后 | 决策滞后 |
| 门槛高 | 不懂 SQL/表结构 | 业务自助受阻 |
| 口径不一 | 各人各算法 | 数据不可信 |
| 重复劳动 | 相似问题反复取数 | 人力浪费 |

### 1.1.3 量化目标

| 指标 | 现状 | 目标 |
|------|------|------|
| 临时取数平均等待 | 1-3 天 | < 10 分钟 |
| 业务自助率 | < 10% | > 50% |
| 口径一致率 | 低 | 高（复用指标口径） |

## 1.2 产品定位

数据分析 Agent 是一个只读的"数据问答入口"：用户用自然语言提问，系统完成查询、执行、分析、可视化与报告输出。它不是 BI 的替代品，而是 BI 的"自然语言前台"。

### 1.2.1 产品原则

- 安全优先：宁可拒答，不可越权。
- 结论先行：先给答案，再给明细。
- 可解释：展示所用 SQL 与口径来源。
- 可追问：支持多轮探索，逐步收敛。

## 1.3 与相关系统的关系

```
业务用户
   │  自然语言
   ▼
数据分析 Agent ──▶ 只读数据库 / 数仓
   │
   ├──▶ 固定查询工具（高频、确定性）
   └──▶ Text2SQL（探索性、受控）
   │
   ▼
图表 / 报告 / 洞察
```

Agent 复用已有指标平台的口径定义，避免"同一问题两个答案"。

### 1.3.1 集成边界

| 系统 | 关系 | 方式 |
|------|------|------|
| 指标平台 | 复用口径 | API 读取指标定义 |
| 权限系统 | 复用权限 | 传入用户上下文 |
| BI 工具 | 互补 | 复杂看板仍走 BI |
| 数仓 | 数据源 | 只读账号连接 |

# 2. 目标用户

## 2.1 用户画像

### 2.1.1 结论先行

四类用户诉求不同：业务要"快"，运营要"全"，管理者要"准且简"，分析师要"灵活"。产品必须同时覆盖，但按优先级分层服务。

### 2.1.2 用户与场景

| 用户 | 场景 |
|------|------|
| 业务人员 | 查询业务数据 |
| 运营 | 生成运营报表 |
| 管理者 | 查看关键指标 |
| 分析师 | 快速探索数据 |

### 2.1.3 用户优先级

| 优先级 | 用户 | 理由 |
|--------|------|------|
| P0 | 业务人员 | 量最大、痛点最强 |
| P1 | 运营 | 报表刚需 |
| P2 | 管理者 | 决策价值高 |
| P3 | 分析师 | 能力要求高 |

## 2.2 典型用户旅程

```
提问："上月各区域销售额对比"
   │
   ▼
系统识别为聚合查询 ──▶ 生成/选择查询
   │
   ▼
执行（只读 + 权限过滤 + LIMIT）
   │
   ▼
返回数据 + 洞察 + 图表
   │
   ▼
用户追问："那华东为什么最高？"
   │
   ▼
多轮探索（带上文）
```

### 2.2.1 多轮探索的价值

数据分析很少一次问清。多轮追问能把"看总数"逐步收敛到"找原因"，这是 Agent 相对固定报表的最大优势。

## 2.3 用户诉求差异

| 用户 | 关注点 | 对产品的要求 |
|------|--------|--------------|
| 业务人员 | 快 | 低延迟、少配置 |
| 运营 | 全 | 可导出、可定时 |
| 管理者 | 简 | 结论先行、图表清晰 |
| 分析师 | 活 | 可看 SQL、可调参 |

### 2.3.1 诉求到功能映射

| 诉求 | 对应功能 |
|------|----------|
| 快 | 缓存 + 固定工具 |
| 全 | 导出 + 定时报告 |
| 简 | 结论先行 + 图表 |
| 活 | 展示 SQL + 参数调整 |

# 3. 功能范围

## 3.1 核心功能

### 3.1.1 结论先行

功能闭环是"查询 → 执行 → 分析 → 图表 → 报告"。其中查询分两条路径：固定查询工具（安全优先）与 Text2SQL（灵活优先）。

### 3.1.2 功能清单

```
核心功能：
├── 自然语言转查询（Text2SQL 或工具调用）
├── 数据查询执行
├── 结果分析与洞察
├── 图表生成
└── 报告输出

非目标：
├── 数据写入
├── 复杂 ETL
```

### 3.1.3 端到端处理链路

```
问题 → 意图理解 → 查询生成 → 校验 → 执行
     → 分析 → 图表 → 报告
```

每一环都可观测、可降级，任何一环失败都要给出明确提示而非静默。

## 3.2 非目标

- 不做数据写入：任何 DML/DDL 一律拒绝。
- 不做复杂 ETL 与数据加工：只读已有宽表/数仓。
- 不做权限系统本身：复用现有权限体系。

### 3.2.1 为什么明确非目标

边界不清会让范围失控。明确"不写、不 ETL、不造权限"，才能把工程资源集中在"只读问答"的安全与准确上。

## 3.3 功能优先级

| 优先级 | 功能 | 理由 |
|--------|------|------|
| P0 | 固定查询工具 | 安全、高频 |
| P1 | Text2SQL | 覆盖长尾 |
| P2 | 分析与洞察 | 提升价值 |
| P3 | 图表 | 提升可用性 |

### 3.3.1 优先级矩阵

| 功能 | 价值 | 风险 | 顺序 |
|------|:----:|:----:|:----:|
| 固定工具 | 高 | 低 | 1 |
| Text2SQL | 高 | 高 | 2 |
| 分析 | 中 | 低 | 3 |
| 图表 | 中 | 低 | 4 |

# 4. 非功能需求

## 4.1 需求与指标

### 4.1.1 结论先行

安全是第一非功能需求，其次是准确与延迟。宁可回答"查不到"，也不能越权或写库。

### 4.1.2 需求与指标

| 维度 | 要求 |
|------|------|
| 安全 | 只读、防注入、防越权 |
| 准确 | 查询结果正确 |
| 延迟 | < 10s |
| 权限 | 按数据权限过滤 |

### 4.1.3 需求来源

需求来自三方：合规部门（只读、审计）、数据团队（防全表扫描）、业务用户（快、准）。三者冲突时，安全优先级最高。

## 4.2 安全需求

| 层级 | 措施 |
|------|------|
| 数据库 | 只读账号、最小授权 |
| 应用 | 表白名单、语法校验、强制 LIMIT |
| 数据 | 行级/列级权限过滤 |
| 审计 | 全量查询日志 |

### 4.2.1 权限层级

| 层级 | 说明 |
|------|------|
| 表级 | 只能访问授权的表 |
| 列级 | 隐藏敏感列 |
| 行级 | 只能看自己的数据 |

三层缺一不可：只做表级权限，行级数据仍会泄露。

## 4.3 性能需求

- 首字节延迟目标 < 3s，整体 < 10s。
- 单查询强制超时（如 10s）与行数上限（如 100）。
- 高频问题命中缓存直接返回。

### 4.3.1 延迟预算

| 环节 | 预算 |
|------|------|
| 意图与生成 | < 4s |
| 执行查询 | < 3s |
| 分析与图表 | < 3s |

总预算 10s，任一环节超时都要降级（先返回数据，再补分析）。

# 5. 验收标准

## 5.1 验收清单

- [ ] 只读，无法执行写操作
- [ ] SQL 注入防护
- [ ] 行数限制
- [ ] 数据权限过滤
- [ ] 查询准确率 > 80%

### 5.1.1 验收门槛

安全类必须 100% 通过（只读、防注入、权限），准确率类允许有阈值（> 80%）。安全项一票否决。

## 5.2 验收方法

| 项 | 方法 |
|----|------|
| 只读 | 注入写语句应被拒 |
| 防注入 | 红队用例 + 静态校验 |
| 行数限制 | 构造大结果集验证截断 |
| 权限过滤 | 越权用例应被过滤 |
| 准确率 | 离线评测集打分 |

### 5.2.1 验收用例示例

```java
@Test
void should_reject_write_operation() {
    assertThrows(UnsafeQueryException.class,
            () -> service.query("删除所有订单", admin));
}

@Test
void should_filter_by_region() {
    QueryResult r = service.query("查询所有订单", eastChinaUser);
    assertTrue(r.sql().contains("region = '华东'"));
}
```

## 5.3 验收数据

验收需给出可复现的数据：评测集、基线版本、通过率、失败用例清单。

### 5.3.1 验收数据模板

| 字段 | 说明 |
|------|------|
| evalSet | 评测集版本 |
| baseline | 基线指标 |
| passRate | 本次通过率 |
| failures | 失败用例 |
| decision | 通过/不通过 |

# 6. 技术选型

## 6.1 选型结论

### 6.1.1 结论先行

框架用 Spring AI 或 LangChain4j；查询以固定工具为主、Text2SQL 为辅；数据库只给只读账号；图表前后端二选一；模型按复杂度分层。

### 6.1.2 选型表

| 组件 | 选择 |
|------|------|
| 框架 | Spring AI / LangChain4j |
| 查询 | 固定查询工具 + Text2SQL |
| 数据库 | 只读账号 |
| 图表 | 服务端渲染 / 前端 ECharts |
| 模型 | 中/大模型 |

### 6.1.3 模型分层

| 任务 | 模型 |
|------|------|
| 意图/改写 | 小模型 |
| Text2SQL | 中/大模型 |
| 分析解读 | 中模型 |
| 图表配置 | 规则优先 |

分层能显著降本：多数请求止步于小模型。

## 6.2 备选方案对比

| 方案 | 安全 | 灵活 | 维护成本 |
|------|:----:|:----:|:--------:|
| 纯固定工具 | 高 | 低 | 低 |
| 纯 Text2SQL | 低 | 高 | 高 |
| 工具 + Text2SQL | 高 | 高 | 中 |

### 6.2.1 选型结论

生产上采用"工具 + Text2SQL"混合：高频、确定性问题走工具，长尾探索走 Text2SQL 且强制防护。

## 6.3 部署形态

```java
@Configuration
public class DataSourceConfig {

    @Bean("readOnlyDataSource")
    public DataSource readOnlyDataSource() {
        HikariConfig cfg = new HikariConfig();
        cfg.setJdbcUrl("jdbc:postgresql://db:5432/dw");
        cfg.setUsername("readonly_user");   // 只读账号
        cfg.setReadOnly(true);
        cfg.setMaximumPoolSize(10);
        cfg.setConnectionTimeout(3_000);
        return new HikariDataSource(cfg);
    }
}
```

### 6.3.1 只读连接的硬约束

只读账号是最后一道防线：即使应用层校验被绕过，数据库层也拒绝写操作。连接池需限制并发与超时，防止慢查询拖垮库。

# 8. 风险

## 8.1 风险与应对

### 8.1.1 结论先行

最大风险是"越权与注入"，其次是"查询错误"。前者靠多层防护兜底，后者靠表结构提示与评测迭代。

### 8.1.2 风险应对

| 风险 | 应对 |
|------|------|
| SQL 注入 | 校验 + 只读账号 |
| 全表扫描 | 强制 LIMIT + 超时 |
| 越权 | 数据权限过滤 |
| 查询错误 | 表结构提示 + 校验 |
| 成本 | 限制查询复杂度 |

### 8.1.3 反例

- 反例一：只靠提示词约束"不要写库"，模型仍可能生成 `UPDATE`。必须靠代码校验与只读账号。
- 反例二：把行级过滤交给模型拼接，模型可能漏加条件。必须在执行前由代码强制注入。

## 8.2 风险等级

| 风险 | 等级 | 后果 |
|------|:----:|------|
| 越权 | 高 | 数据泄露 |
| 注入 | 高 | 数据破坏 |
| 查询错误 | 中 | 误导决策 |
| 成本 | 低 | 费用上升 |

### 8.2.1 等级定义

| 等级 | 判定 |
|------|------|
| 高 | 涉及数据安全或破坏 |
| 中 | 影响决策正确性 |
| 低 | 影响体验或成本 |

## 8.3 兜底方案

- 校验不通过直接拒绝，不"尽力而为"。
- 结果为空时明确说明，不编造。
- 异常时回退固定查询工具。

### 8.3.1 降级策略

| 场景 | 降级 |
|------|------|
| Text2SQL 失败 | 回退固定工具 |
| 分析超时 | 先返回数据 |
| 图表失败 | 返回表格 |
| 权限缺失 | 拒绝并提示 |

# 9. 小结

## 9.1 核心结论

- 目标是自然语言数据分析。
- 核心：查询、分析、图表、报告。
- 安全是首要：只读、防注入、防越权。
- 优先固定查询工具，Text2SQL 需严格防护。
- 分阶段推进。

## 9.2 决策口诀

> 能用固定工具就不放 Text2SQL；能只读就绝不写；能用权限过滤就不靠提示词；安全与准确优先于灵活与炫技。
