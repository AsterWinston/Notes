# 1. 项目背景

## 1.1 业务背景

### 1.1.1 现状与痛点

结论先行：企业现有问答入口分散、响应慢、知识更新滞后，亟需一个统一的智能对话助手。

机制层面，当前内部与外部服务分别依赖工单、FAQ（常见问题，Frequently Asked Questions）页面、人工客服三条独立链路，存在以下问题：

| 痛点 | 表现 | 影响 |
|------|------|------|
| 入口分散 | 员工查制度需登录多个系统 | 效率低 |
| 响应慢 | 工单平均等待数小时 | 体验差 |
| 知识滞后 | FAQ 靠人工维护 | 答案过期 |
| 重复劳动 | 客服大量重复应答 | 成本高 |
| 数据无沉淀 | 对话未结构化管理 | 无法优化 |

### 1.1.2 建设目标

结论先行：用一个大模型（Large Language Model，LLM）驱动的对话助手统一入口，覆盖"问答 + 办理"两类诉求。

目标拆解：

- 统一入口：一个入口承接内部员工与外部客户咨询。
- 知识驱动：答案来自可维护的知识库，可溯源、可引用。
- 任务闭环：能调用工具查询订单、库存等业务数据。
- 可运营：可观测、可评测、可灰度、可回退。

## 1.2 项目定位

### 1.2.1 与既有系统关系

结论先行：本助手是"聚合层"，不替代既有业务系统，而是作为统一对话入口。

```text
+----------------+     +---------------------+
|  用户 (Web/App) | --> |  智能对话助手 (本项目) |
+----------------+     +----------+----------+
                                  |
          +-----------------------+-----------------------+
          |                       |                       |
   +------v------+        +-------v------+        +--------v------+
   | 知识库/向量库 |        | 业务系统 API  |        | 会话/反馈存储  |
   +-------------+        +--------------+        +---------------+
```

### 1.2.2 边界说明

结论先行：明确"做什么"与"不做什么"，避免范围蔓延。

- 做：对话、检索、工具调用、会话管理、反馈收集。
- 不做：语音交互、多模态（图像/视频）、主动推送、模型训练。

# 2. 目标用户与场景

## 2.1 用户画像

### 2.1.1 用户总览

结论先行：三类用户诉求不同，需在同一入口下做差异化权限与话术。

| 用户 | 场景 | 关键诉求 |
|------|------|----------|
| 内部员工 | 查询制度、流程、技术文档 | 准确、可溯源 |
| 外部客户 | 产品咨询、售后支持 | 快速、友好 |
| 客服人员 | 辅助应答、知识检索 | 高效、可复用 |

### 2.1.2 差异化诉求

- 内部员工：关心制度时效与出处，权限较高，可访问内部知识库与部分工具。
- 外部客户：关心产品、价格、售后，权限受限，仅访问公开知识与自身订单。
- 客服人员：需要辅助模式与话术模板，给出建议答案与引用后由人工确认发送。

## 2.2 典型场景

### 2.2.1 知识问答场景

用户问："差旅费报销时限是多久？"，系统检索制度文档并引用原文作答。

### 2.2.2 任务办理场景

用户问："帮我查下订单 A123 的物流"，系统调用订单查询工具返回结果。

### 2.2.3 多轮记忆场景

用户先答"我叫张三"，后问"我叫什么？"，系统需在上下文内正确回忆。

# 3. 功能范围

## 3.1 核心功能

### 3.1.1 功能清单

结论先行：本期以对话为核心，围绕"记忆、流式、检索、工具、会话、反馈"六项展开。

```text
核心功能：
├── 多轮对话（记忆）
├── 流式输出
├── 知识库检索（RAG）
├── 工具调用（查订单、查库存）
├── 会话管理（多会话、历史）
└── 反馈收集（点赞/点踩）

非目标（本期不做）：
├── 语音交互
├── 多模态
└── 主动推送
```

### 3.1.2 关键能力要点

- 多轮对话：记忆窗口保留最近 N 轮，超限压缩为摘要，会话之间互不串扰。
- 流式输出：采用 SSE，首字尽快返回，事件协议为 start/message/done/error。
- 知识库检索：文档分块、向量化、入库，查询时相似度召回 + 重排，并标注引用。
- 工具调用：声明式注册工具，权限与意图双重过滤后动态挂载，并控制超时、重试与幂等。

## 3.2 会话与反馈

- 多会话：用户可创建、切换、删除会话。
- 历史：分页拉取历史消息。
- 反馈：点赞/点踩 + 可选文字评论，负面回流评测集。

## 3.3 非目标

结论先行：本期明确排除语音、多模态、主动推送，以聚焦核心链路。

| 非目标 | 原因 | 后续 |
|--------|------|------|
| 语音交互 | 链路长、成本高 | 远期规划 |
| 多模态 | 需求未验证 | 中期评估 |
| 主动推送 | 合规风险高 | 暂不做 |

# 4. 总体架构

## 4.1 架构分层

### 4.1.1 分层总览

结论先行：采用接入层、应用层、能力层、数据层四层架构，职责清晰、可独立扩展。

```text
+-------------------------------------------+
| 接入层: Web / App / 开放 API               |
+-------------------------------------------+
| 应用层: 对话编排 / 会话 / 反馈 / 权限      |
+-------------------------------------------+
| 能力层: 检索 / 工具 / 记忆 / 护栏 / 模型   |
+-------------------------------------------+
| 数据层: PG / PGVector / Redis / 对象存储   |
+-------------------------------------------+
```

### 4.1.2 各层职责

- 接入层：提供 SSE 与普通接口，负责鉴权、限流与 Trace 透传。
- 应用层：ChatFacade 编排对话，SessionService 管理会话与锁，FeedbackService 收集反馈。
- 能力层：Retriever 检索重排，ToolRegistry 注册路由，Memory 读写记忆，Guardrail 输入输出护栏。
- 数据层：PG/PGVector 存业务与向量，Redis 存会话与缓存。

## 4.2 关键数据流

### 4.2.1 一次对话请求

结论先行：请求依次经过鉴权、加锁、检索、组装、生成、流式返回。

```text
Client -> Gateway -> ChatController -> ChatFacade
        -> SessionLock -> Retriever -> PromptBuilder
        -> ChatModel(stream) -> SSE -> Client
```

### 4.2.2 检索增强流程

```text
Query -> Embedding -> 向量检索(TopK) -> Rerank -> TopN -> 组装提示
```

## 4.3 部署拓扑

| 组件 | 部署形态 | 说明 |
|------|----------|------|
| 应用服务 | 无状态多副本 | 水平扩展 |
| Redis | 主从/集群 | 会话与锁 |
| PostgreSQL | 主从 | 业务与向量 |
| 网关 | 集群 | 流式不缓冲 |

# 5. 数据模型

## 5.1 会话与消息

### 5.1.1 表结构

结论先行：会话与消息落库用于历史与审计，热数据在 Redis。

```sql
CREATE TABLE chat_session (
    id          BIGSERIAL PRIMARY KEY,
    session_id  VARCHAR(64) NOT NULL UNIQUE,
    tenant_id   VARCHAR(64) NOT NULL,
    user_id     VARCHAR(64) NOT NULL,
    title       VARCHAR(200),
    status      SMALLINT DEFAULT 1,
    created_at  TIMESTAMPTZ DEFAULT now(),
    updated_at  TIMESTAMPTZ DEFAULT now()
);

CREATE TABLE chat_message (
    id          BIGSERIAL PRIMARY KEY,
    session_id  VARCHAR(64) NOT NULL,
    role        VARCHAR(16) NOT NULL,
    content     TEXT NOT NULL,
    token_in    INT DEFAULT 0,
    token_out   INT DEFAULT 0,
    latency_ms  INT DEFAULT 0,
    created_at  TIMESTAMPTZ DEFAULT now()
);

CREATE INDEX idx_msg_session ON chat_message(session_id, created_at);
```

### 5.1.2 Redis 结构

| Key | 类型 | 用途 | TTL |
|-----|------|------|-----|
| session:mem:{id} | List | 记忆消息 | 2h |
| session:lock:{id} | String | 分布式锁 | 30s |
| cache:qa:{hash} | String | 答案缓存 | 10m |

## 5.2 知识与向量

```sql
CREATE TABLE kb_document (
    id          BIGSERIAL PRIMARY KEY,
    tenant_id   VARCHAR(64) NOT NULL,
    title       VARCHAR(300),
    source      VARCHAR(500),
    version     INT DEFAULT 1,
    created_at  TIMESTAMPTZ DEFAULT now()
);

CREATE TABLE kb_chunk (
    id          BIGSERIAL PRIMARY KEY,
    document_id BIGINT NOT NULL,
    tenant_id   VARCHAR(64) NOT NULL,
    content     TEXT NOT NULL,
    embedding   vector(1536)
);
```

## 5.3 反馈与评测

```sql
CREATE TABLE chat_feedback (
    id          BIGSERIAL PRIMARY KEY,
    session_id  VARCHAR(64) NOT NULL,
    message_id  BIGINT NOT NULL,
    user_id     VARCHAR(64) NOT NULL,
    rating      SMALLINT NOT NULL,
    comment     TEXT,
    created_at  TIMESTAMPTZ DEFAULT now()
);
```

# 6. 接口设计

## 6.1 对话接口

### 6.1.1 请求与响应

结论先行：对话采用 SSE，事件类型固定四类，便于前端统一处理。

| 项 | 说明 |
|----|------|
| 方法 | GET |
| 路径 | /api/chat/stream |
| 参数 | message、X-Session-Id |
| 响应 | text/event-stream |

### 6.1.2 SSE 事件协议

| 事件 | 数据 | 说明 |
|------|------|------|
| start | {} | 开始 |
| message | 文本片段 | 增量内容 |
| done | {} | 结束 |
| error | {message} | 异常 |

## 6.2 会话与反馈接口

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | /api/sessions | 会话列表 |
| POST | /api/sessions | 新建会话 |
| DELETE | /api/sessions/{id} | 删除会话 |
| GET | /api/sessions/{id}/messages | 历史消息 |
| POST | /api/feedback | 提交反馈 |

## 6.3 错误码

| 码 | 含义 | 处理 |
|----|------|------|
| 40001 | 参数错误 | 提示用户 |
| 40100 | 未认证 | 跳登录 |
| 40300 | 无权限 | 提示 |
| 42900 | 会话忙/限流 | 重试 |
| 50000 | 内部错误 | 降级 |

# 7. 非功能需求

## 7.1 性能与容量

### 7.1.1 延迟预算

结论先行：首字延迟目标 < 1s，需在链路各环节分配预算。

| 环节 | 预算 |
|------|------|
| 鉴权 + 网关 | 20ms |
| 会话加锁 | 20ms |
| 检索 | 150ms |
| 模型首 Token | 600ms |
| 网络回传 | 100ms |

### 7.1.2 容量估算

结论先行：按 100 QPS、单会话平均 5 轮估算资源。

| 指标 | 假设 | 估算 |
|------|------|------|
| 峰值 QPS | 100 | - |
| 单请求 Token | 输入 2000/输出 500 | - |
| 日请求量 | 100 QPS × 8h | ~288 万 |
| 并发连接 | SSE 长连接 | 数百 |

## 7.2 可用性与安全

### 7.2.1 可用性

| 维度 | 要求 |
|------|------|
| 可用性 | 99.9% |
| 故障恢复 | 多副本 + 熔断降级 |
| 数据持久 | 主从 + 备份 |

### 7.2.2 安全

| 维度 | 要求 |
|------|------|
| 注入防御 | 输入过滤 + 提示隔离 + 输出校验 |
| 租户隔离 | 数据按 tenant_id 过滤 |
| 越权防护 | 工具权限校验 |
| 隐私 | 日志脱敏 |

## 7.3 成本

结论先行：单会话成本目标 < ¥0.05，通过分层路由与缓存达成。

| 手段 | 效果 |
|------|------|
| 模型分层 | 简单问题走小模型 |
| 答案缓存 | 高频问题零成本 |
| 上下文裁剪 | 减少输入 Token |

# 9. 技术选型

## 9.1 选型总览

### 9.1.1 组件选型

结论先行：以主流框架 + 中模型 + 复用现有存储为原则。

| 组件 | 选择 | 理由 |
|------|------|------|
| 框架 | Spring AI / LangChain4j | 主流 |
| 模型 | 中模型（qwen-plus/GPT-4o-mini） | 性价比 |
| 向量库 | PGVector | 复用 PG |
| 缓存 | Redis | 会话 + 缓存 |
| 记忆 | Redis | 高性能 |
| 前端 | SSE | 流式 |

### 9.1.2 框架对比

| 框架 | 优势 | 劣势 |
|------|------|------|
| Spring AI | 与 Spring 生态融合 | 生态较新 |
| LangChain4j | 功能丰富 | 抽象较多 |
| 自研 | 完全可控 | 成本高 |

### 9.1.3 模型分层

| 层级 | 模型 | 适用 |
|------|------|------|
| 小 | 小参数模型 | 分类、闲聊 |
| 中 | qwen-plus | 主对话 |
| 大 | 旗舰模型 | 复杂推理兜底 |

## 9.2 选型风险

| 风险 | 应对 |
|------|------|
| 框架 API 变更 | 抽象隔离层 |
| 模型涨价 | 多供应商 + 路由 |
| 向量库性能 | 压测 + 索引调优 |

# 11. 风险与应对
