# 1. 模块定位

本模块把前面所有知识组装成**可写进简历的完整项目**。每个项目统一按「需求 → 设计 → 实现 → 评测/上线」四段式展开。

## 1.1 定位说明

前面的模块解决「单点能力」：RAG 检索、工具调用、记忆管理、可靠性、观测。本模块解决「组合能力」：如何把这些能力拼成一个真正能演示、能讲述、能落地的系统。

一句话概括：这里是**知识的组装车间**，而不是新知识的讲授课堂。

## 1.2 与其他模块关系

```
  5_RAG ─┐
  6_AgentCore ─┤
  7_ToolsAndProtocols ─┼─► 16_Applications ─► 17_Interview
  8_Memory ─┤
  9_Frameworks ─┘
```

- 上游：本模块消费前面模块的能力，不重复讲原理。
- 下游：本模块产出项目经验，直接服务于面试模块。

## 1.3 使用方式

- 先读本 README，确定要做哪个项目。
- 再进入项目子目录，按四段式逐个文件阅读。
- 最后对照评测清单，确认自己是否真正跑通。

建议边读边动手：每读一个设计文档，就在本地把对应链路搭出来，避免只看不练。

# 2. 学习目标

## 2.1 能力目标

- 独立完成端到端 Agent 应用的设计与实现。
- 把 RAG、工具、记忆、可靠性、观测等能力组合落地。
- 形成可演示、可讲述、可面试的项目经验。

## 2.2 产出目标

- 每个项目一份可运行的代码仓库。
- 每个项目一份架构图与数据流说明。
- 每个项目一份评测报告与上线清单。
- 一段三分钟能讲清的项目介绍。

## 2.3 自检标准

| 检查项 | 达标标志 |
|--------|----------|
| 可运行 | 本地一条命令启动 |
| 可演示 | 有 3 个典型场景录屏 |
| 可讲述 | 能解释每个设计取舍 |
| 可评测 | 有量化指标与评测集 |

四个「可」缺一不可：只可运行不可讲述，说明没想清楚设计；只可讲述不可评测，说明无法证明效果。

# 3. 文件清单

每个项目子目录统一包含四个文件：

| 文件 | 大纲 |
|------|------|
| `1_overview.md` | 需求背景、目标用户、功能范围、验收标准 |
| `2_design.md` | 架构设计、技术选型、数据流、接口设计 |
| `3_implementation.md` | 核心实现、关键代码、难点与解决方案 |
| `4_evaluation.md` | 评测方案、指标、上线与运维要点 |

## 3.1 统一四段式

### 3.1.1 各文件职责

| 文件 | 回答的问题 | 关键产出 |
|------|------------|----------|
| `1_overview.md` | 为什么做、给谁用 | 需求与验收标准 |
| `2_design.md` | 怎么设计 | 架构图、接口 |
| `3_implementation.md` | 怎么实现 | 关键代码、难点 |
| `4_evaluation.md` | 好不好、稳不稳 | 指标、上线清单 |

### 3.1.2 命名与目录

目录名使用大驼峰（如 `KnowledgeBase`），文件名使用下划线加序号前缀，保证排序稳定。

### 3.1.3 写作模板

每个文件都遵循「结论先行、再展开论证」的顺序，方便快速浏览与复习。

# 4. 学习顺序与依赖

## 4.1 推荐路径

```
先做 KnowledgeBase（RAG 打底） → Chatbot（加记忆与流式）
      → CodingAgent / DataAnalysisAgent（加工具）
      → ResearchAgent（加多轮与规划）
      → CustomerService / WorkflowAutomation（加权限与流程）
      → MultiAgentSystem（综合）
```

## 4.2 依赖关系

- 上游依赖：`5_RAG`、`6_AgentCore`、`7_ToolsAndProtocols`、`8_Memory`、`9_Frameworks`。
- 下游影响：`17_Interview`（项目经验来源）。

### 4.2.1 依赖说明

先做 KnowledgeBase 是因为 RAG 是最基础也最容易出效果的链路；有了它，后续项目都能复用检索组件。

### 4.2.2 跳过顺序的风险

跳过 KnowledgeBase 直接做 MultiAgentSystem，往往会在检索质量、上下文管理上反复踩坑，反而更慢。

## 4.3 时间安排建议

| 阶段 | 项目 | 建议投入 |
|------|------|:--------:|
| 打底 | KnowledgeBase、Chatbot | 各 1 周 |
| 加工具 | CodingAgent、DataAnalysisAgent | 各 1 周 |
| 加规划 | ResearchAgent | 1 周 |
| 加流程 | CustomerService、WorkflowAutomation | 各 1 周 |
| 综合 | MultiAgentSystem | 2 周 |

# 5. 项目通用方法论

## 5.1 需求到设计

- 明确目标用户与核心场景，砍掉非必要功能。
- 用一句话定义成功指标，例如「问答准确率大于 85%」。
- 先画数据流，再选技术栈。

## 5.2 设计到实现

- 优先保证一条主链路跑通，再做能力扩展。
- 每个外部依赖都要有超时、重试与降级。
- 关键路径加日志与指标埋点。

## 5.3 实现到评测

- 用固定评测集做回归，避免「感觉变好了」。
- 评测与可观测性是项目从 Demo 走向生产的分水岭。
- 上线前跑一遍检查清单，灰度从低风险场景开始。

## 5.4 常见误区

### 5.4.1 只追新不重稳

盲目堆砌新框架，却忽略了超时、重试、幂等这些基本功，系统一压就垮。

### 5.4.2 没有评测就上线

只靠主观感受判断效果，无法发现回归，也无法向他人证明改进。

### 5.4.3 功能过多过散

试图一次做完所有功能，结果每条链路都半成品。应集中做深一条主链路。

# 6. 项目速览

## 6.1 对话与知识类

### 6.1.1 Chatbot

重点是流式输出与多轮记忆，考验上下文管理与体验优化。首字延迟（TTFT）是关键体验指标。

### 6.1.2 KnowledgeBase

重点是检索质量与引用溯源，考验切分、召回与重排。答案必须能指回原文，否则不可信。

### 6.1.3 CustomerService

在知识库之上叠加工单与转人工，考验权限与状态管理。转人工的触发条件是设计难点。

## 6.2 工具与执行类

### 6.2.1 CodingAgent

读写代码、执行测试，考验沙箱隔离与失败恢复。任何执行都要有超时与资源限制。

### 6.2.2 DataAnalysisAgent

自然语言转查询与图表，考验结构化输出与结果校验。SQL 必须做安全审查，禁止写操作。

## 6.3 流程与协作类

### 6.3.1 WorkflowAutomation

审批与编排，考验可靠性、补偿与审计。高额与敏感操作必须人工介入。

### 6.3.2 ResearchAgent

多轮检索与报告生成，考验规划与信息聚合。需要去重与事实核对，避免编造。

### 6.3.3 MultiAgentSystem

多智能体协作，考验通信、分工与冲突消解。角色边界要清晰，否则会互相覆盖。

# 7. 简历与面试表达

## 7.1 STAR 结构

用 Situation（背景）、Task（任务）、Action（行动）、Result（结果）组织项目描述，突出量化结果。

## 7.2 亮点提炼

- 一条主链路讲深，胜过罗列十个功能。
- 主动讲踩坑与取舍，体现工程判断力。
- 用指标说话，避免「效果不错」这类空话。

# 8. 项目验收标准

## 8.1 功能验收

### 8.1.1 主链路

主链路在无故障时 100% 跑通，且连续演示 3 次结果稳定。

### 8.1.2 异常路径

依赖超时、非法输入、权限不足等异常路径均有明确处理与提示。

## 8.2 质量验收

### 8.2.1 指标达标

核心指标达到 `4_evaluation.md` 设定的目标，且评测可复现。

### 8.2.2 代码与文档

代码可一键启动，README 说明清楚，架构图与数据流图齐备。

# 9. 关键知识点速览

## 9.1 核心要点

- 项目要能讲清「为什么这样设计」与「踩过哪些坑」。
- 评测与可观测性是项目从 Demo 走向生产的分水岭。
- 优先保证一条主链路跑通，再做能力扩展。
- 每个项目都应有明确的成功指标。

## 9.2 落地提醒

- 四段式结构统一，便于横向对比与快速复习。
- 上游模块的能力在本模块组合，下游面试模块在此取材。
