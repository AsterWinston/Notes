# 1. 背景与问题定义

## 1.1 业务背景

结论先行：企业内部存在大量"规则明确但处理繁琐"的流程，其瓶颈不在规则本身，而在信息搬运与判断环节，流程自动化 Agent（智能体）正是为此而生。

机制上，企业流程可分为两类：

- 确定性流程：审批流转、状态机跳转、通知发送，规则可枚举、可代码化。
- 判断性流程：申请是否合理、金额是否超标、事由是否充分，需要经验与上下文。

传统工作流引擎（Workflow Engine）擅长前者，LLM（大语言模型）擅长后者。将两者组合，才能覆盖完整链路。

### 1.1.1 典型流程场景

| 场景 | 触发方式 | 判断点 | 人工介入 |
|------|----------|--------|----------|
| 报销审批 | 员工提交 | 金额/类别/重复 | 超标需主管 |
| 请假审批 | 员工提交 | 天数/余额/冲突 | 长假需经理 |
| 工单流转 | 客服创建 | 优先级/归属 | 升级需主管 |
| 采购申请 | 部门发起 | 预算/供应商 | 大额需财务 |
| 合同用印 | 销售发起 | 条款/权限 | 特殊条款法务 |
| 权限开通 | 员工申请 | 角色/时效 | 高权限需审批 |

这些场景的共性：表单字段多、判断依赖经验、流程可枚举、结果需留痕。

### 1.1.2 痛点与现有系统局限

```text
员工填单（漏项） → 审批人来回问 → 补充信息 → 再审批
        │                 │              │
        └── 平均 1~3 天 ──┴── 反复沟通 ──┘
```

- 表单字段多，漏填、错填导致退回。
- 审批人凭经验判断，标准不一致。
- 流程状态分散在邮件/IM，难以追踪。
- 高频重复审批消耗大量管理精力。

现有方案及其局限：

| 现有方案 | 局限 |
|----------|------|
| 纯表单 + 工作流引擎 | 无法理解自然语言，字段仍靠人填 |
| 纯 LLM 对话助手 | 无状态、无补偿、不可审计 |
| 规则引擎 | 规则写死，无法处理语义模糊 |
| RPA 脚本 | 脆弱、难维护、异常即中断 |

结论：单一方案都无法同时满足"理解、可靠、可审计"三重目标。

### 1.1.3 术语表

| 术语 | 英文 | 含义 |
|------|------|------|
| 智能体 | Agent | 承担理解与判断的 LLM 应用 |
| 工作流引擎 | Workflow Engine | 负责编排与持久化的执行引擎 |
| 槽位 | Slot | 表单中的结构化字段 |
| 槽位填充 | Slot Filling | 从文本抽取并补全字段 |
| 补偿 | Compensation | 失败时回滚已执行步骤 |
| 长事务 | Saga | 由补偿保证最终一致的模式 |
| 幂等 | Idempotent | 重复执行结果不变 |
| 留痕 | Audit Trail | 全流程操作记录 |

## 1.2 问题定义与价值

### 1.2.1 核心命题

结论：用 LLM 承担"理解自然语言 + 判断合理性"，用工作流引擎承担"编排 + 持久化 + 补偿"，二者边界清晰。

三个待解决的核心问题：

1. 自然语言如何变成结构化表单？（槽位填充）
2. 判断如何做到可解释、可审计？（规则 + 建议分离）
3. 长流程中断如何恢复？（状态持久化 + Saga 补偿）

### 1.2.2 三种方案对比

| 方案 | 理解能力 | 可靠性 | 可审计 | 结论 |
|------|----------|--------|--------|------|
| 纯工作流引擎 | 弱 | 强 | 强 | 字段仍需人工 |
| 纯 LLM Agent | 强 | 弱 | 弱 | 不可用于生产 |
| 引擎 + Agent | 强 | 强 | 强 | 采用 |

### 1.2.3 量化价值与成功标准

| 指标 | 现状 | 目标 | 衡量方式 |
|------|------|------|----------|
| 平均处理时长 | 1~3 天 | < 4 小时 | 流程埋点 |
| 表单一次通过率 | 约 50% | > 85% | 退回率统计 |
| 人工审批工作量 | 100% | 下降 40% | 自动通过占比 |
| 流程可追溯性 | 邮件散落 | 全链路留痕 | 审计查询 |
| 审批标准一致性 | 因人而异 | 统一规则 | 抽检一致率 |

成功定义（全部满足才算成功）：

- 员工一句话即可发起，系统主动补齐缺失信息。
- 校验结论可解释、可追溯，审批人可一键采纳或推翻。
- 任意节点故障后可自动恢复，不丢单。
- 全流程可审计，满足内控与合规检查。

常见反模式：

| 反模式 | 后果 | 纠正 |
|--------|------|------|
| 让 LLM 直接决定审批 | 不可审计、风险高 | 只给建议 |
| 状态存内存 | 重启丢单 | 持久化 |
| 无幂等设计 | 重复扣款 | 幂等键 |
| 提示词写死业务规则 | 难维护 | 规则外置 |

# 2. 目标用户与角色

## 2.1 用户画像

结论先行：系统服务三类角色，员工重"便捷"，审批人重"辅助"，管理员重"可控"。

### 2.1.1 员工

- 诉求：一句话发起申请、实时查看进度、少填表。
- 交互形态：IM 机器人 / Web 表单 / 移动端。
- 关键指标：发起耗时、一次通过率。

### 2.1.2 审批人

- 诉求：看到申请摘要、风险提示、历史相似案例，快速决策。
- 关键：Agent 只给建议，不代替决策。
- 关键指标：审批耗时、建议采纳率。

### 2.1.3 流程管理员

- 诉求：流程监控、卡点定位、异常处理、制度配置。
- 关键：可配置、可回放、可干预。
- 关键指标：卡单率、补偿成功率。

## 2.2 权限与职责矩阵

| 能力 | 员工 | 审批人 | 管理员 |
|------|------|--------|--------|
| 发起流程 | 是 | 是 | 是 |
| 查看本人流程 | 是 | 是 | 是 |
| 查看全部流程 | 否 | 否 | 是 |
| 审批决策 | 否 | 是 | 否 |
| 修改制度/阈值 | 否 | 否 | 是 |
| 手动补偿/终止 | 否 | 否 | 是 |
| 查看审计日志 | 本人 | 相关 | 全部 |

> 职责边界：Agent 属于"辅助角色"，不持有最终审批权限。

## 2.3 用户旅程

```text
员工：  发起 ─▶ 补充 ─▶ 等待 ─▶ 结果通知
          │                        ▲
审批人：  │      收到待办 ─▶ 看建议 ─┘
          │            │
管理员：  └── 监控看板 ─┴─ 异常干预
```

## 2.4 角色协作流程

结论：三方协作以"流程实例"为纽带，各角色在不同状态介入。

```text
状态          员工      审批人      管理员
CREATED       发起        -           -
SLOT_FILLING  补充        -           -
VALIDATING     -          -          可干预
PENDING       等待      决策         监控
COMPLETED     收通知      -           -
FAILED         -          -          补偿
```

协作规则：

- 员工只能操作本人实例。
- 审批人只能决策分配给自己或本部门的待办。
- 管理员可查看全部并执行补偿/终止。

# 3. 功能范围

## 3.1 核心功能

结论：核心功能围绕"发起 → 填充 → 校验 → 审批 → 补偿"闭环展开。

```text
核心功能：
├── 流程发起（自然语言触发）
├── 表单自动填充（槽位填充）
├── 规则校验
├── 智能审批建议
├── 流程状态查询
└── 异常处理与补偿
```

### 3.1.1 流程发起

- 自然语言识别意图（发起 / 查询 / 补充信息）。
- 创建流程实例并返回流程 ID。
- 支持多轮交互补齐信息。
- 支持从模板或历史申请快速复制。

### 3.1.2 表单自动填充

- 从自然语言抽取槽位（slot），如金额、类别、事由、日期。
- 缺失字段主动追问，已填字段不覆盖。
- 抽取结果需可人工修正。
- 低置信度字段标记待确认。

### 3.1.3 校验、审批与查询补偿

- 代码校验：确定性规则（金额阈值、查重）。
- LLM 校验：模糊规则（事由合理性）。
- 输出统一为 APPROVE / REVIEW / REJECT 三态。
- 建议附理由与置信度，供审批人参考。
- 状态查询：返回当前节点、进度、待办人。
- 异常补偿：任一子步骤失败，按逆序回滚已执行步骤。
- 超时提醒与自动升级。

## 3.2 非目标与边界

结论：明确不做的事，避免范围蔓延。

```text
非目标：
├── 替代工作流引擎
├── 复杂 BPMN 建模
```

### 3.2.1 明确不做的事

| 非目标 | 原因 |
|--------|------|
| 自研流程引擎 | 复用成熟引擎，聚焦 Agent |
| 可视化 BPMN 编辑器 | 由引擎厂商提供 |
| 全自动无人审批 | 合规要求人工确认 |
| 财务记账核心 | 对接既有财务系统 |
| 跨企业流程编排 | 超出当前边界 |

### 3.2.2 反例（不应触发 Agent 的场景）

- 制度明确的硬性拒绝（如超期报销）→ 直接代码拒绝，无需 LLM。
- 结构化 API 已能完成的查询 → 直接查库，不绕 LLM。
- 高风险金额审批 → 必须人工，Agent 仅提示。
- 已撤销流程的重复输入 → 幂等返回，不重复处理。

## 3.3 功能优先级

| 功能 | 优先级 | 理由 |
|------|--------|------|
| 流程发起 | P0 | 入口能力 |
| 槽位填充 | P0 | 决定体验 |
| 规则校验 | P1 | 保证合规 |
| 审批建议 | P2 | 提效增值 |
| 异常补偿 | P3 | 可靠性兜底 |

# 4. 非功能需求

## 4.1 需求矩阵

结论：可靠性、一致性、可审计、合规是四条硬约束。

| 维度 | 要求 | 说明 |
|------|------|------|
| 可靠 | 长流程可恢复 | 任意节点重启后可续跑 |
| 一致 | 状态持久化 | 状态与业务数据一致 |
| 可审计 | 全流程留痕 | 每步操作可追溯 |
| 合规 | 审批合规 | 关键节点人工确认 |
| 性能 | 低延迟 | 首轮响应 < 3 秒 |
| 可扩展 | 水平扩展 | Agent 无状态 |

## 4.2 量化指标（SLO）

| 指标 | 目标值 |
|------|--------|
| 流程实例恢复成功率 | ≥ 99.9% |
| 状态写入延迟 P99 | < 100 ms |
| 审计日志完整率 | 100% |
| 补偿成功率 | ≥ 99% |
| 槽位抽取准确率 | ≥ 90% |
| 首轮响应 P95 | < 3 s |
| 系统可用性 | ≥ 99.9% |

## 4.3 安全与合规

### 4.3.1 数据安全

- 申请数据脱敏后再入 LLM，避免敏感信息外泄。
- 传输加密（TLS）、存储加密、访问最小权限。
- LLM 调用记录留存，满足审计与追溯。

### 4.3.2 权限与审计

| 项 | 要求 |
|----|------|
| 身份认证 | 统一 SSO |
| 操作授权 | 基于角色的访问控制（RBAC） |
| 审计日志 | 不可篡改、可查询 |
| 数据留存 | 满足内控年限要求 |

# 6. 技术选型

## 6.1 选型对比表

结论：工作流引擎选 Flowable 或 Temporal，LLM 选中等规模模型承担判断节点。

| 组件 | 选择 | 备选 | 说明 |
|------|------|------|------|
| 工作流 | Flowable / Temporal | Camunda | 长流程持久化 |
| LLM | 中模型（判断节点） | 大模型 | 成本与延迟平衡 |
| 状态 | 数据库 | Redis | 强一致持久化 |
| 消息 | 队列 | - | 异步解耦 |

### 6.1.1 工作流引擎对比

| 维度 | Flowable | Temporal | Camunda |
|------|----------|----------|---------|
| 模型 | BPMN | 代码即工作流 | BPMN |
| 持久化 | 数据库 | 服务端 | 数据库 |
| 补偿 | 支持 | 原生 Saga | 支持 |
| 学习曲线 | 中 | 中 | 中 |
| 适用 | 传统审批 | 微服务编排 | 企业级 |

### 6.1.2 LLM 选型

- 判断节点用中模型：延迟低、成本可控。
- 复杂抽取可回退大模型，需加超时与降级。
- 关键决策节点建议双模型投票或人工兜底。

### 6.1.3 存储、消息与选型决策

| 组件 | 用途 | 选型建议 |
|------|------|----------|
| 关系库 | 流程状态、审计 | PostgreSQL / MySQL |
| 缓存 | 会话、限流 | Redis |
| 队列 | 异步任务 | Kafka / RabbitMQ |

选型决策记录：

| 决策 | 选择 | 备选 | 理由 |
|------|------|------|------|
| 引擎 | Flowable | Temporal | 团队熟悉 BPMN |
| 模型 | 中模型 | 大模型 | 延迟与成本 |
| 状态 | 关系库 | 内存 | 强一致 |
| 补偿 | Saga | 两阶段提交 | 松耦合 |

# 8. 风险与应对

## 8.1 风险登记表

结论：风险集中在中断、误审批、补偿失败与状态不一致四类。

| 风险 | 应对 |
|------|------|
| 流程中断 | 状态持久化 + 恢复 |
| 误审批 | 关键节点人工确认 |
| 补偿失败 | 告警 + 人工介入 |
| 状态不一致 | 事务 + 幂等 |
| LLM 不稳定 | 约束输出 + 降级 |
| 数据泄露 | 脱敏 + 权限 |

## 8.2 兜底策略

| 场景 | 兜底动作 |
|------|----------|
| LLM 超时 | 降级为人工审批 |
| 引擎不可用 | 熔断 + 排队重试 |
| 补偿失败 | 告警 + 工单人工处理 |
| 数据冲突 | 以数据库为准 + 对账 |
| 抽取失败 | 转纯表单人工填写 |

## 8.3 风险监控指标

| 指标 | 阈值 | 动作 |
|------|------|------|
| 抽取失败率 | > 10% | 切换备用模型 |
| 补偿失败数 | > 0 | 立即告警 |
| 卡单超时数 | 上升 | 排查引擎 |
| 建议采纳率 | < 60% | 复盘提示词 |

## 8.4 应急预案

结论：对每类风险预设"检测—止血—恢复"三段式预案。

| 风险 | 检测 | 止血 | 恢复 |
|------|------|------|------|
| 引擎宕机 | 健康检查 | 熔断 + 排队 | 重启/切主 |
| LLM 故障 | 错误率 | 降级人工 | 切备用模型 |
| 补偿失败 | 告警 | 暂停流程 | 人工补偿 |
| 数据错乱 | 对账 | 冻结写 | 修复 + 回放 |

应急演练：每季度至少一次故障注入演练，验证预案有效。

# 9. 小结

## 9.1 核心结论

- 目标是流程自动化 + 智能判断。
- 核心：发起、填充、校验、审批、补偿。
- 可靠性与可审计是硬要求。
- 用工作流引擎编排，LLM 承担判断节点。
- 确定逻辑给引擎，判断逻辑给 Agent。
- 关键节点必须人工确认，Agent 仅给建议。
- 以 SLO 与评测集作为上线门槛。

## 9.2 落地建议

- 先跑通 P0 的发起与填充，再逐阶段增强。
- 规则尽量前置，减少 LLM 调用与不确定性。
- 自动通过阈值保持保守，随数据积累再放宽。
- 全流程留痕与告警，作为长期运营基础设施。
