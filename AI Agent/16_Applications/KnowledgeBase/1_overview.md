# 1. 背景与问题定义

**结论先行**：企业内部知识分散在 Confluence、PDF 手册、Word 文档、Wiki 中，员工查找困难且效率低下；本项目要构建一套基于 RAG（Retrieval-Augmented Generation，检索增强生成）的知识库问答系统，用自然语言直达答案，并给出可溯源的引用。

## 1.1 业务背景

### 1.1.1 知识分散的现状

企业知识资产分布在多个系统中，格式各异、权限各异、更新频率各异，员工需要跨系统反复检索。

| 来源 | 格式 | 典型内容 | 更新频率 |
|------|------|----------|----------|
| Confluence | 富文本/HTML | 制度、流程、项目文档 | 高 |
| 文件系统 | PDF/Word/Excel | 手册、合同、规范 | 中 |
| Wiki | Markdown | 技术文档、FAQ | 中 |
| 邮件/IM 归档 | 纯文本 | 通知、决议 | 低 |

### 1.1.2 检索困境的根因

传统关键词检索存在三类问题，这也是引入语义检索的根本原因。

- 词汇鸿沟：用户问"报销多久内提交"，文档写"费用发生后 30 日内办理"，关键词无法命中。
- 上下文丢失：长文档切碎后失去章节语义，单块难以自洽。
- 权限失配：跨部门检索可能返回无权访问内容，存在越权风险。

一个典型的失败示例如下，关键词检索无法理解同义表达：

```java
// 关键词检索：精确匹配失败
boolean hit = text.contains("报销");          // 文档写的是"费用结算"
// 语义检索：向量相似度可命中
double sim = cosine(embed("报销多久内提交"), embed("费用发生后 30 日内办理"));
// sim 可能达到 0.8 以上，从而被召回
```

### 1.1.3 现状量化

为立项提供数据支撑，需要对现状做基线测量。

| 指标 | 现状基线 | 目标 |
|------|----------|------|
| 平均查找耗时 | 8 分钟 | < 1 分钟 |
| 一次找对率 | 约 50% | > 85% |
| 重复咨询工单 | 高 | 显著下降 |

## 1.2 为什么选择 RAG

### 1.2.1 RAG 与微调、纯 LLM 的对比

| 方案 | 知识更新 | 幻觉控制 | 成本 | 可溯源 | 适用性 |
|------|----------|----------|------|--------|--------|
| 纯 LLM | 差 | 差 | 低 | 无 | 通用闲聊 |
| 微调 | 差（需重训） | 中 | 高 | 无 | 固定风格/领域语感 |
| RAG | 好（改文档即生效） | 好（可引用校验） | 中 | 强 | 企业知识问答 |

### 1.2.2 RAG 工作流程

```text
离线：文档 → 解析 → 切分 → 向量化 → 向量库
在线：问题 → 检索 → 重排 → 生成 → 引用
```

检索质量决定上限，生成质量决定下限。因此本项目把大部分优化精力放在检索链路上。

### 1.2.3 适用边界

RAG 适合"答案存在于文档中、需要引用、更新频繁"的场景；不适合需要复杂推理、跨文档数值计算或强实时数据的场景。

- 适合：政策问答、手册查询、流程说明。
- 不适合：实时股价、复杂财务报表计算、开放式创作。

## 1.3 项目定位

### 1.3.1 定位声明

- 定位：面向内部员工的知识问答助手，不是通用聊天机器人。
- 边界：只回答知识库内的问题，无依据时明确拒答。
- 原则：先检索后生成，引用可点击溯源。

### 1.3.2 成功标准

| 维度 | 成功标准 |
|------|----------|
| 准确性 | 忠实度 ≥ 90% |
| 安全性 | 零越权 |
| 时效性 | 变更 1 小时内生效 |
| 体验 | P95 延迟 < 3s |

# 2. 目标用户与场景

**结论先行**：系统服务于全体员工的查询需求，但不同角色的高频场景与精度要求不同，需按角色差异化设计。

## 2.1 用户画像

### 2.1.1 用户角色表

| 用户 | 需求 | 高频场景 | 精度要求 |
|------|------|----------|----------|
| 全体员工 | 查询制度、流程、手册 | 报销、考勤、假期 | 高 |
| 新员工 | 快速上手 | 入职指引、工具使用 | 中 |
| HR/行政 | 政策解答 | 政策口径、福利 | 高 |
| 技术支持 | 技术文档查询 | 故障处理、接口说明 | 高 |

### 2.1.2 角色权限矩阵

| 知识域 | 全体员工 | HR | 技术支持 |
|--------|----------|----|----------|
| 公共制度 | 可读 | 可读 | 可读 |
| 人事政策 | 部分 | 可读 | 不可读 |
| 技术文档 | 可读 | 不可读 | 可读 |
| 财务细则 | 部分 | 不可读 | 不可读 |

### 2.1.3 用户访谈要点

- 最常问的问题是什么，是否已有固定答案文档。
- 找不到答案时如何求助，工单流向哪里。
- 对引用与溯源的期望强度。

## 2.2 典型场景

### 2.2.1 场景走查

1. 员工提问"差旅费报销时限"，系统检索员工手册并返回带章节引用的答案。
2. 新员工提问"如何申请 VPN"，系统返回操作步骤并附来源文档。
3. HR 提问"年假折算规则"，系统在权限范围内检索并给出政策原文。

### 2.2.2 用户旅程

```text
登录 → 输入问题 → 查看答案 → 点击引用 → 跳转原文 → 反馈有用/无用
```

反馈数据回流到评测集，用于持续优化。

### 2.2.3 负向场景

- 库外问题应拒答，不得编造。
- 越权问题应返回无权访问，而非静默忽略。

## 2.3 用户价值

### 2.3.1 价值度量

- 降低查找成本：从"翻文档"变为"直接问"。
- 提升一致性：答案基于统一文档口径，减少人工口径分歧。
- 可审计：每次回答附带来源，便于复核。

### 2.3.2 明确不承诺

- 不承诺 100% 准确，不承诺替代人工审批。
- 不承诺覆盖库外知识。

# 3. 功能范围

**结论先行**：核心功能覆盖"导入—解析—切分—向量化—检索—问答—引用—权限—增量更新"闭环；多模态与协作编辑明确排除在首期之外。

## 3.1 核心功能

### 3.1.1 功能清单

```text
核心功能：
├── 文档导入（PDF/Word/Markdown/网页）
├── 自动解析、切分、向量化
├── 语义检索 + 混合检索
├── 基于检索的问答
├── 引用来源展示
├── 权限过滤（按部门）
└── 增量更新
```

### 3.1.2 功能详解

| 功能 | 输入 | 输出 | 关键点 |
|------|------|------|--------|
| 文档导入 | 文件/URL | 文档记录 | 类型校验 |
| 解析切分 | 原始文档 | 文本块 | 标题拼接 |
| 向量化 | 文本块 | 向量 | 批量嵌入 |
| 混合检索 | 问题 | 候选块 | 稠密+稀疏 |
| 问答 | 问题+上下文 | 答案 | 强约束 |
| 引用 | 候选块 | 来源列表 | 可溯源 |
| 权限 | 用户 | 过滤条件 | 强制注入 |
| 增量更新 | 变更文件 | 新索引 | 内容哈希 |

### 3.1.3 数据源接入范围

| 数据源 | 接入方式 | 首期 |
|--------|----------|------|
| 文件系统 | 目录扫描 | 是 |
| Confluence | API 拉取 | 是 |
| 网页 | URL 抓取 | 是 |
| 企业微信文档 | API | 否 |

## 3.2 非目标

### 3.2.1 明确排除项

```text
非目标：
├── 多模态（图片/表格）
├── 实时协作编辑
```

### 3.2.2 排除理由

- 多模态解析成本高、评测难，首期先聚焦纯文本问答。
- 协作编辑与知识问答目标无关，交由现有 Wiki 承担。

排除项需在需求评审中显式确认，避免后期范围蔓延。

## 3.3 功能优先级

### 3.3.1 优先级矩阵

| 优先级 | 功能 | 说明 |
|--------|------|------|
| P0 | 导入 + 基础检索 | 打通数据链路 |
| P1 | 问答 + 引用 | 可用性达标 |
| P2 | 混合检索 + 重排 | 精度提升 |
| P3 | 权限 + 增量更新 | 生产必备 |
| P4 | 评测 + 优化 | 持续迭代 |

### 3.3.2 迭代节奏

每个优先级以 2 周为一个迭代，迭代结束做一次小型评测，指标不达标不进入下一阶段。

# 4. 非功能需求

**结论先行**：非功能需求决定了系统能否上生产，重点在召回率、忠实度、延迟、权限隔离与更新时效五个维度。

## 4.1 质量指标

### 4.1.1 指标定义

| 维度 | 要求 | 度量方式 |
|------|------|----------|
| 召回率 | Recall@5 ≥ 85% | 标注集上计算命中率 |
| 忠实度 | ≥ 90% | 答案可被引用支撑的比例 |
| 延迟 | < 3s | P95 端到端耗时 |
| 权限 | 严格隔离，无越权 | 越权用例全通过 |
| 更新 | 文档变更 1 小时内生效 | 变更到可检索的时间 |

### 4.1.2 指标计算示例

```java
// Recall@K：命中相关文档的比例
double recallAtK(List<String> retrieved, Set<String> relevant, int k) {
    long hit = retrieved.stream().limit(k).filter(relevant::contains).count();
    return (double) hit / relevant.size();
}

// 忠实度：答案中的断言能被引用支撑的比例
double faithfulness(List<Claim> claims, List<Chunk> cited) {
    long supported = claims.stream().filter(c -> isSupported(c, cited)).count();
    return (double) supported / claims.size();
}
```

### 4.1.3 指标权衡

- 召回与延迟：扩大 topK 提升召回但增加延迟，需按预算折中。
- 忠实与覆盖：过度保守会降低有用性，需平衡拒答率。
- 精度与成本：重排提升精度但增加算力。

## 4.2 权限与安全

### 4.2.1 安全要求

- 检索阶段强制注入租户/部门过滤，绝不依赖模型判断。
- 日志脱敏，不记录用户敏感提问原文。
- 上传文件做类型与大小白名单校验。

### 4.2.2 合规要求

- 用户身份由统一认证（SSO）提供，禁止自建口令体系。
- 数据留存符合企业审计要求。

## 4.3 性能与可用性

### 4.3.1 性能预算

| 阶段 | 预算 |
|------|------|
| 查询改写 | < 200ms |
| 混合检索 | < 500ms |
| 重排 | < 400ms |
| 生成 | < 1.5s |
| 合计 P95 | < 3s |

### 4.3.2 容量规划

| 项 | 估算 |
|----|------|
| 文档数 | 5 万份 |
| 平均块数 | 20 块/文档 |
| 总块数 | 100 万 |
| 单块向量 | 1024 维 float32 |

## 4.4 可维护性

### 4.4.1 可观测性

- 配置外部化，模型与向量库可替换。
- 全链路埋点：解析、检索、重排、生成各阶段耗时与命中率。

### 4.4.2 配置示例

# 5. 验收标准

**结论先行**：验收以可量化清单为准，覆盖解析、检索、生成、权限、拒答、引用六个方面。

## 5.1 验收清单

### 5.1.1 功能验收

- [ ] 文档解析正确率 > 95%
- [ ] 无答案时正确拒答
- [ ] 引用可溯源

### 5.1.2 质量验收

- [ ] Recall@5 ≥ 85%
- [ ] 忠实度 ≥ 90%
- [ ] 越权测试通过

## 5.2 验收方法

### 5.2.1 评测集构建

| 验收项 | 方法 | 通过标准 |
|--------|------|----------|
| 解析正确率 | 抽样人工比对 | 字段完整、正文无乱码 |
| 召回率 | 标注问答集 | Recall@5 ≥ 85% |
| 忠实度 | 人工评审引用支撑 | ≥ 90% |
| 越权 | 构造跨部门用例 | 无越权返回 |
| 拒答 | 构造库外问题 | 明确拒答 |
| 引用 | 点击引用定位 | 可跳转原文 |

评测集至少包含 200 条问答对，覆盖各知识域与各用户角色。

### 5.2.2 评测流程

```text
构建评测集 → 跑批 → 计算指标 → 定位失败 → 优化 → 回归
```

每轮优化都需在固定评测集上回归，避免此消彼长。

# 6. 技术选型

**结论先行**：以中文 Embedding 为核心，向量库优先 PGVector（便于与权限元数据同库管理），检索采用混合检索 + 重排。

## 6.1 选型总览

### 6.1.1 组件选型表

| 组件 | 选择 | 备选 |
|------|------|------|
| 框架 | Spring AI / LangChain4j | 自研编排 |
| 解析 | Tika + Docling（复杂版面） | PyMuPDF |
| Embedding | BGE-large-zh / text-embedding-v3 | m3e |
| 向量库 | PGVector / Milvus | Qdrant |
| 重排 | BGE Reranker | Cohere Rerank |
| 模型 | 中/大模型 | 本地化模型 |

## 6.2 关键选型对比

### 6.2.1 向量库对比

| 向量库 | 优势 | 劣势 | 适用 |
|--------|------|------|------|
| PGVector | 与关系数据同库、事务一致 | 超大规模扩展弱 | 中小规模 |
| Milvus | 高吞吐、分布式 | 运维复杂 | 大规模 |
| Qdrant | 过滤能力强 | 生态相对小 | 中等规模 |

### 6.2.2 Embedding 对比

| 模型 | 维度 | 中文效果 | 成本 |
|------|------|----------|------|
| BGE-large-zh | 1024 | 好 | 自托管 |
| text-embedding-v3 | 1024 | 好 | 按量 |

### 6.2.3 框架对比

| 框架 | 优势 | 劣势 |
|------|------|------|
| Spring AI | 与 Spring 生态无缝 | 抽象层较新 |
| LangChain4j | 组件丰富 | 版本迭代快 |
| 自研 | 完全可控 | 开发成本高 |

## 6.3 选型风险

### 6.3.1 风险清单

- 模型升级导致向量维度变化，需支持重建索引。
- 解析器对扫描件效果差，需 OCR 兜底。
- 重排模型增加延迟，需控制候选数量。

# 8. 风险与应对

**结论先行**：主要风险集中在解析质量、检索精度、越权、幻觉与知识过期五类，均有对应缓解措施。

## 8.1 风险登记

### 8.1.1 风险表

| 风险 | 应对 |
|------|------|
| 解析质量差 | 多解析器 + 质量校验 |
| 检索不准 | 分块调优 + 混合检索 + 重排 |
| 越权 | 元数据强制过滤 + 测试 |
| 幻觉 | 强约束提示 + 引用校验 |
| 知识过期 | 增量更新 + 版本管理 |

### 8.1.2 风险等级

| 风险 | 概率 | 影响 | 等级 |
|------|------|------|------|
| 越权 | 中 | 高 | 高 |
| 幻觉 | 高 | 高 | 高 |
| 解析差 | 高 | 中 | 中 |
| 检索不准 | 中 | 中 | 中 |
| 知识过期 | 中 | 低 | 低 |

### 8.1.3 风险监控

- 越权：每日跑越权回归用例。
- 幻觉：抽样人工评审 + 引用校验失败率。
- 解析：解析质量巡检告警。

## 8.2 应急预案

### 8.2.1 降级策略

- 解析失败：降级到纯文本解析并标记待人工处理。
- 向量库故障：切只读缓存或返回降级提示。
- 模型超时：缩短上下文并降低 topK 重试。

### 8.2.2 回滚方案

- 索引使用别名，回滚即切回旧别名。
- 模型与提示词版本化，可快速回退。
