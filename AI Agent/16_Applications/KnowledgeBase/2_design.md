# 1. 整体架构

**结论先行**：系统分为离线索引与在线查询两条链路，二者通过向量库解耦；离线负责把文档变成带权限元数据的向量块，在线负责检索、重排、生成与引用。

## 1.1 架构总览

### 1.1.1 离线索引流水线

```text
┌─────────────────────────────────────────┐
│  离线索引流水线                           │
│  数据源 → 解析 → 切分 → 向量化 → 入库     │
└─────────────────────────────────────────┘
```

离线链路是幂等的：同一份内容重复执行结果一致，便于重跑与补偿。

### 1.1.2 在线查询链路

```text
┌─────────────────────────────────────────┐
│  在线查询                                 │
│  问题 → 改写 → 检索 → 重排 → 生成 → 引用  │
└─────────────────────────────────────────┘
```

在线链路无状态，可水平扩展；所有状态都在向量库与元数据表中。

### 1.1.3 设计原则

- 读写分离：索引写、查询读，互不干扰。
- 无状态服务：在线服务不保存会话，便于扩容。
- 元数据驱动：权限、引用、更新都依赖元数据。
- 可降级：任一外部依赖故障都有兜底。

## 1.2 组件拓扑

### 1.2.1 组件交互图

```text
┌──────────────┐    ┌──────────────┐
│ Confluence   │    │ 文件系统      │
└──────┬───────┘    └──────┬───────┘

       │  索引服务        │

       └────────┬────────┘

       ┌─────────────────┐
       │  问答服务        │
       │  检索 + 重排 + 生成│

```

### 1.2.2 数据流

| 阶段 | 输入 | 输出 | 存储 |
|------|------|------|------|
| 解析 | 文件/URL | 文本 | 无 |
| 切分 | 文本 | 文本块 | 无 |
| 向量化 | 文本块 | 向量 | 无 |
| 入库 | 向量+元数据 | 记录 | 向量库 |
| 检索 | 问题 | 候选块 | 读 |
| 生成 | 上下文 | 答案 | 无 |

## 1.3 部署视图

### 1.3.1 部署拓扑

```text

                              │
                              └→ [LLM 服务]

```

### 1.3.2 扩展策略

- 问答服务无状态，按 QPS 扩容。
- 索引服务按任务队列扩容，避免影响在线。
- 向量库读写分离，索引写、查询读。

# 2. 索引设计

**结论先行**：索引设计的核心是文档模型与切分策略，元数据既要支撑权限过滤，又要支撑引用溯源。

## 2.1 文档模型

### 2.1.1 Document 结构

```text
Document
├── content: 文本内容
└── metadata:
    ├── source: 文档来源
    ├── title: 标题
    ├── section: 章节
    ├── tenantId: 租户
    ├── department: 部门（权限）
    ├── updatedAt: 更新时间
    └── version: 版本
```

### 2.1.2 元数据字段

| 字段 | 类型 | 用途 | 必需 |
|------|------|------|------|
| source | string | 溯源/删除 | 是 |
| title | string | 展示 | 是 |
| section | string | 引用定位 | 否 |
| tenantId | string | 权限隔离 | 是 |
| department | string | 权限隔离 | 是 |
| updatedAt | string | 时效 | 是 |
| version | string | 版本管理 | 否 |

### 2.1.3 元数据扩展

可按需扩展 acl、docType、lang 等字段，但需同步更新过滤表达式与索引。

## 2.2 切分策略

### 2.2.1 递归切分

递归切分按分隔符优先级逐层切分，尽量保持语义完整。

| 参数 | 建议 | 说明 |
|------|------|------|
| chunkSize | 800 | 字符数 |
| overlap | 100 | 重叠避免断句 |

```java
DocumentSplitter splitter = DocumentSplitters.recursive(800, 100);
List<TextSegment> segments = splitter.split(document);
```

### 2.2.2 标题拼接

切分后把章节标题拼到块首，弥补上下文丢失。

```java
String prefix = "《" + title + "》" + section + "：";
String chunkText = prefix + segment.text();
```

### 2.2.3 切分边界

- 表格：尽量整表保留，避免跨块。
- 代码块：按围栏边界切分。
- 列表：保持条目完整。

## 2.3 索引生命周期

### 2.3.1 生命周期阶段

```text
创建 → 生效 → 更新 → 失效 → 清理
```

### 2.3.2 版本策略

版本字段用于区分同源文档的不同代次，删除时按 source 批量清理。

# 3. 检索设计

**结论先行**：检索采用"改写 → 混合召回 → 融合 → 重排 → 权限过滤 → 生成"六阶段流水线，兼顾召回与精度。

## 3.1 检索流水线

### 3.1.1 六阶段流程

```text
查询
  │
  ▼
① 查询改写（多轮指代消解）
  │
  ▼
② 混合检索
  ├── 稠密（向量）Top-20
  └── 稀疏（BM25）Top-20
  │
  ▼
③ RRF 融合 → Top-20
  │
  ▼
④ 重排 → Top-5
  │
  ▼
⑤ 权限过滤（元数据）
  │
  ▼
⑥ 注入上下文 → 生成
```

## 3.2 查询改写

### 3.2.1 指代消解

多轮对话中，"它的报销时限"需结合上文改写为完整问题。

```java
String rewritten = rewriter.rewrite(history, question);
// 输入："它" → 输出："差旅费的报销时限"
```

### 3.2.2 改写兜底

改写失败时回退原文，避免引入错误。

## 3.3 混合检索

### 3.3.1 稠密检索

稠密检索基于向量相似度，擅长语义匹配，不擅长精确术语。

### 3.3.2 稀疏检索

稀疏检索基于 BM25，擅长关键词与专有名词精确匹配。

### 3.3.3 RRF 融合

RRF（Reciprocal Rank Fusion，倒数排名融合）无需分数归一化，鲁棒性好。

```text
score(d) = Σ 1 / (k + rank_i(d))     k 常取 60
```

| 方法 | 优点 | 缺点 |
|------|------|------|
| 分数加权 | 直观 | 需归一化 |
| RRF | 鲁棒、无需调参 | 忽略分差 |

## 3.4 重排与过滤

### 3.4.1 重排

重排模型对候选做交叉编码，精度高于向量召回，但成本高，仅用于少量候选。

### 3.4.2 权限过滤

权限过滤在检索时强制注入，位于融合之后、生成之前。

### 3.4.3 上下文组装

按重排分数排序，编号后拼接到提示词，附带来源元数据。

# 4. 权限设计

**结论先行**：权限模型由租户、部门与 ACL 三层构成，过滤条件在检索请求中强制注入，绝不依赖模型判断。

## 4.1 权限模型

### 4.1.1 租户/部门/ACL

| 维度 | 说明 | 过滤 |
|------|------|------|
| tenantId | 租户隔离 | 必须相等 |
| department | 部门归属 | 相等或 ACL 公共 |
| acl | 公开标记 | PUBLIC 全员可见 |

### 4.1.2 ACL 设计

| 取值 | 含义 |
|------|------|
| PUBLIC | 全员可读 |
| PRIVATE | 仅所属部门 |
| RESTRICTED | 白名单 |

## 4.2 过滤注入

### 4.2.1 强制过滤

```java
SearchRequest.builder()
        .query(question)
        .topK(20)
        .filterExpression("""
                tenantId == '%s' && (department == '%s' || acl == 'PUBLIC')
                """.formatted(user.tenantId(), user.department()))
        .build();
```

> **权限过滤必须在检索时强制注入**，不能依赖模型。

### 4.2.2 表达式构造

过滤条件由服务端根据登录态构造，禁止由客户端传入。

## 4.3 越权防护

### 4.3.1 测试与审计

- 单元测试覆盖跨租户、跨部门用例。
- 集成测试模拟低权限用户检索高密文档。
- 审计日志记录检索条件与返回数量。

### 4.3.2 反例

```java
// 反例：把权限交给模型判断，必然越权
String ctx = docs.stream().map(Document::getText).collect(joining());
// 正确：检索时已过滤，模型只看到有权内容
```

# 5. 接口设计

**结论先行**：对外提供问答与文档管理两组 REST 接口，统一鉴权，统一错误码。

## 5.1 问答接口

### 5.1.1 请求响应

```java
// 问答
POST /api/kb/ask
{
  "question": "差旅费报销时限？",
  "topK": 5
}
→ {
  "answer": "费用发生后 30 天内...",
  "sources": [
    {"title": "员工手册", "section": "第三章", "score": 0.92}
  ]
}
```

### 5.1.2 鉴权

请求头携带令牌，网关校验后把用户身份透传给问答服务。

## 5.2 文档管理接口

### 5.2.1 CRUD

```text
POST   /api/kb/documents        // 上传
DELETE /api/kb/documents/{id}   // 删除
GET    /api/kb/documents        // 列表
```

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | /api/kb/documents | 上传并索引 |
| DELETE | /api/kb/documents/{id} | 删除并清理索引 |
| GET | /api/kb/documents | 分页列表 |

### 5.2.2 上传流程

```text
校验类型 → 存原文 → 解析 → 切分 → 向量化 → 入库 → 记录哈希
```

## 5.3 错误码

### 5.3.1 错误约定

| 码 | 含义 | 处理 |
|----|------|------|
| 400 | 参数错误 | 修正请求 |
| 401 | 未认证 | 重新登录 |
| 403 | 无权限 | 联系管理员 |
| 500 | 服务异常 | 重试 |

### 5.3.2 幂等

上传与删除接口需支持幂等，重复调用不产生副作用。

# 6. 增量更新

**结论先行**：以内容哈希判断变更，新增入库、变更先删后建、删除按 source 清理；全量重建用别名切换保证零抖动。

## 6.1 变更检测

### 6.1.1 内容哈希

```text
文档变更检测（内容哈希）
  │
  ├── 新增 → 解析 + 入库
  ├── 变更 → 删除旧块 + 重新入库
  └── 删除 → 按 source 删除
```

### 6.1.2 哈希实现

```java
static String sha256(byte[] data) throws Exception {
    MessageDigest md = MessageDigest.getInstance("SHA-256");
    return HexFormat.of().formatHex(md.digest(data));
}
```

## 6.2 更新策略

### 6.2.1 增删改

| 变更 | 动作 | 原子性 |
|------|------|--------|
| 新增 | 解析入库 | 事务 |
| 修改 | 删旧+建新 | 先删后建 |
| 删除 | 按 source 删 | 事务 |

### 6.2.2 并发控制

同一 source 的更新串行化，避免并发写导致残留旧块。

## 6.3 全量重建

### 6.3.1 别名切换

```text
大批量重建：
  新索引构建 → 别名切换 → 清理旧索引
```

### 6.3.2 重建流程

切换是原子操作，查询指向别名，重建期间旧索引继续服务。

# 7. 数据模型

**结论先行**：向量表承载内容与权限元数据，元数据表记录内容哈希与版本，二者共同支撑检索、权限与增量更新。

## 7.1 向量表

### 7.1.1 DDL

```sql
-- 向量表（PGVector）
CREATE TABLE knowledge_chunk (
    id          BIGSERIAL PRIMARY KEY,
    doc_id      VARCHAR(64) NOT NULL,
    content     TEXT NOT NULL,
    embedding   vector(1024) NOT NULL,
    tenant_id   VARCHAR(64) NOT NULL,
    department  VARCHAR(64),
    source      VARCHAR(512),
    section     VARCHAR(256),
    updated_at  TIMESTAMP NOT NULL
);

CREATE INDEX ON knowledge_chunk USING hnsw (embedding vector_cosine_ops);
CREATE INDEX ON knowledge_chunk (tenant_id, department);
```

## 7.2 元数据表

### 7.2.1 DDL

```sql
CREATE TABLE document_meta (
    source        VARCHAR(512) PRIMARY KEY,
    doc_id        VARCHAR(64) NOT NULL,
    content_hash  VARCHAR(64) NOT NULL,
    tenant_id     VARCHAR(64) NOT NULL,
    department    VARCHAR(64),
    version       INT NOT NULL DEFAULT 1,
    updated_at    TIMESTAMP NOT NULL
);
```

### 7.2.2 版本管理

每次内容变更 version 自增，便于回滚与审计。

## 7.3 索引与分区

### 7.3.1 索引策略

| 索引 | 目的 |
|------|------|
| HNSW 向量索引 | 近似最近邻 |
| (tenant_id, department) | 权限过滤 |
| source | 删除定位 |

### 7.3.2 分区

超大表可按 tenant_id 分区，减少扫描范围。

# 8. 关键技术点

**结论先行**：六大关键技术点覆盖分块、检索、权限、引用、更新与幻觉，均有明确方案。

## 8.1 技术点清单

### 8.1.1 问题与方案

| 问题 | 方案 |
|------|------|
| 分块质量 | 递归切分 + 标题拼接 |
| 检索精度 | 混合检索 + 重排 |
| 权限 | 元数据强制过滤 |
| 引用 | 元数据记录来源 |
| 更新 | 内容哈希 + 别名切换 |
| 幻觉 | 强约束 + 引用校验 |

## 8.2 设计权衡

### 8.2.1 权衡表

| 决策 | 收益 | 代价 |
|------|------|------|
| 块小 | 精度高 | 上下文碎 |
| 块大 | 上下文全 | 噪声多 |
| 候选多 | 召回高 | 延迟高 |
| 重排 | 精度高 | 成本高 |

### 8.2.2 常见反例

- 只做向量检索，专有名词召回差。
- 权限放在生成后过滤，已越权。
- 元数据缺失，引用无法定位。

# 9. 小结

**结论先行**：设计阶段确定了两条链路、元数据模型、检索流水线、权限注入、接口与数据模型，为实现提供蓝图。

## 9.1 关键结论

- 架构分离线索引与在线查询。
- 元数据设计是权限与引用的基础。
- 检索用混合 + 重排提升精度。
- 权限过滤在检索时强制注入。
- 增量更新 + 别名切换保证可用。

## 9.2 下一步
