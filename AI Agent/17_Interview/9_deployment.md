# 1. Agent 为什么要状态持久化？

## 1.1 标准答案

内存状态会导致重启丢失、无法扩展、无法恢复、无法审计。**方案**：每步保存检查点，状态外置（Redis/DB）。

## 1.2 深入原理

### 1.2.1 问题与选型

重启即丢失、多实例无法共享、崩溃后无法续跑、无历史可审计；存储上 Redis 存热状态、关系库保强一致与审计、对象存储归档大对象。

## 1.3 代码/示例

```java
interface CheckpointStore { void save(String runId, int step, AgentState s); }
```

## 1.4 追问

**追问**：检查点写失败怎么办？重试写，仍失败则终止该步，避免状态不一致。

## 1.5 生产视角

状态外置是水平扩展与故障恢复的前提，不做无法生产化。

# 2. 如何保证恢复的正确性？

## 2.1 标准答案

**幂等**。

- 记录已执行的工具调用签名；
- 恢复时跳过已执行的；
- 写操作必须幂等（幂等键）。

## 2.2 深入原理

### 2.2.1 为何恢复会重复

崩溃发生在"执行成功但未记检查点"的窗口内，恢复时会重放。

### 2.2.2 调用签名

用工具名加参数哈希作为签名，去重判断；写操作靠幂等键保证副作用只发生一次。

## 2.3 代码/示例

```java
record ToolCall(String tool, Map<String, Object> args) {
    String sig() { return tool + ":" + args.hashCode(); }
}
```

## 2.4 追问

**追问**：只读调用也要去重吗？可不做幂等，但重复会浪费成本与配额。

## 2.5 生产视角

"已执行签名集"随检查点持久化，恢复即天然去重。

# 3. 可靠性五件套？

## 3.1 标准答案

```
超时 → 重试 → 幂等 → 限流 → 熔断 → 降级
```

| 手段 | 说明 |
|------|------|
| 超时 | 所有外部调用必设 |
| 重试 | 只重试可重试错误，指数退避 |
| 幂等 | 写操作必须 |
| 限流 | 保护配额与下游 |
| 熔断 | 持续故障时快速失败 |
| 降级 | 备用模型/缓存/兜底 |

## 3.2 深入原理

### 3.2.1 分工与重试

超时防挂死，重试抗抖动，幂等防重复，限流防过载，熔断防雪崩，降级保可用；只重试超时、限流、5xx，退避加抖动避免重试风暴。

## 3.3 代码/示例

```java
Duration backoff(int n, Duration base) {
    return base.multipliedBy(1L << n).plusMillis(ThreadLocalRandom.current().nextLong(50));
}
```

## 3.4 追问

**追问**：顺序重要吗？重要，顺序错会导致重试放大故障。

## 3.5 生产视角

六件套在网关与 SDK 两层同时实施，防止某层遗漏。

# 4. 熔断与重试的组合顺序？

## 4.1 标准答案

```
熔断（外）→ 限流 → 重试（内）→ 实际调用
```

**熔断打开时不应重试**（重试也会立即失败）。

## 4.2 深入原理

### 4.2.1 为何熔断在外

熔断打开直接快速失败，避免无谓重试消耗资源。

### 4.2.2 为何限流在重试外

限流先于重试，防止重试流量绕过限流额度。

## 4.3 代码/示例

```java
enum CircuitState { CLOSED, OPEN, HALF_OPEN }
```

## 4.4 追问

**追问**：半开状态放多少流量？通常放 1 个试探请求，成功即恢复。

## 4.5 生产视角

熔断阈值按依赖分级，核心依赖更保守。

# 5. 幂等如何实现？

## 5.1 标准答案

| 方案 | 说明 |
|------|------|
| 唯一约束 | 数据库唯一键 |
| Redis SETNX | 高性能 |
| 状态机 + 版本号 | 状态流转类 |

**关键**：幂等键标识"一次业务意图"，**重试必须复用**。

## 5.2 深入原理

### 5.2.1 键设计与版本号

幂等键由业务实体、操作类型、时间窗生成，重试复用同键；更新带期望版本，版本不匹配则拒绝以防并发覆盖。

## 5.3 代码/示例

```java
boolean firstTime(String key) { return redis.setIfAbsent(key, "1", Duration.ofMinutes(5)); }
```

## 5.4 追问

**追问**：幂等键过期了怎么办？过期时间须长于最大重试窗口。

## 5.5 生产视角

所有写工具（下单、扣款、发信）强制幂等，缺失视为严重缺陷。

# 6. Token 如何管理？

## 6.1 标准答案

```
上下文按比例分配：
  System 5% + 工具 10% + 检索 40% + 历史 30% + 输出预留 10%+
```

**必须为输出预留空间**，否则响应被截断。

## 6.2 深入原理

### 6.2.1 预算分配

System 5%、工具 10%、检索 40%、历史 30%、输出 10%+。

### 6.2.2 超限策略与计数

裁剪顺序为历史、检索片段数、工具描述；用分词器精确计数，别按字符估算。

## 6.3 代码/示例

```java
record TokenBudget(int total, int retrieval, int history, int outputReserve) {}
```

## 6.4 追问

**追问**：不同模型分词不同怎么办？按目标模型分词器计数，路由前重算。

## 6.5 生产视角

超预算告警并记录，长期超限说明提示或检索设计有问题。

# 7. 如何降低 LLM 成本？

## 7.1 标准答案

1. 模型分层路由（收益最大，省 30%~70%）；
2. 缓存（结果/语义/向量/Prompt）；
3. 上下文裁剪（只放最相关片段）；
4. 输出长度限制；
5. 批处理；
6. 本地 Embedding。

## 7.2 深入原理

### 7.2.1 路由与收益排序

简单走小模型、中等走中模型、复杂走大模型；收益排序为路由 > 缓存 > 裁剪 > 输出限制 > 批处理 > 本地化，降本不得降低评测基线。

## 7.3 代码/示例

```java
interface ModelRouter { String route(Query q); }
```

## 7.4 追问

**追问**：路由错了怎么办？设回退，小模型低置信时升级到大模型。

## 7.5 生产视角

按租户与功能看单位成本，成本异常自动告警。

# 8. 缓存有哪些层次？

## 8.1 标准答案

```
① 结果缓存（相同问题）
② 语义缓存（相似问题）
③ 检索缓存（相同查询）
④ 向量缓存（相同文本）
⑤ Prompt 缓存（模型侧）
```

**语义缓存有误命中风险**，阈值要保守，且按租户隔离。

## 8.2 深入原理

### 8.2.1 各层命中条件

结果缓存按原文，语义缓存按向量相似，检索按查询哈希，向量按文本哈希，Prompt 按前缀。

### 8.2.2 阈值与隔离

语义相似度阈值取高（如 0.95+），缓存键必须含租户标识防跨租户泄露。

## 8.3 代码/示例

```java
String key(String tenant, String q) { return "qa:" + tenant + ":" + sha256(q); }
```

## 8.4 追问

**追问**：要失效策略吗？要，数据更新时主动失效相关缓存。

## 8.5 生产视角

监控命中率与误命中投诉，命中率低说明键设计不合理。

# 9. 多租户如何隔离？

## 9.1 标准答案

```
六样东西必须隔离：
① 数据（向量、记忆、会话）
② 模型与配额
③ 密钥
④ 权限与工具
⑤ 成本与计费
⑥ 审计日志
```

**过滤条件必须服务端注入**，绝不信任客户端。

## 9.2 深入原理

### 9.2.1 隔离维度与服务端注入

数据用元数据过滤，配额按租户限流，密钥独立凭证，计费按租户计量；租户标识由鉴权上下文派生，不取自请求体，越权测试必做。

## 9.3 代码/示例

```java
Filter f(SecurityContext c) { return Filter.eq("tenant_id", c.tenantId()); }
```

## 9.4 追问

**追问**：共享向量库安全吗？可以，但每次查询必须带服务端注入的租户过滤。

## 9.5 生产视角

把"跨租户泄露"列为最高等级缺陷，上线前必做越权测试。

# 10. 如何做可观测？

## 10.1 标准答案

```
三大支柱：
  Trace（调用链）
  Metrics（指标）
  Logs（日志）
```

**LLM 特有**：Token、成本、工具调用、检索命中、Agent 步数。**指标用低基数标签**，采样用"比例 + 错误全采"。

## 10.2 深入原理

### 10.2.1 三大支柱分工

Trace 定位慢在哪步，Metrics 看趋势与告警，Logs 看细节与取证。

### 10.2.2 低基数与采样

标签值域要小，别把用户 ID 当标签；正常请求按比例采样，错误全量采集。

## 10.3 代码/示例

```java
Span s = tracer.spanBuilder("llm.call").setAttribute("model", m).startSpan();
```

## 10.4 追问

**追问**：Trace 存多久？热存 7 天，冷存 90 天或按合规要求。

## 10.5 生产视角

Trace 贯穿接入、模型、检索、工具、状态五层，缺层无法端到端定位。

# 11. 流式输出如何实现？

## 11.1 标准答案

**答**：SSE（Server-Sent Events，服务器推送事件）。

**关键**：网关必须**关闭缓冲**（`proxy_buffering off`），否则看不到流式效果。

## 11.2 深入原理

### 11.2.1 协议与缓冲

SSE 单向服务端推送适合文本流，WebSocket 双向适合交互，轮询作兜底；Nginx 默认缓冲会攒够才发必须关闭，客户端断线要能按偏移续传。

## 11.3 代码/示例

```java
@GetMapping(value = "/chat", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
Flux<ServerSentEvent<String>> chat(String q) { return agent.stream(q); }
```

## 11.4 追问

**追问**：流式下怎么审核？分块审核加关键节点全量审核，或延迟敏感词。

## 11.5 生产视角

监控首字节时间（TTFB）与流式中断率，二者直接影响体验。

# 12. 如何做发布与回滚？

## 12.1 标准答案

发布对象：代码、镜像、配置、Prompt、索引、Agent 定义。**策略**：金丝雀（LLM 首选）、蓝绿、影子。**索引发布**：新索引 + 别名切换，**绝不删旧建新**。

## 12.2 深入原理

### 12.2.1 策略对比

金丝雀小流量渐进，蓝绿两套环境切换，影子旁路对比不生效。

### 12.2.2 索引别名

写入新索引，验证后把读别名切到新索引，旧索引保留待回滚。

## 12.3 代码/示例

```java
interface IndexAlias { void pointTo(String alias, String index); }
```

## 12.4 追问

**追问**：Prompt 也要灰度吗？要，其变更风险等同代码变更。

## 12.5 生产视角

所有发布对象纳入同一变更管理，可审计、可回滚、可复现。

# 13. 如何做容量规划？

## 13.1 标准答案

```
吞吐 = 并发 / 平均延迟
并发 = 吞吐 × 平均延迟
```

分层计算（接入/模型/检索/工具/状态），取各层最小值。**基线预留 + 峰值弹性 + 队列吸收突发**。

## 13.2 深入原理

### 13.2.1 分层瓶颈与利特尔法则

接入看连接数，模型看供应商配额，检索看 QPS，工具看下游限流，状态看 IOPS；并发 = 到达率 × 处理时间，用于估算所需并发。

## 13.3 代码/示例

```java
record Capacity(double rate, double latencyMillis) {
    double concurrency() { return rate * latencyMillis / 1000.0; }
}
```

## 13.4 追问

**追问**：模型层配额不够怎么办？多供应商备份加降级到小模型。

## 13.5 生产视角

按最弱层设容量，压测覆盖端到端而非单层。

# 14. Agent 的上下文爆炸怎么办？

## 14.1 标准答案

- 记忆窗口；
- 摘要压缩；
- 结构化抽取（保留关键实体）；
- 只放最相关的检索片段。

## 14.2 深入原理

### 14.2.1 手段对比

窗口保真高压缩低，摘要中等，结构化压缩比最高。

### 14.2.2 触发与保护

超预算阈值触发，保留最近 N 轮原文；实体、结论、约束不可丢。

## 14.3 代码/示例

```java
interface Compressor { List<Message> compress(List<Message> h, int limit); }
```

## 14.4 追问

**追问**：摘要由谁生成？用小模型生成，成本低且够用。

## 14.5 生产视角

压缩引入信息损失，评测集需覆盖长对话场景。

# 15. 生产事故的常见原因？

## 15.1 标准答案

| 事故 | 根因 | 防御 |
|------|------|------|
| 任务丢失 | 状态在内存 | 状态外置 |
| 重复扣款 | 重试 + 非幂等 | 幂等键 |
| 成本暴涨 | 无预算 | Token 预算 + 告警 |
| 越权访问 | 无租户隔离 | 元数据过滤 |
| 依赖拖垮 | 无熔断 | 熔断 + 降级 |
| 无法定位 | 无 Trace | 全链路追踪 |

## 15.2 深入原理

### 15.2.1 事故分类与复盘

多为工程问题、少为模型问题，工程化不足是主因；按"触发-放大-暴露"复盘找缺口，幂等、隔离、预算优先级最高。

## 15.3 代码/示例

```java
record Incident(String trigger, String amplifier, List<String> missing) {}
```

## 15.4 追问

**追问**：模型能力不足算事故吗？算效果问题，表现为评测退化。

## 15.5 生产视角

把高频事故沉淀为上线检查项与自动化测试。

# 16. 上线检查清单？

## 16.1 标准答案

- [ ] 状态持久化
- [ ] 超时/重试/幂等/限流/熔断
- [ ] Token 预算与成本监控
- [ ] 租户隔离 + 越权测试
- [ ] 全链路 Trace
- [ ] 日志脱敏
- [ ] 评测接入 CI
- [ ] 降级与回滚方案
- [ ] 工具权限最小化

## 16.2 深入原理

### 16.2.1 清单用途

把隐性经验变成显性门槛，防止漏项。

### 16.2.2 分类与自动化

可靠（状态/超时/幂等）、成本（预算/监控）、安全（隔离/脱敏/权限）、运维（Trace/回滚）；能自动校验的尽量脚本化。

## 16.3 代码/示例

```java
interface GoLiveGate { boolean pass(List<CheckItem> items); }
```

## 16.4 追问

**追问**：清单能省吗？不能省，但可按业务风险裁剪细则。

## 16.5 生产视角

每次事故后回填清单，使其持续演进。

# 17. 小结

- 状态外置 + 幂等是生产化的门槛。
- 可靠性五件套缺一不可。
- 成本、Token、多租户、可观测是重点。
- 发布要可灰度、可回滚。
- 生产事故多来自工程，而非模型。
