# 1. 讲述框架（STAR）

## 1.1 STAR 总览

项目讲述要结构化，最常用的是 STAR（Situation 情境、Task 任务、Action 行动、Result 结果），它强迫你把"背景—目标—行动—结果"讲成闭环。

```
S（Situation）：背景与问题
T（Task）：你的目标与职责
A（Action）：你的具体行动
R（Result）：量化结果
```

### 1.1.1 四要素含义

| 要素 | 含义 | 常见错误 |
|------|------|----------|
| Situation | 背景与问题 | 铺垫过长，迟迟不进入重点 |
| Task | 目标与职责 | 职责模糊，说不清自己做了什么 |
| Action | 具体行动 | 记流水账，没有取舍与难点 |
| Result | 量化结果 | 只讲"效果不错"，没有数字 |

### 1.1.2 时间分配

以 5 分钟讲述为例：S 约 30 秒、T 约 30 秒、A 约 3 分钟、R 约 1 分钟。A 是重点，要突出难点与取舍，而非罗列技术名词。

## 1.2 常见变体

### 1.2.1 STARL

在 STAR 基础上增加 L（Learning，反思与收获），适合应届生或转岗者强调成长性。

### 1.2.2 CARL

Context（背景）、Action（行动）、Result（结果）、Learning（收获），结构更简洁，适合 2 分钟版本。

## 1.3 使用要点

### 1.3.1 结构是骨架不是台词

框架用来组织信息，不要背诵；面试官更想听你如何思考和取舍。

### 1.3.2 常见误区

- 把 STAR 讲成时间线，没有重点；
- 只讲技术实现，不讲业务价值；
- 结果没有数字，无法证明做成了。

## 1.4 与面试官的互动

### 1.4.1 先对齐再展开

讲述前用一句话确认岗位方向（偏工程还是偏算法），据此调整讲述侧重。

### 1.4.2 观察反馈

若面试官追问细节，说明方向对，可深入；若频繁打断，说明太长，应加速收敛。

# 2. 项目讲述模板

## 2.1 模板总览

```
【背景】
  业务问题 + 规模（用户数、数据量、QPS）

【挑战】
  技术难点（为什么难）

【方案】
  架构 + 关键技术选型 + 为什么这样选

【实现】
  核心实现 + 踩过的坑

【结果】
  量化收益（准确率、延迟、成本、效率）

【反思】
  如果重来会怎么改进
```

### 2.1.1 六段结构

背景、挑战、方案、实现、结果、反思六段递进：背景给价值，挑战给张力，方案给思路，实现给可信度，结果给证据，反思给成长。

### 2.1.2 每段时长

背景 30 秒、挑战 40 秒、方案 90 秒、实现 90 秒、结果 40 秒、反思 30 秒，合计约 5 分钟。

## 2.2 各段写法

### 2.2.1 背景与挑战

背景用一句话说清业务价值，再补规模数字；挑战要讲"为什么难"，最好是同行也头疼的问题，而不是"业务需求多"。

### 2.2.2 方案与实现

方案讲清架构与选型理由（成本、效果、团队熟悉度）；实现讲关键代码路径与踩坑，体现你真正动过手。

### 2.2.3 结果与反思

结果必须数字化；反思要具体，例如"评测集建晚了""元数据设计晚了"，而不是空泛的"要更努力"。

## 2.3 常见问题

### 2.3.1 背景过长

背景超过 1 分钟就会让面试官失去耐心，价值一句话足矣。

### 2.3.2 只讲方案不讲理由

"我用了 A"不如"我用 A 而不是 B，因为成本和团队熟悉度"。

## 2.4 模板演练

### 2.4.1 逐段打草稿

先按六段各写 3 句话，再打磨成口述稿，避免临场卡壳。

### 2.4.2 录音回听

录音回听，删掉冗余修饰词，把 6 分钟压到 5 分钟。

# 3. 示例：企业知识库问答

## 3.1 背景与挑战

### 3.1.1 背景

内部知识分散在多个系统，员工查找困难，客服重复问题多。

### 3.1.2 挑战

- 文档格式多样（PDF/Word/网页）；
- 检索不准（中文、专有名词）；
- 权限复杂（多部门）。

## 3.2 方案与实现

### 3.2.1 技术选型

- 解析：Tika + Docling（复杂版面）；
- 分块：递归 800/100 + 标题拼接；
- Embedding：BGE-large-zh；
- 检索：混合（稠密 + BM25）+ RRF + 重排；
- 权限：元数据强制过滤。

### 3.2.2 实现难点

- 表格解析丢失 → 转自然语言；
- 检索不准 → 混合检索 + 重排；
- 越权风险 → 服务端强制过滤 + 越权测试。

## 3.3 结果与反思

### 3.3.1 量化结果

- Recall@5 从 62% → 88%；
- 忠实度 93%；
- 客服重复问题减少 40%；
- 单次成本 ¥0.02。

### 3.3.2 反思

- 应更早建评测集（前期盲调浪费）；
- 元数据应更早设计（后补成本高）。

## 3.4 可延伸追问

### 3.4.1 为什么不用微调

标注数据稀缺、迭代慢、成本高，先用 RAG 快速上线，后续再考虑微调。

### 3.4.2 指标怎么测

用人工标注的评测集，固定口径离线计算 Recall@5，线上用 A/B 对照。

## 3.5 完整讲述稿示例

### 3.5.1 两分钟版

> 我们把分散在多个系统的内部文档做成知识库问答：Tika + Docling 解析、递归分块、BGE 向量化，再用稠密 + BM25 混合检索加重排。Recall@5 从 62% 提到 88%，客服重复问题下降 40%，单次成本约 ¥0.02。最难的是表格解析和越权风险，前者转自然语言、后者服务端强制过滤并做越权测试。如果重来，我会先建评测集。

### 3.5.2 常见开场

用"问题—规模—结果"三句话开场，先给结论再展开过程。

# 4. 常见追问

## 4.1 追问速查表

| 追问 | 回答方向 |
|------|----------|
| 为什么用 A 不用 B？ | 说明取舍（成本/效果/团队） |
| 最大的难点？ | 具体技术难点 + 解决过程 |
| 效果怎么验证？ | 评测集 + 指标 + 线上对比 |
| 有什么不足？ | 坦诚 + 改进方向 |
| 你的贡献？ | 明确个人职责 |
| 如果重来？ | 说明反思与成长 |
| 规模有多大？ | 具体数字 |
| 成本多少？ | 单位成本 + 优化过程 |

## 4.2 高频追问深挖

### 4.2.1 为什么用 A 不用 B

从成本、效果、团队熟悉度三个维度对比，给出量化依据，并说明当时的约束。

### 4.2.2 最大的难点

选一个真难点，讲清"卡在哪、怎么定位、怎么解决、效果如何"，而不是"什么都难"。

### 4.2.3 效果怎么验证

离线评测集算指标，线上用灰度或 A/B 对照，口径固定、样本量足够。

## 4.3 应对策略

不确定的细节坦诚说明，不编造；把问题引回自己真正做过的部分。

## 4.4 追问应答模板

### 4.4.1 选型类追问

"我们对比了 A 和 B，A 在中文场景召回高 12%、成本低 30%，团队也更熟，所以选 A；代价是 A 的部署更复杂。"

### 4.4.2 难点类追问

"最难的是 X，定位过程是……，最后用 Y 解决，指标从 P 提升到 Q。"

### 4.4.3 不足类追问

"不足是 Z，当时受限于时间与数据；如果继续做，我会先……。"

# 5. 量化指标

## 5.1 指标分类

```
质量：准确率、召回率、忠实度
效率：延迟、吞吐、步数
成本：单次成本、总成本、降本比例
业务：解决率、满意度、人力节省
```

### 5.1.1 质量与效率

质量看准确率、召回率、忠实度；效率看首字延迟、吞吐、平均步数。

### 5.1.2 成本与业务

成本看单次成本与降本比例；业务看解决率、满意度、人力节省。

## 5.2 指标口径

### 5.2.1 如何定义

每个指标要有明确定义与计算方式，例如 Recall@5 = 前 5 条命中相关文档数 / 相关文档总数。

### 5.2.2 如何采集

离线指标由评测集离线计算，线上指标从 Trace 与埋点聚合。

Java 示例（Recall@k）：

```java
public double recallAtK(List<String> retrieved, Set<String> relevant, int k) {
    Set<String> topK = new HashSet<>(
            retrieved.subList(0, Math.min(k, retrieved.size())));
    long hit = topK.stream().filter(relevant::contains).count();
    return relevant.isEmpty() ? 0.0 : (double) hit / relevant.size();
}
```

## 5.3 表达技巧

### 5.3.1 用对比

用"优化前 vs 优化后"表达，例如"Recall@5 从 62% 提升到 88%"。

### 5.3.2 用单位与比例

用单位成本（单次 ¥0.02）与比例（降本 60%）让收益可感知。

> **必须有量化结果**，否则项目显得"没做成"。

## 5.4 指标陷阱

### 5.4.1 口径不一致

离线用 Recall@5、线上用点击率，口径不同无法对比，必须统一。

### 5.4.2 样本过小

样本量不足时结论不可靠，灰度要保证统计显著性。

# 6. 项目选择建议

## 6.1 优先级

| 优先 | 项目 |
|------|------|
| 高 | 有量化收益的 RAG 系统 |
| 高 | 有工具调用的 Agent |
| 中 | 多 Agent 协作系统 |
| 中 | 模型微调 + 部署 |
| 低 | 纯 Demo |

## 6.2 组合建议

### 6.2.1 三类项目

准备一个 RAG、一个 Agent、一个工程化项目，覆盖检索、工具、可靠性三个能力面。

### 6.2.2 避坑

避免全是 Demo，避免项目太大太空，避免只有技术没有业务价值。

## 6.3 加分项

- 有线上流量与真实用户；
- 有成本优化过程与数字；
- 有失败经历与改进措施。

## 6.4 项目包装

### 6.4.1 提炼主线

把项目抽象成"问题—方案—收益"一条主线，删掉无关技术细节。

### 6.4.2 突出个人贡献

明确"我负责哪一层"，避免把团队成果全揽。

# 7. 讲述技巧

## 7.1 六条原则

1. **先讲价值**，再讲技术；
2. **突出难点**，而非流水账；
3. **量化结果**，用数字说话；
4. **主动说取舍**，体现思考；
5. **准备深挖**，任何细节都可能被追问；
6. **坦诚不足**，展示成长。

## 7.2 表达细节

### 7.2.1 先价值后技术

一句话说清业务价值，再展开技术实现。

### 7.2.2 突出难点

用"最难的是……因为……"句式，主动引导面试官追问。

### 7.2.3 主动说取舍

每个选型都给理由与代价，体现工程判断。

## 7.3 时间控制

准备 2 分钟、5 分钟、10 分钟三个版本，按面试官节奏切换。

## 7.4 表达细节补充

### 7.4.1 控制语速

关键数字放慢语速、加重语气，让面试官记住。

### 7.4.2 用白板

复杂架构用白板边画边讲，比纯口述更清晰。

# 8. 常见陷阱

## 8.1 陷阱清单

| 陷阱 | 问题 |
|------|------|
| 只讲技术不讲价值 | 显得没有业务视角 |
| 无量化结果 | 无法证明效果 |
| 夸大个人贡献 | 追问即露馅 |
| 只讲成功 | 显得缺乏反思 |
| 细节讲不清 | 显得没真正做过 |
| 项目太大太空 | 追问具体实现答不上 |

## 8.2 典型案例

### 8.2.1 只讲技术

只讲用了什么框架，不讲解决了什么业务问题。

### 8.2.2 无量化

说"效果不错"却给不出任何数字。

### 8.2.3 夸大贡献

把团队成果说成个人成果，一追问就露馅。

## 8.3 规避方法

每个论断都配数字与细节，明确个人边界，提前准备不足与改进。

## 8.4 反例改写

| 原话 | 改写 |
|------|------|
| 我用了 RAG | 我用 RAG 把 Recall@5 提到 88% |
| 效果不错 | 忠实度 93%，重复问题降 40% |
| 我参与了 | 我负责检索与重排模块 |

# 9. 准备清单

## 9.1 内容准备

- [ ] 3 个项目，每个能讲 5 分钟
- [ ] 每个项目有量化结果
- [ ] 每个项目的技术选型有理由
- [ ] 每个项目准备 2~3 个难点
- [ ] 每个项目准备 1 个不足与改进
- [ ] 准备好被深挖的细节（代码、参数、指标）

## 9.2 演练准备

### 9.2.1 自测问题

对每个项目自问 10 个追问，确保都能答上。

### 9.2.2 计时演练

录音计时，检查是否超时、是否有口头禅。

## 9.3 材料准备

准备一页架构图与关键指标表，必要时可共享屏幕讲解。

## 9.4 复盘方法

### 9.4.1 记录追问

每次面试记录被追问的问题，补齐答案，形成个人题库。

### 9.4.2 迭代讲述稿

根据反馈持续精简讲述稿，保留最能体现能力的部分。

# 10. 小结

## 10.1 关键结论

- 用 STAR 结构讲述。
- 突出挑战、方案、量化结果、反思。
- 必须有量化指标。
- 主动说取舍，坦诚不足。
- 准备好被深挖的任何细节。

## 10.2 自测清单

- 每个项目能否 5 分钟讲完？
- 每个项目是否有 3 个量化指标？
- 是否准备 2~3 个难点？
- 是否准备 1 个不足与改进？
