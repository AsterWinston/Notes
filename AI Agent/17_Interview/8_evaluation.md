# 1. 为什么 LLM 应用必须评测？

## 1.1 标准答案

LLM（大语言模型）输出非确定，"感觉更好"不可靠。**没有评测的优化都是盲调**，可能"改好 A 改坏 B"。

## 1.2 深入原理

### 1.2.1 非确定性来源

采样参数（温度、top-p）、模型静默升级、检索片段顺序、并发与缓存差异。

### 1.2.2 主观感受为何不可靠

单样例是噪声；人只记成功案例；提示改动常"整体提升、某类下降"。

## 1.3 代码/示例

```java
record EvalCase(String input, String expected, Set<String> tags) {}
```

## 1.4 追问

**追问**：没有标注数据怎么起步？先建 20 条冒烟集人工判断，再逐步积累。

## 1.5 生产视角

评测纳入 CI（持续集成），每次 Prompt、模型、索引变更自动跑并对比基线。

# 2. 评测的三个层次？

## 2.1 标准答案

```
① 组件评测：Embedding、Rerank 等单项
② 系统评测：RAG 端到端、Agent 任务成功率
③ 线上评测：A/B 实验、用户反馈
```

## 2.2 深入原理

### 2.2.1 三层分工

组件定位问题，系统验证组合，线上确认真实效果，缺一层会误判。

### 2.2.2 数据源不同

组件与系统用固定评测集，线上用真实流量与用户反馈。

## 2.3 代码/示例

```java
enum EvalLevel { COMPONENT, SYSTEM, ONLINE }
```

## 2.4 追问

**追问**：三层都要做吗？至少做系统层，组件层用于定位，线上层用于决策。

## 2.5 生产视角

三层对应三套看板，避免"离线很好、线上很差"。

# 3. 离线与在线评测的区别？

## 3.1 标准答案

| 维度 | 离线 | 在线 |
|------|------|------|
| 数据 | 固定评测集 | 真实流量 |
| 速度 | 快 | 慢 |
| 真实性 | 有限 | 高 |

**互补**：离线保不退化，在线验真实效果。

## 3.2 深入原理

### 3.2.1 离线优缺点

可复现、可归因，但评测集与真实分布有偏差。

### 3.2.2 在线优缺点

真实，但慢、有实验成本、需统计显著性。

## 3.3 代码/示例

```java
interface OfflineEval { Map<String, Double> run(Collection<EvalCase> cases); }
```

## 3.4 追问

**追问**：离线通过就能上线吗？不能，仍需小流量灰度验证。

## 3.5 生产视角

离线基线设为硬门槛，不达标禁止发布；在线结果作最终依据。

# 4. RAG 评测指标？

## 4.1 标准答案

| 层次 | 指标 |
|------|------|
| 检索 | Recall@K、MRR、nDCG |
| 生成 | 忠实度、相关性、上下文精确/召回 |
| 端到端 | 答案正确率、拒答准确率 |

## 4.2 深入原理

### 4.2.1 检索指标

Recall@K 看命中，MRR 看首个正确项排名，nDCG 兼顾位置与相关度分级。

### 4.2.2 生成指标

忠实度看答案是否仅来自上下文；上下文精确/召回看片段有用比例与覆盖。

## 4.3 代码/示例

```java
record RagMetrics(double recallAtK, double mrr, double faithfulness) {}
```

## 4.4 追问

**追问**：忠实度高但答案错？说明召回了错误内容，问题在检索层。

## 4.5 生产视角

指标分层展示，否则无法区分"没找到"与"答错"。

# 5. Agent 评测指标？

## 5.1 标准答案

| 维度 | 指标 |
|------|------|
| 结果 | 任务成功率、答案正确率 |
| 过程 | 步数、工具调用准确率、循环检测 |
| 效率 | 耗时、Token、成本 |
| 鲁棒 | 异常输入表现 |
| 安全 | 越权、注入 |

## 5.2 深入原理

### 5.2.1 结果与过程并重

只看结果会放过"碰巧对"，过程指标能发现低效或危险路径。

### 5.2.2 效率是硬约束

Agent 步数线性放大 Token 成本，必须设上限。

## 5.3 代码/示例

```java
record AgentTrace(List<Step> steps, boolean success, int tokens, long millis) {}
```

## 5.4 追问

**追问**：成功但绕远路算通过吗？不算，应扣效率分，避免坏策略。

## 5.5 生产视角

为每类任务设步数与成本预算，超预算终止并记失败。

# 6. 什么是轨迹评测？

## 6.1 标准答案

评测 Agent 的完整动作序列，而非只看结果。

```
只看结果会漏掉"碰巧对"与"越权对"
```

维度：必要性、顺序、工具选择、参数、冗余、循环。

## 6.2 深入原理

### 6.2.1 必要性与顺序

每步是否推进任务，前置依赖是否满足、参数是否来自前序结果。

### 6.2.2 冗余与循环

重复调用与死循环是典型失败模式。

## 6.3 代码/示例

```java
interface TraceEvaluator { double necessity(AgentTrace t); boolean hasLoop(AgentTrace t); }
```

## 6.4 追问

**追问**：轨迹数据从哪来？从可观测的 Trace（调用链）直接采集。

## 6.5 生产视角

把轨迹可视化，让"高效路径"成为提示优化样例。

# 7. LLM-as-Judge 是什么？有什么风险？

## 7.1 标准答案

用模型作为评委打分。**风险**：位置偏差、长度偏差、自偏好、分数聚集。

**缓解**：二元判断或成对比较；交换位置两次；Judge 换模型；人工校准（一致率 < 80% 不可用）。

## 7.2 深入原理

### 7.2.1 四种偏差

位置偏好靠前/靠后，长度偏好更长，自偏好自家模型，分数聚集在 7-8 分。

### 7.2.2 校准

与人工标注算一致率与 Kappa，低于阈值则判据不可信。

## 7.3 代码/示例

```java
record JudgeVerdict(String winner, String reason, double confidence) {}
```

## 7.4 追问

**追问**：成对比较比打分好吗？更稳定，但成本翻倍。

## 7.5 生产视角

Judge 结论只作筛选信号，关键决策仍需抽样人工复核。

# 8. 评测集怎么构建？

## 8.1 标准答案

| 来源 | 质量 |
|------|:----:|
| 真实用户问题 | 高 |
| 专家编写 | 高 |
| LLM 生成 | 中（需审核） |
| 失败案例回流 | 高（针对性强） |

**规模**：50~200 条起步。**覆盖**：典型、边界、无答案、对抗。

## 8.2 深入原理

### 8.2.1 来源权衡

真实问题最贴分布但慢，LLM 生成快但需人工审核。

### 8.2.2 覆盖矩阵

典型测正常能力，边界测临界，无答案测拒答，对抗测抗注入。

## 8.3 代码/示例

```java
record CaseMeta(String source, String type, String tenant) {}
```

## 8.4 追问

**追问**：评测集要版本化吗？要，用例增删都记录，便于对比历史。

## 8.5 生产视角

线上失败案例自动回流，形成"发现-修复-回归"闭环。

# 9. 如何防止评测集过拟合？

## 9.1 标准答案

保留一份**从不用于调优的黄金集**。

- 调优用训练集；
- 最终判断用黄金集；
- 失败案例持续回流。

## 9.2 深入原理

### 9.2.1 过拟合表现

反复针对评测集改提示，评测分涨但线上不涨。

### 9.2.2 黄金集纪律

黄金集只读、只在发布前评估、内容不得泄露进提示或检索库。

## 9.3 代码/示例

```java
enum CaseSplit { TRAIN, DEV, GOLDEN }
```

## 9.4 追问

**追问**：黄金集要多大？几十条即可，但要覆盖高风险场景。

## 9.5 生产视角

黄金集访问需审计，防止无意泄露给调优流程。

# 10. 回归测试怎么做？

## 10.1 标准答案

```
① 单元测试（Mock 模型）
② 集成测试（真实链路）
③ 评测回归（完整评测集）
```

**关键**：维护基线，只升不降；设合理容差；多次运行取均值。

## 10.2 深入原理

### 10.2.1 三层职责

单元测逻辑（毫秒），集成测链路（秒），评测测效果（分钟）。

### 10.2.2 基线与容差

非确定性使分数抖动，需设容差（约 1%~3%）并多次取均值。

## 10.3 代码/示例

```java
void assertNotRegressed(double base, double cur) {
    if (cur < base - 0.02) throw new AssertionError("效果退化");
}
```

## 10.4 追问

**追问**：容差设多大？按历史波动估计，通常 1%~3%。

## 10.5 生产视角

基线存版本库，报告随流水线归档，退化自动阻断发布。

# 11. LLM 应用测试如何 Mock？

## 11.1 标准答案

```java
when(chatModel.call(any(Prompt.class)))
    .thenReturn(mockResponse("你好！"));
```

**CI 中的单元测试绝不真调模型**（慢、贵、不稳定）。

## 11.2 深入原理

### 11.2.1 为何必须 Mock

真实调用数百毫秒到数秒、每次计费、输出会漂移。

### 11.2.2 Mock 边界

只覆盖确定性逻辑（解析、路由、拼装），效果验证放评测回归。

## 11.3 代码/示例

```java
ChatModel fake = prompt -> new ChatResponse("固定回复");
```

## 11.4 追问

**追问**：Mock 会掩盖真实问题吗？会，所以还需少量集成测试。

## 11.5 生产视角

CI 快速跑 Mock 单测，Nightly（每晚）跑真实链路集成测试。

# 12. 如何做线上 A/B？

## 12.1 标准答案

```
① 定义假设与指标
② 按用户哈希分流（稳定）
③ 收集数据（固定周期）
④ 统计显著性检验
⑤ 决策
```

**陷阱**：样本不足、过早决策、多重比较、分流不均。

## 12.2 深入原理

### 12.2.1 稳定分流

按用户 ID 哈希取模，保证同一用户始终同组。

### 12.2.2 显著性

用 t 检验或卡方检验，p < 0.05 且效应量有意义才采纳。

## 12.3 代码/示例

```java
String bucket(String uid, int n) { return Math.floorMod(uid.hashCode(), n) == 0 ? "A" : "B"; }
```

## 12.4 追问

**追问**：LLM 场景分流比多少？通常 1%~5% 灰度，逐步放量。

## 12.5 生产视角

A/B 与成本、延迟一起看，避免"效果好但成本失控"。

# 13. 如何评估 Prompt 变更？

## 13.1 标准答案

```
① 离线对比（快）
② 分维度对比（发现"整体提升但某类下降"）
③ 线上灰度（验证真实效果）
```

**一次只改一个变量**，便于归因。

## 13.2 深入原理

### 13.2.1 单变量原则

多变量同改无法归因，只能得到一个"组合效果"。

### 13.2.2 分维度看板

按意图、租户、难度分组，防止均值掩盖局部退化。

## 13.3 代码/示例

```java
record PromptDiff(String base, String candidate, String changeNote) {}
```

## 13.4 追问

**追问**：分维度波动大怎么办？增大样本量或对关键维度建子集。

## 13.5 生产视角

Prompt 纳入版本管理与发布流程，可回滚、可审计。

# 14. 评测的成本如何控制？

## 14.1 标准答案

- 小模型做 Judge；
- 抽样评测；
- 缓存评测结果；
- 只对关键变更跑完整评测。

## 14.2 深入原理

### 14.2.1 成本来源

Judge 调用、生成调用、人工标注三类成本。

### 14.2.2 分层策略

文案微调跑子集，逻辑变更跑全量，模型切换跑全量加人工。

## 14.3 代码/示例

```java
interface EvalCache { Optional<EvalResult> get(String hash, String model); }
```

## 14.4 追问

**追问**：小模型 Judge 准吗？简单判据够用，复杂判据仍用大模型。

## 14.5 生产视角

给评测设月度预算与告警，防止评测成为成本黑洞。

# 15. 评测失败的诊断？

## 15.1 标准答案

| 症状 | 结论 |
|------|------|
| 答不出 | 检索问题 |
| 答错 | 生成问题 |
| 答偏 | 提示/上下文问题 |
| 噪声多 | 阈值/重排问题 |
| 编造 | 提示未约束 |

## 15.2 深入原理

### 15.2.1 分层定位

先看检索是否召回正确内容，再看生成是否忠实使用。

### 15.2.2 常见根因

答不出多为切分过碎或 Embedding 弱；答错多为上下文噪声；编造多为缺约束。

## 15.3 代码/示例

```java
enum FailureKind { RETRIEVAL, GENERATION, PROMPT, RERANK, HALLUCINATION }
```

## 15.4 追问

**追问**：先看哪个指标？先看检索 Recall，不达标后面无意义。

## 15.5 生产视角

把失败分类计数做成看板，指导优化优先级。

# 16. 小结

- 评测是迭代的前提，三层互补。
- RAG 看检索与忠实度，Agent 看结果与轨迹。
- LLM-as-Judge 要防偏差并校准。
- 保留黄金集防过拟合，评测接入 CI。
- 失败案例必须回流。
