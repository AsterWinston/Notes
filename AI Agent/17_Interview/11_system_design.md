# 1. 答题框架

## 1.1 六步法总览

系统设计题考察的是"在信息不完整时如何做工程决策"，答题要遵循固定框架，先对齐边界再给方案。

```
① 澄清需求（功能 + 非功能）
② 估算规模（用户、QPS、数据量）
③ 高层设计（架构图）
④ 核心组件（逐个展开）
⑤ 关键问题（难点与取舍）
⑥ 演进（如何扩展）
```

### 1.1.1 六步的含义

| 步骤 | 目的 | 输出物 |
|------|------|--------|
| 澄清需求 | 明确做什么、不做什么 | 功能列表 + 非功能指标 |
| 估算规模 | 判断系统量级 | QPS、存储、成本数量级 |
| 高层设计 | 给出整体骨架 | 分层架构图 |
| 核心组件 | 证明方案能落地 | 每层技术选型 |
| 关键问题 | 展示技术深度 | 难点与权衡 |
| 演进 | 展示工程视野 | 分阶段扩展路径 |

### 1.1.2 时间分配

以 45 分钟为例：澄清需求 5 分钟、规模估算 5 分钟、高层设计 10 分钟、核心组件 15 分钟、关键问题 8 分钟、演进 2 分钟。切忌一上来就画图，先对齐边界。

## 1.2 每步的要点

### 1.2.1 澄清需求

先问"谁用、用来做什么、明确不能做什么"。功能需求问清核心链路与边界，非功能需求问清延迟、吞吐、可用性、一致性、成本与合规约束。

### 1.2.2 估算规模

用"假设 + 数量级"而非精确值，典型口径如下：

```
日请求 = 日活 × 人均请求
平均 QPS = 日请求 / 86400
峰值 QPS = 平均 QPS × (3 ~ 10)
存储 = 文档数 × 平均大小 × 副本数
```

### 1.2.3 高层设计与组件展开

高层给分层图（接入 / 应用 / 能力 / 模型 / 基础设施），再逐层展开核心组件。组件只讲关键路径，不堆砌技术名词。

### 1.2.4 关键问题与演进

关键问题挑 2~3 个真正的难点（权限、幻觉、一致性、成本），讲清取舍。演进给出从最小可用版本（MVP，Minimum Viable Product）到规模化的阶段路线。

# 2. 设计一个企业知识库问答系统

## 2.1 需求澄清

### 2.1.1 功能需求

- 文档导入：支持 PDF / Word / 网页等格式；
- 问答：基于企业文档回答并给出引用；
- 引用：答案需标注来源片段；
- 权限：不同部门只能看到授权文档。

### 2.1.2 非功能需求

| 指标 | 目标 | 说明 |
|------|------|------|
| 召回率 | ≥ 85% | Recall@5 |
| 首字延迟 | < 3s | 含检索与生成 |
| 多租户隔离 | 强隔离 | 数据不跨租户 |
| 可用性 | 99.9% | 关键业务链路 |

## 2.2 规模估算

### 2.2.1 数据量与存储

- 文档 10 万篇，向量 100 万条；
- 单条向量 1024 维 float32 约 4KB，100 万条约 4GB；
- 原文与元数据另计，总量在数十 GB 量级。

### 2.2.2 QPS 与成本

- 日活 1000 人，人均 20 次提问，日请求 2 万；
- 平均 QPS ≈ 0.23，峰值 QPS ≈ 50；
- 单次问答含向量化（Embedding）、重排、生成三段成本。

## 2.3 高层架构

### 2.3.1 架构图

```
上传 → 索引服务（解析/切分/向量化）→ PGVector
用户 → 问答服务（检索/重排/生成）→ 模型
```

### 2.3.2 数据流与在线链路

离线链路负责导入与索引，在线链路负责检索与生成，两者通过向量库解耦，索引更新不阻塞在线查询。

## 2.4 核心组件

### 2.4.1 解析与分块

- 解析：Tika / Docling；
- 分块：递归 800 / 100 + 标题拼接；
- 表格转自然语言，避免结构丢失。

### 2.4.2 检索与重排

- Embedding（向量化）：BGE-large-zh；
- 检索：混合（稠密 + BM25）+ RRF（Reciprocal Rank Fusion，倒数排名融合）；
- 重排：BGE Reranker。

### 2.4.3 生成与引用

- 强约束提示 + 引用；
- 引用校验，答案与来源可追溯；
- 资料不足时拒答。

Java 示例（带租户过滤的问答链路）：

```java
public String answer(String question, String tenantId) {
    List<Document> docs = vectorStore.similaritySearch(
            SearchRequest.builder()
                    .query(question)
                    .topK(20)
                    .filterExpression("tenantId == '" + tenantId + "'")
                    .build());
    List<Document> reranked = reranker.rerank(question, docs, 5);
    String context = reranked.stream()
            .map(Document::getText)
            .collect(Collectors.joining("\n---\n"));
    return chatClient.prompt()
            .system("只依据资料回答，资料不足时说明，并给出引用编号。")
            .user("资料：\n%s\n\n问题：%s".formatted(context, question))
            .call().content();
}
```

## 2.5 关键问题

### 2.5.1 权限与多租户隔离

- 元数据强制过滤：过滤条件在服务端拼接，不信任客户端；
- 越权测试：覆盖垂直越权与水平越权两类。

### 2.5.2 幻觉治理

- 强约束提示 + 引用校验 + 拒答；
- 忠实度指标纳入评测集。

### 2.5.3 增量更新

- 内容哈希判断文档是否变化；
- 别名切换实现索引原子替换。

## 2.6 演进路线

- 第一阶段：单机 RAG + PGVector；
- 第二阶段：加缓存、混合检索、重排；
- 第三阶段：多模态、GraphRAG、多租户独立索引。

# 3. 设计一个客服 Agent

## 3.1 需求澄清

### 3.1.1 功能需求

- 自动应答：基于知识库回答常见问题；
- 工具调用：查询订单、创建工单；
- 转人工：无法解决时转接坐席。

### 3.1.2 非功能需求

| 指标 | 目标 | 说明 |
|------|------|------|
| 解决率 | > 60% | 无需人工介入 |
| 转人工率 | < 25% | 过高则成本不降 |
| 响应延迟 | < 2s | 首字 |
| 合规 | 强约束 | 话术不得违规 |

## 3.2 规模估算

### 3.2.1 会话量与并发

- 日会话 1 万，人均 3 轮，日请求 3 万；
- 平均 QPS ≈ 0.35，峰值 QPS ≈ 20；
- 坐席人力按转人工率折算。

### 3.2.2 成本与人力

- 单次成本 = 意图分类 + RAG + 生成；
- 转人工率高则人力成本上升，需设阈值。

## 3.3 高层架构

### 3.3.1 架构图

```
用户 → 情绪识别 → 意图识别 → RAG/工具 → 置信度 → 转人工
```

### 3.3.2 决策链路

先情绪判断，再意图分类，再走 RAG 或工具，最后用置信度决定是否转人工。

## 3.4 核心组件

### 3.4.1 意图与情绪

- 意图分类（LLM 小模型）；
- 情绪识别（愤怒直接转人工）。

### 3.4.2 RAG 与工具

- RAG（知识库）；
- 工具（订单、工单）。

### 3.4.3 转人工

- 转人工（摘要 + 通知）；
- 附带上下文摘要，减少重复沟通。

## 3.5 关键问题

### 3.5.1 置信度与兜底

- 投诉必转人工；
- 置信度低转人工。

### 3.5.2 话术合规

- 话术合规校验；
- 敏感承诺拦截。

## 3.6 演进路线

- 第一阶段：规则 + RAG；
- 第二阶段：意图小模型 + 工具调用；
- 第三阶段：主动服务与坐席辅助。

# 4. 设计一个带状态的 Agent 平台

## 4.1 需求澄清

### 4.1.1 功能需求

- 多步任务：长流程编排；
- 可中断恢复：任务可暂停与续跑；
- 人工审批：关键步骤需人确认。

### 4.1.2 非功能需求

- 状态持久化、可观测、可扩展。

## 4.2 规模估算

### 4.2.1 任务量与并发

- 日任务 5 万，单任务平均 10 步；
- 峰值并发任务 500；
- 队列削峰，Worker 水平扩展。

### 4.2.2 存储与成本

- 每步检查点落库，状态存储量随步数线性增长；
- 长任务需设步数与成本上限。

## 4.3 高层架构

### 4.3.1 架构图

```
API → 任务分发 → 消息队列 → Worker → 状态存储
```

### 4.3.2 任务生命周期

创建 → 入队 → 执行（每步检查点）→ 挂起/恢复 → 完成/失败。

## 4.4 核心组件

### 4.4.1 状态存储与检查点

- 状态存储（每步检查点）；
- 支持按任务 ID 恢复。

Java 示例（检查点落库）：

```java
public void checkpoint(String taskId, int step, Object state) {
    Checkpoint cp = new Checkpoint(taskId, step, serialize(state), Instant.now());
    checkpointRepo.save(cp);
}
```

### 4.4.2 状态机与消息队列

- 状态机（显式流转）；
- 消息队列（削峰）。

### 4.4.3 分布式锁与 Trace

- 分布式锁（会话 / 任务级）；
- Trace（全链路，可观测）。

## 4.5 关键问题

### 4.5.1 恢复幂等

- 恢复幂等（已执行记录）；
- 每步记录执行结果，重放时跳过。

### 4.5.2 并发控制

- 并发控制（乐观锁 / 分布式锁）；
- 避免同一任务被并发执行。

### 4.5.3 人工审批

- 人工审批（挂起 + 恢复）；
- 审批通过后从检查点续跑。

## 4.6 演进路线

- 第一阶段：单机状态机 + 数据库；
- 第二阶段：消息队列 + Worker 集群；
- 第三阶段：多租户、优先级队列、可编排工作流。

# 5. 设计一个多 Agent 协作系统

## 5.1 需求澄清

### 5.1.1 功能需求

- 复杂任务分解、多 Agent 协作。

### 5.1.2 非功能需求

- 质量优于单 Agent、成本可控。

## 5.2 规模估算

### 5.2.1 调用量与成本

- 单任务子 Agent 调用次数 = 分解粒度 × 轮次；
- 成本约为单 Agent 的 2~5 倍。

### 5.2.2 并发与时限

- 子 Agent 可并行，需设全局超时与预算。

## 5.3 高层架构

### 5.3.1 架构图

```
Supervisor → [检索/分析/写作 Agent] → 共享状态 → 汇总
```

### 5.3.2 协作模式

Supervisor 负责分解与汇总，子 Agent 各司其职。

## 5.4 核心组件

### 5.4.1 Supervisor 与子 Agent

- Supervisor（强模型）；
- 子 Agent（各自工具）。

### 5.4.2 共享状态与通信

- 共享状态（外置）；
- 传摘要而非全量历史。

### 5.4.3 终止策略

- 终止策略（步数 / 成本 / 循环）。

## 5.5 关键问题

### 5.5.1 上下文膨胀

- 传摘要而非全量历史；
- 外置状态按需读取。

### 5.5.2 循环与死锁

- 循环检测（调用签名去重）。

### 5.5.3 与单 Agent 对比

- 对比单 Agent 基线，证明收益。

## 5.6 演进路线

- 第一阶段：Supervisor + 2 个子 Agent；
- 第二阶段：动态角色与并行；
- 第三阶段：跨任务记忆与自我优化。

# 6. 设计一个 LLM 网关

## 6.1 需求澄清

### 6.1.1 功能需求

- 统一接入多模型、限流、缓存、成本、降级。

### 6.1.2 非功能需求

- 高可用、低延迟、可观测。

## 6.2 规模估算

### 6.2.1 调用量与配额

- 全公司日调用 100 万次，峰值 QPS 200；
- 按租户分配 RPM（每分钟请求数）/ TPM（每分钟 Token 数）配额。

### 6.2.2 成本与容量

- 成本按模型分层，缓存命中可显著降本。

## 6.3 高层架构

### 6.3.1 架构图

```
应用 → 网关 → [路由/限流/缓存/熔断] → 多模型
```

### 6.3.2 请求链路

鉴权 → 配额检查 → 缓存查询 → 路由 → 模型调用 → 结果缓存与计量。

## 6.4 核心组件

### 6.4.1 路由

- 路由（按任务 / 租户 / 成本）。

### 6.4.2 限流与熔断

- 限流（RPM + TPM）；
- 熔断降级。

### 6.4.3 缓存与成本统计

- 缓存（结果 / 语义 / Prompt）；
- 成本统计。

## 6.5 关键问题

### 6.5.1 多模型一致性

- 统一协议与错误码，屏蔽差异。

### 6.5.2 降级策略

- 主模型故障切备用模型；
- 全部不可用时返回兜底话术。

## 6.6 演进路线

- 第一阶段：统一代理 + 计量；
- 第二阶段：限流、缓存、熔断；
- 第三阶段：智能路由与成本优化。

# 7. 通用答题要点

## 7.1 维度速查

| 维度 | 要点 |
|------|------|
| 需求 | 先澄清功能与非功能 |
| 规模 | 估算 QPS、数据量、成本 |
| 架构 | 分层：接入/应用/能力/模型/基础设施 |
| 可靠性 | 超时/重试/幂等/限流/熔断/降级 |
| 安全 | 租户隔离、权限、注入防御 |
| 可观测 | Trace/Metrics/Logs |
| 成本 | 模型分层、缓存、预算 |
| 取舍 | 主动说明权衡 |

## 7.2 分层与可靠性

### 7.2.1 分层职责

接入层做鉴权限流，应用层做编排，能力层做检索与工具，模型层做推理，基础设施层做存储与队列。

### 7.2.2 可靠性手段

超时、重试、幂等、限流、熔断、降级六件套，缺一不可。

## 7.3 安全、可观测与成本

### 7.3.1 安全与隔离

租户隔离、最小权限、注入防御，安全设计前置。

### 7.3.2 可观测与成本

Trace 关联全链路，Metrics（指标）看延迟与错误率，Logs（日志）做取证；成本靠模型分层与缓存控制。

# 8. 常见追问

## 8.1 追问速查表

| 追问 | 回答方向 |
|------|----------|
| 如何保证不越权？ | 元数据强制过滤 + 越权测试 |
| 如何处理长任务？ | 状态持久化 + 队列 + 流式进度 |
| 如何降本？ | 模型分层 + 缓存 + 裁剪 |
| 如何保证质量？ | 评测集 + CI + 灰度 |
| 如何处理故障？ | 熔断 + 降级 + 转人工 |

## 8.2 高频追问深挖

### 8.2.1 如何保证不越权

过滤条件服务端拼接，越权测试进 CI（持续集成），覆盖垂直与水平越权。

### 8.2.2 如何处理长任务

每步检查点 + 队列削峰 + 流式进度，支持挂起恢复。

# 9. 小结

## 9.1 关键结论

- 先澄清需求与规模，再谈架构。
- 分层设计，逐层展开核心组件。
- 主动说明可靠性、安全、成本、可观测。
- 强调取舍与权衡。
- 用具体数字与方案支撑。

- 能否画出分层架构并说明数据流？
- 能否对每个关键问题给出取舍？
- 能否给出分阶段演进路线？
