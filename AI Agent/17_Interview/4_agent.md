# 1. 什么是 Agent？与 Chatbot 的区别？

## 1.1 标准答案

Agent = LLM（大脑）+ 工具（手脚）+ 记忆（经验）+ 规划（策略），能自主完成多步任务。区别：Chatbot 只回答问题，Agent 会为目标采取行动。

## 1.2 深入原理

### 1.2.1 四组件与本质差异

| 组件 | 作用 |
|------|------|
| LLM | 推理与决策 |
| 工具 | 与外部世界交互 |
| 记忆 | 保存上下文与经验 |
| 规划 | 分解目标、安排步骤 |

Chatbot 是单轮映射（问题→回答）；Agent 是闭环控制（目标→行动→观察→再决策），具备状态与副作用。

## 1.3 代码/示例

```java
var agent = Agent.builder().llm(model).tools(tools).memory(memory).maxSteps(20).build();
String result = agent.run("帮我查订单并申请退款");
```

## 1.4 追问

问：Agent 必须有工具吗？答：生产意义上的 Agent 需要工具，否则只是带记忆的对话。

## 1.5 生产视角

引入 Agent 意味着引入副作用与不可预测性，需配套终止条件、鉴权、幂等与可观测。

# 2. Agent 的核心循环？

## 2.1 标准答案

```
感知 → 规划 → 行动 → 观察 → (循环) → 达成目标
```

终止条件是生命线：正常结束 + 多重硬性上限。

## 2.2 深入原理

### 2.2.1 循环与终止

每轮基于当前状态决策，调用工具后把结果回填，再进入下一轮，直至完成或触发上限。既要正常完成的软终止，也要步数、时间、token 的硬上限，防止失控。

## 2.3 代码/示例

```java
while (state.isRunning() && step++ < maxSteps) {
    Action a = planner.next(state);
    state.apply(executor.run(a));
}
```

## 2.4 追问

问：怎么判断"达成目标"？答：可由模型自评、工具返回值或外部校验器判定，重要场景需外部验证。

## 2.5 生产视角

硬上限必须存在且不可被模型绕过；每轮记录 Trace，便于复盘与计费。

# 3. Agent 与工作流的区别？

## 3.1 标准答案

| 维度 | 工作流 | Agent |
|------|--------|-------|
| 决策者 | 开发者 | 模型 |
| 路径 | 预先确定 | 运行时生成 |
| 可预测性 | 高 | 低 |

能用工作流解决的，不要用 Agent。生产主流是混合模式。

## 3.2 深入原理

### 3.2.1 确定性与混合模式

工作流路径固定、易测试、成本可控；Agent 灵活但不可预测、难调试、成本波动大。混合模式下外层用工作流编排确定步骤，内层在需判断的节点用 Agent，兼顾可控与灵活。

## 3.3 代码/示例

```java
// 伪代码：工作流中嵌入 Agent 节点，仅"决策"步自主
flow.step("校验", this::validate).step("决策", agentNode).step("落库", this::persist);
```

## 3.4 追问

问：什么时候该上 Agent？答：任务路径无法预先枚举、需动态决策时才用。

## 3.5 生产视角

优先工作流，确有必要再局部 Agent 化；为 Agent 节点设独立超时与兜底。

# 4. 自主性分级？

## 4.1 标准答案

| 级别 | 说明 |
|------|------|
| L1 | 建议型 |
| L2 | 审批后执行 |
| L3 | 限定自主 |
| L4 | 高度自主 |
| L5 | 完全自主 |

生产主力是 L3/L4；高风险操作用 L2。

## 4.2 深入原理

### 4.2.1 级别与风险挂钩

级别越高，模型自主决策范围越大；L1 只给建议，L5 全权代理。级别应按操作风险设定：读操作可高自主，写/资金操作应降级为审批。

## 4.3 代码/示例

```java
enum Autonomy { L1_SUGGEST, L2_APPROVE, L3_BOUNDED, L4_HIGH, L5_FULL }
Autonomy level = action.isRisky() ? Autonomy.L2_APPROVE : Autonomy.L4_HIGH;
```

## 4.4 追问

问：能否按操作细分？答：能，同一 Agent 可对不同工具设不同自主级别。

## 4.5 生产视角

用策略引擎按操作风险动态定级，高危必走人工审批，并留审批记录。

# 5. 工具调用机制？

## 5.1 标准答案

```
① 请求带工具 Schema
② 模型返回 tool_calls
③ 客户端执行
④ 用 tool_call_id 回填结果
⑤ 模型继续决策
```

## 5.2 深入原理

### 5.2.1 原生调用与并行

接口把工具定义为 JSON Schema，模型返回结构化调用，客户端执行后按 id 回填，形成闭环。模型可在一轮返回多个 tool_calls，客户端可并行执行再统一回填。

## 5.3 代码/示例

```java
var resp = llm.chat(messages, tools);
for (var call : resp.toolCalls())
    messages.add(ToolMessage.of(call.id(), registry.invoke(call.name(), call.arguments())));
```

## 5.4 追问

问：工具执行失败怎么办？答：把错误信息作为观察回填，让模型决策重试或改道，并设重试上限。

## 5.5 生产视角

工具调用全程记录输入输出与耗时；对写操作做幂等与审计，防止重复副作用。

# 6. 如何设计好工具？

## 6.1 标准答案

| 原则 | 说明 |
|------|------|
| 单一职责 | 一个工具做一件事 |
| 描述清晰 | 说清用途、边界、返回 |
| 参数简洁 | 不超过 5 个，类型明确 |
| 结果结构化 | 便于解析 |
| 写操作幂等 | 可安全重试 |
| 内置鉴权 | 工具级校验 |

## 6.2 深入原理

### 6.2.1 描述即提示与幂等

工具名称与描述是模型选择工具的主要依据，描述含糊会导致误用。Agent 会重试，写操作需用幂等键（如 requestId）保证重复调用不产生重复副作用。

## 6.3 代码/示例

```java
@Tool(description = "按订单号查询订单状态，只读")
OrderStatus queryOrder(@Param("订单号") String orderId) { ... }
@Tool(description = "申请退款，幂等，需 requestId")
RefundResult refund(@Param("订单号") String o, @Param("幂等键") String requestId) { ... }
```

## 6.4 追问

问：工具粒度多细合适？答：过细增加调用轮次，过粗降低复用，按业务原子操作划分。

## 6.5 生产视角

工具集中注册与版本管理；参数做校验与限流；写工具必须有鉴权与审计日志。

# 7. 工具过多怎么办？

## 7.1 标准答案

1. 按场景分组；2. 按权限裁剪；3. 工具检索（先筛再挂）；4. 工具合并。单次挂载建议不超过 10~15 个。

## 7.2 深入原理

### 7.2.1 选择成本与工具检索

工具过多会占用大量上下文，且模型选择准确率下降，易误选。可先用向量检索从工具库选出与当前任务相关的若干工具，再挂给模型。

## 7.3 代码/示例

```java
List<Tool> relevant = toolIndex.search(task, topK(8));
var resp = llm.chat(messages, relevant);
```

## 7.4 追问

问：工具检索会漏工具吗？答：可能，需保留兜底（如"列出全部工具"），并评测检索命中率。

## 7.5 生产视角

按租户/角色裁剪工具集，既降成本又做权限隔离；监控工具误选率。

# 8. Agent 的失败模式？

## 8.1 标准答案

| 失败 | 对策 |
|------|------|
| 死循环 | 步数上限 + 签名去重 |
| 幻觉 | 强约束 + 工具验证 |
| 目标漂移 | 每轮重申目标 |
| 工具误用 | 描述消歧 + 校验 |
| 上下文爆炸 | 窗口 + 压缩 |

## 8.2 深入原理

### 8.2.1 根因与检测

多为状态管理缺失与约束不足：没有上限、没有去重、没有目标锚定。可通过监控循环次数、重复签名、token 增长来提前发现并干预。

## 8.3 代码/示例

```java
if (!seenSignatures.add(call.signature())) {
    messages.add("你已调用过该工具，请勿重复。");
}
```

## 8.4 追问

问：目标漂移怎么防？答：把原始目标固定在系统提示中，每轮注入，并要求对齐检查。

## 8.5 生产视角

为每类失败设监控指标与自动干预（截断、降级、转人工），并纳入回归测试。

# 9. Agent 如何持久化状态？

## 9.1 标准答案

每步保存检查点，状态外置（Redis/DB）：

```
  ├── 消息历史
  ├── 计划
  ├── 已执行工具签名（幂等）
  └── 状态枚举
```

崩溃后从最近检查点恢复，恢复必须幂等。

## 9.2 深入原理

### 9.2.1 外置与幂等恢复

进程可能崩溃或重启，状态必须脱离进程内存，才能恢复与横向扩展。恢复后重放已执行步骤会产生副作用，必须靠幂等键或已执行签名跳过。

## 9.3 代码/示例

```java
record Checkpoint(List<Message> h, Plan p, Set<String> sigs, State s) {}
store.save(runId, new Checkpoint(messages, plan, signatures, state));
```

## 9.4 追问

问：检查点多频繁？答：每步保存一次，成本可接受且恢复粒度细。

## 9.5 生产视角

状态存储需高可用；恢复流程要演练；签名与幂等键统一管理，防重复执行。

# 10. 什么是 Reflexion？

## 10.1 标准答案

Reflexion（反思）：执行 → 评估 → 反思原因 → 改进重试。关键：把反思结果存入记忆，供后续尝试使用。客观验证优于 LLM 自评。

## 10.2 深入原理

### 10.2.1 反思循环与评估来源

失败后让模型分析原因并形成经验，下一次尝试时把经验带入，避免重复犯错。外部校验（测试、工具结果）比模型自评更可靠，自评易产生自信的错误。

## 10.3 代码/示例

```java
for (int i = 0; i < 3; i++) {
    Result r = attempt(task, memory);
    if (r.ok()) break; else memory.add(reflect(r));   // 反思入记忆
}
```

## 10.4 追问

问：反思一定有效吗？答：不一定，错误反思会引入噪声，需配合客观验证筛选。

## 10.5 生产视角

为反思设次数上限；反思结果做质量过滤；客观验证优先，自评仅作辅助。

# 11. Plan-and-Execute 与 ReAct？

## 11.1 标准答案

| 范式 | 说明 |
|------|------|
| ReAct | 边想边做 |
| Plan-and-Execute | 先规划全部再执行 |
| 混合（推荐） | 粗规划 + 步内 ReAct |

## 11.2 深入原理

### 11.2.1 两范式与混合模式

ReAct 每步都重新决策，灵活但易漂移；Plan-and-Execute 先定全局计划，稳定但计划可能过时。混合模式先做粗粒度规划锚定方向，每一步内部用 ReAct 应对变化，兼顾稳定与灵活。

## 11.3 代码/示例

```java
Plan plan = planner.make(task);              // 粗规划
for (Step s : plan.steps()) { executeWithReAct(s); if (plan.needsReplan()) plan = replan(plan); }
```

## 11.4 追问

问：计划失败怎么办？答：支持重规划（Replan），但要设重规划次数上限。

## 11.5 生产视角

长任务推荐混合模式；记录计划与实际执行的偏差，用于优化规划提示。

# 12. 如何防止 Agent 死循环？

## 12.1 标准答案

1. 最大步数上限；2. 工具调用签名去重；3. 提示中声明"不要重复调用"；4. 循环检测（连续相同调用）；5. Token/时间预算。

## 12.2 深入原理

### 12.2.1 成因与多重防线

模型陷入无效重试，或工具反复返回相同结果却无法推进。软约束（提示）可被绕过，硬约束（上限、去重、检测）是兜底，必须叠加使用。

## 12.3 代码/示例

```java
String sig = call.name() + call.arguments();
if (!seen.add(sig) && ++repeated > 3) throw new LoopDetectedException();
```

## 12.4 追问

问：去重会不会误伤合法重复？答：会，合法重试应带幂等键区分，签名应含关键参数与意图。

## 12.5 生产视角

死循环触发时自动中止并转人工；监控循环检测触发率，反推提示与工具设计问题。

# 13. Agent 的记忆分几层？

## 13.1 标准答案

```
上下文（本次请求）
短期记忆（会话内）
长期记忆（跨会话）
  ├── 情景（发生过什么）
  ├── 语义（知道什么）
  └── 程序性（怎么做）
```

## 13.2 深入原理

### 13.2.1 三层结构与三类长期记忆

上下文是当前窗口；短期是会话历史；长期跨会话持久化，支撑个性化与经验复用。情景记忆记录事件，语义记忆记录事实，程序性记忆记录技能与流程。

## 13.3 代码/示例

```java
memory.addEpisodic("用户上次申请了退款"); memory.addSemantic("用户偏好顺丰快递");  // 情景/语义
memory.addProcedural("退款需先校验订单状态");                                     // 程序性
```

## 13.4 追问

问：长期记忆怎么检索？答：通常用向量检索按相关性召回，再注入上下文。

## 13.5 生产视角

长期记忆涉及隐私与合规，需脱敏、可删除（被遗忘权）与访问控制。

# 14. 上下文压缩怎么做？

## 14.1 标准答案

| 策略 | 说明 |
|------|------|
| 滑动窗口 | 丢弃早期 |
| 滚动摘要 | 早期转摘要 |
| 结构化抽取 | 抽取事实/决策/实体（最可靠） |
| 分层摘要 | 多级压缩 |

关键实体（订单号、金额）不能丢，压缩后要校验。

## 14.2 深入原理

### 14.2.1 压缩目标与结构化

目标是在有限窗口内保留对后续决策最有用的信息，丢弃冗余对话。摘要会丢细节，结构化抽取把事实、决策、实体显式保存，最不易丢关键信息。

## 14.3 代码/示例

```java
record Facts(List<String> e, List<String> d, Map<String, String> slots) {}
Facts f = extractor.extract(messages);   // 抽取关键事实
messages = compress(messages, f);        // 用事实替换冗余历史
```

## 14.4 追问

问：压缩会丢信息导致答错吗？答：会，需压缩后校验关键实体是否保留。

## 14.5 生产视角

压缩前后做一致性校验；关键槽位单独存储，不依赖模型摘要。

# 15. Agent 架构有哪些？

## 15.1 标准答案

| 架构 | 适用 |
|------|------|
| 单体 | 简单任务 |
| 规划器-执行器 | 中长任务 |
| 分层 | 复杂系统 |
| 图编排 | 需确定性 |
| 多 Agent | 复杂分工 |

从单体起步，按需演进。

## 15.2 深入原理

### 15.2.1 演进与多 Agent 代价

单体简单但难扩展；规划器-执行器分离规划与执行；分层加管理层；图编排提供确定性；多 Agent 按角色分工，但通信开销大、易发散、难调试，非必要不引入。

## 15.3 代码/示例

```java
// 伪代码：规划器-执行器
Plan p = planner.plan(goal);
for (Step s : p.steps()) executor.execute(s, tools);
```

## 15.4 追问

问：什么时候用多 Agent？答：角色差异明显、可并行、单 Agent 上下文装不下时才用。

## 15.5 生产视角

架构选型匹配任务复杂度，避免过度设计；复杂架构需更强的可观测与成本控制。

# 16. Agent 上线检查清单？

## 16.1 标准答案

- 最大步数/Token/时间上限
- 工具鉴权、按权限裁剪
- 写操作幂等
- 状态持久化、支持恢复
- 全链路 Trace
- 失败兜底与转人工
- 成本监控与预算
- 注入防御
- 评测集接入 CI

## 16.2 深入原理

### 16.2.1 为什么需要清单

Agent 的失败模式多且隐蔽，清单把生产必需的防护固化为流程，防止遗漏。关键分四类：安全（鉴权、注入）、可靠（上限、幂等、恢复）、可观测（Trace、监控）、质量（评测、兜底）。

## 16.3 代码/示例

```java
var agent = Agent.builder().maxSteps(20).maxTokens(50_000).timeout(Duration.ofSeconds(60))
        .tracer(tracer).fallback(humanHandoff).build();
```

## 16.4 追问

问：清单多久复查一次？答：架构或工具变更时必查，日常按季度复查。

## 16.5 生产视角

清单纳入发布门禁，未通过不得上线；线上持续监控并回归验证防护有效性。

# 17. 小结

## 17.1 核心结论

- Agent = LLM + 工具 + 记忆 + 规划。
- 终止条件、幂等、鉴权、可观测是生产关键。
- 失败模式：循环、幻觉、漂移、工具误用。
- 从简到繁，先工作流后 Agent。
- 没有评测与 Trace 的 Agent 无法运维。

## 17.2 速记清单

| 主题 | 一句话 |
|------|--------|
| 定义 | LLM + 工具 + 记忆 + 规划 |
| 循环 | 感知-规划-行动-观察 |
| 选择 | 能工作流就不上 Agent |
| 自主 | 按风险定级，高危审批 |
| 工具 | 单一职责、幂等、鉴权 |
| 安全 | 上限、恢复、Trace、评测 |
