# 1. RAG 是什么？解决什么问题？

## 1.1 标准答案

RAG（Retrieval-Augmented Generation，检索增强生成）= 先检索相关资料，再让模型基于资料回答。解决知识截止、不懂私有知识、幻觉。优先级：提示工程 → RAG → 微调。

## 1.2 深入原理

### 1.2.1 为什么有效与微调边界

把参数化知识换成上下文知识，模型只需阅读理解、无需记忆，知识可实时更新且可溯源。RAG 改知识，微调改行为与风格；知识频繁变化优先 RAG，风格稳定需求才微调。

## 1.3 代码/示例

```java
List<Chunk> docs = retriever.search(query, topK(5));
String context = docs.stream().map(Chunk::text).collect(joining("\n---\n"));
String answer = llm.chat(systemWithContext(context), query);
```

## 1.4 追问

问：RAG 能消除幻觉吗？答：不能，但能大幅降低；检索为空或资料矛盾时仍会幻觉，需拒答机制。

## 1.5 生产视角

优先提示工程，再上 RAG，最后才微调；RAG 需配套评测、监控与引用溯源。

# 2. RAG 的两阶段？

## 2.1 标准答案

```
离线索引：解析 → 切分 → 向量化 → 入库
在线查询：改写 → 检索 → 重排 → 生成
```

效果 = 检索质量 × 生成质量，检索是主要瓶颈。

## 2.2 深入原理

### 2.2.1 职责划分与瓶颈

离线保证数据质量与索引新鲜度，在线保证低延迟与相关性，二者解耦便于独立优化。生成模型已足够强，多数答错源于没检索到或检索到错误内容，故检索质量决定上限。

## 2.3 代码/示例

```java
chunks.forEach(c -> store.upsert(c.id(), embed(c.text()), c.metadata()));
var hits = store.search(embed(rewrite(query)), filter, topK);
```

## 2.4 追问

问：索引多久更新一次？答：按数据时效要求定，可增量更新加定时全量重建。

## 2.5 生产视角

监控索引延迟与新鲜度；检索与生成分别埋点，定位瓶颈在哪一段。

# 3. 分块策略有哪些？

## 3.1 标准答案

| 策略 | 特点 |
|------|------|
| 固定长度 | 简单 |
| 递归 | 保持语义（推荐默认） |
| 按结构 | 尊重文档结构 |
| 语义 | 语义完整但成本高 |
| 父子 | 小块检索、大块喂模型 |

重叠 10%~20%，防语义切断；参数必须评测驱动。

## 3.2 深入原理

### 3.2.1 块大小与父子块

块太小丢上下文，块太大噪声多且稀释向量语义，通常 256~512 token 起步再调。用小块做检索保证精度，命中后返回其父块给模型，兼顾检索与生成。

## 3.3 代码/示例

```java
var splitter = RecursiveSplitter.builder()
        .chunkSize(400).overlap(60).separators(List.of("\n\n", "。", " ")).build();
```

## 3.4 追问

问：要不要按标题切？答：结构化文档优先按标题/章节切，再在节内递归切分。

## 3.5 生产视角

分块参数写入配置并纳入评测矩阵，换文档类型时重新评测，不照搬他人参数。

# 4. Embedding 模型怎么选？

## 4.1 标准答案

| 场景 | 推荐 |
|------|------|
| 中文 | BGE-large-zh、GTE |
| 多语言 | BGE-m3、E5、Jina |
| 无 GPU | OpenAI text-embedding-3 |

注意前缀要求：BGE 查询前缀、E5 的 `query:`/`passage:`。必须用自有数据评测，不能只看榜单。

## 4.2 深入原理

### 4.2.1 双塔与前缀归一化

Embedding 把文本映射为稠密向量，用余弦相似度衡量语义相近，检索即最近邻搜索。部分模型对查询与文档用不同前缀，漏加会显著掉点；向量一般需 L2 归一化。

## 4.3 代码/示例

```java
double sim = cosine(l2norm(embed("query: " + query)),
                    l2norm(embed("passage: " + passage)));
```

## 4.4 追问

问：换 Embedding 要重建索引吗？答：要，向量空间不同不可混用，需全量重嵌入。

## 4.5 生产视角

Embedding 版本化，索引与模型版本绑定；上线前用自有评测集对比 Recall@K。

# 5. 向量库怎么选？

## 5.1 标准答案

| 库 | 适用 |
|----|------|
| PGVector | 已有 PG、中小规模 |
| Milvus | 亿级规模 |
| Qdrant | 复杂过滤 |
| Redis | 高并发、TTL |
| ES | 混合检索 |

多租户务必选支持预过滤的库。

## 5.2 深入原理

### 5.2.1 近似最近邻与预过滤

向量库用 HNSW/IVF 等索引做 ANN 检索，以少量召回损失换取大幅提速。先按元数据过滤再检索（预过滤）能保证结果数量；后过滤可能因不足 K 而返回空。

## 5.3 代码/示例

```java
SearchRequest req = SearchRequest.builder().vector(qv)
        .filter("tenantId == 't1' && status == 'active'").topK(20).build();
```

## 5.4 追问

问：小规模也要上专业向量库吗？答：不必，PGVector 足够，避免过早引入运维复杂度。

## 5.5 生产视角

选型看规模、过滤能力、运维成本与团队栈；预留水平扩展与索引重建方案。

# 6. 稠密检索与稀疏检索的区别？

## 6.1 标准答案

| 维度 | 稠密 | 稀疏（BM25） |
|------|------|--------------|
| 匹配 | 语义 | 词面 |
| 同义词 | 是 | 否 |
| 专有名词 | 否 | 是 |

混合检索是生产标配。

## 6.2 深入原理

### 6.2.1 互补性与 BM25

稠密擅长语义泛化但弱于精确匹配；稀疏擅长关键词与专名但不懂同义，二者互补。BM25 基于词频与逆文档频率加权，并做文档长度归一化，是稀疏检索的经典基线。

## 6.3 代码/示例

```java
var dense = vectorStore.search(q, 30);
var sparse = bm25.search(q, 30);
var merged = rrfFuse(List.of(dense, sparse), 60);
```

## 6.4 追问

问：只用稠密行不行？答：通用问答可以，但含型号、编号、专名的场景会明显掉点。

## 6.5 生产视角

默认上混合检索，尤其企业知识库；分别监控两路召回的贡献度。

# 7. 混合检索怎么融合？

## 7.1 标准答案

RRF（Reciprocal Rank Fusion，倒数排名融合，推荐）：

```
RRF(d) = Σ 1/(k + rank_i(d))，k=60
```

只依赖排名，规避分数不可比问题。

## 7.2 深入原理

### 7.2.1 为什么用排名

不同检索器分数量纲不同，直接加权不可比；RRF 只看名次，鲁棒且无需调参。也可对分数归一化后加权，但需调参，RRF 是更稳的默认选择。

## 7.3 代码/示例

```java
for (var list : lists)
    for (int i = 0; i < list.size(); i++)
        score.merge(list.get(i).id(), 1.0 / (60 + i + 1), Double::sum);
```

## 7.4 追问

问：k 取多少？答：常用 60，对结果不敏感，通常无需精调。

## 7.5 生产视角

融合后接重排，形成"多路召回 → 融合 → 精排"流水线，并记录各路贡献。

# 8. 重排的作用？

## 8.1 标准答案

重排（Rerank）用交叉编码器（Cross-Encoder）精排，精度高于双塔。

```
召回多（20~50）→ 重排 → 取少（3~5）
```

重排救不了糟糕的召回。

## 8.2 深入原理

### 8.2.1 双塔与交叉编码器

双塔分别编码查询与文档，快但交互弱；交叉编码器拼接后联合编码，精度高但慢。交叉编码器无法离线建索引，只能对小候选集打分，因此作为精排阶段。

## 8.3 代码/示例

```java
List<Chunk> candidates = retrieve(query, 30);
List<Chunk> top = reranker.rank(query, candidates).subList(0, 5);
```

## 8.4 追问

问：召回要多少？答：20~50 较常见，太少重排无从选择，太多增加延迟。

## 8.5 生产视角

重排模型单独评测（nDCG）；若召回本身差，优先修分块与检索，而非加重重排。

# 9. 查询改写有哪些技术？

## 9.1 标准答案

| 技术 | 作用 |
|------|------|
| 查询重写 | 口语 → 规范 |
| 多查询扩展 | 多角度召回 |
| 查询分解 | 复杂问题拆分 |
| HyDE | 生成假设答案再检索 |

多轮对话必须结合历史改写，解决指代。

## 9.2 深入原理

### 9.2.1 改写动机与 HyDE

用户输入口语化、含指代、表述与文档不一致，直接检索命中率低。HyDE 先让模型生成假设答案，用答案向量检索，因更接近文档语料分布，常能提升召回。

## 9.3 代码/示例

```java
String rw = llm.chat("结合历史把问题改写为独立查询：" + history + query);
String hyde = llm.chat("基于问题写一段可能的答案：" + rw);
var hits = retrieve(hyde, 20);
```

## 9.4 追问

问：改写会增加延迟吗？答：会，可用小模型或仅在多轮/低召回时触发。

## 9.5 生产视角

改写效果单独评测，监控改写后 Recall@K 提升；多轮场景必须带历史。

# 10. 如何做多租户隔离？

## 10.1 标准答案

```
filterExpression("tenantId == '" + tenant + "'")
```

过滤条件必须服务端注入，绝不信任客户端；必须写越权测试。

## 10.2 深入原理

### 10.2.1 隔离层级与越权风险

可物理隔离（独立库/索引）或逻辑隔离（元数据过滤），后者成本低但对过滤正确性要求高。若过滤条件由客户端传入，攻击者可篡改 tenantId 读取他人数据，是最典型的数据泄露路径。

## 10.3 代码/示例

```java
String tenant = SecurityContext.currentTenant();  // 服务端可信来源
Filter f = Filter.eq("tenantId", tenant);          // 强制注入
var hits = store.search(qv, f, topK);
```

## 10.4 追问

问：写入也要过滤吗？答：要，写时强制打租户标记，读时强制过滤，两端都校验。

## 10.5 生产视角

越权测试纳入回归；过滤逻辑集中封装，禁止各处手写拼接，防表达式注入。

# 11. RAG 效果不好，如何排查？

## 11.1 标准答案

```
① 打印检索结果，看答案是否在上下文中
② 不在 → 检索问题（分块/Embedding/改写/提高 topK）
③ 在但答错 → 生成问题（提示/模型）
```

先定位检索还是生成。

## 11.2 深入原理

### 11.2.1 二分定位与常见根因

RAG = 检索 × 生成，先看上下文是否包含答案，可快速把问题归到某一段。检索侧根因：分块切断、Embedding 不适配、缺改写；生成侧根因：提示未约束、上下文噪声、模型能力不足。

## 11.3 代码/示例

```java
var ctx = retriever.search(query, 5);
log.info("ctx={}", ctx.stream().map(Chunk::text).toList());
boolean inCtx = ctx.stream().anyMatch(c -> c.text().contains(gold));
```

## 11.4 追问

问：怎么知道答案该在上下文里？答：用带标注的评测集，标注每题的支撑文档。

## 11.5 生产视角

建立"检索命中率 + 生成正确率"双指标看板，故障时先看检索命中率。

# 12. RAG 评测指标？

## 12.1 标准答案

| 层次 | 指标 |
|------|------|
| 检索 | Recall@K、MRR、nDCG |
| 生成 | 忠实度、相关性、上下文精确/召回 |
| 端到端 | 答案正确率、拒答准确率 |

## 12.2 深入原理

### 12.2.1 检索与生成指标

Recall@K 衡量前 K 是否含相关文档；MRR 看首个相关的排名；nDCG 考虑排序质量。忠实度衡量答案是否忠于上下文（防幻觉）；相关性衡量是否切题；上下文指标衡量片段质量。

## 12.3 代码/示例

```java
double recall = Eval.recallAtK(goldDocs, retrieved, 5);
double mrr = Eval.mrr(goldDocs, retrieved);
double faith = Eval.faithfulness(answer, context);
```

## 12.4 追问

问：端到端正确率够用吗？答：不够，拆成检索/生成才能定位与优化，端到端只用于验收。

## 12.5 生产视角

指标纳入 CI 回归；忠实度用 LLM 裁判需校准，辅以人工抽检。

# 13. GraphRAG 解决什么问题？

## 13.1 标准答案

解决多跳推理与全局问题：用知识图谱显式建模实体与关系，沿图遍历检索。构建成本高，只在多跳/关系类问题确实重要时用。

## 13.2 深入原理

### 13.2.1 多跳与构建成本

传统 RAG 按块召回，难以连接分散事实；GraphRAG 用实体关系边把事实串起来，支持多跳。但需实体抽取、关系抽取、图构建与社区摘要，前期与维护成本都高。

## 13.3 代码/示例

```java
// 伪代码：多跳遍历
List<Entity> start = graph.findEntities(query);
List<Path> paths = graph.traverse(start, hops(2));
```

## 13.4 追问

问：GraphRAG 能替代传统 RAG 吗？答：不能，它是补充，多数单跳问题传统 RAG 更划算。

## 13.5 生产视角

先评估多跳问题占比，再决定是否引入；可先做局部图而非全量图。

# 14. Agentic RAG 是什么？

## 14.1 标准答案

让 Agent 自主决定是否检索、检索几次、用什么工具。三种模式：检索决策、迭代检索、自适应过滤。简单问题走传统 RAG，复杂问题走 Agentic。

## 14.2 深入原理

### 14.2.1 决策与迭代

并非所有问题都需要检索，Agent 先判断是否需要，避免无谓检索与噪声。一次检索不足时，基于中间结果再检索，逐步逼近答案。

## 14.3 代码/示例

```java
for (int i = 0; i < MAX_ITER; i++) {
    var hits = retrieve(currentQuery);
    if (enough(hits)) break;
    currentQuery = refine(currentQuery, hits);
}
```

## 14.4 追问

问：Agentic 一定更好吗？答：不一定，延迟与成本更高，简单问题用传统 RAG 更快更稳。

## 14.5 生产视角

为 Agentic 设迭代与成本上限；按问题复杂度路由，简单走快速通道。

# 15. 如何减少 RAG 幻觉？

## 15.1 标准答案

1. 强约束提示："只依据资料，不足则拒答"；
2. 要求标注来源；
3. 引用校验（来源必须真实存在）；
4. 提高检索质量；
5. 降低 temperature。

## 15.2 深入原理

### 15.2.1 幻觉来源

资料缺失、资料冲突、上下文噪声、模型过度补全，都会导致编造。

### 15.2.2 拒答与溯源

允许"我不知道"能显著降低幻觉；强制引用并校验引用存在，可拦截编造来源。

## 15.3 代码/示例

```java
String sys = "只依据 <context> 回答；不足则回复\"资料不足\"；结论后用 [docId] 标注来源。";
var answer = llm.chat(sys, context, query);
verifyCitations(answer, context);
```

## 15.4 追问

问：拒答率高了怎么办？答：先提升检索召回，再放宽提示，二者需权衡。

## 15.5 生产视角

监控拒答率与引用有效率；忠实度指标纳入评测，异常时告警。

# 16. RAG 优化顺序？

## 16.1 标准答案

```
1. 建评测集        2. 调分块（收益最大）
3. 加混合检索      4. 加 Rerank
5. 查询改写/HyDE   6. 上下文增强
7. 换模型          8. 微调（最后手段）
```

## 16.2 深入原理

### 16.2.1 收益排序与单变量

分块与检索决定上限，投入产出比最高；换模型与微调成本高、收益不确定，放最后。并行改动无法归因，必须单变量迭代，配合评测对比。

## 16.3 代码/示例

```java
for (Variant v : variants) {
    double s = eval.run(pipeline(v), dataset);
    report.put(v.name(), s);
}
```

## 16.4 追问

问：可以跳过评测集吗？答：不行，没有评测的优化都是盲调，无法判断是否真的变好。

## 16.5 生产视角

按此顺序排期，每步记录收益；优先高杠杆项，避免过早陷入微调。

# 17. 小结

## 17.1 核心结论

- RAG = 检索 + 增强 + 生成，检索是瓶颈。
- 分块、混合检索、重排是三大优化点。
- 多租户必须元数据过滤 + 越权测试。
- 先定位检索/生成，再优化。
- 没有评测的优化都是盲调。

## 17.2 速记清单

| 主题 | 一句话 |
|------|--------|
| 两阶段 | 离线索引 + 在线查询 |
| 分块 | 递归 + 重叠，评测驱动 |
| 检索 | 稠密 + 稀疏混合 |
| 融合 | RRF，k=60 |
| 精排 | 交叉编码器，救不了坏召回 |
| 安全 | 服务端强制租户过滤 |
