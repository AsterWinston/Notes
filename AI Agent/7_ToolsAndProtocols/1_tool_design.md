# 1. 工具设计决定 Agent 上限

> 模型只能调用"被设计出来的工具"。
> 工具设计得好，Agent（智能体）事半功倍；设计得差，模型频繁误用。

## 1.1 核心结论

- 工具是模型与外部世界之间的**唯一接口**，模型无法调用未被封装的能力。
- 工具设计决定 Agent 的**能力上限**，提示工程（Prompt Engineering）只能逼近上限，无法突破上限。
- 工具质量的最终衡量是两个指标：**任务成功率**与**误调用率**。
- 好工具应当"自解释"：模型仅凭名称、描述与 Schema（模式）就能正确选择与调用。

## 1.2 为什么工具设计决定上限

### 1.2.1 行动空间由工具集定义

模型在每一轮对话中只能从已挂载的工具列表里选择，可行动作是工具集的子集：

```
工具集 = { t1, t2, ..., tn }
模型可选动作 ⊆ 工具集
```

即使模型推理能力很强，只要某项能力没有被封装成工具，Agent 就永远无法执行该动作。例如"下单"没有被封装，模型无论怎样规划都做不了。

### 1.2.2 工具质量与误用率的关系

| 工具设计 | 模型行为 | 后果 |
|----------|----------|------|
| 名称模糊 | 凭猜测选择 | 误调用相邻工具 |
| 描述缺失 | 不知道何时用 | 该用不用、不该用乱用 |
| 参数含糊 | 填错参数 | 参数校验失败、重试变多 |
| 结果冗长 | 上下文被占满 | 关键信息被淹没，Token 浪费 |
| 无边界说明 | 越权调用 | 安全风险 |

## 1.3 本文范围与阅读方式

本文聚焦"如何设计工具"；同模块的 `2_function_schema.md` 讲参数 Schema（模式），`3_tool_calling_mechanics.md` 讲调用机制。建议按 1 → 2 → 3 顺序阅读。

# 2. 好工具的标准

## 2.1 七条标准总览

结论先行：一个好工具应当同时满足下列七条，缺一即会在某类场景下退化。

| 标准 | 说明 |
|------|------|
| 单一职责 | 一个工具只做一件事 |
| 语义清晰 | 名称与描述准确表达用途 |
| 边界明确 | 说明何时用、何时不用 |
| 参数简洁 | 参数少、类型明确 |
| 结果结构化 | 返回可解析的结构 |
| 幂等 | 写操作可安全重试 |
| 安全 | 内置鉴权与校验 |

## 2.2 标准逐条拆解

### 2.2.1 单一职责与语义清晰

单一职责意味着工具名可以直接回答"它做什么"。若一个工具需要"看参数才知道做什么"，说明职责过多，应拆分。语义清晰要求名称使用业务领域的词，而非技术实现细节。

### 2.2.2 边界明确与参数简洁

边界明确要求在描述里写清"何时使用、何时不用"，这是降低误调用率最有效的手段。参数简洁建议参数个数不超过 5 个，类型使用具体类型而非统一用 `String`。

### 2.2.3 结果结构化、幂等与安全

结果结构化让模型能稳定解析；幂等保证写操作在重试或重复调用下不产生副作用；安全要求工具内部完成鉴权、校验与审计，而不是依赖调用方自觉。

## 2.3 坏工具的典型症状

- 工具名是 `query`、`handle`、`process` 这类泛动词。
- 描述只有一句话，且与名称重复。
- 一个工具接收 `action` 参数，内部用 `switch` 分流。
- 返回值是大段自然语言文本或对象 `toString()`。
- 写操作没有幂等键，重试即重复扣款。
- 鉴权写在 Controller（控制器）层，工具层可被绕过。

# 3. 命名

## 3.1 命名原则

结论先行：命名采用"动词 + 名词"结构，具体到业务对象，避免与相邻工具混淆。

| 原则 | 说明 |
|------|------|
| 动词开头 | get / create / update / delete / search |
| 具体 | `getOrderById` 而非 `get` |
| 无歧义 | 避免与相邻工具混淆 |

## 3.2 Java 示例：从模糊到清晰

```java
// 反例：模糊，模型无法判断查的是什么、按什么查
@Tool("查询")
String query(String s);

// 正例：动词 + 名词，语义明确
@Tool("按订单号查询订单详情")
OrderResult getOrderById(@P("订单号，格式如 A123") String orderId);
```

## 3.3 命名边界与坑

- 不要用缩写：`qryOrd` 对模型毫无意义。
- 不要用中文拼音：`chaxunDingdan` 语义差。
- 同一动词在整组工具里保持一致：统一用 `get` 或统一用 `query`，不要混用。
- 命名长度适中：过长会占用上下文，过短会歧义。

# 4. 描述设计

## 4.1 描述是模型选择工具的唯一依据

结论先行：模型在决策阶段看不到工具的实现代码，只能读到名称、描述与参数 Schema。描述因此是"工具的产品说明书"。

```
模型决策输入 = 名称 + 描述 + 参数 Schema
模型决策输出 = 是否调用、调用哪个、传什么参数
```

## 4.2 描述模板：用途、边界、返回

### 4.2.1 用途

说清工具做什么、适用于哪些用户意图。用途应使用业务语言而非技术语言。

### 4.2.2 不适用场景

显式列出"不适用场景"，并指名应改用的相邻工具，这是避免误调用的关键。

### 4.2.3 返回值

说明返回哪些字段，让模型知道调用后能拿到什么，从而决定是否值得调用。

```java
@Tool("""
        查询指定订单的详细信息。

        适用场景：
        - 用户询问订单状态、金额、商品、下单时间
        - 需要订单的基础信息以进行后续操作

        不适用场景：
        - 查询物流轨迹（请使用 queryLogistics）
        - 查询退款进度（请使用 queryRefund）

        返回：订单号、状态、金额、下单时间、商品列表
        """)
```

要点：

- **说清用途**；
- **说清不适用**（避免误用相邻工具）；
- **说清返回什么**（让模型知道能拿到什么）。

## 4.3 描述的边界与常见错误

| 错误 | 说明 | 修正 |
|------|------|------|
| 描述与名称重复 | "查询订单" 只说了一遍 | 补充适用/不适用/返回 |
| 描述太长 | 挤占上下文、稀释重点 | 控制在 5~8 行 |
| 描述含实现细节 | "走 MySQL 索引" 与模型无关 | 只写业务语义 |
| 不写不适用 | 相邻工具互相抢调用 | 显式排除 |

# 5. 参数设计

## 5.1 参数设计原则

结论先行：参数少、类型明确、有描述、可选参数显式标注、避免深层嵌套。

| 原则 | 说明 |
|------|------|
| 参数少 | 建议 ≤ 5 个 |
| 类型明确 | 用具体类型而非 String |
| 有描述 | 说明格式与取值范围 |
| 可选参数 | 明确标注 required=false |
| 避免嵌套 | 复杂结构拆解 |

## 5.2 Java 示例

```java
// 反例：参数过多、类型模糊
@Tool("查询")
String query(String a, String b, String c, String d);

// 正例：参数少、类型明确、有描述
@Tool("按日期范围查询订单")
List<Order> queryOrders(
        @P("开始日期，格式 yyyy-MM-dd") String startDate,
        @P("结束日期，格式 yyyy-MM-dd") String endDate,
        @P(value = "订单状态：PAID/CANCELLED，可选", required = false) String status);
```

## 5.3 参数边界与校验

- 参数个数超过 5 个时，考虑拆工具或引入请求对象（但注意嵌套对弱模型的负担）。
- 日期、金额、枚举等都要在描述里写清格式与取值范围。
- 描述只是提示，服务端必须再做一次校验，不能信任模型传入的值。
- 对可选参数，要明确"缺省时"的行为。

# 6. 结果设计

## 6.1 结构化结果

结论先行：返回结构化、精简、含状态、可引用的数据，而不是对象 `toString()`。

```java
// 反例：返回大段文本
return order.toString();

// 正例：结构化、精简、含状态
public record OrderResult(
        String orderId,
        String status,
        BigDecimal amount,
        List<String> items
) {}
```

原则：

- **精简**：只返回模型需要的字段；
- **结构化**：便于解析；
- **含状态**：成功/失败明确；
- **可引用**：包含来源信息。

## 6.2 统一结果包装

### 6.2.1 ToolResult 定义

```java
public record ToolResult<T>(
        boolean success,
        T data,
        String error,
        Map<String, Object> metadata
) {
    public static <T> ToolResult<T> ok(T data) {
        return new ToolResult<>(true, data, null, Map.of());
    }
    public static <T> ToolResult<T> fail(String error) {
        return new ToolResult<>(false, null, error, Map.of());
    }
}
```

统一包装的价值在于：框架层、模型层、日志层都能用同一套字段判断成功与失败。

### 6.2.2 分页与截断

列表结果必须分页，并给出总数与游标，避免一次性回填上千条记录：

```java
public record PageResult<T>(
        List<T> items,
        int page,
        int size,
        long total,
        boolean hasMore
) {}
```

## 6.3 结果设计的边界与坑

- 错误信息要结构化，不要只回 `null` 或抛异常。
- 不要把内部堆栈、SQL 语句回填给模型，既浪费 Token 又有安全风险。
- 大字段（图片 base64、长文本）应转为 URL 或摘要。

# 7. 工具粒度

## 7.1 粒度的两种失败模式

结论先行：工具过粗则参数复杂、难复用；过细则数量膨胀、选择困难。粒度应"按业务动作"划分。

| 粒度过粗 | 粒度过细 |
|----------|----------|
| 一个工具做太多 | 太多工具难选择 |
| 参数复杂 | 调用次数多 |
| 难以复用 | 提示膨胀 |

## 7.2 粒度决策方法

### 7.2.1 按业务动作划分

以"用户意图"为单位而不是"数据字段"为单位：查订单、取消订单、催单是三个动作，因此是三个工具。

### 7.2.2 粒度评估表

| 问题 | 若回答"是" | 建议 |
|------|-----------|------|
| 名称里含"和/以及" | 职责过多 | 拆分 |
| 需要 action 参数分流 | 职责过多 | 拆分 |
| 多个工具总是一起被调用 | 职责过细 | 合并 |
| 单个工具被调用的概率极低 | 过细 | 合并或延迟挂载 |

```java
// 反例：过粗，一个工具做所有事
@Tool("处理订单") String handleOrder(String action, String orderId, String... args);

// 反例：过细，拆分过度
@Tool("获取订单号") String getOrderId(String orderId);
@Tool("获取订单状态") String getOrderStatus(String orderId);
@Tool("获取订单金额") BigDecimal getOrderAmount(String orderId);

// 正例：按业务动作划分
@Tool("查询订单详情") OrderResult getOrder(String orderId);
@Tool("取消订单") ToolResult cancelOrder(String orderId);
@Tool("催单") ToolResult remindOrder(String orderId);
```

## 7.3 粒度反例

- "获取订单号/状态/金额"三个工具本质是一次查询的三个字段，应合并。
- "创建订单并扣库存并发短信"是一个跨域编排，应拆成多个工具，由模型或工作流编排。

# 8. 工具分组与动态挂载

## 8.1 为什么要分组

结论先行：工具数量增长会线性推高选择难度与提示长度。按业务场景分组、按需挂载，可显著降低误调用率与 Token 消耗。

## 8.2 Java 示例

```java
public enum ToolGroup {
    ORDER,      // 订单相关
    REFUND,     // 退款相关
    PRODUCT,    // 商品相关
    USER        // 用户相关
}

// 按场景只挂载相关组
public List<ToolCallback> toolsFor(String scenario) {
    Set<ToolGroup> groups = scenarioGroupMapping.get(scenario);
    return allTools.stream()
            .filter(t -> groups.contains(groupOf(t)))
            .toList();
}
```

## 8.3 分组的边界与坑

- 分组不能造成"该用的工具没挂载"，需要兜底策略（如允许模型申请扩展工具）。
- 跨组工具（如"用户查订单"）应归入最常用的组。
- 挂载决策最好可观测：记录每轮实际挂载了哪些工具，便于排查。

# 9. 工具的安全设计

## 9.1 安全五要素

结论先行：安全必须是工具的内置属性，包含鉴权、归属校验、幂等、审计、可恢复（软删除）五要素。

| 要素 | 目的 |
|------|------|
| 鉴权 | 确认调用者有权限 |
| 归属校验 | 确认对象属于调用者 |
| 幂等 | 重试不产生重复副作用 |
| 审计 | 可追溯谁在何时做了什么 |
| 软删除 | 误操作可恢复 |

## 9.2 Java 示例

### 9.2.1 鉴权与归属

```java
@Tool("删除订单（仅管理员）")
ToolResult deleteOrder(@P("订单号") String orderId) {
    // ① 鉴权
    if (!currentUser().hasRole("ADMIN")) {
        return ToolResult.fail("无权限");
    }
    // ② 归属校验
    if (!orderService.belongsTo(currentUser(), orderId)) {
        return ToolResult.fail("无权操作该订单");
    }
    // ...
}
```

### 9.2.2 幂等与审计

```java
    // ③ 幂等：以幂等键去重
    if (!idempotency.tryAcquire("DELETE_ORDER", orderId)) {
        return ToolResult.ok(orderService.get(orderId));  // 直接返回既有结果
    }
    // ④ 审计
    auditLog.record("DELETE_ORDER", orderId);
    // ⑤ 软删除（可恢复）
    return ToolResult.ok(orderService.softDelete(orderId));
}
```

## 9.3 安全反例

- 只在 UI 层隐藏按钮，工具层不校验权限。
- 用 `orderId` 直接删除而不校验归属，造成越权。
- 写操作无幂等键，模型重试导致重复扣款。
- 无审计日志，出问题无法定位。

# 11. 生产注意事项

## 11.1 常见风险表

| 风险 | 建议 |
|------|------|
| 工具过粗 | 按业务动作拆分 |
| 工具过多 | 按场景动态挂载 |
| 描述模糊 | 写清用途/边界/返回 |
| 结果过大 | 分页 + 截断 + 摘要 |
| 无鉴权 | 工具层强制鉴权 |
| 无幂等 | 引入幂等键 |
| 无审计 | 结构化审计日志 |
| 无超时 | 每工具设超时与降级 |

## 11.2 评测驱动迭代

工具描述与参数不是一次写好就结束，应建立评测集：给定用户问题，期望调用哪个工具、传什么参数。每次修改描述后用评测集回归，观察误调用率变化。

# 12. 小结

## 12.1 核心结论

- 工具设计决定 Agent 能力上限。
- 好工具：单一职责、描述清晰、参数简洁、结果结构化。
- 描述要说清"用途、边界、返回"。
- 工具粒度要适中，按场景分组。
- 安全（鉴权、幂等、审计）是工具的内置属性。

## 12.2 落地清单

- 先设计工具清单，再写实现。
- 每个工具都补上描述模板与参数约束。
- 用评测集验证描述是否被正确理解。
- 上线后持续监控误调用率并迭代。
