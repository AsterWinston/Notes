# 1. 模块定位

工具（Tool）是 Agent 与外部世界交互的唯一通道。模型本身只能生成文本，所有"真实世界动作"——读文件、查数据库、调 API、开浏览器——都必须通过工具完成。本模块讲三件事：如何设计好工具、如何安全地调用、如何用标准协议（MCP/A2A）接入生态。

## 1.1 本模块解决什么问题

Agent 的能力上限，往往不取决于模型，而取决于"它能触达什么"。

| 层次 | 问题 | 本模块对应内容 |
|------|------|----------------|
| 设计层 | 工具怎么写模型才用对 | 工具设计与 Function Schema |
| 机制层 | 模型如何发起调用、结果如何回填 | Tool Calling 机制 |
| 选择层 | 工具过多时如何选对 | 选择与路由 |
| 执行层 | 代码/浏览器/计算机如何安全执行 | 沙箱与执行类工具 |
| 集成层 | 外部 API/数据库如何封装 | 集成类工具 |
| 协议层 | 如何跨进程、跨团队、跨组织接入 | MCP 与 A2A |

### 1.1.1 为什么说工具是"唯一通道"

模型与外界之间没有别的通路：上下文是输入，token 是输出。工具调用把"输出 token"变成"结构化动作意图"，再由运行时执行。因此工具的边界就是 Agent 的能力边界。

### 1.1.2 本模块与其他模块的分工

# 2. 学习目标

学完本模块，应同时具备"知识"与"动手"两个层面的能力。

## 2.1 知识目标

- 掌握工具/函数的 Schema 设计与调用机制。
- 理解工具选择、路由与错误处理。
- 掌握 MCP 协议并会用 Java 开发 MCP Server / Client。
- 理解 A2A 协议及与 MCP 的分工。
- 掌握工具权限与隔离（尤其 MCP Tool 权限隔离）。

## 2.2 能力目标

- 能为一个业务场景设计出"模型一次就能选对"的工具集。
- 能用 Java（JDK 17/21）实现一个可用的 MCP Server 与 Client。
- 能把工具调用失败转化为模型可自我纠错的结构化错误。
- 能判断一个协作场景该用 MCP、A2A 还是框架编排。

## 2.3 前置知识

| 前置 | 说明 |
|------|------|
| JSON / JSON Schema | 工具参数描述的基础 |
| HTTP / SSE | MCP、A2A 的传输底座 |
| Java 17+ | 记录类型、密封类、虚拟线程 |
| 并发与异步 | 长任务、流式、回调 |

## 2.4 学习方法建议

- 先动手写一个最简单的 `@Tool`，建立"调用-回填"的直觉。
- 再逐层加复杂度：校验 → 错误处理 → 沙箱 → 协议。
- 协议部分优先理解"为什么需要"，再看"怎么实现"。

# 5. 关键知识点速览

如果时间有限，先记住下面几条，再回头补细节。

## 5.1 工具设计要点

- 工具描述质量直接影响模型调用准确率。
- 工具返回值必须结构化、可被模型理解，错误也要结构化。
- 单一职责：一个工具只做一件事，参数越少越准。

### 5.1.1 一条好工具的判据

| 判据 | 说明 |
|------|------|
| 名字自解释 | 看到名字就知道用途 |
| 参数最小 | 无冗余、无歧义 |
| 描述含边界 | 何时用、何时不用 |
| 返回结构化 | 便于模型解析与纠错 |

### 5.1.2 常见反例

- 一个工具同时做"查+改"，模型不敢用。
- 参数用自然语言长文本，校验困难。
- 返回一大段 HTML，模型抓不住重点。

## 5.2 协议选型要点

- MCP 统一了"模型如何接入外部能力"，是 Agent 生态的事实标准。
- A2A 解决 Agent 之间协作，MCP 解决 Agent 与工具之间连接。
- 协议为"跨边界"服务：跨进程、跨团队、跨组织时才需要。

## 5.3 生产落地要点

- MCP 必须做权限隔离：不同 Agent/用户可访问的 Tool 不同。
- 所有外部调用都要有鉴权、限流与审计。
- 长任务用异步 + 推送，避免同步阻塞与超时。

## 5.4 自检清单

| 检查项 | 通过标准 |
|--------|----------|
| 工具描述是否清晰 | 模型一次能选对 |
| 错误是否结构化 | 模型能据此纠错 |
| 权限是否隔离 | 最小权限可访问 |
| 是否只在跨边界用协议 | 是 |
| 工具是否可被审计 | 是 |

> 本模块的最终目标：让 Agent 既"够得着"外部能力，又"管得住"外部风险。
