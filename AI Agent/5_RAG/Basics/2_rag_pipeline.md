# 1. 两阶段全景

## 1.1 总体架构

**结论先行**：RAG 流水线（Pipeline）由**离线索引**与**在线查询**两个阶段组成。离线阶段把原始数据变成可检索的索引，在线阶段把用户问题变成带来源的答案。

```
┌─────────────────── 离线索引阶段 ───────────────────┐
│                                                    │
│  数据源        解析          切分         向量化     │
│  ┌────┐     ┌──────┐     ┌──────┐     ┌───────┐   │
│  │文件│────▶│Parser│────▶│Split │────▶│Embed  │   │
│  │DB  │     └──────┘     └──────┘     └───┬───┘   │
│  │Web │                                    │       │
│  └────┘                                    ▼       │
│                                      ┌──────────┐  │
│                                      │VectorStore│ │
│                                      └──────────┘  │
└────────────────────────────────────────────────────┘

┌─────────────────── 在线查询阶段 ───────────────────┐
│                                                    │
│  问题 ──▶ 查询改写 ──▶ 向量化 ──▶ 检索 ──▶ 重排     │
│                                     │              │
│                                     ▼              │
│                              上下文拼装 ──▶ 生成    │
└────────────────────────────────────────────────────┘
```

## 1.2 两阶段的职责划分

### 1.2.1 离线阶段职责

- 采集与解析：把异构数据源转成纯文本。
- 清洗与切分：去噪、分块，形成检索单元。
- 向量化与入库：生成向量并建立索引与元数据。

### 1.2.2 在线阶段职责

- 查询理解：改写、扩展、消歧。
- 召回与重排：先粗后精地筛选片段。
- 拼装与生成：组织上下文并约束模型输出。

## 1.3 两阶段的解耦价值

| 维度 | 离线阶段 | 在线阶段 |
|------|----------|----------|
| 触发方式 | 定时/事件批处理 | 用户请求实时触发 |
| 延迟容忍 | 高（分钟/小时） | 低（毫秒/秒） |
| 主要风险 | 丢信息 | 答错/幻觉 |
| 优化目标 | 召回上限 | 精度与体验 |

> 解耦后可以独立重跑索引、独立扩容查询，互不影响。

## 1.4 数据流与状态

**结论先行**：理解两阶段之间的数据契约，是排查问题的前提。离线阶段产出"文档 + 向量 + 元数据"，在线阶段消费它们并产出答案。

### 1.4.1 离线产出物

| 产出 | 说明 |
|------|------|
| 文本片段 | 检索命中的原文 |
| 向量 | 用于相似度计算 |
| 元数据 | 过滤与引用所需 |
| 索引 | 加速向量检索 |

### 1.4.2 在线消费物

在线阶段按"过滤条件 + 查询向量"取片段，再拼装生成。任何元数据缺失都会在这一步暴露。

## 1.5 一次请求的生命周期

```
请求 → 鉴权 → 缓存查询 → 查询改写 → 检索 → 重排
     → 拼装 → 生成 → 后处理 → 响应
```

每一步都可埋点，用于定位延迟与错误。

# 2. 离线阶段的六个环节

## 2.1 环节总览

| 环节 | 任务 | 关键点 |
|------|------|--------|
| 1. 采集 | 收集数据源 | 覆盖度、更新频率 |
| 2. 解析 | 提取纯文本 | 格式兼容、表格处理 |
| 3. 清洗 | 去噪、去重 | 页眉页脚、乱码 |
| 4. 切分 | 分块 | 块大小、重叠、语义完整 |
| 5. 向量化 | 转向量 | 模型选择、批量、缓存 |
| 6. 入库 | 存储 + 元数据 | 元数据设计、索引 |

## 2.2 采集与解析

### 2.2.1 数据采集

- 来源：文件系统、对象存储、数据库、Web、API。
- 要点：增量识别（用更新时间/哈希）、权限继承、失败重试。

### 2.2.2 文档解析

把 PDF、Word、HTML、Markdown 等转为纯文本。表格建议转 Markdown 或结构化字段，避免直接丢成乱序文本。

```java
DocumentReader reader = new TikaDocumentReader(resource);
List<Document> docs = reader.get();
```

## 2.3 清洗与切分

### 2.3.1 数据清洗

去除页眉页脚、重复段落、控制字符与乱码；对同一文档做哈希去重，避免重复入库稀释检索。

### 2.3.2 文本切分

切分（Chunking）是离线阶段最关键的一步。块太小丢语义，块太大引入噪声。常用递归字符切分，保留段落边界。

```java
List<Document> chunks = new TokenTextSplitter(800, 350, 5, 10000, true).apply(docs);
```

## 2.4 向量化与入库

### 2.4.1 向量化

用嵌入模型（Embedding Model）把文本转为向量。注意：查询与文档必须用**同一个**模型，否则向量空间不一致。

### 2.4.2 入库

写入向量库时同时保存文本、向量与元数据（来源、部门、版本、时间）。

```java
// Spring AI 的 ETL
DocumentReader reader = new TikaDocumentReader(resource);
List<Document> docs = reader.get();
List<Document> chunks = new TokenTextSplitter(800, 350, 5, 10000, true).apply(docs);
vectorStore.add(chunks);
```

```java
// LangChain4j 的 ETL
EmbeddingStoreIngestor.builder()
        .documentSplitter(DocumentSplitters.recursive(800, 100))
        .embeddingModel(embeddingModel)
        .embeddingStore(store)
        .build()
        .ingest(document);
```

> 不确定 API 时按伪代码理解：`read -> clean -> split -> embed(batch) -> upsert`。

## 2.5 ETL 工程化

**结论先行**：离线 ETL 要像数据管道一样建设——可重跑、可增量、可观测。

### 2.5.1 幂等与增量

用文档 ID 作为主键做 upsert，重复执行不产生重复数据；只处理内容哈希变化的文档。

### 2.5.2 批处理与限流

嵌入接口通常有速率限制，需分批并退避重试；大文档先切分再并发嵌入。

```java
// 伪代码：增量索引
for (Document d : changedDocuments) {
    List<Document> chunks = splitter.apply(List.of(d));
    List<float[]> vectors = embeddingModel.embedAll(chunks).content();
    store.upsert(chunks, vectors);   // 幂等写入
}
```

# 3. 在线阶段的五个环节

## 3.1 环节总览

| 环节 | 任务 | 关键点 |
|------|------|--------|
| 1. 查询理解 | 改写/扩展查询 | 口语化 → 检索友好 |
| 2. 检索 | 召回候选 | 召回要多 |
| 3. 重排 | 精排 | 精度要高 |
| 4. 拼装 | 组装上下文 | 顺序、去重、Token 预算 |
| 5. 生成 | 模型回答 | 引用来源、拒答兜底 |

## 3.2 查询理解与检索

### 3.2.1 查询改写

把口语化问题改写成检索友好的表达，或做多查询扩展（Multi-Query）、假设文档嵌入（HyDE）。

### 3.2.2 向量检索

在向量库中按相似度取 topK。召回阶段"宁多勿漏"，给重排留空间。

## 3.3 重排与拼装

### 3.3.1 重排

用交叉编码器（Cross-Encoder）对候选精排，取前 N 条。精度高于纯向量相似度。

### 3.3.2 上下文拼装

去重、按相关性排序、控制 Token 预算；常见做法是把最相关片段放**首尾**，规避"中间遗忘"。

## 3.4 生成与代码示例

```java
// 检索 → 重排 → 拼装 → 生成
List<Document> candidates = vectorStore.similaritySearch(
        SearchRequest.builder().query(q).topK(20).build());
List<Document> reranked = reranker.rerank(q, candidates).stream().limit(5).toList();

String context = reranked.stream()
        .map(Document::getText)
        .collect(Collectors.joining("\n---\n"));

String answer = chatClient.prompt()
        .user("""
                只依据以下资料回答，资料不足时说明：
                %s
                问题：%s
                """.formatted(context, q))
        .call().content();
```

## 3.5 重排的实现方式

**结论先行**：重排把"相关性排序"从近似相似度提升为精确打分，是提升精度的关键一步。

### 3.5.1 交叉编码器

交叉编码器（Cross-Encoder）把"问题 + 片段"一起输入模型打分，精度高但慢，故只用于小候选集。

### 3.5.2 融合排序

对多路召回结果做倒数排名融合（Reciprocal Rank Fusion，RRF），再交给重排模型。

```java
// 伪代码：RRF 融合
Map<String, Double> scores = new HashMap<>();
for (List<Document> list : lists) {
    for (int i = 0; i < list.size(); i++) {
        scores.merge(list.get(i).getId(), 1.0 / (60 + i + 1), Double::sum);
    }
}
```

# 4. 关键参数与默认值

## 4.1 参数一览

| 参数 | 默认 | 说明 |
|------|------|------|
| 块大小 | 500~1000 字符 | 太小丢语义，太大引入噪声 |
| 重叠 | 10%~20% | 防止边界切断语义 |
| 召回数 topK | 10~20 | 召回要多，给重排留空间 |
| 精排后 topN | 3~5 | 喂给模型的片段数 |
| 相似度阈值 | 0.6~0.7 | 过滤无关内容 |

## 4.2 参数影响

### 4.2.1 块大小与重叠

块过小：单块信息不完整，答案被拆散。块过大：一块混入多个主题，检索命中后噪声多。重叠用于缓解边界切断。

### 4.2.2 topK 与 topN

topK 管召回，topN 管喂给模型的数量。topN 过大会挤占上下文并引入噪声，过小可能漏掉关键信息。

### 4.2.3 相似度阈值

阈值过高会漏召回，过低会引入无关内容。建议结合评测集在 0.5~0.75 区间扫描。

> 这些参数**没有万能值**，必须用评测集调优。

## 4.3 调参方法

- 固定其他参数，一次只调一个，观察指标变化。
- 用召回率与精确率同时评估，避免顾此失彼。
- 记录每次实验配置，形成参数台账。

## 4.4 参数组合示例

| 场景 | 块大小 | 重叠 | topK | topN | 阈值 |
|------|--------|------|------|------|------|
| 制度问答 | 800 | 120 | 20 | 5 | 0.65 |
| 客服 | 400 | 60 | 10 | 3 | 0.60 |
| 代码检索 | 600 | 80 | 30 | 6 | 0.55 |

> 上表仅为起点，务必用评测集校准。

# 5. 一次完整查询的时序

## 5.1 时序图

```
t0  用户提问
t1  查询改写（可选，LLM 调用 ~200ms）
t2  查询向量化（~50ms）
t3  向量检索（~50ms）
t4  重排（~100ms）
t5  拼装上下文（~5ms）
t6  模型生成（~1~5s，主要耗时）
t7  返回 + 附来源
```

## 5.2 延迟构成分析

### 5.2.1 检索链路

改写 + 向量化 + 检索 + 重排 + 拼装，合计通常 200~400ms，占总延迟 10%~20%。

### 5.2.2 生成链路

生成是延迟大头，取决于输出 Token 数与模型吞吐。

> 延迟大头在**生成**；检索链路通常只占 10%~20%。优化时先看生成。

## 5.3 优化方向

| 目标 | 手段 |
|------|------|
| 降生成延迟 | 流式输出、小模型、限制输出长度 |
| 降检索延迟 | 缓存热点、向量库索引调优、减少重排候选 |
| 提体感 | 先回"正在检索"状态，再流式吐字 |

## 5.4 并发与吞吐

- 检索链路无状态，可水平扩容。
- 生成受模型吞吐限制，需做排队与限流。
- 向量库是常见瓶颈，注意连接池与索引参数。

# 6. 流水线的常见故障点

## 6.1 故障对照表

| 环节 | 故障 | 表现 |
|------|------|------|
| 解析 | 格式错乱 | 内容缺失、乱码 |
| 切分 | 语义切断 | 答案被拆散 |
| 向量化 | 模型不匹配 | 检索不准 |
| 入库 | 元数据缺失 | 无法过滤/引用 |
| 检索 | 召回不足 | 答不出 |
| 重排 | 阈值不当 | 噪声多或漏召回 |
| 拼装 | 超 Token | 被截断 |
| 生成 | 幻觉 | 编造答案 |

## 6.2 典型故障剖析

### 6.2.1 切分切断语义

答案横跨两块，检索只命中一块，模型看到半截内容而答错。缓解：加大重叠、按标题/段落切分。

### 6.2.2 向量模型不匹配

索引与查询用了不同嵌入模型，向量空间错位，召回质量骤降。缓解：固定模型版本并写入索引元数据。

### 6.2.3 元数据缺失

无法按部门/租户过滤，导致越权或引用不到来源。缓解：入库强制校验元数据 schema。

## 6.3 排查顺序

1. 检查原始文档是否正确解析。
2. 检查目标知识是否被正确切分并入库。
3. 检查检索是否命中该片段（打印召回结果）。
4. 检查重排后是否仍在 topN。
5. 最后才检查提示与生成。

## 6.4 监控指标

| 指标 | 含义 | 告警线 |
|------|------|--------|
| 召回命中率 | 有结果的查询占比 | 低于基线告警 |
| 平均延迟 | 端到端耗时 | P95 超阈值 |
| 拒答率 | 拒绝回答占比 | 异常升高 |
| Token 消耗 | 成本指标 | 超预算 |

# 7. 流式 RAG

## 7.1 基本思路

**结论先行**：检索必须同步完成，生成可以流式返回。用户先看到答案逐步出现，体感延迟大幅降低。

```
检索（同步）→ 生成（流式）
```

## 7.2 代码示例

```java
@GetMapping(value = "/rag/stream", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
public Flux<String> stream(@RequestParam String q) {
    List<Document> docs = retriever.retrieve(q);       // 先检索
    String context = buildContext(docs);

    return chatClient.prompt()
            .user(buildPrompt(context, q))
            .stream()
            .content();                                 // 再流式生成
}
```

## 7.3 边界与坑

- 流式过程中无法再修改检索结果，检索必须前置完成。
- 引用来源需在流开始前确定，可在首帧下发元数据。
- 客户端断连要取消上游生成，避免浪费 Token。

> 可先返回"正在检索…"的状态，提升体感。

## 7.4 SSE 与前端协作

- 用 Server-Sent Events（SSE）承载流式输出。
- 首帧可先发检索到的来源列表，再流式发正文。
- 前端需处理断流与重连。

# 8. 生产注意事项

## 8.1 风险与建议

| 风险 | 建议 |
|------|------|
| 检索延迟高 | 缓存热点查询、向量库调优 |
| 上下文超限 | Token 预算 + 截断策略 |
| 知识过期 | 增量更新 + 版本管理 |
| 租户越权 | 元数据强制过滤 |
| 无评测 | 建黄金集 |
| 全量重建抖动 | 别名切换 |

## 8.2 增量更新

### 8.2.1 变更识别

以文档 ID + 内容哈希判断是否变更，只重嵌入变化部分，降低成本。

### 8.2.2 删除同步

源文档删除时必须同步删除向量库条目，否则会检索到"幽灵知识"。

## 8.3 可观测性

- 记录每次查询的召回片段、分数与最终答案，便于回溯。
- 监控检索命中率、平均延迟、Token 消耗与拒答率。
- 对低分查询告警，发现知识盲区。

## 8.4 成本控制

| 手段 | 效果 |
|------|------|
| 缓存热点问答 | 减少生成调用 |
| 小模型兜底 | 降低单价 |
| 限制输出长度 | 降低 Token |
| 减少重排候选 | 降低重排成本 |

# 9. 小结

## 9.1 核心要点

- RAG 分离线索引与在线查询两阶段。
- 离线决定召回上限，在线决定精度。
- 在线标准链路：查询改写 → 召回 → 重排 → 拼装 → 生成。
- 参数无万能值，必须评测驱动。
- 延迟大头在生成，检索链路优化空间有限。
