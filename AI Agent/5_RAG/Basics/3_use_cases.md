# 1. 场景全景

## 1.1 常见场景一览

**结论先行**：RAG 的落地场景虽多，但核心诉求高度一致——"基于私有知识准确回答"。差异主要在数据形态、实时性要求与错误代价。

| 场景 | 核心诉求 | 关键能力 |
|------|----------|----------|
| 企业知识库问答 | 内部文档可问答 | 文档解析 + 权限过滤 |
| 智能客服 | 基于产品/政策回答 | 多轮 + 转人工 |
| 文档助手 | 长文档理解与摘要 | 父子分块 + 引用 |
| 法律/医疗辅助 | 依据条文/指南回答 | 高忠实度 + 拒答 |
| 研发助手 | 代码/文档检索 | 混合检索 + 代码解析 |
| 电商导购 | 商品知识问答 | 结构化 + 实时数据 |

## 1.2 场景维度划分

### 1.2.1 按数据形态划分

- 非结构化：PDF、Word、Wiki、聊天记录。
- 半结构化：HTML、Markdown、表格。
- 结构化：数据库、商品参数、工单系统。

### 1.2.2 按错误代价划分

| 代价 | 场景 | 策略 |
|------|------|------|
| 低 | 内部问答、导购 | 允许一定容错 |
| 中 | 客服 | 置信度低转人工 |
| 高 | 法律、医疗 | 宁可拒答，必须引用 |

## 1.3 场景选型思路

先问三个问题：数据在哪、实时性多高、错了会怎样。答案决定用纯 RAG、RAG + 工具，还是 RAG + Agent。

## 1.4 常见失败模式

**结论先行**：多数 RAG 项目失败，不是因为模型不好，而是因为检索质量与工程细节没做好。

### 1.4.1 检索侧失败

- 知识未入库：源数据没被采集，问题永远答不出。
- 切分不当：答案被拆散，召回片段不完整。
- 语义鸿沟：用户口语与文档术语不一致。

### 1.4.2 生成侧失败

- 上下文噪声：无关片段干扰，模型答偏。
- 过度推断：资料不足仍强行作答。
- 引用缺失：无法核对，可信度低。

# 2. 企业知识库问答

## 2.1 需求与目标

**需求**：员工用自然语言查询内部制度、流程、手册，答案要准确、可追溯、且不能越权。

```
数据源：Confluence / 飞书 / PDF 手册 / Wiki / 数据库
       │
       ▼
   解析 → 切分 → 向量化 → 入库（带部门/权限元数据）
       │
       ▼
   员工提问 → 按权限过滤检索 → 生成带引用的回答
```

## 2.2 关键设计

- 元数据必须含 `department` / `acl` / `tenantId`；
- 回答必须附来源链接；
- 无资料时明确拒答，不编造。

### 2.2.1 权限过滤

在检索时**强制**拼接过滤条件，而不是检索后再过滤，避免越权内容进入上下文。

### 2.2.2 来源引用

每个片段携带原始 URL 与标题，生成时要求模型在句末标注来源编号。

## 2.3 代码示例

```java
SearchRequest.builder()
        .query(question)
        .filterExpression("department == '" + userDept + "'")
        .topK(5)
        .build();
```

> 生产环境应使用参数化的过滤表达式，避免拼接注入；同时过滤 `tenantId` 与 `acl`。

## 2.4 边界与生产建议

| 风险 | 建议 |
|------|------|
| 权限继承缺失 | 入库时继承源系统 ACL |
| 文档过期 | 保留更新时间，检索可加权 |
| 引用失效 | 定期校验来源链接 |

- 对敏感文档做脱敏后再入库。
- 记录检索日志，支持审计。

## 2.5 多租户设计

**结论先行**：企业知识库往往服务多个部门甚至多个客户，租户隔离必须在检索层强制实施。

### 2.5.1 逻辑隔离

所有片段携带 `tenantId`，检索时强制过滤，做到"同一索引、逻辑隔离"。

### 2.5.2 物理隔离

对合规要求高的租户，使用独立集合（Collection）或独立实例，避免任何串数据风险。

```java
// 强制注入租户过滤
SearchRequest.builder()
        .query(question)
        .filterExpression("tenantId == '" + tenantId + "'")
        .topK(5)
        .build();
```

# 3. 智能客服

## 3.1 需求与目标

**需求**：基于产品手册与政策回答，处理不了时顺畅转人工，且话术符合品牌调性。

```
用户问题
   │
   ▼
意图识别 ──▶ 简单问题 → RAG 回答
   │
   ├──▶ 复杂问题 → 转人工
   └──▶ 投诉类   → 直接转人工
```

## 3.2 关键设计

- 结合对话记忆（多轮上下文）；
- 置信度低时主动转人工；
- 回答要符合品牌话术。

### 3.2.1 多轮与指代消解

客服对话常有指代（"它"、"这个"）。需把历史对话改写成独立问题再检索，否则召回质量差。

### 3.2.2 转人工策略

当检索最高分低于阈值、或意图为投诉/退款时，直接转人工，避免编造。

## 3.3 代码示例

```java
// 多轮改写 + 检索 + 低置信度转人工（伪代码示意）
String standalone = queryRewriter.rewrite(history, currentQuestion);
List<Document> docs = retriever.retrieve(standalone);

if (docs.isEmpty() || topScore(docs) < 0.55) {
    return handoffToHuman(conversationId);
}
return chatClient.prompt().user(buildPrompt(docs, standalone)).call().content();
```

## 3.4 边界与生产建议

- 对话记忆要有长度上限，避免上下文爆炸。
- 转人工要有明确触发条件与话术，别让用户干等。
- 对高频问题做缓存，降低延迟与成本。

## 3.5 评测与迭代

**结论先行**：客服场景要持续评测，否则话术与知识会随业务变化而失真。

### 3.5.1 黄金集构建

从历史工单中抽取高频问题与标准答案，形成评测集，定期回放。

### 3.5.2 指标跟踪

跟踪转人工率、首次解决率与用户满意度，作为 RAG 效果的间接指标。

# 4. 文档助手（长文档）

## 4.1 需求与目标

**需求**：对一份长报告/合同提问，需要定位到具体章节，并给出准确引用。

## 4.2 关键设计

- 用**父子分块**：小块检索、大块喂给模型；
- 保留章节层级元数据，便于引用定位；
- 表格单独处理（转 Markdown 或结构化）。

### 4.2.1 父子分块

小块（子块）用于精确检索，命中后返回其所属大块（父块）给模型，兼顾精度与上下文完整。

### 4.2.2 章节层级

入库时记录 `chapter` / `section` / `page` 元数据，引用时可精确到章节甚至页码。

## 4.3 代码示例

```java
// LangChain4j 父子文档检索器（示意）
ContentRetriever retriever = ParentDocumentContentRetriever.builder()
        .documentRetriever(EmbeddingStoreContentRetriever.builder()
                .embeddingStore(childStore)
                .embeddingModel(embeddingModel)
                .build())
        .documentStore(parentStore)
        .build();
```

## 4.4 边界与生产建议

- 长文档切分要尊重标题层级，避免跨章节合并。
- 表格转文本后需保留行列语义，否则模型读不懂。
- 页码/锚点要能回跳原文。

> 详见 `Advanced/1_parent_document_retriever.md`。

## 4.5 摘要与问答结合

**结论先行**：长文档场景常需"先摘要、再追问"，摘要可作为导航，问答用于定位细节。

### 4.5.1 分层摘要

先生成章节摘要，再在摘要上建立索引，用户可先看摘要再深入。

### 4.5.2 引用回跳

无论摘要还是问答，都必须能回跳原文位置，保证可核对。

# 5. 法律 / 医疗辅助（高忠实度）

## 5.1 需求与目标

**需求**：依据条文/指南回答，错误代价极高，必须可追溯、可复核。

## 5.2 关键设计

| 要求 | 做法 |
|------|------|
| 高忠实度 | 严格"只依据资料"，禁止推断 |
| 必须引用 | 每条结论附条文编号 |
| 拒答机制 | 资料不足明确说"无法确定" |
| 人工复核 | 关键结论转专业人员 |
| 可追溯 | 保留检索与生成全过程 |

### 5.2.1 忠实度约束

提示词中明确禁止"根据常识补充"，要求逐句对应资料，否则拒答。

### 5.2.2 引用与复核

输出必须附条文编号，且关键结论走人工复核流程，系统只做辅助。

## 5.3 代码示例

```java
String prompt = """
        你是法律检索助手。严格依据下列条文回答：
        1) 只能引用给定条文，不得推测；
        2) 每条结论后标注【条文编号】；
        3) 若条文不足以回答，回复"资料不足，无法确定"。
        条文：
        %s
        问题：%s
        """.formatted(context, question);
```

## 5.4 边界与生产建议

> 这类场景**宁可拒答，不可编造**。

- 建立"高风险问题"清单，命中即转人工。
- 版本化条文，确保引用的是现行有效版本。
- 全链路留痕，满足合规审计。

## 5.5 合规与留痕

**结论先行**：高代价场景的合规要求，往往比模型效果更严格，必须优先设计。

### 5.5.1 审计日志

记录检索片段、提示、模型输出与引用编号，支持事后复核。

### 5.5.2 数据合规

遵守数据分级与最小必要原则，敏感信息脱敏后再入库。

# 6. 研发助手

## 6.1 需求与目标

**需求**：检索代码、文档、Issue、API 说明，帮助开发者快速定位答案。

## 6.2 关键设计

- **混合检索**：向量 + 关键词（代码标识符适合关键词）；
- 代码按函数/类切分，保留文件路径元数据；
- 结合 Git 历史做时效过滤。

### 6.2.1 混合检索

代码中的类名、方法名是精确符号，关键词检索（BM25）比纯向量更有效；二者融合能显著提升召回。

### 6.2.2 代码切分

按函数、类、方法切分，保留 `repo` / `path` / `language` 元数据，便于过滤与引用。

## 6.3 代码示例

```java
SearchRequest.builder()
        .query("如何处理认证失败")
        .filterExpression("repo == 'backend' && language == 'java'")
        .build();
```

## 6.4 边界与生产建议

- 代码更新频繁，需增量索引并支持按分支过滤。
- 忽略构建产物与依赖目录，减少噪声。
- 对大文件按函数切分，避免单块过大。

## 6.5 IDE 与工作流集成

**结论先行**：研发助手要嵌入开发者的日常工具，才有使用率。

### 6.5.1 编辑器插件

以插件形式提供问答与代码检索，减少上下文切换。

### 6.5.2 流水线集成

接入 CI/PR 流程，自动检索相关文档与历史 Issue。

# 7. 电商导购

## 7.1 需求与目标

**需求**：基于商品知识回答，并结合实时库存/价格，给出可购买的建议。

## 7.2 关键设计

- **RAG + 工具**：静态知识用 RAG，实时数据用工具调用；
- 商品参数结构化存储，支持精确过滤；
- 价格/库存实时查询，不放进向量库。

### 7.2.1 静态与实时分离

商品描述、卖点等变化慢，进向量库；价格、库存变化快，走工具实时查，避免脏数据。

### 7.2.2 结构化过滤

品类、品牌、价格区间等用元数据过滤，先缩小候选再做语义匹配。

## 7.3 代码示例

```java
Assistant assistant = AiServices.builder(Assistant.class)
        .chatModel(model)
        .contentRetriever(productKnowledgeRetriever)   // 商品知识
        .tools(new InventoryTools(), new PriceTools()) // 实时数据
        .build();
```

## 7.4 边界与生产建议

- 工具调用要有超时与降级，避免拖垮响应。
- 价格展示需明确时效，防止纠纷。
- 敏感类目做合规过滤。

## 7.5 多模态商品

**结论先行**：商品常以图片呈现，多模态 RAG 可支持"以图搜商品"与图文混排。

### 7.5.1 图文联合索引

对商品图与描述文本统一嵌入，支持文本与图片两种查询。

### 7.5.2 以图搜货

用户上传图片，检索相似商品，再结合结构化参数过滤。

# 8. 场景选型对照

## 8.1 选型表

| 诉求 | 方案 |
|------|------|
| 静态知识问答 | 纯 RAG |
| 知识 + 实时数据 | RAG + 工具 |
| 知识 + 多步操作 | RAG + Agent |
| 跨文档多跳推理 | GraphRAG |
| 结构化统计 | Text2SQL（非 RAG） |
| 图片/扫描件 | 多模态 RAG |

## 8.2 选型决策

### 8.2.1 何时加工具

需要实时或精确计算的数据（价格、库存、天气、汇率）应走工具，而非向量库。

### 8.2.2 何时加 Agent

任务需要多步规划（先查 A 再查 B 再对比）时，用 Agent 编排多次检索与工具调用。

### 8.2.3 何时换方案

纯统计/聚合诉求应直接 Text2SQL；跨文档关系推理考虑 GraphRAG。

## 8.3 边界提醒

不要为了"技术先进"而叠加 Agent 或 GraphRAG，复杂度和延迟都会上升；先用最简方案验证需求。

## 8.4 成本与复杂度权衡

| 方案 | 复杂度 | 延迟 | 适用 |
|------|--------|------|------|
| 纯 RAG | 低 | 低 | 静态知识 |
| RAG + 工具 | 中 | 中 | 实时数据 |
| RAG + Agent | 高 | 高 | 多步任务 |
| GraphRAG | 高 | 高 | 多跳推理 |

> 复杂度越高，运维与调试成本越高，收益需与成本匹配。

# 9. 通用落地清单

## 9.1 建设清单

- [ ] 明确知识边界（哪些数据、谁有权访问）
- [ ] 设计元数据（租户、权限、来源、时效）
- [ ] 选择分块策略并评测
- [ ] 选择 Embedding 模型
- [ ] 选择向量库
- [ ] 配置召回 + 重排
- [ ] 提示要求"依据资料 + 引用 + 拒答"
- [ ] 建立评测集与指标
- [ ] 权限过滤与越权测试
- [ ] 监控延迟、命中率、成本

## 9.2 上线前检查

### 9.2.1 功能检查

召回命中率、引用正确性、拒答行为是否符合预期。

### 9.2.2 安全检查

越权测试、提示注入防护、敏感信息脱敏。

## 9.3 上线后运维

- 定期回放黄金集，监控指标漂移。
- 收集用户反馈，补充知识盲区。
- 版本化索引，支持灰度与回滚。

## 9.4 常见误区

- 只调模型不调检索：检索才是瓶颈。
- 忽略元数据：导致无法过滤与引用。
- 追求大而全：知识越杂，噪声越多。
- 没有评测：上线后无法判断好坏。

# 10. 小结

## 10.1 核心要点

- RAG 场景广泛，但核心诉求都是"基于私有知识准确回答"。
- 知识库问答与客服是最高频场景。
- 高忠实度场景必须"宁可拒答，不可编造"。
- 实时数据用工具，静态知识用 RAG，复杂任务叠加 Agent。
- 无论哪个场景，元数据与权限设计都是前提。
