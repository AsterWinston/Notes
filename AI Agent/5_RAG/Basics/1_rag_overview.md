# 1. RAG 是什么

## 1.1 一句话定义

**结论先行**：检索增强生成（Retrieval-Augmented Generation，RAG）是一种"先查资料、再作答"的大模型应用范式。模型不再单凭参数记忆回答，而是先从外部知识库检索相关内容，再把这些内容作为提示（Prompt）的一部分交给模型生成答案。

**机制拆解**：

- 检索（Retrieval）：用用户问题从知识库中找出最相关的若干片段。
- 增强（Augmentation）：把片段拼装进提示词，作为"参考材料"。
- 生成（Generation）：模型只依据参考材料组织答案，并可标注来源。

### 1.1.1 定义拆解

| 关键词 | 含义 | 对应技术 |
|--------|------|----------|
| 检索 | 从海量片段中定位相关信息 | 向量检索、关键词检索、混合检索 |
| 增强 | 把检索结果注入提示 | 上下文拼装、提示模板、Token 预算 |
| 生成 | 模型基于资料输出答案 | 大语言模型（LLM）、流式输出 |

三者缺一不可：只检索不增强，信息进不了模型；只增强不生成，等于人肉读文档；只生成不检索，就是普通问答。

### 1.1.2 与"闭卷考试"的类比

普通大模型像**闭卷考试**：只能凭记忆作答，记错或记不住就编。

RAG 像**开卷考试**：允许翻资料，答案来自你提供的教材，而不是模型的记忆。

> **一句话记忆：RAG 让大模型"开卷考试"——答案来自你的私有知识，而不是模型的记忆。**

## 1.2 三段式流程

```
用户提问
   │
   ▼
① 检索：从知识库找出相关片段
   │
   ▼
② 增强：把片段拼进提示
   │
   ▼
③ 生成：模型基于资料回答
```

### 1.2.1 检索阶段

把用户问题向量化，在向量库中做相似度搜索，返回 topK 个候选片段。这一阶段决定"能不能找到"。

### 1.2.2 增强阶段

对候选片段重排、去重、裁剪，再按固定模板拼进提示词。这一阶段决定"喂给模型什么"。

### 1.2.3 生成阶段

模型读取上下文，按"只依据资料"的约束作答，并输出引用。这一阶段决定"答得对不对"。

## 1.3 最小 Java 示例

下面给出两种主流框架的最小可运行骨架，用于建立直观认识。

### 1.3.1 Spring AI 版本

```java
@Service
public class RagService {

    private final VectorStore vectorStore;
    private final ChatClient chatClient;

    public RagService(VectorStore vectorStore, ChatClient.Builder builder) {
        this.vectorStore = vectorStore;
        this.chatClient = builder.build();
    }

    public String ask(String question) {
        List<Document> docs = vectorStore.similaritySearch(
                SearchRequest.builder().query(question).topK(5).build());
        String context = docs.stream()
                .map(Document::getText)
                .collect(Collectors.joining("\n---\n"));

        return chatClient.prompt()
                .user("""
                        只依据以下资料回答，资料不足时说明：
                        %s
                        问题：%s
                        """.formatted(context, question))
                .call()
                .content();
    }
}
```

### 1.3.2 LangChain4j 版本

```java
interface Assistant {
    String chat(String question);
}

Assistant assistant = AiServices.builder(Assistant.class)
        .chatModel(chatModel)
        .contentRetriever(EmbeddingStoreContentRetriever.builder()
                .embeddingStore(embeddingStore)
                .embeddingModel(embeddingModel)
                .maxResults(5)
                .minScore(0.6)
                .build())
        .build();

String answer = assistant.chat("公司的报销流程是什么？");
```

## 1.4 边界与常见误解

| 误解 | 事实 |
|------|------|
| RAG 能提升模型智力 | 不能，它只补知识，不改能力 |
| 有了 RAG 就没有幻觉 | 仍有，模型可能误读或过度推断 |
| 向量库越大越好 | 越大噪声越多，召回精度可能下降 |
| 接入 RAG 一次到位 | 需要持续评测与调参 |

**生产建议**：把 RAG 当作"检索系统 + 生成系统"的组合来建设，检索质量单独度量，不要只盯最终答案。

# 2. 为什么需要 RAG

## 2.1 大模型的三大固有局限

**结论先行**：大模型虽然强大，但存在知识截止、不懂私有知识、幻觉三大局限，RAG 正是针对这三点的工程解法。

### 2.1.1 知识截止

模型的训练数据有时间边界（Knowledge Cutoff）。训练完成之后发生的事，模型一概不知。例如问"昨天的汇率"，模型只能给出训练期内的旧值。

### 2.1.2 不懂私有知识

企业内部的制度、合同、代码、客服话术从未进入公开训练集，模型天然不知道。即使知道，也无法保证与你当前版本一致。

### 2.1.3 幻觉

当模型缺乏知识时，它倾向于"编造一个看起来合理的答案"，而且语气笃定。这在法律、医疗等高代价场景尤其危险。

## 2.2 RAG 如何对症下药

| 局限 | 说明 | RAG 如何解决 |
|------|------|--------------|
| 知识截止 | 训练数据有时间边界 | 提供最新资料 |
| 不懂私有知识 | 不知道你的内部文档 | 提供企业知识 |
| 幻觉 | 会编造看似合理的内容 | 有据可依，可要求引用 |

**机制拆解**：RAG 把"知识"从模型参数中剥离出来，放进可随时更新的外部库。模型只负责"阅读理解 + 组织语言"，知识由检索负责供给。

## 2.3 反例：RAG 也解决不了的问题

- 需要改变模型**输出风格**：RAG 无效，应微调或用提示约束。
- 需要**多步推理**：如"比较三份合同的违约条款"，单次检索往往不够。
- 需要**精确计算**：如求和、聚合，应交给数据库或工具。
- **知识本身就是错的**：垃圾进、垃圾出，RAG 会忠实复述错误。

> RAG 补的是"知识缺口"，不是"能力缺口"。识别缺口类型，才能选对方案。

# 3. RAG vs 微调 vs 提示工程

## 3.1 三种方案对比

| 维度 | 提示工程 | RAG | 微调 |
|------|----------|-----|------|
| 成本 | 最低 | 中 | 高 |
| 见效速度 | 立刻 | 快 | 慢（需训练） |
| 知识更新 | 手动改提示 | 更新知识库即可 | 需重新训练 |
| 能力改变 | 无 | 无（只补知识） | 可改变风格与能力 |
| 可解释性 | 中 | 高（可引用来源） | 低 |
| 适用 | 格式/风格控制 | 知识问答 | 风格/能力定制 |

## 3.2 决策顺序

```
提示工程 → RAG → 微调
（先用最便宜的手段，不够再升级）
```

### 3.2.1 何时用提示工程

问题可通过**指令**解决：格式约束、角色设定、简单规则、少量示例（Few-shot）。改动成本几乎为零，先试。

### 3.2.2 何时升级到 RAG

当答案依赖**外部且频繁变化的知识**，提示词放不下或维护成本高时，改用 RAG。典型信号：文档量大、更新频繁、需要引用来源。

### 3.2.3 何时才需要微调

当需要改变**模型行为本身**——固定话术、特定领域推理风格、压缩提示长度（把长提示蒸馏进权重）——才考虑微调。微调不是"灌知识"的首选。

## 3.3 组合使用

三者并非互斥，常见组合：

- 微调 + RAG：微调定风格，RAG 供知识。
- 提示工程 + RAG：提示约束引用格式，RAG 供内容。
- 提示工程 + 微调：先用提示验证需求，再蒸馏进模型。

## 3.4 边界与坑

- 微调无法可靠地"注入新知识"，模型仍可能记错或忘记。
- 微调后的模型更新知识需重训，时效性差。
- RAG 与微调同时上，故障定位变难，建议先单独验证。

> 大多数企业"让模型懂我们公司"的需求，RAG 就能解决，**不需要微调**。

# 4. RAG 的价值

## 4.1 业务价值

**结论先行**：RAG 的核心价值在于用较低成本，让模型回答"你的私有、最新、可溯源"的知识。

### 4.1.1 知识时效性

知识库更新即生效，无需重训模型。昨天发布的新政策，今天即可被问到。

### 4.1.2 可溯源

回答可标注来源链接或条文编号，用户可自行核对，显著提升可信度。

### 4.1.3 成本可控

相比微调，无需标注训练数据、无需 GPU 训练，落地快、成本低。

### 4.1.4 数据安全

知识留在自有系统，仅把命中的片段送入模型，不必把全部数据交给模型训练。

## 4.2 价值量化

| 维度 | 无 RAG | 有 RAG |
|------|--------|--------|
| 知识更新周期 | 以周/月计 | 分钟级 |
| 答案可核对 | 不可 | 可（附来源） |
| 新增知识成本 | 重训模型 | 入库即可 |
| 幻觉风险 | 高 | 中（有据可依） |

## 4.3 生产建议

- 为每条知识保留**来源、版本、更新时间**元数据。
- 回答默认附引用，前端可点击跳转原文。
- 把"知识更新"做成流水线，而非人工搬运。

# 5. RAG 的局限

## 5.1 检索侧局限

| 局限 | 说明 |
|------|------|
| 依赖检索质量 | 检索不到就无法回答 |
| 语义鸿沟 | 问法与文档用词不一致时召回差 |
| 长尾覆盖 | 冷门知识可能无对应片段 |

## 5.2 生成侧局限

| 局限 | 说明 |
|------|------|
| 上下文有限 | 只能塞入有限的片段 |
| 中间遗忘 | 长上下文中部信息易被忽略 |
| 过度推断 | 模型可能超出资料范围作答 |

## 5.3 结构化数据局限

- 表格/数值计算不擅长：RAG 检索的是文本，无法直接做聚合。
- 关系型查询弱：需要 JOIN、GROUP BY 的诉求应走 SQL。
- 分块损失信息：切分可能破坏表格结构。

## 5.4 进阶方案映射

### 5.4.1 GraphRAG

用知识图谱（Knowledge Graph）组织实体与关系，支持跨文档多跳推理。适合"实体关系复杂"的场景。

### 5.4.2 Agentic RAG

让 Agent 决定"何时检索、检索几次、如何组合"，支持多轮检索与工具调用。适合复杂任务。

> 这些局限催生了 GraphRAG、Agentic RAG 等进阶方案（见 `Advanced/`）。

# 6. RAG 的两大阶段

## 6.1 离线索引阶段

**结论先行**：离线阶段负责"把知识变成可检索的索引"，决定系统的召回上限。

### 6.1.1 环节拆解

```
文档 → 解析 → 清洗 → 切分 → 向量化 → 入库
```

每一步都可能丢信息：解析丢表格、切分断语义、向量化丢细节。

### 6.1.2 决定召回上限

如果某条知识在离线阶段就被切散或未入库，在线阶段再强也检索不到。**离线是地基。**

## 6.2 在线查询阶段

**结论先行**：在线阶段负责"从索引中精准取出相关内容"，决定系统的精度与体验。

### 6.2.1 环节拆解

```
问题 → 查询改写 → 向量化 → 检索 → 重排 → 拼装 → 生成
```

### 6.2.2 决定精度

同样一批索引，查询改写与重排的质量直接决定最终答案的相关性。

## 6.3 两阶段的依赖关系

```
离线（索引）阶段                    在线（查询）阶段
──────────────────                 ──────────────────
文档 → 解析 → 切分                  用户问题
     → 向量化 → 入库                     │
                                        ▼
                                  查询向量化 → 检索
                                        │
                                        ▼
                                  重排 → 拼装上下文
                                        │
                                        ▼
                                    模型生成
```

- 离线阶段决定**能检索到什么**（召回上限）。
- 在线阶段决定**检索得准不准**（精度）。

> 两阶段解耦：离线可批量重跑，在线需低延迟响应。

# 7. RAG 效果的公式

## 7.1 公式解读

```
RAG 效果 ≈ 检索质量 × 生成质量
```

用乘法而非加法，是因为任一环节为零，整体即为零。检索不到，生成再强也无用；检索很准，生成胡编同样失败。

## 7.2 检索质量的影响因素

- **分块策略**：块大小、重叠、语义完整性。
- **Embedding 模型**：是否适配中文与领域。
- **检索策略**：向量、关键词、混合。
- **重排模型**：是否使用交叉编码器（Cross-Encoder）。

## 7.3 生成质量的影响因素

- **提示设计**：约束、引用格式、拒答指令。
- **模型能力**：上下文窗口、指令遵循能力。
- **上下文组织**：顺序、去重、Token 预算。

## 7.4 瓶颈分析

> 经验：**RAG 的瓶颈 80% 在检索**。检索不到，再强的模型也答不对。

排查顺序建议：先看召回是否命中，再看重排是否把正确片段排前，最后才怀疑生成。

# 8. RAG 典型指标

## 8.1 检索侧指标

### 8.1.1 召回率

Recall@K：正确文档是否出现在前 K 个结果中。衡量"漏没漏"。

### 8.1.2 精确率

Precision@K：检索结果中相关片段的比例。衡量"准不准"。

### 8.1.3 MRR 与 NDCG

- MRR（Mean Reciprocal Rank）：第一个正确结果排名的倒数均值。
- NDCG（Normalized Discounted Cumulative Gain）：考虑排序位置的增益。

## 8.2 生成侧指标

### 8.2.1 忠实度

Faithfulness：回答是否**完全基于**检索内容，有无编造。

### 8.2.2 答案相关性

Answer Relevance：回答是否切题，有无答非所问。

## 8.3 端到端指标

| 指标 | 含义 |
|------|------|
| 召回率 | 正确文档是否被检索到 |
| 精确率 | 检索结果中相关的比例 |
| 忠实度 | 回答是否基于检索内容 |
| 答案相关性 | 回答是否切题 |
| 端到端准确率 | 最终答案正确率 |

## 8.4 指标采集建议

- 建立**黄金集**（问题 + 标准答案 + 应命中文档）。
- 检索与生成指标分开采集，便于定位瓶颈。
- 用 LLM-as-Judge 自动打分，辅以人工抽检。

> 详见 `Evaluation/1_rag_evaluation.md`。

# 9. 什么时候不该用 RAG

## 9.1 不适合的场景

**结论先行**：当需求本质不是"补知识"时，RAG 往往不是最优解。

| 场景 | 更合适方案 |
|------|------------|
| 需要改变模型风格/能力 | 微调 |
| 强结构化查询（统计、聚合） | 直接查数据库 / Text2SQL |
| 实时性要求极高（毫秒级） | 缓存 / 规则引擎 |
| 知识量极小（几段话） | 直接放进提示 |

## 9.2 替代方案对照

| 诉求 | 方案 |
|------|------|
| 风格定制 | 微调 / 提示工程 |
| 精确聚合 | SQL / Text2SQL |
| 毫秒级响应 | 缓存 / 规则 |
| 极小知识 | 直接进提示 |

## 9.3 混合架构

现实中常组合使用：规则前置过滤 → 缓存命中直接返回 → 未命中走 RAG → 需要计算时调工具。RAG 只是其中一环。

# 10. 小结

## 10.1 核心要点

- RAG = 检索 + 增强 + 生成，让模型"开卷考试"。
- 解决知识截止、私有知识、幻觉三大问题。
- 优先级：提示工程 > RAG > 微调。
- 效果 = 检索质量 × 生成质量，检索是主要瓶颈。
- RAG 不是万能的，结构化查询与风格定制要另寻方案。
