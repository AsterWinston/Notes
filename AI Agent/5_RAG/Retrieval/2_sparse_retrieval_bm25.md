# 1. 什么是稀疏检索

**结论先行**：稀疏检索（Sparse Retrieval，稀疏检索）基于**词频统计**做词面匹配，最经典的是 BM25（Best Matching 25）。它不需要神经网络，靠词是否出现、出现几次、词有多稀有来打分。

## 1.1 定义与直觉

### 1.1.1 基本流程

```
查询 ──分词──▶ 词项集合 ──倒排索引──▶ 候选文档 ──BM25 打分──▶ Top-K
```

```
查询："差旅费报销标准"
稀疏：找出包含"差旅费""报销""标准"这些词的文档，按词频与稀有度打分
```

### 1.1.2 稀疏的含义

"稀疏"指文档向量是**高维、绝大多数为 0**（词表维度，只有出现的词非 0）。一个十万词表里，一篇文档可能只有几十个非零维度。

### 1.1.3 名称由来

BM25 全称 Best Matching 25，源自 Okapi 检索系统，是 Okapi BM 系列公式的第 25 次迭代版本。它至今仍是多数搜索引擎的默认打分算法。

## 1.2 与稠密检索的关系

| 维度 | 稀疏检索 | 稠密检索 |
|------|----------|----------|
| 匹配依据 | 词面重叠 | 语义相似 |
| 同义词 | 弱 | 强 |
| 专有名词 | 强 | 弱 |
| 可解释性 | 强 | 弱 |
| 冷启动 | 无需训练 | 依赖模型 |

两者互补，生产实践几乎都是混合使用。

## 1.3 生产建议

| 建议 | 理由 |
|------|------|
| 作为混合检索的一路 | 补齐精确匹配 |
| 保留原始查询 | 稀疏依赖原始词 |
| 与稠密分别评测 | 定位各自贡献 |

# 2. BM25 原理

**结论先行**：BM25 综合考虑词频、逆文档频率、文档长度三个因素，对每个查询词打分后求和。

## 2.1 公式

### 2.1.1 完整公式

```
score(q, d) = Σ  IDF(t) × TF 饱和 × 长度归一化
              t∈q
```

展开后：

```
                  f(t,d) × (k1 + 1)
score(q,d) = Σ  ────────────────────────────────────── × IDF(t)
             t∈q  f(t,d) + k1 × (1 - b + b × |d|/avgdl)
```

其中 `f(t,d)` 为词 t 在文档 d 中的频次，`|d|` 为文档长度，`avgdl` 为平均文档长度。

### 2.1.2 三个因素

| 因素 | 含义 |
|------|------|
| TF（词频） | 词在文档中出现越多，得分越高（但有饱和上限） |
| IDF（逆文档频率） | 词越稀有，区分度越高，权重越大 |
| 长度归一化 | 长文档不因字数多而占优 |

### 2.1.3 一个算例

假设共 100 篇文档，"报销"出现在 5 篇，某文档中该词出现 2 次，取 `k1=1.5, b=0.75`，且该文档长度等于平均长度：

```
IDF   = ln((100 - 5 + 0.5) / (5 + 0.5) + 1) ≈ 2.94
TF 项 = 2 × (1.5 + 1) / (2 + 1.5 × (1 - 0.75 + 0.75 × 1))
      = 5 / 3.5 ≈ 1.43
贡献  = 2.94 × 1.43 ≈ 4.2
```

查询若有多个词，把每个词的贡献相加即得总分。

## 2.2 TF 饱和

```
词出现 1 次 → 得分大幅上升
词出现 10 次 → 得分趋于平缓
```

因为公式里 `f` 在分子分母同时出现，当 `f` 增大时比值趋向 `k1 + 1` 的上限。这防止"堆砌关键词"刷分。

## 2.3 IDF 权重

```
"的"    出现于几乎所有文档 → IDF 极低 → 几乎无区分度
"报销"  出现于少数文档     → IDF 高   → 区分度高
```

常用形式：

```
IDF(t) = ln( (N - n(t) + 0.5) / (n(t) + 0.5) + 1 )
```

其中 `N` 为文档总数，`n(t)` 为含词 t 的文档数。加 0.5 与加 1 是为了平滑，避免除零与负值。

## 2.4 长度归一化

参数 `b` 控制归一化强度：`b=1` 时完全按长度归一，`b=0` 时不归一。长文档天然含更多词，若不归一会被过度偏爱，因此默认 `b=0.75`。

## 2.5 BM25 与 TF-IDF 对比

| 维度 | TF-IDF | BM25 |
|------|--------|------|
| TF 处理 | 线性或对数 | 饱和上限 |
| 长度归一 | 无或简单 | 参数 b 控制 |
| 调参 | 少 | k1、b |

BM25 可看作 TF-IDF 的改良版：给 TF 加上饱和、给长度加上可调归一。

## 2.6 生产建议

| 建议 | 理由 |
|------|------|
| 理解 TF 饱和 | 避免靠重复词刷分 |
| 关注 IDF | 停用词应剔除 |
| 按语料调 b | 文档长度差异大时更关键 |

# 3. 参数

**结论先行**：BM25 只有两个主要参数 `k1` 与 `b`，默认值通常已够用，除非语料特性明显。

## 3.1 k1 与 b

| 参数 | 含义 | 常用值 |
|------|------|--------|
| `k1` | TF 饱和速度 | 1.2~2.0 |
| `b` | 长度归一化强度 | 0.75 |

## 3.2 参数影响

```
k1 小 → 词频很快饱和，少量出现即封顶
k1 大 → 词频影响更持久

b 大 → 强归一化，长文档被压制
b 小 → 弱归一化，长文档占优
```

## 3.3 调参建议

短文本（如标题、问答）适合较小的 `b`；长文档（如合同、手册）适合较大的 `b`。`k1` 一般在 1.2~2.0 之间微调，收益有限，不要过度投入。

## 3.4 生产建议

| 建议 | 理由 |
|------|------|
| 先用默认值 | 收益边际小 |
| 有评测再调 | 避免玄学调参 |
| 按字段分别配置 | 标题与正文不同 |

# 4. 倒排索引

**结论先行**：倒排索引（Inverted Index，倒排索引）是"词 → 文档列表"的映射，是 BM25 能快速检索的基础。

## 4.1 结构

```
词项          文档列表（含词频/位置）
────────────────────────────────────
报销    →   doc1:3, doc5:1, doc9:2
差旅    →   doc1:2, doc9:1
标准    →   doc1:1, doc5:4
```

## 4.2 查询过程

### 4.2.1 求交与合并

查询时：取各词项的文档列表求交集（AND）或并集（OR），得到候选集。真实系统还会用跳表（skip list）加速求交。

### 4.2.2 打分排序

对候选集逐文档计算 BM25 分数并排序，取 Top-K。词项位置信息还可支持短语查询（phrase query）与邻近度打分。

### 4.2.3 短语查询

若要求词序相邻（如"人工智能"不被拆成两个词分散命中），可用短语查询。倒排链中的位置信息让系统能校验词项距离，从而只保留真正相邻的命中。

## 4.3 生产建议

| 建议 | 理由 |
|------|------|
| 索引常驻内存 | 加速倒排链访问 |
| 压缩倒排链 | 降低内存 |
| 定期合并段 | 减少碎片 |

# 5. 实现方式

**结论先行**：生产用 Elasticsearch / OpenSearch，小规模可用 Lucene 内存索引，PostgreSQL 适合已有 PG 的轻量场景。

## 5.1 Elasticsearch / OpenSearch

### 5.1.1 查询

```java
SearchSourceBuilder source = new SearchSourceBuilder()
        .query(QueryBuilders.multiMatchQuery(question, "title", "content")
                .type(MultiMatchQueryBuilder.Type.BEST_FIELDS)
                .tieBreaker(0.3))
        .size(20);
```

### 5.1.2 自定义 BM25 参数

```java
// 自定义 BM25 参数
settings.put("index.similarity.custom_bm25.k1", 1.5);
settings.put("index.similarity.custom_bm25.b", 0.75);
```

`BEST_FIELDS` 取各字段最高分，`tieBreaker` 让次优字段也贡献少量分数，适合"标题权重高于正文"的场景。

### 5.1.3 高亮与解释

ES 支持高亮（highlight），把命中的词在结果中标注出来。这既是稀疏检索可解释性的体现，也能帮用户快速判断结果是否相关。

## 5.2 PostgreSQL 全文检索

```sql
-- 中文需分词扩展（如 zhparser / pg_jieba）
SELECT id, content,
       ts_rank(to_tsvector('chinese', content),
               plainto_tsquery('chinese', ?)) AS score
FROM knowledge
WHERE to_tsvector('chinese', content) @@ plainto_tsquery('chinese', ?)
ORDER BY score DESC
LIMIT 10;
```

注意 PostgreSQL 默认的 `ts_rank` 并非严格 BM25，而是类似的 TF-IDF 变体；若追求 BM25，可考虑扩展或换检索引擎。

## 5.3 Java 内存实现（小规模）

```java
// 基于 Lucene 的 BM25
Directory directory = new ByteBuffersDirectory();
IndexWriter writer = new IndexWriter(directory, new IndexWriterConfig(analyzer));

for (Document doc : documents) {
    org.apache.lucene.document.Document luceneDoc = new org.apache.lucene.document.Document();
    luceneDoc.add(new TextField("content", doc.getText(), Field.Store.YES));
    writer.addDocument(luceneDoc);
}

// 检索
IndexSearcher searcher = new IndexSearcher(DirectoryReader.open(directory));
Query query = new BooleanQuery.Builder()
        .add(new TermQuery(new Term("content", keyword)), BooleanClause.Occur.SHOULD)
        .build();
TopDocs topDocs = searcher.search(query, 10);
```

> Lucene 是 Java 生态最成熟的 BM25 实现。

## 5.4 生产建议

| 建议 | 理由 |
|------|------|
| 大规模用 ES | 分布式、成熟 |
| 轻量用 Lucene | 无外部依赖 |
| 已有 PG 可先用 PG | 减少组件 |

# 6. 中文分词

**结论先行**：BM25 依赖分词，中文必须处理，**领域词典是必备**。

## 6.1 分词器对比

| 分词器 | 说明 |
|--------|------|
| IK Analyzer | ES 常用，支持自定义词典 |
| jieba | Python 生态，也有 Java 版 |
| HanLP | 功能强大 |
| zhparser | PostgreSQL 扩展 |
| pg_jieba | PostgreSQL 扩展 |

## 6.2 自定义词典

```java
// 自定义词典提升领域词分词准确率
// resources/ik/custom.dic:
// 差旅报销
// 报销标准
```

若词典缺失，"差旅报销"可能被切成"差旅/报销"甚至更碎，导致查询与文档的切分不一致而漏召回。

## 6.3 停用词

停用词（stop words）如"的、了、是"对检索无贡献却占索引空间，应配置停用词表剔除。

### 6.3.1 分词粒度

分词粒度（granularity）影响召回与精度：切得太细（字级）召回高但噪声大，切得太粗（词级）精度高但易漏。可用"粗分 + 细分"双索引兼顾。

## 6.4 生产建议

| 建议 | 理由 |
|------|------|
| 建领域词典 | 直接决定效果 |
| 词典版本化 | 便于复现 |
| 维护停用词表 | 降噪 |

> 分词质量直接决定 BM25 效果，**领域词典是必备**。

# 7. 稀疏检索的优势场景

**结论先行**：凡是要精确匹配字符串的场景，稀疏检索都优于稠密。

## 7.1 场景表

| 场景 | 说明 |
|------|------|
| 专有名词 | "A123 订单"精确匹配 |
| 产品型号 | "iPhone 15 Pro Max" |
| 法律条文 | "民法典第 1024 条" |
| 代码标识符 | "getUserById" |
| 缩写/术语 | 领域内固定表达 |

## 7.2 一个案例

查询"错误码 E5021"，稠密检索可能把它当噪声，返回泛泛的"常见错误处理"；稀疏检索能精确命中含 E5021 的运维手册。

### 7.2.1 多字段加权检索

真实场景常需给标题、正文不同权重，可用布尔查询的 boost 实现：

```java
// 伪代码：标题权重高于正文
Query q = new BooleanQuery.Builder()
        .add(new BoostQuery(new TermQuery(new Term("title", term)), 3.0f),
             BooleanClause.Occur.SHOULD)
        .add(new TermQuery(new Term("content", term)),
             BooleanClause.Occur.SHOULD)
        .build();
```

标题命中往往比正文命中更相关，适度提升标题权重能显著改善排序。

## 7.3 生产建议

| 建议 | 理由 |
|------|------|
| 精确类查询走稀疏 | 命中率更高 |
| 结合意图路由 | 不同查询走不同路 |
| 保留字段权重 | 标题优先 |

# 8. 稀疏检索的劣势

**结论先行**：稀疏检索的核心缺陷是**词汇鸿沟**——用户说的词和文档写的词不一致时就失效。

## 8.1 劣势表

| 劣势 | 说明 |
|------|------|
| 无同义词能力 | "报销" 匹配不到 "费用申请" |
| 依赖分词 | 分词错则检索错 |
| 词汇鸿沟 | 用户表达与文档用词不一致时失效 |

## 8.2 词汇鸿沟

```
用户说："怎么把钱要回来"
文档写："费用报销流程"
稀疏：无共同词 → 召回失败
稠密：语义相近 → 成功召回
```

## 8.3 缓解手段

| 手段 | 说明 |
|------|------|
| 同义词扩展 | 查询时补入同义词 |
| 查询改写 | 统一表达 |
| 混合检索 | 引入语义匹配 |

## 8.4 生产建议

| 建议 | 理由 |
|------|------|
| 同义词扩展 | 缓解词汇鸿沟 |
| 查询改写 | 补足表达差异 |
| 混合检索 | 从根上互补 |

> 这正是需要**混合检索**的原因。

# 9. 生产注意事项

**结论先行**：稀疏检索的坑集中在分词、词典、字段权重与索引更新上，每一项都要在上线前确认。

## 9.1 风险表

| 风险 | 建议 |
|------|------|
| 中文未分词 | 装 IK/zhparser |
| 无领域词典 | 维护自定义词典 |
| 停用词缺失 | 配置停用词表 |
| 字段权重不当 | 标题权重高于正文 |
| 只用稀疏 | 搭配稠密检索 |
| 索引未更新 | 增量索引 |

## 9.2 索引更新

文档新增、修改、删除后必须同步索引，否则会返回过期内容。生产常用增量索引（incremental indexing）加定期全量重建。

## 9.3 性能优化

| 手段 | 说明 |
|------|------|
| 缓存热词 | 高频查询直接返回 |
| 减少字段 | 只索引必要字段 |
| 限制 topK | 只取需要条数 |
| 分片并行 | 大索引横向扩展 |

# 10. 小结

## 10.1 核心要点回顾

- BM25 是稀疏检索的标准算法，靠词频与稀有度打分。
- 擅长专有名词、型号、条文等精确匹配。
- 中文必须分词，领域词典是效果关键。
- 弱点是同义词与词汇鸿沟。
- 生产实践几乎都是"稠密 + 稀疏"混合。
