# 1. 什么是稠密检索

**结论先行**：稠密检索（Dense Retrieval，稠密检索）= 用 Embedding（嵌入）向量做语义相似度检索。它把查询和文档都映射到同一个低维连续空间，靠"距离近"判定语义相关。

## 1.1 定义与直觉

### 1.1.1 基本流程

```
查询 ──Embedding──▶ 查询向量 ──ANN──▶ Top-K 相似向量 ──▶ 对应文本
```

"稠密"指向量是**低维、每个维度都有值**（如 1024 维 float），区别于稀疏向量（高维、绝大多数为 0）。

### 1.1.2 为什么能语义匹配

训练时模型见过大量"语义相近则向量相近"的样本，因此"报销"与"费用申请"即使没有共同词，也会落在空间里相邻的位置。这正是稠密检索相对词面匹配的最大优势。

### 1.1.3 ANN 的作用

精确检索要遍历全部向量，规模大时不可接受。近似最近邻（ANN，Approximate Nearest Neighbor）用索引换速度，常见算法：

| 算法 | 思路 | 特点 |
|------|------|------|
| HNSW | 多层图，逐层跳转 | 召回高、内存大 |
| IVF | 先聚类再搜桶 | 省内存 |
| PQ | 向量压缩 | 省内存、损精度 |

## 1.2 向量与相似度

### 1.2.1 常用相似度

| 度量 | 公式直觉 | 说明 |
|------|----------|------|
| 余弦相似度 | 夹角余弦 | 只看向量方向，最常用 |
| 内积 | 方向 + 长度 | 部分模型按内积训练 |
| 欧氏距离 | 直线距离 | 越小越相似 |

### 1.2.2 归一化的意义

若把向量归一化为单位长度，余弦相似度与内积等价，欧氏距离也与余弦单调对应。生产上常统一归一化，避免度量混用导致分数不可比。

### 1.2.3 双塔模型与交叉模型

稠密检索的 Embedding 模型通常是**双塔（bi-encoder，双塔）**：查询与文档分别独立编码，因此文档向量可离线预计算。相对地，交叉编码器（cross-encoder，交叉编码器）把查询与文档拼在一起联合编码，精度更高但无法预计算，只适合重排。

| 模型 | 结构 | 能否预计算 | 典型用途 |
|------|------|------------|----------|
| 双塔 | 查询/文档分开编码 | 能 | 召回 |
| 交叉编码器 | 拼接后联合编码 | 不能 | 重排 |

## 1.3 生产建议

| 建议 | 理由 |
|------|------|
| 查询与文档用同一模型 | 跨模型向量不可比 |
| 索引与查询度量一致 | 否则分数无意义 |
| 记录模型版本 | 便于重建索引 |

# 2. 稠密 vs 稀疏

**结论先行**：稠密擅长语义泛化，稀疏擅长精确匹配，二者互补而非替代。

## 2.1 对比表

| 维度 | 稠密检索 | 稀疏检索（BM25） |
|------|----------|------------------|
| 表示 | 低维稠密向量 | 高维稀疏词频 |
| 匹配 | 语义相似 | 词面匹配 |
| 同义词 | 能召回 | 召回不到 |
| 专有名词 | 可能失准 | 精确匹配 |
| 训练 | 需要模型 | 无需 |
| 解释性 | 弱 | 强 |

## 2.2 一个例子

```
查询："怎么报销"
稠密：能召回"差旅费用申请流程"（语义相近）
稀疏：召回不到（没有共同词）
```

反过来，查询"民法典第 1024 条"，稠密可能召回一堆泛泛的"法律条文"，而稀疏能精确命中含该编号的文档。

## 2.3 混合的必要性

两者的失效场景几乎互补：稠密的短板（编号、型号、代码标识符）正是稀疏的长处，稀疏的短板（同义词、改写）正是稠密的长处。因此生产系统普遍采用混合检索（Hybrid Retrieval，混合检索）。

## 2.4 生产建议

| 建议 | 理由 |
|------|------|
| 默认上混合 | 覆盖面最广 |
| 用融合算法合并 | 如 RRF |
| 分别评测再合并 | 定位短板 |

# 3. 基础实现

**结论先行**：主流 Java 框架都把稠密检索封装为"向量库 + 相似度查询"，Spring AI 与 LangChain4j 的 API 语义一致。

## 3.1 Spring AI

### 3.1.1 基本检索

```java
List<Document> docs = vectorStore.similaritySearch(
        SearchRequest.builder()
                .query(question)
                .topK(10)
                .similarityThreshold(0.6)
                .build());
```

### 3.1.2 带过滤的检索

```java
// 伪代码：按租户与权限过滤
SearchRequest request = SearchRequest.builder()
        .query(question)
        .topK(10)
        .filterExpression("tenant == 'acme' && acl == 'public'")
        .build();
List<Document> docs = vectorStore.similaritySearch(request);
```

## 3.2 LangChain4j

### 3.2.1 ContentRetriever

```java
ContentRetriever retriever = EmbeddingStoreContentRetriever.builder()
        .embeddingStore(store)
        .embeddingModel(embeddingModel)
        .maxResults(10)
        .minScore(0.6)
        .build();
```

### 3.2.2 EmbeddingStore

```java
// 写入：先嵌入再存储
Embedding embedding = embeddingModel.embed(text).content();
store.add(embedding, text, metadata);
```

## 3.3 手写检索流程

若不依赖框架，可手动实现"嵌入 → 相似度 → 排序"，便于理解内部机制。

```java
// 伪代码：手写稠密检索
public List<Doc> search(String query, int topK) {
    float[] q = model.embed(query);
    return store.all().stream()
            .map(d -> Map.entry(d, cosine(q, d.vector())))
            .sorted(Map.Entry.<Doc, Double>comparingByValue().reversed())
            .limit(topK)
            .map(Map.Entry::getKey)
            .toList();
}
```

生产环境应把 `all()` 换成 ANN 索引，否则复杂度是 O(N)，规模一大会拖垮服务。

## 3.4 生产建议

| 建议 | 理由 |
|------|------|
| 封装检索层 | 便于替换向量库 |
| 统一 topK/阈值 | 避免各处不一致 |
| 记录检索日志 | 便于离线分析 |

# 4. 关键参数

**结论先行**：`topK`、`similarityThreshold`、`filterExpression` 是稠密检索的三个核心旋钮，必须用数据校准而非拍脑袋。

## 4.1 参数表

| 参数 | 作用 | 建议 |
|------|------|------|
| `topK` | 返回条数 | 10~20（给重排留空间） |
| `similarityThreshold` | 相似度下限 | 0.6~0.75，需校准 |
| `filterExpression` | 元数据过滤 | 权限/租户必用 |

## 4.2 topK 的权衡

`topK` 太小会漏召回，太大则引入噪声、增加重排与生成成本。常见做法是召回阶段取 20~50，重排后取 3~5 喂给大模型。

## 4.3 阈值的作用

阈值过滤掉低质量结果，避免"无中生有"。但阈值与模型、数据集强相关，同一个 0.7 在不同模型上含义完全不同，因此必须校准。

## 4.4 过滤表达式

元数据过滤（metadata filter）既能实现权限隔离，也能缩小检索范围提升精度。注意：过滤应下推到向量库，而不是检索后再筛，否则会破坏 topK 语义。

## 4.5 生产建议

| 建议 | 理由 |
|------|------|
| 参数集中配置 | 便于调参与回滚 |
| 按场景分档 | 不同意图不同 topK |
| 过滤下推 | 保证召回质量 |

# 5. 召回策略

**结论先行**：召回阶段追求"不漏"，重排阶段追求"排准"。二者目标不同，参数也应不同。

## 5.1 召回要多

### 5.1.1 粗排与精排

```
粗排（召回）目标：不漏掉相关文档 → topK 取大（20~50）
精排（重排）目标：把最相关的排前面 → 取 3~5
```

### 5.1.2 漏斗图

```
全部文档
   │  向量召回 topK=50
   ▼
候选集 50
   │  重排 cross-encoder
   ▼
精排 5
   │  喂给 LLM
   ▼
答案
```

> 常见错误：直接 topK=3 喂给模型，导致相关文档在 5~10 名被漏掉。

## 5.2 多路召回

### 5.2.1 多查询并行召回

```java
// 同一查询用多种方式召回，再合并去重
Set<Document> merged = new LinkedHashSet<>();
merged.addAll(vectorSearch(question, 20));           // 原始查询
merged.addAll(vectorSearch(rewrittenQuery, 20));     // 改写查询
merged.addAll(vectorSearch(hypotheticalAnswer, 20)); // HyDE
```

### 5.2.2 HyDE 直觉

HyDE（Hypothetical Document Embeddings，假设文档嵌入）先让大模型"编"一个假想答案，再用它去检索。因为假想答案的用词更接近真实文档，命中率往往更高。

### 5.2.3 结果融合

多路结果用 RRF（Reciprocal Rank Fusion，倒数排名融合）合并，避免不同路的分数不可比。

```
RRF(d) = Σ  1 / (k + rank_i(d))
        i∈路数
```

```java
// 伪代码：RRF 融合多路结果
Map<String, Double> fused = new HashMap<>();
for (List<Document> list : rankedLists) {
    for (int i = 0; i < list.size(); i++) {
        String id = list.get(i).getId();
        fused.merge(id, 1.0 / (60 + i + 1), Double::sum);
    }
}
List<Document> result = fused.entrySet().stream()
        .sorted(Map.Entry.<String, Double>comparingByValue().reversed())
        .map(e -> byId(e.getKey()))
        .toList();
```

常数 `k` 通常取 60，用于削弱头部名次的绝对优势。

## 5.3 生产建议

| 建议 | 理由 |
|------|------|
| 召回取大 | 给重排留空间 |
| 多路去重 | 避免重复文档 |
| 融合而非加权原始分 | 分数不可比 |

# 6. 稠密检索的失效场景

**结论先行**：稠密检索**不是万能的**，生产几乎都要搭配稀疏检索。

## 6.1 失效表

| 场景 | 原因 | 对策 |
|------|------|------|
| 专有名词/编号 | 模型未见过 | 混合检索（BM25） |
| 精确短语匹配 | 语义泛化 | 混合检索 |
| 短查询 | 信息量不足 | 查询扩展 |
| 领域术语 | 通用模型不懂 | 领域微调 / 换模型 |
| 长文档 | 单向量表达力不足 | 分块 + 父子检索 |

## 6.2 典型案例

查询"工单 A123 的进度"，稠密可能返回一堆"工单处理流程"泛文档，因为它把 A123 当成了噪声；而稀疏能精确锁定含 A123 的记录。

## 6.3 缓解手段

- 混合检索：引入 BM25 补齐精确匹配。
- 查询改写：把口语化查询规范化。
- 领域微调：让模型理解术语。
- 父子检索：小块检索、大块返回。

## 6.4 生产建议

| 建议 | 理由 |
|------|------|
| 混合检索兜底 | 覆盖精确匹配 |
| 保留原始查询关键词 | 便于稀疏路使用 |
| 监控坏例 | 定期补充评测 |

# 7. 相似度阈值校准

**结论先行**：阈值决定"召回多少"，必须用标注数据画分布来选，而非凭经验。

## 7.1 为什么需要校准

不同模型的分数分布差异巨大：有的模型相关样本普遍 0.8+，有的只有 0.5。直接套用别人的阈值，往往要么全滤掉，要么形同虚设。

## 7.2 校准代码

```java
// 用标注数据画分布，选阈值
public void calibrate(List<EvalCase> cases) {
    for (double threshold = 0.4; threshold <= 0.9; threshold += 0.05) {
        double precision = precisionAt(cases, threshold);
        double recall = recallAt(cases, threshold);
        double f1 = 2 * precision * recall / (precision + recall);
        log.info("threshold={} P={} R={} F1={}", threshold, precision, recall, f1);
    }
}
```

## 7.3 分数分布直觉

```
相关样本分数   ██████████ 集中在 0.7~0.9
不相关样本分数 ███        集中在 0.4~0.6
                    ▲
              阈值选在 0.65 附近最合适
```

若两个分布重叠严重，说明模型区分度低，此时微调或换模型比调阈值更有价值。

### 7.3.1 校准与 topK 的联动

阈值与 topK 不是独立的：阈值越低，同样的 topK 会纳入越多低分结果；阈值越高，可能返回不足 topK 条。调参时应固定一个、扫描另一个，观察 F1 与返回条数两条曲线。

## 7.4 生产建议

| 建议 | 理由 |
|------|------|
| 按场景分别校准 | 不同意图分布不同 |
| 定期重校 | 数据分布会漂移 |
| 保留低分兜底 | 避免全部被滤空 |

# 8. 缓存优化

**结论先行**：热点查询（如"如何报销"）缓存收益很高，可同时降低延迟与成本。

## 8.1 缓存层次

| 层次 | 内容 | 命中率 |
|------|------|--------|
| 查询向量缓存 | 文本 → 向量 | 高 |
| 检索结果缓存 | 查询 → 文档列表 | 高 |
| 答案缓存 | 查询 → 最终答案 | 中 |

## 8.2 缓存代码

```java
// 缓存查询向量与检索结果
public List<Document> searchWithCache(String question) {
    String key = sha256(question + tenantId);

    List<Document> cached = cache.get(key);
    if (cached != null) return cached;

    List<Document> docs = vectorStore.similaritySearch(...);
    cache.put(key, docs, Duration.ofMinutes(10));
    return docs;
}
```

## 8.3 失效与一致性

索引更新后，结果缓存必须失效，否则会返回已删除或过期的文档。做法是把"索引版本"编进缓存键，索引一升级键自然全变。

## 8.4 生产建议

| 建议 | 理由 |
|------|------|
| 缓存键含租户 | 防止越权 |
| 缓存键含索引版本 | 保证一致性 |
| 设置 TTL | 防止无限陈旧 |

# 9. 生产注意事项

**结论先行**：稠密检索上线要关注参数、过滤、混合、缓存、监控五个方面，缺一不可。

## 9.1 风险表

| 风险 | 建议 |
|------|------|
| topK 过小 | 召回 20+，重排后取 5 |
| 阈值拍脑袋 | 用标注数据校准 |
| 无过滤 | 权限/租户过滤必加 |
| 纯稠密检索 | 搭配 BM25 混合 |
| 无缓存 | 热点查询缓存 |
| 不监控召回率 | 持续监控 + 告警 |

## 9.2 监控指标

```
召回率（离线评测集）
空结果率（线上）
平均延迟 P50/P99
缓存命中率
```


# 10. 小结

## 10.1 核心要点回顾

- 稠密检索靠语义相似度，擅长同义改写。
- 对专有名词、精确匹配较弱，需搭配稀疏检索。
- 召回要"多"，精排再"少"。
- 阈值与 topK 必须用数据校准。
- 缓存与多路召回是提升效果与性能的常用手段。

## 10.2 下一步行动

- 先用标注集校准阈值与 topK。
- 接入 BM25 组成混合检索。
- 加上重排与缓存，再持续监控召回率。
