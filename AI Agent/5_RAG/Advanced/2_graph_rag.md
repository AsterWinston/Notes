# 1. 传统 RAG 的局限

结论先行：传统 RAG（Retrieval-Augmented Generation，检索增强生成）以"单块向量检索"为核心，面对多跳推理、全局总结与显式关系查询时结构性失效。

## 1.1 三类失败场景

### 1.1.1 多跳推理

```
问题："A 公司和 B 公司有什么关联？"

传统 RAG：
  检索到 A 公司的文档片段
  检索到 B 公司的文档片段
  → 但"关联"信息分散在多处，单块检索无法回答
```

答案需要 A → 中间实体 → B 的链路，单次检索只能命中链路一环。

### 1.1.2 全局总结

"整个知识库的主要主题是什么"这类问题没有对应的"某一块"，Top-K 检索天然无法覆盖全集。

### 1.1.3 关系查询

实体之间的"投资、合作、隶属"关系若未被显式建模，只能靠文本共现碰运气。

## 1.2 根因分析

| 局限 | 说明 |
|------|------|
| 多跳推理弱 | 需要跨文档串联信息 |
| 全局问题弱 | "整个知识库的主要主题是什么" |
| 关系丢失 | 实体间关系未被显式建模 |

本质：向量检索是"点对点相似度"，而上述问题需要"图上的路径"或"集合上的聚合"。

### 1.2.1 图论视角

```
向量检索 = 单点最近邻（1-hop）
多跳问题 = k-hop 可达性
全局问题 = 连通分量 / 社区聚合
```

把问题映射到图操作，即可判断 GraphRAG 是否必要。

## 1.3 何时需要 GraphRAG

只有当多跳与关系类问题确实重要、且普通 RAG 已被验证不够用时，才值得引入 GraphRAG。否则属于过度设计。

# 2. GraphRAG 思路

结论先行：GraphRAG 用知识图谱（Knowledge Graph）显式建模实体与关系，检索时沿图遍历，从而支持多跳与全局聚合。

## 2.1 知识图谱建模

**用知识图谱显式建模实体与关系**，检索时沿图遍历：

```
        ┌─────────┐
        │  A 公司  │
        └────┬────┘
             │ 投资
             ▼
        ┌─────────┐        ┌─────────┐
        │  B 公司  │──合作──│  C 公司  │
        └─────────┘        └─────────┘
```

节点是实体，边是关系，边可带属性（时间、金额、来源）。

## 2.2 索引与检索分离

GraphRAG 的"建索引"成本远高于传统 RAG：每块都要 LLM 抽取，社区还要摘要。因此把重成本放在离线索引阶段，在线检索尽量轻。

### 2.2.1 离线/在线成本分布

| 阶段 | 向量 RAG | GraphRAG |
|------|----------|----------|
| 离线 | 嵌入 | 嵌入 + 抽取 + 摘要 |
| 在线 | 相似度检索 | 图遍历/摘要聚合 |
| 增量 | 插入块 | 重抽取 + 图合并 |

## 2.3 与向量 RAG 的关系

| 维度 | 向量 RAG | GraphRAG |
|------|----------|----------|
| 索引单元 | 文本块 | 实体/关系/社区 |
| 检索方式 | 相似度 | 图遍历 + 摘要 |
| 擅长 | 事实问答 | 多跳/全局 |
| 成本 | 低 | 高 |

二者常组合：向量检索做入口，图谱做关系补全。

# 3. 构建流程

结论先行：GraphRAG 构建是一条五步流水线——分块、抽取三元组、建图归一化、社区检测摘要、双库存储。

## 3.1 五步流水线

```
① 文档 → 分块
② 每块用 LLM 抽取 (实体, 关系, 实体)
③ 合并去重 → 构建知识图谱
④ 社区检测 → 生成社区摘要（用于全局问题）
⑤ 存储：图数据库 + 向量库
```

## 3.2 实体关系抽取

### 3.2.1 提示词设计

```java
public record Triple(String subject, String relation, String object) {}

interface GraphExtractor {
    @UserMessage("""
            从文本中抽取实体与关系，输出 JSON：
            {"triples": [{"subject":"","relation":"","object":""}]}
            文本：{{it}}
            """)
    TripleList extract(String chunk);
}
```

提示词要点：固定输出 schema、限定实体类型、要求给出关系方向。

### 3.2.2 Java 示例

```java
public void buildGraph(List<Document> chunks, GraphStore g) {
    for (Document chunk : chunks) {
        TripleList triples = extractor.extract(chunk.getText());

        for (Triple t : triples.triples()) {
            g.mergeNode(t.subject(), chunk.getMetadata());
            g.mergeNode(t.object(), chunk.getMetadata());
            g.mergeEdge(t.subject(), t.relation(), t.object(), chunk.getId());
        }
    }
}
```

## 3.3 建图与归一化

| 步骤 | 说明 |
|------|------|
| 实体归一化 | 同义词/别名合并为同一节点 |
| 关系归一化 | 同义关系映射到统一谓词 |
| 去重 | 相同三元组只保留一条并合并来源 |
| 溯源 | 边记录来源 chunkId |

### 3.3.1 归一化示例

```java
public String normalize(String entity, Map<String, String> aliasTable) {
    String key = entity.trim().toLowerCase();
    return aliasTable.getOrDefault(key, entity.trim());
}
```

## 3.4 社区检测与摘要

用 Leiden / Louvain 等算法把图划分成社区，对每个社区生成摘要，用于回答全局问题。社区可分层，形成"宏观—中观—微观"的摘要层级。

## 3.5 边界与坑

- LLM 抽取有幻觉，可能生成不存在的实体或错误关系。
- 实体未归一化会导致图膨胀、同名不同节点。
- 社区检测对图规模敏感，超大图需分层或采样。

# 4. 检索方式

结论先行：局部检索沿实体邻域回答具体关系问题，全局检索用社区摘要回答整体问题，两者可按问题类型路由。

## 4.1 局部检索

### 4.1.1 流程

从查询中识别实体 → 图中找邻居 → 取相关子图与原文。

```
查询："A 公司和 B 公司的关系"
  → 识别实体 A公司、B公司
  → 图中找路径 A --投资--> B
  → 取相关文档片段
  → 生成回答
```

### 4.1.2 Java 示例

```java
public String localSearch(String query, int hops) {
    List<String> entities = entityLinker.link(query);
    SubGraph sub = graphStore.neighbors(entities, hops);
    List<String> contexts = sub.edges().stream()
            .flatMap(e -> graphStore.sourceChunks(e).stream())
            .distinct()
            .toList();
    return llm.generate(buildPrompt(query, contexts));
}
```

## 4.2 全局检索

用社区摘要回答"整体性"问题。

```
查询："这批文档的主要主题是什么？"
  → 取各社区摘要（预生成）
  → map-reduce 汇总
  → 生成回答
```

Map 阶段对每个社区摘要生成局部答案，Reduce 阶段合并为全局答案。

## 4.3 混合检索

| 问题类型 | 路由 |
|----------|------|
| 具体事实 | 向量 RAG |
| 实体关系 | 局部图检索 |
| 整体总结 | 全局社区检索 |
| 复杂多跳 | 局部 + 向量混合 |

### 4.3.1 路由判定逻辑

```java
public SearchMode route(String query) {
    if (isGlobal(query)) {
        return SearchMode.GLOBAL;
    }
    if (hasEntity(query)) {
        return SearchMode.LOCAL;
    }
    return SearchMode.VECTOR;
}
```

## 4.4 边界与坑

- 实体链接（Entity Linking）错误会直接导致检索偏航。
- 跳数（hops）过大导致子图爆炸、上下文超限。
- 社区摘要过期后全局答案失真，需随图更新重建。

# 5. 存储选型

结论先行：典型架构是"图数据库 + 向量库 + 关系库"三件套，各司其职。

## 5.1 组件对比

| 组件 | 选项 |
|------|------|
| 图数据库 | Neo4j、NebulaGraph、JanusGraph |
| 向量库 | 任意（存实体/社区摘要的向量） |
| 关系库 | 存抽取结果与溯源 |

> 常见架构：Neo4j（图）+ 向量库（语义检索）+ 关系库（元数据）。

### 5.1.1 图数据库选型矩阵

| 图库 | 查询语言 | 特点 |
|------|----------|------|
| Neo4j | Cypher | 生态成熟 |
| NebulaGraph | nGQL | 超大规模 |
| JanusGraph | Gremlin | 可插拔存储 |

## 5.2 图数据库建模

```
(:Entity {name, type, embedding})
  -[:REL {type, sourceChunkId, weight}]->
(:Entity)

(:Community {id, level, summary})
  -[:CONTAINS]-> (:Entity)
```

实体节点存向量以支持"语义 + 结构"混合检索。

## 5.3 生产建议

| 风险 | 建议 |
|------|------|
| 单库故障 | 图与向量库解耦，独立扩容 |
| 溯源缺失 | 每条边记录来源 chunkId |
| 版本混乱 | 图快照 + 版本号 |

# 6. 实现参考

结论先行：微软 GraphRAG 适合开箱即用的社区摘要路线，Neo4j + LangChain4j 适合自建可控路线。

## 6.1 开源方案

| 方案 | 说明 |
|------|------|
| Microsoft GraphRAG | 开源，社区检测 + 摘要 |
| Neo4j + LangChain4j | 自建图 + 向量混合检索 |
| LlamaIndex PropertyGraph | 属性图索引 |

### 6.1.1 与自建方案对比

| 维度 | Microsoft GraphRAG | 自建 |
|------|--------------------|------|
| 语言 | Python | 任意 |
| 可控性 | 低 | 高 |
| 上手速度 | 快 | 慢 |

## 6.2 Java 生态

Java 侧缺少像 Python 那样成熟的 GraphRAG 框架，通常做法是：

```
LangChain4j 调 LLM 抽取 → Neo4j Java Driver 建图
→ 向量库做实体/摘要检索 → 自写局部/全局检索
```

## 6.3 选型对比

| 需求 | 推荐 |
|------|------|
| 快速验证 | Microsoft GraphRAG |
| Java 技术栈 | Neo4j + LangChain4j 自建 |
| 已有图资产 | 复用现有图数据库 |

# 7. 适用与不适用

结论先行：GraphRAG 适用于关系密集、多跳、全局总结场景，不适合简单事实与高频变更场景。

## 7.1 适用场景

| 适用 | 说明 |
|------|------|
| 多跳推理问题 | 需跨实体串联 |
| 关系密集领域 | 企业、金融、医疗 |
| 全局性总结 | 主题归纳 |
| 知识长期沉淀 | 图谱持续增值 |

## 7.2 不适用场景

| 不适用 | 原因 |
|--------|------|
| 简单事实查询 | 向量 RAG 足够 |
| 单文档问答 | 无需图结构 |
| 实时性要求高 | 抽取与建图慢 |
| 数据频繁变更 | 增量维护复杂 |

> GraphRAG 构建与维护成本高，**只在多跳/关系类问题确实重要时才用**。

## 7.3 反例

- 反例一：客服 FAQ 全是独立问答，建图纯属浪费。
- 反例二：数据每天全量替换，图谱来不及稳定就被推翻。
- 反例三：问题只是"某产品的价格是多少"，一次向量检索即可。

# 8. 成本分析

结论先行：GraphRAG 的成本集中在 LLM 抽取与社区摘要两个环节，规模越大成本增长越快。

## 8.1 成本构成

| 环节 | 成本 |
|------|------|
| 实体抽取 | 每块一次 LLM 调用 |
| 社区摘要 | 每社区一次 LLM 调用 |
| 图存储 | 图数据库运维 |
| 更新 | 增量更新图较复杂 |

### 8.1.1 量级示例

```
1 万块文档 × 每块 800 Token = 800 万 Token 抽取
假设社区 500 个 × 每摘要 1500 Token = 75 万 Token 摘要
```

## 8.2 成本估算公式

```
抽取成本 ≈ 块数 × 单块 Token × 单价
摘要成本 ≈ 社区数 × 摘要 Token × 单价
总成本   ≈ 抽取成本 + 摘要成本 + 存储与运维
```

## 8.3 降本手段

| 手段 | 效果 |
|------|------|
| 小模型抽取 + 强模型校验 | 降低抽取成本 |
| 仅对高价值文档建图 | 控制规模 |
| 缓存社区摘要 | 避免重复生成 |
| 增量抽取 | 只处理新增块 |

# 9. 生产注意事项

结论先行：GraphRAG 落地的关键是抽取质量、图谱规模控制与增量更新策略。

## 9.1 风险清单

| 风险 | 建议 |
|------|------|
| 抽取质量差 | 用强模型 + 校验 |
| 图谱膨胀 | 实体归一化（同义词合并） |
| 更新困难 | 增量抽取 + 版本管理 |
| 成本失控 | 仅对高价值数据构建 |
| 过度设计 | 先验证普通 RAG 是否够用 |

## 9.2 质量校验

| 校验项 | 方法 |
|--------|------|
| 三元组合法性 | schema 校验 + 正则 |
| 实体一致性 | 别名表比对 |
| 关系方向 | 抽样人工复核 |
| 溯源完整 | 每条边必须有来源 |

### 9.2.1 schema 校验示例

```java
public boolean valid(Triple t) {
    return notBlank(t.subject())
            && notBlank(t.relation())
            && notBlank(t.object())
            && !t.subject().equals(t.object());
}
```

## 9.3 运维

- 图与向量库建立一致性校验任务。
- 社区摘要随图变更定期重建，标记版本。
- 上线前用小规模问题集对比"普通 RAG vs GraphRAG"的效果增益。

# 10. 小结

## 10.1 关键结论

- GraphRAG 用知识图谱解决多跳与全局问题。
- 流程：抽取三元组 → 建图 → 社区摘要 → 图检索。
- 局部检索处理实体关系，全局检索处理整体问题。
- 构建与维护成本高，按需使用。
- 先确认普通 RAG 不够用，再上 GraphRAG。

## 10.2 落地清单

```
1. 验证普通 RAG 在多跳/全局问题上的失败率
2. 定义实体与关系 schema
3. LLM 抽取 + 归一化建图
4. 社区检测并生成摘要
5. 局部/全局检索路由
6. 持续校验抽取质量与成本
```
