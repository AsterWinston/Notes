# 1. ANN 与精确搜索的本质权衡

结论先行：向量检索的核心矛盾是精度、速度、内存三者的三角权衡；ANN（Approximate Nearest Neighbor，近似最近邻）用可控的召回损失，换取数量级的速度提升与内存下降。

## 1.1 暴力搜索的复杂度

### 1.1.1 时间复杂度推导

精确最近邻（Exact Nearest Neighbor）需要把查询向量与库中全部 N 个向量逐一计算距离，向量维度为 D。

| 操作 | 复杂度 | 100 万 × 1024 维的直观含义 |
|------|--------|---------------------------|
| 单次距离计算 | O(N × D) | 约 10.24 亿次浮点乘加 |
| 单次结果排序 | O(N log N) | 约 2000 万次比较 |
| 建索引 | O(1)（无索引） | 无额外开销 |
| 内存占用 | O(N × D) | float32 约 4 GB |

即便单次乘加只需 1 纳秒，10 亿次运算也要 1 秒以上，无法满足在线检索毫秒级延迟的要求。

### 1.1.2 何时仍应选择 Flat

- 数据量小于 10 万，暴力扫描的延迟已在可接受范围。
- 对召回率要求 100%，例如合规检索、去重、聚类。
- 需要"精确的 Top-K 顺序"作为评测基准，用于校准 ANN 的召回。

## 1.2 ANN 的近似契约

### 1.2.1 召回率与延迟的帕累托前沿

ANN 不保证返回真正的 Top-K，而是返回"很可能在 Top-K 中"的结果。核心指标：

```
Recall@K = |ANN 返回结果 ∩ 真实 Top-K| / K
```

| 指标 | 含义 | 典型目标 |
|------|------|----------|
| Recall@K | 命中真实近邻的比例 | 0.90 ~ 0.99 |
| P99 延迟 | 99 分位查询耗时 | 10 ~ 100 ms |
| QPS | 每秒查询数 | 按业务定 |
| 内存占用 | 索引常驻内存 | 受机器约束 |

召回率与延迟构成帕累托前沿：调高搜索宽度，召回上升、延迟上升，需要在拐点处取舍。

### 1.2.2 距离度量与归一化

不同索引对度量（Metric）的支持不同，选错度量会导致召回崩塌。

| 度量 | 公式 | 适用 |
|------|------|------|
| 欧氏距离 L2 | sqrt(Σ(aᵢ-bᵢ)²) | 通用、图像 |
| 内积 IP | Σ aᵢbᵢ | 未归一化的推荐 |
| 余弦相似度 | IP / (‖a‖‖b‖) | 文本嵌入（最常用） |

直觉：当所有向量都做 L2 归一化后，余弦相似度等价于内积，内积与 L2 单调对应，三者可统一。**文本嵌入务必归一化**，否则距离被模长污染。

## 1.3 索引分类总览

ANN 索引可归为四大流派：

```
ANN 索引
├── 基于哈希      LSH（局部敏感哈希）
├── 基于树        KD-Tree、Ball-Tree（高维退化）
├── 基于量化      PQ、SQ、OPQ（压缩向量）
├── 基于图        HNSW、NSG、DiskANN（当前主流）
└── 基于聚类      IVF（倒排桶，常与量化组合）
```

## 1.4 本章边界与生产建议

| 风险 | 建议 |
|------|------|
| 度量选错 | 嵌入模型文档指定度量，勿凭感觉 |
| 未归一化 | 写入前统一 L2 归一化 |
| 只看平均延迟 | 关注 P99，长尾才是用户感知 |
| 无基线 | 先用 Flat 跑出真实 Top-K 作为召回基准 |

# 2. 主流索引对比

结论先行：没有"最好"的索引，只有"匹配数据规模、内存预算、写入频率"的索引；HNSW 是通用默认首选，量化用于内存受限，DiskANN 用于超大规模。

## 2.1 多维对比表

| 索引 | 原理 | 召回 | 速度 | 内存 | 是否训练 | 增量写入 |
|------|------|:----:|:----:|:----:|:--------:|:--------:|
| Flat | 暴力 | 100% | 慢 | 高 | 否 | 容易 |
| IVF | 聚类分桶 | 中高 | 快 | 中 | 是 | 较易 |
| HNSW | 分层图 | 高 | 很快 | 高 | 否 | 容易 |
| PQ | 乘积量化 | 中 | 快 | 很低 | 是 | 需重建码本 |
| IVF-PQ | 组合 | 中 | 快 | 低 | 是 | 较难 |
| SQ | 标量量化 | 高 | 快 | 低 | 否/轻 | 容易 |
| DiskANN | 磁盘图 | 高 | 中 | 低 | 是 | 较难 |

## 2.2 构建-查询生命周期

```
建索引阶段                    查询阶段
─────────────                ─────────────
① 采集向量                   ① 查询向量编码
② 训练（如需要）             ② 进入索引导航
③ 写入结构                   ③ 返回候选集
④ 落盘/入内存                ④ 距离精排 Top-K
```

关键区别：IVF / PQ 有"训练"阶段，训练后码本固定；HNSW 无训练，逐条插入即可，因此更适合频繁写入。

## 2.3 常见组合策略

| 组合 | 目的 | 典型场景 |
|------|------|----------|
| HNSW + SQ | 图索引省内存 | 千万级、内存有限 |
| IVF + PQ | 极省内存 | 亿级、可容忍召回下降 |
| IVF + HNSW | 先粗筛再精搜 | 超大规模分层检索 |
| HNSW + 重排 | 图召回 + 精确重排 | 高精度要求 |

## 2.4 选型反例

- 反例一：1000 条数据上 HNSW，收益为负，构建与内存开销反而不如 Flat。
- 反例二：频繁写入场景用 IVF-PQ，每次数据分布变化都要重训，运维爆炸。
- 反例三：追求 100% 召回却用 IVF，无论如何调参都达不到。

# 3. Flat（暴力搜索）

结论先行：Flat 是唯一 100% 精确的索引，是评测基线与小数据集的最优解，但不适合在线大规模检索。

## 3.1 原理与实现

```
查询向量 ──▶ 与所有向量逐一计算距离 ──▶ 排序取 Top-K
```

### 3.1.1 距离计算实现

```java
record Neighbor(int id, float distance) {}

public List<Neighbor> flatSearch(float[] query, float[][] database, int topK) {
    PriorityQueue<Neighbor> heap = new PriorityQueue<>(
            Comparator.comparingDouble(Neighbor::distance).reversed());
    for (int i = 0; i < database.length; i++) {
        heap.offer(new Neighbor(i, l2(query, database[i])));
        if (heap.size() > topK) {
            heap.poll();
        }
    }
    return new ArrayList<>(heap);
}

private float l2(float[] a, float[] b) {
    float sum = 0f;
    for (int i = 0; i < a.length; i++) {
        float d = a[i] - b[i];
        sum += d * d;
    }
    return sum;
}
```

### 3.1.2 SIMD 与批量化

现代向量库用 SIMD（Single Instruction Multiple Data，单指令多数据）与批处理加速暴力扫描：

| 技术 | 效果 |
|------|------|
| SIMD（AVX-512） | 单周期算 16 个 float |
| 多线程分片 | 按 CPU 核数切分库 |
| 内存预取 | 隐藏访存延迟 |

## 3.2 边界与坑

- 数据超过约 10 万后延迟急剧上升，需提前规划迁移。
- 高维（>512）下距离计算成本线性增长。
- 若只做离线评测，Flat 反而是最省心的选择。

## 3.3 生产建议

| 场景 | 建议 |
|------|------|
| 数据 < 10 万 | 直接用 Flat |
| 作为召回基准 | 定期用 Flat 抽样校准 ANN |
| 去重任务 | 用 Flat 保证不漏 |

# 4. IVF（倒排文件）

结论先行：IVF（Inverted File，倒排文件）用聚类把空间切成桶，查询只扫描少数桶，以"可能漏掉边界近邻"为代价换取大幅提速。

## 4.1 机制拆解

```
① 训练：用 K-means 把向量空间聚成 N 个簇
② 写入：每个向量归入最近的簇
③ 查询：只在最近的 nprobe 个簇里搜索
```

### 4.1.1 训练：K-means 聚类

```
        ▲
   ● ●  │  ● ●
  ●  C1 │ C2  ●        查询点 Q 在 C1 附近
   ● ●  │  ● ●        → 只搜 C1（和邻近簇）
  ──────┼──────▶       → 大幅减少计算量
        │
   ● ●  │  ● ●
  ●  C3 │ C4  ●
   ● ●  │  ● ●
```

K-means 目标函数（最小化簇内平方和）：

```
J = Σ_{i=1}^{nlist} Σ_{x ∈ Ci} ‖x - μi‖²
```

### 4.1.2 查询：nprobe 扫描

查询时计算 Q 到各簇中心距离，取最近 nprobe 个簇，仅在这些簇内做精确距离计算。

## 4.2 参数与公式

| 参数 | 含义 | 影响 |
|------|------|------|
| `nlist` | 簇数量 | 越多簇越细，单桶越小，召回与速度平衡点变化 |
| `nprobe` | 查询搜索的簇数 | 越大越准、越慢 |

经验公式：`nlist ≈ 4 × √N`，`nprobe` 取 `nlist` 的 1% ~ 10%。

扫描比例直觉：

```
实际扫描向量数 ≈ N × (nprobe / nlist)
```

## 4.3 Java 示例

```java
public class IvfIndex {
    private final List<float[]> centroids;
    private final List<List<float[]>> buckets;

    public List<float[]> search(float[] query, int nprobe, int topK) {
        int[] nearest = nearestCentroids(query, nprobe);
        List<float[]> candidates = new ArrayList<>();
        for (int c : nearest) {
            candidates.addAll(buckets.get(c));
        }
        return exactTopK(query, candidates, topK);
    }
}
```

## 4.4 边界与坑

- 数据分布变化后旧簇中心失效，需定期重训。
- 边界向量可能被分到错误簇，nprobe 太小时直接漏召回。
- 删除操作会留下空洞，需定期重建。

## 4.5 生产建议

| 风险 | 建议 |
|------|------|
| 训练数据不足 | 至少 256 × nlist 条样本 |
| nprobe 太小 | 从 nlist 的 1% 起调，监控召回 |
| 分布漂移 | 设定重训周期或触发条件 |

# 5. HNSW（分层可导航小世界图）

结论先行：HNSW（Hierarchical Navigable Small World，分层可导航小世界图）是当前最主流的索引，用多层图结构实现对数级查询复杂度，Milvus / Qdrant / PGVector / Elasticsearch 均支持。

## 5.1 机制拆解

```
Layer 2:   A ──────────────── B         （稀疏，快速跳转）
Layer 1:   A ──── C ──── D ──── B        （中等密度）
Layer 0:   A─E─C─F─D─G─H─B─I             （最密，精确搜索）
```

### 5.1.1 插入与邻居选择

新节点以指数衰减概率被分配到高层，逐层向下插入，每层用启发式选择 M 个邻居，兼顾"近"与"多样"，避免邻居全部挤在同一方向。

### 5.1.2 贪心搜索与逐层下降

查询从顶层入口点开始，在当前层贪心移动到更近的邻居，无法更近则下降一层，最终在 Layer 0 做宽度为 efSearch 的局部搜索。

## 5.2 参数与公式

| 参数 | 含义 | 影响 |
|------|------|------|
| `M` | 每节点最大连接数 | 越大越准、内存越多（常用 16 ~ 64） |
| `efConstruction` | 建索引时的搜索宽度 | 越大索引质量越好、建得越慢（常用 100 ~ 500） |
| `efSearch` | 查询时的搜索宽度 | 越大越准、越慢（常用 50 ~ 200） |

```
召回率 ↑  ←  efSearch ↑  →  延迟 ↑
```

## 5.3 Java 示例

```java
public void buildHnsw(List<float[]> vectors, HnswParams params) {
    for (int i = 0; i < vectors.size(); i++) {
        hnswIndex.insert(vectors.get(i), i, params);
    }
}

public List<Integer> search(float[] query, int efSearch, int topK) {
    hnswIndex.setEfSearch(efSearch);
    return hnswIndex.searchKnn(query, topK);
}
```

## 5.4 边界与坑

- `M` 过大导致内存暴涨，且边际收益递减。
- 高维数据图结构退化，需配合量化或降维。
- 大量删除后图连通性受损，召回下降。
- 并发写入需加锁，吞吐低于只读场景。

## 5.5 生产建议

| 风险 | 建议 |
|------|------|
| 参数拍脑袋 | 用标注查询集调 efSearch |
| 内存不足 | M 取 16 ~ 32，配合 SQ |
| 删除频繁 | 定期重建或做逻辑删除 + 合并 |

# 6. PQ（乘积量化）

结论先行：PQ（Product Quantization，乘积量化）把高维向量切成子空间分别聚类编码，将内存压缩数十到数百倍，代价是明显的精度损失。

## 6.1 机制拆解

```
原始向量（1024 维 float32 = 4KB）
      │ 切成 8 段，每段 128 维
      ▼
每段用聚类中心的 ID 表示（1 字节）
      ▼
压缩后 8 字节（压缩 512 倍）
```

### 6.1.1 子空间切分与码本

每个子空间独立跑 K-means 得到 256 个中心（1 字节可索引），形成码本（Codebook）。向量被表示为各子空间中心 ID 的拼接。

### 6.1.2 非对称距离计算

查询向量不编码，与数据库向量的每个子空间中心预计算距离表（ADC，Asymmetric Distance Computation），查询时查表求和，避免全维运算。

```
d(q, x) ≈ Σ_{m=1}^{M} d(q_m, c_{m, id_m})
```

## 6.2 内存与误差公式

| 项 | 公式 |
|----|------|
| 原始内存 | N × D × 4 字节 |
| PQ 内存 | N × M 字节（M 为子空间数） |
| 压缩比 | (D × 4) / M |

误差随 M 增大而减小，但码本训练成本随 M 上升。

## 6.3 边界与坑

- 精度损失明显，通常需配合重排（用原始向量重算 Top-N）。
- 码本依赖训练数据分布，分布漂移后需重训。
- 单独使用 PQ 召回偏低，常与 IVF 组合为 IVF-PQ。

# 7. 标量量化（SQ / Int8）

结论先行：SQ（Scalar Quantization，标量量化）把每个 float32 分量线性映射为 int8，内存降到 25%，精度损失小，是性价比最高的优化之一。

## 7.1 机制

```
float32 (4 字节) → int8 (1 字节)，内存降至 25%
```

线性映射公式：

```
q = round((x - min) / (max - min) × 255)
```

Qdrant、Elasticsearch 均支持 SQ，可作为 HNSW 的内存优化层。

## 7.2 边界与坑

- 极值（min/max）受离群点影响，宜用分位数裁剪。
- 量化后距离有偏，需用对称距离计算减少误差。
- 对精度极敏感场景，量化仅用于粗筛、再重排。

## 7.3 生产建议

| 场景 | 建议 |
|------|------|
| 内存紧张 | HNSW + SQ |
| 精度优先 | SQ 仅做粗筛 + 原向量重排 |
| 数据分布稳定 | 固定量化区间，避免频繁重算 |

# 8. DiskANN

结论先行：DiskANN 把图索引主体放磁盘，内存只保留少量缓存与压缩向量，用 SSD 随机读换取内存占用的大幅下降。

## 8.1 机制

```
内存：PQ 压缩向量（导航用）
磁盘：完整图结构 + 原始向量
查询：内存导航 → SSD 按需读节点 → 重排
```

## 8.2 边界与坑

- 强依赖 SSD 随机读性能，机械盘不可用。
- 磁盘 IO 成为瓶颈，P99 延迟高于纯内存方案。
- 增量更新复杂，常采用批式重建。

## 8.3 生产建议

| 场景 | 建议 |
|------|------|
| 亿级 + 内存受限 | DiskANN |
| 延迟极敏感 | 纯内存 HNSW |
| 读多写少 | 批量重建 + 只读服务 |

# 9. 参数调优方法

结论先行：参数调优的唯一正确方法是"用标注查询集测召回与延迟曲线"，而非凭经验拍数字。

## 9.1 调优流程

```
目标：在满足延迟要求下，最大化召回率

步骤：
1. 准备带标注的查询集（query → 正确文档）
2. 固定数据，调整参数，测 Recall@K 与 P99 延迟
3. 画"召回-延迟"曲线，选拐点
```

## 9.2 Java 示例

```java
public void tuneHnsw(int[] efSearchValues) {
    for (int ef : efSearchValues) {
        setEfSearch(ef);
        double recall = measureRecall(testQueries, 10);
        long p99 = measureP99Latency(testQueries);
        log.info("ef={} recall={} p99={}ms", ef, recall, p99);
    }
}
```

## 9.3 边界与坑

- 标注集太小，召回估计方差大，结论不可靠。
- 只测平均延迟会掩盖长尾。
- 训练/查询数据分布不一致，调参结果无法迁移。

## 9.4 生产建议

| 风险 | 建议 |
|------|------|
| 标注集过小 | 至少数百条查询，覆盖各类问题 |
| 忽略长尾 | 以 P95 / P99 为准 |
| 一次性调参 | 建立定期回归评测 |

# 10. 选型建议

结论先行：先按数据规模缩小候选，再按内存与写入约束定案，最后用评测验证。

## 10.1 按规模选型

| 数据规模 | 推荐索引 |
|----------|----------|
| < 10 万 | Flat / HNSW |
| 10 万 ~ 100 万 | HNSW |
| 100 万 ~ 1000 万 | HNSW（+ 量化） |
| > 1000 万 | IVF-PQ / DiskANN / HNSW + 量化 |

## 10.2 按约束选型

| 约束 | 选择 |
|------|------|
| 内存充足、要高性能 | HNSW |
| 内存受限 | IVF-PQ / SQ / DiskANN |
| 要求 100% 精确 | Flat |
| 写入频繁 | HNSW（无需重训） |

## 10.3 决策树

```
开始
 ├─ 数据 < 10 万？ ──是──▶ Flat
 ├─ 需要 100% 召回？ ──是──▶ Flat / 精确重排
 ├─ 内存充足？ ──是──▶ HNSW（+ SQ）
 └─ 亿级且内存受限？ ──是──▶ IVF-PQ / DiskANN
```

# 11. 生产注意事项

结论先行：索引上线只是开始，持续监控召回率、内存与重建周期才是长期稳定的关键。

## 11.1 风险清单

| 风险 | 建议 |
|------|------|
| 参数拍脑袋 | 用标注数据调优 |
| 索引未建 | 数据量上来前建索引 |
| 内存估算不足 | HNSW 内存 ≈ 向量大小 × (1 + M 开销) |
| 频繁重建 | 增量更新，避免全量重训 |
| 召回率不监控 | 上线后持续监控召回 |

## 11.2 监控指标

| 指标 | 含义 | 告警阈值示例 |
|------|------|--------------|
| Recall@K | 召回率 | 低于 0.9 告警 |
| P99 延迟 | 长尾延迟 | 超过 SLO 告警 |
| 索引大小 | 内存/磁盘占用 | 接近容量上限 |
| 删除比例 | 逻辑删除占比 | 超过 20% 触发重建 |

## 11.3 运维

- 建立索引重建的触发条件（删除比例、分布漂移）。
- 保留 Flat 基线的抽样校准任务。
- 灰度切换新索引，对比召回后再全量。

# 12. 小结

## 12.1 关键结论

- ANN 用少量精度损失换取数量级速度提升。
- HNSW 是当前主流，参数 `M` / `efConstruction` / `efSearch` 决定精度与性能。
- IVF 需训练，参数 `nlist` / `nprobe` 控制召回。
- PQ / SQ 用于降低内存，DiskANN 用于超大规模。
- 参数必须用标注数据调优，并持续监控召回率。

## 12.2 选型口诀

```
小数据用 Flat，通用选 HNSW；
内存不够加量化，亿级规模上磁盘；
度量归一化，参数靠评测。
```
