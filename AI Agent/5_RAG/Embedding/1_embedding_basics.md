# 1. 什么是 Embedding

Embedding（嵌入，又称向量化）是把文本映射到高维向量空间中的一个点，使语义相近的文本在该空间中距离更近。它是 RAG 能"按语义检索"而非"按关键词匹配"的根本原因。

## 1.1 定义与直觉

结论先行：Embedding 是一张"语义坐标表"，把离散文本变成连续向量，使"距离"可以度量"语义相似度"。

### 1.1.1 从关键词匹配到语义匹配

传统检索依赖词面匹配：查询"如何报销差旅费"无法命中文档"差旅费用怎么报"，因为二者几乎没有共同词。BM25 等词频算法虽然做了词权重优化，但本质上仍受限于词面。

Embedding 把两段文本编码到同一空间，即使没有共同词，只要语义相近，向量就接近。这种能力的来源是模型在海量语料上的对比学习：训练目标让语义相近的样本在向量空间靠拢，语义无关的样本被推开。因此向量空间天然带有"语义拓扑"。

### 1.1.2 一个最小示例

```text
"如何报销差旅费"  -> [0.12, -0.34, 0.56, ...]  (1536 维)
"差旅费用怎么报"  -> [0.11, -0.32, 0.58, ...]  <- 距离很近
"今天天气不错"    -> [-0.78, 0.21, -0.05, ...] <- 距离很远
```

Java 调用示意（Spring AI 风格）：

```java
EmbeddingModel model = ...;

Embedding embedding = model.embed("如何报销差旅费").content();
float[] vector = embedding.getOutput();

System.out.println("维度 = " + vector.length);
```

> 说明：不同版本 Spring AI 的取值方法名可能不同（`getOutput()` 或 `output()`），LangChain4j 为 `content().vector()`，以实际版本为准。

## 1.2 Embedding 在 RAG 中的位置

结论先行：Embedding 同时出现在 RAG 的离线索引与在线检索两条链路，两条链路必须使用同一模型、同一维度、同一归一化方式。

### 1.2.1 离线索引阶段

```text
原始文档 -> 切分(chunk) -> 向量化(embed) -> 写入向量库
```

离线阶段对每个 chunk 生成向量并落库。此阶段的成本与文档总量成正比，是向量化开销的主体。

```java
// 伪代码：离线索引
List<Document> docs = loader.load();
List<TextSegment> chunks = splitter.split(docs);

List<Embedding> vectors = embeddingModel.embedAll(chunks).content();
for (int i = 0; i < chunks.size(); i++) {
    vectorStore.add(List.of(new Embedding(chunks.get(i), vectors.get(i))));
}
```

### 1.2.2 在线检索阶段

```text
用户问题 -> 向量化(embed) -> 向量库近邻搜索 -> 返回 Top-K 片段
```

在线阶段只对查询生成一次向量，成本极低，但对延迟敏感，通常要求毫秒级。

两条链路的一致性，是检索正确性的前提：若索引用的模型 A，检索用模型 B，则相似度计算毫无意义。

### 1.2.3 与关键词检索的关系

Embedding 检索（稠密检索）擅长语义，但可能漏掉精确术语、编号、人名。生产系统常把它与 BM25（稀疏检索）混合，再用 RRF（Reciprocal Rank Fusion，倒数排名融合）合并结果。

## 1.3 常见误解与边界

| 误解 | 事实 |
|------|------|
| Embedding 能理解文本 | 它只输出坐标，不生成答案 |
| 维度越高越好 | 维度高表达力强但成本高，需权衡 |
| 相似度可直接当概率 | 相似度只是相对排序依据 |
| 换模型影响不大 | 换模型即全部向量失效 |
| 相似一定语义相同 | 存在多义词、否定句等反例 |

边界总结：Embedding 是"相对"工具，它给出的是排序依据，而不是绝对的真假判断。

# 2. 向量空间的性质

结论先行：向量空间的核心性质是"语义相近则距离小，语义无关则距离大"，但该性质有边界，不能无限外推。

## 2.1 语义相近即距离相近

```text
       ^ 维度2
       |      * 差旅报销
       |    * 费用报销
       |  * 报销流程
       |
       |                    * 天气预报
       |              * 今日天气
       +--------------------------> 维度1
```

- 语义相近 -> 向量距离小；
- 语义无关 -> 向量距离大；
- 向量维度通常为 384 / 768 / 1024 / 1536 / 3072。

这一性质是近邻搜索（ANN，Approximate Nearest Neighbor，近似最近邻）成立的基础：只要"语义近"能近似为"几何近"，就可以用向量索引加速检索。

### 2.1.1 流形假设

模型把文本映射到一个低维流形上，真实语料不会均匀充满整个高维空间，而是聚集在若干"语义簇"附近。这解释了为什么近邻搜索有效。

### 2.1.2 各向异性

实测中，模型输出的向量常集中在某个狭窄锥形区域内，称为各向异性（anisotropy）。这会导致任意两段无关文本的余弦相似度也偏高（如 0.3~0.5），因此阈值不能凭直觉取 0。

## 2.2 维度规模与选择

### 2.2.1 常见维度

| 维度 | 典型模型 | 说明 |
|------|----------|------|
| 384 | bge-small | 轻量，边缘部署友好 |
| 768 | bge-base | 均衡 |
| 1024 | bge-large / bge-m3 | 中文常用 |
| 1536 | text-embedding-3-small | OpenAI 默认 |
| 3072 | text-embedding-3-large | 高表达力 |

### 2.2.2 维度对表达力的影响

维度越高，可编码的语义差异越细，越能区分近义、上下位等微妙关系；但并非线性增益，超过一定维度后边际收益递减，而存储与检索成本线性增长。

## 2.3 边界与反例

- 多义词：同一个词在不同语境可能被编码到相近位置，导致误召回。
- 否定句："推荐使用 A"与"不推荐使用 A"在向量空间可能非常接近。
- 数值与时效："2023 年财报"与"2024 年财报"可能高度相似，但语义指向不同。
- 跨语言：多语言模型可对齐，单语模型无法跨语言检索。
- 长文本：超出模型上下文长度的部分会被截断，导致信息丢失。

## 2.4 生产建议

对领域语料抽样，计算"随机无关对"的相似度基线，作为后续阈值的参考下限。

# 3. 归一化

结论先行：归一化把向量长度统一为 1，使点积等于余弦相似度，从而简化计算并消除长度偏差。

## 3.1 为什么需要归一化

```text
未归一化：向量长度不同，点积受长度影响
归一化后：所有向量长度为 1，点积 = 余弦相似度
```

若向量长度不等，点积会偏爱"长向量"，而长度往往与文本长度相关，从而引入与语义无关的偏置。归一化后所有向量落在单位球面上，点积只反映方向（即语义）。

### 3.1.1 几何直觉

```text
单位圆上的点，夹角越小越相似

        * a
       /
      /  theta
     +----------* b

cos(theta) = a . b   （当 |a| = |b| = 1）
```

### 3.1.2 归一化与度量选择

归一化之后，余弦相似度、点积、欧氏距离三者单调对应，可以自由选择计算最快的一种（通常是点积）。

## 3.2 Java 实现

### 3.2.1 基础实现

```java
public float[] normalize(float[] v) {
    double norm = 0;
    for (float x : v) {
        norm += x * x;
    }
    norm = Math.sqrt(norm);

    float[] result = new float[v.length];
    for (int i = 0; i < v.length; i++) {
        result[i] = (float) (v[i] / norm);
    }
    return result;
}
```

### 3.2.2 数值稳定性

当 `norm` 接近 0（零向量）时应提前返回，避免除零得到 `NaN` / `Infinity`：

```java
if (norm < 1e-12) {
    return new float[v.length];
}
```

使用 `double` 累加可降低大维度下的浮点误差。

## 3.3 边界与坑

| 坑 | 后果 | 避免 |
|----|------|------|
| 零向量 | NaN / Infinity | 判空 |
| 重复归一化 | 无害但浪费算力 | 只做一次 |
| 只归一化部分维度 | 结果错误 | 全维度处理 |
| 索引归一化、查询不归一化 | 度量不一致 | 两侧统一 |
| 用 float 累加 | 大维度误差 | 用 double |

## 3.4 生产建议

多数 Embedding 模型输出已归一化，使用前请确认；若不确定，统一在入库与检索两侧都归一化，保证对称。

# 4. 维度的影响与成本

结论先行：维度直接决定存储与检索成本，需要在表达力与成本之间权衡；大规模场景可用降维或量化降低开销。

## 4.1 维度与存储估算

| 维度 | 优点 | 缺点 |
|------|------|------|
| 低（384/512） | 存储省、检索快 | 表达力弱 |
| 中（768/1024） | 平衡 | — |
| 高（1536/3072） | 表达力强、更准 | 存储与检索成本高 |

存储估算：

```text
1536 维 x 4 字节(float) = 6KB / 向量
100 万向量 ≈ 6GB（不含索引开销）
```

## 4.2 降维与量化

### 4.2.1 Matryoshka 降维

Matryoshka（套娃）表示学习让模型输出的前 N 维本身即构成有效的低维向量，可直接截断使用，无需重新训练。

```java
// OpenAI v3 支持在请求时指定维度
OpenAiEmbeddingOptions.builder()
        .model("text-embedding-3-large")
        .dimensions(1024)   // 从 3072 降到 1024
        .build();
```

### 4.2.2 量化（PQ / SQ）

```text
float32        基准
int8 (SQ)      约 4 倍压缩，精度损失小
PQ             约 8~32 倍压缩，精度损失较大
```

标量量化（SQ，Scalar Quantization）对每一维独立分桶；乘积量化（PQ，Product Quantization）把向量切成子空间分别编码。

```java
// 伪代码：量化后需使用对应的距离近似
byte[] quantized = pq.encode(vector);
float approx = pq.distance(query, quantized);
```

## 4.3 边界与坑

- 降维会损失部分精度，必须重新评测，不能沿用高维阈值。
- 量化后距离计算方式可能改变，需与索引配置一致。
- 降维与量化叠加时误差会累积。

## 4.4 生产建议

> 大规模场景可用降维（Matryoshka 模型）或量化（PQ/SQ）降低存储。

优先在模型侧降维（效果可控），必要时再叠加量化；两者都必须跑检索评测。

# 5. 对称与非对称检索

结论先行：RAG 属于非对称检索，查询短、文档长，二者分布不同，因此许多模型要求对查询与文档分别加前缀。

## 5.1 对称 vs 非对称

| 类型 | 说明 | 例子 |
|------|------|------|
| 对称 | 两段文本地位对等 | 句子相似度、去重 |
| 非对称 | 查询短、文档长 | RAG 检索、问答 |

对称任务中两段文本用同一种编码方式；非对称任务中查询与文档分布差异大，模型需要区分编码。

## 5.2 前缀策略

### 5.2.1 E5 前缀

```java
String queryText = "query: " + question;
String docText = "passage: " + document;
```

### 5.2.2 BGE 指令前缀

```java
// BGE（中文）：查询需加指令前缀，文档不加
String query = "为这个句子生成表示以用于检索相关文章：" + question;
String doc = document;
```

### 5.2.3 封装示例

```java
public class PrefixPolicy {

    public String forQuery(String model, String text) {
        if (model.startsWith("e5")) {
            return "query: " + text;
        }
        if (model.startsWith("bge")) {
            return "为这个句子生成表示以用于检索相关文章：" + text;
        }
        return text;
    }

    public String forDocument(String model, String text) {
        if (model.startsWith("e5")) {
            return "passage: " + text;
        }
        return text;
    }
}
```

## 5.3 边界与坑

- 必须按模型要求加前缀，否则效果下降；
- 文档通常不加前缀，只有查询加，反过来会降低效果；
- 前缀属于模型契约的一部分，换模型必须同步更换前缀逻辑。

## 5.4 生产建议

把前缀逻辑封装在查询 / 文档两条独立方法中，避免混用；在配置中声明模型所需前缀，便于统一维护。

# 6. 向量化的批量与缓存

结论先行：批量调用降低网络往返，内容哈希缓存避免重复向量化，二者是成本控制的主要手段。

## 6.1 批量向量化

```java
// 批量向量化（降低调用次数）
List<Embedding> embeddings = embeddingModel.embedAll(segments).content();
```

批量大小需权衡：过大可能触发 API 限制或超时，过小则往返开销高。常见区间为 16~128。

## 6.2 缓存与去重

### 6.2.1 内容哈希缓存

```java
public Embedding embedWithCache(String text) {
    String hash = sha256(text);
    Embedding cached = cache.get(hash);
    if (cached != null) {
        return cached;
    }

    Embedding embedding = embeddingModel.embed(text).content();
    cache.put(hash, embedding);
    return embedding;
}
```

### 6.2.2 增量更新

```text
文档变更 -> 只对变更 chunk 重新向量化 -> upsert 到向量库
```

增量更新避免了全量重算，是长文档知识库的必备能力。

### 6.2.3 去重

在向量化前对 chunk 做规范化（去空白、统一大小写）再哈希，可消除大量重复片段。

## 6.3 边界与坑

- 缓存需设置淘汰策略（如 LRU + TTL），避免内存膨胀；
- 缓存键必须包含模型版本与维度，换模型后旧缓存必须失效；
- 去重应基于规范化后的文本。

## 6.4 生产建议

> 增量更新时，缓存能大幅降低向量化成本。

# 7. 向量化的成本

结论先行：成本由文本量、模型规格、重复度与重建频率共同决定，换模型会触发全量重算，是最贵的一次操作。

## 7.1 成本构成

| 因素 | 影响 |
|------|------|
| 文本量 | 按 Token 计费 |
| 模型 | large 比 small 贵 |
| 重复 | 去重 + 缓存可省 |
| 重新索引 | 换模型需全量重算 |

## 7.2 成本优化

```text
去重 -> 批量 -> 缓存 -> 本地模型 -> 降维
```

按优先级：先去重（零成本），再批量（减少往返），再缓存（避免重复），最后才考虑本地模型与降维。

## 7.3 边界与坑

本地模型零边际成本，但需要 GPU 与运维投入；当语料规模小时，本地部署的固定成本可能高于按量计费。

## 7.4 生产建议

> 一个 100 万页的知识库，向量化成本可能达数千元，换模型前务必评估。

把成本纳入变更评审：任何换模型提案都应附带成本估算与评测报告。

# 8. 向量质量的可视化与验证

结论先行：上线前必须验证向量质量，最简方式是同类 / 异类相似度对比，系统方式是用标注数据计算排序相关性或检索指标。

## 8.1 快速验证

```java
// 简单验证：同类文本相似度应显著高于异类
double same = cosine(embed("如何报销"), embed("报销流程"));
double diff = cosine(embed("如何报销"), embed("天气预报"));

assert same > diff : "向量质量异常";
```

### 8.1.1 分布观察

把同类与异类的相似度画成直方图，观察两条分布是否可分；若大量重叠，说明模型或前缀有问题。

```text
同类   |####  ####
异类        |  ####  ####
            +----------------> 相似度
```

## 8.2 系统评估

### 8.2.1 Spearman 相关性

用标注的相似句对，计算预测相似度与人工打分的 Spearman（斯皮尔曼）秩相关，衡量排序一致性。

```java
// 伪代码
double rho = spearman(predictedScores, humanScores);
```

### 8.2.2 Recall@K

用检索评测间接衡量：相关文档是否出现在 Top-K 中，反映端到端检索质量。

```java
// 伪代码
double recall = relevantHit / relevantTotal;
```

## 8.3 边界与坑

单句对比只能做冒烟测试，不能代表整体质量；必须覆盖领域语料，且评测集应避免与训练数据重叠。

## 8.4 生产建议

建立固定的评测集与回归流程，每次换模型或调参后重跑，记录指标变化。

### 8.4.1 可视化手段

| 手段 | 用途 |
|------|------|
| 相似度直方图 | 观察分布可分性 |
| t-SNE / UMAP | 观察语义簇 |
| 近邻示例表 | 人工抽查召回质量 |
| 分数分布随 K 变化 | 辅助定阈值 |

# 9. 生产注意事项

结论先行：Embedding 是"一次性决策"，模型、维度、归一化、前缀一旦确定就难以更改，需在建库前统一。

## 9.1 风险清单

| 风险 | 建议 |
|------|------|
| 模型与维度不匹配 | 建库前确定，换模型需重建 |
| 未加前缀 | 按模型文档加 query/passage 前缀 |
| 重复向量化 | 内容哈希缓存 |
| 成本失控 | 去重 + 批量 + 本地模型 |
| 维度误解 | 存储与检索成本按维度估算 |
| 模型漂移 | 升级需全量重建 + 评测 |

## 9.2 上线检查表

```text
[ ] 模型与维度已固定
[ ] 前缀策略已封装
[ ] 归一化已确认
[ ] 评测集与基线已建立
[ ] 缓存与去重已启用
[ ] 模型版本已写入元数据
```

## 9.3 监控与告警

监控向量化 QPS、失败率、缓存命中率与检索命中率；当缓存命中率骤降或失败率上升时告警，往往预示上游文本或配置变更。

### 9.3.1 关键指标

| 指标 | 含义 | 异常信号 |
|------|------|----------|
| 向量化 QPS | 吞吐 | 骤降可能是限流 |
| 失败率 | 稳定性 | 上升需排查 |
| 缓存命中率 | 成本效率 | 骤降说明文本变更 |
| 检索命中率 | 质量 | 下降需重评模型 |

# 10. 小结

结论先行：Embedding 是语义检索的基础，其核心决策（模型、维度、前缀、归一化）需在系统设计早期确定。

## 10.1 核心要点

- Embedding 把语义映射到向量空间，是语义检索的基础。
- RAG 是非对称检索，注意查询 / 文档前缀。
- 维度影响表达力与成本，需权衡。
- 批量 + 缓存能显著降低向量化成本。
- Embedding 模型是"一次性决策"，更换代价高。
