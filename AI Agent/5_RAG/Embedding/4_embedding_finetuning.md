# 1. 什么时候需要微调

**结论先行**：微调（Fine-tuning，微调）是检索效果优化链路的**最后手段**。在动它之前，先穷尽前缀（prefix）、分块（chunking）、度量（metric）、阈值（threshold）、混合检索与重排等更便宜的杠杆；只有当领域差异大到通用模型"根本听不懂"时，微调才值得投入。

## 1.1 微调的定位与决策顺序

### 1.1.1 决策流程图

```
通用 Embedding 效果不佳
        │
        ├── 先排查：前缀、分块、度量、阈值 → 多数问题在此解决
        │
        ├── 再尝试：换更强模型、混合检索、重排、查询改写
        │
        └── 仍不佳 → 领域差异大（专业术语、内部黑话）→ 微调
```

### 1.1.2 为什么微调排最后

微调的成本曲线是非线性的：数据构造、算力、训练、导出、部署、版本管理、重新索引，任何一环都要持续投入。而前面那些手段多数是"配置级"改动，几分钟到几天就能验证。用最小成本换取最大收益，是工程上的基本纪律。

| 优化手段 | 典型成本 | 见效速度 |
|----------|----------|----------|
| 调阈值 / topK | 分钟级 | 快 |
| 分块策略调整 | 小时级 | 中 |
| 换更强模型 | 天级 | 中 |
| 混合检索 + 重排 | 天级 | 中 |
| 领域微调 | 周级 | 慢 |

### 1.1.3 边界与坑

- 若召回率低是**分块切断了语义**造成的，微调无法修复。
- 若问题出在**查询与文档用词不一致**，微调可能有用，但查询改写更便宜。
- 若只是**阈值设得太高**导致召回少，微调是南辕北辙。

## 1.2 需要微调的信号

### 1.2.1 定性信号

| 信号 | 说明 |
|------|------|
| 专业术语检索不准 | 通用模型不认识领域词汇 |
| 同义改写召回差 | 领域表达方式特殊 |
| 通用模型分数区分度低 | 相关/不相关分数接近 |

### 1.2.2 定量信号

用标注集算基线，若出现以下情况，微调收益通常明显：

| 指标 | 现象 | 含义 |
|------|------|------|
| Recall@10 | 明显低于人工上限 | 根本没召回 |
| MRR | 相关文档排名靠后 | 排序能力弱 |
| 分数分布 | 正负样本重叠严重 | 表示空间不可分 |

> **微调是最后手段**，先穷尽提示、分块、重排等手段。

## 1.3 生产建议

| 建议 | 理由 |
|------|------|
| 先建立评测集 | 没有基线无法判断微调是否有用 |
| 记录每一步实验 | 便于回滚与对比 |
| 设置收益门槛 | 例如 Recall@10 提升 <3% 不上线 |

# 2. 微调原理：对比学习

**结论先行**：Embedding 微调的本质是**对比学习（Contrastive Learning，对比学习）**——让语义相近的文本在向量空间里靠得更近，语义无关的推得更远。

## 2.1 核心直觉

### 2.1.1 正负样本对

```
正样本对（语义相近）→ 拉近向量距离
负样本对（语义无关）→ 推远向量距离
```

### 2.1.2 几何直觉

```
       ▲
       │   ●查询  ○正样本   （拉近）
       │
       │            △负样本  （推远）
       └──────────────────────▶
```

模型把"查询—正例"当作引力，"查询—负例"当作斥力，在数千个批（batch）里反复调整，最终形成一个"领域语义地图"。这个过程不改变模型结构，只重塑向量空间里的相对位置。

## 2.2 常用损失函数

| 损失 | 说明 |
|------|------|
| MultipleNegativesRankingLoss | 句对训练，批内其他样本作负例 |
| TripletLoss | (锚点, 正例, 负例) 三元组 |
| ContrastiveLoss | 通用对比损失 |

### 2.2.1 MultipleNegativesRankingLoss（批内负样本）

只需正样本对 (query, doc)，同批其他 doc 自动成为负例。批越大，负例越多，效果通常越好。其目标函数近似 InfoNCE：

```
L = -log( exp(sim(q, d+) / τ)
          ───────────────────────────── )
          Σ_j exp(sim(q, d_j) / τ)
```

其中 `d_j` 遍历批内所有文档，`τ` 为温度。

### 2.2.2 TripletLoss（三元组）

需要显式构造 (anchor, positive, negative)。适合已有难负样本的场景，但数据构造成本高。

### 2.2.3 ContrastiveLoss（通用对比）

对正负样本对分别计算，适合二分类式的相似度任务，但不如前两者在检索场景直接。

## 2.3 温度与批大小

多数实现用带温度（temperature）的 softmax：`exp(sim/τ)`。温度越低，模型对难负样本越敏感；批越大，批内负例越多。二者共同决定训练难度：太简单学不到东西，太难梯度不稳。

## 2.4 生产建议

| 建议 | 理由 |
|------|------|
| 优先用 MNRL | 数据要求低、效果好 |
| 批大小尽量大 | 负例更多，梯度更稳 |
| 监控损失曲线 | 突降可能是坍缩 |

# 3. 训练数据构造

**结论先行**：微调效果的上限由**数据质量**决定，而非模型或超参。三类来源中，真实业务数据最优，LLM 生成最便宜，人工标注最贵。

## 3.1 三种数据来源

| 来源 | 说明 | 质量 |
|------|------|------|
| 真实业务数据 | 用户查询 + 点击/采纳的文档 | 最高 |
| 人工标注 | 人工构造查询-文档对 | 高，成本高 |
| LLM 生成 | 用大模型从文档生成查询 | 中，成本低 |

## 3.2 LLM 生成训练数据

### 3.2.1 查询生成

```java
interface QueryGenerator {
    @UserMessage("""
            根据下面的文档片段，生成 5 个用户可能提出的问题：
            {{it}}
            输出 JSON 数组。
            """)
    List<String> generate(String document);
}

// 构造正样本对
for (String doc : documents) {
    for (String query : generator.generate(doc)) {
        pairs.add(new Pair(query, doc));   // 正样本
    }
}
```

### 3.2.2 数据清洗

LLM 生成的查询常有重复、过短、与文档不相关等问题，需过滤。典型流水线：去重 → 长度下限 → 用现模型算相似度筛掉低分对 → 人工抽检。

```java
// 伪代码：用当前模型过滤明显不相关的生成对
List<Pair> cleaned = rawPairs.stream()
        .distinct()
        .filter(p -> p.query().length() >= 6)
        .filter(p -> cosine(model.embed(p.query()),
                            model.embed(p.doc())) > 0.5)
        .toList();
```

## 3.3 负样本构造

| 类型 | 说明 | 难度 |
|------|------|------|
| 随机负样本 | 随机选不相关文档 | 易 |
| 批内负样本 | 同批其他查询的正例 | 中 |
| 难负样本 | 检索得分高但不相关的 | 难（最有价值） |

### 3.3.1 难负样本挖掘

```java
// 难负样本：用当前模型检索，取"高分但不相关"的文档
List<Document> hardNegatives = currentModel.search(query).stream()
        .filter(d -> !isRelevant(query, d))
        .limit(3)
        .toList();
```

### 3.3.2 假负样本风险

若标注不完整，检索到的"看似不相关"文档可能其实相关，被误当负例会伤害模型。挖掘前务必保证标注覆盖率，或对高分候选做人工复核。

> 难负样本对提升效果最明显，但也最容易导致训练不稳定。

## 3.4 数据规模与配比

| 数据量 | 效果 |
|--------|------|
| 数百对 | 几乎无感 |
| 数千对 | 开始见效 |
| 数万对以上 | 收益趋于饱和 |

正负比例通常 1:1 到 1:7 之间，难负样本占比不宜过高，否则训练早期容易被噪声带偏。

## 3.5 生产建议

| 建议 | 理由 |
|------|------|
| 真实数据优先 | 分布最匹配线上 |
| 保留测试集 | 严禁泄漏进训练 |
| 版本化数据集 | 可复现 |

# 4. 微调流程（Python 生态）

**结论先行**：Embedding 微调目前主要在 Python 生态（sentence-transformers / FlagEmbedding）完成，Java 侧主要用于**推理**。

## 4.1 为什么训练在 Python

深度学习训练框架（PyTorch）、预训练模型权重、社区示例几乎都在 Python。Java 生态更适合把训练好的模型拿来推理与集成。强行在 Java 里训练往往要自己封装 JNI，得不偿失。

## 4.2 sentence-transformers 流程

### 4.2.1 基本流程

```python
from sentence_transformers import SentenceTransformer, losses, InputExample
from torch.utils.data import DataLoader

model = SentenceTransformer("BAAI/bge-base-zh-v1.5")

train_examples = [InputExample(texts=[q, d]) for q, d in pairs]
loader = DataLoader(train_examples, shuffle=True, batch_size=32)
loss = losses.MultipleNegativesRankingLoss(model)

model.fit(
    train_objectives=[(loader, loss)],
    epochs=3,
    warmup_steps=100,
    output_path="models/bge-domain",
)
```

### 4.2.2 参数说明

| 参数 | 含义 | 建议 |
|------|------|------|
| `epochs` | 训练轮数 | 2~5，过多易过拟合 |
| `batch_size` | 批大小 | 尽量大，显存允许 |
| `warmup_steps` | 预热步数 | 总步数 10% 左右 |
| `output_path` | 输出目录 | 与版本号绑定 |

## 4.3 LoRA 与 FlagEmbedding

参数高效微调（LoRA，Low-Rank Adaptation，低秩适配）只训练少量低秩矩阵，显存占用小、可多版本共存。FlagEmbedding 提供面向 BGE 系列的训练脚本，支持对比学习与难负样本。

## 4.4 生产建议

| 建议 | 理由 |
|------|------|
| 固定随机种子 | 结果可复现 |
| 记录超参与数据版本 | 便于追溯 |
| 导出 ONNX | 便于 Java 推理 |

# 5. 在 Java 中使用微调后的模型

**结论先行**：Java 侧不训练，只消费微调后的模型，主流有三种形态：ONNX 本地推理、独立推理服务、云托管。

## 5.1 三种部署形态

### 5.1.1 ONNX 本地推理

把模型导出为 ONNX，用 onnxruntime 在 JVM 内推理。延迟低、无网络依赖，但要自己管理线程与显存。

### 5.1.2 独立服务

用 TEI（Text Embeddings Inference）等把模型部署为 HTTP 服务，Java 通过客户端调用。扩展性好，是生产主流。

### 5.1.3 云托管

调用云厂商的 embedding API，零运维，但数据出境与成本需评估。

## 5.2 Java 调用示例

```java
// 方案一：ONNX 导出后本地推理
EmbeddingModel model = new OnnxEmbeddingModel(
        Path.of("models/bge-domain.onnx"),
        Path.of("models/tokenizer.json"));

// 方案二：部署为独立服务，通过 HTTP 调用
EmbeddingModel model = new TeiEmbeddingModel(
        "http://embedding-service:8080");
```

批量嵌入能显著提高吞吐，注意区分查询与文档的前缀（部分模型要求）。

```java
// 伪代码：批量嵌入并保留前缀
List<String> queries = texts.stream()
        .map(t -> "query: " + t)
        .toList();
List<float[]> vectors = model.embed(queries);
```

## 5.3 生产建议

| 建议 | 理由 |
|------|------|
| 服务化优先 | 便于扩容与灰度 |
| 批量请求 | 提高吞吐 |
| 缓存向量 | 热点文本免重复计算 |

# 6. 微调效果评估

**结论先行**：必须用**留出测试集**对比微调前后，否则无法判断是否真的变好。没有评测的微调是盲调。

## 6.1 评估指标

### 6.1.1 Recall@K

前 K 条里是否包含相关文档，衡量召回能力。公式：

```
Recall@K = 命中相关文档的查询数 / 查询总数
```

### 6.1.2 MRR

第一个相关文档排名的倒数均值，衡量排序质量。相关文档排第 1 得 1 分，排第 2 得 0.5 分。

### 6.1.3 nDCG

考虑多个相关文档的排序与分级相关性，最贴近真实排序质量。它按位置做对数折扣，越靠前权重越大。

## 6.2 评估代码

```java
public double recallAtK(EmbeddingModel model, List<EvalCase> cases, int k) {
    int hit = 0;
    for (EvalCase c : cases) {
        List<String> retrieved = search(model, c.query(), k);
        if (retrieved.contains(c.relevantDocId())) hit++;
    }
    return hit / (double) cases.size();
}
```

```java
// 伪代码：MRR，相关文档为集合
public double mrr(EmbeddingModel model, List<EvalCase> cases, int k) {
    double sum = 0;
    for (EvalCase c : cases) {
        List<String> retrieved = search(model, c.query(), k);
        for (int i = 0; i < retrieved.size(); i++) {
            if (c.relevantDocIds().contains(retrieved.get(i))) {
                sum += 1.0 / (i + 1);
                break;
            }
        }
    }
    return sum / cases.size();
}
```

## 6.3 生产建议

| 建议 | 理由 |
|------|------|
| 至少两个指标 | 召回与排序互补 |
| 分场景统计 | 长尾问题易被平均掩盖 |
| 线上 A/B | 离线提升不等于线上提升 |

# 7. 微调的代价

**结论先行**：微调不是一次性的动作，而是持续的工程负担。投入前先算清全生命周期成本。

## 7.1 成本拆解

| 代价 | 说明 |
|------|------|
| 数据成本 | 构造高质量样本耗时 |
| 算力成本 | 需要 GPU |
| 工程成本 | 训练、导出、部署链路 |
| 维护成本 | 模型版本管理、重新索引 |
| 风险 | 可能过拟合、效果反而下降 |

## 7.2 风险

- 过拟合训练集，测试集反而变差。
- 领域偏移（distribution shift，分布漂移），线上新数据与训练分布不符。
- 与现有重排、混合检索的协同被破坏。

## 7.3 生产建议

| 建议 | 理由 |
|------|------|
| 小步迭代 | 每次只改一个变量 |
| 保留基线模型 | 可一键回滚 |
| 定期复训 | 数据分布会漂移 |

# 8. 替代方案

**结论先行**：在微调之前，绝大多数问题都有更便宜的解法。

## 8.1 替代手段清单

| 方案 | 说明 |
|------|------|
| 换更强的通用模型 | 成本低，见效快 |
| 混合检索（向量+BM25） | 关键词补齐语义短板 |
| 重排模型 | 提升精度 |
| 查询改写 | 把口语化查询改成检索友好表述 |
| 分块优化 | 保持语义完整 |

## 8.2 实践顺序

```
换模型 → 混合检索 → 重排 → 查询改写 → 微调
```

每一环都应在同一评测集上验证，记录增益，避免"感觉变好了"。

## 8.3 生产建议

| 建议 | 理由 |
|------|------|
| 逐项验证 | 每步都测收益 |
| 记录组合效果 | 手段之间有叠加 |

# 9. 生产注意事项

**结论先行**：微调上线是"数据 + 模型 + 索引"三位一体的版本切换，任何一环不同步都会出事故。

## 9.1 常见风险与对策

| 风险 | 建议 |
|------|------|
| 数据泄漏 | 训练/测试集严格隔离 |
| 过拟合 | 早停 + 验证集监控 |
| 无评测 | 必须对比微调前后 |
| 版本混乱 | 记录模型版本与索引版本 |
| 一次性微调 | 定期用新数据迭代 |

## 9.2 版本管理

模型换新意味着**所有文档向量都要重算**。必须建立"模型版本 ↔ 索引版本"的绑定关系，避免新旧向量混用导致检索错乱。

## 9.3 上线检查清单

```
[ ] 评测集未泄漏
[ ] 微调前后指标已对比
[ ] 全量索引已重建
[ ] 灰度流量已配置
[ ] 回滚方案已就绪
```

# 10. 小结

## 10.1 核心要点回顾

- 微调是最后手段，先穷尽其他优化。
- 对比学习是核心，正样本拉近、负样本推远。
- 难负样本价值最高，但也最难训练。
- 训练主要在 Python 生态，Java 侧用于推理。
- 必须用留出测试集对比微调前后效果。

## 10.2 下一步行动

- 先补齐评测集与基线指标。
- 依次尝试换模型、混合检索、重排、查询改写。
- 确需微调时，从小规模高质量数据起步，小步迭代。
