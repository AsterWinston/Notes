# 1. 模块定位

## 1.1 一句话定位

结论先行：当任务复杂到单个 Agent 难以胜任时，就需要多个 Agent 分工协作；本模块讲清多智能体的通信、编排、协作模式与失败模式，并落到 Java 实现。

```
任务复杂度 ↑
   │
   ▼
工作流 → 单 Agent → 多 Agent
   │        │          │
   │        │          └─ 本模块（10_MultiAgent）
   │        └─ 见 6_AgentCore
   └─ 见 4_LLMEngineering
```

机制拆解：多智能体解决的是"单 Agent 能力上限"问题，包括上下文容量、专长广度与并行度；但它同时引入通信、编排与一致性三类新复杂度。

边界与坑：多智能体不是默认选择，只有在工作流与单 Agent 都被证明不足时才应引入。

生产建议：把本模块当作升级路径的第二、三级，先确认前两级确实不够用。

## 1.2 与相邻模块的关系

结论先行：本模块位于 Agent 核心与工程化之间的枢纽位置，向上依赖 Agent 基础与框架，向下支撑应用落地。

| 方向 | 模块 | 关系 |
|------|------|------|
| 上游 | `6_AgentCore` | Agent 循环、工具、记忆 |
| 上游 | `9_Frameworks` | LangGraph4j、Spring AI 等 |
| 平行 | `13_Observability` | Trace 与指标 |
| 平行 | `14_ProductionEngineering` | 成本、灰度、降级 |
| 下游 | `16_Applications` | 多智能体应用系统 |

机制拆解：本模块把单 Agent 基础能力组合成协作系统，并把协作产生的复杂度交给可观测与工程化模块承接。

生产建议：阅读本模块前先确保 Agent 循环与工具调用已理解。

## 1.3 适用与不适用

结论先行：多智能体适合可分解、需多视角或超出单 Agent 上限的任务；对简单、延迟敏感或强确定性的任务不适用。

| 适用 | 不适用 |
|------|--------|
| 任务可分解为子任务 | 单步即可完成 |
| 需要多视角决策 | 延迟极敏感 |
| 超出单 Agent 上下文 | 强确定性流程（用工作流） |
| 需要并行探索 | 成本极度受限 |

机制拆解：判断标准是"协作能否带来超过其开销的增益"，而非任务看起来是否复杂。

生产建议：用单 Agent 基线做 A/B 测试后再决定是否采用多智能体。

# 2. 学习目标

## 2.1 知识目标

结论先行：学完本模块，应理解多智能体的收益与代价、常见编排模式与失败模式。

- 理解多智能体相对单智能体的收益与代价。
- 掌握常见编排模式（Supervisor / Swarm / 分层）。
- 能用 LangGraph4j、Spring AI Alibaba Graph 等实现多 Agent。
- 认识多智能体的失败模式与治理手段。

### 2.1.1 概念与模式

概念层回答"收益与代价"，模式层回答"用哪种拓扑"，两者构成判断基础。

### 2.1.2 实现与治理

实现层回答"怎么用框架落地"，治理层回答"如何不失控"，两者决定能否上线。

机制拆解：知识目标分为概念、模式、实现、治理四类，前两类构成判断基础，后两类决定能否落地。

边界与坑：只记住模式名称而不理解适用条件，容易选错拓扑。

## 2.2 能力目标

结论先行：能力目标强调"能设计、能实现、能评测、能治理"。

| 能力 | 验收方式 |
|------|----------|
| 设计 | 写出 Agent 清单与拓扑 |
| 实现 | 用框架跑通 Supervisor |
| 评测 | 产出单 Agent 基线对比 |
| 治理 | 配置步数、预算与降级 |

机制拆解：四类能力层层递进，设计决定上限，实现决定可用，评测决定取舍，治理决定可运营。

生产建议：以"能否独立交付一个小型多 Agent 系统"为最终检验标准。

## 2.3 自测问题

结论先行：用以下问题检验理解程度，答不上来则回到对应文件。

1. 什么情况下多智能体反而不如单 Agent？
2. 星型拓扑相比网状拓扑的优势与代价是什么？
3. 交接时为什么传摘要而非全量历史？
4. 如何证明多 Agent 比单 Agent 更好？
5. 负向涌现有哪些表现，如何抑制？
6. 上线前必须配置哪些护栏？

机制拆解：前两题考概念，中间两题考工程，最后两题考治理。

# 4. 学习顺序与依赖

## 4.1 学习路径

结论先行：推荐按"概览 → 实现 → 模式 → 治理 → 最佳实践"的顺序推进。

```
概览（1→3） → Java 实现（4→7） → 经典模式（8→9）
      → 风险与治理（10→11） → 最佳实践（12）
```

机制拆解：先建立概念再动手实现，最后用治理与最佳实践收口，符合"先会做、再做好"的认知顺序。

边界与坑：跳读容易形成"知道模式名但不会落地"的空心知识。

生产建议：每读完一组做一次小结，把要点沉淀到自己的设计清单。

## 4.2 依赖关系

结论先行：本模块依赖上游模块，并向下游应用模块输出能力。

- 上游依赖：`6_AgentCore`、`9_Frameworks`。
- 下游影响：`16_Applications/MultiAgentSystem`。

```
6_AgentCore ─┐
             ├─→ 10_MultiAgent ─→ 16_Applications
```

机制拆解：没有 Agent 循环与工具基础，多智能体只是空壳；没有应用承接，能力无法产生价值。

生产建议：跨模块学习时先补齐上游基础。

## 4.3 建议节奏

结论先行：按"两天概念 + 三天实现 + 一天治理"的节奏推进，边学边写代码。

# 5. 常见问题

## 5.1 概念类问题

结论先行：概念类疑问集中在"该不该用"与"和单 Agent 的关系"。

| 问题 | 简答 |
|------|------|
| 多 Agent 一定更强吗 | 不一定，需基线对比 |
| 和工作流冲突吗 | 不冲突，工作流是更简的起点 |
| 至少要几个 Agent | 从 2 个验证，通常不超过 5 个 |
| Swarm 何时用 | 仅开放式、低风险任务 |

机制拆解：概念问题的核心都是"收益是否覆盖复杂度"，回到基线对比即可解答。

## 5.2 工程类问题

结论先行：工程类疑问集中在拓扑、上下文、终止与成本。

| 问题 | 简答 |
|------|------|
| 用哪种拓扑 | 默认星型 Supervisor |
| 交接传什么 | 摘要 + 结构化关键数据 |
| 怎么防死循环 | 步数上限 + 循环检测 |
| 怎么控成本 | 限 Agent 数与轮数 + 预算熔断 |
| 怎么调试 | 完整 Trace + traceId 串联 |

机制拆解：工程问题的答案大多指向"显式护栏"，而非依赖模型自觉。

生产建议：把上述简答固化为团队规范。

# 6. 关键知识点速览

## 6.1 核心结论

结论先行：记住以下五条，即可把握本模块的主干。

- 多智能体的价值在于"分工 + 专业化 + 并行"，而非盲目堆数量。
- 通信与共享状态是复杂度的主要来源。
- 先考虑"能不能用工作流解决"，再考虑多 Agent。
- 没有可观测性的多智能体系统几乎无法调试。
- 任何多 Agent 方案都必须对比单 Agent 基线。

机制拆解：这五条分别对应价值、复杂度、决策顺序、可观测与评测，构成完整闭环。

## 6.2 常见误区

结论先行：初学者最常陷入以下误区，需提前规避。

| 误区 | 真相 |
|------|------|
| Agent 越多越强 | 收益呈倒 U 形 |
| 多 Agent 一定优于单 Agent | 需基线对比 |
| 传全量历史更保险 | 上下文爆炸 |
| 网状通信更灵活 | 通信爆炸 |
| 有日志就能调试 | 需 traceId 串联 |
| 上线后再加护栏 | 应设计阶段内置 |

## 6.3 一页速查表

结论先行：把设计要点浓缩为一页，便于随时对照。

| 维度 | 要点 |
|------|------|
| 拓扑 | 星型优先，慎用网状 |
| 职责 | 单一清晰，写明不负责 |
| 上下文 | 摘要 + 结构化数据 |
| 终止 | 步数上限 + 循环检测 |
| 成本 | 限制 Agent 数与轮数 |
| 可观测 | 完整 Trace + 指标 |
| 评测 | 对比单 Agent 基线 |
| 降级 | 部分结果或转人工 |
