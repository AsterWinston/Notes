# 1. 什么是多智能体

## 1.1 定义

**多智能体系统（Multi-Agent System）** = 多个 Agent 分工协作完成复杂任务。

这里的 Agent（智能体）指一个具备"模型 + 提示词 + 工具 + 记忆"的独立执行单元。多智能体的本质，是把一个复杂任务拆给若干"专职角色"，再通过通信与编排把它们组织起来。

## 1.2 单 Agent 与多 Agent 对比

### 1.2.1 单 Agent 工作方式

```
单 Agent：一个模型处理所有事
多 Agent：多个专职 Agent，各司其职
```

单 Agent 把工具、提示、记忆全部塞进一个上下文，由同一个模型循环决策。它结构简单、链路短，但工具一多就容易"选择困难"。

### 1.2.2 多 Agent 工作方式

多 Agent 把职责拆开：每个 Agent 只面对少量工具和一段聚焦的提示词，彼此通过消息或共享状态协作。

| 维度 | 单 Agent | 多 Agent |
|------|----------|----------|
| 工具数量 | 全量集中 | 按角色拆分 |
| 上下文长度 | 容易膨胀 | 各自隔离 |
| 失败影响面 | 全局 | 局部 |
| 调试难度 | 低 | 高 |
| 成本 | 低 | 高 |
| 并行能力 | 弱 | 强 |

### 1.2.3 典型拓扑

```
              ┌──────────────┐
              │  Supervisor  │
              └──────┬───────┘
        ┌────────────┼────────────┐
        ▼            ▼            ▼
   ┌─────────┐  ┌─────────┐  ┌─────────┐
   │ 检索 Agent│  │ 分析 Agent│  │ 写作 Agent│
   └─────────┘  └─────────┘  └─────────┘
```

上图为集中式（Supervisor）拓扑：由一个主管统一决定下一步交给谁。

## 1.3 最小示例

一个 Agent 的抽象可以非常简单：

```java
public interface Agent {
    String name();
    String description();               // 供编排者理解其能力
    String handle(String instruction);  // 执行并返回结果
}
```

```java
public record ResearchAgent(ChatClient client) implements Agent {

    public String name() { return "researcher"; }

    public String description() { return "检索并整理事实资料"; }

    public String handle(String instruction) {
        return client.prompt()
                .system("你是资料检索助手，只返回可验证的事实。")
                .user(instruction)
                .call()
                .content();
    }
}
```

多个这样的 `Agent` 加上一个编排者，就构成了最小多智能体系统。

# 2. 为什么用多 Agent

## 2.1 收益来源

| 理由 | 说明 |
|------|------|
| 分工专业化 | 每个 Agent 专注一类任务 |
| 上下文隔离 | 避免单一上下文过长 |
| 并行执行 | 独立任务并行 |
| 可独立演进 | 各自优化 |
| 权限隔离 | 不同 Agent 不同权限 |

这五条收益并非自动获得，它们各自有前提条件。

## 2.2 五类收益详解

### 2.2.1 分工专业化

给每个 Agent 一段聚焦的系统提示词，比给一个 Agent 一段"什么都要管"的长提示词效果更好。模型在小而明确的指令空间内，指令遵循（instruction following）更稳定。

### 2.2.2 上下文隔离

当一个 Agent 同时需要读 50 页文档、调用 10 个工具、维护多轮对话时，上下文（context）会被无关信息稀释。拆成多个 Agent 后，每个 Agent 只携带自己需要的那部分信息。

### 2.2.3 并行执行

无依赖的子任务可以并发：检索 A、检索 B、计算 C 三者互不依赖，可同时发起，总延迟近似取最大值而非求和。

```
串行：t = t1 + t2 + t3
并行：t = max(t1, t2, t3)
```

## 2.3 收益的边界

| 收益 | 前提 |
|------|------|
| 专业化 | 任务确实可被清晰切分 |
| 上下文隔离 | 存在"信息只属于某角色"的结构 |
| 并行 | 子任务之间无数据依赖 |
| 独立演进 | 有独立的负责人与指标 |
| 权限隔离 | 安全边界真实存在 |

> 若前提不成立，多 Agent 只会带来额外的通信与协调开销。

## 2.4 与工作流、单 Agent 的定位

| 范式 | 决策方式 | 适用 | 可控性 |
|------|----------|------|--------|
| 工作流 | 预定义路径 | 步骤确定 | 最高 |
| 单 Agent | 模型自主循环 | 任务聚焦 | 中 |
| 多 Agent | 多角色协作 | 任务可分解 | 较低 |

```
可控性高 ←────────────────────────→ 灵活性高
工作流      单 Agent       多 Agent
成本低 ←────────────────────────→ 成本高
```

选择顺序应为：工作流 → 单 Agent → 多 Agent，逐级升级。

# 3. 单 Agent 的局限

## 3.1 四类典型局限

```
工具过多 → 选择困难
上下文过长 → 信息稀释
职责混杂 → 提示难以兼顾
单点失败 → 一处出错全盘失败
```

## 3.2 局限的量化表现

| 现象 | 常见信号 | 根因 |
|------|----------|------|
| 工具选择错误率上升 | 工具数 > 10 | 候选空间过大 |
| 关键信息被忽略 | 上下文 > 数十 K Token | 注意力稀释 |
| 指令互相冲突 | 单提示词包含多目标 | 目标不兼容 |
| 局部错误放大 | 无隔离与重试 | 单点失败 |

## 3.3 一个具体反例

```java
// 单 Agent：一个提示词里塞进检索、分析、写作三类职责
String system = """
    你是全能助手，请完成：
    1. 检索知识库
    2. 分析数据
    3. 撰写报告
    4. 调用计算器
    """;
```

当职责越来越多，提示词会互相干扰；而多 Agent 可将其拆为四个各自聚焦的 Agent。

# 4. 多 Agent 的代价

## 4.1 代价清单

| 代价 | 说明 |
|------|------|
| 复杂度 | 通信、状态、编排 |
| 成本 | 多次调用 |
| 延迟 | 串行链路更长 |
| 调试 | 链路更长更难 |
| 失败模式 | 死循环、责任扩散 |

> **先考虑工作流/单 Agent，不够再上多 Agent。**

## 4.2 成本与延迟模型

### 4.2.1 调用次数放大

```
单 Agent：1 次决策 + 若干工具调用
Supervisor：每轮 1 次主管决策 + 1 次子 Agent 调用
          N 轮 ⇒ 约 2N 次模型调用
```

主管每轮都要看一遍历史和任务，因此主管提示词通常较长，Token（词元）消耗随之上升。

### 4.2.2 延迟放大

| 链路 | 延迟特征 |
|------|----------|
| 单 Agent | 1 次首 Token 延迟 + 生成 |
| 串行多 Agent | 累加 |
| 并行多 Agent | 取最大值 |
| Supervisor | 主管决策延迟 × 轮数 |

### 4.2.3 成本估算示例

```
单 Agent：1 次 × 2K Token = 2K
多 Agent（3 轮）：
  主管 3 × 3K = 9K
  子 Agent 3 × 2K = 6K
  合计 15K（约为单 Agent 的 7.5 倍）
```

> 多 Agent 不是"更聪明"，而是"用更多成本换更强的可分解性"。

## 4.3 何时不该上多 Agent

- 任务可用确定性工作流（workflow）表达。
- 子任务之间存在强顺序依赖，无法并行。
- 上下文很短，单 Agent 完全够用。
- 对延迟极度敏感且预算有限。
- 团队尚无跨 Agent 的可观测能力。

# 5. 常见模式

## 5.1 模式总览

| 模式 | 说明 |
|------|------|
| Supervisor | 主管分发任务 |
| Swarm | Agent 间自主交接 |
| 流水线 | 顺序处理 |
| 并行 | 同时处理 |
| 分层 | 多层组织 |
| 辩论 | 多 Agent 讨论 |

## 5.2 模式对比

### 5.2.1 集中式与去中心化

```
集中式（Supervisor）        去中心化（Swarm）
   ┌────┐                      A ──→ B
   │ 主管│                      ↑     │
   └─┬─┬┘                      └── C ←┘
   A B C                    自主决定交接对象
```

| 维度 | 集中式 | 去中心化 |
|------|--------|----------|
| 决策者 | 主管 | 各 Agent |
| 可控性 | 高 | 中 |
| 瓶颈 | 主管 | 无明显瓶颈 |
| 调试 | 易 | 难 |
| 典型实现 | Supervisor | Swarm |

### 5.2.2 选型建议

| 场景 | 推荐模式 |
|------|----------|
| 任务可预先拆解 | 流水线 / 并行 |
| 需要动态决策 | Supervisor |
| 需要多视角验证 | 辩论 |
| 大规模同类任务 | 分层 |
| 轻量自主协作 | Swarm |

## 5.3 模式速记

| 模式 | 一句话 |
|------|--------|
| Supervisor | 一个主管统一派活 |
| Swarm | 谁合适谁接手 |
| 流水线 | A 做完交 B |
| 并行 | A、B、C 同时做 |
| 分层 | 主管之下还有主管 |
| 辩论 | 多方对同一问题给结论 |

## 5.4 模式的失败倾向

| 模式 | 典型失败 |
|------|----------|
| Supervisor | 主管误判、成为瓶颈 |
| Swarm | 无限交接、责任扩散 |
| 流水线 | 上游错误逐级放大 |
| 并行 | 结果冲突难合并 |
| 分层 | 信息在层间衰减 |
| 辩论 | 无法收敛、成本高 |

# 6. 何时使用

## 6.1 决策流程

```
判断流程：
① 任务能否用工作流解决？ → 能则用工作流
② 能否用单 Agent 解决？ → 能则用单 Agent
③ 任务是否需要多个专业视角？ → 是则多 Agent
④ 是否需要并行？ → 是则多 Agent
⑤ 上下文是否过长？ → 是则拆分多 Agent
```

## 6.2 适合与不适合

### 6.2.1 适合

| 适合 | 说明 |
|------|------|
| 复杂多步任务 | 步骤多、需分解 |
| 需要多专业视角 | 检索/分析/写作并存 |
| 可并行子任务 | 互不依赖 |
| 上下文超长 | 单上下文装不下 |

### 6.2.2 不适合

| 不适合 | 说明 |
|--------|------|
| 简单问答 | 单次调用即可 |
| 单点任务 | 无需分工 |
| 强顺序依赖 | 无法并行 |
| 短上下文 | 隔离无收益 |

### 6.2.3 判断清单

- 任务是否能画成一张明确的流程图？能，则先考虑工作流。
- 工具数量是否超过 10？是，则考虑按角色拆分。
- 上下文是否超过模型有效窗口的一半？是，则考虑隔离。
- 子任务能否并发？能，则并行收益明确。
- 是否有跨 Agent 的 Trace（链路追踪）？没有，则先补可观测。

## 6.3 演进路径

```
阶段一：单 Agent（少量工具）
   │  工具 > 10 或上下文过长
   ▼
阶段二：单 Agent + 工作流编排
   │  需要动态决策
   ▼
阶段三：Supervisor + 若干专职 Agent
   │  规模继续扩大
   ▼
阶段四：分层编排 + 专用框架
```

每一步都应基于真实痛点，而不是"看起来更先进"。

# 7. 关键挑战

## 7.1 挑战清单

| 挑战 | 说明 |
|------|------|
| 通信协议 | 消息格式、共享状态 |
| 编排 | 谁决定下一步 |
| 状态同步 | 多 Agent 状态一致 |
| 终止条件 | 防止无限协作 |
| 成本控制 | 多 Agent 调用多 |
| 可观测 | 跨 Agent Trace |

## 7.2 通信与编排

### 7.2.1 通信协议

Agent 之间传递的消息应结构化，避免自然语言歧义：

```java
public record AgentMessage(
        String from,          // 发送方
        String to,            // 接收方（广播用 *）
        String type,          // REQUEST / RESPONSE / EVENT
        String taskId,        // 关联的任务 ID
        String payload,       // 结构化内容（JSON）
        Instant timestamp
) {}
```

| 方式 | 优点 | 缺点 |
|------|------|------|
| 消息传递 | 解耦、可审计 | 需定义协议 |
| 共享状态 | 简单 | 并发冲突 |
| 黑板（Blackboard） | 灵活 | 难以追踪来源 |

### 7.2.2 编排归属

```java
public class Orchestrator {

    public String run(String task, int maxSteps) {
        List<AgentMessage> history = new ArrayList<>();
        for (int step = 0; step < maxSteps; step++) {
            String next = router.next(task, history);
            if ("FINISH".equals(next)) break;
            AgentMessage reply = agents.get(next).handle(task, history);
            history.add(reply);
        }
        return synthesizer.synthesize(task, history);
    }
}
```

编排者既可以是 LLM（模型决策），也可以是规则（确定性路由）。生产上常采用"规则优先 + 模型兜底"的混合方式。

## 7.3 状态与终止

### 7.3.1 状态同步

| 策略 | 说明 |
|------|------|
| 单一事实源 | 状态集中在编排者 |
| 事件溯源 | 记录事件流，重放还原 |
| 版本号 | 检测并发修改冲突 |

### 7.3.2 终止条件

必须显式设置终止条件，否则协作可能永不停止：

```java
// 三重终止保护（伪代码）
while (true) {
    if (steps >= MAX_STEPS) break;              // 步数上限
    if (elapsed > MAX_DURATION) break;          // 时间上限
    if (costEstimate > MAX_COST) break;         // 成本上限
    if (isDone(state)) break;                   // 业务完成
    step();
}
```

## 7.4 成本与可观测

| 关注点 | 手段 |
|--------|------|
| 成本 | 预算上限、模型路由、缓存 |
| 延迟 | 并行化、减少轮数 |
| 可观测 | 统一 Trace ID、逐轮记录决策 |
| 安全 | 按 Agent 分配最小权限 |

# 9. 小结

## 9.1 核心结论

- 多 Agent 用多个专职 Agent 协作完成复杂任务。
- 收益：专业化、隔离、并行、可演进。
- 代价：复杂度、成本、延迟、调试难。
- **先考虑工作流/单 Agent，不够再上多 Agent。**
- 关键挑战：通信、编排、状态、终止、成本。

## 9.2 决策口诀

> 能工作流就不上 Agent，能单 Agent 就不上多 Agent；只有当任务可分解、可并行、可隔离时，多 Agent 的收益才大于代价。
