# 1. 多智能体失败的全景

## 1.1 失败分类

结论先行：多智能体系统的失败 = 单 Agent 的失败 + 协作本身带来的新失败；后者往往更隐蔽、更难复现。

| 失败 | 说明 |
|------|------|
| 死循环 | Agent 互相踢皮球 |
| 责任扩散 | 都以为别人会做 |
| 通信爆炸 | 消息指数增长 |
| 目标漂移 | 协作中偏离目标 |
| 上下文丢失 | 交接时信息丢失 |
| 成本失控 | Agent 越多成本越高 |
| 状态不一致 | 共享状态冲突 |
| 单点瓶颈 | 主管成为瓶颈 |

机制拆解：这些失败可归为四类——控制类（死循环、单点瓶颈）、协作类（责任扩散、通信爆炸）、语义类（目标漂移、上下文丢失）、资源类（成本失控、状态不一致）。

边界与坑：单个失败常会诱发另一个失败，例如死循环直接导致成本失控。

生产建议：把失败当作"链式反应"来治理，优先掐断最上游的诱因。

## 1.2 与单智能体失败的关系

结论先行：多智能体并未消除单 Agent 的失败（幻觉、工具误用、格式错误），反而放大了其影响面。

```
单 Agent 的失败 + 协作带来的新失败
```

机制拆解：单 Agent 出错只影响一次输出；多 Agent 中，一个 Agent 的错误结论会被下游当作事实继续加工。

边界与坑：只针对单 Agent 做提示优化，无法解决协作层的系统性问题。

生产建议：把单 Agent 的护栏（校验、重试、工具确认）先做扎实，再叠加协作护栏。

## 1.3 失败检测总览

结论先行：统一用一个检测器按固定顺序判断，避免各处置逻辑互相冲突，结论用枚举 `FailureType { NONE, TOO_MANY_STEPS, LOOP, STAGNANT, COST_EXCEEDED }` 表达。

机制拆解：检测顺序通常为——步数 → 循环 → 停滞 → 成本，先命中先返回。

边界与坑：若先判成本再判循环，可能把循环误报为成本问题，掩盖根因。

生产建议：检测结果同时记录到 Trace，用于根因分析。

# 2. 死循环

## 2.1 成因

结论先行：死循环的本质是"没有任何一方愿意或能够终止"，交接权在两个及以上 Agent 间来回传递。

```
Agent A → "这个应该 B 处理" → Agent B
Agent B → "这个应该 A 处理" → Agent A
        ↓ 无限循环
```

机制拆解：

1. 职责边界模糊，A 与 B 都认为对方更合适。
2. 提示词缺乏"何时必须收尾"的约束。
3. 缺少全局步数与重复检测。

边界与坑：两个 Agent 之间的显式互推最易发现，但 A→B→C→A 的三元环更隐蔽。

生产建议：把"谁在什么条件下必须给出结论"写进每个 Agent 的提示词。

## 2.2 检测

结论先行：检测分两层——路径去重（发现回环）与计数阈值（容忍合理重试）。

```java
public boolean isLoop(List<String> path, String next, int threshold) {
    long count = path.stream().filter(next::equals).count();
    return count >= threshold;
}
```

机制拆解：按出现次数判定，`threshold` 取 2 或 3，兼顾容错与止损。

边界与坑：合法的"先查后改再查"会造成重复，故用阈值法而非简单去重。

生产建议：同时记录"相邻重复"（A→B→A→B），这类模式几乎必是死循环。

## 2.3 处置

### 2.3.1 步数上限

结论先行：步数上限是最简单可靠的最后防线，任何多 Agent 循环都必须具备。

```java
for (int step = 0; step < maxSteps; step++) {
    // ... 每轮推进
}
return fallbackAnswer();
```

边界与坑：上限过大等于没有保护；上限过小会让复杂任务被迫中断。

生产建议：按任务类型配置上限，并在触顶时记录告警。

### 2.3.2 强制决策

结论先行：检测到重复后，不让流程继续，而是强制当前 Agent 或主管给出结论。

```java
if (detector.detect(path, cost) != FailureType.NONE) {
    return "已检测到异常（%s），基于当前信息给出结论：%s"
            .formatted(type, bestEffortAnswer());
}
```

边界与坑：强制结论质量可能不高，但优于空转与超时。

生产建议：在提示词中预先告知"超时后必须作答"，让模型提前准备。

# 3. 责任扩散

## 3.1 成因

结论先行：当职责边界重叠或存在"灰色地带"时，每个 Agent 都可能把问题推给别人。

```
问题：多个 Agent 都认为"这不是我的职责"
结果：没人处理
```

机制拆解：

1. Agent 清单描述含糊，缺少"不负责什么"。
2. 提示词未禁止推诿。
3. 缺少默认承接方。

边界与坑：责任扩散与死循环常同时发生——推诿的表现形式就是反复交接。

生产建议：为每个 Agent 明确定义"负责范围"与"明确不负责范围"。

## 3.2 检测

结论先行：从统计上看，某类请求被频繁转交却从未产生最终结果，即责任扩散信号。

| 指标 | 含义 | 异常阈值 |
|------|------|:--------:|
| 转交率 | 收到后转交比例 | > 0.8 |
| 终结率 | 最终给出结论比例 | < 0.1 |
| 平均跳数 | 每次请求跳数 | > 3 |

生产建议：按请求类型分组统计，定位"无人认领"的类别。

## 3.3 处置

结论先行：用提示词强制"给出最佳判断或明确指定处理者"，并设置兜底 Agent。

```java
// 每个 Agent 的提示中明确：
// "如果问题不完全属于你的职责，也要给出你的最佳判断，
//  或明确指出应该由谁处理，不得直接推诿。"
```

机制拆解：要求"最佳判断 + 指定对象"把模糊转交变成可追溯决策。

边界与坑：兜底 Agent 可能成为新瓶颈，需要独立扩容或限流。

生产建议：把兜底 Agent 的处理结果纳入质量抽检。

# 4. 通信爆炸

## 4.1 成因

结论先行：网状拓扑下，Agent 数量增加会让潜在通信对按平方增长。

```
Agent 数量 ↑ → 消息数 O(n²) ↑
```

机制拆解：若每个 Agent 都能与任意其他 Agent 通信，则 n 个节点有 n(n-1)/2 条潜在通道。

边界与坑：即便实际未全部使用，模型被赋予"任意交接"能力也会倾向于频繁转交。

生产建议：默认采用星型拓扑，只在必要时开放有限直连。

## 4.2 量化

结论先行：用组合数即可估算潜在通信对，快速判断是否需要收敛拓扑。

| Agent 数 | 潜在通信对 |
|:--------:|:----------:|
| 3 | 6 |
| 5 | 20 |
| 10 | 90 |

边界与坑：消息数不等于 token 数，长消息会让成本远超节点数增长。

## 4.3 星型拓扑处置

结论先行：把通信收敛为"都连主管"，可将 O(n²) 降为 O(n)。

```
   网状：n 个节点约 n(n-1) 条潜在通道
   星型：n 个节点约 2n 条通道（都连主管）
```

机制拆解：星型下所有消息经由主管中转，主管可统一做去重、合并与限流。

边界与坑：主管成为单点瓶颈与故障点，需要冗余与限流。

生产建议：对主管做水平扩展或按任务分片。

# 5. 目标漂移

## 5.1 成因

结论先行：多轮协作后，各 Agent 聚焦于局部子目标，逐渐偏离最初目标。

```
协作多轮后，Agent 忘记原始目标
```

机制拆解：

1. 原始目标只出现在第一轮，后续轮次未重申。
2. 子任务描述逐渐具体化，掩盖了原始意图。
3. 模型倾向于"完成眼前任务"而非"达成最终目标"。

边界与坑：目标漂移往往表现为"结果正确但答非所问"。

生产建议：把原始目标设为贯穿全程的只读上下文。

## 5.2 检测

结论先行：用"最终结果与原始目标的语义相似度"或"约束满足率"来量化漂移。

```java
public boolean isDrifting(String originalGoal, String currentResult) {
    double sim = embedding.similarity(originalGoal, currentResult);
    return sim < DRIFT_THRESHOLD;   // 例如 0.6
}
```

边界与坑：相似度低不一定漂移（可能只是表述不同），需结合约束检查。

生产建议：把硬约束（必须包含的字段、必须满足的条件）做成可程序化校验的清单。

## 5.3 处置

结论先行：每轮都把原始目标重新注入，并要求产出对齐目标。

```java
// 每轮都带上原始目标
String prompt = """
        原始目标（始终围绕）：
        %s

        当前进展：
        %s
        """.formatted(originalGoal, progress);
```

机制拆解：重申目标相当于给每轮加一个"锚点"，抑制局部优化。

边界与坑：目标文本过长会挤占上下文，应先压缩为要点。

生产建议：在最终汇总前做一次"目标对齐检查"。

# 6. 上下文丢失

## 6.1 成因

结论先行：交接时若只传自然语言摘要，关键数据与约束会在复述中损失。

```
A 的结论传给 B 时信息损失
```

机制拆解：

1. 每跳都做一次文本复述，复述即压缩。
2. 结构化数据被转成散文后难以精确还原。
3. 长对话被截断，早期信息被丢弃。

边界与坑：信息丢失往往在最后一跳才暴露，排查成本高。

生产建议：关键数据与约束用结构化字段传递，而非文本。

## 6.2 结构化上下文

结论先行：用不可变记录承载交接信息，区分目标、摘要、数据与约束。

```java
// 传递结构化上下文，而非纯文本
public record HandoffContext(
        String task,
        String summary,            // 摘要
        Map<String, Object> data,  // 关键数据
        List<String> constraints   // 约束
) {}
```

机制拆解：`task` 保持原始目标不变；`summary` 可滚动更新；`data` 保存精确值；`constraints` 保存硬性要求。

边界与坑：`data` 若被下游覆盖，会丢失上游数据；建议合并而非替换。

生产建议：为 `data` 定义命名空间，避免键冲突。

## 6.3 处置

结论先行：除结构化传递外，还应做"交接校验"——检查必需字段是否齐全。

```java
public void validate(HandoffContext ctx) {
    if (ctx.task() == null || ctx.task().isBlank()) {
        throw new IllegalStateException("原始任务缺失");
    }
    if (!ctx.data().containsKey("orderId")) {
        throw new IllegalStateException("缺少关键数据 orderId");
    }
}
```

边界与坑：校验过严会导致正常流程被阻断，需按 Agent 定制必需字段。

生产建议：把校验失败计入指标，观察丢失热点。

# 7. 成本失控

## 7.1 成因

结论先行：成本近似等于"Agent 数 × 轮数 × 单次调用成本"，任一项失控都会放大总成本。

```
Agent 数 × 轮数 × 单次成本
```

机制拆解：

1. Agent 越多，每轮可选的调用越多。
2. 轮数不受限时，循环会持续烧钱。
3. 上下文膨胀让单次调用越来越贵。

边界与坑：成本曲线是乘积关系，三个因子同时增长会指数级恶化。

生产建议：对三个因子分别设上限，而非只盯总数。

## 7.2 处置

结论先行：用限制、分层、预算、缓存四类手段组合控本。

| 手段 | 说明 |
|------|------|
| 限制 Agent 数 | ≤ 5 |
| 限制轮数 | ≤ 10 |
| 模型分层 | 简单 Agent 用小模型 |
| 预算 | 按任务设上限 |
| 缓存 | 复用中间结果 |

机制拆解：限制管上限，分层降单价，预算做熔断，缓存减重复。

边界与坑：缓存对非确定性输出效果有限，且可能引入过期结果。

生产建议：把预算熔断与用户体验结合，超限时给出"部分结果"。

# 8. 状态不一致

## 8.1 成因

结论先行：多个 Agent 并发读写同一份共享状态时，会出现覆盖、脏读与竞态。

```
多个 Agent 并发写共享状态
```

机制拆解：

1. 无锁的 `HashMap` 并发写可能损坏结构。
2. 读-改-写不是原子操作，会丢失更新。
3. 不同 Agent 对同一键的语义理解不一致。

边界与坑：状态不一致的 bug 难以复现，且常在压力下才暴露。

生产建议：优先让 Agent 无共享状态，状态集中在编排器。

## 8.2 并发与不可变

结论先行：用加锁或不可变数据结构消除竞态，二者可结合。

```java
// 共享状态加锁或使用不可变数据
public synchronized void update(String key, Object value) {
    state.put(key, value);
}
```

机制拆解：加锁简单但串行化；也可改用不可变快照，每次返回新对象，利于并发读取与回滚。

边界与坑：`synchronized` 只保证单 JVM 内一致，多实例需外部协调。

生产建议：跨实例场景使用外部存储或分布式锁，并明确一致性级别。

## 8.3 处置

结论先行：明确"单一写者"原则，配合版本号检测冲突。

```java
public void update(String key, Object value, long expectedVersion) {
    if (version.get() != expectedVersion) {
        throw new OptimisticLockException("状态已被其他 Agent 修改");
    }
    state.put(key, value);
    version.incrementAndGet();
}
```

边界与坑：乐观锁冲突时需要重试策略，否则失败率升高。

生产建议：冲突率纳入监控，过高说明写者划分不合理。

# 9. 失败检测与统一追踪

## 9.1 检测器实现

结论先行：把各类失败判定收敛到一个检测器，按优先级返回单一结论。

```java
public class MultiAgentFailureDetector {

    private static final int MAX_STEPS = 10;
    private static final long MAX_COST = 500_000L;

    public FailureType detect(List<String> path, long cost) {
        if (path.size() > MAX_STEPS) return FailureType.TOO_MANY_STEPS;
        if (hasLoop(path)) return FailureType.LOOP;
        if (cost > MAX_COST) return FailureType.COST_EXCEEDED;
        if (isStagnant(path)) return FailureType.STAGNANT;
        return FailureType.NONE;
    }

    private boolean hasLoop(List<String> path) {
        return path.size() != new HashSet<>(path).size();
    }

    private boolean isStagnant(List<String> path) {
        int n = path.size();
        return n >= 4 && path.get(n - 1).equals(path.get(n - 3))
                && path.get(n - 2).equals(path.get(n - 4));
    }
}
```

机制拆解：`isStagnant` 检测 A→B→A→B 的周期性停滞，比单纯去重更精准。

边界与坑：静态阈值不适应不同任务，需按任务类型参数化。

生产建议：检测器应无副作用且可单测，避免耦合业务逻辑。

## 9.2 统一 Trace

结论先行：以 traceId 为纽带，把每次交接、决策、耗时、token 串成一条链。

| 字段 | 说明 |
|------|------|
| traceId | 贯穿整条任务 |
| spanId | 单次交接（父 span 指向上游） |
| agent | 当前 Agent |
| tokens/latency | 资源消耗 |

机制拆解：父子 span 结构天然对应交接链，可还原成树或图。

边界与坑：只记日志不记关联 ID，事后无法拼出完整链路。

生产建议：接入现有 APM 体系，避免自建孤岛。

## 9.3 熔断与降级

结论先行：检测到失败后要有明确降级路径，而不是直接抛错给用户。

```java
public String runSafely(String task) {
    try {
        return orchestrator.run(task, MAX_STEPS);
    } catch (Exception e) {
        log.error("协作失败 traceId={}", traceId, e);
        return "处理失败，已记录：" + traceId;
    }
}
```

机制拆解：降级可为——返回部分结果、转人工、或提示重试。

边界与坑：静默降级会掩盖问题，必须同时告警。

生产建议：降级率作为核心 SLO 指标之一。

# 10. 生产注意事项

## 10.1 上线检查清单

结论先行：上线前逐项核对，确保关键护栏齐全。

| 项目 | 检查点 |
|------|--------|
| 步数上限 | 已配置且按任务分档 |
| 循环检测 | 去重 + 停滞检测 |
| 职责边界 | 每个 Agent 有"不负责"说明 |
| 拓扑 | 星型优先 |
| 目标锚定 | 原始目标每轮重申 |
| 成本 | 预算 + 熔断 + Trace |

生产建议：把清单固化为发布门禁，缺项阻断上线。

## 10.2 回归测试

结论先行：多 Agent 行为不确定，需用固定用例集做回归，防止提示词改动引入退化。

| 用例类型 | 目的 |
|----------|------|
| 正常分解 | 验证主流程 |
| 边界输入 | 验证兜底 |
| 诱导循环 | 验证检测生效 |

机制拆解：用例断言"最终结果包含关键要素"与"未超预算"，而非逐字匹配。

边界与坑：过度逐字断言会让测试频繁误报，失去价值。

生产建议：每次修改提示词或拓扑后跑全量回归。

# 11. 小结与落地清单

## 11.1 要点回顾

- 多 Agent 失败 = 单 Agent 失败 + 协作失败。
- 典型失败：死循环、责任扩散、通信爆炸、目标漂移。
- 对策：步数上限、明确职责、星型拓扑、重申目标。
- 成本与状态一致性也需专门处理。
- 必须有失败检测与统一 Trace。

## 11.2 落地清单

| 失败 | 首选举措 | 辅助举措 |
|------|----------|----------|
| 死循环 | 步数上限 | 停滞检测 + 强制决策 |
| 责任扩散 | 职责边界 | 兜底 Agent |
| 通信爆炸 | 星型拓扑 | 交接白名单 |
| 目标漂移 | 原始目标只读 | 对齐检查 |
