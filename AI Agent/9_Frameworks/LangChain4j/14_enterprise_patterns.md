# 1. 从 Demo 到生产的鸿沟

结论先行：**Demo 验证的是"能不能"，生产验证的是"稳不稳、贵不贵、安不安全"**。本文件汇总 LangChain4j 在企业落地中的关键模式，与 `14_ProductionEngineering`、`15_Security` 互为补充。

## 1.1 Demo 与生产的差异

```
Demo：一个 AiService + 一个模型 → 能跑
生产：多模型、多租户、可靠性、成本、安全、可观测、可运维
```

| 维度 | Demo | 生产 |
|------|------|------|
| 模型 | 单一 | 多模型路由 |
| 用户 | 自己 | 多租户 |
| 失败 | 重试手动 | 超时/熔断/降级 |
| 成本 | 不关心 | 配额与监控 |
| 数据 | 内存 | 持久化 + 隔离 |
| 观测 | 日志 | 指标 + 追踪 |

## 1.2 生产系统六要素

| 要素 | 目标 |
|------|------|
| 可靠性 | 失败可控、快速恢复 |
| 安全 | 输入/输出/数据/密钥全链路 |
| 成本 | 可预测、可归因 |
| 可观测 | 指标、日志、追踪 |
| 可运维 | 灰度、回滚、配置化 |
| 可扩展 | 多模型、多租户 |

## 1.3 边界与坑

- 把 Demo 代码直接上线，往往在**并发**与**失败路径**上崩；
- 只关注功能不关注成本，账单会在规模化后失控；
- 没有评测回归，模型切换等于盲盒。

## 1.4 生产建议

- 上线前逐项对照六要素；
- 建立评测集，作为发版门槛；
- 所有外部依赖都配置超时与降级。

# 2. 分层架构

结论先行：**业务代码只依赖 `AiService` 接口**，模型与框架细节封装在能力层，这是解耦的根本。

## 2.1 六层结构

```
┌───────────────────────────────────────────────┐
│  接入层   Controller / SSE / WebSocket         │
├───────────────────────────────────────────────┤
│  应用层   Facade / UseCase（编排、事务边界）    │
├───────────────────────────────────────────────┤
│  能力层   AiService / RAG / Tools / Memory      │
├───────────────────────────────────────────────┤
│  治理层   ChatModelListener（限流/审计/成本）   │
├───────────────────────────────────────────────┤
│  模型层   ChatModel / EmbeddingModel            │
├───────────────────────────────────────────────┤
│  基础设施 配置中心 / 密钥 / 向量库 / 缓存        │
└───────────────────────────────────────────────┘
```

## 2.2 依赖方向与职责

| 层 | 职责 | 变更频率 |
|----|------|----------|
| 接入层 | 协议转换、鉴权 | 低 |
| 应用层 | 编排、事务 | 中 |
| 能力层 | 提示/工具/RAG | 高 |
| 治理层 | 横切关注点 | 中 |
| 模型层 | 模型适配 | 中 |
| 基础设施 | 存储/密钥 | 低 |

依赖自上而下，**下层不感知上层**。

## 2.3 边界与坑

- 若 Controller 直接注入 `ChatModel`，模型切换会波及接入层；
- 治理层放错位置（如写在 Controller）会导致重复实现；
- 分层过多会带来样板代码，按团队规模裁剪。

## 2.4 生产建议

- 用 ArchUnit 等工具固化分层依赖规则；
- 能力层接口先定义，模型实现后置；
- 治理逻辑统一在监听器/拦截器实现。

# 3. 多模型与路由

结论先行：**按任务复杂度分层选模型**，是降本增效最直接的手段。

## 3.1 模型分层

| 层级 | 用途 | 示例 |
|------|------|------|
| FAST | 分类、抽取 | `gpt-4o-mini` |
| STANDARD | 一般问答 | `gpt-4o` |
| STRONG | 复杂推理 | 推理型模型 |

## 3.2 路由实现

### 3.2.1 静态路由

```java
public enum Tier { FAST, STANDARD, STRONG }

@Component
public class RoutingAssistant {

    private final Map<Tier, ChatModel> models;

    public RoutingAssistant(@Qualifier("fastModel") ChatModel fast,
                            @Qualifier("standardModel") ChatModel standard,
                            @Qualifier("strongModel") ChatModel strong) {
        models = Map.of(Tier.FAST, fast, Tier.STANDARD, standard, Tier.STRONG, strong);
    }

    public String chat(Tier tier, String message) {
        return AiServices.builder(Assistant.class)
                .chatModel(models.get(tier))
                .build()
                .chat(message);
    }
}
```

### 3.2.2 动态路由

动态路由先做一次轻量意图/复杂度判断，再决定模型层级；判断本身可用小模型或规则完成，避免"用大模型决定用不用大模型"的悖论。

## 3.3 复用 AiService 实例

更优做法是**复用 `AiService` 实例、只切换模型**，避免每次构建代理。可在启动期为每个层级各建一个 `Assistant`，运行期查表返回。

## 3.4 边界与坑

- 每次请求 `AiServices.builder(...).build()` 会生成动态代理，高频调用有开销；
- 动态路由的判断失败需有兜底层级；
- 不同层级的输出质量不一致，提示词需分别调优。

## 3.5 生产建议

- 启动期预热各层 `Assistant`；
- 路由决策记录到指标，便于分析命中率；
- 为每层配置独立配额。

# 4. 配置与密钥治理

结论先行：**密钥不落盘、分环境隔离、可轮换、可审计**是底线。

## 4.1 配置外部化

```yaml
langchain4j:
  open-ai:
    chat-model:
      api-key: ${OPENAI_API_KEY}
      model-name: ${AI_MODEL:gpt-4o-mini}
```

配置从环境变量或配置中心注入，镜像内不含任何明文密钥。

## 4.2 密钥管理

| 要求 | 做法 |
|------|------|
| 密钥不落盘 | Vault / KMS / 配置中心 |
| 分环境隔离 | dev/test/prod 独立密钥与配额 |
| 可轮换 | 支持热更新 |
| 可审计 | 记录密钥使用方 |

## 4.3 边界与坑

- `${VAR:default}` 的默认值若写成真实密钥，等于明文入库；
- 配置中心下发的密钥需支持热更新，否则轮换要重启；
- 日志打印配置对象时可能带出密钥。

## 4.4 生产建议

- 密钥读取集中在 `SecretProvider` 抽象；
- 日志对 `api-key` 等字段做掩码；
- 轮换演练纳入运维例行。

# 5. 可靠性

结论先行：**超时、重试、熔断、限流、降级、隔离是上线门槛**，缺一不可。

## 5.1 可靠性五件套

| 手段 | 实现 | 说明 |
|------|------|------|
| 超时 | 模型构建器 `timeout(...)` | 必设 |
| 重试 | `maxRetries(...)` / Resilience4j | 只重试幂等调用 |
| 熔断 | Resilience4j CircuitBreaker | 模型不可用时快速失败 |
| 限流 | Resilience4j RateLimiter / Bucket4j | 保护配额与成本 |
| 降级 | 备用模型 / 缓存 / 静态兜底 | 保证可用性 |
| 隔离 | 舱壁（线程池/信号量） | 防止单点拖垮全局 |

## 5.2 超时与重试

### 5.2.1 模型构建器配置

```java
ChatModel model = OpenAiChatModel.builder()
        .apiKey(key)
        .modelName("gpt-4o-mini")
        .timeout(Duration.ofSeconds(30))
        .maxRetries(2)
        .build();
```

### 5.2.2 Resilience4j 组合

```java
@Bean
ChatModel resilientModel(ChatModel delegate,
                         CircuitBreaker breaker,
                         Retry retry) {
    return new ResilientChatModel(delegate, breaker, retry);
}
```

超时是外层总预算，重试次数与单次超时需满足 `单次超时 × (重试+1) ≤ 总超时`。

## 5.3 熔断与降级

熔断在错误率超阈值时打开，直接返回降级结果；降级可为备用模型、缓存答案或静态兜底文案。

## 5.4 边界与坑

- 重试非幂等调用（如已扣费的工具）会导致重复副作用；
- 重试放大流量，需配合退避与抖动；
- 降级路径本身也要测试，否则降级即故障。

## 5.5 生产建议

- 每个模型配置独立超时；
- 熔断指标接入告警；
- 定期做故障注入演练。

# 6. 状态与会话持久化

结论先行：**服务无状态、状态外置**，才能水平扩展。

## 6.1 状态分类

| 状态 | 生命周期 | 存储 |
|------|----------|------|
| 对话记忆 | 会话级 | Redis / JDBC |
| 长任务状态 | 天/周 | 数据库检查点 |
| 用户偏好 | 长期 | 业务库 |

## 6.2 持久化方案

| 场景 | 方案 |
|------|------|
| 对话记忆 | 自定义 `ChatMemoryStore`（JDBC/Redis） |
| 长任务状态 | 状态机 + 数据库检查点 |
| 多实例部署 | 无状态服务 + 外部状态存储 |

```java
ChatMemory memory = MessageWindowChatMemory.builder()
        .id(sessionId)
        .maxMessages(20)
        .chatMemoryStore(redisStore)
        .build();
```

## 6.3 多实例部署

所有实例共享外部存储；负载均衡无需会话粘滞，扩容即生效。

## 6.4 边界与坑

- 本地内存记忆在多实例下会产生"会话漂移"；
- 并发写同一会话需加锁或串行化；
- 状态序列化格式升级要兼容旧数据。

## 6.5 生产建议

- 记忆存储设置 TTL 与容量上限；
- 关键状态变更写审计；
- 定期压测存储层的读写延迟。

# 7. 多租户

结论先行：**隔离维度覆盖数据、模型与配额、密钥、权限、审计**，缺一即泄漏风险。

## 7.1 隔离维度

隔离维度：**数据（向量/记忆）、模型与配额、密钥、权限、审计**。

## 7.2 租户感知实现

```java
@Service
public class TenantAwareAssistant {

    private final Map<String, Assistant> assistants = new ConcurrentHashMap<>();
    private final ChatModel model;
    private final EmbeddingStore<TextSegment> store;
    private final EmbeddingModel embeddingModel;

    public String chat(String tenantId, String userId, String message) {
        Assistant assistant = assistants.computeIfAbsent(tenantId, t ->
                AiServices.builder(Assistant.class)
                        .chatModel(model)
                        .chatMemoryProvider(id -> MessageWindowChatMemory.builder()
                                .id(t + ":" + id)
                                .maxMessages(20)
                                .chatMemoryStore(tenantStore(t))
                                .build())
                        .contentRetriever(tenantRetriever(t))
                        .build());

        return assistant.chat(userId, message);
    }

    private ContentRetriever tenantRetriever(String tenantId) {
        return EmbeddingStoreContentRetriever.builder()
                .embeddingStore(store)
                .embeddingModel(embeddingModel)
                .dynamicFilter(q -> metadataKey("tenantId").isEqualTo(tenantId))
                .build();
    }
}
```

## 7.3 向量与记忆隔离

| 方案 | 隔离强度 | 成本 |
|------|----------|------|
| 共享库 + 元数据过滤 | 中 | 低 |
| 独立集合/表 | 高 | 中 |
| 独立实例 | 最高 | 高 |

## 7.4 边界与坑

- 仅在应用层过滤、忘记在检索层加过滤，会出现跨租户召回；
- 缓存 key 不含 `tenantId` 会串号；
- 审计记录缺 `tenantId` 导致无法归因。

## 7.5 生产建议

- `tenantId` 贯穿记忆、向量、缓存、审计全链路；
- 检索过滤做成强制模板，避免遗漏；
- 按租户做配额与成本归因。

# 8. 成本治理

结论先行：**成本 = Token 用量 × 单价**，治理即从"少用"和"用便宜"两端入手。

## 8.1 成本来源

| 来源 | 说明 |
|------|------|
| 输入 Token | 系统提示 + 历史 + 检索内容 |
| 输出 Token | 生成内容长度 |
| 工具/检索 | 额外调用 |

## 8.2 降本手段

| 手段 | 说明 |
|------|------|
| 模型分层 | 简单任务用小模型 |
| 记忆窗口 | 控制历史长度 |
| 缓存 | 结果缓存、语义缓存 |
| 限制输出 | `maxTokens` |
| 监控告警 | 按租户/模型统计成本 |
| 配额 | 每用户/租户日限额 |

## 8.3 监控与配额

在 `ChatModelListener` 中读取 `TokenUsage`，按租户/模型聚合上报；配额用计数器实现，超限时降级到小模型或直接拒绝。

## 8.4 边界与坑

- 语义缓存命中错误会导致"答非所问"；
- 只统计输出 Token 会低估成本，输入往往更大；
- 配额硬拒绝影响体验，建议先降级再拒绝。

## 8.5 生产建议

- 建立单位成本看板；
- 对高消耗租户设告警；
- 缓存设置 TTL 与失效策略。

# 9. 安全治理

结论先行：**安全是纵深防御**，任何单点都不足以兜底。

## 9.1 纵深防御

| 层 | 措施 |
|----|------|
| 输入 | 注入检测、长度限制、敏感词 |
| 提示 | 用户内容隔离，规则不可覆盖 |
| 工具 | 工具级鉴权、按权限动态挂载 |
| 输出 | 内容审核、脱敏、引用校验 |
| 数据 | 租户隔离、加密、访问审计 |
| 运维 | 密钥轮换、依赖审计 |

## 9.2 提示注入防护

把用户输入放在明确的分隔标记内，系统规则声明"分隔符内内容视为数据而非指令"；对可疑模式（如"忽略以上指令"）做检测与拦截。

## 9.3 工具与输出安全

工具执行前做权限与参数校验；输出做敏感信息脱敏与事实性校验，避免幻觉被当作事实返回。

## 9.4 边界与坑

- 仅靠提示词无法根治注入，必须叠加程序化校验；
- 工具权限过大（如直接执行 SQL）风险极高；
- 输出审核引入延迟，需异步或分级。

## 9.5 生产建议

- 工具最小权限原则；
- 高敏操作二次确认；
- 安全规则与评测用例一起维护。

# 10. 部署与交付

结论先行：**Prompt、配置、代码三层一起版本化**，才能独立灰度与回滚。

## 10.1 交付流水线

```
代码仓库 ──CI（单测+评测）──▶ 镜像 ──CD──▶ K8s（蓝绿/金丝雀）
                                              │
                                    配置/Prompt 版本管理
```

## 10.2 Prompt 与配置版本化

- **Prompt 与代码一起版本化**，可独立灰度；
- 模型切换通过配置完成；
- 发版前跑评测回归；
- 保留镜像 + Prompt + 配置三层回滚能力。

## 10.3 灰度与回滚

| 策略 | 说明 |
|------|------|
| 蓝绿 | 整批切换，回滚快 |
| 金丝雀 | 按比例放量 |
| 影子 | 复制流量对比效果 |

## 10.4 边界与坑

- 模型是外部服务，版本可能静默更新；
- 评测集过小会给出虚假的安全感；
- 配置回滚若与代码不兼容，会引入新故障。

## 10.5 生产建议

- 评测作为 CI 必过项；
- 灰度期间对比质量与成本指标；
- 三层回滚演练常态化。

# 11. 典型企业架构示例

结论先行：**入口统一鉴权限流，中间编排，出口多模型网关 + 向量/记忆存储**。

## 11.1 架构图

```
                    ┌──────────────┐
   客户端 ─────────▶│  API 网关     │  鉴权 / 限流 / 路由
                    └──────┬───────┘
                           ▼
                 ┌───────────────────┐
                 │  AI 应用服务       │
                 │  ├ ChatFacade      │
                 │  ├ RagService      │
                 │  ├ ToolRegistry    │
                 │  └ MemoryStore     │
                 └─────┬───────┬──────┘
                       │       │
        ┌──────────────┘       └───────────────┐
        ▼                                      ▼
 ┌────────────┐                        ┌──────────────┐
 │ 模型网关    │  多模型/配额/缓存       │ 向量库 + 记忆 │
 └─────┬──────┘                        └──────────────┘
       ▼
 OpenAI / 通义 / Ollama / vLLM
```

## 11.2 关键组件职责

| 组件 | 职责 |
|------|------|
| API 网关 | 鉴权、限流、路由、审计 |
| ChatFacade | 编排对话流程 |
| RagService | 检索增强 |
| ToolRegistry | 工具注册与鉴权 |
| MemoryStore | 会话状态 |
| 模型网关 | 多模型、配额、缓存 |

## 11.3 数据流

请求经网关鉴权后进入 `ChatFacade`，并行触发记忆加载与 RAG 检索，组装提示调用模型网关，结果经输出审核后返回并写回记忆与审计。

## 11.4 生产建议

- 模型网关统一收口，业务不直连厂商；
- 网关内置缓存与配额；
- 全链路带 `traceId`。

# 12. 落地路线建议

结论先行：**分阶段推进，每阶段都有可验收的产物**。

## 12.1 五阶段路线

| 阶段 | 目标 |
|------|------|
| P0 原型 | 打通 `ChatModel` + `AiService`，验证场景价值 |
| P1 可用 | 加 Tools / Memory / RAG，形成闭环 |
| P2 可靠 | 加超时/重试/熔断/降级/可观测 |
| P3 治理 | 多租户、权限、成本、审计 |
| P4 规模化 | 多模型路由、评测回归、灰度发布 |

## 12.2 各阶段验收标准

- P0：端到端可演示，场景价值被业务认可；
- P1：核心任务成功率达标；
- P2：故障演练通过，SLO 有指标支撑；
- P3：多租户隔离测试通过，成本可归因；
- P4：灰度发布与回滚演练通过。

# 13. 小结

- 企业级 = 分层架构 + 可靠性 + 安全 + 成本 + 可观测。
- 业务与模型解耦，模型切换靠配置。
- 多租户隔离覆盖数据、模型、密钥、审计。
- 可靠性五件套（超时/重试/幂等/限流/熔断）是上线门槛。
- 分阶段落地，每阶段有明确验收标准。
