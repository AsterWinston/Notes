# 1. 规划的基本元素

规划（Planning）问题的本质是：**给定初始状态、目标状态与一组动作，求出一条从初始状态到目标状态的动作序列**。Embabel 把这一过程封装为 GOAP（Goal-Oriented Action Planning，目标导向动作规划）引擎。开发者只需声明"世界是什么样、想要什么样、能做哪些事"，规划器（Planner）负责搜索路径。

本节拆解规划的四个基本元素——状态、目标、动作、规划问题，并给出形式化定义。

## 1.1 状态（State）

结论先行：状态是世界在当前时刻的快照，通常用一组布尔字段或键值对表示；规划器只关心状态是否满足前置条件（Precondition）与目标（Goal）。

### 1.1.1 状态的定义与表示

状态是对"世界当前样子"的最小抽象。它不追求还原真实世界，只保留规划所需的信息。

```
State（状态）：世界当前的样子
  { hasWeather: false, hasBudget: false, planReady: false }
```

状态字段通常有两类：

| 字段类型 | 作用 | 示例 |
|----------|------|------|
| 布尔标志 | 表示某条件是否成立，供前置条件判断 | `hasWeather` |
| 值对象 | 保存中间结果，供动作读取 | `weather`、`plan` |

在 Embabel 中，状态由 `AgentContext` 承载，通过 `setState` / `getState` 读写。规划器看到的只是"键是否存在、值是否满足条件"，因此布尔标志应尽量独立、语义清晰。

### 1.1.2 状态字段的取舍

状态不是越多越好：字段过多会带来**规划空间膨胀**（组合数随字段数指数增长）与**一致性风险**（多字段表达同一事实易矛盾）。

生产建议：只放"会被前置条件或目标引用"的字段；用单一字段表达单一事实；值对象（如天气文本）与标志位（`hasWeather`）分离，便于判断。

## 1.2 目标（Goal）

结论先行：目标是期望达成的状态，规划器从目标出发反向推导需要哪些动作。目标应可判定（可判断是否达成），否则规划器无法终止。

### 1.2.1 目标的表达

目标通常表示为一个或多个"状态约束"：

```
Goal（目标）：期望的状态
  { planReady: true }
```

也可以用类声明表达，便于携带语义：

```java
@Goal(name = "生成旅行行程")
public class TravelPlanGoal {
    // 目标状态：planReady = true
}
```

### 1.2.2 目标的满足判定

规划器需要回答一个问题："当前状态是否已经满足目标？"因此目标必须可判定。

| 目标形式 | 是否可判定 | 说明 |
|----------|-----------|------|
| `planReady == true` | 是 | 布尔比较，明确 |
| `plan != null` | 是 | 存在性判断 |
| "行程让用户满意" | 否 | 主观、无客观判定 |
| "尽可能好" | 否 | 无阈值，无法终止 |

反例：把目标写成"生成一个高质量的行程"会导致规划器无法判断何时停止。正确做法是把它拆成可判定的标志，例如 `planReady == true`，质量评估另设评估动作。

## 1.3 动作（Action）

结论先行：动作是改变状态的最小操作单元，由前置条件（何时可执行）和效果（执行后状态如何变化）声明。规划器把这些声明当作"契约"来搜索路径。

```
Action（动作）：改变状态
  Action: 查天气
    Precondition: { }              （无条件）
    Effect: { hasWeather: true }

  Action: 生成行程
    Precondition: { hasWeather: true, hasBudget: true }
    Effect: { planReady: true }
```

### 1.3.1 前置条件（Precondition）

前置条件是动作可执行的前提，规划器用它判断"某动作能否在某状态下触发"。前置条件写得过松会导致规划出不可执行的路径；写得过紧会导致无解。

| 前置条件写法 | 后果 |
|--------------|------|
| 缺失必要前置 | 规划出无法执行的步骤，运行时失败 |
| 前置过严 | 搜索不到路径，规划失败 |
| 前置与代码实际检查不一致 | 契约失真，行为不可预测 |

生产建议：前置条件必须与动作内部的实际检查保持一一对应，并用单元测试固化。

### 1.3.2 效果（Effect）

效果是动作执行后的状态变化，规划器据此推演。效果是声明式的：规划器不理解动作内部逻辑，只信任你声明的效果。

关键原则：**声明效果必须与实际写入的状态完全一致**。若动作实际写了 `hasWeather` 却没声明，规划器会认为该字段未变化，从而规划出错误序列。

### 1.3.3 动作代价（Cost）

当多条路径都能达成目标时，规划器需要依据代价（Cost）选择较优路径。

```
路径 A：查天气 → 查预算 → 生成行程   （代价 3）
路径 B：查缓存 → 生成行程            （代价 2，若缓存可用）
```

代价可以是步数、时间、金额或 token 数。默认按步数计，可自定义。

## 1.4 规划问题形式化

结论先行：一个规划问题可形式化为四元组（初始状态、动作集合、目标、代价函数），规划即在该空间中搜索。

### 1.4.1 四元组定义

```
规划问题 P = (S0, A, G, C)
  S0：初始状态集合
  A ：可用动作集合（含前置条件与效果）
  G ：目标状态约束
  C ：动作代价函数
解 = 动作序列 [a1, a2, ..., an]，从 S0 出发依次执行后满足 G
```

### 1.4.2 完整示例

```
S0 = { hasWeather: false, hasBudget: false, planReady: false }
G  = { planReady: true }
A  = { 查天气, 查预算, 生成行程 }

查天气：Pre {},               Effect { hasWeather: true }
查预算：Pre {},               Effect { hasBudget: true }
生成行程：Pre { hasWeather, hasBudget }, Effect { planReady: true }

解 = [查天气, 查预算, 生成行程]
```

# 2. 规划过程

规划器的任务是"搜索"。搜索方向决定了算法特性。Embabel 以反向搜索为主，辅以前向搜索与启发式优化。

## 2.1 反向搜索（Regression Planning）

结论先行：反向搜索从目标出发，寻找"能产生该效果的动作"，再递归求解该动作的前置条件，直到所有前置条件都被初始状态满足。

### 2.1.1 从目标倒推

```
目标：planReady = true
  ↓ 需要"生成行程"
前置：hasWeather && hasBudget
  ↓ 需要"查天气"和"查预算"
前置：无
  ↓
得到动作序列：
  1. 查天气
  2. 查预算
  3. 生成行程
```

反向搜索的优点是"目标相关"：它只展开与目标有关的动作，忽略无关动作，搜索空间通常更小。

### 2.1.2 递归与子目标

反向搜索本质是递归：把目标分解为子目标，直到子目标被初始状态满足。若某子目标无法被任何动作的效果产生，则规划失败。

```
求解(G):
  if S0 满足 G: return []
  选择能产生 G 中某效果的动作 a
  子目标 = a.preconditions
  子序列 = 求解(子目标)
  if 子序列 成功: return 子序列 + [a]
  else: 回溯，尝试其他动作
```

## 2.2 前向搜索（Forward Search）

结论先行：前向搜索从初始状态出发，不断应用可用动作，直到某状态满足目标。它更接近"模拟执行"，但搜索空间通常更大。

### 2.2.1 从初始状态推进

```
S0 {hasWeather=false, hasBudget=false}
  → 查天气 → {hasWeather=true}
  → 查预算 → {hasWeather=true, hasBudget=true}
  → 生成行程 → {planReady=true}  命中目标
```

### 2.2.2 A* 与启发函数

前向搜索可结合 A*（A-Star，A 星搜索）与启发函数（Heuristic）加速，优先级 `f(n) = g(n) + h(n)`：`g(n)` 为从起点到 n 的实际代价，`h(n)` 为从 n 到目标的估计代价。启发函数需满足可采纳性（Admissible，不高估）才能保证最优解。

## 2.3 两种搜索对比

| 维度 | 反向搜索 | 前向搜索 |
|------|----------|----------|
| 起点 | 目标 | 初始状态 |
| 搜索空间 | 通常较小 | 通常较大 |
| 适合 | 目标明确、动作多 | 动作少、目标多 |
| 缺点 | 多效果动作处理复杂 | 易爆炸 |

```
        ┌─────────────┐
        │ 目标: 行程   │
        └──────┬──────┘
               │ 需要
        ┌──────▼──────┐
        │  生成行程    │
        └──────┬──────┘
        ┌──────┴──────┐
        ▼             ▼
   ┌─────────┐  ┌─────────┐
   │ 查天气   │  │ 查预算   │
   └─────────┘  └─────────┘
```

## 2.4 完整规划示例

```java
// 1. 定义目标
Goal goal = Goal.of("planReady", true);

// 2. 构造初始状态
AgentContext ctx = AgentContext.builder()
        .withState("hasWeather", false)
        .withState("hasBudget", false)
        .withState("planReady", false)
        .build();

// 3. 调用规划器搜索动作序列
Plan plan = planner.plan(goal, ctx);

// 4. 打印规划结果，便于调试
plan.actions().forEach(a -> log.info("planned action: {}", a.name()));
```

# 3. 定义动作

结论先行：动作通过 `@Action` 注解声明名称、前置条件与效果，方法体实现真实逻辑。声明与实现必须严格一致。

## 3.1 @Action 注解

### 3.1.1 注解参数

| 参数 | 类型 | 含义 |
|------|------|------|
| `name` | String | 动作名称，用于日志与调试 |
| `preconditions` | String[] | 前置条件字段名 |
| `effects` | String[] | 效果字段名 |
| `cost` | double | 动作代价（可选） |

### 3.1.2 命名与描述

动作名应使用动宾结构（如"查天气"），便于日志阅读。避免同名动作，否则规划日志难以区分。

## 3.2 动作的输入与输出

### 3.2.1 参数注入

动作方法可声明参数，由上下文自动注入：

```java
@Action(
        name = "查天气",
        preconditions = {},
        effects = {"hasWeather"})
public void checkWeather(AgentContext ctx, String city) {
    String weather = weatherService.get(city);
    ctx.setState("weather", weather);
    ctx.setState("hasWeather", true);
}
```

### 3.2.2 状态读写

| 操作 | API | 说明 |
|------|-----|------|
| 读取 | `ctx.getState("key")` | 取中间结果 |
| 写入 | `ctx.setState("key", value)` | 保存结果与标志 |
| 判断 | `ctx.hasState("key")` | 检查是否存在 |

## 3.3 动作类型

| 类型 | 实现方式 | 确定性 | 适用 |
|------|----------|--------|------|
| 原生动作 | 纯 Java 逻辑 | 确定 | 计算、校验 |
| LLM 动作 | 调用模型 | 非确定 | 判断、生成 |
| 工具动作 | 调用外部 API | 依赖外部 | 检索、集成 |

## 3.4 边界与反例

反例一：声明了 `effects = {"hasWeather"}`，但方法体忘记 `setState("hasWeather", true)`。规划器认为效果成立，实际状态未变，后续动作读取到空值。

反例二：动作有副作用（如发送邮件）但被规划器重复调用。GOAP 搜索可能多次"预演"动作，真实执行必须与规划分离。

生产建议：动作实现保持幂等，副作用放在执行阶段而非规划阶段。

# 4. 定义目标

结论先行：目标声明"期望达到的状态"，必须可判定。Embabel 支持注解式与 API 式两种定义。

## 4.1 @Goal 注解

```java
@Goal(name = "生成旅行行程")
public class TravelPlanGoal {
    // 目标状态：planReady = true
}
```

注解适合把目标作为领域概念固化，便于复用与文档化。

## 4.2 目标状态表达

### 4.2.1 单条件目标

```java
Goal goal = Goal.of("planReady", true);
```

适合单一终态的场景。

### 4.2.2 多条件目标

```java
Goal goal = Goal.builder()
        .condition("planReady", true)
        .condition("budgetChecked", true)
        .build();
```

多条件目标要求所有条件同时满足，规划器会合并前置需求。

## 4.3 目标优先级与约束

当存在多个目标时，可设定**优先级**（多目标取舍顺序）、**硬约束**（不可违反的边界，如预算上限）与**软约束**（尽量满足，可妥协），避免生成不可接受的方案。

## 4.4 边界与反例

反例：目标之间互相冲突（如"最便宜"与"最舒适"同时最大化）。此时规划器可能无解或结果不稳定。生产建议：把冲突目标显式排序或加权重，而不是同时声明为硬目标。

# 5. 规划执行

结论先行：规划与执行是两个阶段。规划器只产出动作序列，执行器负责真实调用。分离二者是可靠性的基础。

## 5.1 Planner API

### 5.1.1 plan 方法

```java
// 规划器自动搜索动作序列
Plan plan = planner.plan(Goal.travelPlan(), initialState);
```

### 5.1.2 规划器配置

```yaml
embabel:
  planner:
    max-depth: 20          # 最大搜索深度
    max-actions: 100       # 最大动作数
    strategy: regression   # regression | forward
    timeout-ms: 2000       # 规划超时
```

## 5.2 执行器（Executor）

### 5.2.1 顺序执行

```java
// 执行
for (Action action : plan.actions()) {
    executor.execute(action);
}
```

### 5.2.2 失败处理

| 失败类型 | 处理策略 |
|----------|----------|
| 瞬时错误 | 重试（幂等前提下） |
| 前置不满足 | 触发重规划 |
| 不可恢复 | 终止并上报 |

## 5.3 端到端示例

```java
public PlanResult runTravelPlan(String city) {
    AgentContext ctx = AgentContext.builder()
            .withInput("city", city)
            .build();

    Goal goal = Goal.of("planReady", true);
    Plan plan = planner.plan(goal, ctx);

    for (Action action : plan.actions()) {
        try {
            executor.execute(action, ctx);
        } catch (ActionFailedException e) {
            log.warn("action failed: {}, replanning", action.name(), e);
            plan = planner.replan(goal, ctx);
        }
    }
    return new PlanResult(ctx.getState("plan"));
}
```

## 5.4 生产建议

规划阶段禁止副作用，副作用只允许在执行阶段发生；每个动作设置独立超时；记录规划路径与执行路径，二者可能因重规划而不同。

# 6. 动态重规划

结论先行：环境变化时，GOAP 不需要修改流程定义，而是重新搜索路径。这是它相对固定编排最大的优势。

## 6.1 触发时机

| 触发源 | 示例 |
|--------|------|
| 动作失败 | 天气 API 超时 |
| 状态意外变化 | 预算被外部修改 |
| 约束更新 | 用户临时加限制 |

## 6.2 重规划机制

### 6.2.1 局部修复

只重规划失败点之后的子路径，保留已成功的前缀，代价较小。

### 6.2.2 全局重规划

从当前状态重新求解整个目标，适合环境发生根本变化的情况，但代价更大。

## 6.3 示例

```
环境变化 → 重新规划
  例：查天气失败 → 规划器寻找替代路径

原路径：查天气 → 查预算 → 生成行程
新路径：查缓存天气 → 查预算 → 生成行程

重规划调用：planner.replan(goal, ctx)
```

## 6.4 边界与反例

反例：环境频繁抖动导致反复重规划（规划抖动）。生产建议：加入重规划次数上限与退避（Backoff），并对"稳定状态"做缓存。

> GOAP 的优势：**目标不变，路径可自适应**。

# 7. 与传统编排的差异

结论先行：传统编排（Graph）是"流程驱动"，路径由开发者写死；GOAP 是"目标驱动"，路径由规划器搜索。二者不是替代关系，而是适用场景不同。

## 7.1 对比表

| 维度 | Graph 编排 | GOAP |
|------|-----------|------|
| 定义 | 显式节点与边 | 目标 + 动作 |
| 路径 | 固定 | 动态搜索 |
| 变化响应 | 需改图 | 自动适应 |
| 调试 | 易 | 较难 |

## 7.2 决策矩阵

| 需求 | 推荐 |
|------|------|
| 流程稳定、审计严格 | Graph |
| 目标明确、路径多变 | GOAP |
| 需要确定性时延 | Graph |
| 需要自动适应环境 | GOAP |

## 7.3 混合模式

实践中常采用混合：外层用 Graph 固定关键阶段，内层用 GOAP 处理不确定的子任务。

```
Graph: 鉴权 → [GOAP 子规划] → 落库
                 ↑
          目标导向、可重规划
```

# 8. 生产注意事项

结论先行：GOAP 的灵活性以可预测性为代价。生产的核心工作是"给搜索划定边界"。

## 8.1 规划空间爆炸

### 8.1.1 限制动作数量

动作数每增加一个，组合路径可能成倍增长。按领域分组，单次规划只暴露必要动作。

### 8.1.2 分层规划

把大目标拆成多个小目标，分层规划，降低单次搜索规模。

```
高层目标 → 子目标A → 子目标B
              ↓        ↓
           局部动作   局部动作
```

## 8.2 不可预测性

| 风险 | 建议 |
|------|------|
| 路径不唯一 | 固定代价函数、加约束 |
| 结果难复现 | 记录种子与规划日志 |
| 动作副作用 | 规划与执行分离 |

## 8.3 无终止风险

必须设置步数上限、深度上限与超时，否则规划器可能在环中反复搜索。

## 8.4 可调试性

记录每一步规划决策（选择了哪个动作、为何回溯），保留最终动作序列便于复盘，并对关键前置条件编写单元测试。

## 8.5 安全与权限

动作级鉴权：不同角色可见的动作集合不同；目标级约束：防止规划出越权操作。

| 风险 | 建议 |
|------|------|
| 规划空间爆炸 | 限制动作数 |
| 不可预测 | 加约束与验证 |
| 无终止 | 步数上限 |
| 调试难 | 记录规划过程 |

# 9. 小结

## 9.1 核心要点

- GOAP 用状态、目标、动作、前置条件描述规划问题。
- 规划器从目标反向搜索动作序列，也可前向搜索配合启发式。
- 声明（前置条件/效果）必须与实现严格一致。
- 环境变化时自动重规划，局部修复与全局重规划按需选择。

## 9.2 落地清单

- 比 Graph 更灵活，但可预测性较低。
- 需限制动作数与步数。
- 做好规划日志与动作级鉴权。
