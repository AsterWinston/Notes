# 1. 三种方式

结论先行：按"给不给示例、给多少示例"，提示可分为**零样本（Zero-shot）、少样本（Few-shot）、多样本（Many-shot）**三种方式。

## 1.1 方式总览

### 1.1.1 三种方式对比

| 方式 | 说明 | 适用 |
|------|------|------|
| 零样本（Zero-shot） | 只给指令 | 模型已掌握的任务 |
| 少样本（Few-shot） | 给几个示例 | 格式特殊/模型不熟 |
| 多样本（Many-shot） | 大量示例 | 复杂模式（占 Token） |

### 1.1.2 本质区别

三种方式的差别，在于用多少"输入-输出样例"去约束模型的输出分布。示例越多，模式越强，但 Token 成本也越高。

## 1.2 如何选择

### 1.2.1 选择依据

```
任务简单、模型已掌握        → 零样本
格式特殊、需要对齐输出      → 少样本（3~5 个）
模式复杂、类别很多          → 多样本或动态示例
```

```
输入任务
   │
   ├─ 模型已掌握？── 是 ─▶ 零样本
   │                 └─ 否 ─▶ 需要示例
   │
   └─ 输出格式特殊？─ 是 ─▶ 少样本（3~5）
                      └─ 类别很多 ─▶ 动态示例
```

## 1.3 边界与坑

- 对简单任务滥用少样本，白白增加 Token；
- 对格式特殊任务只用零样本，输出格式不稳定；
- 用"示例数量"代替"示例质量"，越多反而越差。

## 1.4 生产建议

- 先用零样本建立基线，不够再加示例；
- 少样本从 3 个起步，按评测决定是否增加；
- 类别多时优先动态选择而非全量堆入。

# 2. 零样本

结论先行：零样本只给指令、不给示例，适用于**模型在预训练中已经掌握**的任务。

## 2.1 定义与适用

### 2.1.1 代码

```java
@SystemMessage("判断下面文本的情感，只输出 POSITIVE 或 NEGATIVE。")
String analyze(String text);
```

适用：任务简单、模型训练时见过。

## 2.2 机制

### 2.2.1 依赖预训练

零样本依赖预训练阶段学到的通用能力与指令遵循（Instruction Following）。任务越常见、输出空间越简单，零样本越可靠。

| 任务特征 | 零样本表现 |
|----------|------------|
| 常见分类 | 好 |
| 自定义标签 | 差 |
| 固定格式 | 一般 |
| 复杂推理 | 差 |

## 2.3 边界与坑

- 输出空间复杂（如自定义标签）时，零样本容易漂移；
- 隐含的格式要求（大小写、标点）零样本难以稳定；
- 任务描述模糊时，零样本的方差明显更大。

## 2.4 生产建议

- 零样本先明确输出集合与格式；
- 用少量测试集确认稳定性，再决定是否加示例；
- 对稳定性要求高的任务默认配低温。

# 3. 少样本

结论先行：少样本通过**模式匹配**显著提升一致性，尤其对格式要求严格的任务。

## 3.1 定义与适用

### 3.1.1 代码

```java
@SystemMessage("""
        判断情感，只输出 POSITIVE / NEGATIVE / NEUTRAL。

        示例：
        这个产品太棒了 → POSITIVE
        质量很差，退货了 → NEGATIVE
        还行吧，凑合 → NEUTRAL
        """)
```

> 少样本通过**模式匹配**显著提升一致性，尤其对格式要求严格的任务。

## 3.2 为什么有效

### 3.2.1 模式匹配优于规则描述

模型更擅长"照着样例做"而非"按一句话推理规则"。示例把抽象要求具体化，等于直接给模型展示了期望的输入-输出映射。

## 3.3 边界与坑

- 示例只覆盖部分类别，未覆盖的类别表现差；
- 示例格式与真实输入不一致，模型难以迁移；
- 示例过多会挤占上下文，也可能导致"过拟合示例"。

## 3.4 生产建议

- 每个类别至少给一个示例；
- 示例格式与线上输入严格一致；
- 从 3~5 个高质量示例起步。

# 4. 示例的选择

结论先行：示例选择遵循**覆盖类别、含边界、格式一致、数量适中、顺序合理**五条原则。

## 4.1 五条原则

| 原则 | 说明 |
|------|------|
| 覆盖各类别 | 每类至少一个 |
| 边界示例 | 包含难判断的 |
| 格式一致 | 输入输出格式统一 |
| 数量适中 | 3~5 个通常足够 |
| 顺序合理 | 从简单到复杂 |

## 4.2 代码示例

### 4.2.1 工单分类

```java
@SystemMessage("""
        分类工单类型，输出 ORDER/REFUND/TECH/OTHER。

        示例：
        我要退货 → REFUND
        订单还没到 → ORDER
        系统报错了 → TECH
        你们几点上班 → OTHER
        """)
```

## 4.3 边界与坑

- 缺少边界示例，模型在模糊输入上乱猜；
- 示例格式不统一，输出格式随之混乱；
- 只选"典型"示例，忽略罕见但重要的类别。

## 4.4 生产建议

- 建立示例库，按类别维护；
- 每类至少一个，边界样本必含；
- 示例与期望输出一起做校验。

# 5. 示例顺序的影响

结论先行：**LLM 对示例顺序敏感**，最后几个示例影响更大（recency）。

## 5.1 Recency 效应

### 5.1.1 现象

```
LLM 对示例顺序敏感：
- 最后几个示例影响更大（recency）
- 把最重要的示例放最后
- 避免示例顺序带来的偏见
```

### 5.1.2 放置策略

把最典型、最希望模型模仿的示例放在最后，把边缘情况放在前面。

## 5.2 代码

```java
// 把最典型的示例放最后
"""
示例1：边缘情况 → 结果
示例2：常见情况 → 结果
示例3：最典型案例 → 结果    ← 放最后
"""
```

## 5.3 边界与坑

- 示例顺序固定后，会引入系统性偏见；
- 把边缘示例放最后，模型可能模仿边缘行为；
- 顺序带来的差异需用评测确认，不能凭感觉。

## 5.4 生产建议

- 最重要的示例放最后；
- 定期打乱顺序做对照，检查是否有顺序偏见；
- 把顺序策略写入示例库规范。

# 6. 示例污染

结论先行：**错误示例会污染模型输出**，示例必须经过校验。

## 6.1 污染来源

### 6.1.1 三类污染

```
错误示例会污染模型输出：
- 示例本身有错 → 模型学到错的
- 示例格式不一致 → 输出格式混乱
- 示例有偏见 → 模型继承偏见
```

## 6.2 代码反例

```java
// ❌ 示例格式不一致
"""
示例：
输入：你好 → 输出：GREETING
"谢谢" - "THANKS"          ← 格式不同
"""
```

> **示例必须经过校验**，与期望输出格式完全一致。

## 6.3 边界与坑

- 人工标注的示例也可能有错，需二次校验；
- 用线上日志自动挖示例时，可能把模型错误输出当标准答案；
- 示例中的偏见会被放大，尤其在敏感领域。

## 6.4 生产建议

- 示例入库前统一校验格式与正确性；
- 定期审查示例库，剔除过时/错误样本；
- 敏感领域做偏见审查。

# 7. 动态示例选择

结论先行：**动态示例（RAG-style few-shot）从示例库中选出与当前输入最相似的示例**，通常优于固定示例。

## 7.1 RAG-style Few-shot

### 7.1.1 流程

```
① 向量化当前输入
② 在示例库中检索最相似的 k 个示例
③ 拼装为 few-shot 提示
④ 追加当前输入，交给模型
```

### 7.1.2 代码

```java
public String buildFewShotPrompt(String input, int k) {
    // ① 向量检索相似示例
    List<Example> examples = exampleStore.searchSimilar(input, k);

    // ② 拼装
    StringBuilder sb = new StringBuilder("示例：\n");
    for (Example e : examples) {
        sb.append("输入：").append(e.input())
          .append("\n输出：").append(e.output()).append("\n\n");
    }
    sb.append("输入：").append(input).append("\n输出：");
    return sb.toString();
}
```

> 动态示例（RAG-style few-shot）比固定示例效果更好，尤其示例库大时。

## 7.2 与固定示例对比

| 维度 | 固定示例 | 动态示例 |
|------|----------|----------|
| 相关性 | 与输入无关 | 与输入相似 |
| Token | 稳定 | 稳定（k 固定） |
| 维护 | 改模板 | 维护示例库 |
| 效果 | 一般 | 通常更好 |

## 7.3 边界与坑

- 检索质量差会引入不相关示例，反而变差；
- 相似度不等于"有用度"，需按任务调优；
- 示例库规模大时，检索延迟与成本上升。

## 7.4 生产建议

- 为示例库维护向量索引并定期更新；
- 对检索出的示例做人工抽检；
- k 值通过评测确定，避免过大。

# 8. 少样本的代价

结论先行：示例不是越多越好，**3~5 个高质量示例通常优于 10 个普通示例**。

## 8.1 四类代价

| 代价 | 说明 |
|------|------|
| Token 占用 | 每个示例都进提示 |
| 成本增加 | 输入 Token 上升 |
| 上下文挤压 | 挤占其他内容空间 |
| 过拟合示例 | 模型只学会示例模式 |

## 8.2 数量权衡

### 8.2.1 3~5 个 vs 10 个

少量高质量示例能清晰传递模式；过量示例会挤占上下文、抬高成本，并让模型过度模仿示例表面形式。

| 示例数 | 效果 | Token 成本 |
|--------|------|------------|
| 0 | 基线 | 低 |
| 3~5 | 通常最佳 | 中 |
| 10+ | 可能下降 | 高 |

## 8.3 边界与坑

- 用数量弥补质量，是最常见的误区；
- 示例增多后效果不升反降，却未做对照实验；
- 忽略 Token 成本，导致线上费用超预期。

## 8.4 生产建议

- 从 3 个示例起步，按评测增减；
- 记录每次示例数量变更的效果与成本；
- 用动态选择替代无脑堆量。

# 9. 在框架中实现

结论先行：Spring AI 用参数占位注入动态示例，LangChain4j 用资源文件外置示例模板。

## 9.1 Spring AI

### 9.1.1 动态示例

```java
// Spring AI：动态示例
List<Example> examples = selectExamples(question);

String answer = chatClient.prompt()
        .system(s -> s.text("""
                分类用户意图。

                示例：
                {examples}
                """)
                .param("examples", formatExamples(examples)))
        .user(question)
        .call()
        .content();
```

## 9.2 LangChain4j

### 9.2.1 资源外置

```java
// LangChain4j
interface Classifier {
    @SystemMessage(fromResource = "/prompts/classify-with-examples.txt")
    Intent classify(String text);
}
```

## 9.3 边界与坑

- 示例硬编码进代码，无法按类别动态调整；
- 资源文件缺失时到运行才报错；
- 动态示例未做格式校验，可能污染提示。

## 9.4 生产建议

- 示例库与模板分离，模板只负责拼装；
- 资源文件纳入版本管理与测试；
- 注入前统一格式化与校验。

# 10. 生产注意事项

结论先行：少样本生产的风险集中在**示例质量、格式一致性与数量**三处。

## 10.1 风险清单

| 风险 | 建议 |
|------|------|
| 示例有错 | 校验示例 |
| 格式不一致 | 统一格式 |
| 示例过多 | 3~5 个 |
| 固定示例 | 动态选择相似示例 |
| 顺序随意 | 重要示例放最后 |
| 示例污染 | 定期审查 |

## 10.2 落地清单

```
上线前：□ 示例已校验  □ 格式统一  □ 数量经评测
        □ 边界示例齐全  □ 重要示例放最后
上线后：□ 监控示例命中  □ 审查示例库  □ 对照实验
```

## 10.3 边界与坑

- 只校验示例格式，不校验示例正确性；
- 示例库长期不更新，逐渐偏离真实分布；
- 动态选择未监控，检索质量下降无人察觉。

## 10.4 生产建议

- 示例入库走校验流水线；
- 定期用真实数据审查与更新示例库；
- 对动态示例的选择质量做监控。

# 11. 小结

结论先行：零样本、少样本、多样本的核心取舍，是**用多少示例换取多强的模式约束**；高质量示例远比数量重要。

## 11.1 核心结论

- 零样本适合模型已掌握的任务。
- 少样本通过模式匹配提升一致性，尤其格式严格的任务。
- 示例要覆盖类别、含边界、格式一致、3~5 个。
- 注意示例顺序与污染。
- 动态选择相似示例效果更好。

## 11.2 自检清单

| 检查项 | 自问 |
|--------|------|
| 方式 | 是否先用零样本建立基线？ |
| 覆盖 | 每类是否都有示例？ |
| 边界 | 是否包含难判断的样本？ |
| 格式 | 示例与线上输入是否一致？ |
| 顺序 | 最重要示例是否放最后？ |
| 质量 | 示例是否经过校验与审查？ |
