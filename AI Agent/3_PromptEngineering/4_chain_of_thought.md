# 1. 什么是 CoT

## 1.1 定义与直觉

### 1.1.1 一句话定义

**思维链（Chain-of-Thought，CoT）** 是一种提示（Prompting）技术：让模型在输出最终答案之前，先生成一段显式的中间推理步骤。

结论先行：CoT 不改变模型本身，而是改变"输出结构"。它把"一步生成答案"变成"多步生成中间步骤"，从而让推理类任务的准确率显著提升。

直觉类比：人类心算 `23 × 47` 时若不打草稿容易出错；把过程写下来，每一步都很简单，错误率自然下降。CoT 就是让模型"打草稿"。

### 1.1.2 与微调、工具调用的区别

| 手段 | 改变对象 | 成本 | 适用 |
|------|----------|------|------|
| CoT 提示 | 输出结构 | 低（仅 Token） | 通用推理 |
| 微调（Fine-tuning） | 模型权重 | 高 | 领域固化 |
| 工具调用（Tool Use） | 外部能力 | 中 | 精确计算/检索 |

> CoT 是三者中门槛最低、见效最快的一种，但能力上限受模型本身约束。

## 1.2 一个可复现的对照实验

### 1.2.1 实验设置

固定模型、固定问题、固定 temperature，仅改变系统提示。

```
直接回答：
  问题：小明有 5 个苹果，吃了 2 个，又买了 3 个，现在有几个？
  模型：6 个          ← 可能算错，且无法判断错在哪

CoT：
  模型：
  1. 开始有 5 个
  2. 吃了 2 个，剩 3 个
  3. 又买 3 个，共 6 个
  答案：6 个          ← 更可靠，错误可定位
```

### 1.2.2 结果解读

- 直接回答的"6"可能来自记忆或猜测，无法验证。
- CoT 的每一步都可独立验算，出错时能定位到具体步骤。
- 结论：CoT 的价值不仅是"更准"，还有"可审计"。

## 1.3 输出结构差异

| 维度 | 直接回答 | CoT |
|------|----------|-----|
| 输出长度 | 短 | 长 |
| 中间步骤 | 无 | 有 |
| 可解释性 | 低 | 高 |
| 错误可定位 | 难 | 易（可看哪一步错） |
| Token 成本 | 低 | 高 |
| 适用任务 | 简单查询 | 多步推理 |

结论：CoT 用"更多 Token"换"更高准确率与可解释性"，是一种显式的成本收益权衡。

# 2. 为什么有效

## 2.1 机制拆解：中间 Token 的作用

```
CoT 把"一步生成答案"变成"多步生成中间步骤"：

  输入 → [中间步骤 1] → [中间步骤 2] → ... → [最终答案]
```

### 2.1.1 分步降低单步复杂度

每一步只涉及一个简单变换，模型在单步上的错误率远低于"一次算完"。

### 2.1.2 中间结果作为上下文

中间结论会被写入上下文，后续步骤可直接引用，形成"接力式"推理。

## 2.2 计算复杂度视角

结论先行：语言模型一次前向传播（Forward Pass）能完成的"串行计算步数"是固定的。CoT 通过生成更多 Token，为模型提供了更多的串行计算机会。

| 观点 | 含义 |
|------|------|
| 固定深度 | 单次前向传播的推理深度有限 |
| Token 即计算 | 每个生成的 Token 可视为一次额外计算 |
| CoT 扩深度 | 中间步骤等效于"把计算摊开" |
| 上限仍在 | 无法突破模型本身的能力上限 |

## 2.3 上下文自回归视角

```
自回归生成：每个新 Token 都能"看到"此前所有 Token

  直接回答：  [问][答]                      ← 答时无草稿可参考
  CoT：       [问][步1][步2][步3][答]        ← 答时参考了步1~3

因此"答案"不再依赖单次隐式计算，而是基于已写下的中间结论。
```

边界与坑：若中间步骤本身写错，后续会"继承"错误，CoT 无法自动纠正系统性错误。

| 视角 | 直接回答 | CoT |
|------|----------|-----|
| 参考信息 | 仅问题 | 问题 + 中间步骤 |
| 计算机会 | 一次 | 多次 |
| 可验证性 | 低 | 高 |

生产建议：对关键计算，把 CoT 与外部工具（计算器、检索）结合，而非只依赖模型自述。

# 3. 零样本 CoT

## 3.1 标准写法

### 3.1.1 触发语

只需一句触发语"让我们一步步思考"（Let's think step by step）：

```java
@SystemMessage("""
        解决问题时，请先分步推理，再给出结论。

        输出格式：
        推理过程：
        1. ...
        2. ...
        结论：...
        """)
```

### 3.1.2 输出格式约束

明确列出"推理过程 / 结论"两个字段，可显著提升输出稳定性。

> 零样本 CoT（Zero-shot CoT）实现简单，对推理类任务提升明显。

## 3.2 Java 实现（Spring AI 风格）

### 3.2.1 系统提示固化

```java
@Service
public class ZeroShotCotService {

    private final ChatClient chatClient;

    public ZeroShotCotService(ChatClient.Builder builder) {
        this.chatClient = builder
                .defaultSystem("""
                        你是严谨的推理助手。
                        回答时先分步推理，再给出结论。
                        格式：
                        推理过程：
                        1. ...
                        结论：...
                        """)
                .build();
    }

    public String solve(String question) {
        return chatClient.prompt()
                .user(question)
                .options(ChatOptions.builder()
                        .temperature(0.2)
                        .build())
                .call()
                .content();
    }
}
```

### 3.2.2 调用与参数

temperature 取低值（0.0~0.3）以稳定推理；需要多样性时另见 Self-Consistency。

## 3.3 触发词敏感性与边界

| 触发语 | 效果 |
|--------|------|
| 一步步思考 | 强，通用 |
| 让我们逐步分析 | 强 |
| 请仔细思考 | 中 |
| 直接回答 | 反而抑制 CoT |

边界与坑：

- 触发词对模型版本敏感，升级模型后需重新评测。
- 对简单任务使用零样本 CoT 会徒增成本而无收益。
- 某些模型（尤其小型模型）可能"复述问题"而非真正推理。

生产建议：把触发语固化进系统提示（System Message），并对输出做结构校验。

# 4. 少样本 CoT

## 4.1 示例设计原则

少样本 CoT（Few-shot CoT）给模型提供带推理过程的示例。

结论先行：示例质量比数量更重要。一个格式规范、推理正确的示例，通常胜过多个含糊示例。

### 4.1.1 格式一致

示例与目标输出结构完全一致，避免模型"模仿格式"时产生歧义。

### 4.1.2 覆盖边界

| 原则 | 说明 |
|------|------|
| 格式一致 | 示例与目标输出结构完全一致 |
| 步骤清晰 | 每步可验证，避免跳步 |
| 覆盖边界 | 含一个易错示例更好 |
| 数量适度 | 1~3 个通常足够 |
| 避免泄漏 | 示例不要与目标问题过于相似 |

## 4.2 Java 实现

```java
@SystemMessage("""
        解决数学问题，先推理再给答案。

        示例：
        问题：小明有 5 个苹果，吃了 2 个，又买了 3 个，现在有几个？
        推理：
        1. 开始 5 个
        2. 吃了 2 个：5 - 2 = 3
        3. 买了 3 个：3 + 3 = 6
        答案：6

        问题：{{question}}
        """)
```

## 4.3 与零样本对比

| 维度 | 零样本 CoT | 少样本 CoT |
|------|-----------|-----------|
| 提示长度 | 短 | 长 |
| 格式控制 | 弱 | 强 |
| 准确率 | 较高 | 更高（复杂任务） |
| Token 成本 | 低 | 高 |
| 维护成本 | 低 | 需维护示例 |

> 复杂、格式要求高的任务用少样本；通用推理先用零样本。

# 5. 显式推理 + 答案抽取

## 5.1 为什么要把推理与结论分开

```
问题：判断这段话的情感并解释。

输出：
情感分析：
- 关键词"太棒了" → 正面
- 语气积极 → 正面
- 无否定词 → 正面

结论：POSITIVE
```

结论先行：程序通常只关心最终结论，但需要推理过程用于审计与调试。因此应把两者拆成不同字段。

## 5.2 Java record 实现

### 5.2.1 LangChain4j 风格

```java
public record Analysis(String reasoning, String conclusion) {}

interface Analyzer {
    @UserMessage("""
            分析情感，先推理再给结论。
            输出 JSON：
            {"reasoning":"...","conclusion":"POSITIVE"}
            文本：{{it}}
            """)
    Analysis analyze(String text);
}
```

### 5.2.2 Spring AI 结构化输出

```java
public Analysis analyze(String text) {
    return chatClient.prompt()
            .user(u -> u.text("分析情感，先推理再给结论。文本：{t}").param("t", text))
            .call()
            .entity(Analysis.class);   // 框架负责映射为 record
}
```

## 5.3 解析失败的处理

| 失败 | 原因 | 对策 |
|------|------|------|
| JSON 不合法 | 模型夹带解释 | 要求纯 JSON，必要时用结构化输出 |
| 字段缺失 | 提示不清 | 明确字段名与取值域 |
| 取值越界 | 未约束枚举 | 提示中列出允许值 |

生产建议：优先使用框架的结构化输出（Structured Output）能力，而非手工解析字符串。

# 6. CoT 的适用场景

## 6.1 适合的任务特征

| 适合 | 原因 |
|------|------|
| 数学计算 | 多步运算易错 |
| 逻辑推理 | 需要显式链条 |
| 多步分析 | 中间结论依赖 |
| 因果判断 | 需要论证过程 |
| 需要解释 | 输出天然含推理 |

结论先行：判断标准是"答案是否依赖多个中间结论"。若是，CoT 通常有正收益。

## 6.2 不适合的任务

| 不适合 | 原因 |
|--------|------|
| 简单事实查询 | 一步即可 |
| 格式转换 | 无需推理 |
| 创意写作 | CoT 反而限制 |
| 简单情感分类 | 无需多步 |
| 延迟敏感场景 | 输出过长 |

## 6.3 决策清单

```
是否需要多步推理？
  否 → 不用 CoT
  是 → 是否需要可解释性？
          否 → 零样本 CoT
          是 → 零样本 + 结论抽取
  是否需要严格格式？
    是 → 少样本 CoT
```

> CoT 会增加输出 Token（成本与延迟），**简单任务不需要**。

# 7. 常见变体

## 7.1 变体总览

| 变体 | 说明 |
|------|------|
| Zero-shot CoT | "一步步思考" |
| Few-shot CoT | 带推理的示例 |
| Self-Consistency | 多条推理路径投票（见 `5_self_consistency.md`） |
| ToT | 树状探索（见 `7_tree_of_thoughts.md`） |
| Least-to-Most | 从简单到复杂 |
| Step-Back | 先抽象再具体 |

## 7.2 变体对比表

| 变体 | 采样次数 | 结构 | 成本 | 典型任务 |
|------|:--------:|------|:----:|----------|
| Zero-shot CoT | 1 | 线性 | 低 | 通用推理 |
| Few-shot CoT | 1 | 线性 | 中 | 格式敏感 |
| Self-Consistency | N | 并行多链 | 高 | 有唯一答案 |
| ToT | 多 | 树 | 很高 | 规划、搜索 |
| Least-to-Most | 1 | 递进 | 中 | 组合难题 |
| Step-Back | 1 | 抽象→具体 | 中 | 原理类问题 |

结论先行：变体的本质是"用多少额外 Token 换多少准确率"。从表中可见，成本与准确率提升大致同向，需按任务价值选择。

## 7.3 选型建议

结论先行：先用零样本 CoT 建立基线，不达标再逐级增加成本。

```
基线：零样本 CoT
  ↓ 不够
格式问题 → 少样本 CoT
  ↓ 不够
答案不稳 → Self-Consistency
  ↓ 不够
需要搜索/规划 → ToT
```

# 8. Step-Back 提示

## 8.1 原理

结论先行：Step-Back 提示让模型"退一步"，先回答一个更抽象、更通用的原理问题，再回到具体问题。

### 8.1.1 抽象问题设计

抽象问题应保留原问题的核心机制，去掉具体数值与情境。

### 8.1.2 回到具体

```
具体问题：为什么这个缓存策略导致内存泄漏？

Step-Back：
  抽象问题：缓存未设置过期与容量上限时通常会发生什么？
  抽象回答：无界缓存持续增长，旧条目无法回收 → 内存增长。
  具体应用：本策略未设置 TTL 与 maxSize，命中率上升后条目只增不减。
  结论：缺少 TTL 与容量上限导致内存泄漏。
```

## 8.2 Java 实现

```java
@UserMessage("""
        先思考这个问题的通用原理，再应用到具体问题。

        通用原理：
        ...
        具体应用：
        ...
        结论：
        ...
        问题：{{it}}
        """)
```

## 8.3 边界与坑

| 坑 | 说明 |
|----|------|
| 抽象过度 | 原理与问题脱节 |
| 成本翻倍 | 需两次思考 |
| 简单问题无益 | 一步可解时多余 |

生产建议：用于"原理型、解释型"问题；对事实型查询不必使用。

# 9. Least-to-Most

## 9.1 原理

结论先行：把复杂问题拆成从易到难的子问题，逐个解决，后续子问题可复用前面答案。

```
问题：一个 3 层嵌套的配置覆盖系统，最终生效值是什么？

子问题1（最简单）：单层覆盖规则是什么？
子问题2：两层叠加时优先级如何？
子问题3：三层叠加并含默认值时呢？
最终答案：综合子问题1~3 得出生效值。
```

## 9.2 Java 实现

```java
@UserMessage("""
        把问题拆解为从简单到复杂的子问题，逐个解决，最后综合。

        子问题1（最简单）：...
        子问题2：...
        ...
        最终答案：...
        问题：{{it}}
        """)
```

## 9.3 与分解式提示的区别

| 维度 | Least-to-Most | 普通分解 |
|------|---------------|----------|
| 顺序 | 严格由易到难 | 无要求 |
| 依赖 | 后续复用前序结果 | 各子问题独立 |
| 适用 | 组合爆炸类难题 | 并列任务 |

# 10. CoT 的局限

## 10.1 正确性不保证

### 10.1.1 不一致的推理

| 局限 | 说明 |
|------|------|
| 可能"假装"推理 | 推理过程与结论可能不一致 |
| 不保证正确 | 分步也可能每步都错 |

### 10.1.2 系统性错误

错误一旦写进中间步骤，会被后续继承，CoT 不会自动回溯修正。

> **CoT 提升概率，不是保证正确**。关键任务仍需工具验证。

## 10.2 成本与延迟

```
直接回答： 输出 ~10 token
CoT：      输出 ~200 token

成本 ≈ 20 倍（输出侧）
延迟 ≈ 生成更长的耗时
```

| 影响 | 说明 |
|------|------|
| 成本 | 输出 Token 显著增加 |
| 延迟 | 首字延迟可能不变，总延迟增加 |
| 吞吐 | 并发场景占用更多配额 |

## 10.3 反例

```
问题：1 + 1 等于几？

CoT 输出：
  1. 这是一个加法问题
  2. 1 加上 1
  3. 结果为 2
  结论：2
→ 完全正确，但纯属浪费。

问题：以下哪句是问候语？（A）你好（B）再见
CoT 反而可能引入噪声，直接分类更稳。
```

# 11. 生产注意事项

## 11.1 成本与延迟控制

### 11.1.1 预算与限流

| 风险 | 建议 |
|------|------|
| 简单任务也用 CoT | 按需使用 |
| 推理过长 | 限制最大输出长度 |
| 成本失控 | 设置 Token 预算与告警 |

### 11.1.2 缓存

对相同问题的推理结果可缓存，避免重复计费。

```java
@Cacheable(value = "cot", key = "#question")
public String solveCached(String question) {
    return chatClient.prompt().user(question).call().content();
}
```

| 缓存键 | 说明 |
|--------|------|
| 问题文本 | 相同问题直接命中 |
| 模型版本 | 换模型需失效 |
| 提示模板版本 | 改提示需失效 |

## 11.2 安全与合规

结论先行：推理过程可能泄露系统提示、内部规则或用户隐私。

| 风险 | 建议 |
|------|------|
| 推理泄露内部信息 | 对输出做过滤 |
| 推理与结论混在一起 | 分开输出，只回传结论 |
| 提示注入 | 对用户输入做隔离与转义 |

## 11.3 评测与灰度

| 风险 | 建议 |
|------|------|
| 无评测 | 验证 CoT 是否真提升 |
| 依赖 CoT 保证正确 | 关键任务用工具验证 |
| 一次性全量上线 | 灰度 + A/B 对比 |

```
灰度流程：
  小流量 A/B → 比较准确率/成本/延迟 → 达标再放量
```

| 指标 | 关注点 |
|------|--------|
| 准确率 | 是否真提升 |
| 成本 | 每请求 Token 数 |
| 延迟 | P50/P95 |
| 稳定性 | 输出格式失败率 |

# 12. 小结

- CoT 让模型分步推理，提升推理类任务准确率。
- 零样本 CoT 只需"一步步思考"。
- 少样本 CoT 给带推理的示例，效果更好。
- 推理与结论分开输出，便于程序消费。
- CoT 增加成本，简单任务不适用。
- Step-Back 与 Least-to-Most 是常见变体。
- 关键任务仍需工具验证，不能只依赖 CoT。
