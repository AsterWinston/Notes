# 1. 为什么 AI 需要合规

AI 应用天然涉及大量数据与生成内容，合规不再是“法务部门的事”，而是工程实现的一部分。

```
AI 应用涉及：个人数据、模型生成内容、数据跨境、行业监管
不合规的后果：行政处罚、民事赔偿、声誉损失、业务下架
```

## 1.1 合规风险来源

| 风险来源 | 说明 |
|----------|------|
| 个人数据 | 对话、记忆、画像中包含个人信息（PII） |
| 生成内容 | 模型可能生成违法、虚假、侵权内容 |
| 数据跨境 | 调用境外模型导致数据出境 |
| 行业监管 | 金融、医疗、政务有额外要求 |
| 训练数据 | 数据来源可能侵权或未授权 |

## 1.2 不合规的后果

- 行政处罚：罚款、责令整改、暂停服务。
- 民事赔偿：用户起诉数据侵权。
- 声誉损失：信任崩塌，客户流失。
- 业务下架：应用商店、平台方强制下架。

> 合规的收益不是“加分项”，而是“准入条件”。

## 1.3 合规、安全与隐私的关系

三者经常被混用，但关注点不同：

| 维度 | 关注点 | 典型手段 |
|------|--------|----------|
| 安全 | 防攻击、防泄露 | 认证、授权、加密 |
| 隐私 | 个人信息处理正当性 | 告知同意、最小必要 |
| 合规 | 满足法规与监管 | 备案、评估、审计 |

- 安全是技术能力，隐私是数据伦理与权利，合规是法律义务。
- 安全做得好，不代表合规；合规也不自动带来安全。
- 工程上应把三者纳入同一套设计，而不是分别打补丁。

# 2. 主要法规框架

## 2.1 中国法规

| 法规 | 核心要求 |
|------|----------|
| 个人信息保护法（PIPL） | 告知同意、最小必要、可删除 |
| 数据安全法 | 数据分级、出境评估 |
| 生成式 AI 服务管理办法 | 备案、内容安全、标识 |
| 网络安全法 | 网络运营者义务、等保 |

## 2.2 境外法规

| 法规 | 地区 | 核心要求 |
|------|------|----------|
| GDPR | 欧盟 | 数据主体权利、跨境限制 |
| AI Act | 欧盟 | 风险分级、透明度 |
| CCPA | 美国加州 | 知情权、删除权 |

## 2.3 法规对比

| 维度 | PIPL | GDPR | CCPA |
|------|------|------|------|
| 同意 | 明确同意 | 明确同意 | 选择退出 |
| 删除权 | 支持 | 支持 | 支持 |
| 出境 | 评估/合同/认证 | 充分性认定等 | 相对宽松 |
| 罚则 | 行政处罚 | 高额罚款 | 罚款+诉讼 |

> 多地区运营需按“最严格标准”实现，避免逐地区定制造成维护成本失控。

## 2.4 合规治理的组织与流程

合规不是一次性动作，需要明确角色与流程：

| 角色 | 职责 |
|------|------|
| 合规负责人 | 法规跟踪、风险评估、对外沟通 |
| 数据保护官（DPO） | 个人信息处理监督、影响评估 |
| 工程团队 | 落地同意、删除、脱敏、审计 |
| 安全团队 | 权限、加密、事件响应 |
| 法务 | 合同、出境路径、争议处理 |

典型流程：

```
法规识别 → 差距评估 → 方案设计 → 工程落地 → 验证审计 → 持续监控
```

> 没有明确责任人的合规要求，最终都会落空。

# 3. 生成式 AI 合规要点（中国）

## 3.1 备案与准入

| 要求 | 落地 |
|------|------|
| 服务备案 | 面向公众的生成式 AI 服务需备案 |
| 用户实名 | 面向公众需实名 |
| 投诉举报 | 提供投诉渠道 |
| 数据来源合法 | 训练数据不得侵权 |

## 3.2 内容安全与标识

| 要求 | 落地 |
|------|------|
| 内容安全 | 训练数据与生成内容合规 |
| 内容标识 | 生成内容需标识（AI 生成） |
| 应急处置 | 发现违法内容可停止生成、消除影响 |

## 3.3 面向公众与内部应用的差异

| 维度 | 面向公众 | 企业内部 |
|------|----------|----------|
| 备案 | 需要 | 通常不需要 |
| 实名 | 需要 | 用工号即可 |
| 内容标识 | 强制 | 建议 |
| 审核强度 | 高 | 中 |

> 企业内部应用与面向公众的服务，合规要求不同，需区分。

## 3.4 备案落地要点

| 要点 | 说明 |
|------|------|
| 主体资质 | 备案主体需具备相应资质 |
| 材料准备 | 模型来源、语料来源、安全评估报告 |
| 安全评估 | 内容安全、数据安全、算法机制 |
| 持续报告 | 重大变更需更新备案信息 |

备案是准入，不是一次性审批：模型升级、语料变更、功能扩展都可能触发重新评估。

# 4. 个人信息保护

## 4.1 告知同意

### 4.1.1 同意范围

```
用户需知情：
- 收集哪些信息
- 用于什么目的
- 是否会提供给第三方（模型厂商）
- 保存多久
- 如何撤回同意
```

### 4.1.2 实现

```java
// 首次使用时展示并记录同意
public void requireConsent(UserContext user) {
    if (!consentService.hasConsented(user.userId(), "AI_SERVICE")) {
        throw new ConsentRequiredException(
                "使用 AI 服务前需同意《AI 服务条款》");
    }
}
```

同意的记录应包含：同意项、版本号、时间戳、来源 IP，以便举证。

## 4.2 最小必要

```
只收集与处理完成业务所必需的数据
```

| 反例 | 正例 |
|------|------|
| 把完整对话存 3 年 | 只存必要信息，30 天过期 |
| 把 PII 发给模型 | 脱敏后发送 |
| 记录完整请求体 | 只记录摘要 |
| 为“以后可能用到”收集全部字段 | 按用途字段最小化 |

## 4.3 用户权利

### 4.3.1 权利清单

| 权利 | 实现 |
|------|------|
| 知情权 | 隐私政策说明 |
| 访问权 | 提供数据导出 |
| 更正权 | 支持修改 |
| 删除权 | 支持删除 |
| 撤回同意 | 支持关闭 |
| 可携带权 | 结构化导出（如 JSON） |

### 4.3.2 删除实现

```java
public void deleteUserData(String userId) {
    conversationStore.deleteByUser(userId);
    memoryStore.deleteByUser(userId);
    profileStore.delete(userId);
    logStore.anonymizeByUser(userId);      // 日志匿名化
    auditLog.record("USER_DATA_DELETED", userId);
}
```

删除的难点在于“副本”：备份、缓存、向量库、第三方模型侧。工程上要做到“可定位、可传播、可验证”。

## 4.4 去标识化与匿名化

| 手段 | 说明 | 可逆性 |
|------|------|--------|
| 脱敏 | 遮蔽部分字符 | 可逆 |
| 假名化 | 用假名替换标识 | 通过映射可逆 |
| 匿名化 | 无法再识别个人 | 不可逆 |

> 注意：单纯的假名化仍属个人信息，出境等场景仍需按个人信息处理。

## 4.5 PII 识别与脱敏实现

在把数据送入模型前，应先识别并脱敏 PII。

| PII 类型 | 示例 | 脱敏方式 |
|----------|------|----------|
| 身份证号 | 110101... | 保留首尾，中间遮蔽 |
| 手机号 | 138****0000 | 遮蔽中间四位 |
| 邮箱 | a***@example.com | 遮蔽用户名 |
| 银行卡号 | **** **** **** 1234 | 仅保留后四位 |
| 姓名 | 张* | 遮蔽后续字符 |

```java
public class PiiMasker {

    private static final Pattern PHONE =
            Pattern.compile("(\\d{3})\\d{4}(\\d{4})");
    private static final Pattern ID_CARD =
            Pattern.compile("(\\d{4})\\d{10}(\\w{4})");

    public String mask(String text) {
        String masked = PHONE.matcher(text)
                .replaceAll("$1****$2");
        masked = ID_CARD.matcher(masked)
                .replaceAll("$1**********$2");
        return masked;
    }
}
```

```java
// 送入模型前统一脱敏
String safePrompt = piiMasker.mask(rawPrompt);
chatClient.prompt().user(safePrompt).call().content();
```

> 脱敏应发生在数据离开可信边界之前；进入模型后再处理已经太晚。

# 5. 数据出境

## 5.1 出境路径

```
敏感数据出境需：
① 安全评估（重要数据）
② 标准合同（个人信息）
③ 认证（个人信息保护认证）
```

## 5.2 分级与出境控制

```java
// 数据分级，控制出境
public class DataResidencyPolicy {

    public boolean canSendToExternalModel(String data, String dataLevel) {
        return switch (dataLevel) {
            case "PUBLIC" -> true;
            case "INTERNAL" -> dataResidencyConfig.allowInternalEgress();
            case "SENSITIVE", "CONFIDENTIAL" -> false;   // 禁止出境
            default -> false;
        };
    }
}
```

| 数据级别 | 出境 | 处理方式 |
|----------|------|----------|
| PUBLIC | 允许 | 直接调用外部模型 |
| INTERNAL | 条件允许 | 按配置或脱敏后出境 |
| SENSITIVE | 禁止 | 境内模型/本地部署 |
| CONFIDENTIAL | 禁止 | 本地部署 |

## 5.3 境内与本地部署

> 敏感场景应使用**境内模型或本地部署**。

选择顺序：本地部署 > 境内合规云模型 > 境外模型。工程上应把模型提供方抽象为可切换的接口，避免因合规变化而重写业务代码。

## 5.4 出境审计与记录

数据出境必须可追溯：记录“什么数据、以什么级别、通过哪条路径、发给谁”。

```java
public record EgressRecord(
        String dataLevel,
        String provider,          // 模型提供方
        String region,            // 数据落地地区
        String legalBasis,        // 评估/合同/认证
        Instant occurredAt,
        String traceId
) {}
```

| 记录项 | 用途 |
|--------|------|
| 数据级别 | 证明未违规出境 |
| 提供方与地区 | 定位数据流向 |
| 法律依据 | 证明出境路径合法 |
| traceId | 关联业务请求 |

# 6. 内容合规

## 6.1 风险与措施

| 风险 | 措施 |
|------|------|
| 生成违法内容 | 内容审核（输入输出） |
| 生成虚假信息 | 事实核查、拒答机制 |
| 侵权内容 | 版权过滤、来源校验 |
| 歧视偏见 | 提示约束 + 审核 |

## 6.2 输入输出审核

```java
public class ContentComplianceService {

    public String review(String output) {
        // ① 敏感词
        if (sensitiveFilter.contains(output)) {
            return "内容不合规，已拦截";
        }
        // ② Moderation API
        if (moderationModel.isFlagged(output)) {
            return "内容不合规，已拦截";
        }
        // ③ AI 生成标识
        return output + "\n\n（本内容由 AI 生成，仅供参考）";
    }
}
```

审核应同时覆盖输入与输出：输入拦截恶意诱导，输出拦截违规生成。

## 6.3 版权与事实性

- 检索增强（RAG）应校验来源授权与许可证。
- 生成内容涉及事实时应提供引用来源。
- 高风险场景（医疗、法律、金融）应加免责声明与转人工。

## 6.4 拒答与转人工

对高风险问题，正确做法是“拒答 + 引导”，而不是强行生成：

| 场景 | 处理 |
|------|------|
| 违法请求 | 明确拒绝并说明原因 |
| 高风险专业建议 | 拒答并建议咨询专业人士 |
| 不确定事实 | 声明不确定，提供来源 |
| 需要人工 | 转接人工客服 |

```java
// 伪代码：拒答策略
if (riskClassifier.isHighRisk(question)) {
    return "抱歉，该问题涉及专业领域，请咨询专业人士。";
}
```

# 7. AI 生成内容标识

## 7.1 显式标识

```java
// 显式标识：用户可见
String labeled = answer + "\n\n【AI 生成内容】";
```

显式标识用于让用户明确知道内容由 AI 生成。

## 7.2 隐式标识

```java
// 隐式标识（元数据/水印）
ResponseMetadata meta = ResponseMetadata.builder()
        .put("aiGenerated", true)
        .put("model", modelName)
        .put("generatedAt", Instant.now().toString())
        .build();
```

隐式标识用于平台侧识别与溯源，通常写入元数据或数字水印。

| 类型 | 可见性 | 用途 |
|------|--------|------|
| 显式 | 用户可见 | 告知用户 |
| 隐式 | 不可见 | 平台溯源、监管核验 |

## 7.3 标识的工程实现

| 环节 | 做法 |
|------|------|
| 生成时 | 在响应中附加显式标识 |
| 存储时 | 元数据写入 aiGenerated 标记 |
| 传播时 | 导出/转发保留标识 |
| 校验时 | 平台侧读取元数据核验 |

> 标识应默认开启，且不因渠道（API、导出、复制）而丢失。

# 8. 审计与可追溯

## 8.1 合规审计模型

合规要求“能说明数据如何被使用”：

```java
public record ComplianceAudit(
        String tenantId,
        String userId,
        String action,              // 数据访问/生成/导出
        String dataCategory,
        String model,
        Instant timestamp,
        String traceId
) {}
```

## 8.2 保留期

| 场景 | 建议保留期 |
|------|-----------|
| 一般业务 | 6 个月 |
| 金融 | 1~3 年 |
| 医疗 | 按行业规定 |
| 安全事件 | 事件后长期保留 |

保留期通常 6 个月 ~ 3 年（按行业要求）。到期应自动归档或销毁，避免“超期存储”本身成为违规。

## 8.3 审计数据的查询与举证

合规审计需要“可查询、可导出、可举证”：

```java
public interface ComplianceAuditQuery {
    List<ComplianceAudit> byUser(String userId, Instant from, Instant to);
    List<ComplianceAudit> byTrace(String traceId);
    byte[] export(String tenantId, Instant from, Instant to);  // 监管导出
}
```

| 场景 | 查询维度 |
|------|----------|
| 用户申诉 | 按 userId |
| 事件复盘 | 按 traceId |
| 监管检查 | 按时间段导出 |

# 9. 行业特殊要求

## 9.1 行业清单

| 行业 | 要求 |
|------|------|
| 金融 | 数据本地化、可解释、留痕 |
| 医疗 | 患者隐私、诊疗建议需资质 |
| 政务 | 等保、国产化、数据不出境 |
| 教育 | 未成年人保护 |

## 9.2 叠加监管

> 行业应用必须叠加行业监管要求。

通用合规是“下限”，行业合规是“叠加”。例如医疗 AI 除 PIPL 外，还要满足诊疗资质与病历管理要求。

## 9.3 行业落地示例

| 行业 | 关键动作 |
|------|----------|
| 金融 | 模型本地化、决策可解释、全量留痕 |
| 医疗 | 数据脱敏、结论加免责、转人工复核 |
| 政务 | 私有化部署、等保测评、数据不出域 |
| 教育 | 未成年人模式、内容强审核、时长限制 |

> 同一套 AI 能力，在不同行业需要不同的合规配置，建议做成可配置策略。

# 10. 合规检查清单

## 10.1 上线前检查

- [ ] 生成式 AI 服务是否需备案
- [ ] 隐私政策是否说明 AI 使用
- [ ] 是否取得用户同意
- [ ] 是否做数据分级与最小化
- [ ] 敏感数据是否脱敏/不出境
- [ ] 是否提供删除与导出
- [ ] 生成内容是否审核与标识
- [ ] 是否保留合规审计日志
- [ ] 训练/检索数据来源是否合法
- [ ] 是否有投诉举报渠道

## 10.2 持续合规

- [ ] 法规变化后是否重新评估
- [ ] 模型/供应商变更是否触发评估
- [ ] 数据保留期是否自动执行
- [ ] 是否定期演练删除与导出

# 11. 生产注意事项

## 11.1 常见风险

| 风险 | 建议 |
|------|------|
| 未备案 | 面向公众服务先备案 |
| 未告知用户 | 隐私政策明确 AI 使用 |
| 数据无分级 | 建立分级与出境策略 |
| 无删除能力 | 支持用户删除 |
| 生成内容无标识 | 显式 + 隐式标识 |
| 无审计 | 保留合规审计 |
| 行业要求遗漏 | 叠加行业监管 |
| 供应商变更 | 变更触发合规评估 |

## 11.2 落地建议

- 把合规要求转成可执行的工程任务，明确责任人与验收标准。
- 合规能力（同意、删除、脱敏、标识、审计）做成通用组件，避免逐业务重复实现。
- 建立合规回归测试，法规或供应商变更后自动触发检查。

# 12. 小结

## 12.1 核心结论

- AI 合规涉及数据保护、内容安全、数据出境、备案。
- 个人信息保护：告知同意、最小必要、支持删除。
- 敏感数据禁止出境，优先境内/本地模型。
- 生成内容需审核与标识。
- 合规是持续要求，需定期审查。

## 12.2 常见误区

- 认为内部应用不需要合规。
- 认为假名化就等于匿名化。
- 只做输出审核，忽略输入审核。
- 保留期“只进不出”，超期数据长期堆积。
