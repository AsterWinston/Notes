# 1. 为什么用 LoRA

## 1.1 全量微调的显存瓶颈

**结论先行**：全量微调的显存瓶颈来自梯度与优化器状态，而非权重本身，70B 规模下总需求约 560GB，普通团队难以承担。

**机制**：训练需要同时保存权重、梯度、优化器状态与激活值四类张量。Adam/AdamW 为每个可训练参数维护 fp32 的一阶动量与二阶动量，再叠加 fp32 主权重副本，开销迅速放大。

### 1.1.1 显存构成拆解

```
全量微调 70B 模型：
  参数        140GB   (bf16, 70B x 2B)
  梯度        140GB   (bf16)
  优化器状态  280GB   (fp32 一阶 + 二阶)
  -----------------------------
  合计约      560GB
  → 需要多张 A100 80GB
```

### 1.1.2 与推理的差异

推理只保留权重与少量激活，无需梯度与优化器状态；训练必须保存反向传播所需的中间激活。这正是两者显存差距的根源，也是 LoRA 的切入点。

## 1.2 LoRA 的成本优势

**结论先行**：LoRA 冻结基座权重，只训练低秩矩阵，可训练参数约占 0.1%~1%，单卡即可完成微调。

```
LoRA：
  只训练低秩矩阵，参数量 0.1%~1%
  → 单卡可微调
```

**机制**：冻结权重不产生梯度，也不进入优化器状态，显存开销从"参数数量级"降到"适配器数量级"。

### 1.2.1 参数效率的量化

**结论先行**：LoRA 的收益随模型宽度增长而放大，模型越大，可训练参数占比越低。

| 模型规模 | 全量参数 | r=16 适配器 | 占比 |
|----------|:--------:|:-----------:|:----:|
| 7B | 7.0B | 约 0.04B | 约 0.6% |
| 13B | 13B | 约 0.06B | 约 0.5% |
| 70B | 70B | 约 0.16B | 约 0.2% |

**机制**：低秩矩阵参数量为 `2 × d × r`，与模型宽度 d 成正比；原权重为 `d × d`，与 d 的平方成正比。因此 d 越大，占比越低。

## 1.3 适用边界与反例

**结论先行**：LoRA 不是万能方案，当任务需要改变模型底层知识分布或追求极限效果时，全量微调仍可能更优。

| 场景 | 推荐方案 | 原因 |
|------|----------|------|
| 领域风格适配 | LoRA | 成本低、可插拔 |
| 指令跟随 | LoRA / QLoRA | 主流做法 |
| 大幅改变知识 | 全量或继续预训练 | 低秩容量有限 |
| 极小数据集 | LoRA | 减少过拟合 |
| 极致效果上限 | 全量微调 | 参数自由度最大 |

**反例**：若任务需要模型学习全新语言或全新词表，LoRA 冻结 embedding 与 lm_head 可能导致学习困难，此时需将这两层纳入训练或改用全量微调。

# 2. LoRA 原理

## 2.1 低秩分解

**结论先行**：LoRA 用两个小矩阵的乘积逼近权重更新量，从而把可训练参数量降低数个数量级。

### 2.1.1 数学形式

**机制**：对原始权重 `W`，冻结不动，引入低秩更新 `ΔW = B × A`。

```
原始权重 W（冻结） + 低秩更新 ΔW = B × A

  W' = W + ΔW = W + B·A

A: d × r    B: r × d    r << d
```

### 2.1.2 参数量估算

```
例：d=4096, r=8
  ΔW 参数量 = 4096×8 + 8×4096 = 65536
  原 W 参数量 = 4096×4096 = 16.7M
  → 只训练 0.4%
```

## 2.2 前向传播

**结论先行**：LoRA 分支与冻结主分支并行，输出相加，因此训练时多一条小分支，合并后无额外开销。

```
        ┌─────────────┐
输入 x ─▶│  W (冻结)    │─▶ Wx
        └─────────────┘
        ┌─────────────┐
    x ─▶│  A ─▶ B     │─▶ BAx      ← 只训练 A、B
        └─────────────┘
        Wx + BAx
```

### 2.2.1 合并的等价性

**结论先行**：由于加法满足结合律，推理时可把 BA 预先加到 W 上，得到等价权重。

**机制**：训练时两条分支并行以保留梯度路径；推理时无需求导，直接合并即可，输出完全一致。

```python
W_merged = W + (alpha / r) * (B @ A)
```

## 2.3 初始化与缩放

**结论先行**：正确的初始化与缩放决定了训练初期是否稳定，A 用随机高斯、B 用零是标准做法。

### 2.3.1 A、B 的初始化

**机制**：A 以高斯分布初始化，B 初始化为全零，使训练开始时 `BA = 0`，模型行为与基座完全一致，避免破坏预训练能力。

### 2.3.2 alpha 缩放

**机制**：实际缩放系数为 `alpha / r`，与 `BAx` 相乘。调大 alpha 相当于放大适配器影响，是除学习率外最有效的调节手段之一。

```
h = Wx + (alpha / r) · BAx
```

**坑**：只调 r 而不同步调 alpha，会改变有效学习率，导致实验不可比。

# 3. 关键参数

## 3.1 参数总览

**结论先行**：LoRA 的可调参数不多，但每一项都显著影响效果与成本，应逐项有依据地设置。

| 参数 | 说明 | 建议 |
|------|------|------|
| `r`（rank，秩） | 低秩维度 | 8~64 |
| `alpha` | 缩放系数 | 2×r |
| `dropout` | Dropout | 0.05~0.1 |
| `target_modules` | 应用层 | q/k/v/o_proj + FFN |
| `bias` | 偏置训练策略 | none |
| `task_type` | 任务类型 | CAUSAL_LM |

### 3.1.1 参数之间的相互影响

**结论先行**：r 与 alpha 共同决定有效缩放，学习率又与缩放耦合，三者应整体调整。

**机制**：有效缩放为 `alpha / r`。若固定 alpha 而增大 r，等效于减弱适配器影响，需同步提高学习率或 alpha，否则会误判为"增大 r 无用"。

## 3.2 r 与 alpha 的取舍

**结论先行**：r 决定容量上限，alpha 决定影响强度，二者需配合调整。

### 3.2.1 r 的选择

| r 取值 | 容量 | 适用 |
|--------|------|------|
| 4~8 | 低 | 简单风格、小数据 |
| 16~32 | 中 | 通用推荐 |
| 64~128 | 高 | 复杂任务、大数据 |

### 3.2.2 alpha 与缩放

**生产建议**：从 `alpha = 2×r` 起步，若欠拟合则增大 alpha 或 r，若过拟合则减小 r 并提高 dropout。

## 3.3 dropout 与 bias

**结论先行**：dropout 是 LoRA 唯一常用的正则化手段，bias 通常保持 `none`。

**边界**：数据量小于 1000 条时建议 dropout 取 0.1；数据充足时可降到 0.05 甚至 0。

## 3.4 完整配置示例

```python
from peft import LoraConfig

lora_config = LoraConfig(
    r=16,
    lora_alpha=32,
    lora_dropout=0.05,
    target_modules=["q_proj", "k_proj", "v_proj", "o_proj",
                    "gate_proj", "up_proj", "down_proj"],
    bias="none",
    task_type="CAUSAL_LM")
```

# 4. target_modules 选择

## 4.1 应用范围与命名

**结论先行**：`target_modules` 决定把适配器挂到哪些线性层，是影响效果最直接的一项。

**机制**：不同模型层名不同，需先打印层名确认。例如 LLaMA/Qwen 系列使用 `q_proj`、`k_proj`、`v_proj`、`o_proj` 与 `gate_proj`、`up_proj`、`down_proj`。

```python
for name, module in model.named_modules():
    if isinstance(module, torch.nn.Linear):
        print(name)
```

## 4.2 各范围对比

**结论先行**：覆盖 FFN 层通常效果更好，但参数量增加，需在效果与成本间权衡。

| 范围 | 参数量 | 效果 |
|------|:------:|:----:|
| 仅 q,v | 少 | 一般 |
| 全部注意力 | 中 | 好 |
| 注意力 + FFN | 多 | 最好（推荐） |

> 覆盖 FFN 层通常效果更好，但参数量增加。

## 4.3 边界与经验

**结论先行**：并非"层越多越好"，数据量小时全模块反而更易过拟合。

**反例**：在几百条数据上训练全模块 LoRA，常见结果是训练损失极低但泛化变差；此时只挂注意力层并降低 r 往往更稳。

# 5. 训练示例

## 5.1 端到端脚本

**结论先行**：一个标准的 LoRA 训练脚本只需加载模型、套用适配器、配置训练参数、训练、保存五步。

```python
from transformers import AutoModelForCausalLM, TrainingArguments
from peft import get_peft_model, LoraConfig
from trl import SFTTrainer

# ① 加载模型
model = AutoModelForCausalLM.from_pretrained(
    "Qwen/Qwen2.5-7B",
    torch_dtype=torch.bfloat16,
    device_map="auto")

# ② 应用 LoRA
model = get_peft_model(model, lora_config)

# ③ 训练
trainer = SFTTrainer(
    model=model,
    train_dataset=dataset,
    args=TrainingArguments(
        per_device_train_batch_size=4,
        gradient_accumulation_steps=4,
        learning_rate=2e-4,          # LoRA 学习率比全量高
        num_train_epochs=3,
        bf16=True,
        output_dir="./output"))

trainer.train()

# ④ 保存适配器
model.save_pretrained("./lora-adapter")   # 只保存 LoRA 权重（几十 MB）
```

## 5.2 逐段解析

**结论先行**：理解每一步的目的，才能在报错时快速定位。

### 5.2.1 加载模型

`torch_dtype=torch.bfloat16` 降低显存；`device_map="auto"` 自动分片到可用显卡。若显存不足，改用第 6 节的 4bit 加载。

### 5.2.2 应用 LoRA

`get_peft_model` 会按 `target_modules` 替换目标层并冻结其余参数，可训练参数比例可用 `print_trainable_parameters()` 查看。

### 5.2.3 训练参数

LoRA 的学习率通常比全量高一个数量级（1e-4~2e-4）；梯度累积用于模拟更大批大小。

| 参数 | 典型值 | 作用 |
|------|:------:|------|
| 学习率 | 2e-4 | 适配器更新步长 |
| 梯度累积 | 4 | 放大有效批 |
| 轮数 | 3 | 数据重复遍数 |
| bf16 | 开 | 降显存、防溢出 |

## 5.3 保存与检查

**结论先行**：默认只保存适配器，务必确认保存目录中包含 `adapter_config.json`。

```
./lora-adapter/
  adapter_config.json     # 适配器配置
  adapter_model.safetensors  # LoRA 权重（几十 MB）
```

**坑**：若误用 `model.save_pretrained` 保存了合并模型，文件体积会回到数 GB 级别。

### 5.3.1 上线前检查清单

**结论先行**：保存后应逐项核对，避免"训练成功但产物不可用"。

| 检查项 | 期望 |
|--------|------|
| 可训练参数比例 | 0.1%~1% |
| 适配器目录大小 | 几十 MB |
| 配置含 target_modules | 是 |
| 加载回测 | 输出与训练末一致 |

# 6. QLoRA

## 6.1 量化基座

**结论先行**：QLoRA 用 4bit 量化基座加载权重，把大模型的权重显存压缩到约四分之一。

### 6.1.1 NF4 量化

**机制**：NF4（4bit NormalFloat，正态浮点）假设权重近似正态分布，按分位数划分量化区间，信息损失小于均匀量化。

### 6.1.2 双重量化

**机制**：对量化常数再做一次量化，进一步压缩每块的元数据开销，通常可再省约 0.5bit/参数。

## 6.2 完整配置

**结论先行**：QLoRA 只需在加载模型时加一个 `BitsAndBytesConfig`，其余与 LoRA 相同。

```python
from transformers import BitsAndBytesConfig

bnb_config = BitsAndBytesConfig(
    load_in_4bit=True,
    bnb_4bit_quant_type="nf4",              # 4bit NormalFloat
    bnb_4bit_compute_dtype=torch.bfloat16,
    bnb_4bit_use_double_quant=True)

model = AutoModelForCausalLM.from_pretrained(
    "Qwen/Qwen2.5-7B",
    quantization_config=bnb_config,
    device_map="auto")
```

## 6.3 对比与边界

**结论先行**：QLoRA 以少量效果换取大幅显存下降，是显存受限时的首选。

| 技术 | 显存 | 效果 |
|------|:----:|:----:|
| 全量 | 极高 | 最好 |
| LoRA | 中 | 接近全量 |
| QLoRA | 低 | 略低于 LoRA |

```
QLoRA = 4bit 量化的基座 + LoRA

效果：
  70B 模型可在单张 48GB 显卡上微调
  效果接近全量微调
```

**坑**：量化基座只能训练，无法直接合并回 4bit 权重；合并需先反量化到 bf16，见第 7 节。

### 6.3.1 显存估算

**结论先行**：QLoRA 下 7B 训练显存约 10~12GB，13B 约 16~20GB，70B 约 40~48GB。

| 规模 | 4bit 权重 | 训练总显存（约） |
|------|:---------:|:----------------:|
| 7B | 约 4GB | 10~12GB |
| 13B | 约 7GB | 16~20GB |
| 70B | 约 35GB | 40~48GB |

**边界**：上表假设序列长度 2048、批大小较小并开启梯度检查点；序列变长会显著抬高激活显存。

# 7. 加载与合并

## 7.1 独立加载

**结论先行**：推理时可用"基座 + 适配器"的方式加载，适配器体积小，便于分发与切换。

```python
from peft import PeftModel

# ① 加载基座 + 适配器
base = AutoModelForCausalLM.from_pretrained("Qwen/Qwen2.5-7B")
model = PeftModel.from_pretrained(base, "./lora-adapter")
```

### 7.1.1 推理加载流程

**结论先行**：独立加载时基座先加载、适配器后注入，二者版本必须匹配。

```
加载基座 → 读取 adapter_config.json → 注入适配器 → 推理
```

**坑**：若基座版本与训练时不一致（例如换了分词器或权重版本），适配器可能报维度不匹配或效果骤降。

## 7.2 合并权重

**结论先行**：合并把适配器写入基座，推理更快，但产物体积回到基座大小。

```python
# ② 合并（可选，合并后推理更快）
merged = model.merge_and_unload()
merged.save_pretrained("./merged-model")
```

## 7.3 方式对比与坑

| 方式 | 优点 | 缺点 |
|------|------|------|
| 不合并 | 适配器小、可切换 | 推理稍慢 |
| 合并 | 推理快 | 体积大 |

**边界**：多任务场景不适合合并，否则需为每个任务保存完整模型；单任务高频推理则建议合并。

# 8. 多适配器

## 8.1 多适配器架构

**结论先行**：一个基座可挂载多个 LoRA 适配器，按业务切换，显著节省存储与加载时间。

```
一个基座 + 多个 LoRA 适配器：
  base + lora-domain-A
  base + lora-domain-B
  → 按需加载，节省存储
```

## 8.2 动态切换

**结论先行**：PEFT 支持在运行时激活不同适配器，适合多租户或 A/B 场景。

```python
model.load_adapter("./lora-domain-A", adapter_name="a")
model.load_adapter("./lora-domain-B", adapter_name="b")
model.set_adapter("a")   # 切换到 A
```

## 8.3 生产管理

**结论先行**：适配器数量增长后，版本与命名管理比技术本身更容易出问题。

| 风险 | 建议 |
|------|------|
| 命名混乱 | 统一命名规范（模型-任务-日期） |
| 版本丢失 | 版本化存储 + 元数据 |
| 加载错误 | 记录基座与适配器版本对应关系 |

# 9. 生产注意事项

## 9.1 参数调优风险

| 风险 | 建议 |
|------|------|
| rank 过小 | 效果不足 |
| rank 过大 | 接近全量，失去优势 |
| target_modules 少 | 效果受限 |
| 学习率过低 | 收敛慢 |

## 9.2 评估与监控

**结论先行**：任何微调都必须与基座对比，否则无法判断收益。

**生产建议**：固定一套留出集，记录微调前后的指标，并监控线上输出的风格漂移。

## 9.3 工程落地

**结论先行**：把适配器当作可版本化的制品来管理，而不是一次性的训练产物。

| 环节 | 做法 |
|------|------|
| 训练 | 固定随机种子与配置快照 |
| 存储 | 适配器 + 配置 + 数据版本一并归档 |
| 部署 | 基座与适配器版本绑定 |
| 回滚 | 保留上一版本适配器 |

# 10. 小结

## 10.1 要点回顾

- LoRA 冻结基座，只训练低秩矩阵，参数量 0.1%~1%。
- 关键参数：r（8~64）、alpha（2×r）、target_modules。
- QLoRA 用 4bit 量化基座，单卡可微调大模型。
- 适配器可合并或独立加载，多适配器可共享一个基座。
- 必须对比基座评估效果。

## 10.2 实践清单

- 先打印层名，确认 `target_modules` 拼写正确。
- 从 `r=16`、`alpha=32`、注意力 + FFN 起步。
- 显存不足时切 QLoRA，并在合并前反量化。
- 适配器纳入版本管理，绑定基座版本。
