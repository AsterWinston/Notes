# 1. 三种定制手段

**结论先行**：让通用大模型适配业务，只有三条主路径——提示工程（Prompt Engineering）、检索增强生成（RAG，Retrieval-Augmented Generation）与微调（Fine-Tuning）。三者成本递增、能力递增，实践中应按"提示 → RAG → 微调"的顺序逐级尝试，微调是最后手段。

## 1.1 手段概览

三种手段作用于模型的层次不同：提示工程改输入，RAG 改上下文，微调改参数。

| 手段 | 英文 | 核心动作 | 是否改参数 | 生效时机 |
|------|------|----------|:----------:|----------|
| 提示工程 | Prompt Engineering | 改写输入提示 | 否 | 立即 |
| RAG | Retrieval-Augmented Generation | 外挂检索知识 | 否 | 立即 |
| 微调 | Fine-Tuning | 用数据继续训练 | 是 | 训练后 |

成本与能力的关系可以直观表示：

```
能力 ↑
  |                                   [微调]
  |                          [RAG]
  |              [提示工程]
  +----------------------------------------→ 成本
```

### 1.1.1 机制差异

- 提示工程：通过系统提示（system prompt）、少样本示例（few-shot）约束输出，模型参数不变。
- RAG：在推理时检索相关文档，拼进上下文，模型"看着资料答题"，知识可实时更新。
- 微调：用领域数据继续训练，把知识/风格"写进"权重，推理时无需额外上下文。

### 1.1.2 边界与坑

- 提示工程无法注入模型完全不知道的知识，也无法稳定改变深层风格。
- RAG 依赖检索质量，检索不到就答不对，且不改变模型的输出风格与能力上限。
- 微调成本高、迭代慢，且知识更新需重新训练。

### 1.1.3 生产建议

先评估需求属于"缺知识"还是"缺能力"：缺知识优先 RAG，缺能力/风格才考虑微调。

## 1.2 成本与能力梯度

**结论先行**：三类手段的成本与更新方式差异显著，选型时先看"知识是否需实时更新"。

| 手段 | 解决什么 | 成本 | 更新 |
|------|----------|:----:|------|
| 提示工程 | 格式、风格、简单任务 | 最低 | 改提示 |
| RAG | 私有知识、时效性 | 中 | 更新知识库 |
| 微调 | 风格、能力、领域适配 | 高 | 重新训练 |

### 1.2.1 成本构成

```
提示工程：人力（写提示、调提示）
RAG：     向量库 + 检索服务 + 文档维护
微调：    数据标注 + GPU + 训练 + 部署 + 评估
```

### 1.2.2 更新代价

- 提示工程与 RAG 属于"在线更新"，改完即生效。
- 微调属于"离线更新"，一次训练往往数小时到数天，且需回归评测。

### 1.2.3 成本量级对比

| 成本项 | 提示工程 | RAG | 微调 |
|--------|:--------:|:---:|:----:|
| 启动人力 | 低 | 中 | 高 |
| 持续算力 | 推理 | 推理 + 检索 | 训练 + 推理 |
| 单次迭代 | 分钟级 | 小时级 | 天级 |
| 数据依赖 | 无 | 文档 | 标注数据 |
| 上线风险 | 低 | 中 | 高 |

从量级看，微调的启动成本可能是 RAG 的 10 倍以上，因此更应慎重。

## 1.3 选型速查

**结论先行**：用一张表快速定位，避免"上来就微调"。

| 你的问题 | 首选手段 | 备选 |
|----------|:--------:|:----:|
| 输出格式不稳定 | 提示工程 | 微调 |
| 不知道公司内部文档 | RAG | 微调 |
| 知识每天变化 | RAG | 无 |
| 想要固定品牌口吻 | 提示工程 | 微调 |
| 领域术语理解差 | 微调 | RAG |
| 要把大模型压成小模型 | 蒸馏（微调） | 无 |

# 2. 决策框架

**结论先行**：先问"问题是什么"，再映射到手段，避免凭直觉选型。

## 2.1 需求诊断树

```
问题是什么？
├── 模型不知道我们的知识 → RAG
├── 模型输出格式不对 → 提示工程
├── 模型风格不符合要求 → 提示工程 / 微调
├── 模型在某领域能力弱 → 微调
├── 需要特定格式的稳定输出 → 提示 + 结构化输出
└── 需要降低成本（用小模型） → 蒸馏 / 微调
```

### 2.1.1 诊断要点

- "不知道"是知识问题，走 RAG。
- "知道但做不好"是能力问题，走微调。
- "知道也能做，只是不稳"是约束问题，先走提示。

### 2.1.2 边界与坑

诊断树不能处理复合需求，例如"既要实时知识又要固定风格"，此时需组合：RAG + 微调。

## 2.2 决策流程代码化

**结论先行**：把决策规则写成代码，便于团队统一口径。

```python
def choose_strategy(need_knowledge: bool,
                    need_realtime: bool,
                    need_style: bool,
                    need_capability: bool,
                    need_cost_reduction: bool) -> str:
    if need_realtime:
        return "RAG"                      # 知识需实时，微调无法做到
    if need_cost_reduction:
        return "distill/finetune"         # 压缩模型成本
    if need_capability:
        return "finetune"                 # 能力提升只能微调
    if need_style:
        return "prompt/finetune"          # 先试提示，不足再微调
    if need_knowledge:
        return "RAG"                      # 补知识
    return "prompt"                       # 默认先优化提示
```

### 2.2.1 使用说明

- 参数为业务判断结果，由产品与技术共同确认。
- 优先级从"硬约束"到"软约束"排列：实时性 > 降本 > 能力 > 风格 > 知识。

### 2.2.2 生产建议

将上述函数接入需求评审流程，作为立项前的强制检查项。

## 2.3 常见误判

| 误判 | 后果 | 纠正 |
|------|------|------|
| 上来就微调 | 浪费算力与时间 | 先试提示 + RAG |
| 用微调补实时知识 | 永远追不上更新 | 改用 RAG |
| 用 RAG 改风格 | 风格不稳定 | 用提示或微调 |
| 忽视数据质量 | 微调效果差 | 先治理数据 |

# 3. 实施优先级

**结论先行**：遵循"先优化提示、再加 RAG、最后微调"的顺序，用最小成本验证可行性。

## 3.1 三阶段推进

```
① 先优化提示（零成本）
② 再加 RAG（补知识）
③ 最后微调（改能力/风格）
```

> **微调是最后手段**，先穷尽提示与 RAG。

### 3.1.1 各阶段目标

| 阶段 | 目标 | 退出条件 |
|:----:|------|----------|
| ① 提示 | 榨干零成本手段 | 提示已优化到极限仍不达标 |
| ② RAG | 补齐知识缺口 | 知识问题解决，能力仍不足 |
| ③ 微调 | 改能力/风格 | 达到验收指标 |

### 3.1.2 边界与坑

- 跳过前两步直接微调，往往连"问题是否真需要微调"都没搞清楚。
- RAG 与微调并非互斥，能力不足时可两者叠加。

## 3.2 阶段验收标准

**结论先行**：每个阶段都要有可量化的验收标准，否则无法判断是否进入下一阶段。

| 阶段 | 验收指标 | 示例阈值 |
|:----:|----------|----------|
| ① 提示 | 格式合规率 | ≥ 95% |
| ① 提示 | 任务准确率 | 达到基线 |
| ② RAG | 检索召回率 | ≥ 90% |
| ② RAG | 事实正确率 | ≥ 95% |
| ③ 微调 | 领域任务提升 | +10 个百分点 |

### 3.2.1 生产建议

验收指标在立项时确定，微调前后用同一评测集对比，避免"感觉变好了"。

# 4. 各手段的边界

**结论先行**：没有万能手段，每种手段都有明确的能力边界，选型就是匹配边界。

## 4.1 能力边界矩阵

| 需求 | 提示 | RAG | 微调 |
|------|:----:|:---:|:----:|
| 补充新知识 | ❌ | ✅ | ✅ |
| 知识实时更新 | ❌ | ✅ | ❌ |
| 改变输出风格 | ⚠️ | ❌ | ✅ |
| 提升领域能力 | ❌ | ⚠️ | ✅ |
| 压缩模型成本 | ❌ | ❌ | ✅ |
| 格式约束 | ✅ | ❌ | ✅ |
| 快速迭代 | ✅ | ✅ | ❌ |

（图例：✅ 擅长，⚠️ 部分可行，❌ 不适用。）

## 4.2 边界背后的机制

### 4.2.1 为什么 RAG 改不了风格

RAG 只在上下文里加事实，不改变权重中的表达习惯，因此风格仍由模型决定。

### 4.2.2 为什么微调做不到实时

微调把知识写进权重，更新需重新训练，天然滞后，不适合高频变化的知识。

### 4.2.3 为什么提示能约束格式

结构化输出（如 JSON Schema、函数调用）由解码阶段约束，属于提示层的强项。

## 4.3 反例

| 反例 | 期望 | 实际 | 教训 |
|------|------|------|------|
| 用提示注入内部文档 | 正确回答 | 模型胡编 | 知识缺失须 RAG |
| 用微调追新闻 | 实时正确 | 训练后即过时 | 实时须 RAG |
| 用 RAG 统一口吻 | 品牌一致 | 口吻漂移 | 风格须微调 |
| 用微调治格式 | 稳定 JSON | 偶发非法 | 先用结构化输出 |

### 4.3.1 反例的代码化

```python
def wrong_choice(problem: str) -> str:
    # 反例：不诊断就选微调
    if problem == "knowledge":
        return "finetune"   # 错：应 RAG
    if problem == "realtime":
        return "finetune"   # 错：应 RAG
    return "finetune"       # 错：先提示

def right_choice(problem: str) -> str:
    table = {
        "knowledge": "rag",
        "realtime": "rag",
        "style": "prompt",
        "capability": "finetune",
        "format": "prompt",
    }
    return table.get(problem, "prompt")
```

对比两个函数即可发现：误判的根源是"默认微调"。

# 5. 微调的类型

**结论先行**：微调按"更新范围"与"训练目标"两个维度分类，选型时先定目标再定方法。

## 5.1 按更新范围分类

| 类型 | 说明 | 成本 |
|------|------|:----:|
| 全量微调 | 更新所有参数 | 最高 |
| LoRA/QLoRA | 只训练低秩矩阵 | 低 |

### 5.1.1 机制对比

```
全量微调：θ' = θ - η·∇L(θ)          所有参数参与更新
LoRA：    θ' = θ + (α/r)·B·A        仅低秩矩阵 A、B 可训练
```

### 5.1.2 边界与坑

- 全量微调易灾难性遗忘，且显存需求极高。
- LoRA 参数量小，但秩（rank）过低会限制表达能力。

### 5.1.3 LoRA 配置示意

```python
from peft import LoraConfig

lora_config = LoraConfig(
    r=16,                      # 低秩维度
    lora_alpha=32,             # 缩放，通常为 2r
    lora_dropout=0.05,
    target_modules=["q_proj", "v_proj"],
    task_type="CAUSAL_LM",
)
```

该配置只训练极少量参数，适合单卡场景快速迭代。

## 5.2 按训练目标分类

| 类型 | 说明 | 成本 |
|------|------|:----:|
| SFT | 指令微调 | 中 |
| DPO/RLHF | 偏好对齐 | 中高 |
| 蒸馏 | 大模型教小模型 | 中 |

### 5.2.1 目标差异

- SFT：学会"照着做"，输入指令-回答对。
- DPO/RLHF：学会"做得更好"，输入偏好对。
- 蒸馏：小模型模仿大模型的输出分布。

### 5.2.2 生产建议

先 SFT 打底，再按需做偏好对齐；蒸馏用于降本场景。

## 5.3 类型对比与选型

| 方法 | 数据形式 | 显存 | 效果 | 适用 |
|------|----------|:----:|:----:|------|
| 全量 | 指令-回答 | 极高 | 最好 | 资源充足 |
| LoRA | 指令-回答 | 低 | 接近 | 主流首选 |
| QLoRA | 指令-回答 | 最低 | 接近 | 单卡场景 |
| DPO | 偏好对 | 中 | 好 | 对齐阶段 |
| 蒸馏 | 教师输出 | 中 | 好 | 降本 |

# 6. 何时该微调

**结论先行**：当提示与 RAG 都已穷尽仍不达标，且具备高质量数据与算力时，才该微调。

## 6.1 微调信号

| 信号 | 说明 |
|------|------|
| 提示已优化到极限 | 效果仍不足 |
| 需要稳定的特定风格 | 提示难以保证 |
| 领域术语理解差 | 通用模型不懂 |
| 需要小模型降本 | 蒸馏 |
| 有高质量训练数据 | 数据是关键 |

### 6.1.1 信号解读

- "提示到极限"意味着已在提示层做过充分实验。
- "稳定风格"指提示无法保证长文本、多轮一致。

### 6.1.2 生产建议

满足两条以上信号再启动微调立项，避免单点冲动。

## 6.2 不该微调的信号

| 信号 | 原因 | 替代 |
|------|------|------|
| 知识频繁变化 | 训练滞后 | RAG |
| 数据质量差 | 垃圾进垃圾出 | 先治理数据 |
| 无评测能力 | 无法验证 | 先建评测 |
| 预算不足 | 训练/部署成本高 | 提示 + RAG |
| 需求不稳定 | 反复变更 | 提示工程 |

### 6.2.1 反例

某团队为"补实时价格"微调模型，结果上线当天价格就变了，最终改用 RAG。

# 7. 微调的代价

**结论先行**：微调不只是"跑一次训练"，而是数据、算力、工程、维护、风险五类成本的总和。

## 7.1 直接成本

| 代价 | 说明 |
|------|------|
| 数据 | 需要高质量标注数据 |
| 算力 | GPU |
| 工程 | 训练、评估、部署链路 |
| 维护 | 模型版本、重新评估 |
| 风险 | 可能过拟合、灾难性遗忘 |

### 7.1.1 成本明细

```
数据：  标注人力 / 采购 / 清洗
算力：  GPU 时租或自建
工程：  数据管道 + 训练脚本 + 评测 + 服务
维护：  版本管理 + 回归测试
风险：  效果回退 + 遗忘
```

## 7.2 隐性成本

| 隐性成本 | 说明 |
|----------|------|
| 迭代周期长 | 一次训练数小时到数天 |
| 团队技能 | 需要懂训练与评估的人 |
| 供应商锁定 | 依赖特定框架与硬件 |
| 技术债 | 多版本并存难维护 |

### 7.2.1 边界与坑

隐性成本常被低估，尤其是"每次数据更新都要重训"的长期负担。

## 7.3 成本估算示例

**结论先行**：用一个简化的量级估算，帮助判断预算是否可行。

```python
def estimate_cost(num_samples, epochs, gpu_hour_price,
                  hours_per_epoch, num_versions=1):
    gpu_cost = epochs * hours_per_epoch * gpu_hour_price
    # 数据标注按每条单价估算
    data_cost = num_samples * 0.5
    total = (gpu_cost + data_cost) * num_versions
    return {"gpu": gpu_cost, "data": data_cost, "total": total}

print(estimate_cost(5000, 3, 2.0, 1.5))
# {'gpu': 9.0, 'data': 2500.0, 'total': 2509.0}
```

### 7.3.1 生产建议

预算评估时把数据成本放在首位，GPU 成本往往不是大头。

### 7.3.2 Java 侧集成成本

Java 应用通常不参与训练，只承担推理调用与业务集成：

```java
public class ModelClient {
    private final HttpClient http = HttpClient.newHttpClient();

    public String infer(String prompt) throws Exception {
        String body = """
            {"model":"my-sft-model",
             "messages":[{"role":"user","content":"%s"}]}
            """.formatted(prompt);
        HttpRequest req = HttpRequest.newBuilder()
            .uri(URI.create("http://localhost:8000/v1/chat/completions"))
            .header("Content-Type", "application/json")
            .POST(HttpRequest.BodyPublishers.ofString(body))
            .build();
        return http.send(req, HttpResponse.BodyHandlers.ofString()).body();
    }
}
```

集成成本主要在多版本模型的路由、回滚与监控。

# 9. 小结

- 三种定制手段：提示工程、RAG、微调。
- 优先级：提示 → RAG → 微调。
- RAG 补知识，微调改能力/风格。
- 微调是最后手段，需数据与算力。
- 明确需求边界，选对手段。
- 决策框架与验收标准要前置，避免凭感觉选型。
