# 1. 什么是 PEFT

## 1.1 定义与动机

**结论先行**：PEFT（Parameter-Efficient Fine-Tuning，参数高效微调）是一类只训练极少量参数即可适配下游任务的方法集合，把可训练参数从 100% 降到 0.01%~5%。

### 1.1.1 全量微调的成本

**机制**：全量微调需要为每个参数保存梯度与优化器状态，显存与存储成本随模型规模线性增长；同时每个任务都要保存一份完整权重，多任务场景下存储迅速膨胀。

### 1.1.2 PEFT 的定位

**结论先行**：PEFT 用少量新增参数逼近全量微调效果，兼顾成本、可插拔性与多任务能力。

```
全量微调：训练 100% 参数
PEFT：    训练 0.01%~5% 参数
```

### 1.1.3 成本对比

**结论先行**：PEFT 在显存、存储与训练时间三个维度同时降低成本。

| 维度 | 全量微调 | PEFT |
|------|----------|------|
| 可训练参数 | 100% | 0.01%~5% |
| 单任务产物 | 完整权重 | 小型适配器 |
| 多任务存储 | 线性膨胀 | 共享基座 |
| 训练显存 | 高 | 低 |

## 1.2 核心思想

**结论先行**：主流 PEFT 方法假设"适配下游任务所需的参数变化位于低维子空间"，因此用少量参数即可表达。

**机制**：加法式方法新增小模块、选择式方法只更新部分原参数、重参数化方法分解更新方向、提示式方法学习软提示，四者殊途同归。

## 1.3 适用边界

**结论先行**：PEFT 在中小规模适配任务上表现优异，但当任务需要大幅改变模型知识或词表时，效果可能明显弱于全量微调。

| 场景 | 是否适合 PEFT |
|------|---------------|
| 领域风格适配 | 适合 |
| 指令跟随 | 适合 |
| 全新语言/词表 | 需额外训练嵌入层 |
| 大规模继续预训练 | 不适合 |

# 2. PEFT 方法分类

## 2.1 四大类别

**结论先行**：按"参数从哪来"划分，PEFT 可分为加法式、选择式、重参数化、提示式四类。

| 类别 | 方法 | 思路 |
|------|------|------|
| 加法式 | LoRA、Adapter、Prefix Tuning | 增加新参数 |
| 选择式 | BitFit、Layer Freezing | 只训练部分原参数 |
| 重参数化 | DoRA | 分解权重更新 |
| 提示式 | Prompt Tuning、P-Tuning | 学习软提示 |

## 2.2 各类别代表方法

**结论先行**：加法式是当前主流，其中 LoRA 因可合并、无推理开销而应用最广。

```
加法式  ── LoRA（低秩矩阵）      ← 主流
        └─ Adapter（瓶颈模块）
        └─ Prefix（前缀向量）
选择式  ── BitFit（只训偏置）
重参数化 ─ DoRA（幅度 + 方向）
提示式  ── Prompt / P-Tuning（软提示）
```

### 2.2.1 插入位置对比

**结论先行**：不同方法的"插入点"决定了它们的推理开销与可合并性。

| 方法 | 插入位置 | 可合并 |
|------|----------|:------:|
| LoRA | 线性层旁路 | 是 |
| Adapter | 层间串联 | 否 |
| Prefix | 每层注意力前 | 否 |
| Prompt | 输入嵌入前 | 否 |
| BitFit | 原偏置项 | 是 |

## 2.3 选择框架

**结论先行**：先用默认选择（LoRA），只有在明确约束下才切换到其他方法。

| 约束 | 首选 |
|------|------|
| 无特殊约束 | LoRA |
| 显存受限 | QLoRA |
| 参数量极致受限 | Prefix / Prompt Tuning |
| 需要更快收敛 | LoRA + 更高学习率 |

# 3. LoRA

## 3.1 原理回顾

**结论先行**：LoRA 冻结基座，只训练低秩矩阵 A、B，用其乘积表示权重更新。

```
W' = W + B·A
（冻结 W，训练低秩 A、B）
```

> 当前最主流。详见 `4_lora_qlora.md`。

## 3.2 关键参数

**结论先行**：r、alpha、dropout 与 target_modules 是决定效果的四项核心参数。

| 参数 | 建议 | 说明 |
|------|------|------|
| r | 8~64 | 低秩维度 |
| alpha | 2×r | 缩放系数 |
| dropout | 0.05~0.1 | 正则化 |
| target_modules | 注意力 + FFN | 应用层 |

### 3.2.1 参数取值经验

**结论先行**：小数据用小 r，大数据可用大 r；alpha 始终跟随 r 成比例调整。

| 数据规模 | r | alpha | dropout |
|----------|:-:|:-----:|:-------:|
| 数百条 | 4~8 | 8~16 | 0.1 |
| 数千条 | 16 | 32 | 0.05 |
| 数万条 | 32~64 | 64~128 | 0.05 |

## 3.3 适用边界

**结论先行**：LoRA 的可合并特性使其推理零额外开销，这是它相对 Adapter 的最大优势。

**边界**：多适配器并存时若逐一合并会产生多份完整模型，通常保持不合并、动态切换。

# 4. Adapter

## 4.1 结构

**结论先行**：Adapter 在每层插入一个"降维-非线性-升维"的小瓶颈模块，并加残差连接。

### 4.1.1 瓶颈结构

```
在每层插入小的适配器模块：

  Transformer 层
    ├── Attention
    ├── Adapter（新增，小）
    ├── FFN
    └── Adapter（新增，小）
```

### 4.1.2 残差连接

**机制**：输出为 `x + up(relu(down(x)))`，残差保证初始时模块近似恒等，不破坏预训练行为。

```python
# Adapter 结构
class Adapter(nn.Module):
    def __init__(self, d_model, bottleneck):
        self.down = nn.Linear(d_model, bottleneck)   # 降维
        self.up = nn.Linear(bottleneck, d_model)     # 升维

    def forward(self, x):
        return x + self.up(relu(self.down(x)))       # 残差
```

## 4.2 与 LoRA 对比

**结论先行**：Adapter 参数量中等但引入额外层，推理有延迟；LoRA 可合并，推理无延迟。

| 对比 | LoRA | Adapter |
|------|:----:|:-------:|
| 推理延迟 | 无（可合并） | 有（额外层） |
| 参数量 | 少 | 中 |
| 主流度 | 高 | 中 |

### 4.2.1 参数量与延迟的量化

**结论先行**：Adapter 的参数量由瓶颈维度决定，延迟则由插入层数决定。

**机制**：单层 Adapter 参数量为 `2 × d × b`（b 为瓶颈维度）；总延迟增量正比于层数乘以每层的小矩阵乘加耗时。

| 瓶颈维度 b | 相对参数量 | 延迟影响 |
|:----------:|:----------:|:--------:|
| d/16 | 低 | 小 |
| d/8 | 中 | 中 |
| d/4 | 高 | 较大 |

## 4.3 边界与坑

**结论先行**：Adapter 的额外层会改变网络深度，对延迟敏感的在线服务不友好。

**坑**：Adapter 层数增多会累积延迟，批处理时尤为明显；若必须使用，应评估端到端吞吐。

# 5. Prefix Tuning / Prompt Tuning

## 5.1 软提示思想

**结论先行**：提示式方法不修改模型权重，而是在输入前拼接可学习的连续向量（软提示）。

```
不修改模型，而是在输入前加可学习的"软提示"：

  [软提示1][软提示2]...[软提示n] 实际输入
         ↑ 可学习参数
```

### 5.1.1 软提示的训练机制

**结论先行**：软提示是连续向量而非离散 token，通过反向传播直接优化，无需对应真实词。

**机制**：软提示向量作为可训练参数加入嵌入序列，梯度经注意力回传；其"含义"由优化过程自行确定，因此不可读、不可直接解释。

## 5.2 两种变体对比

**结论先行**：Prompt Tuning 只在输入层加软提示，Prefix Tuning 在每层都加前缀，后者容量更大。

```python
# Prefix Tuning
prefix = nn.Parameter(torch.randn(num_prefix_tokens, d_model))

def forward(self, x):
    x = torch.cat([self.prefix.expand(batch, -1, -1), x], dim=1)
    return transformer(x)
```

| 方法 | 说明 |
|------|------|
| Prompt Tuning | 只在输入层加软提示 |
| Prefix Tuning | 每层都加前缀 |

## 5.3 优缺点与边界

**结论先行**：提示式参数量极少，但容量受软提示长度限制，且占用上下文窗口。

| 优点 | 缺点 |
|------|------|
| 参数量极少 | 效果受限于软提示容量 |
| 不改模型 | 占用上下文 |

**边界**：软提示会挤占有效上下文长度，长文本任务需预留 token 预算。

# 6. BitFit

## 6.1 原理

**结论先行**：BitFit 只训练偏置项，冻结其余所有参数，参数量约 0.1%。

```
只训练偏置项（bias），冻结其他所有参数：

  参数量 ≈ 0.1%
  效果：在部分任务上接近全量微调
```

## 6.2 代码实现

**结论先行**：实现极简，只需按名称设置 `requires_grad`。

```python
for name, param in model.named_parameters():
    param.requires_grad = "bias" in name
```

### 6.2.1 与 LoRA 的组合

**结论先行**：BitFit 可与 LoRA 叠加，用极低成本进一步扩大可训练范围。

**机制**：把偏置项与 LoRA 适配器同时设为可训练，其余冻结；适合数据量很小但需要更多自由度的场景。

## 6.3 边界

**结论先行**：BitFit 在分类与部分 NLU 任务上性价比高，但在生成类任务上通常弱于 LoRA。

**反例**：对需要学习新输出格式的生成任务，仅调偏置往往不足以改变模型的生成分布。

# 7. DoRA

## 7.1 幅度与方向分解

**结论先行**：DoRA（Weight-Decomposed Low-Rank Adaptation，权重分解低秩适配）把权重更新拆成幅度与方向两部分分别学习。

```
把权重更新分解为"幅度"和"方向"：
  W' = m × (W + BA) / ||W + BA||

效果优于 LoRA，但计算稍多
```

### 7.1.1 公式逐项解释

**结论先行**：DoRA 将"更新方向"与"更新幅度"解耦，分别用低秩矩阵与标量向量表达。

| 符号 | 含义 | 是否可训练 |
|------|------|:----------:|
| `m` | 幅度向量 | 是 |
| `W` | 原始权重 | 否 |
| `B·A` | 低秩方向更新 | 是 |
| `\|\|W + BA\|\|` | 列范数归一化 | 否 |

## 7.2 公式解读

**结论先行**：`m` 是可训练的幅度向量，`(W + BA) / ||W + BA||` 是归一化后的方向，两者相乘得到新权重。

## 7.3 与 LoRA 对比

| 维度 | LoRA | DoRA |
|------|:----:|:----:|
| 参数量 | 少 | 略多（含 m） |
| 效果 | 好 | 略优 |
| 计算开销 | 低 | 稍高 |
| 成熟度 | 高 | 新 |

# 8. 方法对比

## 8.1 综合对比表

**结论先行**：从参数量、效果、推理开销与成熟度四个维度综合比较，LoRA 是当前默认选择。

| 方法 | 参数量 | 效果 | 推理开销 | 主流 |
|------|:------:|:----:|:--------:|:----:|
| 全量 | 100% | 最好 | 无 | — |
| LoRA | 0.1%~1% | 接近全量 | 无 | 是 |
| QLoRA | 同 LoRA | 略低 | 无 | 是 |
| Adapter | 1%~5% | 好 | 有 | 中 |
| Prefix | 0.01%~0.1% | 中 | 有 | 中 |
| BitFit | ~0.1% | 中 | 无 | 少 |
| DoRA | 同 LoRA | 略优 | 无 | 新 |

### 8.1.1 默认选择与例外

**结论先行**：默认选 LoRA，仅在显存或参数预算被硬性约束时才考虑其他方法。

**反例**：为"极致省参数"选择 Prefix Tuning，却用在长上下文任务上，软提示挤占窗口导致效果与吞吐双输。

## 8.2 参数量与效果

**结论先行**：参数量与效果并非线性关系，超过一定阈值后收益递减。

```
效果
  │            ┌──────── 全量
  │        ┌───┘
  │    ┌───┘ LoRA（全模块）
  │  ┌─┘
  │ ┌┘ LoRA（仅注意力）
  │┌┘
  └──────────────────▶ 参数量
```

## 8.3 推理开销

**结论先行**：可合并的方法（LoRA、QLoRA、DoRA）推理零开销，其余方法均有额外成本。

| 方法 | 是否可合并 | 推理开销 |
|------|:----------:|:--------:|
| LoRA | 是 | 无 |
| QLoRA | 需反量化后合并 | 无 |
| DoRA | 是 | 无 |
| Adapter | 否 | 有 |
| Prefix | 否 | 有 |

# 9. 选择建议

## 9.1 按场景选择

**结论先行**：大多数场景应默认 LoRA，再根据显存与参数预算调整。

| 场景 | 推荐 |
|------|------|
| 通用微调 | LoRA |
| 显存受限 | QLoRA |
| 多任务切换 | LoRA 多适配器 |
| 极致省参数 | Prefix / Prompt Tuning |
| 追求效果 | LoRA（全模块）+ 更大 rank |

### 9.1.1 场景与成本量化

**结论先行**：先估算显存与存储预算，再决定方法，可避免反复试错。

| 场景 | 训练显存 | 单任务产物 |
|------|:--------:|:----------:|
| LoRA | 中 | 几十 MB |
| QLoRA | 低 | 几十 MB |
| Adapter | 中 | 数百 MB |
| Prefix | 低 | 数 MB |

## 9.2 决策流程

**结论先行**：按"显存 → 任务复杂度 → 部署方式"的顺序逐层决策。

```
显存是否受限？
  是 → QLoRA
  否 → 任务是否复杂？
         是 → LoRA 全模块 + 大 rank
         否 → LoRA 注意力层
部署是否需要零延迟？
  是 → 选择可合并方法（LoRA / DoRA）
```

## 9.3 组合使用

**结论先行**：PEFT 方法可组合，例如 QLoRA + 多适配器可同时兼顾显存与多任务。

**生产建议**：组合会增加调参维度，建议先固定一种方法跑通基线，再逐步叠加。

# 10. 生产注意事项

## 10.1 方法选择风险

| 风险 | 建议 |
|------|------|
| 方法选择随意 | 优先 LoRA |
| rank 不当 | 8~64，评测调优 |
| 无评测 | 对比基座 |

## 10.2 评测与版本管理

**结论先行**：适配器需要像代码一样版本化，否则线上问题难以复现。

| 风险 | 建议 |
|------|------|
| 适配器管理混乱 | 版本化 + 命名规范 |
| 无法复现 | 保存配置与数据版本 |

## 10.3 部署要点

**结论先行**：多适配器部署时优先采用"单基座 + 动态加载"，避免显存被多份权重占满。

```
单基座 + 动态适配器：
  ┌─────────────┐
  │  共享基座    │
  └──────┬──────┘
     ┌───┼───┐
     ▼   ▼   ▼
    A   B   C   ← 按请求切换
```

# 11. 小结

## 11.1 要点回顾

- PEFT 只训练少量参数，大幅降低微调成本。
- 主流是 LoRA（可合并、无推理开销）。
- Adapter 有推理开销，Prefix/Prompt 参数量极少。
- 选择优先 LoRA/QLoRA。
- 必须评测对比基座。

## 11.2 实践清单

- 先打印可训练参数比例，确认适配器生效。
- 固定一套留出集，对比基座与微调后指标。
- 适配器版本与基座版本绑定管理。
- 多任务优先"单基座 + 动态加载"。
