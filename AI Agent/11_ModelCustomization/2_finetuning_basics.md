# 1. 什么是微调

**结论先行**：微调（Fine-Tuning）= 在预训练模型基础上，用特定数据继续训练，调整模型参数，把"通用模型"变成"专用模型"。

## 1.1 定义与直觉

```
预训练模型（通用）→ 微调（特定任务/领域）→ 专用模型
```

### 1.1.1 机制

预训练让模型学会语言与世界知识，微调则在此基础上用少量高质量数据做"定向再训练"，使模型在目标任务上表现更好。

### 1.1.2 边界与坑

微调不是"喂知识"，而是"调行为"：它能改风格与能力，但知识注入效率低，且容易过拟合小数据。

## 1.2 预训练与微调的关系

| 阶段 | 数据 | 目标 | 数据量 |
|------|------|------|:------:|
| 预训练 | 海量无标注文本 | 学语言与知识 | 极大 |
| 微调 | 少量标注数据 | 学任务与风格 | 小 |

### 1.2.1 训练目标的延续

两者都用因果语言建模（Causal LM）目标，区别只在数据分布与学习率。

### 1.2.2 生产建议

微调学习率应比预训练小 1~3 个数量级，避免破坏已学知识。

## 1.3 微调能改变什么、不能改变什么

**结论先行**：微调擅长改行为（风格、格式、任务能力），不擅长做实时知识注入。

| 能改变 | 不能改变 |
|--------|----------|
| 输出风格与口吻 | 知识的实时性 |
| 特定任务准确率 | 模型参数量与速度 |
| 指令遵循能力 | 基础推理上限 |
| 领域术语理解 | 训练数据之外的领域 |

### 1.3.1 反例

用微调让模型"记住"每天更新的库存数据，结果训练完即过时；正确做法是 RAG。

# 2. 全量微调 vs 参数高效微调

**结论先行**：全量微调更新所有参数、效果最好但成本极高；参数高效微调（PEFT）只训练少量参数，成本低、效果接近，是当前主流。

## 2.1 两类方法对比

| 类型 | 更新参数 | 显存 | 效果 |
|------|----------|:----:|------|
| 全量微调 | 全部 | 极高 | 最好 |
| 参数高效（PEFT） | 少量 | 低 | 接近 |

```
全量微调：70B 模型需要 ~1TB 显存（含优化器状态）
LoRA：    只需几十 GB
```

> **PEFT（如 LoRA）是当前主流**，成本低、效果好。

### 2.1.1 机制差异

```
全量微调：所有 θ 都参与更新，保存一份完整模型
PEFT：    冻结 θ，只训练旁路参数 Δθ，保存 Δθ（几十 MB）
```

### 2.1.2 边界与坑

- PEFT 对"大幅改变能力"的场景可能不足，需提高秩或改用全量。
- 全量微调对显存要求高，单卡通常跑不动大模型。

## 2.2 显存构成拆解

**结论先行**：训练显存远大于推理显存，因为要保存梯度与优化器状态。

| 组成 | 全量微调（混合精度 Adam） | LoRA |
|------|:------------------------:|:----:|
| 权重 | 2 字节/参数 | 2 字节/参数（冻结） |
| 梯度 | 2 字节/参数 | 仅适配器 |
| 优化器状态 | 8 字节/参数 | 仅适配器 |
| 主权重副本 | 4 字节/参数 | 无 |

估算公式：

```
全量微调显存 ≈ 参数量 × 16 字节 + 激活值
例：70B × 16B ≈ 1.12 TB
LoRA 显存     ≈ 基座模型 × 2 字节 + 适配器 + 激活值
```

### 2.2.1 生产建议

显存不足时，优先用 QLoRA（4 比特量化基座）进一步压低基座占用。

## 2.3 选型建议

| 场景 | 推荐 | 原因 |
|------|------|------|
| 单卡小模型 | LoRA/QLoRA | 省显存 |
| 多卡充足预算 | 全量微调 | 效果上限高 |
| 快速迭代 | LoRA | 训练快、可热插拔 |
| 能力大幅改造 | 全量或高秩 LoRA | 表达力需求高 |

# 3. 微调的三个阶段

**结论先行**：对齐一个可用模型通常分三步——SFT 学会遵循指令，奖励建模学习偏好，偏好优化完成对齐。

## 3.1 三阶段总览

```
① SFT（监督微调）：学会遵循指令
② 奖励建模：学习人类偏好（RLHF）
③ 偏好优化：DPO/PPO 对齐
```

### 3.1.1 阶段递进

```
基座模型 → SFT → 指令模型 → 偏好对齐 → 对齐模型
```

### 3.1.2 边界与坑

并非所有场景都要三阶段：多数业务只需 SFT，偏好对齐用于"好/坏回答"难以用规则表达时。

## 3.2 SFT / RM / DPO 各自目标

| 阶段 | 数据 | 目标 |
|------|------|------|
| SFT | 指令-回答 | 学会回答 |
| RM | 偏好对 | 学会打分 |
| DPO/PPO | 偏好对 | 对齐偏好 |

### 3.2.1 数据形态

- SFT：`(prompt, response)`。
- RM：`(prompt, chosen, rejected)`，输出标量奖励。
- DPO：同样用 `(prompt, chosen, rejected)`，但直接优化策略。

### 3.2.2 生产建议

SFT 数据质量决定下限，偏好数据决定上限，两者都需人工审核。

## 3.3 阶段顺序与依赖

**结论先行**：阶段顺序不可颠倒，SFT 是后续对齐的基础。

```
SFT（必需） → RM（可选） → PPO（可选）
                    ↘ DPO（跳过 RM，直接对齐）
```

### 3.3.1 依赖关系

- DPO 不需要显式奖励模型，直接从偏好对优化，工程更简单。
- PPO 需要先训练 RM，链路更重，但可控性更强。

# 4. 训练数据格式

**结论先行**：主流 SFT 数据采用"消息列表"格式，兼容多轮对话与系统提示。

## 4.1 消息格式

```json
{
  "messages": [
    {"role": "system", "content": "你是专业助手。"},
    {"role": "user", "content": "写一首关于春天的诗"},
    {"role": "assistant", "content": "春风拂面花自开..."}
  ]
}
```

### 4.1.1 字段说明

| 字段 | 说明 |
|------|------|
| role | 角色：system/user/assistant |
| content | 文本内容 |

### 4.1.2 边界与坑

多轮样本中若混入多个 assistant 轮次，需确保每轮都参与损失（或被正确掩码）。

## 4.2 损失掩码

**结论先行**：只在 assistant 部分计算损失，user 与 system 部分的标签被忽略。

```
输入：  [system][user][assistant]
标签：  -100   -100   [真实 token]
```

### 4.2.1 掩码原因

若对 user 部分也算损失，模型会学习"复述用户问题"，偏离指令跟随目标。

## 4.3 格式校验

```python
VALID_ROLES = {"system", "user", "assistant"}

def validate_messages(item):
    msgs = item.get("messages", [])
    if not msgs:
        return "空消息"
    for m in msgs:
        if m.get("role") not in VALID_ROLES:
            return f"非法角色: {m.get('role')}"
        if not m.get("content"):
            return "空内容"
    if msgs[-1]["role"] != "assistant":
        return "末条必须是 assistant"
    return None
```

### 4.3.1 生产建议

训练前用校验脚本全量扫描，拦截格式错误，避免训练中途崩溃。

# 5. 关键超参数

**结论先行**：SFT 的核心是"小学习率 + 少轮数"，配合合理的批大小与序列长度。

## 5.1 参数速查表

| 参数 | 典型值 | 说明 |
|------|--------|------|
| 学习率 | 1e-5 ~ 2e-5（SFT） | 比预训练小 |
| 轮数 | 1~3 | 过多过拟合 |
| 批大小 | 视显存 | — |
| 序列长度 | 2048~8192 | — |
| LoRA rank | 8~64 | 低秩维度 |
| LoRA alpha | 2×rank | 缩放 |

### 5.1.1 机制说明

学习率过大易破坏预训练知识，过小则学不动；轮数过多会过拟合小数据集。

### 5.1.2 生产建议

先用小规模数据跑 1 轮验证流程，再放大到全量数据。

## 5.2 学习率与轮数

**结论先行**：两者共同决定"学多少"，需联合调优。

| 数据规模 | 学习率 | 轮数 |
|----------|:------:|:----:|
| < 1k | 1e-5 | 2~3 |
| 1k~10k | 1e-5 | 1~2 |
| > 10k | 2e-5 | 1 |

### 5.2.1 边界与坑

小数据 + 多轮 + 大学习率 = 过拟合与遗忘的双重风险。

## 5.3 LoRA 专属参数

| 参数 | 说明 | 建议 |
|------|------|------|
| rank (r) | 低秩维度 | 8~64 |
| alpha (α) | 缩放系数 | 2r |
| dropout | 适配器 dropout | 0.05~0.1 |
| target_modules | 注入层 | q/k/v/o 投影 |

### 5.3.1 缩放公式

```
ΔW = (α / r) · B · A
```

提高 α/r 会放大适配器影响，等效于增大学习率。

### 5.3.2 生产建议

从 r=16、α=32 起步，效果不足再提高秩，同时关注显存变化。

# 6. 损失计算

**结论先行**：SFT 使用因果语言建模损失，只在 assistant 部分计算。

## 6.1 因果语言建模损失

公式：

```
L = - (1/N) · Σ_t log p(y_t | y_<t; θ)
```

其中 N 为参与计算的 token 数，y_t 为第 t 个目标 token。

### 6.1.1 机制

模型对每个位置预测下一个 token，损失为真实 token 的负对数似然。

### 6.1.2 边界与坑

padding token 必须被掩码，否则会被算进损失，污染梯度。

## 6.2 掩码机制

```
只在 assistant 部分计算损失：
  user 部分的 token 标签设为 -100（忽略）
```

```
位置:   s1 s2 s3 | u1 u2 | a1 a2 a3
labels: -100...  | -100.. | 真实 token
```

### 6.2.1 交叉熵实现

```python
import torch.nn.functional as F

def masked_lm_loss(logits, labels):
    # logits: [B, T, V], labels: [B, T]
    shift_logits = logits[..., :-1, :].contiguous()
    shift_labels = labels[..., 1:].contiguous()
    return F.cross_entropy(
        shift_logits.view(-1, shift_logits.size(-1)),
        shift_labels.view(-1),
        ignore_index=-100,
    )
```

### 6.2.2 生产建议

使用框架提供的 `DataCollatorForCompletionOnlyLM`，避免手写掩码出错。

## 6.3 代码实现

```python
labels = input_ids.clone()
labels[user_token_positions] = -100
loss = cross_entropy(logits, labels)
```

### 6.3.1 多轮掩码

多轮对话中，每个 user 轮次后到下一个 user 之前的 assistant 内容都参与损失；实现上遍历 assistant 片段，把其余位置的标签置为 -100。

# 7. 灾难性遗忘

**结论先行**：灾难性遗忘（Catastrophic Forgetting）指微调后模型丢失原有通用能力，是小数据微调的典型风险。

## 7.1 现象与机制

```
微调可能让模型"忘记"预训练能力
```

### 7.1.1 机制

梯度更新使权重偏离预训练分布，若数据单一、学习率大，则通用能力被覆盖。

### 7.1.2 边界与坑

遗忘往往在上线后才暴露：领域任务变好，但通用问答、多语言能力退化。

## 7.2 对策

| 对策 | 说明 |
|------|------|
| 低学习率 | 减少漂移 |
| 少轮数 | 1~3 轮 |
| 数据混合 | 混入通用数据 |
| LoRA | 只训练少量参数 |
| 正则化 | 约束参数变化 |

### 7.2.1 数据混合示例

按一定比例（如 20%）从通用语料中采样，与领域数据混合后打乱，可显著缓解遗忘。

### 7.2.2 生产建议

微调后必须跑通用能力回归测试，量化遗忘程度。

## 7.3 检测方法

| 方法 | 说明 |
|------|------|
| 通用评测集 | 微调前后对比分数 |
| 领域外抽样 | 人工抽查通用问题 |
| 困惑度监控 | 通用语料困惑度上升即预警 |

# 8. 过拟合

**结论先行**：过拟合指模型记住训练数据、泛化变差，典型信号是训练损失下降而验证损失上升。

## 8.1 信号

| 信号 | 说明 |
|------|------|
| 训练损失下降、验证损失上升 | 典型过拟合 |
| 泛化能力下降 | 在测试集变差 |

### 8.1.1 曲线示意

```
loss
  |  train \___
  |            \____
  |  val   ___/
  |       /  \____  <- 验证损失回升
  +------------------→ steps
        最佳停止点
```

### 8.1.2 边界与坑

小数据集上即使 1 轮也可能过拟合，需用验证集实时监控。

## 8.2 对策

| 对策 | 说明 |
|------|------|
| 早停 | 验证损失回升即停 |
| 少轮数 | 1~3 轮 |
| 更多数据 | 增加数据量 |
| 正则化 | 权重衰减 |

### 8.2.1 早停实现

记录每轮验证损失，若连续若干轮不再创新低，则回退到最优检查点。

### 8.2.2 生产建议

保存验证损失最优的检查点，而非最后一个检查点。

## 8.3 与遗忘的区别

| 维度 | 过拟合 | 灾难性遗忘 |
|------|--------|------------|
| 表现 | 泛化差 | 通用能力退化 |
| 原因 | 记住训练样本 | 权重偏离预训练 |
| 对策 | 早停、正则 | 低学习率、数据混合 |

# 9. 训练框架

**结论先行**：微调主要在 Python 生态，主流框架各有侧重。

## 9.1 主流框架

| 框架 | 特点 |
|------|------|
| HuggingFace Transformers + PEFT | 主流 |
| LLaMA-Factory | 易用，支持多种方法 |
| Unsloth | 快，省显存 |
| Axolotl | 配置化 |
| DeepSpeed | 分布式 |

### 9.1.1 机制差异

- Transformers + PEFT：灵活、生态全，适合二次开发。
- LLaMA-Factory / Axolotl：配置驱动，适合快速实验。
- Unsloth：内核优化，训练更快更省显存。
- DeepSpeed：ZeRO 分片，支撑大模型分布式训练。

### 9.1.2 生产建议

研究阶段用 LLaMA-Factory 快速验证，生产用 Transformers + PEFT 或 DeepSpeed 固化。

## 9.2 选择建议

| 需求 | 推荐框架 |
|------|----------|
| 快速上手 | LLaMA-Factory |
| 极致省显存 | Unsloth |
| 大模型分布式 | DeepSpeed |
| 深度定制 | Transformers + PEFT |

> 微调主要在 Python 生态，Java 侧用于**推理与集成**。

### 9.2.1 Java 集成示例

```java
// Java 侧通常不训练，而是调用微调后的推理服务
public String chat(String prompt) {
    Map<String, Object> body = Map.of(
        "model", "my-sft-model",
        "messages", List.of(Map.of("role", "user", "content", prompt))
    );
    return httpClient.post("/v1/chat/completions", body, String.class);
}
```

# 10. 生产注意事项

**结论先行**：上线前需逐项检查数据、训练、评测与部署风险。

## 10.1 风险清单

| 风险 | 建议 |
|------|------|
| 数据质量差 | 严格筛选 |
| 轮数过多 | 1~3 轮 |
| 灾难性遗忘 | 低学习率 + 数据混合 |
| 无评测 | 微调前后对比 |
| 全量微调成本高 | 用 LoRA |

## 10.2 上线检查单

```
[ ] 训练数据已去重、去泄漏、脱敏
[ ] 验证集与测试集独立
[ ] 领域指标达标
[ ] 通用能力回归通过
[ ] 推理延迟与成本可接受
[ ] 版本与回滚方案就绪
```

### 10.2.1 生产建议

把检查单固化为 CI 流程，任何微调版本上线前自动校验。

# 11. 小结

- 微调在预训练模型上用特定数据继续训练。
- PEFT（LoRA）是主流，成本低效果好。
- 三阶段：SFT → 奖励建模 → 偏好优化。
- 关键超参：低学习率、少轮数。
- 防灾难性遗忘与过拟合是重点。
- 训练在 Python 生态，Java 侧负责推理与集成。
- 上线前必须做回归评测与版本管理。
