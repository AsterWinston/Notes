# 1. 数据是微调的关键

**结论先行**：微调效果由数据质量与数量共同决定，且质量远比数量重要；数据决定微调的效果上限，训练只是逼近这个上限。

## 1.1 质量与数量的关系

```
微调效果 = 数据质量 × 数量
质量远比数量重要
```

> **1000 条高质量数据可能胜过 10 万条低质量数据**（LIMA 结论）。

### 1.1.1 机制

低质量数据会教给模型错误模式，数量再多也只是放大错误；高质量数据信噪比高，梯度方向更准。

### 1.1.2 边界与坑

"质量"并非主观感觉，而是可度量的：正确性、一致性、多样性、格式合规率。

## 1.2 LIMA 结论与直觉

**结论先行**：少量精挑细选的数据即可显著改变模型行为，这是"少而精"策略的依据。

| 策略 | 数据量 | 效果 | 风险 |
|------|:------:|:----:|------|
| 少而精 | 1k 级 | 好 | 多样性不足 |
| 多而杂 | 100k 级 | 不稳定 | 噪声放大 |

### 1.2.1 直觉解释

SFT 是"行为示范"，模型只需少量高质量示范即可学会风格与格式，无需海量样本。

### 1.2.2 生产建议

先把 1k 条数据打磨到高质量，验证流程与效果，再决定是否扩量。

## 1.3 数据决定效果上限

**结论先行**：无论用多好的框架或超参，模型都无法超越训练数据所体现的能力上限。

```
效果
  |            ___________  <- 数据上限
  |        ___/
  |    ___/
  +------------------→ 训练量
```

### 1.3.1 推论

数据天花板低时，调参收益递减；应先提升数据质量再谈调参。

# 2. 数据来源

**结论先行**：数据来源各有权衡，最佳实践是真实数据为主、模型扩充为辅、人工审核兜底。

## 2.1 来源对比

| 来源 | 质量 | 成本 | 规模 |
|------|:----:|:----:|:----:|
| 人工标注 | 最高 | 高 | 小 |
| 真实业务数据 | 高 | 低 | 中 |
| 强模型生成 | 中 | 低 | 大 |
| 开源数据集 | 中 | 低 | 大 |
| 失败案例回流 | 高（针对性强） | 低 | 小 |

> 最佳组合：**真实数据 + 强模型扩充 + 人工审核**。

### 2.1.1 机制

不同来源互补：真实数据贴合业务分布，模型生成补多样性，人工审核保底线。

### 2.1.2 边界与坑

强模型生成的数据可能带有"模型味"（冗长、套话），需人工改写或过滤。

## 2.2 最佳组合

```
真实业务数据（骨干）
      +
强模型扩充（放大规模与多样性）
      +
人工审核（纠错、去偏、保风格）
      ↓
高质量 SFT 数据集
```

### 2.2.1 配比建议

| 来源 | 占比 | 作用 |
|------|:----:|------|
| 真实数据 | 50%~70% | 贴合业务 |
| 模型生成 | 20%~40% | 扩规模 |
| 人工精修 | 10%~20% | 提质量 |

## 2.3 各来源的坑

| 来源 | 典型坑 | 应对 |
|------|--------|------|
| 人工标注 | 成本高、速度慢、标准不一 | 制定标注规范 |
| 真实数据 | 含 PII、噪声、分布偏 | 脱敏 + 清洗 |
| 模型生成 | 幻觉、套话、同质化 | 校验 + 改写 |
| 开源数据 | 许可与质量不明 | 审核许可与抽样 |
| 失败回流 | 样本偏难、覆盖窄 | 补充简单样本 |

# 3. SFT 数据格式

**结论先行**：统一采用消息列表（messages）格式，兼容单轮、多轮与工具调用。

## 3.1 消息格式

```json
{
  "messages": [
    {"role": "system", "content": "你是一个专业的中文助手。"},
    {"role": "user", "content": "解释什么是依赖注入"},
    {"role": "assistant", "content": "依赖注入是一种设计模式..."}
  ]
}
```

### 3.1.1 字段规范

| 字段 | 必填 | 说明 |
|------|:----:|------|
| role | 是 | system/user/assistant |
| content | 是 | 文本内容 |
| tools | 否 | 工具定义（工具调用场景） |

### 3.1.2 边界与坑

system 消息可选，但若训练与推理都带 system，则训练数据也应包含，否则行为不一致。

## 3.2 单轮与多轮

**结论先行**：多轮样本需保证角色交替、末条为 assistant。

```json
{
  "messages": [
    {"role": "user", "content": "北京天气如何"},
    {"role": "assistant", "content": "请允许我查询。"},
    {"role": "user", "content": "好的"},
    {"role": "assistant", "content": "今天晴，25 度。"}
  ]
}
```

### 3.2.1 校验规则

- 角色严格交替（user → assistant → user → ...）。
- 末条必须为 assistant。
- 不出现连续两个相同角色。

## 3.3 工具调用格式

**结论先行**：工具调用（Function Calling）数据需在 assistant 消息中表达调用意图。

```json
{
  "messages": [
    {"role": "user", "content": "查一下上海明天的天气"},
    {"role": "assistant", "content": "",
     "tool_calls": [{"name": "get_weather",
                     "arguments": {"city": "上海", "date": "明天"}}]},
    {"role": "tool", "content": "{\"temp\": 26, \"cond\": \"多云\"}"},
    {"role": "assistant", "content": "上海明天多云，26 度。"}
  ]
}
```

### 3.3.1 生产建议

工具调用数据要覆盖"该调用""不该调用""参数错误"三类边界样本。

# 4. 数据构造方法

**结论先行**：数据构造有三条主线——强模型生成、文档生成问答、真实对话提取。

## 4.1 用强模型生成

```python
def generate_sft_data(seed_instructions, teacher_model):
    data = []
    for instruction in seed_instructions:
        response = teacher_model.chat(instruction)
        data.append({
            "messages": [
                {"role": "user", "content": instruction},
                {"role": "assistant", "content": response}
            ]
        })
    return data
```

### 4.1.1 机制

以种子指令（seed instruction）驱动教师模型（teacher model）产出回答，快速放大数据规模。

### 4.1.2 边界与坑

教师模型会引入自身偏见与幻觉，生成结果必须抽样校验，不能直接入库。

### 4.1.3 生产建议

对种子指令做多样性控制（主题、难度、长度），避免生成数据同质化。

## 4.2 从文档生成问答

```python
def generate_from_docs(documents, teacher_model):
    data = []
    for doc in documents:
        # 生成问题
        questions = teacher_model.chat(
            f"根据下面文档生成 5 个问题：\n{doc}")
        # 生成答案
        for q in questions:
            answer = teacher_model.chat(
                f"根据文档回答：\n文档：{doc}\n问题：{q}")
            data.append({"messages": [
                {"role": "user", "content": q},
                {"role": "assistant", "content": answer}
            ]})
    return data
```

### 4.2.1 机制

先"反向出题"再"据文作答"，把非结构化文档转为指令-回答对。

### 4.2.2 边界与坑

答案必须可溯源到原文，否则会引入幻觉；需加引用校验。

### 4.2.3 生产建议

保留 (doc_id, question, answer) 溯源字段，便于审计。

## 4.3 从真实对话提取

```python
def extract_from_logs(conversation_logs):
    data = []
    for log in conversation_logs:
        if log.is_successful() and log.has_positive_feedback():
            data.append({"messages": log.messages()})
    return data
```

### 4.3.1 机制

从线上日志筛选"成功且获好评"的会话，天然贴合业务分布。

### 4.3.2 边界与坑

日志含 PII 与用户隐私，必须脱敏；成功判定标准需明确。

### 4.3.3 生产建议

优先用真实成功案例做骨干数据，再用生成数据补长尾。

# 5. 数据清洗

**结论先行**：清洗是微调前的必做环节，覆盖长度、质量、去重、有害、格式五类。

## 5.1 清洗流程

```python
def clean_sft_data(data):
    cleaned = []
    for item in data:
        # ① 过滤过短/过长
        if len(item["assistant"]) < 20: continue
        if len(item["assistant"]) > 8000: continue
        # ② 过滤低质量
        if is_low_quality(item["assistant"]): continue
        # ③ 去重
        if is_duplicate(item, cleaned): continue
        # ④ 过滤有害内容
        if contains_harmful(item): continue

        cleaned.append(item)
    return cleaned
```

### 5.1.1 流程示意

```
原始数据 → 长度过滤 → 质量过滤 → 去重 → 有害过滤 → 格式统一 → 干净数据
```

### 5.1.2 边界与坑

清洗规则过严会损失长尾样本，过松则噪声入库；规则需基于抽样分析制定。

## 5.2 清洗项说明

| 清洗项 | 说明 |
|--------|------|
| 长度过滤 | 太短无信息，太长占资源 |
| 质量过滤 | 移除低质量回答 |
| 去重 | 移除重复 |
| 有害过滤 | 移除违规内容 |
| 格式统一 | 统一消息格式 |

### 5.2.1 质量判定维度

- 正确性：事实是否准确。
- 完整性：是否答非所问。
- 风格一致性：是否符合目标口吻。

## 5.3 去重算法

**结论先行**：精确去重看完全一致，近似去重看相似度。

### 5.3.1 精确去重

对每条样本的全文做哈希（如 MD5），哈希相同即视为重复，复杂度 O(n)。

### 5.3.2 近似去重

按字符集合的 Jaccard 相似度（交集大小 / 并集大小）判断，超过阈值（如 0.9）即判为近似重复。

### 5.3.3 生产建议

先用精确去重快速压缩，再对剩余数据做近似去重，兼顾效率与效果。

# 6. 数据配比

**结论先行**：配比决定模型能力分布，应按目标任务调整。

## 6.1 推荐配比

```
一个高质量 SFT 数据集应覆盖：
├── 通用对话（30%）
├── 领域任务（40%）
├── 推理与数学（15%）
├── 代码（10%）
└── 安全拒答（5%）
```

> 配比影响模型能力分布，按目标调整。

### 6.1.1 配比表

| 类别 | 占比 | 作用 |
|------|:----:|------|
| 通用对话 | 30% | 保通用能力，防遗忘 |
| 领域任务 | 40% | 目标能力 |
| 推理与数学 | 15% | 提升推理 |
| 代码 | 10% | 代码能力 |
| 安全拒答 | 5% | 对齐与安全 |

### 6.1.2 边界与坑

领域占比过高会削弱通用能力，需靠通用对话数据"压舱"。

## 6.2 配比调整策略

| 目标 | 调整 |
|------|------|
| 强化领域 | 提高领域任务占比 |
| 防遗忘 | 提高通用对话占比 |
| 提升推理 | 提高推理与数学占比 |
| 增强安全 | 提高安全拒答占比 |

### 6.2.1 生产建议

配比在实验阶段固定并记录，便于复现；变更配比视为新版本。

# 7. 数据规模

**结论先行**：规模随目标复杂度上升，起步 1000 条即可验证流程。

## 7.1 规模建议

| 目标 | 建议规模 |
|------|:--------:|
| 格式/风格微调 | 500~2000 |
| 领域适配 | 2000~10000 |
| 能力提升 | 10000+ |
| 从头对齐 | 100000+ |

> 起步 1000 条即可验证，效果不够再扩。

### 7.1.1 机制

任务越复杂、所需能力越广，覆盖其行为空间所需样本越多。

### 7.1.2 边界与坑

规模不是越大越好，低质量大数据的收益可能为负。

## 7.2 起步策略

```
1000 条高质量 → 跑通流程 → 评估 → 定向扩量
                              ↓
                    哪里差补哪里
```

### 7.2.1 生产建议

按"缺口驱动"扩量：根据评测错误分析，针对性补充样本类别。

# 8. 数据质量检查

**结论先行**：训练前用脚本全量校验结构，拦截格式错误。

## 8.1 校验脚本

```python
def validate_sft_data(data):
    issues = []
    for i, item in enumerate(data):
        msgs = item["messages"]
        # ① 必须有 user 和 assistant
        if not any(m["role"] == "user" for m in msgs):
            issues.append(f"{i}: 缺少 user")
        if not any(m["role"] == "assistant" for m in msgs):
            issues.append(f"{i}: 缺少 assistant")
        # ② 顺序正确
        if not is_valid_order(msgs):
            issues.append(f"{i}: 消息顺序错误")
    return issues
```

### 8.1.1 生产建议

校验失败样本记录到日志，按错误类型统计，反哺数据治理。

## 8.2 常见问题清单

| 问题 | 说明 | 处理 |
|------|------|------|
| 缺 user | 只有 assistant | 补全或丢弃 |
| 缺 assistant | 只有提问 | 补答或丢弃 |
| 顺序错误 | 角色错乱 | 重排或丢弃 |
| 空内容 | content 为空 | 丢弃 |
| 编码异常 | 乱码 | 修复或丢弃 |

# 9. 数据版本管理

**结论先行**：数据必须版本化，保证训练可复现、可回滚。

## 9.1 目录结构

```
data/
├── v1/
│   ├── train.jsonl
│   └── val.jsonl
├── v2/
│   ├── train.jsonl
│   └── val.jsonl
└── manifest.json
```

### 9.1.1 命名规范

| 名称 | 说明 |
|------|------|
| train.jsonl | 训练集 |
| val.jsonl | 验证集 |
| test.jsonl | 测试集（独立） |
| manifest.json | 版本元数据 |

### 9.1.2 边界与坑

只改数据不升版本，会导致"同版本不同结果"，无法复现。

## 9.2 清单文件

```json
{
  "version": "v2",
  "size": 5000,
  "source": "mixed",
  "createdAt": "2026-09-21",
  "changes": ["增加了代码数据", "移除了低质量样本"]
}
```

### 9.2.1 字段说明

| 字段 | 说明 |
|------|------|
| version | 版本号 |
| size | 样本数 |
| source | 数据来源 |
| createdAt | 创建日期 |
| changes | 变更记录 |

## 9.3 版本对比

对比两版的样本 ID 集合，可快速得出新增与删除数量，作为变更记录的依据。

### 9.3.1 生产建议

每次微调记录"数据版本 + 代码版本 + 超参"，形成实验台账。

# 10. 生产注意事项

**结论先行**：数据环节的风险集中在质量、泄漏、重复、配比、版本与隐私。

## 10.1 风险清单

| 风险 | 建议 |
|------|------|
| 数据质量差 | 严格筛选 |
| 数据泄漏 | 训练/测试严格隔离 |
| 数据重复 | 去重 |
| 配比失衡 | 按目标配比 |
| 无版本 | 版本化管理 |
| 含 PII | 脱敏 |

## 10.2 数据泄漏防护

**结论先行**：泄漏会让评测虚高，掩盖真实泛化能力。

```
同一问题/近似问题
   ├── 出现在 train → 泄漏
   └── 又出现在 test → 评测虚高
```

### 10.2.1 生产建议

训练前做一次跨集合近似去重，泄漏率纳入数据验收指标。

# 11. 小结

- 数据质量决定微调效果，质量 > 数量。
- 来源：人工标注、真实数据、模型生成、失败回流。
- 清洗：长度、质量、去重、有害、格式。
- 配比按目标调整，覆盖多类任务。
- 数据必须版本化、隔离、脱敏。
- 训练前全量校验结构与泄漏，训练后按缺口定向扩量。
