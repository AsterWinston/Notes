# 1. 为什么微调后必须评估

微调（Fine-tuning）是对模型参数做有监督或偏好优化的过程，它天然带有不确定性。训练损失下降不代表业务指标提升，因此必须用独立的数据来验证效果，而不是凭感觉判断。

## 1.1 微调的三类结果

```
微调可能：
- 提升了目标能力
- 但损害了通用能力（灾难性遗忘）
- 或者根本没提升（数据质量差）

必须用数据验证
```

### 1.1.1 正向提升

目标能力提升，通用能力基本持平，这是最理想的结果，可直接进入部署流程。

### 1.1.2 此消彼长

目标能力上升，但通用能力明显下降，典型表现是灾难性遗忘（Catastrophic Forgetting）。需要在数据配比上做调整。

### 1.1.3 无效微调

目标与通用能力都没有提升，通常源于数据质量差、格式混乱或训练超参不当。

## 1.2 不评估的代价

| 风险 | 后果 |
|------|------|
| 盲目上线 | 线上质量下降，用户流失 |
| 只测目标能力 | 通用能力退化未被发现 |
| 不做安全测试 | 越狱风险上升 |
| 无基线对比 | 无法判断微调是否值得 |

## 1.3 评估的基本原则

- 用独立评测集，绝不能与训练集重叠。
- 必须对比基座模型，量化提升幅度。
- 目标、通用、安全、格式四个维度都要覆盖。
- 评估结果要有版本记录，可复现。

## 1.4 评估与训练的关系

```
训练 → 评估 → 分析 → 调整数据/超参 → 再训练
          ↑___________________________|
```

评估不是一次性动作，而是训练闭环的一环。只有形成"训练—评估—归因—再训练"的循环，微调才能持续收敛到可用状态。

# 2. 评估维度

## 2.1 五维评估模型

```
① 目标能力：微调想提升的能力
② 通用能力：是否退化
③ 安全性：是否更容易被越狱
④ 格式遵循：输出是否符合要求
⑤ 效率：延迟与成本
```

### 2.1.1 目标能力

衡量微调是否达成初衷，例如领域问答准确率、函数调用正确率、结构化输出合规率。

### 2.1.2 通用能力

衡量模型在未针对性训练任务上的表现，用于发现灾难性遗忘。

### 2.1.3 安全与格式

安全指对越狱与有害请求的拒答能力；格式指输出是否符合约定的结构（JSON、字段、模板）。

## 2.2 维度权重与取舍

| 维度 | 权重建议 | 说明 |
|------|:--------:|------|
| 目标能力 | 40% | 微调的核心目标 |
| 通用能力 | 25% | 防退化 |
| 安全 | 20% | 不可妥协 |
| 格式 | 10% | 工程可用性 |
| 效率 | 5% | 成本约束 |

权重并非固定，安全敏感场景应显著提高安全权重。

## 2.3 评估金字塔

```
        +---------------+
        |   人工评审    |  可信度最高，成本最高
        +---------------+
        | LLM-as-Judge  |  语义质量，中等成本
        +---------------+
        |   基准测试    |  可横向对比
        +---------------+
        | 规则/精确匹配 |  最快最便宜
        +---------------+
```

自下而上成本递增、可信度递增。实践中先用低成本方法快速筛选，再用高成本方法确认。

# 3. 评估方法

## 3.1 方法总览

| 方法 | 说明 | 成本 |
|------|------|:----:|
| 精确匹配 | 与标准答案完全一致 | 低 |
| 规则校验 | 格式、字段 | 低 |
| LLM-as-Judge | 语义质量 | 中 |
| 人工评审 | 最终把关 | 高 |
| 基准测试 | 标准数据集 | 中 |

## 3.2 自动评估

### 3.2.1 精确匹配与规则校验

精确匹配（Exact Match）适用于答案唯一的任务，如分类、抽取、计算。规则校验用于检查 JSON 是否合法、必填字段是否齐全。

```python
import json

def check_format(output, required_fields):
    try:
        data = json.loads(output)
    except json.JSONDecodeError:
        return False
    return all(f in data for f in required_fields)
```

### 3.2.2 LLM-as-Judge

对开放式生成，用更强模型作为裁判打分。裁判提示词需要明确评分维度与量表，并给出示例。

```python
JUDGE_PROMPT = """请为下面的回答打分（1-5 分），只输出分数。
问题：{question}
回答：{answer}
评分标准：1=错误，3=部分正确，5=完全正确。
"""

def judge_score(judge_model, question, answer):
    prompt = JUDGE_PROMPT.format(question=question, answer=answer)
    return int(judge_model.generate(prompt).strip())
```

> 注意：LLM 裁判存在位置偏好与长度偏好，建议随机交换 A/B 顺序取平均。

## 3.3 人工评审与基准测试

- 人工评审：对高价值、低容错场景做人工盲评，是最终把关手段。
- 基准测试：使用 MMLU、HumanEval 等公开数据集，便于横向对比。

## 3.4 方法选择决策

```
任务输出是否唯一？
├─ 是 → 精确匹配 / 规则校验
└─ 否 → 是否有参考答案？
    ├─ 有 → LLM-as-Judge + 关键点覆盖
    └─ 无 → LLM-as-Judge / 人工评审
```

| 场景 | 推荐方法 | 理由 |
|------|----------|------|
| 分类/抽取 | 精确匹配 | 答案唯一 |
| 结构化输出 | 规则校验 | 可程序化验证 |
| 开放问答 | LLM-as-Judge | 语义灵活 |
| 高风险决策 | 人工评审 | 最终把关 |

# 4. 对比基座

## 4.1 为什么必须对比

> **不对比基座，就无法判断微调是否值得。**

同一评测集上，微调模型若没有显著优于基座，说明微调没有产生价值，应回退到 Prompt 或 RAG 方案。

## 4.2 对比实现

```python
def compare_with_base(base_model, finetuned_model, test_cases):
    results = []
    for case in test_cases:
        base_output = base_model.generate(case["prompt"])
        ft_output = finetuned_model.generate(case["prompt"])

        base_score = judge.score(case, base_output)
        ft_score = judge.score(case, ft_output)

        results.append({
            "case": case["id"],
            "base": base_score,
            "finetuned": ft_score,
            "delta": ft_score - base_score
        })

    print(f"基座平均: {avg(r['base'] for r in results):.3f}")
    print(f"微调平均: {avg(r['finetuned'] for r in results):.3f}")
    print(f"提升: {avg(r['delta'] for r in results):.3f}")
    return results
```

## 4.3 统计显著性

小幅提升可能只是噪声。建议：

- 评测样本足够多（目标维度至少 100 条）。
- 报告置信区间或做配对检验。
- 对同一模型多次采样，取平均降低随机性。

## 4.4 对比维度表

| 对比对象 | 目的 |
|----------|------|
| 基座模型 | 判断微调是否有效 |
| 上一版本 | 判断是否退化 |
| Prompt / RAG 方案 | 判断是否值得微调 |
| 商用 API | 判断自建性价比 |

横向对比时应固定解码参数（温度、top_p、max_tokens），否则结论不可比。

# 5. 通用能力评估

## 5.1 灾难性遗忘

```
微调后必须检查通用能力是否退化：
  用通用评测集（如 MMLU 子集）测试
  若明显下降 → 灾难性遗忘
```

灾难性遗忘的根因是梯度更新过度拟合目标分布，覆盖了原有知识。缓解手段是混入通用数据。

## 5.2 通用能力测试集

| 能力 | 测试 |
|------|------|
| 通用知识 | MMLU 子集 |
| 推理 | 数学题 |
| 代码 | HumanEval 子集 |
| 指令遵循 | 自定义用例 |

## 5.3 回归判定

| 指标 | 阈值 | 结论 |
|------|:----:|------|
| 通用能力下降 ≤ 2% | 可接受 | 通过 |
| 下降 2%~5% | 观察 | 调整数据配比 |
| 下降 > 5% | 严重 | 灾难性遗忘 |

## 5.4 缓解策略

```
数据层：混入 10%~30% 通用指令数据
训练层：降低学习率、减少训练轮数、加早停
结构层：使用 LoRA 而非全量微调，冻结更多参数
```

| 策略 | 效果 | 成本 |
|------|------|:----:|
| 数据混合 | 最有效 | 低 |
| 降低学习率 | 中 | 低 |
| 早停 | 中 | 低 |
| LoRA | 高（天然缓解） | 低 |

# 6. 安全评估

## 6.1 安全对齐的脆弱性

安全对齐（Safety Alignment）在微调中极易被破坏：只要训练数据里出现少量不安全的问答对，模型就可能学会顺从有害请求。因此微调后必须重测安全。

## 6.2 越狱测试

```python
def evaluate_safety(model):
    attacks = load_attacks("eval/jailbreak-attacks.json")
    refused = 0

    for attack in attacks:
        response = model.generate(attack["prompt"])
        if is_refusal(response):
            refused += 1

    return refused / len(attacks)
```

## 6.3 安全指标

| 指标 | 含义 | 目标 |
|------|------|:----:|
| 拒答率 | 对有害请求的拒绝比例 | 越高越好 |
| 越狱成功率 | 绕过防护的比例 | 越低越好 |
| 误拒率 | 正常请求被拒比例 | 越低越好 |

> 微调可能降低安全对齐，必须重新测试。

## 6.4 安全数据配比

| 数据类型 | 建议占比 | 说明 |
|----------|:--------:|------|
| 目标领域 | 60%~80% | 主体 |
| 通用指令 | 10%~20% | 防遗忘 |
| 安全拒答 | 5%~10% | 保对齐 |
| 边界对抗 | 1%~5% | 防越狱 |

安全样本过少不足以维持对齐，过多又会挤占目标能力，需在评测中反复权衡。

# 7. 评估集设计

## 7.1 数据结构

```json
[
  {
    "id": "e1",
    "prompt": "解释 Spring 的 IoC 容器",
    "expected": "IoC 是控制反转...",
    "mustContain": ["控制反转", "依赖注入"],
    "category": "domain"
  },
  {
    "id": "e2",
    "prompt": "写一首关于春天的诗",
    "category": "general",
    "evaluator": "llm_judge"
  }
]
```

字段说明：

| 字段 | 含义 |
|------|------|
| `id` | 唯一标识 |
| `prompt` | 输入 |
| `expected` | 参考答案（可选） |
| `mustContain` | 必须包含的关键词 |
| `category` | 所属类别 |
| `evaluator` | 评测器类型 |

## 7.2 类别配比

| 类别 | 占比 |
|------|:----:|
| 目标领域 | 50% |
| 通用能力 | 30% |
| 安全 | 10% |
| 边界 | 10% |

## 7.3 黄金集与防过拟合

- 保留一份"黄金集"（Golden Set），绝不参与训练与调参。
- 评测集一旦用于调参，就会过拟合，需要定期轮换。
- 边界样本（空输入、超长输入、对抗输入）单独成组。

## 7.4 评测集规模

| 维度 | 最少条数 | 说明 |
|------|:--------:|------|
| 目标能力 | 100 | 结论稳定性 |
| 通用能力 | 100 | 检测退化 |
| 安全 | 50 | 越狱用例 |
| 边界 | 30 | 异常输入 |

样本过少时单条差异会显著影响均值，导致结论不可靠。

# 8. 评估报告

## 8.1 报告字段

```python
@dataclass
class FineTuneReport:
    target_improvement: float      # 目标能力提升
    general_regression: float      # 通用能力退化
    safety_score: float            # 安全性
    avg_latency_ms: int
    avg_cost: float
```

## 8.2 结论判定

```python
    def verdict(self):
        if self.target_improvement > 0.05 and self.general_regression > -0.03:
            return "微调有效，可上线"
        if self.general_regression < -0.05:
            return "灾难性遗忘，需调整"
        return "提升不明显，不建议上线"
```

## 8.3 报告模板

```
微调评估报告
  基座：Qwen2.5-7B
  微调：LoRA r=16，1000 步
  评测集：业务集 500 条 + 黄金集 200 条

  目标能力：0.71 → 0.84（+0.13）
  通用能力：0.75 → 0.73（-0.02）
  安全拒答：0.96 → 0.94（-0.02）
  格式合规：0.98 → 0.99（+0.01）
  平均延迟：210ms → 215ms（+2%）

  结论：微调有效，可上线（灰度发布）
```

## 8.4 自动化流水线

```python
def run_evaluation(model, base_model, eval_set):
    report = FineTuneReport(
        target_improvement=delta_target(model, base_model, eval_set),
        general_regression=delta_general(model, base_model, eval_set),
        safety_score=evaluate_safety(model),

    )
    print(report.verdict())
    return report
```

流水线应纳入 CI，每次模型更新自动触发，产出可对比的报告。

# 9. 常见问题

## 9.1 问题诊断表

| 现象 | 原因 | 对策 |
|------|------|------|
| 目标提升但通用退化 | 灾难性遗忘 | 混入通用数据 |
| 都没提升 | 数据质量差 | 检查数据 |
| 格式变差 | 数据格式不一致 | 统一格式 |
| 安全下降 | 对齐被破坏 | 混入安全数据 |
| 过拟合 | 轮数多 | 早停 |

## 9.2 典型案例

- 案例一：领域问答提升 15%，但通用对话答非所问。对策是降低学习率并混入 20% 通用指令数据。
- 案例二：函数调用准确率不升反降。排查发现训练数据中函数签名与实际不一致，统一 schema 后恢复。
- 案例三：输出 JSON 时常缺字段。原因是训练样本格式不统一，统一模板后解决。

## 9.3 根因分析流程

```
指标异常 → 定位维度 → 抽样分析 → 归因 → 修复 → 复测
```

| 维度异常 | 优先排查 |
|----------|----------|
| 目标能力不升 | 数据质量、标注一致性 |
| 通用能力下降 | 数据配比、学习率、轮数 |
| 格式变差 | 训练样本格式、模板一致性 |
| 安全下降 | 安全样本配比、对齐数据 |

# 10. 生产注意事项

## 10.1 风险清单

| 风险 | 建议 |
|------|------|
| 只看目标能力 | 也测通用能力 |
| 不对比基座 | 必须对比 |
| 无安全测试 | 微调后重测 |
| 评测集过拟合 | 保留黄金集 |
| 无版本记录 | 记录模型版本 |

## 10.2 持续评估

- 上线后持续采集线上样本，定期回灌到评测集。
- 对每次模型更新重跑完整评测流水线。
- 建立指标看板，设置质量回退告警。

## 10.3 版本与复现

```
记录内容：
  - 基座模型版本与哈希
  - 训练数据版本与配比
  - 超参数（学习率、轮数、LoRA 秩）
  - 评测集版本与评测脚本版本
  - 评测结果与结论

目标：任一历史版本都能被完整复现
```

# 11. 小结

## 11.1 核心结论

- 微调后必须评估：目标能力、通用能力、安全、格式。
- **必须对比基座**，否则无法判断价值。
- 关注灾难性遗忘（通用能力退化）。
- 安全对齐可能被破坏，需重新测试。
- 保留未参与训练的黄金集。

## 11.2 落地清单

- 评测集覆盖目标、通用、安全、边界四类。
- 评测流程自动化，纳入 CI。
- 报告记录模型版本与关键指标。
- 上线采用灰度，设定回退阈值。
