# 1. 什么是 LLM-as-Judge

LLM-as-Judge（用大模型当评委）是用一个语言模型对另一个模型或系统的输出进行质量判定，以替代部分人工评审的技术。

## 1.1 定义与工作流

结论先行：Judge 的本质是把"主观质量判断"转成"可批量执行的模型调用"，从而让开放生成也能被自动评测。

### 1.1.1 基本流程

```
问题 + 参考答案 + 模型输出 → Judge 模型 → 分数 + 理由
```

一次完整的 Judge 调用包含四个要素：评测指令（Rubric，评分标准）、被评对象（回答，有时含参考资料）、评分空间（二元/分级/成对）、输出格式（便于解析）。

### 1.1.2 与人工评审的关系

Judge 不是替代人工，而是放大人力：人工只用于校准与仲裁，批量判断交给 Judge。

| 维度 | 人工评审 | LLM-as-Judge |
|------|----------|--------------|
| 成本 | 高 | 低 |
| 速度 | 慢 | 快 |
| 一致性 | 低（人各有尺） | 高（同一 Prompt） |
| 准确性 | 最高 | 中（需校准） |
| 可扩展 | 差 | 好 |

## 1.2 优势与风险

### 1.2.1 优势

- 便宜：单次判定成本远低于人工。
- 快：可并发，几分钟跑完数百条。
- 可扩展：支持任意规模与任意维度。
- 可解释：可要求输出理由，便于归因。

### 1.2.2 风险

- 偏差：位置、长度、自偏好等系统性偏差。
- 不稳定：同一输入多次调用可能给不同结果。
- 不可信：未经校准的 Judge 分数只是"看起来合理"。

## 1.3 边界与反例

- 反例：用生成回答的同一模型来当 Judge，会系统性偏好自己的输出。
- 边界：Judge 擅长"语义层面"判断，不擅长精确计算与事实核查。
- 边界：Judge 本身也是 LLM，会受提示注入影响，需对输入做防护。

# 2. 适用场景

结论先行：Judge 适合"语义模糊、无法用规则判定"的场景，不适合"有唯一正确答案"的场景。

## 2.1 适合的场景

### 2.1.1 开放生成质量

摘要、改写、创作等没有唯一答案，只能从相关性、流畅度、信息量等维度判断。

### 2.1.2 RAG 忠实度

判断回答是否完全基于检索到的参考资料、有无幻觉（Hallucination）或矛盾。

### 2.1.3 语义等价

判断两个表达是否语义相同，用于答案比对（比字符串匹配更宽容）。

## 2.2 不适合的场景

### 2.2.1 精确计算与事实核查

数学计算、日期推算、单位换算等应交给代码或工具，Judge 容易算错。

### 2.2.2 高风险决策

医疗、法律、金融等高风险结论必须人工复核，不能只靠 Judge。

## 2.3 场景选择表

| 场景 | 适用 | 说明 |
|------|:----:|------|
| 开放生成质量评估 | 适合 | 无唯一答案 |
| RAG 忠实度判断 | 适合 | 语义蕴含判断 |
| 语义等价判断 | 适合 | 比字符串匹配宽容 |
| 精确计算/事实核查 | 不适合 | 用规则或工具 |
| 高风险决策 | 不适合 | 需人工 |

> 判断准则：如果"正确答案"能被程序化表达，就用规则；否则才用 Judge。

# 3. 打分模式

结论先行：二元判断与成对比较最稳定，分级评分波动最大，能用二元/成对就不要用分级。

## 3.1 四种模式

### 3.1.1 二元

只输出通过/不通过（是/否、FAITHFUL/UNFAITHFUL）。判定空间小，稳定性最高。

### 3.1.2 分级

输出 1~5 或 0~1 的分数。信息量大，但不同批次间口径易漂移。

### 3.1.3 成对比较

给两个回答，判断哪个更好（A/B/TIE）。避免了"分数绝对值无意义"的问题。

### 3.1.4 多维度

对相关性、忠实度、完整性等分别打分，再按权重聚合。

| 模式 | 说明 | 稳定性 |
|------|------|:------:|
| 二元（是/否） | 通过/不通过 | 高 |
| 分级（1~5） | 多级评分 | 中 |
| 成对比较 | A vs B 哪个更好 | 高 |
| 多维度 | 分维度打分 | 中 |

## 3.2 模式选择

```
要"是否达标"       → 二元
要"版本 A vs B"     → 成对比较
要"多维诊断"        → 多维度（每维尽量二元化）
要"绝对分数"        → 分级（最后考虑）
```

## 3.3 边界与坑

- 分级评分存在"分数聚集"（都打 3~4 分），区分度差。
- 成对比较无法给出"绝对质量"，只能排序。
- 多维度打分若维度定义重叠，会出现重复计分。

# 4. 实现：二元判断

结论先行：二元判断是最可靠的 Judge 形式，关键是把判定标准写清楚并把输出解析做鲁棒。

## 4.1 忠实度判断

### 4.1.1 Prompt 设计

Rubric 要明确"什么算忠实"：不编造、不矛盾、不引入参考资料之外的信息。

### 4.1.2 Java 实现

```java
interface Judge {

    @UserMessage("""
            判断模型回答是否忠实于参考资料（不编造、不矛盾）。

            参考资料：
            {{context}}

            模型回答：
            {{answer}}

            只输出 FAITHFUL 或 UNFAITHFUL。
            """)
    String judgeFaithfulness(@V("context") String context,
                             @V("answer") String answer);
}
```

```java
public boolean isFaithful(String context, String answer) {
    String raw = judge.judgeFaithfulness(context, answer);
    return "FAITHFUL".equals(normalize(raw));
}
```

## 4.2 鲁棒解析

### 4.2.1 输出规范化

模型可能输出 "FAITHFUL."、"忠实"、带引号或前后空格，需统一处理：

```java
private String normalize(String raw) {
    if (raw == null) {
        return "UNKNOWN";
    }
    String s = raw.strip().toUpperCase(Locale.ROOT)
            .replaceAll("[^A-Z]", "");
    if (s.contains("UNFAITHFUL")) return "UNFAITHFUL";  // 先判否定
    if (s.contains("FAITHFUL")) return "FAITHFUL";
    return "UNKNOWN";
}
```

### 4.2.2 兜底策略

解析失败时不应默认通过，应记为 UNKNOWN 并重试或转人工。关键用例可多次调用取多数，仍无法解析则抛出异常转人工，绝不静默判为通过。

## 4.3 边界与坑

- 解析时先匹配否定词（UNFAITHFUL 包含 FAITHFUL 子串），否则会误判。
- 解析失败默认"通过"是最危险的错误，会把问题隐藏。
- 单次判定不稳定，关键用例可多次投票。

# 5. 实现：多维度评分

结论先行：多维度评分用于诊断而非决策，聚合权重应由业务定义，且各维度定义不能重叠。

## 5.1 维度定义

### 5.1.1 相关性

回答是否切题、是否回应了用户真实意图。

### 5.1.2 忠实度

回答是否完全基于参考资料，有无编造。

### 5.1.3 完整性

回答是否覆盖了问题所需的全部要点。

## 5.2 Java 实现

```java
public record JudgeResult(
        double relevance,        // 相关性 0~1
        double faithfulness,     // 忠实度 0~1
        double completeness,     // 完整性 0~1
        String reason
) {}
```

```java
interface MultiDimJudge {

    @UserMessage("""
            评估模型回答的质量，每个维度 0~1 分：

            1. relevance：回答是否切题
            2. faithfulness：是否完全基于参考资料
            3. completeness：是否完整回答了问题

            问题：{{question}}
            参考资料：{{context}}
            模型回答：{{answer}}

            输出 JSON：
            {"relevance":0.0,"faithfulness":0.0,"completeness":0.0,"reason":""}
            """)
    JudgeResult judge(@V("question") String q,
                      @V("context") String ctx,
                      @V("answer") String ans);
}
```

## 5.3 加权聚合

```
Score = w1 * relevance + w2 * faithfulness + w3 * completeness
其中 w1 + w2 + w3 = 1
```

例如 `w = (0.2, 0.5, 0.3)`，强调忠实度优先。

```java
public double aggregate(JudgeResult r) {
    return 0.2 * r.relevance()
            + 0.5 * r.faithfulness()
            + 0.3 * r.completeness();
}
```

## 5.4 边界与坑

- 维度越多，判定越不稳定，建议不超过 4 个。
- 权重不要拍脑袋，应与人工排序做相关性验证。
- 各维度语义重叠会导致"重复加分"。

# 6. 成对比较

结论先行：成对比较最适合版本对比，能规避分数绝对值问题，但必须做位置交换。

## 6.1 比较机制

### 6.1.1 输出空间

只允许三种结果：A 更好、B 更好、平局（TIE）。输出空间小，稳定性高。

### 6.1.2 胜率统计

对 N 条用例比较两版本，胜率 = 获胜数 / 总对比数。胜率与置信区间共同判断优劣。

## 6.2 Java 实现

```java
interface PairwiseJudge {

    @UserMessage("""
            比较两个回答的质量，哪个更好？

            问题：{{question}}

            回答 A：
            {{answerA}}

            回答 B：
            {{answerB}}

            评判标准：准确性、完整性、可读性。

            只输出 A 或 B 或 TIE。
            """)
    String compare(@V("question") String q,
                   @V("answerA") String a,
                   @V("answerB") String b);
}
```

## 6.3 位置交换

```java
public String compareWithSwap(String q, String a, String b) {
    String result1 = judge.compare(q, a, b);      // A 在前
    String result2 = judge.compare(q, b, a);      // B 在前

    // 交换后仍一致才可信
    if ("A".equals(result1) && "B".equals(result2)) {
        return "A";
    }
    if ("B".equals(result1) && "A".equals(result2)) {
        return "B";
    }
    return "TIE";                                 // 不一致 → 平局
}
```

> 两次调用成本翻倍，但能显著降低位置偏差。若预算有限，可只对"有争议"的用例做交换。

## 6.4 边界与坑

- 位置交换后仍不一致说明用例区分度低或 Judge 不稳，应记为 TIE。
- 平局过多会降低比较的统计功效。
- 成对比较需保证两回答的可见性对等（都截断到同长度）。

# 7. 已知偏差

结论先行：Judge 的偏差是系统性的，必须在评测流程中主动缓解，而不是期望它"自己准确"。

## 7.1 偏差清单

### 7.1.1 位置偏差

Judge 偏好靠前或靠后的答案。缓解：交换位置两次评估。

### 7.1.2 长度偏差

Judge 偏好更长的回答（显得更全面）。缓解：在 Prompt 中明确"不因长度加分"。

### 7.1.3 自偏好

Judge 偏好与自己风格一致的回答。缓解：用不同模型做 Judge。

## 7.2 其他偏差

### 7.2.1 权威偏差

被自信语气、专业术语影响。缓解：要求"基于事实而非语气判断"。

### 7.2.2 分数聚集

分级评分时集中在中间分。缓解：改用二元或成对比较。

| 偏差 | 说明 | 缓解 |
|------|------|------|
| 位置偏差 | 偏好靠前/靠后的答案 | 交换位置两次评估 |
| 长度偏差 | 偏好更长的回答 | 提示明确不因长度加分 |
| 自偏好 | 偏好自己生成的答案 | 用不同模型做 Judge |
| 权威偏差 | 被自信语气影响 | 要求基于事实判断 |
| 分数聚集 | 都给 3~4 分 | 用二元或成对比较 |

## 7.3 缓解位置偏差

核心做法是"交换位置两次评估，只有两次结论一致才采信"，具体实现见 6.3 的 `compareWithSwap`。若预算有限，可只对"有争议"的用例做交换。

## 7.4 边界与坑

- 缓解手段都有成本（翻倍调用或换模型），需按用例重要性分级。
- 偏差无法完全消除，只能降低；因此 Judge 结果应与人工校准。
- 多个偏差可能叠加，导致结论严重偏离。

# 8. 校准

结论先行：未经人工标注校准的 Judge 不可用于决策，一致率低于 80% 说明不可靠。

## 8.1 为什么校准

Judge 的分数是"模型认为的质量"，不等于"真实质量"。只有用人工标注数据比对，才能知道它是否可信。

## 8.2 一致率计算

### 8.2.1 代码

```java
public void calibrate(List<LabeledCase> labeled) {
    int agreement = 0;
    for (LabeledCase c : labeled) {
        boolean judgeSaysGood = judge.isFaithful(c.context(), c.answer());
        if (judgeSaysGood == c.humanLabelGood()) {
            agreement++;
        }
    }
    double rate = agreement / (double) labeled.size();
    log.info("Judge 与人工一致率: {}", rate);

    if (rate < 0.8) {
        log.warn("Judge 需重新设计提示或更换模型");
    }
}
```

### 8.2.2 混淆矩阵

一致率之外，还应看混淆矩阵，识别 Judge 是"过严"还是"过松"：

| Judge \ 人工 | 好 | 差 |
|--------------|:--:|:--:|
| 判为好 | TP | FP |
| 判为差 | FN | TN |

过严：FN 高（把好答案判差）；过松：FP 高（把差答案判好）。

## 8.3 提升一致率

```
① 细化 Rubric：给出正反例
② 换更强模型
③ 二元化：降低判定难度
④ 多次投票：取多数
⑤ 人工仲裁分歧样本
```

## 8.4 边界与坑

- 校准集必须与调优集隔离，否则一致率虚高。
- 一致率对类别不均衡不敏感，需结合混淆矩阵。
- 模型更新后必须重新校准。

# 9. Judge 模型选择

结论先行：Judge 应选强模型、且与生成模型不同；预算受限时用"小模型 + 二元判断 + 抽样"。

## 9.1 选择维度

| 选择 | 说明 |
|------|------|
| 强模型做 Judge | 更准，成本高 |
| 与生成模型不同 | 避免自偏好 |
| 小模型 + 二元判断 | 性价比高 |
| 多 Judge 投票 | 更稳，成本高 |

## 9.2 组合策略

### 9.2.1 多 Judge 投票

用 2~3 个不同模型判定，取多数（过半即通过），可降低单模型偏差。

### 9.2.2 分层抽样

全量用便宜模型，对"临界样本"再用强模型复核：

```
第一层：小模型判定
第二层：仅对 0.4~0.6 之间的模糊样本用强模型
```

## 9.3 边界与坑

- 多 Judge 若都用同系列模型，偏差高度相关，投票收益有限。
- 强模型也可能有偏差，不能盲信。
- 换 Judge 模型等于换了一把尺子，历史结果不可直接比较。

# 10. 结构化输出

结论先行：让 Judge 输出结构化结果（JSON），是让评测可程序化处理的前提。

## 10.1 为什么结构化

自由文本难以解析，且格式漂移会导致解析失败。结构化输出让字段可索引、可统计、可入库。

## 10.2 Java 实现

```java
// 让 Judge 输出结构化结果，便于程序处理
JudgeResult result = judgeClient.prompt()
        .user(judgePrompt)
        .call()
        .entity(JudgeResult.class);

if (result.faithfulness() < 0.8) {
    report.addFailure(caseId, result.reason());
}
```

## 10.3 容错

Judge 调用可能超时、限流或返回非法结构。应捕获异常，把该条用例标记为"待人工"而非判为通过，并保留原始响应以便排查。

## 10.4 边界与坑

- 结构化输出并非 100% 可靠，需保留原始响应以便排查。
- 数值字段要限制范围（如 0~1），越界视为异常。
- 理由字段可能被注入内容污染，展示时需转义。

# 11. 生产注意事项

结论先行：把 Judge 当成一个需要持续校准的"测量仪器"，而不是一次性脚本。

## 11.1 风险清单

| 风险 | 建议 |
|------|------|
| 未校准 | 用人工标注校准 |
| 位置偏差 | 交换位置评估 |
| 自偏好 | 换不同模型 |
| 分数聚集 | 用二元/成对 |
| 成本高 | 小模型 + 抽样 |
| 无理由 | 要求输出理由 |

## 11.2 落地清单

选二元或成对模式 → 写清 Rubric 与输出格式 → 用人工标注集校准（一致率 >= 80%）→ 缓解位置/长度/自偏好偏差 → 结构化解析 + 失败兜底 → 模型更新后重新校准。

## 11.3 常见坑

- 用 Judge 分数当唯一验收标准，忽略人工复核。
- Judge 与生成用同一模型，结论偏向自身。
- 不记录 Judge 原始输出，问题无法复现。

# 12. 小结

## 12.1 核心结论

- LLM-as-Judge 便宜高效，适合开放生成评估。
- 二元判断与成对比较最稳定。
- 注意位置、长度、自偏好等偏差并缓解。
- 必须用人工标注校准，一致率 < 80% 不可用。
- Judge 与生成用不同模型，避免自偏好。

## 12.2 落地清单

定模式 → 写 Rubric → 校准 → 抗偏差 → 结构化 → 定期复核。
