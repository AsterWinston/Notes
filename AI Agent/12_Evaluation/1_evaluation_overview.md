# 1. 为什么评测是刚需

评测（Evaluation，简称 Eval）是用可复现的量化手段，判断一个大语言模型（Large Language Model，LLM）应用"是否变好、是否变坏"的工程实践。没有评测，任何优化都只能依赖主观"感觉"。

## 1.1 无评测的三大盲区

结论先行：无评测的团队会在三个方向上持续踩坑——改 Prompt 方向不明、换模型隐性退化、上线后效果漂移。

### 1.1.1 盲区一：Prompt 改动方向不明

Prompt（提示词）调整常带来"此消彼长"的效果：

```
改 Prompt 前：A 类问题 90%，B 类问题 80%
改 Prompt 后：A 类问题 82%，B 类问题 91%
```

只看 B 类会觉得"变好了"，只看 A 类会觉得"变坏了"。没有全量评测集，就无法判断净收益是正是负。

### 1.1.2 盲区二：模型替换的隐性退化

更换模型版本（如升级、降本换小模型）时，能力变化是非均匀的：常见问答可能持平，而长链推理、工具调用格式、多语言可能骤降。这类退化在"抽查几条"时几乎发现不了。

### 1.1.3 盲区三：上线后效果漂移

线上数据分布会随时间变化（数据漂移，Data Drift），Prompt、检索库、上游接口也在变。没有持续评测，退化往往在用户投诉时才被感知。

## 1.2 评测的成本收益模型

### 1.2.1 评测成本构成

| 成本项 | 说明 | 量级 |
|--------|------|------|
| 构建成本 | 评测集编写、标注 | 一次性，中 |
| 运行成本 | 调用被测系统与 Judge | 每次，中 |
| 维护成本 | 版本管理、回流 | 长期，低 |
| 机会成本 | 评测占用的工程时间 | 持续，低 |

### 1.2.2 缺陷逃逸成本

缺陷逃逸成本 = 线上故障概率 × 影响面 × 修复代价。评测的作用是把问题拦在发布之前，用可预期的小成本换取不确定的大损失。

## 1.3 边界与反例

- 评测不是万能的：评测集无法覆盖所有真实分布，只能降低风险。
- 评测本身也会引入偏差：用 LLM 当评委（LLM-as-Judge）有系统性偏好。
- 反例：把评测指标当成唯一目标，会导致"过拟合评测集"，指标涨而真实体验降。

# 2. 评测的三个层次

评测不是一个动作，而是分层的体系。结论先行：组件评测管选型，系统评测管发版，线上评测管真实效果。

## 2.1 组件评测

### 2.1.1 组件评测的对象

组件评测（Component Evaluation）针对系统中的单个模块：

```
├── Embedding（向量化）：检索召回是否准
├── Rerank（重排）：精排是否提升相关性
├── 工具调用：参数是否正确、是否该调用
├── 意图识别：分类是否正确
└── 抽取：字段是否完整、准确
```

### 2.1.2 组件评测的指标

| 组件 | 核心指标 |
|------|----------|
| Embedding | Recall@k、MRR |
| Rerank | NDCG@k、MRR 提升 |
| 工具调用 | 调用准确率、参数完全匹配率 |
| 意图识别 | 准确率、混淆矩阵 |

## 2.2 系统评测

### 2.2.1 端到端指标

系统评测（System Evaluation）把整条链路当成黑盒：

```
问题 → 检索 → 组装 Prompt → LLM → 回答
```

关注端到端：任务成功率、答案正确率、忠实度、延迟、成本。

### 2.2.2 分层归因

端到端失败必须能归因到具体层，否则无法修复：

```
失败回答
├── 检索层：没召回相关文档？
├── 生成层：召回了但没用 / 幻觉？
└── 路由层：走错了分支？
```

## 2.3 线上评测

### 2.3.1 A/B 实验

把用户流量随机分为对照组与实验组，比较核心业务指标。A/B 是唯一能验证"真实因果"的手段。

### 2.3.2 用户反馈信号

| 信号 | 强度 | 说明 |
|------|:----:|------|
| 显式点赞/点踩 | 强 | 样本稀疏，有偏 |
| 追问/重问 | 中 | 隐含不满意 |
| 复制/采纳 | 中 | 隐含满意 |
| 会话时长 | 弱 | 噪声大 |

## 2.4 三层对比与衔接

| 层次 | 时机 | 成本 | 反馈速度 | 真实性 |
|------|------|:----:|:--------:|:------:|
| 组件 | 选型时 | 低 | 快 | 低 |
| 系统 | 发版前 | 中 | 快 | 中 |
| 线上 | 发布后 | 高 | 慢 | 高 |

> 三层衔接：组件评测发现问题 → 系统评测确认影响 → 线上评测验证收益。

# 3. 离线评测 vs 在线评测

结论先行：离线评测保证"不退化"，在线评测验证"真提升"，二者缺一不可。

## 3.1 离线评测机制

离线评测使用固定评测集，在发布前运行：

```
评测集(固定) → 被测系统 → Evaluator → 报告
```

优点：可复现、成本可控、可接 CI。缺点：与真实流量存在分布差。

## 3.2 在线评测机制

在线评测使用真实流量，通过分流对比：

```
真实流量 → 分流器 ─┬─→ 版本 A → 业务指标
                   └─→ 版本 B → 业务指标
```

优点：真实。缺点：成本高、周期长、可能影响用户体验。

## 3.3 离线与在线的互补关系

### 3.3.1 离线保不退化

每次提交跑离线回归，作为门禁，防止质量倒退。

### 3.3.2 在线验真实效果

离线通过后，用小流量 A/B 验证业务指标，避免"指标虚高"。

## 3.4 边界与坑

- 离线评测集更新滞后，会与真实分布脱节。
- 在线 A/B 需要足够样本量才能达到统计显著，短周期可能得出错误结论。
- 两者指标口径要一致，否则离线涨、线上跌会互相矛盾。

| 维度 | 离线评测 | 在线评测 |
|------|----------|----------|
| 数据 | 固定评测集 | 真实流量 |
| 成本 | 可控 | 高 |
| 反馈速度 | 快 | 慢 |
| 真实性 | 有限 | 高 |
| 用途 | 回归、选型 | 效果验证 |

# 4. 指标设计原则

结论先行：好指标必须可度量、可对比、反映目标、稳定、可归因；缺一项都会让评测失去意义。

## 4.1 五大原则

### 4.1.1 可度量与可对比

可度量：能自动计算，不依赖人肉判断。可对比：不同版本用同一口径计算，数值直接可比。

### 4.1.2 反映目标与稳定

反映目标：指标要贴合业务目标（如"解决用户问题"而非"输出更长"）。稳定：多次测量波动小，避免噪声淹没真实差异。

### 4.1.3 可归因

失败必须能定位到具体用例、具体环节，否则无法修复。

| 原则 | 说明 |
|------|------|
| 可度量 | 能自动计算 |
| 可对比 | 版本间可比 |
| 反映目标 | 与业务目标一致 |
| 稳定 | 多次测量波动小 |
| 可归因 | 能定位问题 |

## 4.2 指标公式

### 4.2.1 准确率与通过率

```
Accuracy = 通过用例数 / 总用例数
PassRate = 满足全部断言的用例数 / 总用例数
```

### 4.2.2 检索指标

设 TP 为检索到的相关文档，FP 为检索到的不相关文档，FN 为漏掉的相关文档：

```
Precision = TP / (TP + FP)
Recall    = TP / (TP + FN)
F1        = 2 * Precision * Recall / (Precision + Recall)
MRR       = (1/|Q|) * Σ (1 / rank_i)
```

其中 `rank_i` 是第 i 个查询中第一个相关文档的排名。

### 4.2.3 生成指标

```
Faithfulness = 有依据的陈述数 / 总陈述数
Completeness = 覆盖的要点数 / 标准要点数
```

## 4.3 反例与边界

- 反例：用"回答长度"当质量指标，会奖励啰嗦。
- 边界：准确率在类别极不均衡时失效，应辅以混淆矩阵。

# 5. 评测方法

结论先行：方法没有最优，只有匹配——规则类便宜但死板，语义类灵活但引入偏差，人工最准但最贵。

## 5.1 方法总览

| 方法 | 说明 | 成本 | 稳定性 |
|------|------|:----:|:------:|
| 精确匹配 | 与标准答案完全相同 | 低 | 高 |
| 包含匹配 | 包含关键信息 | 低 | 高 |
| 规则校验 | 格式、字段、范围 | 低 | 高 |
| 相似度 | 语义相似度 | 中 | 中 |
| LLM-as-Judge | 模型评分 | 中 | 中 |
| 人工评审 | 人工打分 | 高 | 低 |

## 5.2 规则类方法

### 5.2.1 精确匹配

要求输出与标准答案逐字符相等，适合分类、抽取、格式化输出。

### 5.2.2 包含匹配

要求输出包含全部"必须包含"且不含"禁止包含"的关键信息，适合开放问答。

### 5.2.3 规则校验

校验格式、字段、数值范围，如 JSON 可解析、金额在区间内。

## 5.3 语义类方法

### 5.3.1 相似度

用向量余弦相似度或字符串编辑距离衡量与参考答案的接近程度，需设阈值。

### 5.3.2 LLM-as-Judge

用强模型给输出打分，适合开放生成，但需校准（见第 3 篇）。

### 5.3.3 人工评审

人工打分是金标准，用于构建校准集与黄金集，但成本高、一致性难保证。

## 5.4 方法选择与组合

```
精确/规则  → 能用规则就用规则（便宜稳定）
包含匹配  → 开放问答的兜底
相似度    → 语义近似
Judge     → 复杂语义判断
人工      → 校准与最终裁决
```

## 5.5 Java 实现

```java
public interface Evaluator {

    EvalResult evaluate(EvalCase testCase, String actual);
}
```

```java
public class ContainsEvaluator implements Evaluator {

    @Override
    public EvalResult evaluate(EvalCase c, String actual) {
        boolean pass = c.mustContain().stream().allMatch(actual::contains)
                && c.mustNotContain().stream().noneMatch(actual::contains);
        return EvalResult.of(pass, pass ? 1.0 : 0.0);
    }
}
```

## 5.6 边界与坑

- 包含匹配对同义词无效（"30 天" vs "一个月"）。
- 相似度高不等于正确，可能"形似而意反"。
- Judge 有位置、长度、自偏好等偏差，需缓解。

# 6. 评测集设计

结论先行：评测集是评测的根基，覆盖要全、配比要合理、要与代码一起版本化。

## 6.1 EvalCase 结构

```java
public record EvalCase(
        String id,
        String input,
        String expected,              // 标准答案（可选）
        List<String> mustContain,     // 必须包含
        List<String> mustNotContain,  // 禁止包含
        List<String> relevantDocIds,  // 检索评测用
        Map<String, Object> metadata
) {}
```

## 6.2 覆盖维度

### 6.2.1 问题类型

事实、流程、比较、推理、创作等，按业务实际分布配比。

### 6.2.2 难度与边界

简单、中等、困难；无答案、多意图、模糊表达。

### 6.2.3 对抗

提示注入（Prompt Injection）、越狱（Jailbreak）、诱导性提问。

| 类型 | 占比建议 |
|------|:--------:|
| 典型问题 | 50% |
| 边界情况 | 20% |
| 无答案问题 | 15% |
| 对抗/注入 | 15% |

## 6.3 抽样与配比

评测集不宜只取"容易通过"的样本；应按真实分布抽样，并对高风险场景过采样。

# 7. 评测流程

结论先行：评测是"准备集 → 跑系统 → 打分 → 汇总 → 对比基线"的固定流水线，应尽量自动化。

## 7.1 五步流程

```
① 准备评测集
② 跑被测系统，收集输出
③ 用 Evaluator 打分
④ 汇总指标
⑤ 与基线对比，判断是否达标
```

## 7.2 Java 实现

### 7.2.1 单条评测

```java
public EvalResult evaluateOne(EvalCase c, Assistant assistant) {
    long start = System.nanoTime();
    String actual = assistant.chat(c.input());
    long latencyMs = (System.nanoTime() - start) / 1_000_000;
    EvalResult result = evaluator.evaluate(c, actual);
    return result.withLatency(latencyMs);
}
```

### 7.2.2 批量汇总

```java
public EvalReport evaluate(List<EvalCase> cases, Assistant assistant) {
    List<EvalResult> results = new ArrayList<>();

    for (EvalCase c : cases) {
        String actual = assistant.chat(c.input());
        results.add(evaluator.evaluate(c, actual));
    }

    return EvalReport.builder()
            .total(cases.size())
            .passed(results.stream().filter(EvalResult::passed).count())
            .accuracy(passRate(results))
            .avgLatencyMs(avgLatency(results))
            .avgCost(avgCost(results))
            .build();
}
```

### 7.2.3 并发与重试

评测用例之间相互独立，可并发执行以缩短墙钟时间：

```java
public List<EvalResult> evaluateParallel(
        List<EvalCase> cases, Assistant assistant, int concurrency)
        throws Exception {

    try (var pool = Executors.newFixedThreadPool(concurrency)) {
        var futures = cases.stream()
                .map(c -> pool.submit(() -> evaluateOne(c, assistant)))
                .toList();
        var results = new ArrayList<EvalResult>();
        for (var f : futures) {
            results.add(f.get());
        }
        return results;
    }
}
```

> 注意：被测系统可能限流，需配合重试与退避；Judge 调用也要限流。

## 7.3 边界与坑

- 并发过高会触发限流，导致失败率上升、指标失真。
- 非确定性输出（temperature > 0）应固定随机种子或多轮取平均。
- 网络抖动应重试并记录，不能直接算作失败。

# 8. 阈值与门禁

结论先行：评测只有接入 CI 门禁才有约束力，不达标的提交不允许合并。

## 8.1 门禁机制

门禁（Quality Gate）在 CI 中对评测报告做断言，任一硬指标不达标即失败。

## 8.2 Java 实现

```java
public void assertQuality(EvalReport report) {
    if (report.accuracy() < 0.85) {
        throw new EvalFailedException(
                "准确率未达标: " + report.accuracy());
    }
    if (report.avgLatencyMs() > 3000) {
        throw new EvalFailedException(
                "延迟超标: " + report.avgLatencyMs());
    }
    if (report.avgCost().compareTo(new BigDecimal("0.05")) > 0) {
        throw new EvalFailedException(
                "成本超标: " + report.avgCost());
    }
}
```

## 8.3 基线对比与显著性

### 8.3.1 基线管理

把上一稳定版本作为基线，报告需同时展示"当前值、基线值、差值"。

### 8.3.2 置信区间

小样本下应给出置信区间，避免把噪声当提升：`p̂ ± z * sqrt(p̂(1-p̂)/n)`。
当 `n = 100`、`p̂ = 0.85` 时，95% 置信区间约为 `0.85 ± 0.07`。

## 8.4 边界与坑

- 硬阈值过严会导致"为过门禁而调参"，反而损害真实效果。
- 多指标门禁应区分"硬性"与"观察性"。
- 基线本身也可能退化，需定期重置。

# 9. 评测的反模式

结论先行：评测的失败往往不在工具，而在方法——数据、方法、流程三类反模式最常见。

## 9.1 反模式总览

| 类别 | 反模式 | 问题 |
|------|--------|------|
| 数据 | 评测集太小 | 统计不显著 |
| 数据 | 过拟合测试集 | 效果虚高 |
| 数据 | 只测 Happy Path | 漏边界与对抗 |
| 数据 | 覆盖不均 | 结论以偏概全 |
| 方法 | 人工评审无标准 | 主观不一致 |
| 方法 | Judge 未校准 | 分数不可信 |
| 方法 | 指标口径不一 | 版本不可比 |
| 流程 | 无基线对比 | 无法判断好坏 |
| 流程 | 评测不接 CI | 容易退化 |
| 流程 | 无归因 | 失败无法修复 |

## 9.2 共同根源

三类反模式都源于同一个错误：把评测当成"一次性任务"，而不是持续运营的流程。

## 9.3 自查清单

发布前自查：评测集是否过拟合？方法是否校准？是否接入了 CI 门禁？

# 10. 生产注意事项

结论先行：把评测当产品来运营——先建集、再接 CI、再上线上、最后做归因闭环。

## 10.1 风险清单

| 风险 | 建议 |
|------|------|
| 无评测集 | 先建集 |
| 集太小 | 50~200 条起步 |
| 无版本 | 与代码一起版本化 |
| 无门禁 | 接入 CI |
| 只离线 | 配合线上 A/B |
| 无归因 | 保留失败详情 |

## 10.2 落地清单

```
① 选 50 条真实问题建首版评测集
② 定义 3~5 个核心指标与阈值
③ 编写 Evaluator，接入 CI 触发评测
④ 失败详情归档，回流评测集
⑤ 上线后小流量 A/B 验证
```

## 10.3 常见坑

- 评测报告只给总分，不给失败样例，无法定位。
- 评测脚本与被测代码耦合，重构即失效。
- 评测集含 PII（个人隐私信息），需脱敏。

# 11. 小结

## 11.1 核心结论

- 评测是 LLM 应用迭代的前提，无评测即盲调。
- 三层：组件、系统、线上，分别对应选型、发版、真实效果。
- 离线保不退化，在线验真实效果，二者互补。
- 评测集要覆盖典型、边界、无答案、对抗。
- 阈值门禁接入 CI，失败详情回流。

## 11.2 落地清单

建集 → 定指标 → 写 Evaluator → 接 CI → 归档回流 → 上线 A/B。
