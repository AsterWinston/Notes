# 1. 为什么 LLM 应用更需要可观测

结论先行：传统 Web 服务的可观测性（Observability）已属必需，而 LLM（Large Language Model，大语言模型）应用因为引入了非确定性、长调用链和 Token（词元）成本，可观测性从"锦上添花"升级为"生存前提"。没有可观测性的 Agent（智能体）就是黑盒，无法运维、无法归因、无法优化成本。

## 1.1 非确定性带来的复现困难

结论先行：同样的输入，模型可能给出不同输出，导致"问题无法稳定复现"，因此必须记录当时的完整输入与决策上下文。

机制拆解：模型的采样过程（temperature、top_p、seed）决定了输出分布；即便参数固定，模型版本、系统提示、检索命中的文档片段也会改变结果。传统服务可用"相同请求 → 相同响应"做回归，LLM 应用必须用"相同输入 + 相同上下文 → 可接受范围内的输出"来判断。

| 特性 | 后果 |
|------|------|
| 输出非确定 | 同输入结果不同，难复现 |
| 调用链长 | 一次请求含多次模型/工具/检索 |
| 成本随 Token 变化 | 成本不可预测 |
| 延迟波动大 | 受模型与网络影响 |
| 上下文敏感 | 问题常在"喂给模型的内容" |
| 多步决策 | 失败点难以定位 |

### 1.1.1 采样参数与输出分布

机制拆解：`temperature` 越高，输出越随机；`seed` 只能保证同一后端在同一时刻的可复现性，跨版本不可靠。生产上应在 Trace 中记录采样参数，便于回放时对齐。

```java
public record SamplingParams(
        double temperature,
        double topP,
        int maxTokens,
        Long seed
) {
    public static SamplingParams production() {
        return new SamplingParams(0.2, 0.9, 1024, null);
    }
}
```

### 1.1.2 上下文漂移

机制拆解：多轮对话中，历史消息被截断或摘要，导致同一用户在第 3 轮与第 10 轮得到不同质量。可观测性需要记录"实际喂给模型的最终消息列表"，而非仅记录用户原始输入。

边界与坑：截断策略若只按条数而非 Token 数，容易在长消息时超出上下文窗口；摘要压缩会丢失关键约束，且不可逆。

生产建议：把最终 prompt 的哈希（hash）作为属性写入 Span，既能关联又不泄露原文。

## 1.2 长调用链与多步决策

结论先行：一次 Agent 请求往往包含多轮"模型决策 → 工具调用 → 再决策"，链路深度远超普通服务，任何一步失败都会导致最终答案错误。

机制拆解：ReAct（Reasoning + Acting，推理与行动）类范式让模型交替产生思考与动作。每一次模型调用、工具执行、检索、记忆读写都是一个可观测节点，串联起来才构成完整因果链。

### 1.2.1 调用链深度

```
普通服务：一次请求 = 一条链（深度 3~5）
Agent：   一次请求 = 多轮循环 + 多次模型/工具/检索（深度 10+）
```

### 1.2.2 失败点定位

机制拆解：错误可能来自模型幻觉、工具超时、检索空结果、参数解析失败或循环超限。只有按步骤记录状态，才能回答"第几步开始偏离"。

边界与坑：只记录最终答案，无法区分"模型答错"与"工具返回错数据"。

生产建议：为每个步骤设置独立 status 与耗时，失败步骤显式标记 ERROR。

## 1.3 成本与延迟的不可预测

结论先行：Token 消耗随输入长度和步数动态变化，导致单次请求成本与延迟方差极大，必须把成本作为一等指标监控。

机制拆解：输入 Token 由系统提示 + 历史 + 检索片段决定；输出 Token 由模型生成决定；步数由任务复杂度决定。三者相乘使成本呈长尾分布。

| 维度 | 影响因素 | 观测手段 |
|------|----------|----------|
| 输入成本 | 提示长度、检索片段 | input_tokens 指标 |
| 输出成本 | 生成长度 | output_tokens 指标 |
| 调用次数 | 步数、重试 | 每 Trace 调用数 |
| 延迟 | 模型排队、网络、工具 | P50/P95/P99 |

边界与坑：平均值掩盖长尾，成本超支往往由少数超大请求造成。

生产建议：按租户/用户/模型维度聚合成本，并对 P99 设阈值告警。

# 2. 可观测性三大支柱

结论先行：Trace（追踪）、Metrics（指标）、Logs（日志）三者互补，缺一不可；Trace 回答"这次请求发生了什么"，Metrics 回答"系统整体健康吗"，Logs 回答"具体细节是什么"。

## 2.1 Trace

结论先行：Trace 是单次请求的完整调用链，是定位"为什么这次失败"的核心工具。

机制拆解：一次请求生成唯一 `traceId`，链路上每个操作生成一个 Span（跨度），Span 之间通过 `parentSpanId` 组成树。详见第 5 节与第 2 篇笔记。

```
Trace   一次请求的完整调用链（模型、工具、检索、记忆）
Metrics 延迟、Token、成功率、错误率、成本
Logs    结构化日志（含脱敏后的提示与响应）
```

## 2.2 Metrics

结论先行：Metrics 是聚合的数值时间序列，用于监控趋势与告警。

机制拆解：计数器（counter）、仪表（gauge）、直方图（histogram）三类。延迟用直方图算分位数，成本用计数器累加，并发用仪表采样。

| 支柱 | 回答的问题 | 典型载体 |
|------|------------|----------|
| Trace | 这次请求发生了什么？ | Span 树 |
| Metrics | 系统整体健康吗？ | 时间序列 |
| Logs | 具体细节是什么？ | 结构化事件 |

## 2.3 Logs

结论先行：Logs 记录离散事件细节，是 Trace 的补充，尤其适合记录异常堆栈与原始输入输出。

机制拆解：日志应结构化（JSON），并携带 `traceId`/`spanId` 以便与 Trace 关联。禁止直接记录完整敏感 Prompt。

### 2.3.1 结构化日志字段

机制拆解：统一字段便于检索与聚合。

```yaml
logging:
  pattern:
    console: "%d{yyyy-MM-dd HH:mm:ss} %-5level [%X{traceId}] %logger{36} - %msg%n"
  level:
    root: INFO
    com.example.agent: DEBUG
```

### 2.3.2 日志脱敏

机制拆解：对手机号、身份证、邮箱等做掩码，对 Prompt 做长度截断。

```java
public static String mask(String text, int maxLen) {
    if (text == null) {
        return null;
    }
    String masked = text.replaceAll("\\d{11}", "***********");
    return masked.length() <= maxLen ? masked : masked.substring(0, maxLen) + "...";
}
```

边界与坑：非结构化日志无法聚合查询；日志中泄露 PII（Personally Identifiable Information，个人身份信息）会带来合规风险。

生产建议：统一日志字段规范，包含时间、级别、traceId、模块、消息、脱敏后的载荷。

# 3. LLM 应用特有的观测点

结论先行：除常规的延迟与错误外，LLM 应用有六类特有观测点，覆盖模型、工具、检索、记忆、Agent 与成本质量。

## 3.1 模型调用观测点

结论先行：模型调用是最核心的观测点，必须记录模型名、Token 用量、延迟与结束原因。

机制拆解：`finish_reason` 指示模型为何停止（stop、length、tool_calls），是判断截断与工具触发的重要依据。

### 3.1.1 finish_reason 判定

机制拆解：`stop` 表示正常结束；`length` 表示被 max_tokens 截断，需警惕答案不完整；`tool_calls` 表示触发工具。

| finish_reason | 含义 | 处理 |
|---------------|------|------|
| stop | 正常结束 | 无 |
| length | 被截断 | 提高 max_tokens 或压缩输入 |
| tool_calls | 触发工具 | 继续循环 |
| content_filter | 内容过滤 | 提示用户 |

### 3.1.2 Token 用量采集

机制拆解：从响应的 usage 字段读取，缺失时按字符估算并标记为估算值。

```java
Usage usage = response.getMetadata().getUsage();
span.setAttribute("llm.usage.input_tokens",
        usage == null ? -1 : usage.getPromptTokens());
span.setAttribute("llm.usage.estimated", usage == null);
```

| 属性 | 含义 | 用途 |
|------|------|------|
| `llm.model` | 模型名 | 归因与成本 |
| `llm.usage.input_tokens` | 输入 Token | 成本 |
| `llm.usage.output_tokens` | 输出 Token | 成本 |
| `llm.finish_reason` | 结束原因 | 判断截断 |
| `llm.latency_ms` | 模型耗时 | 性能 |

## 3.2 工具与检索观测点

结论先行：工具与检索是"外部世界"的入口，其参数与结果决定模型决策的正确性。

机制拆解：工具记录名称、参数（脱敏）、耗时、状态；检索记录查询、命中数、相似度分数，用于诊断"答错是否因检索未命中"。

```
① 模型调用：模型名、Token、延迟、finish_reason
② 工具调用：工具名、参数、耗时、结果状态
③ 检索：查询、命中数、相似度分数
④ 记忆：读写、命中条数
⑤ Agent：步数、决策、循环
⑥ 成本：按模型/租户/用户
⑦ 质量：评测分数、用户反馈
```

## 3.3 记忆、Agent 与成本质量

结论先行：记忆与 Agent 步数反映系统行为，成本与质量反映业务结果，二者共同构成运营视图。

机制拆解：记忆读写记录命中条数可发现"记忆未生效"；Agent 步数可发现死循环；成本按维度聚合可发现异常租户；质量分数连接观测与评测。

边界与坑：成本与质量指标容易因高基数标签而爆内存，需按低基数维度聚合。

生产建议：把 Agent 步数与成本纳入同一看板，异常时联动告警。

# 4. 观测数据模型

结论先行：统一的 Span 数据模型是可观测性的地基，字段设计与属性命名决定了后续查询与聚合能力。

## 4.1 Span 数据结构

结论先行：Span 用不可变记录（record）承载一次操作的完整信息。

机制拆解：`traceId` 标识整条链，`spanId` 标识当前操作，`parentSpanId` 建立父子关系，`name` 用于分类，`attributes` 承载业务属性，`status` 表示结果。

```java
public record LlmSpan(
        String traceId,
        String spanId,
        String parentSpanId,
        String name,                    // chat / tool / retrieval
        Instant startTime,
        Duration duration,
        Map<String, Object> attributes,
        SpanStatus status
) {}
```

## 4.2 关键属性

结论先行：属性是查询与聚合的核心，应按语义分组，避免随意命名。

### 4.2.1 模型属性

机制拆解：模型相关属性用于成本归因与性能分析。

```java
span.setAttribute("llm.model", model);
span.setAttribute("llm.usage.input_tokens", inputTokens);
span.setAttribute("llm.usage.output_tokens", outputTokens);
span.setAttribute("llm.finish_reason", finishReason);
```

### 4.2.2 工具与检索属性

机制拆解：工具与检索属性用于诊断决策与召回质量。

```java
span.setAttribute("tool.name", toolName);
span.setAttribute("tool.status", status);
span.setAttribute("retrieval.hits", hits.size());
```

### 4.2.3 组织维度属性

机制拆解：租户与用户维度用于计费与隔离，但注意它们是高基数，只适合放入 Trace 而非 Metrics 标签。

| 属性 | 说明 |
|------|------|
| `llm.model` | 模型名 |
| `llm.usage.input_tokens` | 输入 Token |
| `llm.usage.output_tokens` | 输出 Token |
| `llm.finish_reason` | 结束原因 |
| `tool.name` | 工具名 |
| `tool.status` | 工具状态 |
| `retrieval.hits` | 检索命中数 |
| `agent.step` | Agent 步数 |
| `agent.version` | Agent 版本 |
| `tenant.id` / `user.id` | 租户与用户 |

## 4.3 属性命名与基数控制

结论先行：属性命名应遵循"域.字段"约定，且区分"可作标签"与"仅可存储"。

机制拆解：低基数属性（模型名、状态）可作指标标签；高基数属性（traceId、userId）只能作为 Span 属性或日志字段。

边界与坑：把 `user.id` 设为指标标签会导致时间序列爆炸，内存与查询成本骤增。

生产建议：在埋点 SDK 层做属性白名单校验，拒绝高基数标签。

# 5. 全链路追踪

结论先行：全链路追踪把一次用户请求涉及的所有服务、模型、工具串成一棵树，是端到端定位问题的唯一手段。

## 5.1 一次请求的完整链路

结论先行：从入口到出口的每个环节都应产生 Span。

机制拆解：认证、限流、记忆、检索、模型、工具、数据库、记忆写入依次串接。

```
Trace: 用户提问
├── Span: 认证与限流
├── Span: 记忆读取
├── Span: 检索
│   ├── Span: 查询向量化
│   └── Span: 向量检索
├── Span: 模型调用（第 1 轮）
├── Span: 工具调用 getOrder
│   └── Span: 数据库查询
├── Span: 模型调用（第 2 轮）
└── Span: 记忆写入
```

## 5.2 traceId 贯穿

结论先行：`traceId` 必须在入口生成并全程透传，否则无法把跨服务事件关联到同一次请求。

### 5.2.1 入口生成

机制拆解：网关或第一个服务生成 `traceId`，写入日志 MDC（Mapped Diagnostic Context，映射诊断上下文）与响应头，并在响应中回传以便前端关联。

### 5.2.2 跨服务传播

机制拆解：HTTP 使用 W3C `traceparent` 头，MQ（Message Queue，消息队列）使用消息属性，异步线程需手动传递上下文。

| 场景 | 传播方式 |
|------|----------|
| HTTP | W3C traceparent header |
| MQ | 消息 header |
| 异步线程 | 手动传递上下文 |
| 响应式 | Reactor Context |

边界与坑：线程池复用线程会导致上下文串号，必须显式传递并清理。

生产建议：在框架层统一注入透传逻辑，避免业务代码遗漏。

# 6. 指标设计原则

结论先行：指标设计的第一原则是低基数，第二是关注长尾分位数，第三是分维度可聚合，第四是可告警。

## 6.1 低基数标签

结论先行：标签组合数必须可控，否则时间序列爆炸。

机制拆解：标签基数 = 各标签取值数之积。`model`（10）× `status`（3）= 30 条序列，安全；加入 `userId`（百万）则不可控。

```java
// 正确：低基数标签
registry.counter("ai.requests", "model", model, "status", status).increment();

// 错误：高基数标签（会爆内存）
registry.counter("ai.requests", "userId", userId).increment();
```

## 6.2 分位数与分维度

结论先行：平均值掩盖长尾，延迟必须看 P95/P99；并按模型、租户、接口分维度。

机制拆解：直方图桶（bucket）记录分布，查询时用 `histogram_quantile` 计算分位数。

```yaml
metrics:
  latency:
    type: histogram
    buckets: [50, 100, 250, 500, 1000, 2000, 5000, 10000]
    unit: ms
```

| 原则 | 说明 |
|------|------|
| 标签低基数 | 不用 userId、traceId 作标签 |
| 关注 P99 | 平均值掩盖长尾 |
| 分维度 | 按模型、租户、接口 |
| 可告警 | 每个指标有阈值 |

## 6.3 可告警指标

结论先行：每个关键指标都应有明确阈值与告警动作。

机制拆解：告警基于滑动窗口的比率或分位数，避免瞬时抖动误报。

边界与坑：静态阈值在流量波动时易误报，建议用同比/环比或基线偏离。

生产建议：错误率、P99 延迟、Token 成本、循环步数四类指标优先告警。

# 7. 采样的权衡

结论先行：全量采样成本高，按比例采样有遗漏，生产实践是"正常请求按比例、错误请求全采样"。

## 7.1 采样策略

结论先行：采样需在成本与可诊断性之间权衡。

机制拆解：头部采样在入口决定，一致性好；尾部采样在完成后决定，可按结果（如错误、慢请求）采样。

```
全量采样：完整但成本高（存储、上报）
按比例采样：节省但有遗漏
错误全采样：错误必留，正常抽样
```

## 7.2 采样实现

结论先行：用 `parentBased` 保证同一 Trace 的采样决策一致，并强制采样错误请求。

```java
// 生产：正常请求 10% 采样，错误 100%
if (span.isError() || random.nextInt(100) < 10) {
    exporter.export(span);
}
```

边界与坑：头部采样时错误尚不可知，若需错误全采，应结合尾部采样或两段式上报。

生产建议：保留慢请求与错误请求的完整 Trace，正常请求按比例采样以控成本。

# 8. 观测与评测的关系

结论先行：观测关注运行时实时行为，评测关注整体质量，两者互补，数据必须互通。

## 8.1 互补关系

结论先行：观测发现异常，评测量化质量。

机制拆解：观测提供实时信号，评测提供离线基准；单靠观测无法判断"答得好不好"，单靠评测无法定位"为什么变差"。

```
观测：运行时发生了什么（实时）
评测：整体质量如何（离线/抽样）
```

## 8.2 数据互通闭环

结论先行：观测与评测应形成闭环，互相驱动。

机制拆解：观测数据触发抽样评测；评测失败回溯观测 Trace 定位原因；定位结果反哺评测用例。

- 观测数据 → 发现异常 → 抽样评测；
- 评测失败 → 查观测 Trace → 定位原因。

边界与坑：若两者使用不同 ID 体系，无法关联，闭环断裂。

生产建议：让评测样本携带 `traceId`，实现双向跳转。

# 9. 观测平台选型

结论先行：选型取决于是否 LLM 专用、是否自建、是否与现有监控栈集成。

## 9.1 平台对比

结论先行：LLM 专用平台在 Prompt 管理与评测上更强，通用平台在生态与成本上更优。

| 平台 | 类型 | 特点 |
|------|------|------|
| Langfuse | 开源 LLM 平台 | Prompt 管理 + Trace + 评测 |
| LangSmith | SaaS | LangChain 生态 |
| Arize Phoenix | 开源 | Trace + 评测 |
| Grafana + Tempo | 通用栈 | 与 Prometheus 集成 |
| Jaeger | 开源 | 分布式追踪 |
| Datadog / New Relic | SaaS | 全栈观测 |

## 9.2 选型维度

结论先行：从数据类型、集成成本、合规与预算四个维度评估。

机制拆解：LLM 平台擅长语义化 Span 与评测，通用平台擅长指标与告警；若已有 Prometheus 栈，可优先复用。

边界与坑：SaaS 平台可能涉及数据出境，敏感业务需评估合规。

生产建议：先用开源方案验证，再按规模决定是否迁移 SaaS。

# 10. 实施路线

结论先行：可观测性应分阶段建设，从日志到指标到 Trace 再到平台与自动诊断，逐步深入。

## 10.1 阶段划分

结论先行：五阶段推进，每阶段独立可交付。

```
阶段1：日志（结构化 + 脱敏）
阶段2：指标（Token、延迟、错误、成本）
阶段3：Trace（全链路）
阶段4：平台集成（Langfuse 等）
阶段5：告警与自动诊断
```

## 10.2 交付物与验收

结论先行：每阶段都要有明确交付物与验收标准。

| 阶段 | 交付物 | 验收标准 |
|------|--------|----------|
| 日志 | 结构化日志规范 | 可按 traceId 检索 |
| 指标 | 核心看板 | 覆盖延迟/成本/错误 |
| Trace | 全链路埋点 | 单请求可回放 |
| 平台 | 统一接入 | 观测评测互通 |
| 告警 | 阈值与动作 | 故障可自动通知 |

边界与坑：跳过日志直接上 Trace，往往因缺少原始细节而无法定位。

生产建议：每阶段设可量化验收指标，避免"上了但没用"。

# 11. 生产注意事项

结论先行：可观测性建设最常见的失败不是技术不足，而是数据缺失、泄露与高基数。

## 11.1 常见风险

结论先行：风险集中在 Trace 缺失、敏感泄露、标签爆炸、采样失当、成本失控与关联断裂。

| 风险 | 建议 |
|------|------|
| 无 Trace | 无法定位问题 |
| 记录完整 Prompt | 脱敏 + 截断 |
| 高基数标签 | 用低基数维度 |
| 全量采样 | 按比例 + 错误全采 |
| 无成本监控 | Token/成本一等指标 |
| 无 traceId 贯穿 | 网关生成并透传 |
| 观测与评测脱节 | 数据互通 |

## 11.2 检查清单

结论先行：上线前逐项核对，确保可观测性覆盖到位。

机制拆解：从入口到出口、从数据到告警逐层检查。

| 检查项 | 通过标准 |
|--------|----------|
| traceId 贯穿 | 全链路一致 |
| 敏感数据 | 已脱敏/截断 |
| 指标标签 | 均低基数 |
| 采样策略 | 比例 + 错误全采 |
| 成本监控 | 分维度可查 |
| 告警配置 | 阈值与动作齐备 |

边界与坑：检查清单若无人定期复核，会随时间腐化。

生产建议：把检查项固化为 CI 校验或上线门禁。

# 12. 小结

- LLM 应用因非确定性更需要可观测。
- 三支柱：Trace、Metrics、Logs，分别回答"发生了什么、整体健康吗、细节是什么"。
- 特有观测点：模型、工具、检索、记忆、Agent 步数、成本。
- 指标用低基数标签，关注 P99，采样用"比例 + 错误全采"。
- 观测与评测互补，数据互通形成闭环。
- 实施分五阶段：日志 → 指标 → Trace → 平台 → 告警。
