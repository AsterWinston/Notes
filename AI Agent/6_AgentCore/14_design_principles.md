# 1. 十条核心原则

Agent 工程化的难点不在"能不能做出来"，而在"能不能稳定、可控、可负担地跑在生产上"。本章给出十条经过验证的原则，作为架构与实现的判断依据。

## 1.1 原则总览

| # | 原则 | 一句话 |
|:-:|------|--------|
| 1 | 从简到繁 | 能工作流就不 Agent，能单体就不多 Agent |
| 2 | 目标明确 | 有可验证的成功标准 |
| 3 | 边界清晰 | 工具与权限最小化 |
| 4 | 状态外置 | 可恢复、可扩展 |
| 5 | 全程可观测 | 每步可追溯、可回放 |
| 6 | 失败可控 | 有兜底、有降级、有人工 |
| 7 | 成本意识 | 预算化、可监控 |
| 8 | 评测驱动 | 用数据而非感觉优化 |
| 9 | 安全优先 | 注入防御、权限、审计 |
| 10 | 渐进交付 | 小步上线，逐步放开自主性 |

## 1.2 原则之间的关系

```
从简到繁（选型） ─┬─▶ 目标明确（定义成功）
                 ├─▶ 边界清晰（限定能力）
                 ├─▶ 状态外置（可恢复）
                 └─▶ 全程可观测（可诊断）
                          │
                          ▼
        失败可控 + 成本意识 + 安全优先（运行时护栏）
                          │
                          ▼
                评测驱动 + 渐进交付（持续演进）
```

- **选型类**（1、2、3）：决定系统形态与边界；
- **运行类**（4~7、9）：决定系统能否稳定运行；
- **演进类**（8、10）：决定系统能否持续变好。

## 1.3 如何使用本文

- 设计阶段：用第 1~3 条确定形态与边界；
- 实现阶段：用第 4~9 条逐项检查；
- 上线阶段：用第 12 节检查清单逐项确认；
- 复盘阶段：对照第 13 节反模式，避免重复踩坑。

| 阶段 | 关注原则 | 主要产物 |
|------|----------|----------|
| 设计 | 1 从简到繁、2 目标明确、3 边界清晰 | 架构图、目标清单、工具清单 |
| 实现 | 4 状态外置、5 可观测、6 失败可控 | 状态存储、Trace、兜底链 |
| 上线 | 7 成本、9 安全、12 清单 | 预算、审计、门禁 |
| 演进 | 8 评测驱动、10 渐进交付 | 评测集、放行标准 |

> 原则不是口号，而是要落到**具体产物**上的约束。

# 2. 原则一：从简到繁

## 2.1 演进阶梯

结论先行：**能用工作流解决的，就不要用 Agent**。复杂度必须换来明确的能力提升，否则就是负债。

```
工作流 → 工作流+LLM节点 → 单体 Agent → 规划器-执行器 → 多 Agent
```

每往右一步，能力增强但复杂度、成本、不确定性都上升。**只在必要时演进。**

### 2.1.1 阶梯的六个档位

| 档位 | 形态 | 决策者 | 典型场景 |
|:----:|------|--------|----------|
| 0 | 纯工作流 | 代码 | 规则明确、分支有限 |
| 1 | 工作流 + LLM 节点 | 代码 | 局部需要理解自然语言 |
| 2 | 单体 Agent | 模型 | 工具少、步骤短 |
| 3 | 规划器-执行器 | 模型 + 代码 | 中长任务、需审计 |
| 4 | 图编排 | 代码骨架 + 模型节点 | 需确定性控制流 |
| 5 | 多 Agent | 模型 | 领域异构、需分工 |

### 2.1.2 何时停在哪一级

- 需求能用固定分支表达 → 停在 0/1；
- 需要"走一步看一步"但工具不多 → 停在 2；
- 需要计划可见、可并行 → 升到 3；
- 需要确定性审计与回放 → 升到 4；
- 只有当领域之间**提示与工具无法共存**时，才升到 5。

## 2.2 判定标准

| 现象 | 说明该往右走一步 |
|------|------------------|
| 分支无法枚举 | 工作流写不完 → 引入 Agent |
| 工具数量增长 | 单体选择困难 → 规划器-执行器 |
| 需要确定性审计 | 路径不可预测 → 图编排 |
| 领域明显异构 | 单一 Agent 提示臃肿 → 多 Agent |

## 2.3 边界与反例

- **反例**：为了"技术先进"直接上多 Agent，结果 80% 的线上问题是编排 bug，而非业务问题；
- **边界**：演进不是单向的——当发现某段流程已经稳定，应**主动退回工作流**以降低成本。

# 3. 原则二：目标明确

## 3.1 可验证的成功标准

结论先行：目标必须能被**程序或人明确判断"完成/未完成"**。模糊目标会让 Agent 永远"看起来在做"，却无法判定何时停止。

```java
// 差：模糊
"帮我处理一下客户投诉"

// 好：可验证
"读取工单 T123，判断是否符合退款条件，若符合则发起退款并通知客户"
```

成功标准要能被程序或人明确判断。

## 3.2 代码示例

```java
record Goal(String description, List<String> successCriteria, int maxSteps) {}

Goal goal = new Goal(
        "处理退款工单 T123",
        List.of("已读取工单", "已给出退款判定", "若通过则退款单已创建"),
        8);
```

把成功标准写成**可勾选清单**，既可驱动提示，也可驱动终止判断。

## 3.3 边界与反例

- **反例**：目标写成"尽可能提升满意度"——无终止条件，Agent 会无限优化；
- **边界**：目标过于细碎（把每步都写死）会退化成工作流，失去 Agent 的价值。

# 4. 原则三：边界清晰

## 4.1 工具最小化

结论先行：**工具只暴露必要的，权限遵循最小可用，数据访问有边界**。

```java
// 工具最小化
.tools(permissionService.allowedTools(user))   // 只挂有权限的
```

- 工具只暴露必要的；
- 权限遵循最小可用；
- 数据访问有边界。

## 4.2 权限最小化

```java
public List<Object> toolsFor(User user, String scene) {
    return allTools.stream()
            .filter(t -> permissionService.canUse(user, t, scene))
            .filter(t -> scene.equals(sceneOf(t)))   // 场景隔离
            .toList();
}
```

高风险工具默认**不挂载**，需要时再通过审批临时授予。

## 4.3 边界与反例

- **反例**：给所有用户挂载全部工具，靠提示词约束"不要越权"——提示可被注入绕过；
- **边界**：边界过窄会导致 Agent 频繁"无工具可用"，需在安全与可用间平衡。

# 5. 原则四：状态外置

## 5.1 无状态服务 + 外部状态

结论先行：状态放在内存 = 无法恢复、无法扩展、无法审计。正确做法是服务无状态、状态外置。

```java
// 无状态服务 + 外部状态存储
AgentState state = stateStore.load(taskId);
state = step(state);
stateStore.save(taskId, state);
```

> 状态在内存 = 无法恢复、无法扩展、无法审计。

## 5.2 实现

```java
public interface StateStore {
    AgentState load(String taskId);
    void save(String taskId, AgentState state);
    boolean compareAndSet(String taskId, long expectedVersion, AgentState next);
}
```

- 每次推进都持久化，支持**断点续跑**；
- 写入用版本号做乐观锁，避免并发覆盖；
- 状态结构版本化，兼容老数据。

### 5.2.1 状态存储接口

接口应包含**读取、保存、条件写入**三个能力。缺少条件写入，就无法在多实例下安全推进。

### 5.2.2 乐观锁与版本

```java
AgentState current = store.load(taskId);
long version = current.version();
AgentState next = step(current);
if (!store.compareAndSet(taskId, version, next)) {
    throw new ConcurrentModificationException("状态已被其他实例更新");
}
```

冲突时重读状态并重放，而不是覆盖。

## 5.3 边界与反例

- **反例**：把中间状态存在 `ThreadLocal` 或 `HashMap`，实例重启后任务全部丢失；
- **边界**：并非所有数据都要外置——纯计算中间量可以留在栈上，**可恢复性所需的状态**才必须外置。

# 6. 原则五：全程可观测

## 6.1 四个必答问题

结论先行：没有 Trace 的 Agent，等于黑盒。每一步都要能回答：

```
每一步都要能回答：
- 模型看到了什么？（输入上下文）
- 模型决定了什么？（工具/答案）
- 工具返回了什么？（结果）
- 花了多少？（Token/成本/时间）
```

> 没有 Trace 的 Agent，等于黑盒。

## 6.2 Trace 结构

```
Trace: task-123
├── Span: model.call #1
│    ├── input: 消息摘要（脱敏）
│    ├── output: tool_call getOrder
│    └── usage: {prompt: 820, completion: 45}
├── Span: tool.getOrder
│    ├── args: {"orderId":"A123"}
│    ├── status: SUCCESS
│    └── latency: 120ms
└── Span: model.call #2
     └── output: final answer
```

## 6.3 生产建议

- Trace 必须**可回放**：给定 taskId 能重建完整决策路径；
- 记录 Token、成本、耗时，作为告警依据；
- 日志脱敏，禁止记录 PII 与密钥。

# 7. 原则六：失败可控

## 7.1 降级链

结论先行：失败必须有明确的处理路径，且**绝不允许"编造答案"作为兜底**。

```
失败 → 重试（幂等） → 降级 → 部分结果 → 转人工 → 明确失败
```

> **绝不允许"编造答案"作为失败兜底。**

## 7.2 实现

```java
public Answer handle(Throwable cause) {
    if (retryPolicy.shouldRetry(cause)) {
        return retry();                                  // 幂等重试
    }
    if (fallbackWorkflow.available()) {
        return fallbackWorkflow.run();                   // 降级到工作流
    }
    if (partialResult.exists()) {
        return partialResult.asAnswer();                 // 部分结果
    }
    return Answer.handoff("请人工处理：" + cause.getMessage());   // 转人工
}
```

## 7.3 边界与反例

- **反例**：把部分结果包装成完整答案，本质仍是编造；
- **边界**：重试只对**幂等操作**安全，写操作重试前必须确认幂等键生效。

# 8. 原则七：成本意识

## 8.1 预算模型

结论先行：成本必须**预算化、可监控**，否则会随流量与循环次数悄然失控。

```java
public class CostBudget {
    private final long maxTokensPerTask;
    private final BigDecimal maxCostPerDay;

    public boolean allow(int estimatedTokens) { ... }
}
```

- 按任务设 Token 预算；
- 按租户设日成本上限；
- 简单任务用小模型。

## 8.2 实现

```java
public ChatModel choose(Intent intent, int estTokens) {
    if (intent.isSimple() || estTokens < 500) {
        return smallModel;      // 便宜、快
    }
    return largeModel;          // 复杂任务才用大模型
}
```

模型分层路由能在**几乎不损失质量**的前提下显著降本。

## 8.3 生产建议

- 成本按租户/模型/任务类型多维统计；
- 设日/小时预算告警与硬上限；
- 缓存命中率纳入监控指标。

# 9. 原则八：评测驱动

## 9.1 流程

结论先行：没有评测的优化都是盲调，可能"改好了 A 却改坏了 B"。

```
优化前：先建评测集
优化后：跑评测看是否真的提升
```

> 没有评测的优化都是盲调，可能"改好了 A 却改坏了 B"。

## 9.2 实现

```java
record EvalCase(String input, String expected, List<String> mustNotContain) {}

public EvalReport evaluate(Agent agent, List<EvalCase> cases) {
    int pass = 0;
    for (EvalCase c : cases) {
        String out = agent.run(c.input());
        boolean ok = out.contains(c.expected())
                && c.mustNotContain().stream().noneMatch(out::contains);
        if (ok) pass++;
    }
    return new EvalReport(pass, cases.size());
}
```

## 9.3 边界与反例

- **反例**：只用 3~5 条"手测样例"就宣称提升，样本太小、过拟合；
- **边界**：开放式任务没有唯一答案，需用 LLM-as-Judge 或轨迹评分，且 Judge 本身也要被校准。

# 10. 原则九：安全优先

## 10.1 五层防线

结论先行：安全不是单点，而是**输入、工具、数据、输出、运维**五层叠加。

| 层 | 措施 |
|----|------|
| 输入 | 注入检测、长度限制 |
| 工具 | 鉴权、最小权限 |
| 数据 | 租户隔离、脱敏 |
| 输出 | 内容审核、引用校验 |
| 运维 | 审计、密钥轮换 |

### 10.1.1 输入与工具层

- 输入层识别提示注入、超长输入与编码绕过；
- 工具层做鉴权、最小权限与高风险工具审批；
- 两者共同阻断"外部内容诱导越权"这一主要攻击路径。

### 10.1.2 数据、输出与运维层

- 数据层做租户隔离与字段级脱敏；
- 输出层做内容审核与引用校验，防止泄露与幻觉；
- 运维层保留审计日志并定期轮换密钥。

## 10.2 实现

```java
public String safeRun(String userInput, User user) {
    guard.inspectInput(userInput);                 // 输入层：注入检测
    if (!guard.allowed(userInput)) {
        return "请求被安全策略拦截";
    }
    String out = agent.run(userInput, toolsFor(user, scene));   // 工具层：裁剪
    guard.inspectOutput(out);                      // 输出层：审核
    auditLog.record(user, "agent.run", digest(userInput));
    return out;
}
```

## 10.3 生产建议

- 把外部内容（网页、文档、工具结果）视为**不可信输入**；
- 高风险工具强制人工审批；
- 审计日志独立存储，不可被应用修改。

# 11. 原则十：渐进交付

## 11.1 阶段划分

结论先行：先做只读，再做写入；先审批，再自主；每次放开前先补足可观测与评测。

```
P0 只读能力（L3）→ 观察指标 → P1 写能力（L2 审批）→ 积累信任 → 逐步放开
```

- 先做只读，再做写入；
- 先 L2 审批，再 L3/L4 自主；
- 每次放开前，先补足可观测与评测。

## 11.2 检查点

| 阶段 | 能力 | 放行条件 |
|------|------|----------|
| P0 | 只读查询 | 指标正常、无越权 |
| P1 | 写操作（需审批） | 审批通过率与驳回原因可解释 |
| P2 | 写操作（自动） | 评测通过率达标、兜底就绪 |
| P3 | 高自主 | 长周期无重大事故 |

## 11.3 边界与反例

- **反例**：为赶进度跳过 P0 直接开写权限，一次事故即可摧毁信任；
- **边界**：渐进不等于永远不放开，需设定明确的**放行标准**，否则会止步不前。

# 12. 上线检查清单

## 12.1 清单

- [ ] 有明确的可验证目标
- [ ] 有最大步数 / Token / 时间上限
- [ ] 工具已鉴权，按权限裁剪
- [ ] 写操作幂等
- [ ] 状态已持久化，支持恢复
- [ ] 全链路 Trace 可回放
- [ ] 有失败兜底与转人工
- [ ] 有成本监控与预算
- [ ] 有评测集并接入 CI
- [ ] 注入防御与输出审核已启用
- [ ] 日志已脱敏
- [ ] 有降级与回滚方案

## 12.2 使用方式

把清单落成**上线门禁**：未勾选项必须给出豁免理由与补救期限，避免"先上线再说"。

| 门禁级别 | 未通过项 | 处理方式 |
|----------|----------|----------|
| 阻断 | 鉴权、幂等、上限、脱敏 | 禁止上线 |
| 警告 | Trace、评测、缓存 | 限期补齐 |
| 建议 | 成本多维统计 | 排期优化 |

# 13. 反模式

## 13.1 反模式表

| 反模式 | 问题 | 正解 |
|--------|------|------|
| 一把梭多 Agent | 复杂度爆炸 | 从单体起步 |
| 工具全量挂载 | 误选、越权 | 按场景/权限裁剪 |
| 状态存内存 | 无法恢复 | 外置持久化 |
| 无上限循环 | 烧钱、卡死 | 多重上限 |
| 失败编造答案 | 信任崩塌 | 明确失败/转人工 |
| 无评测上线 | 质量不稳 | 建评测集 |
| 高自主一步到位 | 事故风险 | 渐进放开 |

## 13.2 典型案例

- **状态存内存**：某服务把会话状态放 `HashMap`，滚动发布时用户会话全部丢失——改为 Redis + 版本号后解决；
- **无上限循环**：缺少步数上限，模型在两个工具间反复横跳，单次任务消耗数万 Token——加 `LoopGuard` 后收敛；
- **工具全量挂载**：所有场景共用一个全量工具集，模型频繁误选相邻工具——按场景裁剪后准确率显著回升。
