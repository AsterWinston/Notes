# 1. 核心区别：谁决定下一步

## 1.1 两种控制流

```
工作流（Workflow）：开发者预定义流程，代码决定下一步
Agent：          模型根据当前状态，自主决定下一步
```

```
工作流：
  步骤1 → 步骤2 → 判断 → 步骤3a / 步骤3b → 结束
  （路径在编码时就固定）

Agent：
  目标 → [模型思考] → 选择动作 → 观察 → [模型思考] → ... → 达成
  （路径在运行时由模型生成）
```

## 1.2 一张图看懂差异

```
       工作流                           Agent
  ┌───────────────┐              ┌───────────────┐
  │  代码编排      │              │  模型编排      │
  │  分支写死      │              │  分支动态生成  │
  └───────┬───────┘              └───────┬───────┘
          ▼                              ▼
   可预测、可测试                   灵活、不确定
   成本固定                         成本波动
```

一句话：**工作流把智能放在开发者脑子里，Agent 把智能放在模型里**。

## 1.3 控制权转移的三种层次

控制权并非"全在代码"或"全在模型"，而是分三层逐步转移：

| 层次 | 谁决定 | 典型形态 | 说明 |
|------|--------|----------|------|
| 路径层 | 开发者 | 纯工作流 | 走哪条分支在编码时确定 |
| 节点层 | 开发者 | 工作流 + LLM 节点 | 流程固定，节点内容由模型生成 |
| 决策层 | 模型 | Agent | 连"下一步做什么"都由模型决定 |

> 大多数所谓"Agent 系统"其实只转移到了**节点层**，这是稳定与灵活的常见折中。

## 1.4 同一任务的两种实现对比

以"处理退款申请"为例：

```
工作流实现：
  校验订单 → 判断是否符合政策 → 符合则退款 → 通知用户
  （分支与顺序全部写死在代码里）

Agent 实现：
  给出目标"处理该退款申请" + 可用工具（查订单、查政策、退款、通知）
  → 模型自行决定调用顺序、处理异常、决定是否转人工
```

关键差异：工作流实现中"符合政策"的判断逻辑是**代码**；Agent 实现中是**模型推理**。前者可单测，后者需评测。

# 2. 对比表

## 2.1 全维度对比

| 维度 | 工作流 | Agent |
|------|--------|-------|
| 决策者 | 开发者 | 模型 |
| 路径 | 预先确定 | 运行时生成 |
| 可预测性 | 高 | 低 |
| 灵活性 | 低 | 高 |
| 调试难度 | 低 | 高 |
| 成本 | 可精确估算 | 波动大 |
| 失败模式 | 分支遗漏 | 循环、漂移 |
| 可审计性 | 强（路径可追溯） | 弱（需 Trace 补足） |
| 适用 | 稳定、规则明确的流程 | 开放、需要判断的任务 |

## 2.2 成本与风险对比

| 项 | 工作流 | Agent |
|----|--------|-------|
| 单次成本 | 固定（可预算） | 不定（随步数变化） |
| 延迟 | 稳定 | 波动 |
| 出错后果 | 局部、可定位 | 可能累积、难复现 |
| 治理成本 | 低 | 高（需 Trace/评测/护栏） |

> 结论：**能用工作流的地方，工作流几乎总是更优**——更便宜、更稳、更好审计。

## 2.3 运维与团队维度对比

| 维度 | 工作流 | Agent |
|------|--------|-------|
| 监控指标 | 成功率、耗时 | 步数分布、Token 消耗、工具命中率 |
| 回归测试 | 单元测试 + 集成测试 | 轨迹评测 + 数据集回归 |
| 发布风险 | 低（改动可控） | 高（提示/模型变更影响面大） |
| 团队要求 | 熟悉业务逻辑 | 需懂提示、评测、可观测性 |
| 故障定位 | 看日志与堆栈 | 需回放完整轨迹 |

> Agent 的运维成本往往被低估：**上线只是开始，评测与观测才是长期投入**。

## 2.4 选型打分卡

把 5.2 的判断维度量化为打分卡，便于团队统一决策（每项 0~2 分，越倾向 Agent 分越高）：

| 维度 | 0 分（工作流） | 1 分 | 2 分（Agent） |
|------|---------------|------|--------------|
| 步骤稳定性 | 固定 | 偶变 | 频繁变化 |
| 失败代价 | 高 | 中 | 低 |
| 输入开放性 | 结构化 | 半结构化 | 开放式 |
| 推理需求 | 无 | 少量 | 多步推理 |
| 合规要求 | 强审计 | 一般 | 无 |

> 总分 ≤3 → 工作流；4~6 → 混合；≥7 → Agent。打分卡的价值在于**把主观争论变成可对齐的评分**。

# 3. 工作流示例

## 3.1 代码实现

```java
public String handle(Order order) {
    if (!riskService.isSafe(order)) {
        return "转人工审核";
    }
    PaymentResult payment = paymentService.pay(order);
    if (payment.isFailed()) {
        return "支付失败，请重试";
    }
    inventoryService.deduct(order);
    return "下单成功";
}
```

### 3.1.1 为什么路径固定更可靠

代码决定下一步，意味着**任何输入都走已知分支**：可写单元测试、可精确估算成本、出错可定位。

## 3.2 工作流的优点

- **路径确定**：任何输入都走已知分支；
- **可测试**：每个分支可写单元测试；
- **成本固定**：不依赖模型，无 Token 波动；
- **可审计**：每一步都有明确记录。

## 3.3 工作流的局限

- 分支需要**预先枚举**，需求变化就要改代码；
- 无法处理**开放式输入**（如"帮我处理这个客户问题"）；
- 分支爆炸后难以维护。

## 3.4 工作流的状态与幂等

工作流的可靠性依赖两个工程性质：

- **状态可持久化**：每步进度落库，进程崩溃后可恢复；
- **操作幂等**：同一请求重复执行不产生额外副作用。

```java
public String handleWithIdempotency(String requestId, Order order) {
    if (idempotencyStore.exists(requestId)) {
        return idempotencyStore.getResult(requestId);   // 幂等：直接返回
    }
    String result = doHandle(order);
    idempotencyStore.save(requestId, result);
    return result;
}
```

> Agent 的"副作用"同样需要幂等保护，但路径不确定使幂等键更难定义——这是 Agent 更难治理的根因之一。

## 3.5 工作流的测试与回放

工作流的最大优势之一是**可测试**。建议至少覆盖三类测试：

```java
@Test
void 风控不通过应转人工() {
    Order order = riskyOrder();
    assertThat(workflow.handle(order)).isEqualTo("转人工审核");
}

@Test
void 支付失败应提示重试() {
    when(paymentService.pay(any())).thenReturn(PaymentResult.failed());
    assertThat(workflow.handle(safeOrder())).isEqualTo("支付失败，请重试");
}

@Test
void 正常下单应扣减库存() {
    workflow.handle(safeOrder());
    verify(inventoryService).deduct(any());
}
```

- **分支覆盖**：每个分支都有用例；
- **副作用验证**：用 Mock 校验是否调用了正确的下游；
- **回放**：线上请求可回放，快速复现问题。

> 这些能力是 Agent 难以直接获得的——Agent 的等价物是**轨迹评测**（见 `12_Evaluation`）。

# 4. Agent 示例

## 4.1 代码实现

```java
Assistant agent = AiServices.builder(Assistant.class)
        .chatModel(model)
        .tools(new RiskTools(), new PaymentTools(), new InventoryTools())
        .build();

String result = agent.chat("帮用户完成订单 A123，注意风控");
// 模型自行决定：查风控 → 支付 → 扣库存 → 汇总
```

### 4.1.1 模型如何选择路径

模型读取"目标 + 可用工具 + 当前观察"，逐步决定下一步动作。**路径不存在于代码里，而存在于模型的推理中**，因此能应对未预先枚举的情况。

## 4.2 Agent 的灵活性

- 能处理**未预先枚举**的路径；
- 能根据中间结果**动态调整**；
- 新增能力只需加工具，不必改控制流。

## 4.3 Agent 的代价

- 路径不确定，**可能走弯路**；
- 成本与延迟**波动**；
- 需要额外治理：终止条件、Trace、评测、护栏。

## 4.4 Agent 的可观测性与护栏

Agent 上线必须补齐三样东西：

```
Trace（轨迹）：记录每轮 Thought / Action / Observation
护栏（Guardrail）：限制步数、预算、危险工具
评测（Eval）：用标注轨迹回归，防止提示变更导致退化
```

```java
AgentExecutor executor = AgentExecutor.builder()
        .agent(agent)
        .maxSteps(10)                       // 护栏：最大步数
        .maxTokens(20_000)                  // 护栏：Token 预算
        .listener(new TraceListener())      // 可观测性
        .build();
```

> 缺少这三样，Agent 一旦出问题将**无法复现、无法定位、无法回滚**。

## 4.5 Agent 的成本与延迟控制

Agent 的步数不确定，成本与延迟天然波动。常用控制手段：

| 手段 | 作用 |
|------|------|
| 最大步数 | 硬上限，防死循环 |
| Token 预算 | 超预算即中止 |
| 工具结果裁剪 | 只回填必要字段 |
| 缓存 | 相同子问题复用结果 |
| 模型分级 | 简单步骤用小模型 |

```java
AgentExecutor executor = AgentExecutor.builder()
        .agent(agent)
        .maxSteps(10)
        .maxTokens(20_000)
        .modelRouter(router)          // 按步骤难度选模型
        .build();
```

> 成本控制应**在运行时生效**，而非仅靠事后统计——超支必须能即时中止。

# 5. 关键判断：该用哪个

## 5.1 决策树

```
任务是否有明确、稳定的步骤？
    ├── 是 → 工作流（更可靠、更便宜）
    └── 否 → 步骤是否可枚举但组合多变？
              ├── 是 → 工作流 + 少量 LLM 判断（混合）
              └── 否 → Agent
```

## 5.2 判断维度

| 问题 | 倾向 |
|------|------|
| 失败代价高吗？ | 高 → 工作流 |
| 步骤会经常变吗？ | 会变 → Agent |
| 需要多步推理吗？ | 需要 → Agent |
| 有合规/审计要求吗？ | 有 → 工作流（路径可追溯） |
| 输入高度多样吗？ | 多样 → Agent |
| 单次成本敏感吗？ | 敏感 → 工作流 |

## 5.3 常见反例

- 用 Agent 做"固定三步审批" → 成本翻倍且不稳定；
- 用工作流硬编码所有意图分支 → 分支爆炸、维护地狱；
- 用 Agent 做核心交易 → 一致性风险不可接受。

## 5.4 完整选型案例

场景：客服系统要支持"查订单、退款、投诉、咨询政策"四类诉求。

| 诉求 | 特征 | 选型 |
|------|------|------|
| 查订单 | 输入结构化、路径固定 | 工作流 |
| 退款 | 规则明确、副作用高风险 | 工作流 + 人工审批 |
| 投诉 | 输入开放、需共情与判断 | Agent |
| 咨询政策 | 需检索知识库 | 检索型 Agent |

```java
public String route(Intent intent, String input) {
    return switch (intent) {
        case QUERY_ORDER -> workflow.handleQuery(input);   // 工作流
        case REFUND      -> workflow.handleRefund(input);  // 工作流 + 审批
        case COMPLAINT   -> agent.handle(input);           // Agent
        case POLICY_QA   -> ragAgent.handle(input);        // 检索型 Agent
    };
}
```

> 一个系统内**不同诉求用不同形态**，是成熟团队的常态。

# 6. 混合模式（最实用）

## 6.1 骨架 + 节点

实践中，**大多数生产系统是"工作流骨架 + Agent 节点"**：

```
工作流骨架（可控、可审计）
  ├── 固定步骤：鉴权、意图识别
  ├── 固定分支：简单任务走固定流程
  └── Agent 节点：复杂任务交给模型自主处理
```

## 6.2 代码示例

```java
public String handle(String userInput) {
    // 1. 固定步骤：意图识别（LLM 单次调用）
    Intent intent = classifier.classify(userInput);

    // 2. 固定分支：工作流控制
    return switch (intent) {
        case REFUND -> handleRefund(userInput);      // 固定流程
        case QUERY  -> handleQuery(userInput);       // 固定流程
        case COMPLEX -> agent.handle(userInput);     // 交给 Agent 自主处理
        default -> "暂不支持";
    };
}
```

### 6.2.1 混合模式的分层

- **外层工作流**：负责鉴权、路由、审计与降级，保证主流程可控；
- **内层 Agent**：只在复杂意图下启用，负责开放式推理。

两层的边界即"稳定性与灵活性的分界"。

## 6.3 优势

- 主流程可控、可审计；
- 只在真正需要的地方引入 Agent 的灵活性；
- 成本与风险可局部化。

## 6.4 边界划分原则

| 特征 | 交给工作流 | 交给 Agent |
|------|-----------|-----------|
| 步骤 | 固定 | 不定 |
| 副作用 | 高风险写操作 | 低风险读操作 |
| 输入 | 结构化 | 开放式 |
| 失败代价 | 高 | 低 |

## 6.5 混合模式的常见坑

| 坑 | 表现 | 规避 |
|----|------|------|
| 边界漂移 | Agent 节点逐渐承担高风险写操作 | 定期审查边界 |
| 状态割裂 | 外层与内层各存一份状态 | 统一状态存储 |
| 降级缺失 | Agent 超时后整条流程卡死 | 设超时 + 兜底分支 |
| 重复鉴权 | 内外层各做一次鉴权 | 外层统一鉴权 |
| 观测断层 | 只记外层，不记 Agent 轨迹 | 轨迹与外层 Trace 打通 |

> 混合模式的难点不在"分",而在**边界处的状态、超时与观测如何贯通**。

## 6.6 混合模式完整示例

以"客服工单"为例，外层工作流负责鉴权与路由，内层 Agent 处理复杂诉求，并对 Agent 设超时与降级：

```java
public class TicketService {

    private final WorkflowEngine workflow;
    private final AgentExecutor agent;
    private final AuditLog auditLog;

    public String handle(String userId, String input) {
        // 1. 鉴权（固定步骤）
        if (!authService.canAccess(userId)) {
            return "无权访问";
        }

        // 2. 意图识别（LLM 单次调用）
        Intent intent = classifier.classify(input);

        // 3. 路由：简单走工作流，复杂交 Agent
        String result = switch (intent) {
            case REFUND, QUERY -> workflow.run(intent, input);
            case COMPLEX -> runAgentSafely(input);
        };

        auditLog.record(userId, intent, result);   // 4. 统一审计
        return result;
    }

    private String runAgentSafely(String input) {
        try {
            return agent.handle(input);
        } catch (TimeoutException | MaxStepsExceededException e) {
            return "该问题较复杂，已转人工处理";     // 降级
        }
    }
}
```

> 注意降级分支：Agent 失败时**不能卡死整条流程**，必须有兜底。

# 7. 工作流编排工具

## 7.1 工具对比

| 方式 | 说明 |
|------|------|
| 普通 Java 代码 | 最简单，适合线性流程 |
| Spring StateMachine | 状态机，适合复杂状态流转 |
| 工作流引擎（Flowable/Camunda） | 长流程、可视化、可补偿 |
| LangGraph4j / Spring AI Alibaba Graph | LLM 场景的图编排 |
| LangChain4j Agentic | 声明式顺序/并行/循环编排 |

## 7.2 如何选

- 纯业务规则 → 普通代码/状态机；
- 跨系统长事务 → 工作流引擎（补偿、持久化）；
- LLM 多步编排 → Graph（见 `9_Frameworks/SpringAIAlibaba/4_graph.md`）。

## 7.3 编排工具选型清单

| 问题 | 若是 | 若否 |
|------|------|------|
| 需要跨天/跨系统的长事务吗？ | 工作流引擎 | 继续问 |
| 需要可视化与人工节点吗？ | 工作流引擎 | 继续问 |
| 流程主要由 LLM 决策驱动吗？ | Graph 编排 | 普通代码 |
| 只是线性几步调用吗？ | 普通代码 | 状态机 |

> 不要为"可能用到"的复杂编排提前引入重框架——**复杂度要由需求驱动**。

# 8. 演进路径

## 8.1 工作流 → Agent

```
阶段1：纯工作流（稳定但僵化）
   ↓ 需求变化频繁、分支爆炸
阶段2：工作流 + LLM 节点（灵活一点）
   ↓ 步骤无法预先枚举
阶段3：Agent（灵活但需治理）
```

## 8.2 Agent → 工作流（降级）

反过来也成立：**当 Agent 频繁出错时，把稳定的部分"降级"为工作流**，是常见的优化手段。

```
发现某条路径总是固定的
   → 固化为工作流分支
   → 减少不确定性、降成本、提稳定性
```

## 8.3 演进的工程实践

- **先测量再演进**：用 Trace 统计各路径出现频率，固定路径固化；
- **小步替换**：一次只把一个节点从工作流换成 Agent（或反向），便于对比；
- **保留回退开关**：新形态上线时保留旧实现，异常时一键回退；
- **用评测守住底线**：每次演进都要跑同一套回归集，避免"灵活了但变差了"。

## 8.4 一个演进案例

某团队处理"发票开具"请求的演进过程：

```
阶段1：纯工作流
  → 覆盖标准开票，但"抬头信息不规范"的请求频繁失败

阶段2：工作流 + LLM 节点
  → 用 LLM 规范化抬头信息，成功率高但格式仍偶发错误

阶段3：局部 Agent
  → 仅"信息纠错"这一步交给 Agent，其余仍走工作流
  → 成功率提升，成本可控，且问题可局部定位
```

> 关键经验：**不要把整个流程一次性改成 Agent**，而是找到"最不稳定的一步"局部替换。

# 9. 常见误用

| 误用 | 后果 | 正解 |
|------|------|------|
| 用 Agent 做固定流程 | 成本高、不稳定 | 改工作流 |
| 用工作流硬编码所有分支 | 分支爆炸、难维护 | 局部引入 Agent |
| Agent 无终止条件 | 死循环、成本失控 | 加最大步数 |
| 全流程无人工审批 | 高风险操作失控 | 关键节点加审批 |
| 混合边界不清 | 职责混乱 | 按"步骤/副作用/代价"划界 |

## 9.1 误用案例详解

### 9.1.1 案例一：给固定审批加 Agent

一个三步审批流程（提交 → 主管审 → 财务审）被改成 Agent，结果每次审批都需多轮模型调用，成本上升数倍，且偶发漏审。**教训**：流程确定时，模型只会增加不确定性。

### 9.1.2 案例二：让 Agent 直接操作资金

Agent 被授予"直接转账"工具，无金额上限与审批，一次参数幻觉造成损失。**教训**：高风险写操作必须加护栏（限额、审批、幂等）。

### 9.1.3 案例三：全用工作流硬编码意图

为覆盖所有用户意图，团队写了几百个分支，新增意图就要改代码并全量回归。**教训**：开放式输入应交给 Agent，工作流只兜底。

# 10. 小结

- 本质区别：**谁决定下一步**——代码还是模型。
- 工作流可控、可测、成本固定；Agent 灵活但不确定。
- 生产主流是**混合模式**：工作流骨架 + Agent 节点。
- 选型看任务稳定性、失败代价、合规要求。
- 二者可以双向演进，不是非此即彼。
