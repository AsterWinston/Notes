# 1. 从原理到生产

前 14 篇讲的是"Agent 如何思考与行动"；本篇把它放进真实系统，回答"如何让它稳定运行"。

## 1.1 本篇要解决的问题

原理层回答"能不能做"；运行层回答"能不能持续做对、做稳、做省"。这也是原型（Prototype）与生产（Production）的分水岭：

- 原型：模型能规划、能调用工具、能给出答案即可。
- 生产：进程重启后任务是否还在、依赖故障会不会雪崩、成本会不会失控、问题能否被定位。

## 1.2 三层视角：原理 / 运行 / 企业

```
原理层（本模块 1~14）
   ↓
运行层（本模块 15 + 14_ProductionEngineering）
   ↓
企业层（15_Security + 16_Applications）
```

三层是递进关系：原理决定"能做什么"，运行决定"能不能稳定交付"，企业层决定"能不能在组织内合规地规模化"。

## 1.3 阅读方式与前置知识

- 前置：本模块 `4_agent_loop.md`（Agent 循环）、`10_state_and_control_flow.md`（状态与流程）。
- 关联：`13_Observability`（可观测）、`14_ProductionEngineering`（生产化工程）。
- 建议：先建立"一次请求的完整生命周期"整体图景，再深入具体组件。

# 2. 运行时全景图

## 2.1 分层架构总览

```
┌────────────────────────────────────────────────────────────┐
│                         接入层                              │
│    REST / SSE / WebSocket / 消息队列                        │
├────────────────────────────────────────────────────────────┤
│                       应用编排层                            │
│   任务分发 / 会话管理 / 权限校验 / 幂等控制                  │
├────────────────────────────────────────────────────────────┤
│                      Agent 运行时                           │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐       │
│  │ Planner  │ │ Executor │ │ Memory   │ │ Guardrail│       │
│  └──────────┘ └──────────┘ └──────────┘ └──────────┘       │
│  ┌──────────────────────────────────────────────────┐      │
│  │  状态管理（检查点 / 恢复 / 中断 / 审批挂起）        │      │
│  └──────────────────────────────────────────────────┘      │
├────────────────────────────────────────────────────────────┤
│                       能力层                                │
│   ChatModel / Tools / RAG / MCP / 记忆存储                  │
├────────────────────────────────────────────────────────────┤
│                      可靠性层                               │
│   超时 / 重试 / 幂等 / 限流 / 熔断 / 降级                    │
├────────────────────────────────────────────────────────────┤
│                      观测层                                 │
│   Trace / Metrics / Logs / 成本                             │
├────────────────────────────────────────────────────────────┤
│                     基础设施                                │
│   配置中心 / 密钥管理 / 状态存储 / 向量库 / 缓存              │
└────────────────────────────────────────────────────────────┘
```

## 2.2 各层职责与边界

| 层 | 职责 | 不应承担 |
|----|------|----------|
| 接入层 | 协议适配、鉴权入口、流式转发 | 业务逻辑、模型调用 |
| 编排层 | 任务分发、会话、幂等、权限 | 具体工具实现 |
| 运行时 | 规划、执行、状态、护栏 | 基础设施细节 |
| 能力层 | 模型、工具、检索、记忆 | 重试与熔断策略 |
| 可靠性层 | 超时、重试、限流、熔断、降级 | 业务语义判断 |
| 观测层 | 追踪、指标、日志、成本 | 阻塞主链路 |
| 基础设施 | 存储、配置、密钥、缓存 | 业务编排 |

分层的价值在于"关注点分离"：任何一层出问题，都能被独立替换、独立观测、独立扩容。

## 2.3 数据流与调用链

```
请求 → 接入 → 编排(鉴权/幂等) → 运行时(加载状态)
     → 能力层(模型/工具) → 可靠性包装 → 观测埋点
     → 运行时(保存状态) → 响应
```

调用链上每一次跨层调用都应携带 `traceId`，否则事故排查会退化为"猜测"。

## 2.4 分层带来的常见误区

| 误区 | 表现 | 后果 |
|------|------|------|
| 编排层写业务逻辑 | 在分发器里做规则判断 | 难复用、难测试 |
| 可靠性层做业务降级 | 熔断后返回伪造数据 | 信任崩塌 |
| 观测层同步写库 | 埋点阻塞主链路 | 延迟升高 |
| 能力层内嵌重试 | 各工具各自重试 | 重试风暴 |

分层不是"多写几个类"，而是"让每层只做一件事"。

## 2.5 从单体到分层的演进

```
阶段一：一个类里跑通循环
阶段二：抽出状态存储与工具注册
阶段三：引入可靠性包装与观测
阶段四：拆分为独立服务，接口化
```

每一步都应保持"可运行"，避免大爆炸式重构。

# 3. 一次请求的完整生命周期

## 3.1 九个阶段

```
1. 接入      接收请求，鉴权，生成 traceId / taskId
2. 会话      加载会话状态与记忆
3. 规划      组装上下文，模型规划
4. 执行      循环：决策 → 工具调用 → 观察
5. 审批      命中高风险 → 挂起，等待人工
6. 持久化    每步保存检查点
7. 观测      记录 Trace / Token / 成本
8. 响应      流式或一次性返回
9. 收尾      写入记忆，异步后处理
```

## 3.2 阶段与组件的映射

| 阶段 | 主要组件 | 关键动作 |
|------|----------|----------|
| 接入 | 网关 / 接入层 | 鉴权、限流、生成 ID |
| 会话 | 会话管理器 | 加载历史、拼接记忆 |
| 规划 | Planner | 上下文组装、模型调用 |
| 执行 | Executor | 工具调用、观察回填 |
| 审批 | 审批服务 | 挂起、通知、恢复 |
| 持久化 | 状态存储 | 检查点写入 |
| 观测 | AgentObserver | 埋点、采样 |
| 响应 | 接入层 | SSE 流式推送 |
| 收尾 | 记忆写入器 | 异步落库 |

## 3.3 异常路径与补偿

正常路径只有一条，异常路径却有很多：

- 规划超时 → 降级到固定工作流或返回明确失败。
- 工具失败 → 重试（幂等）→ 降级 → 转人工。
- 审批超时 → 默认拒绝，而非默认放行。
- 进程崩溃 → 从最近检查点恢复，注意避免重复副作用。

> 核心原则：**异常路径也必须被设计**，而不是等它发生。

## 3.4 生命周期与超时预算

一次请求的总超时，应分解到各阶段，避免"某一阶段悄悄吃光全部预算"：

| 阶段 | 建议预算 | 说明 |
|------|----------|------|
| 接入 | 100 ms | 鉴权、限流 |
| 会话 | 200 ms | 状态加载 |
| 规划 | 单次模型超时 | 可重试一次 |
| 执行 | 每步超时 | 步数 × 单步超时 |
| 响应 | 首字节时间 | 流式优先 |

```java
public class TimeoutBudget {
    private final long totalMillis;
    public long remaining() { ... }   // 伪代码

    public long allocate(String stage, long requested) {
        return Math.min(requested, remaining());
    }
}
```

> 总预算耗尽时，应返回"部分结果 + 明确说明"，而不是继续等待。

| 关注点 | 核心问题 | 对应章节 |
|--------|----------|----------|

| 可靠性 | 依赖失败如何不雪崩 | `14/Reliability` |
| 性能与成本 | 如何又快又省 | `14/Performance` |
| 可观测 | 出问题如何定位 | `13_Observability` |
| 安全 | 如何不被滥用/越权 | `15_Security` |

## 4.2 关注点之间的权衡

六大关注点并非彼此独立，常常互相拉扯：

| 目标 A | 与目标 B 的冲突 | 折中手段 |
|--------|----------------|----------|
| 可靠性（多重重试） | 成本 | 幂等 + 指数退避 + 上限 |
| 可观测（全量 Trace） | 性能 | 采样 + 异步上报 |
| 安全（严格审批） | 效率 | 风险分级，只拦高风险 |
| 性能（缓存） | 一致性 | 短 TTL + 显式失效 |

没有"全都要"的方案，只有"按场景排序优先级"的方案。

- 状态、会话、可靠性、性能成本 → `14_ProductionEngineering`。
- 可观测 → `13_Observability`。
- 安全 → `15_Security`。

# 5. 运行时关键组件

## 5.1 任务分发器

### 5.1.1 接口定义

```java
public interface TaskDispatcher {
    String submit(AgentTask task);      // 返回 taskId
    AgentState query(String taskId);
    void cancel(String taskId);
}
```

### 5.1.2 实现要点

- `submit` 必须幂等：相同 `idempotencyKey` 返回同一 `taskId`。
- `query` 要能读到"运行中/挂起/完成/失败"等状态。
- `cancel` 对已进入不可中断区的任务，应标记为"取消待生效"。

## 5.2 状态存储

### 5.2.1 接口定义

```java
public interface AgentStateStore {
    AgentState load(String taskId);
    void save(String taskId, AgentState state);
    void delete(String taskId);
}
```

### 5.2.2 一致性策略

- 乐观锁：`save` 携带版本号，冲突则重试或拒绝。
- 检查点（Checkpoint）：每步或每隔 N 步落盘，兼顾性能与恢复粒度。
- 存储选型：热状态用 Redis，冷归档用关系库/对象存储。

## 5.3 工具注册中心

### 5.3.1 接口定义

```java
public interface ToolRegistry {
    List<ToolCallback> toolsFor(UserContext user, String scenario);
}
```

### 5.3.2 按权限裁剪

工具注册中心不应返回"全量工具"，而应基于用户与场景返回最小集合：

```java
// 伪代码：按权限与场景双重过滤
List<ToolCallback> tools = registry.toolsFor(user, "customer-service");
if (tools.size() > MAX_TOOLS) {
    tools = ranker.topK(tools, MAX_TOOLS);   // 工具过多会降低选择准确率
}
```

## 5.4 可靠性包装

### 5.4.1 接口定义

```java
public interface ReliableInvoker {
    <T> T invoke(Supplier<T> action, Policy policy);
    // policy: timeout / retry / circuitBreaker / rateLimiter
}
```

### 5.4.2 策略组合

```
请求 → 限流 → 熔断判断 → 超时控制 → 重试(幂等) → 降级
```

组合顺序很关键：限流应在最前（保护自己），降级在最后（兜底）。

## 5.5 观测器

### 5.5.1 接口定义

```java
public interface AgentObserver {
    void onStep(String taskId, StepInfo step);
    void onComplete(String taskId, Result result);
    void onError(String taskId, Throwable error);
}
```

### 5.5.2 埋点时机

- `onStep`：每次"决策 → 工具 → 观察"完成后，记录 Token、耗时、工具名。
- `onComplete`：记录总成本、总步数、最终结果。
- `onError`：记录异常类型与上下文，注意脱敏。

## 5.6 组件协作

```
Dispatcher ──► StateStore ◄── Runtime
     │              ▲
     ▼              │
ToolRegistry ──► Executor ──► ReliableInvoker
                    │
                    ▼
                Observer
```

组件之间通过接口解耦，便于替换实现与单元测试。

## 5.7 组件的失败隔离

任一组件失败都不应拖垮整个运行时：

| 组件 | 失败表现 | 隔离手段 |
|------|----------|----------|
| 任务分发器 | 无法提交新任务 | 多实例 + 队列缓冲 |
| 状态存储 | 无法保存/恢复 | 降级为只读或快速失败 |
| 工具注册中心 | 拿不到工具 | 本地缓存兜底 |
| 观测器 | 埋点阻塞 | 异步队列 + 丢弃策略 |

> 观测组件的原则是：**可以丢数据，不可以拖慢主链路**。

# 6. 部署形态

## 6.1 形态对比

| 形态 | 特点 | 适用 |
|------|------|------|
| 单体服务 | 简单 | 中小规模 |
| 无状态多实例 | 可水平扩展 | 高并发 |
| 异步任务队列 | 长任务、削峰 | 深度研究等 |
| 函数计算 | 按需、低成本 | 低频调用 |
| 网关 + 多后端 | 多模型路由 | 企业统一入口 |

## 6.2 选型建议

- 请求-响应短任务：无状态多实例 + 外部状态存储。
- 长任务（分钟级以上）：异步队列 + 任务状态查询接口。
- 突发低频：函数计算，但注意冷启动与连接复用。
- 多模型/多租户：网关统一入口，后端按策略路由。

## 6.3 演进路径

```
单体 → 无状态多实例 → 异步队列 → 弹性伸缩 + 灰度
```

每次演进前，先确认状态已外置、观测已就绪，否则扩展只会放大问题。

## 6.4 部署与状态的一致性

- 无状态实例 + 外部状态存储是水平扩展的前提。
- 异步任务必须有"任务查询"接口，否则用户无法知道进度。
- 多实例下，审批恢复可能落到不同实例，状态必须共享。
- 灰度发布时，新旧版本的状态结构要向后兼容。

```java
// 伪代码：状态结构向后兼容
AgentState state = store.load(taskId);
state = StateMigrator.migrate(state, CURRENT_VERSION);
```

# 7. 运行时成熟度模型

## 7.1 五个级别

| 级别 | 特征 |
|:----:|------|
| L1 可运行 | 能跑通，无持久化、无监控 |
| L2 可观测 | 有 Trace、指标、日志 |
| L3 可靠 | 有超时/重试/熔断/降级 |
| L4 可治理 | 多租户、权限、成本、审计 |
| L5 可规模化 | 弹性伸缩、灰度、评测回归 |

> 目标是把 Agent 从 L1 推到 L4/L5。

## 7.2 各级的落地清单

| 级别 | 达标标志 |
|:----:|----------|
| L1 | 端到端可跑通一个任务 |
| L2 | 任意任务可回放，指标可看板 |
| L3 | 单依赖故障不影响整体可用性 |
| L4 | 可按租户计量成本、可按权限审计 |
| L5 | 可灰度发布、评测回归不通过则阻断上线 |

## 7.3 如何逐级推进

- L1→L2：先补 Trace 与指标，再谈优化。
- L2→L3：为每个外部依赖加超时、重试、熔断。
- L3→L4：引入租户、权限、成本、审计四件套。
- L4→L5：接入 CI 评测、灰度与回滚。

## 7.4 成熟度与团队协作

成熟度不只是技术问题，也对应协作方式：

| 级别 | 团队需要的角色 |
|:----:|----------------|
| L1~L2 | 开发即可 |
| L3 | 需 SRE/运维介入 |
| L4 | 需安全、合规、财务参与 |
| L5 | 需专门的评测与发布流程 |

> 跳过组织准备直接上 L5，往往在"成本审计"和"事故复盘"两处翻车。

# 8. 常见运行时事故

## 8.1 事故清单

| 事故 | 根因 | 防御 |
|------|------|------|
| 服务重启任务丢失 | 状态在内存 | 状态外置 |
| 重复扣款 | 重试 + 非幂等 | 幂等键 |
| 成本一夜暴涨 | 无预算与告警 | Token 预算 + 监控 |
| 越权访问数据 | 无租户隔离 | 元数据过滤 + 鉴权 |
| 依赖宕机拖垮服务 | 无熔断降级 | 熔断 + 降级 |
| 无法定位问题 | 无 Trace | 全链路追踪 |

## 8.2 典型事故复盘

以"重复扣款"为例：

```
用户请求 → 模型调用支付工具 → 网络超时(实际已扣款)
         → 重试机制再次调用 → 重复扣款
```

修复：支付工具必须接收 `idempotencyKey`，服务端对同一键只执行一次。

### 8.2.1 成本暴涨复盘

```
一个循环 Bug → 每步都重新检索全量文档
            → Token 消耗线性放大
            → 无预算告警，直到账单出来才发现
```

修复：步数上限 + Token 预算 + 实时成本告警，三者缺一不可。

### 8.2.2 越权访问复盘

```
用户 A 提问 → 检索未按租户过滤 → 召回用户 B 的文档
           → 模型"如实"回答 → 数据泄露
```

修复：在检索层做元数据过滤，而非"召回后再过滤"。

## 8.3 防御性设计

- 所有写操作幂等；
- 所有外部调用有超时；
- 所有依赖有熔断与降级；
- 所有任务有步数与成本上限；
- 所有异常有兜底与转人工路径。

- [ ] 状态是否已外置并可恢复？
- [ ] 写操作是否幂等？
- [ ] 外部依赖是否有超时、重试、熔断？
- [ ] 是否有步数与成本上限？
- [ ] 是否全链路可观测、可回放？

- [ ] 是否有失败兜底与转人工路径？
- [ ] 是否有评测与灰度回滚机制？
