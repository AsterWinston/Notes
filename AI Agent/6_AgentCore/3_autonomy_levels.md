# 1. 为什么需要分级

自主性（Autonomy）越高，能力越强，但**可控性、可预测性、成本可控性越低**。生产系统需要明确"这个 Agent 被允许自主到什么程度"。

## 1.1 自主性的代价曲线

```
自主性低 ←──────────────────────────────→ 自主性高
可控、可预测                            灵活、能力强
成本低                                  成本高
易审计                                  难审计
```

这条曲线的含义是：自主性不是"越多越好"，而是"越多越贵"。每放开一档，都要用可观测、评测、回滚去兑换。

## 1.2 分级的价值

- **对齐期望**：产品、研发、风控对"Agent 能自己做什么"有统一语言。
- **控制风险**：把高风险动作固定在低自主档，从机制上限制爆炸半径。
- **指导演进**：明确"当前在哪一级、下一级需要补什么能力"。
- **便于配置**：把自主性做成配置项，而非写死在代码里。

## 1.3 常见的误解

| 误解 | 事实 |
|------|------|
| 自主性 = 模型能力 | 自主性是**系统策略**，模型能力只是前提 |
| 越高越好 | 高自主意味着高成本、难审计、难回滚 |
| 一次定死 | 应按任务、按会话、按信任度动态调整 |

## 1.4 与人类驾驶分级的类比

自主性分级并非 Agent 独有。自动驾驶（Autonomous Driving）的 L0~L5 分级提供了很好的类比：

| 自动驾驶 | 对应 Agent | 共同点 |
|----------|-----------|--------|
| L0 无自动化 | L0 纯工作流 | 人完全负责 |
| L1 辅助 | L1 建议 | 系统提示，人执行 |
| L2 部分自动 | L2 审批 | 系统动作，人确认 |
| L3 有条件自动 | L3 限定自主 | 特定条件下系统负责 |
| L4 高度自动 | L4 高度自主 | 常规场景无人介入 |
| L5 完全自动 | L5 完全自主 | 全场景无人介入 |

> 类比的价值：两者都强调"**责任随自主性转移**"，也都遵循"逐步放开"。

# 2. 五级自主性模型

## 2.1 模型总览

| 级别 | 名称 | 决策方式 | 例子 |
|:----:|------|----------|------|
| L0 | 无自主 | 纯代码流程 | 传统工作流 |
| L1 | 建议 | 模型建议，人执行 | 智能补全、推荐 |
| L2 | 审批后执行 | 模型规划，人审批每步 | 敏感操作确认 |
| L3 | 限定自主 | 模型自主，但限定工具/范围 | 知识库问答 Agent |
| L4 | 高度自主 | 模型自主规划与执行，事后审计 | 研究 Agent、编码 Agent |
| L5 | 完全自主 | 无人工介入，自我设定目标 | 实验性，生产慎用 |

## 2.2 级别与决策权

把"决策权"拆开看，各档的差别一目了然：

| 级别 | 谁定目标 | 谁定步骤 | 谁执行 | 谁监督 |
|:----:|:--------:|:--------:|:------:|:------:|
| L0 | 人 | 人 | 代码 | 人 |
| L1 | 人 | 人 | 人 | 人 |
| L2 | 人 | 模型 | 人确认后系统 | 人 |
| L3 | 人 | 模型 | 系统 | 系统 |
| L4 | 人 | 模型 | 系统 | 系统（事后） |
| L5 | 模型 | 模型 | 系统 | 系统 |

> 关键分水岭在 L2/L3 之间：**执行权是否交给人**。

## 2.3 级别不是能力评级

L4 不等于"比 L3 更好的 Agent"，而是"适用于不同风险场景的形态"。一个只做只读问答的系统，L3 已是最优解；强行升到 L4 只会增加成本与风险。

## 2.4 分级与责任归属

自主性提升的同时，责任主体也在转移：

| 级别 | 出错时主要责任方 | 可追溯对象 |
|:----:|------------------|------------|
| L1 | 人（采纳了建议） | 建议内容 |
| L2 | 人（审批通过） | 审批记录 |
| L3 | 系统 + 配置方 | 工具白名单、日志 |
| L4 | 系统 + 设计方 | 全程 Trace、审计 |
| L5 | 系统 + 组织 | 目标设定与预算 |

> 责任无法追溯的高自主系统，本质上不可治理。

# 3. 各级别特征

## 3.1 建议型（L1）

```
用户请求 → 模型给出方案 → 用户自己操作
```

- 风险最低，但效率提升有限。
- 典型：代码补全、文案建议。
- 边界：模型输出只是"素材"，责任与执行仍在人。

## 3.2 审批型（L2）

```
用户请求 → 模型规划 → [人工审批] → 执行 → 汇总
```

- **高风险操作的标准形态**：转账、删除、对外发送。
- 关键点：审批点要"少而准"，过多会失去效率优势。
- 边界：审批必须"默认拒绝"，超时视为拒绝。

### 3.2.1 审批点设计

审批点应满足三个条件，否则会沦为"点击仪式"：

- **高风险**：动作不可逆或影响外部（转账、删除、外发）。
- **低频**：每次都要审批的动作，说明该动作本身就不该自动执行。
- **信息充分**：审批界面要展示"模型将做什么、影响范围、可回滚性"。

### 3.2.2 审批的默认策略

```java
public ApprovalResult decide(ApprovalRequest req) {
    ApprovalResult r = approvalService.waitFor(req, req.timeout());
    if (r == null) {
        return ApprovalResult.rejected("审批超时，默认拒绝");
    }
    return r;
}
```

> 反例：审批超时"默认放行"——这是最危险的实现方式。

## 3.3 限定自主（L3）

```
用户请求 → 模型在限定的工具集与范围内自主执行 → 输出
```

- 常见生产形态：RAG 问答、客服 Agent。
- 约束手段：工具白名单、只读权限、步数上限。
- 边界：越出白名单即中断，转人工而非"自行扩展"。

## 3.4 高度自主（L4）

```
用户目标 → 模型自主规划 → 多步执行 → 自我修正 → 交付
```

- 典型：深度研究、编码 Agent。
- 必须有：步数上限、成本上限、全程 Trace、事后审计。
- 边界：允许自主，但不允许"不可回滚的破坏性动作"。

### 3.4.1 事后审计的要素

L4 的信任建立在"事后可查"之上，审计至少要记录：

| 要素 | 内容 |
|------|------|
| 输入 | 用户原始目标、上下文 |
| 决策 | 每步的模型输出与理由 |
| 动作 | 工具名、参数、返回值 |
| 成本 | 每步与累计 Token/金额 |
| 结果 | 最终交付物与状态变更 |

> 没有审计记录的 L4，等于把风险"托管"给了一个黑盒。

## 3.5 完全自主（L5）

- 自主设定子目标、长期运行。
- 当前更多是研究课题，生产不建议。
- 边界：即便研究场景，也应设置"总预算 + 终止条件 + 人工熔断"。

## 3.6 级别对照小结

| 级别 | 人的角色 | 主要成本来源 | 主要风险 |
|:----:|----------|--------------|----------|
| L1 | 执行者 | 模型调用 | 采纳错误建议 |
| L2 | 审批者 | 审批人力 + 模型 | 审批疲劳、误批 |
| L3 | 监督者 | 模型 + 工具 | 越界、误用工具 |
| L4 | 审计者 | 模型 + 工具 + 长链路 | 目标漂移、成本失控 |
| L5 | 旁观者 | 长期运行 | 不可预测、难回滚 |

# 4. 自主性的五个控制维度

## 4.1 维度清单

| 维度 | 控制手段 | 说明 |
|------|----------|------|
| 工具 | 白名单 / 权限 | 能调用哪些工具 |
| 范围 | 数据/资源边界 | 能访问哪些数据 |
| 步数 | 最大迭代次数 | 防止无限循环 |
| 成本 | Token/金额预算 | 防止成本失控 |
| 审批 | 关键节点人工确认 | 高风险动作拦截 |

## 4.2 策略对象

### 4.2.1 字段设计

```java
public class AutonomyPolicy {
    private final Set<String> allowedTools;
    private final int maxSteps;
    private final long maxTokens;
    private final Set<String> approvalRequiredTools;
}
```

### 4.2.2 校验与生效

```java
public void validate(AutonomyPolicy p) {
    if (p.getMaxSteps() <= 0) {
        throw new IllegalArgumentException("maxSteps 必须为正数");
    }
    if (p.getMaxTokens() <= 0) {
        throw new IllegalArgumentException("maxTokens 必须为正数");
    }
    // 审批集合应是白名单的子集，避免"审批了却无权限"
    if (!p.getAllowedTools().containsAll(p.getApprovalRequiredTools())) {
        throw new IllegalArgumentException("审批工具必须属于允许集合");
    }
}
```

## 4.3 维度落地

- 工具：在注册中心按用户与场景裁剪，而非全量挂载。
- 范围：在检索层做元数据过滤，避免"召回后再过滤"导致泄露。
- 步数：运行时硬计数，达到上限即优雅终止。
- 成本：按任务预算与租户日预算双限制。
- 审批：只在高风险动作设点，且默认拒绝。

## 4.4 维度组合与冲突

五个维度往往需要组合使用，且可能互相冲突：

| 冲突 | 表现 | 处理 |
|------|------|------|
| 工具宽 × 审批少 | 高自主但高风险 | 高风险工具单独列审批 |
| 范围宽 × 成本低 | 检索越广越贵 | 限制召回量 + 缓存 |
| 步数多 × 成本低 | 长链路烧钱 | 每步预算 + 全局预算 |
| 审批多 × 步数多 | 效率崩塌 | 合并审批、批量确认 |

> 设计的顺序建议：**先定工具与范围，再定步数与成本，最后配审批**。

# 5. 分级选型建议

## 5.1 场景对照

| 场景 | 建议级别 | 理由 |
|------|:--------:|------|
| 内容生成、代码补全 | L1 | 人在回路，风险低 |
| 支付、删除、外发 | L2 | 高风险，必须审批 |
| 知识问答、客服 | L3 | 限定范围即可 |
| 研究、编码、数据分析 | L4 | 需要自主多步 |
| 长期自主运行 | L5 | 暂不建议生产 |

## 5.2 选型方法

选型可按三个问题依次判断：

```
1. 动作是否可逆？     不可逆 → L2 起
2. 是否需要多步自主？ 需要   → L3/L4
3. 是否只读？         只读   → 可放宽到 L3/L4
```

## 5.3 选型反例

- 把"删除数据"做成 L4，理由是"内部工具"——一旦提示注入，后果不可逆。
- 把"只读检索"做成 L2，每步都要审批——效率崩塌，用户会绕过系统。
- 把"对外发送邮件"做成 L3，仅靠白名单——收件人范围仍需人工确认。

## 5.4 选型与成本

自主档位直接决定成本结构：

| 级别 | 主要成本 | 成本特征 |
|:----:|----------|----------|
| L1 | 模型调用 | 低且可控 |
| L2 | 模型 + 审批人力 | 人力成本为主 |
| L3 | 模型 + 工具 | 随步数线性增长 |
| L4 | 模型 + 工具 + 长链路 | 可能非线性增长 |
| L5 | 长期运行 | 难预估 |

> 选型时应同时给出"能力上限"与"成本上限"，二者缺一不可。

# 6. 自主性与可靠性

## 6.1 路径爆炸

```
自主性 ↑  →  路径组合数 ↑  →  测试覆盖难度 ↑  →  事故概率 ↑
```

因此：

- **自主性应随信任度逐步提升**（先 L2 跑一段时间，再放开到 L3/L4）。
- 每次提升自主性，都要同步加强**可观测、评测、回滚**能力。
- 自主性是"可配置"的，而不是写死在代码里的。

## 6.2 信任度渐进

| 阶段 | 自主档 | 前置条件 |
|------|:------:|----------|
| 试点 | L2 | 有 Trace、有审批台 |
| 扩大 | L3 | 有评测集、成功率达标 |
| 放开 | L4 | 有审计、有回滚、成本可控 |

> 放开的每一步，都应是"数据驱动"的，而非"感觉可以了"。

## 6.3 与失败模式的关系

高自主会放大所有失败模式：循环、幻觉、工具误用、目标漂移。低自主档相当于在这些失败上加了一层"人工刹车"。详见 `13_failure_modes.md`。

## 6.4 可靠性与护栏

自主性越高，越依赖护栏（Guardrail）来"兜底"：

| 护栏 | 作用 | 触发后动作 |
|------|------|------------|
| 越界检测 | 工具/数据超出白名单 | 中断 + 转人工 |
| 循环检测 | 重复步骤或相似输出 | 中断 + 重规划 |
| 预算护栏 | 接近步数/成本上限 | 降级或收尾 |
| 内容护栏 | 违规输入输出 | 拦截 + 记录 |

```java
// 伪代码：护栏触发即降级并记录
for (Guardrail g : guardrails) {
    if (g.triggered(state)) {
        state.record("guardrail", g.name());
        return state.downgradeAndYield();
    }
}
```

> 护栏不是"可选项"，而是高自主档位的入场券。

# 7. 动态自主性

## 7.1 决策函数

同一次会话中，可以根据任务风险动态调整：

```java
public AutonomyLevel decideLevel(Task task) {
    if (task.isHighRisk()) return AutonomyLevel.L2;      // 需审批
    if (task.isReadOnly()) return AutonomyLevel.L4;      // 读操作可放开
    return AutonomyLevel.L3;
}
```

> 例如：查询类操作 L4，写操作 L2，是常见的差异化策略。

## 7.2 会话内升降级

### 7.2.1 升级条件

- 连续 N 步无异常、无护栏触发；
- 评测指标达标；
- 当前任务已被用户明确授权。

### 7.2.2 降级条件

- 命中护栏（越界、注入、异常工具调用）；
- 成本或步数接近上限；
- 用户显式要求"先问我"。

```java
// 伪代码：会话内动态调整
AutonomyLevel level = policy.getLevel(session);
if (guardrail.triggered()) {
    level = level.downgrade();       // 触发护栏即降级
    session.record("downgrade", level);
}
```

### 7.2.3 升降级的记录

每次升降级都应落成事件，便于事后分析"为什么这个会话会降级"：

```java
public record AutonomyChange(
        String sessionId,
        AutonomyLevel from,
        AutonomyLevel to,
        String reason,
        long timestamp) { }
```

> 升降级记录是"自主性可治理"的证据链。

## 7.3 状态与审批衔接

动态自主性必须与状态管理协同：审批挂起、恢复、降级都要落成检查点，否则进程重启后会"忘记自己已经降过级"。详见 `11_human_in_the_loop.md` 与 `10_state_and_control_flow.md`。

## 7.4 动态自主性示例

一个典型的会话内自主性流转：

```
只读查询(L4) → 需要写操作 → 自动降到(L2) → 人工审批
            → 审批通过执行 → 回到只读 → 恢复(L4)
```

```java
public AutonomyLevel onToolCall(AutonomyLevel current, ToolCall call) {
    if (call.isWrite()) {
        return AutonomyLevel.L2;          // 写操作必须审批
    }
    if (call.isReadOnly() && current == AutonomyLevel.L2) {
        return AutonomyLevel.L4;          // 回到只读可放开
    }
    return current;
}
```

> 差异化策略（读放开、写收紧）是生产中收益最高的动态自主方案。

# 8. 生产注意事项

## 8.1 风险与建议

| 风险 | 建议 |
|------|------|
| 一步到位给高自主 | 从 L2/L3 起步，逐步放开 |
| 自主性不可配置 | 做成策略/配置项 |
| 无步数与成本上限 | 必须硬性限制 |
| 审批点过多 | 只在高风险动作设审批 |
| 无审计 | 全程记录决策与动作 |

## 8.2 反模式

| 反模式 | 问题 | 正解 |
|--------|------|------|
| 全局一个档 | 无法差异化 | 按任务/场景分级 |
| 审批可被跳过 | 形同虚设 | 审批在服务端强制 |
| 上限只写在文档 | 无法拦截 | 运行时硬校验 |
| 降级不持久化 | 重启即复活 | 降级写入检查点 |
| 高自主 + 无 Trace | 出事无法定位 | 先补观测再放开 |

## 8.3 上线检查

- [ ] 每个场景都有明确的自主档位。
- [ ] 工具白名单、数据范围已按最小权限配置。
- [ ] 步数、Token、金额上限均已硬校验。
- [ ] 高风险动作已设审批且默认拒绝。
- [ ] 决策与动作全程可审计。
- [ ] 支持会话内动态升降级并持久化。
- [ ] 放开自主前已完成评测与灰度。

## 8.4 度量与监控

自主性相关指标应纳入监控看板：

| 指标 | 含义 | 用途 |
|------|------|------|
| 审批触发率 | 需审批动作占比 | 判断档位是否过严 |
| 审批通过率 | 审批通过比例 | 判断审批是否有意义 |
| 护栏触发率 | 越界/循环占比 | 判断自主性是否过高 |
| 平均步数 | 每任务迭代次数 | 判断是否接近上限 |
| 单任务成本 | Token/金额分布 | 判断预算是否合理 |
| 降级率 | 会话降级占比 | 判断稳定性 |

> 若审批通过率接近 100%，说明审批点设置过宽或模型已足够可靠，可考虑适度放开。

# 9. 小结

## 9.1 要点回顾

- 自主性分级是"能力与可控性"的权衡工具。
- L2 审批型是高危操作的标准形态，L3/L4 是生产主力。
- 五个控制维度：工具、范围、步数、成本、审批。
- 自主性应可配置、可动态调整、随信任度逐步放开。
