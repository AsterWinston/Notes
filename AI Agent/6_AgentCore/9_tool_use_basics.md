# 1. 工具是 Agent 的手脚

结论先行：没有工具的 Agent 只能"空谈"，工具是 Agent 与外部世界交互的唯一通道，也是其能力边界的真正来源。

## 1.1 为什么工具决定能力边界

### 1.1.1 无工具 Agent 的局限

大语言模型（Large Language Model，LLM）本身只有两类能力：

- 基于训练语料做**文本生成**；
- 在上下文窗口内做**推理与归纳**。

它既无法知道此刻的实时信息（今天的汇率、库存、订单状态），也无法改变任何外部状态（下单、发信、写文件）。因此，脱离工具的 Agent 只能"讨论世界"，不能"作用于世界"。

### 1.1.2 工具带来的三类能力

工具让 Agent 能够：

```
读取世界：查询、检索、读取文件
改变世界：下单、发消息、写文件、调用 API
计算验证：执行代码、数学计算
```

这三类能力对应三种截然不同的风险等级，后文会反复用到这一分类。

## 1.2 工具调用的本质

### 1.2.1 从自然语言到结构化调用

模型输出的是一段自然语言或结构化文本，它并不是真正的函数调用。真正发生的是：

```
模型生成"想调用某工具"的文本
        │
        ▼
框架把它解析成结构化对象（工具名 + 参数）
        │
        ▼
框架在宿主语言（Java）中执行对应方法
```

因此"工具调用"是**模型决策 + 框架执行**的组合，而不是模型自己执行了代码。理解这一点，才能理解为什么参数校验、鉴权必须由框架侧负责。

### 1.2.2 工具 = 受约束的函数

一个工具本质上是"带契约的函数"：

| 契约要素 | 说明 | 对应 Java 元素 |
|----------|------|----------------|
| 名称 | 模型选择工具的依据 | 方法名或注解名 |
| 描述 | 何时用、何时不用 | 注解文本 |
| 参数 | 名称、类型、格式 | 方法参数 |
| 返回值 | 能拿到什么 | 返回类型 |
| 副作用 | 是否改变状态 | 需在描述中声明 |

## 1.3 边界与坑

- 把工具当"万能函数"：模型只会按描述理解能力，描述没写的能力等于不存在。
- 工具越权：工具在宿主侧直接持有高权限，若不校验，模型一句错误决策就能造成真实破坏。
- 混淆"模型调用"与"代码调用"：模型只产生意图，执行永远发生在框架侧。

# 2. 工具调用的完整闭环

结论先行：一次工具调用是"决策—解析—执行—回填—再决策"的闭环，任何一环缺失都会导致 Agent 失去自纠能力。

## 2.1 五步闭环

### 2.1.1 闭环流程

```
用户目标
   │
   ▼
① 模型决策：调用工具 X，参数 {...}
   │
   ▼
② 框架解析：把决策转成结构化调用
   │
   ▼
③ 执行工具：调用真实 Java 方法 / 外部 API
   │
   ▼
④ 结果回填：把结果作为消息返回模型
   │
   ▼
⑤ 模型继续：再决策或输出最终答案
```

### 2.1.2 各步骤职责

| 步骤 | 职责 | 责任方 |
|------|------|--------|
| ① 模型决策 | 选择工具、生成参数 | 模型 |
| ② 框架解析 | 校验参数、类型转换 | 框架 |
| ③ 执行工具 | 真实调用、超时控制 | 框架 |
| ④ 结果回填 | 结构化、精简、追加消息 | 框架 |
| ⑤ 模型继续 | 判断是否还需调用 | 模型 |

## 2.2 闭环的 Java 骨架

### 2.2.1 数据结构

```java
public record ToolCall(String name, Map<String, Object> args) {}

public record ToolResult(boolean success, String content) {
    public static ToolResult ok(Object data) {
        return new ToolResult(true, String.valueOf(data));
    }
    public static ToolResult fail(String message) {
        return new ToolResult(false, message);
    }
}
```

### 2.2.2 编排循环

```java
public String run(String userGoal) {
    List<Message> messages = new ArrayList<>();
    messages.add(Message.user(userGoal));

    for (int step = 0; step < MAX_STEPS; step++) {
        ModelOutput output = model.chat(messages, tools);

        if (output.isFinalAnswer()) {
            return output.text();                       // ⑤ 输出最终答案
        }

        ToolCall call = output.toolCall();              // ① 模型决策
        messages.add(Message.assistant(call));

        ToolResult result = executor.execute(call);     // ②③ 解析并执行
        messages.add(Message.tool(result));             // ④ 结果回填
    }
    return "超过最大步数仍未完成";
}
```

## 2.3 闭环中的失败点

### 2.3.1 失败点清单

| 环节 | 典型失败 | 后果 |
|------|----------|------|
| ① 决策 | 选错工具、参数格式错 | 调用无效 |
| ② 解析 | 参数类型不匹配 | 抛异常或静默失败 |
| ③ 执行 | 超时、外部服务不可用 | 任务卡死 |
| ④ 回填 | 结果过大、格式混乱 | 上下文爆炸、模型误读 |
| ⑤ 继续 | 陷入重复调用 | 死循环、成本失控 |

### 2.3.2 边界与坑

- 缺少步数上限：模型可能反复调用同一工具，必须有 `MAX_STEPS`。
- 缺少超时：外部 API 挂起会拖垮整个 Agent 请求。
- 回填裸异常：异常对象 `toString()` 往往含栈信息，既浪费 Token 又污染上下文。

# 3. 工具的三类形态

结论先行：按副作用与可逆性，工具可分为只读、写、高风险三类，其安全要求依次递增。

## 3.1 只读工具

### 3.1.1 特征与示例

- 不改变任何外部状态；
- 可安全重试（幂等天然成立）；
- 失败通常只需换查询条件。

```java
@Tool("查询订单详情")
OrderResult queryOrder(@P("订单号，如 A123") String orderId) {
    return orderService.find(orderId);          // 纯读，无副作用
}
```

## 3.2 写工具

### 3.2.1 特征与示例

- 改变外部状态；
- 重试会产生重复副作用；
- 必须幂等（Idempotent），即同一请求执行多次与执行一次效果相同。

```java
@Tool("创建订单")
CreateResult createOrder(@P("幂等键") String idemKey,
                         @P("商品编码") String sku,
                         @P("数量") int qty) {
    return orderService.createIdempotent(idemKey, sku, qty);
}
```

## 3.3 高风险工具

### 3.3.1 特征与示例

- 不可逆或影响面大（删除、转账、外发）；
- 一旦误调用难以挽回；
- 必须引入审批闸门。

```java
@Tool("删除用户数据（不可逆）")
void deleteUserData(@P("用户ID") String userId) {
    approvalGate.require("deleteUserData", Map.of("userId", userId));
    userService.hardDelete(userId);
}
```

## 3.4 三类对比与安全要求

### 3.4.1 对比表

| 形态 | 说明 | 例子 | 可否重试 | 安全要求 |
|------|------|------|----------|----------|
| 只读工具 | 不改变状态，可安全重试 | 查询、检索、计算 | 可直接重试 | 低 |
| 写工具 | 改变状态，必须幂等 | 下单、发消息、写库 | 需幂等键 | 中 |
| 高风险工具 | 不可逆或影响大 | 删除、转账、外发 | 需审批 | 高 |

> 三类工具的安全要求依次递增：只读可放开，写要幂等，高风险要审批。

### 3.4.2 边界与坑

- 把"写"误判为"读"：例如"查询并缓存"会写缓存，仍属写操作。
- 只读工具也可能泄露：查询他人订单属于越权，只读不等于安全。
- 高风险工具混在普通工具集中：一旦模型误选，直接造成损失。

# 4. 工具描述的设计

结论先行：模型靠描述决定是否调用、怎么传参；描述质量直接决定调用准确率。

## 4.1 描述的作用

### 4.1.1 模型如何选择工具

模型在每步只看到工具的名称与描述，据此与用户目标做匹配。因此描述要回答三个问题：

1. 这个工具**做什么**；
2. **什么时候用**它；
3. 参数与返回值**长什么样**。

### 4.1.2 描述要素

| 要素 | 目的 |
|------|------|
| 用途 | 让模型知道能力 |
| 适用场景 | 提高召回 |
| 不适用场景 | 避免误用相邻工具 |
| 参数格式 | 减少参数错误 |
| 返回内容 | 让模型知道能拿到什么 |

## 4.2 好描述与坏描述

### 4.2.1 完整 Java 示例

```java
// 差：描述模糊
@Tool("查询")
String q(String s);

// 好：说明用途、参数、返回、限制
@Tool("""
        查询指定订单的详情。
        适用：用户询问订单状态、金额、商品时。
        不适用：查询物流轨迹（应使用 queryLogistics）。
        返回：订单号、状态、金额、下单时间。
        """)
String queryOrder(@P("订单号，格式如 A123") String orderId);
```

### 4.2.2 参数格式规范

| 参数类型 | 描述要点 | 反例 |
|----------|----------|------|
| 日期 | 明确格式 | "日期" → 应为"日期，格式 yyyy-MM-dd" |
| 枚举 | 列出取值 | "状态" → 应为"状态：PAID/SHIPPED/DONE" |

## 4.3 描述消歧

### 4.3.1 相邻工具边界

当两个工具高度相似时，必须在描述中互相点名，例如订单查询需注明"若要查物流请用 queryLogistics"。

### 4.3.2 边界与坑

- 描述过短：模型只能猜，误调用率上升。
- 描述过长：占用上下文、稀释注意力，且可能自相矛盾。
- 描述与实现不符：模型按描述传参却调用失败，是最难排查的坑。

# 5. 工具结果的设计

结论先行：结果回填决定模型能否自我纠错；结构化的结果让模型"看得懂、能引用、可继续"。

## 5.1 结果回填的原理

### 5.1.1 结果如何进入上下文

工具执行后，结果被包装成一条 `tool` 角色的消息追加到消息历史中。模型下一步看到的是**所有历史消息 + 该结果**，据此决定继续调用还是输出答案。

### 5.1.2 结果大小与 Token

| 结果规模 | 影响 |
|----------|------|
| 过小 | 信息不足，模型重复调用 |
| 适中 | 最佳 |
| 过大 | Token 成本上升、挤占上下文、稀释关键信息 |

## 5.2 结构化结果

### 5.2.1 完整 Java 示例

```java
// 差：返回大段非结构化文本
return orderService.getOrder(id).toString();

// 好：结构化、精简、含状态
record OrderResult(String orderId, String status, BigDecimal amount) {}
```

### 5.2.2 四原则

原则：

- **精简**：只回填模型需要的字段，避免 Token 浪费；
- **结构化**：便于模型理解；
- **含状态**：成功/失败明确；
- **可引用**：包含来源，便于溯源。

### 5.2.3 边界与坑

- 结果过大：必须有长度上限，并优先保留状态、ID 等头部字段。
- 大对象直接序列化：含循环引用或巨大嵌套时可能 OOM。
- 无来源信息：模型无法引用，人工排查也无从下手。

# 6. 工具错误处理

结论先行：错误不是异常，而是需要回填给模型的信息；把异常直接抛给模型会破坏闭环。

## 6.1 为什么不能裸抛异常

### 6.1.1 裸抛的后果

- 栈信息冗长，浪费 Token；
- 模型无法理解技术细节，无法自纠；
- 框架可能直接终止整个 Agent 循环。

### 6.1.2 结构化错误

应把错误转成模型能理解的短句，并区分"可重试"与"不可重试"。

## 6.2 错误分类与重试

### 6.2.1 错误分类

| 类别 | 例子 | 建议 |
|------|------|------|
| 参数错误 | 订单号格式错 | 提示模型改参数 |
| 临时错误 | 超时、限流 | 提示稍后重试 |
| 业务错误 | 订单不存在 | 提示换策略或告知用户 |
| 权限错误 | 无权访问 | 停止并转人工 |

### 6.2.2 完整 Java 示例

```java
@Tool("查询库存")
ToolResult queryStock(@P("商品编码") String sku) {
    try {
        int stock = stockService.get(sku);
        return ToolResult.ok(stock);
    } catch (TimeoutException e) {
        return ToolResult.fail("查询超时，请稍后重试");
    } catch (Exception e) {
        return ToolResult.fail("查询失败：" + e.getMessage());
    }
}
```

> **不要把异常直接抛给模型**，而是返回结构化错误，让模型能自我纠错或换策略。

## 6.3 边界与坑

- 把所有错误都写成"失败"：模型无法判断该重试还是该放弃。
- 泄露内部信息：错误消息可能含数据库表名、内网地址，需脱敏。
- 无限重试：临时错误应有次数上限，否则成本失控。

# 7. 工具的选择与路由

结论先行：工具越多，模型选择越难；控制单次可见工具数量与边界清晰度，是提升准确率的关键。

## 7.1 工具过多的代价

- 描述占用上下文，挤压有效信息；
- 相似工具互相干扰，误调用率上升；
- 参数格式混杂，模型容易张冠李戴。

## 7.2 选择策略

### 7.2.1 四种策略

工具过多会导致选择困难。策略：

| 策略 | 说明 |
|------|------|
| 按场景分组 | 订单场景只挂订单工具 |
| 工具检索 | 先筛相关工具再挂载 |
| 描述消歧 | 明确各工具的边界 |
| 数量控制 | 单次不超过 10~15 个 |

> 详见 `7_ToolsAndProtocols/4_tool_selection_routing.md`。

## 7.3 边界与坑

- 检索用纯向量相似度：可能漏掉关键工具，需保留"固定挂载"的核心工具。
- 动态挂载导致不可复现：同一请求两次挂载不同工具，问题难定位。
- 分组粒度过细：场景切换频繁，反而增加维护成本。

# 8. 工具的安全基线

结论先行：安全必须在工具内部实现，而不是依赖模型自觉；鉴权、越权校验、审计、可恢复是四要素。

## 8.1 安全四要素

### 8.1.1 鉴权

确认"是谁在调用"，检查角色与权限。

### 8.1.2 越权校验

确认"这个主体能否操作这个对象"，防止水平越权（访问他人资源）。

### 8.1.3 审计

记录谁、何时、用什么参数、调用了什么工具、结果如何。

### 8.1.4 可恢复

优先软删除、可回滚，为误操作留后路。

## 8.2 完整 Java 示例

```java
@Tool("删除用户数据")
void deleteUserData(@P("用户ID") String userId) {
    SecurityUtils.requireRole("ADMIN");            // ① 鉴权
    if (!SecurityUtils.canAccess(userId)) {        // ② 越权校验
        throw new AccessDeniedException("无权操作");
    }
    auditLog.record(currentUser(), "deleteUserData", userId);  // ③ 审计
    userService.softDelete(userId);                // ④ 软删除（可恢复）
}
```

四要素：**鉴权、越权校验、审计、可恢复**。

## 8.3 边界与坑

- 只在入口校验：绕过 Agent 直接调接口的路径没有防护。
- 审计只在成功时记录：失败的越权尝试同样需要审计。
- 硬删除无备份：不可逆操作应加审批或回收站。

# 9. 工具的可观测

结论先行：工具调用是 Agent 可观测性的重点；没有 Trace，就无法定位"模型为何做错"。

## 9.1 Trace 结构

### 9.1.1 调用链

```
Trace: 用户目标
├── Tool: queryOrder("A123")
│    ├── 参数: {"orderId":"A123"}
│    ├── 耗时: 120ms
│    ├── 状态: SUCCESS
│    └── 结果摘要: {"status":"SHIPPED"}
└── Tool: queryLogistics("SF123")
     ├── 耗时: 340ms
     └── 状态: SUCCESS
```

### 9.1.2 关键字段

| 字段 | 用途 |
|------|------|
| 工具名 | 定位调用了什么 |
| 参数 | 复现问题 |
| 耗时 | 发现性能瓶颈 |
| 状态 | 区分成功/失败 |
| 结果摘要 | 了解模型看到什么 |

## 9.2 Java 埋点

```java
ToolResult execute(ToolCall call) {
    long start = System.nanoTime();
    ToolResult result = dispatch(call);
    long costMs = (System.nanoTime() - start) / 1_000_000;
    tracer.record(ToolSpan.of(call.name(), call.args(), costMs, result));
    return result;
}
```

## 9.3 边界与坑

- 记录完整结果：可能泄露敏感数据，应只记摘要或哈希。
- 缺少父子关系或采样过低：无法还原顺序、故障时无数据可查。

> 工具调用是 Agent 可观测性的重点，详见 `13_Observability/3_agent_trace_and_spans.md`。

# 10. 生产注意事项

结论先行：上线前逐条核对"权限、幂等、超时、结果、错误、数量"六个维度。

## 10.1 风险清单

| 风险 | 建议 |
|------|------|
| 工具无鉴权 | 每个工具内部校验权限 |
| 写操作非幂等 | 幂等键 + 去重 |
| 无超时 | 外部调用必设超时 |
| 结果过大 | 精简 + 截断 |
| 异常裸抛 | 结构化错误 |
| 工具过多 | 按场景裁剪 |

## 10.2 部署检查表

- 每个工具都有清晰的用途、适用、不适用描述。
- 写工具与高风险工具均已实现幂等或审批。
- 所有外部调用设置了超时与重试上限。
- 工具调用已接入 Trace 与监控告警。
- 敏感字段在回填与日志中已脱敏。

# 11. 小结

## 11.1 核心要点

- 工具是 Agent 与外部世界交互的唯一通道。
- 三类工具安全要求递增：只读 < 写 < 高风险。
- 描述决定调用准确率，结果结构决定纠错能力。
- 工具安全四要素：鉴权、越权校验、审计、可恢复。
- 工具调用必须可观测。

## 11.2 落地建议

1. 先写描述再写实现，把"何时用、何时不用"写清楚。
2. 结果一律结构化，并设置长度上限。
3. 错误一律转成模型可读的短句，而非栈信息。
4. 单次挂载工具控制在 10~15 个以内。
