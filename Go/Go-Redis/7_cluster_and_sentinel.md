单机 Redis 有两个绕不过去的问题：容量受限于单机内存，可用性受限于单点故障。主从复制解决读扩展和数据备份，Sentinel 解决自动故障转移，Cluster 解决水平分片。本篇按"主从 → 哨兵 → 集群"的演进顺序讲，重点是客户端怎么配、MOVED/ASK 怎么处理、故障转移期间会发生什么。

# 1. 主从复制

## 1.1 复制模型

```text
        ┌──────────────┐
        │   Master     │  处理写 + 读
        └──────┬───────┘
               │ 异步复制
       ┌───────┴───────┐
       ▼               ▼
 ┌──────────┐    ┌──────────┐
 │ Slave 1  │    │ Slave 2  │  默认只读，分担读流量
 └──────────┘    └──────────┘
```

```bash
# 在从节点执行
REPLICAOF 10.0.0.1 6379
# 或旧命令
SLAVEOF 10.0.0.1 6379
```

★ **关键认知**：主从复制是**异步**的。主节点写完立即向客户端返回成功，再慢慢同步给从节点。这意味着主节点宕机时，还没同步的写会丢失。这是 Redis 无法做到强一致的根本原因，也是 Redlock 争议的源头。

## 1.2 复制过程

```text
1. 从节点连接主节点，发送 PSYNC
2. 主节点执行全量同步：生成 RDB 快照，发送给从节点
3. 从节点加载 RDB
4. 之后主节点把增量写命令通过 replication buffer 持续发给从节点
5. 断线重连时，若 offset 还在 backlog 里，做部分重同步（增量）
```

| 概念 | 作用 |
|------|------|
| `repl_backlog` | 主节点维护的环形缓冲区，支持断线增量同步 |
| offset | 复制进度，主从各自记录 |
| run_id | 主节点标识，变化意味着换了主 |
| 全量同步 | 首次连接或 offset 不匹配时触发，开销大 |

⚠ **关键认知**：全量同步会 fork 子进程生成 RDB，内存翻倍、磁盘 IO 飙升。从节点频繁重连会反复触发全量同步。生产要调大 `repl-backlog-size`，并监控 `master_link_status`。

# 2. Sentinel 哨兵

## 2.1 解决什么问题

主从模式下，主节点挂了需要人工把从节点提升为主。Sentinel 就是自动化的"监控 + 选主 + 通知"：

```text
┌─────────────────────────────────────────┐
│              Sentinel 集群               │
│  ┌────────┐  ┌────────┐  ┌────────┐    │
│  │ sentinel│  │ sentinel│  │ sentinel│  │  互相监控，多数派决策
│  └───┬────┘  └───┬────┘  └───┬────┘    │
└──────┼───────────┼───────────┼──────────┘
       │           │           │
       ▼           ▼           ▼
   ┌────────┐  ┌────────┐  ┌────────┐
   │ Master │  │ Slave1 │  │ Slave2 │
   └────────┘  └────────┘  └────────┘
```

Sentinel 做三件事：

1. **监控**：定期 `PING` 主从节点。
2. **主观下线 / 客观下线**：单个 Sentinel 认为节点挂了是主观下线；达到 quorum 数量认为挂了是客观下线。
3. **故障转移**：选举一个 Sentinel 执行 `SLAVEOF NO ONE`，把从节点提升为主，通知其他节点和新主建立复制。

## 2.2 Go 客户端配置

```go
rdb := redis.NewFailoverClient(&redis.FailoverOptions{
    MasterName:    "mymaster",              // Sentinel 监控的主节点名
    SentinelAddrs: []string{                // 至少给两个，避免单点
        "10.0.0.11:26379",
        "10.0.0.12:26379",
        "10.0.0.13:26379",
    },
    Password:      "secret",                // Redis 密码
    SentinelPassword: "sentinel-secret",    // Sentinel 自己的密码（若有）
    DB:            0,
    PoolSize:      50,
})
```

★ **关键认知**：Sentinel 模式下客户端连的是 **Sentinel 地址**，不是 Redis 地址。客户端先问 Sentinel "主节点是谁"，再连过去。故障转移后，Sentinel 会告诉客户端新主地址，go-redis 自动重连。

## 2.3 故障转移期间会发生什么

```text
时间轴
0s    主节点宕机
      │
      │ 客户端写请求失败（连接断开）
      ▼
5s    Sentinel 主观下线
      │
10s   Sentinel 达到 quorum，客观下线
      │
15s   Sentinel 选出 leader，提升从节点
      │
      │ 客户端仍连着旧主，报错或重试
      ▼
20s   Sentinel 通知客户端新主地址
      │
      ▼
      客户端重连新主，恢复正常
```

⚠ **关键认知**：故障转移期间（通常 10-30 秒）写请求会失败。客户端要配置**重试**和**超时**，业务要能容忍这段时间的写入失败。不要把"Redis 高可用"理解成"零中断"。

# 3. Cluster 集群

## 3.1 分片模型

Cluster 把整个键空间分成 **16384 个槽（slot）**，每个主节点负责一部分槽：

```text
key = "user:1001"
        │
        ▼
  CRC16(key) % 16384 = slot
        │
        ▼
  查槽位表：slot 属于哪个节点
        │
        ▼
  转发到对应节点
```

```text
┌─────────────┐   ┌─────────────┐   ┌─────────────┐
│  Node A     │   │  Node B     │   │  Node C     │
│ slot 0-5460 │   │ 5461-10922  │   │ 10923-16383 │
└──────┬──────┘   └──────┬──────┘   └──────┬──────┘
       │                 │                 │
       ▼                 ▼                 ▼
┌─────────────┐   ┌─────────────┐   ┌─────────────┐
│  Replica A  │   │  Replica B  │   │  Replica C  │
└─────────────┘   └─────────────┘   └─────────────┘
```

```bash
redis-cli --cluster create \
  10.0.0.1:6379 10.0.0.2:6379 10.0.0.3:6379 \
  10.0.0.4:6379 10.0.0.5:6379 10.0.0.6:6379 \
  --cluster-replicas 1
```

## 3.2 槽位与 hash tag

Cluster 只支持 **0 号库**，且多 key 操作要求所有 key 在同一个槽。用 `{}` 指定 hash tag，让标签内的内容参与哈希：

```text
user:{1001}:name     ┐
user:{1001}:profile  ├─ 都按 "1001" 计算槽位，落在同一节点
order:{1001}:items   ┘
```

```bash
CLUSTER KEYSLOT user:{1001}:name   # 查看槽位
CLUSTER INFO                       # 集群状态
CLUSTER NODES                      # 节点列表
```

★ **关键认知**：hash tag 是解决 `CROSSSLOT` 的标准手段，但滥用会让所有 key 挤到一个节点，失去分片意义。只在**确实需要多 key 原子操作**时使用，比如 `{order:1001}` 下的字段。

## 3.3 Go 客户端配置

```go
rdb := redis.NewClusterClient(&redis.ClusterOptions{
    Addrs: []string{
        "10.0.0.1:6379",
        "10.0.0.2:6379",
        "10.0.0.3:6379",
    },
    Password:     "secret",
    PoolSize:     50,              // 每个节点的连接池大小
    MaxRedirects: 3,               // MOVED/ASK 最大重定向次数
    RouteByLatency: true,          // 读请求按延迟选节点
    RouteRandomly:  false,
})
```

★ **关键认知**：Cluster 客户端启动时只需要给**部分节点地址**，它会自动拉取完整的槽位表。给全量地址更稳，但不必强求。⚠ `PoolSize` 是**每个节点**的池大小，3 主 3 从的集群，`PoolSize: 50` 意味着最多 300 条连接。

# 4. MOVED 与 ASK

这两个重定向是 Cluster 最容易让人困惑的地方。

## 4.1 MOVED：槽位永久迁移

```text
客户端 ──GET user:1001──▶ Node A
                          │ slot 属于 Node B
                          ▼
客户端 ◀── -MOVED 3999 10.0.0.2:6379 ── Node A
   │
   └── 更新本地槽位表，重试 Node B
```

- 含义：这个槽**已经永久**属于另一个节点。
- 客户端行为：更新槽位缓存，向新节点重发命令。
- 常见原因：集群扩容/缩容后槽位重新分配。

## 4.2 ASK：槽位正在迁移

```text
客户端 ──GET user:1001──▶ Node A
                          │ 槽正在迁往 Node B，这条 key 已经搬过去了
                          ▼
客户端 ◀── -ASK 3999 10.0.0.2:6379 ── Node A
   │
   └── 发 ASKING 给 Node B，再发原命令（不更新槽位表）
```

- 含义：槽**正在迁移**，这条 key 临时在目标节点。
- 客户端行为：先发 `ASKING`，再发命令，**不更新**槽位缓存。
- 常见原因：集群正在做 resharding。

| 重定向 | 槽位归属 | 客户端动作 | 是否更新缓存 |
|--------|----------|-----------|--------------|
| MOVED | 已永久变更 | 直接向新节点重发 | 是 |
| ASK | 迁移中，临时 | 先 `ASKING` 再重发 | 否 |

★ **关键认知**：用 go-redis 的 `ClusterClient` 时，这两种重定向都由客户端自动处理，业务代码不需要关心。只有用单机客户端连集群时才会频繁看到它们——那本身就是配置错误。

# 5. 故障转移与一致性

## 5.1 Cluster 故障转移

- 每个主节点有从节点，主节点挂了，从节点被提升。
- 需要**多数派主节点**存活，集群才能正常工作（比如 3 主，最多挂 1 主）。
- 故障转移由集群总线投票完成，默认 `cluster-node-timeout` 15 秒。

⚠ **关键认知**：Cluster 的故障转移同样是**异步复制**，主节点挂掉时未同步的写会丢失。而且如果网络分区导致"少数派主节点仍在接受写"，恢复后这些写可能被丢弃。Redis 提供 `min-replicas-to-write` 参数缓解，但无法完全避免。

## 5.2 客户端要配什么

| 配置 | 作用 | 建议 |
|------|------|------|
| `MaxRedirects` | MOVED/ASK 重试上限 | 3-5 |
| `ReadOnly` | 是否允许读从节点 | 可接受旧读时开启 |
| `RouteByLatency` | 按延迟路由读 | 多机房时有用 |
| `PoolSize` | 每节点连接数 | 按单节点 QPS 估算 |
| 超时 | 建连/读写/池等待 | 必须显式设置 |

# 6. 热点 Key

## 6.1 怎么发现

```bash
redis-cli --hotkeys          # 需要 maxmemory-policy 为 LFU
redis-cli --bigkeys          # 找大 key
SLOWLOG GET 10               # 慢查询里反复出现的 key
```

监控上关注：单节点 QPS 明显高于其他节点、单 key 的 `OBJECT FREQ` 很高、网络出口带宽打满。

## 6.2 怎么处理

| 手段 | 说明 |
|------|------|
| 本地缓存 | 热点数据放进程内，减少 Redis 访问 |
| key 拆分 | `hotkey:{1..N}` 分散到多个槽，读时随机选一个 |
| 读写分离 | 热点读走从节点 |
| 限流 | 对极端热点接口做保护 |
| 预分片 | 设计时就按业务维度拆分，避免单 key 承载全量 |

```go
// 读扩散：把热点 key 复制 N 份，读时随机选
func GetHot(ctx context.Context, base string, n int) (string, error) {
    idx := rand.Intn(n)
    key := fmt.Sprintf("%s:%d", base, idx)
    return rdb.Get(ctx, key).Result()
}
```

★ **关键认知**：热点 key 的根因通常是**数据模型设计**——比如把所有配置放一个 Hash、把全站排行榜放一个 ZSet。拆分要在设计阶段做，事后拆成本高得多。

# 7. 三种部署模式对比

| 维度 | 主从 | Sentinel | Cluster |
|------|------|----------|---------|
| 数据分片 | 否 | 否 | 是 |
| 自动故障转移 | 否 | 是 | 是 |
| 容量上限 | 单机内存 | 单机内存 | 多机内存之和 |
| 多 key 操作 | 自由 | 自由 | 需同槽 |
| 客户端 | `NewClient` | `NewFailoverClient` | `NewClusterClient` |
| 运维复杂度 | 低 | 中 | 高 |
| 适用规模 | 小、读多 | 中等、要高可用 | 大容量、高并发 |

# 8. 常见错误与排错

| 现象 | 原因 | 解决 |
|------|------|------|
| `MOVED` 频繁 | 单机客户端连集群 | 换 `NewClusterClient` |
| `CROSSSLOT` | 多 key 不在同槽 | 用 hash tag |
| `CLUSTERDOWN` | 多数派主节点不可用 | 恢复节点，检查网络分区 |
| 写入丢失 | 主从异步复制 | 接受或加业务兜底 |
| 故障转移后连不上 | 客户端缓存了旧地址 | 用 Sentinel/Cluster 客户端自动刷新 |
| 从节点读到旧数据 | 异步复制延迟 | 强一致读走主节点 |
| 扩容后部分 key 报错 | 槽位迁移中 | 客户端处理 ASK，等待迁移完成 |
| 连接数暴涨 | `PoolSize` 按节点翻倍 | 重新估算总连接数 |

⚠ **关键认知**：`CLUSTERDOWN Hash slot not served` 通常不是客户端问题，而是集群槽位没有完全分配（比如 `redis-cli --cluster fix` 没跑完）。先看 `CLUSTER INFO` 里的 `cluster_state` 和 `cluster_slots_assigned`。

# 9. 动手练习

1. 用 Docker 起一主一从，执行 `REPLICAOF`，在主节点写入后在从节点读取，验证复制生效。
2. 用 `CLUSTER KEYSLOT` 查看 `user:1001` 和 `user:{1001}:name` 的槽位，理解 hash tag 的作用。
3. 模拟主节点宕机，观察 Sentinel 或 Cluster 的日志，记录故障转移耗时。

# 10. 小结

| 主题 | 要点 |
|------|------|
| 主从 | 异步复制，读扩展 + 备份，故障需人工 |
| Sentinel | 监控 + 选主 + 通知，客户端连 Sentinel |
| Cluster | 16384 槽分片，只有 0 号库 |
| MOVED | 槽位永久迁移，更新缓存 |
| ASK | 槽位迁移中，临时重定向，不更新缓存 |
| 故障转移 | 有中断窗口，写可能丢失 |
| 热点 Key | 本地缓存、拆分、读写分离 |
