# 2. 高频自检题

## 2.1 基础与连接

**问：`redis.NewClient` 会立即建立连接吗？**

不会。它只构造客户端，真正的连接在第一条命令执行时才建立。所以必须用 `Ping` 探活，不能以 `NewClient` 返回 nil 判断可用。

**问：Context 超时和客户端 `ReadTimeout` 是什么关系？**

两层防线。Context 控制单次调用的总时长；`ReadTimeout` 控制 socket 读操作的时长。只配一个都可能出现"命令挂很久"的情况。

**问：连接池越大越好吗？**

不是。Redis 单线程处理命令，连接过多只增加上下文切换和服务端压力。应先排查慢命令和阻塞命令占用连接，再按 `QPS × 平均耗时` 估算合理池大小。

## 2.2 数据结构

**问：缓存对象用 String 存 JSON 还是 Hash？**

整体读写为主、结构嵌套深 → String + JSON；字段多、经常局部更新 → Hash。Hash 的 `HSET` 只改一个字段，不用全量重写。

**问：ZSet 除了排行榜还能做什么？**

延时队列（score 存到期时间戳）、时间线排序、带权重的去重集合。核心是"分值可以表达任意可排序语义"。

**问：HyperLogLog 能判断某个元素是否存在吗？**

不能。它只做基数估算，不保存原始元素。判断存在性用 Set 或布隆过滤器。

## 2.3 缓存模式

**问：为什么更新数据库后要删缓存而不是更新缓存？**

更新缓存成本高（要算出完整新值），且并发写时到达缓存的顺序可能与数据库相反，导致缓存是旧值。删除让下次读重新加载，天然避免顺序问题。

**问：缓存穿透、击穿、雪崩分别是什么？**

| 概念 | 触发条件 | 核心方案 |
|------|----------|----------|
| 穿透 | 查不存在的数据 | 空值缓存、布隆过滤器 |
| 击穿 | 单个热点 key 失效 | 互斥锁、singleflight |
| 雪崩 | 大量 key 同时失效/Redis 宕机 | TTL 抖动、降级、本地缓存 |

**问：布隆过滤器会误判吗？**

会误判"存在"（假阳性），不会漏判"存在"（假阴性）。所以能安全拦截"一定不存在"的请求。

## 2.4 分布式锁

**问：为什么加锁要用 `SET key value NX EX ttl` 一条命令？**

`SETNX` + `EXPIRE` 是两步，中间崩溃会导致锁永不过期。单条命令原子完成"判断 + 设置 + 过期"。

**问：释放锁为什么用 Lua？**

`GET` 比较 token 和 `DEL` 之间不是原子的，锁可能在这期间过期并被别人拿走。Lua 把两步合成一个原子操作。

**问：锁的 TTL 设多长？**

大于业务最坏执行时间，通常取 2-3 倍。业务本身要有超时，不能依赖无限续期。

**问：Redlock 能保证强一致吗？**

不能完全保证。它依赖多节点时钟和网络假设，GC 停顿、网络分区仍可能破坏互斥。正确性要求高的场景要靠数据库唯一约束、状态机兜底。

## 2.5 批量与原子

**问：Pipeline 是原子的吗？**

不是。它只减少网络往返，命令逐条执行，中途可能插入其他客户端命令，且部分失败不会回滚。

**问：Redis 事务失败会回滚吗？**

不会。执行阶段的错误（如 `WRONGTYPE`）只影响该条命令，其他命令继续执行。需要强原子用 Lua。

**问：Lua 为什么能保证原子？**

Redis 单线程执行脚本，脚本运行期间不处理其他命令。⚠ 但"不被打断"不等于"失败可回滚"。

## 2.6 消息

**问：Pub/Sub 和 Stream 的本质区别？**

Pub/Sub 是即时广播，不持久化，离线订阅者会丢消息；Stream 是持久化日志，支持消费组、ACK、Pending 和回溯。

**问：Stream 怎么保证消息不丢？**

`XREADGROUP` 读取 → 进入 Pending → 处理成功 `XACK` → 移出 Pending。消费者崩溃后，其他消费者用 `XCLAIM` 接管超时消息。

**问：为什么还需要业务幂等？**

Stream 是至少一次投递。"处理成功但 ACK 前崩溃"会导致消息重投，所以业务要用唯一 ID 去重或状态条件保证幂等。

## 2.7 集群

**问：MOVED 和 ASK 的区别？**

MOVED 表示槽位**永久**迁移，客户端更新槽位表；ASK 表示槽位**正在迁移**，客户端先发 `ASKING` 再重发，不更新缓存。

**问：Cluster 为什么不支持多 key 跨槽操作？**

槽位分布在不同节点，跨节点无法在单机内保证原子。需要用 hash tag `{tag}` 让相关 key 落在同一槽。

**问：Sentinel 和 Cluster 怎么选？**

数据量在单机内存内、要高可用 → Sentinel；容量或吞吐超出单机 → Cluster。Cluster 运维复杂度和多 key 限制都更高。

# 3. 本地缓存 + Redis + 数据库

## 3.1 三级读取链路

```text
请求
  │
  ▼
┌─────────────┐  命中   ┌─────────────┐  命中   ┌─────────────┐
│  本地缓存    │ ──────▶ │    Redis    │ ──────▶ │   数据库     │
│ (进程内)     │         │  (共享缓存)  │         │  (最终数据源)│
└─────────────┘         └─────────────┘         └─────────────┘
      ▲                       ▲                       │
      │                       │                       │
      └───────────────────────┴─────── 回填 ──────────┘
```

| 层级 | 延迟 | 容量 | 一致性 | 适用 |
|------|------|------|--------|------|
| 本地缓存 | 纳秒-微秒 | 小（受进程内存限制） | 最弱，需主动失效 | 极热点、配置 |
| Redis | 亚毫秒-毫秒 | 大 | 较强，可集中失效 | 通用缓存 |
| 数据库 | 毫秒-几十毫秒 | 最大 | 最强 | 最终数据源 |

★ **关键认知**：本地缓存的一致性最难保证，因为每个实例各存一份。常用的失效方式是**通过 Redis Pub/Sub 广播失效消息**，各实例收到后删本地 key。这正好是 Pub/Sub "丢了也能恢复"的典型用法——即使某条失效消息丢了，本地缓存也有短 TTL 兜底。

## 3.2 一致性方案

**方案一：先更库，再删 Redis，再广播删本地**

```go
func UpdateUser(ctx context.Context, u *User) error {
    if err := db.UpdateUser(ctx, u); err != nil {
        return err
    }
    key := fmt.Sprintf("user:%d", u.ID)
    rdb.Del(ctx, key)                         // 删共享缓存
    rdb.Publish(ctx, "cache:invalidate", key) // 通知各实例删本地缓存
    return nil
}
```

**方案二：订阅 binlog，异步失效**

数据库变更后由 Canal/Debezium 投递到消息队列，缓存服务消费后删 Redis 和本地缓存。业务代码完全不感知缓存，一致性由数据变更驱动。

**方案三：短 TTL 兜底**

所有缓存都设 TTL，即使某次失效失败，最多脏一个 TTL 周期。这是最简单的兜底，但不能替代主动失效。

| 方案 | 实时性 | 复杂度 | 适用 |
|------|--------|--------|------|
| 更库后删缓存 + 广播 | 秒级 | 低 | 大多数业务 |
| binlog 订阅 | 秒级 | 高 | 多写入口、强一致要求 |
| 短 TTL 兜底 | TTL 级 | 最低 | 所有方案的兜底 |

⚠ **关键认知**：无论哪种方案，都只能做到**最终一致**。真正要求强一致的字段（余额、库存）不要走缓存，直接读库或用数据库事务。缓存的意义是"用可接受的不一致换性能"，不是"假装一致"。

# 4. 生产检查清单

## 4.1 上线前

- [ ] `maxmemory` 已设置，淘汰策略符合业务（纯缓存 `allkeys-lru`/`allkeys-lfu`）。
- [ ] 所有缓存 key 都有 TTL，且 TTL 加了随机抖动。
- [ ] 大 key 已排查（`--bigkeys`），大集合操作用 `SCAN`/`HSCAN`。
- [ ] 客户端是全局单例，配置了连接池、超时、重试。
- [ ] 阻塞命令（`BRPOP`、`XREADGROUP BLOCK`）使用独立客户端。
- [ ] 健康检查区分就绪与存活，Redis 故障时可降级。
- [ ] 分布式锁用 `SET NX EX` + Lua 释放，TTL 大于业务超时。
- [ ] 消息消费有幂等和死信处理。
- [ ] Cluster 多 key 操作使用 hash tag。
- [ ] 慢查询日志已开启，监控接入 Prometheus。

## 4.2 故障预案

| 故障 | 预案 |
|------|------|
| Redis 宕机 | 本地缓存顶一阵、限流、降级读库 |
| 缓存穿透攻击 | 布隆过滤器 + 参数校验 + 限流 |
| 热点 key 打满单节点 | 本地缓存、key 拆分、读写分离 |
| 主从切换 | 客户端自动重连，业务容忍短暂写失败 |
| 内存打满 | 扩容、清理大 key、调整淘汰策略 |
| 消息堆积 | 扩容消费者、监控 Pending、必要时限流生产 |

# 5. 常见认知误区

| 误区 | 纠正 |
|------|------|
| "Redis 单线程所以很慢" | 单线程避免锁竞争，命令本身极快，慢在 O(N) 命令和网络 |
| "加了缓存就一致了" | 缓存只能最终一致，强一致字段不要缓存 |
| "Pipeline 是事务" | Pipeline 只省往返，不保证原子 |
| "Lua 失败会回滚" | Lua 只是不被打断，已执行的命令不会撤销 |
| "分布式锁能保证绝对互斥" | 主从异步复制下仍可能双持锁，正确性靠数据库兜底 |
| "Stream 不会丢消息" | 至少一次投递，需 ACK + 幂等 |
| "连接池越大吞吐越高" | 池过大会增加服务端压力，瓶颈常在慢命令 |
| "Cluster 能随便多 key 操作" | 必须同槽，否则 `CROSSSLOT` |

# 7. 小结

| 主线 | 核心结论 |
|------|----------|
| 连接 | 懒连接、Context 超时、池按并发估算 |
| 结构 | 按访问模式选型，大集合用渐进遍历 |
| 缓存 | Cache Aside 为主，穿透/击穿/雪崩各有对策 |
| 锁 | `SET NX EX` + Lua 释放，业务超时兜底 |
| 原子 | Pipeline 省往返、事务不回滚、Lua 真原子 |
| 消息 | Pub/Sub 广播、Stream 可靠、幂等不可少 |
| 集群 | 主从→Sentinel→Cluster，MOVED/ASK 自动处理 |
| 运维 | 慢查询、内存、连接、监控四件套 |
