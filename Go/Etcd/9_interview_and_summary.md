etcd 的知识点很容易学成散沙：Raft 是 Raft，API 是 API，锁是锁，运维是运维。真正面试和生产里被问到的，往往是它们之间的连接——为什么这个读可能陈旧、为什么这个锁会失效、为什么三个节点看起来都在却不能写。本篇用一张知识地图把这些连接串起来，再给出自检题、检查清单和选型结论。

★ **关键认知**：etcd 的所有应用能力都能回溯到三个原语：**线性一致的读写、带 revision 的 Watch、带 TTL 的 Lease**。锁是 Lease + Txn，服务发现是 Lease + Watch + Prefix，配置中心是 Txn + Watch + Revision。把这三个原语吃透，上层用法都是组合。

# 2. Raft 与一致性自检

## 2.1 基础题

**Q1：3 节点集群挂掉 1 个 Follower，读写正常吗？再挂掉 Leader 呢？**

挂 1 个 Follower 时还剩 2 个节点，达到多数派（2/3），读写正常。再挂掉 Leader 后只剩 1 个节点，不足多数派，既选不出新 Leader，也无法提交写；此时集群不可写，线性一致读也无法完成。必须恢复至少一个节点，让存活数回到 2。

**Q2：为什么 Leader 要等多数派持久化后才能回复客户端成功？**

如果 Leader 只写本地就回复，客户端认为写成功了，但 Leader 随即崩溃，新 Leader 可能没有这条日志。Raft 的选举规则要求候选人日志至少和多数派一样新，因此未复制到多数派的日志可能被覆盖。只有多数派持久化后，这条日志才可能在未来任何合法 Leader 上存在，已提交的写才不会丢。

**Q3：选举超时为什么要随机？**

如果所有 Follower 同时超时，它们会同时变成 Candidate、同时拉票，容易出现平票，然后各自 term + 1 再同时拉票，形成活锁。随机化让大概率只有一个节点先醒来，先拿到多数票成为 Leader，再用心跳压制其他人。

**Q4：为什么生产推荐奇数节点？**

多数派是 `N/2 + 1`。3 节点容忍 1 个故障，4 节点多数派是 3，仍然只能容忍 1 个故障，却多了一台成本和一份复制开销。5 节点容忍 2 个，7 节点容忍 3 个。偶数不增加容错，所以用奇数。

**Q5：Raft 能完全避免脑裂吗？**

Raft 保证同一 term 最多一个 Leader，且任何 Leader 必须获得多数派选票。网络分区时，只有多数派一侧能选出 Leader 并提交日志；少数派一侧无法达到 quorum，不会产生合法的新 Leader。旧 Leader 在失去多数派心跳后会退位。因此不会出现两个都能提交写的 Leader，但可能出现"旧 Leader 短暂以为自己还是 Leader"的窗口，客户端写会被多数派拒绝。

## 2.2 进阶题

**Q6：线性一致读为什么不能直接读 Leader 内存？**

Leader 可能已经被网络分区隔离，但它本地还有旧数据，且不一定知道自己已经不是 Leader。直接读内存会返回过期值。etcd 的 ReadIndex 流程是：记录当前 commitIndex，向多数派发一轮心跳确认自己仍被认可，再等本地状态机 apply 到该 index，最后返回。这样读和写一样，都要经过多数派确认。

**Q7：`WithSerializable()` 牺牲了什么？**

它允许从本地成员的状态机直接读，不经过 Leader 的多数派确认。好处是延迟低、可以分担读压力；代价是可能读到落后于最新提交的状态，尤其是在 Follower 上。它适合监控、批量扫描、可容忍陈旧的场景，不适合锁、CAS、服务发现的关键读。

**Q8：Revision 和 Raft log index 是一回事吗？**

不是。Raft log index 是日志条目的位置，包含配置变更、租约操作等非 key-value 日志；Revision 是 MVCC 键空间的逻辑版本，只在 key-value 事务提交时递增。一次 Raft 提交可能不对应一次 revision 增长，二者不能混用。

**Q9：Watch 能不能当作可靠消息队列？**

不能。etcd 只保留压缩点之后的历史，Watch 断线时间超过保留窗口就会 `ErrCompacted`；事件也可能在重连后重复投递。它适合"状态变更通知"，不适合"必须逐条消费、不能丢"的消息场景。可靠队列要用 Kafka 这类系统。

**Q10：集群失去多数派后，已经提交的数据还在吗？**

在。已提交的数据已经写入多数派磁盘，恢复多数派后仍然存在。失去多数派期间不能写、不能完成线性一致读，但数据不会因为"不可用"而消失。真正会丢数据的是磁盘损坏、未备份的灾难，以及把未提交日志误当成已提交。

# 3. API、锁与运维自检

## 3.1 API 与 Watch

**Q11：`Get("/service")` 和 `Get("/service/")` 有什么区别？**

etcd 的 `WithPrefix()` 是字节前缀匹配。`/service` 会匹配 `/service`、`/service2/x`、`/service/order`；`/service/` 只匹配带斜杠的子路径。服务发现必须统一使用带尾斜杠的前缀，避免跨服务误匹配。

**Q12：为什么 CAS 用 `ModRevision` 而不是 `Version`？**

`Version` 是单个 key 的修改次数，key 被删除后重建会从 1 重新开始，可能出现 ABA：旧读到的 Version 与重建后的 Version 相同，CAS 误判为没变。`ModRevision` 是全局单调递增的，每次写入都不同，能可靠区分"同一个值的不同生命周期"。

**Q13：Put 返回超时，能不能直接重试？**

不能假设没写成功。请求可能已经在 Leader 提交，只是响应丢失。重试前要保证幂等：同样的 key/value 覆盖通常安全；扣减、创建、追加这类操作必须用 Txn + revision 做条件写，或者用业务唯一键去重。

**Q14：先 Get 再 Watch，为什么要用 `Get` 的 revision + 1？**

Get 返回的是 revision R 的快照，Watch 从 R+1 开始才能覆盖"Get 之后、Watch 建立之前"发生的所有写入。`WithRev(0)` 从 Watch 建立时的当前 revision 开始，会漏掉这段窗口里的事件。

**Q15：Watch 报 `CompactRevision` 怎么办？**

说明起点历史已经被压缩，无法回放。正确流程是：重新 Get 全量，重建本地状态，拿到新 revision，再从 `revision + 1` 重新 Watch。生产上把自动压缩保留时间设得比最长断线时间长，减少这种情况。

## 3.2 分布式锁

**Q16：为什么锁的 value 要用唯一 token？**

锁可能因为 TTL 到期而被别人重新持有。释放时如果直接 `Delete(key)`，会删掉别人的锁。唯一 token 让持有者在删除前用 Compare 确认"这把锁还是我的"。

**Q17：etcd 公平锁为什么按 CreateRevision 排队？**

每个等待者创建自己的 key，CreateRevision 是全局单调递增的，天然反映到达顺序。只让排第一的持锁、排第 N 的 Watch 排第 N-1 的 key，就能做到 FIFO 且避免惊群。

**Q18：锁没过期，业务一定安全吗？**

不一定。进程可能发生长时间 GC、网络分区或系统挂起，租约在服务端已经过期，客户端却还没意识到。另一个客户端可能已经拿到锁并开始写。正确性要靠 fencing token（如锁 key 的 CreateRevision）在资源端拒绝旧持有者。

**Q19：etcd 锁和 Redis 锁最本质的差异是什么？**

etcd 锁的加锁、续期、释放都经过 Raft 多数派，故障切换后不会出现"锁状态丢失但客户端以为还持有"的异步复制窗口；Redis 主从异步复制在故障切换时可能丢锁。代价是 etcd 延迟更高、吞吐更低。两者都不能替代资源端的幂等与 fencing。

**Q20：`concurrency.Mutex` 可重入吗？**

不可重入。同一个 Session 对同一个 mutex 再次 `Lock` 会创建第二个排队 key，然后等自己释放，形成死锁。需要嵌套加锁时，应改造代码避免重入，或自行实现带计数的可重入协议。

# 4. 生产检查清单

## 4.1 部署

| 检查项 | 标准 |
|--------|------|
| 节点数 | 3 或 5，奇数，跨机架/可用区 |
| 磁盘 | SSD/NVMe，fsync P99 < 10ms，独立于日志盘 |
| 时间 | 所有节点启用 NTP/chrony |
| 端口 | 2379 客户端、2380 peer，防火墙双向放行 |
| TLS | client 与 peer 都开启，证书 SAN 覆盖所有地址 |
| 身份 | name、initial-cluster、token 三节点一致 |
| 资源 | `LimitNOFILE >= 65536`，内存足够映射 DB |
| 版本 | 集群内版本一致，升级逐个节点进行 |

## 4.2 客户端

| 检查项 | 标准 |
|--------|------|
| 连接 | 进程内单例，`defer cli.Close()` |
| 超时 | 每次 RPC 都有 context deadline |
| 重试 | 只重试可重试错误，写操作必须幂等 |
| Watch | 每服务一个 Watch，回调只入队 |
| 恢复 | 处理 `Canceled` 与 `CompactRevision`，能全量重建 |
| 一致性 | 关键读不用 `WithSerializable()` |
| 租约 | 每租约一个 KeepAlive 协程，消费通道直到关闭 |
| 大小 | value 控制在 KB 级，注意 gRPC 消息上限 |

## 4.3 监控与备份

| 检查项 | 标准 |
|--------|------|
| Leader | `etcd_server_has_leader == 1`，变更次数有告警 |
| 磁盘 | WAL fsync、backend commit P99 有阈值 |
| 容量 | DB 使用率 70% 预警、90% 告警 |
| 提案 | `proposals_failed_total` 持续为 0 |
| Watch | 数量突增有告警，排查客户端泄漏 |
| 备份 | 每日快照，异地保存，保留 7-30 天 |
| 验证 | 每周 `snapshot status`，每季度真实恢复演练 |
| 空间 | 自动 compact + 定期 defrag，NOSPACE 有 runbook |
| 权限 | 开启 RBAC，客户端最小权限 |
| 文档 | 成员变更、恢复、故障演练都有操作手册 |

★ **关键认知**：etcd 的可用性不是"进程活着"，而是"多数派可通信 + 磁盘可 fsync + 有 Leader"。监控要覆盖这三件事，而不是只看端口和 CPU。CPU 很低的 etcd 也可能因为磁盘 fsync 慢而完全不可写。

# 5. 选型总结

## 5.1 etcd、Redis、ZooKeeper 对比

| 维度 | etcd | Redis | ZooKeeper |
|------|------|-------|-----------|
| 一致性 | Raft，强一致 | 主从异步，故障可能丢写 | ZAB，强一致 |
| 数据模型 | 扁平 KV + MVCC | 丰富数据结构 | 树形 znode |
| Watch | 长期流，可按 revision 续订 | Pub/Sub/Stream，语义不同 | 一次性 watcher |
| 临时节点 | Lease | TTL | 会话临时节点 |
| 性能 | 中低，写要多数派落盘 | 高 | 中 |
| 容量 | 小，GB 级 | 大，内存级 | 小 |
| 典型用途 | K8s、配置、选主、锁 | 缓存、计数、会话、轻量锁 | 传统协调、Hadoop/Kafka |
| 运维 | 奇数节点、磁盘敏感 | 相对简单 | 较重，需理解会话 |

## 5.2 决策树

```text
需要强一致的协调数据吗？
  ├── 否 → Redis 缓存/计数/会话
  └── 是
       ├── 已经在 Kubernetes 里？
       │     ├── 是 → 优先用 K8s Service/ConfigMap/Lease
       │     └── 否 → 继续
       ├── 需要高频读写、可容忍极小概率失效？
       │     ├── 是 → Redis + 业务幂等
       │     └── 否 → etcd
       └── 团队已有 ZooKeeper 且生态绑定？
             ├── 是 → 继续用 ZooKeeper
             └── 否 → etcd
```

## 5.3 常见误区

| 误区 | 纠正 |
|------|------|
| etcd 可以当缓存 | 写放大、容量小，吞吐远低于 Redis |
| 强一致等于高可用 | 失去多数派时强一致系统会拒绝服务 |
| 节点越多越稳 | 节点越多写延迟越高，3 或 5 足够 |
| Watch 是可靠队列 | 历史会压缩，事件可能重复 |
| 有锁就绝对安全 | 停顿与分区会导致双持锁，需要 fencing |
| 备份文件存在就行 | 没验证、没演练的备份不可信 |
| 删除 key 就释放空间 | 需要 compact + defrag |
| 调大 quota 就解决 NOSPACE | 还要 compact、defrag、disarm |

⚠ **关键认知**：不要因为 etcd 强一致就把它当成所有协调问题的默认答案。选型先看数据规模、访问频率和一致性要求，再考虑团队是否愿意承担奇数节点、磁盘和备份的运维成本。

# 6. 学习路径

如果你刚接触 etcd，建议按下面的顺序练习：

1. 单机启动，用 `etcdctl` 完成 Put/Get/Delete/Watch。
2. 起三节点集群，故意停一个节点，观察 `endpoint health` 与选主日志。
3. 用 Go 客户端实现带 Lease 的服务注册与发现。
4. 用 Txn 实现 CAS，跑并发测试观察冲突与重试。
5. 用 `concurrency.Mutex` 实现公平锁，验证排队顺序。
6. 做一次快照备份 + 隔离环境恢复。
7. 制造 NOSPACE，走一遍 compact + defrag + disarm。
8. 把上述步骤写成 runbook，做一次故障演练。

★ **关键认知**：etcd 最难的不是 API，而是**边界感**：知道它适合存什么、知道一致性要付出什么代价、知道故障时它会怎么表现。把这三件事想清楚，比记住十个参数更有价值。

# 7. 小结

| 主题 | 结论 |
|------|------|
| 本质 | 基于 Raft 的强一致 KV，核心原语是读写、Watch、Lease |
| 一致性 | 写要多数派持久化；默认读线性一致，串行化读可能陈旧 |
| 数据 | 扁平 key、全局 revision、MVCC，历史会被压缩 |
| 协调 | Lease 管生命周期，Txn 管原子条件写，Watch 管变更 |
| 锁 | Lease + Txn + 排队，正确性最终靠 fencing |
| 发现 | 实例 ID 做 key，租约保活，前缀 + Watch 感知 |
| 配置 | current/versions 分离，Txn 原子发布，灰度用稳定分流 |
| 运维 | 奇数节点、SSD、备份验证、compact/defrag、监控三件事 |
| 选型 | 强一致协调选 etcd，高频缓存选 Redis，已有 ZK 生态可沿用 |

到这里，Go/Etcd 模块的九篇笔记就结束了。下一步建议把第 6、7 篇的代码合并成一个小型注册中心，再补上 Prometheus 指标和快照脚本，形成一个可以真正跑起来的练习项目。
