逃逸分析（escape analysis）和内联（inlining）是 Go 编译器最重要的两项优化。逃逸分析决定变量放栈还是堆（直接影响 GC 压力），内联消除函数调用开销。理解它们，才能真正写出高性能的 Go 代码。

# 1. 逃逸分析是什么

## 1.1 核心问题

★ **关键认知**：Go 编译器需要决定每个变量分配在**栈**还是**堆**。栈分配快但函数返回就失效，堆分配慢但生命周期灵活。**逃逸分析**就是编译期的静态分析，判断"变量的生命周期是否超出函数作用域"：

```
变量逃逸到堆，当：
1. 函数返回了指向局部变量的指针
2. 变量被闭包捕获
3. 变量被赋值给接口类型
4. 变量太大，栈放不下
5. 变量的生命周期无法在编译期确定
```

## 1.2 经典逃逸场景

```go
// 场景1：返回局部变量的指针 → 逃逸
func newInt() *int {
    x := 42
    return &x      // x 逃逸到堆（函数返回后仍需存活）
}

// 场景2：闭包捕获 → 逃逸
func counter() func() int {
    count := 0
    return func() int {
        count++     // count 被闭包捕获，逃逸到堆
        return count
    }
}
```

★ **关键认知**：逃逸分析**是编译期行为**，通过静态分析代码，判断变量能否安全地留在栈上。`newInt` 里的 `x` 如果不逃逸，本来可以放栈上；但因为返回了指针，必须移到堆上由 GC 管理。

# 2. 如何观察逃逸分析

## 2.1 go build -gcflags="-m"

★ **关键认知**：用 `-gcflags="-m"` 让编译器打印逃逸分析结果：

```bash
go build -gcflags="-m" main.go
# 输出示例：
# ./main.go:5:2: moved to heap: x        ← x 逃逸到堆
# ./main.go:10:2: can inline newInt      ← 函数可被内联
```

```
-m    打印一级逃逸分析结果
-m -m 打印更详细的逃逸分析（包括内联决策）
```

## 2.2 逃逸的判定示例

```go
func main() {
    x := 42
    fmt.Println(x)     // x 是否逃逸？
    // 输出：x escapes to heap —— 因为 Println 参数是 interface{}，x 被装箱逃逸
}
```

★ **关键认知**：`fmt.Println(x)` 导致 x 逃逸，是因为 `Println` 接受 `...interface{}`，把 x 装箱成接口，而接口可能被持有，编译器无法保证安全，只能让它逃逸。这也是"调试打印会引入逃逸"的常见现象。

# 3. 逃逸分析的影响

## 3.1 性能影响

★ **关键认知**：逃逸直接决定性能，因为它决定了一个对象是否受 GC 管理：

```
栈上分配（不逃逸）：
  - 分配/释放零成本（栈指针移动）
  - 无 GC 压力
  - 高缓存局部性

堆上分配（逃逸）：
  - 走分配器（mcache 等）
  - 需要 GC 扫描和回收
  - 对象可能分散，缓存不友好
```

★ **关键认知**：减少逃逸是 Go 性能优化的核心手段。一个高频调用的函数，如果每个局部变量都逃逸到堆，GC 压力会显著上升，性能下降。

## 3.2 如何减少逃逸

```
1. 避免返回局部变量的指针（改为返回值）
2. 避免用 interface{} 传递具体类型（用泛型或具体类型）
3. 避免闭包捕获不必要的变量（改为传参）
4. 小对象用值传递而非指针
```

# 4. 内联优化

## 4.1 内联是什么

★ **关键认知**：内联（inlining）是把**函数调用替换为函数体本身**，消除调用开销：

```go
func add(a, b int) int { return a + b }

// 内联前：
c := add(1, 2)      // 需要：压栈参数、跳转、返回

// 内联后（编译器展开）：
c := 1 + 2          // 直接计算，无调用开销
```

## 4.2 内联的好处

★ **关键认知**：内联不只是省掉调用开销，更重要的是**开启了进一步优化**：

```
1. 消除函数调用开销（栈帧、跳转）
2. 让调用处的上下文参与优化（如常量折叠、死代码消除）
3. 内联后可能让原本逃逸的变量不再逃逸（这是内联与逃逸的联动）
```

## 4.3 内联的规则

★ **关键认知**：Go 编译器对可内联函数有限制（避免代码膨胀）：

```
1. 函数体较小（约 80 个节点以内的简单函数）
2. 不含 defer、recover、闭包等复杂结构
3. 不含循环（旧版限制，新版本放宽）
```

```
观察内联：
go build -gcflags="-m -m" | grep "inlining"
# 输出：can inline add
```

★ **关键认知**：`mid-stack inlining`（Go 1.9+）允许内联"调用链中间"的函数，让内联更激进。内联让原本会逃逸的变量留在栈上，是"内联-逃逸"联动的经典例子。

# 5. 内联与逃逸的联动

★ **关键认知**：内联和逃逸分析**相互促进**——内联后，函数体融入调用处，原本"因返回指针而逃逸"的变量可能就留在栈上了：

```go
func newInt() *int {
    x := 42
    return &x
}

// 如果 newInt 被内联到调用处：
func main() {
    x := 42        // 内联后，x 直接是 main 的局部变量
    p := &x        // p 指向栈上的 x，不逃逸！
    use(p)
}
```

★ **关键认知**：这是编译器优化的"协同效应"——单一优化效果有限，多项优化叠加才能发挥威力。理解这种联动，能更好地预测代码的实际性能。

# 6. 其他编译优化

★ **关键认知**：除逃逸分析和内联，Go 编译器还有这些优化：

```
1. 死代码消除（dead code elimination）：移除不可达代码
2. 常量折叠（constant folding）：编译期计算常量表达式
3. 强度削减（strength reduction）：乘除换成移位等
4. 边界检查消除（bounds check elimination）：安全的切片访问省去检查
5. 去虚拟化（devirtualization）：接口调用转直接调用
```

# 7. 实践建议

★ **关键认知**：基于逃逸分析和内联的实践建议：

```
1. 不要过早优化：先写清晰的代码，再用 pprof 定位热点
2. 热点函数用 -gcflags="-m" 检查逃逸
3. 热路径避免 interface{} 和反射
4. 小函数保持简单，便于内联
5. 用 go test -bench 基准测试验证优化效果
```

# 8. 小结

| 概念 | 要点 |

| 观察 | -gcflags="-m" |
| 内联 | 消除调用开销，开启优化 |
