Go 的运行时（runtime）是隐藏在每行代码背后的核心引擎：调度器、栈管理、GC、内存分配都由它负责。其中 **GMP 调度模型**是理解 Go 并发的钥匙——goroutine 之所以能"百万级"运行，全靠这套精巧的用户态调度。

# 1. 运行时概览

## 1.1 runtime 的职责

★ **关键认知**：Go 每个可执行文件都内置了一个完整的运行时，负责：

```
1. 调度：管理 goroutine 在 OS 线程上的调度（GMP）
2. 内存：堆内存分配、栈管理
3. GC：垃圾回收
4. channel、map、slice 等内建类型的底层实现
5. panic/recover、定时器、网络轮询（netpoll）
```

这也是 Go 二进制文件较大的原因——整个运行时被静态链接进程序。

# 2. GMP 调度模型

## 2.1 三个核心概念

★ **关键认知**：Go 调度器围绕三个对象运转：

```
G（Goroutine）：一个 goroutine，包含栈、状态、要执行的函数
M（Machine）：一个 OS 线程，是真正执行代码的内核线程
P（Processor）：逻辑处理器，持有"本地运行队列"，是调度的核心
```

```
GMP 关系示意：
        ┌─────────────┐
        │      M      │  OS 线程（内核调度）
        │  ┌───────┐  │
        │  │   P   │  │  逻辑处理器（用户态调度）
        │  │ ┌───┐ │  │
        │  │ │ G │ │  │  goroutine
        │  │ └───┘ │  │
        │  │  ...  │  │
        │  └───────┘  │
        └─────────────┘
```

★ **关键认知**：P 的数量由 `GOMAXPROCS` 决定（默认等于 CPU 核数）。每个 P 维护一个**本地运行队列**（local run queue），存放待运行的 goroutine。M 必须**绑定一个 P** 才能执行 G。

## 2.2 调度流程

★ **关键认知**：调度器的核心循环是"找 G → 执行 G → 再次找 G"：

```
1. M 绑定 P，从 P 的本地队列取 G 执行
2. 本地队列空 → 从全局队列（global run queue）取
3. 全局也空 → 从其他 P 偷取（work stealing 工作窃取）
4. 都空 → M 进入休眠，P 等待新 G
```

## 2.3 工作窃取（work stealing）

★ **关键认知**：当某个 P 的本地队列空了，它会**从其他 P 的队列尾部偷取一半的 G**：

```
P1: [G1][G2][G3][G4]      P2（空闲）: []
                              ↓ 窃取
P1: [G1][G2]              P2: [G3][G4]
```

★ **关键认知**：工作窃取是 Go 调度器实现**负载均衡**的机制，让空闲的处理器能"偷"到工作，避免某些 P 忙死、某些 P 闲死。这保证了多核利用率和调度公平性。

# 3. 调度触发时机

★ **关键认知**：goroutine 在以下时机被切换（调度点）：

```
1. 主动让出：runtime.Gosched()、channel 阻塞、锁阻塞
2. 系统调用：阻塞型系统调用会解绑 P，让 P 去跑其他 G
3. 抢占式调度：Go 1.14+ 基于信号的抢占
```

## 3.1 系统调用的处理

★ **关键认知**：当一个 goroutine 发起阻塞型系统调用（如读文件），调度器会：

```
1. M 携带 G 进入系统调用（阻塞）
2. 该 M 解绑 P（P 可以被其他 M 接管）
3. 其他 M 绑定这个 P，继续执行 P 队列里的 G
4. 系统调用返回后，G 重新排队，M 尝试重新绑定 P
```

★ **关键认知**：这个"系统调用时解绑 P"的设计，保证了**一个阻塞的系统调用不会拖垮整个 P 上的其他 goroutine**——这是 Go 在网络 I/O 密集场景高性能的关键。而网络 I/O 更进一步，用 netpoll（非阻塞 I/O + 事件循环）实现，goroutine 根本不会真正阻塞在系统调用上。

# 4. goroutine 的栈管理

## 4.1 栈的初始大小与增长

★ **关键认知**：goroutine 的栈**初始只有 2KB**，且可以**动态增长**（最大可达 GB 级）：

```
栈增长策略：
1. 栈从 2KB 开始
2. 函数调用需要更多栈空间时，若不足则触发"栈扩容"
3. 扩容时分配一块更大的栈（通常是 2 倍），把旧栈内容拷贝过去
4. 栈空间剩余过多时，也会"收缩"
```

## 4.2 栈的连续性

★ **关键认知**：Go 1.3 前使用"分段栈"（split stack），后来改为**连续栈**（contiguous stack）——栈扩容时整体拷贝到更大的连续内存。连续栈避免了分段栈的"热分裂"性能问题（反复在栈边界跨越导致频繁扩容）。

★ **关键认知**：栈拷贝时，所有**指向栈上变量的指针**都必须更新（因为它们指向的地址变了）。Go 通过**精确的栈扫描**（记录哪些寄存器/栈槽是指针）实现指针调整，这是 Go 与 C 的关键区别——C 无法移动栈，因为无法精确追踪指针。

# 5. 抢占式调度

## 5.1 从协作式到抢占式

★ **关键认知**：Go 的调度抢占经历了一个重要演进：

```
Go 1.14 之前：协作式抢占
  - goroutine 只在"调度点"（函数调用等）才会让出 CPU
  - 问题：一个没有函数调用的死循环会独占 CPU，导致调度器无法介入

Go 1.14+：基于信号的抢占
  - 运行时定期向线程发送信号（SIGURG）
  - 收到信号的 goroutine 让出 CPU，调度器可以抢占
  - 解决了"死循环饿死其他 goroutine"的问题
```

★ **关键认知**：抢占式调度是 Go 1.14 的重要改进，解决了长期存在的"忙循环导致调度延迟"问题。但注意：Go 的抢占是**异步安全的**（只在安全点抢占），不像操作系统那样硬抢占，因此 goroutine 切换成本极低。

# 6. GOMAXPROCS

★ **关键认知**：`GOMAXPROCS` 决定 P 的数量，即**最多同时并行执行的 goroutine 数**：

```go
runtime.GOMAXPROCS(0)   // 查询当前值（默认 = CPU 核数）
runtime.GOMAXPROCS(4)   // 设置为 4
```

★ **关键认知**：默认等于 CPU 核数是最佳实践——过少浪费多核，过多增加调度和缓存竞争。容器场景需注意：Go 1.6+ 默认用 `runtime.NumCPU()`，但容器可能限制了 CPU 配额，导致 GOMAXPROCS 设置过大，Go 1.21 起已能感知 cgroup 限制。

# 7. 小结

| 概念 | 要点 |
|------|------|
| GMP | G=goroutine, M=线程, P=逻辑处理器 |
| GOMAXPROCS | P 的数量，默认 CPU 核数 |
| 工作窃取 | 空闲 P 偷取其他 P 的 G |
| 系统调用 | 阻塞时解绑 P，不影响其他 G |
| 栈管理 | 2KB 起，连续栈动态增长 |
| 抢占 | 1.14+ 信号抢占，解决忙循环饿死 |
