垃圾回收（GC）是 Go 内存管理的核心，也是"Go 有 GC 却仍能胜任服务端高性能"的关键技术。Go 从早期的"stop-the-world"演进到如今的**并发三色标记 + 混合写屏障**，实现了极低的停顿时间。这一章深入 GC 的算法、机制与调优。

# 1. GC 的演进历史

★ **关键认知**：Go 的 GC 经历了四次重大演进，核心目标始终是**降低停顿时间**：

```
Go 1.3 之前：标记-清除（STW，停顿时间随堆大小增长，秒级）
Go 1.5    ：并发三色标记（引入写屏障，停顿大幅下降）
Go 1.8    ：混合写屏障（消除了重新扫描栈的 STW）
Go 1.9+   ：持续优化，停顿时间稳定在亚毫秒级
```

★ **关键认知**：Go 的 GC 设计哲学是"**低停顿优先**"——宁可吞吐量略降，也要把停顿控制在亚毫秒级。这正契合了服务端应用"对延迟敏感"的需求，是 Go 敢于用 GC 做高并发服务的底气。

# 2. 标记-清除算法基础

## 2.1 三色标记法

★ **关键认知**：Go GC 的核心算法是**三色标记**，用颜色区分对象状态：

```
白色：尚未扫描（可能是垃圾）
灰色：已扫描到，但它的引用还没扫描完
黑色：已扫描，且它引用的对象都已处理
```

## 2.2 标记流程

```
三色标记步骤：
1. 初始：所有对象标记为白色
2. 从根对象（全局变量、栈、寄存器）出发，把根标记为灰色
3. 遍历灰色对象，把其引用的白色对象标灰，自身标黑
4. 重复直到没有灰色对象
5. 剩余的白色对象 = 不可达 = 垃圾，可回收
```

★ **关键认知**：标记过程本质是**从根出发的图遍历**（可达性分析）。遍历完成后，所有"从根可达"的对象是黑色（存活），不可达的是白色（垃圾）。

# 3. 并发标记与写屏障

## 3.1 并发标记的问题

★ **关键认知**：如果 GC 标记和用户代码**并发执行**，会出现"对象引用关系在标记过程中变化"的问题：

```
错误场景：
1. GC 扫描完 A，A 引用 B，A 标黑
2. 用户代码此时修改：A 不再引用 B，而 C 新建了指向 B 的引用
3. B 在标记阶段后仍为白色（被误判为垃圾）→ 回收后 C 引用失效 → 崩溃
```

## 3.2 写屏障（write barrier）

★ **关键认知**：**写屏障**是解决并发标记正确性的关键——在用户代码**写入指针**时插入一段额外代码，保证标记的正确性：

```
写屏障的作用：当用户代码修改对象引用时，记录这次修改，
确保被引用的对象不会被误判为垃圾。

Go 1.8 混合写屏障的核心思想：
1. 栈上的写入不需要屏障（栈是灰色，稍后整体扫描）
2. 堆上写入时，把被引用的对象标记为灰色
```

★ **关键认知**：写屏障让 GC 能在用户代码并发运行的同时安全标记，这是"并发 GC"能实现的前提。代价是每次指针写入都有轻微开销——这也是 Go 指针写操作比 C 略慢的原因之一。

# 4. GC 的四个阶段

★ **关键认知**：Go GC 一个周期分四个阶段：

```
1. 标记准备（STW）：启动写屏障，小停顿
2. 标记（并发）：三色标记，与用户代码并发，主要耗时阶段
3. 标记终止（STW）：停止写屏障，计算清扫任务
4. 清扫（并发）：回收白色对象的内存
```

★ **关键认知**：只有**阶段 1 和 3** 需要 STW（stop-the-world），且这两个停顿极短（微秒到毫秒级）。真正耗时的标记和清扫都与用户代码并发执行。这就是 Go GC 停顿低的原因。

# 5. GC 触发时机

## 5.1 三种触发方式

★ **关键认知**：GC 的触发有三种：

```
1. 堆内存增长：新分配内存达到阈值（默认：堆扩大一倍）时触发
2. 定时触发：超过 2 分钟未 GC 则强制触发
3. 手动触发：runtime.GC()（生产环境不建议）
```

## 5.2 GOGC 调优

★ **关键认知**：`GOGC` 是 GC 最核心的调优参数，控制"堆增长多少触发一次 GC"：

```
GOGC 默认 100（百分比）：
  - 堆内存增长到上一次 GC 后存活内存的 2 倍时，触发 GC
  - GOGC=100：堆翻倍触发
  - GOGC=200：堆 3 倍触发（GC 更少，内存占用更高）
  - GOGC=off：关闭自动 GC（危险，慎用）
```

★ **关键认知**：`GOGC` 是**内存与 CPU 的权衡**——调高 GOGC 减少 GC 频率（省 CPU），但占用更多内存；调低 GOGC 频繁 GC（省内存），但消耗 CPU。调优方向取决于应用是 CPU 敏感还是内存敏感。

# 6. 观察 GC 运行

## 6.1 gctrace 日志

```go
// 设置环境变量 GODEBUG=gctrace=1 运行程序
// 输出示例：
// gc 1 @0.004s 0%: 0.018+1.3+0.008 ms clock, 0.14+0.18/1.2/0.013+0.068 ms cpu, 4->4->0 MB, 5 MB goal, 8 P
```

★ **关键认知**：gctrace 输出各字段含义：

```
gc 1         第 1 次 GC
@0.004s      程序启动后 0.004 秒
0%           CPU 时间占比
0.018+1.3+0.008 ms   STW 标记准备 + 并发标记 + STW 标记终止
4->4->0 MB   GC 前堆 → GC 后堆 → 存活堆
5 MB goal    本次 GC 的目标堆大小
```

## 6.2 runtime/metrics 与 pprof

```
1. runtime/metrics：Go 1.16+ 的官方 GC 指标接口
2. pprof：go tool pprof 分析内存分配热点（见测试章节）
```

# 7. 减少 GC 压力的实践

★ **关键认知**：降低 GC 压力的核心是"**减少堆上分配**"：

```
1. 复用对象：sync.Pool 复用临时对象
2. 减少指针：值类型、切片替代指针切片（指针越多 GC 扫描越慢）
3. 预分配：make 时预分配容量，避免频繁扩容
4. 减少字符串拼接：用 strings.Builder
5. 逃逸分析：让短命对象尽量留在栈上（见逃逸分析章节）
```

★ **关键认知**：GC 的成本和"堆上的对象数量"（尤其是指针数量）成正比。让对象分配在栈上（逃逸分析）、复用对象（sync.Pool）、减少指针，是降低 GC 压力的三大方向。
