前面八篇分别讲了架构、客户端、生产者、消费者、offset、投递语义、Schema 和运维。这一篇不再引入新概念，而是把散落的经验收束成几条能直接落地的规则：消息怎么设计、失败怎么重试、顺序怎么保证、容量怎么估、上线前检查什么。最后用一组自检题帮你找出还没吃透的地方。

# 1. 消息设计

## 1.1 事件信封

不要只发业务字段，给每条消息一个稳定的信封：

```go
type Event struct {
    ID         string          `json:"id"`          // 全局唯一，消费端幂等键
    Type       string          `json:"type"`        // 如 order.created
    Version    int             `json:"version"`     // 事件结构版本
    OccurredAt time.Time       `json:"occurred_at"` // 事件发生时间，不是发送时间
    Producer   string          `json:"producer"`    // 来源服务，便于排查
    TraceID    string          `json:"trace_id"`    // 全链路追踪
    Data       json.RawMessage `json:"data"`        // 具体业务载荷
}
```

信封带来的好处：

- **幂等**：消费端用 `ID` 去重，不依赖 offset。
- **路由**：按 `Type` 分发给不同 handler。
- **演进**：`Version` 支持新旧结构并存。
- **排障**：`Producer` 和 `TraceID` 能快速定位问题链路。

★ **关键认知**：`OccurredAt` 和消息的 Broker 时间戳不是一回事。Broker 时间戳是写入时间，业务时间戳是事件真正发生的时间。做延迟统计、补偿、乱序判断时，必须用业务时间戳。

## 1.2 key 的选择

| key | 效果 | 风险 |
|-----|------|------|
| 订单 ID | 同订单事件有序 | 大订单可能热点 |
| 用户 ID | 同用户事件有序 | 活跃用户热点 |
| 无 key | 均匀分布 | 无序 |
| 固定字符串 | 全局有序 | 单分区，吞吐受限 |

key 要同时满足"有业务意义"和"分布均匀"。如果某个 key 特别热，可以考虑 `tenantID:orderID` 这种复合 key，把顺序性缩小到更细的粒度。

⚠ **关键认知**：给 key 加随机后缀能打散热点，但会破坏"同 key 同分区"的顺序性。只有当你确认不需要顺序、只需要均匀分布时，才能这么做。

## 1.3 大小与保留

- 单条消息建议控制在 100KB 以内，Broker 默认上限是 1MB（`message.max.bytes`）。
- 大文件不要塞进 Kafka，存对象存储，消息里放 URL 或 ID（claim check 模式）。
- 元数据放 headers，不要重复塞进 payload。
- 保留时间按"最长重放窗口"设计，不要无限保留。

# 2. 可靠性与重试

## 2.1 重试策略

只重试可重试错误：网络超时、leader 切换、副本不足。消息过大、Topic 不存在、序列化失败重试多少次都没用。

```go
func backoff(attempt int) time.Duration {
    base := 100 * time.Millisecond
    d := base * time.Duration(1<<attempt) // 指数退避
    if d > 30*time.Second {
        d = 30 * time.Second
    }
    jitter := time.Duration(rand.Int63n(int64(d / 2))) // 抖动，避免同时重试
    return d + jitter
}
```

重试必须配合幂等。超时重试最大的风险不是"失败"，而是"其实成功了但响应丢了"，再试一次就重复。

★ **关键认知**：重试次数不是越多越好。重试会放大下游压力，故障时形成雪崩。设置最大次数、退避和抖动，并在超过上限后转入死信，而不是无限循环。

## 2.2 死信队列

```text
orders
  │ 处理失败
  ▼
orders.retry.1  （1 分钟后重试）
  │ 仍失败
  ▼
orders.retry.2  （5 分钟后重试）
  │ 仍失败
  ▼
orders.retry.3  （30 分钟后重试）
  │ 仍失败
  ▼
orders.dlq      （人工排查 / 告警）
```

死信消息要带上原始消息、失败原因、重试次数、失败时间：

```go
headers := []kafka.Header{
    {Key: "x-original-topic", Value: []byte("orders")},
    {Key: "x-retry-count", Value: []byte("3")},
    {Key: "x-error", Value: []byte(err.Error())},
    {Key: "x-failed-at", Value: []byte(time.Now().Format(time.RFC3339))},
}
```

DLQ 必须有告警和消费方。只建一个 Topic 没人看，等于把消息丢进了黑洞。

⚠ **关键认知**：不要用"消费者 sleep 一段时间再重试"代替重试 Topic。sleep 会占住分区，阻塞后面的消息，还会让 lag 看起来正常但实际延迟巨大。重试要用独立 Topic 和独立的消费节奏。

## 2.3 幂等与去重

| 方案 | 适用 | 注意 |
|------|------|------|
| 去重表 | 通用业务 | 和业务写同一事务 |
| 唯一约束 | 插入型业务 | 捕获冲突当作成功 |
| 状态机 | 有状态流转 | `UPDATE ... WHERE status=...` |

第 6 篇已经展开，这里只强调一句：**至少一次语义下，幂等不是优化，是正确性的一部分。**

# 3. 顺序性

## 3.1 顺序的边界

Kafka 只保证**分区内有序**。要利用这一点：

1. 同一业务实体用同一个 key。
2. 分区数在扩容后不要指望旧 key 还落原分区。
3. 生产端避免多批次乱序（幂等生产者或限制在途请求）。
4. 消费端按分区串行处理，不要把同一分区的消息并发丢给多个 worker。

```text
同 key：order-1001
  → 分区 3
  → [created][paid][shipped]
  → 单消费者按 offset 顺序处理

不同 key：order-1001 与 order-1002
  → 可能在不同分区
  → 处理先后没有保证
```

## 3.2 热点 key

热点 key 会让单个分区成为瓶颈：一个消费者忙死，其他消费者空闲，lag 全压在一个分区上。

处理方式：

- 提升 key 的粒度（`tenantID:orderID`）。
- 业务上拆分热点实体。
- 监控分区级 lag 和字节速率，发现倾斜。
- 如果确实不需要顺序，去掉 key 或加随机后缀。

## 3.3 需要全局顺序时

只能把 Topic 设成单分区：

```bash
kafka-topics.sh --bootstrap-server localhost:9092 \
  --create --topic global-events --partitions 1 --replication-factor 3
```

代价是失去水平扩展能力，吞吐上限就是单分区上限。大多数业务不需要全局顺序，只需要"同一实体有序"。真需要全局顺序时，先问清楚"这个顺序是业务要求，还是实现偷懒"。

★ **关键认知**：顺序性和吞吐是一对 trade-off。分区越多吞吐越高，顺序范围越小；单分区全局有序，但吞吐受限。设计时要明确"谁和谁之间需要顺序"，不要笼统地说"消息要有序"。

# 4. 容量规划

## 4.1 吞吐与分区

```text
分区数 = max(生产峰值 / 单分区写能力, 消费峰值 / 单分区消费能力) × 2
```

示例：生产峰值 50MB/s，单分区按 10MB/s 估算，则至少 5 个分区，乘 2 取 10 个。再检查消费者实例数是否能达到 10 个；如果只能部署 4 个实例，多出来的分区就是闲置的。

## 4.2 磁盘与网络

```text
磁盘 = 每秒字节 × 86400 × 保留天数 × 副本数 × 1.2
```

示例：2,000 条/秒、每条 1KB、保留 7 天、副本 3：

```text
每天约 165GB → 7 天 × 3 副本 ≈ 3.5TB → 加 20% 余量 ≈ 4.2TB
```

网络要算两笔：

- **客户端流量**：生产 + 消费。
- **副本流量**：跨 Broker、跨机架、跨可用区的复制流量。

跨 AZ 复制会产生云厂商的跨区流量费用，规划时要把这部分算进成本。

## 4.3 客户端资源

- 每个 `Writer` 复用，不要按请求创建。
- 异步写入要限制缓冲区大小，防止 OOM。
- 消费者 worker 数量要和分区数、下游承载能力匹配。
- 关注文件句柄、连接数、goroutine 数量。

# 5. 上线检查清单

| 类别 | 检查项 |
|------|--------|
| Topic | 分区数、副本数、`min.insync.replicas`、保留策略 |
| 生产端 | `acks=all`、重试上限、幂等或业务去重、超时 |
| 消费端 | 手动提交、处理幂等、优雅退出、并发模型 |
| 顺序 | key 设计、分区扩容计划、消费单并发 |
| 监控 | lag、错误率、ISR、磁盘、请求延迟 |
| 安全 | TLS、SASL、ACL、最小权限 |

★ **关键认知**：上线检查不是走形式。最容易出事的三个点——**没设 `min.insync.replicas`、消费端没幂等、分区扩容没评估顺序性**——都能在清单里被拦住。

# 6. 自检题

## 6.1 基础

**问：Kafka 消费完消息会删除吗？**

不会。消息由 `retention.ms` 或 `retention.bytes` 删除，消费只推进 offset。需要"处理完即清理"时，要缩短保留时间并接受消息仍可被重读。

**问：为什么 Topic 内不保证全局有序？**

Topic 被分成多个分区，每个分区独立追加，只有分区内有序。跨分区没有全局时钟或统一序列。

**问：`acks=all` 就一定不丢吗？**

不一定。还要看 `min.insync.replicas` 和副本数。如果 ISR 只剩 leader，`acks=all` 也只写了一份。

**问：offset 提交的是当前消息还是下一条？**

下一条。处理 offset=100 后提交 101，表示 100 及之前都已完成。

**问：`ReadMessage` 和 `FetchMessage` 的区别？**

`ReadMessage` 会自动提交 offset；`FetchMessage` 只拉取，需要手动 `CommitMessages`。要做"处理成功再提交"，必须用后者。

## 6.2 进阶

**问：rebalance 期间消息会丢吗？**

通常不会丢，但会重复。新负责人从已提交 offset 继续读，未提交的处理会重放。除非消费端先提交后处理，才可能丢。

**问：幂等生产者能保证业务只执行一次吗？**

不能。它只保证单分区、单生产者会话内不重复，管不到数据库和外部接口。

**问：Kafka 事务能覆盖写 MySQL 吗？**

不能。事务只覆盖 Kafka 内部的写入和 offset 提交。跨系统要靠幂等或 Outbox。

**问：lag 突然上涨应该先做什么？**

先看是生产突增、消费卡住还是 rebalance，再决定扩容、限流还是修消费者。不要直接重置 offset。

## 6.3 场景题

**场景一：订单事件偶尔重复扣款。**

先确认消费端是否幂等。用 `(consumer_group, order_id)` 去重表，把去重记录和扣款放在同一事务；或者让扣款 SQL 带状态条件，重复执行不产生副作用。

**场景二：消费 lag 持续上涨，消费者 CPU 不高。**

大概率卡在下游或锁。看 pprof、下游 p99、数据库连接池；如果是分区倾斜，检查 key 分布；如果是分区数不够，评估扩容。

**场景三：滚动发布时频繁 rebalance。**

放慢发布节奏，调大 `RebalanceTimeout` 和 `SessionTimeout`；Java 客户端可用静态成员；消费逻辑要能容忍重复。不要靠"加消费者"解决，那只会让 rebalance 更频繁。

# 7. 小结

```text
                    ┌─────────────────────┐
                    │   Kafka 基础         │
                    │ 日志 / 分区 / 副本    │
                    └──────────┬──────────┘
                               │
          ┌────────────────────┼────────────────────┐
          ▼                    ▼                    ▼
   ┌────────────┐      ┌────────────┐      ┌────────────┐
   │  生产者     │      │  消费者     │      │  运维       │
   │ acks/批/压缩│      │ 组/offset   │      │ 监控/容量   │
   │ 重试/幂等   │      │ 提交/退出   │      │ 安全/故障   │
   └─────┬──────┘      └─────┬──────┘      └─────┬──────┘
         └───────────────────┼───────────────────┘
                             ▼
                  ┌─────────────────────┐
                  │  可靠交付            │
                  │ 至少一次 + 幂等 + DLQ│
                  └─────────────────────┘
```

| 主题 | 一句话 |
|------|--------|
| 定位 | 分布式提交日志，不是消费即删的队列 |
| 可靠性 | `acks=all` + `min.insync.replicas>=2` + RF>=3 |
| 消费 | 处理成功再提交，至少一次 + 幂等 |
| 顺序 | 同 key 同分区，分区内串行 |
| 重试 | 指数退避 + 抖动 + 死信 |
| 容量 | 按吞吐、保留、副本估算，留 20% 余量 |
| 安全 | TLS + SASL + ACL，三层配合 |
| 排障 | 先看 lag、ISR、磁盘，再改代码 |

Kafka 的难点从来不是"怎么发一条消息"，而是"消息丢了怎么办、重复了怎么办、顺序乱了怎么办、集群撑不住了怎么办"。把这四个问题想清楚，剩下的都是参数和工具。下一步可以挑一个真实业务，从 Topic 设计、生产消费代码、监控告警到故障演练完整走一遍，比继续看文档更有用。
