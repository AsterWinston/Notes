前面八篇分别解决了"能不能跑通""写得对不对""跑得快不快"三类问题。这一篇做三件事：把知识串成一张图，把 GORM 放回技术选型的坐标系里，再用自检题和生产清单把零散结论压实。

# 1. 知识地图

## 1.1 一条请求穿过 GORM 的路径

```text
业务请求
   │
   ▼
┌─────────────────────────────────────────────┐
│ 1. 连接层  gorm.Open / 连接池 / DSN 参数      │  ← 第 1 篇
└───────────────────┬─────────────────────────┘
                    ▼
┌─────────────────────────────────────────────┐
│ 2. 模型层  结构体 / 标签 / 表名 / 迁移        │  ← 第 2 篇
└───────────────────┬─────────────────────────┘
                    ▼
┌─────────────────────────────────────────────┐
│ 3. 构建层  链式 API / Where / Scopes          │  ← 第 3、4 篇
└───────────────────┬─────────────────────────┘
                    ▼
┌─────────────────────────────────────────────┐
│ 4. 关联层  Preload / Joins / Association      │  ← 第 5 篇
└───────────────────┬─────────────────────────┘
                    ▼
┌─────────────────────────────────────────────┐
│ 5. 执行层  事务 / 锁 / SavePoint              │  ← 第 6 篇
└───────────────────┬─────────────────────────┘
                    ▼
┌─────────────────────────────────────────────┐
│ 6. 横切层  钩子 / 插件 / 日志 / 审计          │  ← 第 7 篇
└───────────────────┬─────────────────────────┘
                    ▼
┌─────────────────────────────────────────────┐
│ 7. 优化层  索引 / 执行计划 / 连接池 / 压测    │  ← 第 8 篇
└─────────────────────────────────────────────┘
```

★ **关键认知**：这七层里，**只有第 3、4 层是"GORM 特有知识"，其余六层都是数据库与工程通用能力**。面试和排障时真正拉开差距的，往往是第 5 到第 7 层——事务边界、锁、索引这些"GORM 帮不了你"的部分。

## 1.2 按问题域定位

| 你遇到的问题 | 该回看哪篇 | 关键结论 |
|--------------|------------|----------|
| 连不上库、时区不对 | 第 1 篇 | `gorm.Open` 惰性连接，`ping` 才校验 |
| 字段没进表、表名不对 | 第 2 篇 | 非导出字段被忽略，`TableName` 优先 |
| 更新没生效 | 第 3 篇 | 结构体跳过零值，用 map 或 `Select` |
| 条件多套了一层 | 第 4 篇 | `Or` 要用嵌套 `Where` 分组 |
| 列表页慢、N+1 | 第 5、8 篇 | `Preload` 替代循环查询 |
| 数据写一半、超卖 | 第 6 篇 | 事务边界 + 原子更新 |
| 审计字段到处写 | 第 7 篇 | 回调统一注入 |
| 突然变慢 | 第 8 篇 | 看 `EXPLAIN` 的 `rows` 与 `Extra` |

# 2. GORM 与 sqlx / 原生 SQL 对比

## 2.1 横向对比

| 维度 | database/sql | sqlx | GORM |
|------|--------------|------|------|
| 抽象层级 | 最低 | 低 | 高 |
| SQL 控制力 | 完全 | 完全 | 中（可退化为 Raw） |
| 结构体映射 | 手写 `Scan` | `StructScan` | 自动 |
| 关联加载 | 手写 JOIN | 手写 JOIN | `Preload`/`Joins` |
| 动态条件 | 字符串拼接（易注入） | 字符串拼接 | 链式 API 自动参数化 |
| 迁移 | 无 | 无 | `AutoMigrate`（仅开发） |
| 学习成本 | 低 | 低 | 中高 |
| 隐藏行为 | 无 | 极少 | 钩子、软删除、默认事务 |
| 排查难度 | 低 | 低 | 中（要看生成 SQL） |

## 2.2 选型建议

```text
团队 SQL 能力强 + 查询复杂 + 追求极致性能
        │
        ▼
   database/sql 或 sqlx

业务以 CRUD 为主 + 迭代快 + 团队水平参差
        │
        ▼
      GORM
```

| 场景 | 推荐 |
|------|------|
| 后台管理、内部系统、快速交付 | GORM |
| 报表、复杂多表统计、窗口函数 | 原生 SQL（GORM 的 `Raw` 或 sqlx） |
| 高并发交易核心链路 | 原生 SQL + 显式事务 |
| 需要统一软删除、审计、多租户 | GORM 的钩子/回调更省事 |
| 团队不熟悉 ORM 隐式行为 | sqlx 更可控 |

★ **关键认知**：选型不是"ORM 好还是 SQL 好"，而是"**这类查询由谁来保证正确性**"。简单 CRUD 交给 GORM 省人力，复杂查询交给 SQL 保可控，二者可以在同一个项目里共存。

## 2.3 混用策略

```go
type OrderRepo struct {
    db *gorm.DB
}

// 简单查询：链式 API
func (r *OrderRepo) GetByID(ctx context.Context, id uint) (*Order, error) {
    var o Order
    err := r.db.WithContext(ctx).First(&o, id).Error
    return &o, err
}

// 复杂统计：原生 SQL，仍走 GORM 的连接与事务
func (r *OrderRepo) DailyStat(ctx context.Context, start time.Time) ([]DailyStat, error) {
    var out []DailyStat
    err := r.db.WithContext(ctx).Raw(`
        SELECT DATE(created_at) AS day, SUM(amount) AS total
        FROM orders
        WHERE created_at >= ?
        GROUP BY day
        ORDER BY day
    `, start).Scan(&out).Error
    return out, err
}

// 事务内混用：所有操作都用 tx
func (r *OrderRepo) Pay(ctx context.Context, id uint) error {
    return r.db.WithContext(ctx).Transaction(func(tx *gorm.DB) error {
        if err := tx.Exec("UPDATE accounts SET balance = balance - ? WHERE id = ?", 100, 1).Error; err != nil {
            return err
        }
        return tx.Model(&Order{}).Where("id = ?", id).Update("status", "paid").Error
    })
}
```

⚠ 混用最大的坑是"**事务内用了 `r.db` 而不是 `tx`**"。原生 SQL 与链式 API 都可以混，但必须共享同一个 `tx`，否则事务形同虚设。

# 3. 高频自检问题

## 3.1 模型与迁移

**Q1：`AutoMigrate` 能在生产用吗？**

不能作为唯一迁移手段。它只增不减、不改类型、无版本记录、无回滚，大表加索引还会锁表。生产应用版本化 SQL 迁移工具。

**Q2：`CreatedAt` 为什么没自动填？**

字段名必须是 `CreatedAt`，类型是 `time.Time`。改名、改类型或写成非导出都会失效。

**Q3：软删除后唯一索引为什么冲突？**

软删除只是 `UPDATE deleted_at`，行还在。唯一索引仍会命中。方案是把 `deleted_at` 加入唯一索引，或删除时改写唯一列。

## 3.2 CRUD 与查询

**Q4：`Updates` 为什么没更新零值？**

结构体更新只处理非零字段。用 `map[string]any` 或 `Select("field")` 强制。

**Q5：`Save` 和 `Updates` 有什么区别？**

`Save` 按主键判断插或改，改动时**更新全部字段**；`Updates` 只更新指定字段。局部更新用 `Updates`。

**Q6：`First` 和 `Find` 的差别？**

`First` 带主键排序且未找到返回 `ErrRecordNotFound`；`Find` 不加排序、未找到返回空切片不报错。

**Q7：`Or` 为什么把条件搞乱了？**

`Or` 作用于前面整段条件。含 `OR` 的复杂逻辑用嵌套 `db.Where(...)` 显式加括号。

## 3.3 关联与事务

**Q8：`Preload` 和 `Joins` 怎么选？**

要取关联数据、且主表分页 → `Preload`；要按关联条件过滤主表 → `Joins`。一对多下 `Joins + Limit` 会因行放大导致分页错误。

**Q9：N+1 怎么发现？**

代码审查看"循环里有没有 `db.` 调用"，运行期看 SQL 日志条数是否随结果集线性增长。

**Q10：`db.Transaction` 什么情况下会回滚？**

回调返回非 nil error，或发生 panic。返回 nil 一定提交——所以每个写操作都必须检查 `.Error`。

**Q11：嵌套事务是真事务吗？**

不是。GORM 用 `SAVEPOINT` 实现，内层失败只回滚到保存点，最终提交权在外层。

**Q12：乐观锁和悲观锁怎么选？**

读多写少、冲突低 → 乐观锁（版本号 + 重试）；事务内多步依赖同一行 → 悲观锁（`FOR UPDATE`）；能用一条带条件的原子 UPDATE 解决 → 优先原子更新。

## 3.4 性能与工程

**Q13：为什么加了索引还是全表扫描？**

可能违反最左前缀、列上用了函数、发生隐式类型转换，或区分度太低被优化器放弃。

**Q14：连接池怎么定？**

`MaxOpenConns × 实例数` 要低于数据库 `max_connections` 的安全水位，且 `ConnMaxLifetime` 小于数据库 `wait_timeout`。

**Q15：`RowsAffected == 0` 说明记录不存在吗？**

不一定。MySQL 在"值未变化"时也返回 0。要区分需先查、加 `clientFoundRows` 或用锁。

# 4. 生产检查清单

## 4.1 连接与配置

- [ ] DSN 带 `parseTime=True`、`loc` 与 `charset=utf8mb4`
- [ ] 启动时 `Ping` 校验，而不是只判断 `Open` 的 error
- [ ] 设置 `MaxOpenConns`/`MaxIdleConns`/`ConnMaxLifetime`
- [ ] 生产日志级别 `Warn`，配置慢查询阈值
- [ ] 敏感字段不进入 SQL 日志

## 4.2 查询与索引

- [ ] 列表接口禁止无 `Limit` 的 `Find`
- [ ] 高频查询有对应复合索引，顺序符合最左前缀
- [ ] 分页用游标或限制最大页码
- [ ] 循环内没有数据库调用
- [ ] 大字段用 `Select`/`Omit` 排除

## 4.3 事务与并发

- [ ] 事务内只有数据库操作，无 HTTP/RPC/文件 IO
- [ ] 事务回调内一律用 `tx`
- [ ] 每个写操作的 `.Error` 都被检查
- [ ] 扣减类操作使用原子更新或显式锁
- [ ] 加锁顺序统一，避免死锁

## 4.4 工程与可观测性

- [ ] `*gorm.DB` 只出现在 repository 层
- [ ] 所有查询带 `WithContext`，支持超时与取消
- [ ] 软删除的唯一索引方案已明确
- [ ] 迁移脚本版本化，可回滚
- [ ] 关键接口有基准测试或压测基线

# 5. 全模块总结

| 篇目 | 一句话内核 |
|------|------------|
| 1 概览与快速开始 | GORM 是 `database/sql` 之上的映射层，连接是惰性的 |
| 2 模型与迁移 | 结构体即表结构，`AutoMigrate` 只属于开发期 |
| 3 CRUD | 零值、`Save`、软删除是三大高频坑 |
| 4 查询与作用域 | 条件优先级要显式分组，Scope 让条件可复用 |
| 5 关联 | 外键位置决定关系类型，`Preload` 治 N+1 |
| 6 事务 | 返回 nil 才提交，嵌套是 SavePoint |
| 7 钩子与插件 | 横切逻辑集中管理，钩子必须用 `tx` |
| 8 性能与索引 | 先减 SQL 条数，再看执行计划，最后调池 |
| 9 面试与总结 | 选型看查询复杂度，复杂 SQL 交给原生 |

★ **关键认知**：GORM 的"会用"和"用好"之间隔着一条线——**能不能预测它生成的 SQL**。能预测，你就在用它提效；不能预测，你就是在被它牵着走。练习方式很朴素：每个链式调用后面加一行 `db.ToSQL`，把 SQL 读一遍。

# 6. 下一步

如果这个模块已经读完，建议按三条线继续深入：

1. **数据库底层**：索引的 B+ 树结构、MVCC、间隙锁、执行计划优化器。这些决定了你能否看懂第 8 篇的 `EXPLAIN`。
2. **工程化**：`golang-migrate`/`atlas` 做版本化迁移，`sqlmock` 或 testcontainers 写数据层测试，OpenTelemetry 接入 SQL 链路追踪。
3. **架构演进**：读写分离（GORM 的 `DBResolver` 插件）、分库分表（`gorm.io/sharding`）、缓存一致性。这些是在 ORM 之上再加一层的能力。

# 7. 小结

| 主题 | 要点 |
|------|------|
| 知识地图 | 七层链路中只有构建层与关联层是 GORM 特有 |
| 选型 | 简单 CRUD 用 GORM，复杂统计用原生 SQL，可共存 |
| 混用铁律 | 事务内所有操作共享同一个 `tx` |
| 自检 | 零值、N+1、事务回滚、索引失效是最高频四问 |
| 生产 | 连接池、慢查询、迁移、上下文缺一不可 |
| 核心能力 | 能预测 GORM 生成的 SQL，才算真正掌握 |

至此 GORM 模块结束。回到 `Go/` 目录，可以接着看 `Go-Redis`（缓存与分布式锁）与 `gRPC`（服务间通信），它们和本篇的数据访问层正好组成一个完整的后端服务闭环。
