前十篇讲的是"怎么做"，这一篇讲"怎么判断做得对不对"。微服务的成败往往不在某个框架用得多熟，而在边界划得清不清、数据一致性能不能兜底、团队协作有没有共识。下面把散落在各篇的经验收拢成四组原则、一份反模式清单和一张上线检查表。

# 1. 边界划分

## 1.1 业务边界

好的服务边界有三个特征：

- **高内聚**：一个需求变更主要落在一个服务里。
- **低耦合**：服务之间通过少量、稳定的接口交互。
- **可独立发布**：改这个服务不需要同时改别的服务。

```text
好的边界                       坏的边界
┌──────────┐                  ┌──────────┐
│  订单     │                  │  订单     │
│  履约     │                  │  库存     │
│  支付     │                  │  价格     │
└──────────┘                  └──────────┘
每个服务闭环                   三个服务必须一起改
```

## 1.2 数据边界

★ **关键认知**：**服务边界最终由数据所有权定义**。如果两个服务都能写同一张表，它们实际上是一个服务，只是部署成了两个进程。判断方法：列出每张表的写入方，如果有多个，边界就错了。

| 模式 | 是否推荐 | 原因 |
|------|----------|------|
| 每服务独占 schema | 推荐 | 边界清晰，可独立演进 |
| 共享库不同表 | 谨慎 | 仍有耦合，迁移困难 |
| 共享表 | 禁止 | 无法独立发布，事务边界混乱 |
| 只读副本 | 可接受 | 用于报表、查询，不参与写 |

## 1.3 团队边界

康威定律说：系统结构会复制组织的沟通结构。反过来也成立——**服务边界应该与团队边界对齐**。

| 信号 | 含义 |
|------|------|
| 一个服务需要三个团队同时改 | 边界跨了组织 |
| 一个团队维护十个服务 | 服务过细或人力不足 |
| 服务没有明确 Owner | 出问题没人负责 |
| 发布需要跨团队审批 | 耦合太紧 |

## 1.4 边界检查清单

- 这个服务能否单独部署、单独回滚？
- 它的数据库是否只被自己写入？
- 它是否可以不需要其他服务就能完成核心用例？
- 它的接口变更是否只影响自己？
- 是否有明确的 Owner 和值班人？

五个问题有一个答"否"，就值得重新审视边界。

# 2. 数据一致性

## 2.1 一致性光谱

| 级别 | 实现 | 延迟 | 适用 |
|------|------|------|------|
| 强一致 | 单库本地事务 | 无 | 账户余额、库存扣减 |
| 顺序一致 | 单分区消息 | 低 | 同一订单的状态流转 |
| 最终一致 | Outbox + 消费 | 秒级 | 通知、积分、搜索索引 |
| 弱一致 | 缓存 | 秒到分钟 | 商品详情、推荐 |

★ **关键认知**：**能用本地事务解决的，绝不上分布式事务**。把强一致需求压缩在一个服务内，是成本最低的方案；只有真正跨服务、跨库的场景，才考虑 Saga、TCC 或 Outbox。

## 2.2 事务边界

```text
一个服务 = 一个数据库 = 一个本地事务边界
```

跨服务写操作的四种方案：

| 方案 | 一致性 | 侵入性 | 适用 |
|------|--------|--------|------|
| 两阶段提交（2PC） | 强 | 高 | 极少，性能差 |
| TCC | 强（业务补偿） | 高 | 支付、资金 |
| Saga | 最终 | 中 | 长流程、订单履约 |
| Outbox | 最终 | 低 | 事件驱动，最常用 |

## 2.3 Outbox 再强调

```text
本地事务
├── INSERT orders
└── INSERT outbox(event)

Relay 轮询 outbox → 发 Kafka → 标记已发送
Consumer 按 event_id 幂等消费
```

这套模式解决的是"写库成功但发消息失败"的经典问题。它不追求实时，但保证**只要事务提交，事件最终一定会发出去**。

## 2.4 对账兜底

⚠ **关键认知**：任何最终一致方案都必须配**对账**。消息可能丢、消费可能失败、补偿可能漏，只有定时比对两侧数据，才能发现"静默不一致"。对账结果要能自动修复，至少要做到告警。

# 3. 团队协作

## 3.1 服务所有权

每个服务都要有：

- **Owner 团队**：负责功能、性能、故障。
- **On-call 轮值**：告警有人接。
- **SLO**：可用性、延迟目标。
- **Runbook**：常见故障的处理步骤。

没有 Owner 的服务，最终会变成"谁都能改、谁都不负责"的公共垃圾场。

## 3.2 接口协作

| 实践 | 作用 |
|------|------|
| proto 先行评审 | 变更前先对齐字段与语义 |
| CI 跑 buf breaking | 自动拦截破坏性变更 |
| 版本化路径 | v1/v2 并行，平滑迁移 |
| Deprecation 公告 | 给调用方迁移时间 |
| 契约测试 | 消费者参与验证 |

## 3.3 发布协作

```text
开发 → 单测 → 契约检查 → 集成测试 → 预发 → 灰度 → 全量
                                      │
                                      └─ 观察指标，异常回滚
```

跨服务的变更要约定**发布顺序**：先发兼容新字段的提供者，再发消费者；下线字段则反过来，先停消费者，再删字段。

## 3.4 值班与复盘

| 环节 | 要点 |
|------|------|
| 告警 | 基于 SLO，不基于每个异常 |
| 响应 | Runbook 先行，止血优先 |
| 复盘 | 无指责，聚焦系统改进 |
| 跟进 | 每个 action item 有 Owner 和期限 |

★ **关键认知**：复盘的目的不是找到"谁写错了代码"，而是找到"为什么这个错误能上线、为什么没被监控发现、为什么恢复花了这么久"。前者制造恐惧，后者改进系统。

# 4. 常见反模式

## 4.1 分布式单体

**表现**：服务拆了，但必须一起发布、一起扩容、共享数据库，调用还成环。

**根因**：按技术层或按人头拆，而不是按业务能力拆。

**纠正**：回到领域模型，合并强耦合模块，重新划边界。

## 4.2 共享数据库

**表现**：多个服务读写同一批表，一个服务改字段，其他服务跟着崩。

**根因**：图省事，避免写 API。

**纠正**：每服务独占 schema，跨服务通过 API 或事件；历史数据用同步任务迁移。

## 4.3 服务过细

**表现**：10 人团队维护 20 个服务，一个需求改 8 个仓库。

**根因**：把"微"当成目标，而不是手段。

**纠正**：合并低变更、强耦合的服务；一个服务可以由多个模块组成。

## 4.4 同步调用链

**表现**：A→B→C→D 串行同步，任何一跳慢都会拖垮全链。

**根因**：所有交互都默认同步。

**纠正**：能并行就并行，能异步就异步；为每跳设超时与熔断。

## 4.5 无治理上线

**表现**：服务上线了，但没有超时、没有追踪、没有告警。

**根因**：把"能跑"当成"能上线"。

**纠正**：治理能力随服务一起交付，见第 6 节检查表。

## 4.6 配置散落

**表现**：配置在镜像、环境变量、ConfigMap、配置中心各一份，不知道哪个生效。

**根因**：没有统一的配置规范。

**纠正**：定义优先级，单一事实来源，启动时打印生效配置（脱敏）。

| 反模式 | 症状 | 修复优先级 |
|--------|------|-----------|
| 分布式单体 | 必须一起发布 | 高 |
| 共享数据库 | 改表牵连多服务 | 高 |
| 服务过细 | 维护成本高于收益 | 中 |
| 同步调用链 | 一慢全慢 | 高 |
| 无治理上线 | 故障无法定位 | 高 |
| 配置散落 | 环境行为不一致 | 中 |

# 5. 技术选型建议

| 场景 | 建议 |
|------|------|
| 刚起步、团队小 | 模块化单体，先不拆 |
| 需要快速落地、规范统一 | go-zero |
| 需要灵活扩展、长期演进 | Kratos v2 |
| 已有 K8s | 优先用 Service/ConfigMap，少自建注册中心 |
| 跨云、多数据中心 | Consul 或服务网格 |
| 内部调用 | gRPC + Protobuf |
| 对外 API | REST/JSON 或 grpc-gateway |
| 异步解耦 | Kafka |
| 可观测 | OpenTelemetry + Prometheus + Tempo/Jaeger |

★ **关键认知**：**选型要匹配团队当前能力，而不是匹配大厂架构**。没有平台团队，就不要自建服务网格；没有 SRE，就不要上复杂的多集群方案。先用简单方案跑通，再按痛点演进。

# 6. 上线检查清单

| 类别 | 检查项 |
|------|--------|
| 边界 | 数据是否独占、能否独立发布、是否有 Owner |
| 接口 | proto 是否版本化、是否有兼容性检查 |
| 超时 | 每个 RPC 是否有 deadline、是否逐层递减 |
| 重试 | 是否只重试可重试错误、是否有退避抖动 |
| 熔断 | 是否按接口配置、是否有 Half-Open |
| 限流 | 入口与服务是否都有 |
| 幂等 | 写接口是否支持幂等键 |
| 日志 | 是否结构化、是否带 trace_id |
| 指标 | 是否有延迟/流量/错误/饱和度 |
| 追踪 | 是否接入 OTel、是否透传 traceparent |
| 健康检查 | liveness/readiness 是否分离 |
| 优雅关闭 | 是否先摘除、再排空 |
| 配置 | 是否镜像外注入、是否可追溯 |
| 发布 | 是否滚动、是否可回滚 |
| 数据库 | 迁移是否向前兼容 |
| 测试 | 单测、集成、契约是否覆盖关键路径 |

# 7. 学习路线

```text
1  概览与架构          ← 先想清楚要不要拆
2  Kratos 快速上手      ← 一条完整的最小服务
3  go-zero 快速上手     ← 另一条工程化路线
4  注册发现与配置       ← 服务如何找到彼此
5  RPC 与网关          ← 调用、超时、错误、版本
6  可观测性            ← 出问题怎么查
7  稳定性治理          ← 故障怎么被限制
8  部署                ← 怎么安全上线
9  测试                ← 怎么证明它对
10 最佳实践与总结       ← 怎么判断做对了
```

建议的学习方式：**每学一篇，就在自己的项目里落地一个最小实践**。比如学完第 4 篇，把写死的地址换成注册中心；学完第 6 篇，给一个接口加上 trace_id。只看不练，遇到真实故障还是无从下手。

# 8. 练习

1. 选一个现有系统，用第 1 节的五个问题检查边界，列出最需要合并或拆分的两个服务，并说明理由。
2. 为一个跨服务写操作设计一致性方案：画出事务边界、事件流、幂等键和对账任务。
3. 用第 6 节检查表给一个服务打分，找出三个最可能引发线上故障的缺口，排优先级并给出修复计划。

# 9. 小结

| 主题 | 核心结论 |
|------|----------|
| 边界 | 由数据所有权定义，与团队边界对齐 |
| 一致性 | 优先本地事务，跨服务用 Outbox + 对账 |
| 协作 | 服务有 Owner，接口有契约，变更讲顺序 |
| 反模式 | 分布式单体、共享库、过细、长链、无治理 |
| 选型 | 匹配团队能力，按痛点演进 |
| 上线 | 超时、重试、熔断、幂等、可观测缺一不可 |

微服务不是终点，而是一种**用分布式复杂度换取组织弹性**的交易。什么时候做这笔交易、做多大、怎么控制风险，比学会某个框架重要得多。希望这十篇能让你在下次架构评审时，既能画出漂亮的架构图，也能说清楚它的代价和兜底方案。
