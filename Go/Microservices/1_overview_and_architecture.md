微服务不是"把单体拆小"这么简单，它换来的是一整套分布式代价：网络不可靠、数据不一致、调用链变长、排障变难。本篇先讲清楚什么时候该拆、按什么边界拆、拆完怎么通信，再给出一张 Go 技术栈全景图，让你在动手写第一行代码前就知道自己要付出什么。

# 1. 微服务的取舍

## 1.1 单体架构的边界

单体应用把所有功能打在一个进程里：一个二进制、一个数据库、一次部署。它在早期是**正确选择**，因为本地函数调用没有网络开销，事务天然一致，调试只需一个断点。

真正的问题不在"大"，而在**变更耦合**：

- 改一个促销规则，要重新发布整个应用，回归全部功能。
- 一个慢查询拖垮线程池，整个站点不可用。
- 团队从 5 人涨到 50 人，同一份代码库的合并冲突和发布排队成为瓶颈。
- 不同模块的技术诉求不同，却被迫共用同一套依赖版本。

```text
单体应用的典型瓶颈
┌─────────────────────────────────────────┐
│              一个进程 / 一个库            │
│  订单   库存   支付   用户   报表         │
│    │      │      │      │      │         │
│    └──────┴──────┴──────┴──────┘         │
│        任何一处故障都可能拖垮全局          │
└─────────────────────────────────────────┘
```

★ **关键认知**：微服务解决的是**组织与变更**问题，不是性能问题。如果一个系统访问量不大、团队规模不大、发布频率不高，单体加上良好的模块划分往往比微服务更划算。技术选型要先问"我的痛点是不是变更耦合"，而不是"别人都在用"。

## 1.2 微服务到底是什么

微服务是一种**架构风格**：把应用拆成一组小型、自治的服务，每个服务：

- 围绕一个**业务能力**构建，而不是围绕技术分层。
- **独立部署**，可以单独扩容、单独发布。
- **拥有自己的数据**，不与其他服务共享数据库表。
- 通过**轻量级协议**通信，最常见的是 HTTP/JSON 与 gRPC。
- 由**小团队**端到端负责，从开发到线上运维。

注意最后一条：微服务天然对应康威定律——系统结构会映射组织沟通结构。没有对应的团队边界，硬拆出来的服务很快会退化成"分布式单体"。

## 1.3 收益与成本

| 维度 | 收益 | 代价 |
|------|------|------|
| 发布 | 独立部署，故障隔离 | 需要 CI/CD、版本管理、灰度能力 |
| 扩展 | 按服务扩容，资源更精准 | 容量规划变复杂，需监控每个服务 |
| 技术 | 可异构，按场景选型 | 多语言维护成本上升 |
| 数据 | 各服务自治 | 跨服务事务消失，只能最终一致 |
| 组织 | 团队边界清晰 | 需要平台团队与基础设施投入 |
| 排障 | 单服务日志更聚焦 | 一次请求跨多个进程，必须上链路追踪 |

★ **关键认知**：微服务的成本是**前置**的——你必须先把注册发现、配置中心、日志、指标、追踪、网关、CI/CD 建好，才谈得上享受它带来的灵活性。跳过基础设施直接拆服务，等于把单体的复杂度放大 N 倍。

⚠ **关键认知**：不要用"微服务"当作技术债的遮羞布。一个本身耦合严重、没有测试、没有监控的系统，拆成十个服务后只会得到十个耦合严重、没有测试、没有监控的服务，外加一张更难的排障网络。

# 2. 服务拆分

## 2.1 拆分维度

常见的拆分依据有四类：

| 维度 | 示例 | 适用 |
|------|------|------|
| 业务能力 | 订单、库存、支付、履约 | 最主流，边界稳定 |
| 限界上下文 | 商品上下文、交易上下文 | 复杂业务，DDD 建模 |
| 读写分离 | 查询服务、写入服务 | 读写负载差异极大 |
| 变更频率 | 高频变动的营销、低频的账务 | 发布节奏差异明显 |

不推荐的维度：按技术分层拆（Controller 服务、Service 服务）、按表拆（每张表一个服务）、按团队人头硬拆。

## 2.2 限界上下文

**限界上下文（Bounded Context）** 是领域驱动设计里的核心概念：同一个词在不同上下文里含义不同。例如"商品"在**商品上下文**里关注标题、图片、类目；在**库存上下文**里只关心 SKU 和数量；在**交易上下文**里关心价格快照。

```text
同一个"商品"，三种模型
┌────────────────┐   ┌────────────────┐   ┌────────────────┐
│  商品上下文     │   │  库存上下文     │   │  交易上下文     │
│  Product       │   │  StockItem     │   │  OrderLine     │
│  title         │   │  skuId         │   │  skuId         │
│  images        │   │  available     │   │  priceSnapshot │
│  categoryId    │   │  warehouseId   │   │  quantity      │
└────────────────┘   └────────────────┘   └────────────────┘
```

★ **关键认知**：拆分的正确边界不是"数据表"，而是**业务语义的边界**。如果两个功能对同一个实体有完全不同的理解，它们就应该属于不同服务；硬共享一个模型，会让每次需求变更都牵动多个团队。

## 2.3 粒度判断

判断粒度可以用三个问题：

1. **能否独立发布**？改这个功能时，是否必须同时改另一个服务？
2. **能否独立扩展**？这个模块的压力是否与整体明显不同？
3. **数据是否自治**？这个服务能否不跨库 join 就完成核心逻辑？

三个都答"是"，粒度大致合适；有两个答"否"，说明拆早了。

## 2.4 拆分反例

```text
反例：分布式单体
┌──────────┐  同步调用  ┌──────────┐  同步调用  ┌──────────┐
│ 订单服务  │──────────▶│ 库存服务  │──────────▶│ 价格服务  │
└──────────┘           └──────────┘           └──────────┘
     ▲                                              │
     └────────────── 又调回来 ─────────────────────┘
```

三个服务必须一起发布、一起扩容、共享一个数据库，调用还成环。这种结构既没有单体的简单，也没有微服务的灵活。

⚠ **关键认知**：服务之间出现**循环依赖**，通常不是通信问题，而是边界划错了。先回到领域模型重新划分，不要用"加个异步消息"来掩盖错误的边界。

# 3. 通信方式

## 3.1 同步与异步

| 方式 | 典型协议 | 优点 | 缺点 | 场景 |
|------|----------|------|------|------|
| 同步请求 | HTTP、gRPC | 语义直观、实时返回 | 强耦合、怕雪崩 | 查询、校验、需要立即结果 |
| 异步消息 | Kafka、RabbitMQ | 解耦、削峰、可重放 | 最终一致、需幂等 | 下单后通知、日志、事件驱动 |
| 事件流 | Kafka | 高吞吐、可回溯 | 运维复杂 | 数据管道、CDC |

★ **关键认知**：**同步用于"必须现在知道结果"，异步用于"稍后知道也可以"**。把不该同步的调用做成同步，是雪崩的常见起点；把必须同步的校验做成异步，则会带来超卖和重复。

## 3.2 协议选型

| 协议 | 编码 | 浏览器友好 | 性能 | 适合 |
|------|------|-----------|------|------|
| REST/JSON | 文本 | 是 | 中 | 对外 API、调试友好 |
| gRPC | Protobuf | 需网关 | 高 | 内部服务间调用、流式 |
| GraphQL | JSON | 是 | 中 | 聚合多个数据源的前端 BFF |

Go 生态里，内部调用优先 gRPC，对外暴露用 HTTP，二者通过网关或同一份 proto 注解统一，第 5 篇会展开。

## 3.3 通信的隐性成本

一次本地函数调用大约几十纳秒；一次跨进程 RPC 是**毫秒级**，且多出这些失败模式：

- 连接建立失败、DNS 解析失败。
- 对端进程还在，但线程池已满。
- 请求发出去了，响应丢了，状态未知。
- 超时设置不一致，上游已放弃，下游还在执行。

★ **关键认知**：网络调用必须假设"**可能失败、可能超时、可能重复**"。所以每个 RPC 都要有超时，每个写操作都要考虑幂等，每个调用链都要能追踪。这三件事不是可选项，是分布式系统的基本礼仪。

# 4. Go 技术栈全景

## 4.1 分层结构

```text
┌───────────────────────────────────────────────────────┐
│                      接入层                            │
│   HTTP 网关 / BFF / gRPC-Gateway / APISIX              │
└───────────────────────┬───────────────────────────────┘
                        ▼
┌───────────────────────────────────────────────────────┐
│                    业务服务层                          │
│   user-service   order-service   inventory-service     │
│   每个服务：api / internal(service,biz,data) / cmd       │
└───────────────────────┬───────────────────────────────┘
                        ▼
┌───────────────────────────────────────────────────────┐
│                  基础设施层                            │
│   注册发现(Etcd/Consul)  配置中心  消息队列(Kafka)       │
│   缓存(Redis)  数据库(MySQL)  对象存储                   │

                        ▼

│              可观测与治理层                            │

│   限流  熔断  重试  灰度                               │
└───────────────────────────────────────────────────────┘
```

## 4.2 Kratos 与 go-zero

| 维度 | Kratos v2 | go-zero 1.x |
|------|-----------|-------------|
| 定位 | 面向云原生的微服务框架 | 面向高并发的工程化框架 |
| 接口定义 | Protobuf 优先 | `.api` 文件 + Protobuf |
| 代码生成 | `kratos` CLI + protoc | `goctl` 一站式生成 |
| 传输 | HTTP + gRPC 对等 | HTTP + gRPC 对等 |
| 依赖注入 | Google Wire | 显式装配 |
| 内置治理 | 中间件生态、otel、registry | 熔断、限流、自适应降载 |
| 适合 | 中大型、需要灵活扩展 | 快速落地、团队规范统一 |

两个框架都会在后面两篇用最小可运行服务讲清楚。选型不必纠结"谁更强"，先看团队是否接受其代码生成方式和目录约定。

# 5. 常见误区

| 误区 | 表现 | 纠正 |
|------|------|------|
| 一上来就拆 | 10 人团队拆 20 个服务 | 先模块化单体，按痛点渐进拆 |
| 共享数据库 | 多个服务读写同一批表 | 每服务独占 schema，跨库走 API 或事件 |
| 只拆不管 | 没有追踪、没有超时 | 基础设施先行，治理随服务上线 |
| 同步调用成链 | A→B→C→D 串行 | 能并行就并行，能异步就异步 |
| 把分布式事务当银弹 | 每个写操作都上 Seata | 优先本地事务 + 事件 + 补偿 |
| 忽视契约 | 改字段不通知调用方 | proto 版本化，CI 做兼容性检查 |

⚠ **关键认知**：微服务最常见的失败不是技术选型错误，而是**组织没有准备好**。没有明确的服务 Owner、没有值班机制、没有统一的发布流程，服务越多，故障定位越慢。

# 6. 练习

1. 选一个你熟悉的单体系统，画出它的业务能力图，尝试划出 3 个限界上下文，并说明每个上下文的聚合根。
2. 列举该系统里 5 个跨模块调用，判断哪些必须同步、哪些可以改为事件，并写出理由。
3. 对照上面的收益成本表，给你的系统打分：如果基础设施（注册、配置、日志、追踪）缺三项以上，先补齐再谈拆分。

# 7. 小结

| 主题 | 要点 |
|------|------|
| 定位 | 微服务解决组织与变更问题，不是性能银弹 |
| 拆分 | 按业务能力与限界上下文，不按表、不按技术层 |
| 粒度 | 能独立发布、独立扩展、数据自治 |
| 通信 | 必须同步才同步，其余走异步事件 |
| 成本 | 网络失败、数据一致、排障复杂度都要提前买单 |
| 技术栈 | Kratos 灵活，go-zero 工程化，按团队习惯选 |
