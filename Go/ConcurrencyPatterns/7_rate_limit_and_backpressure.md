并发模式解决"怎么跑得快"，限流与背压解决"跑得太快会死"。上游的流量永远不会体贴你的下游：数据库连接池只有几十个、第三方 API 有配额、CPU 只有几核。如果没有限流，一次流量尖峰就会把下游打挂，然后错误沿着调用链反弹回来，把上游也拖垮。本篇讲清楚令牌桶、漏桶、有界队列这三种工具，以及"队列满了以后到底该怎么办"这个真正决定系统行为的问题。

# 1. 为什么需要限流

## 1.1 过载的连锁反应

```text
流量尖峰
   │
   ▼
下游响应变慢 ──► 请求积压 ──► 内存/连接数上涨
   │                              │
   ▼                              ▼
超时重试增加 ──────────────► 下游更慢（雪崩）
```

★ **关键认知**：过载不是"慢一点"那么简单，而是**正反馈**。响应变慢导致请求堆积，堆积导致重试，重试进一步压垮下游，最终所有请求都超时。限流的作用不是提升吞吐，而是**在过载时保住系统的基本可用性**——宁可拒绝一部分请求，也不能让所有请求一起死。

## 1.2 限流与背压的区别

| 概念 | 作用位置 | 手段 | 目标 |
|------|----------|------|------|
| 限流（rate limiting） | 入口 | 令牌桶、漏桶、计数器 | 控制**速率** |
| 并发限制（concurrency limiting） | 入口/中间 | 信号量、worker 池 | 控制**同时进行数** |
| 背压（backpressure） | 链路内部 | 有界队列阻塞生产者 | 让上游**感知**下游变慢 |

★ **关键认知**：限流是**主动设上限**，背压是**被动传压力**。限流器说"你每秒只能来 100 个"，有界队列说"我满了，你先等着"。两者常常一起用：入口限流挡住突发，链路内的有界队列把压力反推给上游。

# 2. 令牌桶

## 2.1 原理

```text
令牌以固定速率 rate 注入桶中（桶容量 capacity）
        ↓  ↓  ↓
    ┌─────────────┐
    │ ● ● ● ● ●   │  ← 最多存 capacity 个
    └──────┬──────┘
           │ 每个请求取走 1 个令牌
           ▼
     取到 → 放行
     取不到 → 拒绝或等待
```

★ **关键认知**：令牌桶的核心是"**桶里攒的是许可，不是请求**"。它以恒定速率补充令牌，允许桶里预先存一些，因此**能容忍突发流量**（只要突发量不超过容量），同时长期平均速率被限制在 `rate`。这正是它比简单计数器更实用的地方。

## 2.2 手写实现

```go
package limit

import (
    "math"
    "sync"
    "time"
)

type TokenBucket struct {
    mu       sync.Mutex
    capacity float64 // 桶容量，也是最大突发量
    tokens   float64 // 当前令牌数
    rate     float64 // 每秒补充的令牌数
    last     time.Time
}

func NewTokenBucket(rate, capacity float64) *TokenBucket {
    return &TokenBucket{
        capacity: capacity,
        tokens:   capacity, // 初始装满，允许一次突发
        rate:     rate,
        last:     time.Now(),
    }
}

func (b *TokenBucket) Allow() bool {
    b.mu.Lock()
    defer b.mu.Unlock()

    now := time.Now()
    elapsed := now.Sub(b.last).Seconds()
    b.tokens = math.Min(b.capacity, b.tokens+elapsed*b.rate) // 按时间补充
    b.last = now

    if b.tokens >= 1 {
        b.tokens-- // 取走一个令牌
        return true
    }
    return false
}
```

★ **关键认知**：这里**没有后台定时器**，而是每次请求时按"距上次经过的时间"惰性计算应该补多少令牌。这是令牌桶的标准实现技巧——用时间差算补充量，避免为每个限流器起一个 ticker。⚠ `last` 的更新必须在补充之后、判断之前，否则并发调用会重复计算同一段时间。

## 2.3 标准库扩展：x/time/rate

```go
import "golang.org/x/time/rate"

// 每秒 100 个令牌，桶容量 10（即最多突发 10 个）
limiter := rate.NewLimiter(rate.Limit(100), 10)

// 方式一：非阻塞，取不到就返回 false
if !limiter.Allow() {
    http.Error(w, "too many requests", http.StatusTooManyRequests)
    return
}

// 方式二：阻塞等待，直到取到令牌或 ctx 取消
if err := limiter.Wait(ctx); err != nil {
    return // ctx 超时或被取消
}

// 方式三：预约未来某个时间点的令牌
r := limiter.Reserve()
if !r.OK() {
    return
}
time.Sleep(r.Delay())
```

★ **关键认知**：`rate.Limiter` 的三个方法对应三种策略：`Allow` 是**立即拒绝**，`Wait` 是**排队等待**，`Reserve` 是**预约**。绝大多数服务端场景用 `Allow` 做入口保护，用 `Wait` 限制对下游的调用速率。⚠ `Wait` 会阻塞调用方，必须传带超时的 ctx，否则可能等到天荒地老。

# 3. 漏桶

## 3.1 原理

```text
请求 ──► ┌───────────────┐
         │  队列（定长）  │
         └───────┬───────┘
                 │ 以固定速率流出（不管进来多快）
                 ▼
              下游
```

★ **关键认知**：漏桶把**流入整形成恒定速率流出**。请求进来先入队，队列满了就丢弃；出口以固定速率取走。它**不允许突发**，输出曲线是平滑的，因此适合保护对速率极其敏感的下游（如按固定帧率推流、严格配额的第三方接口）。

## 3.2 令牌桶 vs 漏桶

| 维度 | 令牌桶 | 漏桶 |
|------|--------|------|
| 突发流量 | 允许（受容量限制） | 不允许，平滑输出 |
| 核心参数 | rate + capacity | rate + queue size |
| 队列 | 无（令牌即许可） | 有（请求排队） |
| 典型实现 | `x/time/rate` | 定时消费队列 |
| 适用 | 大多数 API 限流 | 严格匀速的下游 |

★ **关键认知**：两者不是对立的。令牌桶限制的是"**进入系统的速率**"，漏桶限制的是"**离开系统的速率**"。很多网关会同时用：入口令牌桶挡住突发，出口漏桶平滑发给下游。

# 4. 有界队列与背压

## 4.1 队列满时的三种选择

有界队列迟早会满，满了以后的行为决定了系统的性格：

| 策略 | 做法 | 优点 | 代价 |
|------|------|------|------|
| 阻塞生产者 | `ch <- job` 直接阻塞 | 不丢任务，压力自然上传 | 上游可能被拖死 |
| 立即拒绝 | `select` + `default` 返回错误 | 快速失败，保护自己 | 会丢任务 |
| 降级 | 返回缓存/默认值/异步补偿 | 用户体验平滑 | 实现复杂，可能掩盖问题 |

```go
// 策略一：阻塞（天然背压）
func submitBlocking(ch chan<- Job, job Job) {
    ch <- job // 队列满就等，压力反推给调用方
}

// 策略二：拒绝（快速失败）
func submitNonBlocking(ch chan<- Job, job Job) error {
    select {
    case ch <- job:
        return nil
    default:
        return errors.New("队列已满，请稍后重试")
    }
}
```

★ **关键认知**：**有界队列 + 阻塞写入**是最纯粹的背压实现——上游的生产速度会被自动限制在下游的消费速度上。⚠ 但如果上游是 HTTP handler，阻塞写入会占住 goroutine 和连接，请求越积越多，最终耗尽连接池。所以入口处通常用"拒绝"而不是"阻塞"，把背压转化成明确的 429/503 响应。

## 4.2 队列容量与延迟

```text
队列长度 L，消费速率 C，则最坏排队时间 ≈ L / C

例：队列 1000，每秒消费 100 → 最坏等 10 秒
```

★ **关键认知**：队列越长，能吸收的突发越多，但**队尾请求的延迟也越大**。一个排了 10 秒才被处理的请求，用户早就断开连接了，处理它纯属浪费资源。所以队列容量要结合**可接受的最大延迟**来定：`容量 ≈ 目标吞吐 × 可容忍排队时间`。

# 5. 过载保护

## 5.1 组合拳

单个手段都不够，生产系统通常是多层防护：

```text
请求
  │
  ▼
[入口限流] 令牌桶：挡住速率突增
  │
  ▼
[并发限制] 信号量/worker 池：挡住同时处理数
  │
  ▼
[有界队列] 队列满 → 拒绝或阻塞
  │
  ▼
[下游超时] context：避免无限等待
  │
  ▼
[熔断/降级] 下游持续失败 → 直接返回兜底
```

★ **关键认知**：限流和并发限制要**同时存在**。限流控制"每秒进来多少"，并发限制控制"此刻有多少在跑"。一个每秒 100 个请求、每个耗时 10 秒的服务，即使限流 100/s，也会有 1000 个请求同时在处理——并发限制必须能把它们压到可承受的范围。

## 5.2 一个简单的自适应思路

固定阈值在流量模式变化时会失准。更稳的做法是看**延迟**：当 P99 延迟超过阈值时，主动降低并发上限；延迟恢复后再慢慢升回去。这类算法（如 Netflix 的 concurrency-limits）实现较复杂，工程上可以先从"固定上限 + 监控告警 + 手工调参"起步，不要一上来就追求全自动。

⚠ **关键认知**：自适应算法如果只看单一指标，容易被噪声带偏。真正上线前要有回放压测和灰度，且保留一个"固定上限"作为兜底下界，防止算法把限额调到 0。

# 6. 完整示例：带限流的批量任务

```go
func processAll(ctx context.Context, jobs []Job) error {
    limiter := rate.NewLimiter(rate.Limit(50), 10) // 全局 50/s，突发 10
    g, ctx := errgroup.WithContext(ctx)
    g.SetLimit(20) // 同时最多 20 个

    for _, job := range jobs {
        job := job
        g.Go(func() error {
            if err := limiter.Wait(ctx); err != nil {
                return err // 等待令牌时被取消
            }
            return handle(ctx, job)
        })
    }
    return g.Wait()
}
```

★ **关键认知**：这里有两层保护：`SetLimit(20)` 限制同时运行数，`limiter.Wait` 限制启动速率。前者防止把下游连接池占满，后者防止瞬间打出一波请求。⚠ 顺序很重要——先拿并发名额再等令牌，否则所有 goroutine 都卡在等令牌上，并发名额反而没被用满。

# 7. 常见错误

```text
1. 只限流不限制并发              → 慢请求堆积，仍然压垮下游
2. 队列无界                      → 内存暴涨，延迟失控
3. 队列满时静默丢弃不记录         → 问题被掩盖
4. 限流器按请求创建而非全局共享    → 每个请求都拿到全新桶，等于没限
5. Wait 不传超时 ctx             → 阻塞到永远
6. 限流阈值拍脑袋                → 与下游真实容量不匹配
7. 只限入口不限出口              → 自己的下游调用仍然超配额
```

⚠ **关键认知**：第 4 条非常隐蔽。`rate.NewLimiter` 必须作为**长生命周期对象**（包级变量、服务结构体字段）复用，如果在 handler 里每次 `New`，每个请求都会得到一个满桶，限流完全失效。

# 8. 练习

**练习 1**：实现一个容量 5、速率 2/s 的令牌桶，用 20 个并发请求测试，统计通过和拒绝的数量。再调整容量为 20，观察突发通过量的变化。

**练习 2**：用 `rate.NewLimiter` + `errgroup.SetLimit` 实现一个批量请求函数，要求全局每秒不超过 10 次、同时不超过 5 个。用 100 个任务测试总耗时是否接近 10 秒。

**练习 3**：实现一个容量 100 的有界任务队列，写两个版本：队列满时阻塞、队列满时返回 429。用一个慢消费者和快生产者分别测试，记录队列长度和拒绝次数的变化。

# 9. 小结

| 主题 | 要点 |
|------|------|
| 限流目标 | 过载时保可用，不是提升吞吐 |
| 令牌桶 | 恒速补充、允许突发，用时间差惰性计算 |
| 漏桶 | 定长队列 + 恒速流出，输出平滑 |
| 背压 | 有界队列阻塞生产者，把压力反推上游 |
| 队列满 | 阻塞、拒绝、降级三选一，入口通常选拒绝 |
| 组合 | 限流 + 并发限制 + 超时 + 熔断，缺一不可 |
| 陷阱 | 限流器必须全局复用，Wait 必须带超时 ctx |
