Hooks "记住状态"这件事,既没有缓存变量、也没有全局变量,靠的是一张**隐藏的链表**。本篇讲清 useState/useEffect 在底层怎么依"调用顺序"对应状态、依赖数组怎么比对、以及为什么规则不可违——把第 15 篇的心智模型落到实现。

# 1. Hooks 的存储:链表

## 1.1 每个组件一条 Hook 链表

```
组件 Fiber 上挂一条"Hook 链表":
  HookNode1 (第一个 useState) → HookNode2 (第二个 useState) → HookNode3 (useEffect)
每个 HookNode 记:自己的状态(memoizedState)、下一个节点的指针(next)
```

★ **关键认知**：每个组件的 Fiber 上挂一条 **Hook 链表**,每个 Hook 占一个节点,记录自己的 `memoizedState`(记住的状态)+ 指向下一个的 `next`。⚠ 渲染时**按调用顺序**依次取用链上的节点——这就是第 15 篇"靠顺序对应状态"的实现真相。

## 1.2 useState 里存了什么

```
useState 的 HookNode:
  memoizedState = 当前值(count)
  queue = 待处理的更新队列(setCount 攒下的更新)
useEffect 的 HookNode:
  memoizedState = { effect 对象 }(含上次的依赖数组,用于比对)
```

★ **关键认知**：`useState` 的节点存**当前值 + 更新队列**;`useEffect` 的节点存**effect + 上次依赖**(用于判断要不要重跑)。⚠ 不同 Hook 在节点里存的 `memoizedState` 含义不同,但都挂在这条链上、按顺序读。

# 2. useState 的执行

## 2.1 挂载与更新

```
首次渲染(mount):
  useState(0) → 建节点,存 0,返回 [0, setCount]
更新:
  useState(初始值) → 按顺序找到已有节点,忽略"初始值",读回存的当前值
  → setCount 触发 → 处理 queue 里的更新 → 得到新值 → 存回 → 下次渲染读新值
```

★ **关键认知**：`useState` 的两次调用(挂载 vs 更新)**行为不同**——挂载时"**写入**初始值",更新时"**忽略初始值、读回已存的值**"。⚠ 这就解释了"初始值只在首次生效"以及"为什么必须按顺序调用"(顺序就是它在链上的位置)。

## 2.2 函数式更新的来源

```jsx
setCount(c => c + 1)   // 这个函数被推进 queue,处理时拿"前一个值"算
```

★ **关键认知**：`setCount(fn)` 的函数式更新,把 `fn` 推进**更新队列**,真正应用时用**链上的最新值**去算,而非闭包里那个旧快照。⚠ 这从实现层解释了第 4 篇"函数式更新能避免闭包旧值"——它绕过了闭包,直接问"队列此刻的最新值"。

# 3. useEffect 与依赖比对

## 3.1 闭包与 cleanup

```
每次渲染,effect 函数都是"新闭包"(捕获本次渲染的 state)
依赖比对:Object.is(上次的 deps[i], 这次的 deps[i])
  全相等 → 不执行
  有变化 → 先跑上次的 cleanup,再执行新 effect
```

★ **关键认知**：每次渲染,effect 函数是**新闭包**(捕获**本次**的 state);React 比对**依赖数组**,变了就"先清理旧的、再执行新的"。⚠ 这套"闭包 + 依赖比对"正是第 8 篇 effect 机制的实现;清理函数被存在节点里,等下次执行前/卸载时调用。

## 3.2 为什么闭包会"旧"

★ **关键认知**：effect 闭包捕获的是"**它创建那次渲染**"的 state;依赖没变、effect 不重跑,闭包就一直是**旧的**。⚠ 所以第 8 篇的"漏依赖读旧值"在实现上就是"React 没让你重跑,你的闭包自然停在原地"——不是 bug,是"快照语义 + 依赖比对"的必然结果。

# 4. 调度与批量

## 4.1 更新队列的批处理

```jsx
setCount(c => c + 1)   // 三个更新被"攒"进 queue
setCount(c => c + 1)
setCount(c => c + 1)
// 批处理:一次处理完 queue 里全部更新,渲染一次
```

★ **关键认知**：连写多个 `setCount`,更新被**推进队列**,React 在合适时机**批量处理**(一次渲染)。⚠ 这是第 4 篇"批处理"的实现:更新不是立即单次应用,而是`进队列、再统一 flush`,这也让函数式更新(逐个基于前值)能正确累加。

## 4.2 与 Fiber 的衔接

★ **关键认知**：Hook 链表挂在 **Fiber** 上,所以"组件重渲染"时 Fiber 还在,Hook 链还在,状态才不丢;组件卸载则 Fiber 丢弃、Hook 链销毁。⚠ 这串起了整个原理图:**Fiber(组件树)→ Hook 链表(状态)→ 依赖比对(更新时机)**,三者环环相扣。

# 5. 一张完全串起来的图

```
setState
  → Hook 节点.queue 入队
  → 调度(优先级,第 30 篇)
  → render:重跑组件函数 → 按顺序读 Hook 链 → 得到新 state → 生成新 Fiber(第 31 篇 Diff)
  → commit:更新 DOM
  → 之后 effect 阶段:比对依赖,决定是否跑副作用
```

★ **关键认知**：把四篇原理串成一线——**Hooks 存/取状态(Hook 链)→ Fiber 承载可中断渲染 → Diff 算最小更新 → commit 落地 DOM**。⚠ 这条"从改状态到界面更新"的完整链路,是 React 面试深水区的终极考点,也是"会用"与"真懂"的分界。

# 6. 本篇小结与下一步

★ **关键认知**：Hooks 靠 Fiber 上的**链表**按调用顺序存状态;useState 挂载写入/更新读回、函数式更新进队列;useEffect 靠 Object.is 比依赖决定重跑。规则不可违,因为顺序即地址。
