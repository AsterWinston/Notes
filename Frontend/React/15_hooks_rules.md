Hooks 用起来顺手,但总有两条"铁律"令人疑惑:只能在顶层调用、只能在 React 函数里调用。它们不是教条,背后是**Hooks 靠"调用顺序"识别状态**的底层机制。本篇把 Hooks 的心智模型与规则讲透,并给出"依赖数组"这一 React 核心设计的完整理解。

# 1. 两条规则

## 1.1 只在顶层调用

```jsx
function Bad({ flag }) {
  // ✗ 违反规则:条件调用 Hook,顺序不稳定
  if (flag) {
    const [a, setA] = useState(0)   // 这次渲染调用了 useState
  }
  const [b, setB] = useState(0)     // 下次渲染 flag=false,这个可能被认成"第一个" → 错乱
}

function Good({ flag }) {
  const [a, setA] = useState(0)     // ✓ 无条件调用,顺序稳定
  const [b, setB] = useState(0)
  if (flag) { /* 用 a/b,而非条件地"声明" */ }
}
```

★ **关键认知**：**Hooks 必须在组件顶层、无条件调用**——不能在 if/循环/嵌套函数里。⚠ 原因(见第 2 节)是 React **靠"第几个 Hook"来对应状态**;条件调用会打乱顺序,导致"这次渲染以为是 state A,下次却对应到了 B",状态彻底错乱。

## 1.2 只在 React 函数里调用

```jsx
// ✗ 不能在普通函数里调 Hook
function notComponent() {
  const [x, setX] = useState(0)   // 报错:没有 React 上下文
}
// ✓ 只能在函数组件或自定义 Hook(useXxx)里
```

★ **关键认知**：Hook **只能**在**函数组件**或**自定义 Hook(`use` 开头)**里调用。⚠ 这同样是"顺序追踪"机制的要求;`eslint-plugin-react-hooks` 的两条规则(`rules-of-hooks`、`exhaustive-deps`)就是机器替你把守这两条铁律。

# 2. 为什么靠"顺序"

## 2.1 状态与顺序的对应

```
第一次渲染:
  const [count, ...] = useState(0)   → 存到"存放槽 #0"
  const [name, ...]  = useState('')  → 存到"存放槽 #1"

第二次渲染:
  const [count, ...] = useState(0)   → 读取"存放槽 #0"(还是 count)
  const [name, ...]  = useState('')  → 读取"存放槽 #1"(还是 name)
```

★ **关键认知**：React 给每个组件维护一份**状态链表/数组**,Hook 每次调用**按顺序**读写对应槽位——**`useState` 里那个初始值只在首次渲染用来写入,之后只是"按位置读回"**。⚠ 所以"哪个 useState 对应哪个状态"完全由**调用顺序**决定,顺序一乱,映射就错(这就是第 32 篇 Hooks 实现的具体机理)。

## 2.2 这也解释了"组件必须是函数"

★ **关键认知**：函数组件的每次调用(渲染)都是**独立执行**,内部 Hook 按稳定的顺序调用,React 在**多次调用之间**用一份 per-component 的存储把它们串起来。⚠ 理解这个,才明白为什么"Hook 只能在顶层"不是风格问题,而是**正确性的硬约束**。

# 3. 依赖数组的心智

## 3.1 deps 是比较引用

```jsx
useEffect(() => {...}, [a, b])   // React 用 Object.is 逐个比较 a、b 与"上一次"是否变了
```

★ **关键认知**：依赖数组的判定是**`Object.is` 逐个比较引用/值**——原始值比值,对象/函数比引用。⚠ 所以"每次渲染都新建一个对象/函数"会让依赖"每次都变",effect 每次都跑——这正是第 9 篇 useMemo/useCallback 存在的理由(稳定引用)。

## 3.2 诚实列出依赖 vs 关规则

```jsx
useEffect(() => {
  console.log(name)        // 用了 name 却不列为依赖 → 读到旧值
}, [])
// ESLint 的 exhaustive-deps 会警告"name 缺失"
```

★ **关键认知**："**依赖数组要诚实**"——effect 里用到的 state/props 都要列进去;漏了就读旧值(闭包快照)。⚠ 用 `// eslint-disable` 关这个警告通常是在**埋雷**;正确做法是"重写代码让它不需要该依赖",或"诚实加进去并处理好逻辑"。

## 3.3 依赖的完整心智链

```
state 是快照 → 闭包捕获快照 → effect 依赖没变就不重跑(读旧值)
→ 所以要"依赖数组诚实" + "值变时用函数式更新"
→ 引用要稳定就 useMemo/useCallback
```

★ **关键认知**：React 的依赖心智是一条环环相扣的链——**快照语义 → 闭包 → 依赖数组 → 函数式更新 → 稳定引用**。⚠ 把这五环串起来,React 里 90% 的"为什么读到旧值 / 为什么无限循环 / 为什么每次重跑"都有了统一答案。

# 4. 与 Vue 的根本差异

| 维度 | React Hooks | Vue 组合式 API |
|------|-------------|----------------|
| 状态标识 | 调用顺序(槽位) | Proxy 对象本身 |
| 依赖 | 手动数组 | 自动追踪 |
| 约束 | 顶层 + 函数内 | 仅 setup 作用域 |
| 记忆化 | useMemo 手动 | computed 自动 |

★ **关键认知**：这组对照是学习两大框架的"锚点"——**React 用"顺序"追踪(所以要规则约束),Vue 用"Proxy"追踪(所以免依赖数组)**。⚠ 没有优劣,是设计取舍:React 的"显式依赖"换来规则清晰可预测,但多了心智负担;Vue 的"自动依赖"体验顺滑,但底层更"魔法"。

# 5. 本篇小结与下一步

★ **关键认知**：Hooks 的两条规则来自"**按调用顺序对应状态**"的底层机制;依赖数组靠 Object.is 比引用;心智铁链"快照→闭包→依赖→函数式更新→稳定引用"。这条链是 React 一切疑难杂症的统一定位法。
