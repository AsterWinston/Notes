Electron 有多个进程,状态也存在多重——UI 状态在渲染进程,持久数据在主进程。**跨进程状态协同**是 Electron 特有的复杂度:谁持有数据、变化怎么推给界面、多个窗口怎么保持一致。本篇讲清这些模式。

# 1. 状态在哪里

## 1.1 三层状态

```
1. UI 状态(渲染进程):组件内部,如"这个抽屉开着""输入框内容"
   → 归 Vue/React 管理,与主进程无关
2. 应用会话状态(主进程):窗口状态、下载任务、当前用户
   → 主进程持有,变化时推给渲染
3. 持久数据(磁盘):文件、DB、配置
   → 主进程读写,是"最终事实"
```

★ **关键认知**：分清状态的**归属**——**UI 状态在渲染(框架管)、会话状态在主进程、持久数据在磁盘**。⚠ 常见混淆:**把本该在渲染的 UI 状态塞进主进程**(过度耦合)或**把该持久化的数据只放在渲染内存**(关窗就丢)。先判"这状态属于哪层",再谈怎么传。

# 2. 主进程持有数据 → 推给渲染

## 2.1 拉取(pull)与推送(push)

```javascript
// 拉取:渲染主动要(适合"打开页面时载入一次")
ipcRenderer.invoke('notes:list') → 主进程查 DB 返回所有笔记

// 推送:主进程主动发(数据变了,立刻通知所有窗口)
win.webContents.send('notes:changed', notes)
```

★ **关键认知**：两种同步方向——**拉取**(渲染 invoke 拿数据,适合"初次加载")与**推送**(主进程变更后 `webContents.send`,适合"实时同步")。⚠ 通常**组合用**:页面载入时拉一次,之后依赖主进程**在数据变化时推送**保持最新;只拉不推,多窗口/长时间运行时数据就"旧"了。

## 2.2 广播给所有窗口

```javascript
// 数据变化:主进程遍历所有窗口广播
function notifyAll(channel, data) {
  for (const win of BrowserWindow.getAllWindows()) {
    win.webContents.send(channel, data)
  }
}
// 某处数据改了 → notifyAll('notes:changed', latest)
```

★ **关键认知**：主进程作为**数据的单一权威**,改了就**广播**给所有窗口,各窗口自行刷新——这是保证**多窗口一致**的核心。⚠ 别让"窗口 A 改了数据、窗口 B 不知道";主进程统一改、统一推,所有界面跟着同一份真相走。

# 3. 渲染进程侧的处理

## 3.1 订阅并更新 UI 状态

```jsx
// React 里,把"主进程推送"接进 hook
function useNotes() {
  const [notes, setNotes] = useState([])
  useEffect(() => {
    window.api.onNotesChanged(setNotes)   // 订阅推送
    window.api.listNotes().then(setNotes) // 初次拉取
  }, [])
  return notes
}
```

★ **关键认知**：渲染进程用**"订阅推送 + 初次拉取"**模式——挂载时拉一次,再订阅主进程的变更推送,两者都落进同一个 UI 状态。⚠ 这是跨进程状态进入框架状态的标准接法(和 Vue 的 useXxx 同理);封装成 `useNotes` 这类 hook 后,组件只管 `useNotes()`。

## 3.2 保持单一数据流

```
用户改数据 → 渲染调 window.api (invoke)
  → 主进程改持久数据 → 广播 changed
  → 所有窗口的订阅回调更新 UI
（改的入口唯一:永远经主进程,渲染不"本地先改再同步"）
```

★ **关键认知**：维护**单一数据流**——**所有修改都经主进程完成**(渲染不直接改本地副本),主进程改完再推回来。⚠ 好处是没有"本地状态与主进程状态谁新"的分叉;渲染进程的数据永远来自主进程的推送,不存在双向打架。

# 4. 状态库与 Electron

## 4.1 框架状态库的角色

★ **关键认知**：Pinia/Redux 这类状态库在 Electron 里**只活在渲染进程内**(管 UI/会话状态),**不能跨进程共享**。⚠ **别指望用一个 Pinia store 同时服务主进程和渲染进程**——进程隔离,状态各有一份;要跨进程,只能走 IPC(主进程是"真相",渲染是"镜像")。

## 4.2 主进程要不要用状态库

★ **关键认知**：主进程通常**不需要**前端状态库——它要的状态(窗口、任务、会话)往往直接存内存变量/模块级单例即可。⚠ 过度在主进程引入复杂状态管理是多余;主进程的"状态"多数就是"一些变量 + 广播函数",简单直白最可维护。

# 5. 实践清单

| 场景 | 做法 |
|------|------|
| 页面载入数据 | invoke 拉取 |
| 数据变化同步 | 主进程改后 webContents.send 广播 |
| 多窗口一致 | 主进程单一权威 + 广播 |
| UI 状态 | 留在渲染进程(框架管) |
| 持久数据 | 主进程读磁盘,是最终事实 |

# 6. 本篇小结与下一步

★ **关键认知**：状态分三层(UI/会话/持久);主进程是数据单一权威,改后广播给所有窗口;渲染进程"订阅 + 拉取"接进框架状态;前端状态库只在渲染进程内,跨进程靠 IPC。
