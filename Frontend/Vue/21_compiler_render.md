到这一篇，我们把最后一块拼图补上：模板里的 `{{ }}`、`v-if`、`@click` 这些**写给人看的语法**，是怎么一步步变成**机器执行的 render 函数**的。本篇讲清编译器三大阶段（parse / transform / generate）、静态提升、PatchFlags 打标与 Block tree 这三样"编译期性能武器"，并点破为什么 Vue 敢用模板而性能依旧能打。

# 1. 编译概览

## 1.1 从模板到 render 函数

```
   <template> 里的模板字符串
          │
          ▼
  ┌───────────┐   parse：模板 → AST（抽象语法树）
  └───────────┘   把 <p>{{ msg }}</p> 解析成结构化的元素节点+指令
          │
          ▼
  ┌───────────┐   transform：AST → 优化后的 AST
  └───────────┘   分析动态/静态、打 patchFlag、做静态提升、识别 Block
          │
          ▼
  ┌───────────┐   generate：AST → 代码字符串
  └───────────┘   生成 render 函数的 JS 代码
          │
          ▼
   render 函数（返回 vnode，见第 20 篇）
```

★ **关键认知**：模板编译**三阶段**——`parse` 把模板字符串变成树（AST），`transform` 在树上做各种优化标注，`generate` 把树变成 JS 代码（render 函数）。⚠ 这一切发生在**编译期（dev 时在浏览器里即时做，build 时在 Rollup 阶段做）**，运行时不接触模板字符串。

## 1.2 一个模板的编译产物

```html
<!-- 模板示例 -->
<div>
  <p>静态文字</p>
  <p>{{ msg }}</p>
</div>
```

★ **关键认知**：`{{ msg }}` 编译后大致等价于 `h('p', null, msg)`——即用 `createElement` 系列（`h`）调用生成 vnode。所以"模板"与"渲染函数/JSX"**殊途同归**：最终都是 `h(type, props, children)` 的调用序列；模板多了一步"编译期翻译与优化"。

# 2. 三阶段详解

## 2.1 parse：字符串 → AST

```
输入：<p class="x" @click="go">{{ msg }}</p>
输出：{
  type: 元素节点,
  tag: 'p',
  props: [{ class }, { on: click }],
  children: [{ type: 插值, content: 'msg' }]
}
```

★ **关键认知**：parse 阶段只做**语法 → 结构**：把标签、属性、指令、插值解析成一颗 AST 树，**不关心语义**。⚠ 它只能发现"语法"错误（标签没闭合等），语义错误（如 `v-if` 和 `v-for` 混用、未知指令）要到后续或运行时才暴露。

## 2.2 transform：优化标注

```
在 AST 上做几件事：
1. 静态提升（hoist）：<p>静态文字</p> 这种永远不变的节点，提到渲染函数外只创建一次
2. 打 patchFlag：{{ msg }} 标记为"动态文本"，@click 标记为"动态事件"
3. 生成 Block：把带动态绑定的节点收进一个 Block 树
```

★ **关键认知**：transform 是**编译优化的主战场**——它遍历 AST，判断哪些节点是静态的、哪些是动态的，并做相应标注。⚠ 这里才是"Vue 编译期优化"真正发生的地方，理解三样武器（静态提升、patchFlag、Block）就看懂了 Vue 性能的根基。

## 2.3 generate：AST → 代码

```
把优化后的 AST 转成代码字符串：
function render(ctx) {
  return h('div', null, [ hoisted1, h('p', { [patchFlag]: 1 }, ctx.msg) ])
}
```

★ **关键认知**：generate 负责**代码生成**：把树转成合法的 `h(...)` 调用序列。生成的 render 函数运行时执行、返回 vnode，交给第 20 篇的 patch 去 diff。三阶段里最难的是 transform，其余是清晰的机械转换。

# 3. 三大编译期优化

## 3.1 静态提升（Static Hoisting）

```html
<template>
  <div>
    <p class="static">这段文字永远不变</p>
    <p>{{ msg }}</p>
  </div>
</template>
```

★ **关键认知**：**永不变化的节点**（无任何动态绑定）会被**提升到 render 函数外部**，只在组件初始化时创建**一次**。此后每次重新渲染复用的是同一个 vnode 对象，不重新创建也不参与 diff。⚠ 静态节点越多，这优化收益越大——大量静态文案、图标、装饰元素都能白嫖这一条。

## 3.2 PatchFlags 打标

```typescript
// 每个动态绑定会被编译器打上一个"位标志"，说明"这里会变、怎么变"
// 例如：
//   {{ msg }}            → TEXT (1)   只需比文本
//   :class="cls"         → CLASS (2)  只需比 class
//   :style="st"          → STYLE (4)
//   @click="go"          → PROPS(事件) 只比事件
//   v-model/多个动态     → 组合标志位
```

★ **关键认知**：编译器给含动态绑定的 vnode 打上 `patchFlag`（一个**位标志**），运行时 patch 时**只处理打了标的字段**——`{{ msg }}` 只比文本、`:class` 只比 class，其余字段零比较。⚠ 这把 diff 从"全字段扫描"变为"按标记精准打击"，是 Vue 3 相比 Vue 2 一个质变的性能提升。

## 3.3 Block tree

```
传统 vnode 树：整棵树是无差别的一层套一层，diff 要全树走一遍
Block tree：只把"带动态节点的"收进一个扁平的 Block 数组

静态：<div> <p>静态</p> [动态节点] </div>
                   （静态部分不进 Block，动态部分被收集）
```

★ **关键认知**：传统 diff 必须**从根递归遍历整棵树**找变化；Vue 3 的 **Block** 把含动态内容的节点**扁平收集**成一个数组，更新时**只需遍历动态节点**，静态子树整个跳过。⚠ Block tree 是"跳过不做无谓比较"的终极形态，配合 patchFlag 一起，让"更新"的成本与**动态节点数量**而非模板总规模成正比。

# 4. 为什么模板反而更优

## 4.1 模板 vs JSX 的编译确定性

| 维度 | 模板 | JSX（React） |
|------|------|-------------|
| 结构 | 静态、可静态分析 | 任意 JS，难静态分析 |
| 编译优化 | 能做（hoist/patchFlag/Block） | 很难（编译器无从下手） |
| 表达力 | 受限（不能任意 JS 语句） | 完全自由 |
| 更新成本 | 与动态节点量成正比 | 较难做等价优化 |

★ **关键认知**：模板"**表达能力受限**"恰恰是它的性能来源——结构足够确定，编译器才能**静态分析**出"哪些会变、哪些不变"，从而做上述优化；JSX 太自由，编译器判断不了，只能运行时硬算。⚠ 这就是"Vue 敢用模板、且性能不落下风"的根本原因，也是一个常被问到的面试深水区。

# 5. 本篇小结与下一步

★ **关键认知**：模板编译三阶段（parse → transform → generate），核心优化三件套——**静态提升**（不变的不重复造）、**patchFlag**（只比会变的）、**Block tree**（只遍历动态节点）。这三样把"更新"的成本从"模板规模"降到"动态绑定数量"。
