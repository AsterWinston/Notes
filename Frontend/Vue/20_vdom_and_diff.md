数据变了，真实的 DOM 到底怎么更新才能又对又快？Vue 的答案是：先在内存里算出新旧**虚拟 DOM（vdom）**的差异（**diff**），再把最小的改动落到真实 DOM。本篇讲清 vdom 的数据结构、patch 的两大类操作、列表 diff 的策略，以及 `key` 为什么直接决定 diff 的正确性——这是理解 Vue 更新机制的第二块拼图（第一块是第 19 篇的响应式）。

# 1. 为什么要虚拟 DOM

## 1.1 直接改 DOM 的代价

★ **关键认知**：真实 DOM 是浏览器里很"昂贵"的结构——每次读布局、每次增删节点都触发回流/重绘。数据一变就全量重建 DOM，性能不可接受。**虚拟 DOM 是一次"编辑计划"**：用轻量 JS 对象描述"界面应该长什么样"，在内存里算出与上一次的差异，最后**只更新变动的节点**。

## 1.2 vnode 就是一个 JS 对象

```typescript
// 一个 <div class="app">count: 0</div> 对应的 vnode 大致长这样
const vnode = {
  type: 'div',                 // 元素类型（'div' 或组件对象）
  props: { class: 'app' },     // 属性
  children: 'count: 0',        // 子节点：字符串或子 vnode 数组
  el: null,                    // 对应的真实 DOM（patch 后回填）
  key: null,                   // 列表复用时的身份标识
  // ... 还有 shapeFlag、patchFlag 等内部标记
}
```

★ **关键认知**：vnode 是**描述界面结构的普通对象**，不是 DOM。它比 DOM 轻几个量级，因此在内存里大量创建、比较都很快。⚠ vnode 的核心字段是 `type`（什么）、`props`（属性）、`children`（子内容）、`key`（列表身份），记住这四个就懂了一半。

# 2. patch：比较并更新

## 2.1 patch 的两大类

```
            patch(旧 vnode, 新 vnode)
                    │
        ┌───────────┴───────────┐
        │  类型不同 / 无 key     │   类型相同
        ▼                       ▼
   直接替换整棵子树          深入比较并对齐
  （卸载旧、挂载新）       （props diff + children diff）
```

★ **关键认知**：patch 是第一道分岔——**type 不同就整棵替换**（旧的卸载、新的挂载，不做细粒度比较），**type 相同才递归比较** props 与 children。⚠ 这就是为什么"把 `<div>` 换成 `<p>` 会重建"：类型一变，Vue 判定为"不同的东西"，干脆推倒重来，比逐字段比较更省。

## 2.2 children 的三种形态

```
children 旧 ─┬─ 文本   → 新文本：直接改 textContent
             ├─ 数组   → 新数组：进入"双端 diff"（见第 3 节）
             ├─ 数组   → 新文本：卸载旧全部，设文本
             └─ 文本   → 新数组：清文本，挂新全部
```

★ **关键认知**：`children` 的 diff 首先看**形态**（文本 ↔ 数组），形态不同的直接重建；**都是数组**才进入真正精细的列表 diff（双端比较）。⚠ 文本 vs 数组的转换是"破坏性"的，所以列表别在"个别文本"和"一批节点"之间来回切换结构。

# 3. 列表 diff：双端比较

## 3.1 双端 diff 的思想

```
 旧: a b c d        新: a b c d
     ▲         ▲       ▲         ▲
   旧头      旧尾     新头      新尾

 每一轮比较四种情况：旧头vs新头、旧尾vs新尾、旧头vs新尾、旧尾vs新头
 命中哪种就处理哪种，指针往中间收窄，直到一方耗尽
```

★ **关键认知**：Vue 3 的列表 diff 是**双端比较**——头头、尾尾、头尾、尾头四种配对逐一尝试，命中即复用以减少移动。⚠ 这与 React 的 diff 策略不同（React 主要从左到右逐个 index 对齐），Vue 的双端策略在"尾部插入/删除"这类常见操作上更高效。

## 3.2 key 决定"复用哪一对"

```typescript
// 无 key：按 index 对齐，重排必错位
const oldList = [{ name: 'A' }, { name: 'B' }]   // 隐含身份 = 下标 0/1
const newList = [{ name: 'C' }, { name: 'A' }, { name: 'B' }]
// 无 key 时 C 被当"旧 0 更新"、A 被当"旧 1 更新"，全错位且要重建

// 有 key：按 key 找相同身份的旧节点复用
// C 是新的(挂载)，A/B 找到旧 A/B 直接复用(最多移动 DOM)
```

★ **关键认知**：`key` 让 diff 能**按身份复用**而非按位置。有 key，插入一个元素只需挂载新节点 + 移动旧节点；无 key，则可能发生"复用错位"（如第 5 篇的输入框文字串行）。⚠ key 必须**唯一且稳定**，用 index 当 key 在"插入/删除/重排"时等价于无 key，复用完全走样。

## 3.3 为什么说"用 index 当 key 是坑"

```
旧： [ itemA, itemB ]        key: 0=A, 1=B
新： [ itemC, itemA, itemB ] key: 0=C, 1=A, 2=B

按 key(即 index) 对齐：0 对 0、1 对 1、2 是新的
   → Vue 认为"下标 0 的节点从 A 变成了 C"（原地改内容）
   → 但那个节点里若绑了组件状态/输入框，状态就错位了
```

★ **关键认知**：index 作 key 时，**下标没变但内容变了的节点会被"原地复用"**——DOM 节点没动，只是把新数据灌进旧节点。静态文本看不出来，一旦节点带状态（input 内容、组件本地 state），就表现为"串行/错乱"。⚠ 结论再次强调：**业务唯一 id 才是 key 的正解**，index 只适用于"纯静态、永不增删排序"的列表。

# 4. patch 的编译期加速

## 4.1 patchFlag：精准跳过

```typescript
// 模板编译时，Vue 会给动态部分打标（第 21 篇详解）
// 例如 {{ msg }} 会标记"这段 children 是动态文本"
// patch 时只比较打了标的字段，静态部分直接跳过
```

★ **关键认知**：传统 diff 要全量比 props/children，Vue 3 借助**编译期**给每个 vnode 打 `patchFlag`（如"动态文本 1" "动态类名" "动态属性"），运行 patch 时**只比这些被打标的部分**，静态内容零开销跳过。⚠ 这是 Vue 比 React"运行时纯 diff"更进一步的地方——把部分 diff 工作**前置到编译期**，这也是第 21 篇要讲的核心。

# 5. 本篇小结与下一步

★ **关键认知**：vdom 是"编辑计划"，patch 负责"算差异、落最小更新"，列表 diff 靠 `key` 实现身份复用，`patchFlag` 把 diff 工作前置到编译期。一块板：**数据 → 触发 effect → 生成新 vnode → diff → 更新真实 DOM**。
