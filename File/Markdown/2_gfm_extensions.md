CommonMark 把 Markdown 的核心语法固定了下来，但表格、任务列表、删除线这些写文档时高频使用的结构并不在里面。GitHub 在此基础上定义了 GFM（GitHub Flavored Markdown），如今已成为技术文档事实上的通用扩展。本篇讲清 GFM 提供了什么、各平台支持到什么程度，以及怎样写出既能用扩展、又不会绑死某个平台的文档。

# 1. 从 CommonMark 到 GFM

## 1.1 为什么需要扩展

CommonMark 只覆盖最基础的块级与行内结构：

| 能力 | CommonMark | 实际写作中的需求 |
|------|------------|------------------|
| 标题、段落、列表、引用 | 支持 | 够用 |
| 围栏代码块 | 支持 | 够用 |
| 表格 | 不支持 | 写参数说明、对比几乎必用 |
| 任务列表 | 不支持 | Issue、待办、检查清单 |
| 删除线 | 不支持 | 表示修订、废弃 |
| 裸网址自动成链 | 不支持 | 粘贴链接时省事 |
| 脚注 | 不支持 | 补充说明、引用来源 |

如果只写 CommonMark，上述结构只能退回 HTML 表格或纯文本，源码可读性会明显下降。GFM 的价值就是把这些"大家都在用"的结构标准化。

## 1.2 GFM 的定位

GFM 是 CommonMark 的**严格超集**，并额外规定了几种扩展。它的规范同样公开，带大量示例，因此不同实现之间的差异比早期 Markdown 小得多。

★ **关键认知**：GFM 的设计是"加法"——核心语法行为与 CommonMark 一致，扩展只在原本不合法或未定义的地方生效。这意味着只用基础语法写的文档，在 CommonMark 和 GFM 下渲染结果基本相同；一旦用了扩展，就绑定了平台能力。

主要扩展清单：

- 表格（tables）
- 任务列表项（task list items）
- 删除线（strikethrough）
- 自动链接（autolinks）
- 过滤危险 HTML（disallowed raw HTML）

脚注、告警块、emoji 短代码属于 GitHub 的产品特性，并不都在 GFM 规范正文里，这一点后文会单独说明。

# 2. 常用扩展

## 2.1 任务列表

在列表项开头写 `[ ]` 或 `[x]`：

```markdown
- [ ] 编写初稿
- [x] 校对错别字
- [ ] 补充示例
```

渲染后每项前面会出现复选框。规则：

- 必须先是列表项，再跟方括号，`[ ]` 内留一个空格表示未完成。
- 已完成可写 `x` 或 `X`。
- 有序列表同样适用：`1. [x] 已完成`。
- 复选框在 GitHub 上可点击，但点击结果不会自动提交到文件，只是界面状态。

嵌套任务列表要靠缩进：

```markdown
- [ ] 发布准备
  - [x] 更新版本号
  - [ ] 写发布说明
```

⚠ 方括号里写成 `[x ]`、`[ x]` 或中文全角方括号都不会被识别，只会原样显示成文本。另外，任务列表在纯文本阅读器里就是普通字符，不要用它承载唯一的进度信息。

## 2.2 删除线

用两个波浪号包裹：

```markdown
旧方案 ~~同步阻塞~~ 已改为异步。
```

GFM 规范允许一个或两个波浪号，但**只支持两个**的实现更多，跨平台时统一写 `~~`。

★ **关键认知**：删除线是**视觉标记**，不是语义化的 `<del>` 替代品。它适合表示"这段文字作废但仍保留痕迹"，不适合表示强调或否定。真正需要语义时，应该改写句子，而不是靠一条横线让读者猜。

## 2.3 自动链接

GFM 会把裸网址、`www.` 开头的域名和邮箱自动变成链接：

```markdown
访问 https://example.com 查看文档。
旧地址 www.example.com 已停用。
联系 admin@example.com。
```

CommonMark 的写法是用尖括号显式包裹：

```markdown
<https://example.com>
<admin@example.com>
```

两者区别：

| 写法 | 是否需要扩展 | 可控性 |
|------|--------------|--------|
| `https://example.com` | 需要 GFM | 省事，但无法指定链接文字 |
| `<https://example.com>` | CommonMark 核心 | 明确，兼容性最好 |
| `[文档](https://example.com)` | CommonMark 核心 | 可自定义文字，最推荐 |

⚠ 自动链接容易把句末标点一起吞掉，或者把网址里的括号截断。遇到 `https://example.com/a_(b)` 这类地址，用显式链接最稳妥。

## 2.4 表格

GFM 表格用竖线和分隔行构成：

```markdown
| 参数 | 类型 | 说明 |
|------|------|------|
| name | string | 用户名 |
| age  | number | 年龄 |
```

表格的对齐、转义和复杂场景会在下一篇展开，这里只需知道它是 GFM 扩展、不是 CommonMark 核心即可。

## 2.5 脚注

正文里写引用标记，文末写定义：

```markdown
Markdown 由 John Gruber 创造[^1]，最初的语法说明并不严格[^2]。

[^1]: 参见 Daring Fireball 上的原始文章。
[^2]: 后来出现的 CommonMark 才用示例固定了边界行为。
```

规则与细节：

- 标记名可以是数字、字母、下划线和短横线，同一文档内必须唯一。
- 定义可以写在任意位置，渲染时通常统一收拢到文末。
- 定义内容需要多段时，后续段落缩进四个空格。
- 同一个脚注可以被引用多次，编号由渲染器决定。

```markdown
这段结论需要补充说明[^long]。

[^long]: 第一段说明。

    第二段说明，需要缩进四个空格。
```

⚠ 脚注**不在 GFM 规范正文**里，它是 GitHub 2021 年加入的产品功能。VitePress、MkDocs 等站点工具通常需要插件或配置才能启用。把关键结论放进脚注，在部分平台上会直接丢失层次。

## 2.6 围栏代码块的语言标识

围栏代码块本身是 CommonMark 核心，GFM 强化了语言标识的展示与高亮：

````markdown
```python
# 计算平均值
def mean(values):
    return sum(values) / len(values)
```
````

语言标识写在开围栏之后，常见取值包括 `js`、`ts`、`python`、`java`、`go`、`bash`、`sql`、`yaml`、`json`、`text`。写不准时宁可写 `text`，也不要留空。

## 2.7 GitHub 平台特性

以下语法只在 GitHub 网页端生效，**不属于可移植的 Markdown**：

```markdown
@octocat 请看一下这个改动。
修复了 #123 描述的问题。
这个思路很棒 :+1:
```

支持的写法：

| 语法 | 效果 | 可移植性 |
|------|------|----------|
| `@用户名` | 提及用户并通知 | 仅 GitHub 系 |
| `#123` | 链接到 Issue 或 PR | 仅 GitHub 系 |
| `:smile:` | 渲染 emoji | 部分平台支持 |
| `> [!NOTE]` | 告警块 | 仅 GitHub 系 |

告警块写法：

```markdown
> [!WARNING]
> 执行前请先备份数据库。
```

支持的类型有 `NOTE`、`TIP`、`IMPORTANT`、`WARNING`、`CAUTION`，类型名必须大写。

★ **关键认知**：平台特性与 Markdown 扩展要分开看。GFM 规范里的表格、任务列表已被广泛实现；`@提及`、告警块则是 GitHub 的渲染约定，换到别的平台就是普通文本。判断标准很简单：**看它是否写进了 GFM 规范**。

# 3. 兼容性与降级

## 3.1 平台支持矩阵

下表中的"原生"指开箱即用，"配置"指需要插件或开启扩展，"不支持"指会原样显示：

| 特性 | CommonMark | GitHub | VS Code 预览 | VitePress | MkDocs Material |
|------|------------|--------|--------------|-----------|-----------------|
| 表格 | 不支持 | 原生 | 原生 | 原生 | 原生 |
| 任务列表 | 不支持 | 原生 | 原生 | 配置 | 配置 |
| 删除线 | 不支持 | 原生 | 原生 | 原生 | 配置 |
| 自动链接 | 不支持 | 原生 | 原生 | 原生 | 配置 |
| 脚注 | 不支持 | 原生 | 原生 | 配置 | 配置 |
| 告警块 | 不支持 | 原生 | 不支持 | 配置 | 不支持 |
| 数学公式 | 不支持 | 原生 | 原生 | 配置 | 配置 |

版本会变化，上表只表达相对关系。真正落地前，用目标平台实际渲染一次，比查文档可靠。

## 3.2 降级策略

写跨平台文档时，可以按下面的顺序取舍：

1. **关键信息只用核心语法**：结论、警告、步骤不要只存在于告警块或脚注里。
2. **扩展用于增强**：表格、任务列表能提升可读性，但去掉后信息仍然完整。
3. **平台特性加兜底**：`@提及` 旁边写清用户名，告警块前面用粗体写"注意"。
4. **在 CI 里验证**：用目标渲染器构建一次，检查是否有原样输出的标记。

★ **关键认知**：文档的可移植性由**目标平台的最小公倍数**决定，而不是由你本地编辑器决定。在 Typora 里好看，不等于在 GitHub、公司 Wiki 和静态站点上都好看。

# 4. 常见坑

| 现象 | 原因 | 修复 |
|------|------|------|
| 任务列表显示成普通文本 | 方括号内空格位置不对 | 写成 `- [ ]` 或 `- [x]` |
| 删除线只有一边生效 | 用了单个 `~` 或符号不配对 | 统一用 `~~` |
| 网址末尾多了标点 | 自动链接把句号吞进去 | 改用显式 `[文字](url)` |
| 表格列数错乱 | 单元格里的竖线没转义 | 写成 `\|` |
| 脚注编号重复 | 标记名在同一文档重复 | 保证标记名唯一 |
| 告警块不显示 | 平台不支持该语法 | 改成粗体提示或引用块 |
| 任务列表嵌套错位 | 子项缩进不足 | 子项相对父项缩进 2 到 4 空格 |

⚠ 另一个隐蔽问题是表格与脚注的**渲染顺序**：表格单元格里的脚注标记在部分实现中不会被收集，导致脚注定义悬空。重要注释尽量写在正文段落里。

# 5. 动手练习

1. 写一个包含任务列表、删除线、脚注和表格的待办文档，分别在 GitHub 和本地 VS Code 预览中查看，记录差异。
2. 把一段使用 `@提及` 和 `> [!NOTE]` 的 GitHub 文档改写成可移植版本，要求换到任意平台后信息不丢失。
3. 故意写出三种错误：`[ x]`、单个 `~` 删除线、表格里未转义的竖线，观察渲染结果并修复。

```bash
# 用 markdownlint 检查扩展语法是否写规范
npx markdownlint-cli2 "docs/**/*.md"
```

# 6. 小结

| 扩展 | 写法 | 可移植性 |
|------|------|----------|
| 任务列表 | `- [ ]`、`- [x]` | 广，但站点工具常需配置 |
| 删除线 | `~~文字~~` | 广，统一用双波浪号 |
| 自动链接 | 裸 URL、`www.`、邮箱 | 广，但标点易误吞 |
| 表格 | 竖线加分隔行 | 广 |
| 脚注 | `[^1]` 加定义 | 中，部分平台需插件 |
| 告警块 | `> [!NOTE]` | 仅 GitHub 系 |

记住一条判断标准：写进 GFM 规范的扩展可以放心用，GitHub 产品特性则要准备降级方案。
