Markdown 是写文档、README、博客和技术笔记最常用的轻量标记语言。它的语法很少，但"看起来能渲染"和"写得规范、跨平台一致"是两件事。本篇从设计定位和解析流程讲起，把标题、段落、强调、列表、链接、引用、代码这些基础语法一次讲清，并指出初学者最容易踩的坑。

# 1. Markdown 是什么

## 1.1 定位与设计哲学

Markdown 由 John Gruber 在 2004 年提出，目标是让作者用**纯文本**写作，同时源码本身就可读，需要时再转换成 HTML。

| 场景 | 典型产物 |
|------|----------|
| 代码仓库文档 | README、CONTRIBUTING、CHANGELOG |
| 技术笔记 | 学习笔记、会议记录 |
| 博客与静态站点 | VitePress、Hugo、Hexo 的内容源 |
| 协作平台 | GitHub Issue、Pull Request 描述 |
| 知识库 | Obsidian、Notion 导入导出 |

它的三条设计原则值得记住：

- **源码可读**：不渲染也能看懂结构，`**粗体**` 比 `<strong>粗体</strong>` 更接近自然书写。
- **纯文本**：能进 Git，能 diff，能用任何编辑器打开。
- **关注内容而非样式**：Markdown 只描述"这是标题、这是列表"，具体字体和颜色交给 CSS。

★ **关键认知**：Markdown 是**源格式**，不是排版软件。它刻意不提供字号、颜色、居中这类控制，因为一旦能精细排版，源码就会退化成另一种 HTML。需要复杂版式时，正确做法是交给主题或 CSS，而不是在正文里堆 HTML。

## 1.2 从文本到 HTML 的解析流程

Markdown 渲染不是"逐条替换符号"，而是分两个阶段构建语法树：

```text
┌──────────────┐
│  Markdown    │  纯文本源文件
└──────┬───────┘
       ▼
┌──────────────┐
│  块级解析     │  识别标题、列表、引用、代码块、段落
└──────┬───────┘
       ▼
┌──────────────┐
│  行内解析     │  在块内部识别强调、链接、行内代码
└──────┬───────┘
       ▼
┌──────────────┐
│     AST      │  抽象语法树
└──────┬───────┘
       ▼
┌──────────────┐
│    HTML      │  交给浏览器或主题样式
└──────────────┘
```

两个阶段的分工非常关键：

- **块级解析**先决定文档骨架：哪几行构成一个列表，哪些行属于代码块内部，引用到哪里结束。
- **行内解析**只在块内部生效，处理 `*强调*`、`[链接](url)`、`` `代码` `` 等。

★ **关键认知**：块级结构优先于行内规则。代码块和行内代码内部的内容不会被再次解析，所以 `` `**不是粗体**` `` 会原样显示。理解这一点，就能解释大部分"为什么我的符号没生效"的问题。

## 1.3 标准与方言

Markdown 最初只有一份非正式语法说明，各实现自由发挥，导致同一份文本在不同平台渲染不同。后来出现了两个关键标准：

| 名称 | 性质 | 说明 |
|------|------|------|
| CommonMark | 严格规范 | 用大量示例固定边界行为，解决歧义 |
| GFM | GitHub 扩展 | 在 CommonMark 之上加表格、任务列表、删除线等 |
| Markdown Extra | PHP 生态扩展 | 表格、脚注、定义列表等 |
| Pandoc Markdown | 文档转换扩展 | 面向学术写作，功能最多 |

⚠ 同一份文档在 GitHub、VS Code、Typora、静态站点生成器里可能显示不同，根源就是方言不同。写跨平台文档时，应尽量只用 CommonMark 核心语法，扩展语法要么确认目标平台支持，要么提供降级写法。

# 2. 基础语法

## 2.1 标题

标题有两种写法，推荐使用井号形式：

```markdown
# 一级标题
## 二级标题
### 三级标题

一级标题
========

二级标题
--------
```

井号形式的规则：

- `#` 后必须有**一个空格**，`#标题` 不生效。
- 最多六级，七级及以上按普通段落处理。
- 井号数量决定层级，与缩进无关。
- 标题前后建议留空行，兼容性最好。

★ **关键认知**：标题层级是**语义结构**，不是字号工具。不要为了"字小一点"从一级直接跳到四级。正确的层级让目录、锚点、屏幕阅读器和搜索引擎都能正确理解文档。

⚠ 下划线形式的标题有副作用：任意一行文字下面跟一排 `=` 或 `-` 都会变成标题。所以分隔线 `---` 前面如果紧贴文字，会把那行文字变成二级标题。

## 2.2 段落与换行

段落由一个或多个连续文本行组成，**空行**才是段落分隔符。

```markdown
这是第一段。
这一行仍属于第一段。

这是第二段。
```

单个换行在渲染后通常变成一个空格，这叫**软换行**。需要强制换行时有两种写法：

```markdown
行尾加两个空格，再换行  
这一行会另起一行

行尾加反斜杠，再换行\
这一行也会另起一行
```

也可以直接写 `<br>`，但会引入 HTML，移植性略差。

⚠ 行尾两个空格是**不可见字符**，很多编辑器保存时会自动删除，导致换行失效。团队协作时更推荐反斜杠或 `<br>`。

## 2.3 强调：粗体与斜体

```markdown
*斜体*、_斜体_
**粗体**、__粗体__
***粗斜体***
```

经验规则：

- 中文正文里优先用 `*` 和 `**`，避免下划线在词内不生效的问题。
- 强调符号内侧不要留空格：`** 粗体 **` 不会生效。
- 强调符号外侧最好留空格或标点，避免和相邻文字粘连。

★ **关键认知**：下划线形式的强调有**词内限制**。像 `foo_bar_baz` 这种词内下划线不会被当成斜体，这是为了避免破坏变量名和文件名。所以写代码标识符时不必担心下划线被吃掉，但也意味着中文夹英文时 `_斜体_` 的行为更依赖上下文。

## 2.4 列表

无序列表可用 `-`、`*`、`+`，有序列表用数字加点：

```markdown
- 第一项
- 第二项
  - 嵌套项
  - 另一个嵌套项

1. 准备环境
2. 编写代码
3. 运行测试
```

规则与细节：

- 符号后必须有空格。
- 嵌套靠缩进，通常 2 到 4 个空格，同一份文档内要统一。
- 列表项之间留空行会变成**松散列表**，每项被包进 `<p>`，间距更大。
- 有序列表的实际编号由渲染器决定，第一项写 `1.` 最常见。

⚠ 同一列表里混用 `-` 和 `*`，部分解析器会把它当成两个独立列表重新开始。缩进不足也会让嵌套项跳出列表，变成普通段落。

## 2.5 链接与图片

行内链接最常见：

```markdown
[OpenAI](https://openai.com)
[OpenAI](https://openai.com "OpenAI 官网")
```

引用式链接适合在文末集中管理地址：

```markdown
请先阅读[安装文档][install]，再查看[配置说明][config]。

[install]: https://example.com/install
[config]: https://example.com/config "配置说明"
```

图片语法只比链接多一个感叹号：

```markdown
![系统架构图](images/arch.png "系统架构")
```

★ **关键认知**：引用式链接的价值在于**地址与正文分离**。同一地址在文中出现多次时，只需维护一处；文末的链接定义也不会打断阅读。长文档和需要频繁换域名的项目尤其适合。

## 2.6 引用

```markdown
> 这是一段引用。
> 引用可以有多行。

> 外层引用
>> 嵌套引用

> 引用里也可以放列表：
> - 第一项
> - 第二项
```

引用用 `>` 开头，可以嵌套，也可以包含标题、列表、代码块等其他块级元素。连续多行只在第一行写 `>` 也能延续，这叫懒 continuation，但显式每行都写更清晰。

## 2.7 行内代码与代码块

行内代码用反引号包裹：

```markdown
执行 `npm run build` 生成静态文件。
```

代码块用三个反引号围起来，并在开头标注语言：

````markdown
```js
// 计算两数之和
function add(a, b) {
  return a + b;
}
```
````

也可以用三个波浪号 `~~~`，效果类似。缩进四个空格也能形成代码块，但无法标注语言，不推荐在新文档中使用。

★ **关键认知**：代码块的语言标识不只是"好看"。它决定语法高亮、部分平台的复制按钮行为，也影响文档站点的搜索索引。养成"开围栏就写语言"的习惯，纯文本也要写 `text`。

## 2.8 分隔线

一行中三个及以上的 `-`、`*` 或 `_` 单独成行，会渲染成分隔线。

⚠ 分隔线必须单独成行，且前后留空行。紧跟在文字下面的 `---` 会被解析成二级标题的下划线，而不是分隔线。

# 3. 转义与特殊字符

Markdown 的语法符号可以用反斜杠转义：

```markdown
\*不是斜体\*
\# 不是标题
1\. 不是有序列表
\[不是链接\]
```

常见可转义字符：`\`、`` ` ``、`*`、`_`、`{}`、`[]`、`()`、`#`、`+`、`-`、`.`、`!`、`|`、`>`。

需要显示 HTML 特殊字符时，可以用实体：

```markdown
小于号写成 &lt;，大于号写成 &gt;，版权号写成 &copy;
```

⚠ 中文输入法下容易打出全角符号，例如全角 `＃`、全角 `＊`，它们不是 Markdown 语法，不会生效。写文档时切换到半角符号输入。

# 4. 常见错误

| 现象 | 原因 | 修复 |
|------|------|------|
| 标题没生效 | `#` 后缺空格，或用了全角 `＃` | 改成半角 `#` 加空格 |
| 粗体没生效 | 符号内侧有空格 | 写成 `**文字**` |
| 换行没生效 | 行尾空格被编辑器删除 | 用反斜杠或 `<br>` |
| 列表断成两段 | 混用符号或缩进不一致 | 统一符号与缩进 |
| 分隔线变成标题 | `---` 紧贴上一行文字 | 前后加空行 |
| 链接 404 | 相对路径写错 | 以当前文件为基准检查 |
| 代码块内容被渲染 | 围栏反引号数量不足 | 外层用更多反引号 |
| 表格错列 | 单元格里的竖线没转义 | 写成 `\|` |

# 5. 动手练习

1. 新建一个 `README.md`，包含一级标题、简介段落、无序列表、一个行内代码和一段带语言标注的代码块，然后用 VS Code 预览检查。
2. 故意制造三个错误：`#标题` 不带空格、`** 粗体 **` 内侧带空格、`---` 紧贴文字。观察渲染结果并说明原因。
3. 用引用式链接改写一段包含五个重复链接的文字，把地址集中到文末，体会维护成本的差异。

```bash
# 用 pandoc 把 Markdown 转成 HTML，验证真实渲染结果
pandoc README.md -f gfm -t html -o readme.html
```

# 6. 小结

| 语法 | 写法 | 关键点 |
|------|------|--------|
| 标题 | `# 标题` | `#` 后必须有空格，最多六级 |
| 段落 | 空行分隔 | 单换行是软换行 |
| 强调 | `**粗体**`、`*斜体*` | 符号内侧不留空格 |
| 列表 | `- 项`、`1. 项` | 缩进统一，符号不混用 |
| 链接 | `[文本](url)` | 引用式适合集中管理 |
| 图片 | `![alt](src)` | alt 描述内容而非"图片" |
| 引用 | `> 内容` | 可嵌套、可含其他块 |
| 代码 | 围栏加语言 | 代码内部不再解析 |
| 分隔线 | `---` | 必须单独成行 |
