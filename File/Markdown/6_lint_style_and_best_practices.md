Markdown 语法简单，团队协作时却很容易写散：有人用 `-` 有人用 `*`，有人标题跳级，有人图片路径大小写混乱。这些问题单看不大，积累起来就会让文档难以维护。本篇讲如何用 lint 工具和团队规范把写法固定下来，并给出可执行的检查清单。

# 1. 为什么需要 lint

## 1.1 一致性的成本

一篇文档的写法不一致，读者最多觉得"有点乱"；一百篇文档不一致，维护者就要为每次改动重新判断风格。常见分歧包括：

| 分歧点 | 写法 A | 写法 B |
|--------|--------|--------|
| 无序列表符号 | `-` | `*` |
| 标题层级 | 从一级逐级下降 | 按视觉需要跳级 |
| 行宽 | 一行一句 | 按 80 列折行 |
| 代码围栏 | 反引号 | 波浪号 |

这些分歧没有绝对的对错，但**同一项目内必须统一**。统一之后，评审只需关注内容，工具也能自动检查。

## 1.2 lint 能发现什么

| 类别 | 例子 | 能否自动修复 |
|------|------|--------------|
| 结构 | 标题跳级、多个一级标题 | 部分 |
| 排版 | 行尾空格、连续空行 | 是 |
| 语法 | 围栏缺语言、裸网址 | 部分 |
| 链接 | 死链、锚点失效 | 否 |
| 资源 | 图片缺失、路径大小写错误 | 否 |

★ **关键认知**：lint 的价值不是"挑错"，而是把**团队约定变成可执行的规则**。写在文档里的规范靠人记，写进配置的规则每次提交都会跑。能自动化的约定，就不要靠自觉。

# 2. markdownlint

## 2.1 安装与运行

markdownlint 是最常用的 Markdown 检查工具，Node 生态下推荐 `markdownlint-cli2`：

```bash
npm install --save-dev markdownlint-cli2
npx markdownlint-cli2 "docs/**/*.md"
npx markdownlint-cli2 --fix "docs/**/*.md"    # 自动修复可修复项
```

也可以全局安装后运行 `markdownlint-cli2 "**/*.md" "#node_modules"`，其中 `#node_modules` 表示排除该目录。

## 2.2 配置文件

在项目根目录放 `.markdownlint.json`：

```json
{
  "MD013": false,
  "MD024": { "siblings_only": true },
  "MD033": { "allowed_elements": ["img", "br", "details", "summary"] },
  "MD041": false
}
```

配置的含义：

- `MD013` 关闭行宽限制，避免中文长句被频繁打断。
- `MD024` 只检查同级标题是否重名，不同章节下允许同名。
- `MD033` 允许少量必要的 HTML 标签。
- `MD041` 关闭"首行必须是标题"，适配有引言段的文档。

## 2.3 常用规则

| 规则 | 含义 | 建议 |
|------|------|------|
| MD001 | 标题逐级递增 | 开启，禁止跳级 |
| MD003 | 标题风格统一 | 统一用井号形式 |
| MD004 | 无序列表符号统一 | 统一用 `-` |
| MD009 | 禁止行尾空格 | 开启，可用 `--fix` |
| MD012 | 禁止连续空行 | 开启 |
| MD013 | 行宽限制 | 中文项目常关闭 |
| MD022 | 标题前后留空行 | 开启 |
| MD024 | 禁止重复标题 | 设为同级检查 |
| MD025 | 只允许一个一级标题 | 开启 |
| MD029 | 有序列表编号风格 | 统一用 `1.` 递增 |
| MD033 | 限制内联 HTML | 按需放行 |
| MD034 | 禁止裸网址 | 开启，改用显式链接 |
| MD040 | 代码围栏必须标语言 | 开启，重点规则 |
| MD046 | 代码块风格统一 | 统一用围栏 |
| MD047 | 文件以单个换行结尾 | 开启 |

★ **关键认知**：规则不是越多越好。每加一条规则，都要问"它解决的是真实问题，还是个人偏好"。像 MD013 行宽，对英文项目有意义，对中文长句频繁误报，就应该关掉或放宽，而不是让作者为了过检查把句子切碎。

## 2.4 与编辑器和 CI 集成

三种接入方式，建议同时使用：

- **编辑器**：安装 VS Code 的 markdownlint 扩展，边写边提示。
- **提交前**：用 husky 加 lint-staged，只检查改动的文件。
- **CI**：每次 Push 和 Pull Request 全量检查，防止绕过。

# 3. 标题层级

## 3.1 单一一级标题

一篇文档通常只有一个 `#` 标题，作为文档标题。小节从 `##` 开始，逐级向下。

```text
# 1. 模块总览
├── ## 1.1 基本概念
│   └── ### 1.1.1 术语定义
└── ## 1.2 使用方式
```

多个一级标题会让目录出现多个并列根节点，也会让页面标题语义混乱。

## 3.2 不跳级

```text
# 1. 模块总览
### 1.1.1 术语定义    ← 从一级直接跳到三级，目录结构断裂
```

跳级的问题不只是"不好看"：

- 自动生成的目录会出现空缺层级。
- 屏幕阅读器按层级导航时会迷惑。
- 锚点和交叉引用容易指错位置。

## 3.3 语义而非字号

标题层级表达的是**内容的从属关系**，不是视觉大小。需要小字号时，用粗体段落或样式，不要用降级标题来"调小"。

★ **关键认知**：标题是文档的**骨架**，不是排版工具。骨架一旦歪了，目录、搜索、锚点、无障碍导航都会跟着歪。判断标题是否合理，看它能不能独立构成一份大纲，而不是看它渲染出来多大。

⚠ 本仓库规定不使用四级及更深的标题。确实需要第四层时，把该行降级为段落开头的 `**小标题**`，既保留层次，又避免标题树过深。

# 4. 行宽与换行

## 4.1 软换行与硬折行

Markdown 源文件有两种常见的换行策略：

| 策略 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| 一行一句 | 每句话单独一行 | diff 清晰、易评论 | 源码行数多 |
| 按宽度折行 | 每行约 80 列 | 编辑器里整齐 | 改一句会重排多行 |
| 整段一行 | 一段不换行 | 编辑自由 | diff 粒度粗 |

三种策略渲染结果一样，差别在**维护体验**。

## 4.2 中文行宽的特殊性

MD013 默认按字符数计算，但中文一个字符占两个显示宽度。80 列的规则对中文往往过窄，导致频繁误报。

处理方式：

- 直接关闭 MD013，交给编辑器的自动折行。
- 或把上限放宽到 120 到 160。
- 表格、代码块、链接行通常需要单独豁免。

## 4.3 对 Git diff 友好

★ **关键认知**：换行策略的第一目标是**让 diff 可读**。一行一句时，改一句话只产生一行 diff；整段一行时，改一个词可能导致整段重排，评审者根本看不出改了什么。多人协作的文档，优先一行一句。

```diff
- 旧版本要求 Node 16。
+ 旧版本要求 Node 18。
```

# 5. 链接检查

## 5.1 相对链接是重灾区

文档站最常见的 404 来源：

- 文件重命名后没有更新引用。
- 相对路径基准算错。
- 锚点随标题改动失效。
- 本地大小写不敏感，线上 Linux 敏感。

## 5.2 使用检查工具

lychee 支持本地文件和锚点检查：

```bash
lychee --offline --include-fragments "./**/*.md"
```

`--offline` 只检查本地链接，适合 CI 的快速阶段；`--include-fragments` 会校验 `#锚点` 是否存在。

Node 生态可以改用 `markdown-link-check`，命令更短，但功能相对少。

## 5.3 放进 CI

```yaml
name: Docs Check

on: [push, pull_request]

jobs:
  links:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: lycheeverse/lychee-action@v2
        with:
          args: --offline --include-fragments "./**/*.md"
```

⚠ 外链检查容易受网络和目标站点限流影响，失败不代表文档有问题。建议本地链接用严格模式，外链单独跑定时任务，或允许失败。

# 6. 图片管理

## 6.1 命名与目录

推荐约定：

- 图片放在使用它的文档同级 `images/` 目录。
- 文件名用小写加连字符：`login-flow.png`。
- 不用中文、空格和特殊符号，避免 URL 编码问题。
- 同一文档的图片加序号前缀，便于排序：`01-overview.png`。

```text
guide/
├── setup.md
└── images/
    ├── 01-login.png
    └── 02-dashboard.png
```

## 6.2 格式与压缩

| 格式 | 适合内容 | 注意 |
|------|----------|------|
| PNG | 截图、图标、需要透明 | 体积大，先压缩 |
| JPEG | 照片、色彩丰富 | 有损，文字会糊 |
| WebP | 网页配图 | 兼容性已很好，体积小 |
| SVG | 流程图、图标 | 矢量清晰，注意脚本安全 |
| GIF | 短动画 | 体积大，优先用视频 |

## 6.3 alt、版权与隐私

- 每张信息型图片都要有 alt，描述它传达的信息。
- 装饰图 alt 留空，避免读屏重复播报。
- 截图前检查是否包含密钥、内网地址、真实用户数据。
- 引用外部图片前确认授权，重要图片尽量本地化。

★ **关键认知**：图片是文档的**长期负债**。它不会被 diff 审查，不会随代码重构自动更新，还占仓库体积。能用一个表格或一段文字说清的，不要用截图；必须用图时，命名、压缩、alt、版权四件事一次做全。

# 7. 文档规范

## 7.1 README 的基本结构

一个合格的 README 通常包含项目名与一句话定位、快速开始、安装、使用示例、配置说明、常见问题、贡献指南和许可证。顺序可以调整，但"这是什么、怎么用、怎么参与"三件事必须在前面。

## 7.2 模板与元信息

团队可以维护一份文档模板，固定标题结构、代码块语言、链接风格。模板不要过度约束，重点固定那些**评审时反复争论**的点。

如果使用静态站点，可以在文件头加 frontmatter：

```yaml
---
title: 快速开始
description: 十分钟搭好开发环境
order: 1
---
```

⚠ frontmatter 不是 Markdown 标准语法，纯文本预览会原样显示。只在站点工具确实需要时使用。

## 7.3 评审清单

| 检查项 | 标准 |
|--------|------|
| 标题 | 编号连续、不跳级、无四级标题 |
| 代码块 | 都有语言标识，注释是中文 |
| 链接 | 本地链接可访问，锚点存在 |
| 图片 | 路径正确、有 alt、已压缩 |
| 术语 | 同一概念全文用同一个词 |
| 结构 | 有引言、有小节、有小结 |
| 可移植性 | 关键信息不依赖平台特性 |

## 7.4 常见错误

- 标题跳级或使用四级标题，导致目录断层。
- 代码围栏漏标语言，页面没有高亮。
- 文件重命名后未更新相对链接，构建出现死链。

# 8. 动手练习

1. 在一个示例仓库里接入 markdownlint-cli2，写一份配置，要求开启标题层级、代码语言和行尾空格检查，关闭行宽检查。
2. 故意制造五处问题：标题跳级、代码块缺语言、死链、重复标题、行尾空格，运行 lint 后逐条修复。
3. 用 lychee 检查一份包含锚点链接的文档，改动一个标题后再次检查，观察锚点失效的报错。

# 9. 小结

| 主题 | 关键做法 |
|------|----------|
| lint | 规则服务团队约定，按项目裁剪 |
| 标题 | 单一 H1、逐级递增、不用四级 |
| 行宽 | 多人协作优先一行一句 |
| 链接 | 本地严格检查，外链定时检查 |
| 图片 | 小写命名、压缩、写 alt、注意隐私 |
| 评审 | 用清单代替口头约定 |

Markdown 模块到这里结束。把这六篇的要点连起来看：先掌握基础语法和解析模型，再用 GFM 扩展提升表达力，接着写对表格、代码和图片，最后用公式图表、文档站和 lint 把零散笔记变成可长期维护的知识库。工具会变，但"源码可读、结构清晰、检查自动化"这三条原则不会变。
