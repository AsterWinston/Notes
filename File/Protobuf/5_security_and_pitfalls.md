Protobuf 常被误认为"二进制所以安全"，这是误解。二进制只让人眼不易读，并不阻止恶意构造。一个几百字节的输入可以触发巨大的内存分配，一段深递归可以让栈溢出，一个被复用编号的字段可以让数据静默错位。本篇按攻击面逐条拆。

# 1. 威胁模型

## 1.1 不可信输入从哪来

```text
┌──────────────┐   公网    ┌──────────────┐
│  第三方客户端 │ ────────► │              │
└──────────────┘           │  你的服务     │
┌──────────────┐   消息队列 │              │
│  上游服务     │ ────────► │  反序列化     │
└──────────────┘           │              │
┌──────────────┐   文件/缓存│              │
│  历史数据     │ ────────► │              │
└──────────────┘           └──────────────┘
```

只要输入不是你自己刚序列化的，就应当按不可信处理。常见风险：

| 风险 | 后果 |
|------|------|
| 超大消息 | 内存耗尽、OOM |
| 深层递归 | 栈溢出、CPU 打满 |
| 超长 varint | 解析器忙等或异常 |
| 重复字段洪水 | 内存放大 |
| 未知字段膨胀 | 消息被"夹带"数据 |
| 类型混淆 | 静默错误数据 |
| 敏感字段泄漏 | 日志、链路追踪泄露 |

★ **关键认知**：Protobuf 的安全性**不来自二进制格式本身**，而来自三件事：解析器的资源限制、schema 的严格演进、以及业务层的输入校验。缺任何一环，二进制都可能成为攻击面。

# 2. 未知字段

## 2.1 保留机制

proto3 解码时遇到不认识的字段编号，不会报错，而是把原始字节存进 `unknownFields`，再次序列化时原样写回。

```go
// 伪代码示意
msg := &pb.User{}
proto.Unmarshal(data, msg)
// msg 里可能有 data 中 schema 未定义的字段
// 再次序列化时这些字节会保留
```

Java 里对应 `getUnknownFields()`，Python 里对应内部 `_unknown_fields`。

## 2.2 未知字段的两面性

好处：

- 新服务端加字段，老网关透传不丢数据。
- 多版本共存时，中间层不需要频繁升级。

风险：

- **数据夹带**：攻击者往消息里塞大量未知字段，中间层原样转发，放大存储和带宽。
- **容量膨胀**：未知字段没有 schema 约束，可以任意长。
- **审计盲区**：日志里看不到这些字段，但它们确实在传输。

正常的 `Ping { int64 ts = 1; }` 只有 1 个字段；攻击者可以再加 1000 个未知编号字段，每个几十 KB，解析后 `unknownFields` 占用数 MB，转发给下游时还会原样带过去。

⚠ **关键认知**：如果服务只做"解析后转发"，应在边界处**显式丢弃未知字段**，而不是默认保留。Go 的 `proto.UnmarshalOptions{DiscardUnknown: true}`、Java 的 `DiscardUnknownFields` 都能做到。

## 2.3 该保留还是丢弃

| 场景 | 建议 |
|------|------|
| 网关透传 | 保留，但要限总大小 |
| 业务服务入口 | 丢弃，减少攻击面 |
| 存储到数据库 | 丢弃，避免历史脏数据累积 |
| 日志采集 | 丢弃，避免泄漏与膨胀 |

# 3. 反序列化资源耗尽

## 3.1 消息大小限制

```go
grpc.NewServer(
    grpc.MaxRecvMsgSize(4*1024*1024),   // 单条消息最大 4 MB
)
// Java 对应 maxInboundMessageSize(4 * 1024 * 1024)
```

★ **关键认知**：**大小限制必须放在最外层**（gRPC、HTTP body、消息队列消费者），而不是等 `Unmarshal` 之后检查。因为内存是在解析过程中分配的，解析完再检查已经晚了。

## 3.2 递归深度

`message Node { Node child = 1; }` 这样的自引用消息，可以被构造成上万层嵌套。解析器递归下降，每层占栈帧，最终栈溢出；即使不溢出，CPU 也会被拖垮。

```java
CodedInputStream in = CodedInputStream.newInstance(bytes);
in.setRecursionLimit(100);        // 递归上限，默认 100
in.setSizeLimit(4 * 1024 * 1024); // 同时限制总大小
User.parseFrom(in);
```

Go 的默认递归上限是 10000，超限返回错误，不会静默截断，业务层应再收紧。

⚠ **关键认知**：**递归深度限制要显式设置**。默认值可能偏宽松（Go 的默认上限是 10000 层），对大多数业务来说 50~100 层已经足够。深度攻击的特点是输入很小、开销很大，是典型的低成本 DoS。

## 3.3 重复字段洪水

`message M { repeated string items = 1; }`：攻击者传一个长度前缀很大、实际元素极多的 packed 字段，解析后生成巨大的 slice。即使总字节数在限制内，**对象数量**也可能爆掉。

```text
100 万个空字符串 packed 后只有约 1 MB
解析后变成 100 万个 Go string 头（每个 16 字节）= 16 MB
```

★ **关键认知**：只限制**字节数**不够，还要限制**元素数量**。业务层对 `repeated` 字段做 `len()` 检查，或用流式解析逐条处理，避免一次性展开。

# 4. 类型混淆

## 4.1 同 wire type 的陷阱

同编号的字段，A 定义成 `int32 value = 1`，B 定义成 `uint32 value = 1`。两者都是 VARINT，字节层面能读，但 `-1` 在 B 里会变成 `4294967295`。没有异常，没有日志，只有业务数据悄悄出错：A 发出 10 字节的 `FF...01`，B 按 uint32 读出 4294967295，业务判断 `value > 0` 时误判为超大值。

## 4.2 编号复用的连锁反应

v1 里 `string name = 2`，v2 没有 `reserved` 就把编号 2 分配给 `int64 phone`。数据库里的老数据是 `[2] = "alice"`，新代码会把字符串当 varint 读，结果解析失败，或者读出一个荒谬的数字。

⚠ **关键认知**：类型混淆的根源几乎都是**编号被复用**。`reserved` 不是风格建议，而是防止这类事故的硬约束。线上任何"数字莫名其妙变大"的 bug，先查编号有没有被复用。

## 4.3 oneof 的类型混淆

v1 里 `string a = 1; string b = 2;` 是两个普通字段，v2 把它们放进同一个 `oneof`。字节完全兼容，但 v1 可以同时设置 `a` 和 `b`，v2 只保留一个。**这是语义不兼容**，静态检测工具未必能报。

★ **关键认知**：兼容性检查要分两层看：**线格式兼容**（字节能不能读）和**语义兼容**（读出来是不是同一个意思）。工具能覆盖前者，后者必须靠评审和契约文档。

# 5. 敏感数据

## 5.1 Protobuf 不加密

```protobuf
message Login {
  string username = 1;
  string password = 2;   // 明文，序列化后依然是明文
}
```

```text
序列化后：0A 05 61 6C 69 63 65 12 08 70 61 73 73 77 6F 72 64
                                            └─ "password" 直接可见
```

只要拿到字节，用 `protoc --decode_raw` 就能看到字符串。**Protobuf 不是加密格式**。

## 5.2 常见泄漏点

| 泄漏点 | 说明 |
|--------|------|
| 日志打印整个消息 | `log.info("{}", request)` 会把敏感字段写进日志 |
| 链路追踪 | 框架自动记录请求体 |
| 错误信息 | 解析异常把原始字节带进堆栈 |
| 数据库字段 | 敏感字段明文落库 |
| 调试接口 | reflection 暴露所有字段 |

```java
// 危险：整条消息进日志
log.info("login request: {}", request);

// 较好：只记录非敏感字段
log.info("login user={}, ip={}", request.getUsername(), clientIp);
```

★ **关键认知**：Protobuf 生成的 `toString()` 会输出**所有字段**，包括密码、token、身份证号。很多框架默认用 `toString()` 打日志，等于把敏感数据主动写进日志系统。要在消息设计阶段就给敏感字段加注释，并在日志层做脱敏。

## 5.3 敏感字段的处理策略

| 策略 | 做法 |
|------|------|
| 不传 | 用 token 代替密码，服务端不接收明文密码 |
| 传输加密 | TLS，或字段级加密 |
| 存储脱敏 | 只存哈希或掩码 |
| 日志脱敏 | 自定义 `toString` 或日志过滤器 |
| 最小化 | 响应里不返回不必要的字段 |

⚠ **关键认知**：`.proto` 是**公开契约**，字段名和结构会出现在客户端、文档、反射接口里。不要用字段名泄漏内部信息，比如 `internal_admin_bypass_flag`。命名要按"这份契约会被所有人看到"来设计。

# 6. 输入校验

## 6.1 schema 管不了的事

Protobuf 只保证**类型正确**，不保证**业务合法**：

```protobuf
message Order {
  int64  amount   = 1;   // 可以是负数
  string currency = 2;   // 可以是任意字符串
  int32  quantity = 3;   // 可以是 0 或负数
}
```

```java
// 这些都能通过反序列化
Order.newBuilder()
    .setAmount(-100)
    .setCurrency("NOT_A_CURRENCY")
    .setQuantity(0)
    .build();
```

## 6.2 校验层次

```text
┌─────────────────────────────────────┐
│ 传输层：大小、超时、TLS              │
├─────────────────────────────────────┤
│ 解析层：递归深度、未知字段、元素数量 │
├─────────────────────────────────────┤
│ 业务层：范围、格式、枚举白名单       │
├─────────────────────────────────────┤
│ 持久层：唯一约束、外键、事务         │
└─────────────────────────────────────┘
```

```java
// 业务校验示例
if (order.getAmount() <= 0) {
    throw new IllegalArgumentException("amount must be positive");
}
if (order.getQuantity() > 1000) {
    throw new IllegalArgumentException("quantity too large");
}
if (!ALLOWED_CURRENCIES.contains(order.getCurrency())) {
    throw new IllegalArgumentException("unsupported currency");
}
```

★ **关键认知**：**schema 是类型契约，不是业务校验器**。`int64` 能表达任意 64 位整数，包括你不想要的负数和天文数字。凡是进入业务的字段，都要在边界处做范围、格式、枚举白名单校验。

# 7. 各语言的注意点

## 7.1 Java

- 旧版 `com.google.protobuf` 与 `protobuf-java-util` 版本要对齐。
- 使用 `CodedInputStream` 时显式设置 `setRecursionLimit` 和 `setSizeLimit`。
- `parseFrom(byte[])` 没有大小上限，公网入口不要直接用。
- `toString()` 会输出全部字段，敏感消息要重写日志输出。

## 7.2 Go

- `proto.Unmarshal` 对超大输入会一次性分配，先在 gRPC 层限制。
- 用 `proto.UnmarshalOptions{DiscardUnknown: true}` 丢弃未知字段。
- 注意 `proto.Clone` 会复制 unknown fields，可能放大内存。
- 不要直接把 `[]byte` 转成 `string` 后长期持有，避免大对象无法回收。

## 7.3 Python

- `ParseFromString` 同样没有大小限制。
- 动态消息（`message_factory`）要防止用不可信的 descriptor 构造类型。
- `_pb2` 模块的 import 有副作用，热加载时注意。

⚠ **关键认知**：不同语言的默认限制不一样，**不要假设默认值安全**。Go 的递归上限 10000、Java 的 100，差了两个数量级。跨语言服务要把限制写进配置，而不是依赖库默认。

# 8. 检查清单

| 检查项 | 做法 |
|--------|------|
| 消息大小 | 入口限制 1~4 MB，按业务调整 |
| 递归深度 | 显式设置 50~100 |
| 元素数量 | 对 repeated 做 `len()` 上限 |
| 未知字段 | 业务入口丢弃，网关按需保留 |
| 编号复用 | CI 跑 `buf breaking` |
| 类型变更 | 按 wire type 判断，不凭记忆 |
| 敏感字段 | 不落日志，不返前端，必要时加密 |
| 业务校验 | 范围、格式、枚举白名单 |
| 依赖版本 | protoc、插件、运行时对齐 |

# 9. 练习

1. 写一个递归消息 `Node { Node child = 1; }`，构造 200 层嵌套并序列化，然后在 Java 里用默认配置解析，观察是否抛异常。再把递归限制调到 50，对比行为。
2. 用 `protoc --decode_raw` 解码一段包含用户名的消息，验证字符串是否明文可见。据此说明为什么不能把密码明文放进 proto。
3. 设计一个公网入口的消息处理流程，列出四层防护（传输、解析、业务、持久）各做什么，并说明如果只做其中一层会有什么风险。

# 10. 小结

| 风险 | 核心对策 |
|------|----------|
| 未知字段夹带 | 业务入口 `DiscardUnknown`，限制总大小 |
| 超大消息 | 入口层限制字节数，解析前拦截 |
| 深递归 | 显式设置递归上限 |
| 元素洪水 | 限制 repeated 长度，流式处理 |
| 类型混淆 | 禁止复用编号，`buf breaking` 进 CI |
| 敏感数据 | 不明文传输、不落日志、不返前端 |
| 业务非法值 | schema 之外再做范围与白名单校验 |
| 默认配置 | 不假设库默认安全，写进配置 |
