学完语法、命名空间、schema、解析、XPath、JAXB 和安全之后，最后要回答的是工程问题：什么时候用 XML，契约怎么管，性能和安全如何长期守住。本篇把前七篇的结论收拢成一份可执行的实践清单。

# 1. 选型：XML、JSON 还是 YAML

## 1.1 三种格式的定位

| 格式 | 最擅长 | 典型场景 |
|------|--------|----------|
| XML | 结构约束、命名空间、文档混合内容 | SOAP、行业报文、Office/SVG、配置文件 |
| JSON | 轻量数据交换、浏览器友好 | Web API、日志、消息 payload |
| YAML | 人类可读的层级配置 | K8s、CI/CD、应用配置 |

一句话记忆：**机器传数据优先 JSON，人写配置优先 YAML，需要严格契约和文档能力时用 XML**。

## 1.2 决策表

| 需求 | 推荐 | 理由 |
|------|------|------|
| 浏览器/移动端 API | JSON | 原生支持、体积小、解析快 |
| 企业标准报文 | XML | 命名空间、XSD、行业规范成熟 |
| 需要数字签名 | XML | XMLDSig 生态完整 |
| 需要 XSLT 转换 | XML | 样式表生态成熟 |
| 复杂表单/文档 | XML | 混合内容表达力强 |
| 应用配置 | YAML/TOML | 可读、可注释 |
| 日志与事件 | JSON | 易检索、工具链丰富 |
| 简单键值 | Properties/TOML | 歧义少 |

## 1.3 不要为了统一而硬转

三种格式可以互转，但会丢信息：

- XML 的命名空间在 JSON 里没有原生对应。
- 属性与子元素的区别在 JSON 里会消失。
- 注释、CDATA、处理指令通常无法保留。
- 日期和数字类型可能退化成字符串。

★ **关键认知**：选型应该跟随**生态和契约**，而不是个人偏好。已有 SOAP 客户端的系统不会因为 JSON 更流行就立刻换协议；新 Web API 也没有必要为了"企业感"套一层 XML。

# 2. Schema 管理

## 2.1 契约优先

推荐先写 XSD，再生成或手写 Java 类：

```text
XSD 契约 ── 代码生成 ──→ Java 类
   │                         │
   └── 文档、校验、测试用例 ◀─┘
```

好处：

- 契约和实现分离，前后端可以并行。
- 生成代码减少手写映射错误。
- XSD 本身就是可执行的文档。

生成代码不要手改，否则下次生成会被覆盖。需要扩展行为时，用组合或适配层，不要直接在生成类里加业务逻辑。

## 2.2 版本与兼容

| 变更 | 兼容性 | 建议 |
|------|--------|------|
| 增加可选元素 | 通常兼容 | 老客户端忽略即可 |
| 增加必填元素 | 不兼容 | 升大版本或先灰度 |
| 删除元素 | 不兼容 | 保留一段时间并标记废弃 |
| 修改类型 | 不兼容 | 新增字段替代，不要原地改 |
| 修改元素顺序 | 不兼容 | `sequence` 下尤其危险 |
| 修改命名空间 | 不兼容 | 视为新契约 |

版本策略：

- 小改动靠可选字段和默认值。
- 大改动用命名空间区分，例如 `https://example.com/order/v2`。
- 不要用元素名带版本号（`orderV2`），命名空间更清晰。
- 保留旧 schema 一段时间，给客户端迁移窗口。

## 2.3 校验位置

- **入口校验**：接收外部 XML 时做 schema 校验，拒绝结构错误的数据。
- **出口校验**：对外发送关键报文前，用同一份 schema 校验，避免生成错误结构。
- **内部不重复校验**：同一份数据在链路里反复校验会浪费性能，边界校验一次即可。
- **测试校验**：把合法/非法样例纳入回归测试。

⚠ schema 校验解决不了业务规则。价格不能为负、订单状态流转是否合法，仍然要在业务层校验。

# 3. 设计规范

## 3.1 命名与结构

- 元素名用一致的风格，常见是 lowerCamel 或 kebab-case，不要混用。
- 避免无意义的 `data`、`value`、`item` 层层嵌套。
- 控制层级深度，超过五六层通常说明模型需要拆分。
- 重复数据用重复元素，不要用逗号拼接字符串。
- 空值语义要明确：缺失、空元素、`xsi:nil` 是三种不同状态。

## 3.2 属性还是元素

| 内容 | 推荐 | 原因 |
|------|------|------|
| id、类型、单位、语言 | 属性 | 简短元数据 |
| 可重复的数据 | 元素 | 属性不能重复 |
| 长文本、富文本 | 元素 | 属性不适合长内容 |
| 需要顺序和结构约束 | 元素 | XSD 表达力更强 |

★ **关键认知**：属性适合描述"这个元素是什么"，元素适合描述"这个元素包含什么"。把业务实体全部塞进属性，会让 schema 和 XPath 都变得难写。

## 3.3 命名空间

- 一套词汇表使用一个稳定的 URI。
- URI 不要带实现细节或临时环境。
- 前缀只是书写别名，不要在代码里硬编码某个前缀。
- 默认命名空间适合主体词汇表，扩展词汇表用前缀。
- 属性默认无命名空间，需要时显式加前缀。

# 4. 性能

## 4.1 先选对解析模型

| 场景 | 选择 |
|------|------|
| 小文件、需要修改 | DOM |
| 大文件、只读统计 | SAX |
| 大文件、需要控制节奏 | StAX |
| 对象映射 | JAXB |
| 查询 | XPath，但避免全文档 `//` |
| 转换 | XSLT，缓存 `Templates` |

## 4.2 常见优化

- 复用 `JAXBContext`、`Schema`、`Templates`、编译后的 `XPathExpression`。
- 不要在循环里重复创建工厂和解析器。
- 不要用字符串拼接生成 XML，用 StAX 或 Marshaller，避免转义错误。
- 关闭不需要的特性，例如命名空间、DTD、XInclude。
- 大文件不要整体读入 `String` 再解析，直接用流。
- 对重复解析的静态配置，可以缓存解析结果。

★ **关键认知**：XML 性能问题通常不是"XML 太慢"，而是**模型选错或对象创建过多**。用 DOM 解析 1 GB 文件，换任何解析库都救不了内存。

## 4.3 大文件策略

```text
单文件很大
   │
   ├─ 只需要部分字段 → StAX 跳过无关子树
   ├─ 只需要统计 → SAX 计数器
   ├─ 需要分片处理 → 按记录边界切分，逐片解析
   └─ 需要随机访问 → 先落库/建索引，不要硬上 DOM
```

# 5. 安全

## 5.1 解析器加固清单

- 禁用 DOCTYPE。
- 禁用外部通用实体和参数实体。
- 禁用外部 DTD 加载。
- 禁用 XInclude。
- 禁止外部 schema 和外部样式表。
- 限制请求体大小、解析时间、实体展开数量。
- 解析服务使用低权限账号，限制内网访问。

```java
var factory = javax.xml.parsers.DocumentBuilderFactory.newInstance();
factory.setFeature(
        "http://apache.org/xml/features/disallow-doctype-decl", true);
factory.setFeature(
        "http://xml.org/sax/features/external-general-entities", false);
factory.setFeature(
        "http://xml.org/sax/features/external-parameter-entities", false);
factory.setXIncludeAware(false);
factory.setExpandEntityReferences(false);
```

## 5.2 输入输出边界

- 不信任任何外部 XML，包括"内部系统"传来的文件。
- 不要把解析结果原样拼进 SQL、HTML 或日志。
- 错误信息不要回显文件内容、绝对路径和堆栈细节。
- 不要执行用户提交的 XSLT。
- 记录日志时对敏感字段脱敏，避免把整份报文打出来。

# 6. 工程实践

## 6.1 测试

| 测试 | 目的 |
|------|------|
| 良构测试 | 确认解析器能读合法文档 |
| schema 合法/非法样例 | 确认约束生效 |
| 安全载荷测试 | 确认 XXE 被拦截 |
| 序列化回归 | 确认字段、命名空间、日期格式不变 |
| 大文件测试 | 确认内存和耗时在预算内 |
| 模糊测试 | 发现解析器边界问题 |

## 6.2 排错

解析错误通常包含行号和列号，先定位到具体位置，再判断是语法、编码还是命名空间问题：

```text
报错：The element type "book" must be terminated by the matching end-tag
  → 检查标签闭合和嵌套
报错：Namespace prefix "o" is not declared
  → 检查 xmlns 声明和作用域
报错：cvc-complex-type.2.4.a: Invalid content was found
  → 检查元素顺序、类型或命名空间
```

## 6.3 依赖管理

- JAXB 的 API 和 runtime 版本要匹配。
- XSLT 2.0/3.0 需要 Saxon，JDK 自带实现主要是 1.0。
- 解析器实现尽量统一，避免同一进程里多个 Xerces/Woodstox 版本冲突。
- 定期升级解析器，安全补丁通常修的就是外部实体和资源消耗问题。

# 7. 学习路径

```text
入门：1 语法 → 2 命名空间
      │
      ▼
契约：3 DTD/XSD
      │
      ▼
处理：4 DOM/SAX/StAX → 5 XPath/XSLT
      │
      ▼
工程：6 JAXB → 7 安全 → 8 实践
```

如果只记三句话：

1. **先判断需不需要 XML**，不要默认用它传 API 数据。
2. **有契约就写 schema**，并在边界校验。
3. **解析不可信 XML 必须加固**，禁 DTD、禁外部实体。

# 8. 常见错误

| 错误 | 后果 | 修正 |
|------|------|------|
| 默认解析器解析用户 XML | XXE、SSRF、文件读取 | 显式禁用 DTD 和外部实体 |
| schema 与实例命名空间不一致 | 校验失败或对象为空 | 对齐 `targetNamespace` 与 `xmlns` |
| 用 DOM 处理超大文件 | 内存溢出 | 换 SAX/StAX 或分片 |
| 字符串拼接生成 XML | 转义错误、结构破坏 | 用 Marshaller 或 StAX Writer |
| `javax` 与 `jakarta` 混用 | `ClassNotFoundException` | 统一包名和依赖版本 |
| 把 schema 校验当业务校验 | 非法业务值通过 | 业务层补规则校验 |
| 复用非线程安全对象 | 并发数据错乱 | 缓存 Context/Templates，新建 Marshaller |
| 加载远程 schema | 启动慢、SSRF 风险 | 使用本地文件或 catalog |

# 9. 动手练习

1. 选一份现有 XML 契约，写出对应的 XSD，并准备三个非法样例验证校验器能拒绝。
2. 给一段使用默认 `DocumentBuilderFactory` 的解析代码加上安全配置，再用文件读取载荷写回归测试。
3. 把同一份用户数据分别写成 XML、JSON、YAML，说明在 API、配置、文档三种场景下你会选哪个，以及理由。

# 10. 小结

| 主题 | 关键结论 |
|------|----------|
| 选型 | JSON 传数据，YAML 写配置，XML 管契约和文档 |
| schema | 契约优先，版本兼容靠可选字段和命名空间 |
| 设计 | 元素承载数据，属性描述元数据 |
| 性能 | 选对解析模型，复用重量级对象 |
| 安全 | 禁 DTD、禁外部实体、限制资源 |
| 测试 | 合法、非法、安全载荷、序列化回归都要覆盖 |
