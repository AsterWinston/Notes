XML 是很多企业系统、配置文件和文档格式的底层语言。语法本身不复杂，但"能解析"和"写对"之间隔着良构、编码和 schema 几道关口。本篇从最基础的文档结构讲起，把 XML 的骨架、语法规则和常见错误一次说清。

# 1. XML 的定位

## 1.1 从标记语言说起

XML（eXtensible Markup Language，可扩展标记语言）用成对的标签描述数据。它只规定"如何标记"，不规定"标记叫什么"，所以叫可扩展。

```xml
<?xml version="1.0" encoding="UTF-8"?>
<book>
  <title>XML 入门</title>
  <author>张三</author>
  <price currency="CNY">59.00</price>
</book>
```

这段文本表达了三层信息：`book` 是根元素；`title`、`author`、`price` 是子元素，顺序有业务含义；`currency` 是 `price` 的属性，描述附加信息。

★ **关键认知**：XML 是**描述结构**的格式，不是编程语言。它没有循环、条件、函数，所有行为都由解析它的程序实现。把 XML 当成"带标签的文本"，比当成"代码"更准确。

## 1.2 XML 与 HTML 的区别

两者都使用尖括号标签，但设计目标不同：

| 维度 | XML | HTML |
|------|-----|------|
| 目的 | 描述数据 | 展示页面 |
| 标签 | 自定义，大小写敏感 | 预定义，大小写不敏感 |
| 闭合 | 必须严格闭合 | 允许省略部分结束标签 |
| 错误处理 | 遇到错误即停止 | 浏览器尽量容错 |
| 校验 | 可用 DTD/XSD | 主要靠规范与浏览器 |

⚠ 不要把 HTML 的宽松习惯带进 XML。`<br>` 在 HTML 里合法，在 XML 里必须写成 `<br/>` 或 `<br></br>`。

## 1.3 典型使用场景

| 场景 | 例子 | 选择 XML 的原因 |
|------|------|-----------------|
| 企业接口 | SOAP、银行报文 | 命名空间、schema、事务规范成熟 |
| 配置文件 | Maven `pom.xml`、Spring 配置 | 层级清晰、工具支持好 |
| 文档格式 | Office Open XML、SVG、RSS | 混合内容、可转换、可校验 |
| 数据交换 | 行业标准报文 | 多方约定统一结构 |
| 构建描述 | Android 布局、Ant | 生态历史包袱与工具链 |

Web API 场景里 JSON 已取代大部分 XML；但在文档、标准报文和已有企业系统中，XML 仍不可替代。

# 2. 文档的基本结构

## 2.1 XML 声明

XML 声明描述版本和编码，通常写成：

```xml
<?xml version="1.0" encoding="UTF-8"?>
```

规则：如果写声明，必须放在文档最开头，前面不能有空白、注释或元素；`version` 必填，常用 `1.0`；`encoding` 可选，省略时默认按 UTF-8 处理；`standalone` 可选，表示是否依赖外部 DTD。

★ **关键认知**：声明不是元素，也不是注释，而是一条**处理指令**。解析器读取它来决定版本和字符编码，但它本身不属于文档数据树。

## 2.2 根元素与元素

XML 文档必须有且只有一个根元素，其他元素都包在根元素里：

```xml
<library>
  <book id="b1"><title>XML 入门</title></book>
  <book id="b2"><title>XPath 实战</title></book>
</library>
```

元素的组成：

```text
<price currency="CNY">59.00</price>
  │       │            │      │
  │       │            │      └─ 结束标签
  │       │            └──────── 文本内容
  │       └───────────────────── 属性
  └───────────────────────────── 开始标签
```

元素规则：标签区分大小写，`<Book>` 和 `<book>` 是两个元素；开始标签和结束标签必须配对；元素必须正确嵌套，不能交叉；空元素可写成 `<br/>`；元素名不能以数字开头，不能包含空格。

```xml
<!-- 正确：先开后关，后开先关 -->
<outer><inner>内容</inner></outer>

<!-- 错误：标签交叉，解析器会直接报错 -->
<outer><inner>内容</outer></inner>
```

## 2.3 属性

属性写在开始标签内部，用名字和值成对出现：

```xml
<user id="42" role="admin" active="true">
  <name>张三</name>
</user>
```

规则：属性值必须加引号，单引号或双引号都可以；同一个元素不能有两个同名属性；属性值里不能直接出现 `<`，`&` 也要转义；属性没有顺序含义；属性名区分大小写。

| 内容 | 推荐形式 | 理由 |
|------|----------|------|
| 标识、类型、单位等元数据 | 属性 | 简短、不参与业务层级 |
| 可能重复的数据 | 子元素 | 属性不能重复 |
| 长文本、富文本 | 子元素 | 属性值不适合放长内容 |
| 需要 schema 约束结构的内容 | 子元素 | 表达力更强 |

⚠ 不要把所有字段都塞进属性。属性适合描述"这个元素是什么"，不适合承载"这个元素包含什么"。

## 2.4 文本与空白

元素之间的文字叫文本节点：

```xml
<message>
  第一行
  第二行
</message>
```

XML 默认保留空白字符，包括空格、制表符和换行。解析器是否合并它们，取决于具体 API。需要保留原始排版时，可以用 `xml:space="preserve"` 提示。

★ **关键认知**：XML 里的换行和缩进也是文本的一部分。用 DOM 读取时，元素之间往往会出现只包含空白的文本节点，所以遍历子节点时通常要过滤空白，不能假设第一个子节点就是业务元素。

## 2.5 CDATA

CDATA 区段用来包裹"不希望被解析"的文本，常见于嵌入 HTML、SQL 或代码片段：

```xml
<description><![CDATA[
  <p>这是一段 HTML</p>
  <p>标签不会被 XML 解析器当成元素</p>
]]></description>
```

规则：以 `<![CDATA[` 开始，以 `]]>` 结束；中间内容原样保留，`<` 和 `&` 不需要转义；CDATA 里不能包含字符串 `]]>`；CDATA 只能出现在元素内容里，不能出现在属性值里。

⚠ CDATA 不是"万能转义"。如果内容里本身有 `]]>`，需要拆分或改用实体转义。

## 2.6 注释与处理指令

XML 注释：

```xml
<!-- 这是一条注释，不会进入数据树 -->
<book><title>XML 入门</title></book>
```

注释不能出现在 XML 声明之前，不能放在标签内部，内容不能包含 `--`，也不能以 `-` 结尾。注释不是数据，解析后通常会被忽略。

处理指令（Processing Instruction，PI）用于把指令传给特定程序：

```xml
<?xml-stylesheet type="text/xsl" href="book.xsl"?>
```

它告诉支持 XSLT 的工具用 `book.xsl` 转换当前文档。PI 的格式是 `<?目标 指令内容?>`，目标名不能是 `xml`。

# 3. 字符与转义

## 3.1 预定义实体

XML 自带五个预定义实体：

| 实体 | 字符 | 使用场景 |
|------|------|----------|
| `&lt;` | `<` | 文本里需要显示小于号 |
| `&gt;` | `>` | 文本里需要显示大于号 |
| `&amp;` | `&` | 文本里需要显示和号 |
| `&quot;` | `"` | 属性值里需要双引号 |
| `&apos;` | `'` | 属性值里需要单引号 |

```xml
<condition>a &lt; b &amp;&amp; b &gt; 0</condition>
```

这段文本解析后的内容是 `a < b && b > 0`。

## 3.2 字符引用

除了实体，还可以用 Unicode 码点表示字符：

```xml
<text>&#60;tag&#62; &#20013;&#25991;</text>
```

`&#60;` 是十进制字符引用，表示 `<`；`&#x4E2D;` 是十六进制字符引用，也表示 `中`。字符引用适合表示键盘难以输入或容易被误解析的字符。

★ **关键认知**：`&` 是 XML 的转义入口。文本里只要出现 `&`，解析器就会尝试读取实体名。想让 `&` 原样显示，必须写成 `&amp;`；想让 `<` 原样显示，必须写成 `&lt;`。这条规则在拼接 XML 字符串时最容易违反。

## 3.3 编码

编码决定字节如何映射成字符：

| 编码 | 特点 | 建议 |
|------|------|------|
| UTF-8 | 兼容 ASCII，互联网主流 | 默认首选 |
| UTF-16 | Java 内部字符串常用 | 文件交换时注意 BOM |
| GBK/GB2312 | 中文历史编码 | 只在遗留系统使用 |
| ISO-8859-1 | 单字节，不含中文 | 避免用于中文内容 |

编码不一致的典型表现是中文乱码，或者解析器在第一个非 ASCII 字符处报错。排查顺序：确认文件实际编码；确认声明里的 `encoding` 与文件一致；确认读取时没有用错字符集；确认没有多余 BOM 或不可见字符。

# 4. 良构与合法

## 4.1 什么是良构

良构（well-formed）指文档满足 XML 语法规则，解析器能完整读出结构。核心要求：

- 有且只有一个根元素。
- 所有标签正确闭合、正确嵌套。
- 属性值都有引号，且没有重复属性。
- 文本中的 `<` 和 `&` 已正确转义。
- 元素名、属性名符合命名规则。
- 注释、CDATA、处理指令的边界正确。

良构是"语法正确"，不涉及业务约束。

## 4.2 什么是合法

合法（valid）指文档不仅良构，还符合指定的 DTD 或 XSD 约束：

```text
良构 ── 语法层：标签闭合、转义正确、结构完整
  │
  ▼
合法 ── 约束层：元素顺序、出现次数、数据类型、必填项
```

下面这段 XML 是良构的：

```xml
<user><age>abc</age></user>
```

但如果 schema 规定 `age` 必须是整数，它就不合法。解析器默认只检查良构，不会自动校验 schema，需要显式开启校验。

★ **关键认知**：**良构是解析的前提，合法是业务的约定**。很多线上事故不是"XML 无法解析"，而是"能解析但字段类型或顺序不符合契约"。

## 4.3 常见错误对照

| 错误 | 错误示例 | 修复 |
|------|----------|------|
| 多个根元素 | `<a/><b/>` | 用一个根元素包起来 |
| 标签未闭合 | `<a><b></a>` | 补全 `</b>` |
| 属性无引号 | `<a id=1/>` | 写成 `id="1"` |
| 重复属性 | `<a id="1" id="2"/>` | 合并或改名 |
| 文本含裸 `&` | `<a>A&B</a>` | 写成 `A&amp;B` |
| 文本含裸 `<` | `<a>1 < 2</a>` | 写成 `1 &lt; 2` |
| 注释含 `--` | `<!-- a--b -->` | 改写注释内容 |
| 大小写不匹配 | `<A></a>` | 统一大小写 |

# 5. 用工具检查

命令行工具 `xmllint` 可以检查良构并格式化输出：

```bash
# 检查是否良构，不输出内容
xmllint --noout book.xml

# 格式化并输出
xmllint --format book.xml
```

# 6. 动手练习

1. 手写一份包含声明、根元素、属性、CDATA 和注释的 XML，然后用 `xmllint --noout` 检查。
2. 找出下面这段 XML 的错误，并说明每一处违反了什么规则：

```xml
<?xml version="1.0" encoding="UTF-8"?>
<users>
  <user id=1>
    <name>张三</name>
  <user>
</users>
```

3. 把一段包含 `<`、`&` 和引号的文本正确转义后放进元素内容，再用解析器读出原文，验证转义是否正确。

# 7. 小结

| 概念 | 要点 |
|------|------|
| XML 定位 | 描述结构的标记语言，不包含行为 |
| 声明 | 位于文档开头，指定版本和编码 |
| 元素 | 必须有且只有一个根，标签严格配对 |
| 属性 | 描述元素元数据，不能重复，必须加引号 |
| 文本 | 默认保留空白，`<` 和 `&` 需转义 |
| CDATA | 原样保留文本，不能包含 `]]>` |
| 注释 | 不能含 `--`，不能放在声明前 |
| 良构 | 语法正确，解析器能读 |
| 合法 | 符合 DTD/XSD 约束 |
