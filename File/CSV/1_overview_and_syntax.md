CSV 看起来只是"用逗号隔开的文本"，很多人以为随手 `split(",")` 就能处理。真实世界里它有 RFC 4180 定义的引号规则、五花八门的分隔符、缺失的表头，以及 Excel 和数据库导出的各种变体。本篇先把 CSV 的结构与边界讲清楚，为后面的解析、编码和流式处理打地基。

# 1. CSV 的定位

## 1.1 为什么还需要 CSV

表格数据格式很多：Excel、Parquet、JSON、数据库表。CSV 仍然长期存在，是因为它满足几个朴素但强大的条件：

- **纯文本**：任何编辑器、任何语言都能打开，不依赖二进制解析器。
- **人可读**：出问题时能直接看文件，而不是面对一堆乱码。
- **通用交换格式**：数据库、报表系统、Excel、埋点导出几乎都支持。
- **实现成本低**：几行代码就能写出解析器，虽然写对并不容易。

| 格式 | 可读性 | 体积 | 类型信息 | 适合场景 |
|------|--------|------|----------|----------|
| CSV | 高 | 中 | 无，全靠约定 | 导出、交换、批量导入 |
| Excel | 高（需软件） | 大 | 有单元格类型 | 人工编辑、报表 |
| JSON | 中 | 大 | 有 | 接口、嵌套结构 |
| Parquet | 低（二进制） | 小 | 有 schema | 大数据分析存储 |

★ **关键认知**：CSV 的本质是**表格数据的文本序列化约定**，不是数据库。它只描述"有几行、几列、每个格子是什么字符"，**不携带类型、不携带 schema、不携带编码声明**。所有"这一列是整数还是字符串"的判断，都由读取方自己完成。

## 1.2 极简结构

一个最小的 CSV 长这样：

```text
name,age,city
张三,23,北京
李四,31,上海
```

它由三部分组成：

```text
┌───────────────────────────────┐
│ name,age,city                 │  ← 表头（header），可选
├───────────────────────────────┤
│ 张三,23,北京                  │  ← 数据行（record）
│ 李四,31,上海                  │
└───────────────────────────────┘
        ↑
     字段（field），用逗号分隔
```

- **记录（record / row）**：一行代表一条数据。
- **字段（field / column value）**：一行中被分隔符切开的每一段。
- **表头（header）**：第一行，给每列起名字。

# 2. 行列结构

## 2.1 记录与字段

CSV 是**二维表**：行是记录，列是属性。这个模型和关系数据库的表一致，所以 CSV 常被当作"最轻量的表"。

```text
        列 0        列 1      列 2
      ┌─────────┬─────────┬─────────┐
行 0  │  name   │   age   │  city   │   ← 表头
      ├─────────┼─────────┼─────────┤
行 1  │  张三   │   23    │  北京   │
      ├─────────┼─────────┼─────────┤
行 2  │  李四   │   31    │  上海   │
      └─────────┴─────────┴─────────┘
```

★ **关键认知**：CSV 的"列"只是**位置约定**，没有名字绑定。第二列之所以是 `age`，是因为表头第二格写了 `age`；一旦表头被删掉或顺序被调换，整个文件的语义就变了。这也是为什么无表头 CSV 极难维护。

## 2.2 表头

表头是可选的第一行。RFC 4180 允许有，也允许没有，但**不提供任何标记说明有没有**。读取方只能靠约定或参数（如 pandas 的 `header=None`）自己判断。

```text
有表头：
id,name,amount
1,alice,100

无表头：
1,alice,100
```

常见的表头问题：

| 问题 | 现象 | 后果 |
|------|------|------|
| 表头缺失 | 第一行数据被当成列名 | 少一行数据、列名是值 |
| 表头重复 | 两列都叫 `name` | 按列名取值时冲突 |
| 表头含空格 | `" name "` | 按 `name` 取不到 |
| 表头含 BOM | `\ufeffid` | 第一列名多出不可见字符 |

## 2.3 等长性

严格来说，**每一行的字段数应当相同**。但现实文件经常不满足：

```text
id,name,amount
1,alice,100
2,bob          ← 只有两列，少一个字段
3,carol,50,extra  ← 多一个字段
```

不同库的处理策略不同：

| 策略 | 代表 | 行为 |
|------|------|------|
| 严格报错 | Go `encoding/csv` 默认 | 字段数不一致直接返回错误 |
| 补空值 | pandas | 缺失列填 `NaN` |
| 截断 / 忽略 | 部分轻量库 | 静默丢弃多余字段 |

⚠ **静默补齐或截断是最危险的**——程序不报错，数据却已经错位。解析生产数据时，应显式检查每行字段数。

# 3. 分隔符

## 3.1 逗号不是唯一

"CSV"里的 C 是 comma，但现实中的 CSV 文件可能用别的分隔符。常见原因有两个：**区域习惯**（欧洲部分地区用分号，因为逗号是小数点）和**数据本身含逗号**（用制表符避开转义）。

| 分隔符 | 常见叫法 | 典型来源 |
|--------|----------|----------|
| `,` | 标准 CSV | 通用导出、数据库 |
| `;` | 分号分隔 | 欧洲 Excel、部分日志 |
| `\t` | TSV | 数据科学、日志、复制粘贴 |
| `\|` | 竖线分隔 | 老系统、报表 |
| 空格 | 空白分隔 | 命令行输出（其实不算 CSV） |

★ **关键认知**：**分隔符不是文件自带的元信息，而是读取方必须事先知道的参数**。同一个文件，用 `,` 读和用 `;` 读会得到完全不同的列。判断分隔符不能只看扩展名，要看内容里哪种字符在每行出现次数稳定。

## 3.2 如何猜测分隔符

一个实用的思路：**统计每行各候选字符的出现次数，选次数最稳定且大于 0 的那个**。

```python
from collections import Counter

def guess_delimiter(sample_lines, candidates=(",", ";", "\t", "|")):
    best, best_score = ",", -1
    for sep in candidates:
        counts = [line.count(sep) for line in sample_lines]
        if not counts or max(counts) == 0:
            continue
        # 出现次数一致的行越多，越可能是真正的分隔符
        stable = Counter(counts).most_common(1)[0][1]
        if stable > best_score:
            best, best_score = sep, stable
    return best
```

⚠ 引号内的分隔符也会被 `count` 统计进去，所以这个启发式只适合快速判断；正式解析应交给 `csv.Sniffer` 或专业库。

# 4. RFC 4180

## 4.1 规则清单

RFC 4180 是 2005 年发布的 CSV 规范（MIME 类型 `text/csv`）。它不长，核心规则如下：

1. 每条记录占一行，行尾用 **CRLF**（`\r\n`）。
2. 最后一条记录可以没有行尾换行。
3. 第一行可以是表头，格式与普通记录相同。
4. 字段之间用**逗号**分隔。
5. 字段可以用**双引号**包裹。
6. 含逗号、双引号或换行的字段**必须**用双引号包裹。
7. 字段内的双引号用**两个双引号**表示（`""`）。
8. 引号内的换行属于字段内容，不是记录分隔。

## 4.2 合法示例

```text
id,name,note
1,alice,"hello, world"
2,bob,"line1
line2"
3,carol,"she said ""hi"""
```

逐行解释：

| 行 | 说明 |
|----|------|
| `1,alice,"hello, world"` | 字段含逗号，必须加引号 |
| `2,bob,"line1` 换行 `line2"` | 字段含换行，**跨了两行文本但仍是一条记录** |
| `3,carol,"she said ""hi"""` | 字段内双引号用 `""` 转义，解析结果是 `she said "hi"` |

```text
"hello, world" 的解析过程：
1. 读到开引号 → 进入引号模式
2. 引号模式内，逗号是普通字符
3. 读到 "" → 输出一个 "
4. 读到闭合引号 → 回到普通模式
5. 再遇到分隔符才切分字段
```

## 4.3 常见的"违背"

真实文件很少严格符合 RFC 4180，下面这些偏离非常普遍：

| 偏离 | 现实情况 | 影响 |
|------|----------|------|
| 行尾用 LF 而非 CRLF | Unix 导出的文件几乎都是 LF | 多数库兼容，但逐字节比对会失败 |
| 只在必要时加引号 | 符合 RFC 的"可以"而非"必须" | 解析器必须同时支持带/不带引号 |
| 不转义内部引号 | 手写文件常见 | 解析结果错乱 |
| 字段数不一致 | 手工编辑、导出 bug | 见 2.3 |
| 文件末尾多空行 | 编辑器自动补 | 可能多出一条全空记录 |
| 加 BOM | Windows / Excel | 第一列名被污染 |

★ **关键认知**：**RFC 4180 是"应然"，不是"实然"**。写解析器时要按规范处理转义，但读真实文件时必须假设它不守规矩。宁可先做一次数据探查，也不要相信扩展名。

# 5. 常见变体

## 5.1 TSV 与制表符

TSV（Tab-Separated Values）用 `\t` 分隔，好处是**文本里天然很少出现制表符**，可以减少转义。但它的转义规则并不统一：有的用 `\t` 字面量，有的用 `\N` 表示 NULL。

```text
id	name	amount
1	alice	100
```

## 5.2 欧洲分号 CSV

欧洲很多地区用逗号表示小数点（`3,14`），所以导出 CSV 时改用分号分隔：

```text
name;price
apple;3,14
pear;2,50
```

如果按逗号解析，`3,14` 会被切成两列，整行错位。这类文件通常还伴随 `;` 分隔与 `,` 小数点的组合。

## 5.3 无表头 CSV

有些系统（尤其是科研数据、矩阵导出）不写表头：

```text
1,2,3
4,5,6
```

读取时必须显式声明 `header=None`（pandas）或不跳过第一行（`csv.reader`）。⚠ **不要写"自动判断有没有表头"的逻辑**——第一行恰好是字符串还是数字，并不足以判断。

## 5.4 注释行与元数据

少数工具会在 CSV 顶部加注释：

```text
# generated at 2026-01-01
# source: sales_db
id,name
1,alice
```

标准 CSV 没有注释语法，`#` 只是一个普通字符。要么在读取前手工跳过，要么在解析器里约定"以 `#` 开头的行忽略"。

## 5.5 行尾与末尾空行

```text
LF:    name,age\n张三,23\n
CRLF:  name,age\r\n张三,23\r\n
```

- 用文本模式读写时，Python 会做换行转换；用二进制模式则原样保留。**文件末尾多一个空行**会产生一条"只有一个空字段"的记录，清洗时要检查最后一行是否为空。

# 6. 常见错误

| 错误 | 原因 | 正确做法 |
|------|------|----------|
| 用 `split(",")` 解析 | 忽略引号和转义 | 用 `csv` 模块或专业库 |
| 认为逗号一定安全 | 字段内容含逗号 | 写入时由库自动加引号 |
| 忽略 BOM | 第一列名带 `\ufeff` | 用 `utf-8-sig` 读取 |
| 按扩展名判断格式 | `.csv` 也可能是 TSV | 先看内容或显式指定 |
| 假设每行字段数相同 | 手工文件常不齐 | 显式校验列数 |
| 把表头当数据 | 未声明 `header` | 明确有无表头 |

# 8. 小结

| 概念 | 要点 |
|------|------|
| 定位 | 纯文本表格交换格式，不带类型和 schema |
| 结构 | 记录 + 字段 + 可选表头，列靠位置约定 |
| 分隔符 | 不固定，必须由读取方指定或探测 |
| RFC 4180 | 逗号分隔、双引号包裹、`""` 转义、CRLF |
| 现实变体 | LF、TSV、分号、无表头、注释、BOM |
| 核心风险 | 字段数不齐、静默错位、末尾空行 |
