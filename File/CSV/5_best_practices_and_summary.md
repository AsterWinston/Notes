前四篇分别讲了语法、解析、编码和大文件。真正把 CSV 用稳，靠的不是某个库，而是一套**约定 + 校验 + 兜底**的工程习惯：列名怎么写、类型怎么定、缺失值怎么表示、坏数据怎么拦、敏感字段怎么处理。本篇把这些收束成一份可执行的清单。

# 1. 为什么需要约定

## 1.1 CSV 的三层约定

CSV 本身只保证"逗号分隔的字符"，其余全靠使用方约定，而且约定分三层：**传输层**（编码、换行、分隔符、引号）、**结构层**（列名、列顺序、列数、表头有无）、**语义层**（类型、单位、时区、缺失标记）。

★ **关键认知**：**CSV 的互操作性来自约定，而不是格式本身**。两个团队都能打开同一个文件，不代表他们对"`amount` 是元还是分""空字符串是缺失还是空值"理解一致。约定必须写下来。

## 1.2 约定的载体

| 载体 | 例子 | 优点 | 缺点 |
|------|------|------|------|
| 文档 | 数据字典 Markdown | 易读、可评审 | 容易过期 |
| 代码常量 | `COLUMNS = [...]` | 与实现同步 | 跨系统共享难 |
| Schema 文件 | JSON Schema、Frictionless Table Schema | 机器可校验 | 需要工具支持 |
| 数据库表结构 | DDL | 强约束 | CSV 导出后失效 |

推荐组合：**一份人读的数据字典 + 一份机器校验的 schema + 代码里的类型声明**，三者互为补充。

# 2. Schema 设计

## 2.1 列名规范

| 规则 | 反例 | 正例 |
|------|------|------|
| 小写蛇形 | `UserName` | `user_name` |
| 只含字母数字下划线 | `金额（元）` | `amount_cny` |
| 不以数字开头 | `1st_order` | `first_order` |
| 不含空格 | `order id` | `order_id` |
| 单位进名字 | `amount` | `amount_cents` |
| 避免缩写歧义 | `qty` | `quantity` |

⚠ 列名一旦对外发布就是契约。改名要当作破坏性变更处理，走版本号或双写过渡，不能悄悄改。

## 2.2 类型契约

CSV 不存类型，所以类型必须写进 schema：

| 逻辑类型 | 推荐表示 | 注意 |
|----------|----------|------|
| 整数 | `int64` | 超范围用字符串，如雪花 ID |
| 小数金额 | 整数分或定点字符串 | 不用 `float`，避免精度误差 |
| 日期 | ISO 8601 `YYYY-MM-DD` | 明确时区 |
| 时间戳 | ISO 8601 带偏移 `2026-01-01T10:00:00+08:00` | 统一 UTC 或统一本地 |
| 布尔 | `true`/`false` | 不用 `Y`/`N`/`1`/`0` 混用 |
| 枚举 | 固定小写值 | 写进 schema 的允许列表 |
| ID | 字符串 | 防前导零、防科学计数法 |

```text
schema 片段（伪代码）：
id          : string,  required, pattern=^[A-Z0-9]{10}$
amount_cents: int64,   required, min=0
created_at  : date,    required, format=YYYY-MM-DD
status      : enum,    required, values=[pending, paid, refunded]
```

★ **关键认知**：**金额一律不要用浮点**。`0.1 + 0.2 != 0.3` 在 CSV 里同样成立。用整数分、定点字符串或 `Decimal`，并在列名里写明单位。

## 2.3 版本与兼容

| 变更 | 是否兼容 | 做法 |
|------|----------|------|
| 末尾加列 | 通常兼容 | 读取方忽略未知列 |
| 中间插列 | 破坏性 | 按位置读的代码会错位 |
| 删列 | 破坏性 | 提前公告、保留一个版本 |
| 改列名 | 破坏性 | 双写或版本化 |
| 放宽类型 | 通常兼容 | 如 int 扩为 string |
| 收紧类型 | 破坏性 | 历史数据可能不满足 |

演进时只在末尾追加列，例如 `v1: id,name,amount_cents` → `v2: id,name,amount_cents,created_at`。

# 3. 校验

## 3.1 结构校验

结构校验回答"表格形状对不对"：

- 表头是否存在、列名是否完全匹配。
- 列数是否与表头一致。
- 是否有重复列名。
- 是否为空文件。
- 编码是否可解码。

```python
import csv

EXPECTED = ["id", "name", "amount_cents", "created_at"]

def check_structure(path):
    errors = []
    with open(path, newline="", encoding="utf-8-sig") as f:
        rows = csv.reader(f)
        header = [h.strip() for h in next(rows, [])]
        if header != EXPECTED:
            errors.append(f"表头不符：{header}")
        for line_no, row in enumerate(rows, start=2):
            if len(row) != len(EXPECTED):
                errors.append(f"第 {line_no} 行字段数 {len(row)}")
    return errors
```

## 3.2 内容校验

内容校验回答"值对不对"：

| 检查 | 例子 |
|------|------|
| 非空 | 必填列不为空 |
| 类型 | `amount_cents` 能转整数 |
| 范围 | `amount_cents >= 0` |
| 格式 | 日期符合 ISO 8601 |
| 枚举 | `status` 在允许集合内 |
| 唯一性 | `id` 不重复 |
| 引用完整性 | `user_id` 在用户表中存在 |

```python
from datetime import date

def validate_row(row):
    errors = []
    if not row["id"]:
        errors.append("id 为空")
    try:
        errors += [] if int(row["amount_cents"]) >= 0 else ["金额为负"]
    except ValueError:
        errors.append("金额非法")
    try:
        date.fromisoformat(row["created_at"])
    except ValueError:
        errors.append("日期非法")
    if row["status"] not in {"pending", "paid", "refunded"}:
        errors.append("状态非法")
    return errors
```

## 3.3 使用现成工具

| 工具 | 语言 | 特点 |
|------|------|------|
| pandas + 手写校验 | Python | 灵活，适合小规模 |
| Pandera | Python | 声明式 schema，与 pandas 集成 |
| Great Expectations | Python | 数据质量套件，适合流水线 |
| Cerberus | Python | 通用字典校验 |
| JSON Schema | 跨语言 | 需先把行转成对象 |
| 数据库约束 | SQL | 导入后由数据库兜底 |

★ **关键认知**：**校验要在数据进入系统的最早环节做**。等数据写进数据库再发现问题，清洗成本会高一个数量级。导入前校验、导入后对账，两头都要有。

# 4. 缺失值

## 4.1 缺失的多种写法

常见写法有：`,NULL,`、`,,`（空字符串）、`,NA,`、`,N/A,`、`,-,`、`,nan,`、`,None,`。

这些写法在语义上不一定相同：

| 写法 | 可能含义 |
|------|----------|
| 空字段 | 未知、不适用、或真的空字符串 |
| `NULL` | 数据库导出的缺失 |
| `N/A` | 人工填写的不可用 |
| `-` | 占位符，通常表示无 |
| `0` | **不是缺失**，是有效值 |

★ **关键认知**：**"缺失"和"空字符串"是两回事**。用户名可以为空字符串（用户就是不填），但金额缺失表示"不知道"。schema 里要明确每列允许哪种，读取时用 `na_values` 把真正表示缺失的标记统一成 `NaN`，同时 `keep_default_na` 防止误伤。

## 4.2 处理策略

| 策略 | 做法 | 适用 |
|------|------|------|
| 保留 | 原样保留 `NaN` | 下游能处理缺失 |
| 删除行 | `dropna(subset=[...])` | 关键字段缺失且量小 |
| 填默认值 | `fillna(0)`、`fillna("unknown")` | 业务有明确默认 |
| 填统计量 | 均值、中位数、众数 | 分析场景，需标注 |
| 单独标记 | 新增 `is_missing` 列 | 缺失本身有信息 |

读取时用 `na_values` 统一缺失标记，例如 `pd.read_csv("data.csv", na_values=["", "NULL", "N/A", "-"])`；关键字段缺失用 `dropna(subset=[...])` 删行，非关键字段填默认值并新增标记列留痕。

⚠ 用均值填充会**压缩方差、扭曲分布**。如果这份数据要用于统计或建模，填充策略必须记录在案，不能默默做。

# 5. 数据质量

## 5.1 检查清单

| 维度 | 问题 | 检查方式 |
|------|------|----------|
| 完整性 | 必填列有空值 | 空值率统计 |
| 唯一性 | 主键重复 | `duplicated()` |
| 有效性 | 类型、范围、格式不对 | schema 校验 |
| 一致性 | 单位、时区、枚举不统一 | 取值分布对比 |
| 及时性 | 数据日期过期 | 最大时间戳检查 |
| 准确性 | 与源系统对不上 | 抽样对账 |

用 `df.info()`、`df.isna().mean()`、`df.nunique()` 就能快速得到 dtype、空值率与基数；需要固定报表时，把它们整理成一张 profile 表定期输出。

## 5.2 指标与监控

把质量做成可观测指标，才能在流水线里告警：

| 指标 | 计算 | 告警阈值示例 |
|------|------|--------------|
| 行数 | `len(df)` | 比昨日下降超过 30% |
| 空值率 | `isna().mean()` | 关键列 > 0 |
| 重复率 | `duplicated().mean()` | > 1% |
| 非法值比例 | 校验失败行 / 总行 | > 0.1% |
| 最大时间 | `max(created_at)` | 落后当前超过 2 小时 |

★ **关键认知**：**数据质量不是一次性任务，而是持续监控**。上游系统改一个字段、换一次导出工具，都可能让下游静默出错。指标 + 告警比"偶尔跑一次校验脚本"可靠得多。

# 6. 安全

## 6.1 注入

| 风险 | 场景 | 防御 |
|------|------|------|
| 公式注入 | 用户输入被 Excel 打开 | 危险前缀转义 |
| CSV 欺骗 | 字段内伪造分隔符与换行 | 用库转义，不手拼 |
| 路径穿越 | 文件名来自用户输入 | 白名单、规范化路径 |
| 命令注入 | 文件名拼进 shell 命令 | 避免拼接，用参数化 |

```python
DANGEROUS_PREFIX = ("=", "+", "-", "@", "\t", "\r")

def safe_cell(value: str) -> str:
    if value and value.startswith(DANGEROUS_PREFIX):
        return "'" + value        # Excel 按文本处理
    return value
```

## 6.2 敏感数据

| 数据 | 处理 |
|------|------|
| 手机号、身份证 | 导出前脱敏或哈希 |
| 银行卡、密码 | 不应出现在 CSV |
| 地址、生日 | 按最小必要原则裁剪 |
| 内部 ID | 避免直接暴露自增主键 |

常用手段是掩码与哈希：手机号保留前 3 位和后 4 位，中间用 `****`；内部 ID 用加盐的 SHA-256 取前 16 位。⚠ 哈希要加盐，否则常见值可以被彩虹表反推。脱敏后的文件仍要按敏感级别管理访问权限。

## 6.3 资源耗尽

不可信 CSV 还可能攻击解析器本身：

| 攻击 | 原理 | 防御 |
|------|------|------|
| 超大字段 | 一个字段几 GB | 限制字段大小 |
| 解压炸弹 | 小 gzip 解压出超大文件 | 限制解压后大小 |
| 超多列 | 几万列拖垮内存 | 限制列数、`usecols` |

防范手段很直接：用 `csv.field_size_limit(10 * 1024 * 1024)` 限制单字段大小，解压时按块累计字节数并在超限时中止。

| 安全 | 注入转义、敏感脱敏、资源上限 |
| 运维 | 行数/空值率/新鲜度指标与告警 |
| 演进 | 只追加列，改名走版本化 |

# 8. CSV 与其他格式的选型

| 场景 | 推荐 | 理由 |
|------|------|------|
| 人工查看、Excel 交换 | CSV / xlsx | 通用、可读 |
| 接口传输 | JSON | 有类型、嵌套 |
| 大数据分析 | Parquet | 列式、压缩、带 schema |
| 配置 | YAML / TOML | 可读、支持注释 |
| 日志流 | JSON Lines | 逐行可追加 |
| 数据库导入导出 | CSV | 工具链成熟 |

★ **关键认知**：**CSV 适合"平面表格 + 人机共读"，不适合嵌套、强类型和大规模分析**。当数据需要 schema、需要随机访问、需要高效压缩时，Parquet 更合适；当数据有嵌套结构时，JSON 更自然。别用 CSV 硬扛所有场景。

# 10. 小结

| 主题 | 要点 |
|------|------|
| 约定 | 传输、结构、语义三层都要写清楚 |
| Schema | 列名规范、类型契约、单位时区、版本兼容 |
| 校验 | 结构 + 内容，尽早做，错误带定位 |
| 缺失值 | 区分缺失与空字符串，策略要留痕 |
| 质量 | 完整性、唯一性、有效性、一致性、及时性 |
| 安全 | 注入转义、敏感脱敏、资源上限 |
| 选型 | 平面人读用 CSV，分析用 Parquet，嵌套用 JSON |

到这里，CSV 模块从语法、解析、编码、大文件到工程实践形成了一个闭环。下一步可以对照 `Json` 模块的设计实践篇，比较两种格式在契约演进和校验思路上的异同。
