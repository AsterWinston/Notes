YAML、JSON、XML、TOML 都能表达结构化数据，但没有一种"通吃"的格式。选错格式，要么写起来痛苦，要么运行时踩坑。本篇从可读性、类型能力、工具生态和安全四个维度对比四种格式，给出场景化选型建议，最后整理一套团队级的 YAML 编写规范与自查清单。

# 1. 四种格式的定位

| 格式 | 设计初衷 | 主流用途 |
|------|----------|----------|
| YAML | 人类友好的数据序列化 | K8s、CI/CD、应用配置 |
| JSON | 轻量的数据交换格式 | Web API、日志、消息 |
| XML | 可扩展的标记语言 | 文档、SOAP、复杂 schema |
| TOML | 简洁的配置文件格式 | Rust/Cargo、Python 工具、静态站点 |

一句话记忆：

- JSON 适合**机器之间传数据**。
- YAML 适合**人写复杂配置**。
- XML 适合**描述文档和强制 schema**。
- TOML 适合**扁平的、无歧义的配置**。

★ **关键认知**：格式没有优劣，只有匹配度。选型的核心问题是"这份数据主要由谁读写、需要多强的结构约束、生态是否指定"。逆着生态选格式，最终都要付转换成本。

# 2. 语法对比

## 2.1 同一份数据

```yaml
server:
  host: 127.0.0.1
  port: 8080
  tags:
    - web
    - api
```

```json
{
  "server": {
    "host": "127.0.0.1",
    "port": 8080,
    "tags": ["web", "api"]
  }
}
```

```toml
[server]
host = "127.0.0.1"
port = 8080
tags = ["web", "api"]
```

```xml
<server>
  <host>127.0.0.1</host>
  <port>8080</port>
  <tags>
    <tag>web</tag>
    <tag>api</tag>
  </tags>
</server>
```

## 2.2 可读性与书写成本

| 格式 | 优点 | 缺点 |
|------|------|------|
| YAML | 层级直观、可注释、少符号 | 缩进敏感、隐式类型坑多 |
| JSON | 结构明确、解析简单、通用 | 引号括号多、不能注释、尾逗号非法 |
| TOML | 无缩进歧义、类型明确、可注释 | 深层嵌套表达笨拙 |
| XML | 表达力强、命名空间、schema 成熟 | 冗长、解析成本高 |

## 2.3 类型与注释

| 能力 | YAML | JSON | TOML | XML |
|------|------|------|------|-----|
| 注释 | `#` | 不支持 | `#` | 尖括号注释 |
| 字符串裸写 | 支持 | 必须双引号 | 支持 | 文本节点 |
| 数字类型 | 整数/浮点 | 单一 number | 整数/浮点/日期 | 需 schema |
| 布尔 | 1.1 有歧义 | 严格 | 严格 | 需 schema |
| 日期 | 可隐式解析 | 无原生 | 原生日期时间 | 需 schema |
| 多行字符串 | `\|` 与 `>` | 需转义 | 多行字符串 | CDATA |

★ **关键认知**：YAML 的"少写字"是用**歧义**换来的，TOML 的"多写字"是用**明确**换来的。配置里如果大量出现 `yes/no`、版本号、日期，TOML 的明确性反而更省心；如果是深层层级（K8s），YAML 的缩进表达更自然。

# 3. 能力对比

| 能力 | YAML | JSON | TOML | XML |
|------|------|------|------|-----|
| 锚点/复用 | 支持 | 不支持 | 不支持 | 通过实体/XInclude |
| schema 校验 | JSON Schema | JSON Schema | 有限 | XSD 强 |
| 多文档 | `---` | 不支持 | 不支持 | 不支持 |
| 命名空间 | 不支持 | 不支持 | 不支持 | 支持 |
| 解析器普及度 | 高 | 最高 | 中 | 高 |
| 流式/大文件 | 一般 | 好 | 一般 | 好（SAX） |

## 3.1 复用能力

YAML 的锚点是独有优势：

```yaml
defaults: &defaults
  timeout: 3s
  retries: 2

serviceA:
  <<: *defaults
  url: https://a.example.com
```

JSON、TOML 没有等价机制，只能靠工具层展开或程序拼接。

## 3.2 schema 强度

如果需要"字段级强约束 + 复杂类型 + 命名空间",XML 的 XSD 仍然最强。如果只需要"结构 + 类型 + 必填",JSON Schema 足够，且能同时约束 YAML 和 JSON。

⚠ **关键认知**：TOML 没有事实标准的 schema，深层结构的约束能力弱。数据模型复杂、需要严格校验时，TOML 不是好选择。

# 4. 选型建议

| 场景 | 推荐 | 理由 |
|------|------|------|
| Web API | JSON | 浏览器原生、库最全 |
| K8s / CI | YAML | 平台标准，无法回避 |
| 应用配置（层级深） | YAML | 层级直观、可注释 |
| 应用配置（扁平） | TOML | 无缩进歧义、类型明确 |
| 文档 / SOAP | XML | 命名空间、XSD、XSLT |
| 日志 | JSON | 易解析、易检索 |
| 简单键值 | Properties/TOML | 比 YAML 更少歧义 |

选型决策图：

```text
这份数据主要给谁用？
  │
  ├── 机器传输 ──────────────► JSON
  │
  ├── 人写配置
  │     ├── 生态已指定 YAML ──► YAML（K8s/CI）
  │     ├── 层级深、需复用 ───► YAML
  │     └── 扁平、要明确 ─────► TOML
  │
  └── 文档 / 强 schema ──────► XML
```

★ **关键认知**：选型的第一优先级是**跟随生态**。K8s 只认 YAML/JSON，CI 平台各有偏好，这些场景没有选择余地。只有在自己设计格式时，才需要在上面的维度里权衡。

# 5. YAML 编写规范

## 5.1 格式约定

| 约定 | 建议 |
|------|------|
| 缩进 | 2 空格，禁用 Tab |
| 键命名 | 与目标平台一致（K8s 用 camelCase） |
| 引号 | 有歧义的值一律加引号 |
| 注释 | 说明"为什么",不复述"是什么" |
| 多文档 | 每个文档前加 `---` |
| 行宽 | 团队统一，建议 120 以内 |

## 5.2 类型约定

```yaml
# 字符串：明确加引号
version: "1.10"
country: "NO"
zip: "01234"

# 数字：确认下游要数字
replicas: 3

# 布尔：只用 true/false
enabled: true

# 空值：显式写 null 或 ""
password: null
note: ""
```

## 5.3 复用约定

```yaml
# 锚点命名带语义，不要用 a/b/c
.defaults: &defaults
  image: node:20
  before_script:
    - npm ci

test:
  <<: *defaults
  script:
    - npm test
```

⚠ **关键认知**：规范要落进工具，而不是只写在文档里。`yamllint` 管风格、`check-jsonschema` 管结构、`pre-commit` 管提交，三者组合才能让规范真正执行。

# 6. 安全实践

| 风险 | 影响 | 防御 |
|------|------|------|
| 不安全加载 | 任意对象实例化 / RCE | 用 SafeLoader / SafeConstructor |
| YAML 炸弹 | 内存耗尽 | 限制别名数量与输入大小 |
| 重复键 | 绕过校验、值被覆盖 | 开启重复键报错 |
| 硬编码密钥 | 泄露 | 用 Secret 管理 / SOPS / Vault |
| 过度权限 | 资源被篡改 | RBAC 最小权限 |

```yaml
# 反面示例：把明文密码直接写进仓库
database:
  password: "prod-secret-123"
```

```yaml
# 正面示例：引用外部密钥
database:
  password: ${DB_PASSWORD}
```

★ **关键认知**：YAML 本身不提供加密。Secret 只是 base64 编码，不是加密。敏感信息必须靠外部密钥管理系统（SOPS、Vault、Sealed Secrets）在提交前或部署时注入。

# 7. 常见错误回顾

| 错误 | 修复 |
|------|------|
| Tab 缩进 | 换空格，编辑器设置 |
| 冒号后无空格 | `key: value` |
| `NO` 被当布尔 | `"NO"` |
| `1.10` 变 `1.1` | `"1.10"` |
| ConfigMap 值写数字 | 加引号 |
| 单文档 API 读多文档 | 用 `loadAll` |
| `new Yaml()` 解析不可信输入 | `SafeConstructor` |
| 跨文档引用锚点 | 每文档单独定义 |

# 8. 动手练习

1. 把同一份"服务配置"分别写成 YAML、JSON、TOML，说明哪种最易读、哪种最明确，并给出你所在项目的选型理由。

2. 用 `yq` 把一份 YAML 转成 JSON，再转回 YAML，对比前后差异（注释、锚点、引号是否保留）。

3. 给一个团队设计三条 YAML 规范（至少覆盖缩进、类型、复用），并说明各自该用哪个工具自动检查。

# 9. 小结

| 主题 | 结论 |
|------|------|
| 定位 | YAML 写配置、JSON 传数据、XML 管文档、TOML 求明确 |
| 优势 | YAML 可读可注释可复用 |
| 代价 | 缩进敏感、隐式类型、安全隐患 |
| 选型 | 先跟随生态，再权衡层级与明确性 |
| 规范 | 2 空格、有歧义加引号、语义化锚点 |
| 安全 | 安全加载、限制资源、外部密钥 |

一句话收束：**YAML 是一把好用的配置工具，但它的便利来自隐式规则，风险也来自隐式规则。把"能跑"变成"写得对、校验过、加载安全",才算真正掌握。**
