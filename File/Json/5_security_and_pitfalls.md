JSON 看起来只是文本，但解析不可信 JSON 可能带来资源耗尽、精度丢失、原型污染和反序列化攻击。本篇面向初学者讲清这些风险的触发条件，并给出解析深度、体积、类型和字段白名单等防御措施。

# 1. JSON 安全风险

## 1.1 深度嵌套与资源耗尽

攻击者可以提交超深嵌套：

```json
{"a":{"a":{"a":{"a": ... }}}}
```

解析器递归构建对象时可能栈溢出，或者消耗大量 CPU 和内存。超大数组也有类似问题：

```json
{"items":[1,1,1,1, ... 数百万个 ...]}
```

防御：

- 限制请求体大小，例如 1 MiB 或 10 MiB。
- 限制嵌套深度。
- 限制数组元素数量。
- 在网关层提前拦截异常大的请求。

★ **关键认知**：只限制 JSON 字符串长度不够。一定长度内仍可能构造出极深嵌套，让解析器递归耗尽栈空间。

## 1.2 超大数字与精度丢失

JavaScript 使用 IEEE 754 双精度浮点数表示所有数字，安全整数范围是：

```text
Number.MAX_SAFE_INTEGER = 9007199254740991
```

超过这个范围，整数可能失真：

```javascript
JSON.parse('{"id":9007199254740993}').id
// 结果可能是 9007199254740992
```

订单号、雪花 ID、数据库 `bigint` 很容易超过这个范围。防御方式：

- 大整数用字符串传输。
- Java 用 `Long`/`BigInteger`，Go 用 `json.Number`，Python 用 `int`。
- 前后端约定 ID 的格式，不要依赖 JavaScript 默认数字精度。

## 1.3 原型污染

JavaScript 中，某些键被合并到对象原型上，可能影响所有对象：

```javascript
const payload = JSON.parse('{"__proto__":{"isAdmin":true}}');

function unsafeMerge(target, source) {
    for (const key in source) {
        if (typeof source[key] === "object") {
            target[key] = target[key] || {};
            unsafeMerge(target[key], source[key]);
        } else {
            target[key] = source[key];
        }
    }
}

unsafeMerge({}, payload);
// 可能导致后续对象的 isAdmin 异常为 true
```

注意：`JSON.parse` 本身通常不会触发原型污染，危险发生在**不安全的深合并、递归赋值或对象展开**。

防御：

- 禁止合并 `__proto__`、`constructor`、`prototype` 等键。
- 使用 `Object.create(null)` 创建无原型对象。
- 使用库的安全合并函数，并升级到修复版本。
- 对用户输入做字段白名单。

# 2. 反序列化风险

## 2.1 类型混淆

把 JSON 直接反序列化成"任意类型"可能被利用。例如 Java 中开启 Jackson 默认类型信息：

```java
// 危险：允许 JSON 指定要实例化的类
ObjectMapper mapper = new ObjectMapper();
mapper.enableDefaultTyping();
```

攻击者可以构造恶意类型链，触发危险方法，造成远程代码执行（RCE）。类似风险也存在于其他语言的动态反序列化中。

## 2.2 白名单与安全配置

| 措施 | 说明 |
|------|------|
| 不开启默认类型 | 只反序列化到明确的 DTO |
| 类型白名单 | 必须使用多态时，限制允许的类 |
| 字段白名单 | 只接受业务需要的字段 |
| 禁用未知字段 | 根据契约决定是否报错 |
| 限制解析特性 | 禁止不必要的高级特性 |
| 升级依赖 | 使用有安全修复的版本 |

Java 示例：

```java
ObjectMapper mapper = new ObjectMapper();
mapper.disable(DeserializationFeature.FAIL_ON_UNKNOWN_PROPERTIES);
// 不要 enableDefaultTyping，除非有严格白名单和充分理由
```

# 3. 数据完整性

## 3.1 重复键

```json
{"role":"user","role":"admin"}
```

不同解析器行为不同：

- 有的取最后一个值。
- 有的取第一个值。
- 有的报错。

不要依赖重复键的顺序。安全敏感场景应在入口检测重复键，或使用严格解析模式。

## 3.2 编码与 BOM

- JSON 规范要求 UTF-8，但部分解析器接受 BOM。
- 带 BOM 的文件可能在首字段前出现不可见字符，导致解析失败。
- 非法编码或错误转义会导致解析异常。

建议：

- 保存为无 BOM 的 UTF-8。
- 明确响应头 `Content-Type: application/json; charset=utf-8`。
- 解析失败时输出错误位置，方便定位。

# 4. 安全实践清单

| 层面 | 措施 |
|------|------|
| 体积 | 限制请求体大小 |
| 深度 | 限制嵌套层级 |
| 数量 | 限制数组长度和对象字段数 |
| 类型 | 只反序列化到明确 DTO |
| 字段 | 白名单、拒绝未知字段 |
| 数字 | 大整数用字符串 |
| 键 | 拦截 `__proto__` 等危险键 |
| 错误 | 只返回安全错误信息，内部细节进日志 |
| 依赖 | 定期升级解析库 |

# 5. 常见错误

| 错误 | 风险 | 正确做法 |
|------|------|----------|
| 直接打印完整 JSON | 日志泄露密码、Token | 脱敏后再记录 |
| 把异常栈返回给调用方 | 泄露内部结构 | 返回统一错误码 |
| 信任客户端字段 | 越权修改角色、金额 | 服务端重新校验 |
| 开启默认类型 | 反序列化 RCE | 禁用或严格白名单 |
| 不限制请求体 | 内存耗尽 | 网关和应用双层限制 |
| 用 `eval` 解析 JSON | 任意代码执行 | 使用标准 JSON 解析器 |

# 6. 小结

| 风险 | 触发条件 | 防御 |
|------|----------|------|
| 资源耗尽 | 超深嵌套、超大数组 | 限制大小、深度、数量 |
| 精度丢失 | 大整数被解析为浮点 | 字符串或大数类型 |
| 原型污染 | 不安全深合并 | 拦截危险键、字段白名单 |
| 反序列化攻击 | 任意类型实例化 | 禁用默认类型、白名单 |
| 重复键 | 解析器行为不一致 | 严格模式或入口检测 |
| 编码问题 | BOM、非法 UTF-8 | 统一 UTF-8 无 BOM |
