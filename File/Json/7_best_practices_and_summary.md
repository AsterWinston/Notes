会写合法 JSON 只是起点，设计一份好用的 JSON 结构还需要考虑命名、嵌套、兼容性和错误表达。本篇汇总接口字段设计、版本演进、统一错误结构和性能体积方面的实践清单。

# 1. 命名与结构设计

## 1.1 字段命名

常见风格：

| 风格 | 示例 | 常见生态 |
|------|------|----------|
| camelCase | `userName` | JavaScript、Java |
| snake_case | `user_name` | Python、Go、数据库 |
| kebab-case | `user-name` | 少见于 JSON 字段 |

建议：

- 同一系统内保持一致，不要同一接口混用多种风格。
- 对外 API 一旦发布，字段名就是契约，不要随意改名。
- 需要适配时用序列化注解转换，不要改数据库字段名。

## 1.2 嵌套层级

```json
{
  "user": {
    "profile": {
      "address": {
        "city": "上海"
      }
    }
  }
}
```

嵌套过深的问题：

- 客户端取值冗长。
- 结构变化影响面大。
- 日志和调试难读。

建议：

- 超过 3-4 层时考虑扁平化或拆分资源。
- 关联对象用 ID 引用，而不是无限嵌套。
- 分组要表达真实业务关系，不要为了"看起来整齐"而嵌套。

## 1.3 数组与分页

列表响应建议包含分页信息：

```json
{
  "items": [
    {"id": 1, "name": "alice"},
    {"id": 2, "name": "bob"}
  ],
  "page": 1,
  "size": 20,
  "total": 135
}
```

或者使用游标分页：

```json
{
  "items": [],
  "nextCursor": "eyJpZCI6MTIzfQ==",
  "hasMore": true
}
```

| 分页方式 | 优点 | 缺点 |
|----------|------|------|
| 页码分页 | 简单、可跳页 | 深分页性能差、数据变动时重复/遗漏 |
| 游标分页 | 稳定、适合大数据 | 不能随意跳页 |

# 2. 兼容性设计

## 2.1 新增字段

新增可选字段通常兼容，因为旧客户端会忽略未知字段。但前提是客户端确实忽略未知字段。

建议：

- 服务端新增字段应保持可选。
- 客户端解析时忽略未知字段。
- 不要把新增字段放进必填校验。

## 2.2 废弃字段

不要直接删除仍被使用的字段。推荐流程：

```text
1. 标记废弃：文档和响应中标注 deprecated
2. 保留过渡期：旧字段继续返回，可能同时返回新字段
3. 监控使用：确认没有调用方依赖
4. 最终移除：在版本升级时删除
```

## 2.3 版本化

| 方式 | 示例 | 优点 | 缺点 |
|------|------|------|------|
| URL 版本 | `/api/v1/users` | 直观、易路由 | URL 变化 |
| Header 版本 | `Accept: application/vnd.api.v1+json` | URL 稳定 | 调试不直观 |
| 字段级兼容 | 只做向后兼容变更 | 无需版本 | 大变更难表达 |

大多数项目使用 URL 版本即可。不要频繁升版本，优先做向后兼容的增量演进。

# 3. 错误处理

## 3.1 统一错误结构

```json
{
  "code": "INVALID_ARGUMENT",
  "message": "参数校验失败",
  "details": [
    {"field": "email", "message": "邮箱格式不正确"},
    {"field": "age", "message": "年龄必须大于 0"}
  ],
  "requestId": "8f14e45f"
}
```

字段说明：

| 字段 | 作用 |
|------|------|
| `code` | 程序可判断的稳定错误码 |
| `message` | 人类可读的简要说明 |
| `details` | 字段级错误，便于表单展示 |
| `requestId` | 排查问题的追踪 ID |

★ **关键认知**：`code` 要稳定，`message` 可以调整。不要让客户端用 `message` 做条件判断。

## 3.2 部分成功

批量操作可能部分成功：

```json
{
  "total": 3,
  "succeeded": 2,
  "failed": 1,
  "results": [
    {"id": 1, "status": "success"},
    {"id": 2, "status": "success"},
    {"id": 3, "status": "failed", "reason": "用户不存在"}
  ]
}
```

HTTP 状态码选择：

- 全部成功：200。
- 全部失败：4xx 或 5xx。
- 部分成功：200 或 207，响应体中明确列出失败项。

不要用 200 表示全部失败，也不要在部分成功时隐藏失败信息。

# 4. 性能与体积

| 方法 | 说明 | 注意 |
|------|------|------|
| 字段裁剪 | 只返回客户端需要的字段 | 避免多个接口返回同一大对象 |
| 分页 | 限制单次返回数量 | 设置最大 size |
| 压缩 | gzip/br | 文本 JSON 压缩收益明显 |
| 避免重复嵌套 | 关联对象用 ID | 减少重复数据 |
| 缓存 | 对稳定数据缓存序列化结果 | 注意用户私有数据 |

# 5. 实践清单

接口设计：

- 字段命名风格统一。
- 嵌套层级控制在合理范围。
- 列表接口有分页。
- 大整数用字符串传输。
- 日期格式统一，带时区。
- 错误结构统一，含稳定错误码。
- 未知字段处理策略明确。

兼容性：

- 新增字段可选。
- 废弃字段有过渡期。
- 版本策略明确。
- 契约变更纳入评审。

安全：

- 不返回内部错误栈。
- 敏感字段脱敏。
- 限制请求体大小。
- 校验字段类型和范围。

# 6. 小结

| 主题 | 核心原则 |
|------|----------|
| 命名 | 全系统一致，发布后不改 |
| 嵌套 | 表达业务关系，避免过深 |
| 分页 | 页码或游标，限制最大 size |
| 兼容 | 新增可选、废弃过渡、版本化 |
| 错误 | 稳定 code + 可读 message + requestId |
| 性能 | 裁剪、分页、压缩、缓存 |
