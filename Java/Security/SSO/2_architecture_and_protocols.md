
# 1. 概述

SSO 的实现并非只有一种固定模式。不同的业务场景、技术栈、安全要求，对应不同的架构设计。本章系统梳理 SSO 的五大架构模式，深入解析各协议的认证流程与底层机制，并提供协议选型决策框架。

# 2. SSO 五大架构模式

## 2.1 集中式认证模式（Centralized）

```
                    ┌─────────────────────┐
                    │   认证中心 (CAS)     │
                    │  ┌───────────────┐  │
                    │  │  用户身份库    │  │
                    │  │  (LDAP/DB)    │  │
                    │  └───────────────┘  │
                    └─────────┬───────────┘
                              │
              ┌───────────────┼───────────────┐
              ▼               ▼               ▼
        ┌──────────┐   ┌──────────┐   ┌──────────┐
        │  应用 A  │   │  应用 B  │   │  应用 C  │
        └──────────┘   └──────────┘   └──────────┘
          无本地用户表   无本地用户表   无本地用户表
```

| 维度 | 说明 |
|------|------|
| **认证责任** | 完全由认证中心负责，各应用不存用户密码 |
| **用户管理** | 集中在认证中心操作，各应用通过 API 获取用户信息 |
| **适用协议** | CAS、OAuth2（授权码模式）、OIDC |
| **典型产品** | CAS Server、Keycloak、Okta、Auth0 |
| **优点** | 用户体系唯一，管理简单，审计方便 |
| **缺点** | 认证中心是单点（需高可用），各应用需改造对接 |

## 2.2 联邦式认证模式（Federated）

```
    ┌───────────────────┐              ┌───────────────────┐
    │   组织 A (IdP)    │              │   组织 B (IdP)    │
    │  (公司AD/企业微信) │              │  (合作伙伴AD)     │
    └─────────┬─────────┘              └─────────┬─────────┘
              │                                  │
              │        ┌──────────────┐          │
              └────────┤  信任联邦圈  ├──────────┘
                       └──────┬───────┘
                              │
                       ┌──────▼──────┐
                       │  SaaS 平台  │
                       │  (SP)       │
                       └─────────────┘
```

| 维度 | 说明 |
|------|------|
| **核心思想** | 多个独立组织的 IdP 通过信任关系互通，用户可用本组织的身份访问合作方的应用 |
| **适用协议** | SAML 2.0、OIDC |
| **信任建立** | 元数据交换（SAML）/ 客户端注册（OIDC） |
| **典型场景** | 大学间联合认证（eduGAIN）、企业间 B2B 合作 |
| **优点** | 各组织保留身份主权，跨组织协作 |
| **缺点** | 信任关系管理复杂，SAML 配置成本高 |

## 2.3 代理式认证模式（Agent-Based / Proxy）

```
    ┌─────────────────────────────────────────┐
    │          SSO 代理 (Proxy)                │
    │                                          │
    │  ┌──────────┐  ┌──────────┐  ┌───────┐ │
    │  │ 协议转换  │  │  适配器   │  │ 过滤器 │ │
    │  │ OAuth→CAS│  │ LDAP→OIDC│  │        │ │
    │  └──────────┘  └──────────┘  └───────┘ │
    └──────────────┬──────────────────────────┘
                   │
    ┌──────────────┼──────────────────────────┐
    ▼              ▼                          ▼
┌───────┐    ┌──────────┐              ┌──────────┐
│ 旧系统 │    │ 新系统    │              │ 外部 SaaS│
│(无SSO)│    │ (OAuth2)  │              │ (SAML)   │
└───────┘    └──────────┘              └──────────┘
```

| 维度 | 说明 |
|------|------|
| **核心思想** | 在请求路径中插入代理层，统一拦截认证请求，对后端应用透明 |
| **反向代理型** | Nginx + auth_request 模块，或 Envoy/Istio 认证过滤器 |
| **网关型** | Spring Cloud Gateway + GlobalFilter 统一认证 |
| **Web 服务器插件** | Apache mod_auth_cas、Nginx lua-resty-openidc |
| **优点** | 后端应用无需改造，协议统一转换，运维灵活 |
| **缺点** | 代理层成为性能瓶颈和单点，增加系统复杂度 |

## 2.4 客户端适配器模式（Agent-Based / SDK）

```
    ┌──────────────────────────────────────────┐
    │              认证中心 (IdP)               │
    └─────┬──────────────┬──────────────┬──────┘
          │              │              │
   ┌──────▼──────┐ ┌─────▼──────┐ ┌────▼──────┐
   │  应用 A     │ │  应用 B    │ │  应用 C   │
   │  ┌────────┐ │ │ ┌────────┐ │ │ ┌───────┐ │
   │  │CAS SDK │ │ │ │OAuth2  │ │ │ │JWT    │ │
   │  │(Filter)│ │ │ │Client  │ │ │ │Filter │ │
   │  └────────┘ │ │ └────────┘ │ │ └───────┘ │
   └─────────────┘ └────────────┘ └───────────┘
      每个应用内置认证 SDK/Filter，各应用主动对接认证中心
```

| 维度 | 说明 |
|------|------|
| **实现方式** | 每个应用引入认证 SDK/Filter，通过配置对接认证中心 |
| **Java 生态** | Spring Security + CAS Client / OAuth2 Client / SAML SP |
| **Node.js 生态** | passport.js + 各协议策略 |
| **优点** | 各应用独立可控，灵活定制认证行为 |
| **缺点** | 每个应用都需改造，SDK 升级需各应用协同 |

## 2.5 混合架构（Hybrid）

```
                    ┌─────────────────────┐
                    │    认证中心          │
                    │  (Keycloak / CAS)    │
                    └─────────┬───────────┘
                              │
        ┌─────────────────────┼─────────────────────┐
        ▼                     ▼                     ▼
┌──────────────┐    ┌──────────────┐    ┌──────────────┐
│  网关层 SSO  │    │  SDK 模式    │    │  代理模式    │
│ (新微服务)   │    │ (旧 Spring)  │    │ (遗留系统)   │
└──────────────┘    └──────────────┘    └──────────────┘
```

实际生产环境中，大型组织往往混合多种模式：
- 核心认证中心：Keycloak / CAS Server
- 新微服务：网关层统一认证（Spring Cloud Gateway + OAuth2）
- 旧 Spring 应用：Spring Security + CAS Client
- 遗留系统（无源码）：Apache/Nginx 反向代理 + auth 插件
- 外部 SaaS：SAML 2.0 联邦

# 3. 各协议认证流程详解

## 3.1 CAS 协议流程

```
浏览器               应用(SP)               CAS Server(IdP)
  │                    │                       │
  │ ① 访问 /app        │                       │
  │───────────────────►│                       │
  │                    │ ② 未登录，302 重定向  │
  │◄───────────────────│  Location: CAS/login  │
  │                    │  ?service=app回调     │
  │                    │                       │
  │ ③ GET /login?service=app回调               │
  │──────────────────────────────────────────►│
  │                    │                       │ ④ 检测 TGC Cookie
  │                    │                       │    (无 → 展示登录页)
  │                    │                       │
  │ ⑤ 输入用户名密码并提交                    │
  │──────────────────────────────────────────►│
  │                    │                       │ ⑥ 验证凭据
  │                    │                       │ ⑦ 生成 TGT + TGC
  │                    │                       │ ⑧ 生成 ST
  │                    │                       │ ⑨ 302 重定向
  │◄──────────────────────────────────────────│
  │ Location: app回调?ticket=ST-xxx           │
  │                    │                       │
  │ ⑩ GET /app?ticket=ST-xxx                  │
  │───────────────────►│                       │
  │                    │ ⑪ 后台验证 ST         │
  │                    │──────────────────────►│
  │                    │                       │ ⑫ 验证ST并返回用户信息
  │                    │◄──────────────────────│
  │                    │ ⑬ 创建局部Session     │
  │                    │ ⑭ 302 去掉ticket参数  │
  │◄───────────────────│                       │
  │                    │                       │
  │ ⑮ 再次访问 /app (带JSESSIONID)            │
  │───────────────────►│                       │
  │◄───────────────页面正常响应                │
```

**核心票据说明：**

| 票据 | 全称 | 创建方 | 存储位置 | 生命周期 | 作用 |
|------|------|--------|---------|---------|------|
| **TGC** | Ticket Granting Cookie | CAS Server | 浏览器 Cookie | 数小时 | 表示全局登录态，用户已认证的凭证 |
| **TGT** | Ticket Granting Ticket | CAS Server | CAS 服务端（内存/Redis） | 数小时 | TGC 的服务端映射，签发 ST 的凭证 |
| **ST** | Service Ticket | CAS Server | URL 参数（一次性） | 数秒~数分钟 | 单次访问某一应用的凭证 |

## 3.2 OAuth 2.0 授权码模式流程

```
用户              User-Agent          客户端(SP)         授权服务器
 │                   │                   │                  │
 │ ① 点击登录        │                   │                  │
 │──────────────────►│                   │                  │
 │                   │ ② GET /authorize  │                  │
 │                   │───────────────────►                  │
 │                   │   ?response_type=code               │
 │                   │   &client_id=xxx                    │
 │                   │   &redirect_uri=xxx                 │
 │                   │   &scope=openid profile             │
 │                   │   &state=随机串                      │
 │                   │                   │                  │
 │                   │                   │ ③ 展示授权页面    │
 │                   │◄──────────────────│                  │
 │                   │                   │                  │
 │                   │ ④ 用户登录并同意授权                  │
 │                   │─────────────────────────────────────►│
 │                   │                   │                  │
 │                   │                   │ ⑤ 302 返回 code  │
 │                   │◄─────────────────────────────────────│
 │                   │  redirect_uri?code=AuthCode&state=xxx│
 │                   │                   │                  │
 │                   │ ⑥ 携带 code 访问回调地址              │
 │                   │───────────────────►                  │
 │                   │                   │ ⑦ POST /token    │
 │                   │                   │─────────────────►│
 │                   │                   │  grant_type=     │
 │                   │                   │   authorization_ │
 │                   │                   │   code           │
 │                   │                   │  &code=AuthCode  │
 │                   │                   │  &client_id      │
 │                   │                   │  &client_secret  │
 │                   │                   │                  │
 │                   │                   │ ⑧ 返回 Token     │
 │                   │                   │◄─────────────────│
 │                   │                   │  {               │
 │                   │                   │   access_token,  │
 │                   │                   │   refresh_token, │
 │                   │                   │   id_token,      │
 │                   │                   │   expires_in     │
 │                   │                   │  }               │
 │                   │                   │                  │
 │                   │ ⑨ 登录成功，建立局部会话               │
 │                   │◄──────────────────│                  │
```

**为什么使用授权码模式最安全：**
1. **授权码不暴露给浏览器**：code 通过前端重定向返回，但 AT 通过后端 channel（client_secret）换取
2. **client_secret 保密**：只有后端持有，前端 SPA 不应使用
3. **PKCE 增强**：即使 code 被截获也无用（见第 6 章）

## 3.3 OIDC（OpenID Connect）协议流程

OIDC 在 OAuth 2.0 基础上增加了 **ID Token** 作为身份证明：

```
OAuth 2.0:  Access Token（授权凭证） + Refresh Token（刷新凭证）
OIDC:       Access Token + ID Token（身份凭证，JWT 格式）

ID Token 结构（JWT）：
{
  "iss": "https://auth.example.com",      // 签发者
  "sub": "user-12345",                     // 用户唯一标识
  "aud": "client-abc",                     // 接收方（客户端ID）
  "exp": 1712345678,                       // 过期时间
  "iat": 1712341978,                       // 签发时间
  "auth_time": 1712341978,                 // 认证时间
  "nonce": "xyz789",                       // 防重放
  "name": "张三",                          // 用户姓名
  "email": "zhangsan@example.com",         // 用户邮箱
  "email_verified": true
}
```

**OIDC 三大认证流程：**

| 流程 | 适用场景 | 核心特征 |
|------|---------|---------|
| **Authorization Code Flow** | 有后端的 Web 应用 | code 换 token，最安全 |
| **Implicit Flow**（已废弃） | 纯前端 SPA（旧） | token 直接返回，不安全 |
| **Hybrid Flow** | 有后端但部分信息需前端消费 | code + id_token + token 组合返回 |

## 3.4 SAML 2.0 协议流程

```
用户           Service Provider        Identity Provider
 │                    │                       │
 │ ① 访问受保护资源   │                       │
 │───────────────────►│                       │
 │                    │ ② 生成 AuthnRequest   │
 │                    │    (SAML XML)         │
 │                    │ ③ 302 重定向到 IdP    │
 │◄───────────────────│                       │
 │                    │                       │
 │ ④ GET IdP SSO URL (携带 AuthnRequest)      │
 │──────────────────────────────────────────►│
 │                    │                       │ ⑤ 验证 Request
 │                    │                       │ ⑥ 展示登录页
 │                    │                       │
 │ ⑦ 输入凭据                                 │
 │──────────────────────────────────────────►│
 │                    │                       │ ⑧ 验证凭据
 │                    │                       │ ⑨ 生成 Assertion
 │                    │                       │ ⑩ 返回包含 Assertion 的 Form
 │◄──────────────────────────────────────────│
 │                    │                       │
 │ ⑪ POST SAML Response 到 ACS URL           │
 │───────────────────►│                       │
 │                    │ ⑫ 验证签名            │
 │                    │ ⑬ 提取用户信息        │
 │                    │ ⑭ 创建会话            │
 │◄───────────────────│                       │
```

**SAML 绑定方式：**

| 绑定方式 | 说明 |
|---------|------|
| **HTTP Redirect** | GET 请求 + Deflate + Base64 编码的 SAML 消息 |
| **HTTP POST** | POST 表单提交 SAML XML |
| **HTTP Artifact** | 先传递一个 Artifact（引用），后端通过 SOAP 交互获取实际 Assertion |
| **SOAP** | 后端直连 SOAP 接口交换消息 |

# 4. 协议对比矩阵

## 4.1 全方位对比

| 对比维度 | CAS | OAuth 2.0 | OIDC | SAML 2.0 |
|---------|-----|-----------|------|----------|
| **核心用途** | 认证 | 授权（+认证） | 认证 | 认证 |
| **数据格式** | XML / JSON | JSON | JSON / JWT | XML |
| **传输绑定** | Cookie + 重定向 | HTTP 重定向 + POST | HTTP 重定向 + POST | 重定向/POST/Artifact/SOAP |
| **单点登出** | ✅ 原生支持 | ❌ 无标准 | ✅ RP-Initiated Logout | ✅ 原生支持 |
| **移动端支持** | 较弱 | ✅ 原生支持 | ✅ 原生支持 | 较弱（XML 冗重） |
| **用户属性传输** | 需额外配置 | ❌ 无标准（需自定义） | ✅ ID Token + UserInfo | ✅ AttributeStatement |
| **令牌格式** | Ticket（简单） | JWT / 不透明 | JWT | XML Assertion |
| **元数据发现** | ❌ 无标准 | ❌ 无标准 | ✅ .well-known/discovery | ✅ Metadata XML |
| **加密/签名** | 可选（HTTPS 为主） | JWS/JWE | JWS/JWE | XML Sign/Encrypt |
| **配置复杂度** | 低~中 | 中 | 中 | 高 |
| **Java 生态支持** | ✅ CAS Client + Spring Security | ✅ Spring Security 5+ | ✅ Spring Security 5+ | ✅ Spring Security SAML |
| **浏览器依赖** | 强依赖 Cookie/重定向 | 中等 | 中等 | 中等 |

## 4.2 安全性对比

| 安全特性 | CAS | OAuth 2.0 | OIDC | SAML 2.0 |
|---------|-----|-----------|------|----------|
| **防重放攻击** | ST 一次性 + HTTPS | state/nonce + PKCE | nonce + PKCE | InResponseTo + NotOnOrAfter |
| **防 CSRF** | ST + 回调验证 | state 参数 | state 参数 | RelayState |
| **防 XSS 窃取 Token** | Cookie HttpOnly | Token 存后端（BFF模式） | Token 存后端 | Cookie/后端 |
| **防中间人** | HTTPS 必须 | HTTPS 必须 + PKCE | HTTPS 必须 + PKCE | HTTPS 必须 + 签名验证 |
| **令牌泄露风险** | 低（ST 短生命周期） | 中（AT 可能长周期） | 低（ID Token 短周期） | 低（Assertion 短周期） |

```
┌─────────────────────────────────────────────────────────────────┐
│                     SSO 协议选型决策树                            │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  Q1: 是否需要跨组织认证（多 IdP）？                               │
│   ├── 是 → 需要 SAML 2.0 或 OIDC                                 │
│   └── 否 → Q2                                                    │
│                                                                  │
│  Q2: 纯 Java Web 应用，不需要移动端？                             │
│   ├── 是 → 推荐 CAS（简单、成熟、SSO/SLO 完整）                   │
│   └── 否 → Q3                                                    │
│                                                                  │
│  Q3: 以下是微服务架构 + 多端（Web/iOS/Android）？                 │
│   ├── 是 → OAuth 2.0 + OIDC + JWT（无状态，云原生友好）           │
│   └── 否 → Q4                                                    │
│                                                                  │
│  Q4: 企业内已有 AD/LDAP，且需要与 Office 365 集成？               │
│   ├── 是 → Azure AD / WS-Federation                              │
│   └── 否 → 根据技术栈选择                                         │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

## 5.1 典型场景推荐

| 场景 | 推荐方案 | 理由 |
|------|---------|------|
| **企业内部 Java Web 系统群** | CAS + Spring Security | 配置简单，社区成熟，SLO 支持好 |
| **微服务 + 前后端分离 + 移动端** | OAuth2 + OIDC + JWT | 无状态，多端统一，云原生无状态 |
| **B2B SaaS 平台** | SAML 2.0 + OIDC（双协议） | 企业客户大多支持 SAML，新客户用 OIDC |
| **互联网 C 端产品矩阵** | OAuth2 + OIDC | Google/微信等主流模式 |
| **金融/政务（高安全）** | SAML 2.0 + 国密 | 签名加密完善，合规要求 |
| **高校联盟（多机构）** | SAML 2.0（CAS 也可） | CAS 在教育领域广泛使用，SAML 适合跨机构 |
| **快速原型/小团队** | Keycloak（单体部署） | 开箱即用，支持 OAuth2/OIDC/SAML 多协议 |

# 6. 架构设计原则

## 6.1 认证与授权分离

```
┌──────────────────────────────────────┐
│           认证中心 (AuthN)             │
│  负责：验证身份、签发 Token           │
└──────────────┬───────────────────────┘
               │ 签发 Token
               ▼
┌──────────────────────────────────────┐
│        业务系统 (AuthZ)               │
│  负责：解析 Token、判断权限、处理业务 │
└──────────────────────────────────────┘
```

**实践要点：**
- 认证中心不做授权（RBAC 除外的基础角色可以放在 Token 中）
- 业务系统根据 Token 中的用户标识自行决定权限
- 好处：认证中心无需感知各系统的业务权限模型

## 6.2 无状态优先

| 对比 | 有状态（Session） | 无状态（JWT） |
|------|-----------------|-------------|
| **原理** | 服务端存储 Session，客户端传 SessionID | 所有信息编码在 Token 中 |
| **扩展性** | 需 Session 共享或粘性路由 | 天然水平扩展 |
| **性能** | 内存查询（快）| 验签（快），无 I/O |
| **吊销** | 直接删除 Session（即时） | 需黑名单或短 TTL（延迟） |
| **占用** | 服务端内存 | Token 更大（HTTP Header） |

## 6.3 纵深防御

```
第一层：网络防护（WAF / 防火墙）
第二层：传输安全（HTTPS / mTLS）
第三层：认证安全（MFA / 强密码 / 锁定策略）
第四层：令牌安全（短 TTL / 签名 / 加密）
第五层：应用安全（CORS / CSRF / XSS 防护）
第六层：审计监控（日志 / 告警 / SIEM）
```

## 6.4 故障降级设计

认证中心故障时，业务系统应支持：
1. **本地认证缓存**：已登录用户可以继续操作一段时间
2. **只读模式**：核心业务只读不写，降级但不完全瘫痪
3. **离线模式**：关键系统（如生产控制系统）支持离线身份验证
