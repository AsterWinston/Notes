
# 1. 概述

**SSO（Single Sign-On，单点登录）** 是一种身份认证机制，允许用户使用一组凭据（如用户名和密码）登录一次后，即可访问多个相互信任的、独立的软件系统，而无需重复输入凭据。

```
┌──────────────────────────────────────────────────────────────────┐
│                        SSO 认证中心                                │
│                    (sso.example.com)                              │
│                                                                   │
│    用户登录一次 ──────► 获得全局会话（Global Session）              │
│                              │                                    │
│         ┌────────────────────┼────────────────────┐              │
│         ▼                    ▼                    ▼              │
│   ┌──────────┐       ┌──────────┐       ┌──────────┐            │
│   │ 系统 A   │       │ 系统 B   │       │ 系统 C   │            │
│   │ 论坛     │       │ 商城     │       │ OA 系统  │            │
│   └──────────┘       └──────────┘       └──────────┘            │
│                                                                   │
│   用户访问任意系统 ———► 无需再次登录（已通过 SSO 验证身份）         │
└──────────────────────────────────────────────────────────────────┘
```

**核心价值（一句话）**：一次认证，处处通行。

# 2. 为什么需要 SSO

## 2.1 解决的核心痛点

| 痛点 | 没有 SSO | 有 SSO |
|------|---------|--------|
| **多次登录** | 用户需在每个系统重复输入用户名密码 | 登录一次，所有系统共享登录态 |
| **密码疲劳** | 用户可能为不同系统设置弱密码或相同密码 | 只需记住一套凭据 |
| **管理成本高** | 管理员需在多个系统分别管理账号 | 统一认证中心管理用户身份 |
| **安全风险大** | 多个登录入口增加了攻击面 | 集中管控认证，统一安全策略 |
| **用户体验差** | 反复跳转登录页，打断操作流程 | 无感切换，流畅体验 |
| **审计困难** | 用户行为分散在不同系统，难以统一审计 | 登录和访问记录集中在认证中心 |

## 2.2 典型应用场景

| 场景 | 说明 | 示例 |
|------|------|------|
| **企业内部系统** | OA、CRM、ERP、HR、邮箱等内部系统集成 | 企业微信/钉钉工作台 |
| **互联网产品矩阵** | 公司旗下多个产品共享用户体系 | Google（Gmail/YouTube/Docs） |
| **SaaS 平台** | 多个第三方 SaaS 服务统一认证 | 使用 Google/微信 登录第三方网站 |
| **微服务架构** | 数十/数百个微服务统一认证 | Spring Cloud + OAuth2 微服务体系 |
| **教育/政府平台** | 教育和政务服务统一身份认证 | 学信网、政务服务平台 |
| **合作伙伴系统** | B2B 场景下合作伙伴系统互通 | 供应链管理系统集成 |

# 3. SSO 发展史

```
1999 ─── Microsoft Passport（最早的商业 SSO 尝试，因隐私争议失败）
2002 ─── SAML 1.0 发布（基于 XML 的企业级联邦身份协议）
2003 ─── CAS 1.0 发布（Yale 大学开源，教育领域广泛使用）
2005 ─── SAML 2.0 发布（成为企业 SSO 的事实标准）
2006 ─── OpenID 1.0（去中心化身份认证，面向消费者互联网）
2010 ─── OAuth 1.0（授权协议，Twitter 推动）
2012 ─── OAuth 2.0 发布（简化授权流程，成为行业标准）
2014 ─── OpenID Connect 1.0 发布（基于 OAuth2 的身份认证层）
2015 ─── JWT 广泛流行（无状态令牌，微服务架构推动）
2017 ─── Spring Security 5.0 发布（原生 OAuth2/OIDC 支持）
2019 ─── FIDO2 / WebAuthn（无密码认证标准）
2022 ─── OAuth 2.1 发布（合并最佳实践，废弃不安全授权模式）
```

# 4. SSO 核心概念

## 4.1 认证 vs 授权

| 维度 | 认证（Authentication） | 授权（Authorization） |
|------|----------------------|----------------------|
| **核心问题** | 你是谁？ | 你能做什么？ |
| **英文缩写** | AuthN | AuthZ |
| **依赖关系** | 先认证，再授权 | 依赖认证结果 |
| **典型技术** | 用户名密码、OTP、生物识别、证书 | RBAC、ACL、OAuth2 Scope |
| **输出物** | 身份凭证（Session/Token） | 权限声明（Roles/Scopes/Permissions） |
| **SSO 关联** | SSO 主要解决认证问题 | 授权在认证之后，由各子系统独立判断 |

## 4.2 核心术语表

| 术语 | 英文 | 说明 |
|------|------|------|
| 身份提供方 | IdP（Identity Provider） | 负责用户身份认证和提供身份信息的服务方 |
| 服务提供方 | SP（Service Provider） | 依赖 IdP 进行身份认证的业务系统 |
| 认证中心 | CAS Server / Auth Server | SSO 的核心，集中管理认证和票据 |
| 全局会话 | Global Session | 用户在 SSO 认证中心建立的登录会话 |
| 局部会话 | Local Session | 用户在每个子系统内建立的登录会话 |
| 票据 | Ticket | 一次认证的凭证，用于在系统间传递认证结果 |
| 令牌 | Token | 代表用户身份的加密字符串（如 JWT） |
| 授权码 | Authorization Code | OAuth2 中用于换取 Access Token 的中间凭证 |
| 访问令牌 | Access Token | 用于访问受保护资源的凭证 |
| 刷新令牌 | Refresh Token | 用于获取新的 Access Token 的长效凭证 |
| ID 令牌 | ID Token | OIDC 中专用于携带用户身份信息的 JWT |
| 声明 | Claim | Token 中包含的用户属性信息（姓名、邮箱等） |
| 回调地址 | Redirect URI / Callback | 认证完成后 IdP 重定向到的地址 |
| 中继方 | RP（Relying Party） | 同 SP，依赖 IdP 进行认证的应用 |
| 单一登出 | SLO（Single Logout） | 在一个系统中登出后，所有系统同时登出 |
| 发现服务 | Discovery | OIDC 中客户端自动获取 IdP 配置的机制 |
| 元数据 | Metadata | SAML 中描述 SP/IdP 能力和端点的 XML 文档 |

## 4.3 SSO 会话模型

```
                     ┌─────────────────────┐
                     │   认证中心 (CAS)     │
                     │                     │
                     │  TGC (Cookie)       │ ← 全局会话凭证（浏览器）
                     │  TGT (Server)       │ ← 全局会话凭证（服务端）
                     │                     │
                     │  用户登录后，CAS 在浏览器写入 TGC Cookie
                     └─────────┬───────────┘
                               │
          ┌────────────────────┼────────────────────┐
          ▼                    ▼                    ▼
   ┌────────────┐       ┌────────────┐       ┌────────────┐
   │  系统 A    │       │  系统 B    │       │  系统 C    │
   │            │       │            │       │            │
   │ JSESSIONID │       │ JSESSIONID │       │ JSESSIONID │ ← 局部会话
   │ (Cookie)   │       │ (Cookie)   │       │ (Cookie)   │
   └────────────┘       └────────────┘       └────────────┘

流程：
1. 用户访问系统 A → 302 跳转到 CAS 登录页
2. 用户在 CAS 登录 → CAS 创建 TGT，浏览器写入 TGC Cookie
3. CAS 签发 ST（Service Ticket），302 跳转回系统 A
4. 系统 A 用 ST 向 CAS 验证 → 验证通过，创建局部会话（JSESSIONID）
5. 用户访问系统 B → 302 跳转 CAS
6. CAS 检测到 TGC Cookie 有效（已登录）→ 直接签发 ST，302 跳回系统 B
7. 系统 B 用 ST 向 CAS 验证 → 验证通过，创建局部会话
   → 用户无需再次输入密码！
```

# 5. SSO 协议族一览

| 协议 | 全称 | 推出年份 | 适用场景 | 认证/授权 | 数据格式 |
|------|------|---------|---------|----------|----------|
| **CAS** | Central Authentication Service | 2003 | 企业内部 Web 应用 | 认证 | XML / JSON |
| **SAML 2.0** | Security Assertion Markup Language | 2005 | 企业级联邦身份 | 认证 | XML |
| **OAuth 2.0** | Open Authorization | 2012 | 授权 / 第三方登录 | 授权（+认证） | JSON |
| **OIDC** | OpenID Connect | 2014 | 现代 Web/Mobile 认证 | 认证 | JSON / JWT |
| **WS-Federation** | Web Services Federation | 2006 | 微软生态 SSO | 认证 | XML (SOAP) |
| **LDAP** | Lightweight Directory Access Protocol | 1993 | 企业内网统一目录 | 认证 | 二进制/LDIF |
| **Kerberos** | — | 1988 | 企业内网 Windows 域 | 认证 | 票据（二进制） |
| **JWT** | JSON Web Token | 2015 | 无状态认证（微服务） | 认证+授权 | JSON |

## 5.1 协议选择建议

```
是否需要企业级标准（SAML）？
├── 是 → 企业内部多 SaaS 集成 → SAML 2.0
└── 否
    ├── 纯 Web 应用，Java 生态 → CAS
    ├── 现代 Web + 移动端 → OAuth 2.0 + OIDC
    ├── 微服务架构 → JWT + OAuth 2.0（无状态）
    └── 微软生态（AD + Office 365） → WS-Federation / Azure AD
```

# 6. SSO 的利与弊

## 6.1 优势

| 优势 | 说明 |
|------|------|
| **用户体验提升** | 一次登录，无缝切换多个应用 |
| **安全策略集中** | 密码策略、MFA、风控在认证中心统一管控 |
| **降低管理成本** | 用户生命周期管理（入职/离职）一次操作，全局生效 |
| **减少攻击面** | 登录入口收敛为单点，便于防护和监控 |
| **审计合规** | 登录操作集中记录，满足合规审计要求 |
| **密码安全** | 用户只需记住一个强密码，减少弱密码风险 |

## 6.2 挑战与风险

| 挑战 | 说明 | 缓解措施 |
|------|------|---------|
| **单点故障** | 认证中心宕机，所有系统无法登录 | 集群化部署 + 多活 |
| **性能瓶颈** | 所有认证请求汇聚到认证中心 | 缓存 + 异步 + 水平扩展 |
| **票据劫持** | Cookie/Token 泄露导致身份冒用 | HTTPS、HttpOnly、Secure、SameSite |
| **凭证关联风险** | 一套密码被盗 → 所有系统沦陷 | MFA 多因素认证 |
| **跨域复杂性** | 不同域名下 Cookie 不可见 | 第三方 Cookie + CORS 或 SAML/OIDC |
| **协议异构** | 新旧系统协议不统一 | 认证网关做协议转换 |
| **登出同步难** | 一处登出需通知所有系统 | SLO 协议（CAS/SAML/OIDC 均支持） |
