压测做久了会发现一个规律：脚本写得好不好是次要矛盾，测试设计对不对才是主要矛盾——目标含糊的压测，跑再多轮也产不出可以拍板的结论；而一次目标清晰、窗口干净、避开统计陷阱的测试，一份报告就能支撑容量决策。本章讲怎么把业务诉求翻译成可判定的性能目标、怎么建立与使用基线、怎么正确地分析结果，以及几个足以让结论作废的经典反模式。

# 1. 测试设计方法论

## 1.1 需求澄清

**性能测试的第一步不是写脚本，而是把"系统要快"翻译成三个可判定的数字：目标吞吐、延迟上限、错误率容忍度。**需求澄清阶段要产出四样东西：

- **关键路径清单**：哪些接口/业务流进入压测范围，依据生产流量排名与业务重要性（下单链路即使 QPS 不高也必须测）。
- **流量画像**：各路径的请求占比、峰谷曲线、数据来源（APM/网关日志），这决定第 7 篇讲的场景强度分配。
- **SLO 三元组**：形如"订单接口在 2000 RPS 下 p95 < 300ms、错误率 < 0.1%"，每个数字都要有出处（产品承诺、历史数据或竞品水位）。
- **环境与数据边界**：在哪个环境测、用什么数据、写入如何回收（第 8 篇）。

**设计考量**：SLA 与 SLO 要区分使用——SLA（Service Level Agreement）是对外承诺，违约有代价；SLO（Service Level Objective）是内部目标，通常比 SLA 严一档（如 SLA p99 < 1s，内部 SLO 定 p99 < 700ms），留出安全边际。压测的及格线应该对着 SLO 画，而不是贴着 SLA 压线通过。

没有明确数字的压测请求（"帮我们看看系统扛不扛得住"）应当被打回去补目标——**无阈值的测试无法产生"通过/不通过"的判定，只能产生一堆无法解读的数字**。

## 1.2 设定基线

**基线（baseline）是同一环境、同一负载下可重复的参照测量，它把"这次慢了"变成"比基线慢了 40%"。**基线的建立流程：先用小负载（单 VU、低到达率）跑通链路，记录无竞争状态下的响应时间作为"理论最优"；再在目标负载下跑标准曲线（预热 + 稳态 + 降载），保存完整报告与环境快照（应用版本、JVM 参数、数据规模、机器规格）。此后每次版本发布或配置变更，用**完全相同的脚本与负载**重跑，与基线对比。

基线的三个使用纪律：

- **基线随环境走**：测试环境的基线不能拿去解读生产表现（见 5.3），环境升级后基线作废重测。
- **基线随数据走**：库里 10 万行和 1000 万行的查询延迟不是一个量级，基线报告必须记录数据规模。
- **对比看分位数不看均值**：p95/p99 的漂移远比平均值敏感——平均值不变而 p99 翻倍，往往意味着出现了新的慢路径。

> **行业实践**：成熟团队把基线测试固化为 CI 里的每日任务（固定负载、固定脚本、结果入库），发布前自动与基线比对，性能回归在合并前就被拦截，而不是等到大促演练时才发现。

# 2. 测试类型与策略

## 2.1 负载测试

**负载测试回答"预期流量下系统表现是否达标"，是唯一以"通过/不通过"为产出的测试类型。**设计要点：负载取业务峰值的 100%（有时加 20-30% 安全系数），稳态窗口足够长（≥ 10 分钟），判定条件预先写死在 thresholds 里，跑完自动给出 exit code：

```javascript
export const options = {
  scenarios: {
    load: {
      executor: "constant-arrival-rate",
      rate: 2000,                    // 目标吞吐：2000 迭代/秒
      timeUnit: "1s",
      duration: "15m",
      preAllocatedVUs: 500,
      maxVUs: 2000,
    },
  },
  thresholds: {
    // 判定条件与 SLO 一一对应，任何一条不达标则 exit code 非 0
    "http_req_duration{scenario:load}": ["p(95)<300", "p(99)<800"],
    "http_req_failed": ["rate<0.001"],        // 错误率 < 0.1%
    "dropped_iterations": ["count==0"],       // 负载发生器必须兑现 rate
  },
};
```

## 2.2 压力测试

**压力测试回答"极限在哪、怎么死的"，它的产出不是通过与否，而是拐点坐标与失效模式。**阶梯加压（第 7 篇 3.2 节）直到触发预定失败判据，全程记录三个关键观察点：

- **拐点（inflection point）**：吞吐停止随负载上升的转折点——这一点之前系统处于"延迟换吞吐"的线性区，之后进入排队主导的非线性区。
- **失效模式**：过载后系统是优雅降级（限流、排队、快速失败）还是雪崩（线程池耗尽、级联超时、集群不可用）；后者比"极限值低"严重得多。
- **恢复行为**：撤掉负载后，系统多久回到基线？需要人工重启吗？（浸泡式恢复观察可以接在压力测试尾部做。）

```text
吞吐 ▲                          拐点
     │                    ╱─────●─────╲   ← 过载后吞吐掉头（排队与重试消耗资源）
     │                 ╱              ╲
     │              ╱  线性区          ╲ 拥塞崩溃区
     │           ╱  （延迟缓升）        （延迟爆炸、错误率飙升）
     └────────┴───────────────────────┴──→ 负载
```

## 2.3 稳定性测试

**稳定性（浸泡）测试回答"时间会带来什么"，专抓累积性缺陷：内存泄漏、连接池耗尽、文件句柄泄漏、日志盘写满、缓存无限增长。**设计要点：负载取日常的 70-80%（刻意避开拐点，确保失败只可能来自累积而非强度），时长 4 小时起步、有条件下 24 小时；观察指标全部看**趋势斜率**而非绝对值——RSS 每小时涨 50MB 且无回落平台，就是泄漏实锤，哪怕测试结束时还没 OOM。Java 应用配合服务端 GC 日志与堆转储（前后各一次对比支配树），数据库侧盯慢查询数量与连接数的时间序列。

## 2.4 突刺测试

**突刺测试回答"流量瞬间翻几倍会发生什么"，验证的是弹性机制而非容量本身。**秒级陡升（第 7 篇 3.1 节的 spike 配方）后重点观察四件事：限流是否按配置生效（而不是直接打穿到数据库）；自动扩容是否在 SLA 时间内完成；扩容完成前的排队是否引发客户端超时重试、重试是否放大了流量（重试风暴）；尖峰过后系统是否自行恢复。突刺测试最常见的发现不是"扛不住峰值"，而是**恢复不了**——弹性伸缩的冷却时间、连接池的重建速度、缓存被击穿后的回源风暴，都在尖峰回落之后才暴露。

# 3. 业务场景建模

## 3.1 用户路径与权重

**路径权重的唯一合法来源是生产数据：网关日志、APM 调用链、埋点统计，拍脑袋的比例会让整个测试的结论失去外推资格。**建模步骤：统计各接口/页面的真实请求占比 → 按占比分配场景强度（到达率场景直接按比例分 rate；闭合场景按"用户数 × 各路径操作频率"折算）→ 保留 5-10% 的长尾路径合并成一个杂项场景，防止只测头部接口。权重要落成文档并定期（季度级）用最新生产数据校准——业务结构会变，去年的画像今年可能已经失真。

## 3.2 思考时间与节奏

**思考时间（think time）决定闭合模型下每个 VU 的真实产出速率，省略它等于把用户变成攻击脚本。**真实用户在页面上停留、阅读、填写，两次请求之间隔几秒到几十秒；压测脚本里的 `sleep()` 就是对这段间隔的建模。它的取值同样来自生产：用户行为分析给出页面平均停留时长，减去服务端处理时间即为思考时间。节奏建模的连带效应要算清楚：加了 5 秒思考时间后，同样 100 RPS 的目标需要约 500 个并发 VU（Little 定律），VU 成本与压测机资源要跟着重估——这也是长思考时间场景更适合用到达率执行器的原因（rate 直接声明，VU 数由调度器托管）。

# 4. 结果分析与结论

## 4.1 关键指标解读

**指标解读的第一原则是分位数优先：平均延迟是被分布骗得最惨的指标。**一次迭代 1000 个请求，990 个 10ms、10 个 2s，平均值 30ms 看起来很健康，但 1% 的用户经历了 2 秒等待——p99 才是这 1% 用户的真实体验。延迟、吞吐、错误率三者的耦合关系是解读的骨架：

```text
延迟 ▲
     │                                    ╱ ← 排队论拐点：利用率接近 100%，
     │                                 ╱      延迟随负载非线性爆炸
     │                            ╱
     │              ─────────╱            ← 线性区：延迟缓慢爬升
     │     ─────────                        （服务时间主导）
     └────────────────────────────────→ 负载（利用率）
```

**吞吐与并发、延迟存在守恒关系**（Little 定律：并发 = 吞吐 × 延迟）：闭合模型里延迟上升必然导致吞吐下降；开放模型里延迟上升导致积压 VU 上升而吞吐维持。因此"吞吐达标但 p95 超标"与"p95 达标但吞吐不足"是两种不同的病：前者通常是慢查询/GC/锁竞争，后者通常是并发度不足或资源饱和。错误率要和延迟一起看：过载时错误率上升若伴随延迟飙升，是容量问题；错误率上升但延迟正常，多半是业务校验或限流在拒绝请求，性质完全不同。

## 4.2 稳态窗口与 ramp-up 排除

**结论只能建立在稳态窗口上：预热段（ramp-up）的样本混入汇总，会把冷启动毛刺算进分位数，把尚未充满的连接池与缓存算进延迟。**k6 的 end-of-test summary 统计全程样本，剔除预热的手段在第 7 篇 4.1 节列过：拉长稳态占比、输出到时序后端框窗口、或用独立预热场景 + 主场景分离。分析时的标准动作：在 Grafana 上框选稳态区间重算分位数，与 k6 汇总值对比——如果两者差距明显（如 p95 差 30% 以上），说明预热/降载污染严重，测试时长结构需要重设计。降载段同样要排除，且要额外检查一个反直觉现象：**降载后延迟不回落甚至继续升高**，这通常意味着系统里还有未消化完的积压（队列、重试），是容量不足的滞后信号。

## 4.3 结论表达

**压测报告的产出是判定，不是数据堆：每一节都以"达标/不达标/存疑 + 一句话依据"开头，数据表作为证据附后。**合格的结论长这样："订单创建接口在 2000 RPS 下 p95 = 240ms（SLO 300ms，达标）、错误率 0.02%（SLO 0.1%，达标）、压测机 dropped_iterations = 0（负载真实兑现）；瓶颈在数据库连接池（利用率 94%），建议扩至 200 后复测。"反面教材是"本次压测共产生 180 万个样本，平均延迟 87ms，详见附表"——没有判定、没有瓶颈归因、没有下一步动作的报告，等于没测。

> **行业实践**：报告固定包含五要素——目标（SLO 原文）、环境（版本/规格/数据规模）、负载配方（执行器参数）、稳态窗口指标（对照 SLO 逐项判定）、瓶颈与建议。缺任何一项，结论的可信度都会被评审方质疑。

# 5. 常见设计误区

## 5.1 只看平均值

**平均值掩盖双峰分布与长尾，是最常见也最隐蔽的误读。**典型场景：命中缓存的请求 5ms、回源的请求 800ms，缓存命中率 90% 时平均值约 80ms，看起来"还行"——但 10% 回源用户的体验是 800ms，且命中率稍有波动平均值就剧烈变化，指标完全失去稳定性。纪律：报告里只出现 p50/p95/p99（必要时 p999），平均值最多作为参考列；k6 的 thresholds 也一律写 `p(95)`/`p(99)` 形式。

## 5.2 协调遗漏（coordinated omission）

**协调遗漏指负载发生器"体贴地"等待慢响应、从而少发请求，导致最慢的那批样本系统性地缺失于统计。**机制拆开看：闭合模型下 VU 发起请求 → 系统卡住 10 秒 → 这 10 秒里该 VU 什么也不做 → 真实世界本应到达的请求根本没被发出 → 汇总数据里"卡顿期间"的样本数为零，p99 被显著低估。这不是 k6 的缺陷，而是所有闭合模型压测工具（JMeter 线程组同理）的固有偏差；系统越接近崩溃，偏差越大——**恰恰在最需要准确数据的过载区，闭合模型最不可信**。

规避手段按有效性排序：

- **改用到达率执行器**（根本解）：开放模型按固定节奏发迭代，系统卡住时 k6 扩容 VU 继续发，排队被如实记录进延迟分布；
- 检查 `dropped_iterations`：到达率模型下它非零说明连 k6 都发不动了，真实延迟比测得的更糟；
- 闭合模型结果仅作相对比较（版本 A vs 版本 B），不用于绝对容量承诺。

## 5.3 压测环境 vs 生产差异

**测试环境的结论外推到生产之前，必须先列出两者的差异清单并评估每一项的影响方向。**常见差异及其失真方向：

| 差异维度 | 典型情况 | 对结论的影响 |
|---------|---------|-------------|
| 机器规格 | 测试环境单机 4C8G，生产 16C64G × N 台 | 容量数字不可线性换算，非线性资源（锁、GC）行为完全不同 |
| 数据规模 | 测试库 1 万行，生产 10 亿行 | 索引深度、缓存命中率、扫描成本全面失真，查询类结论作废 |
| 依赖系统 | 测试环境依赖是 mock 或独立小集群 | 下游延迟与容量被理想化，链路结论偏乐观 |
| 网络拓扑 | 同机房直连 vs 生产跨机房/经过 LB、网关 | RTT 与带宽差异直接进入延迟分布 |
| 流量结构 | 只测了单接口 vs 生产混合流量 | 资源争抢缺失，单接口容量被高估（第 7 篇 5.1） |

处理原则：**能对齐的尽量对齐**（数据量至少同数量级、依赖用真实服务、经同样的网关链路）；**不能对齐的量化折算并在报告里显式声明**（"测试环境为生产 1/4 规格，结论按保守线性折算并保留 30% 余量"）；关键大促前的最终验证，用生产环境的影子流量或全链路压测完成，测试环境的结论只用于版本间的相对比较。

# 6. 小结

| 环节 | 核心纪律 |
|------|---------|
| 目标 | SLO 三元组（吞吐/p95/错误率）先行，无阈值不开测；内部 SLO 严于对外 SLA |
| 基线 | 同环境同负载可重复测量，随版本/数据/环境变更作废重测；CI 每日基线比对拦截回归 |
| 类型选择 | 负载测试出判定、压力测试出拐点与失效模式、浸泡测试看趋势斜率、突刺测试验弹性与恢复 |
| 结果分析 | 分位数优先；结论只建立在稳态窗口；吞吐-延迟-错误率用 Little 定律联合解读 |
| 反模式 | 只看平均值（掩盖长尾）；闭合模型的协调遗漏（过载区系统性低估延迟，用到达率执行器规避）；环境差异不声明（结论不可外推） |

方法论解决"测得对"，但一个团队长期维护几十上百个压测脚本时，"写得乱"会成为新的瓶颈——下一篇进入脚本工程化：模块拆分、公共封装、自定义汇总与 CI 复用。
