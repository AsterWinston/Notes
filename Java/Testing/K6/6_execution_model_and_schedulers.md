# 1. 执行模型概述

## 1.1 VU 与调度核心思想
k6 的执行模型核心是“虚拟用户 + 调度器”。每个 VU 对应一个独立的 JS 运行时实例，由 Go 协程调度执行。调度器负责按照配置的执行器规则驱动 VU 执行与创建。

## 1.2 开放模型与闭合模型
- 闭合模型（Closed Model）：固定并发 VU 数，系统变慢会拉低吞吐
- 开放模型（Open Model）：按到达率驱动请求，更贴近真实流量

# 2. 执行器体系

## 2.1 常见执行器分类
- `constant-vus`：固定并发
- `ramping-vus`：并发随时间变化
- `constant-arrival-rate`：固定到达率
- `ramping-arrival-rate`：到达率随时间变化

## 2.2 执行器选择策略
- 验证并发极限：使用 `ramping-vus`
- 贴近真实流量：使用 `constant-arrival-rate`
- 长稳测试：使用 `constant-vus` 或 `constant-arrival-rate`

# 3. 负载模型设计

## 3.1 目标拆解
- 业务目标转化为吞吐、延迟、错误率
- 通过 SLA/SLO 反推合理并发与到达率

## 3.2 预热与稳定段
- 预热避免冷启动影响数据
- 稳定段用于采样核心指标

# 4. 资源与执行限制

## 4.1 VU 的成本
- VU 数增大带来 JS 运行时实例数量增多
- 高 VU 可能导致客户端 CPU/内存瓶颈

## 4.2 迭代节奏控制
- 使用 `sleep` 或流程拆分控制节奏
- 过快迭代会导致客户端成为瓶颈

# 5. 常见误区

## 5.1 只追求高 VU
- VU 不等于吞吐，吞吐受服务端与客户端共同约束

## 5.2 不区分开放/闭合模型
- 闭合模型不能直接反映真实流量下的排队效应
- 开放模型更适合做容量评估
