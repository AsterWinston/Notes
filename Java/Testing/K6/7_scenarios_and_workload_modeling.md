真实系统的流量从来不是"一群一模一样的用户做一模一样的事"：浏览的人多、下单的人少，白天峰值高、凌晨低谷平。k6 的 scenarios 机制把"不同用户群体在不同时间的行为模式"变成可声明、可组合、可复现的配置，是从"能压接口"到"能模拟业务"的分水岭。本章讲多场景编排、五类典型负载曲线的参数配方，以及采样窗口的设计。

# 1. 场景与 workload 概念

## 1.1 场景的意义

**场景（scenario）是 k6 里一个独立的负载发生器：它绑定了"跑哪个函数（exec）+ 用什么执行器 + 打什么标签（tags）+ 何时开始（startTime）"这四件事。**没有 scenarios 时，k6 用命令行参数生成一个默认场景；一旦声明 scenarios，就进入显式编排模式——多个场景并行运行，各自有独立的 VU 池、独立的指标标签、独立的启停时间。

场景抽象解决的核心问题是**流量结构**：生产环境上，商品详情页的请求量可能是下单接口的 50 倍，如果压测脚本用同一个函数以同一比例混跑所有接口，测出来的容量数字与生产表现对不上。把每类用户行为拆成一个场景、按真实比例配置各自的负载强度，压测流量才具备结构上的相似性。

## 1.2 workload 组成

一份完整的 workload 描述由四个要素构成：

| 要素 | 回答的问题 | 对应配置 |
|------|-----------|---------|
| 强度 | 多大的负载 | 执行器类型 + vus/rate 参数 |
| 结构 | 流量按什么比例混合 | 多个场景的 exec/tags 划分 |
| 形状 | 负载随时间怎么变化 | stages、startTime、duration |
| 边界 | 起止如何收尾 | gracefulRampDown、gracefulStop |

**设计考量**：形状要素里最容易漏掉的是"三段式"——预热段让系统进入热状态，稳态段作为唯一样本窗口，降载段观察资源回收。只有峰值没有平台的负载曲线（比如一路 ramp 上去直接结束），测出的其实是瞬态行为，不能当容量结论用。

# 2. 多场景设计

## 2.1 独立场景配置

**scenarios 里的每个键就是一个场景名，它会作为 `scenario` 标签附着在该场景产生的所有指标上**——这是多场景测试事后分析的关键：结果里可以按 scenario 标签过滤，单独看下单链路的 p95 而不被浏览流量稀释。每个场景独立配置执行器、目标函数与环境：

```javascript
import http from "k6/http";
import { sleep } from "k6";

export const options = {
  scenarios: {
    browse: {                          // 场景一：浏览用户
      executor: "constant-vus",        // 闭合模型，恒定并发
      vus: 20,                         // 20 个并发 VU
      duration: "2m",                  // 跑 2 分钟
      exec: "browseUser",              // 指定执行函数（不写则为 default）
      tags: { user_type: "browser" },  // 自定义标签，随所有指标上报
      env: { PAGE: "home" },           // 场景级环境变量，注入 __ENV
      gracefulStop: "10s",             // 收尾宽限期
    },
    buy: {                             // 场景二：购买用户
      executor: "ramping-arrival-rate",// 开放模型，到达率驱动
      startRate: 5,                    // 初始每秒 5 次迭代
      timeUnit: "1s",
      preAllocatedVUs: 10,             // 预分配 VU
      maxVUs: 50,                      // 扩容上限
      exec: "buyUser",
      tags: { user_type: "buyer" },
      stages: [
        { target: 20, duration: "1m" }, // 1 分钟升到 20 it/s
        { target: 20, duration: "1m" }, // 稳态 1 分钟
        { target: 5, duration: "1m" },  // 降回 5 it/s
      ],
      startTime: "30s",                // 延迟 30 秒启动，错峰
    },
  },
};

export function browseUser() {         // browse 场景的执行函数
  http.get("https://test.k6.io/");
  sleep(Math.random() * 2 + 1);        // 思考时间 1-3 秒
}

export function buyUser() {            // buy 场景的执行函数
  http.post("https://test.k6.io/cart", { item: "book" });
  sleep(1);
}
```

几个容易踩坑的细节：

- **exec 指向的函数必须导出**（`export function`），未指定 exec 时用 `default` 导出函数；不同场景可以共用同一个 exec，只靠 tags/env 区分。
- **env 是场景级环境变量**，在该场景的 VU 里通过 `__ENV.PAGE` 读取；它覆盖全局 `-e` 传入的同名变量，适合做"同一段代码、不同场景不同参数"。
- **startTime 控制场景错峰**：默认所有场景同时启动；把部分场景延后，可以模拟"先有浏览流量打底、购买流量随后进入"的真实时序。
- **整个测试在所有场景都结束后才结束**，总时长 = 各场景（startTime + 自身时长）的最大值。

## 2.2 分流与比例控制

**流量占比有两条实现路径：场景级分流（推荐）与函数内加权分流。**场景级分流把比例显式写进配置——浏览：购买 = 8:2，就配 browse 80 it/s、buy 20 it/s 两个到达率场景；优点是每类流量的指标天然按 scenario 标签分开，缺点是每个场景一份配置，场景多了会臃肿。函数内加权则在单个 exec 里按随机数或权重数组决定走哪条路径：

```javascript
export default function () {
  const r = Math.random();
  if (r < 0.7) {
    browseFlow();          // 70% 走浏览路径
  } else if (r < 0.9) {
    searchFlow();          // 20% 走搜索路径
  } else {
    buyFlow();             // 10% 走购买路径
  }
  sleep(1);
}
```

**设计考量**：核心链路（下单、支付）建议拆成独立场景——它们的 SLO 与浏览接口不同，需要独立的阈值（`http_req_duration{scenario:buy}` 可以只对购买流量设 p95 门禁）；长尾的低频行为可以合并进一个"杂项"场景用权重分流。两种方式的另一个差异是样本量：权重分流下低频路径的样本数 = 总迭代数 × 权重，小比例路径可能样本不足导致分位数抖动，独立场景则可以为它单独指定足够的强度。

# 3. 典型 workload 模式

## 3.1 五种测试类型的参数配方

**冒烟、负载、压力、峰值、浸泡五类测试的区别不在脚本逻辑，而在负载曲线的形状与时长。**同一份业务脚本，换一套场景参数就切换了测试类型：

| 类型 | 目的 | 负载形状 | 典型参数配方 | 关注指标 |
|------|------|---------|-------------|---------|
| 冒烟（smoke） | 验证脚本与链路可用 | 极低强度、极短 | 1-2 VU × 30s-1m，或 per-vu-iterations 各 5 次 | 错误率 = 0，check 全过 |
| 负载（load） | 验证预期流量下的表现 | 升到目标值 + 长稳态 | ramping 至目标 rate → 稳态 ≥ 10m → 降载 | p95/p99、错误率、吞吐是否达标 |
| 压力（stress） | 找容量上限与失效模式 | 持续阶梯加压到崩溃 | ramping-vus/arrival-rate 多级台阶，直到错误率飙升 | 拐点位置、失效是否优雅、恢复能力 |
| 峰值（spike） | 验证突发流量的弹性 | 陡升陡降的窄尖峰 | 基线负载 + 数秒内升 5-10 倍、维持 1-2m、数秒回落 | 限流/扩容是否生效、有无雪崩 |
| 浸泡（soak） | 暴露累积性问题 | 中等强度、超长时长 | 约 70% 目标负载 × 1-4 小时以上 | 内存增长、连接泄漏、延迟缓慢爬升 |

负载测试的标准曲线（也是后续几种的基形）：

```text
rate
 ▲
 │            ┌───────────────────┐
 │           ╱ 稳态段（≥70% 时长）  ╲            ← 唯一样本窗口
 │          ╱     目标负载          ╲
 │         ╱                         ╲
 │        ╱ 预热段                     ╲ 降载段
 │       ╱ (ramp-up)                    ╲(ramp-down)
 └──────┴────────────────────────────────┴──────→ t
```

压力测试的阶梯曲线则是一级级试探，每级留足稳态观察时间：

```text
rate
 ▲                                 ╱╲ ← 崩溃点：错误率飙升、吞吐掉头向下
 │                          ┌─────╯  ╲
 │                   ┌──────╯        （系统失效，记录拐点数据）
 │            ┌──────╯
 │     ┌──────╯  ← 每级台阶 = 一个 stage，
 │─────┘            台阶顶保持 3-5 分钟采样
 └─────────────────────────────────────────→ t
```

峰值测试的关键在"陡"：预热段必须以秒计（如 10s 内从基线升到峰值），否则测的是 ramping 而非 spike：

```javascript
export const options = {
  scenarios: {
    spike: {
      executor: "ramping-arrival-rate",
      startRate: 50,                  // 基线 50 it/s
      timeUnit: "1s",
      preAllocatedVUs: 200,           // 峰值 VU 需求要提前备足
      maxVUs: 2000,
      stages: [
        { duration: "2m", target: 50 },   // 基线运行 2 分钟
        { duration: "10s", target: 500 }, // 10 秒内陡升 10 倍 → 峰值
        { duration: "1m", target: 500 },  // 峰值维持 1 分钟
        { duration: "10s", target: 50 },  // 10 秒内陡降回基线
        { duration: "2m", target: 50 },   // 观察系统是否恢复正常
      ],
      gracefulStop: "30s",
    },
  },
};
```

浸泡测试没有曲线技巧，只有时长纪律：**强度取日常负载的 70-80%（不要取峰值——那测的是压力），持续数小时到一整天**，然后在服务端监控上看内存 RSS、GC 频率、连接数、慢查询数量是否随时间单调爬升。k6 侧要相应调低日志与指标输出的开销，并确保压测机自身能撑住这个时长（客户端内存泄漏会伪装成服务端泄漏）。

## 3.2 阶梯加压 ramping 设计

**阶梯（step）与斜坡（ramp）是两种加压风格，回答的问题不同。**斜坡是线性连续变化，适合绘制平滑的"吞吐-延迟"响应曲线；阶梯是"跳变 + 平台"交替，每个平台是一个可采样的稳态点，适合逐级核对 SLO 并定位"从第几级开始劣化"。设计阶梯的三条经验：

- **台阶跨度**：每级增加当前值的 20-50%，跨度太大会错过拐点，太小则测试过长。
- **平台时长**：至少 3-5 分钟，短于这个时间的平台采不满有统计意义的样本，且系统还没进入新稳态。
- **终止条件**：预先定义"失败"判据（错误率 > 1%、p95 超 SLO 两倍、吞吐不再上升），到达即停，不要盲目压到进程崩溃。

# 4. 指标与采样策略

## 4.1 预热期与稳定期区分

**预热期的样本必须从核心结论中剔除，k6 原生手段有限，需要靠设计规避。**k6 的运行结束汇总统计全程样本，没有内置的"忽略前 N 秒"开关；可用的对策按优先级排列：

1. **拉长稳态段占比**：稳态 ≥ 全程的 70% 时，预热样本对汇总分位数的稀释可以接受。
2. **输出到时序后端**：结果进 Prometheus/Grafana 或 InfluxDB 后框选稳态窗口分析（见第 13、14 篇）。
3. **`--summary-time-unit` 之外的窗口化方案**：用 `handleSummary()`（第 10 篇）自定义统计，或按 scenario 标签把预热用的独立场景与稳态场景分开，前者只作预热不进结论。

> **注意**：给场景打 tags 不能实现时间窗口过滤——tags 区分的是"哪个场景/哪类用户"，不是"哪段时间"。想按时间切样本，只能依赖外部时序系统。

## 4.2 采样精度与性能

**每个指标样本都有采集成本，高到达率下 k6 客户端自身的指标管道可能先成为瓶颈。**k6 对 `http_req_duration` 这类趋势指标默认采用 t-digest 做分位数估计，内存占用可控，但样本的**接收与聚合**仍随 RPS 线性增长；开启 `--out json` 落盘或高频推送到远端时，输出通道的开销在数千 RPS 量级就会显现。平衡原则：压测机 CPU 留给负载生成，输出通道尽量只接一个时序后端；调试用的 `console.log` 与细粒度自定义指标（每次迭代 new 一个 `Counter`/`Trend` 加标签）在生产压测里要克制——标签基数爆炸既吃客户端内存，也会拖垮时序库。

# 5. 负载建模常见错误

## 5.1 不考虑业务路径比例

**单接口压测得出的容量数字，几乎必然高于真实混合流量下的容量。**原因不只是比例失真：不同路径争抢的是同一批资源——浏览接口的缓存压力、下单接口的数据库写锁、搜索接口的 CPU，混合后互相挤兑，系统整体吞吐低于各接口单独压测的"木桶板"。正确姿势是先从生产访问日志/APM 里统计出路径占比，再按 2.2 节的方式映射成场景强度；实在拿不到真实比例时，至少要在报告里注明"本结论仅适用于该流量结构"。

## 5.2 直接使用并发数代替业务量

**并发数是过程量，吞吐与延迟才是结果量——用 VU 数做容量承诺等于用"油门深度"承诺"车速"。**同样的 500 VU，在响应 50ms 的系统上产生约 10000 RPS，在响应 500ms 的系统上只有 1000 RPS，两者对系统的考验差一个数量级。业务方关心的是"大促峰值 8000 QPS 扛不扛得住"，翻译到 k6 就应该是到达率场景的 rate=8000，而不是拍一个 VU 数。如果测试只能用闭合模型，报告中必须同时给出实测吞吐（`http_reqs` 的 rate），并把"VU 数"降级为背景参数。

> **行业实践**：成熟的性能团队把负载脚本与场景参数一起纳入版本管理，场景配置（rate、stages、阈值）随生产流量画像每季度校准一次；压测报告模板固定要求"实测 RPS + p95 + 错误率"三元组，禁止只报 VU 数。

# 6. 小结

| 主题 | 要点 |
|------|------|
| 场景机制 | 一个场景 = exec + 执行器 + tags/env + startTime，指标自动带 scenario 标签 |
| 流量比例 | 核心链路拆独立场景（可单独设阈值），长尾路径函数内加权 |
| 五类测试 | 冒烟（1-2 VU 短跑）、负载（目标值长稳态）、压力（阶梯到拐点）、峰值（秒级陡升陡降）、浸泡（70% 负载数小时） |
| 采样窗口 | 稳态段 ≥ 70% 时长，时间窗口过滤靠外部时序系统 |
| 建模纪律 | 从生产日志取路径比例；容量结论只认 RPS + p95 + 错误率，不认 VU 数 |

gracefulStop 与 gracefulRampDown 的语义在第 6 篇 2.4 节已详述，多场景下它们按场景各自生效。场景解决了"流量长什么样"，但脚本里写死的账号数据会让所有 VU 变成同一个人——下一篇进入数据参数化与关联。
