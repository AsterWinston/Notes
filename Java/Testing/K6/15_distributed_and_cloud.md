# 1. 单机能力的边界

## 1.1 为什么先谈单机上限

**分布式不是"越多机器越好"，而是"单机确实压不动了才需要"——先量化单机边界，再决定要不要引入分布式的复杂度**。分布式压测带来的一系列新问题（时钟对齐、结果聚合、网络带宽、节点一致性、故障节点处理）每一个都会侵蚀结果的可信度，如果一台调优过的施压机就能达到目标负载，就不该付这个代价。判断"压不动了"的标准不是主观感受，而是 k6 自己的信号：`dropped_iterations` 大于 0（到达型调度器没能按计划发起迭代）、`vus` 实际值低于配置值、以及施压机自身的 CPU 饱和。

## 1.2 VU 的资源成本

**k6 的一个 VU = 一个 goroutine + 一个独立的 JS 运行时实例（Sobek，Goja 的分支）+ 一组连接与缓冲区**，这个结构决定了单机的三重瓶颈。

CPU 侧，JS 是**解释执行**而非 JIT，脚本里每一次 `JSON.parse`、每一次 check 的函数调用、每一次模板字符串拼接都消耗真实的 CPU 周期。经验值：简单脚本（一个 GET + 一个 check）单核可以支撑数百到上千 RPS，而带复杂响应解析、大量自定义指标与字符串处理的脚本，单核可能只有一两百 RPS——**脚本复杂度对单机上限的影响常常超过 VU 数量本身**。

内存侧，基线进程约几十 MB，之后每个 VU 增量取决于脚本体积与数据：编译后的程序体在 VU 间有共享，但每个 VU 的堆、闭包环境、`SharedArray` 之外的独立副本都是私有的。一个用了大型 JSON 参数化文件（未用 SharedArray）的脚本，每 VU 多吃几十 MB 很常见，万级 VU 就是几百 GB 级别的需求——这是内存先于 CPU 打爆的典型场景。

文件描述符与端口侧，每条 TCP 连接占一个 fd，`ulimit -n` 默认 1024 在压测场景下必须抬高；同时每个到"目标 IP:端口"的连接占用一个本地临时端口，`net.ipv4.ip_local_port_range` 默认约 2.8 万个，配合 TIME_WAIT 的堆积，**单机对单一目标地址的并发连接数存在硬上限**，这与 k6 无关而是 TCP/IP 协议栈的约束。

```bash
# 压测机内核与资源调优（Linux）
ulimit -n 65535                                            # 文件描述符上限
sysctl -w net.ipv4.ip_local_port_range="1024 65535"        # 扩大临时端口范围
sysctl -w net.ipv4.tcp_tw_reuse=1                          # 允许复用 TIME_WAIT（施压端安全）
sysctl -w net.core.somaxconn=65535                         # 监听队列
sysctl -w fs.file-max=2097152

# k6 侧：限制自身资源占用，避免把压测机打挂
export GOMAXPROCS=8                # 绑定核数，留出余量给系统
k6 run script.js --vus 5000 --duration 10m
```

> **注意**：施压机的网卡带宽是常被忽略的第四个瓶颈。若响应体较大（每个请求返回 1MB JSON），1000 RPS 就是 1 Gbps，千兆网卡直接饱和——此时 `data_received` 指标会贴着一条水平线不动，看起来像"被测系统到极限了"，实际是施压端。判断方法：压测期间在施压机上看 `sar -n DEV 1` 或 `data_received` 的 rate 是否恰好等于网卡容量的某个比例。

# 2. 分布式执行方案

## 2.1 开源版的现状

**开源 k6 本身没有内置的分布式执行能力——`k6 run` 永远是单进程单机**，官方给出的分布式路线是两条：Grafana Cloud k6（托管，商业化）与 k6-operator（Kubernetes 上的自托管分布式执行）。这与 JMeter 形成鲜明对照：JMeter 从很早就有 master/slave 的 RMI 分布式模式，而 k6 团队的选择是**把分布式执行下沉到编排层**——由 Kubernetes 或云平台负责"起 N 个 k6 实例、分发脚本、收集结果"，k6 进程本身只管压。这个取舍让开源内核保持简单，也把分布式的运维成本明确地交给了平台。

## 2.2 测试分段（test execution segmentation）

**分布式 k6 的核心思想是"分段执行 + 后端聚合"：把一个逻辑测试切成 N 段，每段由一个 k6 实例独立执行，所有实例共享同一个 `test_run_id`，指标写入同一个 Remote Write 端点，在存储层自然汇合**。这与 JMeter 的 master 收集 slave 结果的模式根本不同——**没有中心收集节点，聚合发生在时序数据库里**。

```text
                测试计划：10000 VU / 30 分钟
                          │
              ┌───────────┼───────────┐
              ▼           ▼           ▼
        ┌──────────┐┌──────────┐┌──────────┐
        │ k6 pod 1 ││ k6 pod 2 ││ k6 pod N │   每个实例：
        │ 2500 VU  ││ 2500 VU  ││ 2500 VU  │   同一脚本、同一段配置
        └────┬─────┘└────┬─────┘└────┬─────┘   同一 test_run_id
             │           │           │
             └───────────┼───────────┘
                         ▼ Remote Write
              ┌─────────────────────┐
              │ Prometheus / Mimir   │  ◄── 按 test_run_id 聚合
              │ + Grafana            │      sum() 得到全局视图
              └─────────────────────┘
```

分段带来两个必须处理的语义问题。**其一，负载模型如何切分**：`--vus 10000` 切成 4 段就是每段 2500；`ramping-arrival-rate` 的 rate 也要按比例切；但**迭代型（iteration-based）场景要格外小心**——`iterations: 10000` 分段后每段 2500 次迭代，各段完成时刻不同，全局的"测试结束"由最慢的段决定。**其二，阈值在哪一层判定**：每个实例只看到自己那 1/N 的数据，`p(95)<500` 在单段上成立不代表全局成立（反之亦然）。因此分布式模式下**单实例的 thresholds 只能当粗筛**，权威判定必须基于聚合后的数据（Grafana 侧告警，或测试结束后用 PromQL 查询做后置校验）。

k6-operator 是这套分段的官方实现：在 Kubernetes 上以 CRD 描述测试，operator 负责把脚本挂进去、按 `spec.parallelism` 起 N 个 runner pod、注入统一的环境变量与 run id、并在所有 runner 结束后回收。使用形态大致是构建含所需扩展的自定义镜像、写一个 `K6` 资源清单、`kubectl apply` 触发；operator 的新版本已支持分布式执行的 GA 能力，具体字段以对应版本文档为准。

## 2.3 Grafana Cloud k6

**Grafana Cloud k6 是官方托管方案，本地用同一条命令把测试推到云端执行**：

```bash
k6 login cloud                          # 一次性：绑定 token
k6 cloud script.js                      # 上传脚本并在云端执行
k6 cloud --vus 5000 --duration 10m script.js
```

云端执行的收益：施压资源弹性伸缩（无需自备机器，也不受本地带宽/fd 限制）、多地域发压（从靠近真实用户的区域施压，测出含公网链路的真实延迟）、结果自动入库并与历史运行对比、阈值判定由平台在聚合层完成。代价与约束同样明确：**被测系统必须对公网可达**（内网系统需要自托管 runner 或打通网络）、**数据出境到 Grafana 的云端**（合规敏感场景需评估，或改用自托管的 Mimir + operator）、按测试量计费。

## 2.4 自建分布式的思路

不用 operator 也不买云服务时，可以按"分段 + 聚合"模型手工搭一套，本质是把 operator 做的事用脚本重做一遍。关键设计点：**统一 run id 与统一端点**（所有实例写同一个 Prometheus，靠 run id 区分）、**统一时钟**（NTP 同步，否则聚合曲线错位）、**分段参数外置**（脚本从 `__ENV` 读自己的 VU 数，避免维护 N 份脚本）、**统一启停**（并发启动才能形成真正的叠加负载）：

```bash
#!/usr/bin/env bash
# 简易分布式启动脚本：4 台施压机各压 2500 VU
RUN_ID="manual-$(date +%Y%m%d-%H%M%S)"     # 全局唯一 run id，聚合主键
NODES=(loadgen-1 loadgen-2 loadgen-3 loadgen-4)
VUS_PER_NODE=2500

for i in "${!NODES[@]}"; do
  ssh "${NODES[$i]}" "
    k6 run script.js \
      --vus ${VUS_PER_NODE} --duration 10m \
      --tag run_id=${RUN_ID} --tag node=${NODES[$i]} \
      --out experimental-prometheus-rw \
      -e K6_PROMETHEUS_RW_SERVER_URL=http://prom:9090/api/v1/write \
      > /var/log/k6-${RUN_ID}-${i}.log 2>&1
  " &                                        # 后台并发启动，尽可能同时开压
done
wait
echo "run_id=${RUN_ID}，去 Grafana 查看聚合结果"
```

聚合查询就是普通的 PromQL 按 run id 求和：

```text
sum(rate(k6_http_reqs_total{run_id="manual-20261107-1000"}[1m]))   # 全局 RPS
sum(k6_vus{run_id="manual-20261107-1000"})                         # 全局并发
max(k6_http_req_duration_p95{run_id="manual-20261107-1000"})       # 最差段的 p95
```

> **行业实践**：自建脚本方案适合"偶发的大规模压测"，但如果压测是常态化能力（每次发布前跑），维护成本会迅速超过 k6-operator——机器池的伸缩、镜像里扩展版本的更新、失败节点的重试、结果的自动归档，每一项都是长期负担。已有 Kubernetes 集群的团队，operator 是明显更优解。

# 3. 与其他工具的分布式对比

## 3.1 三种模型

**JMeter、Gatling、k6 代表了三种不同的分布式哲学**：JMeter 是"中心 master + RMI 遥控 slave"，master 负责分发计划、收集所有 slave 的采样结果并汇总，模型直观但 master 是单点瓶颈；Gatling（商业版/Gatling Enterprise）是"控制器 + 注入器（injector）"，注入器只负责发压，结果直接上报控制平面，开源版 Gatling 则需要自己拼前端；k6 是"对等实例 + 存储层聚合"，没有中心节点，聚合责任交给时序数据库。

| 维度 | k6（开源 + operator/Cloud） | JMeter distributed | Gatling Enterprise |
|------|---------------------------|-------------------|-------------------|
| 架构模型 | 对等实例，结果在存储层聚合 | master/slave，RMI 通信 | 控制器 + 注入器 |
| 中心节点 | 无（聚合靠 Prometheus） | master（收集全部采样） | 控制平面（商业组件） |
| 结果聚合 | 时序库 PromQL / 云端自动 | master 内存汇总后出报告 | 控制平面聚合出报告 |
| 单节点资源开销 | 低（Go 二进制，无 JVM） | 高（JVM + 每线程栈，1GB/千线程量级） | 中高（JVM + Netty） |
| 同等机器可达 VU/线程数 | 数千~万级 | 数百~千级（线程模型限制） | 数千级 |
| 弹性伸缩 | K8s 原生，秒级起 pod | 需预置 slave 并配置 RMI 端口 | 平台调度 |
| 多地域发压 | Cloud 原生支持 | 需自建跨域 slave + 打通 RMI | 平台支持 |
| 分布式下的阈值判定 | 需在聚合层做 | master 汇总后判定 | 平台判定 |
| 开源版能否分布式 | 需自建/operator（不内置） | 内置 | 不内置（企业版能力） |
| 成本 | 自建免费；Cloud 按量计费 | 免费 | 企业版收费 |

三点值得展开的判断：**其一，JMeter 的线程模型是单机上限的根源**——每个虚拟用户一个平台线程，1MB 默认栈下千级线程就要 GB 级内存加上下文切换开销；k6 的 goroutine 是 KB 级栈的用户态协程，同等机器能承载的并发用户数高一个量级，这是"压万级并发"场景下 k6 更常见的技术原因。**其二，JMeter 的 master 收集全量采样是扩展性瓶颈**——slave 数量增加到十几台后 master 的 RMI 反序列化与内存压力显著，社区常规做法是让 slave 直写数据库而非回传 master。**其三，k6 把聚合外移到时序库既是优点也是坑**：优点是没有中心瓶颈，坑是"没有 master"意味着**没有一个天然的成败判定点**，退出码只反映本实例，全局结论必须另建（见 2.2）。

## 3.2 选型倾向

小规模（单机可承载）永远用单机——**分布式的复杂度只有在收益明确时才值得付**。需要万级以上并发、或多地域真实网络路径、或压测常态化进 CI 时：已有 K8s 且数据不能出内网，选 k6-operator + 自建 Prometheus/Mimir；追求零运维且被测系统公网可达、数据可上云，选 Grafana Cloud k6；存量 JMeter 资产庞大且团队熟悉 JMX，评估迁移成本后再决定是否为了规模上限而换工具，混合期可以让 JMeter 与 k6 的指标都写进同一个 Prometheus 统一呈现。

# 4. 分布式压测的难点

## 4.1 时钟与指标一致性

**跨节点时间偏差会直接破坏聚合的正确性**。时序数据库按时间戳对齐样本，如果施压机 A 的钟快 5 秒，它的曲线整体右移，全局 RPS 的求和在爬坡阶段和结束阶段出现虚假的凹陷与拖尾；更糟的是"某时刻错误率突刺与 SUT 的 GC 停顿"这类关联分析会得出错误结论（见第 14 篇的时间线对齐）。治理：所有施压机与 SUT 接入同一 NTP 源，压测前用 `chronyc tracking` 或 `ntpstat` 验证偏差在毫秒级；K8s 场景下节点时钟由宿主机保证，通常没问题，但要警惕跨可用区/跨云的部署。

第二重一致性问题来自**分段之间不等价**：不同 pod 落在不同规格的宿主机上、走不同的网络路径，某一段明显慢于其他段时，全局 p95 实际由最差的那台施压机决定——这是"客户端噪声污染测试结果"。检测方法：按 `node`/pod 标签分组画各段的 `http_req_duration_p95`，段间差异超过 10% 就要怀疑施压环境不均；对策是固定节点池规格（K8s 的 nodeSelector/亲和性）并在报告中记录施压端规格。

## 4.2 网络与带宽

**客户端网络不足会先于被测系统成为瓶颈，而症状看起来一模一样：吞吐上不去、延迟升高**。四类具体形态：施压机网卡饱和（大响应体场景，见 1.2 的注意事项）；施压机到 SUT 之间的链路带宽/QPS 限制（云上跨 AZ、经 NAT 网关、经负载均衡器时，LB 的连接数与新建连接速率上限尤其常见——**压测把云 LB 打满了，却以为是应用不行**）；出口 IP 被 SUT 侧的 WAF/限流规则识别为攻击而拦截（分布式多机发压时源 IP 集中，触发频次限制的概率更高）；DNS 解析成为隐性瓶颈（每 VU 每迭代解析一次域名，压测机的 DNS 服务器 QPS 上限被打穿，表现为间歇性超时）。

排查方法：**先用一台机器做梯度测试**（VU 从 100 逐级翻倍），画出"RPS vs VU"曲线，若曲线在某个 VU 数后走平而施压机 CPU 未饱和，就去看网络侧（`sar -n DEV`、`ss -s` 的连接与 TIME_WAIT 计数、NAT/LB 的连接数监控）；同时确认 SUT 侧指标是否也在同一时刻出现资源饱和——两边都没饱和而吞吐上不去，几乎必然是中间链路。

## 4.3 结果聚合与成败判定

**分布式下的"测试是否通过"必须有明确的单一判定点，否则每份报告都可以自说自话**。可行的三种落地方式：其一，压测结束后跑一段后置校验（PromQL 查询聚合指标 + 与 SLO 比较，非 0 退出即失败），把它作为 CI 的独立步骤；其二，用 Grafana 的告警规则绑定 run id，测试期间阈值突破即通知；其三，云端方案由平台自动完成聚合判定。无论哪种，**报告里必须同时给出"全局聚合值"和"分段离散度"**——只有全局 p95 而没有段间对比，就无法区分"系统慢"与"某台施压机慢"。

聚合本身的另一处陷阱是**统计量不可简单平均**：全局 p95 不等于各段 p95 的平均值，也不等于最大值（虽然取 max 是保守安全的近似）。精确的全局分位数需要各段推送分位数直方图（histogram）而非单一分位数点，再在查询侧合并——这也是大规模压测中 Prometheus 直方图方案（`histogram_quantile`）优于 k6 预聚合分位数的场景。

# 5. 小结

单机 k6 的上限由四件事决定：JS 解释执行的 CPU 成本、每 VU 独立运行时的内存成本、fd 与临时端口限制、以及网卡与中间链路带宽；先做梯度测试定位真实瓶颈，再谈分布式。开源 k6 不内置分布式，官方路线是 **k6-operator（K8s 分段执行）与 Grafana Cloud k6（托管）**，共同模型都是"把测试切成 N 段、共享同一 run id、结果在时序库聚合"，因此**没有中心成败判定点，阈值必须在聚合层重新判定**。自建方案要解决统一 run id、NTP 时钟、分段参数外置与并发启停四件事。与 JMeter 的 master/slave、Gatling 的控制器/注入器相比，k6 的对等实例 + goroutine 模型在同等硬件下能承载更高并发，代价是聚合与判定的责任外移。分布式特有的坑集中在时钟偏差导致的曲线错位、段间不等价导致的客户端噪声、以及分位数不可简单平均的聚合陷阱。
