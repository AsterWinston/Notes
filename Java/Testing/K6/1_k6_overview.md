# 1. 定义与定位

## 1.1 什么是 k6

k6 是一款**用 Go 编写内核、以 JavaScript 编写测试脚本**的开源负载测试（Load Testing）工具，最初由瑞典公司 Load Impact 开发，2021 年被 Grafana Labs 收购后持续演进，目前是 CNCF 生态与 Grafana LGTM 技术栈中的官方压测组件。它以**单个静态二进制**的形式发布，不依赖 JVM、Python 运行时或任何外部服务，下载解压即可运行——这与 Java 生态的 JMeter（依赖 JVM）、Gatling（依赖 JVM + Scala DSL）形成了鲜明的部署形态对比。

k6 的定位不是"点鼠标录制回放"的测试工具，而是**面向工程师的性能测试即代码（Performance Testing as Code）**方案。它的三个核心特征贯穿整个产品设计：

**脚本即代码**：测试逻辑、断言、数据驱动、负载模型全部用 JavaScript 表达，脚本可以像业务代码一样进 Git、走 Code Review、被 lint 和模块化拆分。压测方案从此有了版本历史和 diff 能力。

**轻量并发运行时**：每个虚拟用户（VU）对应一个独立的 JS 运行时实例（Goja 解释器），由 Go 的 goroutine 调度。单机即可驱动数千 VU，内存和 CPU 开销远低于"一个虚拟用户一个线程"的传统模型。

**指标驱动的质量闸门**：k6 内置丰富的统计指标（Trend/Counter/Rate/Gauge 四类）与阈值（thresholds）机制，测试结束时阈值被突破会以非零退出码结束进程，天然适合嵌入 CI/CD 做性能回归的自动判定。

## 1.2 设计理念与核心取舍

k6 的每一个设计决策都能读出明确的取舍倾向。

**可重复性优先于易用性**。k6 没有官方 GUI 录制器，学习曲线从"打开界面点按钮"变成了"写一个 JS 模块"。换来的是：同一份脚本在任何机器、任何时间运行都产生结构一致的负载模型，团队之间不会因为"我本地的 jmx 文件是旧版"而互相扯皮。

**单机优先，分布式外置**。开源版 k6 刻意不做内置的 Master/Slave 分布式协议——需要横向扩展时，官方给出的路径是 k6 Cloud（SaaS）或 k6-operator（Kubernetes Operator，把一次测试拆成 N 个 Pod）。这是一个典型的 Unix 式取舍：**把一件事做好，把编排交给基础设施**。对大多数 API 压测场景，一台高配机器（8 核 16G）驱动几千 VU 已经够用，分布式反而引入了结果合并、时钟同步等复杂度。

> **设计考量**：JMeter 的分布式压测（RMI 通信 + jmeter-server）是出了名的难配置、难排障；Locust 内置了 master/worker 协议相对好用。k6 选择"开源版不做分布式"，表面看是功能缺失，实际是判断——**Go 协程模型让单机容量比 JVM 线程模型高一个数量级**，多数团队根本触不到单机上限，为小概率需求维护分布式协议不划算。

**性能优先，拒绝运行时开销**。k6 的 HTTP 客户端直接构建在 Go 标准库 net/http 之上，指标采集走内存聚合而非落盘，没有 GUI 进程、没有序列化中间层。脚本层（JS）只负责"表达意图"，真正的高频路径（发包、计时、聚合）全部在 Go 层完成。

## 1.3 适用与不适用场景

### 1.3.1 适用

k6 最擅长的是**协议层 API 压测**：REST/HTTP、GraphQL、WebSocket、gRPC（通过扩展）等无界面协议的负载测试、容量评估与稳定性验证。典型受益场景包括：

- **微服务容量评估**：新服务上线前验证目标 QPS 下的延迟分布与错误率；
- **CI/CD 性能回归**：每次合并主干后跑 2 分钟压测，阈值突破即流水线红灯；
- **复杂业务流脚本化**：登录、下单、支付这类多步骤有依赖的流程，用 JS 的条件分支与变量传递表达，远比 GUI 工具的"参数提取器"清晰；
- **SLO 驱动的持续验证**：与 Grafana/Prometheus 集成后，压测结果直接进入可观测体系，阈值即 SLO。

### 1.3.2 不适用

同样明确的是它不该被用在哪里：

- **强依赖 GUI 录制回放的团队**：k6 没有官方录制器，测试人员若不具备编程能力，上手成本高于 JMeter；
- **重浏览器交互的端到端场景**：k6 的浏览器测试模块（k6 browser，基于 Playwright 协议）在 v0.5x 中仍属实验性质，且浏览器级压测的资源开销与纯协议压测完全不同量级，复杂 E2E 更适合 Playwright/Selenium；
- **没有性能基线、无法定义 SLO 的项目**：k6 的价值在"阈值判定 + 趋势对比"，如果团队连"P95 应该小于多少"都答不上来，工具再好也只是产生一堆没人看的数字。

> **行业实践**：在 Java 微服务体系中，k6 常与 Spring Boot 项目搭配使用——应用代码在 Java 侧，压测脚本在独立的 k6 目录（或直接放在仓库的 `load-tests/` 下）由同一支团队维护。"谁开发谁压测"是 DevOps 文化下的主流分工，这也是 k6 相对 JMeter（通常由专职测试团队持有）在研发团队中更受欢迎的原因。

# 2. 核心能力与优势

## 2.1 脚本化与可编程

k6 脚本是标准的 **ES Module**，用 `import` 引入内置模块（`k6/http`、`k6/metrics`、`k6/check` 等），用 `export default` 声明测试主体，用 `export const options` 声明运行配置。这套结构意味着压测脚本可以直接复用前端工程的全部工具链：ESLint 检查语法、npm 安装第三方 JS 库（k6 支持打包 node_modules 依赖）、多文件模块化组织大型测试套件。

对 Java 背景的读者，一个直观的类比是：**k6 脚本之于压测，相当于 JUnit 5 之于单元测试**——测试逻辑是一等公民代码，而不是配置在 XML/GUI 里的元数据。断言（check）、参数化（SharedArray/环境变量）、生命周期（setup/teardown）都有对应物。

## 2.2 轻量并发模型与性能

理解 k6 的性能优势，需要看清它的**双层架构：Go 内核负责重活，JS 层负责表达**：

```text
┌─────────────────────────────────────────────────┐
│              k6 进程（Go 单二进制）                │
│                                                 │
│   ┌───────────────────────────────────────┐     │
│   │ Go 内核层：                             │     │
│   │  goroutine 调度 / net-http 连接池       │     │
│   │  指标聚合引擎 / 输出引擎 / 执行器        │     │
│   └──────┬──────────┬──────────┬──────────┘     │
│          │ 1:1      │          │                │
│   ┌──────▼────┐ ┌───▼──────┐ ┌─▼────────┐       │
│   │ VU1       │ │ VU2      │ │ VU N     │       │
│   │ Goja JS   │ │ Goja JS  │ │ Goja JS  │       │
│   │ 运行时实例 │ │ 运行时实例│ │ 运行时实例 │       │
│   └───────────┘ └──────────┘ └──────────┘       │
└────────────────────┬────────────────────────────┘
                     ▼  HTTP / WebSocket / gRPC …
                 被测系统（SUT）
```

每个 VU（Virtual User，虚拟用户）= 一个 goroutine + 一个独立的 **Goja** JS 解释器实例。Goja 是用纯 Go 实现的 ECMAScript 引擎（完整支持 ES5.1，覆盖大部分 ES2015+ 特性），它不是 V8，没有 JIT——这是刻意的选择：**解释执行的单条语句速度不如 V8，但每个实例的内存占用只有几百 KB 到几 MB，且没有 JIT 预热和编译线程的抖动**，对" Thousands 个并发实例、每个只跑简单流程"的压测负载形态反而更优。

由于 goroutine 的调度成本（初始栈 2KB，按需增长）远低于操作系统线程（默认栈 1MB），单机驱动 5000 个 VU 对 k6 是常规操作，而 JMeter 用线程模型在同等规模下通常需要多台机器。

> **注意**：Goja 不是 V8 意味着**不能指望在 k6 脚本里跑计算密集的 JS 逻辑**（例如在脚本内做复杂的加解密、大数据排序）。计算会占满解释器所在线程，直接拉低发压能力。重计算应放到被测系统外面预处理，或用 xk6 以 Go 扩展的形式实现。

## 2.3 扩展与生态

k6 的扩展机制叫 **xk6**：一个基于 Go 插件式构建的工具，把 k6 源码与第三方扩展模块一起编译成定制二进制。社区扩展覆盖了协议（gRPC、MQTT、Redis、SQL）、输出（Datadog、New Relic、TimescaleDB）与能力（浏览器自动化）等方向。企业内部的私有协议客户端也可以封装成 xk6 扩展，让压测脚本用统一的 JS 接口调用。

开箱即用的官方集成同样重要：`--out` 参数支持把实时指标输出到 JSON、CSV、InfluxDB、Prometheus（remote write）等后端，配合 Grafana 仪表盘可以在压测进行中实时观察延迟分布与错误率曲线，而不是等测试结束才看汇总报告。

# 3. 关键概念速览

## 3.1 VU、迭代与脚本结构

**VU（Virtual User）是并发执行单元，迭代（Iteration）是 VU 执行一次 `default` 函数的完整过程**。一个最小的可运行脚本如下：

```javascript
import http from "k6/http";
import { check, sleep } from "k6";

// 负载模型：10 个并发 VU，持续 30 秒
export const options = {
  vus: 10,
  duration: "30s",
};

// 每个 VU 循环执行的默认函数 = 一次迭代
export default function () {
  const res = http.get("https://test.k6.io");
  check(res, {
    "status is 200": (r) => r.status === 200,   // 业务断言
  });
  sleep(1);                                     // 思考时间，单位秒
}
```

三个要点值得展开：**VU 之间完全隔离**（各自独立的 JS 运行时，全局变量不共享）；**迭代是统计的基本单位**（`iterations`、`iteration_duration` 指标都以它计数）；**sleep 不是可有可无的**——不加 sleep 的 VU 会以机器最快速度循环发请求，测出来的是"客户端极限"而不是"真实用户负载"，除非你明确在做压力测试。

## 3.2 执行器与负载模型

k6 用**执行器（Executor）**声明负载模型，分为闭合模型与开放模型两大类：

| 模型 | 代表执行器 | 负载语义 | 适用场景 |
|------|-----------|----------|----------|
| 闭合（Closed） | constant-vus / ramping-vus / shared-iterations | 固定 VU 数循环发压，响应变慢则吞吐自动下降 | 模拟"在线用户数"型系统（页面、长连接） |
| 开放（Open） | constant-arrival-rate / ramping-arrival-rate | 按固定到达率启动迭代，不管上一个是否结束 | 模拟真实流量（API 网关、消息入口） |

闭合模型的隐患是**协调遗漏（Coordinated Omission）**：当被测系统变慢时，闭合模型的发压速率也跟着变慢，延迟统计会系统性偏乐观。开放模型按预定到达率强行发起新迭代（必要时扩容 VU），能暴露真实排队延迟。API 压测优先选 arrival-rate 系执行器，这一点在第 2 篇的执行器章节详细展开。

## 3.3 指标、检查与阈值

k6 的结果体系由三层构成：**指标（Metrics）**是原始测量数据，涵盖吞吐（`http_reqs`）、延迟分布（`http_req_duration`）、错误率（`http_req_failed`）、资源消耗（`vus`、`data_received`）等；**检查（check）**是写在迭代里的业务断言，成功与失败计入 `checks` 指标但**不会中断迭代，也不会让请求被标记为失败**；**阈值（thresholds）**是对指标聚合值的硬性约束，例如 `http_req_duration: ["p(95)<500"]`，测试结束时任何阈值被突破，k6 以退出码 99 结束——这正是 CI 质量闸门的实现基础。三者的精确语义与配方见第 5 篇。

# 4. 与常见工具对比

## 4.1 k6 vs JMeter

JMeter 是压测领域的"事实标准老将"：GUI 录制、协议插件丰富（JDBC、JMS、LDAP、TCP……）、社区资料海量、测试人员无需编程即可上手。k6 与它的差异本质上是**两代测试文化的差异**：

| 维度 | k6 | JMeter |
|------|-----|--------|
| 运行时 | Go 单二进制 | JVM（需装 Java） |
| 脚本形式 | JS 代码，进 Git 走 Review | jmx（XML），GUI 编辑为主，diff 不可读 |
| 并发模型 | goroutine + Goja，单机数千 VU | 线程池，单机数百到千级线程 |
| 资源占用 | 低（每 VU 约 1-2MB） | 高（每线程约 1MB 栈 + JVM 开销） |
| GUI | 无（结果输出到 Grafana 等） | 有（录制、调试、实时图表） |
| CI 集成 | 原生（退出码 + 阈值） | 需插件/包装（JMeter Maven Plugin 等） |
| 协议广度 | HTTP/WS/gRPC（扩展） | 极广（内置 + 插件） |

结论并不是一边倒：**研发团队自持、进 CI、API 为主选 k6；专职测试团队、协议杂、依赖录制选 JMeter**。

## 4.2 k6 vs Gatling/Locust

Gatling 是 JVM 阵营的工程化标杆——Scala/Java/Kotlin DSL、异步非阻塞（早期 Netty，现 Pekko）、性能极高、报告精美。它的短板是学习曲线陡峭（函数式 DSL 对普通 Java 开发者不友好）以及开源版功能切割（部分企业特性收费）。Locust 走 Python 路线，脚本就是普通 Python 类，分布式（master/worker）内置且成熟，但 Python GIL 决定了单 worker 吞吐有限，需要更多机器堆并发。

| 维度 | k6 | Gatling | Locust |
|------|-----|---------|--------|
| 脚本语言 | JavaScript | Scala/Java/Kotlin DSL | Python |
| 内核 | Go | JVM（异步） | Python（gevent 协程） |
| 单机并发能力 | 高 | 很高 | 中（受 GIL 限制） |
| 分布式 | Cloud / k6-operator | 企业版 / 自行编排 | 内置 master-worker |
| 学习成本 | 低（JS 普及度高） | 高 | 低（对 Python 团队） |
| 实时指标输出 | 内置多后端 | 内置 HTML 报告为主 | Web UI |

## 4.3 选型建议

**追求工程化与自动化、团队以 Java/前端技术栈为主、压测目标是 API：优先 k6**——JS 的学习成本对这两个群体几乎为零，CI 集成是原生能力。依赖 GUI 录制、协议覆盖面要求广：JMeter 仍是务实选择。Python 团队做大规模分布式压测：Locust 的 master-worker 最省事。对 JVM 系极致性能与精美报告有执念：Gatling 值得投入。

> **行业实践**：不少团队的最终形态是"JMeter 存量 + k6 增量"——历史 GUI 脚本继续由测试团队维护，新服务的压测脚本一律 k6 并进流水线。工具选型不必非此即彼，但**新增部分尽量向代码化倾斜**，因为压测脚本的生命周期管理（版本、复用、评审）只有代码形态才能做好。

# 5. 压测类型与目标

## 5.1 常见测试类型

**负载测试（Load Testing）**验证系统在预期流量下的表现：以生产峰值 QPS（或其 1.2-1.5 倍）为目标，观察延迟分布与错误率是否满足 SLO。这是最常跑、最应该进 CI 的类型。

**压力测试（Stress Testing）**不断加压直到系统崩溃，目的是**找到瓶颈位置与极限容量**——是数据库连接池先耗尽，还是网关先限流？崩溃后能否自愈？结果用于容量规划而非回归判定。

**稳定性测试（Soak/Endurance Testing）**以中等负载运行数小时到数天，观察内存泄漏、连接泄漏、日志膨胀、GC 恶化等慢性问题。Java 服务尤其要关注堆内存曲线是否随时间线性上涨。

**突刺测试（Spike Testing）**模拟流量瞬时飙升（如秒杀开场、推送触达）：

```text
QPS
 │            ┌──┐            ┌──┐
 │            │  │            │  │
 │  ──────────┘  └────────────┘  └───────  基线流量
 └────────────────────────────────────────► t
      突刺阶段          恢复期      再次突刺
```

考察系统在远超日常的瞬时压力下是否触发限流、熔断、扩容，以及流量回落后能否恢复正常。

## 5.2 目标与指标

**压测必须先有量化目标，再谈工具与脚本**。目标通常表达为一组 SLO：例如"订单创建接口在 500 QPS 下，P95 延迟 < 300ms，错误率 < 0.1%"。这三要素——目标负载、延迟分位数、错误率上限——恰好一一映射到 k6 的执行器（负载模型）、Trend 指标（p(95)）与阈值（thresholds），这也是 k6"SLO 即代码"叙事的由来。没有基线的项目应该先跑探索性负载测试建立基线，再据基线定阈值，切忌拍脑袋写出 `p(95)<100` 这种从未被验证过的数字。

# 6. 小结

k6 用"Go 内核 + Goja JS 脚本层"的双层架构，把负载测试从 GUI 配置时代拉进了代码时代：单机数千 VU 的轻量并发、原生 CI 退出码判定、与 Grafana 可观测生态的无缝集成，使它成为 API 压测与性能回归的当前最优解之一；代价是放弃录制器与内置分布式，并把"会写 JS"设为入场门槛。选型上与 JMeter 的分野是文化差异（代码 vs GUI），与 Gatling/Locust 的分野是生态差异（JS vs JVM/Python）。无论选谁，**先定义量化 SLO 再设计负载模型**都是压测有效性的第一前提——工具只是把目标翻译成可重复执行的形式。
