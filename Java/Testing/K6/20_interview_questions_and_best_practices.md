# 1. 最佳实践清单

## 1.1 设计阶段

**性能测试的价值上限在设计阶段就已经决定**——脚本写得再漂亮，测错了场景也是白费。设计阶段要做四件事：明确性能目标与阈值（从业务 SLO 出发，"P95 < 300ms、错误率 < 0.1%"这样的可判定表述，而不是"要快"）；建立可对比的基线（第一次跑的合格结果存档，之后每次运行与基线对比看趋势，绝对值只在同环境下有意义）；确定负载模型（用开放模型还是封闭模型、到达率还是 VU 数，见 2.6）；圈定场景边界（哪些链路进压测、测试数据从哪来、下游依赖 mock 还是真实调用）。

## 1.2 脚本实现

**模块化脚本，避免复制粘贴**：把"登录取 token""下单""查询"抽成独立函数放在模块文件里，场景脚本只做编排——这是 k6 "脚本即代码"的核心收益，与业务代码一样享受重构、复用、版本管理。在此之上：关键步骤全部加 `check` 并用可区分的命名（`check(res, { 'login ok': ... })` 失败率会单独出现在 summary）；参数化数据用 `SharedArray` 加载（大文件）或 CSV；环境差异全部走 `__ENV` 注入，一个脚本适配所有环境；thresholds 写进 `options` 随脚本进仓库，让门禁标准本身也可评审、可演进。

## 1.3 执行阶段

**先小规模验证，再逐步加压**是铁律：任何新脚本先 `--vus 1 --iterations 5 --console-output debug.log` 单 VU 跑通业务链路（数据对不对、token 有没有带上、check 是否通过），确认无误后再按 `stages` 阶梯加压（ramping-vus / ramping-arrival-rate），观察系统在每个台阶的表现而不是直接一棒子打死。执行期间**同时监控客户端与服务端**：k6 侧盯 `http_req_blocked`、`dropped_iterations` 与施压机 CPU（客户端不干净的数据直接作废），服务端盯资源水位、慢查询与线程池。正式压测至少重复 3 次取中位数，单次结果永远不足以下结论。

## 1.4 工具链与协作

把性能测试纳入工程体系而不是一次性活动：脚本与业务代码同仓库同评审（PR 改了接口，性能脚本同步改）；CI 中分层执行（PR 冒烟 + 夜间负载，见第 16 篇）；结果输出到时序库画趋势（`--out experimental-prometheus-rw`），性能劣化按周可见；测试报告附带环境信息、脚本版本、压测端资源数据，让结论可复现、可追溯。

> **行业实践**：成熟团队的 k6 脚本仓库结构通常是 `scenarios/`（场景编排）+ `modules/`（业务函数库）+ `data/`（参数化数据）+ `options/`（分环境的负载与阈值配置），场景文件只有几十行，复杂逻辑全部下沉到模块——评审性能脚本和评审业务代码用同一套标准。

# 2. 常见面试题

## 2.1 k6 与 JMeter 的区别是什么？

最本质的区别是设计哲学：k6 是"面向开发者的测试即代码"，JMeter 是"面向测试人员的 GUI 工具"。具体展开：k6 脚本用 JavaScript 编写、进版本库、可复用业务代码思维做模块化，天然适合 CI/CD 集成（阈值失败退出码 99 直接阻断流水线）；JMeter 以 GUI 拖拽 + XML 测试计划为主，录制回放能力强，对不写代码的测试人员更友好。资源模型上，k6 用 Go 编写、每个 VU 是一个轻量 goroutine 加一个 JS 解释器实例，单机能支撑的并发数量级更高；JMeter 每个虚拟用户是一个真实 Java 线程，线程栈内存开销大，高并发时通常几千人就吃紧，需要更多施压机。生态上，JMeter 积累二十年、协议插件最全（JDBC、JMS、LDAP 等开箱即用），k6 协议支持靠内置模块加 xk6 扩展，HTTP/WebSocket/gRPC/浏览器是主战场。选型结论：工程化、云原生、CI 门禁场景选 k6；传统企业、复杂协议、GUI 协作场景 JMeter 仍有一席之地。

## 2.2 什么是 VU 与迭代？

VU（Virtual User，虚拟用户）是 k6 的并发执行单元，每个 VU 在源码层面对应一个 goroutine 加一个独立的 JS 运行时实例，VU 之间不共享任何 JS 变量状态（SharedArray 共享的也只是底层数据）。迭代（iteration）是 VU 执行一次 `default` 函数的完整流程——一次"用户旅程"，比如登录、浏览、下单这一串动作，迭代结束会产出一组指标样本并递增 `iterations` 计数器。二者的关系由执行器决定：封闭模型下 VU 数量是配置目标，迭代是 VU 忙完一轮自动开始的下一轮，RPS = VU 数 ÷ 迭代耗时；开放模型下迭代到达率是配置目标，VU 只是执行迭代的资源池。面试追问"VU 是不是等于并发用户"时要澄清：VU 模拟的是"会发请求的并发实体"，一个真实用户带思考时间的话，所需 VU 数应按 Little's Law 结合到达率和响应时间换算，而不是简单等同于在线用户数。

## 2.3 checks 和 thresholds 有什么区别？

两者都是断言，但语义与后果完全不同。check 是**迭代级的软断言**：在脚本里对单个响应做布尔判断，结果记入 `checks` 这个 Rate 型指标，失败不会中断测试，只体现在 summary 的通过率里，用于观测业务正确性（状态码 200、返回体字段符合预期）。threshold 是**测试级的硬门禁**：在 `options.thresholds` 里对指标聚合值声明约束（如 `http_req_duration: ['p(95)<500']`、`http_req_failed: ['rate<0.01']`），测试结束时统一判定，不达标则 k6 以退出码 99 结束，配置了 `abortOnFail` 的还会立即中止测试。典型搭配是：check 保证"每个请求业务上是对的"，threshold 把 check 的失败率与延迟分位数升级成"整场测试可不可接受"的判定，接进 CI 就是性能门禁。只写 check 不写 threshold，压测永远"绿"；只写 threshold 不写 check，业务逻辑错了性能数据全是假的。

## 2.4 如何设置阈值？

阈值不能拍脑袋，来源有两个：历史基线与业务 SLO。操作上先跑基线测试拿到当前系统在目标负载下的真实表现（比如 P95 = 200ms、错误率 0.05%），然后按用途分档设定——CI 门禁阈值要在基线上留足余量（共享 runner 波动 20%~50%，基线 200ms 的门禁可以设 350ms，目的是拦"断崖式劣化"而不是抠毛刺）；发布验收阈值对齐 SLO（SLO 是 P95 < 300ms 就设 300ms，失败即阻断）；容量探索阶段用 `--no-thresholds` 干脆关掉判定，只采数据。关键路径要更严格：可以用带标签的阈值语法对单个接口单独设限（`'http_req_duration{endpoint:checkout}': ['p(95)<200']`），核心交易链路比一般查询接口收紧一档。另外阈值要随基线演进定期 review——系统优化后基线降到 120ms，门禁还停在 350ms 就失去了防回归的灵敏度。

## 2.5 如何判断瓶颈在客户端还是服务端？

看三组信号交叉验证。第一组是吞吐与资源的背离：RPS 加不上去（或随 VU 增加不增反降）而服务端 CPU、内存、DB 负载都很平静，同时施压机 CPU 接近打满或 `http_req_blocked` 显著升高，就是客户端瓶颈——压力根本没送达。第二组是延迟分段：k6 把 `http_req_duration` 拆成 blocked/connecting/tls_handshaking/sending/waiting/receiving 几段，`waiting`（TTFB）占大头是服务端处理慢，`blocked` 占大头是施压机连接池/fd/端口不足，`connecting` 大是网络路径或服务端 accept 队列问题。第三组是错误形态：错误随负载爬坡逐渐出现且伴随服务端资源恶化是服务端过载；错误从第一秒就大面积出现是配置/环境问题；`connection reset` 突发要查服务端进程崩溃或 LB 踢连接。确认客户端干净的标准：施压机 CPU < 70%、无 fd/端口告警、`http_req_blocked` P95 < 10ms、开放模型下 `dropped_iterations` 为 0，不满足就先修压测端再谈系统瓶颈。

## 2.6 开放模型和封闭模型的区别是什么？各自适用什么场景？

区别在于"谁是自变量"。封闭模型（closed model，对应 `per-vu-iterations`、`constant-vus`、`ramping-vus` 执行器）以并发数为自变量：固定 N 个 VU 循环执行，一个迭代没结束就不会开始下一个，因此**实际到达率 = VU 数 ÷ 响应时间**，服务端一慢，到达的请求自动变少——负载被系统状态"反向调节"了。开放模型（open model，对应 `constant-arrival-rate`、`ramping-arrival-rate`）以到达率为自变量：按固定速率发射迭代，服务端变慢时 k6 从 VU 池借更多 VU 维持速率，未完成的请求堆积，延迟上升被如实记录。适用场景：封闭模型适合模拟"固定数量的长连接用户"（如 1000 个坐席始终在线）或做压力摸底（看系统在固定并发下的表现）；开放模型适合模拟真实的互联网流量——Web 用户不会因为服务端慢就减少发起请求的请求数，SLO 通常也是按"目标 QPS 下的延迟"定义的，所以**验证容量和 SLO 一律用开放模型**，这也是 k6 官方文档推荐默认用 arrival-rate 执行器的原因。

## 2.7 什么是协调遗漏（coordinated omission）？

协调遗漏是封闭模型负载生成器的结构性测量偏差：当被测系统变慢时，封闭模型的 VU 被慢响应"卡住"，发不出新请求，于是**系统在它最慢、最需要被测的时刻反而收到的负载变少了**，慢请求在统计里被系统性低估——最极端的情况是系统挂死 10 秒，封闭模型这 10 秒里一个请求都没发，延迟统计里完全看不到这次事故。结果是压测报告的 P99 远好于真实用户体验，容量结论虚高。k6 的应对就是开放模型的 `constant-arrival-rate` 执行器：迭代按预定时刻表发射，与系统响应速度解耦，服务端变慢时迭代排队堆积、`vus` 指标上涨、延迟如实飙升，测量不会自我美化。

> **注意**：开放模型也不是免死金牌——如果压测中 `dropped_iterations` 出现或实际 RPS 低于目标值，说明 VU 池不够大（`maxVUs` 限制），到达率已经掉了，测量又开始失真。判据很简单：目标到达率与实际 `http_reqs` 速率对得上，数据才可信。

## 2.8 如何决定压测的并发数（VU 数量）？

用 Little's Law 从业务目标反推，而不是凭感觉：**并发数 L = 到达率 λ × 平均响应时间 W**。比如目标是支撑 500 RPS、接口平均响应 200ms，则稳态需要 500 × 0.2 = 100 个并发在途请求；考虑响应时间毛刺（P95 往往是均值的 2~3 倍）与脚本里的思考时间，配置时留 30%~50% 余量，开放模型下设 `preAllocatedVUs: 150, maxVUs: 400`。若业务给的是"日活/峰值在线用户数"，先换算到达率：峰值 QPS = 峰值在线用户 × 每用户每秒请求频率（有思考时间时频率 = 1 ÷ (思考时间 + 响应时间)）。封闭模型下反向验证：配置 N 个 VU 后实际 RPS = N ÷ (响应时间 + sleep)，压测跑起来看 `http_reqs` 速率是否达到目标，不达标就加 VU。最后记住并发数受两端约束：施压机能不能撑住这些 VU（每 VU 一个 JS 运行时实例，见第 17 篇），以及目标是不是先于施压机到达瓶颈。

## 2.9 k6 有哪些分布式压测方案？

三条路线。第一是**原生分布式执行**（v0.49 引入，v0.5x 仍标注 experimental）：`k6 run --execution-mode=distributed` 启动一个 controller 进程，通过 `K6_INSTANCES` 等环境变量发现多个 instance 进程，controller 把负载配置切分下发、各 instance 本地施压、指标回流聚合，退出码与阈值判定仍由 controller 统一给出——优点是官方内置、配置简单，适合几台到几十台施压机的规模。第二是 **k6-operator**（Kubernetes Operator）：把一次测试声明为 CRD，operator 拉起 controller 与 N 个 instance Pod，弹性伸缩、天然适配云原生团队，是目前自建分布式 k6 的主流方案。第三是 **Grafana Cloud k6**：全托管 SaaS，负载按量付费、自带结果分析与历史趋势，零运维，但测试数据要出内网，金融/政企场景需过合规评估。选型逻辑：单机能达标就永远别分布式（复杂度陡增）；需要 5 台以上施压机且已有 K8s 用 operator；无 K8s 用原生分布式；不想运维直接上云。

## 2.10 SharedArray 的作用是什么？什么时候不该用它？

SharedArray 解决的是 k6 数据参数化的内存放大问题。k6 默认**为每个 VU 独立执行一遍 init 上下文**，`JSON.parse(open('users.json'))` 的结果会在每个 VU 里各存一份副本——1 万个 VU 加载 5MB 的 JSON 就是约 50GB 内存，直接 OOM。`new SharedArray('name', () => JSON.parse(open('./data.json')))` 让数据在进程内只加载解析一次，所有 VU 共享同一份底层存储，内存从 O(VU 数 × 数据量) 降到 O(数据量)。代价是**每次读取元素时仍会拷贝一份返回**（防止某个 VU 修改数据污染其他 VU），所以访问比普通数组慢。不该用的场景：数据量很小（几十条）且访问极频繁的热数据，直接普通数组更快，重复内存可忽略；只跑 1~2 个 VU 的调试；以及需要每 VU 持有可变私有状态的场景（SharedArray 数据本质是只读的）。经验法则：数据文件超过 1MB 或 VU 数超过几百，就上 SharedArray。

## 2.11 如何把 k6 集成到 CI/CD？失败时流水线如何判定？

集成的三个要素：脚本进仓库（与业务代码同评审同版本）、阈值当门禁（k6 在 thresholds 不达标时以退出码 99 退出，流水线据此 fail）、结果做归档（`--out json` 或 `handleSummary()` 产出 summary.json 存为 artifact，关联构建版本画趋势）。平台接入上 GitHub Actions 用官方 `grafana/k6-action` 或 apt 装二进制，GitLab CI 直接跑 `grafana/k6` 镜像（entrypoint 清空），Jenkins 预装二进制并在 shell 里精细处理退出码。流水线判定的关键是**区分退出码语义**：99 = 阈值失败，是真实的性能信号，阻断并通知；107（脚本未捕获异常）、97（配置错误）、100（setup 失败）是脚本/环境故障，数据无效，当构建失败修脚本；103/106 是系统与外部故障，可自动重试一次。分层策略上 PR 只跑 2 分钟内的小规模冒烟（防低级回归），夜间 cron 跑对齐 SLO 的完整负载测试（真门禁），重要结论用自托管 runner 保证硬件一致。

## 2.12 一次完整的压测报告应该包含什么？如何向团队汇报压测结论？

一份可信的报告有五块：测试配置（脚本版本/commit、k6 版本、负载模型与参数、目标环境及其与生产的差异说明）、核心结果（目标到达率下的 RPS、延迟分位数 P50/P95/P99、错误率、checks 通过率，按关键接口分维度）、资源曲线（服务端 CPU/内存/DB/中间件水位随时间变化，与负载阶段对齐）、压测端自身数据（施压机 CPU、`http_req_blocked`、`dropped_iterations`——证明压力是干净送达的）、结论与拐点（系统在多少负载下开始劣化、瓶颈在哪个组件、容量建议与优化项）。汇报时用"结论 + 证据 + 边界"的结构：先给一句话结论（"当前配置可稳定支撑 800 RPS，P95 280ms，瓶颈在数据库连接池"），再附延迟-吞吐曲线与资源截图作证据，最后明确边界（"staging 数据量为生产 10%，生产结论需按数据量修正"）。最忌讳只甩一个平均延迟数字——平均值掩盖尾部，单点数据掩盖趋势，没有压测端数据的结果无法自证清白。

# 3. 常见误区

## 3.1 只看平均值

**平均值在性能领域几乎没有信息量**：100 个请求里 99 个 10ms、1 个 10s，平均值 110ms 看似正常，实际有用户体验到了灾难。延迟分布是长尾的，SLO 一律按分位数定义（P95/P99），k6 的 Trend 指标默认就输出 min/med/avg/max/p90/p95，看报告先看 p95 再看 avg。更进一步，分位数也要按场景聚合——全接口的 P95 会被高频快接口稀释，核心链路要用带标签的阈值单独度量。

## 3.2 不区分业务失败与系统失败

HTTP 200 不等于业务成功：响应 200 但 body 里 `{"code": 500}` 的错误在 `http_req_failed` 里完全不可见，压测报告一片绿而业务全挂。**业务正确性用 check 显式断言**（状态码 + 业务码 + 关键字段），check 失败率进 threshold 做门禁。反过来系统失败（连接超时、5xx）与业务失败（校验不过）的排查方向也不同：前者看基础设施与服务端日志，后者看脚本逻辑与测试数据。

## 3.3 其他高频误区速查

| 误区 | 后果 | 正确做法 |
|------|------|----------|
| 默认参数直接压生产 | 触发限流/事故，或压出的是 CDN 缓存性能 | 专用压测环境，生产压测需报备+白名单+熔断预案 |
| 单次运行下结论 | 被偶发波动误导 | 至少 3 次取中位数，报告附运行次数 |
| 测试数据不参数化 | 所有请求打同一缓存键，性能虚高 | SharedArray/CSV 参数化，数据量贴近生产分布 |
| 忘记施压机监控 | 把客户端瓶颈当系统容量 | 报告必须附压测端资源数据 |
| 长连接场景用短连接压测 | TLS 握手开销污染延迟数据 | 明确协议形态，`noConnectionReuse` 仅专项测试用 |
| 阈值一成不变 | 系统优化后门禁失去灵敏度 | 阈值随基线定期 review |

# 4. 自测与复盘

## 4.1 自测清单

压测结论发出前过一遍：**脚本正确性**——单 VU 跑通、check 全绿、参数化数据无重复消费、关联提取无 undefined；**环境一致性**——目标环境版本与生产一致、数据量级有说明、施压机资源充足且已监控；**数据驱动有效性**——实际到达率达标（`dropped_iterations` 为 0）、负载曲线与设计一致、运行时长覆盖到稳态（ramp-up 期的数据要排除在统计外）；**结果可复现**——重复运行波动在可接受范围、报告附带全部配置信息。

## 4.2 复盘输出

压测的终点不是报告而是行动。复盘输出三件东西：**瓶颈结论**（哪个组件在多少负载下先饱和、证据是哪组指标曲线）；**优化建议**（可执行的改进项，按预期收益排序，如"连接池从 50 调到 200，预期 P95 降 40%"，并约定优化后回归验证）；**遗留风险**（本次没覆盖的场景、环境差异导致的不确定性、需要专项测试的问题）。把每次压测的结论沉淀进基线库，下次运行自动对比——性能测试的价值在于趋势，单次报告只是趋势上的一个点。

# 5. 小结

最佳实践的主线是"设计定上限、脚本保正确、执行防失真、复盘出行动"：设计阶段从 SLO 出发定义可判定的目标与负载模型，脚本阶段模块化 + check 全覆盖 + 环境外置，执行阶段单 VU 验证、阶梯加压、双端监控、多次运行，复盘阶段输出瓶颈结论与可执行的优化项。面试题的知识骨架集中在五组对比上：k6 vs JMeter（开发者代码 vs GUI 工具、goroutine vs 线程）、check vs threshold（迭代级软断言 vs 测试级硬门禁）、开放 vs 封闭模型（到达率自变量 vs 并发数自变量，以及由此产生的协调遗漏）、VU 数与到达率的换算（Little's Law）、单机与分布式的选型（原生 distributed / k6-operator / Cloud）。能把"协调遗漏为什么发生、开放模型如何解决"讲清楚，基本就证明了对负载生成原理的真实理解——这也是 k6 面试里区分度最高的一道题。
