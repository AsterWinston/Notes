# 1. 测试金字塔与测试策略

## 1.1 测试金字塔的意义

测试金字塔强调**“低层多、高层少”**：

- 单元测试数量最多、速度最快
- 切片与集成测试关注协作与配置正确性
- 端到端测试数量最少，用于兜底与回归

在 Spring Boot 项目中，这意味着：

- **业务逻辑优先使用纯 JUnit**，避免 Spring 依赖
- **HTTP 层使用切片测试**（`@WebMvcTest`）
- **全链路验证使用 `@SpringBootTest`**

## 1.2 失败成本与定位能力

| 测试类型 | 失败定位 | 运行成本 | 适用阶段 |
|---------|---------|---------|---------|
| 单元测试 | 高 | 低 | 开发自测 |
| 切片测试 | 中高 | 中 | 功能验证 |
| 集成测试 | 中 | 高 | 回归验证 |
| 端到端 | 低 | 很高 | 发布前兜底 |

核心原则：**失败越昂贵，越靠近金字塔顶端**。

# 2. 需求到测试的映射

## 2.1 业务需求拆解

建议将需求拆成三层：

- 规则与算法（单元测试）
- 模块协作（切片测试）
- 系统完整链路（集成/端到端测试）

## 2.2 设计“可测性”

### 2.2.1 依赖隔离

- 使用依赖注入而不是直接 new
- 避免静态工具类与硬编码配置

### 2.2.2 边界清晰

- 通过接口明确“谁依赖谁”
- 对外部系统使用适配层，便于 Mock 或 Fake

# 3. Spring Boot 项目的测试分层建议

## 3.1 Service 层

- 只依赖 JUnit 5 + Mockito
- 避免启动 Spring 容器

## 3.2 Controller 层

- 使用 `@WebMvcTest`
- 对 Service 依赖使用 `@MockBean`

## 3.3 Repository 层

- 使用 `@DataJpaTest` 或 `@JdbcTest`
- 使用内嵌数据库或测试数据库

## 3.4 端到端链路

- `@SpringBootTest(webEnvironment = RANDOM_PORT)`
- `TestRestTemplate` 或 `WebTestClient`

# 4. 覆盖率、风险与成本

## 4.1 覆盖率的误区

- 覆盖率高不代表质量高
- 关键路径与边界条件比行覆盖更重要

## 4.2 风险优先

- 重要业务流程优先编写测试
- 易出错的边界优先覆盖

## 4.3 运行成本控制

- 通过测试切片减少上下文加载
- 使用 Profile 与 TestConfiguration 限制依赖范围

# 5. 反脆弱与稳定性

## 5.1 易脆测试（Flaky Test）的来源

| 来源 | 典型表现 | 解决思路 |
|------|----------|----------|
| 时间与时区 | 本地通过 CI 失败 | 固定 `Clock`、设置时区 |
| 并发与线程 | 偶发失败 | 限制并行、使用同步工具 |
| 外部系统 | 依赖不稳定 | Mock 或本地替身 |
| 共享数据 | 用例互相污染 | 隔离数据、使用回滚 |

## 5.2 稳定性策略

- 使用 `@DirtiesContext` 清理强污染测试
- 拆分测试边界，减少共享状态
- 对外部依赖使用明确的替身实现
