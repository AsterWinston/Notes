# 1. 测试金字塔与测试策略

测试策略回答的问题是：**有限的测试预算应该花在哪一层、每层写多少、什么时候跑**。Spring Boot 项目里这个问题尤其尖锐——容器型测试成本太高，分层一旦失当，套件会从"几分钟"膨胀到"一小时"，最终团队开始跳过测试。本篇讨论金字塔模型在 Spring 项目里的落位、与奖杯模型之争、CI 分层执行策略与稳定性治理。

## 1.1 测试金字塔的意义

**测试金字塔强调"低层多、高层少"：越底层的测试越便宜、越快、定位越准，就应该写得越多；越顶层的测试越贵、越慢、越脆，只保留少量关键路径。** Mike Cohn 在《Succeeding with Agile》里提出的这个模型，核心逻辑是成本与收益的匹配：

- 单元测试数量最多、速度最快——毫秒级反馈，失败直接指向某个方法的某个分支
- 切片与集成测试关注协作与配置正确性——验证"层与层之间接对了没有"
- 端到端测试数量最少，用于兜底与回归——验证"整个系统作为整体能工作"

在 Spring Boot 项目中，这意味着：

- **业务逻辑优先使用纯 JUnit + Mockito**，避免 Spring 依赖。Service 层的计算规则、状态机、校验逻辑都不需要容器
- **HTTP 层使用切片测试**（`@WebMvcTest` + MockMvc），验证路由、参数绑定、序列化、异常映射
- **全链路验证使用 `@SpringBootTest`**，且只针对核心业务流程写少量用例

倒金字塔（大量端到端测试、少量单元测试）的典型症状：CI 跑 40 分钟、失败后看不出是哪个组件坏了、改一行代码要等全量回归——最终演变成"冰淇淋筒反模式"，测试沦为摆设。

## 1.2 失败成本与定位能力

**选择测试层级的本质是在"定位能力"与"运行成本"之间做交换：**

| 测试类型 | 失败定位 | 运行成本 | 脆弱性 | 适用阶段 |
|---------|---------|---------|--------|---------|
| 单元测试 | 高（精确到方法分支） | 低（毫秒级） | 低 | 开发自测、每次提交 |
| 切片测试 | 中高（锁定单层） | 中（百毫秒~秒级） | 中 | 功能验证、PR 检查 |
| 集成测试 | 中（可能是装配/配置/数据任一环节） | 高（秒级 + 容器启动） | 中高 | 合并主干、回归验证 |
| 端到端 | 低（跨进程、跨服务） | 很高（真实 HTTP + 外部依赖） | 高 | 发布前兜底 |

核心原则：**失败越昂贵，越靠近金字塔顶端**。反过来说，一个断言如果能放在低层验证，放到高层就是纯浪费——高层测试的独有价值只在于验证"低层测不到的东西"：自动配置装配、Bean 之间的真实连接、HTTP 栈行为、跨组件事务边界。

> **设计争议**：金字塔模型在 Spring 社区一直有挑战者。批评者指出，对重度依赖 DI 容器的框架，"纯单元测试"往往需要大量手工构造对象，而一个被缓存复用的容器切片测试可能只比它慢几百毫秒——差距没有金字塔画的那么悬殊。这催生了下一节的奖杯模型。

## 1.3 金字塔与奖杯模型之争

**测试奖杯（Testing Trophy）是 Kent C. Dodds 提出的替代模型：与其追求"单元测试占绝对多数"，不如把重心放在集成测试层，形状像奖杯——集成测试在中部最宽，单元测试和端到端测试在两端收窄。** 口号是"集成测试给你最好的信心回报比"。分歧根源在于对"信心"的定义不同：

| 维度 | 金字塔 | 奖杯 |
|------|--------|------|
| 重心 | 单元测试（数量最多） | 集成测试（信心最高） |
| 隐含假设 | 单元正确 → 整体正确 | 单元正确不代表"接起来"正确 |
| 适合的系统 | 逻辑密集（算法、领域模型） | 集成密集（CRUD 应用、API 编排） |
| 出身社区 | 传统软件工程、敏捷 | 前端/全栈（React 生态） |

**对 Spring Boot 项目，两个模型其实可以调和**：业务逻辑沉淀在 Service 与领域对象里（充血模型）时金字塔适用；应用主要是"接收请求 → 查库 → 拼装响应"的编排型 CRUD（贫血模型）时，单元层可测的东西很少，奖杯更贴合现实——这时最有价值的恰恰是 `@SpringBootTest` + Testcontainers 这种"真库真装配"的集成测试。行业共识：**逻辑复杂偏金字塔，编排型偏奖杯，但两者都同意"少量端到端 + 大量快速反馈"的骨架**。

> **行业实践**：Spring 官方文档（Boot Reference 的 Testing 章节）的立场更接近金字塔——它明确建议"能用纯 JUnit 就不进容器、能用切片就不用全量"，并把 `@SpringBootTest` 定位为验证应用上下文能否正常启动与少量核心流程的兜底手段。

# 2. 需求到测试的映射

## 2.1 业务需求拆解

**好的测试策略从需求拆解开始：需求进来先按"规则与算法 / 模块协作 / 系统完整链路"三层切开，每片落在合适的层级上。** 以"订单金额超过 1000 元打 95 折，VIP 用户叠加 98 折"为例：

- **规则与算法（单元测试）**：折扣计算逻辑——边界值 999.99/1000、VIP 与非 VIP、叠加顺序。纯函数式逻辑用参数化测试穷举，毫秒级跑完几十个用例
- **模块协作（切片测试）**：`OrderController` 接收下单请求、返回正确的 HTTP 状态与 JSON——`@WebMvcTest` + Mock 掉 Service；订单落库查询——`@DataJpaTest`
- **系统完整链路（集成/端到端测试）**：HTTP 请求进来，经过折扣计算、库存扣减、订单落库、事件发布的完整流程——`@SpringBootTest` 一个用例覆盖主干路径即可

拆解的判断标准：**每一层只验证本层新增的正确性，不重复验证下层已经覆盖的逻辑**。端到端测试里不需要再断言"999 元不打折"——那是单元测试的职责；它只需要断言"整个下单流程走通、金额正确"。

## 2.2 设计"可测性"

**可测性不是测试阶段补出来的，是设计阶段决定好的。** Spring 项目里可测性的两个基础要素：

### 2.2.1 依赖隔离

- **使用依赖注入而不是直接 new**：构造函数注入（推荐）让测试可以直接 `new OrderService(mockRepo, mockGateway)`，完全不需要容器；字段注入强迫测试要么起容器要么用反射注入（`@InjectMocks`），这是"字段注入不利于测试"的确切含义
- **避免静态工具类与硬编码配置**：静态方法无法 Mock（除非 mockito-inline 的 static mocking），硬编码 URL 让测试无法指向替身。`Clock`、`Random` 这类环境依赖也应注入而非静态获取

```java
// 错误示范：依赖在内部创建，测试无法替换
public class OrderService {
    private final PaymentClient client = new PaymentClient("https://pay.example.com");
}

// 正确做法：构造函数注入，测试传入替身
public class OrderService {
    private final PaymentClient client;

    public OrderService(PaymentClient client) { // Spring 自动装配，测试手动传入
        this.client = client;
    }
}
```

### 2.2.2 边界清晰

- **通过接口明确"谁依赖谁"**：依赖方向决定了测试能在哪里"切一刀"；清晰的分层（Controller → Service → Repository）让每层可独立测试
- **对外部系统使用适配层**：支付网关、短信服务、第三方 API 都包一层自己的接口（防腐层），便于 Mock 或 Fake；业务代码里散落 `RestTemplate` 调用等于把外部不稳定性引入每个测试

> **设计考量**：可测性设计与"六边形架构"（端口与适配器）的主张高度重合——业务核心不依赖任何技术细节，依赖全部通过端口注入。这不是巧合：**测试替身和架构解耦用的是同一个机制（注入），一个让测试可行，一个让系统可演化**。

# 3. Spring Boot 项目的测试分层建议

## 3.1 Service 层

**Service 层的默认姿势是纯 JUnit 5 + Mockito，不启动 Spring 容器。** 前提是用构造函数注入组织依赖，测试里用 `@ExtendWith(MockitoExtension.class)` + `@Mock` + `@InjectMocks` 即可：

```java
import org.junit.jupiter.api.Test;
import org.junit.jupiter.api.extension.ExtendWith;
import org.mockito.InjectMocks;
import org.mockito.Mock;
import org.mockito.junit.jupiter.MockitoExtension;

import java.math.BigDecimal;

import static org.assertj.core.api.Assertions.assertThat;
import static org.mockito.BDDMockito.given;

@ExtendWith(MockitoExtension.class) // 纯 Mockito，无任何 Spring 组件
class OrderServiceTest {

    @Mock
    private OrderRepository orderRepository;   // 依赖全部替身化

    @InjectMocks
    private OrderService orderService;         // 被测对象，构造时注入上面的 Mock

    @Test
    void should_apply_discount_when_amount_over_1000() {
        given(orderRepository.countByUserId(1L)).willReturn(0);
        assertThat(orderService.calculatePayable(1L, new BigDecimal("2000")))
                .isEqualByComparingTo(new BigDecimal("1900")); // 2000 * 0.95
    }
}
```

例外情况：Service 里用到 Spring 特有机制（`@Transactional` 传播行为、事件发布、AOP 切面）时，纯 Mockito 测不到代理层行为，才值得升级到 `@SpringBootTest`。**事务语义的验证归入集成层**——`@Transactional` 本质是代理织入行为，脱离容器不存在。

## 3.2 Controller 层

**控制器层用 `@WebMvcTest` 切片：只装配 Web 层，Service 依赖用 `@MockitoBean` 顶掉，通过 MockMvc 走 DispatcherServlet 但不打开真实端口。** 这一层验证的是：URL 映射、参数绑定与校验（`@Valid`）、状态码、响应序列化、异常处理器。切片启动比全量容器快一个量级，且失败几乎必然定位在 Web 层。详细写法见第 7 篇（切片）与第 8 篇（MockMvc）。

## 3.3 Repository 层

**仓储层用 `@DataJpaTest`（或纯 JDBC 场景的 `@JdbcTest`），默认接管事务并在每个测试方法后回滚，配合内嵌数据库或 Testcontainers 真实数据库。** 需要区分的两类断言：

- **派生查询与 `@Query` 的正确性**：`@DataJpaTest` + 内嵌 H2 通常够用，但 H2 与 MySQL 的方言差异（函数、锁行为）可能漏掉问题
- **依赖真实方言的行为**（JSON 列、全文索引、特定锁语义）：用 Testcontainers 起真实数据库——代价是启动几秒，但换来的是与生产一致的 SQL 行为

> **行业实践**：对数据库交互复杂的系统，越来越多团队用 Testcontainers 全面替代内嵌数据库做仓储层测试——"H2 上测试通过、MySQL 上生产报错"的案例足够多。数据库测试细节见第 12 篇。

## 3.4 端到端链路

**端到端用 `@SpringBootTest(webEnvironment = RANDOM_PORT)`，通过 `TestRestTemplate` 或 `WebTestClient` 发真实 HTTP 请求，覆盖核心流程完整链路。** 数量控制在"每条核心流程 1-3 个用例"，只断言业务结果（状态码、关键响应字段、落库数据）。外部依赖（第三方 API）在这一层用 WireMock 起本地替身服务而不是 Mock Bean——端到端的价值就在于"连 HTTP 客户端的序列化都验证到"。

## 3.5 分层与 CI 执行策略

**测试分层要落到构建生命周期上才有意义：快的测试频繁跑，慢的测试少跑但不能不跑。** Maven/Gradle 生态的惯用做法是用命名约定区分两类测试，绑定到不同的构建阶段：

```text
CI 分层执行策略

开发者本地 / 每次 push
  └─ mvn test（surefire）
       · *Test.java：单元测试 + 切片测试，1~3 分钟内

PR 合并 / 主干构建
  └─ mvn verify（failsafe）
       · *IT.java：@SpringBootTest 集成测试，
         Testcontainers 起真实依赖，10 分钟左右

夜间 / 发布前
  └─ 完整端到端 + 性能基线
       · 多服务联调、RANDOM_PORT 全链路回归
```

Maven 侧由 `maven-failsafe-plugin` 接管 `*IT.java`（绑定 `integration-test`/`verify` 阶段，完整配置见第 18 篇）；命名约定：`*Test.java` 是快速测试（surefire 默认拾取），`*IT.java` 是集成测试（failsafe 默认拾取）。Gradle 用 `Test` 任务的 include/exclude 或独立 sourceSet 实现同样分流。**分层的收益只有在 CI 里兑现**：所有测试都挤在同一阶段跑，开发者就会习惯性忽略红灯。

# 4. 覆盖率、风险与成本

## 4.1 覆盖率的误区

**覆盖率是有用的烟雾报警器，但不是质量指标。** 行覆盖率 90% 的套件完全可能全是"执行了代码但没有断言"的空转测试；覆盖率 60% 但把关键路径、边界条件、异常分支都覆盖了的套件，防护价值远高于前者。JaCoCo 报告的正确用法是**找"没被覆盖的重要代码"**，而不是追数字：

- 关键路径与边界条件比行覆盖更重要——折扣计算的 999/1000 边界值没测到，比一个 getter 没测到严重一百倍
- 覆盖率目标应该分模块设定：领域核心 80%+，配置与胶水代码不设硬指标
- 分支覆盖率（branch）比行覆盖率（line）更接近"逻辑被验证"的真实程度

> **设计争议**：要不要在 CI 上设覆盖率门禁（低于阈值就构建失败）？支持者认为没有门禁覆盖率必然腐化；反对者认为门禁催生凑数测试。折中的行业实践：**只对新增代码设门禁（diff coverage），存量不设**——阻止腐化比追溯补债现实得多。

## 4.2 风险优先

**测试预算永远有限，分配依据应该是风险而不是代码量。** 风险优先的两个维度：

- **重要业务流程优先编写测试**：下单、支付、扣库存这类"坏了就是资损"的路径值得多层覆盖（单元 + 集成 + 端到端）；后台报表导出坏了可以人工兜底，一层测试即可
- **易出错的边界优先覆盖**：历史 bug 高发区（时间与时区、金额精度、并发状态）是回归重点。实用纪律：**每修一个生产 bug，先补一个能复现它的测试**——同一个坑不掉两次，测试集跟着真实风险自然生长

## 4.3 运行成本控制

控制套件成本的手段按收益排序：

- **通过测试切片减少上下文加载**：能用 `@WebMvcTest` 就不用 `@SpringBootTest`，单笔收益最大
- **收敛上下文配置种类**：让尽可能多的测试类共享同一个缓存容器，配置发散是容器反复重建的元凶（见第 5 篇）
- **使用 Profile 与 TestConfiguration 限制依赖范围**：测试 profile 下关闭不必要的自动配置（定时任务、消息监听）
- **并行执行**：JUnit 5 并行调度对无共享状态的测试类收益显著；容器型测试并行时要确认缓存与外部资源（数据库端口）不冲突

# 5. 反脆弱与稳定性

## 5.1 易脆测试（Flaky Test）的来源

**Flaky Test（同一份代码时而通过时而失败的测试）比没有测试更糟糕——它训练团队忽略红灯。** 四大来源与对策：

| 来源 | 典型表现 | 解决思路 |
|------|----------|----------|
| 时间与时区 | 本地通过 CI 失败；月末/跨年失败 | 注入固定 `Clock`、显式设置时区、避免依赖"当前时间" |
| 并发与线程 | 偶发失败，重跑就过 | 用 Awaitility 轮询替代 `Thread.sleep`、限制并行度、同步工具收敛竞态 |
| 外部系统 | 依赖网络波动失败 | Mock、WireMock 本地替身、Testcontainers 自管生命周期 |
| 共享数据 | 用例互相污染，单独跑通过、全量跑失败 | 事务回滚、每用例独立数据、避免依赖执行顺序 |

排查 Flaky 的第一动作是**在 CI 上重复跑失败用例并保留完整日志**，确认它属于哪一类；"重跑三次总有一次过"不是修复，是把问题藏得更深。异步测试工具（Awaitility、`@RecordApplicationEvents`）见第 15 篇。

## 5.2 稳定性策略

- **使用 `@DirtiesContext` 清理强污染测试**：确实无法还原容器状态时的最后手段，代价是缓存失效（详见第 5 篇）
- **拆分测试边界，减少共享状态**：静态可变字段、单例里的缓存 Map 是跨用例污染两大源头；测试类之间不应有隐式数据传递
- **对外部依赖使用明确的替身实现**：Fake（内存实现）比 Mock 更稳定——Mock 桩配置错了直接 NPE，Fake 至少行为确定
- **隔离测试数据**：每个用例造自己的数据、用完回滚或清理，不依赖"库里已经有那条记录"

> **行业实践**：稳定性的组织保障比技术手段更重要——**Flaky 测试要在 48 小时内修复或隔离（quarantine）**，隔离区定期清理。放任不管的套件会在几周内失去团队信任，届时补测试的成本远高于维护测试。

# 6. 小结

| 主题 | 关键结论 |
|------|---------|
| 金字塔 | 低层多、高层少；每写一个测试先问"这个断言最低能落在哪一层" |
| 奖杯之争 | 逻辑密集型系统偏金字塔，编排型 CRUD 系统偏奖杯；两者共享"少量端到端 + 快速反馈"骨架 |
| 需求映射 | 按"规则/协作/链路"三层拆解，每层只验证本层新增的正确性 |
| 可测性 | 构造函数注入 + 外部依赖走适配层，是测试策略能落地的前提 |
| 分层落位 | Service→纯 JUnit+Mockito；Controller→`@WebMvcTest`；Repository→`@DataJpaTest`/Testcontainers；链路→`RANDOM_PORT` |
| CI 策略 | `*Test` 走 surefire 每次跑，`*IT` 走 failsafe 合并时跑，端到端夜间跑 |
| 覆盖率 | 找未覆盖的重要代码，不追数字；门禁只对新增代码设 |
