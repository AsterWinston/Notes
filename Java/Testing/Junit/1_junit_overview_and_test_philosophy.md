# 1. JUnit 定位与测试理念

JUnit 是 Java 生态中最常用的单元测试框架，核心价值是**用可重复、可自动化的方式验证最小业务单元的正确性**。在工程实践中，它是测试金字塔的底座，与集成测试、端到端测试形成互补。理解 JUnit 不能只停留在 API 层面——它背后是一整套关于"什么样的验证值得自动化、自动化到什么粒度"的工程理念，本篇先把这套理念讲清楚，再给出最小可运行示例，后续篇目才进入 JUnit 4 的架构与用法细节。

## 1.1 JUnit 在测试体系中的位置

软件测试按验证范围从小到大分为三层，每层的关注点、成本和反馈速度都不同：

- **单元测试（Unit Test）**：聚焦最小业务单元（方法/类），快速、隔离、稳定。典型执行时间在毫秒级，一个中型项目可以有几千个单元测试，全量跑完也只需几十秒。
- **集成测试（Integration Test）**：验证多个组件协作与外部依赖（DB、消息队列、HTTP 服务）。需要真实的运行环境，速度以秒到分钟计，失败时定位成本明显更高。
- **端到端测试（E2E）**：从用户视角验证完整链路（如浏览器操作、跨服务调用），成本高、速度慢、稳定性差，通常只覆盖核心业务流程。

**设计动机**：把"可重复验证"前置到研发过程，通过快速反馈降低缺陷成本。缺陷发现得越晚，修复成本越高——这是软件工程里被反复验证的经验规律：编码阶段发现的缺陷修复成本是 1，测试阶段是 10，生产环境是 100。JUnit 这类单元测试框架的意义，就是让尽可能多的缺陷在"成本为 1"的阶段暴露出来。

JUnit 本身并不限定"单元"的边界。它可以驱动一个纯函数的测试，也可以配合 Spring Test 启动整个容器做集成测试——事实上 Spring Boot 的 `@SpringBootTest` 底层（JUnit 4 时代）就是通过 JUnit 的 Runner 机制接入的。所以更准确的说法是：**JUnit 是 Java 测试的执行引擎与断言基础设施**，测试的"层级"由你如何组织被测代码和依赖决定，而不是由框架决定。

## 1.2 单元测试的价值与边界

### 1.2.1 价值

单元测试的回报不只是"抓 Bug"，至少体现在四个方面：

- **回归保护**：改动后快速定位破坏性变更。没有测试的代码库，每次重构都像闭着眼睛过马路；有测试的代码库，`mvn test` 通过就意味着既有行为没有被破坏。
- **设计反馈**：难测试往往意味着设计耦合度过高。一个类如果必须先启动数据库、注入五个依赖、设置三个全局状态才能测一个方法，这本身就是设计问题的信号——测试是"设计的第一使用者"。
- **文档作用**：测试即可执行的规格说明。文档会过时，测试不会——过时的测试会失败，逼着你更新它。读 `should_return_discount_price_when_vip_user` 这样的测试名，比读一段自然语言需求更可靠。
- **重构安全网**：行为可验证，重构更大胆。Martin Fowler 对重构的定义就建立在"行为不变"上，而"行为是否不变"只能靠测试来判定。

### 1.2.2 边界

单元测试同样有明确的不适用范围，越界使用会产生"虚假的安全感"：

- 不适合验证外部系统稳定性（应由集成测试覆盖）。用 Mock 替换掉数据库之后，"SQL 写错了"这类问题单元测试永远发现不了。
- 不适合覆盖复杂流程的用户体验（应由 E2E 覆盖）。页面跳转顺序、多步骤表单的状态流转，用单元测试逐段验证的拼接成本远高于一条 E2E 用例。
- 不适合验证"组件装配是否正确"。Spring 的依赖注入、配置绑定、AOP 代理，这些恰恰是单元测试 Mock 掉的部分，需要集成测试兜底。

> **注意**：一个常见误区是"单元测试覆盖率 100% 就等于没有 Bug"。覆盖率只说明代码被执行过，不说明断言充分——一个没有任何 assert 的测试也能贡献覆盖率。覆盖率是**风险信号**（低覆盖区域风险高），不是**质量目标**。

## 1.3 测试金字塔与测试四象限

**测试金字塔**描述三层测试的数量配比：单元测试多、集成测试中、端到端少。

```
        ┌─────────┐
        │   E2E   │        ← 少量：慢、脆、贵，只覆盖核心链路
       ┌┴─────────┴┐
       │  集成测试  │       ← 适量：验证组件协作与外部依赖
      ┌┴───────────┴┐
      │   单元测试   │      ← 大量：快、稳、便宜，覆盖业务规则
      └─────────────┘
   数量 ↑        单个成本 ↓
   速度 ↓        定位效率 ↑
```

金字塔形状不是审美选择，而是成本结构的直接反映：越往上执行越慢、失败时定位越难、维护越频繁，所以数量必须收敛。反过来的"冰淇淋筒"形态（E2E 一大堆、单元测试寥寥）是典型的反模式，往往意味着回归一次要跑几个小时，团队最终放弃跑测试。

**测试四象限**（Brian Marick 提出，Lisa Crispin 在《敏捷软件测试》中普及）从另一个维度切分测试：

| 象限 | 导向 | 面向 | 典型测试 |
|------|------|------|---------|
| Q1 | 技术导向 | 支持团队 | 单元测试、组件测试 |
| Q2 | 业务导向 | 支持团队 | 契约测试、API 测试、功能示例 |
| Q3 | 业务导向 | 面向客户 | E2E、探索性测试、UAT |
| Q4 | 技术导向 | 面向客户 | 性能测试、安全测试、可靠性测试 |

**启示**：JUnit 主要服务于 Q1"技术导向 + 支持团队"象限，但设计良好的单元测试也能间接表达业务规则——当测试名和数据都来自业务语言时（如 `余额不足时拒绝下单`），单元测试就同时承担了 Q2 的"可执行规格"职责。

## 1.4 TDD/BDD 与 JUnit

**TDD（测试驱动开发）**的核心循环是"红-绿-重构"：先写一个失败的测试（红），再写刚好让它通过的实现（绿），最后在测试保护下重构。

```
┌────────────────────────────────────────┐
│              TDD 循环                   │
│                                        │
│   ┌──────┐   写最小实现   ┌──────┐      │
│   │  红  │ ────────────→ │  绿  │      │
│   │写失败 │               │让测试 │      │
│   │的测试 │ ←──────────── │ 通过 │      │
│   └──────┘    重构后       └──┬───┘      │
│      ↑       回归验证         │          │
│      └─────────┌─────────┐   │          │
│                │  重构   │ ←─┘          │
│                │消除重复 │              │
│                └─────────┘              │
└────────────────────────────────────────┘
```

TDD 的真正产出物不只是测试，还有**被测试倒逼出来的低耦合设计**：你无法为"先 new 一个静态单例再调用"的代码写测试，于是自然会走向依赖注入。它的代价是前期速度慢、对需求不明确的任务不适用（探索性代码先写再补测试更划算）。

**BDD（行为驱动开发）**从行为/场景描述出发，用 Given-When-Then 的自然语言结构组织测试，强调可读性与业务沟通。JUnit 本身是 TDD 风格的工具（方法名 + 断言），BDD 通常通过命名约定、断言组织和 DSL（如 AssertJ 的流式断言、Mockito 的 `when/then`、Cucumber 的场景文件）叠加在 JUnit 之上实现。

> **行业实践**：国内多数团队不做严格 TDD，而是"测试跟随"（写完实现补测试）或"测试先行于提测"（提测前必须补齐核心路径的单元测试）。严格 TDD 对开发者纪律要求高，更适合基础设施库、算法密集模块这类"行为明确、变更频繁"的代码；对 CRUD 业务系统，投入产出比往往不划算。

## 1.5 测试质量指标与反模式

### 1.5.1 指标参考

判断一个单元测试写得好不好，业界常用 **FIRST 原则**：

- **Fast（快速）**：单个测试毫秒级，全量套件分钟内完成。测试一慢，开发者就不跑了，测试就死了。
- **Independent（独立）**：测试之间不共享状态、不依赖执行顺序，任意单独运行结果一致。
- **Repeatable（可重复）**：不依赖随机数、当前时间、网络、操作系统环境，在任何机器上结果相同。
- **Self-validating（自验证）**：结果只有"通过/失败"两种，不需要人工看日志判断。
- **Timely（及时）**：测试与实现代码同期产出，而不是上线后补。

再补两个工程指标：**可读性**（测试名即规格，Given-When-Then 结构清晰，新人 30 秒能看懂一个测试在验证什么）和**覆盖率**（作为风险信号使用，行覆盖率 60%-80% 是多数团队的务实区间，核心模块可以要求更高）。

### 1.5.2 常见反模式

- **过度模拟（Over-Mocking）**：把被测对象的所有协作者都 Mock 掉，测试退化成"验证实现细节"。重构时实现一改测试全红，但行为其实没变——这种测试是负资产。原则：**Mock 你拥有的依赖，不 Mock 值对象和纯函数**。
- **测试相互依赖**：测试 B 依赖测试 A 写入的静态变量，顺序不同导致结果不同。一旦 IDE 或 CI 改变执行顺序就出现"本地绿、CI 红"。
- **超大测试类**：一个测试类几千行、几十个测试方法共享一坨 setup，难维护、定位问题慢。按被测行为拆分测试类。
- **随机/时间依赖**：直接调用 `new Date()`、`Math.random()`，引入偶发失败（Flaky Test）。正确做法是通过时钟抽象（如注入 `Clock`）和固定随机种子把不确定性挡在测试之外。
- **断言缺失或断言过弱**：只断言 `assertNotNull(result)`，或干脆没有断言只验证"不抛异常"。
- **测试逻辑分支**：测试方法里写 if/for 来构造多种场景——测试本身有了逻辑就有了 Bug 的可能。用参数化测试替代。

> **设计争议**：Flaky Test（偶发失败测试）该修复还是该删除？主流意见是**零容忍**：一个"十次跑九次绿"的测试会让团队对红色警报脱敏，进而忽视真正的失败。Google 的工程实践是把 flaky test 自动隔离出主流水线，限期修复，逾期删除。

# 2. 快速示例

先用最小示例建立体感：同一个计算器测试，JUnit 5 和 JUnit 4 各写一遍。两者的差异（`jupiter` 包名、方法可见性、注解来源）正是本系列后续篇目要展开的内容。

## 2.1 JUnit 5 示例

JUnit 5（当前主流，Jupiter 5.10+）的测试类和测试方法**不要求 public**，断言来自 `org.junit.jupiter.api.Assertions`：

```java
import org.junit.jupiter.api.Test;
import static org.junit.jupiter.api.Assertions.assertEquals;

// 被测类：一个最简单的计算器
class Calculator {
    int add(int a, int b) {
        return a + b;
    }
}

// 测试类：JUnit 5 不要求 public
class CalculatorTest {

    @Test
    void add_should_sum_two_numbers() {
        Calculator calculator = new Calculator();
        assertEquals(3, calculator.add(1, 2)); // 期望值在前，实际值在后
    }
}
```

Maven 依赖：

```xml
<dependency>
    <groupId>org.junit.jupiter</groupId>
    <artifactId>junit-jupiter</artifactId>
    <version>5.10.2</version>
    <scope>test</scope>
</dependency>
```

## 2.2 JUnit 4 示例

JUnit 4（本系列 2-5 篇的主角，最后稳定版 4.13.2）要求测试类和测试方法**必须 public**，断言来自 `org.junit.Assert`：

```java
import org.junit.Test;
import static org.junit.Assert.assertEquals;

// 测试类：JUnit 4 要求 public
public class CalculatorTest {

    @Test
    public void add_should_sum_two_numbers() {
        Calculator calculator = new Calculator();
        assertEquals(3, calculator.add(1, 2)); // 期望值在前，实际值在后
    }
}
```

Maven 依赖：

```xml
<dependency>
    <groupId>junit</groupId>
    <artifactId>junit</artifactId>
    <version>4.13.2</version>
    <scope>test</scope>
</dependency>
```

两代框架的关键差异速览（详细对照见第 2 篇）：

| 维度 | JUnit 4（4.13.2） | JUnit 5（Jupiter 5.10+） |
|------|------------------|------------------------|
| 包名 | `org.junit` | `org.junit.jupiter.api` |
| 测试注解 | `@Test`（必须 public 方法） | `@Test`（可 package-private） |
| 前后置钩子 | `@Before` / `@After` | `@BeforeEach` / `@AfterEach` |
| 类级钩子 | `@BeforeClass` / `@AfterClass` | `@BeforeAll` / `@AfterAll` |
| 扩展机制 | Runner + Rule（二选一） | Extension 模型（可组合） |
| 参数化 | `@RunWith(Parameterized.class)` | `@ParameterizedTest` |
| 运行方式 | JUnit 4 Runner | JUnit Platform（可兼容运行 JUnit 4） |

运行测试：

```bash
# Maven：运行全部测试
mvn test

# Maven：只运行某个测试类
mvn test -Dtest=CalculatorTest

# Gradle
gradle test --tests CalculatorTest
```

# 3. 什么时候不使用 JUnit

测试策略的核心是**分层与取舍**，不是"所有东西都用单元测试覆盖"。明确 JUnit 的适用边界，比多写一百个测试更重要。

## 3.1 更适合使用集成/端到端测试的场景

以下场景强行用单元测试（Mock 一切外部依赖）验证，得到的只是"Mock 的行为符合我的想象"，而非"系统真的能工作"：

- **数据库事务与连接池的行为验证**：事务传播、隔离级别、死锁、连接泄漏，都依赖真实数据库引擎的行为。
- **远程服务容错、超时、重试策略**：网络分区、服务降级、熔断恢复，需要真实的网络环境和故障注入。
- **跨进程、跨系统的业务流程**：订单-库存-支付的分布式一致性，单元测试无法覆盖进程间交互。
- **框架装配逻辑**：Spring 的自动配置、Bean 生命周期、AOP 增强，Mock 掉框架等于什么都没测。

这些场景的正确工具是集成测试框架（Testcontainers、Spring Boot Test）、契约测试（Pact、Spring Cloud Contract）和 E2E 工具（Playwright、Selenium）——但它们大多仍然**以 JUnit 作为执行引擎**，这也是 JUnit 生态地位稳固的原因。

## 3.2 维护成本评估

当测试成本明显高于价值时，应调整策略而不是硬撑。典型的"低价值测试"信号：

- 高度不稳定的 UI 测试：每次前端微调就大面积失败，修复测试的时间超过开发功能的时间。
- 需求频繁变化且难以抽象为稳定规则的代码：为"下周就要重写"的逻辑写的精细单元测试，生命周期比实现代码还短。
- 纯粹为了覆盖率指标补的测试：断言空洞、复制粘贴、改一处实现要同步改十个测试。

> **行业实践**：成熟团队用"测试维护成本 / 缺陷拦截收益"来评估测试资产。一个务实的规则是——**如果某个测试在半年内没有拦截过任何回归缺陷，且每次重构都要跟着改**，就应该考虑删除或用更粗粒度的测试替代它。测试也是代码，也有负债。

# 4. 小结

| 主题 | 核心结论 |
|------|---------|
| JUnit 定位 | Java 测试的执行引擎与断言基础设施，是测试金字塔的底座 |
| 三层测试 | 单元（快/多/隔离）→ 集成（组件协作/外部依赖）→ E2E（用户视角/少量核心链路） |
| 单元测试价值 | 回归保护、设计反馈、可执行文档、重构安全网 |
| 测试金字塔 | 数量自下而上收敛，"冰淇淋筒"是反模式 |
| 测试四象限 | JUnit 主战场是 Q1（技术导向/支持团队），好的单测可兼担 Q2 |
| TDD/BDD | TDD 是"红-绿-重构"循环；BDD 靠命名与 DSL 叠加在 JUnit 上 |
| 质量指标 | FIRST 原则；覆盖率是风险信号而非目标 |
| 反模式 | 过度模拟、测试相互依赖、Flaky Test、断言过弱、测试内写分支 |
| 不适用场景 | 真实 DB/网络行为、跨系统流程、框架装配——交给集成与 E2E 测试 |
