# 1. JUnit 定位与测试理念

JUnit 是 Java 生态中最常用的单元测试框架，核心价值是**用可重复、可自动化的方式验证最小业务单元的正确性**。在工程实践中，它是测试金字塔的底座，与集成测试、端到端测试形成互补。

## 1.1 JUnit 在测试体系中的位置

- **单元测试（Unit Test）**：聚焦最小业务单元（方法/类），快速、隔离、稳定。
- **集成测试（Integration Test）**：验证多个组件协作与外部依赖（DB、消息队列）。
- **端到端测试（E2E）**：从用户视角验证完整链路，成本高、速度慢。

**设计动机**：把“可重复验证”前置到研发过程，通过快速反馈降低缺陷成本。

## 1.2 单元测试的价值与边界

### 1.2.1 价值

- **回归保护**：改动后快速定位破坏性变更。
- **设计反馈**：难测试往往意味着设计耦合度过高。
- **文档作用**：测试即可执行的规格说明。
- **重构安全网**：行为可验证，重构更大胆。

### 1.2.2 边界

- 不适合验证外部系统稳定性（应由集成测试覆盖）。
- 不适合覆盖复杂流程的用户体验（应由 E2E 覆盖）。

## 1.3 测试金字塔与测试四象限

- **金字塔**：单元测试多、集成测试中、端到端少。
- **四象限**：
  - 技术导向/支持团队（单元、组件测试）
  - 业务导向/支持团队（契约测试、API 测试）
  - 业务导向/面向客户（E2E、探索测试）
  - 技术导向/面向客户（性能、安全测试）

**启示**：JUnit 关注“技术导向 + 支持团队”的象限，但设计良好的单元测试也能间接表达业务规则。

## 1.4 TDD/BDD 与 JUnit

- **TDD**：先写失败测试，再写实现，再重构。
- **BDD**：从行为/场景描述出发，强调可读性与规范。

JUnit 是 TDD 的核心工具之一，BDD 通常通过命名、断言组织和 DSL（如 AssertJ、Mockito）提升可读性。

## 1.5 测试质量指标与反模式

### 1.5.1 指标参考

- **稳定性**：不依赖随机数、时间、全局状态。
- **执行速度**：单测应在毫秒级或极短时间内完成。
- **可读性**：测试名即规格，结构清晰。
- **覆盖率**：覆盖率不是目标，但可以作为风险信号。

### 1.5.2 常见反模式

- **过度模拟**：测试变成“验证实现细节”。
- **测试相互依赖**：顺序不同导致结果不同。
- **超大测试类**：难维护、定位问题慢。
- **随机/时间依赖**：引入偶发失败（Flaky Test）。

# 2. 快速示例

## 2.1 JUnit 5 示例

```java
import org.junit.jupiter.api.Test;
import static org.junit.jupiter.api.Assertions.*;

class CalculatorTest {
    @Test
    void add_should_sum_two_numbers() {
        Calculator calculator = new Calculator();
        assertEquals(3, calculator.add(1, 2));
    }
}
```

## 2.2 JUnit 4 示例

```java
import org.junit.Test;
import static org.junit.Assert.*;

public class CalculatorTest {
    @Test
    public void add_should_sum_two_numbers() {
        Calculator calculator = new Calculator();
        assertEquals(3, calculator.add(1, 2));
    }
}
```

# 3. 什么时候不使用 JUnit

## 3.1 更适合使用集成/端到端测试的场景

- 数据库事务与连接池的行为验证
- 远程服务容错、超时、重试策略
- 跨进程、跨系统的业务流程

## 3.2 维护成本评估

当测试成本明显高于价值（例如高度不稳定的 UI 测试，或需求频繁变化且难以抽象为稳定规则），应考虑调整测试策略，而不是“为了覆盖率而写测试”。
