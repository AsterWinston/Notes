# 1. 什么是 RocketMQ

Apache RocketMQ 是一个**分布式消息和流处理平台**，以低延迟、高吞吐、高可靠著称。最初由阿里巴巴开发并用于支撑双11等大规模场景，2016年捐赠给 Apache 软件基金会并于2017年成为顶级项目。它的基因是**交易消息**：从阿里内部 MetaQ 演进而来，天生为"订单、库存、账务这类不允许丢、不允许乱、要能回查"的业务消息设计，这与 Kafka 诞生于日志管道、RabbitMQ 脱胎于金融报文路由的出身差异，直接决定三者的能力侧重。

## 1.1 发展历史

| 阶段 | 时间 | 里程碑 |
|------|------|--------|
| 起源 | 2011 | 阿里内部 MetaQ 1.0，用于交易核心链路 |
| 演进 | 2012-2014 | MetaQ 2.0 → RocketMQ 3.0，支持事务消息、顺序消息 |
| 开源 | 2016 | 进入 Apache 孵化器 |
| 毕业 | 2017.9 | 成为 Apache 顶级项目 |
| 5.0 | 2022 | RocketMQ 5.0 发布，架构重构，存算分离，支持 Pop 消费模式 |

**每次大版本的能力跃迁都有清晰的业务推手**：3.x 补齐事务/顺序消息对应集团交易场景；4.x 引入 DLedger（基于 Raft 的自动选主）解决主从人工运维之痛；5.x 的 Proxy 与存算分离则是面向云原生与 Serverless 的重写（详见第 4 节与 20/17 篇源码分析）。

## 1.2 核心特性

- **削峰填谷**：处理瞬时流量高峰，保护下游系统
- **解耦**：生产者和消费者独立演进
- **异步通信**：非阻塞、最终一致性
- **顺序消息**：全局有序和分区有序
- **事务消息**：分布式事务最终一致性
- **定时/延迟消息**：4.x 提供 18 个延迟级别（1s/5s/10s/30s/1m…2h），5.0 起 TimerMessage 支持任意精度定时
- **消息过滤**：Tag 过滤、SQL92 表达式过滤
- **消息重试与死信**：自动重试 + 死信队列兜底
- **高可用**：主从架构 + DLedger 自动选主
- **海量堆积**：基于磁盘存储，支持千亿级消息堆积

这份清单里最能体现"交易基因"的是后四项：**延迟级别、Tag/SQL92 过滤、重试+DLQ、事务回查，在 Kafka 里几乎都要业务方自己造轮子**。顺序性的口径也要记准：RocketMQ 的"顺序"是**分区有序**（同一 MessageQueue 内 FIFO，靠 MessageQueueSelector 把同业务键的路由固定到同一队列），全局有序只能靠单队列部署牺牲吞吐（详见 12_ordered-messages.md）。

> **注意**："海量堆积"不等于"随便堆"。消息默认保留 72h（fileReservedTime），到期即物理删除，堆积超期=消息丢失；消费端长期 lag 还会把读路径从 PageCache 命中拖成随机磁盘读，RT 雪崩。堆积是缓冲能力，不是存储方案。

## 1.3 适用场景

- 异步解耦（订单系统 → 积分系统）
- 流量削峰（秒杀 → 抢购请求缓冲）
- 数据分发（Binlog 同步 → 多下游消费）
- 日志处理（日志收集 → 实时分析）
- 分布式事务（订单+库存+余额一致性）

**阿里系场景是理解这些特性的最好样本**：双十一零点订单创建链路里，交易核心只做落库和发消息，积分、优惠券、物流通知全部异步消费，峰值消息洪峰由 Broker 磁盘缓冲吸收；订单超时关闭用延迟消息（下单时发 delayLevel 对应 30m 的延迟消息，到点由定时任务投递给关单服务）；跨行的"扣库存+加积分"一致性用事务消息的 half 消息 + 回查兜底。反例也要清楚：**日志/埋点这类可丢、超高吞吐、要接流计算生态的场景，Kafka 仍是更主流的选择**。

# 2. 架构与消息模型

## 2.1 四大角色

```text
              ┌─────────────────────┐
              │   NameServer 集群    │  无状态路由注册中心
              └──────┬──────▲───────┘
        注册/心跳(30s)│      │拉取路由(30s)
   ┌────────────────┘      └────────────────┐
   │                                        │
┌──▼───────┐   发送消息    ┌──────────┐   拉取消费  ┌──────────┐
│ Producer │ ───────────→ │  Broker  │ ←───────── │ Consumer │
└──────────┘              │ (M/S集群) │            └──────────┘
                          ├──────────┤
                          │ CommitLog│  消息物理存储（顺序写）
                          │ConsumeQ  │  逻辑分发（消费条目）
                          │ IndexFile│  消息检索
                          └──────────┘
```

| 角色 | 职责 | 集群方式 | 有无状态 |
|------|------|----------|----------|
| **NameServer** | 路由注册与发现、Broker 心跳管理 | 无状态集群（节点间互不通信） | 无 |
| **Broker** | 消息存储、投递、主从复制 | 主从/多副本（DLedger） | 有 |
| **Producer** | 消息生产、发送到 Broker | 无状态 | 无 |
| **Consumer** | 消息消费、偏移量管理 | 集群/广播消费 | 消费进度有状态 |

**NameServer 的极简设计是 RocketMQ 与 Kafka（ZooKeeper/KRaft）最大的架构分野**：节点之间不通信、不选主，仅维护"30 秒心跳存活"的最终一致路由表，AP 取向换取了组件自身的几乎免运维；路由正确性责任下放到 Broker（主动全量注册）与客户端（30s 刷新 + 发送失败重拉），机制细节见 6_nameserver.md 与 21_nameserver-source.md。

## 2.2 消息模型：Topic / Tag / Queue

- **Topic**：消息一级分类，逻辑概念；一个 Topic 的路由由分布在各 Broker 上的若干 MessageQueue 组成
- **Tag**：二级分类，一条消息只能有一个 Tag；Broker 端先按 Queue 粗筛、Consumer 拉取后按 Tag 精过滤，订阅表达式 `tagA || tagB`
- **MessageQueue**：物理分区，最小存储与消费单元，默认写 8 队列；MessageQueue = BrokerName + queueId
- **ConsumerGroup**：同组实例分摊队列（集群模式，一条消息组内只消费一次）或全量消费（广播模式）

```text
Topic: order_topic
├── broker-a: Queue-0..3   （写队列 4 个）
└── broker-b: Queue-0..3
ConsumerGroup: order-service（3 实例，Rebalance 后各领若干 Queue）
```

**队列数是吞吐与顺序性的调节旋钮**：加队列提升并行度，但顺序消息的业务键路由（hash(orderId) % queueNums）在扩缩队列时会打破既有映射，需要停写扩队列的运维动作。堆积能力的口径也要拿准：CommitLog 全 Topic 混写 + 顺序写磁盘，使 RocketMQ 敢宣称"单机十万级 TPS、万亿级堆积"，代价是单条消息的读取要绕一层 ConsumeQueue 索引（存储设计见 8_message-storage-design.md）。

# 3. 主流消息中间件对比

| 维度 | RocketMQ | Kafka | RabbitMQ | Pulsar |
|------|----------|-------|----------|--------|
| 架构 | 注册中心 + Broker 主从 | 分区多副本 + ZooKeeper/KRaft | AMQP Broker | 存算分离 BookKeeper |
| 吞吐量 | 十万级 TPS | 百万级 TPS | 万级 TPS | 十万级 TPS |
| 延迟 | 毫秒级 | 毫秒级 | 微秒级 | 毫秒级 |
| 事务消息 | 原生支持（half+回查） | 支持（0.11+，偏EOS语义） | 不支持 | 原生支持（4.0+） |
| 顺序消息 | 支持（分区有序） | 分区内有序 | 不支持（竞争消费乱序） | 支持 |
| 延迟消息 | 18个级别；5.0任意定时 | 不支持（需外部实现） | 插件支持（延迟交换机） | 支持 |
| 消息过滤 | Tag/SQL92（Broker端） | 不支持（消费端过滤） | 路由键+死信（Broker端） | 支持 |
| 消息重试 | 支持（阶梯延迟+DLQ） | 不支持（需手动） | 支持 | 支持 |
| 社区/生态 | Apache，国内活跃 | Apache，全球最大 | VMware，成熟 | Apache，增长快 |
| 主要场景 | 电商/金融/物流 | 大数据/日志/流处理 | 通用消息路由 | 云原生/多租户 |

对比表之外补三个容易误判的点：**其一，Kafka 的"事务"与 RocketMQ 的"事务消息"不是一回事**——前者是 producer 端 exactly-once 写入 + EOS 流处理语义，不提供业务侧"本地事务与发消息二选一"的半消息回查模型；后者解决的是分布式事务最终一致，这是 RocketMQ 独有杀手锏（机制见 11_transaction-messages.md）。**其二，RabbitMQ 的万级 TPS 是单机队列模型的结果**，它的 routing key + 交换机在"复杂路由拓扑"场景仍无可替代，别拿吞吐一个维度判死。**其三，Pulsar 的存算分离架构最优雅**，但 BookKeeper 运维复杂度劝退了相当一部分中小团队。

## 3.1 选择建议与选型判断

- **高吞吐 + 流处理**：Kafka
- **事务/顺序/延迟 + 电商金融**：RocketMQ
- **复杂路由 + 轻量消息**：RabbitMQ
- **存算分离 + 多租户**：Pulsar

**选型判断按四问走**：① 消息会不会丢、能不能丢？日志可丢选 Kafka，交易不可丢进候选 RocketMQ；② 要不要"发半条"的事务语义或超时延迟？需要就基本锁定 RocketMQ（自研补齐的成本远高于引入）；③ 团队栈在哪？Java/阿里系生态 RocketMQ 文档与人才储备厚，已有 Flink/Spark 流处理管道则 Kafka 连接器最成熟；④ 谁来运维？Kafka/RocketMQ 单集群都能扛，Pulsar 的多组件（Broker+BookKeeper+无ZK或ZK）运维门槛最高。**多数国内业务团队的现实结论是：业务消息用 RocketMQ，日志与数据管道用 Kafka，两者并存而非互斥。**

**设计考量**：

- **吞吐与特性成反比**：Kafka 的百万级 TPS 靠批量+零拷贝+分区顺序写换得，但事务/延迟/过滤等语义要靠外部组件补；RocketMQ 交易特性全，单集群规模上限通常更低。
- **同业务键的顺序诉求优先用消息键路由解决**，不要用"全局单队列"硬保序——那是拿并行度换心理安慰。
- **已有 Spring Cloud/阿里系中台栈的团队**，RocketMQ 与 Sentinel/Nacos/SkyWalking 的联动与文档成本最低，这条隐性收益在选型评分里往往超过一个特性开关。

# 4. RocketMQ 5.x 演进

## 4.1 架构变化

```text
RocketMQ 4.x:  Producer → NameServer → Broker(M/S) → Consumer
RocketMQ 5.x:  Producer → Proxy → NameServer → Broker → Consumer
                              ↓
                         gRPC 协议
```

- **Proxy 组件**：解耦协议层与内核，支持 gRPC/HTTP/Remoting
- **存算分离**：Broker 拆分为逻辑计算层 + 物理存储层
- **Pop 消费模式**：Broker 代理拉取，降低 Consumer 逻辑复杂度
- **轻量级 SDK**：多语言 SDK 通过 Proxy 接入

## 4.2 关键改进

| 特性 | 4.x | 5.x |
|------|-----|-----|
| 协议层 | 自定义 Remoting | gRPC + Proxy |
| 消费模式 | Push/Pull（重平衡在客户端） | 新增 Pop 模式（队列不再绑定客户端） |
| 重平衡 | Client 端 | 可迁移至 Proxy |
| 多语言 | Java SDK | 各语言轻量 SDK |
| 存储 | 本地文件 | 支持对象存储扩展 |
| 定时消息 | 18 固定级别 | TimerMessage 任意时间 |

**5.x 的主线是"把复杂度从胖客户端抽到 Proxy"**：4.x 时代每个语言的 SDK 都要自己实现重平衡、位点管理、失败重试，多语言生态一直薄弱；Pop 模式下 Broker 托管消费队列与不可见时间（类似 SQS 的 visibility timeout），客户端瘦身为"收消息、ACK"，Serverless 场景（函数计算触发器、浏览器端 HTTP 收发）才真正可行。**冷热分层与对象存储归档**让"堆积 72h"的默认保留策略扩展到 TB~PB 级低成本长期保留。

> **设计争议**：5.x 引入 Proxy 也带来质疑——多一跳网络增加延迟与运维组件，存算分离对接对象存储的尾延迟能否满足交易场景，社区至今在实践中磨合。判断口径：**存量 4.x 集群没有多语言/Serverless 需求就不要为升级而升级**；新建云原生集群按 5.x 起步。国内生产大盘仍以 4.8/4.9 + 少量 5.x 灰度并存，选型时以团队云厂商托管版（阿里云消息队列 5.0 系列）实际支持的版本为准。

# 6. 小结

- **RocketMQ 的基因是交易消息**：事务消息（half+回查）、阶梯延迟、Tag/SQL92 过滤、重试+DLQ 四大能力为电商金融而生，这是它与日志出身的 Kafka、路由出身的 RabbitMQ 的本质分野。
- **架构上 NameServer 走极简 AP**，Broker 用 CommitLog 混写换吞吐与堆积，Topic/Tag/Queue/ConsumerGroup 四级模型中队列数是并行度与顺序性的共同旋钮。
- **选型四问**：可丢性、事务/延迟语义、团队生态、运维成本；国内常态是 RocketMQ（业务）与 Kafka（日志管道）并存。
- **5.x 用 Proxy + Pop + 存算分离换取云原生与多语言**，但升级收益要与延迟、运维复杂度权衡，存量集群不为升级而升级。
