绝大多数后端问题最终都能落到 TCP 上：接口偶发超时、连接数暴涨、大量 `CLOSE_WAIT`、吞吐上不去，追下去往往不是业务代码写错了，而是对这条连接在协议层发生了什么一无所知。本篇先把 TCP 的位置、它承诺了什么、握手挥手怎么走、窗口和拥塞控制如何工作讲清楚，为后面用 Java 写 Socket、NIO 和调优打底。

# 1. TCP 的定位

## 1.1 协议栈中的位置

TCP（Transmission Control Protocol，传输控制协议）工作在 TCP/IP 四层模型的**传输层**。它不关心上层传的是 HTTP 报文、MySQL 查询还是自定义二进制协议，只负责把一段连续的字节可靠地从一端送到另一端。

```text
┌─────────────────────────────────────────┐
│ 应用层   HTTP / WebSocket / MySQL / 自定义协议 │
├─────────────────────────────────────────┤
│ 传输层   TCP（可靠字节流）/ UDP（不可靠报文）   │
├─────────────────────────────────────────┤
│ 网络层   IP（寻址与路由，尽力而为）            │
├─────────────────────────────────────────┤
│ 链路层   以太网 / Wi-Fi / 物理介质            │
└─────────────────────────────────────────┘
```

IP 层只保证"尽力而为"：报文可能丢失、重复、乱序、迟到。TCP 在这一层不可靠的土壤上，用确认、重传、排序、去重这些机制，向上伪装成一条**可靠的字节流**。

## 1.2 TCP 提供什么保证

理解 TCP 的承诺范围，比记住它的机制更重要。它保证四件事：

- **面向连接**：通信前必须先握手建立连接，双方各自维护一套状态。
- **可靠传输**：数据不丢失、不重复、按序到达，出错会重传。
- **字节流**：没有消息边界，上层看到的是一条连续的字节河。
- **全双工**：两个方向互不干扰，可以同时收发。

它**不保证**的事情同样关键：

| 不保证的 | 后果 | 由谁弥补 |
|----------|------|----------|
| 消息边界 | 可能出现粘包、拆包 | 应用层协议（长度字段、分隔符） |
| 实时性 | 数据可能在内核缓冲区里等待 | 关闭 Nagle、调小缓冲区、改用 UDP |
| 送达确认到应用 | 收到 ACK 只代表内核收下了 | 应用层 ACK 或业务幂等 |
| 连接活性 | 对端进程崩溃后连接可能长时间"假活" | 心跳 + 空闲检测 |

**设计考量**：TCP 把自己定位成"可靠的字节管道"，把消息语义留给应用层。这个分层让 HTTP、Redis 协议、Dubbo 协议可以各自定义边界规则，但也意味着任何做长连接的系统都必须自己解决粘包和心跳这两个问题——后面第 4、5 篇就专门处理它们。

## 1.3 TCP 与 UDP、HTTP 的关系

UDP 是传输层的另一条路线：无连接、不保证可靠、保留报文边界。两者不是"新旧"关系，而是不同取舍。

| 维度 | TCP | UDP |
|------|-----|-----|
| 连接 | 需要握手 | 无连接 |
| 可靠性 | 确认 + 重传 | 不保证 |
| 数据形态 | 字节流 | 数据报，保留边界 |
| 有序性 | 保证 | 不保证 |
| 头部开销 | 20 字节起 | 8 字节 |
| 拥塞控制 | 有，会主动降速 | 无，应用自己控制 |
| 典型应用 | HTTP/1.1、HTTP/2、MySQL、Redis | DNS、音视频、游戏、HTTP/3（QUIC） |

HTTP 与 TCP 是"使用者"与"被使用者"的关系，而不是并列关系：

```text
HTTP/1.1  ── 一条 TCP 连接上串行处理请求（可 Keep-Alive 复用）
HTTP/2    ── 一条 TCP 连接上多路复用多个流
HTTP/3    ── 跑在 QUIC 之上，QUIC 又跑在 UDP 之上
```

**注意**：HTTP/2 解决了应用层的队头阻塞，但底层仍是 TCP。一旦发生丢包，TCP 要等重传完成才向上交付后续数据，所有复用的流都会被卡住。HTTP/3 改用 UDP 上的 QUIC，正是为了绕开这个传输层队头阻塞。

# 2. 三次握手

## 2.1 报文与状态变迁

建立连接需要交换三个报文，同时同步双方的初始序列号（ISN）。序列号是后续所有确认和重传的基准。

```text
客户端                                    服务端
  │                                          │
  │  CLOSED            LISTEN                │
  │                                          │
  │ ───── SYN, seq=x ──────────────────────> │  SYN_RCVD
  │  SYN_SENT                                │
  │                                          │
  │ <─── SYN+ACK, seq=y, ack=x+1 ─────────── │
  │                                          │
  │ ───── ACK, ack=y+1 ────────────────────> │  ESTABLISHED
  │  ESTABLISHED                             │
  │                                          │
  │            连接建立，可以收发数据            │
```

三个报文各自的作用：

- **第一次 SYN**：客户端说"我想建连接，我的起始序列号是 x"。
- **第二次 SYN+ACK**：服务端说"收到了，我的起始序列号是 y，期待你下一个字节是 x+1"。
- **第三次 ACK**：客户端说"收到你的 y 了，期待 y+1"。这一次确认让服务端确信客户端具备接收能力。

`seq` 和 `ack` 都是 32 位无符号数，超过 `2^32-1` 后回绕。初始序列号并不是从 0 开始，而是基于时钟等因素随机生成，防止旧连接的报文被新连接误认。

## 2.2 为什么不是两次或四次

**两次不够**。如果只有 SYN 和 SYN+ACK，服务端无法确认客户端收到了自己的 SYN+ACK。更危险的是网络里滞留的旧 SYN 可能让服务端单方面建立一个"僵尸连接"，白白占用资源。第三次 ACK 补齐了"客户端 → 服务端"这个方向的确认。

**四次不必要**。第二次报文把 SYN 和 ACK 合并发送，是因为服务端此时既有确认要发、又有自己的 SYN 要发，合并不会损失任何语义。

> **行业实践**：攻击者常利用"只发 SYN 不回 ACK"的方式耗尽服务端的半连接队列，这就是 SYN Flood。防御手段包括 `tcp_syncookies`、增大 `somaxconn` 与 `tcp_max_syn_backlog`，以及在上游设备做清洗。

## 2.3 半连接队列与全连接队列

握手过程涉及内核里的两个队列，很多"连接建立慢"或"客户端超时但服务端没日志"的问题都出在这里：

```text
        收到 SYN
           │
           ▼
   ┌───────────────┐   收到第三次 ACK    ┌───────────────┐
   │  半连接队列    │ ──────────────────> │  全连接队列    │
   │ (SYN queue)   │                     │ (accept queue)│
   └───────────────┘                     └───────┬───────┘
                                                 │ accept()
                                                 ▼
                                            应用进程
```

- **半连接队列**：收到 SYN、尚未完成握手的连接，由 `tcp_max_syn_backlog` 控制。
- **全连接队列**：已完成握手、等待应用 `accept()` 的连接，长度由 `listen(fd, backlog)` 与 `somaxconn` 中较小者决定。

**注意**：如果应用 `accept()` 太慢，全连接队列会满，新完成的握手被丢弃，客户端表现为"连接超时"，而服务端业务日志里什么都看不到。排查时可以看 `ss -lnt` 输出里监听 socket 的 `Send-Q`（当前全连接队列上限）和 `Recv-Q`（当前排队数）。

# 3. 四次挥手与 TIME_WAIT

## 3.1 挥手过程

TCP 是全双工的，两个方向要各自关闭，所以需要四次挥手。

```text
主动关闭方                                被动关闭方
  │  ESTABLISHED       ESTABLISHED          │
  │                                         │
  │ ───── FIN, seq=u ─────────────────────> │  CLOSE_WAIT
  │  FIN_WAIT_1                             │
  │                                         │
  │ <──── ACK, ack=u+1 ──────────────────── │
  │  FIN_WAIT_2                             │
  │                                         │  （应用还可继续发数据）
  │ <──── FIN, seq=w ────────────────────── │  LAST_ACK
  │                                         │
  │ ───── ACK, ack=w+1 ───────────────────> │  CLOSED
  │  TIME_WAIT                              │
  │  （等待 2MSL 后 CLOSED）                  │
```

关键状态：

| 状态 | 出现在哪一方 | 含义 |
|------|--------------|------|
| `FIN_WAIT_1` | 主动关闭方 | 已发 FIN，等对方 ACK |
| `FIN_WAIT_2` | 主动关闭方 | 已收到 ACK，等对方 FIN |
| `CLOSE_WAIT` | 被动关闭方 | 收到 FIN，等本地应用调用 `close()` |
| `LAST_ACK` | 被动关闭方 | 已发 FIN，等最后 ACK |
| `TIME_WAIT` | 主动关闭方 | 等 2MSL，确保最后 ACK 送达并清除旧报文 |

## 3.2 TIME_WAIT 为什么存在

`TIME_WAIT` 常被误认为"浪费资源"，但它有两个不可替代的作用：

- **保证最后一个 ACK 能到达**：如果这个 ACK 丢了，对端会重发 FIN，此时主动关闭方还处于 `TIME_WAIT`，可以重发 ACK。若直接进入 `CLOSED`，对端会收到 RST。
- **让旧连接的残余报文消亡**：等待 2MSL（Maximum Segment Lifetime，报文最大生存时间，Linux 上通常按 60 秒计）后，旧连接两个方向上滞留的报文都已过期，不会串到复用了同一四元组的新连接里。

**设计考量**：缩短 `TIME_WAIT` 看似能腾出端口，但代价是可能让旧报文污染新连接，表现为"新连接刚建立就收到莫名其妙的数据"。所以 RFC 建议等待 2MSL，而不是能省则省。

## 3.3 大量 TIME_WAIT 与 CLOSE_WAIT

两个状态经常被混淆，处理方向完全不同：

| 现象 | 原因 | 处理方向 |
|------|------|----------|
| 主动关闭方大量 `TIME_WAIT` | 短连接过多，或主动关闭频繁 | 改用连接池/长连接；必要时开 `tcp_tw_reuse` |
| 被动关闭方大量 `CLOSE_WAIT` | 应用收到 FIN 后没调用 `close()` | 修代码，检查连接泄漏 |
| `TIME_WAIT` 占满本地端口 | 四元组空间被耗尽 | 扩大端口范围、复用连接、增加目标 IP |
| 连接刚建立就被重置 | 旧报文串扰或对端进程已退出 | 检查 `TIME_WAIT` 设置与对端状态 |

> **行业实践**：调 `tcp_tw_reuse=1` 只对**主动发起连接**的一方有效，且依赖时间戳；`tcp_tw_recycle` 在 NAT 环境下会导致连接异常，新内核已移除，不要再使用。根治 `TIME_WAIT` 的正确姿势永远是连接复用，而不是调内核参数。

`CLOSE_WAIT` 堆积几乎一定是代码 bug：

```java
// 错误示范：收到 EOF 后既不关闭也不复用，连接永远停在 CLOSE_WAIT
Socket socket = serverSocket.accept();
InputStream in = socket.getInputStream();
int b;
while ((b = in.read()) != -1) {
    // 只处理数据，对端关闭后 read 返回 -1，循环退出，
    // 但 socket 没有 close，句柄和连接泄漏
}
// 正确做法：循环结束后必须在 finally 或 try-with-resources 中关闭
```

# 4. 可靠传输的机制

## 4.1 序列号、确认与累计确认

TCP 把字节流按字节编号。接收方通过 `ack` 字段告诉发送方"我已经连续收到这个序号之前的所有字节"。这种**累计确认**意味着一个 ACK 可以确认多段数据，也意味着一旦中间丢了一段，后面的数据即使到达也只能先缓存。

发送端的每个字节在逻辑上处于四种状态之一：

```text
已发送并确认 │ 已发送未确认 │ 可发送未发送 │ 不可发送
             └──── 发送窗口 ────┘
```

## 4.2 超时重传与快速重传

发送方为已发送未确认的数据启动定时器（RTO，Retransmission Timeout）。超时未收到 ACK 就重传。RTO 是动态估算的，依据往返时间 RTT 的平滑值和抖动。

**快速重传**是另一条路径：如果发送方连续收到三个针对同一序号的重复 ACK（说明后面的包到了、中间那个丢了），就不等超时直接重传丢失的那段。

```text
发送方                     接收方
  │ ── seg 1 ─────────────> │ 收到，ACK 2
  │ ── seg 2 ────────X      │ （丢失）
  │ ── seg 3 ─────────────> │ 收到，仍 ACK 2（重复 ACK 1）
  │ ── seg 4 ─────────────> │ 收到，仍 ACK 2（重复 ACK 2）
  │ ── seg 5 ─────────────> │ 收到，仍 ACK 2（重复 ACK 3）
  │ <── 三个重复 ACK，立即重传 seg 2 ──
```

SACK（Selective Acknowledgment，选择性确认）进一步让接收方告诉发送方"我收到了哪些不连续区间"，避免一次丢包导致整段重传。

# 5. 滑动窗口与流量控制

## 5.1 发送窗口与接收窗口

如果每发一个包都要等 ACK，吞吐会被 RTT 死死限制。滑动窗口允许发送方在未收到确认前连续发送一批数据。

接收方在每个 ACK 里携带 `window` 字段，表示自己还能接收多少字节，这就是**流量控制**——防止发送方发得太快把接收方缓冲区撑爆。

```text
发送方维护的窗口 = min(拥塞窗口 cwnd, 接收方通告窗口 rwnd)

┌───────────────────────────────────────────────┐
│ 已确认 │ 已发送未确认 │ 可发送 │ 不可发送        │
└───────────────────────────────────────────────┘
         ← 窗口右移，新的字节进入可发送区 →
```

窗口大小直接决定**带宽时延积**能覆盖多少数据。一条 RTT 为 40ms、带宽 100Mbps 的链路，若窗口只有 64KB，理论吞吐会被压到约 13Mbps。

## 5.2 零窗口与坚持定时器

当接收方缓冲区满，会通告 `window=0`。发送方暂停发送，并启动**坚持定时器（persist timer）**定期发送零窗口探测，询问"现在能收了吗"。否则一旦对方后续的窗口更新报文丢失，双方会永久僵死。

**注意**：应用层读取太慢（比如业务线程被阻塞）会让接收缓冲区一直满，表现为对端发送卡住。这时抓包会看到 `window=0` 和周期性探测，问题不在网络，而在消费速度。

# 6. 拥塞控制

流量控制关心"接收方能不能收"，拥塞控制关心"网络能不能承受"。发送方维护一个**拥塞窗口 cwnd**，实际发送量取 cwnd 与 rwnd 的较小值。

## 6.1 慢启动与拥塞避免

```text
cwnd
 │                        ╱ 拥塞避免（线性增长）
 │                      ╱
 │                    ╱
 │              ┌───╱  达到 ssthresh
 │        ╱╲    │
 │     ╱    ╲   │ 丢包 → cwnd 减半，ssthresh 下调
 │  ╱        ╲__│
 └──────────────────────────────> 时间
   慢启动（指数增长）
```

- **慢启动**：cwnd 从很小开始，每收到一个 ACK 就加一个 MSS，效果是指数增长。
- **拥塞避免**：cwnd 超过慢启动阈值 ssthresh 后，每个 RTT 只增加一个 MSS，改为线性增长。
- **拥塞事件**：超时通常意味着严重拥塞，cwnd 降到 1 重新慢启动；三个重复 ACK 意味着轻度拥塞，走快速恢复，cwnd 减半后继续。

## 6.2 快速恢复与现代算法

快速恢复的思路是：既然还能收到重复 ACK，说明网络没完全瘫痪，不必退回慢启动从 1 开始，直接减半继续发送即可。

不同内核版本的默认算法不同：

| 算法 | 特点 | 适用 |
|------|------|------|
| Reno | 丢包即减半，经典实现 | 教学、老系统 |
| CUBIC | 以时间为轴的三次函数增长，高带宽长距表现好 | Linux 默认 |
| BBR | 基于带宽和 RTT 建模，不把丢包当拥塞信号 | 跨国、弱网、高丢包链路 |

> **行业实践**：跨境传输或卫星链路常用 BBR。它不依赖丢包判断拥塞，在有随机丢包的链路上吞吐明显优于 CUBIC。但 BBR 对缓冲区公平性有争议，多流竞争时可能挤占 CUBIC 流，需结合业务评估。

# 7. 常见错误

| 错误认知 | 实际问题 | 正确理解 |
|----------|----------|----------|
| "TCP 会保证消息完整到达应用" | 内核收到 ≠ 应用处理完 | 需要应用层 ACK 与幂等 |
| "TIME_WAIT 是垃圾，越少越好" | 缩短后旧报文串扰 | 优先复用连接，谨慎调参 |
| "`CLOSE_WAIT` 多要调内核" | 是应用没关连接 | 修代码，查泄漏 |
| "握手完成就能发数据" | 全连接队列满时握手结果被丢 | 关注 `accept()` 速度与 backlog |
| "窗口越大越快" | 窗口受 cwnd 与 rwnd 双重限制 | 结合带宽时延积计算 |
| "调大 `SO_RCVBUF` 一定提速" | 缓冲区过大增加延迟 | 按带宽时延积设置，不是越大越好 |

# 8. 自检与练习

**练习一**：用 `ss -tan state time-wait | wc -l` 统计本机 `TIME_WAIT` 数量，连续观察一分钟，判断是稳定值还是持续增长。持续增长说明短连接比例过高。

**练习二**：访问一个远端服务，用 `ss -tin` 查看该连接的 `cwnd`、`rtt`、`retrans` 等字段，解释为什么在高延迟链路上单连接吞吐上不去。

**练习三**：写一个只 `accept()` 不读取、也不关闭的小服务端，用客户端压测，观察服务端 `CLOSE_WAIT` 与客户端 `TIME_WAIT` 分别涨在哪里，说明原因。

# 9. 小结

| 主题 | 记住这一句 |
|------|-----------|
| 定位 | TCP 是在不可靠 IP 之上包装出来的可靠字节流 |
| 三次握手 | 同步双方序列号并确认双向收发能力 |
| 四次挥手 | 全双工两个方向各自关闭 |
| TIME_WAIT | 保证最后 ACK 送达并清除旧报文，不是浪费 |
| 滑动窗口 | 窗口 = min(cwnd, rwnd)，决定单连接吞吐上限 |
| 拥塞控制 | 慢启动指数增长，拥塞后减半，算法可选 CUBIC/BBR |

协议层的机制决定了后面所有工程实践的上限：为什么长连接要心跳、为什么粘包必须由应用层解决、为什么调优要先看 RTT 和窗口。下一篇进入 Java 代码，从 `Socket` 与 `ServerSocket` 开始，把这条连接真正建立起来。
