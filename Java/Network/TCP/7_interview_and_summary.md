前六篇分别讲了协议、Socket、NIO、粘包、心跳和调优，但它们在生产里从不孤立出现：一次"接口偶发超时"可能同时牵涉窗口、重传、线程池和心跳。本篇先把知识串成一张地图，再用自检题检验掌握程度，最后给出抓包排错手法和生产检查清单，作为整个 TCP 模块的收口。

# 1. 知识地图

## 1.1 分层视角

TCP 的问题可以按"协议层、内核层、应用层、工程层"四层理解，排错时顺着层往下找，比凭直觉猜快得多。

```text
┌─────────────────────────────────────────────────────┐
│ 工程层  连接池 / 心跳 / 重连 / 背压 / 限流              │
├─────────────────────────────────────────────────────┤
│ 应用层  消息边界 / 编解码 / 线程模型 / 缓冲区            │
├─────────────────────────────────────────────────────┤
│ 内核层  全连接队列 / 收发缓冲 / 拥塞窗口 / 重传           │
├─────────────────────────────────────────────────────┤
│ 协议层  三次握手 / 四次挥手 / 滑动窗口 / TIME_WAIT       │
└─────────────────────────────────────────────────────┘
```

| 层 | 出问题时典型症状 | 主要排查工具 |
|----|------------------|--------------|
| 协议层 | 连接建立慢、大量 TIME_WAIT | `ss`、`tcpdump` |
| 内核层 | 重传高、窗口为 0、accept 队列溢出 | `netstat -s`、`ss -tin` |
| 应用层 | 粘包、乱码、线程被占满 | 日志、线程栈、`jstack` |
| 工程层 | 断线不重连、重连风暴、内存涨 | 监控、压测、应用指标 |

## 1.2 七篇的串联

| 篇目 | 解决的问题 | 留下的问题 |
|------|------------|------------|
| 1. 协议总览 | 连接如何建立、数据如何可靠传输 | 怎么用代码建立连接 |
| 2. Socket 基础 | 阻塞式收发与关闭 | 一条连接一个线程撑不住 |
| 3. NIO 与 Selector | 少量线程管大量连接 | 字节流没有消息边界 |
| 4. 粘包与拆包 | 三种划界协议与解码器 | 连接"假活"怎么办 |
| 5. 心跳与重连 | 空闲检测、退避、会话恢复 | 吞吐和延迟怎么优化 |
| 6. 性能调优 | 参数、线程、背压、零拷贝 | 如何系统排查与验收 |
| 7. 本篇 | 地图、自检、抓包、清单 | —— |

**设计考量**：这个顺序不是知识点罗列，而是"写一个能上线的长连接服务"的真实路径：先懂协议，再写阻塞版，发现扩展性问题换 NIO，换完发现边界问题，解决边界后发现连接假活，最后才谈性能。跳着学容易记住 API，却拼不出完整链路。

# 2. 高频自检题

## 2.1 握手与挥手

**Q：为什么握手是三次而不是两次？**

答：两次只能让客户端确认服务端能收能发，服务端无法确认客户端收到了自己的 SYN+ACK，也无法确认客户端的接收能力。第三次 ACK 补齐了"服务端 → 客户端"这个方向的确认，同时避免网络中滞留的旧 SYN 让服务端建立无效连接。

**Q：TIME_WAIT 的作用是什么？可以调小吗？**

答：两个作用，一是保证主动关闭方最后一个 ACK 能重发（对端重传 FIN 时还能响应），二是等待 2MSL 让旧连接的残余报文过期，避免污染复用同一四元组的新连接。不建议调小；大量 TIME_WAIT 的正解是连接复用，必要时用 `tcp_tw_reuse` 缓解。

**Q：CLOSE_WAIT 很多说明什么？**

答：说明被动关闭方收到了 FIN，但本地应用没有调用 `close()`。这是代码问题，通常是连接泄漏或异常路径漏关，调内核参数没有用。

**Q：SYN Flood 打的是哪个队列？**

答：主要打半连接队列（`tcp_max_syn_backlog`），攻击者发大量 SYN 但不回第三次 ACK。防御手段有 `tcp_syncookies`、增大队列、上游清洗。

## 2.2 可靠性与窗口

**Q：TCP 如何保证可靠？**

答：序列号 + 确认 + 超时重传 + 快速重传 + 校验和 + 去重排序。接收方用累计确认告知连续收到的位置，发送方用 RTO 或三个重复 ACK 触发重传，SACK 可以只重传真正丢失的区间。

**Q：滑动窗口和拥塞窗口有什么区别？**

答：滑动窗口（接收窗口 rwnd）是接收方通告的"我还能收多少"，属于流量控制，防止压垮接收方；拥塞窗口 cwnd 是发送方根据网络状况估算的"网络还能承受多少"，属于拥塞控制。实际发送量取两者较小值。

**Q：高 RTT 链路上单连接吞吐上不去，为什么？**

答：吞吐受窗口限制，`吞吐 ≈ 窗口 / RTT`。RTT 大而窗口小时，管道填不满。需要增大窗口（或启用窗口缩放）到带宽时延积，或者用多连接并行。

## 2.3 I/O 模型与粘包

**Q：BIO、NIO、AIO 的核心区别？**

答：BIO 在 accept/read/write 上阻塞，一连接一线程；NIO 用 Selector 多路复用，读写非阻塞，少量线程管大量连接；AIO 把读写也交给内核异步完成，通过回调通知。Java 生态主流是 NIO，Netty 也基于它。

**Q：粘包是 TCP 的缺陷吗？**

答：不是。TCP 是字节流，本来就不定义消息边界。所谓粘包拆包，是应用层协议没有定义边界。解决办法是定长、分隔符或长度字段，其中长度字段最适合二进制协议。

**Q：ByteBuffer 的 flip、clear、compact 分别做什么？**

答：`flip` 把 limit 设为 position、position 归零，切到读模式；`clear` 重置 position 和 limit 到初始状态，丢弃全部内容；`compact` 把未读数据移到开头，position 指向剩余长度，适合半包场景保留残片。

**Q：为什么长度字段必须按字节算？**

答：TCP 传输的单位是字节，字符数取决于编码。一个中文字符在 UTF-8 下是 3 字节，按字符数写长度会导致接收端少读或多读，后续全部错位。

## 2.4 长连接与调优

**Q：TCP keepalive 能替代应用层心跳吗？**

答：不能。内核默认 2 小时才开始探测，且只能判断链路是否通，无法判断对端业务进程是否健康。应用层心跳可以秒级检测、携带状态、跨中间设备。

**Q：断线重连为什么要指数退避加抖动？**

答：固定间隔在服务端故障期间会持续施压，恢复瞬间大量客户端同时重连形成惊群。指数退避让压力随失败次数衰减，抖动把重连时间打散，避免同步。

**Q：Nagle 和延迟 ACK 为什么会叠加出约 40ms 延迟？**

答：Nagle 要等前一个包的 ACK 才发下一个小包，接收方的延迟 ACK 又要等最多 40ms 才回。两者互相等待，形成"谁都不先动"的僵局。延迟敏感场景应关闭 Nagle。

**Q：背压是什么？没有背压会怎样？**

答：背压是让下游的处理速度反向传导给上游，使生产者降速。没有背压时，中间队列会无限增长直到 OOM，或者丢数据而不被感知。

# 3. 抓包与排错

## 3.1 ss 与 netstat

`ss` 是现代 Linux 推荐的连接查看工具，比 `netstat` 快得多，因为直接读内核。

```bash
# 所有 TCP 连接及状态
ss -tan

# 只看监听端口，Recv-Q 是当前排队，Send-Q 是 backlog 上限
ss -lnt

# 查看某条连接的详细 TCP 信息：cwnd、rtt、重传、窗口
ss -tin dst 10.0.0.5

# 按状态统计
ss -s
```

`ss -tin` 的关键字段：

| 字段 | 含义 | 异常信号 |
|------|------|----------|
| `cwnd` | 拥塞窗口 | 长期很小说明拥塞或丢包 |
| `rtt` | 往返时间 | 波动大说明链路不稳 |
| `retrans` | 重传次数 | 持续增长说明丢包 |
| `rcv_space` | 接收缓冲剩余空间 | 长期为 0 说明消费慢 |
| `snd_wnd` | 对端通告的发送窗口 | 长期为 0 说明对端不收 |

```bash
# netstat 仍可用于全局统计（ss 不提供）
netstat -s | grep -iE "retrans|listen|overflow|reset"
```

## 3.2 tcpdump

`tcpdump` 抓的是链路层以上的报文，是定位协议层问题最直接的证据。

```bash
# 抓某端口的所有流量，写文件供 Wireshark 分析
tcpdump -i eth0 -nn -s 0 port 9000 -w tcp.pcap

# 只看握手与挥手（SYN/FIN/RST）
tcpdump -i eth0 -nn 'tcp[tcpflags] & (tcp-syn|tcp-fin|tcp-rst) != 0'

# 抓某客户端与服务端的往返
tcpdump -i eth0 -nn host 10.0.0.5 and port 9000
```

常用过滤器：

| 过滤表达式 | 作用 |
|------------|------|
| `host 10.0.0.5` | 指定主机 |
| `port 9000` | 指定端口 |
| `tcp[tcpflags] & tcp-syn != 0` | 只抓 SYN |
| `tcp[tcpflags] & tcp-rst != 0` | 只抓 RST |
| `greater 1000` | 包长大于 1000 字节 |

**注意**：生产环境抓包要限制时长和文件大小（`-c`、`-W`、`-G`），否则在高流量网卡上几分钟就能写出几十 GB。抓包本身也有性能开销，尽量在镜像流量或低峰期做。

## 3.3 典型现象对照

| 抓包现象 | 含义 | 排查方向 |
|----------|------|----------|
| SYN 有去无回 | 服务端未监听、被防火墙丢 | 检查端口、安全组、`ss -lnt` |
| SYN 重传多次 | 服务端不回 SYN+ACK | 半连接队列满或丢包 |
| 握手完成但立刻 RST | 应用 `accept` 后立即关闭、或端口复用冲突 | 查应用日志 |
| 大量重复 ACK | 中间有丢包 | 查重传率与链路质量 |
| 窗口为 0 | 接收方消费慢 | 查应用读取速度 |
| FIN 后长时间 CLOSE_WAIT | 应用没关连接 | 查代码与句柄 |
| 连接被 RST | 对端进程崩溃或超时关闭 | 查对端日志与超时配置 |

## 3.4 一次完整的排错流程

```text
① 确认现象：超时发生在建连阶段还是传输阶段？
        │
        ▼
② 看连接状态：ss -tan 找异常状态与队列
        │
        ▼
③ 看协议指标：ss -tin 的 rtt/retrans/cwnd，netstat -s
        │
        ▼
④ 抓包验证：tcpdump 看握手、ACK、FIN、RST
        │
        ▼
⑤ 看应用：jstack 线程栈、GC 日志、线程池指标
        │
        ▼
⑥ 定位后修复，再压测验证
```

**设计考量**：排错最忌讳"跳步"。有人在没确认超时发生在哪个阶段时就去调 `SO_RCVBUF`，结果问题在应用线程池，白折腾。先分段，再下钻。

# 4. 生产检查清单

## 4.1 代码层

| 检查项 | 合格标准 |
|--------|----------|
| 连接关闭 | 所有路径都用 try-with-resources 或 finally |
| 超时 | 连接、读、业务整体超时都显式设置 |
| 编码 | 收发文统一显式 UTF-8 或协议指定编码 |
| 粘包 | 有明确的消息边界与解码器 |
| 线程 | I/O 线程不做阻塞操作 |
| 异常 | 单连接异常不影响其他连接 |
| 心跳 | 双向空闲检测，间隔与超时匹配 |
| 重连 | 指数退避 + 抖动 + 成功重置 |

## 4.2 配置层

| 检查项 | 建议 |
|--------|------|
| `ulimit -n` | 大于预期连接数 1.5 倍 |
| `somaxconn` / backlog | 与 accept 速度匹配 |
| 临时端口范围 | 出站连接多的机器扩大 |
| `TCP_NODELAY` | 延迟敏感业务开启 |
| keepalive | 作为兜底开启，不替代心跳 |
| 缓冲区 | 按带宽时延积设置，不盲目调大 |

## 4.3 监控层

| 指标 | 阈值思路 |
|------|----------|
| 连接数 | 突增或缓慢上涨都要告警 |
| 重传率 | 超过 1% 开始关注 |
| P99 延迟 | 与基线对比，不只看绝对值 |
| accept 队列溢出 | 出现即告警 |
| 直接内存 | 接近上限前预警 |
| `CLOSE_WAIT` 数量 | 持续增长说明泄漏 |
| 心跳失败率 | 短时间升高说明网络或服务异常 |

> **行业实践**：把这套清单变成上线前的自动化检查项，比写在文档里更有效。尤其是 `ulimit -n`、超时设置和 `CLOSE_WAIT` 监控，这三项在事故复盘里出现频率最高。

# 5. 常见错误

| 错误 | 后果 | 正确做法 |
|------|------|----------|
| 只看 `netstat` 不看 `ss` | 高连接数下卡顿甚至超时 | 用 `ss` |
| 抓包不限大小 | 磁盘被写满 | `-c`/`-G`/`-W` 限制 |
| 把 RST 一律当故障 | 误判正常关闭 | 结合 FIN 与应用日志判断 |
| 未确认阶段就调参 | 掩盖真实问题 | 先分段定位 |
| 监控只看平均值 | 长尾问题漏报 | 看 P95/P99 |
| 心跳与读空闲相等 | 周期性误断 | 读空闲取 2.5-3 倍 |
| 重连无上限 | 网络恢复前持续空转 | 退避 + 最大间隔 |

# 6. 综合练习

**练习一**：启动一个 NIO 服务端，用 `tcpdump` 抓一次完整交互，在 Wireshark 里用 `Follow TCP Stream` 还原消息内容，标出三次握手、数据、四次挥手各自的时间点。

**练习二**：构造一个"客户端发 1MB、服务端只读前 1KB 就停"的场景，用 `ss -tin` 观察 `rcv_space` 与窗口变化，再用 `tcpdump` 确认零窗口探测包。

**练习三**：给出一个"服务端 CPU 不高、连接数也不多，但 P99 延迟偶发 3 秒"的现象，按本篇的排错流程写出你的排查步骤，至少覆盖连接状态、协议指标、应用线程三个层面。

# 7. 小结

| 主题 | 记住这一句 |
|------|-----------|
| 知识地图 | 协议层 → 内核层 → 应用层 → 工程层，逐层定位 |
| 握手挥手 | 三次确认双向能力，四次各自关闭，TIME_WAIT 不可省 |
| 窗口 | 发送量取 min(cwnd, rwnd)，吞吐受 BDP 限制 |
| I/O 模型 | BIO 一连接一线程，NIO 多路复用是主流 |
| 消息边界 | 应用层责任，定长/分隔符/长度字段三选一 |
| 长连接 | 心跳 + 空闲检测 + 退避重连 + 会话恢复 |
| 调优 | 先定位再调参，先正确性再性能 |
| 排错 | `ss` 看状态，`ss -tin` 看协议，`tcpdump` 看证据 |

TCP 模块到这里就闭环了：从协议机制到 Java 实现，从单连接收发到万级连接调度，从功能正确到性能与稳定性。继续往前走有两条路，一是读 Netty 源码，看工业级框架如何把本篇的每个细节工程化；二是往上层走，回到 HTTP/2、gRPC 或自研 RPC，理解它们如何在 TCP 之上重新定义消息、流与连接复用。
