# 1. DNS 中的 UDP

## 1.1 为什么 DNS 用 UDP

DNS 查询是典型的"一问一答、报文很小、要求低延迟"。用 TCP 的话，每次查询都要先三次握手，DNS 解析时间会从毫秒级涨到几十毫秒，而浏览器打开一个页面可能要解析十几个域名，累积起来非常可观。

```text
UDP 查询：  客户端 ── 查询 ──► 服务器 ── 响应 ──► 客户端    （1 个 RTT）

TCP 查询：  握手（1.5 RTT）→ 查询 → 响应 → 挥手          （至少 2.5 RTT）
```

**设计考量**：DNS 把"可靠性"交给了应用层——客户端自己设超时，超时没响应就换一台 DNS 服务器重试。这样做的好处是简单、快，而且 DNS 服务器本身是无状态的，一台服务器可以轻松扛住海量查询。

## 1.2 查询与响应

一次 DNS 查询的报文结构：

```text
┌──────────┬──────────┬──────────┬──────────┬──────────┐
│ 头部 12B  │ 问题区    │ 回答区    │ 授权区    │ 附加区    │
│ ID/标志   │ QNAME    │ RR       │ NS       │ 额外记录  │
└──────────┴──────────┴──────────┴──────────┴──────────┘
```

头部里的 **ID** 是 16 位随机数，用来匹配请求和响应。客户端收到响应时会核对 ID，不匹配就丢弃，防止把旧响应或伪造响应当成当前查询的结果。

```bash
# 观察一次查询的完整过程
dig +noall +answer example.com
# 查看是否走了 UDP
dig +qr example.com
```

## 1.3 截断与 TCP 回退

传统 DNS 的 UDP 响应上限是 **512 字节**。如果响应超过这个大小，服务器会把头部的 **TC（Truncated）** 标志置 1，返回一个截断的响应。客户端看到 TC=1，必须改用 TCP 重新查询。

```text
客户端                                     DNS 服务器
  │ ── UDP 查询 ────────────────────────► │
  │ ◄── 响应，TC=1（内容被截断）──────────── │
  │ ── TCP 连接 + 重新查询 ──────────────► │
  │ ◄── 完整响应 ──────────────────────── │
```

EDNS0（Extension Mechanisms for DNS）把 UDP 上限扩展到 4096 字节，减少了回退到 TCP 的概率。但超过 4096 字节的响应（比如 DNSSEC 签名、大量记录）仍然需要 TCP。

**注意**：`TC=1` 的响应里通常只包含部分记录，不能直接使用。客户端必须重新查询，否则会拿到不完整的结果。

## 1.4 Java 里的 DNS

Java 的 `InetAddress.getByName()` 会自动走系统解析器，底层可能是 UDP 也可能走其他机制（比如 hosts 文件、mDNS）。它不暴露 TC 标志和响应大小，所以排查 DNS 问题时通常还是用 `dig` 或 `nslookup`。

```java
import java.net.InetAddress;

// 只做一次解析，结果由 JVM 缓存（受 networkaddress.cache.ttl 控制）
InetAddress addr = InetAddress.getByName("example.com");
System.out.println(addr.getHostAddress());
```

# 2. 音视频与实时通信

## 2.1 为什么不用 TCP

音视频的核心指标是**端到端延迟**和**流畅度**，不是"每一帧都必须到达"。TCP 的重传和按序交付会导致一个丢包卡住后续所有数据，形成队头阻塞：

```text
TCP：帧 1 丢失 → 后续帧 2、3、4 已到达但必须等帧 1 重传 → 播放卡顿
UDP：帧 1 丢失 → 直接跳过，继续播帧 2、3、4 → 画面轻微花屏但不卡
```

一个 30fps 的视频流，每帧只有 33ms 的展示窗口。等一个 200ms 的重传，早就过了播放时间，重传回来也没用了。

## 2.2 RTP 与 RTCP

RTP（Real-time Transport Protocol）负责传输媒体数据，RTCP（RTP Control Protocol）负责质量反馈，两者通常成对使用：

```text
┌──────────────┐        ┌──────────────┐
│  RTP         │        │  RTCP        │
│  媒体数据      │        │  统计与控制    │
│  序号/时间戳   │        │  丢包率/RTT   │
└──────┬───────┘        └──────┬───────┘
       │                       │
       ▼                       ▼
          同一个 UDP 通道（不同端口）
```

RTP 头部包含序号和时间戳。序号用于检测丢包和乱序，时间戳用于音视频同步和抖动缓冲。RTCP 周期性发送接收报告，告诉发送方"我收到了多少、丢了多少、抖动多大"，发送方据此调整码率。

## 2.3 抖动缓冲与前向纠错

网络抖动意味着包的到达间隔不均匀。**抖动缓冲**（jitter buffer）先把收到的包缓存一小段时间，再按时间戳匀速播放，把抖动抹平：

```text
到达：  [包1] --- [包3] [包2] ------ [包4]
         │
         ▼ 抖动缓冲（缓存 40ms）
播放：  [包1] [包2] [包3] [包4]   均匀输出
```

缓冲越大，抗抖动能力越强，但延迟也越高。实时通话通常把缓冲控制在 20 到 60ms。

**前向纠错**（FEC）是另一条思路：发送方额外发送冗余数据，接收方在丢包时用冗余恢复，不必等重传。代价是带宽增加，通常用于抗连续丢包。

## 2.4 弱网下的取舍

| 网络状况 | 策略 |
|----------|------|
| 轻微丢包（< 1%） | 忽略，靠 FEC 和丢包隐藏 |
| 中度丢包（1% 到 5%） | 降码率、增加 FEC |
| 严重丢包（> 5%） | 降低分辨率/帧率，优先保音频 |
| 高延迟抖动 | 增大抖动缓冲，牺牲一点延迟换流畅 |

> **行业实践**：WebRTC 的拥塞控制（GCC、BBR）会根据 RTCP 反馈动态调整码率。音频通常比视频优先级更高——丢视频用户能忍，丢音频通话就没法进行了。

# 3. 游戏网络

## 3.1 状态同步

多人在线游戏通常以固定频率发送**状态快照**：服务器每 50ms 收集所有玩家位置，打包发给每个客户端。

```text
服务器 tick（20Hz）：
  t=0ms    发送快照：玩家 A(10,20)、B(30,40)
  t=50ms   发送快照：玩家 A(11,21)、B(30,41)
  t=100ms  发送快照：玩家 A(12,22)、B(31,41)
```

快照本身不需要可靠：丢了一个，下一个很快就到，旧状态没有重传价值。这是 UDP 在游戏里最核心的优势——**旧数据过时了，重传反而有害**。

## 3.2 客户端预测与服务端校正

如果客户端每次都等服务端确认再移动，操作会有明显的延迟感。**客户端预测**让本地先按输入移动，同时把输入发给服务器；服务器计算权威位置后回传，客户端再平滑校正。

```text
客户端按下右键
   │
   ├── 本地立即移动（预测）
   └── 发送输入给服务器
          │
          ▼
       服务器计算权威位置
          │
          ▼
       回传位置，客户端对比预测值
          │
          ├── 一致 → 继续
          └── 不一致 → 平滑拉回（避免瞬移）
```

**设计考量**：预测和校正的难点不在算法，而在"如何在不让玩家察觉的情况下修正错误"。直接瞬移会让玩家觉得卡顿，通常用插值在几百毫秒内慢慢纠正。

## 3.3 发送频率与可靠性分级

| 数据类型 | 频率 | 可靠性 | 说明 |
|----------|------|--------|------|
| 位置同步 | 20 到 60Hz | 不可靠 | 最新状态覆盖旧状态 |
| 技能释放 | 事件触发 | 可靠 | 丢一次会导致逻辑错误 |
| 聊天消息 | 事件触发 | 可靠 | 必须按序、不丢 |
| 心跳 | 1 到 5 秒 | 不可靠 | 丢失可容忍 |

同一个游戏可以同时维护两条通道：一条不可靠的实时通道，一条可靠的指令通道。这也是可靠 UDP 设计里"按通道区分可靠性"的典型应用。

# 4. 监控与日志

## 4.1 StatsD

StatsD 是经典的指标采集协议，默认走 UDP 8125 端口。应用把计数、计时、直方图以文本形式发过去，采集端聚合后写入时序数据库。

```text
应用 ──► "api.request:1|c" ──UDP──► StatsD ──► Graphite/Prometheus
         "api.latency:35|ms"
```

选择 UDP 的理由很直接：指标上报必须在业务线程里足够轻量，不能因为监控后端慢而阻塞业务。丢几个点对趋势影响不大，而 TCP 的重连和阻塞可能拖垮整个应用。

**注意**：UDP 报文有大小限制，StatsD 通常把多个指标打包成一个包发送，但不要超过 MTU（约 1432 字节），否则会被 IP 分片，丢一片就整包丢失。

## 4.2 syslog over UDP

syslog 默认走 UDP 514 端口，日志发送方只管发，不关心对方是否收到。这在日志量巨大时能避免阻塞，但代价是可能丢日志。

| 场景 | 是否适合 UDP |
|------|--------------|
| 调试日志、访问日志 | 适合，丢失可接受 |
| 审计日志、安全日志 | 不适合，必须可靠 |
| 容器日志采集 | 视情况，通常用本地 agent 缓冲 |

> **行业实践**：关键日志通常采用"本地落盘 + 异步转发"：应用先写本地文件，再由采集 agent（Filebeat、Fluent Bit）读取并转发。这样即使网络中断，日志也不会丢，agent 还能做重试和限速。

## 4.3 采样与丢失容忍

监控系统普遍做**采样**：不是每个请求都上报，而是按比例采样。采样率 1% 时，即使 UDP 丢了几个包，统计结果的误差也在可接受范围内。

```text
实际请求 10000 次 → 采样 1% → 上报 100 条 → UDP 丢 2 条 → 统计基于 98 条
误差约 2%，对趋势判断完全够用
```

# 5. 抓包排错

## 5.1 tcpdump 常用过滤

```bash
# 抓指定端口的 UDP
tcpdump -i any -nn udp port 9000

# 抓指定主机的 UDP
tcpdump -i eth0 -nn udp and host 192.168.1.10

# 抓组播
tcpdump -i eth0 -nn udp and dst 239.1.1.1

# 显示完整内容（排查协议格式）
tcpdump -i any -nn -X udp port 9000

# 统计每秒包数，判断是否真有流量
tcpdump -i any -nn udp port 9000 -c 100 -w udp.pcap
```

## 5.2 常见现象判读

| 现象 | 可能原因 | 排查方向 |
|------|----------|----------|
| 发送端有包，接收端没有 | 路由、防火墙、NAT 映射 | 逐跳抓包，查 ACL |
| 收到包但校验和错误 | 链路误码、网卡 offload | 关闭 checksum offload 对比 |
| 包长度小于预期 | IP 分片丢失、缓冲区截断 | 看 IP 层分片标志 |
| 大量重复包 | 重传机制、链路层重发 | 看序号和时间间隔 |
| 只有单向流量 | NAT 映射单向、防火墙 | 检查回程路由 |
| 组播收不到 | 网卡选错、IGMP 未加入 | 查网卡和 IGMP 报文 |

## 5.3 Wireshark 技巧

- 用 `udp.port == 9000` 过滤，再用 `Statistics → Conversations` 看流量分布。
- 对自定义协议用 `Decode As` 指定解析器，或者直接看 `Data` 字段。
- 用 `Follow → UDP Stream` 把一次会话的报文串起来（仅对固定五元组有效）。
- 关注 `ip.ttl`、`udp.length`、`udp.checksum.status` 这几个字段。

**注意**：本机抓包看到"校验和错误"很常见，因为网卡的 checksum offload 把计算推迟到硬件，抓包时拿到的是未计算的值。不要据此判断报文真的损坏。

## 5.4 Java 侧的排查点

| 现象 | 检查 |
|------|------|
| 收不到包 | 是否 `bind` 了正确端口、是否指定了网卡 |
| 数据被截断 | 缓冲区大小、`getLength()` 用法 |
| 中文乱码 | 两端编码是否一致 |
| 线程卡死 | 是否设置了 `setSoTimeout` |
| 服务端重启端口占用 | `setReuseAddress`、残留进程 |
| 组播不通 | `joinGroup` 是否指定了正确网卡 |

# 6. 高频自检题

## 6.1 UDP 和 TCP 最本质的区别是什么？

TCP 在内核里维护连接状态，用序号、确认、重传、窗口把不可靠的 IP 包装成可靠字节流；UDP 只做端口寻址和可选的校验，把可靠性、有序性、拥塞控制全部留给应用层。选择哪一个，取决于业务能否容忍丢包，以及是否需要自己控制传输策略。

## 6.2 UDP 会粘包吗？

不会。UDP 保留消息边界，一次 `send()` 对应一次 `receive()`。但"保留边界"不等于"消息完整"：超过 MTU 的报文会被 IP 分片，丢一片就整包丢失，接收方什么也收不到。

## 6.3 UDP 首部为什么只有 8 字节？

因为它只包含端口、长度、校验和这四个必要字段，不携带序号、确认号、窗口、标志位等可靠性信息。这些信息被移到了应用层，由使用 UDP 的协议自行决定是否需要。

## 6.4 UDP 校验和是可选的，为什么还不关？

IPv4 下填 0 表示不校验，但关闭后比特错误会直接进入业务逻辑。现代网卡支持校验和卸载，计算成本很低，没有理由关闭。IPv6 强制要求校验和，因为 IP 层不再提供首部校验。

## 6.5 为什么 DNS 用 UDP 却很少丢查询？

DNS 客户端自己实现了超时和重试：超时没响应就换服务器重发。DNS 服务器无状态，一台可以服务海量查询，丢个别查询的代价远小于为每个查询维护 TCP 连接。

## 6.6 DatagramPacket 接收时最容易犯什么错？

用 `buf.length` 而不是 `packet.getLength()` 当作有效长度，导致缓冲区尾部的空字节被解码成脏数据。正确做法是用 `getData()`、`getOffset()`、`getLength()` 三个参数构造字符串。

## 6.7 为什么 UDP 服务端通常只需要一个接收线程？

UDP 没有连接，所有客户端的数据报都进入同一个 socket 的接收队列。多线程 `receive()` 会让报文被随机分给某个线程，增加状态管理的复杂度。正确做法是单线程收包、投递到有界队列，由工作线程池处理业务。

## 6.8 可靠 UDP 为什么必须有去重？

只要存在重传，就必然存在重复：原包可能已经到了，只是 ACK 丢了，发送方重传后接收方会收到两份。不去重会导致业务重复执行，比如重复下单、重复扣款。

## 6.9 UDP 打洞为什么要求双方同时发包？

NAT 的过滤规则要求"内部先向对方发过包"才允许对方进来。单方面发包时，对方的 NAT 还没放行，包会被丢弃。双方同时发包，才能让各自的 NAT 都建立放行记录。

## 6.10 线上 UDP 服务丢包，怎么排查？

先确认丢在哪一段：发送端抓包看是否发出，接收端抓包看是否收到，中间看 NAT 和防火墙。如果两端都有包但应用没收到，检查缓冲区是否太小、接收队列是否满、端口是否绑错。如果是组播，还要检查网卡和 IGMP 加入情况。

# 7. 模块总结

## 7.1 知识地图

```text
UDP 模块
├── 协议层（第 1 篇）
│   ├── 8 字节首部、伪首部校验和
│   ├── 无连接、不可靠、保留边界
│   └── 与 TCP 的取舍
├── 编程层（第 2 篇）
│   ├── DatagramSocket / DatagramPacket
│   ├── 超时、编码、缓冲区
│   └── 单接收线程 + 队列 + 线程池
├── 可靠性（第 3 篇）
│   ├── 序号、确认、重传、去重
│   ├── 滑动窗口与拥塞控制
│   └── 自研 vs QUIC/KCP
├── 一对多（第 4 篇）
│   ├── 广播与组播、IGMP
│   ├── MulticastSocket、TTL、网卡
│   └── 局域网发现
├── 穿越（第 5 篇）
│   ├── NAT 类型、映射生命周期
│   ├── STUN / TURN / ICE
│   └── 打洞与保活
└── 场景（第 6 篇）
    ├── DNS、音视频、游戏、监控
    └── 抓包排错
```

## 7.2 选型清单

| 需求 | 推荐方案 |
|------|----------|
| 可靠传输、不想自己实现 | TCP 或 QUIC |
| 低延迟、可容忍丢包 | 裸 UDP |
| 需要可靠但想控制重传策略 | QUIC / KCP |
| 局域网服务发现 | 组播（mDNS）或注册中心 |
| 跨公网 P2P | STUN + 打洞，失败回退 TURN |
| 指标/日志上报 | UDP + 采样 + 本地缓冲 |
| 实时音视频 | RTP/RTCP，WebRTC |
| 联机游戏 | 状态快照 + 预测校正，双通道 |

> **行业实践**：真正成熟的系统很少"纯 UDP"，而是按数据类型分层：实时状态走不可靠通道，关键指令走可靠通道，发现阶段用组播，跨网段用中继。把可靠性做在"消息"级别，而不是"连接"级别，是 UDP 架构和 TCP 架构最大的思维差异。

# 8. 练习与自检

**练习一**：用 `dig +trace` 跟踪一次完整解析，记录哪些步骤走 UDP、哪些走 TCP，解释为什么根服务器查询通常用 UDP 也能完成。

**练习二**：用 Wireshark 抓一段自己写的 UDP 回声服务，找出每个包的 `udp.length`、`ip.ttl` 和 `udp.checksum.status`，判断是否存在截断或校验错误。

**练习三**：设计一个"游戏位置同步 + 聊天"的双通道协议：位置用不可靠 UDP，聊天用可靠 UDP。写出两种通道各自的报文格式和重传策略，并说明为什么不能用同一种可靠性等级。

自检问题：DNS 的 TC 标志是什么？音视频为什么宁可丢帧也不重传？游戏为什么需要客户端预测？监控系统为什么能接受 UDP 丢包？

# 9. 小结

| 主题 | 记住这一句 |
|------|-----------|
| DNS | 一问一答、报文小，UDP 足够；超过 512 字节看 TC 回退 TCP |
| 音视频 | 延迟优先，丢帧比重传更划算，靠 FEC 和抖动缓冲 |
| 游戏 | 旧状态没有重传价值，双通道区分可靠性 |
| 监控日志 | 可采样、可容忍丢失，UDP 避免阻塞业务 |
| 排错 | 分段抓包定位丢在哪一层，注意 checksum offload 的假象 |
| 选型 | 可靠优先 TCP/QUIC，实时优先 UDP，跨网用 TURN 兜底 |

UDP 模块到这里结束。它看起来只是一条"不可靠的传输通道"，但正是这种不替你决定的设计，让 QUIC、WebRTC、游戏协议和监控系统可以按自己的需求定制传输策略。理解了 UDP，再回头看 TCP 的可靠性和拥塞控制，会更清楚每一项机制是在解决什么问题、又付出了什么代价。
