公网上的两台主机想直接通过 UDP 通信，中间通常隔着至少一层 NAT。NAT 的设计初衷是节省 IPv4 地址，但副作用是外部主机无法主动"敲开"内部端口。P2P 下载、视频通话、联机游戏、远程桌面，这些需要端到端直连的场景，都要在 NAT 的约束下找到一条能走通的路。本篇讲清 NAT 的几种类型、STUN 如何探测公网地址、UDP 打洞为什么需要双方同时发包、保活为什么不能省，以及这条路上哪些情况注定失败。

# 1. NAT 为什么会让 UDP 变复杂

## 1.1 NAT 的基本工作

NAT（Network Address Translation，网络地址转换）在路由器上维护一张映射表，把内部私网地址转换成公网地址。内部主机发出去时改写源地址和源端口，收到回包时按映射表改回来。

```text
内部主机                      NAT 路由器                    公网服务器
192.168.1.10:5000  ──────►  公网 IP:40001  ──────────────►  1.2.3.4:3478
                             │
                             │ 映射表：
                             │ 192.168.1.10:5000 ↔ 公网IP:40001
                             │
192.168.1.10:5000  ◄──────  公网 IP:40001  ◄──────────────  1.2.3.4:3478
```

关键点在于：**映射是由内部主机主动发包建立的**。外部主机如果先发包到 `公网IP:40001`，而映射表里还没有这一条，路由器不知道该转给谁，只能丢弃。

## 1.2 端口映射的生命周期

NAT 映射不是永久的。不同设备、不同协议的超时时间差别很大：

| 协议 | 常见映射超时 | 说明 |
|------|--------------|------|
| UDP | 30 秒到 5 分钟 | 普遍较短，不同厂商差异大 |
| TCP 已建立 | 数小时到数天 | 有连接状态，超时更长 |
| TCP 半开 | 几十秒 | 未完成握手 |

**注意**：UDP 映射超时后，路由器删掉表项，后续从公网发到那个端口的包会被直接丢弃。但内部主机并不知道映射已经失效，仍以为通道可用——这就是"连接看起来还在，实际发不出去"的典型现象。

## 1.3 谁先发包谁先建立映射

NAT 的方向性决定了一条规则：**想让外部能发进来，内部必须先发出去一次**。这次发送会在 NAT 上建立映射，之后外部发到该映射端口的包才能被转发进来。

```text
第一步：内部 → 外部（建立映射，NAT 记住"这个端口对应内网哪台机器"）
第二步：外部 → 内部（命中映射，被转发）
```

UDP 打洞的全部技巧都建立在这条规则上：让通信双方各自先向对方的方向发一个包，把自己这一侧的 NAT 映射"打开"，然后再互相发包。

# 2. NAT 类型

## 2.1 全锥形

**全锥形 NAT**（Full Cone NAT）最宽松：内部地址 `IP:port` 第一次向外发包后，NAT 分配一个公网端口，之后**任何外部主机**发到这个端口都能被转发进来，不限制来源。

```text
内部 192.168.1.10:5000 ──► NAT 映射到 公网:40001
外部任意主机:任意端口 ──► 公网:40001 ──► 转发给 192.168.1.10:5000
```

打洞最容易，只要有一方知道对方的公网映射地址，直接发即可。

## 2.2 地址受限锥形

**地址受限锥形 NAT**（Restricted Cone NAT）只允许**曾经通信过的 IP** 发进来，但不限制对方的端口。

```text
内部 192.168.1.10:5000 曾发给 5.6.7.8:任意端口
则 5.6.7.8:任意端口 → 公网:40001 可以进来
但 9.9.9.9:任意端口 → 公网:40001 被丢弃
```

打洞时需要双方先向对方 IP 发过包，哪怕内容没人收到，也能"开权限"。

## 2.3 端口受限锥形

**端口受限锥形 NAT**（Port Restricted Cone NAT）最严格也最常见：只允许**曾经通信过的 IP 和端口**发进来。

```text
内部 192.168.1.10:5000 曾发给 5.6.7.8:6000
则 5.6.7.8:6000 → 公网:40001 可以进来
但 5.6.7.8:6001 → 公网:40001 被丢弃（端口不同）
```

打洞要求双方同时向对方的**确切公网 IP 和端口**发包，时序和地址必须都正确。

## 2.4 对称型

**对称型 NAT**（Symmetric NAT）对每个不同的目标地址分配**不同的公网端口**：

```text
192.168.1.10:5000 → 5.6.7.8:6000   映射到 公网:40001
192.168.1.10:5000 → 9.9.9.9:7000   映射到 公网:40002  ← 端口不同
```

这打破了打洞的基础：你通过 STUN 服务器得到的公网端口，只对那个 STUN 服务器有效；向对方发包时，NAT 会分配另一个端口，对方拿到的地址和实际发包的地址对不上。

| 类型 | 映射规则 | 过滤规则 | 打洞难度 |
|------|----------|----------|----------|
| 全锥形 | 一个内网地址对应一个公网端口 | 不限来源 | 容易 |
| 地址受限锥形 | 同上 | 限制来源 IP | 较易 |
| 端口受限锥形 | 同上 | 限制来源 IP + 端口 | 需精确时序 |
| 对称型 | 每个目标分配不同端口 | 限制来源 IP + 端口 | 通常失败，需中继 |

## 2.5 判定方法

RFC 3489 定义了经典的判定流程，用两台不同 IP 的 STUN 服务器做探测：

```text
1. 向服务器 A 发请求，拿到公网地址 X
2. 向服务器 B 发请求，拿到公网地址 Y
   ├── X != Y  → 对称型 NAT
   └── X == Y  → 继续
3. 让服务器 B 用另一个端口向 X 发包
   ├── 收到   → 全锥形
   └── 收不到 → 继续
4. 让服务器 B 用原端口、但换个 IP 向 X 发包
   ├── 收到   → 地址受限锥形
   └── 收不到 → 端口受限锥形
```

**注意**：现代 NAT 设备很多是混合行为，不完全符合 RFC 3489 的四类划分。RFC 5389 之后的 STUN 更关注"能不能拿到映射地址"和"过滤行为"，而不再强行归类。实际工程里更重要的是用 ICE 框架做连通性测试，而不是纠结 NAT 的精确类型。

# 3. STUN

## 3.1 它解决什么问题

STUN（Session Traversal Utilities for NAT）是一个轻量协议，作用是让客户端问服务器："**你看到的我的公网地址和端口是什么？**" 客户端把这个地址告诉对端，对端就知道该往哪里发包。

```text
┌──────────┐        ┌──────────────┐        ┌──────────┐
│ 客户端 A  │ ─────► │ STUN 服务器   │ ◄───── │ 客户端 B  │
│ 内网       │        │ 公网 IP       │        │ 内网       │
└──────────┘        └──────────────┘        └──────────┘
     │                                            │
     └──── 拿到自己的公网映射，通过信令交换 ────────┘
```

STUN 服务器不转发业务数据，只在握手阶段帮忙"照镜子"。它的负载很低，一个公网 IP 就能服务大量客户端。

## 3.2 交互过程

STUN 报文格式（简化）：

```text
 0                   1                   2                   3
┌───────────────┬───────────────┬───────────────────────────────┐
│ 消息类型 (16)   │ 消息长度 (16)  │ Magic Cookie (32)             │
│ 0x0001=Binding│               │ 0x2112A442                    │
├───────────────┴───────────────┴───────────────────────────────┤
│ Transaction ID (96 位，12 字节)                                 │
├───────────────────────────────────────────────────────────────┤
│ 属性：XOR-MAPPED-ADDRESS（编码后的公网地址）                       │
└───────────────────────────────────────────────────────────────┘
```

客户端发一个 Binding Request，服务器回 Binding Response，其中 `XOR-MAPPED-ADDRESS` 属性就是服务器观察到的客户端公网地址。之所以用 XOR 编码，是为了避免某些 NAT 设备错误地改写报文里的 IP 地址。

```text
客户端                                     STUN 服务器
  │ ── Binding Request (事务 ID=T) ──────► │
  │                                        │ 记录源地址 1.2.3.4:40001
  │ ◄── Binding Response (T, XOR-MAPPED) ── │
  │     公网地址 = 1.2.3.4:40001            │
```

## 3.3 局限性

STUN 只能解决"知道自己的公网地址"，不能解决"对方能发进来"。如果双方都是对称型 NAT，或者一方在对称型 NAT 后面，STUN 拿到的地址与实际发包的映射不一致，打洞仍然失败。

此外，STUN 需要客户端能访问到公网上的 STUN 服务器。在只允许特定端口出网的企业网络里，STUN 流量可能被防火墙拦截。

# 4. UDP 打洞

## 4.1 基本原理

打洞（hole punching）利用 NAT 的"内部先发包就建立映射"规则。假设 A 和 B 都在 NAT 后面，各自通过 STUN 拿到了公网映射地址 `A_pub` 和 `B_pub`：

```text
A 内网 ── NAT_A ── A_pub
B 内网 ── NAT_B ── B_pub
```

接下来 A 向 `B_pub` 发包，B 向 `A_pub` 发包。这两个包可能都会被对方的 NAT 丢弃（因为对方的映射还没建立或过滤规则不允许），但**发送这个动作本身**会在各自的 NAT 上打开一个允许对方进来的洞。之后再重发，就能穿透。

```text
第一步：A → B_pub  （A 的 NAT 记录：允许 B_pub 进来）
        B → A_pub  （B 的 NAT 记录：允许 A_pub 进来）

第二步：A → B_pub  （这次 B 的 NAT 已经有 A_pub 的放行记录，转发成功）
        B → A_pub  （同理，A 的 NAT 转发成功）
```

## 4.2 信令流程

打洞需要一个**信令通道**来交换公网地址。这个通道通常走 TCP、WebSocket 或已有的 HTTP 服务，因为它必须可靠。

```text
┌────────┐          ┌──────────────┐          ┌────────┐
│ 客户端 A │          │ 信令服务器     │          │ 客户端 B │
└───┬────┘          └──────┬───────┘          └───┬────┘
    │ 1. 登录 + 上报 STUN 地址 │                     │
    │ ──────────────────────► │                     │
    │                         │ ◄────────────────── │
    │ 2. 请求连接 B            │                     │
    │ ──────────────────────► │                     │
    │ 3. 下发 B 的地址          │ 3. 下发 A 的地址      │
    │ ◄────────────────────── │ ──────────────────► │
    │                         │                     │
    │ 4. 双方同时向对方公网地址发包（打洞）              │
    │ ◄───────────────────────────────────────────► │
    │                         │                     │
    │ 5. 洞打通后，业务数据直接点对点传输               │
    └─────────────────────────────────────────────► │
```

## 4.3 为什么需要同时发包

如果只有 A 单方面发包，B 的 NAT 可能在第一个包到达时把它丢弃（因为 B 侧还没建立放行记录），A 会一直重试，直到超时。双方同时发包，才能保证"我发出去的包到达时，你那边已经允许我进来"。

```text
A 发 → B 的 NAT：丢弃（B 侧还没放行）
B 发 → A 的 NAT：丢弃（A 侧还没放行）
A 发 → B 的 NAT：放行（B 侧刚才发过包，已记录 A）
B 发 → A 的 NAT：放行（A 侧刚才发过包，已记录 B）
```

**注意**：这个"同时"不需要严格同步，只要双方都在一个较短的时间窗口内（比如几百毫秒到几秒）持续重发即可。工程实现通常让双方以固定间隔重发若干次，直到收到对方的包或超时。

## 4.4 Java 中的最小实现

打洞本身没有特殊 API，就是普通的 `DatagramSocket` 收发。关键在于"持续向对方地址发包，直到收到回应"。

```java
import java.net.DatagramPacket;
import java.net.DatagramSocket;
import java.net.InetSocketAddress;
import java.nio.charset.StandardCharsets;

public class HolePuncher {
    /** peer 是从信令服务器拿到的对方公网地址 */
    public static boolean punch(InetSocketAddress peer, int localPort) throws Exception {
        try (DatagramSocket socket = new DatagramSocket(localPort)) {
            socket.setSoTimeout(500);
            byte[] probe = "PUNCH".getBytes(StandardCharsets.UTF_8);
            byte[] buf = new byte[64];

            // 在 5 秒内持续向对方发包，同时尝试接收
            long deadline = System.currentTimeMillis() + 5000;
            while (System.currentTimeMillis() < deadline) {
                socket.send(new DatagramPacket(probe, probe.length, peer));
                try {
                    DatagramPacket p = new DatagramPacket(buf, buf.length);
                    socket.receive(p);
                    String msg = new String(p.getData(), p.getOffset(), p.getLength(),
                                            StandardCharsets.UTF_8);
                    if ("PUNCH".equals(msg)) {
                        System.out.println("打洞成功，对端: " + p.getSocketAddress());
                        return true;
                    }
                } catch (java.net.SocketTimeoutException e) {
                    // 这一轮没收到，继续下一轮
                }
            }
            return false;
        }
    }
}
```

**注意**：这段代码假定本地端口固定。实际打洞中，本地端口必须和 STUN 探测时使用的端口一致，否则 NAT 会为同一个内网 socket 的不同目标分配不同映射，导致对方拿到的地址失效。所以 `DatagramSocket` 必须在 STUN 探测之前创建并保持不关闭。

# 5. TURN 与中继

## 5.1 何时必须中继

当打洞失败（对称型 NAT、防火墙严格、双方不在同一网络），唯一的办法是让双方都连到一个公网中继服务器，由它转发数据。TURN（Traversal Using Relays around NAT）就是干这个的。

```text
A ──► TURN 服务器 ──► B
      （双向转发，所有流量经过中继）
```

TURN 是最可靠的方案，但代价也最大：所有业务流量都经过服务器，带宽成本、延迟、单点故障都落在中继上。

## 5.2 TURN 的代价

| 代价 | 说明 |
|------|------|
| 带宽 | 每路连接双向流量都算在服务器上，视频通话成本很高 |
| 延迟 | 多一跳，跨地域时延迟明显增加 |
| 容量 | 中继服务器需要按并发连接数规划 |
| 成本 | 云上按流量计费，长期运营成本不低 |

> **行业实践**：WebRTC 的标准做法是优先直连（STUN 打洞），失败时回退到 TURN。典型比例是 80% 到 90% 的连接能直连，10% 到 20% 需要中继。TURN 服务器的容量规划要按最坏情况（比如全员在公司防火墙后）留足余量。

## 5.3 ICE 框架

ICE（Interactive Connectivity Establishment）是把 STUN 和 TURN 组合起来的框架。它收集所有可能的候选地址，逐一做连通性测试，选最快的一条。

```text
候选地址收集：
  1. 本机内网地址（host candidate）
  2. STUN 得到的公网映射（server reflexive candidate）
  3. TURN 分配的中继地址（relay candidate）
       │
       ▼
连通性检查：双方两两配对，互发 STUN Binding 请求
       │
       ▼
选择优先级最高且能通的一对，用于业务数据
```

| 候选类型 | 来源 | 优先级 | 适用 |
|----------|------|--------|------|
| host | 本机网卡 | 最高 | 同一局域网 |
| srflx | STUN 映射 | 中 | 锥形 NAT 打洞 |
| relay | TURN 分配 | 最低 | 对称型 NAT、严格防火墙 |

**设计考量**：ICE 的核心价值是"不假设网络环境"，而是把所有可能的路径都试一遍，用探测结果决定走哪条。这比"先猜 NAT 类型再决定策略"更可靠，因为真实网络的 NAT 行为经常无法精确归类。

# 6. 保活

## 6.1 为什么需要保活

NAT 映射会在空闲一段时间后过期，过期后外部再也发不进来。如果双方长时间不通信（比如视频通话中静音、游戏挂机、推送通道空闲），映射被回收，下次发包时对端可能收不到，表现为"连接突然断了"。

保活（keepalive）就是定期发一个空包或心跳包，刷新 NAT 映射和防火墙状态。

## 6.2 间隔怎么定

间隔要小于 NAT 映射的最短超时。常见取值是 **15 到 25 秒**：

| 间隔 | 效果 | 风险 |
|------|------|------|
| 5 秒 | 几乎不会过期 | 流量和唤醒开销大，移动端耗电 |
| 15 到 25 秒 | 覆盖大多数 NAT 超时 | 少数超时更短的设备仍可能掉线 |
| 60 秒以上 | 省流量 | 大量 NAT 已过期，连接假死 |

**注意**：保活包不能太大，否则移动网络下会显著耗电。一般 1 到 20 字节足够，只要能让 NAT 看到这个五元组有流量即可。

## 6.3 保活报文的设计

保活包最好带一个递增的序号或时间戳，方便对端判断是否真的收到了：

```java
import java.net.DatagramPacket;
import java.net.DatagramSocket;
import java.net.InetSocketAddress;
import java.nio.ByteBuffer;
import java.util.concurrent.Executors;
import java.util.concurrent.ScheduledExecutorService;
import java.util.concurrent.TimeUnit;

public class UdpKeepAlive {
    private final DatagramSocket socket;
    private final InetSocketAddress peer;
    private long pingSeq = 0;

    public UdpKeepAlive(DatagramSocket socket, InetSocketAddress peer) {
        this.socket = socket;
        this.peer = peer;
    }

    public void start() {
        ScheduledExecutorService timer = Executors.newSingleThreadScheduledExecutor();
        // 每 20 秒发一次保活包
        timer.scheduleAtFixedRate(() -> {
            try {
                ByteBuffer bb = ByteBuffer.allocate(9);
                bb.put((byte) 0x01);          // 类型：PING
                bb.putLong(++pingSeq);         // 序号，用于检测丢包
                byte[] data = bb.array();
                socket.send(new DatagramPacket(data, data.length, peer));
            } catch (Exception e) {
                // 发送失败不等于连接已断，交给业务层判断
                System.err.println("保活发送失败: " + e.getMessage());
            }
        }, 20, 20, TimeUnit.SECONDS);
    }
}
```

对端收到 `PING` 后应回一个 `PONG`，让发送方知道通道仍然双向可用。如果连续多个周期没有收到 `PONG`，才判定连接失效。

**设计考量**：单向保活只能刷新"我这一侧"的 NAT 映射，如果对方那一侧的映射已经过期，你发过去的包会被丢弃。所以保活必须是双向的：双方都定期发，或者收到 PING 后立即回 PONG，让两个方向的流量都存在。

# 7. 失败场景与安全边界

## 7.1 常见失败

| 场景 | 现象 | 处理 |
|------|------|------|
| 双方都是对称型 NAT | 打洞拿到的地址与实际映射不一致 | 回退 TURN |
| 企业防火墙只允许 80/443 | UDP 完全被拦 | 用 TCP 中继或 HTTPS 隧道 |
| NAT 映射超时 | 空闲后突然收不到包 | 保活间隔调小 |
| 多网卡选错出口 | STUN 拿到的是另一张网卡的地址 | 显式绑定网卡和端口 |
| 移动网络切换 | IP 变化，旧映射失效 | 重连 + 重新打洞（QUIC 连接迁移） |
| 端口预测失败 | 对称型 NAT 端口跳跃 | 无法预测，改用中继 |

## 7.2 安全风险

UDP 打洞在安全上要格外小心，因为它本质上是在防火墙上"开洞"：

- **未授权访问**：打洞后，任何知道这个映射地址的主机都可能向该端口发包。业务层必须做身份认证，不能只靠"地址对了"就信任。
- **放大攻击**：如果服务端收到一个小请求就回一个很大的响应，攻击者可以伪造源地址，把流量放大后打向受害者。UDP 没有握手，天然容易被反射放大（DNS、NTP 都是重灾区）。
- **状态耗尽**：攻击者可以向服务端发送大量伪造的打洞请求，让服务端为不存在的会话分配资源。
- **内网穿透滥用**：打洞技术也可能被恶意软件用来绕过企业防火墙，建立隐蔽通道。

> **行业实践**：WebRTC 在打洞之上强制使用 DTLS 加密和身份验证，STUN/TURN 服务器也要做认证（TURN 用长期凭证或短期令牌）。自研打洞协议时，至少要做到：业务报文加密、对端身份校验、限制单 IP 的会话数、对异常大的响应限速。

# 8. 常见错误

| 错误 | 后果 | 正确做法 |
|------|------|----------|
| 以为 STUN 能解决所有 NAT | 对称型 NAT 下打洞失败 | 准备 TURN 回退 |
| 打洞时重新创建 socket | 本地端口变了，映射对不上 | 一个 socket 用到底 |
| 只单向保活 | 对端映射过期，收不到包 | 双向保活或 PING/PONG |
| 保活间隔 60 秒以上 | 大量 NAT 已回收映射 | 15 到 25 秒 |
| 多网卡不绑定出口 | STUN 地址与实际发包地址不一致 | 显式绑定网卡 |
| 打洞后不做认证 | 任意主机可发数据进来 | 加密 + 身份校验 |
| 忽略移动网络切换 | IP 变了，连接假死 | 监听地址变化并重连 |
| 用 UDP 放大响应 | 被利用做反射攻击 | 响应大小与请求匹配，验证源地址 |

# 9. 练习与自检

**练习一**：用两台不同网络的机器（比如手机热点和家庭宽带），分别运行一个 STUN 客户端，记录拿到的公网地址，再用 `tcpdump` 抓包对比实际发包的源端口，判断各自的 NAT 类型。

**练习二**：实现一个带 PING/PONG 的保活通道，故意把间隔设为 5 分钟，观察连接在空闲后多久失效。再把间隔改成 20 秒，验证连接能长期保持。

**练习三**：模拟打洞失败：让一端只发不收（不调用 `receive`），观察另一端是否一直重试、最终超时。思考真实系统中应该如何区分"对方还没收到"和"对方根本不可达"。

自检问题：为什么打洞必须双方同时发包？对称型 NAT 为什么无法打洞？TURN 和 STUN 的本质区别是什么？

# 10. 小结

| 主题 | 记住这一句 |
|------|-----------|
| NAT 映射 | 内部先发包才建立，空闲会过期 |
| NAT 类型 | 锥形可打洞，对称型通常只能中继 |
| STUN | 让客户端知道自己的公网映射地址，不转发业务数据 |
| 打洞 | 双方同时向对方公网地址发包，借发送动作打开 NAT |
| TURN | 打洞失败时的中继兜底，可靠但成本高 |
| ICE | 收集所有候选地址，逐一测试，选最优路径 |
| 保活 | 间隔小于 NAT 超时，必须双向 |
| 安全 | 打洞等于开洞，业务层必须认证和加密 |
