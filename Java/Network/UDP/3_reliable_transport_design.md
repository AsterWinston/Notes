前两篇说明了 UDP 只保证"发出去"，不保证"送到达"。一旦业务要求消息不丢、不重、不乱序，就必须在 UDP 之上自己补一套可靠传输。这件事远不只是"超时重传"四个字：序号怎么编、确认怎么回、重传什么时候触发、重复包怎么识别、窗口怎么滑动、拥塞怎么控制，每一步都有取舍。本篇按"最小可用"到"接近工程"的顺序拆解这些机制，最后给一个可运行的简化可靠层。

# 1. 为什么要在 UDP 上做可靠传输

## 1.1 UDP 只提供最小语义

UDP 交付给应用层的只有三样东西：一个完整的数据报、来源地址、一个可能出错的校验结果。它不告诉你报文是否丢失，不保证到达顺序，也不去重。要在这之上实现可靠传输，本质上是在应用层重新实现传输层的一部分职责。

```text
应用要的语义               UDP 实际提供          中间缺的部分
─────────────────────────────────────────────────────────────
每条消息都到达        →    尽力而为           →   确认 + 重传
按发送顺序交付        →    可能乱序           →   序号 + 重组
每条消息只交付一次    →    可能重复           →   去重窗口
发送速率不压垮网络    →    无拥塞控制         →   拥塞控制算法
```

**设计考量**：可靠 UDP 不是为了"取代 TCP"，而是为了在特定约束下拿到 TCP 给不了的东西。比如游戏需要在 50ms 内恢复一个关键状态包，而 TCP 的 RTO 最小值通常在 200ms 以上；比如 QUIC 要消灭传输层队头阻塞，就必须自己管理每个流的重传。脱离这些约束去自研可靠 UDP，通常是在重复造一个更差的 TCP。

## 1.2 可靠 UDP 的适用边界

| 场景 | 是否值得自研可靠层 | 原因 |
|------|--------------------|------|
| 文件传输、数据库同步 | 否 | TCP 已经足够，且经过充分调优 |
| 实时音视频 | 部分 | 只对关键帧做选择性重传，其余靠 FEC |
| 多人在线游戏 | 是 | 需要按对象重要性区别对待，TCP 无法表达 |
| 跨公网低延迟 RPC | 视情况 | QUIC 已成熟，优先直接用 |
| 自建内网协议 | 视情况 | 内网丢包低，可能只需要简单确认 |

> **行业实践**：绝大多数团队不需要自己写可靠 UDP。优先考虑 QUIC（HTTP/3、gRPC over QUIC）、KCP、UDT 这类成熟实现。自研的收益通常只在"协议语义高度定制"时才会出现，而代价是拥塞控制、路径 MTU 发现、NAT 保活这些坑要自己踩一遍。

一个可靠层至少要回答四个问题：**怎么编号**（每条消息一个序号，还是每个字节一个序号）、**怎么确认**（逐条、累计还是选择确认）、**什么时候重传**（固定超时、动态 RTO 还是重复确认）、**发多快**（有没有窗口和拥塞控制）。不同的答案组合出不同的协议：TCP 选择"字节序号 + 累计确认 + 动态 RTO + 滑动窗口 + 拥塞控制"；KCP 选择"消息序号 + 选择确认 + 可配置重传"，把实时性放在吞吐之上。

# 2. 序号与确认

## 2.1 给消息编号

最直接的方式是**按消息编号**：每个应用层消息分配一个递增的 `seq`，接收方按 `seq` 排序和去重。

```text
发送方                              接收方
seq=1  [消息 A]  ────────────────►  收到 1，交付 A，期望 2
seq=2  [消息 B]  ────────────────►  收到 2，交付 B，期望 3
seq=3  [消息 C]  ─────X（丢失）      仍在期望 3
seq=4  [消息 D]  ────────────────►  收到 4，缓存，仍期望 3
```

按消息编号的语义清晰，一条消息要么完整交付，要么不交付。缺点是消息大小不一时，窗口不好用字节衡量。TCP 选择**按字节编号**，让窗口、重传、流量控制都以字节统一计算，代价是消息边界需要额外标记。

**注意**：序号字段的位宽决定了能同时"在途"多少条消息。16 位序号最多 65536 个，超出后会回绕，接收方必须用模运算比较大小，不能简单用 `>`。这是实现里最容易出 bug 的地方之一。

## 2.2 确认报文与确认方式

接收方收到消息后回一个 ACK，最小的 ACK 只需要携带"我期望的下一个序号"和"我还能收多少"：

```text
┌──────────┬──────────┬──────────────┐
│ 类型 ACK │ 确认号    │ 可选：接收窗口 │
│ 1 字节    │ 4 字节    │ 2 字节        │
└──────────┴──────────┴──────────────┘
```

| 方式 | 含义 | 优点 | 缺点 |
|------|------|------|------|
| 累计确认 | `ack=N` 表示 N 之前全部收到 | 实现简单，ACK 可合并 | 一条丢失导致后续全部无法确认 |
| 选择确认 SACK | 额外告诉对方"我还收到了这些区间" | 只重传真正丢失的包 | 报文变长，实现复杂 |
| 逐条确认 | 每条消息一个 ACK | 语义直接 | ACK 数量翻倍，开销大 |

```text
累计确认：收到 1,2,4,5  →  ack=3
           发送方只知道 3 之前到了，不知道 4、5 是否到达

选择确认：收到 1,2,4,5  →  ack=3, sack=[4-5]
           发送方立刻知道只需重传 3
```

**设计考量**：实时性优先的协议（游戏、音视频）几乎都会用 SACK 或类似的区间确认，因为等待累计确认会让一个丢包拖住整条流。而吞吐优先、丢包率低的场景，累计确认足够，且实现简单、不易出错。

# 3. 超时与重传

## 3.1 RTO 的估算

固定超时在跨公网时几乎不可用：RTT 可能从 10ms 波动到 500ms，固定值要么频繁误重传，要么丢包后长时间不恢复。工程上普遍采用**动态 RTO**：

```text
SRTT   = (1 - α) * SRTT + α * RTT测量值            // 平滑 RTT，α 通常 0.125
RTTVAR = (1 - β) * RTTVAR + β * |SRTT - RTT测量值|  // RTT 波动，β 通常 0.25
RTO    = SRTT + 4 * RTTVAR                          // 留出足够余量
```

**注意**：`RTO` 需要设下限（比如 100ms 到 200ms），否则在低延迟链路上会把正常抖动误判为丢包。每次重传后还要**指数退避**：RTO 翻倍，避免网络已经拥塞时继续加压。超过最大重试次数后判定连接失效，通知应用层。

## 3.2 重传的触发方式

| 触发方式 | 条件 | 特点 |
|----------|------|------|
| 超时重传 | 定时器到期仍未确认 | 兜底机制，延迟至少一个 RTO |
| 快速重传 | 收到 N 个重复 ACK | 无需等超时，延迟低 |
| 选择性重传 | 收到 SACK 指出缺口 | 只补真正丢失的包 |
| 应用层 NACK | 接收方主动报告缺口 | 适合有反馈通道的实时协议 |

```text
发送方                          接收方
seq=1 ────────────────────────► 收到，ack=2
seq=2 ────────X（丢失）
seq=3 ────────────────────────► 收到，仍 ack=2  ← 重复 ACK 1
seq=4 ────────────────────────► 收到，仍 ack=2  ← 重复 ACK 2
seq=5 ────────────────────────► 收到，仍 ack=2  ← 重复 ACK 3
      ◄── 三个重复 ACK，立即重传 seq=2 ──
```

快速重传的前提是"后续的包还能到达接收方"，说明网络没完全断，只是个别包丢了。如果后续包也全丢，就只能等超时。

## 3.3 重传放大的风险

重传会在网络中多产生一份流量。如果所有接收方都在同一时刻重传，会形成**重传风暴**，把本来只是轻微拥塞的网络彻底压垮。这就是 TCP 在超时后要把拥塞窗口降到 1、重新慢启动的原因。

> **行业实践**：KCP 允许调用方选择"是否开启拥塞控制"。关闭后吞吐更高、延迟更低，但多条流共享瓶颈链路时会互相抢占，甚至把链路打崩。公网服务不要关闭拥塞控制，除非你能保证流量上限。

# 4. 去重与乱序处理

## 4.1 重复从哪来

接收方可能收到同一个序号多次，原因包括：发送方超时重传但原包其实已经到了（只是 ACK 丢了）、快速重传和超时重传同时触发、中间设备重复投递、发送方状态回滚后重发旧序号。**只要网络里存在重传，就必然存在重复**，接收方必须显式去重，否则业务会重复执行——转账两次、下单两次、扣库存两次。

## 4.2 去重窗口

最简单的方式是记录"已交付的最大序号"和"已交付的区间位图"。位图长度就是一个**滑动窗口**：窗口之外的旧序号直接丢弃（判定为重复或过期），窗口之内的新序号按位置标记。

```text
期望序号 = 100
收到 102 → 缓存数据，仍等待 100
收到 100 → 交付 100，期望变 101
收到 101 → 连续交付 101、102，期望变 103
```

实现上用 `TreeMap<Long, byte[]>` 保存乱序包，用一个 `expected` 指针表示下一个期望序号：小于 `expected` 的直接丢弃，大于等于 `expected + windowSize` 的也丢弃，其余放入 `TreeMap`，然后从 `expected` 开始连续取出交付。

**设计考量**：窗口大小的选择是延迟与内存的权衡。窗口越大，能容纳的乱序包越多，内存占用也越大；窗口太小，稍一乱序就会丢包，触发重传。

## 4.3 乱序重组

乱序本身不是错误，但如果业务对顺序敏感，就必须等缺口补齐再交付。这里有一个关键决策：**要不要为了等一个丢失的包而阻塞后续交付？**

| 策略 | 行为 | 适用 |
|------|------|------|
| 严格按序 | 缺口不补，后面全部缓存 | 文件、配置同步 |
| 允许跳过 | 超过等待阈值就跳过缺口 | 音视频、实时状态 |
| 完全无序 | 只去重，按到达顺序交付 | 幂等的独立事件 |

> **行业实践**：游戏的位置同步包通常"只发最新状态"，旧序号丢了就丢了。而可靠消息通道（聊天、指令）必须严格按序。同一个应用里可以同时存在两种通道，用不同的可靠性等级区分。

# 5. 滑动窗口与流量控制

## 5.1 发送窗口

如果每发一条就等一个 ACK，吞吐会被 RTT 限制死。滑动窗口允许发送方在未收到确认前连续发送一批数据：

```text
┌──────────┬──────────────┬──────────────┬──────────────┐
│ 已确认    │ 已发送未确认   │ 可发送未发送   │ 不可发送      │
└──────────┴──────────────┴──────────────┴──────────────┘
            ←────── 发送窗口 ──────→
```

发送方维护三个指针：已确认位置、已发送位置、窗口右边界。每收到一个 ACK，窗口右移。吞吐上限约为 `窗口大小 / RTT`，这就是**带宽时延积**：RTT 40ms、带宽 100Mbps 的链路要跑满需要约 500KB 窗口，窗口设小了怎么优化代码都上不去。

## 5.2 接收窗口与通告

接收方在 ACK 里携带"我还能接收多少"，发送方据此调整发送量，这就是**流量控制**。接收缓冲区快满时通告窗口趋近 0，发送方暂停并定期探测。

```text
接收方                      发送方
缓冲区剩余 64KB  ──ACK(win=64K)──►  可以继续发 64KB
缓冲区剩余 4KB   ──ACK(win=4K)───►  只剩 4KB 额度
缓冲区满         ──ACK(win=0)────►  暂停，定期发探测包
```

**设计考量**：UDP 没有内核帮忙做流量控制，接收缓冲区是应用自己管理的队列。可靠层必须把"通告窗口"和"实际队列容量"严格对应，否则发送方会一直发，直到接收方 OOM。

## 5.3 与 TCP 的差异

| 维度 | TCP | 典型可靠 UDP |
|------|-----|---------------|
| 窗口单位 | 字节 | 消息条数或字节，可区分优先级 |
| 拥塞信号 | 丢包、ECN | 丢包、RTT、显式反馈 |
| 重传粒度 | 按段 | 按消息，可只重传关键帧 |
| 队头阻塞 | 全连接共享 | 可按流或通道隔离 |
| 参数调整 | 内核态，受限 | 用户态，完全可控 |

# 6. 拥塞控制边界

## 6.1 为什么不能照搬 TCP

TCP 的拥塞控制假设"丢包等于拥塞"，这在有线网络里大致成立，但在 Wi-Fi、移动网络、卫星链路上经常不成立：随机误码也会丢包，一见丢包就减半，吞吐会被误码拖垮。可靠 UDP 可以把丢包率、RTT、ECN、应用层反馈组合起来判断，这是它相对 TCP 的灵活之处。

## 6.2 常见做法

| 算法 | 思路 | 代表 |
|------|------|------|
| 类似 Reno/CUBIC | 丢包驱动，窗口增减 | 早期可靠 UDP 实现 |
| BBR 类 | 建模带宽与最小 RTT，不把丢包当唯一信号 | QUIC 的 BBR 变体 |
| 固定速率 | 应用给定发送速率 | 内网监控上报 |
| 令牌桶限速 | 控制平均速率与突发 | 日志、指标采集 |

## 6.3 无拥塞控制的后果

如果不做拥塞控制，发送方会以应用能产生的最大速率发包。一旦超过瓶颈链路容量，中间队列被填满，开始大量丢包，重传又进一步增加流量，形成**拥塞崩溃**：吞吐趋近于 0，延迟飙升。

```text
无拥塞控制：发送速率 ↑ → 队列满 → 丢包 ↑ → 重传 ↑ → 崩溃
有拥塞控制：发送速率 ↑ → 检测到丢包 → 降速 → 队列排空 → 恢复
```

**注意**：即使在内网，也要给发送速率设上限。一个写错的重传循环可以在几秒内把交换机端口打满。

# 7. 一个可运行的最小可靠层

## 7.1 报文格式

下面实现一个只支持"按序、去重、超时重传"的简化版本，不包含窗口和拥塞控制，用于理解机制，不要直接用于生产。

```text
┌────────┬────────┬──────────┬──────────────┐
│ 类型 1B │ 序号 4B │ 确认号 4B │ 载荷 N 字节   │
│ 1=DATA │        │          │              │
│ 2=ACK  │        │          │              │
└────────┴────────┴──────────┴──────────────┘
```

## 7.2 核心逻辑

```java
import java.net.*;
import java.nio.ByteBuffer;

public class MiniReliable {
    private static final byte DATA = 1, ACK = 2;
    private final DatagramSocket socket;
    private final InetSocketAddress peer;
    private long nextSeq = 1, expected = 1;   // 发送序号 / 接收期望

    public MiniReliable(DatagramSocket socket, InetSocketAddress peer) {
        this.socket = socket;
        this.peer = peer;
    }

    private byte[] frame(byte type, long seq, long ack, byte[] body) {
        return ByteBuffer.allocate(9 + body.length)
                .put(type).putLong(seq).putLong(ack).put(body).array();
    }

    /** 发送并等待确认，超时重传一次；真实实现应异步 + 指数退避 */
    public void send(byte[] body) throws Exception {
        long seq = nextSeq++;
        byte[] data = frame(DATA, seq, 0, body);
        socket.send(new DatagramPacket(data, data.length, peer));
        socket.setSoTimeout(1000);
        byte[] buf = new byte[64];
        try {
            while (true) {
                DatagramPacket p = new DatagramPacket(buf, buf.length);
                socket.receive(p);
                ByteBuffer bb = ByteBuffer.wrap(p.getData(), p.getOffset(), p.getLength());
                if (bb.get() != ACK) continue;
                bb.getLong();                        // 跳过对端序号
                if (bb.getLong() >= seq) return;     // 收到累计确认
            }
        } catch (SocketTimeoutException e) {
            socket.send(new DatagramPacket(data, data.length, peer));  // 重传
        }
    }
}
```

接收端的循环同样用 `ByteBuffer` 解帧：若 `seq == expected` 就交付并自增，然后无论是否交付都回一个 `ack=expected` 的确认包；`seq < expected` 视为重复包直接丢弃，但仍要回 ACK，避免发送方一直重传。

## 7.3 局限

这段代码只实现了"按序、去重、超时重传"，和工程实现还差很多：没有发送窗口，每条消息串行等待 ACK，吞吐受 RTT 限制；没有乱序缓存，乱序包被丢弃后触发不必要重传；RTO 固定 1 秒且只重传一次，低延迟链路恢复慢、高延迟链路误重传，持续丢包时也可能无限重传；没有拥塞控制，多流并发时不会退让；也没有处理序号回绕。

**设计考量**：真正可用的实现，建议参考 KCP 源码或 QUIC 规范。它们的价值不在于代码量，而在于把上面每一项边界条件都处理过了——尤其是序号回绕、RTO 异常值、窗口为 0 时的探测。

# 8. 常见错误

| 错误 | 后果 | 正确做法 |
|------|------|----------|
| 只用超时重传，不做快速重传 | 丢包后至少等一个 RTO | 结合重复 ACK 或 NACK |
| RTO 固定不变 | 高延迟误重传，低延迟恢复慢 | 动态估算 + 指数退避 |
| 无重试上限 | 对端下线后无限重传 | 限制次数并通知应用层 |
| 接收方不去重 | 业务重复执行 | 序号窗口 + 幂等键 |
| 窗口无限大 | 接收队列 OOM | 通告窗口与队列容量绑定 |
| 序号比较用 `>` | 回绕后判定错误 | 模运算比较 |
| 无拥塞控制 | 多流竞争时拥塞崩溃 | 至少做速率上限 |
| 重传原包不更新序号 | 接收方无法区分新旧 | 重传带原序号，配合去重 |

# 9. 练习与自检

**练习一**：把 `send` 改成异步：单独一个线程处理 ACK，发送方把 `seq` 放入 `inFlight` 后立即返回。思考为什么真实实现需要"发送窗口"而不是"一次只在途一条"。

**练习二**：给接收端加上乱序缓存，用 `TreeMap` 保存 `seq > expected` 的包。故意丢弃序号 2，让 3、4 先到，验证补齐后能一次交付 2、3、4。

**练习三**：把固定 1 秒超时改成基于 RTT 的动态 RTO，用两倍的 `SRTT` 作为初始值，观察在人为延迟（用 `tc` 或代理）下的重传次数变化。

自检问题：累计确认和选择确认各适合什么场景？为什么重传必须保留原序号？滑动窗口大小和带宽时延积是什么关系？

# 10. 小结

| 主题 | 记住这一句 |
|------|-----------|
| 序号 | 按消息或按字节编号，窗口和去重都依赖它 |
| 确认 | 累计确认简单，SACK 能避免无谓重传 |
| 重传 | 动态 RTO 兜底，快速重传降低延迟，必须指数退避 |
| 去重 | 有重传就必然有重复，接收方必须显式去重 |
| 滑动窗口 | 窗口大小决定吞吐上限，约等于带宽时延积 |
| 拥塞控制 | 不做会拥塞崩溃，做得好才能多流公平共存 |
| 工程实现 | 优先用 QUIC/KCP，自研要补齐回绕、退避、探测等边界 |

可靠层解决的是"点对点、单播、能建立会话"的场景。但很多 UDP 应用面对的是"一个包发给一群主机"——局域网设备发现、直播分发、集群心跳。下一篇进入广播与组播，讲清 `MulticastSocket`、IGMP 和 TTL 这些只在 UDP 世界里才存在的机制。
