HTTP/2 和 HTTP/3 解决的是 HTTP/1.1 在高并发、弱网下的性能瓶颈。本篇用初学者能理解的顺序讲清二进制分帧、多路复用、头部压缩和 QUIC，并说明 Java 中如何启用和验证这些协议。

# 1. HTTP/1.1 的瓶颈

HTTP/1.1 有三个典型问题：

1. **应用层队头阻塞**：同一连接上的响应必须按请求顺序返回，前一个慢会拖住后面。
2. **头部冗余**：每次请求都重复发送大量相同的头，例如 `User-Agent`、`Cookie`。
3. **连接数限制**：浏览器通常对同一域名限制 6-8 个并发连接，超过后请求排队。

```text
HTTP/1.1：每个连接一次只能等一个响应
连接 1: 请求 A ────────> 响应 A
连接 2: 请求 B ────────> 响应 B
连接 3: 请求 C ────────> 响应 C
```

为了绕过限制，常见做法是域名分片、雪碧图、资源合并，但这些都是在规避协议限制，而不是真正解决。

# 2. HTTP/2

## 2.1 二进制分帧

HTTP/2 把报文拆成二进制帧：

```text
HTTP/1.1 文本：
GET /users HTTP/1.1
Host: example.com

HTTP/2 帧：
┌──────────────┬──────────────┬──────────────┐
│ Frame Header │ Frame Payload│ ...          │
└──────────────┴──────────────┴──────────────┘
```

核心概念：

| 概念 | 含义 |
|------|------|
| 帧（frame） | HTTP/2 的最小传输单位 |
| 流（stream） | 一次请求-响应对应的逻辑通道 |
| 消息（message） | 一个完整的请求或响应，由多个帧组成 |

二进制协议比文本协议更容易解析，也更容易扩展。帧头中包含流 ID，接收方据此把帧组装回不同的请求和响应。

## 2.2 多路复用

一条 TCP 连接上可以同时打开多个流：

```text
一条 TCP 连接
├── Stream 1: 请求 A ──> 响应 A
├── Stream 2: 请求 B ──> 响应 B
└── Stream 3: 请求 C ──> 响应 C
```

帧可以交错发送，响应不必按请求顺序返回。这样只需要少量连接就能承载大量并发请求，减少了握手和连接管理开销。

但 HTTP/2 并没有解决所有问题：

- 底层仍是 TCP，TCP 丢包会导致所有流等待重传。
- 服务端和客户端都需要支持 HTTP/2。
- 某些代理和网关可能只支持 HTTP/1.1。

## 2.3 头部压缩

HTTP/2 使用 HPACK 压缩头部：

- **静态表**：预定义了常见头部，例如 `:method: GET`、`content-type`。
- **动态表**：连接双方维护已发送的头部，后续用索引引用。
- **哈夫曼编码**：进一步压缩字符串。

效果是重复头部不再每次完整传输，尤其对 Cookie 较多的请求收益明显。

## 2.4 服务端推送

服务端可以在客户端请求 HTML 时主动推送 CSS、JS 等资源，减少往返：

```text
客户端请求 index.html
        │
        ▼
服务端响应 index.html
同时推送 style.css、app.js
```

但服务端推送在实际中较难用好：

- 客户端可能已经缓存了资源，推送造成浪费。
- 推送资源与客户端解析 HTML 的时机难以协调。
- 主流浏览器已逐步移除对 HTTP/2 Server Push 的支持。

现代替代方案通常是 `preload`、`preconnect` 和更合理的资源加载策略。

# 3. HTTP/3

## 3.1 QUIC 与 UDP

HTTP/3 基于 QUIC，QUIC 运行在 UDP 之上：

```text
HTTP/1.1、HTTP/2 → TCP → IP
HTTP/3          → QUIC → UDP → IP
```

QUIC 在用户态实现可靠性、加密、拥塞控制和多路复用。这样做的好处：

- 不需要修改操作系统内核和中间设备。
- 每个流独立处理丢包，避免 TCP 层的队头阻塞。
- 建连和加密合并，减少握手往返。
- 支持连接迁移。

QUIC 默认加密，TLS 1.3 集成在握手过程中，减少了协议层数。

## 3.2 0-RTT 与连接迁移

**0-RTT** 允许客户端在恢复连接时立即发送数据，不必等待完整握手：

```text
首次连接：完整握手
后续连接：客户端直接发送 0-RTT 数据
```

收益是降低延迟，但存在**重放风险**：攻击者可能截获并重复发送 0-RTT 数据。因此 0-RTT 只适合幂等请求，例如 GET，不应直接用于支付、下单等操作。

**连接迁移**利用 QUIC 的连接 ID，而不是四元组来标识连接。手机从 Wi-Fi 切换到移动网络时，IP 变了但连接仍可继续，适合移动场景。

# 4. Java 中的支持

Java 11 `HttpClient` 支持 HTTP/2：

```java
HttpClient client = HttpClient.newBuilder()
    .version(HttpClient.Version.HTTP_2) // 优先协商 HTTP/2
    .build();

HttpResponse<String> response = client.send(
    HttpRequest.newBuilder(URI.create("https://example.com")).GET().build(),
    HttpResponse.BodyHandlers.ofString()
);

System.out.println(response.version()); // 实际协商结果可能是 HTTP_2 或 HTTP_1_1
```

注意：

- `HTTP_2` 是"优先使用"，不是强制。服务端不支持时会回退到 HTTP/1.1。
- HTTPS 场景通过 ALPN 协商协议。
- 标准 JDK `HttpClient` 目前不内置 HTTP/3 支持；需要 HTTP/3 时可使用支持 QUIC 的第三方库，或通过支持 HTTP/3 的网关/CDN 终止。
- 验证协议版本可以查看 `response.version()`，或用浏览器 DevTools 的 Protocol 列。

# 5. 选型与兼容

| 版本 | 传输层 | 主要优势 | 部署成本 | 适用场景 |
|------|--------|----------|----------|----------|
| HTTP/1.1 | TCP | 兼容性最好、调试简单 | 低 | 内部服务、老系统 |
| HTTP/2 | TCP | 多路复用、头部压缩 | 中 | 现代 Web、API 网关 |
| HTTP/3 | QUIC/UDP | 弱网性能好、连接迁移 | 高 | 移动端、跨境、弱网 |

选型建议：

- 对外 Web 服务优先启用 HTTP/2，通常由 Nginx、网关或 CDN 完成。
- 移动端、弱网场景可以评估 HTTP/3，但要确认客户端、网关和网络链路都支持。
- 内网服务不必盲目追求新协议，稳定性和可观测性更重要。

# 6. 小结

| 主题 | 要点 |
|------|------|
| HTTP/2 | 二进制分帧、多路复用、HPACK，解决应用层队头阻塞 |
| HTTP/3 | 基于 QUIC/UDP，解决 TCP 层队头阻塞，支持 0-RTT 和连接迁移 |
| Java 支持 | HttpClient 支持 HTTP/2，HTTP/3 需第三方库或网关 |
| 选型 | 结合场景、部署成本和兼容性，不只看理论性能 |
