很多接口超时、连接泄漏和性能问题，根源都在连接管理。本篇从三次握手、四次挥手讲到 Keep-Alive、连接池和超时体系，帮助初学者理解一次 HTTP 调用在连接层面的完整生命周期。

# 1. 短连接与长连接

## 1.1 三次握手与四次挥手

TCP 建立连接需要三次握手：

```text
客户端                                服务端
  │                                     │
  │ ──────── SYN (seq=x) ─────────────> │
  │                                     │
  │ <──── SYN + ACK (seq=y, ack=x+1) ── │
  │                                     │
  │ ──────── ACK (ack=y+1) ───────────> │
  │                                     │
  │            连接建立                  │
```

三次握手的目的是确认双方的发送和接收能力都正常，并同步初始序列号。只有两次不够，因为服务端无法确认客户端能收到自己的响应。

关闭连接需要四次挥手：

```text
客户端                                服务端
  │ ──────── FIN ────────────────────> │
  │ <─────── ACK ───────────────────── │
  │ <─────── FIN ───────────────────── │
  │ ──────── ACK ────────────────────> │
  │                                     │
  │            连接关闭                  │
```

主动关闭方会进入 `TIME_WAIT`，等待 2MSL 后彻底释放。`TIME_WAIT` 的作用是：

- 确保最后一个 ACK 能到达对端。
- 让旧连接的延迟报文在网络中消失，避免影响新连接。

⚠ 高并发短连接场景可能出现大量 `TIME_WAIT`，表现为端口耗尽或连接建立变慢。解决方向通常是连接复用，而不是简单调小等待时间。

## 1.2 Keep-Alive

HTTP/1.1 默认使用长连接，请求完成后不立即关闭 TCP 连接，而是保留下来复用：

```http
HTTP/1.1 200 OK
Connection: keep-alive
Keep-Alive: timeout=60, max=100
```

- `timeout`：连接空闲多久后关闭。
- `max`：该连接最多处理多少个请求。

长连接减少了握手和 TLS 开销，但会占用服务端资源。服务端通常会设置空闲超时，避免大量闲置连接堆积。

★ **关键认知**：Keep-Alive 复用的是 TCP 连接，不是 HTTP 会话。连接复用时，请求之间仍然相互独立，不能依赖连接上的隐含状态。

# 2. 连接复用

## 2.1 连接池

连接池维护一组可复用的连接，请求到来时借出，完成后归还：

```text
        ┌──────────────────────────┐
        │        连接池             │
        │  ┌────┐ ┌────┐ ┌────┐    │
        │  │ C1 │ │ C2 │ │ C3 │    │
        │  └────┘ └────┘ └────┘    │
        └───────┬──────────────────┘
                │ 借出 / 归还
                ▼
           业务请求
```

连接池的关键参数：

| 参数 | 作用 | 设置过小的后果 | 设置过大的后果 |
|------|------|----------------|----------------|
| 最大连接数 | 限制并发连接 | 请求排队、延迟升高 | 占用服务端资源、触发限流 |
| 最大空闲连接 | 保留多少空闲连接 | 频繁新建连接 | 浪费资源 |
| 空闲超时 | 空闲连接保留多久 | 频繁重建 | 连接被对端关闭后仍被使用 |
| 获取连接超时 | 等待可用连接的最长时间 | 请求长时间挂起 | 快速失败，但可能误伤 |

连接池不是越大越好。下游服务的处理能力有限，连接池过大只会把压力更快地传过去。

## 2.2 队头阻塞

HTTP/1.1 的管道化要求响应按请求顺序返回。如果第一个请求很慢，后面的响应都要等待，这就是应用层队头阻塞：

```text
请求 A ──> 处理很慢 ──────────────> 响应 A
请求 B ──> 已处理完 ── 等待 A ────> 响应 B
请求 C ──> 已处理完 ── 等待 B ────> 响应 C
```

HTTP/2 通过多路复用在一条连接上并行多个流，缓解了应用层队头阻塞。但底层 TCP 丢包时，所有流仍会受影响，直到丢包重传完成。

# 3. 超时体系

## 3.1 连接、读取、写入超时

| 超时 | 含义 | 典型值 | 设置过长的后果 |
|------|------|--------|----------------|
| 连接超时 | 建立 TCP 连接的最长时间 | 1-5 秒 | 网络故障时请求长时间挂起 |
| 读取超时 | 等待响应数据的最长时间 | 5-30 秒 | 下游变慢时线程被占满 |
| 写入超时 | 发送请求体的最长时间 | 5-30 秒 | 大请求上传卡住 |
| 整体请求超时 | 从发起到完成的总时间 | 根据业务 | 无法及时释放资源 |

★ **关键认知**：连接超时和读取超时是两件事。连接超时只覆盖握手阶段，连接建立后服务端迟迟不返回数据，属于读取超时。只设置其中一个，仍可能出现请求无限等待。

## 3.2 重试与幂等

重试只应针对**可恢复的瞬时错误**，例如连接超时、502、503。以下情况不应盲目重试：

- 400、401、403、404 等客户端错误，重试也不会成功。
- POST 创建订单、支付等非幂等操作。
- 下游已经过载，重试会加剧雪崩。

重试策略：

```text
第 1 次失败 → 等待 100ms + 随机抖动
第 2 次失败 → 等待 200ms + 随机抖动
第 3 次失败 → 放弃并返回错误
```

随机抖动（jitter）用于避免大量客户端在同一时刻重试。对非幂等操作，使用幂等键让服务端识别重复请求。

# 4. Java 客户端连接池实践

Java 11 `HttpClient` 的连接池配置：

```java
HttpClient client = HttpClient.newBuilder()
    .connectTimeout(Duration.ofSeconds(3)) // 连接超时
    .version(HttpClient.Version.HTTP_2)    // 优先使用 HTTP/2
    .build();

HttpRequest request = HttpRequest.newBuilder()
    .uri(URI.create("https://example.com/api/users"))
    .timeout(Duration.ofSeconds(10))       // 单次请求超时
    .GET()
    .build();

HttpResponse<String> response = client.send(
    request,
    HttpResponse.BodyHandlers.ofString()
);
```

OkHttp 的连接池配置：

```java
ConnectionPool pool = new ConnectionPool(
    20,                      // 最大空闲连接数
    5, TimeUnit.MINUTES      // 空闲连接保留时间
);

OkHttpClient client = new OkHttpClient.Builder()
    .connectionPool(pool)
    .connectTimeout(3, TimeUnit.SECONDS)
    .readTimeout(10, TimeUnit.SECONDS)
    .writeTimeout(10, TimeUnit.SECONDS)
    .build();
```

⚠ 客户端对象通常应复用。每次请求都新建 `HttpClient` 或 `OkHttpClient` 会导致连接池、线程池反复创建和销毁，性能反而更差。

# 5. 常见错误

| 错误 | 后果 | 正确做法 |
|------|------|----------|
| 不关闭响应体 | 连接无法归还连接池 | try-with-resources 或显式关闭 |
| 只设置连接超时 | 服务端不返回时请求挂起 | 同时设置读取/请求超时 |
| 连接池过大 | 下游被打垮 | 根据下游容量设置 |
| 对 POST 盲目重试 | 重复创建、重复扣款 | 只重试幂等请求或使用幂等键 |
| 每次请求新建客户端 | 连接无法复用 | 复用客户端实例 |
| 关闭整个客户端 | 其他请求受影响 | 只在应用关闭时释放资源 |

# 6. 动手练习

用 Java 11 `HttpClient` 连续请求同一个地址 10 次，记录每次耗时：

1. 第一次请求通常包含 TCP/TLS 握手，耗时较高。
2. 后续请求复用连接，耗时应明显降低。
3. 尝试把 `HttpClient` 放到循环内部每次新建，对比耗时差异。
4. 给请求设置 1 秒超时，访问一个故意延迟的接口，观察异常类型。

# 7. 小结

| 主题 | 要点 |
|------|------|
| 连接建立 | 三次握手确认双方能力，四次挥手关闭 |
| TIME_WAIT | 保证可靠关闭和旧报文消失，不要随意缩短 |
| Keep-Alive | 复用 TCP 连接，减少握手和 TLS 开销 |
| 连接池 | 控制并发和资源，不是越大越好 |
| 超时 | 连接、读取、写入、整体超时要分别考虑 |
| 重试 | 只对幂等或可恢复错误重试，避免雪崩 |
