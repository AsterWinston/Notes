HTTP 是 Java 后端开发中最常打交道的协议，但很多初学者只会调用接口，说不清一次请求到底经过了什么。本篇从请求-响应模型和 TCP 的关系讲起，梳理 HTTP 版本演进，并说明 Java 技术栈中不同 HTTP 客户端的位置。

# 1. HTTP 是什么

## 1.1 请求-响应模型

HTTP 是一种**应用层**的请求-响应协议。客户端先发送请求，服务端处理后再返回响应，典型过程如下：

```text
浏览器 / Java 客户端                        服务端
        │                                      │
        │  1. 建立 TCP 连接（HTTPS 还要 TLS）   │
        │─────────────────────────────────────>│
        │                                      │
        │  2. 发送请求报文                      │
        │     GET /users/42 HTTP/1.1            │
        │     Host: example.com                 │
        │─────────────────────────────────────>│
        │                                      │
        │  3. 处理请求                          │
        │                                      │
        │  4. 返回响应报文                      │
        │<─────────────────────────────────────│
        │     HTTP/1.1 200 OK                   │
        │     Content-Type: application/json    │
        │     {"id":42,"name":"alice"}          │
```

一次请求至少包含：

- **请求方法**：想做什么，例如 GET、POST。
- **请求目标**：访问哪个资源，例如 `/users/42`。
- **请求头**：描述请求的元信息，例如 `Host`、`Authorization`。
- **请求体**：可选，例如 POST 的 JSON 数据。

响应包含：

- **状态码**：结果大类，例如 200、404、500。
- **响应头**：描述响应的元信息，例如 `Content-Type`、`Cache-Control`。
- **响应体**：实际数据，例如 HTML、JSON、图片。

★ **关键认知**：HTTP 本身不保存请求之间的状态。每个请求都应携带足够的信息让服务端独立处理，这也是 Cookie、Session、Token 等机制存在的原因。

## 1.2 HTTP 与 TCP 的关系

网络分层可以简化为：

```text
┌────────────────────────────┐
│ 应用层：HTTP、DNS、SMTP     │  ← 定义报文格式和交互语义
├────────────────────────────┤
│ 传输层：TCP、UDP           │  ← 负责端到端传输
├────────────────────────────┤
│ 网络层：IP                 │  ← 负责寻址和路由
└────────────────────────────┘
```

HTTP/1.1 和 HTTP/2 都运行在 TCP 之上，HTTP/3 运行在 QUIC（基于 UDP）之上。

TCP 提供的是**可靠、有序的字节流**。HTTP 在这个字节流上定义自己的报文边界：用 `Content-Length` 或分块传输标明消息体到哪里结束。因此：

- TCP 保证字节不丢失、不乱序，但不保证应用层消息完整。
- HTTP 负责把字节流解析成一个个请求和响应。
- 应用层超时、重试、幂等性，仍然需要自己设计。

# 2. HTTP 版本演进

## 2.1 HTTP/1.0 到 HTTP/1.1

HTTP/1.0 默认每个请求使用一个 TCP 连接，请求完成后关闭。频繁请求会反复经历握手和挥手，开销很大。

HTTP/1.1 的主要改进：

- **默认长连接**：通过 `Connection: keep-alive` 复用 TCP 连接。
- **管道化**：允许连续发送多个请求，但响应必须按顺序返回。
- **Host 头**：支持同一 IP 上托管多个域名。
- **分块传输编码**：服务端可以在不知道总长度时边生成边发送。
- **更多缓存控制**：`Cache-Control`、`ETag` 等。

管道化并没有真正解决队头阻塞：前一个响应慢，后面的响应仍然要等待。因此浏览器通常不会大量使用管道化，而是为同一域名建立多个连接。

## 2.2 HTTP/2

HTTP/2 的核心变化是**二进制分帧**和**多路复用**：

- 一条 TCP 连接上可以同时存在多个流（stream）。
- 每个流由多个帧（frame）组成，帧可以交错发送。
- 响应不再必须严格按请求顺序返回。
- 使用 HPACK 压缩头部，减少重复头部带来的开销。

HTTP/2 解决了 HTTP/1.1 的应用层队头阻塞，但底层仍然是 TCP：如果 TCP 丢包，所有流都会受影响。这就是 HTTP/3 出现的原因。

## 2.3 HTTP/3 与 QUIC

HTTP/3 基于 QUIC，QUIC 运行在 UDP 之上，把可靠性、加密和拥塞控制放到用户态实现：

- 避免 TCP 层的队头阻塞，一个流丢包不一定影响其他流。
- 支持 0-RTT 建连，减少重复连接开销。
- 支持连接迁移，例如手机从 Wi-Fi 切换到移动网络时保持连接。

但 0-RTT 有重放风险，不是所有请求都适合。HTTP/3 的部署还依赖客户端、服务端、网关和网络的共同支持。

# 3. 在 Java 技术栈中的位置

## 3.1 浏览器、网关、服务端

一个常见的 Java Web 链路：

```text
浏览器
  │ HTTPS
  ▼
Nginx / API 网关
  │ HTTP 或 HTTPS
  ▼
Spring Boot 服务
  │
  ├── 数据库
  ├── Redis
  └── 其他微服务
```

- 浏览器负责同源策略、缓存、Cookie 和 TLS 校验。
- 网关负责 TLS 终止、路由、限流、鉴权和日志。
- Spring Boot 负责业务处理。
- 服务间通信可能是 HTTP、gRPC 或消息队列。

理解每一层由谁负责，排查问题时才不会把网关配置错误误判成 Java 代码问题。

## 3.2 常见 Java HTTP 客户端

| 客户端 | 特点 | 适用场景 |
|--------|------|----------|
| `HttpURLConnection` | JDK 自带，API 较老 | 简单请求、无第三方依赖 |
| Java 11 `HttpClient` | JDK 自带，支持同步/异步、HTTP/2 | 现代 Java 项目首选 |
| OkHttp | 连接池、拦截器、生态成熟 | Android、需要拦截器和服务端调用 |
| Apache HttpClient | 连接管理完善、企业项目常见 | 复杂连接池、老项目 |

初学建议先掌握 Java 11 `HttpClient`，再了解 OkHttp 的拦截器模型。不要同时学四套 API，先把 HTTP 本身理解清楚。

# 4. 学习路线与工具

建议阅读顺序：

1. 报文与状态码：知道一次请求长什么样。
2. 连接管理：理解 Keep-Alive、连接池和超时。
3. HTTPS：理解证书和 TLS 握手。
4. 缓存与 Cookie：理解浏览器行为。
5. Java 客户端：把协议知识落到代码。
6. 跨域与安全：理解前后端联调中的边界。

常用工具：

- `curl`：构造请求、查看响应头、测量耗时。
- 浏览器 DevTools：查看请求头、响应、Timing、Cookie。
- Wireshark：抓包分析 TCP/TLS，适合排查底层问题。
- `openssl s_client`：查看证书链和 TLS 握手细节。

# 5. 小结

| 主题 | 要点 |
|------|------|
| HTTP 定位 | 应用层请求-响应协议，依赖 TCP 或 QUIC 传输 |
| 版本演进 | 1.1 长连接、2 多路复用、3 基于 QUIC 解决 TCP 队头阻塞 |
| Java 客户端 | 初学优先 Java 11 HttpClient，复杂场景再看 OkHttp/Apache |
| 排查思路 | 先分清楚问题在浏览器、网关、网络还是 Java 服务 |
