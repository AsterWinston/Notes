
# 1. 什么是Jenkins

Jenkins 是一个开源的**持续集成（Continuous Integration，CI）**和**持续交付/部署（Continuous Delivery/Deployment，CD）**自动化服务器。它由 Kohsuke Kawaguchi（川口耕介）于 2004 年创建，最初是作为 Hudson 项目开发，后于 2011 年从 Oracle 分离并更名为 Jenkins。

核心定位：**自动化一切构建、测试、部署相关的重复性工作**。

# 2. 为什么需要Jenkins

在没有持续集成工具的软件开发时代，团队面临以下痛点：

| 痛点 | 描述 |
|------|------|
| **集成地狱** | 开发周期结束时才合并代码，冲突频繁且难以定位 |
| **手动构建部署** | 开发人员手动执行编译、测试、打包、部署，效率低且易出错 |
| **反馈延迟** | 代码提交到发现问题的周期过长（可能数天或数周） |
| **环境不一致** | 开发、测试、生产环境配置不同，导致"在我机器上能运行" |
| **重复劳动** | 每次发布执行相同的手工操作，耗时且无聊 |

Jenkins 解决了这些问题：
- **自动化CI流程**：代码提交即触发构建→测试→反馈，缩短反馈周期
- **流水线化CD流程**：从编译到部署全流程自动化，减少人工介入
- **插件化生态**：1000+ 插件支持几乎所有开发工具的集成
- **分布式架构**：Master/Agent 架构，支持大规模并行构建
- **Pipeline as Code**：用代码定义构建流程，可版本化管理

# 3. CI/CD基础概念

## 3.1 持续集成（CI）

持续集成是指开发人员频繁地将代码合并到主干（trunk/main），每次合并都通过自动化构建（包括编译、测试、静态分析等）来验证，从而尽早发现集成问题。

CI 的核心实践：
- **频繁提交**：每天多次提交代码到主干
- **每次提交都触发构建**：确保每次变更都经过验证
- **快速反馈**：构建失败立即通知相关开发人员
- **保持构建绿色**：不允许失败的构建长期存在
- **自动化测试**：单元测试、集成测试自动化执行

## 3.2 持续交付（CD）

持续交付是在持续集成的基础上，确保软件可以随时被可靠地发布到生产环境。代码经过 CI 验证后，自动部署到类生产环境（如测试环境、预发布环境），经过验收测试后，只需要人工确认即可发布到生产环境。

## 3.3 持续部署（Continuous Deployment）

持续部署是持续交付的进一步延伸，将通过所有自动化测试的代码**自动部署到生产环境**，整个过程无需人工干预。这要求测试覆盖率足够高、测试质量足够好。

## 3.4 三者的区别

| 概念 | 阶段 | 人工介入 |
|------|------|---------|
| 持续集成（CI） | 构建+测试 | 无（自动触发） |
| 持续交付（CD） | CI + 交付到类生产环境 | 发布到生产需要人工确认 |
| 持续部署（Continuous Deployment） | CI + 部署到生产 | 全过程无人工介入 |

# 4. Jenkins发展历史

| 时间 | 事件 |
|------|------|
| 2004 | Kohsuke Kawaguchi 在 Sun Microsystems 创建 Hudson |
| 2007 | Hudson 成为最流行的 CI 工具 |
| 2010 | Oracle 收购 Sun，Hudson 归属 Oracle |
| 2011.1 | Hudson 社区与 Oracle 产生分歧，投票更名为 Jenkins |
| 2011.2 | Jenkins 1.0 发布，Hudson 继续存在但逐渐消亡 |
| 2014 | Jenkins 1.580 引入 Pipeline Plugin（Workflow） |
| 2016 | Jenkins 2.0 发布，Declarative Pipeline 成为默认 |
| 2017 | Blue Ocean 界面发布，Pipeline 可视化编辑 |
| 2018 | Jenkins X 发布（面向 Kubernetes 的 CI/CD 解决方案） |
| 2020 | Jenkins 2.235+ 全面推荐 Pipeline，传统 FreeStyle 仍支持 |
| 2022 | Jenkins 2.346+ 提升 Java 11 最低要求，逐步淘汰 Java 8 |
| 2023+ | 持续演进，聚焦 Kubernetes 集成、云原生、可观测性 |

# 5. Jenkins的核心特性

| 特性 | 说明 |
|------|------|
| **Pipeline as Code** | 使用 Jenkinsfile 定义构建流程，支持声明式和脚本式语法 |
| **Master/Agent 架构** | 支持分布式构建，Master 负责任务调度，Agent 执行具体任务 |
| **插件生态** | 1000+ 插件覆盖 SCM、构建工具、测试框架、部署平台、通知等 |
| **Web UI** | 友好的 Web 管理界面，支持配置、监控、管理等操作 |
| **REST API** | 提供完善的 API 接口，支持外部系统集成和自动化管理 |
| **安全机制** | 支持认证（LDAP/SSO）、授权（Role-Based）、凭据加密 |
| **可扩展性** | 支持插件开发、共享库、自定义步骤等扩展方式 |
| **高可用** | 支持多 Master/Active-Active 架构，具备故障恢复能力 |
| **Pipeline 可视化** | Blue Ocean 提供现代化 Pipeline 可视化界面 |

## 6.1 Jenkins的优势

1. **极高的灵活性**：Pipeline 语法强大，几乎可以实现任何自动化流程
2. **丰富的插件生态**：1000+ 插件覆盖几乎所有开发工具
3. **成熟的社区**：2004年至今，积累了大量的文档、实践经验和问题解决方案
4. **完全自托管**：数据完全由自己控制，安全审计可控
5. **Master/Agent 架构**：支持大规模分布式构建
6. **Pipeline as Code**：Jenkinsfile 可以纳入版本控制，实现基础设施即代码

## 6.2 Jenkins的劣势

1. **部署维护成本高**：需要专人维护 Jenkins 服务器，插件升级、安全补丁等
2. **学习曲线陡峭**：Jenkins 的配置和 DSL 语法需要较长时间学习
3. **插件质量参差不齐**：第三方插件可能存在兼容性问题、安全问题或维护停滞
4. **UI 老旧**：传统 UI 界面不够友好（Blue Ocean 有所改善）
5. **性能问题**：大量 Pipeline 执行时，Master 可能成为瓶颈
6. **配置管理复杂**：大量配置存储在 Master 文件系统中，备份和迁移复杂性高

# 7. Jenkins的适用场景

- **企业内部DevOps平台建设**：需要完全自托管、数据安全的场景
- **复杂构建流程**：需要多平台、多环境、多步骤的复杂构建场景
- **大规模并行构建**：需要 Agent 弹性扩缩的大规模 CI 场景
- **异构环境**：需要在不同操作系统（Linux/Windows/Mac）上构建的场景
- **合规要求高**：需要详细审计日志、权限控制的企业场景
- **已有Java技术栈**：团队对 Java 生态熟悉的场景

# 10. 总体架构概览

Jenkins 采用 **Master/Agent 架构**（也称为 Controller/Agent）：

```
                        ┌─────────────────┐
                        │    Jenkins UI    │
                        │  (Web Dashboard) │
                        └────────┬─────────┘
                                 │
                        ┌────────▼─────────┐
                        │    Jenkins Master │
                        │   (Jenkins Core)  │
                        │                   │
                        │  ┌─────────────┐  │
                        │  │  Build Queue  │  │
                        │  └─────────────┘  │
                        └────────┬─────────┘
                                 │
              ┌──────────────────┼──────────────────┐
              │                  │                  │
     ┌────────▼────────┐ ┌──────▼────────┐ ┌──────▼────────┐
     │   Agent 1       │ │   Agent 2     │ │   Agent N     │
     │ (Linux)         │ │ (Windows)     │ │ (Docker/K8s)  │
     │ Maven, Docker   │ │ MSBuild, NuGet│ │ Dynamic Pods  │
     └─────────────────┘ └───────────────┘ └───────────────┘
```

- **Master（Controller）**：负责任务调度、配置管理、UI 展示、构建队列管理
- **Agent（Node）**：执行具体的构建任务，可以是物理机、虚拟机、容器或 Pod
- **构建队列**：Master 根据 Agent 的标签和可用性，将待执行的任务分配到合适的 Agent
