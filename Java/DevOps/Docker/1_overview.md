
# 1. Docker 解决了什么问题

Docker 是一个开源的容器化平台，用来将应用程序、运行时、系统工具、依赖库和配置一起打包成标准化镜像，并以容器的方式运行。它最核心的价值不是“启动一个隔离进程”本身，而是把应用交付物标准化，让开发、测试、预发和生产环境尽量保持一致。

传统部署中，一个 Java 应用能否正常运行，往往依赖很多宿主机条件：JDK 版本、系统库版本、环境变量、目录权限、启动脚本、端口占用、配置文件位置等。只要其中一个条件不一致，就容易出现“我本地能跑，线上不能跑”的问题。Docker 通过镜像把这些运行条件固化下来，使应用从“依赖某台机器”变成“依赖一个镜像”。

```text
传统部署:                        容器化部署:
┌──────────────────────┐        ┌──────────────────────┐
│       物理机/VM       │        │     物理机/VM         │
│  ┌──────────────┐    │        │  ┌────┐ ┌────┐ ┌────┐│
│  │    App A     │    │        │  │App │ │App │ │App ││
│  │  + Lib A     │    │        │  │ A  │ │ B  │ │ C  ││
│  │  + Deps A    │    │        │  │+Lib│ │+Lib│ │+Lib││
│  ├──────────────┤    │        │  └────┘ └────┘ └────┘│
│  │    App B     │    │        │   Docker Engine       │
│  │  + Lib B     │    │        ├──────────────────────┤
│  │  + Deps B    │    │        │      Host OS          │
│  ├──────────────┤    │        └──────────────────────┘
│  │    OS        │    │
│  └──────────────┘    │
└──────────────────────┘
```

从工程角度看，Docker 主要解决三个问题：

| 问题 | 传统方式的痛点 | Docker 的解决方式 |
|------|----------------|-------------------|
| 环境不一致 | 不同机器安装的软件和配置不同 | 镜像包含应用运行所需依赖 |
| 交付不标准 | 交付物可能是 jar、脚本、配置、文档的组合 | 镜像成为统一交付单元 |
| 扩缩容慢 | 新机器需要安装环境和初始化配置 | 拉取镜像即可启动容器 |

# 2. 容器的本质

容器不是一台轻量级虚拟机，而是宿主机上的一个或一组受限制的进程。Docker 利用 Linux Namespace 为进程提供隔离视图，利用 Cgroups 限制资源使用，再通过 UnionFS 提供分层文件系统。容器内看起来像有独立系统，实际上仍然共享宿主机内核。

可以把容器理解为：

```text
容器 = 隔离的进程 + 受限制的资源 + 独立的根文件系统
```

这个理解很重要。它解释了为什么容器启动很快，因为不需要启动完整操作系统；也解释了为什么容器隔离性弱于虚拟机，因为容器和宿主机共享同一个内核。

# 3. 容器 vs 虚拟机

| 维度 | 容器 Docker | 虚拟机 VMware/KVM |
|------|-------------|-------------------|
| 隔离级别 | 进程级隔离，共享宿主机内核 | 硬件级虚拟化，每个 VM 有独立内核 |
| 启动速度 | 秒级甚至毫秒级 | 通常分钟级 |
| 镜像大小 | 通常 MB 到数百 MB | 通常 GB 级 |
| 资源利用率 | 高，共享 OS 内核 | 较低，每个 VM 运行完整 OS |
| 部署密度 | 单机可运行更多实例 | 单机实例数相对较少 |
| 安全隔离 | 弱于 VM，需要额外安全加固 | 隔离边界更强 |
| 可移植性 | 高，符合 OCI 标准的镜像可跨平台运行 | 依赖虚拟化平台和系统镜像 |

容器适合解决应用交付、快速扩缩容、微服务部署和 CI/CD 环境一致性问题；虚拟机更适合强隔离、多操作系统内核并存、传统基础设施虚拟化等场景。二者不是简单替代关系，而是面向不同隔离层级的技术。

# 4. Docker 的核心优势

| 优势 | 说明 |
|------|------|
| 环境一致性 | 镜像固化运行环境，降低开发、测试、生产差异 |
| 快速交付 | 构建一次镜像，可在多个环境重复部署 |
| 快速启动 | 容器本质是进程，不需要启动完整 OS |
| 资源高效 | 多个容器共享宿主机内核，额外开销较小 |
| 版本可追溯 | 镜像 Tag、Digest、Registry 让交付物可追踪 |
| DevOps 友好 | 易于接入 CI/CD、灰度发布、自动化部署 |

需要注意的是，Docker 不能自动解决所有部署问题。应用配置管理、服务发现、负载均衡、滚动发布、故障自愈、日志采集和监控告警，通常还需要 Compose、Kubernetes、CI/CD 平台和可观测性系统配合。

# 5. Docker 核心概念

| 概念 | 说明 |
|------|------|
| Image | 镜像，应用及依赖的只读模板 |
| Container | 容器，镜像运行后的实例 |
| Dockerfile | 镜像构建脚本，描述如何生成镜像 |
| Registry | 镜像仓库，用于存储和分发镜像 |
| Volume | 数据卷，用于持久化容器数据 |
| Network | 容器网络，用于容器间和外部通信 |
| Compose | 多容器应用编排工具 |

镜像和容器的关系类似于“类和对象”。镜像是静态模板，容器是运行时实例。同一个镜像可以启动多个容器，每个容器拥有自己的运行状态、网络、可写层和生命周期。

# 6. Docker 生态

```text
┌───────────────────────────────────────────────────┐
│                  Docker 生态                       │
│                                                   │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐       │
│  │ Docker   │  │ Docker   │  │ Docker   │       │
│  │ Engine   │  │ Compose  │  │ Swarm    │       │
│  │ 容器引擎 │  │ 本地编排 │  │ 集群编排 │       │
│  └──────────┘  └──────────┘  └──────────┘       │
│                                                   │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐       │
│  │ Docker   │  │ Docker   │  │containerd│       │
│  │ Hub      │  │ Registry │  │ runc     │       │
│  │ 公共仓库 │  │ 私有仓库 │  │ OCI运行时│       │
│  └──────────┘  └──────────┘  └──────────┘       │
└───────────────────────────────────────────────────┘
```

Docker Engine 负责构建、运行和管理容器；Docker Compose 适合在单机上描述和启动多容器应用；Docker Registry 负责镜像存储和分发；containerd 和 runc 是更底层的容器运行时组件。理解这些组件的边界，有助于区分“构建镜像”“运行容器”“编排服务”分别由谁负责。

# 7. OCI 标准

OCI 是 Open Container Initiative，开放容器标准。Docker 早期推动了容器技术普及，后来将镜像格式和运行时规范标准化，使不同容器工具之间可以互操作。

| 标准 | 说明 |
|------|------|
| OCI Runtime Spec | 定义容器运行时规范，runc 是典型实现 |
| OCI Image Spec | 定义镜像格式、层、配置和元数据 |
| OCI Distribution Spec | 定义镜像在 Registry 中的分发方式 |

OCI 的意义在于避免容器生态被单一厂商绑定。只要镜像符合 OCI 规范，Docker 构建的镜像也可以被 containerd、Podman、Kubernetes 等工具使用。

# 8. Docker、Podman、containerd 对比

| 维度 | Docker | Podman | containerd |
|------|--------|--------|------------|
| 定位 | 通用容器平台 | 无守护进程容器工具 | 底层容器运行时 |
| 守护进程 | dockerd | 默认无 daemon | containerd daemon |
| Rootless | 支持 | 原生体验较好 | 不是主要使用入口 |
| Compose | Docker Compose 生态成熟 | 可使用 podman-compose | 不提供 Compose |
| Kubernetes 关系 | 构建镜像常用，运行时不再强依赖 | 更贴近 Linux/K8s 原生模型 | K8s 常用 CRI 运行时 |
| 适用场景 | 开发、本地调试、通用生产 | 安全要求更高、无 daemon 场景 | Kubernetes 节点运行时 |

Docker 更像完整产品，提供 CLI、构建、运行、网络、卷和 Compose 体验；containerd 更偏底层运行时，常作为 Kubernetes 节点运行容器的基础组件；Podman 则强调无守护进程和 rootless，适合对安全边界要求更高的 Linux 环境。

# 9. 适用场景与局限性

Docker 适合以下场景：

1. 微服务应用部署，每个服务用独立镜像交付。
2. CI/CD 流水线，使用镜像作为标准构建和发布产物。
3. 本地开发环境，快速启动 MySQL、Redis、Kafka 等依赖服务。
4. 测试环境隔离，为不同分支或不同团队提供独立运行环境。
5. Java、Go、Node.js 等服务端应用的标准化部署。

Docker 的局限性也需要明确：

1. 容器共享宿主机内核，不能像虚拟机一样运行不同内核。
2. 容器隔离弱于虚拟机，生产环境需要最小权限、资源限制和镜像扫描。
3. 单机 Docker 不负责复杂调度、自动扩缩容和跨节点故障转移。
4. 有状态服务容器化需要谨慎设计数据持久化、备份和恢复。
5. 容器不是性能优化工具，应用本身的问题不会因为容器化自动消失。
