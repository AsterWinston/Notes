
# 1. 先明确比较维度

很多“Docker vs XX”的争论之所以没有结论，是因为比较维度混在一起了。正确做法是按层次比较：

1. **打包方式**：把应用与依赖如何封装起来？
2. **运行隔离**：进程、文件系统、网络如何隔离？
3. **交付方式**：如何分发与版本化？
4. **编排治理**：多实例、多主机、HA、发布如何管理？
5. **资源与安全**：如何限制与加固？

Docker 主要解决的是“容器化打包 + 运行”这一层；编排则是另一个层次的问题（见 `17_orchestration.md`）。

# 2. Docker vs 虚拟机（VM）

## 2.1 Docker 的特点

1. 共享宿主机内核，启动快、资源开销小。
2. 镜像分层，交付效率高。
3. 适合微服务与快速迭代。

## 2.2 VM 的特点

1. 每个虚拟机有自己的操作系统内核，隔离更强。
2. 启动相对慢、资源开销大。
3. 适合强隔离、异构内核、传统虚拟化场景。

## 2.3 选择建议

1. 需要快速交付、密集部署、CI/CD：Docker 更合适。
2. 需要更强隔离、完整 OS 语义、特殊内核特性：VM 更合适。

# 3. Docker vs Podman

Podman 的常见卖点：

1. Rootless 体验更自然。
2. 无中心 daemon 模式（架构上不同）。
3. 与 OCI 生态兼容较好。

Docker 的优势：

1. 生态成熟、文档与工具链广泛。
2. 团队学习成本低，实践案例多。

选择建议：

1. 你要的是“Docker 生态与使用习惯”，Docker 仍是主流选择。
2. 如果你特别关注 rootless/daemon-less 体验，可评估 Podman。

# 4. Docker vs Kubernetes

这不是同一层次的替代关系：

1. Docker 主要解决容器构建与运行。
2. Kubernetes 解决大规模编排治理。

关系可以理解为：

```text
应用构建 -> 镜像制作（Docker） -> 单机/多机运行 -> 编排治理（Kubernetes）
```

选择建议：

1. 本地开发、测试、小规模部署：Docker/Compose 足够。
2. 多副本、跨节点、HA、发布策略：Kubernetes 更适合。

# 5. Docker vs 直接在宿主机运行

宿主机直接跑应用的缺点：

1. 依赖污染，版本冲突难控制。
2. 环境不可复制。
3. 部署/回滚/迁移困难。

Docker 的优势：

1. 环境一致性更好。
2. 更容易在 CI/CD 中标准化。
3. 回滚简单（切换镜像版本）。

# 6. 选型地图（实用版）

| 场景 | 推荐 |
|------|------|
| 开发环境一致性 | Docker + Compose |
| 单机多服务联调 | Compose |
| 小团队快速交付 | Docker/Compose |
| 企业级多集群治理 | Kubernetes |
| 强隔离传统系统 | VM |
| 偏 rootless/daemonless | Podman 可评估 |

# 7. 面试要点

| 问题 | 答题关键词 |
|------|------------|
| Docker 和 VM 的区别 | 共享内核 vs 独立内核，启动速度、隔离、资源开销 |
| Docker 和 K8s 的关系 | 不同层次：构建/运行 vs 编排治理 |
| 为什么还需要 VM | 强隔离、异构 OS、历史系统兼容 |
| Docker 的核心价值 | 一致性、可移植、可交付、可回滚 |
