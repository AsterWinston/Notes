
# 1. 先分清两类性能问题

Docker 性能通常分两类：

1. **构建性能**：`docker build` 慢，CI 慢。
2. **运行性能**：服务在容器里跑得慢，或抖动大。

两者优化手段完全不同，不要混在一起。

# 2. 构建性能优化

## 2.1 让缓存生效：Dockerfile 分层设计

原则：把“变化慢”的步骤放前面，“变化快”的步骤放后面。

常见例子（Java/Maven 思路）：

1. 先 COPY `pom.xml` 或 `build.gradle`。
2. 先下载依赖（可缓存）。
3. 再 COPY 源码并编译。

否则每次改一行代码都会导致依赖层缓存失效。

参考：`8_dockerfile_best.md`。

## 2.2 `.dockerignore` 减少上下文

构建上下文越大，上传与计算越慢。

务必排除：

1. `.git/`
2. `target/`、`build/`
3. 本地缓存与临时文件
4. 密钥与配置

## 2.3 BuildKit 缓存复用

构建慢的主要原因往往不是 CPU，而是依赖下载。

策略：

1. CI 中启用 BuildKit。
2. 配置缓存导入/导出（跨 pipeline 复用）。

参考：`15_cicd.md`。

# 3. 运行性能优化

## 3.1 CPU：限制与抖动

你要同时关注两件事：

1. 容器是否被限制（`--cpus` 太小导致节流）。
2. 宿主机是否过载（多个容器竞争 CPU）。

快速观察：

```bash
docker stats
```

参考：`12_resource_limits.md`。

## 3.2 内存：OOM 与 GC 行为

容器内存上限设置不合理会导致：

1. 频繁 GC、吞吐下降。
2. 直接 OOMKilled（进程被内核杀死）。

排查：

1. `docker inspect` 看 `State.OOMKilled`。
2. 结合应用自身 GC 日志/指标。

## 3.3 存储：OverlayFS 与随机 IO

运行时性能常见误区：

1. 把高 IO 的数据写在容器可写层（overlay2）。

建议：

1. 数据库、队列、索引等高 IO 数据放 volume（或 bind mount 到高性能磁盘）。
2. 明确磁盘与文件系统类型，避免共享盘抖动。

参考：`6_volume.md`。

## 3.4 网络：端口映射与连接路径

排查思路：

1. 服务间访问走内部网络（服务名），避免多余的 NAT 路径。
2. 如果遇到连接异常或延迟，先确认 DNS、网络模式（bridge/host）以及端口映射是否符合预期。

参考：`7_network.md`。

# 4. 性能验证：用数据说话

优化前后至少要做两件事：

1. **对比基线**：同一负载下的 QPS/延迟/错误率。
2. **确认资源边界**：CPU/内存/IO 是否触顶。

Docker 原生工具起步：

```bash
docker stats
docker events --since 30m
```

更深层的性能分析需要结合宿主机与应用层工具（这章不展开平台栈）。

# 5. 常见反模式

1. 不设资源限制：出现抖动时难定位根因。
2. 只看容器内指标，不看宿主机是否过载。
3. 数据写在容器可写层导致 IO 性能差。
4. 把构建慢归因于“Docker 慢”，但实际是上下文过大与缓存失效。

# 6. 面试要点

| 问题 | 答题关键词 |
|------|------------|
| 构建慢怎么优化 | Dockerfile 分层、.dockerignore、BuildKit 缓存 |
| 运行慢先看什么 | docker stats（CPU/内存/IO/网络） |
| 为什么 volume 可能更快 | 避免写入 overlay 可写层，减少叠加开销 |
| OOM 怎么排查 | inspect OOMKilled + 宿主机 OOM 日志 + 应用 GC |
