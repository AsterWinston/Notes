
> 版本说明：本文档基于 **Nginx 1.24.x / 1.26.x**（Stable/Mainline），操作系统以 Linux（CentOS 7+/Ubuntu 20.04+）为主。

Nginx 几乎已经是 Java 后端架构中的事实标准：Tomcat / Spring Boot 集群前面的 SSL 终结、静态资源托管、API 入口与负载均衡，通常都由它承担。本篇回答两个问题——Nginx 是什么、它凭什么能扛住高并发，即进程模型与事件驱动机制；随后与 Apache / Tomcat 做横向对比，梳理生态与版本选择，为后续各篇打下基础。

---

# 1. 什么是 Nginx

- **Nginx**（engine x）是一款高性能的 **HTTP 服务器** 和 **反向代理服务器**，同时支持 **IMAP/POP3/SMTP 邮件代理**。
- 由俄罗斯程序员 **Igor Sysoev** 于 2004 年发布，采用 **事件驱动（Event-Driven）** 架构，专门为解决 **C10K 问题**（单机万级并发连接）而设计。

理解 Nginx 的定位，关键在区分"处理连接"和"执行业务"两件事。一条 HTTP 请求的生命周期里，绝大部分时间其实花在**等待**上——等待客户端发完请求体、等待后端数据库返回、等待响应发回客户端。Nginx 的设计目标是把这些"等待"管理好，而不是在这些"等待"之间插入计算。所以它的核心能力是**以极低的内存和 CPU 代价维持海量并发连接**，动态逻辑则反向代理交给后端应用。

| 特性 | 说明 |
|------|------|
| 高性能 | 单机可支撑数万甚至十万级并发连接 |
| 低内存消耗 | 基于异步非阻塞模型，内存占用远低于传统多进程模型 |
| 热部署 | 支持平滑升级、不停机修改配置 |
| 模块化 | 核心精简，功能通过模块扩展（官方/第三方） |
| 生态丰富 | OpenResty、Tengine、Kong 等二次开发版本 |

C10K 问题在 2004 年前后之所以是难题，是因为当时主流服务器（Apache prefork、早期 IIS）普遍采用**每连接一进程/一线程**的模型：并发连接数直接等于进程或线程数，每个线程默认栈就是 MB 级，上下文切换开销随并发数线性甚至超线性增长。Nginx 反其道而行——连接数与"执行单元"数解耦，用**一个固定的 worker 进程数**去服务任意多的连接，这才是它高并发的本质。

> **注意**：Nginx 的高并发指的是**并发连接数**，不等于业务计算能力。CPU 密集的动态内容（模板渲染、序列化大对象）仍应放到后端应用或做缓存，把 Nginx 当"万能应用服务器"用是常见的架构误用。

# 2. 架构：多进程模型与事件驱动

## 2.1 Master / Worker 多进程模型

Nginx 启动后以 **Master-Worker 多进程**方式运行，进程之间职责严格分离：

```text
                     ┌──────────────────┐
                     │    Master 进程    │  读/验配置、绑定端口、
                     │                  │  fork 并管理 Worker、处理信号
                     └────────┬─────────┘
            fork（不处理请求） │ 信号控制：HUP/USR2/QUIT/WINCH
      ┌───────────┬───────────┼───────────┬───────────┐
      ▼           ▼           ▼           ▼           ▼
 ┌─────────┐ ┌─────────┐ ┌─────────┐ ┌─────────┐
 │Worker 1 │ │Worker 2 │ │Worker 3 │ │Worker N │   各自运行独立事件循环
 │ (epoll) │ │ (epoll) │ │ (epoll) │ │ (epoll) │   互不共享连接
 └─────────┘ └─────────┘ └─────────┘ └─────────┘
```

**Master 进程不处理任何网络请求**，它只负责四件事：解析并校验配置、绑定监听端口、fork/回收 Worker、响应外部信号。真正的请求处理全部在 Worker 中完成，每个 Worker 是一个单线程事件循环，Worker 之间通过独立的监听 socket 竞争接受连接（新版默认 `reuseport` 可让每个 Worker 拥有独立监听队列），不存在连接所有权共享，因此不需要加锁。

**设计考量**：

- **多进程而非多线程**：一个 Worker 崩溃只影响自己持有的连接，Master 感知退出后立即补齐新 Worker，故障隔离干净；进程间无共享内存，从根上回避了锁竞争与内存安全问题。
- **worker_processes auto**：与 CPU 核数 1:1 绑定，让每个 Worker 独占一个核的缓存与时间片，减少上下文切换；超过核数不会提升吞吐，反而增加调度开销。
- **容量估算**：对外最大并发 ≈ `worker_processes × worker_connections`。但注意**反向代理场景一条客户端连接会占用两个连接位**（client→Nginx 与 Nginx→upstream 各占一个 fd），估算对外承载时要除以 2。

> **注意**：`worker_connections` 受进程文件描述符上限约束，两者必须一起调大——同时修改系统级 `ulimit -n`（或 systemd unit 里的 `LimitNOFILE`）和 Nginx 的 `worker_rlimit_nofile`，否则压测时会看到大量 "Too many open files" 错误写入 error.log。

## 2.2 epoll 事件驱动

Worker 内部是**单线程 + 非阻塞 I/O + epoll**（Linux；BSD 系为 kqueue，Solaris 为 eventport）的事件循环：所有 fd 注册进一个 epoll 实例，线程阻塞在 `epoll_wait` 上，内核把"就绪事件"批量返回，Worker 逐个处理，处理逻辑本身极短，绝不在此阻塞。

```text
loop:
    events = epoll_wait(epfd)         // 等待内核返回就绪的 fd 事件
    for ev in events:
        if 可读:  收数据 → 解析协议 → location 路由 → 回文件/转发后端
        if 可写:  继续发送该连接的响应缓冲
    处理到期定时器（keepalive 超时、proxy_read_timeout 等）
```

这样一条连接在"等待"阶段**不消耗任何执行单元**，它的存在形式只是内核里的一个 fd 加 Nginx 进程中的一个连接结构体，内存开销在 KB 量级。对比线程模型：10 万连接若每线程 8 MB 栈需要 800 GB 内存，而 Nginx 维持 10 万空闲连接通常只需百 MB 级内存——这就是同年代 Apache 无法企及的数量级差距。

> **行业实践**：Java 世界的 Netty/Tomcat NIO 与 Nginx 是同一套思想（多路复用 + 事件循环 + 非阻塞），理解了本篇的 epoll 模型，再看 Netty 的 EventLoop 与 Reactor 模型会非常快——面试中也常被要求对比这两者。

# 3. Nginx 主要应用场景

Nginx 在架构中的角色可以一句话概括：**站在应用前面的"流量管家"**。凡是与"连接、协议、加密、路由、分发"有关而与"业务计算"无关的事，都适合放到 Nginx 层统一做。

| 场景 | 说明 |
|------|------|
| **静态资源服务器** | 高效处理 HTML、CSS、JS、图片、视频等静态文件 |
| **反向代理** | 隐藏后端服务器，统一入口，分发请求 |
| **负载均衡** | 将请求分发到多台后端服务器，提高可用性 |
| **SSL 终结** | HTTPS 证书集中管理，后端 HTTP 通信 |
| **HTTP 缓存** | 缓存后端响应，加速访问 |
| **API 网关** | 鉴权、限流、日志、协议转换 |
| **四层代理** | TCP/UDP 流转发（Stream 模块） |
| **WebSocket 代理** | WebSocket 反向代理与负载均衡 |

其中"SSL 终结 + 反向代理"组合对 Java 体系价值最大：证书只在 Nginx 一处维护，后端 Tomcat/Spring Boot 之间走明文 HTTP，省去每台应用服务器配证书、升级 JDK TLS 支持的运维负担；同时慢客户端的数据收发由 Nginx 的非阻塞模型吸收，后端应用线程只面对"已经收完请求的快速代理"，Tomcat 的线程池压力显著下降。

# 4. Nginx vs Apache vs Tomcat

三者的根本差异在**并发模型**与**职责定位**。Apache 传统 prefork 模型每连接一进程，worker/event 模型改为线程池复用，但整体仍是"连接占用执行单元"的同步思路；Nginx 从第一天起就是"连接不占用执行单元"的异步思路。Tomcat 则根本不是同一层的竞品——它是 Servlet 容器，价值在运行 Java 动态代码，其连接层（NIO）性能再强也不适合直接暴露给公网海量长连接。

| 对比维度 | Nginx | Apache | Tomcat |
|----------|-------|--------|--------|
| 定位 | HTTP 服务器 + 反向代理 | HTTP 服务器 | Servlet 容器 / Java 应用服务器 |
| 并发模型 | 异步非阻塞、事件驱动 | 同步多进程 / 多线程（prefork/worker/event） | 多线程（基于 Java NIO/BIO） |
| 静态资源 | 高性能，首选 | 较好，但不如 Nginx | 弱，不建议直接暴露 |
| 动态内容 | 反向代理到后端 | 通过模块（mod_php 等） | 原生支持 Servlet/JSP |
| 内存消耗 | 低且稳定 | 较高，并发增加时明显增长 | 较高（JVM 内存） |
| 配置灵活性 | 简洁直观 | 丰富（.htaccess 等） | 中等 |
| 热部署 | 支持平滑重载 | 需重启 | 通常需重新部署 |

把"每连接一进程"的模型放到长连接时代看缺陷会更直观：

| 维度 | Apache prefork | Apache worker/event | Nginx |
|------|----------------|---------------------|-------|
| 并发单位 | 1 进程/连接 | 线程池 + 保持连接线程 | 事件循环，无每连接线程 |
| 空闲长连接代价 | 进程常驻，内存 MB 级/连接 | 由专用线程托管，代价较小 | 仅 fd + 连接结构，KB 级/连接 |
| 上下文切换 | 进程级，最重 | 线程级 | 几乎没有 |
| 万级并发可行性 | 差（需要数千进程） | 可以 | 轻松 |

**为什么 Nginx 特别适合做高并发反向代理**，可以归结为四点：其一，代理工作本质是"两头挂连接 + 转发字节"，恰好是事件驱动模型的甜点区，没有任何业务计算；其二，`proxy_buffering` 让 Nginx 先把后端响应收进缓冲，慢客户端拖传输时不占用后端连接，**快后端与慢客户端被解耦**；其三，TLS、HTTP/2、压缩、限流、重试都能在入口层集中完成，后端保持极简；其四，`nginx -s reload` 平滑重载意味着改路由、换证书不停机，这对入口组件是刚需。

> **行业实践**：`Nginx（前端）→ Tomcat / Spring Boot / Go / Node.js（后端应用）` 是互联网标准组合。但 Apache 并非落后——它的 `.htaccess` 分布式配置、mod_php 等成熟模块让存量 LAMP 系统替换成本高，与 Nginx 共存（甚至 Nginx 前置挡 Apache）仍大量存在；Kubernetes 时代的 Ingress-NGINX 同样沿用"事件驱动入口 + 应用后端"这一格局。

# 5. Nginx 发展历史与生态

| 版本线 | 说明 |
|--------|------|
| **Nginx Open Source** | 开源社区版，官方维护（Stable/Mainline） |
| **Nginx Plus** | 商业版，提供高级负载均衡、主动健康检查、Dashboard 等 |
| **OpenResty** | 基于 Nginx + LuaJIT 的 Web 平台，国内广泛使用（章亦春开发） |
| **Tengine** | 阿里巴巴开源的 Nginx 分支，增加动态模块加载等特性 |
| **Kong / APISIX** | 基于 OpenResty 的 API 网关 |

Nginx 于 2019 年被 F5 收购，商业版即 F5 Nginx Plus。开源版与商业版的差距不在基础性能，而在**运维与流量治理的高级能力**：

| 能力 | 开源版 | Nginx Plus |
|------|--------|------------|
| 主动健康检查 | 无（需第三方 check 模块） | 内置 `health_check` |
| 会话保持 | 无（需 sticky 第三方模块） | 内置 `sticky cookie` |
| 运行时动态改 upstream | 无（reload 或自研方案） | REST API + KV store，不 reload 摘挂节点 |
| 会话共享（跨 worker 状态） | 仅共享内存 zone | 节点间会话复制 |
| 慢启动 slow_start、优先级 priority | 无 | 有 |
| 监控 Dashboard / API | 仅 stub_status | 完整状态 API |
| 支持 | 社区 | F5 商业 SLA |

> **注意**：开源版的"缺口"在国内大多被 OpenResty/Lua 生态补齐——动态路由、鉴权、配合 etcd/Consul 的服务发现注册（如 upsync、或直接用 APISIX/Kong）都不必购买 Plus。选型时先问"社区方案能否覆盖"，再考虑 Plus。

# 6. 版本选择建议

| 版本类型 | 特点 | 适用场景 |
|----------|------|----------|
| **Mainline**（主线版） | 奇数版本号（如 1.25.x），功能最新，迭代快 | 追求新特性，非关键环境 |
| **Stable**（稳定版） | 偶数版本号（如 1.24.x），只修复 Bug，长期维护 | 生产环境推荐 |

官方对两条分支的承诺是：**Mainline 吸收全部新特性与安全修复，Stable 只收安全与 Bug 修复**，且历史上 Stable 的修复滞后 Mainline 极短，两者安全性差异不大；官方自身建议生产用 Stable，而"想要新特性（如 1.25.1 起将 `listen ... http2` 独立成 `http2 on;` 指令）"才用 Mainline。本笔记技术口径取 1.24+/1.26。

> 生产环境 **推荐使用 Stable 版本**。国内也可考虑 OpenResty 或 Tengine。

# 7. 学习路线建议

```text
概述 → 安装 → 核心概念 → 核心配置 → 静态资源 → 反向代理 → 负载均衡
  → SSL/TLS → Rewrite → 日志 → 缓存 → 压缩 → 安全 → 限流
  → 性能调优 → 高级特性 → 监控 → 高可用 → 实战配置 → 总结
```

建议的推进方式：前半程（概述到负载均衡）解决"看懂配置、搭得起服务"，是日常使用频率最高的部分；后半程（日志到实战）解决"上得了生产"——压测调优、可观测性、高可用与故障处置。每学完一篇，最好在自己的 Nginx 实例上把示例配置跑通并用 `curl -v` / 浏览器 DevTools 验证行为，Nginx 的很多规则（location 优先级、proxy_pass 尾斜杠）只靠读是记不牢的。

# 8. 小结

| 要点 | 一句话结论 |
|------|-----------|
| 定位 | 高并发"连接管家"：HTTP 服务器 + 反向代理 + 负载均衡 + SSL 终结，不跑业务 |
| 进程模型 | Master 管理配置与 Worker，Worker 单线程事件循环，互不共享连接 |
| 并发本质 | epoll + 非阻塞让空闲连接只花 KB 级内存，连接数与执行单元解耦 |
| 对比 Apache | 每连接一进程/线程 vs 事件驱动；长连接越多差距越大 |
| 对比 Tomcat | 不是竞品而是分工：Nginx 管流量入口，Tomcat 跑 Java 动态代码 |
| 生态 | OpenSource / Plus / OpenResty / Tengine / Kong；Plus 差集多可由社区补齐 |
| 版本 | 生产用 Stable（本笔记口径 1.24+/1.26），要新特性用 Mainline |
