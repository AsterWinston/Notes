# 1. 概述

Kibana Machine Learning 基于 ES 内嵌的 **X-Pack ML 引擎**（C++ 实现、Lucene 库同源），提供**异常检测、分类和回归**能力，无需编写代码。它的定位不是替代数据科学工具链，而是把"给一段时序数据、自动学出正常模式、偏离即报异常"这件事做成**开箱即用的运维能力**——你不需要先知道阈值是多少，模型会从 30 天历史里自己学出来，这对阈值难定的周期性业务量（白天高夜里低的 QPS、工作日与周末差异巨大的订单数）尤其有价值。

```text
ML 工作流:
  1. 选择索引/Data View
  2. 选择 ML Job 类型
  3. 配置 Detector（检测器）
  4. 运行 Datafeed 输入数据
  5. 查看 Anomaly Explorer 结果
  6. 设置告警
```

引擎侧的关键组件分工要理清：**Job** 定义"检测什么"（检测器、函数、桶参数），**Datafeed** 定义"数据从哪来"（轮询查询把新文档喂给 Job），**模型状态**（native 进程内存中的概率模型）定义"学到什么程度"。三者都持久化在 `.ml-anomalies-*`、`.ml-config` 等系统索引中，Job 的异常结果本身就写回 ES 索引，因此 Anomaly Explorer、告警、Discover 查异常共用同一份数据。

> **注意**：8.x 的 ML 节点是**独立角色的专用节点**（`xpack.machine_learning: true`），模型运行在节点内存中而非堆内——规划容量时要按"模型内存总量 + 30% 余量"预留 ML 节点的 `ml.max_open_jobs` 与物理内存，与数据节点的堆内存是两笔账。小规模试用可以直接在数据节点开 ML 角色（单节点全家桶），生产集群超过一定规模后建议拆分。

# 2. Job 类型

异常检测类 Job 按"分析对象是单条时间线还是一个群体"划分，选错类型是 ML 用不好的第一原因：

| Job | 说明 | 适用场景 |
|-----|------|---------|
| **Single Metric** | 单指标异常检测 | CPU 异常、QPS 异常 |
| **Multi Metric** | 多指标联合分析（可含 by/split 维度） | CPU + Memory + Disk 联合 |
| **Population** | 群体行为异常（个体在总体中的偏离） | 某台服务器/某个用户行为异常 |
| **Categorization** | 非结构化日志自动归类再检测 | 错误日志自动归类、新错误模式 |
| **Advanced** | 自由选择函数组合的专家模式 | rare、count_by_category 等高级函数 |

检测函数（detector function）决定"对数据做什么统计"，与 Job 类型正交，常用组合值得记住：

| 函数 | 语义 | 典型场景 |
|------|------|---------|
| `mean` / `high_mean` / `low_mean` | 桶内均值的整体升降 | 延迟升高、订单量下跌 |
| `sum` | 桶内求和 | 总量型指标 |
| `rare` | 出现频率极低的实体 | 从未见过的进程名、罕见错误码 |
| `count_by_category` | 按类别计数（配合 categorization） | 某类日志突增 |
| `high_freq_items` / `by_field` 组合 | 分维度的高频偏离 | 按接口拆分的错误率 |

## 2.1 Single Metric Job

单指标 Job 是最基础的形态：**一条时间线、一个统计量、按固定桶滚动检测**。配置时真正需要决策的是 Bucket span——它决定模型对"多长时间窗口内的偏离"敏感：5m 的桶能抓到短时毛刺但噪声多、模型内存占用高；1h 的桶平滑但会淹没短促异常。经验做法是**先按业务可容忍的最大故障持续时间的 1/3 设置**，例如"希望 15 分钟内发现异常"就从 5m 试起。

```text
ML → Create job → Single metric
  Index: metricbeat-*
  Time field: @timestamp
  Detector: high_mean(system.cpu.user.pct)
  Bucket span: 15m

结果: 按 15 分钟窗口统计 CPU 均值，检测超出正常范围的窗口

Anomaly Score:
  0-25: 正常
  25-50: 轻微异常
  50-75: 中度异常
  75-100: 严重异常
```

异常分数（anomaly score）是**归一化到 0–100 的严重度**，由概率模型算出该桶数据的罕见程度后映射而来，不同 Job 之间可直接比较——这是它比"业务原始值"更适合做告警条件的原因：不需要每条业务线约定各自的分位数，统一按 score > 75 告警即可分层。与之配套的 `record score`（单实体分数）和 `model bucket score`（桶级最高分）在写 ML 告警规则时应选后者，桶级分数才是这一时间窗整体严重度的代表。

## 2.2 Population Job

Population（总体）Job 常被误解，它检测的不是"某个实体自己的时序异常"，而是**某个子集相对于总体的行为偏离**。经典表达是"这次请求的响应时间，相对于这台主机历史上处理同类请求的表现，是否异常"：函数用 `by_field_name` 的 mean/high_mean，`by_field` 填 client（如 host），`over_field` 填个体（如 process name）。**Multi Metric 加 split 已经覆盖了大部分"按维度检测"需求，Population 适合"每个个体有各自的正常模式、要抓掉队个体"的场景**，例如 CDN 场景里某一台边缘节点相对全网其他节点行为异常。

## 2.3 Categorization Job

分类 Job 先对文本字段做**模式归纳（自动抽取模板，变量部分参数化）**，再对每个类别做 `count_by_category` 检测。它解决的痛点是：日志里没有结构化错误码时，普通规则只能"全文匹配关键字"，无法回答"这条新错误以前出现过吗"。

```text
ML → Create job → Categorization

Index: logs-*
Detector: Count → By → mlcategory
Categorization field: message

效果: 自动将相似的日志消息归类
  - Category 1: "Connection refused to {host}:{port}" (150次)
  - Category 2: "OOM killer killed process {pid}" (3次)
  - Category 3: "Disk usage exceeded {percent}%" (1次)
```

新出现的类别会被模型直接标记为异常（probability 极低），**"从未见过的错误模式"正是这类告警最有价值的输出**。代价也要讲清楚：分类在 ingest 侧靠 runtime 计算，对高吞吐日志流有可观的 CPU 开销，且 category 定义会随样本漂移——**不要对超过日均数十亿条的日志全量开 categorization**，先用查询把范围缩到 error/fatal 级别再建 Job。

# 3. 建模关键参数与日历

Jobs UI 向导背后的三个参数决定模型质量，排障 ML 效果差时基本都查这三处：

**Bucket span**（时间粒度）与 **Datafeed frequency**（喂数据频率）：前者是分析窗口，后者是轮询间隔，frequency 通常 ≤ bucket span，让桶提前积累数据；两者都设很小会造成任务队列拥堵（`job too many buckets`）。

**Model Memory Limit**：模型常驻内存，默认 300MB 只够低基数场景。检测的 by/split 字段基数（distinct 值数量）是内存消耗的主因，基数上万时应上调到 1GB 并关注 `model_memory_status`——出现 `SOFT_LIMIT_REACHED` 时模型停止学习新实体，**异常检测会在无声中降级**，务必给该状态配置告警。

```json
PUT /_ml/anomaly_detectors/cpu_anomaly
{
  "job_id": "cpu_anomaly",
  "analysis_config": {
    "bucket_span": "15m",
    "detectors": [
      { "detector_description": "CPU 高均值异常",
        "function": "high_mean",
        "field_name": "system.cpu.user.pct" }
    ],
    "overall_score": 50,
    "model_memory_limit": "512mb"
  },
  "data_description": { "time_field": "@timestamp", "time_format": "epoch_millis" },
  "filters": ["@timestamp >= now-30d"]
}
```

**日历（Calendars / Scheduled Events）**处理"已知异常期"：把大促、月度结算、计划维护登记进日历，模型把这些时段**从"正常基线学习"中排除**——否则每月底批量结算都会污染基线，导致下个月误报连天。这是 ML 误报治理中投入产出比最高的一步：

```text
Stack Management → ML → Calendar Jobs
  Calendar: "大促窗口"
    ├── 2026-11-10 20:00 → 23:59 (单事件)
    └── 每月 1 日 00:00-02:00 (周期事件: 批量对账)
  关联 Job: orders_qps_anomaly
```

> **行业实践**：新 Job 一律先跑 **30 天历史回填（rewind）** 再打开实时 Datafeed，让模型先见过一个完整的"周周期 + 月周期"；上线后头两周只告到测试群不发值班，用于观察误报率，稳定后再切正式通道。直接新建空模型就开始告警，第一周必然是风暴。

# 4. Anomaly Explorer

Anomaly Explorer 是异常结果的**统一调查视图**，四个功能区构成完整的下钻路径：

```text
ML → Anomaly Explorer
  ├── 时间线: 异常分数随时间变化 (整体严重度曲线)
  ├── 异常列表: 按严重程度排序 (跨 Job 汇总, 支持搜索/过滤)
  ├── 详细视图: 选定异常的上下文数据分析 (Single Bucket View)
  │     ├── Actual vs Typical 曲线对照
  │     ├── 相关字段贡献度 (哪些维度组合导致该异常)
  │     └── 一键跳转 Discover 看原始文档
  └── Forecast: 基于历史数据预测未来值 (上限受数据量限制, 最长约 60 天)
```

调查时的实用技巧：**用"相关字段"面板判断异常归属**——Multi Metric Job 报出延迟异常时，相关字段视图会显示哪些 `by_field` 维度（哪个服务、哪个接口）贡献最大，相当于自动完成了下钻定位；Single Bucket View 里 Actual（实际值）与 Typical（模型认为的正常值）的差异幅度就是分数来源，两者几乎重合却报高分的情况，一般是模型内存不足导致部分实体未学习，应先查模型状态而不是继续深挖业务。

# 5. Data Visualizer

Data Visualizer 是建 Job 前的**数据体检工具**，回答"这份数据适合做什么类型的 ML"：

```text
ML → Data Visualizer
  ├── 选择索引 → 分析字段分布
  ├── 数值字段: min/max/avg/percentiles 分布
  ├── 关键字字段: Top values + 占比 (评估基数, 预判模型内存)
  ├── 时间字段: 数据是否连续、是否有乱序/延迟写入
  └── 建议: 哪些字段适合做 ML Job 的 Detector
```

两个最容易被忽略的检查项：**数据延迟**（若 `@timestamp` 与写入时间差大，Datafeed 查询要加 `delay` 参数，否则桶会因迟到数据反复重开）和**基数预估**（keyword 字段 Top values 占比接近 100% 说明高基数，不适合做 by_field）。Visualizer 给出的"推荐 Job"只是基于字段类型的机械建议，仍需人工判断业务含义。

# 6. ML 告警

ML 异常分数进入 Alerting 体系的方式是 **Machine Learning rule 类型**（Platinum+），支持按 overall score、最大 record score、特定 entity 的组合条件触发：

```text
创建 ML 规则:
Rule → Create rule → Machine Learning
  Job: cpu_anomaly
  Condition: overall score > 75
  Check every: 15m

Action:
  Connector: Slack
  Message: "CPU anomaly detected: score={{context.anomalyScore}}"
```

8.x 的 ML 规则可以**同时关联多个 Job**（单规则/多规则两种模式），例如把同一集群的 CPU、内存、磁盘三个 Job 合成一条"主机资源异常"告警，任何一个 Job 高分都触发，消息里带上 job_id 与 entity——比分每个 Job 建一条规则更符合值班视角。

> **注意**：ML 规则的 `Check every` 与 Job 的 `bucket span` 对齐（或其整数倍）才不会"同一桶重复告警"或"漏桶"。另外 **Job 停了（closed/failed）不等于告警消失**，ML 规则对无结果桶按"正常"处理，必须另外监控 Job 健康状态——用 `_ml/anomaly_detectors/_find` 加定时检查，或升级助手里的 ML 健康项。

# 7. Inference 与推理模型

ML 在 8.x 中的第二块版图是 **Inference**（训练/导入模型 + 推理部署），与异常检测共用 ML 节点但用途完全不同：

- **训练路径**：UI 内直接训练 **Dataframe Analytics**（回归、分类，如"欺诈概率"），导出为模型；
- **导入路径**：上传第三方训练的 PyTorch/NEL/openNN 模型（REST：`PUT _ml/inference/`），8.10+ 走统一的 **Eland / Inference API**；
- **推理部署**：模型注册为 Inference Endpoint，供 Ingest Pipeline、ESQL、RAG 调用。

```json
PUT /_ingest/pipeline/ml_inference
{
  "processors": [
    {
      "inference": {
        "model_id": "my-model",
        "target_field": "ml_result",
        "field_map": { "message": "text_field" }
      }
    }
  ]
}
```

**设计考量**：ingest 时逐文档推理（如日志自动分类、情感标注）延迟敏感、吞吐受限，推理模型应部署在独立 ML 节点并与异常检测 Job 隔离内存预算；8.x 后期语义推理（embedding/reranker，配合向量检索与 Elastic 推理服务 ELSER）也在同一套 Inference API 上，如果团队用 ML 主要为了向量搜索，关注点是推理端点与 GPU/量化配置，而不是异常检测那套参数。

# 8. License 与什么场景值得开 Platinum

ML 是 Elastic License 分层中最"硬"的功能之一，规划成本时要先看清边界：

| 功能 | License |
|------|---------|
| 异常检测 / Datafeed / Anomaly Explorer | Platinum（30 天 trial 可用） |
| Dataframe Analytics（回归/分类） | Platinum |
| Inference（第三方模型推理） | Enterprise |
| ML 告警规则 | Platinum |
| 异常检测 API（结果读回自建平台） | Platinum |

> **行业实践**：值得为 ML 上 Platinum 的信号通常是三条同时满足——**① 指标有强周期性与多维度**（阈值规则已经疲于奔命）、**② 日志缺少结构化错误码**（分类检测有独占价值）、**③ 安全团队要用 ML 规则做 UEBA 类检测**。反之，如果场景是"CPU 超 90% 就告警"这类固定阈值，Metric threshold 规则加静态阈值就够了，没必要为此付费开 ML 节点。试用期内（license.self_generated.type: trial）把候选场景各建一个 Job 跑两周，用误报率数据决定是否升级，是最经济的决策路径。

# 9. 常见误用

- **拿 ML 当阈值告警的替代品**：模型需要学习期，突发型故障（发布引起的错误率飙升）在 ML 还没学完基线时毫无反应，这类场景静态规则响应更快——两者是互补而非替代。
- **一个 Job 塞过多 detector**：单 Job 建议不超过 5 个 detector，检测器之间共享模型内存，混装会同时拖垮精度和内存。
- **忽略迟到数据与乱序**：Datafeed 不加 delay、时间字段用 ingest 时间而非事件时间，桶结果会持续抖动。
- **模型内存不设监控**：SOFT_LIMIT 后模型停止学习，检测静默退化，几周后才被业务发现"ML 早就不报异常了"。
- **把 categorization 当全文检索用**：它的类别是统计归纳，不保证语义精确，关键业务分类仍需显式字段或 ingest pipeline 规则。

# 10. 小结

- **能力边界**：异常检测（时序基线自学习）、日志分类（新模式发现）、Dataframe Analytics/Inference（监督模型），前两者 Platinum，推理属 Enterprise——先对号入座再谈建设。
- **参数三板斧**：bucket span 决定敏感度、model memory 决定能不能学全、日历决定基线干不干净，ML 效果问题九成出在这三处。
- **与告警协同**：ML 规则统一按 anomaly score 分层告警，但要额外监控 Job 健康与模型内存状态，否则"不告警"比"误告警"更危险。
- **落地节奏**：30 天回填 → 影子告警两周 → 切正式值班；没有周期性或多维下钻需求的场景，不要为了"用 ML"而开 Platinum。
