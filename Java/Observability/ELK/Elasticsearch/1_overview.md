# 1. 概述

Elasticsearch（简称 ES）是一个基于 Apache Lucene 的**分布式搜索和分析引擎**，提供近实时的全文检索、结构化搜索和数据分析能力。2010 年由 Shay Banon 发布，现为 Elastic NV 旗下核心产品。

理解 ES 的定位要先承认一个事实：**Lucene 本身只是一个 jar 包级别的检索库**，它解决了"单机如何高效地建索引、查索引、算相关性"的问题，但没有解决"数据如何分布到几十台机器、节点挂了谁来接管、如何用一个 HTTP 接口把索引写进去"的问题。ES 的全部价值就在于把 Lucene **产品化、分布式化、服务化**：每个 Lucene 索引被包装成分片（Shard），分片被自动分配到集群节点并带副本容错，所有操作统一暴露为 RESTful API，再在其上叠加了聚合框架、生命周期管理、安全体系这些企业级能力。因此面试里那句"ES 和 Lucene 什么关系"的标准回答是：**Lucene 是引擎，ES 是开着这辆引擎的车、并建了整套交通系统的平台**。

```text
┌──────────────────────────────────────────────────────────┐
│                  Elasticsearch                            │
│                                                          │
│  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐  │
│  │  全文检索     │  │  聚合分析     │  │  近实时处理    │  │
│  │  (Full Text) │  │ (Aggregation)│  │  (NRT)       │  │
│  └──────┬───────┘  └──────┬───────┘  └──────┬───────┘  │
│         └─────────────────┼─────────────────┘           │
│                           ▼                              │
│              ┌──────────────────────┐                    │
│              │    Lucene (核心引擎)   │                    │
│              │  - 倒排索引            │                    │
│              │  - 分词/分析           │                    │
│              │  - 评分/排序           │                    │
│              └──────────────────────┘                    │
└──────────────────────────────────────────────────────────┘
```

## 1.1 典型场景

ES 在生产系统中的角色大致分三类，每一类对配置的取舍完全不同：

- **站内搜索**（电商商品搜索、文档检索、App 内搜索）：核心诉求是**相关性**和**容错**，用户搜"苹果手机"要能把"iPhone 15"召回，拼音、错别字、同义词都要在 analyzer 层处理，权重调优（boost、function_score）是日常工作量的大头。
- **日志与可观测性**（ELK Stack、APM、Metrics）：核心诉求是**高吞吐写入**和**时序查询**，特点是"写多读少、按天滚动、过期删除"，因此用 Data Stream + ILM（索引生命周期管理）而非手工建索引，refresh_interval 通常调大甚至设为 -1。
- **数据分析与安全**（Kibana 报表、SIEM 威胁检测、地理围栏）：核心诉求是**聚合能力**，靠 Bucket/Metric 聚合在十亿级文档上做秒级多维统计，这部分能力是 MySQL 的 GROUP BY 难以覆盖的。

> **行业实践**：多数互联网公司同时存在"搜索集群"和"日志集群"两套 ES，**绝不混部**。搜索集群追求低延迟、查询缓存命中率高；日志集群追求写入吞吐、段合并压力大。两种负载的 JVM 堆配置、分片规划、刷新策略互相冲突，混部会导致搜索 P99 毛刺和日志写入排队互相拖累。

## 1.2 核心能力

| 能力 | 说明 | 典型场景 |
|------|------|---------|
| **全文检索** | 分词、相关性评分、高亮 | 电商搜索、站内搜索 |
| **聚合分析** | 分组统计、直方图、时序分析 | 日志分析、运营报表 |
| **近实时** | 文档索引后 ~1s 可搜索 | 实时日志、监控告警 |
| **分布式** | 水平分片、副本容错 | 海量数据存储 |
| **多租户** | 索引别名、索引模板 | 多应用共享集群 |

这里的"近实时（NRT, Near Real-Time）"是 ES 与传统认知差异最大的一点，也是无数线上"为什么刚写的文档查不到"工单的根源。文档写入后先进入内存 buffer 和 translog，此时**只有 GET by ID 能读到它**（走 translog）；要等 refresh（默认 1 秒）把 buffer 生成可搜索的 Lucene segment 之后，才能被 search 命中。ES 选择近实时而非实时，是因为 Lucene 的段结构不可变——每次可搜索化都要新起 segment，若每写一条就刷一次，段文件数量会爆炸、合并压力和打开的文件句柄数都不可承受。**1 秒是"写入吞吐"与"搜索新鲜度"之间的工程折中**。

# 2. Lucene 基础

Elasticsearch 底层基于 **Apache Lucene**，Lucene 是一个高性能的全文检索库：

| Lucene 概念 | Elasticsearch 概念 | 说明 |
|-----------|------------------|------|
| Index | Index | 文档集合 |
| Document | Document | 数据单元（JSON） |
| Field | Field | 文档的键值对 |
| Term | Term | 分词后的词项 |
| Segment | Segment | 不可变的索引分块（最终持久化单元） |

**ES vs Lucene**：ES 在 Lucene 上增加了**分布式集群、RESTful API、JSON 文档模型、聚合分析**等能力。

需要建立一个贯穿全系列笔记的心智模型：**ES 的"索引"不是 MySQL 的 B+ 树索引，而是一个倒排索引数据库**。MySQL 的二级索引是"值 → 行指针"的有序结构，擅长等值和范围；Lucene 的倒排索引是"词项 → 文档列表"的映射——写入时把文本分词成 term，为每个 term 维护一张 posting list（包含该词的文档 ID 链表），查询"iPhone AND 手机"时只需对两条 posting list 求交集，复杂度与命中文档数成正比，而与全表数据量无关。这就是为什么 `LIKE '%iPhone%'` 在千万行表上是全表扫描，而 ES 在十亿文档上依然是毫秒级。**Segment 不可变**则是另一个根基设定：更新和删除都不改老段，只写新段、给老段打删除标记，靠段合并（merge）最终清理——第 2 篇的写入流程、第 5 篇的"无原地更新"、第 13 篇的写入调优全部从这里推导出来。

# 3. ES vs 传统数据库

| 维度 | Elasticsearch | MySQL |
|------|--------------|-------|
| **数据模型** | 文档（JSON） | 表（行列） |
| **查询语言** | Query DSL (JSON) | SQL |
| **全文检索** | ★★★★★（倒排索引） | ★★☆☆☆（LIKE '%xx%'） |
| **聚合分析** | ★★★★★（Bucket/Metric） | ★★★☆☆（GROUP BY） |
| **事务支持** | ✗ | ✓（ACID） |
| **实时性** | 近实时（~1s refresh） | 实时 |
| **水平扩展** | ★★★★★（Shard 分片） | ★★★☆☆（分库分表） |
| **适用场景** | 搜索、日志分析、监控 | 核心业务数据存储 |

这张表最容易读出的错误结论是"ES 更快，所以用 ES 替换 MySQL"。两者不是竞争关系而是**互补关系**：MySQL 是 Source of Truth（真相源），承载事务和强一致；ES 是从库派生出的**只读加速视图**，专门伺候那些 MySQL 干不动的查询（全文、模糊、多维聚合）。典型的架构是把两侧连起来：

```text
┌─────────┐   binlog    ┌──────────────┐   bulk    ┌──────────────┐
│  MySQL  │ ──────────→ │ Canal/Flink  │ ────────→ │Elasticsearch │
│ (真相源) │             │ (同步管道)    │           │  (搜索视图)   │
└─────────┘             └──────────────┘           └──────┬───────┘
     ▲                                                    │
     │                 用户搜索请求只读 ES                  ▼
     └── 下单/支付等写操作仍走 MySQL                 ┌──────────┐
                                                   │   用户    │
                                                   └──────────┘
```

**设计考量**：

- **为什么不直接双写**：应用里"先写 MySQL 再写 ES"的两段式写入没有事务保证，第二步失败就会出现两侧不一致；正确姿势是订阅 binlog 异步同步，接受秒级延迟，并保证 ES 侧可全量重建。
- **为什么不把 ES 当主存储**：ES 不支持多文档 ACID 事务、外键约束和跨分片的强一致读，`refresh_interval` 窗口内的数据不可搜索；订单、库存、余额这类"错一条就是资损"的数据绝不能以 ES 为准。
- **一致性兜底**：同步链路必须做对账/重放机制（按 binlog 位点补数），并且文档 _id 与主表主键对齐，让重放天然幂等。

> **注意**：即使有了全文检索需求，也不要"为 LIKE 而迁 ES"。MySQL 8.x 的全文索引、以及带 `pg_trgm`/GIN 索引的 PostgreSQL 在中小数据量下足够用；引入 ES 意味着引入一整套集群运维、同步链路与一致性补偿成本，一般只在数据量过千万、或查询模式包含分词相关性/多维聚合/高亮时才值得。

# 4. 版本演进（8.x 语义）

ES 的大版本迭代中有几处对使用者影响深远的语义变化，选型和升级时首先要核对：

| 版本 | 关键变化 | 影响 |
|------|---------|------|
| 5.x | 移除 Lucene 3.x 索引兼容 | 5.x 之前建的索引必须 reindex |
| 6.x | 移除 mapping type（一索引一 type） | `_doc` 成为唯一 type 名 |
| 7.x | 默认开启 kNN 向量检索雏形、废弃 `include_type_name` | Java High Level REST Client 开始退出历史舞台 |
| 8.x | **默认开启安全认证与 TLS**；`term` 向量检索升级为 `knn` 原生 API；Java Client 全面换成 Elasticsearch Java Client；基于 9.x Lucene 引入 **BBQ（Better Binary Quantization）向量压缩** | 不再支持 `_doc` 之外的 type 参数；老插件需适配 |

8.x 最值得注意的三点：**其一，安全默认开启**——zip/docker 安装后 HTTP 端口自动启用 TLS 并生成 elastic 超级用户密码，本地测试图省事要显式 `xpack.security.enabled=false`，但生产环境这条不是可选项，详见第 3 篇。**其二，向量检索（kNN/RRF 混合检索）成为一等公民**——ES 从"关键词搜索引擎"升级为可承载语义检索的平台：dense_vector 字段 + HNSW 索引做向量近邻，配合 RRF（Reciprocal Rank Fusion）把 BM25 关键词得分和向量相似度排名融合，这是当前 RAG 应用的主流底座。**其三，客户端生态重切**——旧的 RestHighLevelClient 已移除，官方推荐基于 API 规范自动生成的 Elasticsearch Java Client，升级 8.x 时应用侧改造量主要集中在这一层。

> **注意**：Lucene 段的向后兼容承诺是"**只读过去、不写过去**"——新版本能读上一大版本索引的 segment，但集群一旦有节点混用不同大版本，索引就不再向后兼容。因此滚动升级必须整集群一次一个大版本（7.17 → 8.x），且升级前用 `_migration/deprecations` API 清理告警项。

# 5. vs Solr

| 维度 | Elasticsearch | Apache Solr |
|------|--------------|-------------|
| **社区活跃** | ★★★★★ | ★★★☆☆ |
| **分布式** | 原生支持 | 依赖 ZooKeeper |
| **REST API** | ✓ | ✓ |
| **聚合分析** | 强大 | 强大 |
| **实时性** | 近实时 | 近实时 |
| **机器学习** | 内置 | 需扩展 |
| **运维复杂度** | 低 | 中 |
| **生态** | ELK Stack | 较独立 |

两者同根同源（都基于 Lucene），传统意义上的技术差异早已被互相抄作业抹平——Solr 的 Cloud 模式同样支持自动分片与副本，聚合能力也不弱。真正的分野在**生态与运维模型**：Solr 的分布式元数据托管在 ZooKeeper 上，意味着多维护一套 ZK 集群；ES 把集群协调内置进自身（Master 选举 + 集群状态发布），装一个就能跑。更重要的是围绕 ES 的 Kibana、Logstash、Beats 构成的 ELK 全家桶，以及检索之外的 APM、安全（SIEM）、企业搜索产品线，让"日志分析"和"搜索"两个场景都能开箱即用地闭环；Solr 在这一层几乎需要全部自建。

> **行业实践**：国内新建搜索/日志基础设施时 Solr 占比已经很低，选型争议基本收敛为"用 ES/OpenSearch，还是用商业云托管服务"。OpenSearch 是 Elastic 将 license 改为 SSPL 之后 AWS 主导的 fork 分支，API 与 ES 7.10 之前高度兼容，但 2.x 之后与 ES 8.x 的向量检索、ILM 等特性路线已经明显分岔，选型时要按特性逐项核对而不是只看"兼容 ES"的宣传。

# 6. 适用场景

```text
✓ 适用:
  - 全文搜索引擎(电商、文档检索)
  - 日志集中分析(ELK Stack)
  - APM 监控数据存储
  - 时序数据分析
  - 地理空间搜索(Geo Point/Shape)

✗ 不适用:
  - 核心交易数据(无事务)
  - 频繁更新的数据(段合并压力大)
  - 需要多表 JOIN 的复杂关系查询
  - 单条数据需要严格一致性的场景
```

把"不适用"清单背后的机制说透：

- **核心交易数据**：无 ACID 事务与行锁，跨分片写入无原子性；乐观并发控制（`_seq_no`/`_primary_term`，见第 5 篇）只能防单文档冲突，不能替代事务。
- **高频更新的数据**：每次 update 本质是"标记删除 + 重新索引"，段里积累大量删除文档会拖慢查询（要遍历被标删的文档）并触发持续 merge，写放大严重。经验上更新比例超过日增文档 10% 的场景就要重新设计（如改为 append-only + 别名为视图）。
- **多表 JOIN**：倒排索引里没有 JOIN 算子，父子关联只能用 nested 或 join 字段模拟，性能均远不如关系库；宽表化（在写入前由应用拼装好冗余字段）才是 ES 的正确姿势。
- **深分页与精确计数**：from+size 需要每个分片收集排序数据后在协调节点归并，第 10000 页意味着每分片先取出 10010 条；深分页要用 search_after（见第 12 篇）。

> **注意**：还有一类常被忽略的反模式——**把 ES 当 KV 存储做 term 查询**。按 _id 的 GET 走 translog 和缓存没问题，但用 keyword 字段大量精确匹配来替代 Redis/MySQL 点查，等于放弃了 ES 的看家本领，还要白白承担近实时延迟和集群运维成本。

**小结一句**：ES 的准确定位是**面向"搜索与分析"的分布式派生存储**，凡"必须强一致、必须事务、必须原地改"的数据留在 MySQL；ES 只接住那些 MySQL 查不动、算不动的查询。

# 7. 小结

| 要点 | 一句话 |
|------|--------|
| ES 与 Lucene 的关系 | Lucene 是单机检索引擎，ES 提供分布式、REST API、聚合与运维体系 |
| 根基心智模型 | 倒排索引（term → posting list）+ 不可变 Segment，全系列笔记由此推导 |
| 三大典型场景 | 站内搜索（重相关性）、日志可观测（重吞吐）、聚合分析（重多维统计） |
| 与 MySQL 的分工 | MySQL 是真相源，ES 是 binlog 异步同步出来的只读加速视图 |
| 近实时（NRT） | refresh 默认 1s，写入即可 GET、~1s 后才能 search，是吞吐与新鲜度的折中 |
| 8.x 关键语义 | 安全默认开启 TLS、kNN/RRF 向量检索、全新 Java Client、BBQ 压缩 |
| 不适用清单 | 核心交易、高频更新、多表 JOIN、把 ES 当 KV 点查 |
