# 1. 一致性与 CAP

## 1.1 CAP 与 BASE

### 1.1.1 CAP 定理到底怎么理解？"三选二"是误读吗？

**三个字母的精确定义（别背模糊版）**：
- **C（Consistency）**：这里指**线性一致性**——所有操作看起来像在某个全局时间点原子执行，读总能读到"最近一次成功写"（不是 ACID 的 C，也不是"各副本最终一样"）；
- **A（Availability）**：**每个发往非故障节点的请求都能在有限时间内得到非错误响应**（不保证数据最新，但不能超时/报错）；
- **P（Partition Tolerance）**：网络分区（节点间消息丢失/延迟）时系统仍能继续运行。

**"三选二"的准确说法**：**网络分区在分布式系统中不可避免（P 必须接受）**，所以真正的问题是"**分区发生时，选 C 还是选 A**"：
- **CP**：分区时**拒绝服务/阻塞**，保证不返回不一致的数据（ZooKeeper 少数派不可用、etcd 失去多数派不写）；
- **AP**：分区时**继续服务但可能返回旧数据/接受冲突写**，恢复后再合并（Eureka 各节点独立、DNS）。
- **"CA"** 只在**没有分区**（单机/理想网络）时成立——把它当"第三种可选项"就是误读。

**两个必须补的现代视角**：
1. **CAP 只描述"分区期间"的行为**，不描述平时——平时大多数系统都在"一致性与延迟"之间权衡，这是 **PACELC**（Partition→A/C；Else→Latency/Consistency）的补充：**没有分区时，强一致也要付延迟代价**（多副本确认、跨地域 RTT）；
2. **"选 CP"不等于"永远不可用"**：CP 系统在**多数派正常**时可用，只有"少数派分区"才牺牲可用；**"选 AP"也不等于"永远不一致"**：多数时候是最终一致，冲突只在分区窗口出现。

**答题收口**："CAP 是**分区时刻的取舍定理**，不是'平时三选二'——工程上更常用的是 PACELC 与'按数据/按操作分级'：**同一系统里，账户余额走 CP、商品评论走 AP**，才是真实世界的答案。"

### 1.1.2 BASE 与 ACID 有什么区别？柔性事务的边界在哪？

**ACID（关系库的事务）**：原子性、一致性、隔离性、持久性——**强一致、悲观并发、短事务**；适合"钱、库存、订单状态"这类**不允许中间态**的场景（16_mysql.md 3.1.1）。

**BASE（分布式系统的工程哲学，不是定理）**：
- **Basically Available（基本可用）**：故障时允许**降级**（响应变慢、部分功能不可用、限流），但核心可用；
- **Soft State（软状态）**：允许**中间状态**存在（订单"支付中"、库存"冻结中"），不要求任何时刻都一致；
- **Eventually Consistent（最终一致）**：**经过一段时间（通常秒~分钟）后**，所有副本/服务达到一致——**不保证多久，但保证最终**（需要"对账/补偿"兜底）。

**ACID vs BASE 的对照（答题表）**：

| 维度 | ACID | BASE |
|------|------|------|
| 一致性 | 强（事务结束即一致） | 最终（中间态可见） |
| 可用性 | 分区/故障时可能阻塞 | 优先可用（降级） |
| 事务边界 | 单库短事务 | 跨服务长流程 |
| 实现 | 数据库事务/锁 | 消息/补偿/对账/幂等 |
| 适用 | 金融核心账务 | 电商交易、社交、日志 |

**柔性事务的边界（成熟度）**：**BASE 不是"放弃正确性"，而是"把一致性从'实时'换成'可验证的最终'"**——前提是：① **中间态可被业务接受**（订单"处理中"而不是"成功"）；② **有补偿/对账**（3.2.2）；③ **幂等**（3.2.1）。**没有对账的"最终一致"等于"永远不一致"**——这是面试里区分"背概念"与"做过系统"的一句话。

## 1.2 一致性模型谱系

### 1.2.1 强一致、线性一致、顺序一致、因果一致、最终一致怎么排？

**从强到弱（记住"越强越贵"）**：

| 模型 | 保证 | 代价/场景 |
|------|------|----------|
| **线性一致性（Linearizability）** | 所有操作像在**全局实时顺序**上原子执行；读一定读到最近成功写 | 最强（CAP 的 C）；多副本确认、跨区 RTT；Spanner/etcd |
| **顺序一致性（Sequential）** | 所有节点看到**同一个全局顺序**，但不要求与真实时间一致（各进程内保序） | 比线性弱（不要求实时）；分布式共享内存 |
| **因果一致性（Causal）** | **有因果关系的操作**按顺序可见；无因果的并发的可不同顺序 | 中等；社交评论/消息回复；向量时钟 |
| **读己之写（Read-your-writes）** | 自己写完，自己后续读能读到 | 会话级；主从复制的"刚写就读"问题（16_mysql.md 6.1.3） |
| **单调读（Monotonic reads）** | 读到某版本后，不会读到更旧版本 | 会话级；防止"刷新页面数据倒退" |
| **最终一致（Eventual）** | 无更新后，副本**最终**收敛到同一值 | 最弱；DNS/CDN/缓存/异步复制 |

**关键辨析**：**"强一致"在面试里通常指线性一致**（但很多人把它与"最终一致"对立，中间还有因果/会话级）；**"顺序一致"不等于"线性一致"**（前者不要求实时，后者要求"写完成后立刻可见"）；**因果一致性是"反熵"与"性能"的甜点**——多数业务（评论、聊天）只需要"回复不早于原帖"，不需要全局线性。

**工程映射**：**线性一致**→ 分布式锁/选主/账户扣减（etcd/ZK/DB 事务）；**因果**→ 协同编辑/消息流（向量时钟/CRDT）；**最终**→ 搜索索引/缓存/CDN（24_elastic_search.md 的同步延迟）。**答题时先问"这个业务能接受读到多旧的数据"**——一致性模型是业务语义，不是技术炫耀。

### 1.2.2 会话保证（读己写/单调读/单调写）怎么在业务里落地？

**四个会话级保证**（比全局一致弱、比最终一致强，**单客户端视角**）：
1. **读己之写（RYW）**：用户自己提交后，自己的下一次读能看到——**登录后看资料、下单后看订单**；
2. **单调读**：同一用户不会"刷新后看到更旧的数据"（读副本轮询时常见）；
3. **单调写**：同一客户端的写按顺序生效（避免"先创建后删除"被乱序执行）；
4. **写后读跨设备**：会话保证的延伸（同一账号多端），通常要"粘滞/主库读/版本号"。

**落地手段（按代价排）**：
- **粘滞会话**：同一用户固定路由到同一副本（Nginx `ip_hash`/一致性哈希，12_nginx.md）；简单但"节点挂/扩缩容"就破；
- **读主库/强制主**：写后关键读走主（Hint，3.2.2 的读写分离）；最可靠但主压力大；
- **版本号/位点**：客户端带"我见过的版本"，服务端保证"不低于该版本"（16_mysql.md 6.1.3 的 GTID 位点、搜索的 `_seq_no`）；
- **客户端缓存 + 本地回填**：写完直接把结果放本地（前端乐观 UI），绕开"立刻读"；
- **业务兜底**：写完跳详情页用返回体渲染，不重新查（最便宜）。

**易错**：把"最终一致"当"随便旧"（用户会感知"我改的没保存"）；只做 RYW 不做单调读（用户在两个副本间"数据跳变"）；会话粘滞当"一致性方案"（它是可用性权宜，故障时失效）。

# 2. 共识与复制

## 2.1 共识算法

### 2.1.1 Raft 的 Leader 选举与日志复制怎么工作？

**三个角色**：**Leader**（处理写、发日志）、**Follower**（被动同步）、**Candidate**（选举中）；**Term（任期）**是逻辑时钟，**每个 Term 最多一个 Leader**。

**Leader 选举（五步）**：
1. 节点启动为 **Follower**，随机**选举超时**（150~300ms，随机化防分裂票）；
2. 超时未收到 Leader 心跳 → 变 **Candidate**，`Term+1`，**投自己**，向所有节点发 `RequestVote`；
3. 获得**多数派（>N/2）**选票 → 成为 **Leader**，定期发 **AppendEntries（心跳）** 维持权威；
4. 平票/超时 → 重新 `Term+1` 再选（随机超时降低碰撞）；
5. 收到**更高 Term** 的消息 → 立即降级为 Follower（**旧 Leader 自动退位**，2.1.2 的脑裂防护）。

**日志复制（写路径）**：
```text
客户端 → Leader：追加日志条目（未提交）
Leader → 所有 Follower：AppendEntries（带 prevLogIndex/prevLogTerm）
Follower 校验"前一条日志的 index+term 匹配"→ 追加 → 返回成功
Leader 收到多数派成功 → commitIndex 前移（已提交）→ 应用到状态机 → 响应客户端
Leader 在下一次 AppendEntries 中告知 Follower 新的 commitIndex
```
**日志匹配特性**：若两个日志在**相同 index+term** 有相同条目，则**之前的所有条目都相同**——这是"一致性检查"与"快速回退"的基础（Follower 不匹配时 Leader 递减 nextIndex 重试，或按 term 快速定位分歧点）。

**两个工程细节**：**快照（Snapshot）**压缩日志（否则日志无限增长）；**线性一致读**（ReadIndex/Lease Read）避免"只读也走日志"的性能损耗。

### 2.1.2 Raft 如何保证安全（选举限制/提交规则/脑裂）？

**三条安全规则（Raft 的"不丢已提交日志"）**：
1. **选举限制（Election Restriction）**：Candidate 的日志必须**至少和多数派一样新**（比较最后一条的 `term`，term 相同比 `index`）——**落后节点当不上 Leader**，已提交条目不会因"新 Leader 没有它"而丢；
2. **提交规则（Commit Rule）**：Leader **只能通过"当前 Term 的条目 + 多数派复制"来推进 commitIndex**；**不能仅凭"旧 Term 条目在多数派"就提交**（可能被未来的 Leader 覆盖）——这是 Raft 论文里最反直觉、也最容易被面试追问的一条；
3. **Leader 完整性**：已提交的条目一定出现在未来所有 Leader 的日志里（由 1+2 推出）。

**脑裂（Split-Brain）怎么防**：
- **Quorum（多数派）**：只有拿到多数派的 Leader 才能提交——网络分区后**少数派选不出 Leader/无法提交**，不会出现"两个都能写"；
- **Term 递进**：旧 Leader 在少数派里"自嗨"，一旦与多数派恢复通信、看到更高 Term，**立即降级并回滚未提交日志**；
- **Fencing（栅栏令牌）**：**外部资源**（如共享存储/锁服务）不一定懂 Raft 的 Term——要用**单调递增的 fencing token** 让资源拒绝"旧 Leader 的迟到请求"（4.2.1 展开）。

**易错**：以为"多数派写入=已提交"（还要当前 Term + 规则 2）；以为"旧 Leader 会立刻知道"（分区期间它不知道，恢复后才知道）；把 Raft 的"安全性"与"外部系统的幂等"混为一谈（客户端重试仍要幂等，3.2.1）。

### 2.1.3 Paxos 与 Raft 的区别？为什么工程上偏好 Raft？

**Paxos（Basic/Multi-Paxos）**：
- **Basic Paxos**：两阶段（Prepare/Promise → Accept/Accepted），**多数派**达成"某个值"的共识；**只解决"一个值"**的共识；
- **Multi-Paxos**：选出 Leader 后**复用** Prepare 阶段，连续对多个值达成共识（日志复制）——但**规范宽松**（Leader 选举、日志连续性、成员变更都留给实现），**工程化难度高**。

**Raft 的"可理解性设计"**：把共识**拆成三个独立子问题**——**Leader 选举、日志复制、安全性**，并给出**强 Leader**（日志只能从 Leader 流向 Follower）、**日志连续性**（Log Matching）、**成员变更**（联合共识/单节点变更）的明确规则——**实现者照着写就能对**，这是 etcd/Consul/TiKV 选它的原因。

| 维度 | Paxos | Raft |
|------|-------|------|
| 可理解性 | 理论严谨、实现自由度高 | **为易懂而设计**，规则明确 |
| Leader | 非必需（Basic） | **强 Leader**（选举产生） |
| 日志 | 无严格顺序约束 | **严格连续、只能 Leader→Follower** |
| 工程 | Multi-Paxos 需大量补丁 | etcd/Consul/TiKV 直接落地 |
| 代表 | Google Spanner/Chubby（Paxos 变体） | etcd、Consul、TiKV、Kafka KRaft |

**收口**："**Paxos 是'共识的理论基座'，Raft 是'共识的工程说明书'**——两者都靠多数派，但 Raft 把'怎么选主、怎么复制、怎么保证不丢'写成了可实现的规则；面试问区别，答'强 Leader + 日志连续性 + 可理解性'三点就够。"

## 2.2 复制与分区

### 2.2.1 主从、多主、无主复制各有什么一致性问题？

| 复制模型 | 机制 | 一致性/冲突 | 典型 |
|---------|------|------------|------|
| **单主（Leader-Follower）** | 写只进主，异步/同步复制到从 | 异步=可能读到旧数据/主挂丢未复制写；同步=延迟高 | MySQL 主从、Redis 主从、Kafka Leader |
| **多主（Multi-Leader）** | 多个节点都能写，互相复制 | **写冲突**（同时改同一行）——LWW/CRDT/业务合并 | 多活数据库、协同编辑 |
| **无主（Leaderless）** | 客户端写多个副本，读多个副本 | **Quorum**（R+W>N 才有"读到最新"的保证）；冲突用版本/向量时钟 | Dynamo/Cassandra/Riak |

**单主的两个"坑"**：**异步复制**（主提交即返回）在**主挂时**可能丢掉"已确认但未复制"的写（半同步/`min.insync` 是补丁，21_seata.md 2.1.2 的同款账）；**读从库**有复制延迟（会话一致性，1.2.2）。

**多主的冲突解决**：**LWW（最后写入赢）**简单但会**静默丢更新**（时钟不可靠时更糟）；**版本向量**能检测冲突但**要业务合并**；**CRDT**（可交换的数据结构，计数器/集合）能自动收敛——**"多主"不是免费的可用性，冲突处理是核心成本**。

**无主的 Quorum**：`R + W > N` 保证"读集合与写集合有交集"（至少一个副本有最新值），但**不保证线性一致**（没有全局顺序/事务）；**read repair / hinted handoff** 修复落后副本；**sloppy quorum** 提升可用性但弱化一致性。

**答题句**："**复制模型决定'故障时丢什么'**——单主丢'未复制的写'、多主丢'冲突中的一方'、无主丢'没被读到的旧值'；选型先问'哪种丢失业务能接受'。"

### 2.2.2 一致性哈希与虚拟节点解决什么问题？还有哪些坑？

**普通哈希的问题**：`hash(key) % N`——**N 变化（扩容/缩容）时几乎所有 key 都要重新映射**（缓存大面积失效、数据大迁移）。

**一致性哈希**：把哈希空间组织成**环（0~2^32-1）**，节点与数据都映射到环上，**数据顺时针找第一个节点**——增删一个节点只影响**相邻区间**（约 1/N 的数据迁移），大幅降低抖动。

**虚拟节点**：物理节点少时，环上分布不均（**数据倾斜/热点**）——给每个物理节点映射**多个虚拟节点**（如 150 个）散布在环上，数据落到虚拟节点再归到物理节点——**分布更均匀、扩缩容迁移更平滑**。

**四个坑**：① **热点 key**（一致性哈希解决"节点分布"，不解决"单 key 过热"——要本地缓存/拆 key，27_redis.md 2.2.4）；② **虚拟节点数**（太少不均、太多元数据开销）；③ **节点权重**（异构机器要按容量分配虚拟节点）；④ **扩缩容时的迁移量**（虽然只影响相邻区间，但大集群仍需限速/预热）。

**现代替代**：**Rendezvous/HRW 哈希**（每个 key 对每个节点算权重取最大，增删节点只影响该 key，天然均匀）、**Jump Consistent Hash**（桶数变化时迁移最小、无元数据）、**有界负载一致性哈希**（Google 的算法，防止单节点过载）——报得出名字即加分。

# 3. 分布式事务

## 3.1 事务模型

### 3.1.1 2PC/3PC 的原理与缺陷？

**2PC（两阶段提交）**：
```text
阶段1 Prepare：协调者问所有参与者"能否提交" → 参与者执行事务（锁资源）但不提交，回 Yes/No
阶段2 Commit/Rollback：全 Yes → 通知提交；任一 No/超时 → 通知回滚
```
**三个缺陷（必答）**：**同步阻塞**（Prepare 后资源锁一直持有到阶段 2，吞吐暴跌）；**协调者单点**（协调者挂了，参与者一直等——"悬挂事务"）；**不一致**（阶段 2 部分参与者收到 Commit、部分没收到，网络恢复后状态分裂）。

**3PC（三阶段）**：**CanCommit → PreCommit → DoCommit**，引入**超时**（参与者在 PreCommit 后等不到 DoCommit 可**自行提交**）——**降低阻塞**，但**不能解决网络分区下的不一致**（分区时一半提交一半回滚），且**多一轮 RTT**；工程上**很少直接用 3PC**（XA 生态以 2PC 为主，21_seata.md 4.2.1）。

**为什么数据库还用 2PC**：**单机/同库多资源**（MySQL 内部 redo/binlog 的两阶段，16_mysql.md 4.2.2）与 **XA**（跨库但强一致、低并发）——**2PC 的问题是"跨网络、跨服务、长事务"放大后的**，不是协议本身"错"。

**答题收口**："2PC 用**阻塞换一致**，3PC 用**超时换少阻塞**但没换来一致——分布式事务的现代答案不是'更强的 2PC'，而是**TCC/Saga/消息**（3.1.2）把'锁'换成'补偿'。"

### 3.1.2 TCC、Saga、本地消息表、事务消息怎么选？

| 方案 | 一致性 | 侵入 | 适用 |
|------|--------|------|------|
| **TCC** | 强（业务预留，最终一致） | **高**（Try/Confirm/Cancel + 幂等/防悬挂） | 高并发核心链路（库存/账户），21_seata.md 3.1 |
| **Saga** | 最终（补偿） | 中（正向+补偿） | 长流程/跨组织/遗留系统（21_seata.md 4.1） |
| **本地消息表** | 最终 | 中（同库 outbox + 投递器） | 不想依赖特定 MQ、要自持证据链 |
| **事务消息** | 最终 | 低（MQ 半消息+回查） | 已用 RocketMQ、下游异步（13_rocketmq.md 2.3.1） |
| **2PC/XA** | 强（阻塞） | 低 | 低并发强一致、同库多资源（21_seata.md 4.2.1） |

**选型四问**：① **要不要同步结果**（要→TCC/2PC；不要→消息/Saga）；② **参与方是否可控**（外部系统只有正向/撤销 API→Saga）；③ **并发与热点**（高并发→TCC/消息，别用 XA 锁连接）；④ **失败补偿能力**（有对账/人工→Saga/消息；没有→别上最终一致）。

**答题纪律**：**先问"能不能不分布式事务"**（领域拆分/单库事务，15_spring_cloud.md 1.2.3、21_seata.md 5.1.2）——**框架是最后手段**。

### 3.1.3 Seata 的模式与 CAP 定位？

（细节在 21_seata.md，这里给"理论定位"）
- **AT**：一阶段本地提交 + undo_log + 全局锁，二阶段异步补偿——**偏 AP/最终一致**（默认全局读未提交、失败靠补偿），性能好；
- **TCC**：业务预留 + 补偿——**一致性由业务定义**（可做到接近 CP 的隔离），侵入高；
- **Saga**：长事务补偿——**最终一致**，中间态可见；
- **XA**：数据库 2PC——**CP/强一致**（连接与锁持有到裁决，性能差）。

**一句话**："Seata 不是'一种一致性'，是**四种一致性档位**——按业务选档，而不是'上了 Seata 就强一致'（21_seata.md 5.1.1 的总表）。"

## 3.2 幂等与补偿

### 3.2.1 幂等的本质是什么？幂等键怎么设计？

**本质**：**同一业务意图被执行多次，结果与执行一次相同**——不是"代码里加个 if"，而是**系统对"重复"的识别与拒绝/合并**。

**六种实现（按可靠性排）**：
1. **数据库唯一约束**（最强）：业务唯一键（订单号/请求 ID）建唯一索引，重复插入直接失败——**与业务写入同事务**；
2. **状态机**：只允许"待支付→已支付"，重复支付请求被状态拒绝（订单/工单天然幂等）；
3. **幂等表/去重表**：`(biz_type, biz_id)` 唯一，记录"已处理 + 结果"，重复请求返回原结果；
4. **乐观锁/版本号**：`UPDATE ... WHERE version = ?`，重复更新影响 0 行；
5. **Redis SETNX**：性能高但**与业务不同事务**（先 SET 后业务失败=丢；先业务后 SET=重复窗口）——只适合"削量"；
6. **分布式锁**：串行化同一业务键（成本高，锁的可靠性又是新问题，4.1.3）。

**幂等键（Idempotency-Key）设计**：**客户端生成**（UUID/业务单号）、**与请求体指纹绑定**（同键不同体=拒绝）、**服务端持久化"键→结果"**（重复请求**返回首次结果**而非再执行）、**TTL 覆盖重试窗口**、**并发同键返回 409/等待**（5.2.1 的订单设计）。

**易错**：用"消息 ID"做幂等（重发是新 ID）；只做"插入幂等"不做"更新幂等"（重复扣款）；幂等表与业务表不同事务（状态漂移）；把"接口幂等"当"业务幂等"（下单与支付是两个意图）。

### 3.2.2 补偿与对账怎么设计？"最终一致"怎么保证真的最终？

**补偿的三层**：
1. **实时补偿**：失败立即重试（退避+抖动，避免风暴）；
2. **异步补偿**：MQ 重试/延迟队列/定时任务扫"中间态"（订单超时关单、支付回调补单）；
3. **离线对账**：T+1 比对"业务终态 vs 资源实况"（订单 vs 支付流水、库存 vs 扣减记录）——**兜住所有漏网**。

**对账的设计要点**：**幂等**（重复对账不重复补偿）、**差异分类**（少扣/多扣/状态错）、**人工工作台**（差异不能自动修的进人工，21_seata.md 5.2.2）、**可追溯**（每次补偿有日志/单据）、**告警**（差异率超阈值）。

**"最终一致"真的最终吗（灵魂追问）**：只有**"补偿/对账闭环 + 监控 + 人工兜底"**都成立时才成立——**没有对账的最终一致=永远不一致**（1.1.2 的收口）。**工程上的三个证据**：中间态有超时兜底、失败有重试上限与死信、差异有日报/告警。

**收口**："分布式事务的终点不是'框架保证'，是**'状态机 + 幂等 + 补偿 + 对账'四件套**——框架把概率拉高，对账把概率兜底。"

# 4. 分布式协调与选型

## 4.1 协调服务

### 4.1.1 ZooKeeper 的 ZAB、Watch、会话与典型用途？

**ZAB（ZooKeeper Atomic Broadcast）**：类 Paxos 的**主备原子广播**——**Leader** 处理写、**Follower** 转发写并同步；**zxid（epoch + counter）**标识事务顺序；**恢复模式**（选主/同步）与**广播模式**（正常写）；**多数派**确认后提交——**CP**。

**核心机制**：**会话（Session）**（客户端与 Leader/Follower 的长连接 + 超时；会话过期→临时节点删除）；**临时节点（Ephemeral）**（会话断开自动删——服务注册/锁的基础）；**顺序节点（Sequential）**（全局递增序号——队列/锁排队）；**Watch**（**一次性触发**：节点变化通知一次，要重新注册——"为什么 Watch 会丢"的答案）；**ACL** 权限。

**典型用途**：**配置管理**（节点存配置 + Watch）、**命名服务**、**分布式锁**（临时顺序节点 + 最小节点持有）、**选主**（临时节点争抢）、**集群成员**（临时节点列表）——**Kafka 旧版/K8s 旧版/HBase** 都曾依赖它。

**边界（为什么不适合注册中心）**：**写性能有限**（所有写走 Leader + 多数派）、**CP**（分区时少数派不可用）、**Watch 一次性**（大量客户端要反复注册）、**会话超时**（GC/网络抖动误判）——4.1.2 展开。

### 4.1.2 注册中心为什么多用 AP？ZK/Eureka/Nacos/Consul 怎么选？

**注册中心的本质**：**服务地址的"最终一致缓存"**——客户端拿到**稍旧**的列表，比"拿不到列表"好得多（15_spring_cloud.md 3.1.2 的论证）：**AP 优先**，短暂不一致可接受；**CP 注册中心在分区时会把"少数派的服务"下架**，造成大面积调用失败——**用一致性换来了更大的不可用**。

| 方案 | CAP | 健康模型 | 现状 |
|------|-----|---------|------|
| **ZooKeeper** | **CP**（ZAB） | 会话/临时节点 | 强一致但写性能/可用性不适合大规模注册；Kafka 旧版已弃用 |
| **Eureka** | **AP**（自我保护） | 客户端心跳（30s）+ 剔除（90s） | Netflix 停更，存量；自我保护是"宁可留着坏实例" |
| **Nacos** | **AP + CP 分级**（临时实例 Distro/持久实例 Raft） | 客户端心跳/gRPC 长连接 | 国内主流，注册+配置一体 |
| **Consul** | **CP**（Raft）+ 可选 stale read | 服务端健康检查/Serf | 多 DC/服务网格场景 |

**选型口径**：**Java 微服务 + 国内生态 → Nacos**（AP 注册 + CP 配置、控制台/灰度）；**已有 Consul/多语言/多 DC → Consul**（注意 CP 与 stale read 的取舍）；**ZK 只用于协调（锁/选主/配置），不作为大规模注册中心**；Eureka 只维护存量（17_nacos.md 5.1 的对比）。

**答题收口**："**注册中心选 AP 不是'不要一致性'，是'把一致性降级为最终一致，并把可用性放在第一位'**——服务发现的错误代价（调用失败）远大于短暂看到旧实例（重试可解）。"

### 4.1.3 分布式锁的三种实现与 RedLock 争议？

**三种实现**：
1. **Redis**：`SET key value NX PX ttl`（原子加锁）+ **Lua 脚本校验 value 再删**（防误删别人的锁）；**Redisson** 的 watchdog 自动续期（27_redis.md 4.1.2）；**主从异步复制**下主挂可能丢锁（两个客户端同时持锁）；
2. **ZooKeeper/etcd**：临时顺序节点/Lease + **Watch**；**会话断开自动释放**；**强一致**（多数派）——代价是性能与运维；
3. **数据库**：唯一索引/`SELECT FOR UPDATE`/乐观锁——简单但性能差、易死锁。

**RedLock 争议（必答的"深度题"）**：antirez 提出"**向 N 个独立 Redis 节点加锁，多数派成功且总耗时 < TTL 才算成功**"；**Kleppmann 反驳**：① RedLock 依赖**时钟假设**（节点时钟漂移/GC 停顿会让 TTL 提前失效）；② 没有 **fencing token**，旧持有者的迟到写仍可能生效；③ 对"效率型锁"够用，对"正确性型锁"不够——**推荐用带 fencing 的 etcd/ZK**。**结论**：**Redis 锁适合"防重复/降并发"（效率），不适合"绝对互斥"（正确性）**；要正确性就上 **etcd/ZK + fencing token**（4.2.1）。

**易错**：`SETNX` + `EXPIRE` 两条命令（非原子，中间宕机死锁）；删锁不校验 value（删了别人的）；TTL 太短业务没跑完（锁自动释放，两个持有者）；把 Redisson 的 watchdog 当"永不过期"（进程挂了一样释放）。

## 4.2 一致性与可用性权衡

### 4.2.1 脑裂怎么防？Quorum 与 Fencing Token 怎么配合？

**脑裂**：网络分区让**两个"主子"同时认为自己是 Leader**——双写导致数据冲突/损坏。

**三层防护**：
1. **Quorum（多数派）**：只有拿到多数派的节点才能当 Leader/提交——**分区后最多一边有多数派**（2.1.2 的 Raft、ZK 的过半机制）；**这是"选主"层的防护**；
2. **Term/Epoch 递增**：新 Leader 任期更大，旧 Leader 恢复通信后**自动降级**（2.1.1）；
3. **Fencing Token（栅栏令牌）**：**外部资源**（共享存储/数据库/下游服务）不认识"谁是 Leader"——每次选主发放**单调递增的 token**，资源侧**拒绝比已见 token 更小的请求**——**这是"资源"层的最后防线**（Kleppmann 的核心建议，4.1.3）。

**工程例子**：**分布式锁 + fencing**（锁服务发 token，数据库写带 token，旧持有者的写被拒）；**Kafka 的 Leader Epoch**（2.1.1 的日志截断）；**K8s 的 Lease/leader election**（`resourceVersion` 乐观并发）。

**易错**：只做 Quorum 不做 fencing（旧 Leader 的**外部副作用**仍生效）；把"租约（Lease）"当绝对安全（时钟漂移/GC 停顿会破坏）；脑裂恢复后不校验数据（冲突已写入）。

### 4.2.2 时钟与顺序：Lamport、向量时钟、混合逻辑时钟各解决什么？

**物理时钟的问题**：NTP 有漂移/回拨，**不能用于"判断事件先后"**（跨机器）；单机 `System.currentTimeMillis` 也可能回拨（2.2.1 的雪花 ID 回拨问题）。

**三种逻辑时钟**：
- **Lamport 时钟**：每个事件 `counter++`，消息带 counter，接收方取 `max(local, msg)+1`——**保证"有因果关系的事件"顺序一致**（$a \to b \Rightarrow L(a) < L(b)$），但**反过来不成立**（`L(a)<L(b)` 不代表有因果）；
- **向量时钟（Vector Clock）**：每个节点一个向量，记录"我知道的每个节点的最新计数"——能**检测并发冲突**（不可比较=并发），用于 Dynamo/Cassandra 的冲突检测；代价是**元数据随节点数增长**；
- **混合逻辑时钟（HLC）**：物理时间 + 逻辑计数（`(physical, logical)`），**接近物理时间且保因果**——CockroachDB 等用；**TrueTime（Spanner）** 用"不确定区间 + commit-wait"把物理时钟误差压到可接受，实现**外部一致性**。

**工程映射**：**"谁先谁后"用逻辑时钟/版本号**（不要相信 `update_time` 判断并发）；**"同一秒内多事件排序"用序列号**（数据库自增/雪花）；**跨系统因果**用 traceId/时间线（排查用，不用于正确性）。

**收口**："**分布式系统没有'全局现在'**——顺序要么由**共识**定义（Raft 的日志 index），要么由**逻辑时钟**推导（因果），要么由**物理时钟 + 不确定性边界**逼近（TrueTime）；拿 `now()` 排序是最常见的错误。"

# 5. 工程与面试

## 5.1 架构题

### 5.1.1 设计一个"最终一致"的订单-库存系统，怎么落地？

**先划边界（最重要的一步）**：**订单与库存是两个聚合**（15_spring_cloud.md 1.2.3）——**下单**必须"创建订单 + 锁定/扣减库存"，**支付**要"改订单状态 + 扣减/释放库存"，**取消**要"释放库存"。核心决策：**同步强一致（TCC/本地事务）还是异步最终一致（消息/Outbox）**——按"超卖容忍度"定。

**推荐架构（下单用"预扣 + 确认"、其余异步）**：

```text
下单请求
 ① 订单服务：本地事务创建订单（状态=待支付）+ 写 outbox（OrderCreated）
 ② 库存服务：消费 OrderCreated → Try 预扣库存（冻结字段/记录 reservation），
    幂等键=orderId；成功回执（或由库存发 StockReserved）
 ③ 订单服务：收到预扣成功 → 订单=待支付（可发起支付）；超时未支付 → 取消并释放
 ④ 支付成功 → 支付服务写 outbox（PaymentSucceeded）→ 订单=已支付 → 库存确认扣减
 ⑤ 任何一步失败/超时：补偿（释放预扣/关单）+ 对账（T+1 校验订单与库存/支付流水）
```

**四个关键设计（面试要主动说）**：
1. **Outbox（本地消息表）**：业务写与消息写**同一本地事务**，独立投递器/CDC 发 MQ（13_rocketmq.md 2.3.2）——**解决"订单成功、消息没发"**；
2. **幂等**：消费端按 `orderId+bizType` 去重（唯一索引/状态机），重投不重复扣（3.2.1）；
3. **预扣 vs 直接扣**：预扣（冻结）能**防超卖**且**可释放**；直接扣减要配"取消回补"与对账——高并发下预扣 + 过期释放（定时任务）更稳（21_seata.md 3.1.1 的 TCC 语义）；
4. **超时与补偿**：订单超时未支付 → 关单 + 释放预扣（MQ 延迟消息/定时扫表，13_rocketmq.md 2.2.1）；**所有中间态都有"出口"**（超时/失败/人工）。

**一致性的诚实表述**："**下单成功≠库存最终扣减**（秒级延迟），但**不会超卖**（预扣）/ **不会少卖**（对账补偿）"——**业务可接受 + 有兜底**才叫"最终一致"（1.1.2）。

**易错**：在订单本地事务里直接调库存 RPC（超时/回滚边界不清）；用"消息发送成功"当"库存扣成功"（消费失败/重复）；没有对账（1% 的异常永远查不出来）；预扣没有过期释放（库存永久冻结）。

### 5.1.2 设计一个分布式 ID / 分布式锁服务，怎么选型？

**分布式 ID（按"有序性/可用性/成本"选）**：
| 方案 | 特点 | 适用 |
|------|------|------|
| **雪花（Snowflake）** | 时间有序、64 位、依赖 workerId/时钟 | 大多数业务；注意**回拨/workerId 分配**（22_sharding_sphere.md 2.2.1） |
| **号段（Segment/美团 Leaf）** | DB 批量领号、内存发号、趋势递增 | 高 QPS、可接受"段"跳跃；DB 是弱依赖 |
| **Redis INCR** | 简单、递增 | 低~中 QPS；Redis 可用性是约束（27_redis.md 4.2.2） |
| **UUID/ULID** | 无中心、ULID 时间有序 | 不要求短/可读；ULID 优于 UUID（有序） |
| **数据库自增/序列** | 简单、严格递增 | 单库/低并发；分库分表下不可用 |

**分布式锁（按"正确性要求"选）**：**效率型**（防重复提交/降并发）→ Redis（SET NX PX + Lua，Redisson 看门狗）；**正确性型**（资金/库存互斥）→ **etcd/ZooKeeper（临时节点/Lease）+ fencing token**（4.1.3）；**数据库**（唯一索引/行锁）适合低并发、强一致的短临界区。

**锁服务的四个设计点**：**租约/续期**（业务没跑完锁不能过期——watchdog/Lease）；**可重入**（同线程/同请求 ID 可重入，记录持有者+计数）；**公平性**（ZK 顺序节点/Redis 队列）；**故障释放**（会话断开/租约到期自动释放，不留死锁）。

**答题收口**："**ID 的核心是'趋势有序 + 不撞号'，锁的核心是'正确性等级'**——先问业务能接受什么（ID 可读？锁丢一次行不行？），再选实现；'RedLock 万能'和'Redis 锁不安全'都是懒答案（4.1.3）。"

## 5.2 收口

### 5.2.1 分布式系统的故障模型与设计原则是什么？

**故障模型（先定义"可能坏成什么样"）**：
- **崩溃停止（Crash-stop）**：节点挂了不再回来；
- **崩溃恢复（Crash-recovery）**：挂了会重启（磁盘状态还在）——大多数系统的假设；
- **网络故障**：分区、丢包、重复、乱序、延迟（**最现实也最麻烦**）；
- **拜占庭故障（Byzantine）**：节点会"撒谎"（恶意/硬件错误）——区块链场景；**普通业务一般不设防**。

**六条设计原则（面试按"故障→对策"报）**：
1. **超时 + 重试（退避 + 抖动）**：网络不可靠，**所有远程调用都要有超时**；重试要**幂等**（3.2.1），退避防风暴（18_feign.md 2.2.3）；
2. **幂等**：重复是常态（重试/消息/用户点击）——**唯一键/状态机/去重表**；
3. **隔离（舱壁）**：线程池/连接池/集群隔离，**一个依赖挂了不拖死全部**（20_sentinel.md 1.2.2）；
4. **熔断/降级**：快速失败 + 兜底（缓存/默认值/关闭非核心），**别让慢调用耗尽资源**（15_spring_cloud.md 3.2.3）；
5. **补偿 + 对账**：最终一致的兜底（3.2.2）；
6. **可观测**：日志/trace/指标（**没有观测的分布式系统=黑盒**，15_spring_cloud.md 4.2）。

**"CAP 选择"落到设计**：**按数据分级**（钱=CP/强一致；评论=AP/最终一致）；**按操作分级**（读可旧、写要准）；**按故障阶段**（平时优化延迟 PACELC，分区时保核心）。

**收口**："分布式系统的设计不是'消灭故障'，是**'假设一切都会坏，并让坏的时候影响可控'**——超时、幂等、隔离、熔断、补偿、观测，六件事覆盖了 90% 的线上问题。"

### 5.2.2 面试里怎么把分布式理论与项目结合？

**错误答法**：背 CAP/BASE/Raft 定义，被问"你们项目怎么用的"就卡住。

**正确结构：**"**场景 → 约束 → 选择 → 代价 → 兜底**"（以订单-库存为例）：
- **场景**：下单要扣库存，跨服务、跨库；
- **约束**：不能超卖（强约束）、要扛大促（高并发）、团队不接受 XA 的锁；
- **选择**：预扣（TCC 思想）+ Outbox/MQ 最终一致 + 幂等消费；
- **代价**：中间态（待支付/冻结）可见、秒级延迟、需要补偿任务；
- **兜底**：超时释放、T+1 对账、差异人工工单。

**三个"加分动作"**：① **主动说"我们没上分布式事务框架"**——用本地事务 + 消息 + 对账解决，**成本更低**（21_seata.md 5.1.2 的"最好的分布式事务是少用"）；② **说清"一致性等级"**：哪些数据强一致、哪些最终一致，**按业务分级**；③ **讲一次事故/权衡**：比如"早期用 2PC 导致连接池耗尽，后来改 TCC/消息"——**有代价的决策才是真实经验**。

**理论题的收口句**："**CAP/BASE/Raft 是'词汇表'，项目里的'为什么这么选、坏了怎么办'才是答案**——面试官要的不是你背过论文，而是你**在约束下做过取舍**。"
