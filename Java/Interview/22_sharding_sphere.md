# 1. 定位与架构

## 1.1 从分片到数据库治理

### 1.1.1 ShardingSphere 到底是什么？只是分库分表工具吗？

**出身与现状**：起点是当当网开源的**分库分表 jar**（Sharding-JDBC，作者沈晓磊团队），捐入 Apache 孵化后已成为**顶级项目**；现行版本线 5.5.x。今天的它早已不是"分片工具"，官方定位是**分布式数据库治理生态**——把异构数据库聚合成一个"分布式关系库"并对上层提供额外数据库服务。

**能力全景（从功能清单归纳，答题报得出"分片只是其一"即换维度）**：

| 能力域 | 内容 | 本篇落点 |
|--------|------|---------|
| 数据分片 Sharding | 分库/分表/读写分离的数据路由，分布式主键，事务 | 块 2、3 |
| 数据迁移 Migration | 在线弹性扩缩容：全量+增量+校验+切换 | 4.2.1 |
| 数据安全 | 透明加密（Encrypt）、展示脱敏（Mask）、访问控制（Proxy 权限） | 4.1.1 |
| 流量治理 | 影子库/表（压测隔离）、SQL 审核（Auditor） | 4.1.2 |
| 异构查询 | SQL Federation（跨库联邦查询）、DB Gateway（异构统一入口） | 3.1.3 |
| 管控面 | DistSQL 管理语言、Cluster 模式治理中心、Agent 可观测 | 4.2.2 |

**一句话架构（三层记忆法）**：**接入层**（JDBC/Proxy 两端）→ **内核**（SQL 解析→路由→改写→执行→归并的五步流水线，1.1.3）→ **管控面**（DistSQL/治理中心/存储元数据）。所有"功能"都是插进内核的**可插拔规则**——这正是 5.x "Pluggable"设计哲学：内核不认识"分片"，分片、加密、影子都是插件级规则（**架构追问的满分答案**：为什么一个中间件能同时做分片和加密？因为它们在内核里都只是"改写 SQL 的规则"）。

**与"分库分表"这道题的关系**：分库分表的动机、时机与通用代价（连接爆炸、跨片事务、扩容难）已在 16_mysql.md 6.2.1/6.2.2 讲透——ShardingSphere 是这些问题的**工程化解法集合**，而不是问题本身。

### 1.1.2 JDBC 和 Proxy 两种形态什么区别？Sidecar 去哪了？

**两端对照**：

| 维度 | ShardingSphere-JDBC | ShardingSphere-Proxy |
|------|---------------------|----------------------|
| 形态 | **jar 包**，增强版 DataSource 嵌在应用进程内 | **独立进程**的数据库服务器，接管 MySQL/PostgreSQL/openGauss 等协议 |
| 侵入 | 语言绑定 Java；接入=改数据源+配置规则 | 对应用透明（连它如同连 MySQL）；**异构语言/黑盒系统**唯一解 |
| 性能 | 少一跳网络，接近原生 | 多一跳转发 + 独立容量要压测；但应用侧零 CPU 负担（解析/归并算力和连接池都外移） |
| 运维 | 规则随应用发布（配置漂移风险：N 个应用 N 份规则） | 规则集中管理（DistSQL/治理中心统一），**升级治理逻辑不动应用** |
| 典型场景 | 单 Java 栈、追求极致 RT | 多语言、DBA/BI 工具直连、统一数据服务入口 |

**选型句**："Java 应用内用 JDBC（性能与简洁），异构与集中治理用 Proxy，**两者混部是官方推荐的完整形态**——JDBC 直连吃性能、Proxy 兜住所有旁路流量（报表、脚本、非 Java 服务），两端底层是同一套内核与规则。"（追问"混部规则怎么不打架"——Cluster 模式下规则在治理中心只有一份，两端共享，4.2.2。）

**Sidecar 的下落（旧文纠偏位）**：早年路线图里的 ShardingSphere-Sidecar（云原生 DB Mesh 形态）**从未成为独立 GA 产品**——其思想由两件事接住：**Proxy 本身可当 mesh 数据面**配服务网格（K8s 下每 Pod 旁挂 Proxy/或以 Proxy 为集群级入口，32_kubernetes.md），以及 **Agent**（挂在 JDBC/Proxy 上的可观测与增强探针，不接管数据路径）。今天答题报"双端 + Agent"，再背"三件套含 Sidecar"就是 2019 年的教材了。

### 1.1.3 一条 SQL 在 ShardingSphere 内核里经历哪几步？

**五步流水线**（内核的骨架，DB 网关类组件大同小异——能默出这五步并各带一个例子即学霸）：

```text
① SQL 解析（Parse）：方言引擎 + SQL 文本 → AST（语法树）
   —— 词法/语法/语义三级；决定"这是什么语句、动了哪些表、条件长什么样"
② SQL 路由（Route）：按规则决定去哪
   —— 数据源路由（分片键值 → 库）+ 表路由（→ 物理表）；
     命中绑定表/广播表规则、影子路由、读写分离路由都在这一层（无分片键 → 全路由，2.1.3）
③ SQL 改写（Rewrite）：把逻辑 SQL 改造成物理 SQL
   —— 逻辑表名→物理表名、IN 列表拆片、分页补偿改写（3.1.2）、
     加密列条件改写（4.1.1）、分布式主键填充（2.2.1）、/* SHARDINGSPHERE_HINT: */ 注释路由
④ SQL 执行（Execute）：并发地发往各数据源
   —— 自动加载连接池；同一逻辑操作的多物理语句并行执行；
     事务上下文决定"同一连接"还是"各拿各的"（LOCAL/XA/Seata，3.2.1）
⑤ 结果归并（Merge）：多结果集拼成一个"逻辑结果集"
   —— 流式/内存/装饰器三种归并（3.1.1）
```

**两个易错**：① 说成"先改写再路由"——**没有路由依据就无法改写**（知道去哪片才知道表名/分页怎么改）；② 把解析说成"正则"——是真正的**方言级语法树**（ANTLR 系），这也是它对"没见过的 SQL 要么支持要么明确报错"（SQL 审核兜底）的原因；5.x 另有 **SQL Translator**（方言互译，让 Proxy 用 MySQL 协议喂 PG 后端）报得出即冷门加分。

**追问预备**："性能耗在哪"——解析有 AST 缓存（同模板 SQL 免重解析），大头在路由×执行×归并：单片命中时开销≈原生 + 常量级，全路由/内存归并才是事故位（每步的省法分别对应 2.1.3/3.1.x）。

## 1.2 核心概念

### 1.2.1 逻辑表、实际表、数据节点、分片算法是什么关系？

**四个名词一条链**（以"4 库 × 每库 4 表"为例）：

| 概念 | 是什么 | 例 |
|------|--------|----|
| 逻辑表（Logic Table） | 应用 SQL 里写的**唯一表名**，不存在于任何库 | `t_order` |
| 实际表（Actual Table） | 数据库里真实分片表 | `db0.t_order_0..3` … `db3.t_order_0..3` |
| 数据节点（Data Node） | **库 + 表**的最小路由单元 | `ds_3.t_order_2` |
| 分片算法（Sharding Algorithm） | 分片键值 → 数据节点的函数 | `user_id % 4` 定库、`(user_id / 4) % 4` 定表 |

运行关系：应用对着逻辑表写 SQL → 内核按分片算法把它**投影**到一个或若干数据节点 → 改写、执行、归并。**逻辑库/存储单元（storage unit）**是库层的对应抽象（5.x DistSQL 里数据源以 `REGISTER STORAGE UNIT` 注册）。

**配分片的两条设计纪律（老题答深）**：
1. **分片总量按"终局"定**：按取模分片时，库/表数决定**不可逆**（改模数=重洗全量数据，4.2.1 的迁移再难也不如当初多切几片便宜）——经典句式"**分片键选错毁所有，分片数量算少悔十年**"，单表预估 500 万~2000 万行/表是常见红线（与 16_mysql.md 2.1.2 树高账、6.2.1 拆分时机同源于"单 B+ 树容量"）；
2. **逻辑表名全库统一**：同构分片（每库表结构、表数完全一致）才吃得下广播与弹性机制，异构散表会把运维复杂度打回手工时代。

**易错**：把"数据节点"说成"数据源"——少了一层表维度；追问"不分片的表去哪"——5.x 的**单表规则（Single Table）**自动发现并负载到某存储单元（旧版靠 defaultDataSource，新文旧文交替期的高频露馅点）。

### 1.2.2 绑定表和广播表各解决什么问题？

**绑定表（现名：分片表引用关系 reference rule）**——解决**分片表 JOIN 的笛卡尔积路由**：

```text
未绑定：t_order JOIN t_order_item（都按 user_id 分 4 库）
  → 路由算法互不知情：库1.order × 库1.item、库1.order × 库2.item……16 种组合全查一遍
绑定后（同分片键、同算法的表声明为一个 reference）：
  → 只查"同片对同片"：库i.order ⋈ 库i.item，4 次；且 JOIN 条件里的分片键继续生效
```

配套纪律：**JOIN 的 WHERE 要带分片键**（否则每片组合仍是全路由），绑定关系用 `CREATE SHARDING TABLE REFERENCE RULE` 一类 DistSQL/配置显式声明（5.x 术语从"bindingTable"演进为"sharding reference"，答题点一句"新版叫引用规则"即时效感）。

**广播表（broadcast table）**——解决**小字典表的跨片 JOIN**：配置、地区、币种这类"行数少、人人要 JOIN"的表**每库一份全量**，写操作自动扇出到所有分片（近似"每库缓存同一份"）；JOIN 时永远是本地命中，零跨片成本。**约束要讲**：广播表写放大=库数倍、事务一致性靠内核并发执行保证（不是 DB 级原子）——**低写频高频读**才配当广播表；高频写的"字典"要么上独立服务+缓存（27_redis.md），要么归入分片（16_mysql.md 2.2.6 的反向思路）。

**追问位**："绑定表和广播表能一起用吗"——能：`t_order ⋈ t_order_item`（绑定）再 `⋈ t_currency`（广播）在每片本地完成，这是分片环境关联查询的标准姿势（跨**不同分片键**的两张大表 JOIN 不在此列，见 3.1.3）。

# 2. 分片设计

## 2.1 分片键与策略

### 2.1.1 分片键怎么选？什么是基因法？

**四条原则（按事故代价排序，通用推导见 16_mysql.md 6.2.1，这里是落地细则）**：
1. **覆盖主查询**：最常出现在 WHERE 的字段优先——分片系统的第一性能定律是"**一次查询只打一片**"；查不到分片键=全路由（2.1.3），选键时把 Top SQL 逐条对着打勾，而不是拍业务头脑；
2. **分布均匀、抗倾斜**：哈希均匀（user_id）优先于范围/枚举（region、按天日期——大促当天=一个片爆量，其余围观；时间键只能用 range 分片+热点预案）；NULL 要规避（路由语义不明，配 null 值策略兜底）；
3. **终身稳定**：分片键不可变（改分片键=搬家：先删后插跨片事务）——选**生来不变**的列（user_id、order_no），别选"当前归属"这类会变的字段；
4. **与主键合体最佳**：业务主键即分片键时路由、幂等、去重全顺；不重合时用基因法弥合。

**基因法（Gene Method，本题的灵魂，必考）**：痛点——订单表按 `user_id` 分片（买家视角查询准），但运营要"**按 order_id 查单**"，order_id 里没有 user 基因 → 全路由。解法——**生成 order_id 时把 user_id 的分片位嵌进 ID 尾数**：

```text
分片算法：库 = user_id % 4
发号：order_id = 业务前缀 + snowflake(41bit) + (user_id % 4) 的基因位（如低 2~4 bit）
查询：按 order_id 查 → 取基因位 → 直接定位分片（无需再查 user）
```

代价与纪律：基因位要防**被中间系统截断/格式化**（Long 转 String 走一圈、精度丢失的 JS number 都是事故点——16_mysql.md 5.2.4 的 ID 选型账在此续上）；扩缩容时模数若变，基因位含义要同步重算（与 4.2.1 的迁移预案合并考虑）。**收口句**：基因法的本质是"**让 ID 携带路由信息**"，同一思想在分库分表全家桶里反复出现（雪花 ID 含机器位、号段含租户位，2.2.1）。

### 2.1.2 分片策略有哪几种？Inline、Complex、Hint 各怎么用？

**5.x 的策略三族 × 算法两层**（先掰正旧文的"Standard/Complex/Inline/Hint 并列"——Inline 本质是 standard 的免代码特化）：

| 策略 | 形态 | 适用 | 例 |
|------|------|------|----|
| **标准分片（Standard）** | 单分片键；精确（=/IN）+ 范围（BETWEEN）两个回调 | 绝大多数 | MOD/HASH_MOD/按范围归档 |
| **复合分片（Complex）** | 多分片键共同决定（每键一个值/区间） | 双维度（user+tenant） | 两键哈希混合 |
| **提示分片（Hint）** | 不走 SQL 解析，外部指定分片值 | 特殊路由/DBA/无键表 | 2.1.3 详 |
| （表达式特化）**Inline/Groovy** | 配置里一行表达式自动建算法 | 简单取模/区间 | `t_order_$->{user_id % 4}` |

**内置算法报名字即可**：`MOD`（取模）、`HASH_MOD`（哈希取模，分布更匀）、`VOLUME_RANGE`/`RANGE`（区间，按天归档表）、`INTERVAL`（时间间隔自动建表，配合单表/分表的流水类业务）；主键生成器 `SNOWFLAKE`/`UUID`/`COSID`（2.2.1）。自定义走 SPI（实现分片算法接口注册即可——5.x 接口名与回调签名以版本文档为准，旧版 PreciseShardingAlgorithm/RangeShardingAlgorithm 的"两回调"结构是记忆锚）。

**Inline 的边界**：Groovy 表达式编译成算法，**只支持单分片键的精确匹配**；范围查询不满足时会退化为全路由——"用 INLINE 取模后 BETWEEN 查询慢"的先查这里（旧文档强调 INLINE 不支持范围，5.x 有增强但保守口径照旧：范围需求换 RANGE/标准策略显式实现 range handler）。

**HintManager 用法与场景**（旧题吸收，姿势要新）：

```java
try (HintManager hintManager = HintManager.getInstance()) {   // try-with-resources 防泄漏（ThreadLocal）
    hintManager.addDatabaseShardingValue("t_order", 7L);       // 指定去哪个库（表级同理 addTableShardingValue）
    // 执行不带分片键的 SQL：UPDATE t_order SET status=... WHERE external_no=?（external_no 非分片键）
}
```

场景：① SQL 条件里没有分片键但**业务知道该去哪个片**（旁路单号查询）；② DBA 运维/数据修复定向打片；③ 读写分离强制走主（3.2.2 的一致性兜底）。另有 **SQL 注释 Hint** 形态（`/* SHARDINGSPHERE_HINT: ... */`，对 Proxy/异构语言友好——两端通用能力）。**易错**：Hint 不 close = 下个请求带病路由；Hint 是旁路不是常态，全应用一堆 Hint 说明分片键选错了（2.1.1）。

### 2.1.3 不带分片键的 SQL 会怎样？"全路由"怎么处理才体面？

**默认行为**：没有分片键值可算 → **路由到全部数据节点**（4 库 16 表就发 16 条物理 SQL），结果再内存归并。SELECT 还能忍（慢+吃连接），**UPDATE/DELETE 全路由 = 每个分片都扫一遍锁一遍**，`WHERE 非分片键` 的批量写在分片环境是 P0 姿势错误（单库版灾难见 21_seata.md 2.2.1 同款，这里还多叠一层连接占用）。

**四条正解按优先级**：
1. **改查询习惯**：把分片键带上（前端传/服务层补查）——成本最低收益最大；
2. **基因/索引表**：按非分片键（手机号、外部单号）查是刚需 → 建**异构索引表**：`t_order_mobile(user_id, mobile) → 按 mobile 分片`，双写（或 MQ 最终一致扇出，13_rocketmq.md 2.3.1）；"多维查询"在分片世界不是路由问题，是**数据冗余问题**——这句话是本题的分水岭；
3. **Hint 定向**：调用方其实知道片号（多租户按租户建库）——Hint 强制路由（2.1.2），代码显式、性能确定；
4. **Federation/异构下沉**：报表、运营后台的跨片多维查询**根本不该打穿分片库**——走 SQL Federation 或（更常规）**同步到 ES/ClickHouse 类分析引擎**（24_elastic_search.md）；分片库服务 OLTP，分析流量另开一栈（16_mysql.md 6.2.2"新问题的业界解"在查询侧的具象）。

**易错**：指望"加索引解决全路由"——索引救的是**单片内**扫描，跨 16 张表的物理语句条数与连接占用一条没少；把"全路由"当报错——它是**静默变慢**，性能排查要从"物理 SQL 条数"看起（`show` 执行计划/SQL 日志/Proxy 审计都数得出条数，4.2.2）。

## 2.2 分布式主键

### 2.2.1 分片后主键怎么生成？ShardingSphere 内置方案与雪花坑？

**为什么"每表 AUTO_INCREMENT"直接报废**：各分片各自递增 → 全局撞号（order_0 和 order_1 都有 id=1）；`MAX(id)+1` 抢号有竞态（16_mysql.md 5.2.4 的推导在此复用，一句话带过即可）。

**内置三族**（keyGenerateStrategy 配置，INSERT 不带主键时**自动填充**）：
1. **SNOWFLAKE（默认）**：64bit = 符号位 + 41bit 毫秒时戳 + 10bit workerId + 12bit 序列；趋势递增、对 B+ 树友好（16_mysql.md 2.2.6）。ShardingSphere 对**时钟回拨**有容错：小幅回拨等待/容忍（阈值内置可配，超阈值直接抛异常拒绝发号——宁可失败不发错号；具体参数名以版本文档为准）；**workerId 分配**是隐藏考点：默认基于本机 IP/进程号推导——容器化后 IP 复用、缩容漂移都可能撞 workerId（10 位只有 1024 槽），生产要么显式注入（环境变量/K8s StatefulSet 序号），要么换注册式分配（COSID 家族思路，32_kubernetes.md 的下沉实例）；
2. **UUID**：唯一无忧、**无序致命**——主键随机 → 页分裂、二级索引膨胀（16_mysql.md 2.2.6 的反例本例），分片环境只建议做业务号不做聚簇主键；5.x 的 UUID 策略已带有序变体；
3. **COSID/号段（扩展）**：号段模式（DB 批量领段缓存内存发，2~3 位数量级 QPS 上限、断网有缓冲段）与第三方 COSID 中心——要"绝对短且单调"的业务单号用它；跨分片库无状态的还有 Redis INCR 家族（27_redis.md 4.2.2，代价：强依赖 Redis 可用性）。

**设计纪律（答题增量）**：① **主键与分片键解耦**——主键谁也不代表，分片键管路由（两者想合体走基因法，2.1.1）；② 发号**放中间件层还是业务层**要全局统一（ShardingSphere 自动填充只对"经过它"的写生效——绕过中间件直连分片库的脚本自带 id 就能撞规则，4.1.2 影子压测同款"旁路必失控"）；③ ID 对外暴露时防遍历（雪花可推断产量，业务单号加混淆）。

**易错**："UUID 主键 MySQL 性能差所以别用分片"——因果错位，差在**B+ 树聚簇索引**这一层（换有序主键即用）；"雪花有时钟依赖所以机房要统一 NTP"——对，但**回拨容错行为要报得出**（等/抛两派，ShardingSphere 属混合策略），这是这题真正在考的东西。

# 3. 查询·事务·读写分离

## 3.1 结果归并

### 3.1.1 多分片结果集怎么拼成"一个结果"？归并引擎的三种姿势？

**问题定性**：路由把一条逻辑 SQL 变成 N 条物理 SQL、N 个结果集；归并（Merge）层负责让应用拿到"仿佛查了一个库"的**统一游标**。三种归并按内存代价排序：

| 归并 | 机制 | 触发条件 | 例 |
|------|------|---------|----|
| **流式归并** | N 个结果集各持游标，按排序键**多路归并**边比边吐，内存驻留 N 行 | ORDER BY 列在 SELECT 中且可用 | `ORDER BY order_time` 跨 16 片吐 10 行 |
| **内存归并** | 全量结果收进内存再排序/分组/去重 | ORDER BY 列不在 SELECT、GROUP BY、DISTINCT | `DISTINCT user_id` 各片去重后全局去重 |
| **装饰器归并** | 在流式/内存之上做**聚合翻译** | COUNT/SUM/MAX/MIN/AVG | AVG 拆成 SUM+COUNT 双下推再相除 |

**聚合下推的翻译账（必考细节）**：`SELECT AVG(amount), COUNT(*) FROM t_order` 跨片**不能**"AVG 的 AVG"——改写层把 AVG 拆为 `SUM(amount) AS _sum, COUNT(amount) AS _cnt` 下发，归并层 Σ_sum/Σ_cnt 再合成；`MAX` 直接取各片 MAX 的 MAX；`COUNT` 求和。**"中间件帮我翻译聚合函数"是 ShardingSphere 被低估的能力**，答题把 AVG 拆解写出来就赢一半。

**内存归并的爆炸半径**：`SELECT * ... ORDER BY create_time LIMIT 10` 若 create_time 不在 SELECT 列（或被 `SELECT *` 掩盖的投影错位）→ 各片全量进内存再排——归并层的"功能正确、性能降级"红线；治理动作与 3.1.2 分页、2.1.3 全路由同一批（SQL 审核插件把这类写法拦在上线前，4.2.2）。

**易错**：① 把流式归并说成"把各片排好序再首尾相接"——是**多路归并**（K 个游标比头元素）；② 忘了归并还管 GROUP BY 的补集（改写层补投影列 → 归并层算完 → 输出前再把补的列裁掉，"改写-归并"是一对连体设计）。

### 3.1.2 分片下深分页为什么更慢？ShardingSphere 怎么改写、怎么治？

**先算账**：`LIMIT 100000, 10` 逻辑上"跳过 10 万取 10"，但**每片都不知道全局位次**——改写层的标准动作是每片下发 `LIMIT 0, 100010`（取够全局可能用到的前缀），归并 16 × 100010 行后截 10 行。**放大系数 = 分片数**：单库深分页已经慢（16_mysql.md 5.1.3 的"回表×偏移扫描"账），分片环境还要再乘一层网络传输与内存归并——**这是分片系统性能投诉的头号来源**。

**框架内的缓解**：流式归并省内存（排好序的头 10 行到达即可断流？——**不能**，必须各片都吐到 100010 才能保证全局序，流式只省"全驻内存"不省"扫描与传输"，把这个误区讲清是本题真正考点）。

**工程正解（把 16_mysql.md 5.1.3 的方案升级到分片维度）**：
1. **游标翻页（无限滚动）**：`WHERE (sort_col, id) > (上页末值) ORDER BY sort_col LIMIT 10`——每片各取 10、归并取 10，**放大系数从 100010 变 10**；牺牲"跳页"换性能，App 列表场景标配；
2. **两步定位**：先只查主键（覆盖索引，各片 LIMIT 0,100010 换成 10 列宽的行——传得动），再按全局 10 个 id 反查详情（单片精确命中）——16_mysql.md 5.1.3 延迟关联的分片版；
3. **业务约束**：搜索类"第 N 页封顶"（前端限 100 页）、运营导出走异步任务 + 分析库（2.1.3 第 4 条）；
4. **数据布局**：按时间 range 分片 + 时间键入查询，深分页退化为单片内问题（2.1.1 的选键反推）。

**收口句**："分片不解决深分页，只放大深分页——**治它的钥匙永远在'位次如何被确定'**：要么让数据自己携带位次信息（游标），要么把翻页需求请出 OLTP。"

### 3.1.3 跨库 JOIN 怎么办？SQL Federation 是什么、边界在哪？

**场景分型（先分类再给药）**：
1. **同分片键、已声明引用关系**（订单 ⋈ 明细）：绑定路由本地 JOIN，无跨库问题（1.2.2）；
2. **不同分片键的两张大表 JOIN**（订单 ⋈ 用户，订单按 user_id、用户按 id……等等，**用户按 id 分片且 id 即 user_id 时其实同键**——真异构键如"商品 ⋈ 订单明细"）：分片世界没有"中间件帮你 shuffle"的免费午餐；
3. **分片库 ⋈ 未分片小库/异构库（MySQL ⋈ PG）**。

**三条出路**：
- **冗余与广播**：把被 JOIN 的一侧做成广播表（小表，1.2.2）或**基因/索引表**（大表，2.1.3）——把 JOIN 问题降维成"每片本地可完成"；
- **应用层组装**：先查驱动集 → 按分片键分组 → IN 批量点查另一侧 → 内存拼装（分片环境的"B 树 Nested Loop"）——**代码丑但可控**，高并发主链路常见；
- **SQL Federation**：5.x 内置的联邦引擎（Apache Calcite 支撑）——把跨数据源 JOIN/聚合改写成"下推 + 本地计算"混合计划，让 ②③ 两类查询**能跑**；开关打开后按标准 SQL 语义执行。**边界三句诚实话**：联邦不是 MPP——大结果集跨库拉取的性能仍受制于最慢一侧与归并内存（报表量级会教做人）；方言与函数下推能力随版本演进（以版本文档为准）；**它保功能正确，不保你的 SLA**——分析流量终归该走数仓/ES（24_elastic_search.md），联邦是给"零星跨源查询"的兜底，不是给核心链路的捷径。

**DB Gateway 顺带一句**（与 Federation 别混）：Gateway 是 **Proxy 的协议接入能力**（MySQL 协议喂 PG/Oracle 后端等异构聚合），解决"入口方言统一"，不解决"跨片 JOIN 性能"（1.1.3 的 Translator 同族）。

## 3.2 事务与读写分离

### 3.2.1 ShardingSphere 的三种事务类型？为什么默认反而是 LOCAL？

**类型全景**（`@ShardingSphereTransactionType` / 配置 `transactionType`，属性细节以版本文档为准）：

| 类型 | 机制 | 语义 | 代价 |
|------|------|------|------|
| **LOCAL（默认）** | 各分片各自本地事务，连接随用随还 | 单分片内事务 = 原生 ACID；**跨分片原子性无保证**（第 3 片失败，前 2 片已提交） | 零开销 |
| **XA** | 嵌入 Atomikos/Narayana 等 JTA 管理器，逻辑事务横跨多 XAResource，两阶段提交 | 跨分片强一致 | 连接与 DB 事务管理器全程占用（Seata XA 同款账，21_seata.md 4.2.1）；性能显著降 |
| **SEATA** | 对接 Seata：LOCAL 之上加 `@GlobalTransactional`，分支事务由各分片的 AT/XA 执行 | 跨**服务+跨分片**的全局事务；AT 一阶段本地提交、快速释放 | Seata 依赖全家桶（TC 部署、undo_log 每库一份，21_seata.md 5.2.1） |

**"为什么默认 LOCAL"的三层论证（旧文说"默认集成 Seata"是过时错误，纠偏位）**：
1. **概率设计**：好的分片键让绝大多数事务**单分片命中**（一个用户的一笔订单操作只落一片，2.1.1）——跨片事务是少数派，不该让全量流量为它付协调成本；
2. **降级观**：真正跨服务/跨片的一致性诉求应先在**架构层**解决（消息异步、Saga 补偿，21_seata.md 5.1.2）——中间件事务是"必须同步原子"那一小撮的武器；
3. **历史包袱**：早年版本默认接 Seata AT，5.x 明确改为 LOCAL——**升级评审要重查事务类型**，"升级后事务语义变了"是真实事故类别（旧文"默认 BASE/Seata"正源于 4.x 时代）。

**XA 的实现细节（追问位）**：ShardingSphere 的 XA 不是"接一个 XA datasource"，而是**内核持有跨片多连接、统一由 JTA 管理器编排二阶段**——应用侧照常 `@Transactional`；Atomikos/Narayana 依赖显式引入（special-api 文档目录里三种都有）。**Seata 集成的资源视角**：分片环境的每个物理库都是一个 RM 资源——20 库 = 20 分支（全局锁与 undo_log 分布到每库，分片 × 分布式事务的**组合复杂度要主动报**：锁热点、迁移期间的事务切换预案，4.2.1）。

**易错**："LOCAL 就是没事务"——错，单片内完整 ACID；错的是把 LOCAL 用于跨片写原子性的场景。判断口径：**一条业务操作会打几个分片？会不会部分成功？** 后者不允许时用 XA（同服务跨片）或 Seata（跨服务），再反问一句"能不能改成单片命中/异步化"（先架构后中间件，15_spring_cloud.md 1.2.3 同款纪律）。

### 3.2.2 读写分离怎么配？主从延迟下的一致性怎么保？

**规则形态**（readwrite-splitting rule，5.x 与分片规则正交——分片库的每库都可以再挂一主多从）：

```yaml
rules:
  - !READWRITE_SPLITTING
    dataSources:
      ds_rw:
        writeDataSourceName: ds_0_primary
        readDataSourceNames: [ds_0_replica1, ds_0_replica2]
        transactionReadQueryType: PRIMARY    # 事务内读默认强制主库（一致性内置项）
        loadBalancerName: rr
    loadBalancers:
      rr:
        type: ROUND_ROBIN                    # 另有 RANDOM；权重类走 SPI 自定义
```

**机制三句**：写（及事务内读）走主、独立 SELECT 按均衡算法摊到从库；LB 内置轮询/随机，**按延迟自适应摘除不是 5.x 内核的现役主打能力**（旧文"心跳检测自动摘除延迟从库"属 4.x 读写分离实现，5.x 把健康判定交给外部——报"路由归中间件、摘除归探活体系"即纠偏到位，K8s readiness/云 LB/DBA 监控各显神通，32_kubernetes.md）。

**延迟账与一致性谱（主从复制原理见 16_mysql.md 6.1.1/6.1.3，这里是中间件侧的消费）**：
1. **写后立读（read-your-writes）**——最危险窗口：刚插的订单刷不出来。对策按代价升序：① **事务内强制主**（`transactionReadQueryType: PRIMARY`，默认已如此——事务提交后的**新请求**依旧可能读从，这层不覆盖）；② **Hint 强制主**：`HintManager.setReadwriteSplittingOnly()` 包住"写后读"关键路径（2.1.2 的 Hint 家族在此的第二用途）；③ **延迟感知路由**：应用比较 binlog 位点/GTID（自己维护"该从库追到哪"）——重，一般不上；④ **业务兜底**：写接口直接返回新对象渲染页面，绕开读依赖（最便宜也最常用）；
2. **会话粘滞**：同一用户短时间读同一片从库（减少跨副本跳变）——LB 换成按用户哈希的自定义算法（SPI）；
3. **容忍窗口声明**：报表/列表标注"数据延迟 ≤ N 秒"——把一致性问题降级为产品语义，常常才是正解。

**容量侧两笔账**：从库承接读流量的**比例假设**要按真实读写比验证（8:2 的库摊到 2 从 1 主仍会把从打满——主仍要接事务内读与 Hint 读）；**从库数与连接放大**：应用连接池 × 从实例数，Proxy 混部时更要算中间件自身连接（16_mysql.md 6.1.3 的"连接治理"在此续账）。

**易错**：把读写分离当"分库分表的附赠品"随便开——**它改变一致性语义**（本征最终一致），开启前要按接口逐条过"这个读能容忍多旧"；"从库挂了自动切主"——5.x 内置路由不做熔断切换（熔断在探活层/LB 层），主挂读写全停是 HA 问题不是中间件问题（16_mysql.md 6.1.2 的 MGR/半同步选型才是答案）。

# 4. 功能扩展与运维

## 4.1 数据安全与流量隔离

### 4.1.1 透明加密（Encrypt）和展示脱敏（Mask）的区别？各怎么落地？

**先把旧文的混淆掰开**（"内置 AES/MD5 自动加解密、查询条件自动转换、这就是脱敏"——把两个功能说成了一个，面试撞上必露馅）：

| 维度 | Encrypt（数据加密） | Mask（数据脱敏） |
|------|--------------------|------------------|
| 保护对象 | **落库数据**（拖库/备份泄露/DBA 直读） | **查询结果**（越权展示、客服看全号） |
| 可逆性 | 可逆（密钥在应用/KMS） | 单向（脱敏值不回滚） |
| 存储 | 密文列（可保留明文列用于兼容） | 存储不动 |
| 生效点 | 写入加密 / 读取解密 / **等值条件改写** | SELECT 输出时打码 |
| 典型算法 | AES/SM4 家族（密钥管理是命门） | `MASK_FROM_X_TO_Y`（手机号 138****1234）、摘要类 `MASK_MD5` 等（内置清单以版本文档为准） |

**Encrypt 的机制与代价**：规则声明逻辑列 → 物理密文列；INSERT 自动加密写入，SELECT 自动解密返回（应用只见明文）；**WHERE 对加密列的等值/IN 查询改写成对密文列比较**（确定性加密才可能——同明文同密文）；**LIKE/范围/排序在密文上不成立**（随机 IV 或语义丧失），需要时上"明文摘要列辅助查询"或退回业务层设计（把可检索字段留明文、敏感载荷加密的"信封"模式）。**迁移姿势**：存量数据不是装上规则就自动加密——历史明文列要么用 4.2.1 的迁移思路刷数，要么"新读走密文、旧读兼容明文"双列过渡（字段只加不改的发布纪律，19_spring_cloud_gateway.md 3.2.1 同款）。密钥进 KMS/配置中心加密项，**别硬编码**（11_spring_security.md）。

**Mask 的机制与边界**：只作用于**返回结果集**——存储与等值查询不受影响，性能代价≈无；配置按列声明算法即可。组合拳形态：库里密文（防内部与泄露）+ 出口脱敏（防展示越权）+ 审计（4.2.2），三件事分层清晰即高分。

**易错**：① "MD5 加密手机号"——MD5 是摘要不是可逆加密，手机号这类小空间值 MD5 可彩虹表穷举（要摘要就加盐/HMAC，密码场景的口径 11_spring_security.md 讲透）；② 以为加密后"查询条件随便写"——只有确定性加密 + 等值谓词可行（上面的边界段）；③ 脱敏配置在 Proxy、加密配置在 JDBC 规则不一致——两端共享内核与治理中心（Cluster 模式），规则应以一份为准（4.2.2）。

### 4.1.2 影子库、影子表是干什么的？压测流量怎么被"认出来"？

**要解决的问题**：生产环境做全链路压测，压力必须打穿**真实拓扑**（网关→服务→分片库），但绝不能污染真实数据——**影子（Shadow）**规则给 ShardingSphere 装了个"流量分流阀"：判定为压测的 SQL **改写去影子数据源/影子表**，正常流量原样。

**两种形态**：
- **影子库**：整套镜像实例（同构库表），压力打向独立资源池——**性能数据干净**（真实库的磁盘/连接不受挤压），成本是要养一套影子集群；
- **影子表**：同库内 `t_order_shadow` 镜像表（内核自动建表/加后缀）——省资源，但**热点资源与真实业务共抢**（真实 TPS 被压测挤兑，容量测试口径失真——两形态的取舍是这题的深水区，别只报定义）。

**"压测标"怎么进来（shadow source 三选）**：① **HINT**：`HintManager.setShadowDatabase(true)` / SQL 注释 `/* SHARDINGSPHERE_HINT: SHADOW_DB=true */`——脚本级压测常用；② **正则**：SQL 命中规则进影子；③ **列值**：`WHERE shadow_flag = 1` 类字段判定——**生产全链路压测的正解是端到端染色**：压测流量入口打标（网关写 `X-Shadow` 头，19_spring_cloud_gateway.md 3.2.1 的灰度分流同款机制）→ RPC 透传（18_feign.md 4.2.1 的拦截器三件套之第三件）→ 应用把标记塞进 HintManager/上下文 → ShardingSphere 分流。**压测标断在哪一环，哪一环就写真实库**——染色链路演练是压测上线前的必做项（与灰度标、XID 的透传纪律同构，1_java.md 3.4 ThreadLocal 治理在此三连击）。

**运维配套**：影子数据清理任务（压测后 truncate 窗口）、影子库/表的容量与真实库同步（schema 变更要双发，4.2.1 迁移工具顺手可用）、**影子账号与生产隔离**（防"压测标丢了打真实库"的最后防线是账号权限而不是标记本身——这句报出来即实战派）。

## 4.2 弹性与治理

### 4.2.1 在线扩容（数据迁移）的原理？DistSQL 的迁移生命周期？

**问题回顾**：模数分片下加库/加表意味着存量数据重分布（2.1.1 "算少悔十年"的救赎方案，16_mysql.md 6.2.2 的扩容难题在此落到产品件）。**5.x 内置 Migration 模块**（旧代靠 ElasticJob+Canal 外挂，已收编为内核能力），生命周期五段：

```text
① 规划：新规则声明（如 4 库 8 表 → 8 库 16 表），内核计算"哪些数据节点要动"
② 全量：按 chunk 分片搬运存量（源库快照读，速率与线程数受控——
   别把迁移打成线上全表扫描风暴，16_mysql.md 5.1.2 同款纪律）
③ 增量：订阅 binlog（MySQL）/WAL（PG）追平迁移期间新写入（机制同 14_canal.md）
④ 校验：行数/内容（CRC 类算法，CHECK MIGRATION / START MIGRATION CHECK）
⑤ 切换：COMMIT MIGRATION 原子换规则（治理中心广播，各计算节点生效）；
   不满意 ROLLBACK MIGRATION 退回旧规则——切换前双份数据、切换后旧数据待清理
```

**DistSQL 动词族**（报名字即证明用过）：`MIGRATE TABLE INTO`（单表→分片表：最常见的"入伙"操作）、`SHOW MIGRATION LIST/STATUS`、`CHECK MIGRATION`、`STOP/START MIGRATION`、`COMMIT/ROLLBACK MIGRATION`。**三个经典场景**：单库→分库分表（迁移即改造）、分片扩容（4→8 库）、**异构库入平台**（PG 数据搬进 MySQL 集群统一治理，配 Gateway/Translator）。

**工程要点（比原理更值钱的四句）**：
1. **双写窗口不存在**——迁移期读写照旧走旧规则、增量追新写，这是它优于"停机导数"的根本；但要接受**切换瞬间的连接重置**与规则广播的短暂视图差（4.1.1 治理中心的推送语义）；
2. **校验不是可选项**：内容校验的开销按"低峰跑全量 + 抽样高频"设计，校验不过绝不 COMMIT；
3. **分布式事务与迁移叠加要预案**：Seata/XA 在途分支跨越切换点——**迁移动作前冻结全局事务发布窗口**（大促冻结的同款纪律，21_seata.md 5.2.2）；
4. **缩容是反向迁移**：把目标片的数据搬空再下线存储单元（`UNREGISTER STORAGE UNIT` 前先用 `SHOW RULES USED STORAGE UNIT` 核对没规则依赖它——报错文案即检查清单）。

### 4.2.2 DistSQL 是什么？Standalone 与 Cluster 模式差在哪？

**DistSQL = 管控 SQL**：像操作数据一样操作**规则**的专用语言，四类动词：
- **RDL**（规则定义）：`CREATE SHARDING TABLE RULE`、`CREATE ENCRYPT RULE`、`CREATE READWRITE_SPLITTING RULE`……——改分片规则不再改 YAML 重启；
- **RQL**（规则查询）：`SHOW SHARDING TABLE RULE`、`SHOW STORAGE UNITS`、`SHOW MIGRATION STATUS`——"当前系统怎么配的"可查询化（旧 YAML 时代靠 grep 配置文件的运维代差）；
- **RAL**（运行管理）：`ENABLE/DISABLE COMPUTE NODE`、读写分离熔断开关（`ALTER READWRITE_SPLITTING RULE DISABLE`——从库故障应急摘除，3.2.2 的"探活层"缺位在管控面的补位件）、`LOCK/UNLOCK CLUSTER`（变更窗口互斥）、`EXPORT/IMPORT METADATA`；
- **RUL**（调试）：`PREVIEW SQL`——**一条逻辑 SQL 会发成哪些物理 SQL、打到哪些节点，上线前当场验**（2.1.3 全路由排查、3.1.2 分页验证的利器，报得出 PREVIEW 即真用过）。

**运行模式**：
- **Standalone**：元数据存本地（内存/JDBC 持久化）——单机开发测试；重启规则还在（5.x 的 standalone 也持久化了，旧文"重启丢规则"是更早年代的坑），但**多实例各存各的**=配置漂移温床；
- **Cluster**：ZooKeeper 为治理中心——规则/元数据/计算节点状态集中，**JDBC 与 Proxy 共享同一份真相**、DistSQL 变更秒级广播全体节点、新计算节点启动自动拉规则入伙（1.1.2 混部选型的底层承诺在此兑现；与业务配置中心 Nacos 的分工：Nacos 管应用配置，治理中心管**数据层拓扑**——两个"配置中心"不是一回事，答串了扣分）。

**可观测与应急配套**：Proxy 原生 Prometheus 指标（连接数/路由分布/物理 SQL 耗时）+ **Agent**（无侵入挂在两端上的 metrics/tracing/logging 插件，1.1.2 的下落在此闭环）；`SHOW COMPUTE NODES` 看集群成员版本与状态（灰度升级新节点时逐个看，RAL 的 DISABLE 节点是发布预案件）。

# 5. 选型与实践

## 5.1 方案对比

### 5.1.1 分片方案怎么选：ShardingSphere、MyCat、云分布式数据库、自研？

**先记一句判决框架**：分片改造只有两条路——**在现有 MySQL 上加一层"智能"**（中间件路线）或**换掉"数据库本身"**（新引擎路线）；再往旁边站一层问"要不要分"（16_mysql.md 6.2.1 的替代谱：读写分离、归档冷热分层、单表容量治理、分区表）。

| 方案 | 形态 | 拿到什么 | 付出什么 |
|------|------|---------|---------|
| **ShardingSphere-JDBC** | 客户端 jar | 性能最好、无额外故障域；全家桶功能（加密/影子/迁移/联邦） | Java 绑定；规则随应用治理；连接池/版本升级绑定发布节奏 |
| **ShardingSphere-Proxy** | 独立代理 | 异构语言透明接入、集中治理（DistSQL/Cluster） | 多一跳 + 新故障域（它自己要 HA）、容量单独压测 |
| **MyCat** | 独立代理（开源老炮） | 功能够用、社区素材多 | 演进停滞、SQL 语义边角坑多、治理面弱——**新项目基本不再选**，面试报"历史地位+现状态"即可 |
| **云原生分布式 DB**（PolarDB-X、OceanBase、TiDB 家族） | 新数据库引擎 | 原生分布式事务/在线扩片/计算下推/MPP，**应用近乎透明** | 换引擎=迁移工程 + 成本 + 生态锁定；自运维门槛高（多托管）；细节语义（自增序列、隔离级别、函数支持）要重新对表 |
| **自研分片** | 代码 | 极致贴合业务 | 重复造轮子+轮子没人检——除非只有"按租户路由"这类极简需求，否则报"不推荐" |

**口径三条**：① **存量 MySQL 栈 + Java 主导 → ShardingSphere-JDBC 起步，异构/治理诉求出现时补 Proxy**（两端同内核的混部优势是它对"渐进式架构"最友好的一点）；② **愿意接受引擎替换、要透明弹性 → 云分布式库**——"买能力"与"买中间件"是两种预算哲学，面试把代价结构讲清即不站错队；③ 无论选谁，**分片键、热点、跨片查询、扩容预案这四件事都躲不掉**——中间件解决"执行"，不解决"设计"（2.1 全篇的通用化收口，呼应 21_seata.md 5.1.2 的"架构优先"句）。

## 5.2 落地实践

### 5.2.1 分库分表上线的踩坑清单？

**按事故代价排序的十条**（每条=症状+根因，面试报 5 条带细节胜过背 20 条名词）：
1. **跨片写靠 LOCAL 硬扛**：症状=偶发"钱扣了货没出"且无框架报错；根因=多片写事务只有片内原子性（3.2.1）；解法=单片命中设计→XA/Seata→异步补偿三级判断；
2. **分片键倾斜**：上线三月某库爆量（大租户/热点商户全在一片）——2.1.1 的均匀性没做实，事后只能加盐重分布或大租户独库（4.2.1 迁移流程救场）；
3. **深分页与全路由混用**：后台报表一条 `ORDER BY 非索引列 + LIMIT 大偏移` 打出千条物理 SQL 拖死 Proxy——PREVIEW SQL 验收上线（4.2.2），报表流量迁分析栈（2.1.3）；
4. **DDL 没打全所有分片**：新字段部分片没有 → INSERT 列不匹配间歇报错；根因=DDL 不属于分片内核的自动广播范围；解法=迁移脚本遍历所有数据节点 + `REFRESH TABLE METADATA` 刷治理中心元数据（16_mysql.md 5.1.1 的 Online DDL 每片各跑）；
5. **绕过中间件的写**：DBA 脚本/老服务直连分片库，主键撞号、影子数据漏进真实表——分片系统的"绕过即失控"（2.2.1/4.1.2），账号权限与 Proxy 统一入口收编；
6. **容器化 workerId/配置漂移**：雪花 workerId 随 Pod 名复用 → 凌晨主键冲突（2.2.1）；standalone 模式下 N 个应用 N 份 YAML 手改不一致 → 同逻辑表路由打架（4.2.2 上 Cluster 的硬理由）；
7. **事务类型跨代升级**：4.x 默认 Seata → 5.x 默认 LOCAL，升级没核对语义 → "跨片写不再回滚"静默事故（3.2.1 纠偏段的现实版——**中间件升级回归要覆盖事务用例**）；
8. **读写分离当免费性能**：事务内读默认主库没意识到、从库延迟引发"下单后查不到"客诉（3.2.2 一致性谱）；
9. **迁移窗口没冻结预案**：扩容切换与发版/大促重叠，校验失败回滚时又叠了 DDL（4.2.1 工程要点 3/4）；
10. **监控只看接口 RT**：物理 SQL 条数、各片连接池水位、治理中心版本 diff 不设指标——分片系统的故障是**分片维度的**，聚合指标会抹平它（4.2.2 观测面；5.2.2 收尾）。

### 5.2.2 怎么验证分片方案上线就绪？给一套评审动作。

**把清单变成动作（面试给这套"怎么做"远胜"有什么"）**：
1. **路由验真**：核心接口全量过 `PREVIEW SQL`——每条 SQL 的物理下发数、命中节点写进设计文档（预期单片命中的成了 16 片，当场拦下）；
2. **压测分层**：基准=同 SQL 单库版对照；压测走影子库（4.1.2），关注 Proxy/JDBC 两端各自的瓶颈位（Proxy 看连接数与 CPU 解析开销，JDBC 看连接池×分片数的放大，3.2.2 连接账）；**热点键专项**：大租户/爆款 SKU 单独压（2.1.1 倾斜、21_seata.md 2.2.2 热点同构）；
3. **故障演练**：从库摘除（3.2.2 DISABLE 开关实操）、单分片库主挂（该片写全停、其他片无恙的"半瘫"预期要向业务确认——**分片没有单点，只有分区点**）、治理中心失联（ZK 抖动时规则只读不改、缓存继续服务，4.1.1 同款"能用不能变"）；
4. **数据正确性**：迁移校验（CHECK MIGRATION）之外，上线跑**双读比对**任务（新旧规则各查一遍 diff，金融口径必备）；
5. **预案落名**：扩容 runbook（4.2.1 五段 + 冻结窗口）、回滚 runbook（ROLLBACK/IMPORT METADATA 恢复规则）、**极端预案**——"中间件带不动"的退路（Proxy 摘除退回单库、流量降级到只读，12_nginx.md 的降级分层思想落到数据层）。

**收口句**："分库分表的上线就绪 = **路由可预期（PREVIEW）、容量可放大（影子压测）、故障可分区（演练）、数据可校验（双读）、退路可执行（runbook）**——五件事有名字有动作，这题就答完了；背特性清单而不谈验收的，是没上过线的。"
