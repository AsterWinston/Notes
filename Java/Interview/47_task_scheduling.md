# 1. 知识点
- **定时任务应用场景**: 数据报表定时生成、订单超时自动取消、数据定时同步、缓存定时刷新、日志定时清理、定时发送通知
- **Quartz**: Java生态最经典的定时任务框架，支持Cron表达式、JDBC持久化任务、集群部署、Misfire处理策略
- **Quartz核心组件**: Job(任务定义实现Job接口)、JobDetail(任务详情描述)、Trigger(触发器CronTrigger/SimpleTrigger)、Scheduler(调度器核心引擎)
- **Quartz JobExecutionContext**: 任务执行上下文，包含JobDetail、Trigger、Scheduler引用、mergedJobDataMap等，在Job的execute方法中获取
- **Cron表达式**: 七域：秒 分 时 日 月 周 年(可选)。如`0 0/5 * * * ?`表示每5分钟执行。`?`表示不指定，只能用于日和周。`L`最后一天/最后一个星期几。`W`最近工作日。`#`第几个星期几
- **Quartz Misfire策略**: 任务因调度器宕机或线程池满错过执行时的处理。WITH_MISFIRE: 立即触发一次。DO_NOTHING: 等待下一个触发点。IGNORE_MISFIRE: 立即触发所有错过的
- **Quartz JDBC持久化**: 将Job和Trigger信息存储到数据库(11张表)，调度器重启后自动恢复任务，支持集群部署(多个调度器竞争DB行锁保证只有一个执行)
- **Quartz集群**: 多节点共享数据库任务表，通过数据库行锁(SELECT...FOR UPDATE)实现任务互斥执行，保证同一任务不会在多节点同时执行。不支持分片
- **Spring @Scheduled**: Spring内置轻量级定时任务注解。`cron` Cron表达式、`fixedDelay`固定延迟(上次执行结束到下次开始的间隔)、`fixedRate`固定频率(任务开始的间隔，允许并行)
- **@Scheduled局限性**: 单机执行(不支持集群)、不支持动态添加/修改任务、不支持分片、无管理界面、Misfire无处理。适合简单场景
- **XXL-JOB**: 大众点评开源分布式任务调度平台，轻量级、功能完善，国内使用广泛。核心组件：调度中心(Admin)和执行器(Executor)
- **XXL-JOB调度中心**: Admin集群部署，负责任务配置管理、Cron解析、任务调度触发(路由到执行器)、失败重试、告警、任务日志
- **XXL-JOB执行器**: Executor应用内嵌，启动时注册到调度中心。接收调度请求、执行任务、返回执行结果。支持自动注册和手动录入
- **XXL-JOB路由策略**: 调度中心选择哪个执行器执行任务。FIRST(第一个)、LAST、ROUND(轮询)、RANDOM、CONSISTENT_HASH、LEAST_FREQUENTLY_USED、LEAST_RECENTLY_USED、FAILOVER、BUSYOVER、SHARDING_BROADCAST
- **XXL-JOB阻塞处理策略**: 单机串行(默认，排队)、丢弃后续调度(正在执行时跳过)、覆盖之前调度(正在执行时终止旧任务开始新任务)
- **XXL-JOB分片广播(SHARDING_BROADCAST)**: 调度中心向所有执行器广播任务，执行器根据分片参数(shardIndex/total)处理自己的那部分数据。如3个执行器处理全量数据各负责1/3
- **XXL-JOB分片实现**: `select * from user where id % total == shardIndex`，各执行器按模运算处理不同数据分片
- **XXL-JOB GLUE模式**: 任务代码直接在Admin界面编辑(Groovy/Shell/Python/PHP/Node.js/PowerShell)，无需发布应用，适合临时任务、调试
- **XXL-JOB任务依赖**: 子任务功能。父任务执行完毕后自动触发子任务，支持多级依赖链。可用于任务编排(如数据导入→数据清洗→报表生成)
- **XXL-JOB失败重试与告警**: 任务失败自动重试(可配置重试次数)，支持邮件/钉钉/企业微信告警。任务超时也可配置处理策略
- **XXL-JOB任务日志**: 每次触发记录执行日志(调度时间、执行器、参数、结果、耗时)，支持日志查询和清理
- **Elastic-Job**: 当当开源的分布式调度方案，基于ZooKeeper协调。支持分片、弹性扩容、失效转移。分为ElasticJob-Lite(无中心)和ElasticJob-Cloud(容器化)
- **Elastic-Job vs XXL-JOB**: Elastic-Job是去中心化(基于ZK选举)，XXL-JOB是中心化(调度中心)。XXL-JOB有更强的可视化管理界面，入门更简单
- **PowerJob**: 新一代分布式任务调度框架，支持MapReduce分布式计算、工作流(DAG任务编排)、在线编辑、容器化。性能优于XXL-JOB(自研通讯框架)
- **PowerJob vs XXL-JOB**: PowerJob支持更复杂的工作流(DAG)、MapReduce任务(海量数据处理)、在线日志查看、容器化部署。XXL-JOB更轻量，满足大部分定时调度需求

# 2. 面试题

## 2.1 Quartz的Misfire策略有哪些？怎么处理？
Misfire(错过触发)发生在调度器宕机、线程池满、任务执行时间过长超过下次调度时间等场景。

**CronTrigger策略**：
- `MISFIRE_INSTRUCTION_IGNORE_MISFIRE`：忽略错过的触发(立即执行所有错过的)
- `MISFIRE_INSTRUCTION_FIRE_ONCE_NOW`：立即执行一次，之后按正常Cron调度
- `MISFIRE_INSTRUCTION_DO_NOTHING`：等待下一个Cron周期(默认)

**处理建议**：
- 报表生成等补做有意义：用FIRE_ONCE_NOW
- 时间敏感任务(如定时通知)：用DO_NOTHING(过期的通知没意义)
- 需要严格执行次数：用IGNORE_MISFIRE

生产环境常用DO_NOTHING + 告警，避免补做大量任务导致雪崩。

## 2.2 Quartz集群模式如何工作？能解决什么问题？
Quartz集群基于数据库共享存储(11张表，以QRTZ_开头)。多个Quartz Scheduler实例共享同一数据库：
1) 每个Scheduler实例从数据库读取Trigger信息
2) 竞争数据库行锁(SELECT...FOR UPDATE)获取任务执行权
3) 获得锁的节点执行任务，更新数据库任务状态
4) 其他节点循环等待获取下一个任务

**解决的问题**：
- 高可用：一个节点宕机，其他节点接管
- 多任务并发：多个任务可分布在不同节点执行
- 场景：多实例应用部署定时任务，防止重复执行

**局限性**：不支持任务分片、大量任务时数据库成为瓶颈、时间同步要求高。

## 2.3 XXL-JOB的架构和核心组件是什么？
**调度中心(XXL-JOB Admin)**：独立部署，提供Web管理界面。负责任务CRUD、Cron解析、调度触发(HTTP调用执行器)、失败重试、告警、日志、用户权限管理。可集群部署(Nginx负载均衡)。

**执行器(XXL-JOB Executor)**：嵌入业务应用。启动时注册到调度中心(心跳发现)，接收HTTP调度请求，执行任务逻辑(反射调用标记了@XxlJob的方法)。支持自动注册和手动录入注册。

**调度流程**：Admin触发任务 → 查询注册的执行器列表 → 按路由策略选择执行器 → 发送HTTP请求(携带任务参数) → 执行器执行任务 → 回调Admin报告结果 → Admin记录日志。

**任务线程模型**：执行器内部维护任务线程池，线程池满时按阻塞策略处理。

## 2.4 XXL-JOB的分片广播如何工作？适用什么场景？
分片广播(SHARDING_BROADCAST)流程：
1) Admin将任务广播到所有执行器节点
2) 每个执行器收到相同的任务但不同的分片参数：shardIndex(分片序号0开始)、shardTotal(总分片数=执行器数量)
3) 业务代码根据分片参数处理不同数据集：`SELECT * FROM table WHERE id % shardTotal = shardIndex`

**适用场景**：
- 数据量大的定时任务(如每天全量扫描千万级用户表并处理)
- 需要多机器并行加速的场景
- 如3台机器，每台各处理1/3数据(如id%3=0,1,2)

**注意事项**：执行器宕机时分片参数动态变化，可能导致数据重复/遗漏，需业务做好幂等。

## 2.5 XXL-JOB的阻塞处理策略有哪些？如何选择？
| 策略 | 行为 | 适用场景 |
|------|------|---------|
| 单机串行(默认) | 排队等待上次执行完 | 任务不能并发，需严格顺序 |
| 丢弃后续调度 | 正在执行则跳过本次 | 定时任务执行一次即可，不补做 |
| 覆盖之前调度 | 终止旧的，执行新的 | 最新一次最重要(如实时数据更新) |

选择：数据统计汇总用单机串行；发送通知用丢弃(通知一次就行)；缓存刷新用覆盖(需要最新数据)。

## 2.6 XXL-JOB和Elastic-Job各有什么优缺点？
**XXL-JOB**：
- 优点：中心化架构(管理方便)、Web界面功能完善、上手简单、中文文档全、社区活跃、支持GLUE在线编辑
- 缺点：调度中心强依赖(中心化单点风险，需集群)、调度延迟(HTTP远程调用)、不支持DAG工作流

**Elastic-Job**：
- 优点：去中心化(ZK协调，无调度中心单点)、弹性扩缩容(增加节点自动分片)、失效转移(节点宕机自动迁移)
- 缺点：依赖ZooKeeper(运维成本)、管理界面功能较少、配置复杂、社区增长速度慢于XXL-JOB

一般中小型团队推荐XXL-JOB(够用+好用)，对高可用要求极高的场景可考虑Elastic-Job。

## 2.7 PowerJob相比XXL-JOB有什么优势？
| 维度 | XXL-JOB | PowerJob |
|------|---------|----------|
| 工作流 | 子任务链(线性) | DAG图(复杂编排) |
| 分布式计算 | 分片广播(简单) | MapReduce(Map Reduce合并) |
| 通讯 | HTTP(性能一般) | 自研框架(高性能) |
| 容器化 | 不支持 | 原生支持K8s |
| 在线日志 | 需下载查看 | Web端直接查看 |
| 适用 | 常规定时任务 | 任务编排+海量数据处理 |

如果业务有复杂的任务依赖DAG、大数据量处理，推荐PowerJob；常规定时任务XXL-JOB足够。

## 2.8 @Scheduled注解的fixedDelay和fixedRate有什么区别？
- `fixedDelay`：固定延迟时间，从**上次任务执行结束**开始计时，到下次任务开始的时间间隔。任务不会并发执行。
- `fixedRate`：固定频率，从**上次任务开始执行**开始计时，到下次任务开始的时间间隔。若单次执行时间超过间隔，本次执行完后立刻开始下次(不会并行，默认单线程)。

示例：`fixedRate=5000`，任务执行耗时2000ms → 间隔为5000(从开始) → 每5秒一次。若任务执行耗时7000ms → 间隔为7000(实际执行完才触发下次)。

建议：任务执行耗时稳定的用fixedRate；不确定耗时的用fixedDelay；要保证两次执行不重叠的都使用单线程池+fixedDelay。

## 2.9 为什么项目中使用XXL-JOB而不是Spring自带的@Scheduled？
Spring `@Scheduled` 底层使用 `ScheduledExecutorService`，适用于简单单机定时任务，但存在明显局限性：

| 维度 | @Scheduled | XXL-JOB |
|------|-----------|---------|
| 可视化管理 | 无，任务状态不可见 | Web控制台，任务配置/状态/日志一目了然 |
| 集群支持 | 不支持，多实例重复执行 | 原生集群，通过路由策略避免重复 |
| 任务分片 | 不支持 | 分片广播，多节点并行处理大数据 |
| 失败重试 | 需自行实现 | 内置失败重试+告警(邮件/钉钉/企微) |
| 动态管理 | 需改代码重启 | 动态添加/修改/暂停/恢复任务 |
| 调度日志 | 无集中日志 | 每次触发记录详细执行日志 |
| 高可用 | 单点 | 调度中心+执行器均支持集群 |
| GLUE模式 | 不支持 | 支持在线编辑(Groovy/Shell等) |

**结论**：`@Scheduled` 适合开发测试或极简单的单机场景。生产环境分布式部署推荐XXL-JOB，可视化、可运维、可扩展。
