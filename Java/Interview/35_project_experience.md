# 1. 项目表达框架

## 1.1 结构与量化

### 1.1.1 怎么讲清项目架构？30 秒、3 分钟、10 分钟三版怎么准备？

**面试官听架构，想确认三件事**：你**是否真的理解全局**（不是只写自己那摊）、**能否分层表达**、**知道每个组件的取舍**。**准备三版**：

**30 秒版（电梯陈述，先给全景）**：
> "这是一个电商交易系统，微服务架构：接入层 Nginx + Gateway 做统一鉴权和限流；业务层按领域拆了用户/商品/订单/支付/库存约 20 个服务，Spring Cloud Alibaba 体系（Nacos 注册配置、Sentinel 限流熔断、Feign 调用）；数据层 MySQL 分库分表 + Redis 缓存 + RocketMQ 削峰 + ES 搜索；部署在 K8s，Prometheus + SkyWalking 观测。我主要负责订单域（下单/支付/履约），也参与过网关与稳定性建设。"

**3 分钟版（分层 + 关键取舍）**：在 30 秒骨架上补：**为什么这么拆**（领域边界/团队规模）、**关键链路**（下单→库存→支付→履约的调用与消息）、**数据流**（MySQL 为真相、ES/缓存为投影、MQ 解耦）、**一两个取舍**（如"库存没用 XA，用预扣 + 最终一致"）。

**10 分钟版（能画图 + 讲演进）**：白板画**部署图/调用图**；讲**演进史**（单体 → 拆分 → 分库分表 → 容器化），每一步的**痛点与触发**；讲**容量与故障**（峰值 QPS、瓶颈在哪、怎么扛）；讲**你负责模块的深水区**（一个具体设计/优化/事故）。

**画图三要素（白板题必备）**：**分层**（接入/业务/中间件/数据/运维）、**方向**（同步调用实线、消息虚线）、**标注**（关键组件 + 你的模块）。**别画成"全家桶堆砌"**——每个组件说得出"为什么在这"。

**易错**：上来就讲自己模块（没有全局）；组件名报一堆但说不清数据流；架构图与简历/项目描述不一致（追问就穿帮）；把"公司架构"说成"我设计的"（诚实区分"参与/负责/主导"）。

### 1.1.2 项目指标怎么量化？QPS/TPS/DAU 怎么换算才可信？

**三类指标（面试官会交叉验证，别拍脑袋）**：
1. **规模**：DAU/MAU、订单量/日、服务数/实例数、数据量（表行数/存储 TB）、团队规模；
2. **流量**：**峰值 QPS**（按接口）、TPS（按业务事务）、消息量/日、缓存命中率；
3. **质量**：可用性（99.9%/99.95%）、P99 延迟、错误率、故障次数/恢复时长（DORA，33_cicd.md 5.1.1）。

**换算公式（把"感觉"变成"算得出来"）**：
```text
平均 QPS ≈ DAU × 人均请求数 / 86400
峰值 QPS ≈ 平均 QPS × 峰值系数（集中度，常见 3~10；大促另算）
并发数 ≈ 峰值 QPS × 平均响应时间（Little 定律；如 5000 QPS × 0.2s = 1000 并发）
容量/存储 ≈ 日增数据量 × 保留天数 × 副本/索引膨胀系数
```
**可信表达的三条纪律**：① **说区间与口径**（"订单创建接口峰值约 5000 QPS，大促 1.2 万"）；② **能解释怎么来的**（监控/压测/日志统计，不是"大概"）；③ **与架构对得上**（5000 QPS 配 3 个实例、每实例 1700——单机能力要合理；说 10 万 QPS 但只有 2 台 4C8G 就露馅）。

**追问预案**："峰值怎么测的"（全链路压测/线上监控）；"瓶颈在哪"（DB/缓存/带宽/下游，报一个具体的）；"扩容怎么做"（HPA/加副本/分片，32_kubernetes.md 4.2.1）；"大促怎么准备"（2.1.3）。

**易错**：QPS 与 TPS 混用（2.1 的对照）；把"日请求量/86400"当峰值（低估一个数量级）；指标与故障故事矛盾（说高可用但讲不出降级）。

## 1.2 选型与取舍

### 1.2.1 技术选型怎么答？给三个真实例子。

**万能框架（四步）**：**场景与约束 → 候选对比 → 选择依据（业务/团队/成本）→ 落地效果与代价**。

**例 1：注册中心选 Nacos**
- 场景：20+ 服务、300+ 实例，要注册发现 + 配置管理；
- 候选：Eureka（AP 但停更）、ZK（CP、写性能/可用性不适合大规模注册，34_distributed_theory.md 4.1.2）、Consul（CP、多 DC 强但团队不熟）、Nacos（AP 注册 + CP 配置）；
- 依据：**服务发现要 AP**（分区时宁可旧列表）、**配置要可靠**（Nacos 持久实例/CP）、团队 Spring Cloud Alibaba 背景、一体化省运维；
- 代价：Nacos 自身要高可用（3 节点 + MySQL）、版本升级要跟（17_nacos.md 5.1）。

**例 2：消息队列选 RocketMQ**
- 场景：订单事件、削峰、事务消息（下单后通知）；
- 候选：RabbitMQ（低延迟但堆积弱）、Kafka（吞吐强但无原生事务消息/延时）、RocketMQ（事务消息/延时/重试齐全）；
- 依据：**业务消息要事务消息与重试**、团队 Java 栈、国内生态；
- 代价：运维一套 MQ、NameServer/Broker 的容量与监控（13_rocketmq.md 5.1）。

**例 3：缓存选 Redis + Caffeine 两级**
- 场景：商品详情高读、热点集中；
- 候选：仅 Redis（网络 RT + 热点打满单分片）、仅本地（一致性差）、两级（本地挡热点 + Redis 共享）；
- 依据：**热点读**用本地挡、**一致性**用短 TTL + 失效广播；
- 代价：本地缓存一致性窗口、内存成本（27_redis.md 2.1.2）。

**答题收口**："选型不是'选最强的'，是**在业务约束、团队能力、运维成本下选最合适的**——并且**说得出代价**（没有代价的选型=没想过）。"

### 1.2.2 "为什么不用 X" 怎么答才不踩坑？

**原则**：**不贬低、不硬吹、讲约束**——面试官可能就是想听你对 X 的理解。

**三步答法**：① **承认 X 的优点**（显示你懂）；② **说明本项目约束**（数据量/团队/时间/合规）；③ **给出选择后的验证**（效果/代价）。

**示例（为什么不用 Dubbo 用 Spring Cloud）**：
> "Dubbo 的 RPC 性能和治理很成熟；我们团队是 Spring 背景、要快速落地，Spring Cloud 与 Boot/配置中心/网关集成成本更低，HTTP 调试也更方便；代价是性能不如 RPC——但我们的瓶颈在 DB 不在 RPC，所以够用。如果后面有高频核心链路，会考虑局部下沉 Dubbo/gRPC。"（15_spring_cloud.md 2.1.3 的选型口径）

**示例（为什么不用 Kafka 用 RocketMQ）**：Kafka 吞吐/生态强，但我们需要**事务消息/延时/重试**，且团队已有 RocketMQ 运维经验；日志类场景仍会用 Kafka（31_kafka.md 5.1.1）。

**三个禁忌**：**"X 太老了/太差"**（暴露无知）；**"领导定的"**（没有思考）；**"没考虑过"**（诚实但减分——补一句"如果重来我会怎么评估"）。

**收口**："'为什么不用 X'考的是**技术判断力**——能说出 X 的适用边界、本项目的约束、以及'什么情况下会换'，比硬选一个赢。"

# 2. 深度技术故事

## 2.1 性能与稳定性

### 2.1.1 性能优化怎么讲成故事？（从 2.5s 到 200ms 的完整链路）

**七段式模板**：**背景 → 现象（量化）→ 定位（证据）→ 根因 → 方案（权衡）→ 结果（对比）→ 沉淀（防复发）**。

**示例（订单列表 2.5s → 200ms）**：
- **背景**：订单列表页，日均 200 万 PV，大促翻 5 倍；
- **现象**：P99 从 800ms 涨到 2.5s，DB CPU 70%→95%，超时告警；
- **定位**：SkyWalking 显示一次列表查询触发 **N+1 次用户/明细查询**；Arthas `trace` 显示 SQL 扫描 20 万行；`EXPLAIN` 显示 `type=ALL`（无索引）；
- **根因**：① 循环查用户（N+1）；② 查询条件 `(user_id,status,create_time)` 无联合索引；③ 深分页 `OFFSET 100000`；
- **方案**：**一次 JOIN/批量 IN** 替代 N+1；建**联合索引**（最左前缀匹配）；**游标分页**（`id < lastId`）；用户信息加 **Caffeine 本地缓存**（TTL 60s）；**异步**写浏览日志；
- **结果**：P99 200ms、DB CPU 45%、QPS 承载翻倍；**代价**：缓存一致性窗口（可接受）、游标分页不支持跳页（产品确认）；
- **沉淀**：慢 SQL 告警（>1s）、SQL 审核门禁、压测基线（16_mysql.md 5.1.2、33_cicd.md 3.2）。

**三个"讲得好"的细节**：**有对比数字**（前后、代价）；**有被否决的方案**（"也考虑过加 Redis 缓存整页，但一致性/内存成本高，先做 SQL 优化"）；**有防复发**（不只是"改了代码"）。

**易错**：只说"加了缓存"（面试官会追问穿透/一致性/失效）；把"优化成果"夸成 10 倍但说不出测量方法；不讲代价（显得没做过权衡）；把团队成果说成个人（诚实边界）。

### 2.1.2 线上故障怎么讲？（CPU/Full GC/MQ 积压/慢 SQL 的 STAR 模板）

**通用结构**：**影响（用户/业务/时长）→ 发现（监控/告警/客诉）→ 止血（降级/回滚/扩容）→ 定位（证据链）→ 根因（直接/根本）→ 修复 → 复盘（行动项）**。

**四个高频故障的"一句话根因 + 关键证据"**：

| 故障 | 典型根因 | 关键证据 | 止血/修复 |
|------|---------|---------|----------|
| **CPU 100%** | 死循环/正则回溯/频繁 GC | `top -Hp` + `jstack` 线程栈；GC 线程高看 `jstat` | 限流/摘节点；修代码/调参（30_linux.md 2.1.3） |
| **Full GC 频繁** | 内存泄漏/堆太小/大对象 | `jstat -gcutil` FGC 增长；dump + MAT 引用链 | 扩容/重启止血；修泄漏/调堆（2_jvm.md 5.3.1） |
| **MQ 积压** | 消费慢/消费者挂/生产突增 | lag 曲线、消费线程栈、下游 RT | 扩消费者/批量/迁移 Topic（13_rocketmq.md 3.3.2） |
| **慢 SQL** | 缺索引/大表 Join/锁等待 | 慢日志、`EXPLAIN`、`SHOW PROCESSLIST` | 加索引/改写/限流；SQL 审核（16_mysql.md 5.1.2） |

**示例（MQ 积压 80 万）**：大促前营销消息突增 + 消费端同步调用积分服务变慢 → lag 半小时涨到 80 万；**止血**：消费者扩容 4→12、批量消费、积分调用改异步/降级；**根因**：消费逻辑串行 + 下游无限流；**复盘**：lag 斜率告警、消费端压测、下游隔离（线程池/信号量）。

**复盘纪律（33_cicd.md 5.2.2）**：**Blameless**（对事不对人）、**时间线**、**5 Whys**、**行动项有 owner/截止**、**演练验证**（不是"加强责任心"）。

**易错**：只讲"我们重启恢复了"（没根因）；把"用户投诉"当发现渠道（监控缺失）；复盘行动项全是"加强测试"（不可执行）；夸大/缩小影响（面试官会交叉问）。

### 2.1.3 高并发/大促怎么讲？（容量规划、限流降级、压测）

**五段式**：**目标 → 容量评估 → 改造 → 演练 → 大促保障**。

1. **目标**：峰值 QPS/订单量、可用性目标（99.95%）、核心链路清单；
2. **容量评估**：按 1.1.2 的公式算 QPS/并发/存储；**全链路压测**（生产影子/独立环境）找瓶颈（DB/Redis/带宽/下游）；**单机基线 × 实例数 × 安全系数（0.7）**；
3. **改造**：**缓存**（热点/多级）、**异步/削峰**（MQ）、**限流**（网关/接口/热点参数，20_sentinel.md）、**降级**（非核心功能开关）、**隔离**（线程池/集群）、**扩容**（HPA/预留资源）、**DB**（读写分离/分库分表/索引）；
4. **演练**：**全链路压测 + 故障注入**（杀实例/断依赖/限流触发）、**预案演练**（降级开关、回滚）；
5. **保障**：**大促值班**、**监控大盘**（QPS/错误率/P99/DB/缓存/MQ）、**限流阈值**按压测值设、**一键降级**、**回滚预案**、**容量水位**（80% 告警）。

**示例口径**："大促峰值订单创建 1.2 万 QPS，是日常 6 倍；我们做了：库存预扣（TCC 思路）、下单异步化（MQ 削峰）、网关按用户限流、非核心（推荐/评论）降级、DB 分库分表 + 热点库存分桶；压测验证到 1.5 万 QPS，P99 < 300ms；大促当天零故障。"

**易错**：只讲"加了机器"（没有瓶颈分析）；限流阈值拍脑袋（没压测）；降级没演练（真出事不敢点）；把"没出事故"当"设计好"（可能是流量没到）。

## 2.2 一致性与数据

### 2.2.1 分布式事务/最终一致怎么结合项目讲？

**先给结论**："我们**没有上分布式事务框架**，用**本地事务 + 消息（Outbox）+ 幂等 + 对账**实现最终一致——因为跨服务强一致的成本（锁/可用性）大于业务收益。"（34_distributed_theory.md 5.1.1 的架构）

**讲清四件事**：
1. **边界**：哪些操作必须原子（订单创建 + 库存预扣）、哪些可最终一致（积分/通知/搜索索引）；
2. **方案**：本地事务写业务 + outbox；投递器/CDC 发 MQ；消费端幂等（唯一键/状态机）；失败重试 + 死信；
3. **异常**：超时/重复/乱序怎么处理（幂等键、版本号、状态机）；**补偿**（超时关单/释放库存）；**对账**（T+1 订单 vs 支付 vs 库存）；
4. **代价**：中间态可见（"待支付/冻结"）、秒级延迟、需要人工工作台。

**示例（下单-库存）**：预扣（冻结）→ 支付成功确认扣减 → 超时释放；**为什么不用 XA**：连接/锁持有到裁决，大促扛不住；**为什么不用 TCC 全家桶**：只有库存一个热点，局部用预扣即可，其他走消息（21_seata.md 5.1.1）。

**追问预案**："消息丢了怎么办"（outbox + 对账）；"重复消费"（幂等）；"库存超卖"（预扣 + 唯一约束 + 对账）；"对账发现差异"（分类/自动补偿/人工）。**易错**：说"用了 Seata 就强一致"（AT 默认全局读未提交，21_seata.md 2.1.3）；只讲框架不讲业务兜底。

### 2.2.2 数据迁移、分库分表、缓存一致性怎么讲？

**分库分表（22_sharding_sphere.md）**：**为什么拆**（单表 > 2000 万/磁盘/写入瓶颈，16_mysql.md 6.2.1）→ **怎么拆**（按 user_id 哈希、基因法、双写/迁移）→ **代价**（跨片 JOIN/事务/深分页/扩容）→ **怎么解**（绑定表/广播表/异步索引/游标分页/迁移工具）。

**数据迁移（四步）**：**双写**（新旧库同时写，读旧）→ **全量 + 增量**（历史数据搬 + binlog 追平）→ **校验**（行数/抽样/checksum）→ **灰度切读/切写**（按用户/比例）→ **回滚预案**（双写窗口保留）。

**缓存一致性（27_redis.md 2.1.2）**：**Cache-Aside**（读缓存→ miss 查 DB 回填；写 DB 后**删缓存**）——**为什么删不是更新**（并发写乱序）；**延迟双删**（删→更新 DB→延迟再删）；**binlog 订阅**（Canal 异步失效，14_canal.md）；**短 TTL 兜底**；**热点 Key** 本地缓存 + 逻辑过期。

**示例口径**："订单表 4 库 16 表按 user_id 哈希；迁移用双写 + binlog 追平 + 校验，灰度按用户 ID 切读，切写后观察一周再下线旧库；缓存用 Cache-Aside + 删除 + binlog 失效，热点商品加本地 Caffeine 60s。"

**易错**：分片键选错（查询全路由，22_sharding_sphere.md 2.1.1）；迁移不做校验（数据错到线上才发现）；缓存"先删后写"或"写完不删"（脏数据）；只说方案不说回滚。

# 3. 架构与设计题

## 3.1 系统设计

### 3.1.1 现场系统设计题怎么答？（澄清→估算→高层→深入→权衡）

**六步框架（白板顺序）**：
1. **澄清需求（3~5 分钟，别急着画）**：功能（核心用例）、非功能（QPS/延迟/一致性/可用性）、边界（不做啥）；**问出关键约束**（读多写少？强一致？预算？）；
2. **估算**：QPS/存储/带宽（1.1.2 的公式）；**找出瓶颈**（写多→DB/MQ；读多→缓存/CDN）；
3. **API 与数据模型**：核心接口（方法/参数/返回）、表/索引/分片键；
4. **高层架构**：接入→服务→存储→异步链路；**画图讲数据流**；
5. **深入 1~2 个点**（面试官会指定）：如"库存怎么防超卖""消息怎么不丢""深分页怎么解"——**用专题篇的深度答**；
6. **权衡与故障**：CAP/一致性、扩容、监控、降级、成本。

**示例（秒杀系统）**：读多写少 + 瞬时高并发 + 不能超卖 → **前端**（静态化/CDN/按钮防重）→ **网关**（限流/黑名单）→ **服务**（库存预扣 Redis Lua/分段库存、异步下单 MQ、幂等）→ **DB**（最终扣减/对账）→ **兜底**（售罄降级/排队页）；**权衡**：Redis 扣减的可靠性 vs DB 强一致（最终对账）。

**三个加分动作**：**主动说"先不做什么"**（MVP 边界）；**给出两个方案并选一个**（显示权衡）；**讲失败路径**（"如果 Redis 挂了怎么办"）。

**易错**：一上来堆组件（没有需求澄清）；只画 happy path（没有失败/降级）；数据模型与访问模式不匹配（没想查询）；不估算（容量拍脑袋）。

### 3.1.2 微服务拆分/DDD 怎么结合项目讲？

**拆分依据（按优先级）**：**业务能力/领域边界**（DDD 限界上下文）> **团队组织**（康威定律）> **变更频率/伸缩需求**；**不是"按技术层拆"**（Controller/Service/DAO 拆服务是反模式）。

**DDD 的落地（别背名词）**：**战略**（子域：核心/支撑/通用；限界上下文：订单/库存/支付）；**战术**（聚合根：订单是聚合根，订单行是实体；值对象：金额/地址；领域事件：OrderCreated）；**数据库**：**一服务一库**（15_spring_cloud.md 1.2.3），跨服务只通过 API/事件。

**拆分的代价与节奏**：**分布式事务/跨服务查询/联调/运维**成本上升；**单体优先**（模块化单体）→ 按痛点**渐进拆分**（绞杀者模式：新功能新服务、老功能逐步迁）；**别一次性拆 20 个服务**（团队扛不住）。

**示例口径**："我们从单体按领域拆了订单/库存/支付/商品四个核心域，先拆**变更最频繁 + 伸缩需求最强**的订单；库存因为强一致留在同库事务，支付独立（合规/对账）；拆完用 API + 事件解耦，DB 独立，跨域查询走 BFF/读模型。"

**易错**：按表拆（订单表一个服务、订单明细一个服务）；共享数据库（"微服务"但一个库，15_spring_cloud.md 1.2.3）；拆完没有治理（链路/限流/契约）；把 DDD 当"分层代码模板"（Aggregate/Repository 名词堆砌）。

## 3.2 工程实践

### 3.2.1 CI/CD、代码评审、测试怎么讲？

**CI/CD（33_cicd.md）**：**一条流水线**（PR 快速检查 → 主干全量 → 制品 → 部署）；**一次构建、到处部署**；**自动化门禁**（单测/覆盖率/扫描/质量门）；**发布策略**（滚动/金丝雀/蓝绿）；**回滚**（镜像/配置/数据三层）；**度量**（部署频率/前置时间/失败率/恢复时间）。

**代码评审（26_git.md 3.1.2）**：**小 PR**（<400 行）、**自审**、**关注点**（正确性/边界/异常/性能/安全/可测试）、**blocking vs nit**、**24h 响应**；**用工具兜底**（格式/lint/静态扫描），人看"设计与逻辑"。

**测试（33_cicd.md 3.1）**：**金字塔**（单测多、集成中、E2E 少）；**Testcontainers** 起真实依赖；**契约测试**（微服务）；**flaky 治理**（隔离+修复，不重跑）；**覆盖率**（新代码门禁，别刷数字）。

**示例口径**："我们把 Jenkins 迁到共享库 + 声明式流水线，PR 流水线 8 分钟（单测+扫描+Sonar 增量），主干构建镜像并推 Harbor（digest 固定），ArgoCD 同步 K8s；发布用金丝雀 + 指标门禁，回滚 1 分钟内；DORA 前置时间从 3 天降到 4 小时。"

**易错**：只说工具名（没有流程与门禁）；测试只有"单元测试"（集成/E2E 缺失）；评审说"看得细"（没有关注点/机制）；发布没有回滚。

### 3.2.2 监控、告警、值班、复盘怎么讲？

**可观测三支柱（15_spring_cloud.md 4.2.2）**：**Metrics**（Prometheus + Grafana：QPS/错误率/P99/资源/中间件）、**Logs**（ELK/Loki + traceId）、**Traces**（SkyWalking/OTel：跨服务链路、SQL/缓存耗时）。

**告警设计（症状而非原因）**：**SLO/错误预算**（可用性/延迟）；**用户视角**（下单成功率、支付成功率）> 资源指标（CPU 高不一定有故障）；**分级**（P0 电话/P1 群/P2 工单）；**抑制/聚合**（防风暴）；**每条告警有 runbook**（怎么查/怎么止血）。

**值班与复盘**：**on-call 轮值**、**升级路径**（15 分钟未解决升级）、**事故指挥**（谁止血/谁沟通）；**复盘**（时间线/根因/行动项/演练，33_cicd.md 5.2.2）。

**示例口径**："核心链路配了 SLO（下单 99.95%），告警按错误率/延迟燃烧率；每季度做一次故障演练（杀实例/断 Redis/限流），复盘行动项进 Jira 跟踪；值班有 runbook 和升级机制。"

**易错**：只监控 CPU/内存（用户无感）；告警太多（疲劳，最后没人看）；没有 runbook（新人值班抓瞎）；复盘不跟踪（同样故障重演）。

# 4. 软技能与追问

## 4.1 行为面试

### 4.1.1 "最有成就感/最难/最后悔"的项目怎么答？

**三个问题的考察点不同（别用同一个故事套）**：
- **最有成就感**：**影响力 + 你的独特贡献**（不是你参与的最大项目，而是"因为你有何不同"）；
- **最难**：**技术/协作复杂度 + 你的坚持与方法**（考察深度与抗压）；
- **最后悔**：**反思能力 + 成长**（考察自我认知，不是真的"比惨"）。

**统一结构（STAR + 判断）**：**背景（一句话）→ 任务/约束 → 行动（你的决策与取舍）→ 结果（量化）→ 反思（如果重来）**——**"反思"是区分 senior 的关键**。

**"最有成就感"示例**：把下单链路 P99 从 2.5s 降到 200ms，大促零故障——**重点讲"我如何定位 N+1/索引/分页、如何说服产品接受游标分页、如何做压测验证"**，而不是"我们上了 Redis"。

**"最难"示例**：老系统迁移（单体→微服务/分库分表），**跨团队 + 数据一致性 + 不能停机**——讲**分阶段（绞杀者）、双写/校验/灰度、回滚预案**，以及"最难的不是技术，是让 5 个团队按同一节奏走"。

**"最后悔"示例**：早期为"未来扩展"过度设计（抽象了四层存储适配，结果只接了一种），**后来重构删掉**——反思："**用真实需求驱动抽象，Rule of Three（设计模式篇 1.1.2）**"；**别选"后悔没努力"这种假答案**。

**易错**：故事与简历矛盾；把团队成果全揽（追问细节就露馅）；"最后悔"甩锅别人/公司；没有量化结果；讲成流水账（没有决策点）。

### 4.1.2 团队冲突、推动落地、带人怎么答？

**技术冲突（最常见）**：**对事不对人 + 用数据/实验说话 + 接受"两个方案都可行时按 owner 决策"**。
> 示例："选型时我主张 Nacos、同事主张 Consul；我们列了约束（团队熟悉度/多 DC/运维成本），做了一周 PoC 压测，最后按'当前阶段团队效率优先'选 Nacos，并约定'如果多 DC 成为硬需求再评估 Consul'——**冲突变成了共同决策**。"

**推动落地（跨团队/无授权）**：**找到共同目标（不是"我的方案"）+ 小步试点 + 用结果说话 + 向上管理**。
> 示例："推动全公司接 CI 门禁，先在一个团队试点（发布事故降 50%），拿数据给平台负责人，再做成模板推广；**先证明，再推广**。"

**带人/ mentoring**：**因材施教 + 给舞台 + 反馈**（不是"帮他写代码"）；讲**具体动作**（代码评审、设计评审、周会分享、任务拆解）与**结果**（他独立负责了 X/晋升）。

**易错**：把"冲突"讲成"我赢了"（不成熟）；推动落地只说"我提了建议"（没有执行）；带人只说"我教了他"（没有方法/结果）；贬低前同事/领导。

## 4.2 反问与收口

### 4.2.1 反问环节问什么？怎么判断团队？

**四个高质量问题（按优先级）**：
1. **业务与成功标准**："这个岗位/团队今年最重要的目标是什么？我怎么衡量自己做得好？"（显示结果导向）；
2. **技术现状与挑战**："当前架构最大的痛点/技术债是什么？团队在做什么投入？"（判断是否有真事做）；
3. **工程文化**："代码评审/测试/发布/on-call 是怎么做的？"（判断成熟度，33_cicd.md）；
4. **成长与协作**："团队的分工/晋升/技术分享机制？"（判断是否值得去）。

**别先问**：薪资/加班/福利（等 offer 阶段或 HR 面再谈）；"公司做什么"（官网能查，显得没做功课）。

**红绿灯（判断团队）**：**红灯**——"我们没有测试/评审""上线靠人肉""on-call 没有 runbook""一个人维护所有系统"（英雄文化）；**绿灯**——有 CI/监控/复盘、有技术债清单、有明确的 owner、鼓励提问。

**收口**："反问不是'走流程'，是**你在评估他们**——问出'他们怎么工作'，比问'福利好不好'更能判断值不值得去。"

### 4.2.2 不会的问题、被质疑、谈薪怎么应对？

**不会的问题（三步）**：**承认边界**（"这块我没深入做过"）→ **展示推理**（"但从 X 原理推断，可能是 Y；如果是 Z 场景，我会先验证 A"）→ **给跟进**（"我回去查一下/这个问题我感兴趣"）。**禁忌**：胡编（追问即穿帮）、沉默、"这个没用过"就结束。

**被质疑（技术/方案）**：**先确认前提**（"你担心的是并发下的一致性，对吗？"）→ **给证据/边界**（"在 QPS<X、冲突率<Y 时方案成立；超过则用 Z"）→ **该认就认**（"你说得对，这个场景我没考虑到，我会改成……"）。**别防御**——面试官在测"协作与反思"，不是辩论赛。

**谈薪（offer 阶段）**：**给区间不给死数**（基于市场/当前包/岗位职责）；**总包视角**（base/奖金/股票/补贴/成长）；**不虚报 competing offer**（背调/诚信风险）；**先确认职级与职责**（钱与 level 挂钩）；**表达诚意但守底线**（"这个范围我可以接，希望再争取 X"）。

**"为什么离职"**：**讲成长/技术/业务方向**（"当前系统趋于稳定，我想做更大规模的挑战"），**不吐槽前公司/领导**；**职业空窗**：诚实 + 说明期间的学习/项目（开源/证书/复盘）。

**收口**："软技能题考的是**成熟度**——不会就承认、被质疑就验证、谈薪就专业；**技术可以学，协作与诚信是底线**。"

# 5. 项目复盘与准备

## 5.1 素材库

### 5.1.1 面试前怎么整理"项目素材库"？

**五类素材（每类 2~3 个，能随时调取）**：
1. **STAR 卡片**：性能优化、故障、迁移、选型、冲突——每张**背景 1 句/行动 3 点/结果 1 个数字/反思 1 句**；
2. **架构图**：一张"全局图"（分层/数据流/你的模块）+ 一张"核心链路图"（下单/支付）；
3. **指标表**：QPS/数据量/可用性/延迟/团队规模（**口径与来源**要能解释，1.1.2）；
4. **取舍清单**：3~5 个"为什么不用 X/为什么这么选"（1.2）；
5. **问题清单**：你准备问公司的（4.2.1）+ 你被问过答不好的（复盘补）。

**准备方法**：**写下来 → 讲出来（录音/对练）→ 删到 2 分钟 → 准备追问**；**每个数字都能追溯**（监控/压测/日志）；**简历每一条都准备一个故事**（面试官照着简历问）。

**易错**：素材太多（记不住，讲成流水账）；只准备"成功"（失败/反思更显成熟）；数字夸大（交叉验证穿帮）；不练口述（现场卡壳）。

## 5.2 收口

### 5.2.1 怎么把"我做过"讲成"我能做成"？

**三个层次（面试官按此判断级别）**：
1. **执行层**："我按需求写了 X"——** junior**；
2. **负责层**："我负责 X，解决了 Y 问题，拿到 Z 结果"——**middle**；
3. **判断层**："**在 A/B 约束下，我选择 C 而不是 D，因为 E；代价是 F，我用 G 兜底；结果是 H；如果重来我会 I**"——**senior/lead**。

**升级表达的四把钥匙**：
- **讲决策而非任务**：每个故事至少一个"我选择了…因为…"；
- **讲权衡而非完美**：主动说代价/被否决的方案（没有完美方案，只有取舍）；
- **讲影响而非代码**：业务指标/团队效率/故障下降，而不只是"用了什么技术"；
- **讲复用而非一次性**：沉淀了模板/规范/工具，让别人也能做成（5.1.1 的素材库）。

**示例对比**：
> 普通："我用 Redis 做了缓存，接口快了。"
> 高级："商品详情 QPS 高、DB 压力大；我评估了'整页缓存（一致性差）'与'字段级缓存 + 本地 Caffeine（一致性好、内存可控）'，选了后者；用 binlog 失效 + 短 TTL 兜底；P99 从 800ms 降到 120ms，DB QPS 降 60%；这套'两级缓存 + 失效'沉淀成了团队模板。"

**收口句**："面试不是'证明你做过'，是**证明你会在新环境里做成**——把'做过的事'翻译成'判断力 + 方法 + 结果'，就是 senior 的信号。"
