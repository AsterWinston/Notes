# 1. 知识点
- **关系型数据库**：基于关系模型，行列二维表结构，严格Schema，支持SQL，ACID事务，代表MySQL/PostgreSQL/Oracle/SQL Server
- **非关系型数据库**：灵活数据模型，弱Schema或Schemaless，BASE理论，分键值/KV/文档/列族/图/时序等类型，代表Redis/MongoDB/HBase/Neo4j/InfluxDB
- **关系型 vs 非关系型对比**：关系型适合复杂查询和事务强一致性场景，NoSQL适合高并发读写、海量数据、灵活Schema的互联网场景
- **CAP定理**：一致性Consistency（所有节点同一时刻数据相同）、可用性Availability（非故障节点正常响应）、分区容错性Partition Tolerance（网络分区下系统仍工作），三者只能同时满足两个
- **CAP倾向**：传统关系型数据库偏CA（单机）、NoSQL偏AP（多数）或CP（如HBase/MongoDB可配），P必须保证
- **BASE理论**：Basically Available基本可用、Soft state软状态（允许中间状态）、Eventually consistent最终一致性，是AP的延伸
- **最终一致性**：数据更新后不要求立即一致，但保证在没有新更新的情况下最终所有副本达成一致
- **数据库范式-1NF**：列的原子性，每个字段不可再分（如地址拆分为省市区），是关系模型最基本要求
- **数据库范式-2NF**：满足1NF且非主键列完全依赖于主键（消除部分依赖），联合主键时避免属性只依赖部分主键
- **数据库范式-3NF**：满足2NF且非主键列不传递依赖于主键（即非主键列不能依赖于其他非主键列）
- **BCNF范式**：3NF加强版，消除主键列对非主键列的函数依赖（候选键间的依赖），实际中较少单独追求
- **反范式化**：故意引入冗余列（如订单表冗余用户名），以空间换时间减少关联查询，提升读性能，是实际项目中常见优化
- **ER模型-实体**：客观存在且可相互区分的事物（如用户、订单），在数据中对应一张表
- **ER模型-属性**：实体的特征（如用户姓名、年龄），对应表的列
- **ER模型-关系**：实体间的联系，1:1（用户-身份证）、1:N（部门-员工、用户-订单）、M:N（学生-课程），需通过中间表实现多对多
- **SQL执行顺序**：FROM→ON→JOIN→WHERE→GROUP BY→HAVING→SELECT→DISTINCT→ORDER BY→LIMIT（理解这个顺序对写复杂查询和优化至关重要）
- **FROM子句**：确定数据源表，笛卡尔积（多表）构建初始数据集
- **ON + JOIN**：根据连接条件筛选匹配行，生成连接后结果集
- **WHERE**：对连接后的行进行条件过滤，在分组前执行，不可使用聚合函数
- **GROUP BY**：按指定列分组，分组后每组一行
- **HAVING**：对分组后的结果过滤，可使用聚合函数
- **SELECT**：选择要显示的列，计算表达式和聚合函数，去重（DISTINCT）
- **ORDER BY**：对结果集排序
- **LIMIT**：限制返回行数
- **垂直拆分**：按业务模块拆分数据库，如用户微服务→用户库、订单微服务→订单库，解耦且独立扩展
- **水平拆分-路由键选择**：选查询频繁且分布均匀的字段（用户ID、订单ID），避免跨分片join和聚合
- **基因法**：将分库分表的路由键融入到主键ID中（如高位存放分片基因），实现通过ID直接定位目标库表
- **分库信号/分表信号**：水平拆分的触发条件——单表超过500W-2000W行或磁盘占用超阈值、单库并发连接数/IO接近瓶颈
- **分布式主键-Snowflake**：64位Long，1位保留 + 41位毫秒时间戳(69年) + 10位机器ID(1024节点) + 12位序列号(每毫秒4096个)，趋势递增、高性能本地生成
- **分布式主键-号段模式**：Leaf框架从数据库批号段（每次取一段ID范围），用完再取，减少DB交互，如美团Leaf-segment
- **分布式主键-Redis生成**：利用Redis的INCR原子递增，简单但需配置持久化防丢失和单点故障
- **分布式主键-UUID**：全局唯一但无序，索引插入时页分裂严重，占用36字符空间大，不推荐作为主键
- **自增ID问题**：分库分表后多库各自自增导致ID冲突，不适于分布式场景
- **INNER JOIN**：内连接，返回两表中匹配的行（取交集）
- **LEFT JOIN**：左外连接，左表全部行 + 右表匹配行，右表无匹配填NULL
- **RIGHT JOIN**：右外连接，右表全部行 + 左表匹配行（可用LEFT JOIN等价替代）
- **FULL JOIN**：全外连接，返回两表所有行不匹配的填NULL（MySQL不直接支持，用LEFT JOIN UNION RIGHT JOIN模拟）
- **CROSS JOIN**：交叉连接，笛卡尔积，无ON条件时左表每行和右表每行组合
- **NATURAL JOIN**：自然连接，自动匹配同名字段进行等值连接，不常用（危险），建议显式JOIN
- **Nested-Loop Join**：嵌套循环连接算法，外层表每行扫描内层表匹配，小表驱动大表
- **Block Nested-Loop Join**：BNL，将驱动表数据分块读入Join Buffer减少对内层表的扫描次数
- **Hash Join**：MySQL 8.0.18引入，构建阶段对内层表建哈希表，探测阶段外层表逐行哈希查找，等值连接效率优
- **数据库视图**：虚拟表，基于查询定义，不存储数据，简化复杂查询、提供安全层控制列访问，更新受限（单表简单视图可更新）
- **视图优缺点**：优点——简化复杂查询、安全隔离、逻辑数据独立；缺点——多层视图影响性能、更新限制多、难以调试
- **存储过程**：预编译SQL集合存于数据库，减少网络传输（一次调用执行多条）提高效率，可封装业务逻辑
- **存储过程优缺点**：优点——减少网络开销、封装复用、预编译执行快；缺点——难以版本控制、调试困难、迁移成本高、将业务逻辑耦合在数据库中
- **互联网公司少用存储过程**：不符合微服务分层架构（逻辑应放在应用层）、难以横向扩展（计算压力集中在DB）、DevOps不友好（CI/CD无法管理）、数据库迁移时改造成本高
- **触发器**：在INSERT/UPDATE/DELETE前后自动执行的SQL，用于审计日志、数据校验、级联更新
- **触发器风险**：隐性逻辑难排查（不知何时执行）、级联触发可能导致复杂死锁、影响批量操作性能
- **全文索引**：InnoDB 5.6+支持，MySQL 5.7+内置ngram中文分词器，对TEXT字段建立倒排索引，替代LIKE '%xx%'性能问题
- **搜索引擎方案**：大数据量全文搜索建议用Elasticsearch/Solr，MySQL全文索引适合轻量场景
- **数据库迁移方案**：停机迁移（停服→导出→导入→验证）、双写迁移（老库新库同时写→切换读→下架老库）、增量迁移（binlog/Canal订阅增量→全量快照+增量追赶→切换读）
- **数据归档-冷热分离**：热数据（近期频繁访问）存放高性能存储，冷数据（历史数据）迁移到归档库/对象存储/廉价存储，定期分区转移
- **读写分离**：主库负责写，从库负责读，通过中间件（ProxySQL/ShardingSphere/Atlas）路由
- **读写分离延迟问题**：主从复制存在延迟导致读从库读到旧数据，解决方案：写完立即读强制走主库、业务容忍延迟（如列表页不要求实时）、MGR强一致性集群

# 2. 面试题

## 2.1 关系型数据库和非关系型数据库有什么区别？如何选择？
关系型数据库基于行列二维表和严格的Schema，支持SQL和ACID事务，适合复杂关联查询和强一致性场景（金融、订单）。非关系型数据库Schema灵活、扩展性强、分布式天然支持，适合海量数据高并发（日志、社交媒体）、Schema频繁变更、低延迟KV访问等场景。选择需考虑数据模型、一致性要求、扩展需求和团队技术栈。

## 2.2 请解释CAP定理，并举例说明各种数据库的CAP倾向
CAP定理指分布式系统无法同时满足一致性Consistency、可用性Availability、分区容错性Partition Tolerance，只能同时满足两个。P必须保证（网络分区不可避免），在CP和AP之间选择。CP系统：分区时牺牲可用性保证一致性，如HBase、MongoDB（可配majority write Concern）。AP系统：分区时允许短暂不一致保证可用性，如Cassandra、DynamoDB。CA系统：单机数据库在不分区情况下满足CA，如传统MySQL/Oracle单机。

## 2.3 数据库三范式分别是什么？为什么实际开发中会反范式化？
1NF：字段原子性不可再分；2NF：非主键列完全依赖于主键（消除部分依赖）；3NF：非主键列不传递依赖主键。反范式化是为性能故意冗余数据，如订单表冗余用户名避免每次查询订单都需要关联用户表。原因：互联网场景读远大于写，适当的冗余减少JOIN提升读性能，用空间换时间。

## 2.4 ER模型中实体间的关系有哪些？
1:1（一对一）：如用户-身份证，可在任意一侧存储关联。1:N（一对多）：如部门-员工、用户-订单，在多的一方存外键。M:N（多对多）：如学生-课程，必须创建中间关联表，分别存双方外键组成联合主键。ER图是数据库设计的重要工具。

## 2.5 SQL语句的执行顺序是什么？为什么要理解它？
执行顺序：FROM → ON → JOIN → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT。理解此顺序对于复杂查询调试至关重要：比如SELECT中定义的别名在WHERE中不可用（WHERE先于SELECT执行），HAVING可以使用聚合函数而WHERE不能。

## 2.6 分库分表的设计原则是什么？
垂直拆分按业务维度，将不同业务的数据放到不同数据库；水平拆分需选择合适的路由键（查询频繁、数据分布均匀），常见使用用户ID/订单ID哈希取模。分片键应尽量满足单次查询只落一个分片，避免跨分片JOIN和聚合。此外，使用基因法将分片信息融入主键ID，使ID可直接定位分片。

## 2.7 分布式主键的常用方案有哪些？各有什么优缺点？
- **Snowflake**：64位Long，趋势递增、本地高性能生成，缺点依赖机器时钟，时钟回拨需处理。
- **号段模式**（如美团Leaf）：从DB批量取号段，减少DB交互，可撑较高并发，依赖数据库。
- **Redis生成**：INCR原子自增，简单但需配置持久化和高可用。
- **UUID**：全局唯一简单，但无序导致索引页分裂性能差，存储空间36字符大。
- **自增ID**：单库好用，但分库分表会产生ID冲突。

实际选型Snowflake最为常用，美团的Leaf号段模式也是成熟方案。

## 2.8 JOIN有哪几种类型？各自的区别？
- INNER JOIN：取两表交集
- LEFT JOIN：左表全量 + 右表匹配（不匹配NULL）
- RIGHT JOIN：右表全量 + 左表匹配（可用LEFT等价）
- FULL JOIN：两表全量（MySQL不直接支持，需UNION模拟，Oracle/PG支持）
- CROSS JOIN：笛卡尔积不加条件
- NATURAL JOIN：自动匹配同名字段等值连接

实际中INNER JOIN和LEFT JOIN最常用。

## 2.9 MySQL中JOIN的几种算法分别是什么？
- Nested-Loop Join：外层表遍历每行去内层表匹配，最基础算法
- Block Nested-Loop Join：驱动表数据分块放入Join Buffer减少对内层表的扫描次数
- Hash Join（MySQL 8.0.18+）：内层表构建哈希表，外层表哈希探测，等值JOIN最优

优化器根据数据量和索引自动选择最优算法。

## 2.10 数据库视图的优缺点是什么？
优点：简化复杂查询（预定义复杂JOIN）、安全隔离（仅暴露视图列给用户）、逻辑数据独立性。缺点：性能开销（每次查询视图都重算底层SQL且不能传WHERE下推）、更新限制（涉及多表的视图不可更新）、复杂视图嵌套调试困难。

## 2.11 什么是存储过程？为什么互联网公司很少使用？
存储过程是预编译并存储在数据库中的SQL代码块，可带参数、逻辑控制，减少网络开销、封装复用。互联网公司少用的原因：1）业务逻辑放入DB不符合微服务分层架构；2）DB难以横向扩展，计算压力集中于DB；3）版本控制和CI/CD困难，调试不便；4）数据库迁移（如MySQL→TiDB）改造成本巨大。

## 2.12 触发器的应用场景和风险是什么？
应用：审计日志自动记录（INSERT后写日志表）、数据校验（BEFORE INSERT校验）、级联操作。风险：逻辑隐性难以排查（触发器何时触发不直观）、级联触发导致复杂死锁和性能问题、批量操作时逐行触发影响性能。生产环境建议在应用层实现类似逻辑。

## 2.13 读写分离架构下主从延迟如何解决？
1）写完立即读或关键业务场景强制走主库（Hint路由）；2）使用半同步复制或MGR减少延迟；3）开启并行复制提升从库回放速度；4）业务上容忍一定延迟（列表查询、统计等非实时场景）；5）中间件支持延迟阈值配置自动摘除延迟过大的从库。

## 2.14 数据库迁移有哪些方案？
- 停机迁移：停服→全量导出→导入→验证→切换，最简单但有停机窗口
- 双写迁移：新老库同时写入→切换读流量到新库→观察→下架老库，适合不能长时间停机的场景
- 增量迁移：全量快照 + binlog/Canal订阅增量数据追赶→数据追平后切换读→最终切换写，停机时间最短

增量迁移是目前主流方案，常配合Canal监听binlog实现。

## 2.15 数据库冷热分离（数据归档）如何实现？
1）按时间分区表（MySQL Partition），定期将历史分区转移到归档库或冷存储。2）定时任务迁移：每日/每周将超过阈值时间（如6个月）的数据INSERT到归档表后从热表DELETE。3）读写分离下，归档库用低配机器+大容量磁盘降低成本。4）应用层感知（查询路由）或对应用透明（中间件路由）。

## 2.16 SQL中WHERE和HAVING有什么区别？
WHERE在GROUP BY分组前对原始行进行过滤，不能使用聚合函数；HAVING在GROUP BY分组后对分组结果过滤，可以使用聚合函数（SUM/COUNT/AVG等）。执行顺序上WHERE先于GROUP BY，HAVING后于GROUP BY。例如：WHERE age>18 GROUP BY city HAVING COUNT(*)>10。
