# 1. 定位与数据模型

## 1.1 是什么、和关系库怎么对应

### 1.1.1 Elasticsearch 是什么？和 MySQL 的本质差异在哪？它不擅长什么？

**定位一句话**：基于 Lucene 的**分布式搜索与分析引擎**——强项是**全文检索（相关性排序）与大规模聚合分析**，近实时（NRT）、天生分片与副本；**不是**关系型数据库的替代品（无事务、无 JOIN、无严格的即时一致性）。

**与 MySQL 的对照（先讲清"能对应什么"，再讲"对应不了什么"）**：

| Elasticsearch | MySQL | 说明 |
|---------------|-------|------|
| Index（索引） | 表（早期文档比作 Database，7.x 后语义已收敛） | 一个索引=一类文档集合 + 一份 Mapping |
| Document（文档） | Row（行） | JSON，带 `_id` 与 `_source` |
| Field（字段） | Column（列） | Mapping 定义类型与分词 |
| Mapping | Schema（但更严格：**字段类型基本不可改**） | 改类型要重建索引（5.1.2） |
| DSL（Query DSL） | SQL | 声明式 JSON；聚合≈GROUP BY 的强化版 |
| `_bulk` | 批量 DML | 单条失败不影响其余（要逐条查结果） |

**四条本质差异（决定"该不该用"）**：
1. **近实时而非实时**：写入默认 1s 后才可被搜索（refresh，2.1.2），**没有"读己之写"的强一致**——刚写入立刻查可能查不到；MySQL 的读己之写靠同库事务，语义完全不同；
2. **无事务、无跨文档原子性**：单文档操作原子（一条文档要么整体写入成功），跨文档/跨索引**没有 ACID**（`_bulk` 不是事务，部分成功是常态）——资金/库存类"必须原子"的写必须留在 MySQL（16_mysql.md 3.1.1）；
3. **无 JOIN（或极弱）**：靠**建模扁平化**（宽表/嵌套/冗余字段）代替关联（3.1.3）——"照着范式设计 ES 表"是新手第一大错；
4. **不可变存储**：文档更新=**标记删除+写新文档**（2.1.3），高频 update 的写放大远高于 MySQL 的原地更新——"把 ES 当主库做高频状态流转"是选型事故。

**不擅长清单**（面试问"什么时候不该用"照此答）：强事务/强一致（账户、库存）、复杂关联查询（报表 JOIN）、高频更新（状态机流转）、精确计数（聚合是近似的，3.2.1）、小数据量（几万行 MySQL 加索引就够，运维 ES 是负债）、主存储（ES 应视为**可重建的检索副本**，真相在 DB——5.1.1）。

**收口**："ES 的正确位置是**读写分离后的'读'侧专精**：MySQL 存真相、ES 存'为查询优化过的投影'，靠 binlog/消息最终一致地同步——把这句话答出来，后面所有设计题都有了锚。"

### 1.1.2 Type 为什么被移除？Index、Document、Field、Mapping 的现代语义是什么？

**Type 的历史与现状**（版本题必须答对，旧文"多 Type"已经是历史）：Lucene 层面**一个索引就是一堆倒排表，本来没有"表"的概念**——6.x 之前用 Type 在同一个索引里模拟多表（`/index/type/id`），代价是**同一索引内同名不同类型的字段共用一套 Mapping**（`user` 在不同 type 里类型冲突就炸），且**每个 Type 都产生独立的 segment 字段开销**（稀疏性问题）。演进线：6.x 多 Type 标废弃 → 7.x 默认 `_doc`、多 Type 不可新建 → **8.x 彻底移除 Type**（URL 不再含 type；`include_type_name` 移除）。**取向**：**一类文档一个索引**（或用 `_doc` 单一类型），跨类型关联靠宽表/嵌套（3.1.3）。

**现代语义（8.x/9.x 口径）**：
- **Index**：文档集合 + 分片/副本配置 + Mapping + Settings 的载体；"表"的最近似物，但**分片数创建即定**（4.1.2）；
- **Document**：JSON 文档，`_id` 可自定（业务主键）或自动生成；`_source` 保存原始 JSON（1.2.2）；
- **Field**：Mapping 定义类型（`text`/`keyword`/数值/日期/布尔/geo/`nested`/`dense_vector` 等）与是否索引、是否 doc_values；
- **Mapping**：**动态推导（dynamic mapping）默认开启**——新字段按值猜测类型（字符串→text+keyword 双字段、数字/日期自动识别），这也是"字段爆炸"与"类型冲突"的来源（3.1.1）；
- **别名（alias）**：索引的别名指针，**重建索引切换的枢纽**（5.1.2），也用于按月切索引的统一查询入口。

**两处 2026 时效点**：**8.x 起安全默认开启**（TLS + 密码/证书，`elastic` 用户 + enrollment token，别再照搬"裸 HTTP 9200"的教程）；**9.x（2025 年发布，基于 Lucene 10）为当前主线**，8.x 仍在维护——版本题答"Type 已在 8.x 移除、安全默认开启、9.x 是 Lucene 10 代"即到位，具体 minor 以官方 release notes 为准。

**易错**：把 "Index" 说成数据库、"Type" 说成表（7.x 前的旧映射，8.x 已无 Type）；认为 Mapping 能像 MySQL `ALTER TABLE MODIFY` 随便改类型——**已有字段只能有限修改**（如新增 multi-field、改分词器要重建），改类型=建新索引 + reindex + 别名切换（5.1.2）。

## 1.2 存储结构

### 1.2.1 倒排索引怎么工作？Term Index、Term Dictionary、Posting List、FST 各是什么？

**正排 vs 倒排一句话**：正排是"文档 → 词"，倒排是"**词 → 文档列表**"——搜索先对查询分词，再去倒排表里按词取交集/并集，**不必扫全量文档**。

**三层结构（从大到小）**：

```text
① Term Index（词典索引）：FST 结构，常驻堆外/page cache
   作用是"前缀跳表"：只存词条前缀路径，快速定位到 Term Dictionary 的 block 偏移
   ——省内存的关键：不需要把全部词条装进内存，只需装前缀索引
② Term Dictionary（词典）：所有词条按字典序排的"大字典"，分 block 存磁盘
   按 Term Index 定位到 block 后，块内二分/扫描找到目标 Term
③ Posting List（倒排列表）：该词条出现在哪些文档（docId）、词频（TF）、位置（phrase 用）
   docId 有序 → 用跳表（skip list）/位图压缩加速多词交集（AND 即多列表求交）
```

**为什么用 FST 而不是 HashMap/红黑树**：词条是**海量且共享前缀**的字符串（英文词根、中文词典、URL）——FST（有限状态转换器）把"字典"压成有向无环图，**前缀共享 + 后缀共享**，内存占用比哈希小一个量级，且支持前缀/范围遍历（`prefix` 查询、词典遍历）。代价是实现复杂、只读构建（写入新词条=新 segment，2.1.3 的不可变性又对上了）。

**查询侧的完整链路**：查询分词 → 每个 Term 走 ①→②→③ → 多列表求交/并（跳表跳跃）→ 得到候选 docId → 取 **BM25 相关性评分**（TF-IDF 的现代替代，默认评分算法）→ 排序/聚合 → 取 `_source` 返回（2.2.1 的两阶段）。

**易错**：① 说"倒排索引存在内存"——**倒排表在磁盘 segment 里**，靠 page cache 加速；常驻的是 Term Index 一类的小结构（4.2.2 的内存账）；② 把"分词"和"倒排"混为一谈——分词（Analyzer）决定"词条长什么样"，倒排决定"词条怎么查文档"，**同一个字段用不同分词器，建出来的倒排完全不同**（3.1.2）；③ `text` 字段默认不分词大小写/标点——`keyword` 才是"整串精确值"（2.2.3 的 term 查询必须打在 keyword 上）。

### 1.2.2 Doc Values 和 `_source` 有什么区别？为什么排序聚合不用倒排索引？

**一句话分工**：**倒排索引服务"找文档"（where/打分），Doc Values 服务"取字段值算"（sort/agg），`_source` 服务"把原文档还给你"（fetch 返回）**。

| | Doc Values | `_source` |
|--|-----------|-----------|
| 布局 | **列式**（field → docId 顺序的值数组），磁盘存储、page cache 加速 | **行式**（整条原始 JSON，按文档压缩存） |
| 建立时机 | 写入 segment 时生成（可 `doc_values: false` 关闭） | 默认保存整个 JSON（可关闭，或 8.x 起的 synthetic source） |
| 用途 | **排序、聚合、脚本取值** | GET 返回、reindex 重建、update 内部读取 |
| 能否关闭 | 能（关掉则该字段不能排序/聚合） | 能（但 reindex/局部更新会受限，慎关） |
| 文本字段 | `text` 默认**没有** Doc Values（分词后的值无法按"列"排序）——要排序/聚合用 `keyword` | 有 |

**为什么排序聚合不能走倒排**：倒排是"**词 → 文档集合**"——问"按价格排序"需要的是"**文档 → 价格**"，从倒排反查等于对每个词条做一次全文档归并，代价灾难；列式 Doc Values 让"取第 N 个文档的字段值"变成**顺序读**（同类值连续存放，压缩友好、缓存友好），聚合就是列上的一次扫描。**这就是"倒排+列存"双结构并存的根本原因**——一个负责"找得到"，一个负责"算得快"。

**易错三条**：① 对 `text` 字段做聚合/排序 → 报 `Fielddata is disabled`，**别开 fielddata**（把倒排加载进堆，4.2.2 的 OOM 头号来源），改 Mapping 加 `keyword` 子字段（`fields: {keyword: {type: keyword}}`）；② 以为 `_source` 是"缓存"——它是**存储**（磁盘），关掉后 GET 拿不到原始文档、update 只能靠脚本；③ 8.11+ 的 **synthetic `_source`**（从 Doc Values 重建原文档，省存储）是"列存反向服务行读"的现代解法，报得出即时效加分（重建有损，字段类型限制以文档为准）。

# 2. 写入与读取

## 2.1 写入链路

### 2.1.1 一条文档写入的完整流程？Refresh、Flush、Translog 三者的关系？

**全链路（写一条文档）**：

```text
① 客户端 → 任意节点（成为本次请求的协调节点）
② 路由：shard = hash(routing) % 主分片数（routing 默认 _id）
   → 定位主分片，转发到主分片所在节点
③ 主分片：写入 Lucene 的 in-memory buffer + 追加 translog（WAL），
   同时把请求并行转发给所有 in-sync 副本分片
④ 主分片等待全部副本确认（默认 wait_for_active_shards=1，但副本在同步列表里就必须全回）
⑤ 协调节点收到成功 → 返回客户端（此时"已持久"取决于 translog durability：
   默认 request = 每次请求 fsync translog；async = 每 5s 批量 fsync）
⑥ 后台 refresh（默认 1s）：buffer 里的文档生成新 segment 落到文件系统缓存
   → 此刻起**可被搜索**（但还在 OS cache，未 fsync）
⑦ 后台 flush（translog 超 512MB 或检查周期到）：segment fsync 到磁盘，
   translog 提交并滚动新文件——这才完成"落盘级持久化"
```

**三个概念的准确分工（最高频的混淆点）**：

| 动作 | 干什么 | 触发 | 解决什么 |
|------|--------|------|---------|
| **refresh** | buffer → 新 segment（OS cache），打开搜索器 | 默认每 1s / `refresh=wait_for` | **可见性**（近实时） |
| **translog 写** | 记录每次操作（WAL），可重放 | 每次写（durability=request 时同步 fsync） | **进程崩溃不丢**（未 refresh 的也能恢复） |
| **flush** | segment fsync 落盘 + translog 提交滚动 | translog 达 `flush_threshold_size`（512MB）等 | **回收 translog、减少恢复重放量** |

**三个追问口径**：① "写成功=落盘了吗"——**默认 request 模式下 translog 已 fsync（主+副本），进程崩溃不丢**；但"可搜索"要等 refresh、"segment 落盘"要等 flush——三者是三个不同承诺；② "为什么写副本是并行且必须等全部"——副本在 in-sync 列表里就代表"承诺的冗余"，等它们确认才回客户端，**所以副本数影响写延迟**（4.2.1 的`副本=0 提速`账）；③ "更新怎么走"——`update` 在内部是"GET 原文档 + 改 + 重新索引整条"（2.1.3 的不可变推论），高频 update 的写放大要算进容量。

**易错**：把 flush 说成"把 buffer 刷盘"（那是 refresh+flush 的组合效果，flush 的主体是 **translog 提交与 segment fsync**）；以为 `refresh=wait_for` 是"立即落盘"（只是等下一次 refresh 完成，与持久化无关）；忘记 **translog durability=async 的 5 秒窗口**会丢"已 ack 未 fsync"的写（可靠性要求高的索引保持 request）。

### 2.1.2 为什么 ES 是"近实时"？refresh_interval 和写入吞吐怎么权衡？

**近实时的机制根源**：写入先进 buffer（不可搜索），refresh 才生成**新的只读 segment**并打开新的搜索视图（searcher）——**默认 1 秒的窗口就是"写后不可见"的时长**。这不是缺陷而是**吞吐换可见性的设计**：每次 refresh 都要建 segment、打开 searcher、触发 merge 压力，做得越勤，写吞吐越低、小 segment 越多（2.1.3）。

**三个参数档位（答题给"场景→档位"）**：

| 场景 | refresh_interval | 说明 |
|------|------------------|------|
| 默认搜索服务 | `1s` | 近实时够用；ES 7+ 还有 **search idle 优化**（`index.search.idle.after` 默认 30s：长时间无查询的分片跳过 refresh，直到下次搜索）——低峰自动省资源 |
| 日志/指标类（可容忍延迟） | `30s`~`60s` | 写入吞吐显著提升，可见性换分钟级 |
| 批量导入/重建索引 | 临时 `-1`（关闭） | 导入完恢复 `1s` 再**手动 refresh** 一次；配合副本=0 是标准"导数据模式"（4.2.1） |

**要不要"写后立刻查得到"**：需要时三选——① 写请求带 `refresh=wait_for`（**阻塞到下一次 refresh 完成**，延迟≈1s，别在高频写路径用）；② `refresh=true`（强制立刻 refresh，**只用于低频单条**，批量用等于自杀）；③ **按 `_id` GET 走实时的 translog 读**（realtime GET 不受 refresh 影响）——"写完按主键回查"场景的正确解法。

**易错**：把"近实时"说成"最终一致所以可能丢"——**不丢**（translog 保证崩溃恢复），只是**不可见**；把 `refresh_interval=-1` 用在生产常规索引上——写入永远不可搜（直到手动 refresh），是"数据写进去了为什么搜不到"的经典事故；调大 refresh 后忘了**同步调大搜索侧的等待逻辑**（前端"提交后跳列表页看不到新数据"的客诉会变多）。

### 2.1.3 Segment 不可变意味着什么？合并（Merge）与 Force Merge 为什么不能乱用？

**不可变性是 Lucene 的性能基座**：segment 一经生成**永不修改**——没有原地更新、没有锁、可以放心用 mmap/page cache、可以并发搜索而无需同步；换来的是**删除与更新的特殊语义**：

```text
删除：不在 segment 里抹数据，只在 .liv 位图里标记"该 docId 已删"
更新：= 旧文档标记删除 + 新文档写入新 segment（整条重写）
合并：后台 merge 策略（TieredMergePolicy）把若干小 segment 合成大 segment，
      合并时**真正丢弃被标记删除的文档**、重建倒排与 Doc Values
```

**由此推出三个工程结论**：
1. **更新/删除是"逻辑删 + 重写"**：高频 update 的索引会积累大量"墓碑"，**磁盘与 merge 压力双涨**——状态频繁变化的实体不适合 ES（1.1.1 的不擅长清单），且 `_id` 复用会引入版本冲突语义（`_seq_no/_primary_term` 乐观并发）；
2. **小 segment 越多，查询越慢**：每个查询要在**每个 segment** 上各查一遍再归并——refresh 频繁 + 写入碎 → 查询延迟碎片化；merge 是自愈机制，但 merge 本身吃 IO/CPU（"写入高峰后磁盘 IO 飙高"常是 merge 在追债）；
3. **delete_by_query 很贵**：逐条"标记删除"，大数据量删除的正确姿势是**按索引/按时间删**（ILM 直接删整个索引，4.2.3）——"删 1 亿条日志用 delete_by_query"是容量事故。

**Force Merge 的纪律**：`POST index/_forcemerge?max_num_segments=1` 把 segment 合并到 1 个——**只对"只读索引"在低峰执行**（历史日志、归档索引）；对**活跃写入索引**执行会：① 反复被后续写入作废（白干）；② 巨量 IO 打满磁盘；③ 大 segment 后续 merge 更贵。官方口径："force merge 只在索引不再写入时做"——报得出这条即及格；再补一句"**能靠 ILM 滚动+归档就不手动 force merge**"即满分。

**易错**：把 "flush" 与 "merge" 混谈（flush 是持久化，merge 是优化布局）；认为 force merge 能"压缩存储"——它回收的是**已删除文档与碎片**，不是压缩算法（压缩靠 codec 与 mapping 设计）；在集群高负载时跑 force merge 触发 merge throttling，把正常写入拖慢（merge 限流参数可调，但调它是"止疼药"）。

## 2.2 读取与检索

### 2.2.1 一次搜索请求在集群里怎么走？为什么分片数直接决定查询开销？

**两阶段（query then fetch）**：

```text
Query 阶段（散射）：
  协调节点把查询发给**每个分片的一份拷贝**（主或副本，轮询分摊）
  每个分片本地执行：倒排查找 → 打分/排序 → 取 **from+size 条**候选（docId + sort 值 + score）
  各分片返回"局部 TopK"给协调节点

Fetch 阶段（聚集）：
  协调节点归并各片 TopK → 全局 TopK → 只对最终命中的文档
  按 shard 分组发 multi-get 取 `_source` → 拼装返回客户端
```

**为什么分片数=查询成本**：查询**必须打满所有分片**（没有 routing 时无法预先排除）——总成本 ≈ `分片数 × 每片候选数(from+size)`：分片越多，协调节点归并的堆越大、网络往返越多、尾部延迟越差（一个慢分片拖全场）。这就是"**不要过度分片**"的查询侧论证（4.1.2 的容量侧论证互补）。**优化杠杆**：① 能用 routing 就把查询收敛到单片（按用户/租户查询，22_sharding_sphere.md 的分片键思想在 ES 的对应物）；② `track_total_hits: false`（不需要精确总数时省一次全量计数）；③ 只取需要的字段（`_source` 过滤/`stored_fields`）减少 fetch 阶段；④ filter 缓存与 index sorting（2.2.3）。

**两个进阶追问**：**"打分为什么可能不准"**——各分片本地算 IDF（词条在全库的稀有度）时只有本片统计，分片间文档分布不均会漂移评分，`search_type=dfs_query_then_fetch` 先做一次全局词频收集再打分（多一轮往返，精度换延迟，一般不用）；**"读请求打主还是副本"**——默认两者都参与（负载分摊），`preference` 可指定（`_local`/`_primary`/自定义字符串保证同类查询打到同一副本以利用缓存）。

### 2.2.2 深度分页怎么解？from/size、scroll、search_after、PIT 怎么选？

**问题本质**：`from=10000&size=10` 时**每个分片都要返回 10010 条候选**（局部 TopK 无法提前剪枝），协调节点内存排序 10010×分片数 条——翻得越深越指数级（相对 page size），且 `max_result_window` 默认 **10000** 会直接报错。

**四种方案对照**：

| 方案 | 机制 | 一致性视图 | 适用 | 代价 |
|------|------|-----------|------|------|
| `from+size` | 每片取 from+size 归并 | 每次请求独立（可能有并发变更） | 浅分页（前几页） | 深了必炸 |
| **scroll** | 生成**快照游标**，逐批拉取 | 固定快照 | **数据导出/全量遍历**（离线） | 上下文占资源（要 `clear_scroll`/超时）；官方已不推荐用于用户分页 |
| **search_after** | 带上一页最后一条的**排序值**作为起点（`> last_sort`） | 无状态，两次请求间数据可能变 | **实时无限滚动/深分页** | 不能跳页；**排序必须唯一**（加 `_id`/`_shard_doc` 兜底，否则重复/漏条） |
| **PIT + search_after** | 先开 point-in-time（保留搜索视图），后续在 PIT 内翻页 | **固定视图 + 无状态翻页** | 深分页 + 结果稳定性要求 | PIT 有存活期（`keep_alive`）与资源占用，要主动关闭 |

**工程口径（按场景直接给答案）**：C 端列表/无限滚动 → **PIT + search_after**（排序加唯一 tiebreaker）；后台导出/对账 → **scroll**（或 PIT 遍历），控制并发与超时；前端"跳页"需求 → 限制深度（如最多 100 页）+ `search_after` 的"上一页/下一页"式交互，**别硬扛 from=100000**；只需要总数 → 单独 `_count` 或聚合（近似），不要把总数算进分页请求。

**易错**：scroll 用完不清理（上下文堆积吃堆，监控看 open_contexts）；search_after 排序字段有重复值（同一时间戳多条 → 翻页重复/丢失）；改了排序还沿用旧 search_after 值（语义完全不同）；PIT 与索引滚动（rollover）混用——PIT 固定在旧索引视图，切换后新数据不可见（4.2.3 的滚动索引要配合）。

### 2.2.3 match、term、bool、filter 的区别？为什么 filter 更快？

**查询类型速查**：

| 类型 | 是否分词 | 打分 | 典型用途 |
|------|---------|------|---------|
| `match` | **是**（对查询文本用字段的分词器） | 是（BM25） | 全文搜索（标题/描述） |
| `term` | **否**（精确词条） | 是（可 constant_score 关掉） | 枚举/状态/`keyword` 精确值 |
| `terms` | 否 | 是 | IN 列表 |
| `match_phrase` | 是 | 是 | 短语（依赖位置信息，`slop` 容忍间隔） |
| `range` | 否 | 是 | 数值/日期区间 |
| `bool` | — | 组合 | `must`（参与打分）/`filter`（不打分）/`should`（可配 minimum_should_match）/`must_not` |
| `exists`/`prefix`/`wildcard` | 否 | 视情况 | 存在性/前缀（**前导通配符极慢**） |

**为什么 filter 快（三个层面）**：
1. **不算分**：跳过 BM25 的词频/文档频率统计与评分计算——评分是 CPU 大头之一；
2. **可缓存**：filter 结果进入 **filter cache**（按 segment 缓存"哪些 docId 命中"），重复查询直接命中文档位图，**连倒排都不用再走**；
3. **可提前剪枝**：过滤在打分前把候选集缩小，后续评分/排序只在小集合上做。

**正确写法（把结构化条件全塞 filter）**：

```json
{
  "query": {
    "bool": {
      "must":   [ { "match": { "title": "分布式事务" } } ],   // 只有它参与相关性
      "filter": [ { "term": { "status": "ON_SALE" } },
                  { "range": { "price": { "gte": 100, "lte": 500 } } } ],
      "must_not": [ { "term": { "deleted": true } } ]
    }
  }
}
```

**三个高频坑**：① **`term` 打在 `text` 字段上**——写的是"北京"、倒排里是分过词的"北京/京"，term 精确匹配常常查不到（要打 `.keyword` 子字段，1.2.2）；② `match` 默认是**词间 OR**（`"分布式 事务"` 命中"分布式"或"事务"），要 AND 用 `operator: and` 或 `minimum_should_match`；③ 用户输入直接进 `query_string`（支持 Lucene 语法）——语法报错与注入式查询风险，**用户搜索框一律用 `match`/`multi_match`**。

# 3. 建模与查询能力

## 3.1 Mapping 与分词

### 3.1.1 Mapping 设计有哪些原则？动态映射与"字段爆炸"怎么防？

**Mapping 的地位**：字段类型、分词器、是否索引、是否 Doc Values 全在这里定，而**类型一旦写入数据就基本不能改**——所以"建模错=重建索引"（5.1.2 的代价），设计要在第一次导入前过审。

**六条设计原则（按踩坑频率排）**：
1. **`text` 与 `keyword` 分清楚**：要分词检索用 `text`（标题/正文），要精确匹配/排序/聚合用 `keyword`（状态/编码/用户名）；最常见做法是**一个字段双类型**（`text` + `fields.keyword`），一份数据两种用法：
   ```json
   "title": { "type": "text", "analyzer": "ik_max_word",
              "fields": { "keyword": { "type": "keyword", "ignore_above": 256 } } }
   ```
2. **不搜索的字段 `index: false`**（省倒排），不排序/聚合的字段 `doc_values: false`（省列存），只存不取的关 `_source` 要谨慎（1.2.2）；
3. **数值别用"字符串模拟"**：价格用 `scaled_float`（缩放整数）避免浮点误差，时间用 `date` 带明确 `format`，IP 用 `ip` 类型（支持 CIDR 查询）；
4. **控制字段基数**：`ignore_above` 防超长字符串进 keyword；**多值字段天然支持**（数组不需要特殊类型），但对象数组要小心（3.1.3 的 object 扁平化陷阱）；
5. **动态映射要收口**：生产索引建议 `dynamic: strict`（未知字段直接拒写）或 `dynamic: false`（收下但不索引），配合 `dynamic_templates` 统一规则（如所有 `*_at` → date、所有 `*_id` → keyword）；
6. **预留演进空间**：新增字段走 multi-field/新字段没问题，**改类型/改分词器=重建**——重要索引从第一天就配别名（5.1.2）。

**"字段爆炸"是什么、为什么致命**：动态映射下，**每个新字段都会进入集群状态（cluster state）的 mapping**——若业务拿"动态 key"当字段（`metric_user_123`、`tag_环境_地域`、日志里把整段 JSON 拍平），字段数从几十涨到几万：① **master 每次更新 cluster state 都要广播全集群**，元数据膨胀拖慢一切（4.1.1）；② 每个字段的倒排/Doc Values 开销叠加；③ 触发 `index.mapping.total_fields.limit`（默认 **1000**）后**写入直接失败**。防线：`flattened` 类型（把任意 KV 塞进一个字段，牺牲类型精度换结构稳定）、`dynamic: strict`、按实体拆索引、日志侧用 ECS 固定字段集。

**易错**：给 `text` 字段排序/聚合（fielddata 报错，4.2.2）；以为 `dynamic: false` 能"自动忽略坏字段"——它**收下并放进 `_source` 但不索引**，查询不到（"数据在但搜不到"的谜案）；改完 mapping 只在测试环境验证就上线——**存量数据不会因 mapping 变更而重新索引**（新字段对旧文档为空，要 reindex 补）。

### 3.1.2 中文分词怎么落地？IK 的两种模式怎么选？

**Analyzer 三段式（先在概念上站住）**：**Character Filter**（字符预处理：HTML 去标签、全角转半角）→ **Tokenizer**（切成词条）→ **Token Filter**（小写化、同义词、停用词、词干化）。中文的难点全在 Tokenizer：**标准分词器对中文按"单字"切**（Unicode 文本分段对 CJK 逐字）——"南京市长江大桥"被切成"南/京/市/长/江/大/桥"，搜"长江大桥"会命中一堆噪声，**所以中文必须换分词器**。

**IK 的两种模式（必考对照）**：

| 模式 | 切法 | 例 | 取舍 |
|------|------|----|------|
| `ik_smart` | **粗粒度**（最简切分，少歧义） | 南京市 / 长江大桥 | 词条少、索引小、查询快；召回略低 |
| `ik_max_word` | **细粒度**（穷尽所有成词组合） | 南京市 / 南京 / 京市 / 市长 / 长江大桥 / 长江 / 大桥 | 召回高；索引膨胀、噪声词多、打分可能被短词稀释 |

**工程标配（索引与查询用不同分词器）**：`index_analyzer=ik_max_word`（建索引时词条全，保证召回）+ `search_analyzer=ik_smart`（查询时收敛，减少误召回）——ES 允许 `analyzer` 与 `search_analyzer` 分开配，这是"中文搜索效果调优"的第一板斧。**自定义词典**：业务专有名词（品牌名、型号、地名）进 `main.dic`/远程词典（HTTP 定时拉取，集群统一更新）；**停用词**（的/了/是）与**同义词**（"手机/移动电话"）用 token filter 处理——同义词在**索引期**还是**查询期**展开，决定重建成本（查询期灵活、索引期性能好，是经典权衡）。

**其他选项一句话**：拼音插件（pinyin token filter，支持"zhongguo"搜"中国"、首字母缩写）；`smartcn`（Lucene 系 CJK 二元切分，无词典、开箱即用但效果一般）；Jieba 系社区插件（词典生态好，但非官方、版本兼容要自测）。**验证工具**：`_analyze` API 直接看"这句话会被切成什么"——调分词先跑它，别靠猜。

**易错**：同一个字段索引 `ik_max_word`、查询却用 `standard`（切法不一致→查不到，**分词器不匹配是"明明有数据搜不到"的常见根因**）；IK 词典热更新后**存量索引不会重建**（新词只对新写入生效，历史数据要 reindex）；把 `ik_max_word` 同时用于查询（短词噪声导致"搜'南京'命中'市长'相关文档"的评分混乱）。

### 3.1.3 对象数组、Nested、Join、宽表怎么选？ES 建模的第一原则是什么？

**第一原则：按"查询"建模，不按"范式"建模**——ES 的文档是**自包含的检索单元**，设计顺序是"列出所有查询/排序/聚合 → 决定文档边界与冗余字段 → 最后才谈关联"。照 MySQL 三范式拆成多索引再 JOIN，是 ES 性能与复杂度的双重灾难。

**四种关联手段的取舍**：

| 手段 | 机制 | 适用 | 代价 |
|------|------|------|------|
| **宽表/冗余（默认答案）** | 关联字段直接拍进同一文档（下单时把商品名/类目冗余进订单） | 90% 场景；读多写少、关联端稳定 | 写放大与更新扩散（商品改名要刷历史订单——多数业务可接受"快照语义"） |
| **object（对象/对象数组）** | JSON 嵌套对象，**扁平化索引**（`user.name`、`user.age`） | 一对一对象；对象数组**且不需要跨字段关联** | **对象数组的字段关联丢失**：`[{a:1,b:2},{a:3,b:4}]` 查 `a=1 AND b=4` 会误命中（索引把它们拍平成 a:[1,3]、b:[2,4]） |
| **nested** | 数组元素**各自独立成隐藏文档**，用 `nested` 查询 + `inner_hits` | 对象数组**必须保持元素内字段关联**（订单行：SKU 与数量、价格必须同属一行） | 每个 nested 文档都是独立 Lucene 文档：查询走 `nested` 特殊路径、**更新要重写整个根文档**、`nested` 字段/对象数有上限（默认 50/10000） |
| **join（父子文档）** | 同索引内 `join` 字段声明父子，`has_child`/`has_parent` | 父子**一对多且更新模式合适**（父更新不牵动子重索引） | 一个索引只能一个 join 字段、父子必须同分片（routing 绑父 id）、查询代价高——官方明确"少用" |

**决策句**："**能冗余就冗余（宽表），必须保关联才 nested，跨实体强关联请回 MySQL 查完再喂 ES**"——join 类型是最后手段，不是"ES 版外键"。

**另外两个建模点**：**时序数据按时间切索引**（`logs-2026.11`/data stream，4.2.3）——归档与删除都以"整索引"为单位，避免 delete_by_query（2.1.3）；**Runtime fields**（查询期计算字段，7.11+）适合"偶发分析维度"，避免为一次性需求改 mapping 重建索引。

**易错**：用 object 存订单行还期望"SKU=A 且数量=2"精确匹配（nested 存在的原因）；nested 字段更新时以为"只更新一行"——实际是整条根文档重写（高频更新场景要重新评估建模）；父子文档想跨索引建（join 只能同索引同分片）。

## 3.2 聚合

### 3.2.1 聚合分几类？terms 聚合为什么"不精确"？cardinality 为什么是近似值？

**三类聚合**（答题按"桶/度量/管道"报，比背函数名专业）：
- **Bucket（桶）**：把文档分组——`terms`（按字段值分组，≈GROUP BY）、`date_histogram`（按时间间隔分桶）、`range`/`histogram`、`composite`（**可分页的桶遍历**）、`filters`、`nested`/`reverse_nested`（配合嵌套建模）；
- **Metric（度量）**：桶内算数——`sum/avg/min/max/stats`、`percentiles`（分位数，**也是近似**，TDigest）、`cardinality`（去重计数）、`top_hits`（桶内取样例文档）；
- **Pipeline（管道）**：在其它聚合结果上再算——`derivative`（环比/导数）、`moving_avg`、`bucket_script`（自定义公式）、`bucket_sort`（桶内排序/截断）。

**terms 聚合不精确的机制（本题核心）**：聚合是**分片本地先算、协调节点合并**——每个分片只知道"本片内出现最多的前 N 个词条"（`shard_size`，默认 ≈ `size × 1.5 + 10`），**全局稀有词条可能在某个分片排不进局部 TopN 而漏掉**，导致：① 某些桶的 `doc_count` 偏小（少算）；② 排名可能与全量精确结果不同；响应里的 `doc_count_error_upper_bound` 就是"上界误差估计"。**对策**：调大 `shard_size`（精度↑、内存↑）；用 **`composite` 聚合分页遍历**（每页用 `after_key` 续，语义精确且可扩展）；确实要精确就用 **`_count`/`filters` 定向查**或离线预聚合（transforms/数仓，5.2.2）。

**cardinality 近似的原因**：去重计数用 **HyperLogLog++**（概率草图）——固定内存估算基数，误差率由 `precision_threshold` 控制（值越大越准、内存越多；默认 3000，最高约 40000）。**取舍**：UV/独立用户数这类指标"误差 1%~5% 可接受、要省内存"→ 直接用；**要精确计数**（财务口径）→ 回 DB/数仓算。

**两个高频追问**：① "**聚合为什么比查询更吃资源**"——聚合要扫**所有命中文档的字段值**（Doc Values 全列扫描）+ 每分片构建桶 + 协调节点合并桶，`search.max_buckets`（默认 65536）就是防桶爆炸的护栏；② "**大基数 terms 聚合很慢怎么办**"——先加 `filter` 缩小范围（filter 后聚合）、用 `composite` 分批、对 `keyword` 字段做 `eager_global_ordinals`（索引期预建全局序数）、或把聚合下沉到预计算（transform/rollup）。

**易错**：对 `text` 字段聚合（fielddata 报错或 OOM，4.2.2）；拿 terms 聚合的 `doc_count` 当精确值做对账；`date_histogram` 忘配时区（默认 UTC，报表差 8 小时——`time_zone` 参数）；嵌套聚合忘记 `nested`/`reverse_nested` 导致子文档重复计数。

# 4. 集群与运维

## 4.1 集群架构

### 4.1.1 节点角色怎么划分？为什么 Master 要奇数个？脑裂怎么防？

**角色家族（7.9+ 的 `node.roles` 体系）**：

| 角色 | 职责 | 生产建议 |
|------|------|---------|
| **master**（master-eligible） | 集群状态管理：索引创建/删除、Mapping/Settings 变更、分片分配与迁移；**不存数据、不跑查询** | 专用 3 台（小集群可与 data 混部但要有 3 个 eligible） |
| **data** | 存分片、执行 CRUD/搜索/聚合 | 主力机型；7.10+ 再分 hot/warm/cold/frozen 数据层（4.2.3） |
| **ingest** | 写入前管道（grok/转换/enrich） | 写入链路重时独立，避免抢 data 的 CPU |
| **coordinating（无角色）** | 只做请求分发与结果归并（2.2.1 的协调节点专职化） | 大集群/高并发查询时加，挡在 data 前面 |
| **ml / transform / remote_cluster_client** | 机器学习、持续聚合、跨集群检索 | 按需 |

**"Master 要奇数个"的准确原理**：master 选举靠**多数派（quorum）**——N 个投票节点需要 ⌊N/2⌋+1 票。**3 个容忍挂 1 个，5 个容忍挂 2 个**；**2 个是最差配置**（要 2 票全活，挂一个就失去多数派，还不如 1 个）；**偶数（4/6）不比相邻奇数更可靠**（4 个同样只容忍 1 个，却多养一台）——所以 3 或 5，**超过 5 收益递减**（选举与状态广播成本上升）。ES 7.0 起用**基于投票配置（voting configuration）的集群协调**取代了 `minimum_master_nodes` 手工配置，并会自动收缩投票集合（`cluster.auto_shrink_voting_configuration`）。

**脑裂防护（旧题必答，答法要新）**：
- **机制层**：多数派投票天然防脑裂——少数派分区选不出 master，只能等待；7.x 的协调层还会做"任期/状态版本"校验，防止旧 master 复活后乱指挥；
- **配置层**：`discovery.seed_hosts` 列全候选、**首次引导**用 `cluster.initial_master_nodes`（**只在初始化时用，之后必须删掉**，否则重启可能形成新集群）；
- **运维层**：不要两台 master-eligible 凑合；跨机房部署时**多数派必须落在同一可靠侧**（2 机房 3 节点=一边 2 一边 1，断网时"1"那侧失去多数派，是设计上的取舍而非 bug）；网络分区恢复后检查旧节点是否被正确 rejoin。

**一个被低估的追问**："**mapping 爆炸为什么会拖垮 master**"——mapping/settings/路由表都在 **cluster state** 里，每次变更广播全集群；字段数上万时 cluster state 体积膨胀，master 处理变更变慢、节点间状态同步延迟，表现为"建索引卡住、集群像假死"（3.1.1 的字段爆炸在集群层的后果）。

### 4.1.2 分片与副本怎么规划？分片数为什么创建后基本不能改？

**"不能改"的根因**：路由公式 `shard = hash(routing) % 主分片数`——**主分片数是哈希模数**，改了意味着**几乎所有文档都要换分片**（不是"挪一点数据"，是"全量重分布"）。所以：**主分片数创建即定；副本数随时可调**（副本只是拷贝，不参与路由计算）。ES 提供了 `_split`（拆分，目标数须为原来的整数倍）与 `_shrink`（收缩）两个 API，但都有前置条件（如只读、同节点等）且本质仍是重写数据——**工程上更常用"新建索引 + reindex + 别名切换"**（5.1.2）。

**规划口径（数量题的标准答案）**：
- **单分片 10~50GB** 是常用区间（日志/时序偏小、搜索偏大也行），**单分片文档数**控制在 2 亿以内量级（倒排与段管理的经验值）；
- **每 GB 堆内存对应分片数 < 20**（官方长期口径）——32GB 堆的节点，分片总数最好压在 600 以内；
- **单节点分片数上限默认 1000**（`cluster.max_shards_per_node`），超了新建索引直接失败；
- **小索引别拆多片**（几百万行 1 个主分片足够），分片不是"越多越并行"——每个分片都有固定开销（段元数据、merge、集群状态条目、查询扇出，2.2.1）；
- **按数据层与故障域规划**：hot 层多分片吃写入并行、warm/cold 层合并收缩、跨可用区用 `allocation awareness` 保证副本不同机架。

**副本的两个作用**：**读扩展**（查询分摊）+ **高可用**（主挂副本顶）；代价是**写放大**（每份副本都要写，2.1.1 的 ack 账）与存储翻倍——搜索读多写少可加副本，日志写入重可先 0 副本批量导入再恢复（4.2.1）。

**易错**：单节点集群配 1 副本 → 永远 Yellow（副本无处分配，4.1.3）；"分片越多写入越快"——单节点上分片只增加开销；扩节点后不 rebalance（新节点闲置，`_cluster/reroute` 或等自动分配，注意迁移带宽限流）；用日期做 index 名却不配模板/ILM（每天一个新索引、分片数失控，4.2.3）。

### 4.1.3 Green/Yellow/Red 分别意味着什么？Yellow/Red 怎么排查？

**语义（先把"为什么黄"讲准）**：
- **Green**：所有主分片与副本分片都已分配；
- **Yellow**：**所有主分片正常**（数据完整、读写可用），但**部分副本未分配**——最常见于"单节点 + 副本数≥1"（副本不能与主同节点）；风险是**失去冗余**（该节点挂即 Red），性能上少了一份读分摊；
- **Red**：**至少一个主分片未分配**——那部分数据**读写不可用**（索引部分分片缺失），是真正的故障态。

**排查三板斧（按顺序）**：
1. `GET _cluster/health?level=indices` 定位到具体索引与未分配数量；
2. `GET _cat/shards?v&h=index,shard,prirep,state,unassigned.reason` 看 `UNASSIGNED` 的原因码（`NODE_LEFT`/`ALLOCATION_FAILED`/`CLUSTER_RECOVERED` 等）；
3. **`GET _cluster/allocation/explain`**——ES 直接告诉你"这个分片为什么分配不出去"（磁盘水位？过滤规则？节点数不够？重试次数超限？），这是最高效的一条命令。

**常见根因清单**：节点下线/重启（等待恢复，别急着 reroute）；**磁盘水位**（85% 低水位不再分配新分片、90% 尝试迁走、95% 触发 flood stage——索引变只读 `read_only_allow_delete`，要清盘后手动解锁）；`allocation` 过滤/数据层属性配错（如 warm 层没有对应节点）；分片数超过单节点上限；副本数 > 数据节点数-1；分片分配重试超限（`index.allocation.max_retries`，处理后 `_cluster/reroute?retry_failed=true`）。

**Red 的处置逻辑**：先判断"是节点暂时离线（等它回来/副本提升）还是数据真丢（主分片所在磁盘损坏）"——有副本时 ES 会自动把副本提升为主（短暂 Red 后自愈）；**无副本且节点回不来**，只能从**快照恢复**（4.2.3）——这就是"生产必须配副本 + 快照"的运维论证，也是单节点测试集群 Yellow 属于正常、生产 Red 必须当事故的两套口径。

## 4.2 容量与可靠性

### 4.2.1 写入性能怎么调？刷新、副本、bulk、translog 各自的账怎么算？

**先定位瓶颈再调参（顺序即答案）**：写入慢先看**是 CPU（分词/merge）、磁盘（fsync/merge）、还是瓶颈在协调与副本确认**——`_nodes/stats` 的 indexing/merge/refresh 时间、线程池拒绝（429）分别指向不同层。

**六板斧（按收益与风险排序）**：
1. **Bulk 批量化**：单条 index 请求的网络与 per-request 开销占大头——`_bulk` 一批 **5~15MB**（不是"条数"，条数取决于文档大小），并发 2~4 个客户端压满；**必须逐条检查返回的 `errors`/`items`**（部分失败静默丢数据是经典事故），429 要**指数退避重试**；
2. **导入模式三件套**：初始化/重建时 `refresh_interval=-1`（或 30s）、`number_of_replicas=0`、`translog.durability=async`——导完恢复 `1s`/副本数并手动 refresh；**这是"临时加速"不是常态配置**；
3. **Translog 策略**：`durability=request`（默认，每次 fsync）最稳、写延迟最高；`async`（5s 批量）吞吐高但**崩溃丢 5 秒**——日志类可接受、订单类不可；
4. **减少写放大**：避免高频 update/delete（2.1.3 的墓碑与重写）、避免无谓的 nested（每次更新整根文档）、`doc_values:false`/`index:false` 省索引开销、字段越少越好（3.1.1）；
5. **分片与硬件**：分片数要给足写入并行（但别过 4.1.2 的红线）；**SSD** 对 fsync 与 merge 是质变（HDD 上 ES 写吞吐会被 fsync 钉死）；堆内存留给 indexing buffer（4.2.2）；
6. **Merge 限流别乱动**：默认的 merge 限速是为了**不让后台 merge 抢死前台写**——调高只会在写入高峰制造更长的 IO 排队；高峰写慢有时是"merge 在还债"，看 merge 指标而非盲目调参。

**两个追问**：① "**为什么副本=0 能快**"——省掉副本写与 ack 等待（2.1.1），但导入期间无冗余，**只用于可重跑的批量**；② "**写入被拒 429 怎么办**"——先看是 write 线程池队列满还是磁盘限流，短期的正解是**降速/加批量/加节点**，而不是无限调大队列（排队=延迟雪崩，5_tomcat.md 的排队账在此换层重演）。

### 4.2.2 堆内存怎么配？fielddata 为什么会 OOM？熔断器管什么？

**内存三分法（一句话记住）**：**堆给"元数据与计算"，剩下的给 page cache 喂 Lucene 的段文件**——所以 **堆不超过物理内存 50%**，且**不超过 ~30GB**（超过就失去压缩指针 compressed oops，同样的对象占更多内存，得不偿失）；ES 8.x 自带 JDK 17+，默认 G1。

**堆里的住户与熔断器**：

| 住户 | 说明 | 相关熔断/上限 |
|------|------|--------------|
| Segment 元数据 | 每个 segment 的词典/删除位图等常驻结构 | 分片越多越吃（4.1.2 的 20:1 口径） |
| indexing buffer | 写入缓冲（默认堆的 10%） | — |
| **fielddata** | 把 `text` 字段的倒排**加载进堆**供排序/聚合 | `indices.breaker.fielddata.limit` 默认 **40%** 堆 |
| 请求/聚合中间结果 | 大聚合、大排序的桶与堆 | `indices.breaker.request.limit` 默认 60% |
| 各种缓存 | 节点查询缓存（filter，约 10%）、request cache | — |

**fielddata 是 OOM 头号惯犯的原因**：`text` 字段默认没有 Doc Values（1.2.2），一旦对它排序/聚合，ES 只能**把整字段的倒排+词条加载进堆**——高基数文本（消息内容、URL）几千万文档就是几个 GB 的堆增量。**正确处置**：不是调大 fielddata 熔断，而是**改 Mapping 加 `keyword` 子字段**（或 `doc_values`），从根上把"列式磁盘读"换回正轨；临时救火可 `fielddata: true` + 监控，但**永远不是长期方案**。

**熔断器（circuit breaker）的定位**：**拒绝"会 OOM 的请求"而不是等 OOM 杀进程**——超限抛 `CircuitBreakingException`（429/503），保护节点整体可用（"一个大聚合拖死全集群"的防御）。**配套系统参数**：`bootstrap.memory_lock: true`（锁堆防 swap）、关闭 swap / `vm.swappiness=1`、关透明大页（THP 造成停顿毛刺）、`vm.max_map_count=262144`（mmap 段文件数上限，不配会 `max virtual memory areas` 报错）。

**追问**："**堆越大越好吗**"——不。堆大→GC 停顿长、page cache 变小→段文件读盘变多；搜索型集群常见 16~31GB 堆 + 大内存机器；"**为什么 swap 是灾难**"——GC 与查询路径被换出到磁盘，延迟从毫秒到秒级抖动，且可能触发节点被踢出集群。

### 4.2.3 日志/时序数据怎么管？ILM、数据流、快照各是什么角色？

**三件套分工**：**数据流（data stream）管"写入口"**、**ILM 管"生命周期"**、**快照管"最后兜底"**。

**数据流（7.9+，日志/指标的现代标准形态）**：对应用暴露一个写别名（`logs-app-prod`），背后是**一串隐藏的后备索引（backing indices）**；写入永远进"当前写索引"，**rollover** 时新建一个后备索引并切换写指针；查询自动跨全部后备索引（对应用透明）。**好处**：不用自己算日期后缀、rollover 原子、按时间查询自动合并结果。

**ILM（索引生命周期管理）五阶段**：

| 阶段 | 典型动作 | 目的 |
|------|---------|------|
| **hot** | rollover（`max_primary_shard_size: 50gb` / `max_age: 1d`）、priority 高 | 写入与热查询 |
| **warm** | forcemerge（只读段合并，2.1.3）、shrink、迁移到 warm 节点 | 降段数、降资源 |
| **cold** | 迁移到廉价存储/节点、可 freeze | 极少查询但仍可搜 |
| **frozen** | **searchable snapshot**（段存对象存储、本地只留缓存） | 归档级成本、仍可查 |
| **delete** | 删除索引 | 保留期合规 |

**快照（snapshot）**：仓库（S3/OSS/NFS）里的**增量备份**——首次全量、后续只存变化的段；**SLM 策略**定时执行；恢复（restore）是 Red 事故的兜底（4.1.3）与"迁集群/换版本"的通道。**注意**：快照不是"实时一致读"（备份瞬间的段边界），恢复后要接受秒级窗口；**快照不能替代副本**（副本扛节点故障、快照扛集群级灾难）。

**规划口径三句**：① 日志类**一个数据流 + 一个 ILM 策略**覆盖到底（模板里绑定 `index.lifecycle.name`）；② 保留期由业务合规定（delete 阶段 `min_age`），**别用 delete_by_query 清理历史**（2.1.3）；③ 冷热分层按**成本/查询频率**划（warm 降副本、cold 降机型、frozen 上对象存储）——"所有数据都放 hot 层"是容量预算失控的第一原因。

**易错**：数据流配了 ILM 却没配 rollover（写索引无限增长到 50GB 上限后拒绝写入——`index.lifecycle.rollover_alias` 与模板绑定漏配）；手动对数据流后备索引做写操作（数据流是**只追加**，更新/删除要按 `_id` 且语义受限）；快照仓库权限/路径配错直到恢复时才发现（**恢复演练**是备份体系的一部分，没演练过的备份等于没有）。

# 5. 工程实践

## 5.1 与数据库的协同

### 5.1.1 MySQL 与 ES 怎么同步？双写、Canal、消息各有什么坑？

**先说定位**：ES 是**检索副本**，真相在 MySQL（1.1.1）——所以同步方案的核心指标是"**最终一致 + 可重放 + 可对账**"，而不是"实时强一致"。

**四条路线对照**：

| 方案 | 机制 | 优点 | 坑 |
|------|------|------|----|
| **应用双写** | 业务代码写 DB 后同步写 ES（或反之） | 简单直接、延迟低 | **部分失败**（DB 成功 ES 失败）、事务边界（写库回滚了 ES 已写）、并发乱序（两个线程的更新到达 ES 顺序颠倒→旧值覆盖新值）；要配补偿任务与版本号 |
| **binlog 订阅（CDC）** | Canal/Debezium 解析 binlog → MQ → 消费者写 ES（14_canal.md） | **与业务解耦**、可回放、天然覆盖所有写路径（含后台脚本） | 链路长（延迟秒级）、DDL/字段映射要维护、MQ 堆积与重复投递要幂等 |
| **业务事件（MQ）** | 领域事件（订单已创建）发 MQ → 搜索服务消费写 ES | 语义清晰、可只同步需要的字段 | 事件漏发=数据缺失；事件定义与业务演进耦合；顺序要靠分区键 |
| **定时全量/增量拉取** | Logstash JDBC input/自研扫表 | 简单、适合初始化 | 非实时；**删除难感知**（除非软删标记）；扫表压力 |

**生产推荐组合**：**CDC 为主（binlog → MQ → ES）+ 定时对账兜底**——覆盖全、可重放；应用不为"写搜索"承担额外失败路径。

**幂等与顺序（同步题的真正考点）**：
- **`_id` 用业务主键**（订单号/用户 ID）：重复投递=覆盖同一条文档（天然幂等）；
- **乱序**：同一文档的两次更新可能乱序到达——用 **`version_type=external`**（版本号取 `update_time` 或业务版本，旧版本写入被拒）或 `if_seq_no/if_primary_term` 乐观并发；**没有版本保护时"最后到达者赢"可能倒退数据**；
- **删除**：CDC 的 delete 事件要转成 ES 的 delete（按 `_id`）；软删方案则同步 `deleted` 字段并在查询侧过滤（两种都要在全量重建时保持一致）；
- **失败处理**：消费失败进重试队列/死信（13_rocketmq.md 3.2 家族），**别无限阻塞分区**；监控"同步延迟/失败数/对账差异"三件套（14_canal.md 的位点与 lag 面板）。

**一致性的诚实口径**："**秒级最终一致**是设计目标；'写完立刻搜到'要么业务侧接受（前端延迟展示/乐观 UI），要么写后按 `_id` GET 原始数据（2.1.2 的实时 GET），**不要为搜索链路的实时性把 ES 变成同步强一致的瓶颈**。"对账任务（按日/小时抽样比对 DB 与 ES 的文档数与关键字段）是所有同步方案的共同兜底。

### 5.1.2 重建索引与别名切换怎么做？零停机重建的完整流程？

**触发重建的场景**：改字段类型/分词器（3.1.1）、加 keyword 子字段、分片数调整（4.1.2）、Mapping 混乱需重来、版本升级迁移。

**零停机七步（面试就按这七步报）**：

```text
① 建 v2 索引：新 Mapping/Settings（分片数、分词器、副本），命名 order_v2
② 准备别名：业务代码只认别名 order_search（从一开始就这么设计，5.1.1）
③ 全量回填：_reindex（可 slices=auto 并行、wait_for_completion=false 异步 + _tasks 看进度）
   或从 MySQL 重新灌数据（数据量小/需要清洗时更干净）
④ 增量追平：CDC/双写继续把新变更写到 v2（回填期间 v1 仍在服务）
⑤ 校验：文档数、抽样字段、关键查询结果对比（v1 vs v2 双读 diff）
⑥ 原子切换：一次 _aliases 请求里 remove v1 + add v2（同一请求是原子的）
⑦ 观察与回滚：观察错误率/延迟，异常则反向切回 v1；稳定后删 v1、释放资源
```

**两个细节决定成败**：
1. **写别名与切换的配合**：数据流/写别名场景用 `is_write_index` 标记"当前写索引"，切换时把写指针移过去；应用若写具体索引名，切换瞬间会写旧索引——**别名纪律必须从第一天执行**；
2. **`_reindex` 的姿势**：`dest.op_type=create` 防止覆盖 v2 已有文档、`slices` 并行但别把集群打满、大索引分批（按时间范围切片）避免长事务式压力；**reindex 读的是 v1 的搜索视图（近实时），回填期间 v1 的新写入要靠第 ④ 步补**——忘了增量追平 = 丢切换前最后一分钟的数据。

**回滚与演练**：别名切换是**秒级可逆**的（再切回 v1），但 v1 若已停止同步就回滚不了——所以**切换后观察窗口内保持 v1 的增量同步**，窗口过了再拆。**演练**：小索引先跑一遍全流程，把"reindex 耗时、校验脚本、alias 命令"固化成 runbook（5.2.1 的运维纪律）。

## 5.2 踩坑与选型

### 5.2.1 生产高频事故清单怎么答？

**按"症状 → 根因 → 动作"组织（面试报 5 条带细节胜过背 20 条名词）**：

| 症状 | 根因 | 处置 |
|------|------|------|
| 集群 Red/Yellow | 节点离线、磁盘水位、分配过滤（4.1.3） | `allocation/explain` 定位；清盘/改过滤/等节点回归；无副本则快照恢复 |
| 写入 429 / 队列拒绝 | write 线程池满、merge/fsync 打满 IO、bulk 过大 | 降速+批量调优（4.2.1）；看 `_cat/thread_pool`；加节点而非调大队列 |
| 查询变慢、GC 频繁 | fielddata 加载 text 字段、大聚合、分片过多（4.2.2/4.1.2） | 改 keyword/Doc Values；拆聚合；`search.max_buckets` 护栏；扩堆需谨慎 |
| 字段爆炸、建索引卡住 | 动态 mapping + 动态 key（3.1.1） | `flattened`/`dynamic: strict`、拆索引、清理超限模板 |
| 搜不到数据 | refresh 未到（2.1.2）、分词器不一致（3.1.2）、term 打 text（2.2.3）、同步断链（5.1.1） | 按链路逐段验证：写入→refresh→分词→查询语法→同步位点 |
| 深分页超时/内存爆 | from+size 过深（2.2.2） | `search_after`+PIT、限制页码、导出走 scroll |
| 聚合数与业务不符 | terms 近似、cardinality 近似（3.2.1）、时区（date_histogram） | `shard_size`/composite；精确口径回 DB；统一 `time_zone` |
| 磁盘持续涨 | 无 ILM、副本过多、merge 空间、快照未清理（4.2.3） | 数据流+ILM；副本与保留期复核；快照仓库容量告警 |
| Master 不稳/集群假死 | cluster state 过大、master 负载混部、网络分区（4.1.1） | 专用 master、清理 mapping、检查投票配置 |
| 发布后大量 401/证书错误 | 8.x 安全默认开启、证书过期（1.1.2） | 证书轮换、客户端同步更新 CA |

**诊断工具箱**（比清单更值钱）：`_cluster/health`、`_cat/*`（indices/shards/nodes/thread_pool/allocation）、`_nodes/stats`、`_tasks`（长任务）、`_nodes/hot_threads`（卡在哪）、**慢日志**（`search.slowlog`/`index.slowlog` 阈值设好）、`_profile`（单查询算子级耗时）、`_cluster/allocation/explain`。**纪律**：所有变更（mapping/ILM/别名）走模板与版本控制，禁止手改生产索引——"一次手滑"是事故清单里出现频率最高的根因（33_cicd.md 的发布纪律在数据层的投影）。

### 5.2.2 什么时候不该用 ES？和 ClickHouse、向量库怎么分工？

**不该用 ES 的六个信号**（对应 1.1.1 的四条本质差异）：① 需要跨文档事务/强一致（账户、库存）；② 复杂多表 JOIN 报表；③ **高频更新**（状态机、计数器——不可变存储的写放大）；④ 要求**精确**计数/求和（聚合近似）；⑤ 数据量小（几 GB 以内，MySQL 索引足够）；⑥ 把 ES 当**唯一存储**（无副本、无快照的"主库"是定时炸弹）。

**ES vs ClickHouse（分析场景的经典对照）**：

| 维度 | Elasticsearch | ClickHouse |
|------|---------------|------------|
| 强项 | **全文检索/相关性排序**、灵活 schema、近实时写入、聚合够用 | **大规模 OLAP 聚合**（列存+向量化+MPP）、高压缩、SQL 生态 |
| 写入 | 近实时、单文档/批量皆可、更新代价高 | 批量导入为王（小批高频写是弱项）、**更新/删除昂贵**（MergeTree 的 mutation） |
| 查询 | 相关性/模糊/多字段搜索强；大宽表 GROUP BY 相对弱 | 大宽表聚合极快；全文检索需额外引擎（如 ClickHouse 的倒排/词典功能有限） |
| 成本 | JVM 堆+存储，资源弹性一般 | 压缩率高、单位查询成本低 |
| 选型句 | "**要搜**（相关性/分词/模糊）选 ES" | "**要算**（大聚合/报表/日志分析）选 ClickHouse"——日志场景两者都能做，按"检索体验 vs 分析成本"取舍 |

**ES vs 向量库**：ES 8.x+ 内置 `dense_vector` 与 kNN（HNSW），支持**混合检索（BM25 + 向量 + RRF 融合）**——"已有 ES、向量规模中等、要文本+语义混合"直接用它；**十亿级向量、极致低延迟、专用索引调优**才考虑 Milvus/Qdrant 等专用库（运维多一套系统）。**判断轴**：向量规模、是否需要与全文检索融合、团队运维能力。

**收口三句**：① ES 的定位是**搜索与分析引擎**，不是数据库——选型先问"真相在哪、能不能重建"；② 检索与分析的边界正在模糊（ES 的 ES|QL/TSDB、ClickHouse 的检索增强），但**各自的成本结构没变**——按负载特征选，不按热度选；③ 许可证与发行版（Elastic License/SSPL vs OpenSearch 分支）在合规敏感的企业里也是决策项，报一句"许可证与托管形态一起评估"即周全（2026 口径以各自官方为准）。
