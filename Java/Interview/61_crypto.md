# 1. 知识点
- **密码学分类**: 对称加密(共享密钥)、非对称加密(公私钥对)、摘要算法(哈希/不可逆)、数字签名(私钥签名公钥验签)、密钥协商(DH/ECDHE)
- **对称加密**: 加密和解密使用相同的密钥。算法：AES(首选)、DES(已破解废弃)、3DES(废弃)、SM4(国密)
- **AES(Advanced Encryption Standard)**: 目前最广泛使用的对称加密标准，密钥长度128/192/256位，分组加密，安全性高速度快
- **AES工作模式**: ECB(电子密码本，弱，相同明文→相同密文，不安全)、CBC(密码分组链接，前块密文与当前块明文XOR后加密，需IV初始向量)、CTR(计数器模式，流加密)、GCM(Galois/Counter Mode，带认证加密，推荐)
- **ECB模式缺点**: 相同明文块产生相同密文块，无法隐藏数据模式(企鹅图片的轮廓仍然可见)。不应使用
- **CBC模式**: 每个明文块先与前一个密文块XOR再加密，IV初始化向量保证相同明文产生不同密文。不并行加密，需填充
- **GCM模式推荐**: 提供加密+完整性验证(AEAD，Authenticated Encryption with Associated Data)。速度快(可并行)，防篡改。是AES的推荐模式
- **非对称加密**: 公钥加密、私钥解密。算法：RSA、ECC(椭圆曲线)、SM2(国密)。比对称加密慢数百倍，适用于密钥交换和数字签名
- **RSA**: 最广泛使用的非对称算法。密钥长度推荐2048+位(1024已不安全)。适用于小数据加密和数字签名
- **RSA原理**: 基于大整数分解的数学难题。生成两个大质数p和q，n=p*q。公钥(e,n)，私钥(d,n)。加密：c=m^e mod n；解密：m=c^d mod n
- **ECC椭圆曲线**: 比RSA密钥更短、安全性更高、速度更快。256位ECC≈3072位RSA安全性。适合移动端/嵌入式
- **摘要算法(Hash)**: 任意长度输入→固定长度输出，不可逆，无法从hash值还原原文。MD5(128位，已破解)、SHA-1(160位，已破解)、SHA-256/SHA-512(安全)、SHA-3(最新标准)
- **MD5**: 128位输出，已可构造碰撞(不同输入产生相同hash)，不应用于安全场景。仅可用于非安全校验(文件完整性快速检查)
- **SHA-256**: 256位输出，当前安全，比特币、TLS等广泛使用。SHA-2家族包括SHA-224/256/384/512
- **Hash特性**: 定长输出、不可逆(单向)、雪崩效应(输入微小变化→输出巨大差异)、抗碰撞(很难找两个不同输入相同输出)
- **数字签名**: 发送方用私钥对消息摘要签名，接收方用公钥验签。保证：完整性(消息未被篡改)、身份验证(确实来自发送方)、不可否认(发送方不能抵赖)
- **数字签名流程**: 发送方对原文计算Hash → 用私钥加密Hash得到签名 → 发送原文+签名 → 接收方用公钥解密签名得到Hash1 → 对原文计算Hash得Hash2 → 比较Hash1==Hash2
- **数字签名算法**: RSA-PSS(推荐)、ECDSA(椭圆曲线)、EdDSA(Ed25519)、SM2
- **数字证书(X.509)**: 由CA(Certificate Authority，证书颁发机构)签名，绑定公钥与身份信息(域名/组织)。包含：序列号/颁发者/有效期/主体/公钥/CA数字签名
- **证书链**: 根CA(自签名，可信) → 中间CA → 网站证书。验证时逐级向上验证签名，直到根CA。根CA证书预先内置在浏览器/操作系统中
- **HTTPS加密过程(TLS握手)**: 客户端Hello(支持的加密套件+随机数1) → 服务端响应(选定加密套件+随机数2+证书) → 客户端验证证书，生成预主密钥，用服务器公钥加密发送 → 双方根据三个随机数生成会话密钥(对称密钥) → 之后用AES对称加密通信
- **TLS 1.2 vs 1.3**: 1.3减少握手到1-RTT(1.2需2-RTT)、移除不安全算法(RSA密钥交换、RC4、3DES、CBC)、只保留AEAD加密模式(GCM/CCM)
- **JWT签名算法**: HS256(HMAC+SHA-256，对称，签发验证同一key)和RS256(RSA+SHA-256，非对称，私钥签发公钥验证)
- **JWT签名选择**: 内部服务间(少量消费者)用HS256(简单快速)；对外开放/SSO/多消费者用RS256(公钥可分发、私钥不外泄)。关键：secret/key必须足够长且安全保管
- **API签名**: 请求方对参数排序+拼接+MD5/SHA256摘要(含密钥)，防止数据篡改和重放攻击。签名中通常包含时间戳+nonce防重放
- **API签名流程**: 1)参数按ASCII排序 2)拼接成k1=v1&k2=v2格式 3)加上timestamp和nonce 4)拼接secret_key 5)计算MD5/SHA256得到sign 6)请求携带sign、timestamp、nonce
- **Nonce防重放**: 随机值一次性使用，服务端记录已使用的nonce(Redis key=nounce, TTL=签名有效期)。防止攻击者重放相同请求
- **密码存储算法**: BCrypt(PBKDF2变体，内置随机盐+可调迭代次数，存储格式含算法标识+cost+salt+hash)、SCrypt(内存密集型，防GPU/ASIC暴力破解)、Argon2(最新密码哈希竞赛冠军)
- **BCrypt存储格式**: `$2a$10$N9qo8uLOickgx2ZMRZoMyeIjZAgcfl7p92ldGxad68LJZdL17lhWy` => 算法标识$2a$ + cost10 + 22字符salt(前22字符) + 31字符hash
- **密钥协商DH(Diffie-Hellman)**: 在不安全信道上协商共享密钥。双方各自生成私钥和公钥，交换公钥后各自计算得到相同的共享密钥，中间人无法推导
- **ECDHE**: 基于椭圆曲线的DH密钥交换，支持前向安全性(Forward Secrecy)。TLS握手后即使服务器私钥泄露，历史通信内容也无法解密(每次会话独立密钥)
- **前向安全(Forward Secrecy)**: 每次TLS会话生成独立的临时密钥对(ECDHE)，会话结束后私钥销毁。即使长期私钥泄露，也无法解密历史会话
- **国密算法**: SM1(对称加密)、SM2(非对称加密/签字)、SM3(摘要256位)、SM4(对称加密128位)。国内金融/政务系统要求

# 2. 面试题

## 2.1 对称加密和非对称加密的区别和使用场景？
| 维度 | 对称加密(AES) | 非对称加密(RSA/ECC) |
|------|--------------|-------------------|
| 密钥 | 同一个密钥加解密 | 公钥加密，私钥解密 |
| 速度 | 快(硬件加速) | 慢(数百倍~千倍) |
| 密钥分发 | 难(需安全通道) | 易(公钥可公开) |
| 适用数据 | 大数据 | 小数据/密钥交换 |
| 算法 | AES, SM4 | RSA, ECC, SM2 |

实际使用场景：
- **对称加密**：HTTPS数据传输加密(TLS中会话层使用AES-GCM)、数据库字段加密、文件加密
- **非对称加密**：TLS握手密钥交换(ECDHE)、数字签名(代码签名、证书)、JWT/Token签名
- **混合使用**：HTTPS中，非对称加密交换对称密钥，然后用对称加密传输数据。结合两者优点

## 2.2 AES的ECB、CBC、GCM模式有什么区别？
| 模式 | ECB | CBC | GCM |
|------|-----|-----|-----|
| 并行加密 | 可以 | 不可以 | 可以 |
| 并行解密 | 可以 | 可以 | 可以 |
| 需要IV | 不需要 | 需要 | 需要(nonce) |
| 安全级别 | 弱(泄露数据模式) | 中(不防篡改) | 高(防篡改+加密) |
| 完整性保护 | 无 | 无 | 有(GMAC认证) |
| 推荐使用 | 不要用 | 过渡方案 | 首选 |

ECB致命缺陷：相同明文块产生相同密文块，能看出数据模式(如位图的轮廓清晰可见)。CBC无需填充或padding，但存在padding oracle攻击风险(通过分析填充错误解密)。GCM是AEAD模式，加密同时生成认证标签，能检测篡改，是当前首选。

## 2.3 RSA和ECC(椭圆曲线)加密的对比和选择？
| 维度 | RSA | ECC |
|------|-----|-----|
| 相同安全级别 | 3072位 | 256位 |
| 密钥长度 | 长(2048-4096位) | 短(256-521位) |
| 性能 | 密钥生成慢、加密快、解密慢 | 密钥生成快、加解密都快 |
| 签名大小 | 大(256-512字节) | 小(64-132字节) |
| 成熟度 | 最成熟，广泛支持 | 越来越成熟 |
| 适用 | 兼容性优先 | 性能/资源受限优先 |

推荐：新系统优先ECC(密钥短性能好，移动端友好)，需要老系统兼容的用RSA。TLS证书已广泛支持ECC(ECDSA)。

## 2.4 MD5和SHA-256的区别？MD5还能用在哪？
| 维度 | MD5 | SHA-256 |
|------|-----|---------|
| 输出长度 | 128位(16字节) | 256位(32字节) |
| 安全性 | 已破解(可构造碰撞) | 当前安全 |
| 速度 | 快 | 较慢 |
| 碰撞 | 已被证明可构造 | 目前无法构造碰撞 |

MD5已破解，不能用于：密码存储、数字签名、证书。仍可用的场景：1)文件完整性快速校验(仅防意外损坏，不防恶意篡改) 2)非安全场景的去重标识(如大文件秒传Hash之一)

SHA-256是当前推荐的安全Hash算法，用于数字签名、区块链接、TLS证书等安全场景。

## 2.5 什么是数字签名？如何实现不可否认性？
数字签名是发送方用私钥对消息摘要加密生成的，接收方用发送方的公钥可验证。

流程：发送方计算消息Hash → 用私钥加密Hash得到签名 → 发送消息+签名。接收方用发送方公钥解密签名得到Hash1 → 自己计算消息Hash得到Hash2 → 比较Hash1==Hash2。匹配说明：1)消息未被篡改(完整性) 2)确实是该私钥持有者发送(身份认证) 3)发送方不能否认发送过(不可否认性，因只有他持有私钥)

Java实现：Signature类，signature.initSign(privateKey)签名、signature.initVerify(publicKey)验证。RSA_PSS和ECDSA是推荐算法。

## 2.6 HTTPS的加密过程是怎样的？
以TLS 1.2为例：
1) **Client Hello**：客户端发送支持的TLS版本、加密套件列表、客户端随机数(Random1)
2) **Server Hello**：服务器确认TLS版本、选定加密套件、返回随机数(Random2)+数字证书(含服务器公钥)
3) **客户端验证证书**：验证证书链(CA签名链)、有效期、域名匹配。通过后生成预主密钥(Pre-Master Secret，48字节随机数)
4) **密钥交换**：客户端用服务器公钥(RSA)或通过ECDHE协商对预主密钥加密发送。RSA模式：客户端加密Pre-Master Secret发送。ECDHE模式：双方通过交换临时公钥各自计算出Pre-Master Secret(前向安全)
5) **会话密钥生成**：双方用Random1+Random2+Pre-Master Secret通过PRF(伪随机函数)生成会话密钥(对称密钥，用于AES加密)
6) **加密通信**：双方发送Finished消息(加密的，验证握手成功) → 之后所有通信使用AES对称加密

TLS 1.3简化握手为1-RTT，并移除RSA密钥交换(不安全，无前向安全)，只保留(EC)DHE。

## 2.7 JWT中HS256和RS256的区别？如何选择？
| 维度 | HS256 | RS256 |
|------|-------|-------|
| 算法 | HMAC-SHA256(对称) | RSA-SHA256(非对称) |
| 密钥 | 单一secret | 公私钥对 |
| 签发 | 用secret签名 | 用私钥签名 |
| 验证 | 用secret验证 | 用公钥验证 |
| 性能 | 快 | 慢(但验证一次) |
| 密钥管理 | secret需安全分发(多服务共享有风险) | 私钥集中管理，公钥可分发 |

选择：
- 单体应用/内部少量微服务：HS256(简单)
- SSO/OAuth2/多消费者场景：RS256(安全，多个服务只需持有公钥即可验证)
- 服务端签发、客户端验证：RS256(公钥给客户端，私钥不外泄)
- JWT secret必须足够强(HS256用至少256位随机值，RS256私钥2048+位)

## 2.8 API接口签名如何防篡改和防重放？
签名流程：
1) 参数收集：除签名(sign)外的所有请求参数+Body
2) 参数排序：按参数名ASCII码字典序排序
3) 拼接：`key1=value1&key2=value2` 格式
4) 加防重放字段：timestamp(时间戳，毫秒)+nonce(随机字符串，UUID)
5) 拼接secret：`拼接串 + &secret=分配的安全密钥`(secret不在请求中传输)
6) 计算签名：`MD5/SHA256(拼接后的字符串)`
7) 客户端发送请求：携带sign、timestamp、nonce

防重放：
- 服务端验证：timestamp与服务器时间差<60秒(防止过期重放)
- nonce去重：`SETNX nonce_key value EX 60`存入Redis，重复nonce拒绝
- 这样攻击者在60秒内无法使用相同参数+相同nonce重放，不同nonce则签名不同(因nonce参与签名计算)

## 2.9 BCrypt为什么适合存储密码？
1) **内置随机盐(Salt)**：每次hash自动生成不同盐值，相同密码每次hash结果不同，防止彩虹表攻击
2) **可调计算成本(Work Factor)**：strength参数(如10)控制迭代次数=2^10次，可随硬件发展调整。每次+1破解难度翻倍
3) **慢哈希设计**：故意使计算变慢(每次几百毫秒)，增加暴力破解成本。用户登录感受不到(几百ms可接受)，但对攻击者百万次尝试影响巨大
4) **成熟经过验证**：基于Blowfish算法，使用广泛，经过安全社区验证
5) **存储格式自包含**：`$2a$10$salt+hash`存储包含算法版本、cost、salt、hash。验证和升级cost都很方便

```java
BCryptPasswordEncoder encoder = new BCryptPasswordEncoder(10);
String hash = encoder.encode("myPassword");  // hash包含salt
boolean ok = encoder.matches("myPassword", hash);  // 自动提取salt
```
