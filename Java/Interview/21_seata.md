# 1. 定位与架构

## 1.1 为什么需要、谁来解

### 1.1.1 为什么需要分布式事务？本地事务为什么顶不住？

**问题从拆库那刻诞生**：单体时代一个 `@Transactional` 包住订单、库存、券——同一连接、同一 InnoDB 事务，ACID 白拿（实现账见 16_mysql.md 3.1.1）。微服务"一服务一库"的数据层纪律（15_spring_cloud.md 1.2.3）之后，"下单 = 扣库存 + 核销券 + 记订单"变成**跨 N 个服务、N 个数据库的多个本地事务**——每个本地事务只能对自己那个库负责，**没有任何一个本地事务能替整体做原子性裁决**。

**"不用框架行不行"的三条土路都要能反驳（面试考的就是这段）**：
1. **顺序 RPC + try-catch 手工补偿**：第 3 步失败时前 2 步早已提交——"往回删"本身就是新的分布式操作（删也可能失败）；补偿语义、状态记录、重试全部手搓，等于自研一个劣质 Seata；
2. **先扣本地、异步通知下游**：中间态窗口从毫秒级拉长到秒~分钟级，且"通知必达"自己又是一个要解决的问题（事务消息，13_rocketmq.md 2.3.1）——这条路不是绕开一致性，是把强一致降级成最终一致（是否可接受是业务问题，见 5.1.2）；
3. **崩了就对账人工修**：小流量可行，大促时人工消化不了——对账只能兜底，不能当主链路。

**理论定位一句**：跨资源的一致性方案只有两个家族——**同步协调**（2PC 系：Seata AT/XA、TCC，调用方拿到全局裁决才返回）与**异步最终一致**（事务消息/本地消息表/Saga 补偿，接受窗口期）。BASE 与柔性事务的概念框架在 34_distributed_theory.md；Seata 是同步家族里工程化最完整的一支。

**Seata 是谁**：阿里开源（2019.1 公开，内部前身支撑过多届双 11），现以 **Apache Seata（incubating）** 身份在 Apache 孵化器演进（仓库 `apache/incubator-seata`，2.x 线文档现行；包坐标从 io.seata 向 org.apache.seata 迁移，具体从哪个版本起以 release note 为准）。产品形态：**独立部署的协调器 TC（seata-server）+ 嵌在应用里的客户端 SDK**，提供 AT/TCC/Saga/XA 四种模式（逐个展开见块 2~4，总表 5.1.1）。

**成熟的收口句**："上分布式事务框架是**最后手段**——架构上更优解永远是领域拆分让一致性边界回到单库（15_spring_cloud.md 1.2.3 的聚合根纪律）；拆不动、必须跨服务原子性时，才按隔离与侵入的取舍选 Seata 的某个模式。"

### 1.1.2 TC、TM、RM 分别是什么？XID 在其中扮演什么角色？

**三组件一 ID**（Seata 全局事务的最小解剖）：

| 角色 | 本体 | 职责 |
|------|------|------|
| **TC**（Transaction Coordinator） | 独立部署的 seata-server | 维护全局事务与分支事务的状态机；接收 TM 的开始/提交/回滚请求；**驱动**各分支的二阶段提交或回滚；AT 模式下还兼任**全局锁的服务端**（2.1.2） |
| **TM**（Transaction Manager） | 应用内 SDK（`@GlobalTransactional` 的 AOP 切面） | 定义全局事务边界：向 TC **开启**全局事务（领 XID）、方法结束时按异常规则向 TC **裁决**提交或回滚 |
| **RM**（Resource Manager） | 应用内 SDK（DataSourceProxy / TCC 代理 / XA 代理） | 管理**分支事务**：向 TC 注册分支、报告分支状态、执行 TC 下达的分支提交/回滚（AT 里就是 undo_log 的清理与反向补偿，2.1.1） |

**XID**：TC 生成的全局事务唯一标识（历史格式含 TC 地址信息，如 `ip:port:transactionId` 家族），是**把散落 N 个服务的本地事务串成一个全局事务的那根线**——TM 开启时获得，随 RPC 沿调用链透传，每个 RM 注册分支时绑定（透传机制与断链场景单列 1.2.2 深讲，链路同构于 traceId 的 propagation，15_spring_cloud.md 4.2.1）。

**两套事务的层级关系（概念题的满分图）**：

```text
全局事务（TC 裁决，XID 标识）
 ├── 分支1：order-db 的本地事务（RM1 在阶段1自己提交/回滚，16_mysql.md 4.2.2 意义上的真本地）
 ├── 分支2：stock-db  的本地事务（RM2）
 └── 分支3：coupon-db 的本地事务（RM3）
裁决规则：所有分支一阶段成功 → 全局提交；任一失败/超时 → 全局回滚（各分支用各自模式的语言"撤销"已提交的效果）
```

**易错**：① 把 TM/RM 当独立进程——它们只是 SDK 里的角色，进程只有 TC 是独立的；② "TC 记录业务数据"——TC 只存**状态与锁**（global_table/branch_table/lock_table，5.2.1），业务数据永远在业务库；③ 一个应用可以同时是 TM（作为发起者）和 RM（作为参与者），角色跟着调用位置走、不跟着服务走。

## 1.2 全局事务生命周期

### 1.2.1 @GlobalTransactional 标注的方法从头到尾经历了什么？（以 AT 为例）

**一条完整时间线**（发起方 order-service 调 stock-service、coupon-service，全 AT）：

```text
① TM 拦截 @GlobalTransactional：向 TC 开启全局事务 → TC 生成 XID，
   写入客户端根上下文（RootContext，ThreadLocal）
② 业务执行：order-db 的 SQL 被 DataSourceProxy 拦截 →
   作为分支1 向 TC 注册（带 XID）→ 阶段1 本地提交（机制见 2.1.1）
③ 发起 RPC：Feign/Dubbo 拦截器把 XID 塞进请求头透传（1.2.2）
④ stock-service 收到请求：服务端拦截器从头里取出 XID 绑定本地上下文 →
   其 DB 操作同样走 ② 成为分支2——coupon 同理分支3
⑤ 方法正常返回：TM 向 TC 裁决"全局提交" → TC 把全局状态置为提交中，
   **异步**通知各 RM 二阶段提交（AT 的二阶段提交只删 undo_log，不阻塞用户响应）
⑥ 方法抛异常（命中回滚规则）：TM 裁决"全局回滚" → TC 逐个通知 RM
   按 undo_log 反向补偿 → 补偿完成释放全局锁 → 全局状态回滚成功
   （若补偿失败：回滚重试队列 + 告警，5.2.2 的 rollback-undone 事故位）
```

**三个必须讲准的细节**：
1. **"提交"发生在用户返回之前，但"清理"发生在之后**——AT 的 ⑤ 用户感知到的成功 = 所有分支**一阶段已本地提交 + TC 已记录提交裁决**；undo_log 删除是后台异步（性能来源之一，2.2.2 也会成为排查误导源：查 undo_log 时已提交事务的记录可能已清）；
2. **回滚的不对称成本**：提交=删日志（便宜），回滚=快照反向恢复+校验（贵且可能失败）——**AT 的设计赌注是"绝大多数全局事务会成功"**，用一阶段的贵换提交路径的快，失败路径补偿（2.1.1）；
3. **超时兜底**：`@GlobalTransactional(timeoutMills = ...)` 默认 60s（值以版本文档为准），到点 TC 主动发起全局回滚——**长事务不是"挂着等"，是被 TC 杀**（Saga 除外，它的超时语义在 4.1.2）。

**易错**：以为 @GlobalTransactional 能包住"没被代理的数据源/没走集成 RPC 的调用"——不能，它只协调注册进来的分支，漏网分支照旧自顾自提交（1.2.2 的静默降级正是这个坑的产物）；**回滚范围**可用 `rollbackFor/noRollbackFor` 指定，与 Spring `@Transactional` 的默认回滚规则（只 RuntimeException/Error）是否一致——**以当前版本文档 + 单测为准**，别背死。

### 1.2.2 XID 是怎么跨服务透传的？丢失与"异步断链"为什么是最阴险的事故？

**机制三件套**：
1. **绑定**：TM 开启事务后 XID 存在客户端 `RootContext`（ThreadLocal）——同线程内的分支自动带上；
2. **传出**：RPC 客户端拦截器把 XID 写进请求头/attachment——**Feign 走 RequestInterceptor（18_feign.md 4.2.1 的扩展点在 Seata 的用法）**，Dubbo 走 attachment，gRPC/HttpClient 有对应集成；Seata 与主流框架的自动集成靠 starter 内置这些拦截器；
3. **接续**：下游服务端拦截器（HTTP Filter/Dubbo Filter）取出 XID → `RootContext.bind()` → 下游的 DataSourceProxy/TCC 代理注册分支时挂到同一全局事务上；返回路径上解绑。

**断链场景清单（这题的硬核，按"静默程度"排序）**：

| 场景 | 后果 | 症状与对策 |
|------|------|-----------|
| **线程池/@Async/MQ 消费** | ThreadLocal 不过线程边界，新线程里没有 XID | **静默降级**：分支变成纯本地事务照常提交，不报错——出问题时全局回滚管不到它（1_java.md 3.4 ThreadLocal 治理的 Seata 版）。对策：显式把 XID 带过去并 `RootContext.bind(xid)`（消费完解绑），或承认跨线程就该走异步一致性（13_rocketmq.md 2.3.1） |
| **未代理的数据源** | 同一应用里第二个 DataSource 没包 DataSourceProxy / 有人拿原生 Connection 写库 | 同样静默：改动不在分支列表里，回滚不恢复它。对策：全局收编数据源入口（统一 Bean 工厂）、DDL 账号权限收紧 |
| **自定义/第三方 HTTP 调用** | 没走被集成的客户端（手写 RestTemplate 没配拦截器、三方 SDK 自管连接） | XID 不出门，下游整段裸奔。对策：补拦截器；对接方无 Seata 时改 Saga/TCC/消息（4.1.2） |
| **网关透传但应用未接** | SCG/Nginx 能把头原样带过去（19_spring_cloud_gateway.md 的路由语义），下游没引 SDK 等于没传 | 检查清单归到"每服务接入面"，不是网关的事 |
| **MQ 链路** | 生产者事务与消费者事务**默认是两个世界**——消费者里恢复 XID 意味着"全局回滚要撤销一条已经异步扇出的消息"，语义不成立 | 正解：要么消费端开新全局事务（自己的原子性自己保），要么这段本来就该用事务消息（13_rocketmq.md 2.3.1） |

**排查工具箱**：TC 控制台/事务查询接口看**全局会话的分支列表**——期望有 3 个分支只注册了 2 个，断点就在没出现的那个服务；应用日志里 `RootContext.getXID()` 打点（入口、RPC 前、异步任务内三点一线）；`branch register` 相关 WARN。

**收口**：XID 透传是**约定而非强制**——它复用了 RPC 上下文这条"顺路车道"，凡是不走寻常路的执行路径（换线程、换协议、换连接）都会掉出车道。**上 Seata 的接入评审清单，一半内容就是这张表**：每个数据源、每类客户端、每个线程池、每个消费者，逐条问"XID 到不到得了"。

# 2. AT 模式

## 2.1 核心机制

### 2.1.1 AT 的两阶段为什么敢没有 prepare？undo_log 和数据快照怎么工作？

**先看对照组**：MySQL 内部 2PC 的一阶段是 prepare——**事务挂着所有行锁等全局裁决**，这正是 XA 模式的性能死穴（4.2.1）。Seata AT 的翻盘思路：**把"等待"换成"先斩后奏 + 可逆日志"**——一阶段直接本地提交、立刻释放数据库锁与连接，把"撤销的可能性"物化成数据。

**一阶段（每个分支的本地事务里原子完成）**：

```text
① 拦截业务 SQL（DataSourceProxy + SQL 解析器）
② 解析元数据：定位受影响行 → 查询 before image（改前快照）
③ 执行业务 SQL → 查询 after image（改后快照）
④ 组装 undo_log（xid/branch_id/表名/行主键/两个快照/SQL 类型）
⑤ 向 TC 申请涉及行的全局锁（2.1.2）+ 注册分支
⑥ 业务 SQL、undo_log 插入、全局锁获取——同一个本地事务提交
   （原子性关键：undo_log 没写成功，业务改动同样不生效）
```

**二阶段**：
- **全局提交**：异步删掉各分支 undo_log，完事——**没有任何"提交"动作要做**（数据早就提交了），提交成本≈一次 RPC + 删一行日志；
- **全局回滚**：取 undo_log → **校验**：拿当前数据与 after image 比对——一致才用 before image 生成反向 SQL 恢复（恢复与删 undo_log 同本地事务）；**不一致=有绕过 Seata 的本地写入插了队**，此时自动回滚会毁掉那笔"账外"数据——Seata 拒绝回滚、告警、等人工（5.2.2 的 rollback-undone）。

**为什么快照+校验这套能成立（设计考量段）**：AT 把"事务日志"从数据库引擎层（redo/undo，16_mysql.md 4.1.1）**上提到了应用数据层**——它记录的不是物理页改动而是**行级逻辑快照**，所以能跨连接、跨本地事务做逻辑撤销；代价是一阶段的读写放大（2.2.2）与对"行可精确定位"的强要求（表必须有 PK/UK，2.2.1）。

**易错**：① "AT 二阶段提交是执行 commit"——是**清理 undo_log**；② "AT 完全无侵入"——业务代码无侵入 ≠ 架构无侵入：DataSourceProxy、undo_log 表、TC 依赖、SQL 约束（2.2.1）都是隐形侵入；③ 把 undo_log 说成 MySQL 的 undo——两套东西，一个是 InnoDB MVCC 的引擎内部版本链（3.1.3），一个是 Seata 的应用层表，别在面试里握手。

### 2.1.2 全局锁是什么？防的不是脏读，到底防什么？

**先排除误解**：全局锁不防并发读写（那是本地锁与隔离级别的事，16_mysql.md 3.1.2/3.2.1），它防的是**两个全局事务写同一行的交叉回滚**——

```text
无全局锁的灾难：
全局事务A：改库存 100→99（一阶段已本地提交，等全局裁决）
本地事务B（或另一个全局事务）：把同一行 99→98 并提交
此时 A 被判回滚：按快照把行恢复成 100 —— B 的 98 被抹掉，
   B 的业务"已提交成功"从此蒸发 = 脏写/丢失更新，比脏读严重一个量级
```

**机制**：**写隔离靠全局锁串行化**。分支一阶段本地提交前，先向 TC 申请该分支**改动到的每一行**（按 PK/UK 定位）的全局锁；拿到才提交，拿不到（有别的分支持有——其他全局事务的在途分支、或自己前一个全局事务）就**重试等待**，超时则本分支回滚重试；锁持有到**全局裁决完成**（提交=清 undo_log 时释放，回滚=补偿完成后释放）。本质是"**本地锁管一个本地事务周期，全局锁管一个全局事务周期**"。

**三个工程推论（这题的分水岭在这）**：
1. **全局锁只在中间态窗口内碍事**：全局事务一旦裁决，锁即释放——短事务低争用时几乎无感；但同一行被高频卷进全局事务（库存热点行）时，全局串行把吞吐钉死（解法见 2.2.2 的热点账）；
2. **它挡不住"不速之客"**：全局锁只对**经过 Seata 代理的写**生效——没被代理的本地写库、其他应用的直连、DBA 手改，都不查这把锁（一阶段提交后本地锁已放，数据在中间态是"裸"的）；事后发现被绕过 → after image 校验拒绝回滚（2.1.1），这是**最后一道防线而不是预防**——写权限收敛与入口收编才是预防；
3. **实现位置在 TC**：db 存储模式下是 `lock_table` 的行（唯一索引充当闩锁），file 模式下是 TC 进程内存 map（5.2.1 的存储选型账在此汇拢）；死锁场景——两个全局事务交叉持锁互相等待（AB-BA），Seata 没有强检测器，靠**全局超时**（默认 60s，1.2.1）把一对死锁一起杀（对比 16_mysql.md 3.2.3 本地死锁的自动检测，机制差异是常见追问）。

**易错**：把全局锁说成"分布式锁"然后被追问 Redis 锁的区别——它的粒度是**行级、按数据版本语义设计、由事务框架自动加放**，和 27_redis.md 4.1.1 那种"临界区互斥"的业务锁是两条物种线；答题点一句"全局锁防的是回滚踩踏，不是临界区并发"即回身位。

### 2.1.3 AT 提供什么隔离级别？"读脏中间态"有哪几种解法？

**先把概念分层**：Seata 讨论的是**全局隔离**——全局事务之间（以及全局事务与非 Seata 并发操作之间）可见到什么程度；数据库自己的 RC/RR 隔离（16_mysql.md 3.1.2）仍在本地层照常工作，两层各自记账。

**默认档位：全局读未提交**——注意这不是 ANSI 那个 RU 的复刻，而是 AT 设计的**直接推论**：一阶段本地已提交，其他任何连接当然读得到这行中间态；全局事务之间写已串行（全局锁，2.1.2），读不互斥。**窗口有多大**：一阶段提交 → 全局裁决完成，通常几十毫秒~秒级；低峰期无感，高并发长事务链下"读到将回滚的数据"真实存在（下游拿脏数据做了决策=业务级事故）。

**四种解法按代价排（这题的主体）**：
1. **接受它**：读的业务语义能容忍瞬时脏（如统计、非资金校验）——默认档即合理；
2. **`SELECT FOR UPDATE` 升全局读已提交**：AT 拦截这类悲观读——**先查该行是否被在途全局事务持有全局锁**，有则等待/重试（与写共享同一把全局锁，读写在中间态窗口内互斥），无则读最新已提交数据——写路径带锁读（业务本来就悲观，16_mysql.md 3.2.4 的扣减姿势）时零额外心智；
3. **`@GlobalLock` 注解 + 本地事务**：只读方法标注后不注册分支、不开全局事务，仅让普通 SELECT 也走全局锁校验——给报表/查询服务用的"轻量读增强"（代价：每个带注解的读都可能被中间态拖等，别给高 QPS 查询默认加）；
4. **业务状态位（实践中最常用）**：中间态行带业务状态（"处理中"），对外接口只暴露终态——把隔离问题翻译成状态机问题；Seata 管数据原子性、状态位管业务可见性，两者不互斥且后者常常才是正解（Saga 的中间态治理同款思路，4.1.2）。

**顺带两条周边纪律**：DB 隔离级别层面，团队常规把业务库跑 **RC**——RR 的 next-key/gap 锁（16_mysql.md 3.2.2）会让一阶段快照与本地锁冲突面变大，而 Seata 的全局锁本来就是行级（按 PK/UK），RC 语义下更干净；另外"全局事务内的自己人"读自己的分支改动天然可见（本地早已提交），不存在读自己写的问题。

**收口句**：AT 的隔离性题眼就一句——"**写靠全局锁串行，读默认放行；要读不脏，要么借全局锁（for update/@GlobalLock），要么别在数据层谈可见性，在业务状态层谈**"。

## 2.2 使用边界与成本

### 2.2.1 AT 模式的使用坑与硬性约束有哪些？

**约束不是可选风格，违反=功能失效或事故，逐条给"为什么"**：

1. **表必须有 PK 或唯一键**：快照按主键/唯一键定位行、全局锁按它建行锁（2.1.2）——无 PK 表（常见于历史宽表、日志表）**无法用 AT**（不能可靠定位"我改了哪几行"），迁移方案：补自增主键，或该资源改走 TCC/Saga；复合唯一键同样可用；
2. **UPDATE/DELETE 的 WHERE 必须走索引且精确圈定行**：一阶段要"改前先查、改后再查"（2.1.1 ②③）——无索引条件 = 两次全表扫描 + 快照集爆炸；官方姿势甚至建议带主键/唯一键更新；**`UPDATE ... WHERE 1=1` 式批量更新是 AT 的性能核弹**（锁住成排全局锁，别人全在等）——改批处理为分批 + 精确条件；
3. **SQL 支持面有边界**：DDL 不参与全局事务（**事务进行中的 schema 变更会让快照解析错位**，大表 DDL 走 16_mysql.md 5.1.1 的 Online DDL/gh-ost 纪律并避开流量窗口）；复杂语句（多列子查询更新、join update 等）支持度随版本变化——**以所用版本的 SQL 支持清单为准**，上线前对新写法做冒烟；
4. **写入必须全走代理**：绕过 DataSourceProxy 的写=脏写风险 + 回滚被校验拒绝（2.1.2 推论 2）——同库的其他服务、定时任务、DBA 脚本都要收进清单；
5. **undo_log 必须建在每个业务库**（与业务表同库同事务，2.1.1 ⑥ 的原子性前提）；多数据源服务要每个都建；表膨胀监控（4.x 的清理任务/回滚卡住时积压，5.2.2）；
6. **分支内不要再嵌"本地提交依赖"**：一阶段提交即生效，分支方法里的**缓存更新/发 MQ** 等副作用在回滚时**不会**被撤销（回滚只恢复数据库行）——"AT 回滚撤销一切"是错觉，副作用要么挪到裁决后（监听全局提交事件，较新版本有事务钩子/事件机制，报得出即加分），要么设计成可容忍脏触发（幂等消费 + 状态校验）；
7. **嵌套与传播**：`@GlobalTransactional` 默认 REQUIRED（加入当前 XID），需要"新全局事务"的场景用 Propagation 的 REQUIRES_NEW 类语义（枚举与默认值以版本文档为准）；AOP 老毛病同样适用——**同类自调用不过切面、异常被 catch 咽掉就不回滚**（与 7_spring.md 事务代理同源，Spring 事务的坑在 Seata 上原样再踩一遍）。

**支持库清单（2026 官方口径）**：MySQL、Oracle、PostgreSQL、MariaDB、TiDB、达梦、PolarDB-X 2.0、SQLServer 等（DB2 开发中）——面试报"MySQL/Oracle/PG + 国产与分布式库都在演进，以官网为准"即可。

### 2.2.2 AT 的性能账怎么评估？热点行怎么破？

**单笔分支的增量成本清单**（相对"无 Seata 的同一笔本地事务"）：

| 项 | 量级 | 备注 |
|----|------|------|
| before/after image 两次查询 | 2 次索引读（与业务 SQL 同本地事务） | WHERE 精确主键时近乎免费，否则放大（2.2.1 约束 2） |
| undo_log 插入 + 快照序列化 | 1 次写 + CPU | 快照含两个镜像，宽表/大字段成本高（TEXT/BLOB 大行慎用 AT） |
| 全局锁申请 + 分支注册 | 1 次到 TC 的 RPC（合并优化后） | 内网同机房毫秒级；TC 跨机房部署时这笔 RT 直接进每一笔事务 |
| 二阶段提交 | 异步，不占用户 RT | 但占 TC/DB 后台资源 |

**定性结论**：低争用场景下 AT 单分支开销在**毫秒级、吞吐折损可控**（官方与社区压测长期给出的量级印象，具体数字以你自己的基准测试为准——**面试永远报"我怎么测"而不是"官网说几"**）；真正决定 AT 生死的是两个二阶变量：**全局锁争用**与**TC 网络距离**。

**热点行账（AT 的能力天花板，必考）**：秒杀扣库存这类"单行高并发卷入全局事务"场景——全局锁把并行度强行压成串行（2.1.2），**吞吐上限≈单行锁的排队速率**，比本地行锁竞争还多一层 RPC 往返。三条破法（按改造深度）：
1. **让热点离开全局事务**：库存预扣/回补改用 TCC 的"冻结字段"语义——冻结 100→扣减 95→回补 100，并发下各冻各的额度，互不等锁（3.1.1/3.1.3）；或 Redis 原子计数 + 异步落库对账（27_redis.md 4.2.2 的计数器 + 13_rocketmq.md 2.3.1 的一致性兜底）；
2. **拆行摊热点**：单行库存拆 N 行子库存、按请求路由到不同子行（全局锁不再同一条）——22_sharding_sphere.md 的分片思想在同库内的投影；
3. **缩窗口**：热点资源的操作从长全局事务里**摘出来单独成短事务**（裁决更快=锁持有更短，1.2.1 的窗口账）。

**工程优化清单（收尾用）**：TC 与应用同机房部署 + 长连接复用（Netty 到 TC 的连接池化，SDK 内置）；事务粒度最小化（只包住必须原子的写，读与副作用挪出边界，2.2.1 约束 6）；批量写合并成分支内少量精确 SQL（反例见 2.2.1 约束 2）；大事务拆分（一个全局事务挂 50 个分支的长链条，回滚代价与超时风险都指数涨，5.2.2）。

**易错**：把"AT 比本地事务慢 5%"这类流传数字当圣旨——开销是**结构性清单**（上表）不是常数，热点场景下锁排队才是主项；答题报得出"成本构成 + 热点破法"远胜报百分比。

# 3. TCC 模式

## 3.1 TCC 机制与选型

### 3.1.1 TCC 的三个阶段各做什么？和数据库 2PC 是什么关系？

**一句话定性**：TCC 是**应用层的两阶段提交**——把"资源预留"从数据库行锁上提到**业务语义**（冻结字段/状态位），协调者仍是 Seata TC，但一阶段"prepare"的内容由你自己定义。

**三个阶段**（一次扣库存资金操作）：

```java
@TwoPhaseBusinessAction(name = "deductStockAction",
        commitMethod = "confirm", rollbackMethod = "cancel")
public interface StockTCCAction {
    // Try：校验 + 预留——可用库存 100 → 冻结 20（total=100, freezed=20）
    // 业务改动本地提交；@BusinessActionContextParameter 把关键参数塞进 actionContext 带给二阶段
    boolean tryDeduct(@BusinessActionContextParameter(paramName = "skuId") Long skuId,
                      @BusinessActionContextParameter(paramName = "count") Integer count);
    // Confirm：真扣——freezed 20 → deducted（Try 成功者由 TC 远程驱动调用）
    boolean confirm(BusinessActionContext ctx);
    // Cancel：释放预留——freezed 归还（Try 失败/其他分支失败时 TC 驱动）
    boolean cancel(BusinessActionContext ctx);
}
```

**与 2PC（及 XA，4.2.1）的血缘与分歧**：

| 维度 | DB 2PC/XA | TCC |
|------|-----------|-----|
| 预留的形态 | **行锁 + 挂起的事务**（资源被数据库扣住） | **业务字段/状态**（数据库照常提交，锁与连接即刻释放） |
| 参与者粒度 | 数据库连接/资源管理器 | 任意服务接口（DB、缓存、MQ、HTTP 第三方都能"参与"） |
| 隔离效果 | 由 DB 隔离级别保证 | 由**业务设计**保证（冻结数据对其他业务可见=自定义隔离级别） |
| 二阶段失败 | 悬挂事务靠 XA RECOVER | Cancel/Confirm 靠**重试 + 幂等**（3.1.2） |
| 成本 | 业务零侵入、性能差 | 业务高侵入、性能好且可控 |

**为什么 Confirm/Cancel 必须设计成幂等**：TC 到分支的 RPC 超时后**会重试**（裁决不能丢）——"调了两次 confirm 扣了两次钱"的系统不配叫分布式事务。幂等判定靠 actionContext 里的 (xid, branchId) + 业务状态（细节即 3.1.2 三座大山的地基）。

**易错**：把 Try 理解成"开启事务不上锁"——Try 的核心动作是**把资源划进"已预订未成交"的业务分区**并本地提交；"Try 只校验不占用"的系统在并发下会超卖（校验通过的瞬间别人也校验通过）——**预留必须落成数据，这是 TCC 的第一性原理**。

### 3.1.2 幂等、空回滚、悬挂这三座大山为什么会发生？fence 机制怎么自动化解决？

**三座大山共同根源一句话**：TC ↔ 分支之间的网络**不保证不丢、不保证不重、不保证有序**——于是每个异常剧本都以"某个方法在不该出现的时候出现了"呈现。逐个拆（时间线都发生在 Try/Cancel 竞走的网络上）：

1. **重复提交/回滚（幂等诉求）**：confirm 请求送达、执行成功、响应丢——TC 超时重试 confirm 再至。解法：以 (xid, branchId) 为幂等键，二阶段动作前先查"做没做过"，做过直接返回成功；
2. **空回滚（empty rollback）**：try 请求在网络上丢了/迟迟未到，但 TC 视角 Try 超时 → 判全局回滚 → **cancel 先到**。此时没有任何预留可释放——cancel 必须认出"这是一个没有 try 的回滚"，标记成功返回，而不是报"找不到冻结记录"异常（异常会引发无限重试）；解法：cancel 落一条"已回滚"状态记录；
3. **悬挂（hanging）**：cancel（空回滚）完成后，**姗姗来迟的 try 才到达**——若照常执行，预留资源再无人释放（TC 认为这个分支早已回滚完毕），资源永久泄漏。解法：try 执行前查"该 xid+branchId 是否已被回滚标记"，是则拒绝执行。

**可见三座大山的共同结构**：都需要一张**记录事务边界状态的屏障表**（fence/屏障日志：xid、branch_id、action_name、status：Try 收到/Confirm 成功/Cancel 成功）——每个阶段执行前判表、执行后写表，状态迁移天然幂等，cancel 先至被记录后 try 可判悬挂。**手写要点**：判表与业务动作要在**同一个本地事务**里（否则屏障与业务状态漂移）。

**框架化现状（时效口径）**：Seata 较新版本内置 **TCC fence 机制**——业务库建 `tcc_fence_log` 屏障表，`@TwoPhaseBusinessAction(useTCCFence = true)` 开启后，幂等/空回滚/悬挂由框架在代理层自动判定处理，业务只写三个方法本体（具体开关属性与表结构以所用版本文档为准；该机制 1.5.x 引入、2.x 持续完善）。**面试的正确姿势**：先讲清三座大山的产生机理（这是能力证明），再补一句"现代版本用 fence 表把这层模板代码框架化了，但屏障表本身多一次读写、且要求表与业务同库同事务——理解原理仍是排查的前提"。

**业务设计侧的两条补充纪律**（fence 管不到的部分）：
- **预留资源的时效性**：冻结的库存/金额要有"预订超时自动释放"的兜底任务（全局事务被杀、Cancel 一直失败的最终防线——与 5.2.2 的对账同源）；
- **Try 失败要快速失败**：校验不通过直接抛业务异常（让 TM 尽早裁决回滚），不要"软Try"——拖长中间态窗口等于放大三座大山的发作概率。

**收口句**："三座大山不是 Seata 的缺陷，是**网络重试语义在业务接口上的投影**——谁手写二阶段接口谁踩一次；屏障表 + 幂等 + 状态判定的三板斧在任何自研 TCC 里都得原样存在。"

### 3.1.3 TCC 和 AT 怎么选？能混用吗？

**把 2.2.2 热点账与 3.1 侵入账并排看**，选择其实是被场景推着走的：

| 决策因子 | 倾向 AT | 倾向 TCC |
|----------|---------|----------|
| 开发预算 | 快交付、资源是标准 CRUD 表 | 核心链路允许养三个接口 + 状态设计 |
| 争用画像 | 行级冷数据（订单明细、流水记录） | **热点资源**（库存、账户余额、券、广告预算）——全局锁串行受不了（2.1.2/2.2.2） |
| 隔离要求 | 默认全局 RU + 增强够用（2.1.3） | 要"冻结即不可用"的业务级隔离——预留语义自己定义 |
| 资源类型 | 受支持的关系库（2.2.1 清单） | **非 DB 资源**：Redis 预留、MQ 通知、第三方预占接口 |
| 回滚代价 | 接受快照恢复的校验失败风险（5.2.2） | 接受 cancel 失败靠重试+对账 |

**经验配比（生产常见形态）**：一个业务域里**少数热点服务用 TCC、大量普通服务用 AT、异步尾巴交给消息**——三者靠同一个 XID 挂在同一个全局事务下。

**混用是被官方支持的设计**（"AT + TCC 混合模式"长期在功能清单首页，官网原文 "TCC mode... and mix with AT for greater flexibility"）：TC 不关心分支什么模式，RM 按资源类型分别驱动——同一个全局事务里订单表走 AT、库存走 TCC 完全成立。**易错**：担心"混用会不会互相不认识"——认识的，XID 就是通用货币（1.1.2）。

**答题收口**：选型题报三轴——**侵入预算、热点程度、资源类型**；再补一句"边界之外还有 Saga（长流程，4.1）与 XA（强隔离低并发，4.2）"即闭环（总表见 5.1.1）。

# 4. Saga 与 XA

## 4.1 Saga 长事务

### 4.1.1 Saga 的状态机怎么驱动正向执行与反向补偿？

**模型渊源一句**：Saga 是 1987 年数据库界为"长事务"提出的论文方案——把全局事务拆成一串**各自本地提交的子事务 T1..Tn，配一串补偿动作 C1..Cn**；失败时从断点**逆序执行补偿**（T3 失败 → 执行 C2、C1）。Seata Saga 是其在微服务上的工程化：**状态机引擎编排**路线（不是靠事件各服务自发接力，4.1.2 有对比）。

**与 AT/TCC 的结构差异（先立骨架）**：**没有 Try/预留**——每个步骤直接执行真实业务并本地提交（一阶段即终态写入），"回滚"是**语义补偿**（下单成功→发"取消单"把状态推回，而不是删记录）；也**没有全局锁**（2.1.2 的串行成本为零，这是它对长链条的胜任原因）。

**Seata 实现三件套**：
1. **状态机定义**（JSON DSL，官方有可视化 Saga Designer）：`ServiceTask`（正向服务）+ `Choice`（分支）+ `CompensateState` 等元素；每个正向任务配 `compensateState`（补偿服务名）；支持重试配置（`retry`/`catch`/超时）、输入输出映射（`InputMappings/OutputMappings`）、状态终态声明（成功/失败终态）；定义可放应用资源文件，也可存数据库表 `state_machine_def`（控制台热发布——**改流程定义不用发版**，这是编排引擎的产品价值）；
2. **状态机引擎（嵌在发起方应用）**：`engine.startMachineById(...)` 驱动逐步执行；每步经 RPC 调用服务（XID 照常透传，1.2.2）；**执行实例与状态落库**（`state_machine_inst`/history 类表，在发起方业务库）——崩溃后由恢复/重试调度继续推进，补偿链不断；
3. **补偿语义细节**：正向可配"失败即重试 N 次再走补偿"（forward 策略）；补偿服务同样要求**幂等 + 容忍空补偿 + 防悬挂**——和 3.1.2 同族问题换了马甲（补偿在断点之后被异步驱动，乱序与重投概率更高），答题点一句"三座大山在 Saga 的补偿接口上同样成立"即显贯通。

**时序对照（把"没有一阶段"说准）**：

```text
正常：T1✓本地提交 → T2✓本地提交 → T3✓本地提交 → 全局完成（用户视角异步结束）
失败：T1✓ → T2✓ → T3✗（重试后仍败） → C2（撤销T2的效果） → C1 → 全局补偿完成
       补偿链某步持续失败 → 实例状态滞留 + 告警 + 人工（4.1.2 运维面）
```

**易错**：把 Saga 说成"低一致性所以不能用"——它的正确定位是**中间态窗口长的业务**（本来就是"部分成功后退货"语义的场景：旅行订单、跨机构转账对账），窗口被业务状态位遮掩后用户无感（4.1.2）。

### 4.1.2 Saga 适用什么场景？长事务与中间态怎么治理？

**适用画像（三个特征命中两个就该考虑 Saga）**：
1. **链路长/参与方多**：七八个服务串一条流程（下单→风控→库存→物流→开票），AT/TCC 的全局锁或预留资源会陪跑全程——Saga 每步本地提交、零占用；
2. **参与方不受控**：外部机构/遗留系统只有正向+撤销两个 API（银行冲正、供应商取消单）——塞不进 Try/Confirm 的三段式，正好对上"服务 + 补偿"的两段式；无 Seata 集成的 HTTP 三方也是它（1.2.2 断链表）；
3. **流程本身是业务对象**：审批流、理赔流——改流程 = 发状态机定义（4.1.1 控制台热更），比改代码发布便宜一个量级。

**中间态治理（Saga 真正的工程难度所在）**：
- **状态位是唯一的可见性盾牌**：全局未完成时业务实体状态是"处理中/冻结中"，对外 API 与报表只认终态——**数据已提交但结论可能被补偿**是 Saga 的默认世界观（4.1.1），"补偿不可见"靠业务语义设计而非框架；
- **补偿的不对称性要提前谈崩**：T2 扣了券、C2 还券时"已过期/被占用"怎么办？**补偿≠回滚，业务上常只能"尽力恢复 + 差异走人工"**——跨机构场景这条写进接口协议比写进代码重要（对账文件、差错池）；
- **超时与推进节奏**：步骤级超时、全局超时、重试次数都在状态机定义里显式声明（默认值随模板走，评审流程定义时逐条过）；长流程"卡在中途"是常态——实例表按状态扫的**卡单工作台**（人工推进/强制补偿）是 Saga 上线必备件，框架只保推进不保业务正确；
- **并发语义自查**：同一实体的多个 Saga 实例并行（同订单两次退款流程）时没有全局锁替你把关——**业务唯一键 + 状态机版本检查**（乐观锁思路，16_mysql.md 3.2.4）自己补上。

**编排 vs 编舞（概念追问位）**：Seata Saga 是**编排**（central engine 掌握全流程）；纯事件驱动的"编舞"式长事务（各服务听事件自行接力）没有中央状态机、追踪靠链路系统——可维护性随步数指数恶化。**微服务长流程选编排、简单扇出选消息**（13_rocketmq.md 2.3 家族），"Saga 还是事件"多数时候是"这条流程需不需要被当成一个可查询、可干预的对象"。

## 4.2 XA 模式

### 4.2.1 XA 模式的原理是什么？和 AT 怎么选——什么时候值得为强隔离买单？

**机制**：Seata XA 模式 = **把数据库自己的 2PC 用 TC 串起来**——一阶段执行业务 SQL 后调 JDBC `XAResource.prepare()`（数据库把事务挂起：行锁持有、binlog 写满但标记 NOT YET COMMITTED，16_mysql.md 4.2.2 的组内兄弟 4.2.3 的"双 1"账在这多算一遍全局 RT）；二阶段 TC 裁决后各分支 `commit()/rollback()`——**没有 undo_log、没有快照、没有全局锁**（本地锁本来就还没放，2.1.2 的活数据库干了）。

**代价结构（三个"一直"）**：
1. **数据库连接被事务全程占用**（prepare 到 commit 期间连接不能归还池）——连接池是本地事务模型下按"事务毫秒级"设计的，全局事务秒级时**池饥饿**是最先撞的墙（18_feign.md 3.1.2 的池账在 DB 侧重演）；
2. **行锁一直持有**：锁等待与死锁面从本地窗口拉长到全局窗口（16_mysql.md 3.2.3 排查复杂度 ×N）；
3. **prepare 的持久化成本一直在**：双 1 配置下每个分支一阶段一次全量 fsync，二阶段再来一次 commit fsync——组提交的余量被跨 RPC 的裁决节奏吃空（16_mysql.md 4.2.3）。

**收益**：**全局 ACID 名实相符**——中间态对其他事务不可见（prepare 未提交），隔离级别由数据库保证，无 AT 的全局 RU 烦恼（2.1.3）、无绕过写风险敞口（脏写由本地锁挡到裁决完成，2.1.2 的"不速之客"在 XA 这里进不来）；业务代码同样零侵入。

**XA vs AT 对照收口**（官方口径就是"高一致性/高隔离 + 低并发选 XA"）：

| 因子 | AT | XA |
|------|----|----|
| 隔离 | 全局 RU + 增强（2.1.3） | DB 级强隔离，无中间态可见窗口 |
| 脏写防护 | 全局锁 + 事后校验 | 本地行锁扛全程 |
| 资源占用 | 一阶段即释放连接与锁 | 连接与锁持有到裁决 |
| 并发容量 | 中高（热点另议，2.2.2） | 低——TPS 天花板≈锁窗口 × 行争用 |
| 悬挂风险 | 回滚失败人工（5.2.2） | **prepared 悬挂**：TC 失忆/崩溃后需 `XA RECOVER` 对账清理（DBA 工具流程，重启后 TC 按存储的会话恢复决策，5.2.1 db 存储的意义在此） |

**选型一句话**：资金账务级、并发不高、参与库支持 XA（MySQL/Oracle/MariaDB 家族，官网清单）→ XA；一般业务要吞吐 → AT。**易错**：说"XA 是强一致所以优于 AT"——一致性强度与可用性/吞吐是光谱两端（34_distributed_theory.md 的 CAP 权衡在此的具象），**"优"取决于你付得起哪种故障**：XA 付的是容量，AT 付的是窗口期脏读与回滚失败的人工。

**追问预备**："MySQL 的 XA 有什么历史坑"——5.7 及之前 XA prepare 崩溃后恢复依赖 binlog 与 `XA RECOVER` 手工链、主从复制对 XA 事务的传递有约束（8.0 显著改善）——报"历史上有、8.0 后收敛、用前对版本"的三段式即可，不展开成 DBA 课。

# 5. 选型与运维

## 5.1 全景选型

### 5.1.1 AT、TCC、Saga、XA 四种模式怎么选？

**总表**（四轴来自 2.2/3.1/4.1/4.2 各题的论证，这里是合并判决）：

| 维度 | AT | TCC | Saga | XA |
|------|----|----|------|----|
| 业务侵入 | 零（接数据源+约束，2.2.1） | 高（三接口+状态+fence/屏障，3.1.1） | 中（正向+补偿成对、流程定义，4.1.1） | 零（同 AT，DB 需支持 XA） |
| 全局隔离 | 默认全局 RU，可增强（2.1.3） | 业务自定义（预留可见性自己设计） | 弱——中间态已提交，靠状态位遮蔽（4.1.2） | 强（DB 保证，无中间态窗口，4.2.1） |
| 资源类型 | 受支持的关系库 | **任意**（DB/缓存/MQ/第三方预占） | 任意（HTTP 服务皆可编排） | 支持 XA 的库（MySQL/Oracle/MariaDB） |
| 性能画像 | 中高；热点行被全局锁串行（2.2.2） | 高（预留并行，无全局锁） | 高并发无压力，但终态慢（长链条） | 低（连接+锁持到裁决，4.2.1） |
| 事务时长适配 | 短（毫秒~秒） | 短~中 | **长**（分钟~天，状态机持久推进） | 短（持锁成本随时长线性涨） |
| 失败语义 | 快照自动补偿（校验防脏写） | Cancel 重试+幂等（三座大山） | 逆序业务补偿+人工卡单台 | DB rollback / XA RECOVER 悬挂清理 |
| 典型场景 | 通用 CRUD 微服务改造、快交付 | 库存/额度/券等热点核心链路 | 跨机构、审批流、遗留系统串联 | 账务强一致 + 低并发 |

**判决树（答题主线，比表更值钱）**：
1. **要不要立刻拿到全局结论？** 不要 → 出 Seata 区，走事务消息/本地消息表（5.1.2）；
2. 要，且参与资源**有可预留的业务语义 + 是热点/非 DB** → **TCC**；
3. 要，资源是标准关系库 → 再看并发与隔离：**高并发争用普通行 → AT；强隔离低并发（资金记账）→ XA**；
4. 链路长/跨组织/参与方不可控 → **Saga**；
5. 同域内**混用合法且常见**（3.1.3）：订单 AT + 库存 TCC + 物流 Saga 挂同一个 XID。

**收口补一句架构观**：模式选型的上一层是**域设计**——拆得好的一大部分服务根本不需要全局事务（15_spring_cloud.md 1.2.3），Seata 的四种模式解决的是"拆完仍然跨不开"的那一小撮。

### 5.1.2 Seata 和事务消息、本地消息表怎么分工？"最好的分布式事务"是什么？

**先立决策轴：调用方是否需要同步拿到一致性结论**——这条轴切出两个世界：

| | Seata（同步协调系） | 事务消息/本地消息表（异步最终一致系） |
|--|---------------------|--------------------------------------|
| 语义 | 调用返回时全局已裁决（提交或已补偿） | 本地事务与"通知下游"原子绑定，下游何时完成不在返回路径上 |
| 一致性窗口 | 毫秒~秒（模式各异，2.1.3/4.1.2） | 秒~分钟（13_rocketmq.md 2.3.1 半消息+回查的收敛节奏） |
| 耦合 | 强：TC、各分支同步在线、超时预算全链对齐 | 弱：下游挂了消息堆积，恢复后追平（13_rocketmq.md 3.3.2） |
| 失败处置 | 框架自动补偿（AT 快照/TCC cancel） | 消费重试+死信+幂等（13_rocketmq.md 3.2 家族） |
| 典型误配 | 给纯通知型动作套 @GlobalTransactional（多养 TC 依赖、拉长 RT） | 给"必须立刻成功否则整单失败"的动作套消息（用户看到成功、库存实际没扣） |

**分工句式（把两类缝起来的标准答案）**：**主链路同步协调、旁路异步扇出**——下单核心（订单+库存+券）要同步裁决用 Seata；下单成功后的积分/推送/风控留痕用事务消息（那是"派生业务"，通知语义不是协调语义，3.2 轴）。两者可以同场：Saga 步骤执行后发消息扇出、AT 分支提交后由监听钩子投递（2.2.1 约束 6 的副作用治理位）。

**本地消息表的定位**：与事务消息同族解、不依赖特定 MQ（13_rocketmq.md 2.3.2 已对比）——对 Seata 的关系是**替代下游扇出段**而非替代全局事务本体。

**"最好的分布式事务是少用/不用"的完整论证**（这题的高分段，分三层）：
1. **设计层**：按聚合根拆库，让 90% 业务动作落回单库本地事务（15_spring_cloud.md 1.2.3 的数据所有权纪律）——跨服务改动要么合并聚合、要么事件驱动重划边界；
2. **语义层**：区分"协调"与"通知"——通知一律异步化（消息家族），协调只留真正原子的那一小撮给同步框架（5.1.1 判决树第 1 步）；
3. **兜底层**：真用了 Seata，也要承认补偿可能失败（5.2.2）——**业务对账与人工工作台是体系的最后一环，框架只是把到达概率拉到很高，不是把概率做到 1**。

**易错**："上了 Seata 就强一致了"——AT 默认隔离连脏读都不挡（2.1.3），Saga 中间态本质是最终一致（4.1.2）；**Seata 是"自动补偿的协调框架"，不是分布式 ACID 魔法**，这句收口放结尾。

## 5.2 部署与实践

### 5.2.1 seata-server 怎么部署？客户端怎么找到 TC？存储模式怎么选？

**部署骨架**：TC 是**无业务状态**的状态机进程（全局/分支/锁状态全在外部存储，见下）——多实例 + 注册中心即集群水平扩展；**事务协议端口 8091**（客户端 Netty 长连接）与**控制台端口 7091** 都要通防火墙（漏开 8091 的症状=应用启动正常、开全局事务即连不上 TC——17_nacos.md 9848 之坑的 Seata 复刻，接入检查清单第一条）。

**客户端定位 TC 的两跳**（配置题的核心）：

```yaml
seata:
  enabled: true
  application-id: order-service
  tx-service-group: order-tx-group          # ① 本应用的事务组名（默认取应用名，建议显式）
  service:
    vgroup-mapping:
      order-tx-group: default               # ② 组名 → TC 集群名
    grouplist:
      default: 10.0.0.9:8091                # ③ 集群名 → TC 地址（不用注册中心时手写）
  registry:
    type: nacos                             # ③' 或用注册中心发现 seata-server 集群（17_nacos.md）
  config:
    type: nacos                             # TC 侧配置也统一走配置中心（5.2.2 动态调参的通道）
```

- **经典事故**：`service group 'xxx' could not be found`——tx-service-group 与 vgroup-mapping 键不一致（大小写/环境前缀漂移），或映射的集群名在注册中心查不到 seata-server 实例；多环境共用注册中心时 TC 集群名没隔离（namespace 纪律同 17_nacos.md 4.1.1）；
- 组这层抽象的用意：**应用与 TC 集群解耦**——迁移/扩缩容 TC 只改映射，客户端配置不发版；一个 TC 集群服务多个 tx-group，一个 tx-group 只指向一个集群。

**存储模式四选**（TC 状态存哪，直接决定 HA 与性能上限）：

| store.mode | 形态 | 定位 |
|------------|------|------|
| file | 进程内存 + 本地文件 | 开发/单机压测；**TC 重启即失忆**——在途全局事务的裁决悬空（业务侧靠超时+对账收拾残局），严禁生产 |
| db | MySQL 等共享库（`global_table`/`branch_table`/`lock_table`） | **生产主流**：TC 实例间共享状态、任一实例可接管推进；TC 挂了重启即恢复会话；代价是状态读写过 DB（全局锁争用高时 db 模式 QPS 吃紧——锁表行竞争与索引纪律要盯，16_mysql.md 相关） |
| redis | TC 状态存 Redis | 借 Redis 的 HA 拓扑（主从+哨兵，27_redis.md 3.2.3）与更快读写；注意主从异步窗口的状态丢失风险按 27_redis.md 2.1.2/3.2.2 的口径评估——"状态可重放、业务不可重放"的差别要想清楚 |
| raft | TC 内嵌 Raft 自管复制（存算一体，自选举） | 免外部存储的新路线，**官网当前标注公测（beta）**——采用前按所用版本文档评估成熟度 |

**应用侧接入清单**（评审模板）：AT 的每个业务库建 `undo_log`（XA 无快照、不需要，4.2.1）；TCC 参与方库建 `tcc_fence_log`（开 fence 时，3.1.2）；Saga 发起方库建状态机定义/实例表（seata_saga 脚本，4.1.1）；数据源统一 DataSourceProxy（2.2.1 约束 4）；RPC 集成拦截器逐项核对（1.2.2 断链表反查）；客户端与 server 版本按官方兼容矩阵对齐（跨大版本协议不兼容是硬约束，报"升级前对版本矩阵"即可）。

**K8s 一句话**：TC 用 StatefulSet/Deployment + Service 注册进 Nacos 均可，注意**客户端到 TC 是长连接**——滚动升级 TC 要走优雅下线（连接排空，10_springboot.md 4.1.2 机制同态；32_kubernetes.md 的 preStop 纪律），硬杀 TC = 给 5.2.2 制造在途悬空。

### 5.2.2 Seata 上线后：性能瓶颈、故障剧本和运维体系各长什么样？

**先给故障矩阵（按"谁死了"组织，面试按这张表答最稳）**：

| 故障剧本 | 系统行为 | 你要做的 |
|----------|---------|---------|
| TC 单实例宕 | db/redis/raft 模式：其他实例继续推进已有会话，客户端重连换节点 | 无感；验证客户端重试日志 |
| TC 集群全灭 | **新全局事务开不出**（业务报异常，快速失败保护）；已一阶段提交的分支**悬在中间态**无人裁决 | TC 恢复后：db 模式按持久化会话自动续裁决（提交/回滚继续走）；file 模式=失忆，**中间态数据靠对账人工收敛**（5.2.1 严禁生产的原因在此兑现） |
| RM 二阶段失败：AT 回滚校验不过（after image ≠ 当前值） | 拒绝自动回滚 → 分支卡在回滚重试，全局会话挂"回滚中"（**rollback-undone 告警**） | 查绕过写源（2.1.2 推论 2），人工把该行数据与业务影响对齐后清理 undo/推进——**这是 AT 运维的头号剧本，值班手册必备** |
| TCC cancel/confirm 重试不收敛 | 屏障状态与业务状态漂移、资源永久冻结（3.1.2） | 预留超时释放任务 + 差错池；对账修数 |
| 分支服务全程不可用（Try 阶段失败） | 已提交的其他分支被全局回滚 | 正常路径；若回滚链也失败升级人工 |
| 全局超时（默认 60s，1.2.1） | TC 主动发起回滚 | 长链路要显式调 timeoutMills，**别拿默认值硬扛批处理** |

**性能瓶颈的三个已知位置（2.2.2 账目的运维版）**：
1. **全局锁热点行**——监控"分支 lock 等待/重试次数"与 lock_table 竞争；解法永远是"让热点离开全局事务"（TCC 冻结/Redis 计数/拆行，2.2.2 三板斧）而不是加大超时；
2. **TC 往返距离与频率**——每一分支两次 RPC 起步（注册+锁、裁决通知），TC 跨机房部署时 RT 结构性抬高：同机房 + 长连接复用，TC 容量按压测（它是状态机不是数据面，单机 TPS 通常远高于业务瓶颈，但**锁争用风暴**会把它打进排队，5.2.1 db 模式再叠一层 DB）；
3. **快照读写放大**——宽表/大字段/低选择度 UPDATE 让 undo_log 体积和解析成本失控（2.2.1 约束 2 的监控面：undo_log 增长率、清理滞后）。

**观测与告警体系（把"状态机"盯住的四组指标）**：
- **存量**：在途全局事务数与其年龄（> 超时 80% 预警）——TC 控制台/查询 API + 自采；
- **裁决质量**：回滚率、rollback-undone 数、二阶段重试深度——**回滚率突增=上游依赖出事的领先指标**；
- **锁健康**：全局锁等待时长/重试次数 TOP 资源（配合 27_redis.md 4.1.1 的业务锁监控同屏看，两层锁体系一张图）；
- **积压**：undo_log 存量与清理滞后、tcc_fence_log/saga 实例表滞留状态——**积压清单就是待人工清单**。

**预案与降级**：压测/大促前演练三件事——杀 TC 验恢复（db 模式）、杀分支验回滚链、热点接口验 TCC/消息切换开关；**应急总闸**：客户端可按应用停开新全局事务（配置开关 + 熔断，20_sentinel.md 思路），存量排空——"关新放旧"比硬切安全；对账任务长期在线（业务终态 vs 资源实况的差异扫描），它是所有补偿型系统共同的最后防线（5.1.2 兜底层）。

**收口句**："Seata 运维的本质是**盯一台分布式状态机**——正常时它比谁都能自愈，异常时它把'概率上的万一'变成'清单上的待办'：**在途、回滚失败、锁积压、表滞留四类指标常扫，对账与人工工作台常备**，这套纪律适用于四种模式的全部组合。"
