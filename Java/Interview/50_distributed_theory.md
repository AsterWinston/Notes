# 1. 知识点
- **CAP定理**: 分布式系统中，一致性(C)、可用性(A)、分区容错性(P)三者只能同时满足两个。C指所有节点在同一时刻看到相同数据；A指每个请求都能获得非错误响应；P指系统在任意网络分区(消息丢失)下仍能持续运行
- **一致性(Consistency)**: 所有节点在同一时间看到相同的数据，即读操作总是能读到最新的写入结果
- **可用性(Availability)**: 每个请求都能获得一个非错误的响应(不保证包含最新数据)，但不会超时或返回错误
- **分区容错性(Partition Tolerance)**: 系统在任意网络分区(部分节点间消息丢失或延迟)的情况下仍能正常提供服务
- **CAP取舍原则**: 网络分区不可避免(P必须选)，因此实际是在CP和AP之间做取舍，正常情况下可兼顾CA
- **ZooKeeper的CP特性**: 当发生网络分区时，ZK会从集群中移除半数以下节点所在的分区，这些节点不可用，保证了强一致性但牺牲了可用性
- **Eureka的AP特性**: Eureka优先保证可用性，网络分区时各节点仍可接受注册，等网络恢复后再进行数据同步，可能读到旧数据
- **Nacos的AP/CP切换**: Nacos支持AP和CP两种模式，服务注册发现默认AP模式，配置管理可选CP模式，通过临时实例和持久化实例区分
- **ZooKeeper不适合服务发现的原因**: 注册中心通常有大量服务实例(可达数十万)，ZK的CP特性导致网络抖动时大量节点不可用，且ZK不是为高频写入设计的
- **BASE理论**: 对CAP中AP方案的延伸，Basically Available(基本可用)、Soft State(软状态)、Eventually Consistent(最终一致性)，核心思想是牺牲强一致性换取可用性
- **基本可用(Basically Available)**: 系统出现故障时允许损失部分可用性，如响应时间变长、部分功能降级，但核心功能仍可用
- **软状态(Soft State)**: 允许系统中的数据存在中间状态，该中间状态不影响系统整体可用性，即允许不同节点的数据副本存在短期不一致
- **最终一致性(Eventually Consistent)**: 系统中的所有数据副本在经过一段时间的同步后，最终能达到一致的状态，不要求实时一致
- **强一致性**: 写入后任何读操作都能读到最新数据，等同于线性一致性，对系统性能影响大，实现复杂
- **弱一致性**: 写入后不一定能立即读到最新数据，系统不保证多长时间后数据能达到一致
- **因果一致性**: 有因果关系的操作按顺序被观察到，无因果关系的操作顺序无限制，是比最终一致性更强的一致性保证
- **会话一致性**: 在同一个会话(客户端与服务器的连接)中保证读写的一致性，不同会话之间可能不一致
- **单调读保证**: 客户端读到某个数据版本后，后续读不会读到更旧的版本
- **单调写保证**: 同一个客户端的写操作被顺序执行，保证写入顺序一致
- **线性一致性(Linearizability)**: 分布式系统最强的的一致性模型，所有操作看起来像是原子地在某个时间点全局顺序执行，等同于CAP中的C
- **Paxos算法**: 分布式共识算法的理论基础，通过Prepare和Accept两阶段提交实现分布式节点间达成一致，分为Basic-Paxos和Multi-Paxos
- **Basic-Paxos两阶段**: 第一阶段Prepare(Promise)，提议者发送提案编号获取承诺；第二阶段Accept，提议者在获得多数派承诺后发送提案值
- **Multi-Paxos**: 对Basic-Paxos的优化，通过选举出Leader减少Prepare阶段的次数，多轮提案复用同一个Leader
- **Raft协议**: 为可理解性设计的共识算法，包含Leader选举、日志复制、安全性三个核心部分，比Paxos更工程化
- **Raft Leader选举**: 节点以Follower启动，选举超时(Election Timeout)随机150-300ms后变为Candidate，向其他节点请求投票，获得多数票当选Leader
- **Term任期**: Raft中全局的逻辑时钟，每个任期最多一个Leader，Term必须大于等于自己的Term才接受请求，保证Leader的唯一性
- **Append Entries**: Leader将日志条目通过AppendEntries RPC复制到所有Follower，多数派(过半数)确认后提交(commit)该日志条目
- **Raft日志复制**: Leader发送AppendEntries，Follower检查prevLogIndex和prevLogTerm匹配后追加日志，确认成功后Leader推进commitIndex
- **Raft安全性**: 选举时Candidate的日志必须足够新(term更大或term相同index更大)才能成为Leader，已提交的日志不会被覆盖
- **Raft vs Paxos**: Raft将共识分解为独立的子问题(Leader选举、日志复制、安全)，更易于理解和工程实现；Paxos理论上更通用但难以工程化
- **脑裂处理**: Raft中旧Leader失联后新Leader当选，旧Leader重连后发现自身Term落后，自动降级为Follower，其未提交日志被新Leader覆盖
- **分布式CAP设计策略(CP)**: 保CP牺牲A，适用于对数据一致性要求高的场景，如ZooKeeper配置管理、分布式锁，网络分区时拒绝服务
- **分布式CAP设计策略(AP)**: 保AP牺牲C，适用于对可用性要求高的场景，如Eureka服务发现、DNS，网络分区时允许读取旧数据
- **一致性Hash**: 将整个哈希空间组织成环(0到2^32-1)，节点和数据都映射到环上，数据顺时针找到最近的节点存储，增删节点只影响相邻节点
- **虚拟节点**: 为每个物理节点创建多个虚拟节点分布在环上，解决一致性Hash中数据倾斜(热点)问题，节点数少时也能均匀分布
- **一致性Hash应用**: 分布式缓存(Redis集群)、分布式存储、负载均衡，减少节点变更时的缓存失效和迁移量
- **两阶段提交(2PC)**: 协调者第一阶段询问所有参与者是否准备好提交(Prepare)，第二阶段根据所有参与者的响应决定统一提交(Commit)或回滚(Rollback)
- **2PC问题**: 同步阻塞(所有参与者等待协调者决策时资源锁定)、单点故障(协调者宕机)、数据不一致(第二阶段部分提交成功)
- **三阶段提交(3PC)**: 在2PC基础上增加预提交阶段和超时机制，分为CanCommit、PreCommit、DoCommit三阶段，减少阻塞时间
- **3PC改进**: 引入超时机制，参与者在等待超时后可自动提交(前提是已收到PreCommit)，解决2PC的阻塞问题，但仍有数据不一致风险
- **2PC vs TCC**: 2PC作用于数据库层面(资源管理器)，TCC(Try-Confirm-Cancel)作用于业务层面，TCC更灵活但开发成本高
- **Seata与CAP**: Seata AT模式倾向于AP(最终一致性)，通过全局事务协调器和undo_log实现；TCC模式可由业务控制倾向于CP
- **幂等机制**: 相同的操作执行一次和多次产生相同的结果。实现方式包括数据库唯一键约束、token防重(Redis)、状态机约束等

# 2. 面试题

## 2.1 什么是CAP定理？为什么分布式系统只能三选二？
CAP定理由Eric Brewer在2000年提出。C(Consistency)指所有节点在同一时刻看到相同数据；A(Availability)指每个请求都能获得非错误响应；P(Partition Tolerance)指系统在网络分区时仍能正常运行。由于网络分区在分布式系统中不可避免(P必须选择)，实际选择是在CP和AP之间。ZooKeeper选择CP(网络分区时剔除半数以下节点保证一致性)，Eureka选择AP(网络分区时各节点仍可注册保证可用性)。Nacos支持AP和CP切换，满足不同场景需求。

## 2.2 BASE理论和ACID有什么区别？
ACID是传统关系型数据库的事务模型(原子性、一致性、隔离性、持久性)，追求强一致性。BASE理论(Basically Available基本可用、Soft State软状态、Eventually Consistent最终一致性)是分布式系统对CAP中AP的延伸，核心是牺牲强一致性换取可用性和性能。BASE适合大规模分布式系统(如电商、社交)，ACID适合金融等对一致性要求极高的场景。

## 2.3 ZooKeeper为什么不适合做服务发现/注册中心？
ZooKeeper是CP系统，当网络分区时(如ZooKeeper集群半数以下节点失联)，整个集群不可用。注册中心管理数十万服务实例，高频心跳和注册请求，ZK的写入性能有限。网络抖动导致ZK剔除节点后服务发现不可用，影响整个微服务体系。而Eureka(AP)在网络分区时各节点仍可独立工作，保证服务发现的可用性，更适合注册中心场景。

## 2.4 请解释Raft协议的Leader选举过程
1. 所有节点以Follower状态启动，每个Follower有随机选举超时时间(150-300ms)
2. Follower在超时时间内未收到Leader心跳，转为Candidate，Term+1，投票给自己
3. Candidate向其他节点发送RequestVote RPC，请求投票
4. 若获得多数派(过半数)选票，成为Leader，开始发送心跳(AppendEntries)
5. 若选举超时(多个Candidate平分选票)，Term+1重新选举
6. Leader通过定期心跳(AppendEntries)维持权威，Follower收到心跳重置选举超时

## 2.5 Raft如何保证日志复制的正确性？
Leader收到客户端请求后，将命令封装为日志条目，通过AppendEntries RPC并行发送给所有Follower。Follower检查日志条目的prevLogIndex和prevLogTerm是否匹配，匹配则追加日志。Leader在收到多数派确认后将日志条目标记为已提交(commit)，然后在响应客户端后异步通知Follower提交。Leader提交后才应用到状态机，保证已提交的日志最终被所有节点执行。日志匹配特性(Log Matching Property)保证相同index和term的日志有相同内容。

## 2.6 分布式系统中出现脑裂(Split-Brain)怎么办？
脑裂指网络分区导致集群中出现多个Leader。Raft解决方案：每个Term最多一个Leader，新Leader当选后Term递进。旧Leader(少数派分区)在重连后发现更高的Term，自动降级为Follower，其未提交的日志被新Leader覆盖。ZooKeeper通过半数以上机制，只有多数派分区能提供服务，少数派分区不可用。RedLock(红锁)要求超过半数Redis节点加锁成功，防止脑裂时多个客户端同时获锁。

## 2.7 一致性Hash是什么？虚拟节点解决什么问题？
一致性Hash将hash空间(0~2^32-1)组织成环形，节点和数据通过hash映射到环上的位置，数据顺时针路由到最近的节点。增删节点时只影响环上相邻节点间的数据(约1/n)，大幅减少缓存失效。但节点数少时数据分布不均匀(热点)。虚拟节点解决此问题：物理节点映射多个hash值(如每个节点150个虚拟节点)，虚拟节点均匀分布在环上，数据到达虚拟节点后实际存储到对应物理节点。

## 2.8 2PC和3PC有什么区别？
2PC两阶段：Prepare(询问所有参与者是否可提交，资源锁定但未真正提交) → Commit(所有参与者说YES则通知提交)。问题：同步阻塞(Prepare后一直等协调者)、单点故障(协调者宕机无法决策)、不一致(Commit阶段部分成功)。3PC三阶段：CanCommit(询问能否提交) → PreCommit(预提交，发送事务内容，参与者锁定但不提交) → DoCommit(最终提交)。改进：引入超时机制，参与者在等待DoCommit超时后若已收到PreCommit可自动提交，减少阻塞时间，但不能完全解决数据不一致问题。

## 2.9 TCC和2PC有什么区别？何时使用TCC？
2PC作用于数据库资源层(如XA事务)，由资源管理器实现，对业务透明但同步阻塞、性能差。TCC(Try-Confirm-Cancel)作用于业务层：Try阶段预留资源并检查；Confirm阶段确认执行业务(要求幂等)；Cancel阶段释放Try预留的资源(要求幂等)。TCC各阶段独立可异步化，性能更好，但需业务方实现补偿逻辑。TCC适合高并发、跨服务事务场景(如订单库存扣减)，2PC适合数据库层面的简单分布式事务。

## 2.10 请对比Paxos和Raft共识算法
| 维度 | Paxos | Raft |
|------|-------|------|
| 可理解性 | 理论严谨但难以理解 | 设计目标就是易懂，更直观 |
| 工程化 | 实际实现需大量优化(Multi-Paxos) | 天然工程友好，有标准实现 |
| Leader选举 | 可在任意节点提议 | 严格的Leader选举机制 |
| 日志复制 | 无严格顺序保证 | 严格按Leader顺序复制 |
| 流行度 | 理论基石 | 实际系统主流选择(etcd/Consul/TiKV) |
Raft将共识问题分解为Leader选举、日志复制、安全三个独立子问题，降低了工程实现难度。

## 2.11 Seata如何平衡CAP？有哪几种模式？
Seata AT(自动补偿)模式：默认AP倾向，通过全局事务协调器(TC)协调分支事务，利用undo_log实现自动回滚，最终一致性。TCC模式：业务自定义Try/Confirm/Cancel逻辑，可偏向CP。Saga模式：长事务拆分为有序子事务，每个子事务有补偿操作，适合无锁定长事务。XA模式：基于XA协议，强一致性CP，性能较差。Seata通过多种模式满足不同一致性需求。

## 2.12 什么时候需要保证幂等性？如何实现？
在以下场景必须保证幂等：网络超时重试(客户端重复提交)、MQ消息重复消费(at-least-once语义)、定时任务重复执行(多实例部署)、用户重复点击。实现方式：1)数据库唯一键约束(如订单号唯一索引) 2)Token防重(先获取token存Redis，提交时校验并删除token，使用Lua脚本保证原子性) 3)状态机约束(已支付状态不能再支付) 4)乐观锁(update时带version条件) 5)分布式锁(获取锁成功才执行) 6)全局请求ID(每次请求生成唯一requestId，用Redis setnx去重)
