# 1. 定位与原理

## 1.1 CDC 与 Canal

### 1.1.1 Canal 是什么？解决什么问题？

**定位**：阿里开源的 **MySQL binlog 增量订阅与消费组件**——CDC（Change Data Capture，变更数据捕获）的 Java 生态代表实现。它把"数据库里发生了什么变更"变成**可订阅的事件流**：INSERT/UPDATE/DELETE 连同变更前后值实时推给下游（缓存、搜索引擎、数仓、异构库、MQ）。

**它替代的是哪些坏味道方案**：
1. **应用双写**：业务代码里"写 MySQL 顺手写 Redis/ES"——耦合灾难：每加一个下游改一次代码、两份写没有事务、主流程被下游抖动拖垮、双写顺序无法保证；
2. **DB 触发器**：数据库内挂触发器外呼——行级开销、调试黑洞、把连接资源耗在 UDF 上；
3. **定时扫表**：靠 update_time 轮询——漏 DELETE、时间精度与负载两难、大表扫描雪上加霜。

**CDC 的解法**：变更捕获下沉到**复制协议层**——binlog 本就是 MySQL 为"重放变更"设计的完备日志，订阅它等于"挂在主从复制通道上旁听"，对业务零侵入、对 MySQL 只是一个从库连接。Canal 与 Debezium/Maxwell 同属此类（4.1.1）。

**典型场景**：CQRS 读模型重建、MySQL→Redis/ES/HBase/异构 MySQL 同步、多数据中心复制、实时数仓 ODS 入口、缓存失效广播——凡是"源是 MySQL、下游要跟着变"的需求都在这条流水线上。

### 1.1.2 Canal 的工作原理？内部链路是怎样的？

**一句话**：**伪装成 MySQL 从库**，走完主从复制的"接收段"，把本该回放 SQL 的"执行段"换成解析投递。

**协议层四步**：
1. Canal 用 MySQL 账号连上 Master（需要 `REPLICATION SLAVE/CLIENT` 权限 + binlog 开启），发送 **COM_REGISTER_SLAVE + COM_BINLOG_DUMP**（带起始位点）——与真从库的握手一字不差；
2. Master 按位点把 binlog event **持续推**给 Canal（推模式，非轮询）；
3. Canal 解析二进制 event 为结构化 `CanalEntry`（RowChange：before/after 镜像、列元数据、事务边界 TRANSACTION_BEGIN/END）；
4. 按订阅方规则过滤后投递。

**内部组件流水线**（Instance 内四段，追问必拆）：

```text
EventParser   —— 连接 MySQL、拉取并解析 binlog（canal-parser 模块）
EventSink     —— 按 filter 规则（库表/字段/DDL）过滤、归并分发
EventStore    —— 内存 RingBuffer 暂存事件（默认），按 clientId 隔离消费视图
EventConnector—— 交付出口：TCP 供 Canal Client 拉取 / MQ 适配器直接外发
```

`canal.instance.parser.threadName` 等之外记住主干：**Entry 的位点由 `positionManager` 记录（内存/文件/ZK），消费方 ack 之后才推进**（3.1.1）——这是全部可靠性语义的支点。

**MQ 模式简化链路**：`entry.type = KAFKA/RMQ/PULSAR` 时 EventSink 之后直接打平发到 MQ，跳过 Client 长连接——生产主流形态（2.2.2）。

**对源库的影响**：一个 dump 连接 + 网络流量，**无 SQL 侵入、无锁**；挂从库上拉（保护主库连接数与 IO）是标配姿势。

### 1.1.3 MySQL 主从复制的原理？Canal 与真从库的差别？

**双线程经典模型**：
1. **Master**：事务提交时把变更从 binlog cache 一次性刷入 **binlog**（`sync_binlog` 控制落盘强度）；
2. **Slave IO 线程**：向 Master 发 dump 请求，把收到的 event 顺序写入本地 **relay log**，并把读位点记进 `master.info`/connection metadata；
3. **Slave SQL（执行）线程**：从 relay log 读 event 回放（可用 `slave_parallel_workers` 按库/组提交并行，**并行会乱序——与 MQ 分区乱序同构**，见 3.1.2 延伸）；
4. 位点表示：`file:position`（传统）或 **GTID**（`uuid:序号` 集合，位点不再依赖具体文件，从库切换/重建自动化程度大增）。

**Canal 与从库的差别一张嘴**：**前半段相同、后半段不同**——Canal 也要 dump、也维护位点，但**不写 relay log、不回放 SQL**；它把 event 解析成结构化事件直接投递下游。所以"Canal 相当于一个只取不执行的从库"：源库视角多一个 slave 连接，容量与延迟特性照搬复制链路（主库大事务、网络抖动照样传导为 Canal 延迟，3.3.1）。

**易错**：① Canal 必须**有真实 MySQL 协议连接**，它不是读文件的离线工具；② 从库延迟就是 Canal 的延迟下限——**挂在从库拉时，从库慢多少 Canal 就慢多少**，挂主库拉少一跳但吃主库资源，这取舍常被追问。

## 1.2 binlog 与位点

### 1.2.1 binlog 三种格式的区别？为什么 Canal 要求 ROW？

| 格式 | 记录内容 | 优点 | 致命伤 |
|------|---------|------|--------|
| STATEMENT | 原始 SQL 语句 | 日志小 | **不确定性函数**（UUID()/NOW()/RAND()、自增并发）主从可能不一致——下游更不可信 |
| ROW | 每行变更的 before/after 镜像 | **数据完备精确** | 量大（wide update：改一列也写整行镜像；大事务膨胀） |
| MIXED | 默认 STATEMENT，检测到不安全语句自动切 ROW | 折中 | 下游要处理两种格式，Canal 解析行为不确定 |

**Canal 要 ROW 的原因**：订阅方要的是"**数据变成了什么**"，不是"执行了什么语句"——缓存更新需要 after 值、ES 重建文档需要整行、异构库 upsert 需要前后镜像；STATEMENT 还得反向解析 SQL（函数值在从库执行时刻与主库不同），工程上不可行。**配套要求**：`binlog_format=ROW` + `binlog_row_image=FULL`（默认 FULL；MINIMAL 只镜像必要列——Canal 拿不到完整行，下游做不了整行重建，这个参数是隐藏考点）。

**MIXED 实际处置**：Canal 能解 MIXED（两种 event 都能读），但**同步链路一律钉死 ROW** 出运维口径；`slow.sql`/审计类下游才容忍 STATEMENT。

### 1.2.2 Canal 的位点是什么？宕机后如何找回继续消费？

**位点 = "我读到 binlog 哪里了"**：`(mysql-bin.000003, 4567)` 文件+偏移二元组（GTID 开启则记 GTID 集合，`canal.instance.gtidon=true`——跨主从切换位点语义不漂移，4.2.2 相关）。

**三种存储形态**（`canal.instance.memory.persistent` / 集群模式）：
1. **memory**：只在内存 RingBuffer 视图里记位点，进程重启丢；
2. **file**：持久化到本地 `conf/{instance}/position.meta`——单机的默认姿势，**换机器即断档**；
3. **ZooKeeper（集群模式）**：位点与运行状态写到 `/otter/canal/destinations/{instance}/...`——**HA 切换的接管依据**（4.2.2），多机部署必须用它。

**断档后的回退（rollback）机制**：新起 Instance 若本地无位点，按 `canal.instance.rollbackTime`（分钟级回溯窗口，默认 10 分钟量级）向 Master 回退请求——**从 rollback 时间点最近的 event 重发**；找不到回退锚点则按 `canal.masterPosition`/起始策略处理。所以"Canal 重启后这几分钟可能重复推"是**设计内行为**（at-least-once，3.1.1），下游按主键幂等消化。

**人工重置位点**（运维高频）：控制台/接口把位点设到指定时间戳或文件位点——**往前拨=重放**（幂等前提）、**往后拨=跳过**（丢数据，需要全量对账补偿）：语义与 RocketMQ 位点重置完全同构（13_rocketmq.md 3.1.3），面试可互相引用。

# 2. 部署与高可用

## 2.1 Server 与 Instance

### 2.1.1 Canal Server、Instance、Admin、ZooKeeper 各是什么角色？

**四层关系**：

```text
Canal Server（JVM 进程）—— 承载若干 Instance 的运行时
  └ Canal Instance（destination）—— 一个实例绑定一个 MySQL 数据源（或主从一组），
      内含完整 Parser→Sink→Store 流水线与独立位点；配置在 conf/{instance}/instance.properties
Canal Admin（独立 Web 控制台）—— 集中管理：Server 集群注册、Instance 配置下发、
      启停、位点查看、监控——没有 Admin 时配置全靠改 properties 文件+重启
ZooKeeper —— 两个用途：集群模式下的选主/接管协调 + 位点持久化（1.2.2/2.2.2）
```

**部署常识**：一个 Server 可跑多 Instance（多库分散在同几台 Canal 上）；**一个 Instance 只对一个 MySQL 源**——要同步 50 个库就 50 个 instance 或按容量分组。端口：Server 默认 TCP 11111（Client 消费口），Admin 默认 8081。

**Admin 与 ZK 的分工易混**（追问点）：Admin 是**管控面**（人操作：配置、启停、监控），ZK 是**数据面协调**（机器操作：谁活着、谁是主、位点在哪）——Admin 挂不影响运行中的同步，ZK 挂影响 HA 接管能力（已运行的主继续跑，切换能力丢失）。

### 2.1.2 Canal 如何实现高可用？主备切换时位点怎么办？

**单机模式的脆弱**：file 位点 + 单 Server——进程/机器一挂，同步停摆，等人拉起；生产不可接受。

**集群模式（基于 ZK 的主备）**：
1. 多台 Canal Server 配置同一 destination，启动时在 ZK `/otter/canal/destinations/{destination}/cluster/` 下**竞争创建临时顺序节点**，最小序号者当选该 instance 的运行节点；
2. 只有主节点连 MySQL 拉 binlog（**同一时刻一个 instance 全集群单活**——防位点双写打架）；
3. 主挂 → 临时节点消失 → 其余 Server 监听到变化，新主按序号规则接管，**先从 ZK 读回位点**再继续 dump（1.2.2）——接管不丢不跳，代价是**切换窗口内下游延迟抖动**（秒级到十秒级，取决于会话超时与检测周期）；
4. 位点定期（或 ack 驱动）刷回 ZK，保证新主拿到的是"已确认消费到哪"。

**GTID 的加持**：主备切换若伴随 **MySQL 侧**主从切换，传统 file:position 在新主上可能对不上（文件序号各库独立）——GTID 模式下位点是事务集合，Canal 可无缝换源（1.2.2/1.1.3），生产强烈建议。

**易错与追问**：① "Canal HA = 多机同时消费？"——不是，是**单活主备**；多机并行消费同一 binlog 是MQ 分区分配的事（2.2.2），Canal instance 本身不拆并行拉取；② Admin 集群模式与 ZK 集群模式区别——Admin 可代为编排但底层协调仍靠 ZK；③ MQ 模式下 HA 简化：Canal 挂只产生延迟，**MQ 侧位点在 broker**，恢复后继续投——下游消费不受影响（这是推荐 MQ 化的又一个理由）。

## 2.2 消费交付形态

### 2.2.1 Client 直连、MQ、Adapter 三种交付方式怎么选？

**三条路**：

| 方式 | 机制 | 优点 | 局限 |
|------|------|------|------|
| **Canal Client**（TCP 直连 Server，protobuf） | `subscribe/getWithoutAck(batch)/ack/rollback` | 位点语义显式（ack 才推进，at-least-once）、可控性最强 | 强耦合 Canal Server：Server HA 切换要客户端重连、消费端要自己写全部逻辑、水平扩展受 instance 单活制约 |
| **MQ 适配**（`entry.type=kafka/rocketmq`） | Server 侧直接把事件打平投 MQ | **解耦 + 削峰 + 广播**：下游多团队各自建消费组、堆积能力交给 MQ（13_rocketmq.md 3.3.2 的 lag 模型）、Canal 故障只留延迟 | 多一套 MQ 运维；顺序要靠分区策略约束（3.1.2）；消息体格式要约定（FlatMessage） |
| **Canal Adapter** | 现成连接器直写目标：**RDB**（MySQL→MySQL/Oracle 异构表）、**ES**（文档同步）、HBase | 零代码接入预编译 SQL/映射、全增量衔接内置 | 目标类型有限、定制逻辑（过滤加工）弱于自写消费、adapter 本身也要做 HA |

**口径**：**生产默认推 MQ 化**——哪怕单下游；Client 直连留给"要精细控制 ack/回滚的自研平台"；Adapter 适合"标准场景快上线"（库表镜像、ES 同步）。面试加分句：三种形态本质是"位点托管在哪"——Client 在 Canal、MQ 在 broker、Adapter 在自身消费进度，**可靠性模型跟着交付形态变**（3.1.1）。

### 2.2.2 MQ 里的 Canal 消息长什么样？分区策略怎么定？

**两种序列化**：`canal.mq.flatMessage=true` 时发**打平 JSON（FlatMessage）**，一行一条：

```json
{"database":"shop","table":"orders","type":"UPDATE","es":1699999999000,"ts":1700000000001,
 "isDdl":false,"sql":"","mysqlType":{"id":"bigint","status":"tinyint"},
 "pkNames":["id"],"data":[{"id":"1001","status":"2", ...}],
 "old":[{"status":"1"}]}
```

`data`=变更后行（after image），`old`=变更列的原值（before 差量）——下游做缓存重建/变更对比全靠这两段。`flatMessage=false` 则发原始 CanalEntry protobuf（省体积、解析依赖 SDK）。

**Topic 与分区**（顺序与并行度的权衡开关）：
- Topic 分配：`canal.mq.dynamicTopic` 按库表拆 topic（`binlog.*`）或全走单一 topic——**大表独立 topic** 防热点挤爆别人；
- 分区策略：默认轮询（吞吐优先、**顺序无保证**）；`canal.mq.partitionHash`（按**主键哈希**：同一行永远同分区→**单行有序**）；表级路由（同表同分区→单表有序）；事务分组（同事务同分区→事务内有序，实现最弱）；
- 与 Kafka/RocketMQ 分区语义衔接：分区内有序 + 消费端按分区单线程（13_rocketmq.md 2.1.1、31_kafka.md）。

**设计口诀**：**下游按什么粒度消费有序，就按什么粒度分区**——按行（用户/订单状态机）用 pk hash；按表（审计流水）表级；对顺序完全无要求的统计类才用轮询换最大并行度。

# 3. 一致性与工程实践

## 3.1 投递语义

### 3.1.1 Canal 保证不丢不重吗？投递语义到底是什么？

**结论**：**at-least-once**——不丢有机制保障，重复是设计内行为，**幂等是消费方的合同义务**。

**"不丢"的支点**：位点只在**确认后**推进——Client 模式 ack 之后 positionManager 才前移；MQ 模式 Canal 收到 broker 的发送确认（RocketMQ 同步发送 / Kafka acks 配合，13_rocketmq.md 4.2.1 同理）才回位点。Canal 进程在"取了没确认"窗口内崩溃 → 重启回退重发（1.2.2 rollback）——宁可重发不可漏发。

**"重"的三个来源**（面试把场景列全才算真懂）：
1. **崩溃窗口**：事件已投出、位点未推进 → 重启重发（最常见）；
2. **rollback 粗粒度**：回退到"时间戳附近的 event"，边界上必然重叠几分钟；
3. **消费失败重投**：MQ 消费组的 retry/DLQ 机制（13_rocketmq.md 3.2.1）叠加。

**消费端合同**：变更事件按**主键 upsert**（"最后写赢"语义天然幂等——UPDATE 重放结果不变）；DELETE 重放无害（重复删除幂等）；**要区分新旧版本时带位点/时间戳做条件更新**（`WHERE ts <= :newTs` 或版本号比对，13_rocketmq.md 3.2.3 方案④）。**反例**："先查再写"非原子去重（Redis 判断后写缓存）在并发重放下照样翻车——去重要落进原子操作或唯一索引。

**追问**："能不能 exactly-once"——Canal→下游没有跨系统事务，做不到；at-least-once + 幂等消费 = effectively-once，这是所有 CDC 管道的通用答案（Debezium 亦然，4.1.1）。

### 3.1.2 变更事件的顺序如何保证？哪些环节会乱序？

**源头是有序的**：binlog 全局单调（事务提交顺序写入，1.1.3）——Canal 解析与投递**不改序**。乱序发生在**并行化的每一跳**：

| 环节 | 乱序原因 | 对策 |
|------|---------|------|
| Canal→MQ | 默认轮询分区：同 key 两条落不同分区 | 分区键策略：pk hash/表级（2.2.2） |
| MQ→消费者 | 消费组多实例分摊分区（分区内仍有序） | 单行变更恒同分区即安全（2.1.1） |
| 消费者内部 | 线程池并发处理同一 key 的两事件 | 按 key 再分片（本地队列 hash 到固定线程）或同 key 串行化 |
| 下游写入 | ES/Redis 并发写"后发先至" | 版本条件更新/last-write-wins + 单调时间戳 |

**极端场景**：一条 UPDATE 产生两条事件，第一条因异常进了重试队列（延迟 10s 重投）、第二条已成功——**新旧状态倒挂**——重试队列是 CDC 链路乱序的最大温床：下游必须带版本判定（3.1.1），或消费失败时**整链路停机保序**（顺序敏感库表同步的常见运维选择：宁可延迟不可错乱）。

**与数据库并行的镜像**：从库组提交并行回放同样要处理"库内并行、跨库有序"的难题（1.1.3）——**分布式系统里"顺序 = 同一串行通道内的顺序"，先定义串行域（行/表/事务），再保证该域全链路单通道**，这句话是本题的满分收口。

## 3.2 典型同步场景

### 3.2.1 用 Canal 做 MySQL→Redis 缓存同步怎么落地？

**标准链路**：Canal → MQ → 缓存同步消费者：

1. **事件→动作映射**：INSERT/UPDATE → 按 after 镜像写/更新缓存（或直接**删除**旧 key）；DELETE → 删 key；宽表整行 JSON 或 Hash 结构按访问模式定（27_redis.md）；
2. **"删优于写"**：更新缓存要构造完整值（多表聚合场景拿不全），**删除让下一次读回源重建**更安全；确实要写则保证**带版本/时间戳条件**（防乱序倒挂，3.1.2）；
3. **幂等与位点**：同 key 重复事件无害（最后写赢）；消费者**处理成功才提交 MQ 位点**（at-least-once 的消费端姿势，3.1.1）；
4. **TTL 兜底**：所有缓存 key 仍设过期——Canal 链路是**加速器不是唯一真相**，链路断掉时 TTL+回源保证自愈。

**对比"业务代码维护缓存"**（本题的架构价值）：双写方案要在每个写路径埋失效逻辑、漏一处就脏；Canal 把"库变"当作唯一事实源，**新增下游零业务改造**；代价是引入组件与秒级延迟——读缓存要容忍短暂旧值（最终一致）。追问"那延迟双删还要吗"——双删解决的是"主流程写库+删缓存之后、并发读把旧值回填"的窗口问题（27_redis.md）；Canal 方案里回填写入同样会被后续 binlog 事件覆盖/删除，窗口大幅收窄但不归零——**TTL 仍是最后的兜底防线**，两方案别在面试里说成互相取代。

### 3.2.2 Canal 同步到 ES 要注意什么？

**链路**：Canal → MQ → ES 写入消费者（或 canal-adapter 的 ES 连接器零代码直连，2.2.1）。要点六件：

1. **文档 id = 主键**：所有事件翻译成 **upsert/delete by id**——天然幂等（3.1.1 的"最后写赢"）；宽表/多表聚合文档要自定义 id 与聚合刷新逻辑（binlog 只给你单表行，多表 join 文档要么冗余列、要么收到事件回源重查拼装）；
2. **全量先行、增量锚定**（见 3.2.3 的通用流程——ES 场景最常考的就是这个衔接）；
3. **批量写入**：攒批（百条级或 1~5s）走 Bulk API——逐条写 ES 在高峰期必然拖出堆积（ES 刷新与分片特性见 24_elastic_search.md）；
4. **顺序**：同 id 事件乱序=文档新旧倒挂——pk hash 分区 + 同 id 串行（3.1.2 全套）；
5. **DDL 与字段**：新增列后 ROW 事件 data 自带新字段，ES **动态 mapping 自动吃进**——但类型推断可能不合意（新列默认 text 而非 keyword），**显式 mapping + 变更单**仍是纪律（3.3.2）；
6. **对账**：定期 count/抽样比对 MySQL vs ES（时间窗口内的差异告警）——"最终一致"要靠对账闭环兜底，不是信仰。

**追问"删除事件丢了怎么办"**：MQ 重试+死信兜住大部分；剩下的靠对账（MySQL 已删、ES 还在→补删）；ES 侧软删除/过期索引策略减少残留影响面。

### 3.2.3 存量全量 + 增量 Canal 怎么衔接不丢不重？

**问题**：Canal 只能从"某个位点"开始增量；上线那天下游是空的——全量灌入与增量切换之间的缝隙就是丢数据/重数据的发生地。

**标准五步（背流程 + 讲清每步防什么）**：

```text
① 记录当前 binlog 位点 P0（先记后灌——保证增量起点不晚于全量快照）
② 全量迁移：DataX/SELECT 分批导出灌入下游（耗时期间业务照常写）
③ 全量完成时记录位点 P1
④ 从 P0 启动 Canal 增量回放：P0→P1 区间与全量重叠（重放风险）→ 靠幂等消化（3.1.1）
   P1 之后的增量无缝衔接 → 不丢
⑤ 追平（lag 归零）后双核对账，切读流量，全量程序下线
```

**为什么起点是 P0 而不是 P1**：全量快照读到的行是"迁移过程中各时刻值的混合体"（第 1 万行是 T1 时刻的、第 100 万行是 T2 时刻的）——从 P0 起重放**这段时间的全部变更**，任何中途修改都被增量覆盖修正；从 P1 起则丢掉"P0→P1 之间改过、之后没再改"的行——经典丢数场景。**幂等让重叠无害，位点提前让遗漏没有**。

**加分项**：超大表全量分片并行迁移时按主键段切；迁移期 MySQL 从库执行（保护主库）；Debezium 类工具的 snapshot 模式就是把这套流程产品化（4.1.1）；切流前 lag 监控（3.3.1）+ 对账差异修复脚本先行灰度验证。

## 3.3 延迟与故障

### 3.3.1 Canal 同步延迟大怎么排查？

**延迟链条拆解**（先建模型再定位）：`源库写入 → Canal 解析 → 投 MQ → MQ 堆积 → 消费者处理 → 下游写入`——**每段都有自己的观测位**：

| 症状组合 | 定位段 | 典型根因 |
|---------|--------|---------|
| Canal 位点落后源库当前 binlog 多 | **捕获段** | 挂在延迟从库（1.1.3，最常见！）、大事务/大表 DDL 阻塞解析（3.3.3）、网络 |
| Canal 位点不落后、MQ lag 大 | **消费段** | 下游写入慢（ES bulk 未调、DB 锁）、消费者并行度不足、毒消息重试循环（13_rocketmq.md 3.2.1） |
| 两段都不落后、用户仍感知旧数据 | **下游自身** | ES refresh_interval、Redis 读走了另一从库副本 |

**排查动作**：Admin/日志看 instance 的"store 位点 vs sink 位点 vs ack 位点"三级差值（Canal 内部解析→投递→确认各段健康）；MQ lag 面板（13_rocketmq.md 3.3.2 的堆积三板斧原样适用）；`SHOW MASTER STATUS` 对照源库进度。

**应急**：消费段慢——扩消费者（按分区数封顶，先扩分区再扩实例）；捕获段慢——切主库直拉（评估源库压力）/拆 instance 分组；毒消息——暂停该分区消费、修数据恢复（3.1.2 停机保序）。**治本**：延迟监控按段拆（end-to-end lag 指标进告警），别等下游业务报"数据不对"才发现同步断了。

### 3.3.2 DDL 变更（加列/改类型）时同步链路会发生什么？

**Canal 的 DDL 处理**：`canal.mq.filterDdl`（默认 true=DDL 事件**过滤掉**，只透传行变更）；即使透传，DDL event 里只有语句文本，下游也很少真敢自动执行。

**三类目标端的连锁反应**（这题价值在分端讲）：
1. **缓存/消息下游**：加列后 ROW 事件的 data 多出字段——老消费者按已知 key 取值，**新列静默丢失**（不报错！），上线新列消费逻辑要发版；改/重命名列类型变化 → 消费者解析异常 → 毒消息进重试循环（3.3.1），**发布顺序纪律：下游先兼容、源库再变更**；
2. **ES**：新列自动进文档（动态 mapping）但类型不受控（3.2.2）——正式变更单：先 PUT mapping 再 DDL；
3. **异构 RDB（adapter 库表同步）**：目标表**不会自动跟列**——DDL 后同步报错停摆（字段对不上），人工 ALTER 目标表 + 位点回退重放该时间窗（幂等消化，3.1.1）。

**高危 DDL 顺带讲**：大表 ALTER（instant/inplace/copy 的行为差异，16_mysql.md）期间 binlog 事件量与解析负载陡增；**分区/重命名表**会让"按表名路由"的 dynamicTopic/分区策略瞬间错位——库表变更是 CDC 链路最高频的事故窗口，**变更评审必须把同步链路列为受影响方**。

### 3.3.3 大事务/超大表对 Canal 有什么影响？怎么处理？

**大事务**（一次 update 百万行、批量导入）：binlog 内该事务 event 连片巨大 → ① EventParser **单事务逐条解析**，内存压力（parser buffer 膨胀、甚至 Full GC）；② 投递端洪峰：几十万个行事件几秒内涌向 MQ——分区不均则单分区热点；③ 下游写入风暴（ES refresh、缓存击穿式回源）。

**对策分侧**：
- **源头侧（治本）**：批处理拆小事务（每 500~1000 行 commit 一次——**顺带缩短主从复制延迟与 rollback 窗口**）；大批量导入走"离线通道 + 事后对账"而非生产库；
- **链路侧**：MQ 化吸收突发（13_rocketmq.md 3.3.2 堆积能力就是干这个的）、消费者限速 + 批量（3.2.2 bulk）；
- **Canal 侧**：instance 内存参数、`canal.instance.memory.bufferSize` 与 ringbuffer 容量调优、大事务期间监控 GC/位点差。

**超大表视角**：单表变更占比高时给该表**独立 topic/分区策略**（`dynamicTopic`，2.2.2），防"一张爆款表饿死其余 99 张表的同步时效"。收口句："CDC 链路对大事务没有豁免权——**源库的事务粒度纪律决定下游的平稳度**"，能主动讲到源头侧才算完成。

# 4. 选型对比

## 4.1 CDC 与同步工具选型

### 4.1.1 Canal、Debezium、Maxwell 怎么选？

**同门比**：三者都是"伪装从库读 binlog"的 CDC（1.1.2 的模型通用），差在**生态位与工程完备度**：

| 维度 | Canal | Debezium | Maxwell |
|------|-------|----------|---------|
| 支持数据库 | **MySQL 专精**（MariaDB 兼容） | MySQL/PG/MongoDB/SQL Server/Oracle/DB2 全家 | 仅 MySQL（+MariaDB） |
| 运行形态 | 独立 Server + Client/MQ/Adapter（2.2.1） | **Kafka Connect 插件**（源连接器），也嵌嵌入式引擎 | 独立进程，直接产 JSON 到 Kafka |
| 全量快照 | 无内置（靠 DataX 衔接，3.2.3） | **内置 snapshot 模式**（consistent change snapshot：锁-free 一致性快照+增量无缝衔接——它的招牌） | 无（依赖 Kafka topic 初始导入） |
| Schema/DDL | filter 透传，DDL 靠人工纪律（3.3.2） | **schema history topic**：DDL 版本化、事件带 schema 演进（结构化最完善） | schema 存 DB（maxwell 库） |
| 运维依赖 | ZK（HA）+ 自身集群 | Kafka + Connect 集群（重，但团队本有 Kafka 则顺） | 最轻 |
| 社区与语境 | 阿里主导、中文资料多、MQ 适配全（RocketMQ/Kafka/RabbitMQ/Pulsar） | Red Hat，国际事实标准，CloudEvents/Debezium Server 输出多 | 社区小、功能聚焦 |

**选型口径**：**国内 Java 栈 + MySQL + 需要 RocketMQ/Adapter 现成件 → Canal**（默认答案）；**多数据源、已有 Kafka/Connect 平台、要大范围"快照+增量"开箱 → Debezium**（其一致性快照正是 3.2.3 手工流程的产品化）；**只要"binlog→Kafka JSON"最简链路、不想养平台 → Maxwell**。追问"选型核心看什么"——看你的**技术栈重心在中间件侧还是数据管道侧**：Canal 自建一套交付体系，Debezium 把你引向 Kafka Connect 生态，没有能力代差只有生态归属。

### 4.1.2 Canal 和 DataX 什么关系？实时和离线怎么分工？

**物种区分**：DataX（阿里开源，插件式 **批量 ETL**：MySQL→Hive/ES/异构库，全表切片并行搬）**没有实时语义**——跑一次搬一次；Canal **只懂增量**（binlog 从某位点起的事件流，1.2.2）——两者是**接力赛不是决赛对手**（4.1.1 Debezium 内置快照后这类工具"全量段"的活也被中间件收编了一半）。

**标准配合**（3.2.3 的五步流程即两者接口）：
- **离线侧 DataX**：存量迁移、字段映射加工、每日全量校准（对账后修复差异的重武器）；
- **实时侧 Canal**：上线后持续增量；
- **数仓视角**：ODS 层"T+1 全量 + 实时增量"两路并进，**下游按场景选一路线消费**（报表容忍 T+1、交易监控吃实时）——Flink CDC（本质 Debezium/Canal 内核 + 流计算）近年把"增量入仓"又前推了一层，面试提到即加分。

**易错**：拿 Canal 做"历史数据搬迁"（它只能回放保留期内的 binlog，4.1 之外的历史不在日志里）；拿 DataX 每 5 分钟全量抽小表"伪实时"（大表场景源库被扫穿、延迟分钟级起步）——**边界感**是这题唯一考点。

### 4.1.3 什么场景不适合用 Canal？它的边界在哪？

**反向盘点（比"能干什么"更能体现工程判断）**：

1. **非 MySQL 源**：Canal 只吃 MySQL binlog——PG/Mongo/Oracle 的变更捕获另起炉灶（Debezium/Flink CDC）；**多源异构平台化时 Canal 撑不起统一架构**；
2. **强实时要求**：复制链路 + MQ + 消费 = 端到端秒级常态，**亚秒/毫秒级"数据就绪"做不到**（1.1.3 延迟传导）；缓存读自己的实时状态请回源或用写路径双删策略（3.2.1 的"加速器不替代真相"）；
3. **跨库分布式一致性**：Canal 是**事件管道**不是分布式事务——要求"两个库原子生效"该走 Seata 或业务补偿（21_seata.md），别指望同步链路"差不多同时"当成事务用；
4. **强顺序状态机下游**：3.1.2 的乱序风险与"停机保序"运维成本，高敏金融状态同步宁可直连双写+对账；
5. **小团队低运维预算**：Canal + ZK + MQ 三套件要养（2.1.1/2.1.2）——日变更量很小时，"业务事件直接发 MQ（Outbox 表方案，13_rocketmq.md 2.3.2）"更省：**Canal 的价值在"改不动的业务代码 + 多下游扩散"，两者皆无时它是过度设计**；
6. **隐私与合规过滤**：binlog 是全字段镜像（ROW，1.2.1）——敏感列进下游前的脱敏/最小订阅要在消费侧专门做，Canal 只提供粗粒度字段过滤（数据分级合规要自己补层）。

**收口姿态**：Canal 解的是"**已有 MySQL 事实源、下游要多而快、业务不能改**"三角——三边缺一个就有更便宜的解（自研事件总线/直连双写/批量抽取），选型题能报出"什么时候不用它"才闭环。
