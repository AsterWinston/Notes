# 1. 知识点
- **镜像(Image)**：分层只读的打包模板，包含运行应用程序所需的文件系统、环境和依赖，每一层都是增量变化
- **联合文件系统(UnionFS)**：Docker 镜像分层的技术基础，将多个文件系统层的目录内容合并到同一挂载点
- **overlay2**：当前推荐的联合文件系统存储驱动，性能好、缓存在内核 inode 更高效
- **基础镜像**：镜像构建的起点，如 alpine、ubuntu、openjdk 等，最小的基础镜像 scratch
- **容器(Container)**：镜像的运行实例，隔离资源和进程，在镜像层之上创建一个可读写层
- **仓库(Registry)**：存储和分发镜像的仓库，如 Docker Hub、Harbor，用于镜像的 push 和 pull
- **数据卷(Volume)**：Docker 管理的持久化存储方式，独立于容器生命周期，容器间可共享
- **绑定挂载(Bind Mount)**：将宿主机目录或文件直接挂载到容器中，路径由用户指定
- **bind类型挂载**：将宿主机文件系统上的任意文件或目录绑定挂载至容器，适合开发阶段代码热更新
- **网络bridge**：默认网络模式，创建虚拟网桥 docker0，各容器通过虚拟网桥互联，通过容器名 DNS 通信
- **host网络**：容器直接使用宿主机网络，没有网络隔离，性能最好但端口冲突风险
- **none网络**：容器无网络连接，完全隔离
- **overlay网络**：跨 Docker 宿主机容器互联，用于 Swarm 集群
- **Docker vs 虚拟机**：Docker 共享宿主机 OS 内核，无 Hypervisor 层，启动秒级，资源利用率高；虚拟机模拟完整 OS，有独立内核，启动分钟级，隔离性强
- **共享Host OS内核**：Docker 容器直接运行在宿主机内核上，不虚拟化内核，这是和虚拟机最本质的区别
- **Hypervisor**：虚拟机管理程序，运行在硬件和 Guest OS 之间，Docker 不需要这层的开销
- **FROM**：指定基础镜像，Dockerfile 第一条指令，可写多个 FROM（多阶段构建）
- **ENV**：设置环境变量，在构建和运行阶段都生效
- **COPY vs ADD**：COPY 从宿主机复制文件到镜像；ADD 功能更强但复杂，支持自动解压 tar 文件和远程 URL
- **EXPOSE**：声明容器运行时监听的端口，仅用于文档说明，不实际发布端口
- **RUN**：构建镜像时执行的命令，在 shell 中运行，每执行一次生成新层
- **CMD**：容器启动时的默认命令，可被 docker run 后的命令覆盖
- **ENTRYPOINT**：容器启动的固定命令，不会被 docker run 后的命令覆盖，CMD 可为其提供默认参数
- **CMD 与 ENTRYPOINT 配合**：ENTRYPOINT 定义固定执行程序，CMD 提供默认参数，两者配合使用更加灵活
- **WORKDIR**：设置工作目录，后续 RUN、CMD、ENTRYPOINT 都基于此目录
- **ARG**：构建时传入的变量声明，配合 --build-arg 使用，作用域仅为构建阶段
- **HEALTHCHECK**：容器健康检查指令，定义检测命令/间隔/超时/重试次数，返回状态 healthy/unhealthy
- **多阶段构建**：在一个 Dockerfile 中使用多个 FROM 指令，编译阶段在一个镜像中完成，运行阶段只复制编译产物，最终镜像只包含运行时必需的文件
- **docker run**：创建并启动容器，-it 交互式、-d 后台运行
- **-P**：随机映射 EXPOSE 的端口到宿主机
- **-p**：指定端口映射（宿主机端口:容器端口）
- **-v**：挂载数据卷或绑定挂载
- **--name**：给容器指定名称
- **--restart=always**：容器退出时总是自动重启
- **docker exec**：进入正在运行的容器中执行命令
- **docker logs**：查看容器日志输出
- **docker cp**：在容器和宿主机之间互相复制文件
- **docker commit**：将当前容器状态保存为新的镜像
- **docker save**：导出镜像为 tar 文件
- **docker load**：从 tar 文件导入镜像
- **docker system prune**：清理未使用的镜像/容器/网络/数据卷等无用对象，释放磁盘空间
- **Docker网络bridge默认**：默认桥接网络，各容器分配独立内部 IP，通过容器名 DNS 互连通信
- **自定义网络**：可创建自定义 bridge 网络，提供 DNS 解析和网络隔离，容器通过容器名互相访问
- **docker volume管理**：docker volume create/ls/rm/prune 命令管理 Volume 数据卷
- **存储写时复制**：容器层是读写层，修改镜像中的文件会先复制到容器层再修改（Copy-on-Write）
- **Docker Compose**：用于定义和运行多容器 Docker 应用，通过 YAML 文件编排服务
- **docker-compose.yml**：Compose 编排文件，版本号/服务(services)/网络(networks)/卷(volumes)定义
- **docker-compose up -d**：根据 docker-compose.yml 编排文件后台启动所有服务并关联网络
- **buildx多平台构建**：Docker Buildx 支持构建针对多操作系统/架构的镜像（如linux/amd64, linux/arm64）
- **镜像优化**：使用 alpine 轻量基础镜像、多阶段构建减少镜像体积、合并 RUN 命令减少层数
- **合并RUN命令减少层**：多条 RUN 命令用 && 连接合并为一条，减少镜像层数
- **alpine轻量基础镜像**：Alpine Linux 仅约 5MB，相比 Ubuntu 节省大量空间，推荐生产使用
- **.dockerignore**：类似 .gitignore，排除构建上下文中不需要的文件，加快构建速度并减小镜像
- **合理清理缓存**：在同一层安装依赖后清理 apt/yum 缓存，避免垃圾文件进入镜像

- **Docker网络模型**: Bridge(默认/容器通过docker0虚拟网桥连接，各独立IP); Host(共享宿主机网络命名空间/性能最好/端口冲突); Container(与另一容器共享网络命名空间); None(无网络接口仅loopback); Custom Network(用户自定义bridge/overlay/macvlan/ipvlan)
- **Dockerfile命令详解**: FROM(基础镜像); EXPOSE(声明端口); WORKDIR(工作目录); ENV(环境变量); ADD(复制+自动解压压缩包); COPY(复制文件); VOLUME(挂载点); RUN(构建时执行命令); CMD(默认启动命令，可被docker run覆盖); ENTRYPOINT(启动命令，不被docker run参数覆盖); ARG(构建参数); HEALTHCHECK(健康检查); USER(切换用户); LABEL(元数据标签)

# 2. 面试题

## 2.1 Docker 镜像的分层结构是什么？有什么好处？
Docker 镜像由多层层层叠加组成，每一层对应 Dockerfile 中的一条指令。这些层是只读的，使用联合文件系统技术叠加在一起。好处：
1. **复用共享层**：不同镜像可以共享相同的基础层，节省磁盘空间和拉取时间
2. **构建缓存**：如果某一层未改变，构建时可以复用缓存加速构建
3. **增量更新**：更新镜像时只需拉取变化的层，不需要下载完整镜像
每个镜像层有唯一的 SHA256 摘要值，确保内容不可变和可验证。

## 2.2 Docker 和虚拟机的区别是什么？
| 对比维度 | Docker | 虚拟机 |
|---------|--------|-------|
| 内核 | 共享宿主机 OS 内核 | 每个 VM 有独立 OS 内核 |
| 启动速度 | 秒级甚至毫秒级 | 分钟级 |
| 磁盘使用 | MB 级别 | GB 级别 |
| 内存占用 | 较少，按需分配 | 需要固定分配 |
| 隔离性 | 进程级隔离 | 硬件级隔离（更强） |
| 性能 | 接近原生性能 | 有虚拟化损耗 |
| 管理程序 | 不需要 Hypervisor | 需要 Hypervisor（如 VMware、KVM） |

## 2.3 简述 CMD、ENTRYPOINT 和 RUN 的区别？
- **RUN**：构建时(build)执行，将结果固化为镜像的一层，常用于安装软件包、编译等
- **CMD**：运行时(docker run)执行，是容器启动的默认命令，如果 docker run 指定了其他命令则被覆盖
- **ENTRYPOINT**：运行时(docker run)执行，是容器启动的固定命令，docker run 的额外参数作为 ENTRYPOINT 的参数传递
组合使用：`ENTRYPOINT ["java"]` + `CMD ["-jar", "app.jar"]`，执行时等同于 `java -jar app.jar`；docker run 时可传 `-Xmx2g` 覆盖 CMD 参数，最终执行 `java -Xmx2g`

## 2.4 COPY 和 ADD 指令有什么区别？
- **COPY**：纯粹从构建上下文中复制文件到镜像中，功能单一，推荐优先使用
- **ADD**：在 COPY 基础上增加了两个功能：如果源是 URL 会自动下载；如果源是本地 tar 压缩包会自动解压。因为 ADD 行为不够直观，官方推荐尽量使用 COPY，只在需要自动解压 tar 文件时才使用 ADD

## 2.5 什么是多阶段构建？有什么好处？
多阶段构建是在一个 Dockerfile 中定义多个 FROM 指令，每个 FROM 开启一个新的构建阶段。通常第一阶段用于编译源码（包含 SDK、编译器、构建工具），第二阶段只复制编译后的产物（如 jar 包、二进制文件），形成最终的运行镜像。好处：
1. 最终镜像只包含运行时所需的文件，大幅减小镜像体积
2. 编译依赖和工具不进入生产镜像，提高安全性
3. 减少容器攻击面，降低安全风险

## 2.6 Docker 的网络模式有哪些？
- **bridge（桥接，默认）**：通过虚拟网桥 docker0 连接，各容器分配独立 IP，相互隔离，通过端口映射对外暴露
- **host（主机）**：容器直接使用宿主机网络栈，无网络隔离，性能最好，但端口不能冲突。宿主机端口 80 被占用则容器也不能绑定 80
- **none（无网络）**：容器只有 lo 回环接口，完全网络隔离，用于安全敏感场景
- **overlay（覆盖网络）**：跨宿主机容器通信，用于 Swarm 集群和容器编排
- **container（容器网络）**：新容器共享指定容器的网络命名空间
- **自定义网络**：用 `docker network create` 创建，同网络的容器可通过容器名互相访问（内置 DNS）

## 2.7 Docker 的数据持久化方式有哪些？
1. **Volume（数据卷）**：Docker 完全管理，存储在宿主机 `/var/lib/docker/volumes/` 下，容器删除后数据可以保留，可以由多个容器共享，是推荐的方式。命令：`docker volume create/rm/ls`
2. **Bind Mount（绑定挂载）**：将宿主机指定路径挂载到容器指定路径，宿主机路径由用户指定，Docker 不管理。适合开发阶段代码热更新
3. **tmpfs Mount**：数据存储在宿主机内存中，容器停止后丢失，用于敏感数据或临时文件

## 2.8 Dockerfile 最佳实践有哪些？
1. 使用轻量基础镜像（如 alpine），减少攻击面和镜像大小
2. 使用多阶段构建，编译与运行分离
3. 合并 RUN 命令，使用 `&&` 连接多个命令，减少镜像层数
4. 将经常变化的内容放在 Dockerfile 后面，利用构建缓存加速
5. 使用 `.dockerignore` 排除不需要的文件
6. 安装依赖后清理缓存（`apt-get clean`、`rm -rf /var/lib/apt/lists/*`）
7. 尽量使用 COPY 而非 ADD
8. 不以 root 用户运行容器，用 USER 指令切换到非特权用户
9. 在 CMD 中使用 exec 形式（`CMD ["executable", "param1"]` 而非 shell 形式）

## 2.9 Docker Compose 是什么？有哪些核心概念？
Docker Compose 是 Docker 官方提供的一个工具，用于定义和运行多容器 Docker 应用，通过一个 YAML 文件配置所有服务，用一条命令启动所有服务。

核心概念：
- **services**：定义一个或多个容器服务，每个服务相当于 docker run 的配置（镜像、端口、卷、环境变量、依赖等）
- **networks**：定义容器之间的网络，服务默认加入同一网络可以互相访问
- **volumes**：声明数据卷，可以在多服务间共享数据
- **docker-compose up**：创建并启动所有服务（-d 后台运行）
- **docker-compose down**：停止并删除所有服务、网络、卷（-v 删除卷）

## 2.10 如何优化 Docker 镜像大小？
1. **选择轻量基础镜像**：使用 alpine 代替 ubuntu，或使用 scratch 构建最小镜像
2. **多阶段构建**：编译阶段和运行阶段分离，只复制必要产物
3. **合并 RUN 指令**：用 && 将多个命令合并，减少镜像层数
4. **清理构建缓存**：`apt-get clean`，`rm -rf /var/lib/apt/lists/*`
5. **使用 .dockerignore**：排除不必要的文件（node_modules、.git、target 等）
6. **精简运行时依赖**：只安装运行时必需的包，不安装 dev 依赖
7. **选择合适的 JDK**：Java 使用 jre 镜像而非 jdk 镜像，或使用 jlink 自定义精简 JRE

## 2.11 docker commit 和 Dockerfile 构建有什么区别？
`docker commit` 是将运行中的容器当前状态直接保存为新镜像，操作简单但不利之处在于：构建过程不可复现，镜像层不透明，团队协作困难，不具备版本管理能力，不推荐生产使用。Dockerfile 构建是声明式的，记录了完整的构建过程，可版本控制、自动化、可复现，是 DevOps 的最佳实践。

## 2.12 什么是 Buildx 多平台构建？
Docker Buildx 是 Docker CLI 的一个插件，支持为多个 CPU 架构（amd64、arm64、s390x 等）和操作系统（linux、windows）构建镜像。使用 emulation（模拟器如 QEMU）或 cross-compilation（交叉编译）技术，一条命令可以生成多架构镜像并推送为同一个 manifest list。典型的命令：
```bash
docker buildx build --platform linux/amd64,linux/arm64 -t myimage:latest --push .
```
这对于苹果 M 系列芯片（ARM）和 Intel/AMD（x86）服务器混合部署至关重要。

## 2.13 Docker网络模型有哪些？各有什么特点？
- **Bridge（桥接，默认）**：通过虚拟网桥docker0连接，各容器分配独立内部IP，通过端口映射对外暴露服务，容器间可通过IP或容器名（自定义网络）通信
- **Host（主机）**：容器直接使用宿主机网络命名空间，无网络隔离，性能最优，但端口不能冲突（宿主机端口80被占用则容器也无法绑定80）
- **Container（容器）**：新容器与指定容器共享同一网络命名空间，共享IP和端口空间，通过localhost通信，适合Pod模式
- **None（无网络）**：容器仅包含loopback回环接口，完全网络隔离，适用于安全敏感场景或不需要网络的批处理任务
- **Custom Network（自定义网络）**：通过`docker network create`创建，支持bridge、overlay（跨主机）、macvlan（直连物理网络）、ipvlan模式，内置DNS容器名解析

## 2.15 Docker 的写时复制（Copy-on-Write）机制在分层结构中是如何工作的？
镜像层（Image Layer）是只读的，多个容器可以共享同一个基础镜像层。当容器启动时，Docker 在镜像层栈的顶部添加一个**可读写容器层（Container Layer）**。这就是 Copy-on-Write（写时复制）的工作：

1. **读操作**：从顶部容器层开始向下逐层查找文件，直到在某个镜像层中找到。上层文件覆盖下层同名文件。
2. **写操作（修改已有文件）**：如果文件存在于某个只读镜像层中，Docker 先将该文件**复制到顶部容器层**（这就是"Copy"），然后在该副本上执行修改操作。原始镜像层的文件保持不变，其他容器仍然可以共享原文件。
3. **写操作（创建新文件）**：直接在顶部容器层中创建，不涉及镜像层。
4. **删除操作**：在容器层创建一个"白名单"（whiteout）文件标记该文件已被删除，镜像层中的原文件保持不变。

**好处**：
- 同一个镜像层被 N 个容器共享时，只占用一份磁盘空间。
- 容器写入的文件和数据只存在容器层中，容器被删除后写入数据丢失（除非挂载 Volume）。
- 共享层减少了启动时间——不需要为每个容器复制完整的文件系统。

## 2.16 如何查看 Docker 镜像的分层结构？
```bash
# 查看镜像的历史分层（每一层的创建命令和大小）
docker history <image>

# 使用 docker inspect 查看层的详细 SHA256 摘要
docker inspect <image> | jq '.[0].RootFS.Layers'

# 查看本地所有镜像层及磁盘占用
docker system df -v

# 可视化分层工具 dive（第三方）
dive <image>
```
`docker history` 输出中的 `<missing>` 标签表示该层可能是从远程仓库拉取而来的，本地没有该层对应的中间容器——这是正常现象。

## 2.17 Dockerfile 哪些指令会创建新层？哪些不会？
| 会创建新层的指令 | 说明 |
|----------------|------|
| RUN | 执行命令并提交结果为新的一层 |
| COPY | 将文件从构建上下文复制到镜像，产生新层 |
| ADD | 类似 COPY，但支持远程 URL 和自动解压 tar，同样产生新层 |
| 不会创建新层的指令 | 说明 |
|----------------|------|
| CMD | 仅声明默认启动命令，写入镜像元数据 |
| ENTRYPOINT | 仅声明固定启动命令，写入镜像元数据 |
| ENV | 仅声明环境变量，写入镜像元数据 |
| EXPOSE | 仅声明端口，写入镜像元数据 |
| WORKDIR | 仅声明工作目录，写入镜像元数据 |
| USER | 仅声明用户切换，写入镜像元数据 |
| LABEL | 仅声明标签，写入镜像元数据 |
| ARG | 构建参数，构建阶段有效，不进入最终镜像 |
| HEALTHCHECK | 仅声明健康检查命令，写入镜像元数据 |

**关键实践**：RUN 是唯一能够执行脚本命令的指令，每一行 RUN 都产生一层。因此合并多条 RUN 是减少层数的核心手段（`RUN cmd1 && cmd2 && cmd3`）。COPY 和 ADD 也会产生层，但通常没法合并。

## 2.18 镜像层共享是如何实现的？有什么优势？
层共享基于层的**内容寻址（Content Addressable）存储**：

1. 每个镜像层根据其内容计算一个唯一的 SHA256 哈希值（ID）。
2. Docker 本地存储中，相同哈希值的层只存储一份，不同镜像共享相同的层。
3. 当构建新镜像时，如果某层的内容哈希已经存在本地，Docker 直接复用——不会重建该层。

**场景说明**：假设有 3 个 Java 应用镜像，它们的基础层（`FROM openjdk:11-jre`）的 SHA256 完全相同。这 3 个镜像在磁盘上只保存一份 `openjdk:11-jre` 层，而非 3 份。以此类推，操作系统基础层（如 alpine）可以被几十个镜像共享。

**优势**：
- **节省磁盘**：基础层只存一份，实际生产环境可节省 80%+ 的磁盘空间。
- **加速拉取**：`docker pull` 时如果本地已有某个共享层，直接跳过该层的下载。《docker pull》输出中的 `Already exists` 就是共享层的体现。
- **加速推送**：仓库中同样哈希的层不会重复存储。`docker push` 时同样共享层无需重复推送。

## 2.19 联合文件系统（overlay2）在分层结构中扮演什么角色？
联合文件系统（UnionFS）是 Docker 分层架构的技术底座，目前推荐的后端是 **overlay2**。

**overlay2 工作原理**：
- 镜像层以 `lowerdir` 的形式挂载（多个 lowerdir 用 `:` 分隔，按栈排列）。
- 每个镜像层对应一个目录，存储各自修改的文件（以文件为单位，而非目录级别）。
- 容器可读写层作为 `upperdir` 位于最顶层。
- `merged` 目录是联合挂载的视图——将 lowerdir 和 upperdir 的所有文件合并为一个统一的文件系统呈现给容器。

**联合文件系统视角**：
```
merged/      ← 容器看到的文件系统（所有层合并的视图）
  ├── upper/   ← 容器层（可读写），所有修改都在这里
  ├── lower1/  ← 镜像层 3（应用 jar 包层）
  ├── lower2/  ← 镜像层 2（安装依赖层）
  └── lower3/  ← 镜像层 1（基础 OS 层，如 alpine）
```

**overlay2 相比旧 driver（devicemapper、aufs）的优势**：
- 内核原生支持（Linux 4.0+），性能更好。
- 使用 inode 索引，减少内存占用。
- 支持多达 500 个 lowerdir 层（但在 Docker 中强制限制为 128 层以内）。

## 2.20 Docker 构建缓存与分层结构的关系是什么？如何利用分层优化构建速度？
Docker 构建缓存与镜像的层是**一一对应**的。构建镜像时，Docker 会为每一步（每条 RUN/COPY/ADD 指令）检查是否存在与指令内容匹配的缓存层：

1. Docker 逐行处理 Dockerfile。
2. 对于当前指令，Docker 检查之前构建中是否存在**相同的指令 + 相同的基础层**——如果是，直接复用缓存层，跳过执行。
3. 一旦某条指令的缓存没有命中（例如 COPY 的文件内容变了），**从该指令开始的所有后续指令都会重新执行**——这条原则被称为"缓存失效链"。

**利用缓存优化构建速度的策略**：
1. **将不容易变化的指令放在 Dockerfile 前面**：先 COPY 依赖描述文件（`pom.xml`、`package.json`）→ RUN 安装依赖 → 最后 COPY 源代码。
   ```dockerfile
   COPY pom.xml .              # 依赖变更少，缓存命中率极高
   RUN mvn dependency:resolve  # 依赖不变就直接复用
   COPY src ./src              # 源码变更频繁，放在最后
   RUN mvn package             # 每次只重新编译变更的源码
   ```
2. **合并 RUN 命令兼得层少 + 命中率高**：缓存以整条指令为单位。短的合并命令如果部分文件变化，可以拆分为"下载依赖 + 安装依赖"两条，分别缓存。
3. **使用 `.dockerignore`**：排除 `target/`、`.git/` 等目录，避免文件变化导致 COPY 层缓存失效。
4. **避免 `ADD <URL>`**：URL 远程资源变化不可控，可能导致缓存不可预期地失效。改用 `RUN curl/wget` 同理也要注意缓存失效时机。

## 2.21 Docker 的分层结构是怎么样的？
Docker 镜像采用**分层堆叠**的存储模型，每一层对应 Dockerfile 中的一条指令（RUN / COPY / ADD），底层由联合文件系统（overlay2）实现。

**完整的分层模型**（以 Java 应用为例，从下往上）：

```
┌──────────────────────────────────┐
│  容器层（Container Layer）        │  ← 读写层，容器运行时所有修改（新增/修改/删除）都在这里
│  (thin r/w layer)                │     容器删除后该层消失
├──────────────────────────────────┤
│  镜像层 4：COPY app.jar          │  ← 应用代码，这些层是
├──────────────────────────────────┤     只读共享的
│  镜像层 3：RUN mvn build         │
├──────────────────────────────────┤
│  镜像层 2：RUN apt-get install   │
├──────────────────────────────────┤
│  镜像层 1：FROM ubuntu:22.04     │  ← 基础 OS
└──────────────────────────────────┘
```

**文件查找机制**：当容器读写文件时，overlay2 自顶向下逐层查找。上层有同名文件则覆盖下层——这就是"上层遮盖下层"的效果。所以 `COPY app.jar` 可以覆盖基础镜像中同名文件，只需在上层写入同名路径。

**容器层与镜像层的交互**：

| 操作类型 | 行为 |
|---------|------|
| 读取文件 | 从上往下逐层查找，第一个匹配的层返回数据。上层文件覆盖下层同名文件 |
| 修改文件 | 若文件在只读镜像层 → Copy-on-Write：先将该文件复制到容器层，再修改容器层的副本。原镜像层文件不变 |
| 新增文件 | 直接在容器层创建 |
| 删除文件 | 在容器层创建一个 whiteout（白名单文件），标记下层同名文件为"已删除"，物理文件仍存在于镜像层 |

**核心特点总结**：
1. 镜像层只读、容器层读写——同镜像启动的所有容器共享同一份镜像层，各自的容器层独立。
2. 层通过 SHA256 内容哈希标识，相同内容 = 相同层 ID → 本地磁盘只存一份。
3. 拉取镜像时，已存在的层直接跳过（输出 `Already exists`），只拉取新层。
4. `docker run` 时仅为容器创建一个薄薄的空读写层，启动极快。
5. overlay2 将存储粒度细化到**单个文件**，而非整个目录。只有实际被修改的文件才会从镜像层 Copy-on-Write 到容器层，完全未被触碰的文件始终共享自镜像层。
