# 1. 概念与流水线设计

## 1.1 CI/CD 基础

### 1.1.1 CI、持续交付、持续部署有什么区别？持续集成的真正前提是什么？

**三个词的定义（别混着说）**：
- **CI（持续集成）**：开发者**频繁（每天多次）把代码合入主干**，每次合入**自动触发构建 + 测试**——目标是**尽早暴露集成冲突**（"集成地狱"的解药）；
- **持续交付（Continuous Delivery）**：CI 之后**自动把制品部署到类生产环境**，保证"**任何一次通过流水线的提交都可随时上生产**"——**上生产仍需人工审批**；
- **持续部署（Continuous Deployment）**：连生产也**全自动**（无人工门），前提是测试/监控/回滚都足够可靠。

**持续集成的四个前提（这题的深度所在，很多人只背定义）**：① **自动化测试**（没有测试的"频繁合并"只是频繁制造事故）；② **快速反馈**（流水线分钟级，慢了开发者就绕过）；③ **主干开发/短命分支**（长期分支=集成地狱的温床，26_git.md 3.1.1）；④ **构建与依赖可重复**（锁版本、私服、缓存，3_maven.md）。

**"持续交付 vs 持续部署"的取舍**：金融/强合规场景要**人工审批**（审计要求），互联网 C 端可以全自动；**人工门不是"安全"本身**——如果审批只是"点一下通过"，它提供的是**责任归属**而不是质量（质量靠自动化门禁，3.2）。

**价值收口**："CI/CD 的收益不是'少点几下部署按钮'，而是**把发布从'事件'变成'日常'**——发布频率越高、单次变更越小、故障定位越快（DORA 指标，5.1.1 展开）。"

### 1.1.2 一条合格的流水线分哪些阶段？质量门禁放在哪？

**标准阶段（Java 微服务版，从左到右）**：

```text
① 触发：push / PR / tag / 手动
② 检出 + 环境准备（JDK/Maven 缓存、依赖私服）
③ 编译 + 静态检查（lint/format/编译）
④ 单元测试（+ 覆盖率）
⑤ 代码质量/安全扫描（SonarQube、依赖漏洞、密钥扫描）
⑥ 集成测试（Testcontainers/契约测试）
⑦ 打包（jar/镜像）+ 镜像扫描 + 签名 + SBOM
⑧ 发布制品（Nexus/Harbor，带版本与 digest）
⑨ 部署 Dev → 自动化冒烟/E2E
⑩ 部署 Staging（类生产）→ 回归/压测
⑪ 生产门禁（审批/变更窗口）→ 滚动/金丝雀发布
⑫ 发布后验证（指标/日志/探针）→ 失败自动回滚 → 通知
```

**门禁设计的三条原则**：
1. **越早越便宜**：能在 PR 阶段拦的（编译/单测/静态扫描）不要留到部署后——**修复成本随阶段指数上升**；
2. **门禁必须"可解释"**：覆盖率低于阈值/有高危漏洞/质量门失败 → **失败信息要指向具体文件与规则**，否则开发者会绕着走；
3. **分级门禁**：**PR 流水线（快，分钟级）** vs **主干流水线（全量，构建+发布）** vs **发布流水线（审批+灰度为王）**——别用一条巨长的流水线跑所有场景。

**产物与阶段的对应**：**构建一次、到处部署**（2.2.2）——镜像 digest 在 ⑧ 固定，后续环境只做"提升"（promotion），**绝不重新构建**。

**易错**：把"部署成功"当"发布成功"（还要验证业务指标）；所有检查塞一个 Job（失败难定位、无法并行）；生产门禁只配"人工点同意"（没有自动化验证=形式主义）。

## 1.2 流水线工程

### 1.2.1 流水线为什么慢？缓存、并行、增量、自托管怎么优化？

**先定位瓶颈（不要盲目加机器）**：看每个 stage 的耗时占比——通常大头是**依赖下载**（Maven/npm）、**测试**、**镜像构建**、**排队等 Runner**。

**六板斧（按收益排）**：
1. **依赖缓存**：Maven `.m2`/Gradle cache/npm cache/Docker layer cache——CI 里用**持久化缓存目录**（GitHub Actions `actions/cache`、GitLab `cache:`、Jenkins volume）；**私有仓库/代理**（Nexus，2.2.1）比公网快一个量级；
2. **并行**：测试分片（JUnit 5 parallel/按包拆分到多个 Job）、矩阵构建（多 JDK/多模块）、Job 间 DAG（GitLab `needs`/GitHub `needs`）——**stage 内并行、stage 间串行**是默认，能用 DAG 就别串行；
3. **增量**：Maven/Gradle 增量编译、**只跑受影响的模块/测试**（monorepo 的 test impact analysis）、Docker BuildKit 缓存（23_docker.md 3.2.1）；
4. **自托管 Runner**：托管 Runner 有冷启动/额度/网络限制；自建（K8s Runner/EC2 Spot）可**预热、内网拉依赖、控制成本**——但要自己管安全与升级（2.1.1）；
5. **减少重复**：PR 流水线只跑"快检查"，全量测试放主干/夜间；**制品复用**（下游环境不重新构建）；
6. **失败快**：lint/编译放最前、`fail-fast`、超时设置（别让一个卡死的测试占 1 小时）。

**度量**：流水线 P50/P90 时长、排队时间、失败率、**"从提交到可部署"的 lead time**（DORA，5.1.1）——没有度量的优化都是猜。

**易错**：缓存了"不该缓存"的东西（`target/` 里的旧 class 导致增量错误）；并行测试共享同一数据库（互相污染，3.1.2）；自托管 Runner 不隔离（恶意 PR 偷 Secrets）；缓存 key 不含依赖文件 hash（永远命中旧缓存）。

### 1.2.2 Pipeline as Code 怎么组织？Jenkinsfile 与共享库怎么设计？

**为什么 Pipeline as Code**：流水线**进版本库**——可评审、可回滚、可复用、与代码同生命周期（"UI 点出来的流水线"是运维事故源）。

**Jenkins 的组织方式**：
- **Multibranch Pipeline**：每个分支/PR 自动发现 `Jenkinsfile`，PR 流水线天然隔离；
- **Declarative Pipeline**（推荐）：`pipeline { agent/stages/steps/post }` 结构化，内置 `post` 处理成功/失败；**Scripted** 用于极复杂逻辑（2.1.2）；
- **共享库（Shared Library）**：`vars/`（全局步骤，如 `standardPipeline()`）、`src/`（Groovy 类）——**把"构建 Java 服务"的重复逻辑收敛成一条调用**，避免每个仓库复制 200 行 Jenkinsfile；
- **凭据**：`credentials()` 绑定到环境变量/文件，**别把密码写进 Jenkinsfile**；**Agent** 用标签选择（`agent { label 'maven' }`），构建环境用容器（`agent { docker { image 'maven:3.9-eclipse-temurin-21' } }`）。

**GitHub Actions / GitLab CI 的组织**：**可复用工作流**（GitHub `workflow_call`、GitLab `include`/`extends`/`!reference`）、**复合 Action**、**模板仓库**；**分支保护 + 必需检查**（26_git.md 3.1.2）让"流水线通过"成为合并前提。

**设计纪律**：**流水线代码也要测试**（共享库的单元测试、`jenkinsfile-runner`/本地 lint）；**幂等**（重复执行不产生副作用）；**参数化**（环境/版本作为输入，不硬编码）；**失败可诊断**（每步有清晰日志与产物）。

**易错**：共享库一改全公司流水线挂（要版本化/灰度）；Jenkinsfile 里 `sh` 拼接用户输入（命令注入）；PR 流水线能读生产凭据（权限隔离，2.1.1 的 OIDC）；`agent any` 跑到不该跑的节点（标签/资源隔离）。

# 2. 工具与平台

## 2.1 主流工具

### 2.1.1 Jenkins、GitHub Actions、GitLab CI 怎么选？

| 维度 | Jenkins | GitHub Actions | GitLab CI |
|------|---------|----------------|-----------|
| 形态 | 自托管（Controller/Agent） | SaaS + 自托管 Runner | 一体化（GitLab + Runner） |
| 生态 | **插件最多**（历史包袱也最多） | Marketplace Actions 丰富 | 内置 Registry/Review App/安全扫描 |
| 维护成本 | **高**（升级/插件/安全） | 低（托管） | 中（自托管 GitLab） |
| 定制能力 | **最强**（Groovy/任意脚本） | 中（YAML/Action） | 中高（YAML/模板） |
| 内网/合规 | 强（完全自控） | 依赖 GitHub（可自托管 Runner） | 强（私有部署） |
| 适合 | 复杂历史流水线/强定制/内网 | GitHub 生态/开源/云原生团队 | GitLab 全家桶/DevSecOps 一体 |

**选型口径**：**已在 GitHub → Actions（最低摩擦）；已在 GitLab → GitLab CI（一体化）；需要极致定制/存量 Jenkins → 保留但**收敛共享库与安全**（插件升级、凭据管理、Agent 隔离）；**多平台混合**时用"**Git 平台原生 CI + 统一制品/部署层**"避免重复建设。

**成本视角**：托管 CI 的**分钟数/并发额度**在大仓库会变成真金白银；自托管便宜但**人力与安全**是隐形成本——"**总拥有成本 = 额度费 + 维护人力 + 事故成本**"。

**易错**：为"工具先进"迁全家（迁移成本 > 收益）；Jenkins 插件不升级（CVE 重灾区）；托管 Runner 跑私有依赖（网络不通/慢）；把 CI 当"唯一质量保障"（本地钩子/评审同样重要，26_git.md 4.3.1）。

### 2.1.2 Jenkins 的 Scripted 与 Declarative 有什么区别？Agent 与共享库怎么设计？

| 维度 | Scripted | Declarative |
|------|----------|-------------|
| 语法 | Groovy 脚本（`node {}`） | 结构化 DSL（`pipeline { stages { ... } }`） |
| 学习曲线 | 陡（要会 Groovy） | 平缓（声明式） |
| 错误处理 | 手写 try-catch/finally | 内置 `post { always/failure/success }` |
| 校验 | 运行时才报错 | 更早校验/可视化（Blue Ocean） |
| 适用 | 高度动态/复杂逻辑 | **标准流水线（推荐）** |

**Agent 设计**：**Controller 不跑构建**（安全与稳定），构建在 **Agent**（静态 VM/动态 K8s Pod/容器）；用**标签**匹配能力（`maven`/`docker`/`gpu`）；**动态 Agent**（Kubernetes 插件按需起 Pod）省资源但要处理镜像预热与缓存（1.2.1）；**隔离**：每个构建独立工作区（`cleanWs`）、**不要共享可写目录**、限制 `sh` 权限。

**共享库的分层**：`vars/standardJavaPipeline.groovy`（一条龙：build/test/scan/image/publish）+ `src/com/company/...`（工具类）——**业务仓库只写"参数"**（服务名/环境/审批人）；**版本化**（`@Library('ci@v2')`）+ 灰度（先在一条流水线验证）。

**易错**：Controller 上跑 `mvn`（资源与安全双风险）；Agent 用 root/挂 docker.sock（逃逸面，23_docker.md 5.2.2）；共享库无测试（一改全挂）；`post` 里回滚逻辑依赖"上一次成功版本"但没记录（回滚失败）。

### 2.1.3 GitHub Actions 与 GitLab CI 的核心概念怎么对应？

**概念映射**：

| 概念 | GitHub Actions | GitLab CI |
|------|----------------|-----------|
| 流水线定义 | `.github/workflows/*.yml`（Workflow） | `.gitlab-ci.yml`（Pipeline） |
| 触发 | `on: push/pull_request/workflow_dispatch/schedule` | `rules`/`only/except`/`workflow:` |
| 执行单元 | Job（默认并行） | Job（按 stage 串行，stage 内并行） |
| 步骤 | Step（`uses`/`run`） | `script`/`before_script`/`after_script` |
| 复用 | Reusable Workflow / Composite Action | `include`/`extends`/`!reference`/CI 组件 |
| 缓存/产物 | `actions/cache`/`actions/upload-artifact` | `cache:`/`artifacts:` |
| 密钥 | Secrets/Environments | CI/CD Variables（masked/protected） |
| 部署环境 | Environments + protection rules | Environments + Review Apps |
| 自托管 | Self-hosted Runner | GitLab Runner（shell/docker/k8s executor） |

**进阶能力**：**矩阵（matrix）** 多版本并行；**DAG（`needs`）** 跳过 stage 串行限制；**OIDC 联合云凭据**（GitHub/GitLab 都能给云厂商短期 token，**不再存长期 AK**——供应链安全的关键，3.2.2）；**环境审批**（生产 Environment 配 required reviewers）。

**易错**：`on: pull_request_target` 处理不可信代码（可拿到 Secrets，安全大坑）；GitLab 的 `only/except` 与 `rules` 混用（行为混乱）；缓存 key 不带 lock 文件 hash（2.1.1 的坑）；fork PR 默认拿不到 Secrets（需要设计"维护者批准后运行"）。

## 2.2 制品与依赖

### 2.2.1 Nexus、Harbor、Artifactory 怎么分工？

| 工具 | 主战场 | 能力 |
|------|--------|------|
| **Nexus** | **Maven/Java 私服**（也可 npm/PyPI/Docker） | proxy（代理公网）、hosted（内部发布）、group（聚合）；版本与权限 |
| **Harbor** | **容器镜像** | 项目/RBAC、复制、漏洞扫描、不可变 tag、签名（23_docker.md 4.1.2） |
| **Artifactory** | **通用制品**（几乎所有包格式） | 企业级元数据/复制/权限，商业 |

**分工原则**：**依赖（jar/npm）进 Nexus，镜像进 Harbor，二进制/通用包进 Artifactory/对象存储**——**"制品"与"依赖"要分开**：依赖是"别人产的"（proxy 缓存），制品是"我们产的"（hosted，版本化、可追溯、保留策略）。**内网价值**：加速（局域网缓存）、稳定（公网挂了不慌）、合规（依赖白名单/漏洞拦截）。

**治理**：**保留策略**（保留最近 N 个 release + 全部线上版本，SNAPSHOT 定期清理）、**不可变**（release 版本禁止覆盖）、**权限**（谁能发布/删除）、**审计**（谁在何时拉了哪个版本）。

**易错**：把 SNAPSHOT 发到生产（覆盖语义，不可复现）；Harbor 的 tag 可覆盖（开不可变策略，4.1.1 同源）；私服磁盘爆满（清理策略/外置存储，30_linux.md 2.2.3）；依赖全走公网（限流/断网即停摆）。

### 2.2.2 "一次构建、到处部署"怎么落地？不可变制品与版本号怎么管？

**核心原则**：**同一个制品（同一 digest）从测试一路提升到生产**——**绝不"每个环境重新构建"**（重新构建=不同二进制/不同依赖，测试环境验证的就不是生产要跑的东西）。

**落地四步**：
1. **构建一次**：CI 产出 jar/镜像，**镜像按 digest 固定**（`image@sha256:...`），打上**不可变 tag**（版本号 + git sha）；
2. **制品晋级（promotion）**：Dev → Staging → Prod 只改"部署清单里的 digest/tag"（或 Helm values/ArgoCD 的 image 字段），**制品本身不动**；
3. **配置外置**：环境差异走 ConfigMap/配置中心/环境变量（12-factor），**不要为环境重新打包**；
4. **可追溯**：版本号（SemVer）↔ git commit ↔ 构建号 ↔ 镜像 digest ↔ 部署记录——**出问题能反查到"哪次提交、哪条流水线、哪个制品"**。

**版本号策略**：`主.次.补丁` + 预发布（`-rc.1`）+ 构建元数据（`+sha`）；**SNAPSHOT 只用于开发**（不可复现）；**发布 tag 由流水线打**（26_git.md 3.2.1）；**保留最近 N 个可回滚版本**（1.2.1 的回滚账）。

**易错**：CI 里 `latest` 覆盖（无法回滚/审计）；每次部署重新 `mvn package`（"测试过的"和"上线的"不是同一个）；版本号手工改（漏改/冲突）；制品与源码对不上（没有 commit 记录）。

# 3. 测试与质量

## 3.1 测试策略

### 3.1.1 测试金字塔是什么？CI 里各层怎么执行？Testcontainers 解决什么？

**金字塔（按"数量 × 速度 × 成本"）**：

| 层 | 数量 | 速度 | 依赖 | CI 时机 |
|----|------|------|------|---------|
| **单元测试** | 多 | 毫秒 | 无（mock） | **每次 push/PR**（快反馈） |
| **集成测试** | 中 | 秒~分钟 | DB/MQ/HTTP | PR/主干（Testcontainers） |
| **契约测试** | 中 | 秒 | 服务间契约 | PR（消费者驱动） |
| **E2E/UI** | 少 | 分钟 | 完整环境 | **Staging/夜间**（慢且脆） |
| **性能/压测** | 极少 | 分钟~小时 | 类生产 | 发布前/定时 |

**反模式**：**冰淇淋筒**（大量 E2E + 少量单测）——慢、flaky、定位难；正确是**"底层多而快、顶层少而准"**，E2E 只覆盖**关键用户旅程**（下单/支付）。

**Testcontainers（集成测试的正解）**：用 Docker 起**真实依赖**（MySQL/PostgreSQL/Kafka/Redis），测试结束自动销毁——比 H2/嵌入式假货**保真**（SQL 方言/事务/隔离级别都真实）；Spring Boot 里 `@Testcontainers` + `@Container` + `@DynamicPropertySource` 注入连接信息；**CI 需要 Docker**（DinD 或挂 docker.sock，注意安全）。**代价**：启动时间（镜像预热/复用）、资源；**纪律**：一套容器给一个测试类/共享复用、测试数据隔离（3.1.2）。

**契约测试（微服务必备）**：消费者定义"我期望的响应"，生产者在 CI 里验证（Pact）——**避免"改接口→联调才发现"**，比 E2E 快且稳（18_feign.md 的接口契约）。

**易错**：单测连真实数据库（慢且互相污染）；E2E 覆盖所有组合（维护地狱）；集成测试用 H2 代替 MySQL（生产 SQL 跑不过）；测试依赖执行顺序（3.1.2）。

### 3.1.2 不稳定测试（flaky）怎么治理？

**flaky 的危害**：团队开始"重跑直到绿"——**测试失去信任，等于没有**；门禁形同虚设。

**六类根因**：① **时间**（`now()`/时区/超时边界）；② **随机/并发**（线程调度、未加锁共享状态）；③ **测试间污染**（共享数据库/静态变量/端口）；④ **异步等待**（`sleep` 代替条件等待、轮询不稳）；⑤ **外部依赖**（第三方接口/网络抖动）；⑥ **资源竞争**（CI 并行时 CPU/内存/端口冲突）。

**治理五步**：
1. **识别**：记录重跑次数（JUnit `rerunFailingTestsCount` 只是止血）、按测试统计失败率、**建立 flaky 列表**；
2. **隔离**：flaky 测试移出阻塞门禁（quarantine），**限期修复**（不是永久跳过）；
3. **修复根因**：时间注入 `Clock`、唯一测试数据（UUID）、每测试清理、条件等待（Awaitility）、依赖容器化（Testcontainers）；
4. **并行安全**：测试数据按命名空间隔离、端口随机、事务回滚/独立 schema；
5. **防止回归**：新测试评审"是否确定性"、CI 保留失败现场（截图/日志/容器日志）。

**答题收口**："**flaky 不是'测试环境的问题'，是'代码/测试设计的问题'**——重跑是止疼药，隔离+修复才是治疗；一个团队对 flaky 的容忍度，直接决定 CI 的可信度。"

## 3.2 质量与安全门禁

### 3.2.1 SonarQube 怎么接？覆盖率怎么算才不骗人？

**接入三步**：① 项目创建 + token；② CI 里 `mvn sonar:sonar`（或 Scanner）上传分析；③ **Quality Gate**：`waitForQualityGate abortPipeline: true`——**不达标即失败**（门禁必须"能拦住"，否则只是报表）。

**Quality Gate 的常用条件**：**新代码**覆盖率 ≥ 80%、新代码 0 个 Blocker/Critical、重复率 < 3%、安全热点评审完成——**"新代码"口径比"整体"更合理**（存量技术债不阻塞日常提交，但新债不许加）。

**覆盖率不骗人的四招**：① **分支覆盖**（不只行覆盖）；② **排除生成代码/配置类**（Lombok/MapStruct/DTO）；③ **合并集成测试覆盖率**（JaCoCo agent 挂到集成测试，别只算单测）；④ **变异测试（PIT）**抽查"测试是否真能发现 bug"（覆盖率高但断言弱是常见假象）。

**易错**：只上传报告不设门禁（没人看）；覆盖率刷到 100% 但全是 getter/无断言（数字游戏）；把 Sonar 的"代码异味"当"必改"（按严重级别与团队规则分级）；分析耗时拖慢流水线（放主干/夜间，PR 只分析增量）。

### 3.2.2 SAST、DAST、依赖扫描、SBOM、签名怎么组成供应链安全？

**一条"左移 + 纵深"的链**：

| 环节 | 工具 | 拦什么 |
|------|------|--------|
| **代码** | SAST（CodeQL/Semgrep/SpotBugs）、**密钥扫描**（gitleaks） | 注入/硬编码密码/危险 API |
| **依赖** | OWASP Dependency-Check、Dependabot/Snyk、私服代理拦截 | **已知 CVE**（Log4Shell 类） |
| **容器** | Trivy/Grype（镜像层扫描）、基础镜像更新 | OS 包/语言依赖漏洞 |
| **运行前** | DAST（OWASP ZAP）扫测试环境 | 运行时漏洞（XSS/SQLi） |
| **物料** | **SBOM**（Syft/CycloneDX，`buildx --attest`） | "我到底装了什么" |
| **签名** | **cosign** 签镜像 digest | 防篡改/来源可信 |
| **准入** | OPA/Kyverno 验签+策略 | 未签名/高危镜像禁止部署（23_docker.md 4.1.2、32_kubernetes.md 3.2.2） |

**三个关键认知**：① **扫描不是"零漏洞"，是"风险可见 + 可决策"**——高危必须修、中低危有豁免流程（记录原因与期限），否则团队会关掉扫描；② **漏洞是"时间函数"**（今天干净的镜像三个月后可能有新 CVE）——**仓库侧持续扫描 + 定期重建**才有效；③ **身份与凭据**：CI 到云/K8s 用 **OIDC 短期凭据**，别存长期 AK（2.1.3）；**构建环境隔离**（不可信 PR 不给 Secrets）。

**收口**："供应链安全 = **代码可信（评审/SAST）+ 依赖可信（扫描/锁版本）+ 制品可信（SBOM/签名）+ 运行可信（准入/最小权限）**——四段缺一段，攻击者就从缺口进来。"

# 4. 部署与发布

## 4.1 部署策略

### 4.1.1 滚动、蓝绿、金丝雀怎么选？回滚怎么做？

（详细机制见 32_kubernetes.md 5.1.1，这里给"发布决策"视角）

| 策略 | 何时选 | 回滚速度 | 关键前提 |
|------|--------|---------|---------|
| **滚动** | 无状态服务默认、资源有限 | 中（再滚回去） | **新旧版本兼容**（接口/DB/缓存） |
| **蓝绿** | 要**秒级回滚**、版本差异大 | **最快（切流量）** | 双倍资源、DB 兼容、入口切换 |
| **金丝雀** | 高风险变更、需要**真实流量验证** | 快（清零流量） | 流量切分能力（Mesh/Gateway/Argo Rollouts）+ 指标门禁 |

**"自动回滚"的四个层次**：**探针失败**（K8s 自动不切流/重启）；**部署后验证**（错误率/延迟/业务指标超阈值 → 自动 `rollout undo`）；**金丝雀分析**（Argo Rollouts/Flagger 按 Prometheus 指标自动推进/回滚）；**数据层**（**不可自动回滚**——见 4.1.2）。

**发布门禁的指标**：错误率（5xx/异常）、P99 延迟、关键业务指标（下单成功率）、日志错误关键词、探针——**没有指标的金丝雀只是"随机放量"**。

**易错**：只回滚应用不回滚配置（配置错误继续）；回滚镜像但 DB 已迁移（4.1.2）；蓝绿切换忘 DNS/TTL（客户端还打旧 IP）；金丝雀流量按 Pod 比例而非请求比例（长连接下失真）。

### 4.1.2 数据库变更与发布的兼容性怎么处理？

**铁律：数据库变更必须"向后兼容"，且与应用发布解耦**——因为**旧版本代码可能还在跑**（滚动/金丝雀期间新旧共存），而**DB 回滚几乎不可行**（数据已写）。

**Expand-Contract（扩展-收缩）四步**：
1. **Expand**：加新列/新表（**可空/有默认值**）、加索引——旧代码不受影响；
2. **双写/回填**：应用同时写新旧结构，后台任务回填历史数据；
3. **Switch**：新代码读新结构，验证数据一致；
4. **Contract**：确认无旧代码使用后，**下一个版本**再删旧列/旧表（**绝不在同一次发布里删**）。

**发布顺序**：**先跑 DB 迁移（独立 Job/Init Container）→ 再滚动应用**；迁移脚本用 **Flyway/Liquibase** 版本化（可审计/可重放）；**大表 DDL** 走 Online DDL/gh-ost/pt-osc（16_mysql.md 5.1.1），避开高峰。

**回滚策略**：**应用可回滚，DB 只能"向前修复"**——所以每次迁移都要有**回滚脚本或补偿方案**（如加列可保留、删列只能从备份恢复）；**禁止**在发布同一版本做"改列类型/删列/重命名"（旧代码立刻崩）。

**易错**：发布时 `ALTER TABLE` 改字段类型（锁表+旧代码不兼容）；以为"事务能回滚发布"（DDL 隐式提交，16_mysql.md）；回填任务与线上写冲突（加锁/覆盖）；灰度期间新代码读不到旧数据（没有双写/兼容读）。

## 4.2 环境与发布治理

### 4.2.1 多环境怎么管理配置与审批？

**环境分层**：dev（开发自测）→ test/QA（集成）→ staging（**类生产**：同拓扑、脱敏数据、压测）→ prod；**每层用同一个制品**（2.2.2），只差配置与规模。

**配置管理**：环境差异走**配置中心/环境变量/ConfigMap**（12-factor），**镜像内不含环境配置**；**敏感信息**进 Vault/云密钥服务/External Secrets（32_kubernetes.md 3.2.1），**不进 Git 明文**；**配置变更也走评审与回滚**（配置事故和代码事故一样多）。

**审批与权限**：生产部署用**Environment protection**（required reviewers/等待时间/限制分支）；**职责分离**（开发者不能自审自发生产）；**变更窗口/冻结期**（大促、财务结账）；**审计**（谁在何时部署了什么版本——GitOps 的 Git 记录天然可审计，4.2.2）。

**临时环境（Review App）**：每个 PR 起独立命名空间/子域，评审完自动销毁（GitLab Review Apps/Argo CD ApplicationSet）——**评审"看得见"，联调不抢环境**；成本要控制（TTL/资源限额）。

**易错**：staging 与 prod 差异巨大（"测试环境好的，生产挂了"）；生产配置手工改（漂移）；审批人不懂变更内容（形式审批）；临时环境忘记回收（资源泄漏）。

### 4.2.2 GitOps 与 CI/CD 怎么分工？

**分工一句话**：**CI 负责"产出并登记制品"，CD（GitOps）负责"把 Git 里的期望状态同步到集群"**。

```text
开发者 push → CI：测试/构建镜像/扫描/推送 Harbor → 更新"部署清单仓库"里的 image tag（或 ArgoCD Image Updater）
                                              ↓
ArgoCD/Flux（集群内）：监听清单仓库 → 对比集群实际状态 → 自动/手动 Sync → 漂移检测/回滚（git revert）
```

**GitOps 的四个收益**：**单一真相**（Git 即集群状态，审计/回滚天然）、**拉模式更安全**（集群主动拉，CI 不需要集群凭据）、**漂移检测**（手工 `kubectl edit` 会被纠正/告警）、**多集群/多环境**（目录/ApplicationSet 管理）。

**边界**：GitOps 管**声明式资源**（Deployment/Service/ConfigMap）；**数据库迁移/一次性 Job** 仍由 CI 或独立流程触发（`PreSync` hook/Job）；**Secrets** 用 SealedSecrets/External Secrets（不能明文进 Git）；**紧急变更**要留"破窗"流程（事后补 Git）。

**易错**：CI 直接 `kubectl apply`（集群凭据散落、无漂移检测）；GitOps 同步了但应用没起来（只看 Sync 状态不看 Health）；`selfHeal` 把调试中的手工改动改回去（调试用暂停同步）；清单仓库与代码仓库版本不联动（image tag 更新遗漏）。

### 4.2.3 Feature Flag 与渐进式交付怎么用？

**核心价值**：**把"部署（deploy）"与"发布（release）"解耦**——代码可以先上生产但**开关关闭**，按需对用户/租户/比例打开。

**四种典型用法**：**灰度放量**（按用户 ID 哈希/白名单/百分比）；**A/B 实验**（不同策略对比指标）；**Kill Switch**（出问题一键关功能，不用回滚部署）；**Trunk-based 开发**（未完成功能藏在开关后，短命分支，26_git.md 3.1.1）。

**工程纪律**：
1. **Flag 有生命周期**：上线稳定后**删除开关与死代码**（flag debt 会指数增长）；
2. **默认安全**：开关服务不可用时用"安全默认值"（关闭新功能/降级）；
3. **可观测**：每个 flag 的曝光与业务指标绑定（不然灰度无意义）；
4. **测试**：开关的开/关两种路径都要测（别只测开启态）；
5. **权限**：谁能改生产 flag（审计/审批）。

**工具**：Unleash（开源自托管）、LaunchDarkly（商业）、FF4J、云厂商配置中心；轻量场景用配置中心（17_nacos.md）+ 代码判断即可，**不必上重平台**。

**易错**：flag 永久留着（代码里几十个 if，没人敢删）；flag 判断放在核心链路高频处（性能/一致性）；灰度按"实例"而非"用户"（同一用户体验跳变）；没有"关闭时的降级路径"。

# 5. 度量与实践

## 5.1 度量

### 5.1.1 DORA 四指标是什么？怎么用才不变成"KPI 表演"？

**四个指标（DORA/Accelerate 的研究结论：交付速度与稳定性正相关，不是取舍）**：

| 指标 | 定义 | 说明 |
|------|------|------|
| **部署频率（Deployment Frequency）** | 多久部署一次生产 | 高绩效团队"按需/每天多次"；低绩效"每月或更少" |
| **变更前置时间（Lead Time for Changes）** | 从提交到生产运行的时长 | 衡量"从代码到用户"的流速（含评审/排队/构建/审批） |
| **变更失败率（Change Failure Rate）** | 导致故障/回滚/热修的部署占比 | 衡量"发布质量"（不是"故障总数"） |
| **恢复服务时间（Time to Restore）** | 从故障到恢复的时长 | 衡量"发现+响应+修复"能力（MTTR 的 DORA 口径） |

**四指标的组合含义**：**部署频率低 + 变更失败率高 + 恢复慢 = 典型的"大爆炸发布"组织**（一次上很多、出问题不敢动）；**高频 + 低失败 + 快速恢复 = 小步快跑 + 自动化兜底**。**关键认知**：DORA 度量的是**系统能力（流程/自动化/文化）**，不是"某个人的绩效"——拿来排名就必然被 gaming（刷小变更、拆分部署、隐瞒故障）。

**怎么用（改进闭环）**：先**基线测量**（别一上来定目标）→ 找**瓶颈**（前置时间长？多半卡在评审/环境/手工测试；恢复慢？多半缺可观测/回滚）→ 做**能力建设**（自动化测试、小批量、特性开关、可观测、演练）→ 再看指标是否改善。**配套指标**：流水线时长/排队、评审时长、测试 flaky 率、MTTD（发现时间）——它们是"过程指标"，比结果指标更可操作。

**易错**：把"部署次数"当唯一目标（天天发空包）；把变更失败率算成"所有 bug"（DORA 只算"由变更导致的故障"）；用 DORA 做部门排名（数据失真+文化毒化）。

## 5.2 综合

### 5.2.1 设计一条从提交到生产的完整流水线（Java 微服务），怎么落地？

**分三条流水线（PR / 主干 / 发布），对应不同节奏**：

```text
【PR 流水线（<10 分钟，必过门禁）】
checkout（浅克隆）→ 缓存 .m2 → 编译 + 单测（并行分片）→ 静态检查/格式
→ 依赖漏洞扫描 + 密钥扫描 → 契约测试 → （可选）构建镜像验证
→ SonarQube 增量分析 + Quality Gate（新代码覆盖率/0 高危）
→ 失败：阻断合并（branch protection + required checks）

【主干流水线（合并后，全量）】
全量单测 + 集成测试（Testcontainers：MySQL/Kafka/Redis）
→ Sonar 全量 + 质量门 → 构建镜像（BuildKit 缓存）→ Trivy 扫描
→ cosign 签名 + SBOM + provenance → 推送 Harbor（digest 固定 + 不可变 tag）
→ 更新 GitOps 清单仓库的 image digest（或 ArgoCD Image Updater）

【CD（GitOps + 渐进式）】
ArgoCD 同步 Dev → 冒烟测试 → 自动晋升 Staging → 回归/压测
→ 生产审批（Environment protection）→ Argo Rollouts 金丝雀（5%→25%→50%→100%）
→ 每步校验指标（错误率/P99/业务成功率）→ 异常自动回滚（git revert/rollout abort）
→ 发布后观察窗口 → 通知 + 记录发布版本
```

**必须配套的六件事**：① **DB 迁移独立 Job**（Flyway/Liquibase，Expand-Contract，4.1.2）；② **配置/密钥外置**（ConfigMap/Vault/OIDC）；③ **可观测**（Prometheus/日志/trace，指标驱动金丝雀，32_kubernetes.md 5.2.2）；④ **特性开关**（部署与发布解耦，4.2.3）；⑤ **回滚预案**（镜像/配置/数据三层，4.1.1）；⑥ **权限与审计**（谁能发生产、发了什么版本）。

**答题技巧**：先说"**三条流水线 + 制品一次构建**"的骨架，再挑 2~3 个点讲深（如"金丝雀的指标门禁"或"DB 兼容"）——**比罗列工具更有说服力**。

### 5.2.2 发布导致的事故怎么复盘？怎么防止"同样的坑再踩"？

**复盘（Blameless Postmortem）五段式**：
1. **事实与影响**（时间线、影响用户/订单/时长、SLO 损失）——**先对齐事实，不评价人**；
2. **根因分析**（5 Whys/故障树）：直接原因（如配置错）→ 流程原因（为什么没拦住）→ 系统原因（为什么这个错误"可发生"）；
3. **处置复盘**（发现→响应→恢复各花了多久，哪个环节慢：监控没告警？回滚不熟？权限不在？）；
4. **行动项**（**可执行、有 owner、有截止**：加配置校验/加金丝雀门禁/加告警/补演练；避免"加强责任心"这种不可执行项）；
5. **沉淀**（runbook/测试用例/自动化检查——**把教训变成系统能力**，而不是文档里的一句话）。

**防止复发的手段（按有效性排）**：**自动化门禁**（配置 schema 校验、发布前 diff、金丝雀指标）> **演练**（回滚演练/故障注入/混沌工程）> **流程**（审批/冻结期）> **培训**（最弱）。**"人不可能不犯错，系统要假设人会犯错"**——这是复盘文化的核心。

**发布事故的常见根因（提前布防）**：配置差异（staging≠prod）、DB 不兼容（4.1.2）、依赖版本漂移（锁版本+私服）、容量不足（压测）、回滚没演练、监控盲区（业务指标没埋）。

**易错**：复盘变成"批斗会"（隐瞒真相）；行动项全是"加强测试"（没有具体动作）；复盘完不跟踪（同样事故半年后重演）；只修直接原因不修流程（下一个配置照样错）。

### 5.2.3 CI/CD 的常见反模式有哪些？

**十条"看起来在 CI/CD，其实在制造风险"**：

1. **雪花环境/手工改生产**：配置漂移，重建不出来——用 IaC/GitOps（4.2.2）；
2. **每个环境重新构建**：测试的不是上线的那个二进制——一次构建、制品晋级（2.2.2）；
3. **长命分支 + 大爆炸合并**：集成地狱、评审失真——trunk-based/短命分支（26_git.md 3.1.1）；
4. **一条巨长的流水线**：30 分钟才反馈，开发者绕过——拆 PR/主干/发布（5.2.1）；
5. **没有测试或"CI 剧场"**：绿灯但没验证——测试金字塔 + 门禁（3.1）；
6. **Secrets 进代码/日志**：泄露——密钥管理 + 扫描（3.2.2）；
7. **没有回滚/回滚没演练**：出事只能"向前修"——回滚预案 + 演练（4.1.1）；
8. **审批形式化**：点同意的人不看内容——审批 + 自动化验证结合（4.2.1）；
9. **忽略 flaky**：重跑直到绿，门禁失效——隔离+修复（3.1.2）；
10. **流水线是"某个人的黑盒"**：只有一人会改——Pipeline as Code + 共享库 + 文档（1.2.2）。

**两个"伪反模式"（要会辩证）**：**"周五不发布"**——如果流程成熟（小批量/自动回滚/值班），周五发布不是问题；若靠人肉兜底，任何时间都危险；**"审批"**——合规场景必需，但**审批不能替代自动化**（它只提供责任归属）。

**收口句**："**CI/CD 的成熟度不看工具多新，看三件事：反馈多快、制品可不可信、故障能不能快速恢复**——这三件事做好，工具只是壳。"
