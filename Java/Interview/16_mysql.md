# 1. 架构与存储引擎

## 1.1 体系架构

### 1.1.1 MySQL 的整体架构是怎样的？

**四层结构（自上而下）**：

1. **连接层**：TCP 网络处理、身份认证（账号+密码+host）、权限校验，**每个连接对应一个线程**，thread cache 复用线程避免频繁创建；`max_connections`/`wait_timeout` 在这一层，连接池（Hikari）正是为压制"连接开销+连接数上限"而生；
2. **服务层**：
   - **SQL 接口**：识别 DML/DDL/DCL；
   - **查询缓存**：key=SQL+结果，任何更新即失效、命中率极低——**8.0 彻底移除**（旧简历写"调 query_cache_size"已属过时知识）；
   - **解析器**：词法分析 → 语法分析 → 解析树 → 预处理器（检查表/列存在、语义合法性）；
   - **查询优化器（CBO）**：基于成本选执行计划——索引选择、join 顺序、子查询转换（IN→semi-join）、常量折叠；统计信息（直方图/索引基数）不准是"优化器选错索引"的头号根因；
   - **执行器**：按执行计划调用存储引擎接口逐行取数、过滤、返回；
3. **引擎层**：**可插拔**，经 Handler API 与上层交互（InnoDB/MyISAM/Memory 行为差异都在这层，见 1.2.1）；
4. **存储层**：数据文件（.ibd）、redo/undo/binlog、配置文件物理落盘。

**分层设计的好处**：SQL 语义与存储实现解耦——换引擎不改 SQL、优化器可针对不同引擎能力选择下推策略。

### 1.1.2 一条 SQL 从客户端到返回结果经历了什么？SELECT 和 UPDATE 有什么不同？

**SELECT**：客户端 → 连接器（认证/权限）→（8.0 无查询缓存）→ 解析器/预处理器 → 优化器 → 执行器循环调引擎 `read_row` → InnoDB 判断页在 Buffer Pool 与否（不在则读盘）→ 按 MVCC 可见性返回行 → 结果集回传。

**UPDATE** 多出的关键步骤（顺序即 WAL 精髓）：

1. 取行（当前读，加锁）；
2. **写 undo log**（记录旧版本，供回滚与 MVCC）；
3. Buffer Pool 中改数据页（变脏页）；
4. **写 redo log（prepare 状态）**；
5. 写 **binlog** 并 fsync；
6. **redo log 标记 commit**——两阶段提交把"引擎自己的恢复能力"和"Server 层的归档/复制"缝在一起（见 4.1.2）。

**易错**：① "先查更新列再更新"是**当前读**，会看到最新值而非快照；② 脏页不是提交就刷盘——checkpoint + LRU 回收异步刷（1.2.2），崩溃靠 redo 前滚，所以"提交即持久"承诺由 redo 而非数据页兑现。

## 1.2 InnoDB 与内存结构

### 1.2.1 InnoDB 和 MyISAM 的区别？为什么 InnoDB 成为默认？

| 特性 | InnoDB | MyISAM |
|------|--------|--------|
| 事务 | ACID 完整（undo+redo） | 无 |
| 锁 | **行锁**（+MVCC 读写不互斥） | 表锁（读写互斥） |
| 外键 | 支持 | 不支持 |
| 索引组织 | **聚簇**（数据按主键组织） | 非聚簇（数据/索引分离 .MYD/.MYI） |
| 崩溃恢复 | redo 自动恢复（crash-safe） | 需 repair，易坏 |
| count(*) | 需扫描（MVCC 可见性逐行判） | 元数据计数器 O(1) |
| 全文索引 | 5.6+ | 早期独有（8.0 前） |
| 空间/压缩 | 表空间文件 .ibd | 三文件 |

**结论**：8.0 连系统表都已 InnoDB 化，MyISAM 仅剩存量兼容场景；选型无须纠结——除非"只读/静态、以 count 和简单查询为主"的极端场景。Memory 引擎（重启全丢、哈希索引）基本被"临时表 + TempTable 引擎"取代。

### 1.2.2 Buffer Pool、Change Buffer、自适应哈希索引分别是什么？

- **Buffer Pool**：InnoDB 的页缓存（默认 16KB/页），数据页与索引页都经它访问，命中率决定数据库"快不快"。**改进版 LRU** 防全表扫描污染：链表分 **young 5/8 + old 3/8**，新页进 **old 区头部**，在 old 区停留超 `innodb_old_blocks_time`（默认 100ms）后再次访问才晋升 young 头部——一次全表扫描灌进来的页会在 old 区被"验证"淘汰，不冲垮热点数据。另有 **flush list**（脏页链表，checkpoint 依据）与**预读**（线性连续读到阈值后多读 8 页）。
- **Change Buffer**：对**非唯一二级索引**的插入/修改，若目标索引页不在 Buffer Pool，先缓存在 change buffer（Buffer Pool 内独立区域），等页被读入时合并——把"随机读+随机写"换成"顺序写+延后合并"。**适合写多读少**；写后立即范围读该列、唯一索引、以及写极密集导致合并频繁时收益倒挂（`innodb_change_buffering` 可调，8.0.32 后改名 `innodb_change_buffering_hot` 语义收紧）。
- **自适应哈希索引（AHI）**：InnoDB 统计热点索引页，**自动**在 B+ 树之上建哈希索引加速**等值**查询（不支持范围/排序），系统行为不可手工干预——对 B+ 树的"补充而非替代"，哈希结构本身不能做主索引的原因见 2.1.1。

### 1.2.3 Double Write（双写缓冲）解决什么问题？

**问题：部分写失效（torn page）**——InnoDB 页 16KB，磁盘扇区 512B/4KB，刷脏页中途断电可能"页写了一半"；redo 是**整页物理变更**的日志，半坏页连页头都不可靠，无法直接前滚恢复。

**机制**：刷脏页前先**顺序**写入共享的双写缓冲区并 fsync → 再离散写入各自数据文件。崩溃恢复：redo 前滚前先校验页完整性，坏页用双写区副本覆盖；双写区本身损坏则原页完好，redo 照常恢复。

**代价与演进**：等于页"写了两次"，顺序写部分对 SSD 影响有限；支持**原子写**的设备（Fusion-io、部分 NVMe 场景）可关 `innodb_doublewrite`；8.0.20+ 双写缓冲独立文件（不再占 ibdata1，避免热点争用）。

# 2. 索引

## 2.1 数据结构与成本模型

### 2.1.1 为什么 InnoDB 用 B+ 树而不是 B 树、红黑树、跳表或哈希？

**磁盘索引的第一性约束：树高 ≈ IO 次数**——每次下探读一页。

| 对比 | 为什么 B+ 树胜出 |
|------|------------------|
| vs B 树 | B+ **非叶只存 key**（扇出更大、树更矮）；叶子双向链表（范围查询顺序遍历，B 树要中序回跳）；同数据量下非叶层 IO 更少 |
| vs 红黑树/AVL | 二叉树千万级数据高约 24 层 = 24 次随机 IO；B+ 树 3 层装下千万级（见 2.1.2） |
| vs 跳表 | 跳表是"内存链表+索引"，指针密集、节点分裂要连锁调整，落盘后局部性差；Redis/BoltDB 选它是因为内存场景并发简单 |
| vs 哈希 | 等值 O(1) 漂亮，但**范围/排序/LIKE 前缀全废**，冲突链退化；Memory 引擎/自适应哈希（1.2.2）只在"纯等值热点"补充 |

**结论句**：B+ 树=矮（IO 少）+ 叶子链表（范围友好）+ 页内有序二分（内存定位快）三者兼得，是磁盘关系型的必然选择。

### 2.1.2 一棵 B+ 树能存多少数据？树高对查询有什么影响？

**估算模型**（InnoDB 页 16KB，行 1KB）：

- 非叶节点存"key + 页号"（bigint 主键约 8+3=11 字节，按 ~16B 算）：一页 ≈ 1000 个路标；
- 叶节点存整行 1KB：一页 ≈ 16 行；
- **树高 2**：1000 × 16 ≈ 1.6 万行；**树高 3**：1000 × 1000 × 16 ≈ **1600 万行**（千万级数据 3 层封顶）。

**工程含义**：

1. 主键查最坏 3 次页 IO，且**根页常驻内存**（Buffer Pool），实际多数 1~2 次；
2. 行越窄/主键越短 → 叶页装更多行、非叶扇出更大 → 更矮；**用 UUID 做主键会让聚簇索引变胖**（主键 36B vs 8B）——这是它被诟病的又一层原因（2.2.6）；
3. "单页行数"决定范围扫描物理连续性：聚簇索引下主键区间扫描 = 顺序读相邻页，代价低。

## 2.2 索引模型与使用规则

### 2.2.1 什么是聚簇索引、二级索引和回表？

- **聚簇索引**：叶子存**整行**——"索引即数据"，InnoDB 表就是一棵聚簇索引（没有显式主键则依次选：NOT NULL 唯一索引 → 隐藏 6 字节 rowid 生成的假主键索引，所以**每张表必须有主键**是工程铁律）；
- **二级索引**：叶子存"索引列 + 主键值"；经二级索引找到主键后，再进聚簇索引取完整行——**回表**，一次逻辑查询两次 B+ 树下降；
- 回表代价模型：二级索引筛出的主键越多，聚簇索引随机 IO 越多——"命中率高、返回行多"的二级索引反而可能不如全表顺序扫描（优化器据此放弃索引，见 2.2.5）。

**延伸**：InnoDB"索引有序性"与主键单调性直接影响插入形态——乱序主键（UUID）在叶子层**页分裂 + 碎片 + change buffer 失效**式放大写；单调自增/趋势递增雪花追加在链尾（2.2.6）。

### 2.2.2 什么是覆盖索引和索引下推（ICP）？

**覆盖索引**：查询需要的列**全部**在所用索引里（二级索引叶子的"列+主键"已够），EXPLAIN Extra 显示 `Using index`——**免回表**，深分页/列表页"只查 id"都靠它。注意它是"查询与索引的配合关系"，不是索引种类。

**索引下推（Index Condition Pushdown，5.6+）**：`WHERE a>10 AND b=5` 用联合索引(a,b)——a>10 之后 b 不再满足最左连续可用，5.5 以前会把 a>10 的行全部回表、在服务层过滤 b；5.6 起在**引擎层遍历索引时先用索引里已有的 b 值过滤**，只回 b=5 的行：

```text
MySQL 5.5:  a>10 → 全部回表 → 服务层过滤 b=5
MySQL 5.6+: a>10 → 索引内过滤 b=5 → 仅命中行回表   Extra: Using index condition
```

效果：回表次数锐减。前缀索引与 ICP 的配合（5.7 后支持）见 2.2.4。

### 2.2.3 联合索引的最左前缀原则是什么？范围条件后会怎样？

**结构决定语义**：联合索引 (a,b,c) 先按 a 排，a 同再按 b、c 排——只有从最左列开始的条件组合才能利用有序性二分定位。

```sql
WHERE a=1                  -- 用 a
WHERE a=1 AND b=2          -- 用 a,b
WHERE a=1 AND b>2 AND c=3  -- 只能用到 a,b（b 是范围，排序连续性断了）；
                           -- c 的条件可走 ICP 在索引层过滤，不产生"定位"作用
WHERE b=2                  -- 不走 (a,b,c)（除非 8.0.13 skip scan）
ORDER BY a, b              -- 可用索引序；ORDER BY b 不可
ORDER BY a ASC, b DESC     -- 需 8.0 降序索引才免 filesort（见 5.2.5）
```

**误区修正**："b>2 AND c=3 完全没用"不准确——b 的范围扫描 + c 的 ICP 过滤仍显著减少回表；"ORDER BY a, c WHERE b=5 一定 filesort？"b=5 不锁序，是的。**8.0.13+ Skip Scan**：第一列基数极低（如性别）时可"跳跃分组"替代最左，EXPLAIN 显示 `Using index for skip scan`。

### 2.2.4 前缀索引适合什么场景？有什么限制？

长文本列（URL/描述）用 `column(N)` 只索引前 N 字符，省空间提扇出。**N 的定法**——比较区分度：

```sql
SELECT COUNT(DISTINCT LEFT(url, 6)) / COUNT(*) FROM t;   -- 逐列试算，接近整列值即可
```

**四条限制**：① 不支持覆盖索引（索引里没有完整值，取该列必回表）；② `ORDER BY 该列` 无法用（前缀序≠全列序）；③ 5.7 前前缀列不支持 ICP；④ N 取太小→大量等值前缀进"页内再比较/回表验证"，失去过滤意义。

**替代方案**：CRC32/MD5 哈希列 + 原值精查（哈希冲突时仍要比对原值）；真·全文场景用全文索引或外置 ES（见 24_elastic_search.md）。

### 2.2.5 索引失效的常见场景有哪些？优化器为什么不选索引？

**规则侧失效**：

1. 对索引列用函数/表达式：`WHERE YEAR(create_time)=2024`（改区间：`create_time >= '2024-01-01' AND < '2025-01-01'`）或建**生成列+索引**；
2. 列参与运算：`id+1=10`；
3. **隐式类型转换**：varchar 列 `phone=13800000000`（无引号）——列侧被 CAST 函数包裹失效；int 列用数字、字符串列用字符串；**字符集/collation 不一致**（utf8 vs utf8mb4、_ci vs _bin）连 join 列都能废掉索引；
4. LIKE 左模糊 `%xx`；
5. 联合索引不满足最左；
6. OR 连接了非索引列；
7. `!= / NOT IN` 不"必然"失效——命中值极少时优化器仍会用（见下）。

**成本侧放弃**：二级索引方案 = 回表随机 IO 成本对比全表顺序扫描，命中行比例高（经验值 >20%~30%）或表很小时**全表更快**；统计信息（索引基数）过期误判——`ANALYZE TABLE` 刷新。**8.0 直方图**（`column_statistics`）给非索引列分布信息辅助决策。**隐藏索引**验证法（5.2.5）："删索引会不会出事"用 `ALTER TABLE ... ALTER INDEX ... INVISIBLE` 灰度一周再真删，是索引治理的正确姿势。

### 2.2.6 主键用自增、UUID 还是雪花？

| 维度 | 自增 | UUID(36/二进制16) | 雪花(64bit) |
|------|------|-------------------|-------------|
| 插入局部性 | **最佳**（尾部追加） | 最差（随机页分裂、碎片、写放大） | 较好（趋势递增） |
| 聚簇索引体积 | bigint 8B | 16~36B，**所有二级索引跟着膨胀**（叶子都存主键） | 8B |
| 分库分表 | 各库撞号（需步长/号段，见 22_sharding_sphere.md） | 全局唯一 | 全局唯一，可反解时间 |
| 暴露业务量 | 是（可枚举爬取） | 否 | 可加偏移混淆 |
| 依赖 | 无 | 无 | 时钟（回拨见 9_mybatis_plus.md 3.1.2） |

**实践口径**：对外暴露的实体主键（订单/用户）→ 雪花/号段（业务可读性再叠编码）；内部单库小表 → bigint 自增；**别用 UUID 字符串做主键**——性能账本（页分裂+二级索引膨胀）在千万级表上都是真金白银。自增耗尽与 ID 生成器详见 5.2.4。

# 3. 事务、MVCC 与锁

## 3.1 事务与隔离级别

### 3.1.1 ACID 四大特性在 MySQL 里靠什么实现？

| 特性 | 机制 | 一句话 |
|------|------|--------|
| 原子性 A | **undo log** | 事务要么全做要么全不做——回滚日志把已做操作"逆序撤销" |
| 一致性 C | AID 共同保障 + 业务约束 | 事务前后数据满足约束（唯一键/外键/业务不变量）——**C 是目的，ABD 是手段** |
| 隔离性 I | **锁 + MVCC** | 并发事务互不干扰：读写靠 MVCC 快照互不阻塞，写写靠锁排队 |
| 持久性 D | **redo log（WAL）+ 刷盘策略 + double write** | 提交即持久——先写日志再写页，宕机前滚恢复 |

**答题进阶**：被追问"为什么 redo 能保证持久性而数据页不能"——数据页**随机 IO 且可能写一半**（1.2.3），redo 是**顺序追加写 + fsync**，提交点以 redo 落盘为准。

### 3.1.2 四个隔离级别分别解决什么问题？怎么实现的？

| 级别 | 脏读 | 不可重复读 | 幻读 | 实现手段 |
|------|------|-----------|------|---------|
| READ UNCOMMITTED | ✗ 可发生 | ✗ | ✗ | 读不加锁、直接读最新（含未提交） |
| READ COMMITTED | ✓ | ✗ 可发生 | ✗ | **语句级**新快照（MVCC） |
| REPEATABLE READ（InnoDB 默认） | ✓ | ✓ | 基本抑制 | **事务级**快照 + Next-Key Lock |
| SERIALIZABLE | ✓ | ✓ | ✓ | 读写全部加锁串行 |

三类异常定义要能脱口而出：**脏读**=读到别人未提交（会回滚）的数据；**不可重复读**=同事务两次读同一行结果不同（UPDATE 导致）；**幻读**=同事务两次范围读，行数"多出来"（INSERT 导致）——"行变了"vs"行多了"是区分关键。

Oracle 默认 RC、SQL Server 默认 RR、MySQL 默认 RR——跨库迁移时隔离级别假设要重审（RC 下间隙锁消失，锁冲突模式完全不同，见 3.2.2）。

### 3.1.3 MVCC 的实现原理是什么？

**三件套：隐藏列 + undo 版本链 + ReadView**。

1. **隐藏列**：每行带 `DB_TRX_ID`（最后修改它的事务 id）、`DB_ROLL_PTR`（指向 undo log 里的上一版本）——同一条记录被修改时旧版本留在 undo 链上，形成**版本链**；
2. **ReadView**：快照读（普通 SELECT）时生成的"可见性名单"：`m_ids`（生成时刻活跃未提交的事务集合）、`min_trx_id`（最小活跃）、`max_trx_id`（下一个将分配的）、`creator`；
3. **可见性判断**（沿版本链从新到旧找第一个可见版本）：
   - trx_id == creator → 自己改的，可见；
   - trx_id < min_trx_id → 早已提交，可见；
   - trx_id ≥ max_trx_id → ReadView 之后才开的事务，不可见；
   - 中间 → 在 m_ids 里？未提交不可见；不在？已提交可见；
4. 全链不可见 → 该行对本事务不存在（快照语义）。

**收益**：读不加锁、读写不互斥——"MVCC 把锁竞争降级为版本选择"。代价：长事务让版本链拉长、undo 膨胀不能 purge（见 3.2.3 死锁题外的经典追问——**为什么不要开长事务**）。

### 3.1.4 RC 和 RR 的 MVCC 区别在哪？RR 真的杜绝幻读了吗？

**ReadView 生成时机是分水岭**：

- **RC**：每条 SELECT **重新生成** ReadView → 别的事务中途提交的新版本会被看到（不可重复读）；
- **RR**：事务**第一条快照读**生成后**一路复用** → 整个事务内快照一致（可重复读）。

**RR 与幻读的完整答案（高频深挖）**：

1. **快照读**下：MVCC 固定 ReadView，新插入的行不在版本可见范围——**看不到幻影**；
2. **当前读**下（UPDATE/DELETE/FOR UPDATE）：靠 **Next-Key Lock** 锁住"范围+间隙"（3.2.2），别人插不进来——**常规场景防住**；
3. **仍会出现的缝隙**：事务先快照读（没加锁），另一事务插入并提交一行，本事务随后**对该行所在范围执行 UPDATE**——当前读看到幻影并把更新作用在新行上，随后再快照读还能"看见它被改了"——**快照读与当前读混用时 RR 防不住**。补救：`SELECT ... FOR UPDATE` 提前锁范围，或升级 SERIALIZABLE。

**为什么 MySQL 默认 RR**：历史原因是 STATEMENT binlog 下 RC 有主从不一致风险（不确定的执行顺序）；ROW 格式普及后该约束消失——**互联网主流实践改为 RC**：无间隙锁 → 锁冲突/死锁少、支持并发插入热点行、配合业务幂等即可；改 RC 前评估依赖"可重复读语义"的代码。

## 3.2 锁机制

### 3.2.1 InnoDB 有哪些锁？

| 锁 | 粒度/对象 | 要点 |
|----|----------|------|
| 表锁 | 整表 | DDL、MyISAM 主战场；意向锁 **IS/IX** 属于表锁层——"表内某行已有 S/X"的登记牌，让表级加锁不必逐行扫 |
| 行锁 Record Lock | **索引记录** | S（共享读）/X（排他写）；`SELECT ... LOCK IN SHARE MODE / FOR UPDATE`、DML 自动加 |
| Gap Lock | 记录间**间隙** | 只存在于 **RR**，间隙间互相兼容（都能持有同一间隙的 gap），专门拦插入 |
| Next-Key Lock | Record + Gap，左开右闭 (a, b] | RR 下**默认加锁单位**，防幻读主力 |
| 插入意向锁 | 间隙上的 INSERT 意图 | 本质是"特殊 gap"——与 gap 锁冲突（插不进去就等），插入意向锁之间不互斥（同间隙可并发插不同值） |
| 自增锁 AUTO-INC | 表级 | `innodb_autoinc_lock_mode`：0 传统（statement 级锁）/1 连续（普通 insert 轻量互斥、批量语句仍表锁）/**2 交错**（并发最好，8.0 默认；ROW binlog 才可用） |

**补充**：MDL（元数据锁，DDL 与 DML 互斥的"隐形杀手"，见 5.2.1 Online DDL 阻塞链）；TLS（事务级只增不减，不是两阶段锁协议）。

### 3.2.2 不同查询场景下加锁规则是什么？

**RR 下标准模型（以索引上"值点+间隙"表示）**：

| 场景 | 锁 |
|------|-----|
| 唯一索引等值，**命中** | 单行 Record Lock（next-key 退化） |
| 唯一索引等值，**未命中** | 该值两侧 Gap Lock（防插入幻象） |
| 非唯一索引等值，命中 | 命中行 Next-Key Lock + **向后扫到第一个不满足等值的记录，锁其前方 gap**（扫描线右侧的"下一行"是边界哨兵——经典死锁源） |
| 范围查询 | 覆盖区间逐段 Next-Key + 右端哨兵 gap；**走不了索引（无索引列/失效）→ 全表聚簇索引 next-key ≈ 锁全表** |
| UPDATE/DELETE 走二级索引 | 二级索引上加锁 + **回表处聚簇索引也加锁**（主键冲突死锁高发） |

**RC 差异**：gap lock 基本消失（仅外键/唯一冲突检测保留），只锁命中行——"锁冲突少一半"就是 RC 被互联网选用的直接理由。8.0 的 `innodb_locks_unsafe_for_binlog` 时代描述已过时。

### 3.2.3 死锁如何产生？怎么排查和预防？

**经典案例**：两个事务反向锁两行——`T1: update id=1 → update id=2`、`T2: update id=2 → update id=1`，互相等对方持有的 X 锁。InnoDB 有**等待图（waits-for）检测**，发现环路即回滚**undo 量小**的一方（错误码 1213），另一方继续。

**排查**：

1. `SHOW ENGINE INNODB STATUS` → `LATEST DETECTED DEADLOCK` 段：两个事务、各自 HOLD/LOCK WAIT 的锁与 SQL；
2. `information_schema.innodb_trx`（当前事务）、`performance_schema.data_lock_waits`（8.0 替代旧 innodb_lock_waits）实时等待链；
3. `innodb_print_all_deadlocks=ON` 把**所有**死锁打进 error log（生产必开）；
4. 应用侧：捕获 `DeadlockLoserDataAccessException` 做**重试**（死锁是并发常态，不是 bug）。

**预防**：

1. **固定加锁顺序**（多行更新按主键升序）；
2. 事务尽量短小、隔离级别降级 RC（消灭 gap）；
3. 更新走索引、别用无索引列条件更新（锁全表放大器）；
4. 热点行拆分行/异步串行化（见 27_redis.md 库存方案）；
5. `innodb_lock_wait_timeout` 兜底（默认 50s 太长，业务侧 5~10s）。

**追问**：死锁 vs 锁等待？——没有环路只是排队，`data_lock_waits` 长链 = 某慢事务持锁不放（undo 膨胀/长事务，回看 3.1.3 代价），不是死锁但更危险（不自动回滚）。

### 3.2.4 乐观锁和悲观锁怎么选？并发扣减库存怎么写？

- **悲观锁**：`SELECT ... FOR UPDATE` 先锁再算再写——冲突高、强一致场景，吞吐受行锁排队限制；
- **乐观锁**：version 字段 CAS（`UPDATE ... SET x=?, version=version+1 WHERE id=? AND version=?`，0 行=冲突）——**读多写少**；冲突高重试雪崩。
- **最优解往往是"无锁原子语句"**：`UPDATE stock SET num=num-1 WHERE sku_id=? AND num>0`——单行 UPDATE 本身是原子的（行锁瞬时），`num>0` 兼当业务条件，**无需显式 version 也无需 select for update**；超高并发再把扣减前置到 Redis（Lua 原子预扣，见 27_redis.md），DB 异步落账。MP 的 @Version 用法见 9_mybatis_plus.md 3.2.3。

# 4. 日志体系

## 4.1 日志总览

### 4.1.1 MySQL 有哪些日志？各自作用？

| 日志 | 层级 | 内容/方式 | 用途 |
|------|------|----------|------|
| **binlog** | Server | 逻辑变更，**追加写** | 主从复制、数据恢复（PITR）、CDC 订阅（见 14_canal.md） |
| **redo log** | InnoDB | 数据页物理变更，**循环写**（4 个 ib_logfile 环形组） | 崩溃恢复（crash-safe，WAL 前滚） |
| **undo log** | InnoDB | 逻辑逆操作（INSERT→DELETE、UPDATE→旧值），版本链 | 事务回滚 + MVCC 快照（见 3.1.3） |
| **relay log** | Slave | 从 IO 线程收到的 binlog 副本，SQL 线程重放后删除 | 复制中间缓冲 |
| **slow query log** | Server | 超 `long_query_time` 的语句（含扫描行/锁等待） | 慢 SQL 治理入口（见 5.1.2） |
| **error log** | Server | 启停/运行错误、死锁记录 | 故障排查第一现场 |
| general query log | Server | 所有语句 | 仅调试（性能损耗大，生产关闭） |

**redo log 循环写模型**：write pos 追 checkpoint 年龄——checkpoint 前移 = 脏页刷完一段 redo 可覆盖；**脏页刷不动 → redo 写满 → 全库停写**（checkpoint age 逼近 100% 是事故信号，调大日志总量 `innodb_redo_log_capacity`〔8.0.30+ 替代 file_size×num_files〕或提刷盘能力）。

### 4.1.2 binlog 三种格式怎么选？

| 格式 | 记录 | 优点 | 缺点 |
|------|------|------|------|
| STATEMENT | SQL 原文 | 日志量小 | `UUID()/NOW()/RAND()` 等不确定函数主从值不同；`LIMIT` 无 ORDER 结果不定 |
| **ROW（推荐）** | 每行变更前后镜像 | 精确、可回放可审计 | 量大（大事务 UPDATE 全表 → 全行镜像）；DDL 不记录内容 |
| MIXED | 默认 STATEMENT，不确定场景自动切 ROW | 折中 | 主从切换行为分析复杂 |

**生产默认 ROW**：主从一致性、binlog 审计（配合 `binlog_row_metadata=FULL` 列名可读）、CDC 工具（canal/Debezium）都要求 ROW + `binlog_row_image=FULL`（默认）。**ROW 大事务瘦身**：把"一次 UPDATE 500 万行"拆成批次（每批几千行 + sleep），binlog 体积与从库延迟同时受益（见 6.1.3）。

## 4.2 redo 与 binlog 的协同

### 4.2.1 有了 redo log 为什么还要 binlog？

**职责不同、层级不同、形态不同**：

| 维度 | redo log | binlog |
|------|----------|--------|
| 层级 | InnoDB 引擎层 | Server 层（所有引擎共享） |
| 内容 | 物理：页 x 偏移 y 改成 z | 逻辑：行前像/后像或 SQL |
| 写法 | 循环固定大小（会被覆盖） | 追加，不覆盖 |
| 用途 | 崩溃恢复（**保证提交的事务在 InnoDB 里不丢**） | 复制/归档/恢复（**给"另一个维度"：从库与其他工具**） |
| 能力边界 | 只服务本引擎恢复，不告诉别人发生了什么 | 无 crash-safe 能力（不知道页是否已刷） |

两者缺一不可：没有 redo——InnoDB 断电页半坏无法安全恢复；没有 binlog——主从复制/任意时间点恢复/订阅无据可依。

### 4.2.2 两阶段提交（2PC）的流程和必要性？

**问题定义**：一次 UPDATE 要同时落 redo（供崩溃恢复）与 binlog（供从库/备份）。若各写各的，崩溃时机不同会出现**两者内容不一致**——"以 redo 恢复的库"和"以 binlog 恢复的库"数据不同（主从不一致、备份不可信）。

**流程（XID 串联两边）**：

```text
1. redo 写 prepare（含 XID）        ← 此时崩溃：redo 是 prepare 且无 binlog → 回滚
2. 写 binlog 并 fsync               ← 此时崩溃：binlog 完整但 redo 未 commit
3. redo 写 commit                    ← 恢复规则：binlog 完整 + XID 在 redo prepare 列表 → 补齐提交
```

**恢复规则**（追问必答）：redo 有 prepare 无 commit、**binlog 完整** → 提交；binlog 不完整/缺失 → 回滚。以 **binlog 为准**裁决——保证"从库收到的与主库最终一致"。

**代价**：一次提交两次 fsync 串行化，TPS 受限 → **组提交**（见 4.2.3）。

### 4.2.3 "双 1" 配置和组提交是什么？宕机会丢什么数据？

**刷盘三参数**：

- `innodb_flush_log_at_trx_commit`：1 = 每次提交 redo fsync（不丢）；**2** = 提交写 page cache、每秒 fsync（OS 崩溃丢 1s，MySQL 进程崩溃不丢）；0 = 每秒 fsync；
- `sync_binlog`：1 = 每次提交 binlog fsync（最安全，性能损耗最大）；N = 攒 N 个事务 fsync；0 = OS 决定。

**双 1（1+1）**：金融/核心库标配——性能损失靠**组提交**找补：binlog 组提交（`binlog_group_commit_sync_delay/no-wait`）把多个事务的 fsync 合并成队列 leader 一次；parallel redo 队列（8.0）同思路。

**宕机丢失矩阵**：

| 配置 | 断电（OS 崩溃） | mysqld 进程崩溃 |
|------|----------------|-----------------|
| 双 1 | 不丢 | 不丢 |
| trx=2 | 丢已 ack 约 1s | 不丢 |
| trx=0/2 + sync_binlog≠1 | 最多丢各 1s（组合最坏） | — |

**一句话权衡**："性能 vs RPO"——先问业务能不能丢，再定参数；异步复制从库天然可能更丢（见 6.1.2）。

# 5. 性能优化与表结构设计

## 5.1 执行计划与 SQL 优化

### 5.1.1 EXPLAIN 怎么看？type 和 Extra 各字段什么含义？

**关键列**：`type`（访问类型）、`key`（实际用的索引，与 possible_keys 不一致=优化器另有所选，见 2.2.5）、`rows`（预估扫描行数）、`filtered`（过滤后剩余比例）、`Extra`（执行细节）、`ref`（索引匹配到哪些列/常量）。

**type 从优到劣**：`system > const（主键/唯一等值）> eq_ref（join 唯一匹配）> ref（非唯一等值）> range（索引范围）> index（全索引扫）> ALL（全表）`——线上治理基线：**消灭 ALL，大表查询到 range 以上**（小维表 ALL 可接受）。

**Extra 高频值**：

| 值 | 含义/处置 |
|----|-----------|
| Using index | 覆盖索引，最优 |
| Using index condition | ICP 生效 |
| Using where | 引擎返回后服务层再过滤 |
| Using filesort | **额外排序**（非"写文件"）：排序列无可用索引或方向不匹配——加大 sort_buffer 只能缓解，根治靠索引序（最左前缀 + 8.0 降序索引） |
| Using temporary | 临时表（GROUP BY/DISTINCT 无索引、UNION）——优先用索引序消解 |
| Using join buffer (Block Loop / hash join) | 被驱动表关联列缺索引，补索引才是正解 |

**工具升级**：`EXPLAIN ANALYZE`（8.0.18+）真实执行并给出**实际行数/耗时/迭代次数**——对比估算 rows 偏差即可定位"统计信息失真"；`EXPLAIN FORMAT=JSON` 看成本构成。

### 5.1.2 慢查询如何定位和优化？

**闭环四步**：

1. **采集**：`slow_query_log=ON` + `long_query_time`（核心系统 0.1~0.5s）+ `log_queries_not_using_indexes`（慎用，小表噪音大）；
2. **聚合分析**：`mysqldumpslow -s t -t 10`（Top10 总耗时）或 **pt-query-digest**（按指纹聚合：总耗时、次数、锁等待、分发比）——**先按"总耗时=单次×次数"排序**，单次 30ms 每秒跑 100 次的 SQL 比一天一次的 10s 报表更该治；
3. **诊断**：EXPLAIN/EXPLAIN ANALYZE（5.1.1）看执行计划；顺带检查是否**锁等待伪装成慢查询**（slow log 含 Lock_time）、Buffer Pool 命中率、是否 filesort/temporary；
4. **处置**：加/改索引（最左前缀、覆盖）、改写 SQL（函数列改区间、大 IN 拆批）、分页与 count 方案（5.1.3/5.1.4）、结构治理（冷热分表、归档）、必要时缓存挡读（27_redis.md）。

**工程配套**：慢日志进监控告警（pt-query-digest 定时报告/云平台 SQL 洞察）；DDL 走审核平台门禁（见 33_cicd.md）；**全量 SQL 审计**（性能 schema `events_statements_summary_by_digest`）——没抓进慢日志的高频中速 SQL 才是容量大头。

### 5.1.3 深分页 LIMIT 1000000,10 为什么慢？怎么优化？

**根因**：InnoDB 没有"跳行"能力——`LIMIT m,n` 要**取出前 m+n 行再丢弃前 m 行**；二级索引下每行还要**回表验证**（MVCC 可见性），成本 O(m) 且多为无用功。

**三板斧**：

1. **延迟关联（覆盖索引 + 二次定位）**——先窄索引扫出主键，再按 10 个主键回表：

```sql
SELECT t.* FROM t
JOIN (SELECT id FROM t WHERE status=1 ORDER BY id LIMIT 1000000, 10) x ON t.id=x.id;
-- 子查询走覆盖索引不回表，回表次数从 100 万+10 降到 10
```

2. **游标分页（连续翻页正解）**：记住上一页末尾 id——`WHERE id > 100000 ORDER BY id LIMIT 10`，O(1) 定位；代价是失去"跳页"能力（前端改滚动加载/无限下拉）；
3. **业务限制**：最深 N 页、超出导出走异步任务/ES search_after（见 24_elastic_search.md）。

MP/PageHelper 不解决此问题（见 6_mybatis.md 3.2.2、9_mybatis_plus.md 4.2.3）——分页插件只负责"把 SQL 拼对"。

### 5.1.4 count(*) 为什么慢？怎么优化统计行数？

**InnoDB 不给 O(1) 的原因**：MVCC——同一时刻不同事务看到的行数不同（1.2.1/3.1.3），无法维护全局计数器；MyISAM 的"快"是没有事务的代价。

**写法差异与真相**：`count(*) = count(1) ≠ count(id) ≠ count(列)`——前两者是"数行"，优化器自动选**最小可用二级索引**扫（叶子只存"列+主键"，一页装得多 IO 少）；`count(列)` 额外做 NULL 判断；`count(常量)` 非 NULL 常量≈数全部行。**count 优化 = 索引选择优化**，不是括号里写什么。

**真优化**：① 精确值：按维度建**计数表**（业务事件驱动增减，需处理幂等与一致性——本地事务内更新，或 Redis INCR 对账）；② 近似值：`EXPLAIN rows` / `SHOW TABLE STATUS` / `information_schema` 估算（误差可到 ±40%）；③ 分页 total 场景：`searchCount=false` + 缓存总数（9_mybatis_plus.md 4.2.2）；④ 限制实时总数功能（"共约 100 万条"）。

### 5.1.5 MySQL 的 join 算法有哪些？为什么说"小表驱动大表"？

| 算法 | 条件 | 机制 | 成本 |
|------|------|------|------|
| **Index NLJ** | 被驱动表关联列**有索引** | 驱动表逐行 → 被驱动表索引点查 | 驱动表行数 × 树高 IO，最优 |
| BNL（Block NLJ） | 无索引 | 驱动表块装进 join buffer → 每块全扫被驱动表 | 被驱动表被扫 ⌈驱动/buffer⌉ 遍 |
| **Hash Join（8.0.18+）** | 无索引、等值连接 | 小表建内存哈希表（超 join_buffer_size 落盘分块）→ 大表探测 | 两表各扫一遍，替代 BNL |

"小表驱动大表"的准确表述：优化器本身会挑 join 顺序（成本模型）；工程要点是**被驱动表关联列必须有索引**（没索引时 8.0 之前灾难、之后 hash join 兜底但吃内存）。多表 join 注意 8.0 已取消 `MAX_JOIN_SIZE` 下"优化器搜索深度"的老式 hint 依赖——**join ≤ 3 张表**仍是团队规范；跨库 join 禁止（改冗余字段或应用层组装，见 6.2.2）。BNL/Hash 对 **LEFT JOIN** 的驱动选择有约束（outer join 驱动表固定），写 SQL 时"过滤条件多的表放驱动侧"。

### 5.1.6 IN 和 EXISTS 怎么选？子查询有哪些坑？

**经典口诀已半过时**："内层表小用 IN、外层小内层大用 EXISTS"源于优化器实现差异；**8.0 对 semi-join 自动改写**（IN/EXISTS/INNER JOIN+DISTINCT 等价转换：materialization / FirstMatch / LooseScan），多数场景两条路殊途同归——EXPLAIN 看策略，不必背口诀。

**仍然成立的坑**：

1. **子查询返回列必须与外层类型/collation 一致**，否则索引失效（2.2.5）；
2. `IN (子查询)` 老版本相关子查询逐行执行；`NOT IN` 遇 NULL 全集变空（NULL 比较非真非假）→ **用 NOT EXISTS 或加 IS NOT NULL 保护**；
3. `IN (列表)` 元素数量控制（万级改临时表/join，见 6_mybatis.md 2.3.2）；
4. 派生表（FROM 子查询）8.0.14+ 默认**合并**进外层，老版本物化——"加索引没用"的元凶之一。

## 5.2 表结构与变更

### 5.2.1 Online DDL 原理？大表加字段怎么做最安全？

**三种算法**（`ALGORITHM=` 显式声明，`SHOW WARNINGS` 看降级原因）：

| 算法 | 机制 | DML 阻塞 |
|------|------|---------|
| INSTANT | 只改元数据（8.0 加列默认末尾追加；8.0.29 支持任意位置/含默认值大改） | 否 |
| INPLACE | 原地重建（加索引等）：prepare 拿 MDL-X → **降 MDL-S** 扫聚簇索引建索引，期间 DML 记入 **row log** → commit 再升 MDL-X 回放 row log | 首尾短暂；中段不阻塞 |
| COPY | 建新表→全拷→改名 | 全程阻塞写（8.0 起锁级别可控） |

**隐形雷区：MDL 元数据锁**——DDL 等 MDL-X 时被**长事务/慢查询**的 MDL-S 挡住，DDL 排队又会**卡死后续所有查询**（MDL 队列公平排队）："一条 DDL 拖垮全库"事故的标准成因。对策：DDL 前查 `innodb_trx` 杀长事务、设 `lock_wait_timeout` 短（拿不到就放弃重试）、业务低峰。

**超大表（百 GB 级）更稳的工程方案**：**gh-ost / pt-online-schema-change**——影子表拷贝 + binlog 增量回放（gh-ost 不触发器、可暂停限流），切表时短暂锁；顺带控制 binlog 洪峰与从库延迟（见 6.1.3）。变更纪律：所有 DDL 走审核平台 + 灰度库演练 + 回滚预案（8.0 原子 DDL 保证失败不留半态，见 5.2.5）。

### 5.2.2 CHAR 和 VARCHAR 怎么选？VARCHAR(255) 为什么常被说"无所谓"？

| 维度 | CHAR(n) | VARCHAR(n) |
|------|---------|------------|
| 长度 | 定长，空格补齐 | 变长，1~2 字节长度前缀 |
| 上限 | 255 **字符** | 行总量 65535 **字节**约束（utf8mb4 下单列最多 16383 字符） |
| 取回 | 尾部空格被裁剪（PAD SPACE 对比） | 原样 |
| 页效应 | 定长更新不分裂 | 变长更新可能挪位 |
| 适用 | 等长短串：MD5、状态码、手机号 | 其余字符串 |

**存储细节**：Compact/Dynamic 行格式下 **CHAR 也按实际长度存**；超过 767B（页的 1/2）的列存**溢出页 + 本地 20B 指针**（DYNAMIC 只存 20B 指针，COMPRESSED 压缩存）——varchar(8000) 超长内容落盘链外，**行内扫描仍快**（本地小片段），不是灾难。

**"varchar(255) vs varchar(20)" 真相**：长度前缀按实际内容算，内存/磁盘占用**几乎一样**；差别在① 排序/临时表可能按声明长度预分配（老版本 filesort 临时表放大内存）② 语义约束（声明 64 = 业务契约）。规范做法：按业务上限声明、统一团队习惯，不必教条压到 20。

**字符集**：utf8≠真 UTF-8（最多 3 字节，emoji 存不进）；**utf8mb4 + utf8mb4_general_ci（8.0 默认 0900_ai_ci）** 是建库标准；索引 767 字节限制在 DYNAMIC 行格式 + innodb_large_prefix（5.7+ 默认）下放宽到 **3072 字节**（utf8mb4 ≈ 768 字符前缀，超长列用前缀索引，2.2.4）；**连接层 character_set_client 与列 collation 不一致**会让 join/比较走不了索引（2.2.5）。

### 5.2.3 DATETIME 和 TIMESTAMP 怎么选？

| 维度 | DATETIME | TIMESTAMP |
|------|----------|-----------|
| 范围 | 1000~9999 年 | 1970~**2038-01-19**（4 字节） |
| 时区 | 存字面值，无时区概念 | 存 UTC，按会话 `time_zone` 换算 |
| 大小 | 5 字节 + 小数秒 | 4 字节 + 小数秒（8 字节含微秒） |
| 自动值 | 显式默认 | `DEFAULT CURRENT_TIMESTAMP ON UPDATE ...` |

**实践口径**：① 跨时区业务**全链路存 UTC**（DATETIME 或 BIGINT 时间戳皆可），展示层转换——TIMESTAMP 的 2038 与隐式时区双雷，大厂规范普遍弃用 TIMESTAMP 改 **DATETIME(3)/BIGINT**；② MySQL 驱动 `serverTimezone`/JVM 时区/库时区三者要对齐（"差 8 小时"根因，见 6_mybatis.md 2.1.4）；③ `ON UPDATE CURRENT_TIMESTAMP` 与业务审计字段（自动填充）二选一主导，别让两套机制互相覆盖（9_mybatis_plus.md 3.2.1）。

### 5.2.4 自增 ID 快用完了怎么办？分布式 ID 怎么选？

**INT AUTO_INCREMENT（21.47 亿）接近上限**：到顶后继续插入报 `Duplicate entry`；**在线解法**：`ALTER TABLE t MODIFY id BIGINT UNSIGNED`（int→bigint 兼容单调空间，INPLACE 元数据级但大表仍建议 gh-ost 通道）；预防：新表一律 bigint。

**分布式 ID 方案对比**（2.2.6 主键选择的延续）：

| 方案 | 特点 | 适用 |
|------|------|------|
| DB 号段（Leaf-Segment） | 取一段缓存在内存分发；双 Buffer 防取号毛刺 | 趋势递增、可反查、依赖 DB 弱耦合 |
| Redis INCR | 原子、高性能 | 持久化策略要盯（AOF everysec 重启可能重号） |
| **雪花 Snowflake** | 本地生成、含时间；机器位分配与回拨处理是关键 | 主流（MP 内置，见 9_mybatis_plus.md 3.1.2） |
| UUID | 无序、太长 | 不推荐作主键 |
| 容器/单元化发号 | 每单元预留号段（步长隔离） | 分库分表自建方案（6.2.2） |

**趋势递增 + 全局唯一 + 信息位**是工业设计的三角约束；业务编号（订单号）常叠加"日期+随机+校验位"对外防爬（暴露量级的回看 2.2.6）。

### 5.2.5 MySQL 8.0 有哪些值得知道的新特性？

| 类别 | 特性 |
|------|------|
| 优化器/执行 | **Hash Join**、降序索引、Skip Scan、直方图统计、`EXPLAIN ANALYZE` |
| 索引治理 | **隐藏索引（INVISIBLE）**灰度删索引、降序索引 |
| DDL | **原子 DDL**（失败自动回滚不留中间态）、Instant 加列增强、`ALTER TABLE ... ALGORITHM` 显式化 |
| 复制 | **WriteSet 并行复制**、事务级持久化变量、binlog 压缩 |
| SQL 能力 | 窗口函数、CTE（含递归）、`JSON_TABLE`/`->>`、行构造器比较 |
| 安全 | **caching_sha2_password** 默认、角色管理、双密码轮转 |
| 架构 | 查询缓存移除、数据字典事务化（.frm 废除）、Resource Group、utf8mb4 默认、持久化缓冲池（冷启动预热） |
| 云原生 | 8.0.30 redo 容量单一参数、8.4 LTS 延续 |

**面试答题姿势**：报菜名只讲 3~4 个能展开的——**隐藏索引 + 原子 DDL + Hash Join + WriteSet 并行复制**各带一句"解决什么问题"（分别对应：删索引怕出事、DDL 失败残留、BNL 大表关联慢、主从延迟），远胜背全表。

# 6. 主从复制与扩展

## 6.1 主从复制

### 6.1.1 主从复制的原理？涉及哪些线程？

**三线程链路**（依赖 binlog 的位置坐标：老式 file+pos，现用 GTID）：

1. **Master Binlog Dump 线程**：从库 IO 连上后，按位点读 binlog 事件推送（有延迟参数 `MASTER_DELAY`）；
2. **Slave IO 线程**：接收事件写入 **relay log**（+ master.info 记位点）；
3. **Slave SQL 线程**：读 relay log **重放**，串行或并行（见 6.1.2）。

**前置条件**：server-id 唯一、binlog=ROW、从库开 relay-log；新实例搭主从：物理备份（xtrabackup）/逻辑导入 → 指定主库位点/GTID 追平。

**追问：复制的是 SQL 还是数据？**——ROW 格式复制的是**行事件**（前后镜像），从库按事件写行、不重执行 SQL——这就是 STATEMENT 下"不确定函数主从不一致"而 ROW 不会的原因（4.1.2）。半同步/MGR 的日志流同样基于事件，不改变这条本质。

### 6.1.2 异步、半同步、组复制（MGR）有什么区别？

| 模式 | 确认时机 | RPO | 性能影响 | 备注 |
|------|---------|-----|---------|------|
| **异步（默认）** | 主库提交即返回 | **可能丢事务**（主库宕机、binlog 未传完） | 零 | 绝大多数互联网默认 |
| 全同步 | 所有从库回放完 | 0 | 一个从库慢拖死全局 | 几乎没人用 |
| **半同步（lossless 版）** | 至少 1 从库 **ACK"写入 relay log 落盘"** | 严格 0 丢需 AFTER_SYNC（5.5 的 AFTER_COMMIT 仍可能读到未同步数据） | +1 次 ACK RTT | 跨城容灾常用；配合 `rpl_semi_sync_master_timeout` 降级异步 |
| **MGR/Paxos** | 多数派日志达成共识 | 0（多数派） | 写放大、网络敏感 | 自动选主/故障剔除；单主/多主模式；云 RDS 高可用底座同源 |

**易错**：半同步 ACK = "从库**落盘 relay log**"而不是"回放完成"——从库挂了主库也会等不到 ACK（超时降级）；"数据不丢"≠"数据已读到"。**并行复制**（从库回放提速）：5.7 按库并行、8.0 **WriteSet** 按"无冲突事务组"并行（`binlog_transaction_dependency_tracking=WRITESET`），从库线程 `slave_parallel_workers` + 模式 `DATABASE/LOGICAL_CLOCK`。

### 6.1.3 主从延迟如何排查？读己之写问题怎么解？

**症状**：写主后立刻读从，查不到/读到旧值；`SHOW REPLICA STATUS` 看 `Seconds_Behind_Source`（注意该值是"IO 与 SQL 两路延迟的粗指标"，定位到具体库用 pt-heartbeat）。

**根因清单**：① 从库**单线程/低并行度**回放（最普遍）——开 WriteSet 并行；② **大事务**（一次 DELETE 千万行，主库 1 分钟、从库重放更久且阻塞队列——拆批，见 4.1.2）；③ DDL 大表拷贝（5.2.1 gh-ost 走通道）；④ 从库硬件/只读流量叠加（从库还承担分析查询，回放饿死——资源隔离）；⑤ 网络（跨地域丢带宽，半同步慎配）。

**读己之写（write-your-own-read）方案**（按成本排序）：

1. **写后强制读主**：会话打标（写事务后 N 秒内路由主库——proxy/应用层双判）；
2. **关键读直接走主**：事务内 SELECT、下单后查单、支付回跳；
3. **GTID 等待**：`WAIT_FOR_EXECUTED_GTID_SET(gtid, timeout)` 读到已知位点后再查从——正确性最好，运维复杂；
4. **缓存兜底**：写后更新 Redis，读走缓存（27_redis.md 的 Cache-Aside + 延迟双删谱系，注意一致性语义别偷换）；
5. 业务免疫：弱一致展示（计数、历史列表）容忍延迟，文案"约"字化。

## 6.2 分库分表与扩展

### 6.2.1 分库分表有哪几种方式？什么时候该拆？

**四个方向**：

| 方式 | 切法 | 解决 |
|------|------|------|
| 垂直分库 | 按业务域拆库（用户库/订单库/商品库） | 单库连接数与容量瓶颈、业务隔离（微服务配套，见 15_spring_cloud.md） |
| 垂直分表 | 宽表拆冷热列（主表 + 扩展表） | 行宽 → 单页行数少、缓存命中率低 |
| 水平分库 | 同表按分片键散到多库（user_id % 16） | 单库写吞吐/容量 |
| 水平分表 | 同库内拆子表 | 单表数据量（B+ 树层与索引维护成本） |

**拆分时机（先单表后一切）**：经验阈值——单表 **5000 万~1 亿行 / >2GB 索引失控 / 单库 TPS 顶到物理机上限**；在此之前优先：索引与 SQL 治理（5.1 全套）→ 读写分离（6.1 主从+延迟）→ 缓存（27_redis.md）→ 冷热归档（数据只热存半年）；**仍不够才分片**——分片是"架构手术"，跨分片分页、join、事务、扩容的复杂度会以年计偿还。

### 6.2.2 分库分表带来哪些新问题？业界怎么解？

| 问题 | 方案 |
|------|------|
| **全局 ID** | 雪花/号段发号（5.2.4，禁各库各自自增） |
| **跨分片查询**（分页/聚合/非分片键条件） | 轻度：广播查 + 内存归并（ShardingSphere 归并引擎）；重度：**异构索引**——binlog 订阅把数据冗余进 ES（按任意条件查，见 14_canal.md + 24_elastic_search.md）/ClickHouse |
| **跨分片 join** | 禁；字典表**广播表**（每片一份）、冗余字段、应用层组装 |
| **跨分片事务** | 最终一致（本地消息表/事务消息，见 13_rocketmq.md、34_distributed_theory.md）；强一致用 Seata AT（见 21_seata.md） |
| **扩容 rebalance** | 预分片（逻辑片 1024 个固定，物理片迁移映射）；一致性哈希（27_redis.md）；双写迁移 + 校验 + 切读（灰度三板斧） |
| **热点/倾斜** | 按 key 二次散列（加盐）、热点单独分片 |
| 路由层选谁 | **ShardingSphere-JDBC**（客户端 jar，性能最好，绑定 Java）/ **Proxy**（独立代理，多语言透明）——选型、分片算法与生态细节见 22_sharding_sphere.md |

**一句话收尾**：分库分表的本质是"用**路由与一致性工程**换单机上限"——面试答完四方向与中间件，落点放在"我会先治理索引/读写分离/缓存，量级确实到顶才分片，并预留 3 倍增长"，比背方案更显工程判断。
