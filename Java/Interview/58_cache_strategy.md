# 1. 知识点
- **Cache-Aside(旁路缓存)**: 最常用的缓存模式。读：先读缓存，命中返回，未命中读DB并回写缓存。写：先写DB，再删除缓存(不是更新缓存)
- **Cache-Aside为什么删缓存而不是更新**: 多个并发写操作可能导致缓存与DB顺序不一致(写DB1→写DB2→写缓存2→写缓存1最终缓存是旧值)。删除缓存是懒惰策略，下次读时自然会加载最新值
- **Cache-Aside延迟双删**: 写DB → 删除缓存 → 等待几百毫秒(delay) → 再次删除缓存。解决并发读写导致的缓存不一致(读请求在写请求删除缓存后、写DB前读取了旧数据回写缓存)
- **延迟双删步骤**: 1)删除缓存 2)更新DB 3)延迟(如500ms，根据业务读耗时估算) 4)再次删除缓存。第二次删除为了清除在步骤2期间并发读请求写入的脏缓存
- **Read-Through**: 缓存层代理数据库读操作。应用程序只与缓存交互，缓存未命中时缓存层自动从DB加载数据。对应用透明
- **Write-Through**: 缓存层代理数据库写操作。应用程序写入缓存，缓存层同步写入DB。保证缓存和DB数据一致，但写入延迟高(需等DB写入完成)
- **Write-Behind(Write-Back)**: 应用程序写入缓存即返回(异步)，缓存层异步批量写入DB。性能最高，但有数据丢失风险(缓存宕机未刷盘的写丢失)
- **Write-Behind实现**: 应用→缓存写入→消息队列(Kafka)→异步消费→批量写入DB。适合写多读少、允许短暂数据丢失的场景(如计数、日志)
- **缓存一致性最终一致性方案**: 先更新DB → 删除缓存(非更新) → 配合Canal订阅binlog异步删除/更新缓存(延时双删兜底)
- **Canal+MQ缓存一致性**: Canal监听MySQL binlog变化 → 发送消息到MQ(RocketMQ/Kafka) → 消费者删除/更新对应缓存 → 实现缓存与DB的最终一致性
- **多级缓存**: 本地缓存(Caffeine/Guava Cache, JVM堆内, 纳秒级)作为一级 → 分布式缓存(Redis, 微秒级)作为二级 → 数据库持久层。逐级查询
- **Caffeine本地缓存**: 高性能Java本地缓存库，使用Window TinyLFU淘汰算法，支持过期策略(基于大小、时间、引用)、异步加载
- **本地缓存同步**: 多实例部署时本地缓存存在不一致问题。方案：Canal监听binlog → 广播缓存更新消息 → 各实例更新本地缓存；或设置短过期时间容忍不一致
- **缓存预热**: 系统启动时提前将热点数据加载到缓存，避免启动瞬间大量请求穿透到DB。实现：启动时异步拉取热点数据写入Redis/本地缓存
- **缓存预热策略**: 定时任务分析访问日志识别热点数据、启动时加载预定义的热点数据集、根据业务周期性预热(如大促前)
- **热点Key探测**: 通过客户端埋点统计Key访问频率，或使用Redis的hotkey检测工具。发现热点后采用二级拆分策略
- **热点Key解决方案**: 将热点Key复制多份(如hotkey_1, hotkey_2...)，key拆分散列到不同节点，客户端随机/轮询访问不同副本，避免单节点压力过大
- **BigKey(大Key)**: Redis中单个key的value过大。问题：阻塞Redis(大key删除DEL阻塞)、网络带宽打满、数据倾斜
- **BigKey发现**: `redis-cli --bigkeys`命令扫描、`MEMORY USAGE key`分析、RDB文件分析工具(rdb-tools)
- **BigKey处理**: 拆分大value为多个小key、使用Hash结构分field存储、压缩value、换用其他存储(如对象存储OSS/MinIO只存URL)、大list分片
- **缓存穿透**: 查询不存在的数据(缓存和DB都没有)，大量请求穿透缓存直接打DB。解决：布隆过滤器、缓存空值(null)设置短过期时间
- **缓存击穿**: 热点Key过期瞬间，大量并发请求同时查询DB。解决：互斥锁(只有一个线程查DB回写缓存)、永不过期(逻辑过期、异步更新)
- **缓存雪崩**: 大量缓存Key同时过期，或Redis集群宕机，请求全部打到DB。解决：过期时间加随机值(TTL ± random)、多级缓存、熔断降级、Redis集群高可用
- **布隆过滤器**: 概率型数据结构，判断一个元素是否存在集合中。可能存在误判(说不存在一定不存在，说存在不一定存在)。用于缓存穿透的快速过滤

# 2. 面试题

## 2.1 Cache-Aside模式下为什么是删除缓存而不是更新缓存？
1) **并发写顺序问题**：两个并发写操作(A和B)同时更新DB和缓存，A先更新DB，B后更新DB，但B先更新缓存，A后更新缓存。最终缓存是A的值，DB是B的值，数据不一致。
2) **双写不一致**：更新DB成功、更新缓存失败，数据不一致。
3) **写多读少浪费**：数据更新频繁但读取很少，更新的缓存可能从未被读取，浪费资源。
4) **删除缓存是懒加载**：只有当真正需要时(下次读)，才从DB加载最新数据。所以正确的Cache-Aside是写时删缓存、读时加载。

## 2.2 什么是延迟双删？为什么需要它？
延迟双删：写DB → 删除缓存 → 延迟N毫秒 → 再次删除缓存。场景说明：线程A读数据(缓存未命中)读DB得到旧值；线程B写DB更新为新值并删除缓存(此时缓存已不存在)；线程A将旧值写入缓存。结果是缓存中为旧值，DB为新值。延迟双删第二次删除就是为了清除这种并发读请求写入的旧缓存。延迟时间需要大于"读DB+写缓存"的时间。

## 2.3 缓存穿透、击穿、雪崩分别是什么？如何解决？
| 问题 | 描述 | 解决方案 |
|------|------|---------|
| 缓存穿透 | 查不存在的数据，缓存和DB都没有 | 布隆过滤器过滤、缓存空值(短TTL) |
| 缓存击穿 | 热点Key过期，大量并发查DB | 互斥锁(单线程加载)、永不过期(异步更新) |
| 缓存雪崩 | 大量Key同时过期或Redis宕机 | 过期时间+随机、多级缓存、集群高可用、熔断降级 |

**缓存穿透详解**：恶意攻击者查询不存在的ID(-1, 超大数)穿透缓存打DB。解决：1)布隆过滤器预先存储所有存在的ID，不存在的直接拦截 2)查询DB也不存在时缓存空值，设置短过期时间(30s-5min)。

**缓存击穿详解**：热点Key(如爆款商品)过期瞬间，大量请求涌入DB。解决：1)加互斥锁(Mutex)，只有获得锁的线程才能查DB回写缓存，其他线程等待 2)设置Key"永不过期"，在value中存逻辑过期时间，后台异步任务检测过期时更新。

**缓存雪崩详解**：大量Key设置相同的过期时间，同时过期导致DB压力骤增。解决：1)过期时间在基础TTL上增加随机值(如±10%) 2)使用多级缓存(本地缓存兜底) 3)Hystrix/Sentinel限流熔断 4)Redis集群/哨兵保证高可用。

## 2.4 多级缓存架构如何设计？本地缓存如何同步？
架构：L1本地缓存(Caffeine) → L2分布式缓存(Redis) → L3数据库。请求先查L1，L1命中返回(纳秒级)；L1未命中查L2，L2命中回写L1后返回(毫秒级)；L2未命中查DB，DB结果写入L2和L1。本地缓存同步方案：1)Canal监听binlog → 发布缓存更新消息 → 各应用实例消费消息更新本地缓存 2)发布订阅模式，一个实例更新DB后发布消息通知其他实例 3)缩短本地缓存过期时间(如几秒)，容忍短暂不一致。

## 2.5 如何发现和解决Redis BigKey问题？
**发现**：使用`redis-cli --bigkeys`扫描各类型最大key；`MEMORY USAGE key`精确查看key占用内存；`DEBUG OBJECT key`查看序列化长度；rdb-tools工具离线分析RDB文件。

**解决**：
1) String过大：分片，拆成多个小key(user_info_1, user_info_2)，或将大对象存到对象存储(OSS/MinIO)，Redis只存URL
2) Hash过大：拆成多个Hash key，按field hash取模分片
3) List/Set过大：分页加载，控制集合大小
4) 删除大Key：使用`UNLINK`异步删除(Redis 4.0+)代替`DEL`，或分批删除(LIST的LTRIM、ZSET的ZREMRANGEBYRANK)

**预防**：设置key大小告警阈值(如10MB)、设计时避免大value、定期巡检。

## 2.6 Write-Behind模式适用于什么场景？有什么风险？
适用场景：1)写操作频繁、对写入延迟敏感(应用写完缓存即返回，无需等DB写入) 2)允许短暂数据丢失(如页面浏览计数、用户行为日志) 3)批量写入优化(缓存攒批后异步批量写DB，减少DB压力)。实现方式：应用写Redis → 异步刷盘线程将变更推送到Kafka → 消费者消费消息批量写入DB。

风险：1)数据丢失：Redis宕机，未刷盘的写入永久丢失 2)数据不一致窗口长：异步延迟可能达秒级甚至分钟级 3)实现复杂：需要保证消息可靠性和有序性。

## 2.7 缓存和数据库数据一致性如何保证？
业界方案"先更新DB，后删除缓存" + 多种兜底策略：
1) **基本策略**：更新DB → 删除缓存。大部分场景有效。
2) **延迟双删**：更新DB → 删除缓存 → 延迟 → 再次删除缓存。解决并发读写入脏缓存。
3) **Canal Binlog兜底**：Canal监听binlog → 发MQ → 消费者异步删除/更新缓存。即使第一步删除缓存失败也有兜底。
4) **消息队列保证**：更新DB和删除缓存通过MQ保证最终一致性，缓存删除失败可重试。
5) **设置合理过期时间**：即使以上都失败，缓存过期后自然一致(最终兜底)。
最终一致性的保证不是单一手段，而是多层保障的组合。

## 2.8 如何设计一个热点Key自动探测和防护方案？
1) **探测阶段**：客户端SDK埋点统计每个Key的访问QPS，上报到中心化的统计服务；或分析Redis的MONITOR/SLOWLOG；或使用Lua脚本在Redis侧统计
2) **判定阶段**：QPS超过阈值(如单Key > 5000 QPS)判定为热点Key
3) **防护阶段**：热点Key自动复制多份(hotkey_1, hotkey_2, ..., hotkey_N)，客户端侧随机选择副本读取，将流量分散到不同Redis节点
4) **本地缓存兜底**：热点Key自动加载到本地Caffeine缓存，设置短过期时间(如1s)，大幅减少对Redis的访问
5) **动态调整**：热点Key冷却后自动恢复普通模式，释放副本

## 2.9 缓存预热如何设计实现？
方案设计：
1) **启动预热**：应用启动时监听Spring的ApplicationReadyEvent事件，异步线程加载预定义的热点数据到缓存
2) **定时预热**：定时任务(如每天凌晨)分析昨天的访问日志Top N Key，预热到Redis
3) **手动预热**：提供管理接口，大促前手动触发预热脚本
4) **分层预热**：先预热Redis(大批量)，再预热本地缓存(精选超热点)
5) **预热监控**：记录预热耗时、数据量、成功率，预热失败告警
实现注意：预热任务需要限流避免打爆DB；预热数据需要设置合理的TTL；支持增量预热和全量预热两种模式。
