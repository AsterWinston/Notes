本篇覆盖 Nacos 的高频面试题，按"主题块 → 详细分块 → 题目 → 解答"组织。五个主题块：定位与数据模型、注册与发现原理、配置中心原理、生产实践、对比与选型。Spring Cloud 体系全景与"注册中心/配置中心选型总表"见 15_spring_cloud.md（2.1、3.1、4.1 各题），本篇深入 Nacos 本体。

# 1. 定位与数据模型

## 1.1 产品定位

### 1.1.1 Nacos 是什么？为什么注册中心和配置中心要做成一个组件？

**定位**：阿里开源的"**动态服务发现、配置管理与服务管理平台**"（Naming and Configuration Service）——一个组件同时交付注册中心 + 配置中心 + 服务元数据治理控制台，对应替代 Eureka + Config Server + Bus 三件套；2026 年 3.x 代际又叠加了 **AI 资源注册**（MCP Server/Agent/Prompt 的注册发现，4.1.2），产品叙事从"微服务基建"扩到"智能体基建"。

**二合一的真实收益**（不止"少部署一个组件"）：
1. **统一数据模型**：Namespace/Group 同时管辖服务与配置——环境隔离、业务线分组一套概念管到底（1.1.2），改环境不再"注册中心一套 namespace、Git 配置库一套分支"双头维护；
2. **统一推送通道**：实例变更与配置变更都走同一条 gRPC 长连接（2.x），客户端 SDK 只养一个；
3. **治理联动**：按标签路由、灰度引流这类策略**同时消费服务元数据与配置**——两者同库同控制台才有"改条规则立即作用于这批实例"的体验（1.2.2）；
4. 权限、审计、监控一份；跨机房容灾一套预案。

**代价也要说**：单组件故障域合并（4.2.1 的本地缓存机制兜底）；"注册 + 配置"两套一致性模型在同一进程里并存（Distro 与共享 DB 各管各的，2.2.1/3.1.3）——**耦合的是管控面，不是数据面**，这句能答出来才算真理解架构。

### 1.1.2 Nacos 的数据模型与隔离体系是怎样的？

**服务侧五层**：`Namespace（环境/租户）→ Group（业务线分组）→ Service（服务名）→ Cluster（逻辑集群）→ Instance（IP:Port+weight+metadata+healthy）`；**配置侧三层**：`Namespace → Group → DataId`（dataId 约定 `${app}-${profile}.yaml` 等，3.1.1）。

**每层的工程语义**：
- **Namespace**：强隔离边界——dev/test/prod 或不同租户，**互相完全不可见**；Spring 侧配 `spring.cloud.nacos.namespace`（用 namespace ID 不是名字，新手坑）；3.x 起配置与服务命名空间**独立管理**（AI 资源也纳入命名空间体系）；
- **Group**：弱隔离、按业务线/项目分组，`DEFAULT_GROUP` 兜底；
- **Cluster**：**服务治理的逻辑分组**——同机房就近调用（消费者优先拿同 cluster 实例，跨机房延迟治理）、按 cluster 做健康检查策略与路由规则的挂载点；
- **Instance 的三要素**：`weight`（流量权重，1~100 整数配 Nacos，LoadBalancer 按权重分配，2.1.3 消费链路）、`metadata`（KV 自由标签：version/zone/k8s 信息——灰度与路由的原料，1.2.2）、`healthy/ephemeral`（2.1.2/1.2.1）。

**易错**："Cluster 是部署集群吗"——不是，一个服务的实例**本来就散布在多个物理集群/机房**；Nacos 的 Cluster 只是**给实例贴的同域名**，用来表达"逻辑分组 + 就近策略"，名字劝退率高，主动澄清即加分。

## 1.2 服务模型与治理原料

### 1.2.1 临时实例和持久化实例有什么区别？

**两种被"认定活着"的方式**（`ephemeral` 字段，Spring 侧 `spring.cloud.nacos.discovery.ephemeral` 默认 true）：

| 维度 | 临时实例（ephemeral=true） | 持久化实例（ephemeral=false） |
|------|---------------------------|-------------------------------|
| 存活判定 | **客户端上报**：心跳（1.x）/长连接（2.x，断连即知） | **服务端主动探测**：TCP/HTTP/MySQL 健康检查 |
| 不健康后果 | 超时剔除（30s/秒级） | **只标 unhealthy，不删除**——实例记录永久存在 |
| 一致性协议 | Distro（AP，2.2.1） | JRaft（CP，2.2.2） |
| 典型对象 | 微服务（弹性、可再生） | 基础设施：MySQL、Redis、老网关——**注册方不知道自己"没了"**（没装 SDK 的服务也只能靠探测） |

**设计动机**（追问必答）：弹性服务"死了就该消失"——注册表不该有鬼；基础设施"故障时要被看见"——摘除即失明，运维需要它还挂在注册表上标红。注册主体也决定模式：应用 SDK 注册走临时（自带 ephemeral），**控制台/第三方代注册**的基础设施走持久化（被注册方不会说话，只能探测）。

### 1.2.2 权重、元数据如何支撑流量治理与灰度发布？

**三个治理原语**：
1. **weight 调流量比例**：`10.0.0.1:8080 weight=1`（新）与 `weight=10`（稳）→ LoadBalancer 加权轮询——机器性能不齐、**新机预热**（5_tomcat.md 4.1.1 JIT 冷启动同理）、按比例放灰度都靠它；控制台直接改权重**实时生效**（不用发版）；weight=0 等效摘流量（排障隔离单实例的标准动作）；
2. **metadata 打标**：`version=v2 / zone=sh-a / gray=true`——消费侧按请求特征匹配标签路由：网关读 `X-Gray` 头 → 过滤 Nacos 实例列表只放灰度组（19_spring_cloud_gateway.md 自定义 predicate/LoadBalancer supplier；SDK 侧自定义 `ServiceInstanceListSupplier`，15_spring_cloud.md 3.2.2）；
3. **cluster 分组**：灰度实例直接建个 `canary` cluster，路由规则按 cluster 整组切——比逐实例打标更粗粒度更省心。

**全链路灰度的 Nacos 角色**（高频体系题，收口见 15_spring_cloud.md 5.2.1 平台化路线）：入口打标（网关写 tag 到请求头/RPC attachment）→ **每一跳**消费时按 tag 过滤实例（Feign/Dubbo 拦截器 + Nacos 元数据查询）→ 无灰度实例自动回退稳定版（兜底路由）；标签透传依赖链路中间件全支持（线程池透传坑同 11_spring_security.md 5.2.2）。Nacos 在这条链路里**只是"标签注册表 + 路由依据"**——调度决策全在消费端/网关侧。

**配置灰度**是另一件事（按 IP beta 发布，3.2.1），面试"灰度发布"先反问是哪一层：流量灰度还是配置灰度——先澄清再展开即超出预期。

# 2. 注册与发现原理

## 2.1 连接与同步机制

### 2.1.1 Nacos 服务注册与发现的完整流程？1.x 和 2.x 有何不同？

**注册线**（临时实例视角）：
1. 应用启动，SDK 组装 Instance（IP/Port/cluster/ephemeral/metadata）发注册请求；
2. **1.x**：HTTP API（8848），注册进 Server 内存注册表（`namespace@@group@@service` 为 key 的 ConcurrentHashMap）；**2.x**：**gRPC 长连接（9848）**，实例记录与连接绑定（一个连接可携带多个订阅/注册）；
3. 保活：1.x 客户端 **5s 心跳**（light beat 轻量化）；2.x **免心跳——连接即存活**，TCP 断开、心跳超时（连接层 keepalive）Server **秒级感知并剔除**（对比 1.x 的 15s/30s 判死，时效代差）；
4. Server 间同步：本节点数据经 Distro 异步复制到其他节点（2.2.1）。

**发现线**：
1. 消费者启动即**全量拉取**目标服务列表，落本地缓存（供 LB 实时查询——每次调用查内存不查网络）；
2. 变更感知：1.x = **UDP push**（Server 变更时向订阅者推一条通知，客户端收到再回查）+ 定时轮询兜底；2.x = **gRPC 双向流 push**（变更直接推列表/增量）；
3. 消费端把新列表交给 Spring Cloud LoadBalancer（15_spring_cloud.md 3.2.2 的 supplier 缓存刷新）。

**答"为什么要 2.x 换 gRPC"**（本题的代际考点）：1.x 三笔债——心跳风暴（万级实例×每 5s 一条 HTTP 请求）、UDP push 不可靠（无鉴权、丢包即通知丢失、防火墙难治理）、拉取周期造成的收敛延迟；gRPC 长连接**一条连接承载注册+心跳+订阅+推送**（HTTP/2 多路复用），断连即剔除把故障感知从"十秒级"压到"秒级"，push 从"通知+回查"两段式变成直接推送。代价：连接是有状态的，Server 重启全量重连风暴、运维排查从"curl API"变成"看连接"——技术选型没有单向碾压。

### 2.1.2 Nacos 的健康检查体系？

**按实例类型两套通道**（1.2.1 的落地）：
- **临时实例**：客户端证明活着——1.x 心跳超时阈值（**15s 标 unhealthy、30s 删除**，控制台可配 beatInterval 后同步变）；2.x 连接断开即时剔除；
- **持久化实例**：服务端主动探测三种模式：**TCP**（连接成功即健康）、**HTTP**（状态码 + 超时判定，2.5.x 起对探测目标 URL 做安全校验防注入）、**MySQL**（JDBC 探活，专为 DB 注册场景）——探测参数**自适应 RT**：连续失败判定用滑动窗口的 min/max 阈值（源码默认：TCP 1000~5000ms、MySQL 2000~3000ms、HTTP 500~5000ms，`factor` 收缩系数动态调整判死线），"auto change health check"开关控制自动伸缩。

**两个细节考点**：① `healthy` 与 `enabled/weight=0` 的三层语义——探测失败标 unhealthy（不分发）、控制台手动"下线"（enabled=false，不分发、无告警噪音）、weight=0（理论可分、实际无流量）——**排障时三层都要查**（"为什么没有流量进来"检查单）；② 客户端消费列表默认**只含健康实例**，全挂时降级返回全集还是空（`subscribe` 参数与自我保护联动，2.2.3）。

### 2.1.3 服务变更如何实时通知到消费者？

**1.x 通知链**：Server 检测到实例变化（注册/剔除/健康翻转）→ 遍历该服务订阅者表 → **UDP 包发 `service:checksum` 通知** → 客户端校验本地 checksum 不一致 → 回查拉最新列表。三笔旧账：UDP 不可靠（丢了等下轮轮询）、多一跳"通知→回查"、端口与鉴权治理麻烦（UDP 包无身份验证，靠 checksum 兜正确性）。

**2.x 通知链**：gRPC 双向流上 **`NotifySubscriberRequest` 直接推新实例列表**，连接内建可靠语义（HTTP/2 流控 + keepalive 自检），断连期间变更靠**重连后全量对齐 + 版本号校验**兜底。

**通用兜底设计（任何 push 系统都同款）**：**push 只是"加速"，拉取是"校准"**——客户端定时全量比对（防漏）+ 本地快照持久化（Server 全挂还能用最后一次列表，4.2.1）；Nacos 的 `pushCacheMillis/cacheMillis` 语义（1.x SwitchDomain 默认 push 缓存 10s）控制"通知后多久内列表被认为可信"。对比同类机制：Apollo 长轮询通知（15_spring_cloud.md 4.1.3）、ZK watch（一次性通知 + 重注册）、Canal binlog 位点回查——"**不可靠信道上的状态收敛**"是同一道题的不同解法。

## 2.2 一致性模型

### 2.2.1 Distro 协议是怎么工作的？为什么自研而不用 Raft 跑全部数据？

**定位**：Nacos 为**临时实例（高频变更、AP 场景）**自研的最终一致协议。机制三件套：
1. **责任分片**：每个服务（按 hash）有**责任节点**——客户端连到任意 Server 注册，该 Server 若不对此服务负责则**转发给责任节点**受理（写入口灵活、归属确定）；
2. **异步复制**：责任节点写入内存成功后**立即返回**，同时异步把变更同步到其他节点——不等待多数确认（这就是 AP 的代价：分区时各节点可能给短暂不同的视图）；
3. **校验补偿**：节点间定时互发**数据摘要（checksum）**（SwitchDomain：服务同步周期 5s、节点状态 2s），比对差异触发补同步；**新节点加入拉全量快照**；节点失联超 10s 判 expired、其责任数据接管重建。

**为什么不 Raft 一把梭**（设计论证，这题灵魂）：地址表数据的三个画像决定协议——① **变更频率高**（扩缩容/健康翻转，Raft 每次过半写 = 放大 + 延迟）；② **容忍短暂陈旧**（消费端拿到旧列表的代价是一次调用重试，15_spring_cloud.md 3.1.2"过期路由可接受"同款论证）；③ **数据可从真实进程重建**（节点全丢，实例会重新注册——**注册表是"投影"不是"账本"**，无需持久化共识）。反向证据：持久化实例（基础设施）才是账本型数据——所以它才走 JRaft（2.2.2）。**"同一系统内按数据画像分级定一致性"**是本题真正的答题框架。

### 2.2.2 JRaft 在 Nacos 里用在哪？和 Distro 怎么对照？

**实现**：Nacos 内嵌蚂蚁 **JRaft**（Raft 的 Java 实现，bolt/自研 RPC + Protobuf，日志复制 + 过半提交 + Leader 选举 + 快照），用于：**持久化实例**的元数据与状态、配置模块部分元数据、以及 3.3 新增**分布式锁**的 Raft 一致性（4.1.2）。

**与 Distro 对照表**（旧文 2.7 的修正版，两处旧口径错误见下）：

| 维度 | Distro | JRaft |
|------|--------|-------|
| 目标 | AP 可用优先 | CP 一致优先 |
| 写入 | 任意节点受理（转发责任节点）| **仅 Leader**，过半落日志才应答 |
| 一致 | 最终一致（异步复制+verify 补偿） | 强一致（线性化） |
| 选举 | 无 Leader 概念 | 有，选举期不可写 |
| 数据形态 | 可重建的"投影"（临时实例） | 必须留存的"账本"（持久实例/锁） |
| 性能画像 | 高、写延迟低 | 每次写过半 RTT |

**旧口径纠偏（面试别沿袭）**：① "配置中心靠 JRaft 同步"——**不准确**：配置正文一致性靠**共享数据库**（3.1.3），Raft 管的是部分元数据/新场景；② "CP 用于金融注册、AP 用于电商"是简化叙事——真实判据是**数据是不是账本、变更频不频繁**（2.2.1 画像），金融系统的微服务地址表照样 AP 临时实例——"支付链路强一致"体现在**事务层**（21_seata.md），不是注册表。

### 2.2.3 Nacos 的自我保护机制？和 Eureka 的有何异同？

**触发与行为**：当某服务**健康实例占比低于保护阈值**（阈值可由服务端开关配置，默认口径以所用版本文档为准——旧资料流传的 0.85/15% 两说混用，别死记）时，Server **停止剔除不健康实例**、继续按原列表分发——控制台会给出保护状态提示；健康比例恢复后退出保护。

**和 Eureka 的哲学对照**（同：AP 信仰；异：判定与粒度）：

| | Nacos 自我保护 | Eureka 自我保护 |
|--|----------------|-----------------|
| 判定输入 | **健康实例占比**（以注册表内实例健康为准） | **续约比例**（实收心跳/预期心跳） |
| 视角 | "这个服务还剩几成活的" | "我这一侧网络还通不通" |
| 粒度 | 按服务 | 按 Server 全局（15 分钟窗口） |
| 触发后 | 停止剔除、保留全集 | 停止剔除、保留全集 |

**为什么必须有这机制**：网络分区/GC/机房抖动会让 Server"看起来"大批实例同时失联——若照常剔除，注册表清空 → 恢复后全量重注册风暴 + 期间调用全线失败 = **二次雪崩**；保护模式把"宁可放过"写成合同。**残留风险**：保护期间下发的列表混入死实例 → 客户端必须自带重试/熔断（15_spring_cloud.md 3.2.3），**AP 系统的一致性兜底永远在消费端**——这句是这类题的标准收口。

# 3. 配置中心原理

## 3.1 配置模型与生效链路

### 3.1.1 Nacos 配置的组织模型与优先级？

**坐标三元组**：`Namespace + Group + DataId` 唯一定位一份配置；DataId 命名约定（Spring Cloud 自动按这三类拉取）：
1. `${spring.application.name}.${file-extension}`（主配置）；
2. `${spring.application.name}-${profile}.${file-extension}`（profile 配置）；
3. `shared-configs` / `extension-configs` 列表项（显式声明的共享/扩展配置，各带 group 与 `refresh` 开关）。

**优先级（高→低，背错一次踩一次坑）**：**profile 主配置 > 主配置 > extension-configs（列表后项压前项）> shared-configs（同样后压前）> 本地 application.yml**。工程惯例：shared 放全公司公共件（日志级别、密钥引用地址）、extension 放业务线公共件、应用自己的留在主配置——**层级越高越具体，具体覆盖通用**。

**Boot 3 接入形态（2026 口径）**：`bootstrap.yml` 已退役——**`spring.config.import: nacos:app.yaml`**（或 `optional:nacos:`）走 ConfigData API（10_springboot.md 3.1.2 的加载机制、15_spring_cloud.md 4.1），连接参数挂 `spring.cloud.nacos.config.*`；旧教程的 bootstrap 写法在新工程会"配置无声失效"——**这是目前 Nacos 面试题第一大实操考点**。

**动态刷新开关**：主配置默认全量监听刷新；shared/extension 按项配 `refresh-enabled`（不配则改了不生效）——排查"改了配置没反应"先分层检查：dataId 对吗 → refresh 开了吗 → namespace 用 ID 了吗 → 应用侧 Bean 姿势对吗（3.1.2）。

### 3.1.2 配置动态推送与 Spring 侧刷新的完整链路？Nacos 2.x 改了什么？

**Server→客户端通道**：
- **1.x 长轮询**：客户端 `ConfigLongPolling` 线程发起 hold 请求（超时 30s，**Server 29.5s 主动返回防中间件切断**），请求带全部监听项的 **MD5 集合**；发布时 Server 比对 MD5 只回"哪些 dataId 变了"——**通知与传输分离**（客户端再发一次普通拉取取全文）；该模型无状态、穿透友好，是 Apollo 同款设计（15_spring_cloud.md 4.1.3）；
- **2.x gRPC**：注册/配置**共用长连接**（9848），发布后 Server 沿连接直接 `ConfigChangeNotifyRequest` → 客户端回 `ConfigQueryRequest` 取新值（仍是"通知+取数"两段，但同连接内完成、多路复用不占线程）；连接断开期间变更靠重连全量对齐 + MD5 校验兜底（2.1.3 的"push 加速、拉校准"通例）。

**客户端刷新链（Spring 侧）**：新配置写入 `NacosPropertySource` → 发 `RefreshEvent` → Spring Cloud Context `ContextRefresher.refresh()`：Environment 更新 → **@ConfigurationProperties 直接 rebind**（免代理、不重建 Bean）/ **@RefreshScope Bean 清缓存等下次访问重建**——通用机制全解见 15_spring_cloud.md 4.1.2；Nacos 侧独立开关：全局 `spring.cloud.nacos.config.refresh-enabled` 与 import 级 `refreshEnabled=false`（某些"启动期决策型"配置就该重启才变，显式关掉动态刷新是成熟做法）。

**排障口诀**（现场价值题）：改了没生效按序查——控制台发布状态（灰度中？）→ 监听查询看该 IP 的 MD5 对不对（3.2.1）→ 应用日志有无 `Refresh keys changed` → 目标 Bean 是 @ConfigurationProperties / @RefreshScope / @Value 无作用域（**@Value 不加 @RefreshScope 永不刷新**）。

### 3.1.3 配置的存储模型？Nacos 集群如何保证配置一致？

**存储两模式**：单机内嵌 **Derby**（开箱玩）；生产**外接 MySQL**——核心表：`config_info`（当前版本，UNIQUE 约束 tenant+group+dataId）+ `his_config_info`（每次发布/删除/回滚的历史行，支持按时间回滚）+ `config_tags_relation`（标签检索）。

**一致性模型（这题的硬核区分点）**：**配置数据的一致性锚在共享数据库，不在节点复制协议**——集群所有节点读写同一 MySQL，发布落库后各节点**从 DB 加载 + 内存缓存 + 监听广播**；所谓"集群"对配置而言是**无主从的水平扩展 + 共享后端存储**（对比命名模块 Distro 节点间同步——两套模块两套一致性策略，1.1.1 "耦合的是管控面不是数据面"的注脚）。由此推出的三个运维事实：
1. **MySQL 是配置的 SPOF**——主从、备份、慢查询治理按核心 DB 标准做（16_mysql.md）；
2. 集群短暂不一致窗口在"DB 写入成功 → 各节点缓存刷新/通知丢失重查"之间，靠 MD5 对账收敛；
3. **derby 模式升集群必须先迁库**（历史事故常客，"单机 Nacos 数据丢了"= derby 文件随容器销毁——挂载持久卷，23_docker.md）。

**读路径性能**：配置读取走节点**内存缓存**（CacheItem 带 MD5）+ 定时与 DB 增量对账（防外部改库绕过发布）；写路径发布走"校验→落库→发布事件→通知"链路；**3.3 起还加了加密发布 CAS 与条件查询**（AI 资源时代配置治理的补强，4.1.2）。

## 3.2 配置治理

### 3.2.1 配置灰度发布、监听查询、历史回滚分别怎么用？

**灰度发布（配置层）**：控制台对目标 dataId 选"**beta 发布**"填**目标 IP 列表**（按实例圈定，不再按标签——标签灰度属流量层 1.2.2）→ 仅匹配 IP 的客户端收到新配置 → 验证通过"**批量发布**"全量转正；beta 期间原配置对其他人**一字不变**——发布事故的标准止血动作：先灰度一台再铺开。2.x/3.x 还有**批量灰度（BETA/滚动分批）**与历史灰度记录查看。**纪律配套**：灰度完成必须"停止灰度"，忘关 beta 残留 = 下任发布者拿到"为什么这台机器配置不一样"的悬案（监听查询第一时间能戳破）。

**监听查询**：控制台按 dataId/IP 查"哪些客户端正在监听、各自缓存的 MD5 与当前值是否一致"——**配置排障第一工具**：发布后看目标 IP 是否已收到（MD5 变了=收到了；没变=连接/namespace/refresh 开关问题，3.1.2 清单）。3.2.4 版本还修了"跨集群节点聚合监听状态丢 namespace 过滤"的口径问题——细节不必背，知道查询是按节点汇总的即可。

**历史与回滚**：每次发布/回滚/删除都进 `his_config_info`——控制台一键回滚到任意历史版本（本质是**以历史内容再发一次新版本**，链路照走、灰度照用）；发布前 diff 新旧对比、变更审计（谁、何时、从哪台）是合规基线。**对比 GitOps**：Nacos 的发布记录是"运维账本"、Git 管配置是"研发账本"——团队要么认 Nacos 为唯一变更入口 + 导出进 Git 审计，要么把 Nacos 发布纳入流水线（33_cicd.md），**双头发布必出漂移**。

### 3.2.2 Nacos 权限与安全模型？配置里放敏感信息怎么办？

**权限三件套**：
1. **认证**：开启 `nacos.core.auth.enabled=true` + 配置 **token 密钥对**（`nacos.core.auth.plugin.nacos.token.secret.key`——默认密钥必须换，旧密钥可伪造 token 全站接管）+ server 互信身份键（集群节点间 gRPC/内部 API 鉴权，3.2.4/3.3 起强制对齐——旧集群升级前先把 identity key 配齐，否则滚动升级中途互信失败，release notes 明说的坑）；
2. **授权 RBAC**：角色 → 对 namespace/group/dataId 与服务的管理/读/写权限；命名空间即权限边界；
3. **控制台与 API 分离**（3.x console 独立进程）——管控流量与客户端数据流量物理隔离。

**敏感配置实践**：Nacos 存明文 + DBA 可见 = 合规不合格——路线一：**客户端解密插件**（3.x 官方 `config-encryption-plugin` SPI，落地 KMS/自定义算法，SDK 拿密文本地解密）；路线二：Nacos 只存**密文引用**，真身进 Vault/KMS（15_spring_cloud.md 4.1.1 的 Config-Vault 分工）；路线三（最低配）：namespace 权限收紧 + 审计 + 环境变量注入密钥。**至少做一层**——"配置中心里躺着生产 DB 密码明文"是安全审计必死项（30 后补：3.3 起客户端 API 鉴权默认开启，"忘关匿名访问"的时代在收尾）。

# 4. 生产实践

## 4.1 部署与演进

### 4.1.1 Nacos 生产部署要配哪些东西？9848 端口是什么？

**集群基线**：≥3 节点（JRaft 过半要求，持久实例/锁功能依赖选举）；**外接 MySQL**（主从 + 定期备份，3.1.3）；节点同机房/同网络域，负载均衡仅对 **8848**（HTTP）做 VIP——**gRPC 端口必须直连或四层透传**：
- `9848 = 主端口+1000`：客户端 gRPC（注册/配置长连接）；
- `9849 = 主端口+1001`：Server 节点间 gRPC（Distro/JRaft）；
- 偏移可配（3.3 起支持按属性独立配置）但默认口径先记死。

**第一大新手坑就在端口**：升级 2.x 后 LB/防火墙只开了 8848——客户端日志 `gRPC SDK connect failed ... 9848`，表现成"服务注册不上/配置不刷新"的玄学故障；七层 LB（Nginx http）也撑不住长连接语义，要么 stream 四层、要么客户端直连节点列表（**gRPC 不走 VIP、由 SDK 对多节点做轮询建连**是常见生产做法）。

**容量与配套**：连接数主导容量（2.x 一应用一长连接：万级实例=万级连接 + 心跳开销转移到连接层 keepalive，3000~5000 节点/连接单 Server 参考量级以压测为准）；JVM 堆不必大但**网络与 fd 上限要抬**（12_nginx.md 1.2.1 同款账）；监控四件套：节点状态（集群列表）、连接数与推送延迟、配置发布成功率/监听一致性（3.2.1 工具化）、MySQL 侧主从延迟；告警接值班。**客户端侧**：同应用多 namespace 拆分实例、`serverAddr` 逗号列全节点、K8s 用 Headless Service/DNS（23_docker.md、32_kubernetes.md）。

### 4.1.2 1.x → 2.x → 3.x 各代际的关键变化？

**1.x（HTTP 时代）**：8848 一把梭——心跳 5s、UDP push、长轮询配置；AP/CP 双协议就位但通道效率受限（2.1.1 三笔债）。

**2.x（连接化，2021 GA）**：
1. **gRPC 长连接**承载注册/心跳/订阅/推送/配置全流量（9848/9849）——断连即剔除、push 直推、性能与时效跨代；
2. **写读模型优化**：客户端按连接管理、服务端内存与同步压力下降；配置仍保留长轮询兼容 1.x；
3. **滚动升级兼容**："双写双读 + 请求迁移"——2.x Server 同时接 1.x HTTP 与 2.x gRPC：1.x 心跳写转 gRPC 侧、新注册写 HTTP 侧（迁移期互相同步），所以**服务端先升、客户端后升**即可不停机过渡；升级检查单：端口连通、混跑期 Distro 兼容开关、客户端版本下限。

**3.x（2025+，现役主线）**：
1. **Console 与 Server 分离**（独立进程/可独立升级）——管控面与数据面彻底拆家（安全面也收窄：客户端 API 不再暴露控制台逻辑）；
2. **AI Registry**：MCP Server/Agent/Prompt/Skill 的注册、版本、可见性与检索（3.2/3.3 起混合关键词+向量检索）——注册中心从"服务"扩到"智能体资源"；
3. 新能力：可选 **DNS 服务发现**、**分布式锁 SDK**（Raft 一致性+watchdog）、鉴权默认开启趋势（3.3 客户端 API auth default-on）、**Spring Boot 4/Jackson 3 兼容**、Server 需 **Java 17**（Client 仍 Java 8，2.5.x 线继续给 Java 8 存量送维护修复）；
4. 兼容清理：v1/v3 API 分代、废弃 Pipeline/MCP import 接口置 410——升级前按 release notes 对表。

**答题框架**：别背流水账，报**三段主线**——"2.x 把通道从请求级改成连接级（时效与规模），3.x 把架构从单体拆成平面（Console/AI/锁都是新平面上的功能），Java 基线从 8 迁到 17"。

## 4.2 可用性与故障

### 4.2.1 Nacos 整个挂了会发生什么？微服务会停摆吗？

**分层看（这题反直觉的答案才值钱）**：
1. **存量调用不受影响**：消费者手里是**本地缓存的服务列表**（内存 + 磁盘快照 `snapshot/`），Nacos 失联时继续按最后一次列表发起调用——注册中心不在调用链路上（15_spring_cloud.md 3.1.1）；
2. **配置读不受影响**：客户端本地快照兜底（3.1.3 同源设计），**启动顺序有坑**：实例重启且 Nacos 不可用 → 拉配置失败 → 按 `optional:nacos:` 与否决定启动成败——强依赖写法会让"注册中心故障"升级为"应用全部起不来"，**生产建议 optional + 本地基线配置**；
3. **变更能力丧失**：注册新实例/摘除故障实例/发布配置全部停摆，扩缩容与应急止血失效——**"能用但不能变"就是中间件半死的准确画像**；
4. 恢复后：客户端重连、全量心跳/重注册对齐，Distro 快照补偿（2.1.1/2.2.1；2.x 连接型实例的快照覆盖注册丢失问题在 2.5.5 修过——恢复期观察注册表完整性是升级纪律）。

**预案模板**：注册中心故障 → 冻结发布与扩缩容、禁止杀实例（会永久丢地址）；监控上"**推送延迟/连接丢失率**"比"节点存活"更早暴露 Nacos 亚健康；RTO 目标按"管控可停、数据面不瘫"设计；客户端日志级别与本地快照目录保留策略提前定。**收口句**："Nacos 高可用设计的答案不在 Server 集群本身，而在**客户端的缓存哲学**——把注册中心从强依赖降级为弱依赖。"

### 4.2.2 Nacos 常见故障场景如何处置？

**按症状给处方**（面试把"现象→根因→动作"配对讲）：
1. **"服务列表偶尔多一个已杀掉的实例"**：自我保护触发（2.2.3，查保护状态开关）/客户端心跳与 LB 缓存叠加（LoadBalancer 缓存周期 15_spring_cloud.md 3.2.2）——先分清 Server 视图还是 Client 视图脏；
2. **"注册成功但消费拿不到"**：namespace 不一致（用 ID 不用名）、group 不匹配、服务名大小写/后缀（`@@` 拼接模型 1.1.2）、ephemeral 属性两边不同（临时注册的实例持久视图里查不到）；
3. **"配置发布没反应"**：3.1.2 四步清单（发布状态/监听查询/refresh 日志/Bean 作用域）；
4. **"集群节点列表只剩自己"**：9849 未通（节点间 gRPC 被防火墙掐）/identity key 不一致（3.2.4 起强校验，release notes 点名）/MySQL 连不上（配置模块瘫痪但命名可能还活着——**两模块故障面分开诊断**，1.1.1 的注脚）；
5. **"全量重启后部分实例丢了"**：老版本 Distro 快照覆盖重连注册的 bug（2.5.5 修复）——**集群重启前摘流、重启后核对注册表**是操作纪律；
6. 性能类："推送延迟大"看连接数/GC/慢 SQL（3.1.3 MySQL 是配置侧咽喉）；"控制台卡"在 3.x 拆 console 后本就不是问题。

**治未病清单**：Server/客户端版本对齐节奏（2.x 客户端配 3.x Server 的兼容矩阵按官方文档）、鉴权与 identity key 全节点一致（3.2.2）、快照目录可写且随容器持久化、监听查询与保护状态进日常巡检面板——**"注册中心是变更枢纽"：它平时存在感最低，出事时全系统都依赖它做过变更**。

# 5. 对比与选型

## 5.1 注册中心对比

### 5.1.1 Nacos 和 Eureka 的机制差异体现在哪？

**总表已在 15_spring_cloud.md 3.1.2 给过（CAP 倾向、健康模型、多 DC、现状定位），本题只讲 Nacos 机制视角的四条增量差异**——面试先甩一句"总维度对照"再深入机制，层次立刻不同：

1. **一致性可按数据分级，而不是全局站队**：Eureka 只有 AP 一个姿态（自我保护再坐实）；Nacos 把"地址表按数据画像拆协议"——临时实例 Distro(AP)、持久实例 JRaft(CP)（2.2.1/2.2.2），**同一注册中心内两套一致性模型并存**。答题纠偏点：这不代表"金融选 CP 注册"（15_spring_cloud.md 3.1.2 已论证地址表本质是投影）——CP 侧真实用户是"注册方不说话的基础设施"，而不是"重要业务"；
2. **故障感知通道代差**：Eureka 三拍（客户端 30s 心跳 → Server 90s 剔除 → 客户端 30s 拉取，最坏 ~180s 收敛）；Nacos 2.x 断连即剔除、gRPC 直推（2.1.1），**秒级**收敛——同样叫"最终一致"，收敛速度差一个数量级，这是 2.x 换 gRPC 最直观的业务红利；
3. **治理能力是产品级 vs 协议级**：Eureka 交付的是注册表本身（客户端 SDK 各凭本事）；Nacos 自带**权重/元数据/Cluster/标签路由原料 + 控制台操作面**（1.2.2 的灰度三原语、beta 发布、监听查询）——"注册中心要不要长控制台"两家给出了相反答案，国内运维语境下 Nacos 的产品化是决定性优势；
4. **推送可靠性工程**：Eureka 无推送（纯拉 + 客户端缓存），一致性全靠窗口期忍耐；Nacos 1.x 的 UDP push 走了另一极端（不可靠通知，2.1.3 三笔旧账）→ 2.x 用连接级 push + 拉取校准收回——**"推拉结合 + 本地快照兜底"（4.2.1）是 Nacos 对 Eureka 纯拉模型在时效维度的反超**，而 Eureka 的纯拉在实现极简维度反过来制衡。

**收口**：两者都信奉"注册表短暂陈旧可接受"（AP 底色），差异在**把哪些治理动作收进服务端**与**用什么通道收敛**——选型上 2026 年已无悬念：新建不用 Eureka（Netflix 停更，15_spring_cloud.md 3.1.2），这题的价值在讲清"机制差在哪"而非"谁赢了"。

### 5.1.2 Nacos 对比 Consul、Apollo 各看什么？

**对 Consul（同为注册+配置，15_spring_cloud.md 3.1.2 表外讲机制分歧）**：
- **健康模型哲学**：Consul 以**服务端探测**为主角（agent 本地检查、Serf gossip 判活），注册方可以完全无 SDK（HTTP 注册/服务定义文件都行）；Nacos 以**客户端 SDK** 为主角（临时实例自报，1.2.1）——前者对非 Java 栈与黑盒系统友好，后者对 Spring 全家桶体验顺滑（自动注册零配置）；
- **多 DC 原生度**：Consul 的 **WAN 联邦**（server 间跨 DC gossip + 网关代理）是设计目标级能力，跨机房服务目录开箱即用；Nacos 多单元/多活靠 namespace/分组 + 应用层同步预案自搭（4.1.1 的部署边界）——**跨国多 DC 强诉求时 Consul 仍是机制更干净的答案**；
- 配置侧 Consul KV 弱治理（无灰度/回滚审计这类产品件，3.2.1 全家桶是 Nacos 的强项）；K8s 语境 Consul 已让位原生 Service（15_spring_cloud.md 5.2.1），Nacos 靠 SCA 生态守住 Java 阵地——**两者竞争面在缩，各自主场在固化**。

**对 Apollo（配置中心专精，15_spring_cloud.md 4.1.1 选型表之外补机制）**：
- **生效通道同代不同款**：Apollo 至今 HTTP 长轮询（notification 挂 60s，按 namespace 粒度，15_spring_cloud.md 4.1.3）；Nacos 2.x 走 gRPC 直推（3.1.2）——时效 Apollo"秒级够用"、Nacos"毫秒级近实时"，但 Apollo 无状态服务端对 LB/网关最友好（4.1.1 长连接治理成本的反面教材互读）；
- **数据模型分歧**：Apollo 以 **App + Cluster + Namespace** 组织配置、灰度/审计/权限流是**企业治理级**（发布审批、灰度按机房集群圈定、全局搜索回滚细）；Nacos 三元组 + beta 按 IP（3.2.1）治理件轻量一档——**"配置要不要走审批流"是两家用户画像的分水岭**：金融/大厂强合规 → Apollo；互联网节奏 + 注册配置一体省事 → Nacos；
- 存储侧同构（都锚共享 MySQL，一致性策略 3.1.3 同款），运维件数 Apollo 更多（Portal/Admin/Config 三服务，15_spring_cloud.md 4.1.1 表）——**Nacos 赢在一体化与生态默认，Apollo 赢在治理纵深**，答题报出"按组织对配置变更的管控强度选"即闭环。

**收口句**：对比题的通用作答纪律——**先指认总表（15_spring_cloud.md 3.1.2/4.1.1），再讲本篇机制增量（协议分级、连接代差、治理产品化）**；选型结论永远是"场景 + 组织"双轴，单轴报答案都是背书。
