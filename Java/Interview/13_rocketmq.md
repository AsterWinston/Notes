# 1. 架构与基本概念

## 1.1 总体架构

### 1.1.1 RocketMQ 的整体架构由哪些组件构成？各自职责？

**四大件**（阿里开源、电商与金融场景打磨出的业务消息中间件，Java 编写）：

| 组件 | 职责 | 形态要点 |
|------|------|---------|
| NameServer | **轻量路由注册中心**：Broker 向其注册 Topic 路由，Producer/Consumer 定期取路由 | 无状态、节点间互不通信、部署简单，可视为"最终一致的服务发现"（1.1.2） |
| Broker | **消息存储与投递主体**：收发消息、Topic 管理、消费队列管理、重试/死信/定时服务、HA 复制、持久化与过期删除 | 以 Master/Slave（或 DLedger 组）为单位部署，是集群里真正的"重"角色（4.1 存储、4.2 高可用） |
| Producer | 发送消息：同步/异步/单向/批量（1.2.1） | 从 NameServer 拿路由后**直连 Broker**，按队列选择策略写入 |
| Consumer | 消费消息：PushConsumer（事实标准）/ SimpleConsumer（5.x）；集群/广播（3.1） | 本质都是 Pull（长轮询，3.1.2），客户端自己做 Rebalance（4.x） |

**数据模型三层**：Topic（逻辑分类）→ MessageQueue（物理分区，并行与有序的基本单位，1.1.3）→ Message（带 Tag/Key/Property 的消息体）。**路由链路**：Broker 每 30s 向**所有** NameServer 注册心跳 → Producer/Consumer 每 30s 拉取路由 → 与 Broker 通信收发。注意**客户端直接对 Broker 收发**，NameServer 不在数据路径上——它挂了只影响"拿新路由"，已有连接照常工作，这是它敢做这么轻的根本原因。

**与通用 MQ 概念对齐**：Topic≈Kafka 的 topic/队列、Queue≈partition、Consumer Group≈消费组语义；"Broker 组内一主多从 + Group 下多 Queue"的两级结构是其部署特色（4.2.2）。

### 1.1.2 NameServer 为什么自研而不用 ZooKeeper？

**结论**：路由注册这件事**不需要强一致**，ZooKeeper 的 CP 语义是杀鸡用牛刀还引入运维负担——NameServer 用"AP + 全量复制 + 无副本同步"把注册中心削到了极简。

**机制对照**：

| 维度 | NameServer | ZooKeeper |
|------|-----------|-----------|
| 一致性模型 | AP：节点间**零通信**，每个节点各自维护全量注册表 | CP：ZAB 过半写入才应答 |
| 数据同步方式 | Broker 向**每台** NS 重复注册（30s 心跳），天生多副本 | Leader 同步、Follower 转发写 |
| 节点故障影响 | 任一 NS 挂掉：客户端换一台拿路由即可 | 过半不可用整个集群不可写 |
| 脏数据风险 | 短暂过期路由（Broker 挂了 NS 最多 120s 才摘除：每 10s 扫描、超 120s 无心跳剔除） | 强一致无此问题 |
| 运维 | 两个 jar 跑完事，无磁盘规划 | 独立集群、myid、过半原则 |

**过期路由为什么可接受**（答题深度所在）：客户端拿到"已死 Broker"的路由后发送失败，**Producer 默认重试会换其他 Broker**（1.2.1），一次失败被链路自愈兜住；路由短暂不一致的代价被上层容错消化，所以无需为此付出 CP 的复杂度和延迟。**设计哲学**：把一致性要求最高的活（消息不丢）留在 Broker 存储层（4.2），注册层只做尽力而为——分层定级、各取所需。

**追问**："NS 挂一台会不会脑裂"——NS 之间本来就没有"裂"可言：无主从、无同步、允许各自数据略有差异，客户端视角只是"路由视图短暂不同"，不构成正确性问题。

### 1.1.3 Topic 和 Queue 什么关系？分区数为什么重要？

**关系**：Topic 是用户视角的逻辑频道；服务端把它切成 **N 个 MessageQueue** 散布在各 Broker 上——Queue 才是存储、并行消费、顺序保障的物理单位（一个 Queue 属于一个 Broker，一段连续的 CommitLog+ConsumeQueue 视图，4.1.1）。默认建 Topic 每 Broker 8 读 8 写队列。

**Queue 数决定三件事**：
1. **消费并行上限**：集群模式下 Queue 是分配的最小粒度，**消费实例数 > Queue 数则多出的实例空转**（3.3.1）——"扩容没效果"先查 Queue 数；
2. **顺序域**：局部有序按业务 key 哈希进同一 Queue（2.1.1）——Queue 数就是哈希桶数；
3. **堆积容量摊薄**：单 Queue 内 offset 连续，消费进度按 Queue 记录（3.1.3），多队列才能多机并行追。

**扩缩容 Queue 数的代价（高频事故题）**：
- 扩容：触发全体 Rebalance，队列重新洗牌——**顺序业务直接破功**（原属同一 Queue 的订单被分到两个桶，各自有序、整体乱序），必须先停写或新旧 Queue 双写过渡，让同一 key 的**在途消息消费完**再切；
- 缩容：不能物理删除有剩余消息的队列，要等消费完、且 rebalance 视图收敛后再缩；
- 缩容/扩容都让"重置位点"的对照系变复杂（3.1.3）。

**5.x 补充**：LiteTopic（轻量级队列，百万级主题场景）与 LMQ（4.9+，把"每用户一个小队列"的成本降下来）解决的是"Topic/Queue 数量爆炸导致元数据与调度膨胀"——传统 MQ 按队列建模的粒度之争，与 Kafka 分区数焦虑同根（31_kafka.md）。

## 1.2 客户端与版本演进

### 1.2.1 同步、异步、单向发送有什么区别？怎么选型？批量呢？

**三种方式一个源头**（底层都是向 Broker 发 `SEND_MESSAGE` 请求，差别只在"等不等回应、怎么等"）：

| 方式 | API | 语义 | 场景 |
|------|-----|------|------|
| 同步 sync | `producer.send(msg)` 阻塞拿 `SendResult` | 最高可靠：确认落盘（按刷盘/复制策略）才算成功 | 交易、通知等**默认选择** |
| 异步 async | `send(msg, SendCallback)` | 不占调用线程，回调 onSuccess/onException（回调在独立线程池，别在里面做重活） | 高吞吐且要结果反馈：日志上报、埋点 |
| 单向 oneway | `sendOneway(msg)` | 发完就走，**不知道成没成功** | 允许丢的场景：广播打点、心跳 |

**同步发送的隐藏可靠性**：`retryTimesWhenSendFailed=2`——同步失败共 3 次尝试且**每次换 Broker**（`latencyFaultTolerance` 还会给慢/坏 Broker 降权一段时间）；异步默认重试 2 次但**同一队列**。由此引出必考追问：**发送重试 = 重复消息的第一来源**（Broker 收到并写成功、ACK 路上丢了，客户端超时重试 → 两份）——所以"重试次数别乱调大 + 消费端必须幂等"（3.2.3）。

**批量消息**：`send(List<Message>)` 打包一个请求（省 RT 与系统调用），约束：同一 Topic、**总大小 ≤ 4MB**（单条限制在批上同样成立，4.3.1）；Kafka 风格的"客户端攒批提吞吐"RocketMQ 原生没有强需求——CommitLog 单文件混写本就摊薄了随机性（4.1.1）。

**易错**：oneway 在事务/顺序场景是灾难；`SendStatus` 的 `FLUSH_DISK_TIMEOUT/FLUSH_SLAVE_TIMEOUT` **也是发送成功**——消息已进 Broker（内存），只是承诺的持久化/复制没达标，别当失败重试（重试反而放大重复）。

### 1.2.2 RocketMQ 5.x 有哪些架构级变化？

**一句话**：4.x 是"富客户端连 Broker"，5.x 转向"**Proxy 接入层 + 存储计算分离 + 轻量客户端**"的云原生形态。

| 变化 | 内容 | 动机 |
|------|------|------|
| **Proxy 代理层** | 新增无状态 Proxy：gRPC/Remoting 多协议接入、协议转换，客户端不再直连 Broker | 网络隔离（Broker 藏内网）、无损升级、多语言统一入口、Serverless 弹性 |
| **gRPC 多语言 SDK** | 官方 Go/Python/C++ 等客户端走 gRPC；Java 侧提供**轻量 SimpleConsumer**（显式 receive/ack，无本地 rebalance） | 生态开放；把消费调度权从胖客户端上移 |
| **Pop 消费模式** | Broker 端"不可见时间"语义：一次 Pop 拿多条、处理完显式 ACK、超时自动重投——**多客户端可共消费同一 Queue**，客户端无需 Rebalance | 弹性扩缩（Serverless 秒级）、终结"实例数 ≤ 队列数"的并行天花板（1.1.3） |
| **定时消息增强** | 任意时间精度定时（时间轮实现），不再局限 18 级（2.2.1） | 业务调度刚需 |
| **HA 解耦** | **RocksMQController**（Controller 集群）接管选主：Replica 灵活扩、Slave 可承担读（Acting-Master） | DLedger 三副本捆绑存储的运维负担（4.2.2） |
| 可观测与治理 | OpenTelemetry metrics 原生输出；ACL 动态配置、多数据源 | 云环境运维标准件 |

**答题姿态**：5.x 不是"加功能"而是**架构换代**——接入与存储解耦（Proxy）、客户端瘦身（SimpleConsumer/Pop）、运维弹性化（Controller）三条线全部指向 K8s/Serverless 部署形态（23_docker.md、32_kubernetes.md）；面试问"你们用 4.x 还是 5.x"，能讲出这三条线的取舍（客户端升级成本 vs 弹性收益、老 Remoting 协议兼容）就是加分答案。

# 2. 消息类型与高级特性

## 2.1 顺序消息

### 2.1.1 RocketMQ 如何实现顺序消息？全局有序和局部有序怎么选？

**先立框架**：MQ 的"有序"只在**单 Queue 内**天然成立（Queue 即 append-only 序列，21 行讲透见 4.1.1）——所以顺序问题的本质是"**让该排队的消息进同一个 Queue，并保证同一 Queue 同一时刻只有一个线程在消费**"。

**生产端**：`MessageQueueSelector` 按业务 key 取模——

```java
producer.send(msg, (mqs, m, arg) -> {
    int idx = Math.abs(arg.hashCode()) % mqs.size();   // arg = orderId
    return mqs.get(idx);
}, orderId);
```

**消费端**：`MessageListenerOrderly`——RocketMQ 对每个**本地 ProcessQueue 加锁**（再配 Broker 端队列锁防多实例并发），保证一个 Queue 串行消费；消费失败返回 `SUSPEND_CURRENT_QUEUE_A_MOMENT`：**原地挂起该队列稍后重试**（`suspendCurrentQueueTimeMillis`，默认 1s），不进重试队列、不进死信——有序消费没有"跳过这条"的选项。

**全局有序**：Topic 只配 1 个 Queue + 单消费实例——吞吐退化成单机串行，几乎没人这么用；正确思路是**把顺序域缩小**：同一订单的消息有序、不同订单并行（局部有序），极端才用单队列。

**两个必考追问**：
1. **队头阻塞**：一条毒消息一直失败 → 整个 Queue 停摆、后面全堵——有序消费的固有代价，工程对策：重试上限 + 人工熔断（把毒消息转储、放行队列），别指望 MQ 自己恢复；
2. **扩队列破坏顺序**：rehash 换桶，在途消息新旧队列各一段（1.1.3）——发布顺序消息的 Topic 前**队列数一次配足**。
3. **发送重试也破序**：同批消息逐条同步发，第一条超时重试、第二条已先到——严格顺序要 `retryAnotherBrokerWhenNotStoreOK=false` 并考虑"顺序 + at-least-once 本就是矛盾体，幂等仍要带"。

**场景落点**：订单状态机（创建→支付→发货）、binlog 同步（同一行的变更必须保序，14_canal.md 的下游正解）。

## 2.2 延时与定时消息

### 2.2.1 延时消息怎么实现？为什么 4.x 只有固定 18 个级别？

**4.x 机制**：`setDelayTimeLevel(1~18)`，级别表 = `1s 5s 10s 30s 1m 2m 3m 4m 5m 6m 7m 8m 9m 10m 20m 30m 1h 2h`（Broker 参数 `messageDelayLevel` 可改但全集群口径要一致）。流程：发送时消息**被改写到内部 Topic `SCHEDULE_TOPIC_XXXX`**——每个级别一个 Queue（级别 Queue 内到期时间天然单调，无需排序结构！），真实目标 Topic/Queue 存在消息属性里；Broker 的定时扫描服务查各级别 Queue 头部，到期消息**重写回 CommitLog** 投递到原 Topic，此后与普通消息无差别。**消费端零感知**，精度为"扫描周期级"（秒级）。

**为什么用级别而不是任意时间**（设计考量，这题的灵魂）：任意延时需要**按到期时间排序**的结构（时间轮/最小堆）——每条消息插入都要维护排序，写放大与并发复杂度高；级别方案把"排序"转化为"N 个各自有序的 FIFO 队列头部检查"，实现 O(1) 插入。消费重试（3.2.1）的退避正是借用这套级别机制实现的。

**5.x 定时消息**：引入 **TimerMessageStore**——两级时间轮（秒针盘+分针盘）支持**任意时间精度**的定时（默认上限数天、可配），消息进 `TimerWheel` Topic；从此"订单 N 分钟后关单"不再被迫向上取整到 30m/1h 档。**选型口径**：级别够用用 4.x（成熟），真需要任意时间上 5.x 或自建（Redis zset/延迟队列方案见 27_redis.md）。

**经典用法与坑**：订单超时关单 = 下单发延时消息 + 到期查状态补偿（**兜底语义**，别当精确闹钟用——扫描与消费延迟叠加、重复投递照常有，处理逻辑幂等，3.2.3）；级别消息"重写回原 Topic"意味着**存储双份**（延时期内 CommitLog 体积膨胀是正常现象，别误判为堆积）。

## 2.3 事务消息

### 2.3.1 RocketMQ 事务消息的原理？半消息和回查是怎么回事？

**解决的问题**：本地事务（写 DB）与发消息这两步跨资源，无法用本地事务包住——要么"发了消息、事务回滚"（幽灵消息），要么"事务提交、进程死亡消息没发"（漏发）。事务消息给出**最终一致**方案：消息先占位、本地事务裁决后才可见，裁决丢了中间件**反向追问**。

**三方时序**（TransactionListener 两个回调 + 一个中间件事务表思想）：

```text
① Producer → Broker：发半消息（half，写入内部 Topic RMQ_SYS_TRANS_HALF_TOPIC，消费端不可见）
② Broker 返回成功 → Producer 执行 executeLocalTransaction()（本地 DB 事务）
③ 按结果二阶段：成功 → Commit（Broker 把消息重写回真实 Topic 投递）；失败 → Rollback（丢弃）
④ ②③ 之间 Producer 宕机/网络断 → Broker 对"长时间未决"的半消息定期**回查**
   checkLocalTransaction()（每 60s 一轮、最多 15 次，超次默认当作回滚丢弃）
```

`TransactionListener`：`executeLocalTransaction()` 返回 COMMIT/ROLLBACK/UNKNOW——**UNKNOW 是关键选项**：本地事务还没走完（如异步链路）就返回 UNKNOW，把裁决交给回查；`checkLocalTransaction()` 里按业务单据状态反推（"订单已支付记录存在 → COMMIT"），**查的是业务状态而非消息发送记录**——这是回查能成立的原因：本地事务的结果必然落在业务数据里。

**故障矩阵**（答全这张表才算懂）：① 半消息发送失败 → 本地事务干脆不执行（半消息成功是前提）；② ② 之后 Commit 丢失/宕机 → 回查兜底；③ 回查查到的业务结论与重试冲突（回查时事务刚好回滚）→ 靠回查实现返回 ROLLBACK 收尾；④ 15 次回查仍无结论 → 丢弃（告警 + 人工，**别把它当"反正会自动恢复"的黑盒**）。

**语义边界**：事务消息保证的是"**本地事务提交 ⇒ 消息必然发出**"（单向蕴含）；消息发出≠下游必然消费成功——消费侧仍靠重试/死信/幂等（3.2）。回查只对**同一 Producer Group** 的在线实例发起，实例全下线期间回查会失败累计——发布时别让事务回查断粮。

### 2.3.2 事务消息 vs 本地消息表，怎么选？

**同一问题的两种解**：本质都是"**把消息写入放进本地事务，异步投递 + 状态核对**"——本地消息表是自己实现这套，事务消息是中间件内置这套（半消息 = 消息表记录，回查 = 扫表核对，Commit = 标记投递）。

**方案对比**：

| 维度 | RocketMQ 事务消息 | 本地消息表（自建） | 最佳努力通知 |
|------|------------------|-------------------|--------------|
| 一致性 | 最终一致，中间件托管 | 同 DB 事务内写表，强前提；投递靠扫表程序 | 尽力发 + 定时补偿轮询 |
| 开发量 | 实现两个回调即可 | 表设计、扫表、状态机、清理都要写 | 最少，但只保"尽力" |
| 侵入性 | 依赖 RocketMQ 能力 | 换 MQ 也能用（**与中间件解耦**） | 无 |
| 时效 | 秒级（回查周期） | 扫表周期，可做到亚秒 | 分钟级容忍 |
| 运维 | 半消息积压、回查失败数要监控 | 表膨胀、扫表慢查询要治理 | 补偿任务与业务耦合 |

**选型答法**：栈里 RocketMQ 是既定设施、且要事务语义的场景多 → 事务消息（少养一套扫表基建）；**不能把消息中间件写进架构基因**（多云多 MQ、金融强审计要全自持证据链）→ 本地消息表；只是"发失败可容忍、下游能轮询对账"（对第三方回调通知）→ 最佳努力通知。Seata AT/TCC 是另一维度——那是对**跨服务数据同步强一致**的补偿型方案（21_seata.md、34_distributed_theory.md），与"异步通知最终一致"不是替代关系，别在面试里混成一锅。

## 2.4 消息过滤

### 2.4.1 Tag 过滤和 SQL92 属性过滤的原理与代价？

**两级过滤架构**（Broker 粗筛 + Client 精筛）：

```java
consumer.subscribe("OrderTopic", MessageSelector.byTag("pay || refund"));   // Tag
consumer.subscribe("OrderTopic", MessageSelector.bySql("region = 'east' AND amount > 100")); // SQL92
```

- **Tag**：生产端 `setTags("pay")`；ConsumeQueue 条目里存的是 **tag 的 8 字节 hashCode**（4.1.1 的 20 字节三元组之一）——Broker 拉取时**按 hashcode 比对**先筛一轮（不读消息体，极快）。**hash 会碰撞**：A 与 B 两个 tag 哈希相同会"误命中"，所以消费者拿到消息后**再按 tag 字符串精确比对**去重——这就是"Broker 粗筛 + Client 精筛"两级设计的由来，追问"为什么还会收到不匹配的 tag"答碰撞即可。约束：一条消息多个 tag 时消费端只能拿首个 tag 比对，**tag 集合别当属性列表滥用**；
- **SQL92**：对用户属性（`putUserProperty`）按表达式过滤——Broker 需要**读 CommitLog 消息体属性**才能求值（ConsumeQueue 的 hash 位不够用），代价明显更高：必须 `enablePropertyFilter=true`，且过滤发生在遍历存储之后，**过滤谓词越宽越像全量扫描**（堆积时 SQL 过滤会放大消费延迟）。

**工程边界**：过滤解决的是"**订阅端分流**"，不是"**服务端路由重设计**"——同一 Topic 内 tag/属性是有限维度（业务动作、租户标记），高基数维度（userId）别拿来做过滤（每个消费者全表扫属性，等于没滤）；真正按租户物理隔离走 Topic 拆分或 LMQ（1.1.3）。与消费组的关系：过滤失败的**不投递不占重试**（被滤掉的位点照样推进——**"SQL 过滤 + 后续想重放"只能重置位点重扫存储**，受 4.1.3 保留期约束）。

# 3. 消费机制

## 3.1 消费模式与进度

### 3.1.1 集群消费和广播消费有什么区别？

**语义分野**（`MessageModel`，默认 CLUSTERING）：

| 维度 | 集群消费 CLUSTERING | 广播消费 BROADCASTING |
|------|--------------------|-----------------------|
| 一条消息被消费几次 | 组内**一个**实例消费 | 组内**每个**实例都消费 |
| 位点存哪 | **Broker** 统一维护（consumerOffset.json，3.1.3） | 4.x：**消费者本地文件**（重启换机即丢进度） |
| 失败重试 | 有：重试队列 + 死信（3.2.1/3.2.2） | **无**：失败就失败，不重投 |
| 并行扩容 | 有效（Queue 在实例间重分配） | 无意义（每实例全量） |
| 典型场景 | 业务处理（订单、库存） | 本地缓存刷新、配置广播、节点间状态同步 |

**答题落点**：广播的"每实例全量 + 无重试"决定了它只适合**丢了也无所谓、可重复执行**的通知型消息——缓存失效广播丢了靠 TTL 自愈这类；**拿广播做可靠业务是误用**（实例滚动重启期间本地位点漂移，消息要么重复要么错过）。配置推送场景今天更多交给注册/配置中心（17_nacos.md 的长轮询推送模型与广播语义异曲同工，面试可比一句）。**5.x 改进**：广播改由**服务端实现**（基于 Pop 的组播语义），位点统一回 Broker、运维可见——4.x 本地位点之坑在新版本被填平，报得出这条演进即高分。

**易错**："广播消费 = 所有消费组都收到"错——广播是**组内**每个实例；跨组各自消费全量是"多 Consumer Group"的订阅模型（同一条消息被组 A、组 B 各消费一次，与组内模式无关），这层"组间发布/订阅、组内竞争"的区分是本题第一考点。

### 3.1.2 PushConsumer 真的是"推"吗？长轮询怎么实现？

**结论**：RocketMQ 没有真推——**Push = 长轮询 Pull 的封装**。客户端 `PullMessageService` 单线程不断对每个 ProcessQueue（本地队列视图，每 Queue 一个）发起 pull 请求；"实时性"由 **Broker 挂起请求**制造：

```text
① Consumer 发 Pull（带 offset、订阅表达式、suspendTimeout）
② Broker 查 ConsumeQueue：有消息 → 立即返回（FOUND）
③ 无消息且开了长轮询 → PullRequestHoldService 把请求挂起不回复
   - 新消息写入 CommitLog → Reput 链路通知 NotifyMessageArrivingListener → 立即唤醒挂起请求返回
   - 或挂起超时（十秒量级）→ 返回空响应，客户端下一轮继续
④ 客户端拿到消息 → 投递消费线程池 → 消费完更新本地 offset → 继续 pull
```

**三重节制防失控**（pull 不是无脑循环）：`pullBatchSize=32`（每次最多 32 条）；**流控阈值** `pullThresholdForQueue=1000` 条或 `pullThresholdSizeForQueue=100MB`——ProcessQueue 本地堆积超限就推迟下轮 pull（**背压设计：消费慢则少拉，别让消息在客户端内存里堆爆**）；订阅变化时清 ProcessQueue 重拉。

**长轮询 vs 短轮询**：短轮询固定间隔空转（延迟=间隔、请求全是浪费）；长轮询"无消息让请求飞一会儿"，延迟降到**写入即唤醒**的近实时、无效请求几乎归零。同一思想：HTTP 长轮询（4_java_web.md）、Nacos 配置推送（17_nacos.md）、Kafka consumer 的 fetch 超时——面试串起来讲是体系化信号。

**追问**：① "消费实时性和吞吐谁控？"——**消费者自己**（pull 语义），Broker 不越权塞数据，天然适配能力参差的消费端；与 Kafka 同模型，对比 RabbitMQ 真推 + qos 信用流控（37_rabbitmq.md）是另一套哲学；② "OFFSET_ILLEGAL 何时出现"——请求的 offset 落在已删除文件区间（4.1.3），Broker 按策略返回边界 offset，客户端校正继续——"消息被过期删了"的消费端症状。

### 3.1.3 消费进度（offset）如何管理？重置位点会发生什么？

**位点链路**（集群模式）：消费线程处理完 → `ConsumeMessageService` 把该 ProcessQueue 已消费的**最小连续 offset** 写进本地 `OffsetStore`（TreeMap）→ 定时（约 5s 客户端提交 + Broker 侧约 10s 落盘）**提交给 Broker** 持久化（`consumerOffset.json`）→ 重启/迁移实例后从 Broker 拉回续消费。**要点**：提交粒度是"连续完成的最小值"——一条慢消息会**卡住整批位点**；期间实例崩溃，未提交部分会**整批重投**（3.2.3 重复来源之一）。

**新组起始位置**（`ConsumeFromWhere`）：`CONSUME_FROM_LAST_OFFSET`（默认：新组从队列尾部开始，**历史消息视为已过**——上线新消费组"没消息进来"先看这个）、`FIRST_OFFSET`（从头全量，注意早已过保留期被删的部分拿不到）、`TIMESTAMP`（按时间点定位，重置的标准玩法）。

**重置位点的两种语义**（控制台/mq-admin 按时间重置，事故高发操作）：
1. **往前拨（回溯）**：历史消息**重新投递**——前提：消息还在保留期内（4.1.3，默认 72h 且磁盘紧张更短）+ **消费逻辑幂等**（回溯重放 = 人为制造重复风暴）；
2. **往后拨（跳过）**：中间的消息**永久错过**——先确认可否离线补偿（从 DB/binlog 对账重推），"先跳过止血、再对账补数"是标准组合拳。

**易错**：位点重置只对**停止中的消费组**生效才可控（在线消费时重置会被客户端上报覆盖——控制台"重置报错"的常见根因）；广播模式 4.x 位点在本地，Broker 上重置无效（3.1.1）。追问"at-least-once 怎么变成 exactly-once"——MQ 侧做不到（Kafka 事务也只是 producer 侧 EOS 特例），**消费幂等 = 唯一正解**（3.2.3）。

## 3.2 失败重试与去重

### 3.2.1 消费失败后 RocketMQ 如何重试？有序消费的重试有何不同？

**普通（并发）消费**：监听器返回/null 或抛异常 → 消息**离开原队列**进入该消费组的**重试 Topic `%RETRY%+group`**，延迟递增后再投——实现直接借用延时级别机制（2.2.1）：`delayLevel = reconsumeTimes + 3`，即第 1 次重试 10s、第 2 次 30s、第 3 次 1m……一路到 2h；**默认最多 16 次**（`maxReconsumeTimes` 可调），每次重试 `reconsumeTimes` 随消息属性带上——消费代码里读它可以"第 3 次以后改走人工"。**原队列位点照常推进**：失败不阻塞后续消息（与有序消费的分水岭）。

**重试队列的归属细节**：`%RETRY%group` 的队列数与消费实例数联动（每实例认领一个重试队列，避免并发消费同一条重试消息）；重试消息回到**组内任意实例**（不保证同实例），跨实例重试状态共享靠 Broker 存储——这就是它比"本地内存重试"耐重启的原因。

**有序消费**：不能进重试队列（打乱顺序）——`SUSPEND_CURRENT_QUEUE_A_MOMENT` **原地挂起、同队列同位点无限重试**（默认间隔 1s）：毒消息 = 队头永久阻塞（2.1.1），**没有死信兜底**。工程对策：重试计数（orderly 也带 reconsumeTimes）超阈值后**人工介入**：暂停消费 → 摘出问题消息（导出/改状态）→ 恢复消费。

**答题延伸**：重试风暴的放大效应——下游 DB 抖动导致全量失败 → 重试消息与正常消息**叠加双倍流量**打向同一个脆弱下游；对策：消费侧对"依赖不可用"类异常**快速失败拉长延迟级别**（返回 RECONSUME_LATER 前把 delayLevel 手动设大）、熔断（20_sentinel.md）、以及"重试 Topic 与主 Topic 分开监控告警"。

### 3.2.2 什么是死信队列？死信怎么处理？

**成因**：重试到顶（默认 16 次）仍未成功的消息被投递进 `%DLQ%+consumerGroup`——**再也不会自动重试**，静躺等处置。进入条件还有：消息本身过期（重试期间躺过了保留期，Broker 直接判死，4.1.3）。

**与重试队列三连辨**（这题的送分区）：

| 维度 | `%RETRY%group` | `%DLQ%group` |
|------|----------------|--------------|
| 消息去向 | 延迟后继续尝试消费 | 不再投递 |
| 生命周期 | 短暂中转 | 按 Topic 保留期存储 |
| 语义 | "还没放弃" | "已放弃，等人来" |

**处置 SOP**（答出闭环才是实操派）：
1. **监控前置**：DLQ 堆积量是**一级告警指标**（控制台/云监控/Dashboard 的 topic 维度 diff）——"死信队列没人看 = 故障黑洞"；
2. **诊断**：DLQ 消息带完整上下文（原 Topic/Queue、reconsumeTimes、body），顺着 trace 查最后一次异常（4.3.2）；
3. **修复后重放**：临时起一个订阅 `%DLQ%group` 的消费者把消息**回投原 Topic**（或人工修复数据后重放）——重放前同样幂等准备（回溯语义，3.1.3）；
4. **分级策略**：核心链路死信 = P2 事件；批量死信先查"是不是下游故障的连锁"（一次故障炸出上万死信，重放要**限流重放**，直灌回主 Topic 等于二次攻击）；
5. **保留与清理**：DLQ 也吃存储，设人工处置 SLA 或归档转储，别养成"垃圾场"。

**广播与有序没有死信**（3.1.1/3.2.1 的推论）——"你们的有序消息失败怎么办"的诚实答案是"队头挂起 + 告警人工"，这是有序消费的固有运维成本，主动讲出比背概念值钱。

### 3.2.3 消息为什么会重复？幂等怎么做？

**重复的四个来源**（RocketMQ 承诺 at-least-once，重复是设计内行为）：
1. **发送重试**：Broker 写成功、ACK 丢失 → 客户端超时重发 → 两份（1.2.1）；
2. **消费重投**：处理成功但 offset 未及提交实例崩溃/rebalance（3.1.3 的"连续最小值"提交粒度）→ 整批重来；
3. **重试队列**：失败重投本身就是一次新消息，**上一次可能已部分执行**；
4. **人为回溯**：位点重置/消息补发（3.1.3）。

**幂等方案按强度排序**：

```text
① 业务唯一键 + DB 唯一索引（最强）：消费动作与"去重记录"放同一本地事务
   insert ignore / on duplicate 进去重表（bizId=msgKey 或订单号+动作），冲突即已处理
② 状态机条件更新（业务天然幂等时首选）：
   update orders set status='PAID' where id=? and status='UNPAID'   -- affected=0 即重复
③ Redis setnx + TTL：性能高，但"去重记录"与业务动作不同事务——Redis 说没处理过、
   DB 其实已处理（或相反）的裂缝存在，只适合弱一致场景或做①的前置高速挡
④ 版本号/序列比对（消息带生产序号，消费端记"已处理到哪"）
```

**msgKey 的正确用法**：业务唯一键放 Key（`setKeys(orderNo)`）让控制台**可按 key 查轨迹**（4.3.2），消费端从消息里取同一字段做去重——"用 msgId 去重"是伪解：同一逻辑消息两次投递的 msgId 不同（重发是新消息）。**设计纪律**：能走②就不加表（订单支付状态机天然幂等）；用①就去重表与业务同库同事务；③只做缓存式削量。**面试收口句**："MQ 不保 exactly-once 是共识不是缺陷——把幂等做进消费端，at-least-once + 幂等 = 事实上的 effectively-once。"

## 3.3 负载均衡与堆积

### 3.3.1 Consumer Group 的队列分配（Rebalance）原理？

**客户端自主重分配**（4.x，每实例每 20s 一轮 `RebalanceService`）：取 Topic 路由（Queue 全集）+ 消费组心跳成员列表 → **本地一致地计算**分配结果 → 认领新 Queue（从 Broker 拉 offset 建 ProcessQueue）、释放旧 Queue。**没有中心调度者**——靠"输入相同 + 算法相同 = 输出相同"的约定式一致，成员变化经 Broker 心跳视图收敛，期间存在**双重消费的窗口**（旧主尚未释放、新主已认领：靠 offset 语义消化，3.2.3 重复来源 2 的变体）。

**分配策略**（`AllocateMessageQueueStrategy`）：

| 策略 | 算法 | 特点 |
|------|------|------|
| Averagely（默认） | 队列按序**连续切段**分给各实例 | 直观；实例增减整段搬家 |
| AveragelyByCircle | 轮询逐个发牌 | 相邻队列分散到不同实例（读盘更分散） |
| ConsistentHash（较新版本） | 一致性哈希 | 实例增减只搬最小份额——队列频繁变化的弹性场景 |
| ByConfig / ByMachineRoom | 手工指定 / 机房优先 | 容灾布局定制 |

**三个必答结论**：① **并行天花板 = Queue 数**（1.1.3）：实例多于队列开始空转，"扩 Pod 不涨吞吐"先数队列；② **策略必须全组一致**：不同实例配了不同 strategy = 分配结果不重合，出现漏消费/双消费——滚动发布带配置变更时最容易踩；③ **容器化部署的实例身份**：默认 `clientIP@instanceName`，同机多实例/固定 IP 复用要显式 `setInstanceName`（23_docker.md、32_kubernetes.md 场景标配）。**5.x 的终结**：Pop 消费下重分配上移服务端，客户端实例与队列解耦——弹性扩缩秒级生效（1.2.2）。

### 3.3.2 消息大量堆积怎么排查和处理？

**先把指标说对**：堆积量 = 每个 Queue 的 `maxOffset - consumerOffset` 求和（Broker 侧即可算，控制台/Dashboard 的"消费延迟/consumer lag"就是它，与 Kafka lag 同义，31_kafka.md）。**堆积定义的是消费跟不上，不是消息"存了很多"**——CommitLog 反正顺序写全存（4.1.1）。

**排查三步**：
1. **看曲线分型**：消费 TPS 也高 = **进水超标**（上游异常放大：重试风暴 3.2.1、全量回溯 3.1.3、真业务峰值）；消费 TPS 低/零 = **排水故障**——继续细分"全组零（挂了/位点卡）"与"个别队列堆（毒消息队头阻塞 2.1.1、单队列热点 1.1.3）"；
2. **抓消费现场**：消费线程池快照——RocketMQ 4.x 消费线程池用大容量队列，**`consumeThreadMax` 常年不生效、有效并发≈consumeThreadMin（默认 20）**（5.x 修正为显式配对）；jstack/Arthas 看线程堆在哪：慢 SQL（16_mysql.md）、下游 RPC 超时、锁等待——**单条消息处理时长决定上限，先优化单条再谈加实例**；
3. **验幂等与重试放大**：堆的是主 Topic 还是重试 Topic——后者暴涨说明在"失败循环"里空转（重试消息与新消息抢同一线程池，进一步压垮消费）。

**应急工具箱（按风险排序）**：
- **横向扩容**（实例数 ≤ 队列数前提下有效；不够先扩队列——顺序 Topic 禁用，2.1.1）；
- **提并发/修单条**：线程池参数、批量消费 `consumeMessageBatchMaxSize`（配合幂等）；
- **跳过 + 离线补偿**：位点重置到新时刻止血，错过消息走对账重推（3.1.3 的两段式，业务确认后才许执行）；
- **中转搬迁**：临时写一个高并发消费者把堆积消息**批量搬运**到新 Topic（队列数 ×10）再并行消费——"队列数不够"时的标准解法（原组位点语义不受污染）；
- **降级入口**：上游非核心消息改 oneway/丢弃、削峰限流前置（20_sentinel.md、12_nginx.md）。

**预防面**：lag 告警阈值（分钟级增长斜率比绝对值更早发现问题）、容量基线（队列数按峰值 TPS 定标）、大促前压测消费端、堆积保留期核对（72h 内追不完的消息会**真的丢**，4.1.3——"堆积不怕、过期才怕"是这题的最强收口句）。

# 4. 存储、可靠性与高可用

## 4.1 存储引擎

### 4.1.1 CommitLog + ConsumeQueue 的存储模型为什么这样设计？

**两层结构**：

```text
CommitLog（消息本体，全局混写）
  所有 Topic 的消息按到达顺序追加进同一串 1GB 定长文件（mmap 映射，4.1.2）
  消息记录含：topic/queue 坐标、body、properties、tag、存储时间戳等
ConsumeQueue（消费索引，按 Topic-Queue 各一条）
  定长 20 字节条目 = commitlog offset(8B) + size(4B) + tagHashcode(8B)
  每文件默认 30 万条 ≈ 6MB；消费时先定位索引，再按 offset 回 CommitLog 取消息体
IndexFile（可选哈希索引）：按 msgKey/时间查询用，与消费路径无关（4.3.2 轨迹查询）
```

**写入流程**：请求 → 追加 CommitLog（顺序写，毫秒内返回）→ 返回 offset；**ReputMessageService** 后台近乎实时地解析 CommitLog，分发构建各 ConsumeQueue 条目与索引——读写解耦，消费路径两段式（索引定位 → 随机读体）。

**核心设计动机（"为什么不像 Kafka 每分区一个日志"，本题灵魂）**：Kafka 的 partition 各自成文件，分区数上千时**顺序写退化**（多文件并发追加 = 磁盘头的随机写，页缓存被切片稀释）；RocketMQ 把所有 Topic 混进单一 CommitLog——**写吞吐与 Topic/队列数量基本无关**，"万级队列不崩"的底气就在这。代价对称交换：读变成"索引 + 随机读体"（靠 PageCache 热区与 mmap 缓解）、Topic 删除清理复杂（混写无法整文件删，靠过期整段淘汰）。**20 字节只存 hashcode** 是同一哲学的延伸：索引要小到能长期驻内存，精确比对推迟到消费端（2.4.1 两级过滤的根源）。

**易错**："ConsumeQueue 里存消息"——不存，只存坐标；"消息按 Topic 物理分开"——不，物理混写、逻辑分队列。答对这两句就超过了背概念的一半人。

### 4.1.2 RocketMQ 的性能地基：PageCache、mmap、零拷贝、TransientStorePool？

**四件套逐层拆**：

1. **PageCache**：读写都经操作系统页缓存——写先进内核缓冲、由 OS 异步刷盘（或显式 force），读命中热数据不落盘；消息"刚写完就被拉走"的典型流式访问模式下命中率极高，**RocketMQ 的性能前提 = 足够内存留给 OS**（JVM 堆反而不用大，Broker 堆常见 8G 以内、剩余全给页缓存——与业务应用调优方向相反，这反差是考点）；
2. **mmap**：MappedByteBuffer 把 CommitLog 文件映射进虚拟地址空间——省"read 到用户缓冲区"的拷贝与 syscall，写侧同样免 send；注意 mmap 脏页刷盘时机不由应用精确控（异步刷盘的可靠性讨论由此引出，4.2.1）；
3. **零拷贝（读路径）**：Consumer 拉取消息时，未压缩、可直接返回的场景用 `FileChannel.transferTo()`（sendfile 语义）——数据 **PageCache → DMA → 网卡**，全程不进用户态；一旦需要解压或重写属性则退回用户态处理（零拷贝路径有前提，追问必答）；
4. **TransientStorePool（可选）**：堆外划分专用写缓冲（默认 5 块×1G）：写先落 transient pool → Commit 进 mmap → 异步 Force——**读写缓冲分离**，避免"消费大读"把页缓存挤掉导致写也变读盘（写抖动治理），Broker 开 `transientStorePoolEnable` 用于写重场景。

**一条数据生命线的记忆法**：Producer 请求 → mmap/池写（顺序）→ 页缓存可见 → Reput 建索引 → Consumer 长轮询命中 → transferTo 零拷贝出网卡——**整条链路零多余拷贝**，4.1.1 的"混写顺序化"与这题的"路径最短化"合起来就是 RocketMQ 高性能的全部秘密。

### 4.1.3 消息保留多久？磁盘满了会发生什么？

**默认口径**：消息保留 `fileReservedTime = 72h`——过期由清理任务删除（`deleteWhen=04` 每日凌晨整点批删 + 每小时水位检查）。**关键转折**：72 小时是**上限而非承诺**——磁盘水位优先：使用率超过阈值（默认 75% 起删，越紧张删得越狠）时**未到期文件照样淘汰**；逼近写满（约 90%）Broker 直接**拒写**（磁盘告急保护，`diskMaxUsedSpaceRatio`）。

**三个工程后果（这题的价值全在展开它们）**：
1. **堆积即丢消息**：3.3.2 的"72h 内追不完就真的没了"——过期删除不区分是否被消费（RocketMQ 按存储周期清理，不追踪全局消费完成状态；"都消费完才删"的语义是 RabbitMQ 模型，37_rabbitmq.md）；
2. **回溯窗口有边界**：位点重置只能回到现存文件（3.1.3）；消费端撞 `OFFSET_ILLEGAL` 时 Broker 按策略返回可用边界（往前恢复到最早存留、或跳到最新——配置语义要提前知道）；
3. **磁盘规划 = 消息容量规划**：峰值写入速率 × 保留期 + 索引/提交日志余量；"缩保留期救火"要评估回溯与补账能力损失。

**易错**：把 72h 说成"消息默认最多存 72 小时且一定存得到"——后半句错；"删消息按 Topic"——删的是**整段 CommitLog 文件**（混写模型决定，Topic 无法单删，4.1.1）。追问"为什么不做 RabbitMQ 式的 ACK 删除"——存储模型不同：日志追加架构上"哪条被消费过"是位点语义而非对象状态，逐条删除会摧毁顺序写；**用固定周期换极简高性能**，这是 RocketMQ 与 Kafka 共同的取舍。

## 4.2 可靠性与高可用

### 4.2.1 RocketMQ 如何保证消息不丢失？全链路逐段分析。

**分层记账**（"不丢"是链条乘积，任何一环掉链子整体归零——按生产→存储→消费三段列全）：

| 环节 | 丢法 | 对策 | 残余风险 |
|------|------|------|---------|
| Producer → Broker | oneway 无回执；异步回调没处理异常 | 同步发送（1.2.1）+ 检查 `SendResult`；事务消息（2.3.1）保"本地提交⇒必发出" | 重试引发重复（→幂等，3.2.3） |
| Broker 接收 | 写进内存即 ACK，宕机页缓存丢 | **刷盘策略**：同步刷盘 GroupCommitService 串行 force 后回 ACK（吞吐大减）；默认异步约 500ms 一刷，宕机丢窗口内消息 | 单机刷盘再强也防不了机房级故障 |
| Broker 副本 | 主挂了从没有这条 | **复制策略**：同步双写 SYNC_MASTER（从 ACK 后才回客户端）+ 主从异步复制为默认（丢单风险在从） | 双写 RT 升、吞吐降 |
| Consumer | 位点先提交、处理中崩溃（自动提交批语义，3.1.3） | 业务处理成功再返回 CONSUME_SUCCESS；失败靠重试 → 死信（3.2）人工兜底 | "消费成功但位点没提"变重复——幂等闭环 |

**组合决策**（面试给姿态而非背参数）：金融强一致 = 同步刷盘 + 同步双写 + 事务消息 + 幂等消费，性能砍半换确定性；普通业务 = 异步刷盘 + 异步复制 + 重试兜底，**接受"毫秒级窗口丢失"的概率并被监控覆盖**；全链路再加两道保险：**发送对账**（业务流水 vs 消息轨迹 4.3.2 定期核对）与**消费侧补偿**（状态机超时扫单）。收口句："MQ 的可靠是个 SLA 谈判——参数组合决定丢的概率量级，工程上再用对账把残余风险压到可接受。"

### 4.2.2 RocketMQ 高可用架构怎么演进？主从、Dledger、Controller 什么关系？

**三段演进**：

1. **Master-Slave（4.x 经典）**：Broker 组一主多从，从节点异步/同步复制；**主挂从不能接管写**——Producer 写入中断（NameServer 摘除要最多 120s，1.1.2），消费仍可从从节点读；切换靠人工/外部脚本。同步双写（SYNC_MASTER）解决"单机丢"（4.2.1），解决不了"可用性"；
2. **DLedger（4.x 后期）**：Raft（Ratis 实现）重造 Broker 组——**过半写入才算提交**、Leader 选举与自动切换内置、主从身份动态；强一致与自动 failover 到手，代价：**每组固定 3/5 副本**（成本绑定选举合法性）、过半网络分区即不可写、与存储层耦合运维重；
3. **Controller（5.x）**：**把"选主"从存储节点剥离**到独立 Controller 集群（Controller 自身用 Raft 选主，轻量无状态于消息）——Broker 回归 Master/Slave 简单模型，故障由 Controller 侦测心跳并把 Slave 提升为新 Master；副本数不再受选举法定人数捆绑、支持 Slave Acting-Master 分担读、与容器化/弹性部署（1.2.2、23_docker.md）合拍。**与 Kafka KRaft 去 ZK 化同代思想**：控制面独立、数据面简单（31_kafka.md）。

**NameServer 层 HA**：全量互副本、无脑裂（1.1.2）——部署≥2 台即可。客户端韧性兜底：发送失败换 Broker 重试（1.2.1）天然消化切换窗口——"MQ 的高可用是服务端复制 + 客户端容错共同构成的"，只答服务端即不完整。

## 4.3 运维治理

### 4.3.1 消息大小限制是多少？超大消息怎么处理？

**限制清单**：Broker 默认 `maxMessageSize = 4MB`（单条上限，超限直接拒收）；客户端发送体超过 **4KB 自动压缩**（`compressMsgBodyOverHowmuch`，Broker 端透明解压）；批量消息**总大小 ≤ 4MB**（1.2.1）；5.x Proxy/gRPC 链路另有帧上限（默认口径不变）。对比记忆：Kafka 默认 1MB、RabbitMQ 无硬上限但实践劝退（31_kafka.md、37_rabbitmq.md）。

**超限方案（按推荐序）**：
1. **传引用不传数据（正解）**：消息只放业务 ID + 关键字段，Consumer 回查 DB/缓存——"MQ 传递事件通知，不承担载体的仓库"：数据在源头（DB/对象存储），消息是信封；附带红利：大小恒定、幂等有天然 key（3.2.3）；
2. **压缩**：文本类 JSON 可压 5~10 倍，对"略超阈值"有效，对已压缩内容（图片/视频）无用；
3. **对象存储 + URL**：大文件进 MinIO/OSS（25_minio.md），消息带下载地址 + 元数据——URL 有效期与安全域自己管好；
4. **拆分 + 重组**：批次 ID 分片发送、消费端聚合——复杂度高（乱序、缺片、超时判定都要管），除"消息总线硬约束"外不建议。

**反例识别**："拿 MQ 当文件传输/大对象通道"的架构病灶：CommitLog 被大块污染（4.1.1 的顺序写红利变内存污染）、拉取延迟放大、重试一次搬一次——面试答"为什么不放宽 maxMessageSize 要传引用"，把这段病灶讲清就赢。

### 4.3.2 消息轨迹、监控告警、ACL 分别怎么落地？

**消息轨迹（MsgTrace）**：`setEnableMsgTrace(true)`（Producer/Consumer 独立开关）后，各环节把"发生在自己身上的事"异步上报到内部 Topic `RMQ_SYS_TRACE_TOPIC`——**发送时间、存储 Broker/队列、每次投递与消费结果、重试链路、耗时**；控制台按 msgId **或 msgKey**（业务单号，1.2.1/4.3.1 埋的钩子）检索还原全程。用途口径："我的消息丢没丢"三连判：有没有存储记录（没=生产/Broker 段，查 SendStatus 与 4.2.1）、有没有投递记录（没=订阅/位点问题，3.1.3）、投递几次失败几次（=重试死信走向，3.2）。生产开销：异步上报、量不大，但**超高吞吐 Topic 可关**；跨组/系统 Topic 权限单独放开。

**监控告警四板斧**：① 堆积 lag（3.3.2，按增长斜率告）；② 消费失败率与重试 Topic 水位（3.2.1 风暴前兆）；③ **DLQ 增量**（3.2.2 一级告警）；④ Broker 侧：刷盘耗时/页缓存命中、`TransientStorePool` 水位、磁盘水位与保留期实际值（4.1.3）、事务半消息积压与回查失败数（2.3.1）。云版 Dashboard/Prometheus 直采，开源 4.x 走 JMX/exporter，5.x 原生 OpenTelemetry（1.2.2）。

**ACL**：`plain_acl.yml` 配 AccessKey/SecretKey + 对 Topic/Group 的 pub/sub 粒度权限（超级账户豁免），Broker 开启 `accessValidationEnabled`；典型事故："新组上线忘授权，消费静默无权限"——**ACL 报错在客户端日志而非控制台**，排查要先看授权维度。5.x 动态 ACL（不重启热更、支持多数据源）；与网关/内网隔离组合：Proxy 模式（1.2.2）让"谁能连哪"收口在接入层——安全治理三件套：**账号最小权限 + 网络边界 + 审计（轨迹）**。

# 5. 选型对比

## 5.1 MQ 选型

### 5.1.1 RocketMQ 和 Kafka 怎么选？

**先给结论**：**业务消息选 RocketMQ，日志/流数据选 Kafka**——差异不在"谁更快"，在**为谁优化**：RocketMQ 为"业务事件的低延迟、丰富语义、可运维"优化，Kafka 为"海量吞吐的连续管道与流生态"优化。

| 维度 | RocketMQ | Kafka |
|------|----------|-------|
| 存储 | 全局混写 CommitLog + 20B 索引（队列数万级不崩，4.1.1） | Partition 独立 Segment（吞吐王者；分区数千级后顺序写退化、副本再平衡痛） |
| 吞吐/延迟 | 10 万级 TPS，ms 级延迟稳定 | 百万级 TPS（攒批+页缓存榨干）；尾延迟对批参数敏感 |
| 消息语义 | **事务消息、顺序（队列级+强约束）、18 级延时/定时、Tag/SQL 服务端过滤**（2.x 整章就是它的差异化） | 分区内有序；延时/过滤/事务语义另建（Kafka 事务=流处理 exactly-once 生产端，与 RocketMQ 最终一致事务不是一回事，2.3.1） |
| 消费模型 | Push（长轮询封装）+ 流控背压、重试/死信开箱 | 消费者自治 offset、失败处理自己搭（DLQ 靠约定） |
| 高可用 | 主从/同步双写/DLedger/Controller（4.2.2）、NameServer 极简 | ISR + Controller/KRaft，生态成熟 |
| 生态 | 国内云原生支持好、与 Spring 集成完善、业务系统全家桶 | 大数据管道事实标准（Flink/Connect/Streams） |

**追问深水区**：① "Kafka 能补业务语义吗"——能补但都在业务层自建（延时靠 zset/调度、事务靠 outbox），**中间件替你背 vs 你自己背**的差别；② "RocketMQ 能抢 Kafka 流场景吗"——吞吐差一个量级且流处理生态缺失，别硬凹；③ 双栈常态：日志上 Kafka、业务上 RocketMQ，选型不是站队是分工。

### 5.1.2 RocketMQ 和 RabbitMQ 怎么选？

**物种差异**：RabbitMQ 是 **broker 路由模型**（Exchange 绑定路由：direct/topic/fanout/header，AMQP 血统，Erlang）——队列是**对象状态**（消息在队列里等消费，ACK 后删除）；RocketMQ 是**日志存储模型**（队列=索引视图，消息是日志流上的区间）——这一个根差异派生出全部实践区别：

| 维度 | RocketMQ | RabbitMQ |
|------|----------|----------|
| 堆积能力 | **磁盘级强堆积**（4.1.3 周期淘汰，72h 量级扛得住） | 弱：内存+磁盘队列，堆积到量级性能塌方（对象模型使然） |
| 延迟/时效 | ms 级（长轮询近实时） | **μs~ms 级路由更敏捷**，小流量低延迟体验更好 |
| 失败语义 | 重试队列+死信原生（3.2） | DLX 机制类似（绑定在交换机上） |
| 顺序/事务/定时 | 原生 | 顺序靠单消费者；无事务消息等价物；延时靠插件/过期队列（37_rabbitmq.md 细讲） |
| 协议与生态 | 私有协议 + 5.x gRPC；国内云与 Java 生态 | AMQP 标准、多语言客户端成熟、路由灵活（复杂拓扑利器） |
| 运维心智 | 队列数大不怵、Topic 平铺 | 队列/绑定关系治理、镜像/quorum 队列选择 |

**选型口径**：日均亿级业务消息、要重试死信/事务/延时/堆积全套 → RocketMQ；中小规模、拓扑复杂（多路由规则、跨团队标准协议接入）、对单条延迟极敏感 → RabbitMQ。两家的"消费模型"对照一句话收尾：RabbitMQ 推给你（qos 流控），RocketMQ 你来拉（长轮询）——**推派把节奏权给 broker，拉派把节奏权给消费者**，架构气质不同（37_rabbitmq.md）。
