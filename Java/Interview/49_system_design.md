# 1. 知识点
- **系统设计面试目标**: 考察候选人的架构设计能力、技术广度、沟通能力、Trade-off权衡能力，而非得出标准答案
- **短链系统概述**: 将长URL转换为短URL的服务，如`https://t.cn/A1b2C3` → 重定向到原始URL。核心组件：发号器、映射存储、重定向服务、缓存
- **短链发号器**: 生成全局唯一自增ID(号段模式/雪花算法)，将十进制ID转为62进制(0-9 a-z A-Z)得到短码。如ID=10000 → 62进制="2Bi"
- **短链301 vs 302**: 301永久重定向(浏览器缓存，后续不请求短链服务，适合稳定链接)；302临时重定向(每次都请求短链服务，适合需要统计的链接)。短链系统通常用302可做流量统计
- **短链缓存设计**: 热门短链查询频繁，短码→长链映射存Redis，预热热门数据。布隆过滤器过滤不存在的短码防止缓存穿透
- **短链幂等设计**: 同一长链多次请求生成短链，应返回相同的短码。通过长链→短码的反向映射(Redis/DB)实现，先生成短码再检查是否已存在
- **短链防盗链**: 限制Referer来源、增加访问token/签名验证、设置链接有效期
- **秒杀系统核心挑战**: 超高并发(瞬时流量是平时的几十倍)、不能超卖(库存不能为负)、数据库压力、黄牛刷单
- **秒杀前端限流**: 按钮置灰(点击后立即disabled)、验证码(分散用户请求)、答题/滑块、限购(同一用户限购件数)
- **秒杀后端架构**: Redis预扣库存(Lua原子操作) → 异步下单MQ削峰 → 数据库最终扣减(乐观锁) → 订单异步生成
- **Redis预扣库存Lua脚本**: 原子操作：先检查库存是否>0，是则decr库存并返回成功，否则返回失败。保证高并发下库存不会超卖
- **秒杀动静分离**: 秒杀页面(HTML/CSS/JS/图片)部署到CDN，静态资源不走应用服务器；动态数据(库存、秒杀状态)通过Ajax异步获取
- **秒杀流量削峰**: 请求进入令牌桶/Sentinel限流 → 排队(放入MQ) → 消费者按固定速率处理 → 保证DB不被冲垮
- **IM系统核心**: WebSocket长连接、消息可靠性(ACK确认)、在线/离线消息处理、群聊扩散策略、海量连接管理
- **IM在线推离线拉**: 用户在线时消息实时推送(WebSocket)；离线时消息存储到离线消息表，用户上线后主动拉取(Pull)
- **IM消息ACK机制**: 客户端收到消息后发送ACK确认，服务端未收到ACK则重试(最多3次)。保证消息不丢不重(幂等)
- **IM单聊读扩散**: 消息发送者写入自己的发件箱，同时推送到接收者在线收件箱(在线)或离线消息表(离线)。每个人只需要查自己的收件箱
- **IM群聊写扩散**: 消息发送者写一次，扩散写入到所有群成员的收件箱。适用于小群(<500人)。大群(万人)用读扩散(群成员都读同一个群消息队列)
- **IM大群优化**: 万人大群使用读扩散模式(只存一份消息，群成员拉取)，按时间/offset分页拉取。在线推送+离线拉取结合
- **IM全局消息ID**: 使用雪花算法或号段模式生成趋势递增的ID，方便按时间排序和分页拉取
- **限流器算法**: 令牌桶(Token Bucket)、漏桶(Leaky Bucket)、固定窗口计数器、滑动窗口(Sliding Window)
- **令牌桶算法**: 以固定速率向桶中放入令牌，请求需获取令牌才能执行，桶满则丢弃令牌。允许突发流量(桶容量)，适合有突发特性的场景
- **漏桶算法**: 请求进入漏桶，以固定速率流出处理。强制平滑限流，不能突发。适合保护下游系统(恒定速率)
- **滑动窗口限流**: 将时间窗口细分为多个小格子，统计当前窗口内的请求数。比固定窗口更精确(解决窗口边界的突发问题)。可用Redis ZSet实现
- **滑动窗口Redis实现**: ZSet的score为当前时间戳，每个请求ZADD一个member。统计时ZREMRANGEBYSCORE移除窗口外的数据，ZCARD获取窗口内请求数
- **分布式ID生成器设计**: 见独立专题，号段模式/雪花算法/美团Leaf等方案
- **API网关设计**: 路由转发、鉴权认证、限流熔断、协议转换、日志监控，核心功能：动态路由、负载均衡、API聚合
- **分布式Session**: 多服务器共享用户登录状态。方案：Redis集中存储Session(Sticky Session/JWT无状态替代/Spring Session)
- **文件上传系统**: 分片上传(大文件切割成小片)、断点续传(记录已上传分片)、秒传(文件Hash匹配，已存在则无需上传)、签名(防盗链+防篡改)
- **CDN**: 内容分发网络，将静态资源分发到地理分散的缓存服务器。用户请求通过DNS解析被路由到最近CDN节点，加速静态资源访问、减轻源站负载。适用于: 静态页面/图片视频/下载加速
- **猜你喜欢功能设计**: 用户行为埋点→每个商品点击记录product_id到Redis ZSet(score递增)→取Top即可得到用户偏好TopN→查Redis/DB获取商品标签→ES搜索相似商品→推送。核心: Redis ZSet排序 + ES相似检索
- **防大量无效商品请求导致黑名单膨胀**: (1) Canal监听DB新增操作;(2) XXL-JOB定时任务同步最大product_id;(3) 若请求product_id > 最大product_id，判定无效请求提前拒绝;(4) 避免不存在商品ID被加入黑名单

# 2. 面试题

## 2.1 如何设计一个短链系统？
**核心流程**：1)用户提交长URL 2)发号器生成唯一ID 3)ID转62进制得到短码 4)存储长链→短码映射到DB 5)返回短链URL。

**重定向流程**：1)用户访问短链 2)服务端解析短码转回ID 3)查缓存(Redis)获取长链，未命中查DB 4)302重定向到长链。

**高并发优化**：
- 发号器使用号段模式(Leaf)，提前批量预取ID
- 短码→长链映射存Redis，设置合理TTL
- 布隆过滤器防止缓存穿透(不存在的短码直接404)
- 幂等设计：同一长链查反向映射返回已有短码

**数据库设计**：
```sql
CREATE TABLE short_url (
  id BIGINT PRIMARY KEY,
  short_code VARCHAR(8) UNIQUE,
  long_url TEXT,
  created_at DATETIME,
  expires_at DATETIME
);
CREATE UNIQUE INDEX idx_long_url_hash ON short_url(long_url_hash);
```

## 2.2 秒杀系统的核心设计要点是什么？
**整体架构**：CDN(静态页) → 网关(限流) → 应用服务器(预扣库存) → MQ(削峰) → 消费者(异步下单) → DB(持久化)

**核心策略**：
1) **前端**：按钮置灰、验证码、限购限制
2) **网关层**：令牌桶限流，超过QPS直接拒绝
3) **应用层**：Redis预扣库存，Lua脚本原子扣减`if redis.call('get', KEYS[1]) > 0 then return redis.call('decr', KEYS[1]) else return -1 end`。扣减成功后发MQ消息异步下单
4) **DB层**：乐观锁(version)扣减库存防止超卖`UPDATE product SET stock = stock - 1, version = version + 1 WHERE id = ? AND stock > 0 AND version = ?`
5) **订单**：异步生成，秒杀成功即刻返回"排队中"，MQ消费时创建订单
6) **监控**：实时库存数量监控、QPS监控、MQ积压监控

## 2.3 IM系统如何处理离线消息？
**存储**：离线消息存入离线消息表(msg_id, from_user, to_user, content, send_time, status)。

**推送方式**：
- 在线：消息实时Push(WebSocket)
- 离线：消息存入离线表，待用户上线
- 用户上线后：客户端发起离线消息拉取请求，服务端从离线表查询未拉取的消息，批量返回

**拉取模式**：按`send_time DESC`分页拉取，客户端记录lastPullTime，每次拉取lastPullTime之后的消息。拉取完标记已读并从离线表清理(或移到历史消息表)。

**优化**：离线消息表按user_id分片存储；新消息到来时先查用户在线状态，在线则推送，离线则存表；设置离线消息保留期限(如7天)。

## 2.4 群聊消息的写扩散和读扩散分别适用于什么场景？
**写扩散**：消息发送时复制到每个群成员的收件箱。优点：成员拉取消息快(只拉自己的收件箱)。缺点：写入放大严重(500人群发一条消息需500次写入)。适用：小群(≤500人)。

**读扩散**：消息只存一份(群消息表)，成员拉取时从群消息表读取。优点：写入简单(一条消息一次写入)。缺点：所有成员都读同一张表，读压力大；需处理每个成员已读位置。适用：万人大群。

**混合策略**：根据群人数动态切换。小群用写扩散，大群用读扩散。大群在线用户在线推送(基于群消息队列)，离线用户拉取。

## 2.5 请设计一个限流器，要求支持不同的时间精度(秒/分/时)
采用Redis + Lua实现滑动窗口限流：
```
-- KEYS[1]: 限流key, ARGV[1]: 窗口大小(秒), ARGV[2]: 限制数量, ARGV[3]: 当前时间戳
local window = tonumber(ARGV[1])
local limit = tonumber(ARGV[2])
local now = tonumber(ARGV[3])
local windowStart = now - window * 1000
redis.call('ZREMRANGEBYSCORE', KEYS[1], 0, windowStart)
local count = redis.call('ZCARD', KEYS[1])
if count < limit then
    redis.call('ZADD', KEYS[1], now, now .. '-' .. math.random())
    redis.call('PEXPIRE', KEYS[1], window * 1000)
    return 1
else
    return 0
end
```
支持分级限流(总接口限流+单IP限流+单用户限流)，使用注解`@RateLimiter(key="userId", limit=100, window=60)`。令牌桶实现在本地内存维护，支持突发流量。

## 2.6 文件上传系统如何设计分片上传和断点续传？
**分片上传**：客户端将大文件切割为固定大小(如5MB)的分片，每个分片按顺序上传。服务端记录每个分片的上传状态。

**流程**：
1) 客户端请求初始化上传(文件名、总大小、分片大小) → 服务端返回uploadId，在Redis记录(上传ID, 分片信息)
2) 客户端逐个上传分片，携带uploadId + chunkIndex
3) 服务端接收分片保存为临时文件(uploadId_chunkIndex)，更新Redis中分片状态
4) 全部分片上传完成，客户端请求合并 → 服务端按序合并分片生成最终文件，更新DB文件记录

**断点续传**：客户端上传前请求服务端已上传的分片状态(GET /upload/status?uploadId=xxx)，服务端Redis查询已上传分片列表返回。客户端跳过已上传分片，只上传缺失分片。

**秒传**：客户端上传前计算文件Hash(MD5/SHA256)，请求检测(GET /upload/check?hash=xxx)。服务端查DB是否存在相同hash的文件，存在则直接返回文件URL，无需上传。

## 2.7 API网关的核心功能和架构设计？
**核心功能**：
1) 路由转发：根据URL、Header等规则将请求路由到对应微服务
2) 认证鉴权：统一JWT/OAuth2验证，鉴权后透传用户信息
3) 限流熔断：Sentinel/令牌桶，保护下游服务
4) 日志监控：记录所有请求日志、QPS、错误率、延迟
5) 协议转换：HTTP→gRPC/Dubbo
6) API聚合：客户端一次请求聚合多个微服务结果

**架构设计**：前端→Nginx(L4负载均衡)→网关集群→各微服务。网关自身无状态，可水平扩展。配置存Nacos/Apollo可动态更新。

## 2.8 什么是CDN？它的工作原理是什么？
CDN(内容分发网络)通过遍布各地区的缓存节点，将静态资源分发到离用户最近的节点。工作原理：用户DNS解析时，CDN调度系统根据请求来源IP(地理位置/运营商)返回最优节点IP；节点有缓存直接返回，无缓存则回源站拉取后缓存并返回。适用于静态页面加速、图片视频加速、下载分发、直播加速等场景。

## 2.9 如何设计猜你喜欢功能？
**核心流程**：
1. **用户行为埋点**：前端记录用户对商品的点击、浏览、加购等行为
2. **Redis ZSet存储偏好**：每次点击/行为将product_id写入Redis ZSet，score递增(代表对该商品的兴趣度)
3. **获取偏好TopN**：通过ZREVRANGE获取score最高的Top N商品
4. **标签提取**：查询Redis/DB获取TopN商品的标签/类目/属性
5. **ES相似检索**：基于标签在ES中进行相似商品检索(余弦相似度/向量检索)
6. **推送展示**：将检索结果返回前端展示

**技术栈**：埋点SDK → Kafka(行为流) → Flink/Spark(实时计算) → Redis ZSet(用户偏好) → ES(相似检索)。冷启动用户可用协同过滤或热度推荐兜底。

## 2.10 怎么防止大量的空商品请求导致黑名单变大？
**问题**：恶意/爬虫大量请求不存在的商品ID，被风控系统加入黑名单后导致黑名单膨胀。

**解决方案**：
1. **Canal监听DB新增**：Canal监听商品表的INSERT操作，实时感知新增商品
2. **XXL-JOB定时同步**：定时任务定期同步当前最大product_id到Redis
3. **请求前置校验**：请求到达时先判断product_id是否在有效范围(product_id ≤ max_product_id)，无效请求直接拒绝
4. **避免误伤**：不在有效范围内的无效请求提前返回400，不进入后续风控逻辑，避免不存在的商品ID被加入黑名单导致黑名单膨胀
