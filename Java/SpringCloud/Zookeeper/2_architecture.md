
# 1. 整体架构概览

ZooKeeper 采用 **Leader-Follower 主从架构**，所有写操作由 Leader 处理，Follower 和 Observer 提供读服务。

```text
┌─────────────────────────────────────────────────────────────────────┐
│                        Client (多个客户端)                            │
│               │               │               │                      │
│         TCP Connection    TCP Connection    TCP Connection            │
│               │               │               │                      │
│               ▼               ▼               ▼                      │
│  ┌──────────────────────────────────────────────────────────────┐   │
│  │                     ZooKeeper Ensemble（集群）                 │   │
│  │                                                                │   │
│  │   ┌──────────┐     ┌──────────────┐     ┌──────────────┐     │   │
│  │   │  Leader  │◄───►│  Follower 1  │◄───►│  Follower 2  │     │   │
│  │   │          │     │              │     │              │     │   │
│  │   │ 处理写请求│     │  接收读请求   │     │  接收读请求   │     │   │
│  │   │ 发起提案 │     │  参与投票    │     │  参与投票    │     │   │
│  │   │ 提交事务 │     │  转发写请求  │     │  转发写请求  │     │   │
│  │   └──────────┘     └──────────────┘     └──────────────┘     │   │
│  │                                                                │   │
│  │                        ┌──────────────┐                       │   │
│  │                        │  Observer    │                       │   │
│  │                        │              │                       │   │
│  │                        │  只读不投票   │                       │   │
│  │                        │  横向扩展读  │                       │   │
│  │                        └──────────────┘                       │   │
│  └──────────────────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────────────────┘
```

# 2. 三大服务器角色

## 2.1 Leader（领导者）

Leader 是 ZooKeeper 集群的核心节点，是整个集群的**唯一写入口**和**协调中枢**。

```
Leader 职责：
┌─────────────────────────────────────────────────────────────┐
│  1. 写操作处理                                               │
│     · 接收客户端直接发来的写请求                              │
│     · 接收 Follower 转发的写请求                              │
│     · 准备请求（生成 zxid）                                   │
│                                                              │
│  2. 提案发起与协调                                           │
│     · 将写请求转化为 Proposal 提案                            │
│     · 按 zxid 顺序广播给所有 Follower                         │
│     · 收集 Follower 的投票（ACK）                             │
│                                                              │
│  3. 提交决策                                                 │
│     · 当收到半数以上 Follower 的 ACK 后，提交事务             │
│     · 先本地提交（写入事务日志 + 更新内存数据库）              │
│     · 然后广播 COMMIT 消息给所有 Follower                     │
│                                                              │
│  4. 会话管理                                                 │
│     · 管理所有客户端的 Session                                │
│     · 维护 Session 超时检测                                   │
│     · Session 过期后清理临时节点                              │
│                                                              │
│  5. Watch 触发                                               │
│     · 数据变更时通知设置了 Watch 的客户端                     │
└─────────────────────────────────────────────────────────────┘
```

**Leader 的选举与任期**：集群启动或 Leader 宕机时会触发 Leader 选举。每个新 Leader 对应一个新的 epoch（朝代），epoch 用于区分不同任期的操作。

## 2.2 Follower（跟随者）

Follower 集群中的**普通成员**，参与投票但**不能主动处理写请求**。

```
Follower 职责：
┌─────────────────────────────────────────────────────────────┐
│  1. 请求处理                                                 │
│     · 直接处理读请求（从本地内存数据库读取）                   │
│     · 将写请求转发给 Leader                                   │
│                                                              │
│  2. 参与投票                                                 │
│     · 收到 Leader 的 Proposal 后进行 ACK 投票                 │
│     · 参与 Leader 选举                                       │
│                                                              │
│  3. 数据同步                                                 │
│     · 接收 Leader 广播的 Proposal 和 Commit                   │
│     · 按顺序应用到本地内存数据库                               │
│     · 定期与 Leader 进行差异同步                              │
│                                                              │
│  4. 连接维持                                                 │
│     · 维护与 Leader 之间的长连接                              │
│     · Leader 心跳检测（Follower 定期发送 PING）               │
└─────────────────────────────────────────────────────────────┘
```

## 2.3 Observer（观察者）

Observer 是一种**不参与投票**的特殊 Follower，用于**横向扩展读能力**（在 ZooKeeper 3.3.0 引入）。

```
Observer 存在的理由：

问题：为什么需要 Observer？
┌────────────────────────────────────────────────────────────────┐
│  ZooKeeper 的写性能取决于投票速度。当集群节点数增加时：           │
│                                                                │
│  3节点：需要 ≥2 票 → 写性能高                                   │
│  5节点：需要 ≥3 票 → 写性能下降                                 │
│  7节点：需要 ≥4 票 → 写性能显著下降                              │
│  9节点：需要 ≥5 票 → 写性能进一步下降                            │
│                                                                │
│  结论：增加 Follower 会提升读，但会降低写性能（投票开销增大）     │
│                                                                │
│  Observer 设计：不参与投票，只同步数据并提供读服务               │
│  → 读能力线性扩展，写性能不受影响                                │
└────────────────────────────────────────────────────────────────┘

Observer 职责：
┌─────────────────────────────────────────────────────────────┐
│  1. 只读服务（与 Follower 相同）                              │
│  2. 接收 Leader 的 Proposal 和 Commit（但不投票）             │
│  3. 参与 Leader 选举的投票（但不参与事务投票）⚠️                 │
│  4. 部署在需要就近读服务的区域                                 │
└─────────────────────────────────────────────────────────────┘
```

**角色对比总结**：

| 特性 | Leader | Follower | Observer |
|------|--------|----------|----------|
| 处理读请求 | ✓ | ✓ | ✓ |
| 处理写请求 | ✓ 直接处理 | ✗ 转发给 Leader | ✗ 转发给 Leader |
| 参与事务投票 | ✓（发起者） | ✓ | ✗ |
| 参与 Leader 选举 | ✓ | ✓ | ✓ |
| 影响写性能 | — | 增加投票节点 | 无影响 |
| 扩展读能力 | — | 有限 | 线性扩展 |
| 数据一致性 | 全量 | 全量 | 全量 |

# 3. 客户端-服务端交互模型

```text
┌──────────────────────────────────────────────────────────────┐
│                    Client ↔ Server 交互                        │
│                                                               │
│   ┌──────────┐                        ┌──────────────┐       │
│   │  Client  │◄───── TCP 长连接 ────►│ Server Node  │       │
│   │          │                        │              │       │
│   │ · 维护   │   1. Connect （握手建立会话） │              │       │
│   │   Session│   2. Request（CRUD + Watch）  │              │       │
│   │ · 心跳   │   3. Response（结果/事件）    │              │       │
│   │ · Watch  │   4. Heartbeat（Session 保活） │              │       │
│   │   管理   │   5. Watch Event（事件通知）   │              │       │
│   └──────────┘                        └──────────────┘       │
│                                                               │
│   关键特性：                                                   │
│   · 客户端任意连接一个 Server 节点即可工作                     │
│   · 客户端本地管理 Watch 和重连逻辑                            │
│   · 连接断开会自动重连到其他节点（Session 迁移）               │
└──────────────────────────────────────────────────────────────┘
```

## 3.1 请求处理路径

```text
写请求路径（Write Path）：
Client ──write──► Follower ──forward──► Leader
                                           │
                              ┌────────────┼────────────┐
                              │            │            │
                         Proposal     Proposal      Proposal
                              │            │            │
                              ▼            ▼            ▼
                          Follower1    Follower2    Observer
                              │(ACK)       │(ACK)       │(无ACK)
                              └────────────┼────────────┘
                                           │
                                       过半ACK?
                                           │
                              ┌────────────┴────────────┐
                              ▼                         ▼
                          COMMIT Broadcast       内存DB + 事务日志
                              │
                    ┌─────────┼─────────┐
                    ▼         ▼         ▼
               Follower1  Follower2  Observer
              (应用到本地内存数据库)

读请求路径（Read Path）：
Client ──read──► 任意节点 ──从本地内存数据库读取──► Client
                 (无需与 Leader 通信，直接返回本地数据)
```

## 3.2 请求的顺序保证

```text
全局顺序保证：
┌──────────────────────────────────────────────────────────────┐
│                                                               │
│   Client A: set(/a, "1")  ──► Leader ──► zxid = 0x100000001 │
│   Client B: set(/b, "2")  ──► Leader ──► zxid = 0x100000002 │
│                                                               │
│   所有 Follower 按 zxid 顺序 (0x100000001 → 0x100000002) 应用 │
│   读到 zxid=0x100000002 的节点一定也包含了 zxid=0x100000001   │
│                                                               │
│   客户端顺序：                                                 │
│   同一客户端发送的请求按 FIFO 顺序处理                         │
│   不同客户端之间不保证顺序                                     │
└──────────────────────────────────────────────────────────────┘
```

# 4. 数据存储层

## 4.1 存储架构

每个 ZooKeeper 节点维护两份核心数据文件：

```text
Server 节点数据目录 (dataDir)：
┌────────────────────────────────────────┐
│  data/                                  │
│  ├── version-2/                         │
│  │   ├── log.1       ← 事务日志 (TxnLog) │
│  │   ├── log.2                           │
│  │   ├── log.3                           │
│  │   ├── snapshot.0  ← 数据快照 (Snap)  │
│  │   ├── snapshot.1000                  │
│  │   └── snapshot.2000                  │
│  └── myid           ← 节点唯一ID        │
└────────────────────────────────────────┘
```

## 4.2 内存数据库（DataTree）

```text
ZooKeeper 内存数据库 = DataTree（ConcurrentHashMap 实现）

DataTree 结构：
┌───────────────────────────────────────────────┐
│  nodes: Map<String, DataNode>                  │
│  │                                              │
│  │  "/" → DataNode                             │
│  │  "/config" → DataNode                       │
│  │  "/config/db" → DataNode {data: "...", ...} │
│  │  "/services" → DataNode                     │
│  │  "/services/order" → DataNode               │
│  │  ...                                        │
│  │                                              │
│  watchTable: Map<String, Set<Watcher>>         │
│  存储所有 Watch 注册信息                         │
│                                                  │
│  ephemerals: Map<Long, Set<String>>             │
│  关联 SessionId 和临时节点                       │
└───────────────────────────────────────────────┘

特性：
· 所有数据在内存中 → 读操作极快
· 每个写操作同时写入事务日志（磁盘）保证持久化
· 定期生成快照（snapshot），减少恢复时的日志回放量
```

## 4.3 事务日志（Transaction Log）

事务日志是 ZooKeeper 持久化保证的核心：

```text
事务日志特点：
┌─────────────────────────────────────────────────────────────┐
│  · 每条写操作在提交前先写入事务日志                           │
│  · 日志文件大小可配置（默认 64MB），满后滚动新建              │
│  · 使用组提交（Group Commit）优化磁盘 I/O                     │
│  · 日志记录格式：[checksum][length][TxnHeader][Record]      │
│                                                              │
│  TxnHeader 包含：                                            │
│    · clientId：客户端 ID                                     │
│    · cxid：客户端操作序号                                    │
│    · zxid：ZooKeeper 事务 ID                                 │
│    · time：操作时间                                          │
│    · type：操作类型（CREATE/DELETE/SET_DATA 等）              │
└─────────────────────────────────────────────────────────────┘
```

## 4.4 快照（Snapshot）

```text
快照机制：
┌─────────────────────────────────────────────────────────────┐
│  · 定期将整个 DataTree 序列化到磁盘（默认 100K 事务一次）     │
│  · 文件名格式：snapshot.<last_zxid>                          │
│  · 恢复流程：                                                │
│    1. 加载最新的快照文件                                      │
│    2. 重放快照之后的所有事务日志                              │
│    3. 得到完整的最新内存数据库                                │
│                                                              │
│  配置参数：                                                  │
│    snapCount：多少次事务触发一次快照，默认 100000             │
│    snapRetainCount：保留最近几个快照，默认 3                  │
│    autopurge.snapRetainCount：自动清理时保留的快照数           │
│    autopurge.purgeInterval：自动清理间隔（小时）               │
└─────────────────────────────────────────────────────────────┘
```

# 5. 会话（Session）模型

```text
Session 生命周期：
┌─────────────────────────────────────────────────────────────────┐
│                                                                   │
│  Client                        Server                             │
│    │                             │                                │
│    │──── Connect ───────────────►│  创建 Session                  │
│    │                             │  · 生成 sessionId              │
│    │◄──── sessionId ─────────────│  · 设置 sessionTimeout         │
│    │                             │                                │
│    │──── Heartbeat(PING) ───────►│  更新 session 活跃时间          │
│    │     (每 sessionTimeout/3)   │                                │
│    │                             │                                │
│    │──── Heartbeat(PING) ───────►│  持续保持活跃                   │
│    │                             │                                │
│    │      (网络中断)              │                                │
│    │                             │  sessionTimeout 时间后          │
│    │                             │  判定 Session 过期              │
│    │                             │  · 清理该 session 的临时节点    │
│    │                             │  · 清理注册的 Watch             │
│    │                             │                                │
│    │◄─── SessionExpired ─────────│  客户端收到过期通知             │
│    │                             │                                │
└─────────────────────────────────────────────────────────────────┘

Session 关键数据（服务器端）：
┌──────────────────────────────────────────────────────────┐
│  SessionTrackerImpl 维护：                                │
│    · sessionsById: Map<Long, SessionImpl>                 │
│    · sessionSets: Map<Long, SessionSet>（分桶管理超时）    │
│    · 过期算法：分桶轮询                                     │
│                                                           │
│  SessionImpl 包含：                                       │
│    · sessionId：会话 ID                                   │
│    · timeout：超时时间（ms）                                │
│    · tickTime：系统基本时间单位                              │
│    · isClosing：是否正在关闭                               │
└──────────────────────────────────────────────────────────┘
```

# 6. Watch 机制架构

```text
Watch 模型：
┌──────────────────────────────────────────────────────────────┐
│                                                               │
│  Client                        Server                          │
│    │                             │                             │
│    │── exist("/a", watch=true) ─►│ 在 watchTable 中注册         │
│    │                             │  "/a" → {watcher1}          │
│    │                             │                             │
│    │                    (其他客户端更改 /a)                      │
│    │                             │                             │
│    │                             │ 触发 watch，构造 Event       │
│    │◄── WatchedEvent ────────────│ 发送给客户端                 │
│    │     (type, state, path)     │                             │
│    │                             │                             │
│    │── getData("/a") ───────────►│ 客户端重新读取最新数据       │
│    │                             │                             │
│    │                             │ watch 是 One-time trigger    │
│    │                             │ 触发后自动删除               │
│    │                             │ 如需持续监听，需重新注册      │
└──────────────────────────────────────────────────────────────┘

Watch 类型：
┌──────────────────────────────────────────────────────────────┐
│  · NodeCreated：节点被创建                                    │
│  · NodeDeleted：节点被删除                                    │
│  · NodeDataChanged：节点数据变化（setData）                   │
│  · NodeChildrenChanged：子节点列表变化（增/删子节点）         │
└──────────────────────────────────────────────────────────────┘
```

# 7. 网络通信架构

## 7.1 端口配置

```text
每个 ZooKeeper 节点使用三个端口：

zoo.cfg 中的配置：
┌──────────────────────────────────────────────────────────────┐
│  clientPort=2181          ← 客户端连接端口                    │
│  server.1=host1:2888:3888  ← 集群内部通信                     │
│                             2888：Follower 连接 Leader 端口   │
│                             3888：Leader 选举端口             │
└──────────────────────────────────────────────────────────────┘
```

## 7.2 NIO 网络模型（ZooKeeper 3.x）

```text
ZooKeeper 3.x 使用 Java NIO 实现网络通信：

NIOServerCnxnFactory：
┌──────────────────────────────────────────────────────────┐
│                                                           │
│  AcceptThread             SelectorThread x N              │
│  ┌────────────┐          ┌──────────────────────┐       │
│  │ accept()   │──queue──►│ processAccept()      │       │
│  │ (Server    │          │ read()/write()       │       │
│  │  Socket)   │          │                      │       │
│  └────────────┘          │ SelectorThread        │       │
│                          │   · 负责 I/O 操作      │       │
│                          │   · 数量可配(默认 N)   │       │
│                          └──────────────────────┘       │
│                                                           │
│  请求处理链（RequestProcessor Chain）：                    │
│  ┌──────────┐   ┌──────────────┐   ┌──────────────────┐ │
│  │PreProcess│──►│SyncRequest   │──►│FinalRequest      │ │
│  │Processor │   │Processor(ZAB)│   │Processor(提交)   │ │
│  └──────────┘   └──────────────┘   └──────────────────┘ │
└──────────────────────────────────────────────────────────┘
```

ZooKeeper 3.6+ 引入了基于 Netty 的网络通信实现（`NettyServerCnxnFactory`），提升了高并发下的性能和稳定性。

# 8. 集群配置与通信

## 8.1 集群成员配置

```text
zoo.cfg 集群配置示例（3节点）：

# 基础配置
tickTime=2000
initLimit=10
syncLimit=5
dataDir=/var/lib/zookeeper/data
dataLogDir=/var/lib/zookeeper/log

# 集群配置

# Observer 配置（可选）
server.4=zk4.example.com:2888:3888:observer
```

## 8.2 节点间通信协议

```text
QuorumCnxManager（集群连接管理器）：
┌──────────────────────────────────────────────────────────┐
│                                                           │
│  Leader ↔ Follower 通信：                                  │
│    · LEADERINFO：Leader 通告自己当选                       │
│    · ACKEPOCH：Follower 确认 epoch                        │
│    · DIFF/TRUNC/SNAP：数据同步方式                         │
│    · PROPOSAL：Leader 发起提案                             │
│    · ACK：Follower 投票                                   │
│    · COMMIT：Leader 提交                                   │
│    · PING：心跳                                          │
│    · REVALIDATE：Session 验证                             │
│                                                           │
│  Leader ↔ Observer 通信：                                  │
│    · 同上，但 Observer 不发送 ACK（事务投票）               │
│                                                           │
│  选举通信（QuorumCnxManager）：                            │
│    · 每个节点之间建立双向连接                               │
│    · 发送 Vote 消息交换选举信息                             │
│    · 通过 myid 确定连接方向（小 id 连接大 id）              │
└──────────────────────────────────────────────────────────┘
```

# 9. 请求处理器链（Request Processor Pipeline）

这是 ZK 最核心的数据处理架构：

```text
Leader 请求处理器链：
┌──────────────────────────────────────────────────────────────────┐
│                                                                   │
│  Client Request                                                   │
│       │                                                           │
│       ▼                                                           │
│  ┌───────────────┐                                                │
│  │PrepRequest    │  1. 预处理：生成 zxid，设置 session 信息        │
│  │Processor      │                                                │
│  └───────┬───────┘                                                │
│          │                                                        │
│          ▼                                                        │
│  ┌───────────────┐                                                │
│  │Proposal       │  2. 生成 Proposal，持久化到本地事务日志          │

│          │                                                        │
│          ▼                                                        │

│  │               │     广播 COMMIT 给所有 Follower                 │
│  └───────┬───────┘                                                │
│          │                                                        │
│          ▼                                                        │
│  ┌───────────────┐                                                │
│  │ToBeApplied    │  4. 应用变更到本地内存数据库                     │

│  │Processor      │     返回结果给客户端                            │
│  └───────────────┘                                                │
│                                                                   │
└──────────────────────────────────────────────────────────────────┘

Follower 请求处理器链：
┌──────────────────────────────────────────────────────────────────┐

│  │Processor      │      └──────────────┘                          │
│  │               │  2. 收到 Leader 广播的 COMMIT                    │
│  │               │     应用到本地内存数据库                         │
│  │               │     触发 Watch                                 │
│  │               │     返回结果给客户端                            │
│  └───────────────┘                                                │
```

# 10. 关键数据结构

## 10.1 zxid（ZooKeeper Transaction ID）

```text
zxid 结构（64 位长整型）：
┌──────────────────────────────────────────────────────┐
│  Bit 63 ──────── Bit 32 │ Bit 31 ──────── Bit 0     │
│  ┌──────────────────────┐┌──────────────────────────┐│
│  │    epoch（32位）       ││    counter（32位）         ││
│  │    Leader 任期编号    ││   事务计数器             ││
│  └──────────────────────┘└──────────────────────────┘│
│                                                       │
│  示例：zxid = 0x200000005                             │
│    epoch   = 0x2 = 2（第 2 任 Leader）                │
│    counter = 0x5 = 5（该任期内第 5 个事务）            │
│                                                       │
│  规则：                                               │
│    · 每次 Leader 更换，epoch 递增                     │
│    · 同一任期内 counter 递增                           │
│    · zxid 在同一任期内一定是单调递增的                 │
└──────────────────────────────────────────────────────┘
```
