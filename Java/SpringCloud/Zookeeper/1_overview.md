
# 1. 分布式系统协调的挑战

在从单体架构向分布式架构演进的过程中，应用被拆分为多个独立部署的服务节点。这种演进带来了巨大的优势，但同时也引入了一系列新的挑战：

```
┌──────────────────────────────────────────────────────────────────┐
│                    单体 vs 分布式                                  │
│                                                                   │
│   单体架构                      分布式架构                          │
│   ┌─────────────┐              ┌──────┐  ┌──────┐  ┌──────┐      │
│   │  单一进程    │              │ 服务A │  │ 服务B │  │ 服务C │      │
│   │  单一数据库  │      →      │      │  │      │  │      │      │
│   │  内存锁/队列 │              └──┬───┘  └──┬───┘  └──┬───┘      │
│   └─────────────┘                 │         │         │           │
│                                    └────┬────┴────┬────┘           │
│                                         │         │                │
│                                   需要协调 ？   需要协调 ？          │
│                                   ┌──────┐  ┌──────┐              │
│                                   │锁？  │  │配置？│              │
│                                   │选举？│  │发现？│              │
│                                   └──────┘  └──────┘              │
└──────────────────────────────────────────────────────────────────┘
```

分布式系统中需要解决的典型问题：

| 问题 | 单体中的解决方案 | 分布式中的挑战 |
|------|-----------------|---------------|
| **配置管理** | 配置文件放在 classpath | 多节点配置需要统一管理和动态更新 |
| **服务发现** | 方法调用 | 服务节点动态上下线，消费者需感知 |
| **分布式锁** | synchronized / ReentrantLock | 跨 JVM 的互斥访问 |
| **分布式队列** | BlockingQueue | 跨 JVM 的生产者-消费者模型 |
| **集群选主** | 不存在此问题 | 多节点中选出一个 Leader 协调工作 |
| **命名服务** | JNDI | 全局统一的命名空间和 ID 生成 |
| **集群管理** | 不存在此问题 | 节点的加入、退出、健康监控 |

# 2. ZooKeeper 是什么

Apache ZooKeeper 是雅虎研究院开发的一个**开源的分布式协调服务**，最初是 Hadoop 的一个子项目，后于 2011 年成为 Apache 顶级项目。其设计灵感来源于 Google 的 Chubby 论文（《The Chubby Lock Service for Loosely-Coupled Distributed Systems》）。

> **核心定位**：ZooKeeper 不是一个数据库，也不是一个消息队列。它是一个为分布式系统提供**协调原语**（Coordination Primitives）的基础设施服务。

```text
ZooKeeper = 分布式协调服务
  ├── 数据存储：内存树形结构（ZNode Tree）
  ├── 通知机制：Watch 触发器
  ├── 一致性协议：ZAB（ZooKeeper Atomic Broadcast）
  └── 协调原语：锁、队列、选举等（基于上述基础构建）
```

**核心设计目标（来自官方文档）：**

| 目标 | 说明 |
|------|------|
| **简单** | 提供类似文件系统的层次命名空间，操作原语少而精 |
| **可靠** | 集群过半节点存活即可对外提供服务 |
| **有序** | 所有更新操作被全局排序，保证 FIFO 顺序 |
| **高效** | 基于内存的数据模型，读写比例 10:1 场景下性能极高 |
| **可复制** | 多副本架构，基于 ZAB 协议保证数据一致性 |

# 3. ZooKeeper 与 CAP 理论

## 3.1 CAP 理论回顾

| 属性 | 全称 | 含义 |
|------|------|------|
| **C** | Consistency | 一致性 — 所有节点同一时刻看到相同数据 |
| **A** | Availability | 可用性 — 每个请求都能得到非错误的响应 |
| **P** | Partition Tolerance | 分区容错 — 网络发生分区时系统仍能工作 |

根据 CAP 定理，一个分布式系统最多只能同时满足其中两个。由于网络分区（P）在分布式系统中不可避免（物理光纤被挖断、交换机故障、网络抖动），因此分布式系统真正需要抉择的是**在 C 和 A 之间如何取舍**。

## 3.2 ZooKeeper 的选择：CP 系统

```text
                    Network Partition（网络分区）
                              │
        ┌─────────────────────┼─────────────────────┐
        │                     │                     │
   ┌────┴────┐           ┌────┴────┐           ┌────┴────┐
   │  Server1 │  Leader   │  Server2 │  Follower │  Server3 │
   │  (存活)  │     ✗     │  (存活)  │           │  (存活)  │
   └─────────┘           └─────────┘           └─────────┘
   少数派分区                         多数派分区
   (不可用)                           (继续工作)

   结果：少数派分区不可用 → 牺牲 A，保证 C
```

ZooKeeper 选择 **CP 模型**（一致性和分区容错），关键特征：

- **过半机制（Quorum）**：写入必须获得半数以上节点确认才返回成功（`N/2 + 1`）
- **ZAB 协议**：保证所有副本的数据变更顺序完全一致
- **Leader 独写**：所有写请求必须由 Leader 处理，Follower 只转发写请求给 Leader
- **故障时的行为**：Leader 宕机后，集群进入**短暂的不可用**（选举新 Leader），期间拒绝写入，直到选出新 Leader

```text
CP 模型的代价（对比 AP 模型）：
┌────────────────────────────────────────────────────────┐
│  场景：3节点集群，1个节点网络分区                        │
│                                                         │
│  CP（ZooKeeper）：                                      │
│    分区节点（1个）：拒绝读写 → 不可用                    │
│    多数节点（2个）：正常服务                             │
│    保证了数据一致性                                      │
│                                                         │
│  AP（Eureka）：                                         │
│    分区节点（1个）：继续服务（可能有脏数据）              │
│    多数节点（2个）：正常服务                             │
│    牺牲了一致性                                          │
└────────────────────────────────────────────────────────┘
```

## 5.3 分布式锁

在多个服务实例竞争中同一资源时，需要分布式锁保证互斥访问：

```text
ZooKeeper /locks/resource_A
    │
    ├── /_c_0000000001 (Node1 - 获得锁)
    ├── /_c_0000000002 (Node2 - 等待)
    └── /_c_0000000003 (Node3 - 等待)

原理：
1. 所有竞争者创建临时顺序节点
2. 序号最小的获得锁
3. 锁释放后（节点删除），下一个序号最小的获得通知并获取锁
```

## 5.4 集群选主（Leader Election）

```text
多个候选者同时竞争（如多个调度器实例，仅允许一个执行）：

/nodes/master
    ├── /candidate_0000000001  ← 序号最小，成为 Master
    ├── /candidate_0000000002  ← 监听前一个节点
    └── /candidate_0000000003  ← 监听前一个节点

Master 宕机 → 临时节点自动删除 → candidate_0000000002 感知 → 成为新 Master
```

# 6. 设计哲学与核心原则

## 6.1 设计哲学

| 原则 | 说明 |
|------|------|
| **面向协调，不面向存储** | 每个 ZNode 数据量不超过 1MB（建议 KB 级别），不适合大文件存储 |
| **全序广播** | 所有状态变更操作拥有全局唯一的事务 ID（zxid），保证全序 |
| **顺序一致性** | 客户端看到的更新顺序与它们被发送到 ZooKeeper 的顺序相同 |
| **原子性** | 每次更新操作要么在所有服务器上成功，要么全部失败 |
| **单一系统镜像** | 无论客户端连接到哪个服务器，看到的系统视图相同 |
| **持久性** | 更新一旦成功，数据便被持久化（事务日志 + 快照），不会丢失 |
| **及时性** | 系统的客户视图在特定时间范围内是最新的（最终一致） |

## 6.2 性能特征

```text
典型性能指标（3.4.x+，3节点集群）：

┌─────────────────────────────────────────────────────┐
│ 读操作（直接读取本地内存副本）：                       │
│   · 吞吐量：100K+ QPS / 节点                         │
│   · 延迟：< 1ms（本地内存）                           │
│                                                      │
│ 写操作（ZAB 协议同步）：                              │
│   · 吞吐量：10K ~ 20K QPS / 集群                     │
│   · 延迟：2~10ms（依赖网络和磁盘）                     │
│                                                      │
│ 数据容量：                                           │
│   · 单 ZNode：默认 1MB 上限                          │
│   · 总 ZNode 数：理论上无限制，建议 < 100万            │

```
