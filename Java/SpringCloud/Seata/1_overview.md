
# 1. 分布式事务问题

在微服务架构中，一次业务请求往往跨越多个服务和数据库。以电商下单为例：

```
用户下单
  ├── 订单服务 ── INSERT order
  ├── 库存服务 ── UPDATE inventory (扣减)
  └── 账户服务 ── UPDATE account (扣款)
```

三个操作分属不同的数据库，无法用单一数据库的本地事务保证一致性。**分布式事务**就是要在这种场景下，确保所有操作要么全部成功，要么全部失败。

# 2. CAP 与 BASE 理论

| 理论 | 含义 | 说明 |
|------|------|------|
| **C**onsistency | 一致性 | 所有节点同一时刻数据相同 |
| **A**vailability | 可用性 | 服务始终可用，正常响应 |
| **P**artition Tolerance | 分区容错 | 网络故障时系统仍能工作 |

分布式系统必须选择 **P**（网络分区不可避免），在 C 和 A 之间权衡：
- **CP**（放弃 A）：ZooKeeper — 强一致，但故障时可能不可用
- **AP**（放弃 C）：Eureka — 高可用，但数据可能不一致
- **BASE**：Basically Available + Soft state + Eventually consistent

Seata 选择了 **BASE 理论**，追求**最终一致性**而非强一致性。

# 3. Seata 是什么

Seata（Simple Extensible Autonomous Transaction Architecture）是阿里巴巴开源的**分布式事务解决方案**，2019 年 1 月正式开源，现为 Apache 顶级项目的前身（已捐赠）。

```
┌───────────────────────────────────────────────────────┐
│                      Seata 生态                         │
│                                                        │
│   ┌──────────┐    ┌──────────┐    ┌──────────┐        │
│   │ AT 模式   │    │ TCC 模式  │    │ Saga 模式 │        │
│   │ (自动)    │    │ (手动)    │    │ (编排)    │        │
│   └──────────┘    └──────────┘    └──────────┘        │
│                                                        │
│   ┌──────────┐    ┌──────────┐    ┌──────────┐        │
│   │  XA 模式  │    │ TC Cluster│    │ Nacos/ZK  │       │
│   │ (数据库级) │    │ (高可用)   │    │ (注册/配置) │      │
│   └──────────┘    └──────────┘    └──────────┘        │
└───────────────────────────────────────────────────────┘
```

**核心能力**：
- **AT 模式**：对业务零侵入，自动生成回滚日志（undo_log）
- **TCC 模式**：两阶段资源预留，高性能自定义实现
- **Saga 模式**：长事务编排，补偿式回滚
- **XA 模式**：基于数据库 XA 协议的两阶段提交

# 4. Seata vs 其他方案

| 维度 | Seata AT | Seata TCC | 可靠消息 | 最大努力通知 | LCN |
|------|---------|----------|---------|------------|-----|
| **一致性** | 最终一致 | 最终一致 | 最终一致 | 最终一致 | 强一致（LCN6前） |
| **侵入性** | 低（仅代理数据源） | 中（需实现TCC接口） | 低 | 低 | 低 |
| **性能** | 中 | 高 | 高 | 高 | 低（锁资源） |
| **回滚** | 自动 | 需手动补偿 | 无回滚（需补偿） | 无回滚 | 自动 |
| **适用场景** | 大部分业务 | 高性能场景 | 异步解耦 | 通知类 | 遗留系统 |
| **维护状态** | ✓ 活跃 | ✓ | 需自建 | 需自建 | 已停维 |

# 5. 核心设计理念

1. **三大角色分离**：TC（事务协调器）、TM（事务管理器）、RM（资源管理器）解耦
2. **两阶段提交**：Phase 1 — 执行业务 + 记录 undo_log；Phase 2 — 提交或回滚
3. **undo_log 自动补偿**：AT 模式核心，通过代理数据源自动生成反向 SQL
4. **全局锁**：防止脏写，保证写隔离
5. **xid 全局事务 ID**：通过 Dubbo Filter / Feign Interceptor 自动在 RPC 调用中传播
