# 1. 分布式事务要解决的问题

在微服务架构中，一次业务请求往往跨越多个服务和数据库。以电商下单为例：

```text
用户下单
  ├── 订单服务 ── INSERT order      (db_order)
  ├── 库存服务 ── UPDATE inventory  (db_stock)
  └── 账户服务 ── UPDATE account    (db_account)
```

三个操作分属不同的数据库，甚至不同的服务、不同的机器，无法用单一数据库的本地事务保证一致性。**分布式事务**就是要在这种场景下，确保所有操作要么全部成功，要么全部失败。

本地事务的 ACID 之所以"免费"，是因为单一数据库引擎能在一个进程内统一调度锁、日志与提交协议。拆成微服务后，前提全部被打破：事务边界跨进程、参与者各有自己的连接池与锁、网络可能超时、节点可能宕机。真正困难的是中间状态——分支 1 已提交、分支 2 失败时，谁来负责把分支 1 撤销？撤销失败又怎么办？

> **注意**：分布式事务的第一决策不是"选哪个框架"，而是"该不该用"。能通过业务设计避免跨库事务（单聚合根设计、读时聚合、最终一致的异步化）永远优于引入协调器；只有"必须原子、业务不可拆分"的链路才值得付出分布式事务的性能与运维成本。

# 2. 理论基座：CAP、BASE 与 2PC

| 理论 | 含义 | 说明 |
|------|------|------|
| **C**onsistency | 一致性 | 所有节点同一时刻数据相同 |
| **A**vailability | 可用性 | 服务始终可用，正常响应 |
| **P**artition Tolerance | 分区容错 | 网络故障时系统仍能工作 |

分布式系统必须选择 **P**（网络分区不可避免），在 C 和 A 之间权衡：**CP**（放弃 A）如 ZooKeeper，强一致但故障时可能不可用；**AP**（放弃 C）如 Eureka，高可用但数据可能不一致。业务数据库无法接受长期不一致，于是出现了 **BASE**——Basically Available（基本可用）、Soft state（软状态）、Eventually consistent（最终一致）：允许中间窗口内的不一致，靠补偿与收敛保证终态正确。

Seata 的四种模式正是分布在这条谱系上：**AT/TCC/SAGA 属于 BASE 阵营**（追求最终一致、优先可用性），**XA 属于 ACID 阵营**（复用数据库 2PC，接近强一致）。理解这个定位，比记住模式名字更重要。

# 3. Seata 是什么

Seata（Simple Extensible Autonomous Transaction Architecture）是阿里巴巴开源的**分布式事务解决方案**，2019 年 1 月正式开源（前身是 Fescar 项目），后续进入 Apache 孵化体系，当前主线是 2.x。

```text
┌───────────────────────────────────────────────────────┐
│                      Seata 生态                         │
│                                                        │
│   ┌──────────┐    ┌──────────┐    ┌──────────┐        │
│   │ AT 模式   │    │ TCC 模式  │    │ Saga 模式 │       │
│   │ (自动补偿) │    │ (手动预留) │    │ (状态编排) │      │
│   └──────────┘    └──────────┘    └──────────┘        │
│                                                        │
│   ┌──────────┐    ┌──────────┐    ┌──────────┐        │
│   │  XA 模式  │    │ TC Cluster│    │ Nacos/ZK  │      │
│   │ (数据库级) │    │ (协调集群) │    │ (注册/配置) │     │
│   └──────────┘    └──────────┘    └──────────┘        │
└───────────────────────────────────────────────────────┘
```

它的三种核心角色构成整个体系的最小闭环：

```text
        ┌────────── begin / commit / rollback ──────────┐
        │                                               ▼
┌───────────────┐  全局事务决策   ┌────────────────────────────┐
│      TM       │ ─────────────→ │            TC              │
│ Transaction   │ ←───────────── │   Transaction Coordinator  │
│ Manager       │  xid / 状态     │  (Seata Server, 独立部署)   │
└───────────────┘                └──────────┬─────────────────┘
        ▲                                   │ 分支注册 / 状态上报 / 2nd 阶段指令
        │ @GlobalTransactional              ▼
        │ 所在服务入口            ┌────────────────────┐  RPC(xid 传播)  ┌──────────────┐
   ┌────┴─────┐                 │        RM          │ ←─────────────→ │     RM       │
   │ 订单服务  │ ───────────────→│ Resource Manager   │  资源分支事务     │ (账户服务)    │
   └──────────┘                 │ (数据源代理/TCC代理) │                 └──────────────┘
                                └────────────────────┘
```

| 角色 | 全称 | 职责 | 落地形态 |
|------|------|------|---------|
| **TC** | Transaction Coordinator | 维护全局/分支事务状态，驱动全局提交或回滚 | 独立部署的 Seata Server |
| **TM** | Transaction Manager | 定义全局事务边界：开启、提交、回滚 | `@GlobalTransactional` 注解所在方法 |
| **RM** | Resource Manager | 管理分支资源：向 TC 注册分支、汇报状态、执行 2nd 阶段 | 各服务内的数据源代理 / TCC 切面 |

**设计考量**：TM/RM 都是**嵌在业务应用进程里的客户端逻辑**，只有 TC 是独立协调服务。这个"胖协调器、薄参与者"的结构决定了：TC 的存储与网络成为集群吞吐瓶颈（性能调优核心，见性能篇），也让业务服务无需为事务状态持久化负责。

# 4. 四种模式一览

| 模式 | 侵入性 | 一致性 | 回滚方式 | 典型场景 |
|------|--------|--------|---------|---------|
| **AT** | 零（仅代理数据源） | 最终一致 | 自动生成 undo_log 反向 SQL | 大多数单库 SQL 可覆盖的业务 |
| **TCC** | 高（Try/Confirm/Cancel 三接口） | 最终一致 | 手动 Cancel 释放预留资源 | 高性能、资源需提前锁定（库存、额度） |
| **Saga** | 中（每步配补偿服务） | 最终一致 | 逆序执行补偿 | 长流程、含外部系统/人工节点 |
| **XA** | 零（需 XA 驱动） | 强一致 | 数据库原生 XA ROLLBACK | 遗留系统、异构 DB、短事务强一致 |

一句话记忆：**AT 用 SQL 换代码，TCC 用代码换性能，SAGA 用编排换时长，XA 用锁换一致**。模式间可在同一全局事务内混用，选型展开见模式选择篇。

# 5. 与其他方案的对比

分布式事务不是 Seata 独有赛道。传统方案里最常见的是**可靠消息最终一致**与**最大努力通知**：

| 维度 | Seata AT | Seata TCC | 可靠消息(RocketMQ 事务消息) | 最大努力通知 | 手工补偿/对账 |
|------|---------|-----------|---------------------------|-------------|--------------|
| 一致性 | 最终一致（秒级） | 最终一致（秒级） | 最终一致（秒~分钟级） | 最终一致（依赖对方重试） | 事后一致（天级） |
| 实时性 | 高，同步感知结果 | 高 | 中，异步解耦 | 低 | 低 |
| 侵入性 | 低（代理数据源） | 中（三接口） | 低~中（监听器/半消息） | 低 | 需自建状态表 |
| 调用方感知下游结果 | 能（同步回滚） | 能 | 不能（只保证消息投递） | 不能 | 不能 |
| 基础设施 | TC Server | TC Server | 事务消息支持的 MQ | MQ/回调通道 | 对账批处理 |
| 维护状态 | 活跃社区 | 活跃 | 依赖 MQ 选型 | 依赖通道 | 纯自研 |

**适用判断**：下单扣库存这类**调用链上需要立即知道成败**的场景，Seata 合适；"下单成功后发积分"这类**下游慢一点无所谓、只要求不丢**的场景，事务消息反而更优——异步化解耦、不占同步链路 RT。最大努力通知适用于对第三方（银行、开放平台）场景：己方无法强制对方回滚，只能反复通知加对账兜底。

> **行业实践**：成熟团队通常是**组合拳**——核心资金链路用 Seata AT/TCC 保证强实时收敛，边缘副作用（积分、通知、营销）走事务消息异步化，跨企业链路用最大努力通知+T+1 对账。把"全部链路都上分布式事务"当成目标是反模式，代价是整条链路的吞吐和可用性都绑在协调器上。

# 6. 核心设计理念

1. **三角色分离**：TC/TM/RM 各司其职，协调状态集中、执行决策就近。
2. **两阶段提交抽象**：Phase 1 各分支执行并"表态"（undo_log/预留资源/准备状态），Phase 2 由 TC 驱动全局提交或回滚。
3. **xid 全链路传播**：全局事务 ID 随 RPC 上下文（Dubbo attachment / Feign 拦截器 / MQ header）自动透传，业务无感。
4. **以数据换回滚**：AT 靠 undo_log 镜像做反向 SQL，TCC 靠业务状态表做幂等补偿，Saga 靠流程状态机做逆序编排。
5. **可靠性兜底**：分支悬挂检测、空回滚/幂等防御、TC 重启后从存储恢复事务继续推进。

# 7. 版本演进与 2.x 要点

| 版本 | 时间 | 里程碑 |
|------|------|--------|
| 0.x | 2018 | 内部版本 Fescar |
| 0.1.0 | 2019.1 | 正式开源，更名 Seata |
| 1.0.0 | 2019.12 | GA，AT/TCC/Saga 三大模式完整 |
| 1.3.0 | 2020.9 | TCC 幂等增强、Saga 状态机引擎 |
| 1.4.0 | 2021.2 | 支持 XA 模式 |
| 1.5.0 | 2022.7 | 性能优化、Raft 存储模式 |
| 1.6~1.7 | 2023-2024 | Spring Boot 3 兼容、JDK 21/虚拟线程支持 |
| 2.0 | 2024 | 引入 **Apache Server 化重构**（控制台、多租户）、协议优化 |
| 2.x | 2025-2026 | 稳定性收敛，存储/传输持续优化，与 Spring Cloud 2023+ 对齐 |

> **注意**：2.x 与 1.x 在**配置键结构、注册发现模型、Server 目录布局**上有不兼容变化（如 `registry.conf`/`file.conf` 在 2.x 被统一为 `application.yml` 风格的 server 配置）。升级要同时核对三件事：TC Server 版本、客户端 `seata-spring-boot-starter` 版本、Spring Cloud Alibaba 版本矩阵，三者版本错位是生产事故的高发区。

# 8. 选型前置问题清单

引入 Seata 之前，把下面六个问题答清楚，能过滤掉一半的错误引入：

1. **这个一致性需求必须同步满足吗？** 下游能接受分钟级异步收敛 → 考虑事务消息而不是 Seata。
2. **参与者能否改造？** 遗留系统只给 JDBC 接口 → AT/XA；能写三接口 → 才考虑 TCC。
3. **事务时长什么量级？** 秒级 → AT/TCC/XA；小时/天级或含人工节点 → SAGA。
4. **隔离要求多高？** 能接受全局窗口内的中间态 → AT/TCC；必须数据库级强隔离 → XA。
5. **团队能否运维 TC？** 至少要有注册中心、共享存储（DB/Redis/Raft）与监控告警；没有运维容量时宁可先消息表。
6. **性能预算多少？** AT 大约 20-30% 的吞吐折损、XA 可能腰斩，压测基线决定模式与集群规模。

# 9. 小结

Seata 的定位是把"跨服务跨库的原子性"从每家自研补偿逻辑，收敛为一套 TC/TM/RM 的标准化协调机制：TC 集中维护事务状态，TM 圈定全局边界，RM 就近执行分支与二阶段动作，xid 在链路里自动传播。四种模式——AT（SQL 换代码）、TCC（代码换性能）、SAGA（编排换时长）、XA（锁换一致）——覆盖了从最终一致到强一致的完整光谱。

同时要守住两条边界：Seata 服务于 BASE 场景（AT/TCC/SAGA）与有限强一致场景（XA），**不是跨企业事务方案**，通知类弱一致场景交给事务消息与对账更划算；而引入协调器意味着引入一个新的集群级依赖，收益与运维成本要在选型前置清单里算清楚，再决定在链路的哪些段落在、哪些段落用异步化绕开它。
