# 1. 模式对比矩阵

AT/TCC/SAGA/XA 四种模式的差异，最终收敛在五个可度量的维度上：**性能、侵入性、隔离性、回滚方式、适用范围**。先把全景表立起来，后面的决策树和场景映射都由它推导。

| 维度 | AT | TCC | Saga | XA |
|------|-----|-----|------|-----|
| **实现复杂度** | 低 | 高 | 中 | 低 |
| **业务侵入性** | 无 | 高（三阶段接口） | 中（每步补偿服务） | 无 |
| **回滚方式** | 自动 undo_log 反向 SQL | 手动 Cancel 释放预留 | 逆序执行补偿 | 数据库 XA ROLLBACK |
| **性能** | 中高（额外 3 SQL+2 RPC） | 高（无 DB 层额外 SQL） | 高（异步编排） | 低（锁持有到全局裁决） |
| **锁粒度** | 全局行锁（TC 逻辑锁） | 业务层资源预留 | 无锁 | 数据库行锁（物理、长） |
| **一致性级别** | 最终一致 | 最终一致 | 最终一致 | 强一致 |
| **读隔离性** | 默认读未提交（可 @GlobalLock 补救） | 取决于预留实现 | 无隔离（中间态可见） | 数据库隔离级别 |
| **资源类型** | 仅关系型数据库 | 数据库 + RPC + MQ + 任意 | 任意服务（HTTP/MQ/人工） | 仅支持 XA 的数据库 |
| **幂等要求** | 框架保证 | Try/Confirm/Cancel 都要幂等 | 服务与补偿都要幂等 | 数据库保证 |
| **依赖组件** | undo_log 表 + TC | 业务控制表 + TC | 状态机引擎/流程服务 + TC | XA 驱动 + TC |
| **故障恢复** | 自动（TC 驱动补偿） | 需处理空回滚/悬挂/防击穿 | 逆序补偿 + 人工兜底 | XA RECOVER |

三句话提炼：**AT 的复杂度在框架，TCC 的复杂度在业务，SAGA 的复杂度在流程**。XA 框架和业务都不挑，但对数据库和运行时长按下不表的重注（锁窗口），决定了它的适用面最窄。

> **注意**：读隔离一行是选型时最常被低估的差异。AT 的全局事务窗口内，已提交未决的中间态对其他读取者是**可见**的（默认）；TCC 冻结金额、Saga 订单已创建待审批等中间态同样可见，需要业务状态字段自行挡读。只有 XA 提供真正数据库级的隔离。"用户能不能在事务窗口里读到半更新数据"这个问题,答案决定隔离方案，而不是反过来被模式默认值绑架。

# 2. 选择决策树

```text
需要分布式事务？
  │
  ├── 否（能单库聚合根/异步消息/对账兜底）──→ 不用 Seata，收工
  │
  └── 是
        │
        ├── 事务时长？
        │     ├── 秒级以内 → 继续往下
        │     └── 分钟/小时/天级，含外部或人工节点 → SAGA
        │
        ├── 参与者资源类型？
        │     ├── 全是关系型 DB
        │     │     ├── 必须数据库级强隔离？
        │     │     │     ├── 是，且并发低/无热点行 → XA
        │     │     │     └── 是，且高并发热点 → 回到架构设计（拆事务）
        │     │     ├── 高并发核心链路，能接受三接口改造 → TCC
        │     │     └── 默认路线，快速上线 → AT
        │     └── 含非 DB 资源（RPC/MQ/HTTP 外部 API）
        │           ├── 资源方能提供预留/释放接口 → TCC
        │           └── 资源方只能正向调用+补偿接口 → SAGA
        │
        └── 遗留库不能加 undo_log 表 / 驱动支持 XA → XA（备选 AT）
```

决策树里埋了两个容易被跳过的分支：第一问永远是"能不能不用分布式事务"——单服务聚合根重构、事件最终一致的收益长期大于任何模式；第二是"强一致 + 高并发热点"的组合在四种模式里没有解，出现这个需求说明事务边界画错了，要拆而不是选。

# 3. 典型业务映射

## 3.1 AT —— 电商下单（通用首选）

```text
场景：电商下单
  订单服务（MySQL）→ 账户服务（MySQL）→ 库存服务（MySQL）
  涉及：3 个数据库，同构 MySQL
  要求：最终一致，秒级收敛
  选择：AT 模式 ✓
  理由：零侵入、自动回滚、性能好
```

AT 的主场特征完全吻合：同构关系库、SQL 简单可解析、团队不想为事务改造业务。风控、营销、优惠券核销这类"标准 CRUD + 跨服务调用"链路，默认都落到 AT。

## 3.2 TCC —— 红包发放与库存扣减（高性能）

```text
场景：红包发放 / 热点库存扣减
  红包服务 → 发送 100 元红包
    Try:    冻结账户 100 元（balance→frozen），生成红包记录
    Confirm: 扣减冻结金额 → 红包到账
    Cancel:  解冻 100 元，回收红包

  涉及：账户余额（DB）、红包记录（DB）、消息推送（MQ）
  要求：高并发 + 高性能 + 资源提前锁定
  选择：TCC 模式 ✓
  理由：自定义预留机制，比全局锁更灵活，可覆盖 MQ 等非 DB 资源
```

库存扣减是 TCC 最经典的映射：Try 冻结（可售→预扣）、Confirm 真实出库、Cancel 解冻。之所以不用 AT，是因为秒杀级热点行会让 AT 全局锁排队雪崩，而 TCC 把"锁"变成业务字段上的原子 UPDATE，冲突控制完全自主；且"发 MQ 通知"这类资源只有 TCC 能纳入事务。

## 3.3 SAGA —— 差旅报销（长流程编排）

```text
场景：差旅报销流程
  员工提交 → 经理审批 → 财务打款 → 通知员工
  整个流程可能需要数小时甚至数天，含人工审批节点。

  涉及：多个服务 + OA 人工节点 + 银企直连
  要求：最终一致，允许中间状态长期存在
  选择：SAGA 模式 ✓
  理由：无锁、长事务、可编排、支持补偿与人工干预
```

SAGA 的判断标志：**事务里有"世界不能陪着等"的环节**。人工审批、外部银行回调、跨天对账，用 AT/XA 会让 DB 锁和 TC 会话陪跑数小时，纯属资源自杀；SAGA 的每一步都是独立本地事务，状态机持久化推进，失败逆序补偿，天然支持超时、重试、人工介入节点。

## 3.4 XA —— 跨异构库转账（强一致）

```text
场景：核心账务跨行转账（遗留系统）
  账户A（Oracle）→ 扣款 1000
  账户B（DB2）    → 入账 1000

  涉及：2 个异构数据库，均支持 XA
  要求：强一致（不允许少钱或多钱），事务时长 < 秒级，非热点账户
  选择：XA 模式 ✓
  理由：数据库原生 2PC，隔离真实，异构库统一接入，遗留系统零改造
```

注意适用前提全部成立才敢选 XA：短事务、非热点、异构库、不能加 undo_log。四个条件缺一个，答案就要重写（热点→重设计，同构高并发→AT）。

# 4. 混合模式

Seata 支持同一全局事务内混合不同模式的分支——TC 眼里只有"分支事务 + 二阶段动作"，不关心分支用什么模式注册：

```java
@GlobalTransactional
public void createOrder(Order order) {
    // 分支1: AT 模式（订单/库存，本地库标准 CRUD）
    orderMapper.insert(order);           // AT 数据源代理自动注册

    // 分支2: TCC 模式（账户扣款，需要预留+确认）
    accountTccService.tryDebit(userId, amount, orderId);  // TCC 切面注册

    // 分支3: 通知服务走远程 AT（下游服务自己的数据源代理）
    notificationClient.notify(order);
}
```

**混合使用注意**：

- **回滚语义对齐**：全局回滚时 AT 分支走 undo_log、TCC 分支走 Cancel、XA 分支走 XA ROLLBACK，任一分支的二阶段动作失败都会重试到超时人工介入——混合链路的恢复演练要按"最坏分支"设计。
- **隔离水位取最弱**：全局事务的可观察中间态由隔离性最差的分支决定（AT 读未提交/SAGA 无隔离），不能因为链路里有一个 XA 分支就以为整体强一致。
- **超时预算统一**：`@GlobalTransactional(timeoutMills)` 覆盖所有分支；混入长耗时分支（外部 HTTP）会把全局超时拉长，锁/预留窗口同步放大，预算要按最长分支算。
- **故障排查复杂度翻倍**：一个 xid 下混着不同 branch_type，排查时要先分辨分支模式再选恢复手段（undo_log vs 业务表 vs XA RECOVER），日志与监控必须带上 branch_type 维度。

> **行业实践**：混合模式在真实系统里是常态而非例外——一次下单几乎必然同时触碰"标准 CRUD（AT）+ 额度预留（TCC）+ 外部通知（补偿）"。主流做法是**主链路统一模式、边缘分支按需混用**，而不是每个分支各选最优；模式越多，团队心智与故障面越不可控。

# 5. 性能参考基准

```text
测试条件：4C8G，MySQL 5.7，单表 10w 行，100 并发，同构库

| 模式   | TPS    | P99 RT | CPU  | 锁等待 |
|--------|--------|--------|------|--------|
| 无事务 | 5000   | 15ms   | 40%  | —      |
| AT     | 4200   | 22ms   | 55%  | 中     |
| TCC    | 4600   | 18ms   | 50%  | 低     |
| Saga   | 4800   | 16ms   | 45%  | 无     |
| XA     | 2500   | 45ms   | 60%  | 高     |
```

> AT 模式开销主要来自 undo_log 写入（额外 SQL）和前置/后置镜像查询；TCC 的开销在业务控制表读写；Saga 单步性能≈本地事务但收敛慢；XA 的折损直接来自锁持有窗口与连接占用。以上为参考基线，**热点行、事务时长、分支数三个变量任何一个变化，量级就会漂移**，选型前务必用自家模型压测（方法与调优见性能篇）。

# 6. 选型建议总结

| 优先级 | 场景 | 推荐模式 |
|--------|------|---------|
| 0 | 能用单库/异步消息/对账解决 | 不上分布式事务 |
| 1 | 通用分布式事务（同构 DB、快速落地） | AT |
| 2 | 高并发核心链路 + 可改造 + 含非 DB 资源 | TCC |
| 3 | 长事务 / 编排 / 外部系统与人工节点 | SAGA |
| 4 | 强隔离 + 短事务 + 异构 DB / 遗留系统 | XA |

最终建议：**一个系统的全局事务模式种类不超过两种**（典型组合 AT 打底 + TCC 攻坚热点），把 SAGA 留给真正的长流程域，把 XA 留给异构与遗留边界。模式选择是架构决策，评审时按"时长→资源→隔离→并发→改造成本"五问走一遍决策树，比争论框架优劣有效得多。

# 7. 小结

四模式光谱一句话各自行：**AT 用 SQL 换代码**（框架自动补偿，适合绝大多数同构库场景，默认首选）；**TCC 用代码换性能**（三接口自主预留释放，扛热点、覆盖非 DB 资源，但幂等/悬挂/空回滚都要业务自己防）；**SAGA 用编排换时长**（无锁长流程、可含人工与外部节点，隔离最弱、补偿设计最重）；**XA 用锁换一致**（数据库原生 2PC 真隔离、异构通吃，代价是吞吐随事务时长线性恶化）。

落到工程实践：先问能不能不用分布式事务，再用决策树按"时长→资源类型→隔离要求→并发热点→遗留约束"裁剪，主链路模式统一、边缘按需混用且种类克制，最后用自家业务模型压测验证——性能表上的数字是方向感，不是保证书。
