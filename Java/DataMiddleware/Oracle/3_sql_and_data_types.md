# 1. SQL 基础与 schema

Oracle 的 SQL 与标准 SQL 大体一致，但有几个本地化特征必须先建立认知，否则写出来的语句会在别处能跑、在这里报错。

## 1.1 用户即 schema

在 Oracle 中，**schema 是一个用户所拥有的对象的集合**。创建用户 `app_user` 时，Oracle 自动创建一个同名 schema；该用户建的所有表、索引、视图、序列都归这个 schema 所有。这和 MySQL"schema 等同 database"、PostgreSQL"schema 是数据库下的命名空间"都不同。

带来的直接影响是：**表名默认不带库名前缀，但跨 schema 必须写全名**。

```sql
-- 当前用户查询自己的表，直接写表名
SELECT * FROM orders;

-- 跨 schema 查询，必须写 schema 前缀
SELECT * FROM app_user.orders;
```

> **设计考量**：用户与 schema 绑定，让权限管理和对象归属天然一致，也便于做多租户隔离（每个业务域一个 schema）。代价是迁移到其他数据库时需要把"schema 前缀"重新映射成"库名或 schema 名"，这是 Oracle 迁移工作量的一部分。

## 1.2 SQL 分类

| 分类 | 代表语句 | 说明 |
|------|---------|------|
| DDL | `CREATE`、`ALTER`、`DROP`、`TRUNCATE`、`COMMENT` | 定义对象结构，自动提交 |
| DML | `INSERT`、`UPDATE`、`DELETE`、`MERGE` | 修改数据，需显式提交 |
| DQL | `SELECT` | 查询数据 |
| DCL | `GRANT`、`REVOKE` | 权限控制，自动提交 |
| TCL | `COMMIT`、`ROLLBACK`、`SAVEPOINT` | 事务控制 |

Oracle 的 DDL 是**隐式提交**的：执行 `CREATE TABLE` 前会先把当前事务提交。这一点和 PostgreSQL 的事务性 DDL 不同，写迁移脚本时要特别注意别把 DDL 和 DML 混在一个事务里期望一起回滚。

## 1.3 双引号与大小写

Oracle 的标识符默认**不区分大小写**，不加引号时会统一转成大写存储。加了双引号就变成大小写敏感，之后每次引用都必须带同样的引号和大小写。

不加引号时 `CREATE TABLE orders` 实际存为 `ORDERS`，查询写 `orders` 也能识别；加了双引号的 `"OrderDetail"` 则严格区分大小写，之后每次引用都必须带同样的引号和大小写。

> **注意**：不要为了"看起来像驼峰"而给表名加双引号。这会让所有 SQL、ORM 映射、运维脚本都变复杂。统一用小写加下划线、不加引号，是最省心的做法。

# 2. 数据类型

Oracle 的数据类型体系比 MySQL 更细，尤其是字符和数值。选错类型不会立刻报错，但会在存储、索引、比较、迁移时埋下隐患。

## 2.1 字符类型

| 类型 | 说明 | 最大长度 | 适用 |
|------|------|---------|------|
| `CHAR(n)` | 定长字符串，不足补空格 | 2000 字节 | 固定长度编码，如国家代码 |
| `VARCHAR2(n)` | 变长字符串，按字节或字符计 | 4000 字节（SQL）/ 32767（PL/SQL） | 绝大多数业务字段 |
| `NVARCHAR2(n)` | 国家字符集变长字符串 | 4000 字符 | 多语言、Unicode |
| `CLOB` | 字符大对象 | 4GB | 长文本、JSON、日志 |
| `RAW(n)` | 二进制定长 | 2000 字节 | 哈希值、密钥 |

`VARCHAR2` 的 `n` 默认按**字节**计算，不是字符。在 `AL32UTF8` 下，一个汉字通常占 3 个字节，所以 `VARCHAR2(10)` 最多只能存 3 个汉字；要按字符计，必须显式写 `VARCHAR2(10 CHAR)`。

> **行业实践**：涉及中文的字段一律写 `VARCHAR2(n CHAR)`，避免"英文够用、中文截断"的线上事故。Oracle 没有 MySQL 那种 `utf8mb4` 与 `utf8` 的坑，但字节语义的坑同样常见。

`VARCHAR` 在 Oracle 里是 `VARCHAR2` 的同义词，但官方建议**始终写 `VARCHAR2`**，因为 `VARCHAR` 的语义在不同版本间可能变化，而 `VARCHAR2` 是 Oracle 保证向后兼容的类型。

## 2.2 数值类型

| 类型 | 说明 | 适用 |
|------|------|------|
| `NUMBER(p, s)` | 定点数，`p` 总位数，`s` 小数位 | 金额、精确计算 |
| `NUMBER` | 无精度限制的数值 | 不推荐，容易存进意外精度 |
| `BINARY_FLOAT` | 32 位浮点 | 科学计算 |
| `BINARY_DOUBLE` | 64 位浮点 | 科学计算 |
| `INTEGER` / `INT` | `NUMBER(38)` 的别名 | 自增主键、计数 |

金额字段必须用 `NUMBER(p, s)`，例如 `NUMBER(18, 2)` 表示最多 18 位、其中 2 位小数。不要用 `FLOAT` 或 `BINARY_DOUBLE` 存金额，二进制浮点无法精确表示 0.1，累加会出现误差。

```sql
-- 正确：金额用定点数，最多 18 位、2 位小数
CREATE TABLE payment (
    id      NUMBER(19)     NOT NULL,
    amount  NUMBER(18, 2)  NOT NULL,
    currency CHAR(3)       DEFAULT 'CNY'
);
-- 错误示范：用 BINARY_DOUBLE 存金额，累加会出现精度误差
```

## 2.3 日期与时间

Oracle 有两个日期类型，初学者常混用：

| 类型 | 精度 | 说明 |
|------|------|------|
| `DATE` | 到**秒** | 包含年、月、日、时、分、秒，没有小数秒和时区 |
| `TIMESTAMP` | 到**纳秒**（默认 6 位小数秒） | 可带时区，`TIMESTAMP WITH TIME ZONE` |
| `TIMESTAMP WITH LOCAL TIME ZONE` | 存 UTC，按会话时区显示 | 跨时区业务推荐 |

```sql
-- DATE 只到秒，插入带毫秒的时间会被截断；TIMESTAMP 保留小数秒
CREATE TABLE event_date (created_at DATE);
INSERT INTO event_date VALUES (TIMESTAMP '2026-11-06 10:20:30.123456');
```

> **注意**：`DATE` 的默认显示格式由 `NLS_DATE_FORMAT` 决定，常见是 `DD-MON-RR`。写 SQL 时不要依赖隐式格式，插入和比较都用 `DATE '2026-11-06'` 或 `TO_DATE('2026-11-06', 'YYYY-MM-DD')`。隐式转换在不同客户端可能给出不同结果，是线上事故的高发点。

## 2.4 大对象类型

| 类型 | 内容 | 最大 | 说明 |
|------|------|------|------|
| `CLOB` | 字符大对象 | 4GB | 长文本、XML、JSON |
| `BLOB` | 二进制大对象 | 4GB | 图片、文件、序列化数据 |
| `NCLOB` | 国家字符集 CLOB | 4GB | 多语言长文本 |
| `BFILE` | 外部文件指针 | 取决于文件系统 | 数据库外的大文件 |

`CLOB` 在 JDBC 中要用 `getClob()` / `setClob()` 或 `getString()`（小数据量时）处理。注意 `CLOB` 不能直接用于 `GROUP BY`、`DISTINCT`、`ORDER BY`，也不能建普通 B-tree 索引，需要全文索引或函数索引配合。

## 2.5 其他常用类型

19c 起可用 `JSON` 类型，底层仍是 `VARCHAR2`/`CLOB` 加约束；Oracle SQL 层长期没有 `BOOLEAN` 列类型（23ai 才有），布尔值通常用 `CHAR(1)` 加 `CHECK` 约束，或 `NUMBER(1)`。

# 3. 序列与主键

Oracle 直到 12c 才引入 `IDENTITY` 列，长期以来的标准做法是**序列（Sequence）+ 触发器**或**序列 + 应用取号**。

## 3.1 序列的基本用法

```sql
-- 创建序列：从 1 开始，每次加 1，缓存 20 个值
CREATE SEQUENCE seq_orders
  START WITH 1
  INCREMENT BY 1
  NOCACHE
  NOCYCLE;

-- 取下一个值
SELECT seq_orders.NEXTVAL FROM dual;
```

`CACHE` 能减少序列争用，但实例崩溃时缓存中未使用的值会丢失，导致主键出现**空洞**。这对业务通常无害，但如果要求主键连续（如发票号），就不能依赖序列，需要单独的号码表加锁取号。

## 3.2 12c 之后的 IDENTITY 列

```sql
-- 12c 起支持标准写法
CREATE TABLE orders (
    id      NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    user_id NUMBER NOT NULL,
    amount  NUMBER(18, 2) NOT NULL
);

-- 允许显式插入 id（GENERATED ALWAYS 则不允许）
INSERT INTO orders (id, user_id, amount) VALUES (100, 1, 99.00);
```

> **设计考量**：`GENERATED BY DEFAULT` 允许应用自己指定 id，适合数据迁移和分库分表；`GENERATED ALWAYS` 强制由数据库生成，语义更严格。迁移历史数据时通常选前者。

## 3.3 序列与 MySQL 自增的差异

| 维度 | Oracle 序列 | MySQL AUTO_INCREMENT |
|------|------------|---------------------|
| 归属 | 独立对象，可被多表共享 | 绑定在表列上 |
| 取值 | 显式 `NEXTVAL` 或 `IDENTITY` | 插入时自动填充 |
| 缓存 | `CACHE n`，崩溃可能跳号 | `auto_increment_increment` 等 |
| 回滚 | 取号后回滚**不会**归还 | 自增值同样不回退 |
| 多实例 | RAC 下可用 `ORDER`/`NOORDER` 控制 | 主从需配 `auto_increment_offset` |

> **注意**：序列取号后即使事务回滚，号也不会退回。这不是 bug，而是为了保证并发下不争用。业务不要假设主键连续。

# 4. 分页

Oracle 没有 MySQL 的 `LIMIT`，历史上用 `ROWNUM`，12c 之后有了标准的 `OFFSET ... FETCH`。

## 4.1 12c 之前的 ROWNUM 写法

`ROWNUM` 是**结果集生成时**分配的伪列，从 1 开始，只有满足条件的行才会继续分配下一个号。因此 `WHERE ROWNUM <= 10` 能取前 10 行，但 `WHERE ROWNUM > 10` 永远为空。

```sql
-- 错误示范：想取第 11-20 行，结果永远为空
SELECT * FROM orders WHERE ROWNUM > 10 AND ROWNUM <= 20;

-- 正确做法：先子查询分配行号，再在外层过滤
SELECT *
FROM (
    SELECT o.*, ROWNUM rn
    FROM (SELECT * FROM orders ORDER BY created_at DESC) o
    WHERE ROWNUM <= 20
)
WHERE rn > 10;
```

## 4.2 12c 之后的 OFFSET FETCH

```sql
-- 取第 11-20 行，按创建时间倒序
SELECT *
FROM orders
ORDER BY created_at DESC
OFFSET 10 ROWS FETCH NEXT 10 ROWS ONLY;
```

| 写法 | 版本 | 优点 | 缺点 |
|------|------|------|------|
| `ROWNUM` 嵌套 | 所有版本 | 兼容老库 | 语句冗长，易写错 |
| `OFFSET ... FETCH` | 12c+ | 语法清晰、标准 | 深分页性能同样差 |
| `ROW_NUMBER()` 窗口 | 所有版本 | 灵活，可分组取前 N | 需要排序，开销大 |

> **行业实践**：深分页（`OFFSET 100000`）在 Oracle 里同样低效，因为数据库仍要扫描并丢弃前 10 万行。更好的做法是**基于游标的分页**（记住上一页最后一条的 `id` 或 `created_at`，用 `WHERE id > :last_id` 继续取），把复杂度从 O(offset) 降到 O(1) 索引定位。

# 5. NULL 语义

NULL 表示"未知"，不是 0，也不是空字符串。Oracle 的 NULL 有几个必须记住的规则。

## 5.1 三值逻辑

任何与 NULL 的比较结果都是 `UNKNOWN`，`WHERE` 只保留结果为 `TRUE` 的行，所以 `UNKNOWN` 等于被过滤。

```sql
-- 下面两条都不会返回 remark 为 NULL 的行
SELECT * FROM orders WHERE remark = 'x';
SELECT * FROM orders WHERE remark != 'x';

-- 正确做法：用 IS NULL / IS NOT NULL
SELECT * FROM orders WHERE remark IS NULL;
```

## 5.2 NULL 与空字符串

**Oracle 把空字符串 `''` 当作 NULL 处理**，这是它与 MySQL、PostgreSQL 最大的语义差异之一。

```sql
-- 在 Oracle 中返回 1，因为 '' 就是 NULL
SELECT COUNT(*) FROM dual WHERE '' IS NULL;

-- 插入空字符串，实际存的是 NULL
INSERT INTO t (name) VALUES ('');
SELECT COUNT(*) FROM t WHERE name IS NULL;  -- 能查到
```

> **注意**：从 MySQL 迁移到 Oracle 时，`name = ''` 这种判断会失效（永远不成立），必须改成 `name IS NULL`。反过来，`NOT NULL` 约束下插入 `''` 在 Oracle 会直接报错，而 MySQL 允许空字符串。

## 5.3 聚合与 NULL

`COUNT(*)` 统计行数，`COUNT(column)` 只统计该列非 NULL 的行。`SUM`、`AVG`、`MAX`、`MIN` 都**忽略 NULL**，这会让平均值与直觉不符。

```sql
-- 假设 3 行：10、20、NULL
SELECT COUNT(*)        FROM t;  -- 3
SELECT COUNT(amount)   FROM t;  -- 2
SELECT AVG(amount)     FROM t;  -- 15，不是 10
SELECT SUM(amount)     FROM t;  -- 30
```

> **设计考量**：业务上"未知"和"零"必须区分。金额字段若允许 NULL，报表求和会漏掉未知行；若默认填 0，又混淆了"没填"和"填了 0"。常见做法是用 `NVL(amount, 0)` 在展示层统一，但统计口径要在需求阶段就定义清楚。

# 6. 常用函数与示例

```sql
-- 字符串、数值、日期
SELECT UPPER('abc'), SUBSTR('abcdef', 2, 3), INSTR('abcabc', 'b') FROM dual;
SELECT ROUND(3.14159, 2), TRUNC(3.14159, 2), MOD(10, 3) FROM dual;
SELECT SYSDATE, SYSDATE + 1, SYSDATE - 1/24 FROM dual;  -- 现在、明天、一小时前
SELECT TO_CHAR(SYSDATE, 'YYYY-MM-DD HH24:MI:SS') FROM dual;
-- 空值与条件
SELECT NVL(remark, '无'), NVL2(remark, '有', '无') FROM t;
SELECT CASE WHEN amount > 100 THEN '大额' ELSE '小额' END FROM orders;
SELECT DECODE(status, 'A', '启用', 'D', '停用', '未知') FROM t;
```

# 7. 常见错误

| 现象 | 根因 | 处理 |
|------|------|------|
| `ORA-00942: 表或视图不存在` | schema 前缀错、对象名大小写、权限不足 | 确认当前用户与对象全名 |
| `ORA-01722: 无效数字` | 字符串与数字隐式转换失败 | 显式 `TO_NUMBER`，避免隐式转换 |
| `ORA-01861: 文字与格式字符串不匹配` | 日期格式与 `NLS_DATE_FORMAT` 不一致 | 用 `TO_DATE` 显式指定格式 |
| `ORA-01438: 值大于此列允许的精度` | `NUMBER(p, s)` 溢出 | 扩大精度或校验入参 |
| `ORA-12899: 值太大` | `VARCHAR2` 字节数超限 | 改 `CHAR` 语义或扩长 |
| 分页结果为空 | `ROWNUM > n` 用法错误 | 用子查询先分配行号 |
| `''` 判断失效 | Oracle 把空串当 NULL | 改用 `IS NULL` |

## 7.1 隐式转换是性能杀手

如果 `id` 是 `NUMBER`，而 SQL 写成 `WHERE id = '100'`，Oracle 会把 `id` 隐式转成字符串再比较，导致**索引失效**、走全表扫描。正确做法是让参数类型与列类型一致，写成 `WHERE id = 100`。

# 9. 小结

| 主题 | 核心结论 |
|------|---------|
| schema | Oracle 用户即 schema，跨 schema 必须写全名 |
| 字符类型 | `VARCHAR2(n)` 按字节，中文场景用 `VARCHAR2(n CHAR)` |
| 数值类型 | 金额用 `NUMBER(p, s)`，不要用二进制浮点 |
| 日期类型 | `DATE` 到秒，`TIMESTAMP` 到小数秒，比较要显式转换 |
| 序列 | 独立对象，取号不回滚，12c 起可用 `IDENTITY` |
| 分页 | 老版本用 `ROWNUM` 子查询，12c+ 用 `OFFSET FETCH` |
| NULL | 空串即 NULL，比较用 `IS NULL`，聚合忽略 NULL |
