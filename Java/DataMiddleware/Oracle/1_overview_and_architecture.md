# 1. Oracle 的定位

Oracle Database 是甲骨文公司的商业关系型数据库，长期占据金融、电信、政务、能源等核心系统的位置。它和 MySQL、PostgreSQL 最大的不同在于**商业授权模式**：核心功能按处理器核数或用户数收费，很多高级能力（RAC、Data Guard、分区、高级压缩、诊断包）需要额外购买选件。这决定了 Oracle 的学习重点不只是"SQL 怎么写"，还包括"这套体系为什么这样设计"以及"哪些能力是付费的"。

从技术特征看，Oracle 的标签是**实例与数据库分离、共享磁盘架构、成熟的优化器与执行计划管理、以及一整套运维工具链**。它不像 MySQL 那样按存储引擎分叉，也不像 PostgreSQL 那样把扩展交给社区，而是把事务、锁、备份、高可用都收进一个统一的体系里，代价是概念多、参数多、安装重。

## 1.1 版本与生态

Oracle 的版本号采用 `主版本.发布版本` 的形式，写作时间点（2026 年）生产环境最常见的是 **19c** 和 **21c**。带 `c` 表示 Cloud，从 12c 开始统一用这个后缀。长期支持版本（Long Term Release）是 19c，官方支持周期很长；21c 是创新版本（Innovation Release），新特性多但支持周期短，通常用于评估而不是长期承载核心业务。

| 版本 | 发布时间 | 定位 | 值得关注的变化 |
|------|---------|------|---------------|
| 11g | 2007 | 上一代主力 | 自动内存管理、结果缓存、Data Guard 增强 |
| 12c | 2013 | 多租户起点 | 可插拔数据库（PDB/CDB）、In-Memory 选件、自动分区 |
| 18c | 2018 | 小版本 | 自治数据库能力下放、PDB 快照克隆 |
| **19c** | 2019 | **长期支持** | 自动索引、Active Data Guard 增强、JSON 增强、PDB 最多 3 个免费 |
| 21c | 2021 | 创新版本 | 原生 JSON 类型、区块链表、In-Memory 增强、PDB 级 Data Guard |
| 23ai | 2024 | 新一代 | AI Vector Search、JSON 关系二元性、True Cache |

> **行业实践**：国内核心系统仍以 11g 和 19c 为主，新项目若必须选 Oracle，直接上 19c；21c 及以后版本更适合做技术验证，因为创新版本的支持窗口短，升级路径也更陡。

## 1.2 实例与数据库

Oracle 最容易让初学者困惑的概念是**实例（Instance）与数据库（Database）是分开的**。

- **实例**：内存结构（SGA、PGA）加后台进程的集合，是"运行中的数据库软件"。
- **数据库**：磁盘上的一组物理文件（数据文件、控制文件、重做日志文件），是"数据本身"。

一个实例在同一时刻只能挂载（mount）并打开（open）一个数据库；反过来，一个数据库在普通单机架构下也只被一个实例打开。RAC（Real Application Clusters）打破了后一条限制：多个实例通过共享存储同时打开同一个数据库。这正是 Oracle 与 MySQL 主从架构在思路上最根本的差异——RAC 是**多实例共享一份数据**，MySQL 主从是**多份数据各自复制**。

```text
        ┌──────────────────────────────┐
        │           实例 Instance       │
        │  ┌────────┐   ┌────────────┐ │
        │  │  SGA   │   │ 后台进程    │ │
        │  └────────┘   └────────────┘ │
        └──────────────┬───────────────┘
                       │ 打开 / 挂载
                       ▼
        ┌──────────────────────────────┐
        │          数据库 Database      │
        │  数据文件 + 控制文件 + 重做日志 │
        └──────────────────────────────┘
```

数据库的启动分三个阶段，理解这三步就理解了实例与数据库的关系：

| 阶段 | 命令 | 做了什么 |
|------|------|---------|
| NOMOUNT | `STARTUP NOMOUNT` | 只启动实例，读参数文件、分配 SGA、启动后台进程 |
| MOUNT | `STARTUP MOUNT` | 根据参数找到控制文件并读取，知道数据文件和日志在哪 |
| OPEN | `STARTUP` | 打开数据文件和重做日志，接受用户连接 |

> **注意**：`SHUTDOWN IMMEDIATE` 是生产环境最常用的关闭方式，它回滚未提交事务、断开连接、写检查点后关闭；`SHUTDOWN ABORT` 相当于拔电源，下次启动需要做实例恢复，除非万不得已不要用。

## 1.3 SGA：共享全局区

**SGA（System Global Area）** 是实例启动时分配的一块共享内存，所有服务器进程和后台进程都能访问。它由几个池组成，每个池服务不同的目的。

```text
┌────────────────────────── SGA ──────────────────────────┐
│  ┌──────────────┐  ┌──────────────┐  ┌───────────────┐  │
│  │ Buffer Cache │  │ Shared Pool  │  │ Redo Log Buffer│  │
│  │   数据块缓存  │  │ SQL/字典缓存  │  │   重做日志缓冲  │  │
│  └──────────────┘  └──────────────┘  └───────────────┘  │
│  ┌──────────────┐  ┌──────────────┐  ┌───────────────┐  │
│  │  Large Pool  │  │  Java Pool   │  │ Streams Pool  │  │
│  └──────────────┘  └──────────────┘  └───────────────┘  │
└──────────────────────────────────────────────────────────┘
```

### 1.3.1 Buffer Cache

Buffer Cache 缓存从数据文件读入的**数据块**（默认 8KB，由 `DB_BLOCK_SIZE` 决定，建库后不可改）。查询时服务器进程先在这里找块，命中就直接读内存，未命中才触发物理读。它是 SGA 中通常最大的一块。

Buffer Cache 内部用**LRU 链表**管理，并分为冷端和热端，还引入了**接触计数（touch count）**来防止全表扫描把热数据挤出去。Oracle 还提供多个缓冲池：`KEEP` 池用于钉住小热表，`RECYCLE` 池用于大表扫描，`DEFAULT` 池是默认区域。这种细粒度控制在 MySQL 的 Buffer Pool 里要靠 LRU 调参近似实现。

```sql
-- 查看 Buffer Cache 命中率，OLTP 系统通常应在 95% 以上
SELECT name, value
FROM v$sysstat
WHERE name IN ('session logical reads', 'physical reads');

-- 按缓冲池查看块数量与大小
SELECT pool, block_size, buffers, buffers * block_size / 1024 / 1024 AS mb
FROM v$buffer_pool;
```

### 1.3.2 Shared Pool

Shared Pool 存放**解析后的 SQL、执行计划、数据字典缓存、PL/SQL 代码**。它最核心的组件是 **Library Cache**（共享游标）和 **Row Cache**（数据字典行缓存）。

一条 SQL 执行前必须经过**硬解析**：语法检查、语义检查、权限检查、生成执行计划。硬解析要消耗大量 CPU 和 Shared Pool 内存。如果应用拼装 SQL 时把参数直接拼进字符串，每条 SQL 文本都不同，就会产生大量硬解析，Shared Pool 被撑爆，进而引发 `ORA-04031`。正确做法是用**绑定变量**。

```sql
-- 错误示范：字面量直接拼进 SQL，每换一个 id 就是一条新 SQL
SELECT * FROM orders WHERE id = 1001;

-- 正确做法：使用绑定变量，执行计划可复用
SELECT * FROM orders WHERE id = :id;
```

> **行业实践**：Java 应用应统一使用 `PreparedStatement`，MyBatis 用 `#{}` 而不是 `${}`（后者是字符串替换）。这不只是为了防 SQL 注入，也是为了复用游标、减少硬解析。

### 1.3.3 Redo Log Buffer

Redo Log Buffer 是**重做日志的写缓冲区**。任何 DML 产生的变更都会先以重做记录（redo entry）的形式写进这里，再由 LGWR 后台进程刷到磁盘上的重做日志文件。它通常不大（几十到几百 MB），但它是 Oracle 持久化的起点。

### 1.3.4 Large Pool、Java Pool 与 Streams Pool

Large Pool 用于大块内存分配，典型场景是 RMAN 备份、并行查询、共享服务器模式的会话内存。Java Pool 供 JVM 在数据库内运行使用（Java 存储过程）。Streams Pool 用于高级复制和 GoldenGate 的部分场景。普通 OLTP 系统里这三块通常很小，甚至可以交给自动内存管理去分配。

## 1.4 PGA：程序全局区

与 SGA 相对，**PGA（Program Global Area）是每个服务器进程私有的内存**，不和别人共享。它主要包含：

- **排序区（Sort Area）**：`ORDER BY`、`GROUP BY`、`DISTINCT`、连接排序都在这里做；不够就落临时表空间。
- **哈希区（Hash Area）**：哈希连接、哈希聚合使用。
- **会话变量、游标状态、绑定变量值**。

PGA 的关键参数是 `PGA_AGGREGATE_TARGET`（总目标）和 `PGA_AGGREGATE_LIMIT`（硬上限）。注意它是"所有会话合计"的目标，不是单会话上限。一条 SQL 有多个排序节点时，会同时占用多份排序区，所以"连接数 × 单会话 PGA"这种算法经常会低估峰值。

```sql
-- 查看 PGA 使用与建议值
SELECT name, value, unit FROM v$pgastat;

-- 查看当前各会话 PGA 占用
SELECT sid, serial#, program, pga_used_mem / 1024 / 1024 AS used_mb,
       pga_alloc_mem / 1024 / 1024 AS alloc_mb
FROM v$process
ORDER BY pga_alloc_mem DESC
FETCH FIRST 10 ROWS ONLY;
```

> **注意**：`PGA_AGGREGATE_TARGET` 设得过小，大量排序会落盘，临时表空间迅速膨胀；设得过大，多个并发会话可能把物理内存打满，触发操作系统 OOM。经验值是物理内存的 20% 左右，再结合 `v$pgastat` 的 `over allocation count` 观察。

## 1.5 后台进程

实例启动时会拉起一组后台进程，它们是 Oracle 能持续运行的基础。下面几个必须认识。

| 进程 | 全称 | 职责 |
|------|------|------|
| DBWn | Database Writer | 把 Buffer Cache 中的脏块异步写回数据文件 |
| LGWR | Log Writer | 把 Redo Log Buffer 刷入重做日志文件，提交时同步写 |
| CKPT | Checkpoint | 更新控制文件和数据文件头，记录检查点位置 |
| SMON | System Monitor | 实例恢复、清理临时段、合并空闲空间 |
| PMON | Process Monitor | 清理异常终止的进程、释放资源、注册监听 |
| ARCn | Archiver | 归档模式下把写满的重做日志复制到归档目录 |
| MMON | Manageability Monitor | 收集 AWR 快照、触发自动调优任务 |
| MMNL | Manageability Monitor Lite | 轻量级统计信息落盘 |

### 1.5.1 DBWn 与 LGWR 的分工

这是 Oracle 持久化最重要的两条线。**LGWR 负责"日志先落盘"，DBWn 负责"数据块后落盘"**。事务提交时，Oracle 不要求数据块已经写回磁盘，只要求该事务的重做记录已经落盘（**WAL 原则，Write-Ahead Logging**），所以提交很快。崩溃后，用重做日志重放"已提交但数据块未写"的变更，再用回滚段（undo）撤销"未提交但数据块已写"的变更，这就是**实例恢复**。

```text
事务提交
   │
   ▼
Redo Log Buffer ──LGWR──▶ 在线重做日志文件（必须落盘才算提交成功）
                                │
                                │ 之后某个时刻
                                ▼
Buffer Cache 脏块 ──DBWn──▶ 数据文件（可以延迟）
```

### 1.5.2 CKPT 与检查点

检查点（Checkpoint）记录一个"到这个时间点为止，Buffer Cache 里的脏块都已经或即将写回"的位置。它的作用是**缩短崩溃恢复的时间**：恢复时只需从最后一个检查点开始重放重做日志，而不是从头重放。检查点越频繁，恢复越快，但 DBWn 的写压力越大。

### 1.5.3 SMON 与 PMON

SMON 在实例启动时执行**实例恢复**，并在运行期清理临时段、合并表空间中的空闲 extent。PMON 负责监控服务器进程，进程异常死亡时回滚其未提交事务、释放锁和 PGA，并把服务信息从监听器注销。理解这两个进程，就能理解为什么 Oracle 崩溃后重启往往能"自愈"。

### 1.5.4 ARCn 与归档

只有数据库处于 **ARCHIVELOG 模式**时 ARCn 才会工作。它把写满的在线重做日志文件复制到归档目录，形成连续的归档日志链。归档日志是 RMAN 增量备份和 **PITR（时间点恢复）** 的基础，生产库几乎都要求开启归档。

```sql
-- 查看归档模式与归档目的地
ARCHIVE LOG LIST;
SHOW PARAMETER log_archive_dest_1;

-- 查看归档进程
SELECT * FROM v$archive_processes;
```

## 1.6 物理存储结构

从磁盘角度看，Oracle 数据库由三类文件组成。

| 文件 | 作用 | 丢失后果 |
|------|------|---------|
| 数据文件（Data File） | 存放表、索引、undo 等实际数据 | 丢失则数据不完整，需从备份恢复 |
| 控制文件（Control File） | 记录数据库结构、数据文件与日志文件位置、SCN | 丢失则实例无法 mount，必须有多路复用 |
| 在线重做日志文件（Online Redo Log） | 记录所有变更，用于实例恢复 | 丢失当前日志可能丢数据，必须多组多成员 |

此外还有**参数文件（SPFILE/PFILE）**、**密码文件**、**告警日志（alert log）**、**跟踪文件（trace）**、**归档日志**。控制文件和重做日志必须做**多路复用（multiplexing）**，即同一份内容写到不同磁盘的多个成员上，避免单点损坏。

## 1.7 逻辑存储结构

Oracle 在物理文件之上又抽象了一层逻辑结构，从大到小是：**表空间（Tablespace）→ 段（Segment）→ 区（Extent）→ 块（Block）**。

```text
表空间 USERS
  └── 段：表 ORDERS 的段
        ├── 区 1（8 个连续块）
        ├── 区 2（8 个连续块）
        └── 区 3（8 个连续块）
              └── 块（默认 8KB，最小 I/O 单位）
```

- **表空间**：逻辑存储容器，一个表空间对应一个或多个数据文件。常见的有 `SYSTEM`、`SYSAUX`、`UNDO`、`TEMP` 和用户表空间。
- **段**：一个数据库对象占用的空间，比如一张表、一个索引、一个 undo 段。
- **区**：段内连续分配的一组块，是空间分配的单位。
- **块**：Oracle 读写的最小单位，默认 8KB。

> **设计考量**：把不同业务放到不同表空间，好处是备份、恢复、配额、I/O 分布都能独立控制。例如把大表和历史数据放独立表空间，可以单独做只读或按表空间恢复。这是 Oracle 相对 MySQL"库即目录"更细的一层管理能力。

## 1.8 一条 SQL 的生命周期

一条 `SELECT` 在 Oracle 中的路径大致如下：

```text
客户端
  │ 1. 通过监听器建立连接，派生服务器进程
  ▼
服务器进程
  │ 2. 在 Shared Pool 的 Library Cache 中查找是否有相同 SQL 文本
  │    ├─ 命中 → 软解析，复用执行计划
  │    └─ 未命中 → 硬解析：语法/语义/权限检查 → 优化器生成计划
  ▼
优化器（CBO，基于代价）
  │ 3. 根据统计信息估算各访问路径代价，选执行计划
  ▼
执行器
  │ 4. 读：先查 Buffer Cache，未命中再从数据文件读入
  │    写：修改 Buffer Cache 中的块 + 生成 redo
  ▼
返回结果（按行或批量 fetch）
```

几个容易被忽略的点：

- **软解析与硬解析的区别**决定了高并发下的 CPU 开销。绑定变量是减少硬解析最直接的手段。
- **优化器是 CBO（Cost-Based Optimizer）**，它的判断依赖统计信息。统计信息过期，执行计划就可能突然变差，这是 Oracle 生产事故的常见根因。
- **结果集是逐行 fetch 的**，JDBC 默认 `fetchSize=10`，大结果集会因此产生大量往返，需要显式调大。

## 1.9 与 MySQL、PostgreSQL 对比

| 维度 | Oracle | MySQL（InnoDB） | PostgreSQL |
|------|--------|----------------|------------|
| 实例与数据库 | 分离，一个实例打开一个库（RAC 例外） | 实例即库，一个实例多个库 | 一个实例多个库 |
| 进程模型 | 多进程 + 共享内存 | 多线程 | 多进程 |
| 默认隔离级别 | READ COMMITTED | REPEATABLE READ | READ COMMITTED |
| MVCC 实现 | undo 段 + SCN | undo log + 版本链 | 堆表多版本 + VACUUM |
| 索引组织 | 堆表，主键是普通唯一索引 | 主键即聚簇索引 | 堆表，无聚簇索引 |
| Schema | 用户即 schema，表和用户绑定 | Schema 等同 Database | 数据库下的命名空间 |
| 高可用 | RAC + Data Guard | 主从复制 + MGR | 流复制 + 逻辑复制 |
| 分区 | 原生分区（需选件） | 原生分区 | 声明式分区 |
| 备份 | RMAN | mysqldump / XtraBackup | pg_dump / pg_basebackup |
| 授权 | 商业授权，按核收费 | 开源（GPL）+ 商业版 | 开源（类 BSD） |

> **行业实践**：Oracle 的优势不在"单机跑得快"，而在**成熟的优化器、完整的高可用方案、以及金融级的事务与恢复能力**。选型时不要只比 TPC-C 数字，要看团队是否具备运维 RAC、Data Guard、RMAN 的能力，以及授权成本能否接受。

## 1.10 常见误区

**误区一：把"数据库"和"实例"混为一谈。** 重启实例不等于重建数据库；数据文件还在，实例起来后照样能打开。反过来，删了实例参数文件也不一定丢数据，但控制文件丢了就很麻烦。

**误区二：认为提交（COMMIT）等于数据已经写进数据文件。** 提交只保证 redo 落盘，数据块可能还在内存里。这正是 Oracle 能快速提交的原因。

**误区三：看到 Buffer Cache 命中率低就盲目加大 SGA。** 全表扫描多的系统命中率天然低，加内存未必有用。要先看是物理读多还是逻辑读多，再看 SQL 本身。

**误区四：忽视统计信息。** Oracle 的执行计划高度依赖统计信息，长期不收集会让优化器"瞎猜"，表现为同一条 SQL 时快时慢。

## 1.11 练习

**练习一**：启动一个 Oracle 实例（可用 Docker 镜像或本地安装），依次执行 `STARTUP NOMOUNT`、`ALTER DATABASE MOUNT`、`ALTER DATABASE OPEN`，每步观察 `V$INSTANCE` 的 `STATUS` 字段变化，并解释每一步做了什么。

**练习二**：查询 `V$SGA` 与 `V$PGASTAT`，算出当前 SGA 各组件占比，并说明在 16GB 内存的 OLTP 服务器上，`SGA_TARGET` 与 `PGA_AGGREGATE_TARGET` 大致应该如何分配。

**练习三**：写两条 SQL，一条用字面量、一条用绑定变量，在 `V$SQL` 中分别统计它们的执行次数与硬解析次数，说明绑定变量为什么能降低 CPU 消耗。

# 2. 小结

| 主题 | 核心结论 |
|------|---------|
| 定位 | 商业关系型数据库，核心优势是优化器、高可用与恢复体系 |
| 实例与数据库 | 实例是内存加进程，数据库是磁盘文件，二者分离 |
| SGA | Buffer Cache、Shared Pool、Redo Log Buffer 是三大核心池 |
| PGA | 每进程私有，排序与哈希区是内存峰值的主要来源 |
