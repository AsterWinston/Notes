# 1.基础概念

## 1.1什么是事务？ACID 是什么？

事务是一组不可分割的数据库操作，要么全部成功（COMMIT），要么全部失败（ROLLBACK）。

| 特性 | 说明 | MySQL 实现 |
|------|------|-----------|
| 原子性 | 事务是不可分割的最小单元 | undo log |
| 一致性 | 事务前后数据保持一致状态 | redo + undo + 锁 |
| 隔离性 | 并发事务之间互不干扰 | MVCC + 锁 |
| 持久性 | 事务提交后数据永不丢失 | redo log |

## 1.2并发事务带来哪些问题？

| 问题 | 描述 | 示例 |
|------|------|------|
| 脏读 | 读到其他事务未提交的数据 | B 修改了数据未提交，A 读到了修改值 |
| 不可重复读 | 同一事务内两次读到同一条数据不同 | A 第一次读 a=100，B 修改 a=200 提交，A 再读 a=200 |
| 幻读 | 同一查询条件两次返回行数不同 | A 第一次查 dept=1 有 5 人，B 插入 dept=1 新员工提交，A 再查有 6 人 |

## 1.3事务隔离级别

| 级别 | 脏读 | 不可重复读 | 幻读 |
|------|------|-----------|------|
| READ UNCOMMITTED | ✓ | ✓ | ✓ |
| READ COMMITTED | ✗ | ✓ | ✓ |
| REPEATABLE READ（默认） | ✗ | ✗ | 部分 |
| SERIALIZABLE | ✗ | ✗ | ✗ |

# 2.索引

## 2.1索引的底层数据结构是什么？

B+Tree。为什么不是其他结构：
- 二叉树 → 顺序插入退化为链表
- 红黑树 → 树高，IO 次数多
- Hash → 不支持范围查询和排序

## 2.2聚簇索引和二级索引的区别？

| 类型 | 叶子节点内容 | 数量 |
|------|------------|------|
| 聚簇索引 | 完整行数据 | 有且仅有一个 |
| 二级索引 | 主键值（需回表） | 可有多个 |

## 2.3什么是回表？如何避免？

通过二级索引查到主键值后，再到聚簇索引查找完整行的过程叫回表。

**避免方法**：覆盖索引——SELECT 的列都在索引中，无需回表。
```sql
-- idx(name, age) → SELECT name, age 即为覆盖索引
```

## 2.4什么是最左前缀法则？

联合索引中，查询必须从索引的最左列开始，且不能跳过中间列。跳过的列之后索引失效。
```sql
-- idx(a, b, c)
WHERE a=1 AND b=2 AND c=3  -- 全索引
WHERE a=1 AND b=2           -- a, b 索引
WHERE a=1                   -- 仅 a 索引
WHERE b=2 AND c=3           -- 索引失效（没有 a）
```

## 2.5索引失效的常见场景？（高频）

1. 违反最左前缀法则
2. 索引列使用函数/运算：`WHERE YEAR(create_time) = 2026`
3. 隐式类型转换：`WHERE phone = 13800138000`（phone 是 VARCHAR）
4. LIKE 前置模糊：`WHERE name LIKE '%三'`
5. OR 两边不全为索引列
6. 不等于 `!=` / `NOT IN`（部分情况）
7. 优化器评估全表扫描更快

# 3.存储引擎

## 3.1InnoDB vs MyISAM 区别？

| 特性 | InnoDB | MyISAM |
|------|--------|--------|
| 事务 | ✓ | ✗ |
| 行锁 | ✓ | ✗（表锁） |
| 外键 | ✓ | ✗ |
| MVCC | ✓ | ✗ |
| 崩溃恢复 | redo log | 修复表 |
| 存储文件 | .ibd | .MYD + .MYI |
| 默认 | 5.5+ 默认 | 5.5 之前默认 |

## 3.2InnoDB 四大特性？

1. **Insert Buffer / Change Buffer**：缓存非唯一二级索引的变更
2. **Double Write**：防止部分页写入导致数据损坏
3. **Adaptive Hash Index**：自动为热点数据建立 Hash 索引
4. **Redo Log**：崩溃恢复，保证持久性

# 4.锁

## 4.1MySQL 有哪些锁？

| 粒度 | 锁类型 | 特点 |
|------|--------|------|
| 全局锁 | FLUSH TABLES WITH READ LOCK | 全库只读 |
| 表锁 | 读锁/写锁、MDL、意向锁 | InnoDB 和 MyISAM 都支持 |
| 行锁 | Record Lock（S/X）、Gap Lock、Next-Key Lock | InnoDB 专有 |

## 4.2什么是间隙锁？为什么需要？

间隙锁锁定索引记录之间的间隙，防止其他事务在间隙中 INSERT，从而防止幻读。仅在 RR 隔离级别下生效。

## 4.3乐观锁和悲观锁的区别？

| 类型 | 实现 | 优点 | 缺点 | 场景 |
|------|------|------|------|------|
| 悲观锁 | `SELECT ... FOR UPDATE` | 强一致 | 并发低 | 写冲突频繁 |
| 乐观锁 | 版本号 `UPDATE ... WHERE version=?` | 高并发 | 重试开销 | 读多写少 |

## 4.4如何排查死锁？

```sql
SHOW ENGINE INNODB STATUS\G;  -- 查看 LATEST DETECTED DEADLOCK
```

减少死锁方法：相同顺序访问资源、缩短事务、使用 RC 隔离级别减少间隙锁。

# 5.MVCC

## 5.1什么是 MVCC？如何实现？

多版本并发控制，每行数据维护多个版本，使读不阻塞写、写不阻塞读。

**实现依赖**：
1. 三个隐藏字段：DB_TRX_ID、DB_ROLL_PTR、DB_ROW_ID
2. undo log 版本链
3. ReadView（读视图）：决定哪些版本对当前事务可见

## 5.2快照读 vs 当前读？

| 类型 | 读取内容 | 加锁 | 示例 |
|------|---------|------|------|
| 快照读 | 历史版本 | 否 | 普通 `SELECT` |
| 当前读 | 最新版本 | 是 | `SELECT ... FOR UPDATE`、UPDATE、DELETE |

## 5.3RC 和 RR 的 MVCC 有什么区别？

- **RC**：每次 SELECT 生成新的 ReadView → 能读到其他事务已提交的修改
- **RR**：只在第一次 SELECT 生成 ReadView，后续复用 → 保证可重复读

# 6.日志

## 6.1redo log、undo log、binlog 的区别？

| 日志 | 层面 | 作用 | 存储 |
|------|------|------|------|
| redo log | InnoDB 引擎 | 崩溃恢复（持久性） | ib_logfile |
| undo log | InnoDB 引擎 | 事务回滚 + MVCC | undo 表空间 |
| binlog | Server 层 | 主从复制、数据恢复 | binlog 文件 |

## 6.2WAL 机制是什么？

Write-Ahead Log：先写日志（redo log），再写磁盘（数据页）。崩溃恢复时通过 redo log 重放已提交但未刷盘的事务。

# 7.主从复制

## 7.1主从复制原理？

```
主库事务提交 → 写 binlog → 从库 I/O 线程拉取并写 relay log → 从库 SQL 线程重放
```

## 7.2主从延迟的原因和解决方案？

**原因**：从库性能差、大事务、单线程重放、网络延迟。

**方案**：
- 并行复制（5.7 LOGICAL_CLOCK、8.0 WRITESET）
- 提升从库硬件
- 拆库分散负载
- 半同步复制

# 8.优化

## 8.1如何优化慢 SQL？

1. 慢查询日志找出慢 SQL
2. EXPLAIN 分析执行计划（关注 type、key、Extra）
3. 检查是否命中索引、是否有 filesort、temporary
4. 加索引、改写 SQL、优化表结构
5. 验证效果

## 8.2如何优化大数据量分页？

```sql
-- 游标分页
SELECT * FROM t WHERE id > last_id ORDER BY id LIMIT 10;

-- 子查询 + 覆盖索引
SELECT * FROM t WHERE id >= (SELECT id FROM t LIMIT 1000000, 1) LIMIT 10;
```

## 8.3如何优化 COUNT(*)？

- EXPLAIN 的 rows 估算（近似值）
- 维护计数表或 Redis 计数器
- `SELECT TABLE_ROWS FROM information_schema.TABLES`（估算）

# 9.架构

## 9.1分库分表策略？

- 垂直拆分（按业务）：用户库、订单库分开
- 水平拆分（按行）：取模、范围、一致性哈希
- 分片键选择：高区分度、业务相关、避免跨分片

## 9.2数据迁移方案？

停止迁移（停机）vs 双写迁移（平滑）：先全量同步 → 开启双写 → 校验一致性 → 切读 → 停旧写。

## 9.3读写分离如何解决主从延迟？

- 刚写完的关键数据强制读主库
- 半同步复制减少延迟窗口
- 缓存补偿

# 10.其他

## 10.1CHAR vs VARCHAR？

- CHAR：定长，255 字符上限，适合固定长度字段（MD5、手机号）
- VARCHAR：变长，省空间，适合变长字段（姓名、邮箱）

## 10.2DATETIME vs TIMESTAMP？

- DATETIME：范围 1000~9999，无时区，无 2038 问题 → 推荐
- TIMESTAMP：范围 1970~2038，时区感知，有 2038 问题

## 10.3SQL 注入如何防范？

- PreparedStatement 参数化查询（核心方案）
- `#{}` 替代 `${}`（MyBatis）
- 输入白名单校验
- 最小权限原则

## 10.4MySQL 8.0 有哪些新特性？

窗口函数、CTE（含递归）、原子 DDL、降序索引、不可见索引、函数索引、角色管理、检查约束、直方图、双密码、克隆插件、Skip Scan、哈希 JOIN。

## 10.5DB主键如何选择？

| 策略 | 适用场景 |
|------|---------|
| 自增 ID（AUTO_INCREMENT） | 单机 MySQL |
| 雪花算法（Snowflake） | 分布式系统 |
| UUID（转 BINARY(16)） | 需要无中心 ID 生成 |
| 数据库号段 | 需要批量获取 ID 的高性能系统 |

> 自增 ID 性能最好（有序 → 无页分裂），分布式场景用雪花算法（趋势递增 + 全局唯一）。

## 10.6线上误删数据怎么办？

1. **立即停止所有写入**！
2. 若有备份：全量恢复 + binlog 增量恢复到误删前一刻
3. 若删除不久且 binlog 完整：通过 `mysqlbinlog` 回放反向操作
4. 若 Redis 有缓存且数据来自数据库：先尝试从缓存恢复
5. 定期演练恢复流程（备份不是保险，能恢复才是保险）
