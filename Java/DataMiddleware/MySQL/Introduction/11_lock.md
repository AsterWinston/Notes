# 1. 锁概述

锁是计算机协调多个进程或线程**并发访问某一资源**的机制。在数据库中，除传统的计算资源（CPU、RAM、I/O）争用外，数据也是一种供多用户共享的资源。如何保证数据并发访问的**一致性**和**有效性**是所有数据库必须解决的问题。锁冲突也是影响数据库并发访问性能的重要因素。

MySQL 的锁按粒度从大到小分为：

| 锁粒度 | 锁定范围 | 并发度 | 适用引擎 |
|--------|---------|--------|---------|
| **全局锁** | 整个数据库实例 | 最低（读写都阻塞） | — |
| **表级锁** | 整张表 | 低 | MyISAM、Memory、InnoDB |
| **行级锁** | 单行记录 | 高 | InnoDB |

> InnoDB 支持行级锁，是其在 OLTP 场景下高并发能力的核心基础之一。

# 2. 全局锁

全局锁对整个数据库实例加锁，实例进入**只读**状态，所有 DDL 和 DML（除 SELECT）都会被阻塞。

## 2.1 加锁与解锁

```sql
-- 加全局读锁
FLUSH TABLES WITH READ LOCK;

-- 解锁
UNLOCK TABLES;
```

## 2.2 典型场景——全库逻辑备份

使用 `mysqldump` 备份时，为了保证数据一致性（所有表在同一时刻的快照），早期需要加全局锁：

```sql
-- 加锁后执行备份（业务基本停滞）
FLUSH TABLES WITH READ LOCK;
-- 在另一个终端：mysqldump -u root -p mydb > backup.sql
UNLOCK TABLES;
```

## 2.3 不加锁的一致性备份

InnoDB 引擎可通过 `--single-transaction` 参数实现不加锁的**一致性备份**（基于 MVCC 的快照读）：

```bash
mysqldump --single-transaction -u root -p mydb > backup.sql
```

**原理**：启动一个大事务，利用 MVCC 的 RR 隔离级别获取备份开始时的数据快照，全程不加锁。

> **注意**：`--single-transaction` 仅对 InnoDB 表有效。如果库中混有 MyISAM 表，这些表的备份数据仍可能不一致。这也是统一使用 InnoDB 的另一个理由。

## 2.4 全局锁的影响

- **主库上备份**：备份期间所有写入被阻塞，业务基本瘫痪
- **从库上备份**：备份期间从库无法执行主库同步的 binlog → 导致主从延迟
- **结论**：生产环境备份务必使用 `--single-transaction` 或物理备份工具（XtraBackup）

# 3. 表级锁

表级锁每次操作锁住整张表，锁定粒度大，锁冲突概率高，并发度低。

## 3.1 表锁

### 3.1.1 读锁 vs 写锁

| 锁类型 | 加锁方可读 | 加锁方可写 | 其他会话可读 | 其他会话可写 |
|--------|-----------|-----------|------------|------------|
| **读锁** | ✓ | ✗ | ✓ | ✗（阻塞） |
| **写锁** | ✓ | ✓ | ✗（阻塞） | ✗（阻塞） |

```sql
-- 加读锁
LOCK TABLES user READ;
-- 加写锁
LOCK TABLES user WRITE;

-- 释放所有表锁
UNLOCK TABLES;   -- 或断开客户端连接
```

> **读锁（共享锁）**：所有会话都能读，但都不能写。适合"维护窗口期间禁止写入"的场景。
> **写锁（排他锁）**：只有加锁的会话能读写，其他会话的读写都被阻塞。调试或紧急维护时偶尔使用。

## 3.2 元数据锁（MDL, Metadata Lock）

MDL 是系统自动控制的锁，用于保证表**元数据（结构）**与**数据**的一致性。当表上有活动事务时，不允许修改表结构（防止 DML 和 DDL 冲突）。

- **访问表时自动添加**，事务提交后释放
- **不需要显式操作**

### 3.2.1 锁类型与兼容性

| 锁类型 | 触发 SQL | 兼容 |
|--------|---------|------|
| **MDL_SHARED_READ** | SELECT | 与除 EXCLUSIVE 外的所有锁兼容 |
| **MDL_SHARED_WRITE** | INSERT、UPDATE、DELETE | 与除 EXCLUSIVE 外的所有锁兼容 |
| **MDL_EXCLUSIVE** | ALTER TABLE | 与其他所有锁互斥 |

**常见问题**：长事务持有 MDL_SHARED_READ 锁 → ALTER TABLE 请求 MDL_EXCLUSIVE 被阻塞 → 后续所有新请求的 MDL_SHARED_READ 也排队等待 → **整个表不可读写**！

```sql
-- 查看当前 MDL 锁
SELECT * FROM performance_schema.metadata_locks;
```

> **解决方法**：执行 DDL 前，先检查是否有长事务（`SHOW PROCESSLIST`），kill 长事务后再 DDL，或使用支持 Online DDL 的工具。

## 3.3 意向锁（Intention Lock）

**为什么需要意向锁？**

场景：事务 A 锁定了一行（行锁），事务 B 想对整张表加锁。如果没有意向锁，事务 B 需要遍历表中的**每一行**来判断是否有行锁存在——这在百万行表上不可接受。

**解决方案**：事务 A 加行锁前，先在表上加**意向锁**（表级锁），通知其他事务"这张表里有些行我锁住了"。事务 B 只需检查意向锁就能快速判断。

### 3.3.1 分类

| 类型 | 含义 | 触发 SQL | 与表锁互斥关系 |
|------|------|---------|---------------|
| **意向共享锁（IS）** | 事务准备在某些行加共享锁 | `SELECT ... LOCK IN SHARE MODE` | 与表写锁（X）互斥 |
| **意向排他锁（IX）** | 事务准备在某些行加排他锁 | `INSERT/UPDATE/DELETE/SELECT ... FOR UPDATE` | 与表读锁（S）和表写锁（X）都互斥 |

**意向锁之间不互斥**——IS 和 IX 可以共存（因为行级锁可以共存）。

```sql
-- 查看意向锁及行锁的加锁情况
SELECT
  object_schema, object_name, index_name,
  lock_type, lock_mode, lock_data
FROM performance_schema.data_locks;
```

# 4. 行级锁（InnoDB）

行级锁每次操作锁住对应的行数据，锁定粒度最小，锁冲突概率最低，并发度最高。**InnoDB 的行锁是加在索引上的**。

## 4.1 行锁（Record Lock）

锁定单条索引记录，防止其他事务对其进行 UPDATE 和 DELETE。

### 4.1.1 共享锁（S）和排他锁（X）

| 锁类型 | 允许读 | 允许写 | 其他事务可读 | 其他事务可写 | 触发语句 |
|--------|--------|--------|------------|------------|---------|
| **共享锁（S）** | ✓ | ✓ | ✓ | ✗（阻塞） | `SELECT ... LOCK IN SHARE MODE` |
| **排他锁（X）** | ✓ | ✓ | 快照读 ✓ / 当前读 ✗ | ✗（阻塞） | `INSERT/UPDATE/DELETE/SELECT ... FOR UPDATE` |

```sql
-- 加共享锁（MySQL 5.7 语法，8.0 中推荐用下面方式）
SELECT * FROM user WHERE id = 1 LOCK IN SHARE MODE;

-- 加共享锁（MySQL 8.0 推荐，更符合 SQL 标准）
SELECT * FROM user WHERE id = 1 FOR SHARE;

-- 加排他锁
SELECT * FROM user WHERE id = 1 FOR UPDATE;
```

> **普通 SELECT（不加 FOR UPDATE/FOR SHARE）是快照读**，不加任何锁（基于 MVCC），不阻塞也不被阻塞。

### 4.1.2 重要注意事项

1. **InnoDB 的行锁是加在索引上的**。如果不通过索引检索数据，InnoDB 将对表中所有记录加锁——**行锁升级为表锁**
2. 针对唯一索引的等值匹配，对已存在的记录加锁 → 优化为**行锁**
3. RC 和 RR 级别下都支持行锁

```sql
-- ✓ 通过索引过滤，精确行锁
SELECT * FROM user WHERE id = 1 FOR UPDATE;  -- 只锁 id=1 的行

-- ✗ 未通过索引过滤，升级为表锁
UPDATE user SET status = 0 WHERE name = '张三';  -- name 没有索引
```

## 4.2 间隙锁（Gap Lock）

锁定索引记录之间的**间隙**（不含该记录本身），防止其他事务在这个间隙中 INSERT 新记录，从而防止**幻读**。

**仅在 REPEATABLE READ 隔离级别下生效**。

```sql
-- 假设表中有 id = 5 和 id = 10 两行
-- 间隙锁会锁定 (5, 10) 这个区间
SELECT * FROM user WHERE id > 5 AND id < 10 FOR UPDATE;
-- 此时无法插入 id = 6, 7, 8, 9 的记录
-- 但可以插入 id = 4 或 id = 11 的记录
```

### 4.2.1 间隙锁的加锁规则

| 查询条件 | 加锁情况 |
|---------|---------|
| 唯一索引等值匹配存在的记录 | 不加间隙锁，只加行锁 |
| 唯一索引等值匹配**不存在**的记录 | 间隙锁（防止该间隙中插入相同值的记录） |
| 普通索引等值匹配 | 向右遍历时最后一个不满足条件的值退化为间隙锁 |
| 范围查询（唯一索引） | 访问到不满足条件的第一个值为止（包括其前间隙） |

### 4.2.2 间隙锁的共存

间隙锁的**唯一目的**是防止其他事务在间隙中插入新记录。因此**一个事务在某个间隙上加的间隙锁，不会阻止另一个事务在同一间隙上也加间隙锁**——间隙锁之间不互斥。

## 4.3 临键锁（Next-Key Lock）

**行锁（Record Lock） + 间隙锁（Gap Lock）的组合**。同时锁定一条记录和它前面的间隙。

**仅在 REPEATABLE READ 隔离级别下生效**。

```
假设数据为：5, 10, 15, 20
临键锁区间：(负无穷, 5], (5, 10], (10, 15], (15, 20], (20, 正无穷)
```

```sql
-- 对 id = 10 加临键锁（InnoDB 默认行为，RR 级别）
-- 锁定：id = 10 的行 + 间隙 (5, 10)
-- 即阻止 INSERT id = 6,7,8,9 + 阻止 UPDATE/DELETE id = 10
SELECT * FROM user WHERE id = 10 FOR UPDATE;
```

**InnoDB 默认在 RR 级别使用临键锁进行搜索和扫描，以防止幻读。**

## 4.4 插入意向锁（Insert Intention Lock）

插入意向锁是一种**特殊的间隙锁**，在 INSERT 操作时自动加锁。当一个事务想要在某个间隙插入数据时，会先加一个"插入意向锁"，表示"我想在这里插入，但被其他间隙锁阻塞了"。

**插入意向锁之间不互斥**——多个事务可以同时在**不同位置**插入数据到同一个间隙。

```
数据：5, 10
事务 A 锁定了间隙 (5, 10)（间隙锁）
事务 B 想插入 id = 6 → 加插入意向锁 → 被事务 A 阻塞
事务 C 想插入 id = 7 → 加插入意向锁 → 也被事务 A 阻塞
事务 A 提交后 → 事务 B 和 C 的插入意向锁都释放，数据插入完成
```

# 5. 锁的总结对比

| 锁分类 | 颗粒 | 适用引擎 | 适用隔离级别 | 互斥关系 |
|--------|------|---------|------------|---------|
| 全局锁 | 实例 | 所有 | — | 阻塞所有写 |
| 表锁（读/写） | 表 | 所有 | — | 读共享，写互斥 |
| 元数据锁（MDL） | 表 | 所有 | — | 读共享，写互斥 |
| 意向锁（IS/IX） | 表 | InnoDB | — | 与表级锁互斥 |
| 行锁（S/X） | 行 | InnoDB | RC, RR | S共享，X互斥，S与X互斥 |
| 间隙锁（Gap） | 间隙 | InnoDB | RR | 间隙锁之间不互斥 |
| 临键锁（Next-Key） | 行+间隙 | InnoDB | RR | 组合行锁和间隙锁 |
| 插入意向锁 | 间隙 | InnoDB | RR | 插入意向之间不互斥 |

# 6. 死锁（Deadlock）

## 6.1 什么是死锁

两个或多个事务相互持有对方需要的锁，形成循环等待，谁也走不下去：

```
事务 A：锁定 id=1 → 等待 id=2 的锁
事务 B：锁定 id=2 → 等待 id=1 的锁
→ 死锁
```

## 6.2 死锁检测

InnoDB 自动检测死锁（`innodb_deadlock_detect = ON`，默认开启），选择回滚**代价最小**的事务（一般是持有锁较少的事务）。

```sql
-- 查看最近一次死锁信息
SHOW ENGINE INNODB STATUS\G
-- 查看 LATEST DETECTED DEADLOCK 部分
```

## 6.3 减少死锁的建议

- **以相同顺序访问资源**：所有事务按相同顺序更新表和数据行
- **事务尽量短**：减少锁持有时间
- **避免在事务中进行用户交互**
- **使用低隔离级别**：RC 减少间隙锁，降低死锁概率
- **利用索引精确锁定**：避免不通过索引导致的表锁
- **使用乐观锁**：版本号机制替代悲观锁（适用于低冲突场景）

# 7. 乐观锁与悲观锁

| 类型 | 实现方式 | 优点 | 缺点 | 适用场景 |
|------|---------|------|------|---------|
| **悲观锁** | `SELECT ... FOR UPDATE`，数据库层加锁 | 强一致性 | 并发低、可能死锁 | 写冲突频繁 |
| **乐观锁** | 版本号/时间戳，更新时检查 | 无锁等待、并发高 | 冲突时重试开销 | 读多写少、冲突低 |

```sql
-- 悲观锁
START TRANSACTION;
SELECT stock FROM product WHERE id = 1 FOR UPDATE;
-- 判断库存充足
UPDATE product SET stock = stock - 1 WHERE id = 1;
COMMIT;

-- 乐观锁（版本号）
-- 表中有 version 字段
UPDATE product
SET stock = stock - 1, version = version + 1
WHERE id = 1 AND version = @current_version;
-- 如果 affected_rows = 0，说明版本已变更，重试
```
