# 1. 基础题

## 1.1 Mycat 是什么？Mycat 1.x 和 2.x 有什么区别？

Mycat 是一个开源的分布式数据库中间件，**站在应用与 MySQL 之间、讲 MySQL 协议的代理层**：应用像连单库一样连它的 8066 端口，由它完成分库分表路由、读写分离、跨片结果归并与分布式主键生成，对应用基本透明（协议兼容但 SQL 能力有边界）。1.x 与 2.x 是两代产品而非版本递进：1.6.x 用自研 NIO Reactor + 阿里 Druid 解析器 + 三份 XML 配置，SQL 改写是字符串级手工操作，改配置基本要重启；2.x 整体重写为 Netty 事件驱动 + Apache Calcite 计划级优化（谓词/投影/LIMIT 下推、RBO 为主），配置换成 JSON 四件套（datasources/clusters/schemas/users）并支持 reload 热生效，事务从弱 XA 升级为原生 XA，SQL 支持度（JOIN、子查询）显著提升。一句话概括差异：**1.x 是"会路由的转发器"，2.x 是"带查询优化器的联邦查询代理"**；面试里能讲出"字符串改写 vs RelNode 计划变换"这一层就超过多数回答。

## 1.2 Mycat vs ShardingSphere-Proxy 如何选择？

| 维度 | Mycat2 | ShardingSphere-Proxy |
|------|--------|---------------------|
| 社区活跃度 | 低（更新缓慢） | 高（Apache 顶级项目，迭代快） |
| SQL 兼容性 | MySQL 协议为主 | MySQL + PostgreSQL/openGauss 多方言 |
| 配置方式 | JSON 文件 / 配置中心推送 | DistSQL 在线语法管理元数据 |
| 分布式事务 | XA | XA / Seata / BASE 多种 |
| 治理能力 | 基础监控 | APM 插件、数据脱敏、影子库压测齐备 |
| 生态形态 | 仅 Proxy | JDBC + Proxy + K8s Operator 三形态 |

选型逻辑一段话讲完：**新项目默认 ShardingSphere-Proxy**——社区活跃度、SQL 支持面、治理功能与全局二级索引（GSI）能力全面占优，且 JDBC 形态给了"先嵌入后代理"的演进余地；**Mycat2 适合三类存量场景**——已有 Mycat1.x 深度使用积累要平滑升级、非 Java 异构语言栈只能走代理形态、团队对 Mycat 路由行为有多年运维手感。被追问"为什么 Mycat 社区弱"时如实回答：核心维护带宽有限、文档与英文社区停滞，这是事实层面的减分项，不必硬辩。

## 1.3 Mycat 的分片策略有哪些？

| 策略 | 算法 | 适用场景 |
|------|------|---------|
| 取模 | `id % N` | 均匀分布主键 |
| 范围 | `id BETWEEN a AND b` | 区间查询 |
| 一致性Hash | MurmurHash | 扩容友好 |
| 日期 | `yyyy-MM-dd` 分区 | 时间序列 |
| 枚举 | 映射表 | 地区/类型 |

补充一层实践判断：取模最直白但扩容要 rehash，所以生产惯例是**逻辑分片数一步到位（64/128 片）而物理实例逐步加**，count 永不变；范围/日期分片天然支持"冷热分离 + 整片归档"，但新数据全打最新分片会造成写热点；一致性 Hash 靠虚拟桶（MurmurHash + virtualBucket）逼近均匀，适合动态增减节点但要接受部分迁移；枚举分片本质是"自定义路由表"，多租户大客户独占分片这类业务约束靠它落地。

# 2. 原理题

## 2.1 Mycat2 如何处理一条跨分片的 COUNT(*) 查询？

流程是**解析→路由→并行下发→改写归并**四步：Calcite 把 SQL 解析为计划树，Validator 确认表存在，路由层发现 WHERE 不含分片键、目标是全部 N 个分片；于是向 N 个分片**并行**下发 `SELECT COUNT(*) FROM orders`（各片走自己的索引扫描），总 RT 约等于最慢分片而非各片之和；各分片返回单行计数值，归并层做求和（COUNT 满足结合律，两段式聚合内存 O(1)），合成最终结果。可以顺势展开的加分点：带 WHERE 时下发语句保留 WHERE 但每片都要执行；`COUNT(DISTINCT x)` 则**不能**两段式合并——同值跨片重复，只能把各片去重集拉回中间件再全局去重，代价与基数成正比（第 12 篇）。

## 2.2 Mycat2 的 ER 表和全局表有什么区别？跨分片 JOIN 怎么办？

| 维度 | ER 表 | 全局表 |
|------|-------|--------|
| 数据分布 | 子表与父表在同一分片 | 全量副本在每个分片 |
| 数据量 | 随业务增长 | 小（< 10 万行） |
| 写入开销 | 单分片 | 所有分片（XA 事务） |
| JOIN | 与父表在本分片 JOIN | 任意分片可 JOIN |

一段话讲透设计动机：ER 表的本质是**"把业务上必然一起访问的数据钉在同一个分片"**——order_items 按 orders 的分片键分布，"查订单带明细"单片完成、跨片事务消失；全局表的本质是**"用写放大换 JOIN 本地化"**——字典表每片一份全量副本，任何分片的 JOIN 都能本地完成，但一次 UPDATE 变 N 节点广播，所以数量与变更频率都要克制。至于**不同分片键的两张分片表 JOIN**：Mycat 只能退化为驱动侧路由 + 被驱动侧逐行点查/拉全量，两层全扫相乘是灾难形态，生产解法是映射表（全局索引模式）、冗余分片键列或应用层分步组装——**JOIN 能力不是中间件"给不给"的问题，是数据摆放的问题**。

## 2.3 Mycat2 如何实现读写分离？

三层机制：**拓扑层**在 clusters.json 把数据源组织成 MASTER_SLAVE 集群，声明 master 与 replicas 及权重；**判定层**靠 SQL 解析结果——INSERT/UPDATE/DELETE/DDL 与显式事务一律走 master，无事务的 SELECT 按 readBalanceType（轮询/随机/权重）分发到 replicas，主库可配权重 0 完全不接读；**保护机制**是心跳：从库复制延迟超 slaveThreshold 自动踢出读池、追平自动回池，从库宕机秒级摘除。追问"写后读一致性"答三板斧：事务内读恒走主库；写后立刻读用 Hint `/*!mycat:db_type=master*/` 强制主库，或应用层显式双数据源路由；对延迟不敏感场景交给权重池自然消化。**设计考量**必须点出局限：Mycat 的读写分离是**语句级路由**而非"会话级因果一致性"，"先写后读"落到哪个从库、延迟多大它不承诺——这是应用要自己兜底的语义边界。

## 2.4 Mycat2 的 XA 事务执行流程？

BEGIN 后事务涉及的每个分片连接各自开启本地事务；COMMIT 时 Mycat 作为协调者对全部分片执行 `XA PREPARE`，MySQL 写 prepare 状态的 binlog 并返回 ok；**全部分片 PREPARE 成功**才逐片 `XA COMMIT`，任一片失败则对已 prepare 的分支统一 `XA ROLLBACK`。开销账：多两轮网络往返、prepare 阶段 InnoDB 刷盘 fsync、持锁时间拉长，实测相对本地事务损耗约 20-40%。必须主动说出两个风险点以显示深度：其一，**悬挂事务**——prepare 成功后协调者宕机，分支状态留在 MySQL（`XA RECOVER` 可查），Mycat 重启不会自动决议，需要人工/脚本按 recover 列表补 commit/rollback；其二，XA 只保证跨分片写的原子性，**不解决"部分分支读到的数据在并发下已过时"**的隔离问题。最佳实践仍是：ER 分片让事务尽量单片化，XA 只兜底低频强一致场景。

## 2.5 Calcite 在 Mycat2 中的作用？SQL 支持有哪些局限？

**作用四件事**：SQL 解析（MySQL 语法到 SqlNode）、语义校验（结合逻辑 Schema 查表列类型）、关系代数优化（谓词下推、投影裁剪、LIMIT 下推、AVG→SUM/COUNT 改写、子查询展开——RBO 为主 CBO 辅助）、执行计划生成供 Router/归并器消费。这正是 2.x JOIN/子查询支持度远超 1.6.x（Druid 解析 + 字符串改写）的根本原因。但**局限同样要背下来**：存储过程/函数不支持（设计取舍，透传无法处理跨片语义）；跨不同分片键的大表 JOIN 只能退化执行、生产不可用；`COUNT(DISTINCT)`、高基数 GROUP BY 需拉明细回中间件；无分片键的深分页 OFFSET 成本 O(offset×片数)；部分 SET 会话变量、锁函数跨片语义要么受限要么只在单片生效。高分答法是给出"判定式"：**一条 SQL 的成本由"路由到几个片 × 每片返回多少行 × 中间件归并什么形态"三个因子决定，Calcite 能优化后两个常数，救不了第一个**。

> **设计争议**：被追问"有了 Calcite 是不是就能当查询引擎用"时，正确姿态是泼冷水：Calcite 的 CBO 拿到的统计信息粗（甚至缺失），而真正执行扫描的后端 MySQL 还要跑自己的优化器，两层各按各的统计决策，中间件层做重 CBO 收益存疑——所以 Mycat2 实际是 RBO 为主、CBO 仅在 join 顺序等局部决策上点缀。承认"优化器救不了跨片传输的硬成本"，比宣称"Calcite 无所不能"更能加分。

## 2.6 Mycat 的心跳机制是怎么工作的？和 Druid 连接池的探活有什么区别？

Mycat 用**独立的探测连接**周期性对每个后端数据源执行 heartbeatSQL（1.6.x 默认 `select user()` 写在 dataHost 的 `<heartbeat>`；2.x 是 datasource 级 JSON 配置 `SELECT 1` 可换），连续 maxRetry 次失败（默认 3）即把节点标记 OFFLINE、从路由/读权重摘除，恢复后自动回池；对主从集群还解析 `SHOW SLAVE STATUS` 的 Seconds_Behind_Master，超 slaveThreshold 的从库暂时退出读池；minSwitchTimeInterval 做切换防抖防乒乓。与 Druid 的本质区别是**角色不同**：Druid 的 testWhileIdle/validationQuery 验证"我池里这条 TCP 连接还能用吗"，是连接级质量保障；Mycat 心跳回答"这个实例活着吗、是主是从、延迟多少"，是成员拓扑管理。因此最佳分工是：用了 Mycat 后应用池关掉 testOnBorrow 只留 testWhileIdle，后端死活交给离数据库更近、有全局视图的 Mycat。追问"心跳发现主库挂了怎么办"补一句生产立场：**Mycat 自带的自动提升只是兜底，企业做法是 MHA/Orchestrator/云 RDS 做选主仲裁，Mycat 被动跟随新主**——中间件自己判断"旧主死透没有"是不安全的。

# 3. 实践题

## 3.1 如何选择分片键？

四条原则按重要性排：**高频查询 WHERE 条件覆盖率高**（先做生产 SQL 条件词频普查，保护流量最大的访问路径，覆盖不到的走映射表/ES 旁路）；**不可变**（UPDATE 分片键=数据迁移）；**区分度高、分布均匀**（低区分度或时间前缀趋势 ID 直接取模必热点，ID 方案要与分片算法成对设计）；**业务聚合根**（订单按 user_id 服务 C 端列表，订单详情用 order_id→user_id 全局索引表两跳）。再补两条反例显示功力：不要选日期做分片键（写热点 + 查询恒跨片），不要选频繁更新的列。收尾一句："**分片键选错，后面所有的 JOIN、分页、扩容、事务优化全是在还债**"。

## 3.2 分库分表后如何做跨分片分页？

先看朴素方案的成本：`ORDER BY id LIMIT 20 OFFSET 10000` 要**每个分片各取 offset+limit=10020 条**，归并排序后截取第 10001-10020 条——中间件经手 10020×片数行只为留下 20 行，深页必挂。标准优化是**游标分页**：把 OFFSET 换成 `WHERE id > 上次最大 id ORDER BY id LIMIT 20`，成本降回 O(limit×片数)，排序键不唯一时用 (create_time,id) 复合游标；代价是只能连续翻页不能跳页。total 数字单独处理：COUNT 全分片求和很贵且与页内容无一致性保证（两次查询没有全局快照），实践上"异步估算 + 前端只显示约 N 条/前 100 页"是行业默认。最后给架构级替代：需要任意跳页 + 复杂筛选的列表本质是搜索场景，同步到 ES 做检索、回 Mycat 按 ID 精确取数，"OLTP 走分片库、检索走 ES"是教科书分工。

> **注意**：这题的失分点是只答"游标分页"就收声。面试官追问的往往是"业务非要跳页怎么办"——标准答案序列：游标优先 → 限制最大页深（超出不给翻）→ total 异步/近似 → 真跳页需求承认它属于检索域、外移 ES。把"中间件救不了跳页"说清楚比背算法更加分。

## 3.3 Mycat2 如何实现不停机扩容？

先亮结论：**Mycat 热加载只改变中间件的"知识"，不改变数据的位置**，扩容的真工作量在数据搬迁。标准动线（第 15 篇）：新 MySQL 实例建好物理表 → 配置里加新分片置 `backup` 状态（存在但不接流量）→ reload → 存量数据按新规则迁移 + Canal 追增量 → 双校验（行数/抽样/checksum）→ 状态改 active → reload 切流。前提是第一天就把 count 定终局（如 128 逻辑分片），日常扩容只是"逻辑分片整体搬家"——若被迫改 count（取模 rehash），几乎全部数据要重分布，业界更稳的做法是双写迁移（新旧两套并行、切读后下线旧套），回滚能力完全不同。加分点：扩容窗口冻结其他规则变更、每步留回滚点、新分片先备份后动手。

## 3.4 分片表要做 DDL（加字段），你的流程是什么？

**绝不通过 Mycat 顺手执行分片表 DDL**——那是逐片普通语句，中途失败就产生"半张表有新列"的碎片态。正确流程五步：变更单评审（列定义、默认值、是否回填）→ 用 gh-ost/pt-online-schema-change **逐分片、先从库后主库**在线执行（避免复制延迟雪崩与锁表）→ 全部片完成后 reload Mycat 刷新表元数据（元数据滞后时新列不可见/报错）→ 应用代码发布（读新列的逻辑必须在元数据 reload 之后）→ 观察。全局表要额外把"所有分片副本"纳入 DDL 清单。追问"字段回滚"：删列同理逐片执行，但代码先发"不依赖该列"的版本再收表结构，顺序是"先兼容后变更"。这道题考的是变更纪律，**答出"reload 刷新元数据"这一步即证明真用过**。

# 4. 架构题

## 4.1 Mycat2 自身如何保证高可用？

**实例层**：Mycat 无状态，≥2 实例 + Keepalived VIP（非抢占模式、健康检查实测 8066 端口而非 pgrep）/LVS/云 SLB 做入口分发，单实例故障由 LB 秒级摘除，容量按"N-1 台扛全量峰值"规划；**配置层**：接 Nacos/ZK 配置中心，保证多实例路由一致 + 变更可回滚（配置漂移比宕机更危险，会静默错路由）；**数据层**：Mycat 不替 MySQL 做仲裁，通过心跳跟随专职 HA（MHA/Orchestrator/云 RDS），自己只负责摘除与切流；**客户端才是 RTO 大头**：长连接不会自动漂移，VIP 切换后应用连接池里的死连接要等超时/校验失败才重建，所以 JDBC 侧 retriesAllDown、connectTimeout 是 HA 方案的组成部分。追问脑裂：VRRP 分区可能双 VIP，但 Mycat 双活无害（无状态）；真正的脑裂防线在数据层（Galera/quorum 仲裁或专职 HA 的旧主隔离），答清"**中间件层无所谓、数据库层才致命**"即到位。

## 4.2 Mycat2 的性能瓶颈在哪里？

按影响面排序四座山：**1. 跨分片查询**——全片扫描的连接放大（一条 SQL 借 N 条后端连接）与木桶效应（RT 取决于最慢分片），归并排序/聚合吃堆内存，这是第一瓶颈，解法永远在路由层不在参数层；**2. 跨片 XA 事务**——两轮网络往返 + prepare fsync，20-40% 损耗且有悬挂风险；**3. 后端连接池**——Little's Law 算出的配额被实例数叠加、被跨片查询放大，池满后 connectionTimeout 排队直接传染应用线程池；**4. 中间件自身 CPU/内存**——解析与归并的开销、GC 停顿（Mycat 对停顿极敏感，一次 Full GC 全员超时）、Buffer Pool 打满引发分配阻塞。Calcite 解析开销通常被计划缓存摊薄、不是瓶颈。答完主动给"排查顺位"：先看 EXPLAIN 分片数、再看池水位与慢模板、最后才动 JVM/线程参数——顺序即经验。

## 4.3 分布式主键方案如何选择？

| 方案 | 适用场景 |
|------|---------|
| Snowflake | **首选**，无依赖，高性能 |
| 数据库序列 | 需要严格递增的场景 |
| UUID | 不需要排序的场景 |
| Redis INCR | 已经使用 Redis 的场景 |

Mycat 的全局序列（1.6.x 的 `MYCAT_SEQUENCE` + 两张序列表 + 本地时间戳模式，2.x 的对应实现）本质是"号段/时钟 + 多节点互斥取号"，核心纪律四条：**workerId 全局唯一且容器化环境要中心化注册**（重复 workerId=重复 ID 事故）；**趋势递增 ID 不要直接取模分片**（写热点，配合 MurmurHash 或在 ID 生成时打散低位）；**迁移/双写期间必须调整起始序列值做号段隔离**（1.x→2.x 切换唯一的数据级风险点）；业务单号含日期前缀时，前缀做归档键、分片键仍用散列 ID。一句话：**ID 方案、分片算法、扩容方式三者必须一起设计，单独谈任何一个都是纸上谈兵**。

# 5. 对比与迁移题

## 5.1 Mycat2 分库分表 vs 应用层分库分表？

| 维度 | Mycat2 | 应用层（ShardingSphere-JDBC） |
|------|--------|---------------------------|
| 部署方式 | 独立中间件 | SDK 嵌入 |
| 语言限制 | 无（MySQL 协议） | Java |
| 网络开销 | +1 跳 | 直连数据库 |
| 运维复杂度 | 需维护中间件并做 HA | 随应用发布 |
| 性能 | 中（代理层开销） | 高（直连） |
| 治理归属 | DBA/平台一处收口（审计、限流、账号） | 随应用版本走 |

判断逻辑：**异构语言栈与强治理需求选 Proxy（Mycat），Java 高敏核心链路选 JDBC 省一跳**；两者可混用——在线 Java 核心用 JDBC，旁路与异构流量走代理。答出混用可能性显示架构视野。

## 5.2 从 Mycat 1.6.x 迁移到 2.x，你会关注哪些兼容性问题？

按风险等级列四个关注面：**SQL 行为**——双向差异：2.x 靠 Calcite 解锁 JOIN/子查询（收益），但 1.x 勉强能跑的存储过程透传、部分 hint 写法、sqlMaxLimit 自动补 LIMIT 的默认行为在 2.x 不同（从"静默截断"可能变"全量返回"或报错），回归样本必须取 1.x 生产语句统计 Top 200 而非测试用例；**分片路由结果**——分片函数映射名换了（PartitionByLong→PartitionByRange 等）但结果一个都不能变，逐值对拍是迁移唯一验收标准，"同名不同实现"（MurmurHash 的桶参数默认值）是最阴的坑；**全局序列**——序列表结构与取值实现不同，切换必须设新起始值防号段重叠，这是唯一可能产生数据事故的一项；**运维面**——管理命令从 `show @@datasource` 换 `/*!mycat:showDataSources*/`、ZK 集群模式换配置中心、日志格式标准化，脚本与监控同步改造。落地路径：双代理并存按应用灰度、只读先行、结果 diff 比对、1.x 保留一个完整业务周期再下线——"配置翻译三成力、双跑验证五成力"。

# 6. 小结

| 高频追问 | 一句话兜底答案 |
|---------|---------------|
| 最大边界 | Mycat 优化的是"扫几个片、传多少行、怎么合并"，改不了"必须扫所有片"的命运 |
| 设计分水岭 | 架构好坏在分片键与数据摆放，不在中间件本身 |
| 运维三纪律 | 分片键不可改、count 不可动、DDL 走 DBA 工具再 reload |
| HA 心智 | 实例随便死、配置不许漂、仲裁交专职、客户端才是 RTO 大头 |
