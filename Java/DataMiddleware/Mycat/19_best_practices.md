# 1. 分片键设计原则

**分片键是整个分库分表系统里最不可逆的设计决策**：数据一旦按某个键分布，改分片键就等于全量重分布数据（第 15、18 篇都强调了这一点）。它同时决定三件事：路由命中率（性能上限）、JOIN 可能性（功能上限）、扩容方式（演进上限）。90% 的"MySQL 单表抗不住了"最终会退化成"MySQL 集群被全分片扫描打垮"，源头几乎都在分片键选错。

```text
✓ 分片键选择优先级：
  1. 高频查询的 WHERE 条件列
  2. 不可变的业务主键
  3. 区分度高的列（避免数据倾斜）

✗ 避免使用的分片键：
  1. 频繁修改的列 → 修改可能触发数据迁移
  2. 区分度低的列 → 数据倾斜
  3. 不在查询条件中的列 → 全分片扫描
```

**"高频查询的 WHERE 条件列"要先做一次流量普查**：把生产慢日志/语句统计里该表的全部查询条件做词频，覆盖率最高的那个等值列就是分片键候选——常见冲突出现在"按订单号查详情"与"按用户查订单列表"两类流量都高的订单系统：以 order_id 分片则列表查询全分片扫描，以 user_id 分片则详情查询全分片扫描。**行业收敛做法是主表按"聚合根查询方"分片（订单按 user_id 服务"我的订单"），另一类访问用辅助手段**：全局二级索引表（order_id→user_id 映射，先查键再精确路由）、或异构到 ES。选主表分片键时优先保护 C 端高频路径，B 端/运营查询整体旁路出去。

**常见分片键模式**：

| 业务场景 | 推荐分片键 | 算法 |
|---------|-----------|------|
| 订单系统 | `order_id` (Snowflake) | 取模 |
| 用户系统 | `user_id` | 取模 / Hash |
| 日志系统 | `create_time` | 日期分片 |
| 多租户 SaaS | `tenant_id` | 枚举 / 取模 |
| 电商商品 | `seller_id` | 取模 |
| 金融交易 | `trade_no` | 取模 |

表中"订单按 order_id 取模"一行有前置条件值得警惕：**order_id 必须由均匀散列的 ID 方案生成**（Snowflake 低位序列、或取模友好的随机编码）。若用"时间+序列"的自增式订单号直接取模，写入会集中在少数分片（热点），读旧单倒是均匀的——这是 ID 方案与分片算法必须**成对设计**的原因，见第 4 节。

> **设计争议**：按时间分片（月表）看起来对日志/流水类天然合理，但代价是**查询永远跨片**（用户查"最近三个月"固定 3-4 个分片），且历史数据集中在旧分片导致容量不均。更稳的形态是"哈希分片保均匀 + 时间做表内分区/归档键"，把时间从路由维度降级为生命周期管理维度。多租户 SaaS 按 tenant_id 分片则相反是共识——**大客户单独建片、小客户哈希混部**的混合策略比纯哈希更贴近商业现实。

# 2. ER 分片与 JOIN 设计

**JOIN 能力不是中间件"给不给"的问题，是数据摆放的问题**。Mycat 能高效执行的 JOIN 只有三种形态（机制见第 11 篇 4.4）：ER 表同片 JOIN、同分片键同算法 JOIN、分片表×全局表 JOIN。设计上把这三条当成 JOIN 的"合法语法"来用：

- **主-子关系用 ER 表**：orders 按 user_id 分片，order_items 也用 user_id（或通过 parent 关系继承父表分片键）分片，"某用户的订单+明细"永远单片完成。ER 表的价值不在"支持 JOIN"，在**把业务上天然同行的数据钉在同一分片**——跨分片事务、跨片归并同时被消掉。
- **JOIN 键 = 分片键**：两张表都以 user_id 分片且算法一致，JOIN 可逐分片下推；一旦一张表按别的键分片，这个 JOIN 立刻退化为灾难形态。
- **应用层组装是正当手段不是降级**：先查 orders（带分片键，精确路由），拿 id 列表批量查 items（IN 路由）——"分步查询 + 内存 JOIN"在 OLTP 高频路径上往往比中间件跨片 JOIN 更快、更可控。MySQL 时代"能 JOIN 就别拆"的直觉在分片世界里要反转：**默认按单表写，JOIN 是需要设计支撑的例外**。

高频非分片键访问的处理优先级：**映射表（全局二级索引的穷人版）> ES 旁路 > 加冗余列改查询 > 全分片扫描**。Mycat 自身没有全局二级索引，映射表用 Mycat 建一张按 order_id 分片的全局索引表（存 order_id→user_id）即可实现两跳精确路由，简单可靠。

# 3. 数据源规划

```text
容量评估公式：

每分片数据量 = 预估总量 / 分片数
每分片 QPS = 总 QPS × (精确分片比例 / 分片数 + 全扫描比例)

示例：
  预估 1 亿条订单
  目标单表 ≤ 2000 万条
  → 分片数 = 10000万 / 2000万 = 5 → 向上取 8（2 的幂）

  总 QPS = 5000
  精确路由比例 = 80% (QPS = 4000)
  全分片扫描比例 = 20% (QPS = 1000)

  每分片 QPS = 4000/8 + 1000 = 500 + 1000 = 1500
  → 单 MySQL 实例可承载
```

公式里"2 的幂"不是玄学：扩容时 count 翻倍是唯一能让一半存量数据保持原分片归属的取模演进方式（配合路由映射表甚至可以不搬数据），预留了它，第 15 篇的 rehash 灾难就永远不会降临。容量口径也要双指标：**单表行数 ≤ 2000 万是 MySQL 索引深度与 DDL 耗时的经验线，单片数据量 ≤ 几百 GB 才是备份恢复/迁移可行性的硬约束**，宽表场景往往先撞后者。

> **行业实践**：数据源规划的纪律是"**逻辑分片数远大于物理实例数**"——第一天就建 64 或 128 个逻辑分片（`dn0..dn127`），初期 4 个 MySQL 实例每个扛 16-32 个分片，扩容 = 把整段逻辑分片搬到新实例，**分片算法（count）永远不动**。这条纪律把扩容从"数据重分布工程"降为"搬迁 + 改映射"，是 Mycat 生态最一致的实践经验。

# 4. ID 方案

**ID 方案与分片方案耦合设计**（第 1 篇/第 6 篇细讲机制，此处只讲选型纪律）：

| 方案 | 趋势性 | 与分片的配合 |
|------|--------|------------|
| Snowflake（Mycat 全局序列） | 趋势递增、低位均匀 | 直接取模友好；**注意机器位规划**，多机房部署时钟回拨处理 |
| 数据库号段 | 递增 | 递增 ID 直接取模会写热点，宜"取模前先打散"或按业务键分片 |
| UUID | 无序 | 取模均匀但主键性能差（页分裂），分库分表下不推荐做主键 |
| 业务单号 | 不可控 | 若含时间前缀必热点，不能直接当分片键 |

纪律三条：**① 上线后 ID 生成器不可换**（换 = 存量键分布不可知）；**② workerId 分配走配置中心注册**，防止容器环境重复部署产生重复 ID——这是 Mycat 全局序列 1.x/2.x 共同的运维要求；**③ 迁移/双写期间新旧 ID 段隔离**（改起始值），第 18 篇里唯一的数据级风险点就在这一项。

# 5. 全局表使用规范

```text
适合作为全局表的表：
  ✓ 数据量 < 10 万行
  ✓ 修改频率低（天/周级别）
  ✓ 被多个分片表关联查询

不适合作为全局表：
  ✗ 数据量大且增长快
  ✗ 频繁修改
  ✗ 只需要在特定分片使用（用 ER 表）
```

**全局表的成本模型要算给团队听**：一次 UPDATE 变成 N 节点广播（Mycat 层多语句/XA 语义，失败还要处理各副本一致性）、每次 DDL 变更要执行 N 遍、扩容时新分片必须先回填全量副本才能 active。全局表数量克制的经验线：**单 schema 全局表 ≤ 5 张、单表 ≤ 10 万行**；字典表若"只被某个区域的表 JOIN"，用枚举分片把数据与其消费者钉在一起，比全局复制更省。

# 6. 索引与查询规范

```sql
-- 分片表的索引设计注意事项：

-- 1. 分片键必须在索引中（通常就是主键）
CREATE INDEX idx_id ON orders(id);     -- 已有主键索引

-- 2. 非分片键需要全局索引 → 用全局表或 ES
-- Mycat2 没有全局二级索引，跨分片非分片键查询 = 全表扫描

-- 3. 每张分片表独立建索引
-- ER 子表的关联键必须有索引
CREATE INDEX idx_order_id ON order_items(order_id);
```

索引设计在分片下与单 MySQL 无异（**每张物理表都是一个完整 InnoDB，本地索引照常生效**），变化的是**索引救不了的路由问题**：没有分片键的 WHERE 会演变成"每个分片各自走一遍它的索引"——N 倍连接占用 + N 倍 RT 尾延迟，索引再好也只是把每片耗时从 50ms 压到 5ms，总耗时仍受最慢分片支配。查询规范按第 17 篇优先级落进代码 CR：分片键必带、LIMIT 必带、SELECT 列明确（禁 `SELECT *`：列裁剪的前提与网络字节数都靠它）、深分页走游标。

# 7. 读写分离与事务使用规范

```json
// 推荐配置
{
  "clusters": {
    "order_cluster": {
      "clusterType": "MASTER_SLAVE",
      "readBalanceType": "BALANCE_ALL",
      "master": { "name": "master", "weight": 0 },     // 不参与读
      "replicas": [
        { "name": "slave1", "weight": 10 },
        { "name": "slave2", "weight": 10 }
      ]
    }
  }
}
```

**建议**：
- Master 权重设为 0，专注写入
- Slave 权重按配置分配（高性能机器权重大）
- 关键业务（如支付后查订单）强制走 Master

"写后读"一致性的三板斧按侵入度排序：事务内/写后 N 秒内读 → Hint 强制主库；再进一步 → 应用层"写走写库连接、读走读库连接"的显式路由；兜底 → 从库延迟监控（第 13 篇 slaveThreshold）自动踢出读池。不要把一致性指望在中间件的读权重上。

```text
1. 尽量单分片事务（WHERE 包含分片键）
2. 跨分片事务自动升级为 XA：注意性能开销（20-40%）
3. 事务超时控制：
   - 默认 30s，大事务适当延长
   - 写操作事务 < 5s（避免长时间锁）
4. 全局表修改 = 多节点 XA 事务（慎用）
```

跨分片事务的终极纪律：**能靠 ER 分片避免就不要靠 XA**——同一业务事务的操作对象应尽量落在同一分片（同一用户的数据放同片是比任何事务协议都强的保证），真正跨片的写场景（转账类）考虑业务拆分（TCC/消息最终一致），把 XA 留给低频、强一致的收尾场景。

# 8. 监控与告警

```text
必须监控的指标：
□ Mycat2 前端连接数（接近 maxCon 时告警）
□ 后端连接池利用率（> 80% 告警）
□ QPS 和 RT（P50 / P99）
□ 分片命中率（越低性能越差）
□ 数据节点健康状态
□ JVM 堆内存 / GC 频率

推荐告警阈值：
□ 数据节点 OFFLINE → 立即告警
□ 前端连接 > 80% → 告警
□ P99 RT 突增 3 倍 → 告警
□ Full GC > 1 次/分钟 → 告警
```

**监控基线是"变更可对比"的前提**：上线第一天就要留存四条周同期基线（QPS/RT 分位/错误率/分片命中率），此后任何变更（SQL 上线、扩容、版本迁移）的验收都表达为"与基线对比无劣化"，而非"看起来没问题"。第 13 篇的 Prometheus/Grafana 指标体系是数据来源，这里强调的是**把基线当合同**的工程习惯。

# 9. 变更纪律：DDL 与扩容

**不要绕过 Mycat 直接对某个分片做变更，也不要"顺手"通过 Mycat 做 DDL**：

> **注意**：正确动线是——DDL 由 DBA 工具（gh-ost/pt-online-schema-change）**逐分片**执行（顺序：从库先行→主库，避开复制延迟放大），全部完成后 reload Mycat 刷新表元数据（第 15 篇边界表）。经 Mycat 下发 DDL 到分片表是逐片执行的普通语句，中途失败即产生"半张表有新列"的碎片状态，修复成本远高于工单流程。

扩容纪律在第 3 节已给（逻辑分片 >> 物理实例、count 不动），补三条流程纪律：**先备份后动手**（扩容窗口内任何一次误路由都要能靠快照止损）；**新分片必须走 backup→迁移→校验→active 全链**（第 15 篇），跳过校验直接 active 是教科书事故；**扩容窗口内冻结规则类配置变更**，双跑混合配置 + 数据搬迁两个变量叠加时无人能定位问题。

## 9.1 DON'T 清单（团队红线贴墙版）

```text
✗ 不要用分片键以外的列做 WHERE 高频查询
✗ 不要在大表中使用 DISTINCT + ORDER BY（无分片键）
✗ 不要在分布式事务中做批量全分片操作
✗ 不要用 OFFSET 做深度分页（用游标/WHERE id > ?）
✗ 不要频繁修改全局表（每次 UPDATE 都是 XA 事务）
✗ 不要在生产环境直接修改配置文件而不 reload
✗ 不要忘记定期清理日志文件
✗ 不要在 Mycat2 层做复杂的 JOIN（推给应用层或 ES）
```

```text
□ 慢 SQL 报表周知（谁的全分片扫描又涨了）
□ 全分片扫描类语句占比逐月下降（治理要有趋势证据）
□ 全局表数量与行数季度盘点
□ 分片数据倾斜检查（max/min 分片行数比 > 2 即预警）
□ ID 生成器 workerId 分配表审计
□ 连接池配置与容量基线季度复核
```

# 11. 小结

| 主题 | 纪律 |
|------|------|
| 分片键 | 流量普查定键、与 ID 方案成对设计、聚合根查询方优先，上线后不可改 |
| JOIN | ER/同键/全局表三种合法形态；默认单表，JOIN 靠摆放数据实现而非中间件 |
| 容量 | 逻辑分片 ≫ 物理实例，count 永不动；行数与数据量双指标 |
| 全局表 | ≤5 张、≤10 万行、低变更频率；写成本 = N 副本广播 |
| 事务 | ER 同片优先，XA 只兜底；写后读一致性靠强制主库 Hint/显式路由 |
| 变更 | DDL 逐分片走 DBA 工具再 reload；扩容全链校验；配置即代码 + 金丝雀 |

一句话总纲：**Mycat 时代的好架构，是让中间件尽量无事可做的架构**——分片键让路由精确、ER 让 JOIN 本地化、全局表克制、事务同片，中间件退化成透明管道时，才是这套体系最稳的状态。下一篇（20 排错）给这堵墙上的裂缝编号。
