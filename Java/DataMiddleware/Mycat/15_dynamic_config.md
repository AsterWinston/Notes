# 1. 概述

**Mycat 2.x 的动态配置（热加载）是与 1.6.x 最本质的运维差异之一**：1.6.x 改配置基本靠重启（`reload` 命令只覆盖极少数场景且行为不透明），而 2.x 把配置模型重做成了"可增量替换的运行时元数据"，数据源、分片规则、用户权限的绝大多数变更可以在线生效。对 7×24 的在线业务，"不重启改配置"决定了扩容、切流、限权这些日常运维动作从"凌晨变更窗口"变成"随手操作"。

Mycat2 支持在不重启服务的情况下动态修改配置，包括数据源、分片规则、用户权限等。

```text
┌────────────────────────────────────────┐
│          配置变更方式                    │
│                                         │
│  1. 管理端口 SQL 命令 (9066)              │
│  2. HTTP API                            │
│  3. 配置中心推送 (ZK/Nacos)              │
│  4. 修改配置文件 + reload 命令            │
└────────────────────────────────────────┘
```

四种方式不是并列关系而是**入口与通道**：管理端口命令是"操作入口"，配置文件/配置中心是"变更来源"。集群部署下推荐只保留一条动线——改配置中心，实例监听推送；本地文件 + 逐台 reload 仅适合单机或临时救急，多实例用它会立刻制造配置漂移（见第 14 篇）。

# 2. 管理端口操作

Mycat 用两个端口划分职责：8066 面向应用（MySQL 协议），9066 面向运维（管理员连接，命令以 MySQL 客户端为载体）。

```sql
-- 连接管理端口
mysql -h 127.0.0.1 -P 9066 -u root -p123456

-- 重新加载配置
/*!mycat:reloadConfig*/

-- 查看当前数据源
/*!mycat:showDataSources*/

-- 查看当前 Schema
/*!mycat:showSchemas*/
```

> **注意**：9066 的 reload/管理命令**没有任何审批与灰度语义**，连上就能改，这是它必须只监听内网/本机、由堡垒机或运维平台代理访问的原因（详见第 16 篇安全）。成熟的团队会把"直连 9066 敲命令"列为禁用操作，所有变更通过平台化流程（工单→校验→推送配置中心→分批生效）落地，管理端口只留作查询与应急通道。

1.6.x 的管理命令风格不同（`reload @@config_all`、`show @@datasource`），2.x 换成 `/*!mycat:xxx*/` 注释指令形态，运维脚本迁移时要整体替换（见第 18 篇不兼容项）。

# 3. 配置中心模式

```yaml
# mycat.yml
server:
  mode: cluster
  configCenter:
    type: nacos
    address: nacos1:8848,nacos2:8848,nacos3:8848
    namespace: mycat2
    group: MYCAT_GROUP
```

```text
Nacos 配置变更流程：
  1. 运维修改 Nacos 中的配置文件
  2. Nacos 推送变更通知给所有 Mycat2 实例
  3. Mycat2 校验新配置
  4. 增量更新（仅更新变更的部分）
  5. 热加载生效
```

**配置中心模式解决了单机 reload 解决不了的两个问题**。一是**一致性广播**：变更只发一次，所有实例在各自节奏内应用到同一份配置，配合版本号还能审计"此刻全集群是否都在 v27"。二是**生效顺序控制**：配置中心推送到达各实例存在秒级时间差，期间集群处于"混合配置"状态——对新增分片这类变更，混合窗口意味着一部分实例知道 dn2、另一部分不知道，同一逻辑表的行数在两拨实例上"看法不同"。**变更类型决定这个窗口是否危险**：加用户、调权重几乎无害；改分片算法则是窗口内路由不一致、直接产生错误路由数据，必须在业务写入停摆或双写迁移的保护下操作（见第 5 节扩容动线）。

ZK 模式（1.6.x 内置、2.x 亦支持）与 Nacos 的机制差异在推送模型：ZK 靠 watcher 回调（session 断开期间的变更要靠启动时全量拉取补偿），Nacos 长轮询 + 本地快照缓存（配置中心整体不可用时实例按最后一次拉取的配置继续运行，**新增实例此时无法启动**——配置中心的可用性要在部署架构上先于 Mycat 满足）。

# 4. 增量配置更新

Mycat2 的配置更新采用**增量策略**，只更新变更的部分：

```text
新增数据源：
  1. 校验新数据源连接可用
  2. 创建连接池
  3. 注册到路由表
  4. 生效（新请求使用新数据源）

修改分片规则：
  1. 校验新规则
  2. 更新路由表
  3. 旧分片连接池逐步关闭
  4. 告警：分片规则变更可能导致数据路由错误

删除表：
  1. 从路由表移除
  2. 关闭对应的数据源连接池
```

增量的关键在"**替换的是元数据对象，不是进程**"：路由表、Schema 定义、用户表这些运行时结构用新版本整体换引用（读多写少，实际是 volatile 引用交换 + CopyOnWrite 思路），进行中的请求持有旧引用走完，新请求看到新引用。因此热加载对**单条 SQL 内部是一致的**——不会出现"路由用旧规则、表结构用新规则"的撕裂；不一致只存在于**实例之间**（上面第 3 节的混合窗口）。

**热生效的边界**必须背下来，这是面试与生产双重高频点：

| 变更项 | 热生效？ | 说明 |
|--------|---------|------|
| 数据源增删改（含心跳参数） | 是 | 新连接池即建即用，旧池排空销毁 |
| 用户/权限/ipWhiteList | 是 | 新连接立即生效；**已建立的前端连接保持登录时的权限快照** |
| 逻辑表/分片规则（新增表） | 是 | 校验后原子替换路由元数据 |
| 分片算法/分片数修改 | 机制上是 | **数据不会自动搬家**，改完旧数据全部路由错乱，必须配合迁移 |
| 全局表新增 dataNode | 是 | 需要先把物理表建好并回填，再改配置 |
| server 级参数（端口、reactor 数、JVM 参数） | 否 | 涉及监听器与线程模型，需重启 |
| mycat.yml 启动引导配置 | 否 | 它本身是"找到配置中心的钥匙"，只能重启换 |
| 后端 MySQL 的表结构（DDL） | 不涉及 | Mycat 的 table metadata 要 reload 才认识新列 |

> **注意**：最后一行是日常最坑的一条——**在 MySQL 上加了列，Mycat 不知道**。1.6.x 时代只能重启；2.x 对对应 schema 做一次 reload 即可刷新列元数据。DDL 变更动线因此固定为："先改所有分片的物理表（gh-ost/pt-osc），再 reload 中间件元数据"，顺序反了会出现"元数据有列但部分分片物理表没有"的半坏状态。

# 5. 在线分片扩容

扩容是动态配置能力价值的最大化体现，但**reload 只解决"让 Mycat 知道新分片"，不解决"把数据搬到新分片"**——后者才是扩容的真工作量。

```text
步骤：
  1. 准备新 MySQL 实例并建表
  2. 在 Mycat2 配置中添加新分片（status=backup）
  3. 【reloadConfig】加载新配置
  4. 数据迁移（全量 + 增量）
  5. 验证数据一致
  6. 修改分片状态为 active
  7. 【reloadConfig】生效

示例配置变更：

// 原配置：2 个分片
{
  "dataNodes": "dn0.orders,dn1.orders",
  "sharding": { "count": 2 }
}

// 新配置：4 个分片
{
  "dataNodes": "dn0.orders,dn1.orders,dn2.orders,dn3.orders",
  "sharding": { "count": 4 }
}
```

流程里 `backup` 状态的设计意图值得点出：**新分片先"存在但不接流量"**——Mycat 路由时把它排除在外，迁移工具与校验脚本却能访问它。这样"配置变更"与"流量变更"被拆成两个独立动作，各自可验证可回滚。

> **设计争议**：取模类算法 `count: 2 → 4` 意味着**几乎所有存量数据的归属分片都变了**（id % 4 与 id % 2 的映射只对一半数据不变），本质是全量 rehash，动保成本巨大。因此分片数在第一天就要按终局规划（如直接建 64/128 个逻辑分片、少实例多逻辑分片地物理合并部署），扩容时只做"逻辑分片搬家"，永远不动 count——这是第 19 篇"容量与扩容纪律"的核心论点。对确实需要 rehash 的扩容，业界更倾向用**双写迁移方案**（新旧两套分片并写 + 存量搬运 + 校验切读）替代上表的"backup 原地扩容"，可回滚性远好于直接改规则。

# 6. 灰度发布配置

```json
// 灰度配置：为新分片设置权重，逐步引入流量
{
  "dataNodes": {
    "dn0": { "weight": 100 },
    "dn1": { "weight": 100 },
    "dn2": { "weight": 5 }    // 新分片，先放 5% 流量
  }
}
```

权重灰度适用于**读写分离负载均衡与多机房就近路由**的流量调整；分片路由本身是确定性的（分片键决定归属），不存在"5% 流量打到新分片"的连续灰度——新分片要么按规则接管一批键区间，要么不接管。两类"灰度"不要混为一谈，配置里的权重字段只作用于前者。

# 7. 配置回滚

```sql
-- 方式 1：管理端口回滚到上一次配置
/*!mycat:rollbackConfig*/

-- 方式 2：Nacos 历史版本回滚
-- 在 Nacos 控制台 → 配置管理 → 历史版本 → 回滚

-- 方式 3：Git 管理的配置文件
git revert <commit>
./mycat reload
```

**回滚的难点不在配置本身，而在"配置背后的事实已经变了"**。数据源地址回滚无害；分片规则回滚的前提是数据没按新规则写过——一旦 active 后有写入落在新分片，回滚配置就制造孤儿数据，必须先停写、把增量倒回去。所以回滚预案要在变更评审时就写清楚：**回滚窗口（过了这个时间点就不能只回配置）、回滚动作序列、验证方法**，而不是留一句"出问题就回滚"。配置中心的历史版本是审计与应急的最后依托，Nacos 保留所有版本但**不会替你判断哪个版本能安全回退**。

# 8. 配置校验

```java
// Mycat2 在加载配置前进行校验
public class ConfigValidator {

    public void validate(SchemaConfig config) {
        // 1. JSON 格式校验
        // 2. 数据源连接可达性校验
        // 3. 分片键在表定义中存在
        // 4. 全局表数据节点一致性
        // 5. 分片算法参数合法性
        // 6. 循环依赖检查（ER 表）
    }
}
```

校验失败的 reload 会被拒绝并保持旧配置运行——这是热加载最重要的安全阀：**错误的配置宁可生效不了，不能生效半截**。但要注意校验的"可达性"探测只保证"此刻能连上"，不保证"密码策略/只读状态/超级权限限制"等业务前提；生产变更平台应把校验清单外扩一层：目标数据源与预期集群拓扑一致、ER 关系上下游表都在配置内、容量水位检查等，都过了才触发 reload。

# 9. 配置变更审计

```yaml
# 配置审计日志
server:
  audit:
    enabled: true
    logFile: /var/log/mycat2/audit.log
```

```text
# audit.log 格式
2024-01-15 10:30:00|admin@192.168.1.100|reloadConfig|SUCCESS
2024-01-15 10:35:00|admin@192.168.1.100|addDataNode|dn3|SUCCESS
2024-01-15 10:40:00|admin@192.168.1.100|updateShardRule|orders|FAILED: invalid count
```

审计日志回答三个问题：**谁、把什么、改成了什么、成没成**。排障时的标准动线是"故障时间点 ± 最近一次配置变更"，没有这条记录，中间件类故障的定位时间会翻倍。注意 audit.log 只记录管理端口动作，配置中心侧的修改记录（Nacos 历史版本）与之互补，两边都要纳入日志采集。

# 10. 最佳实践

1. **变更前备份**：任何配置变更前备份当前配置
2. **变更窗口**：配置变更在业务低峰期进行
3. **灰度验证**：新配置先在测试/预发环境验证
4. **回滚预案**：提前准备回滚操作和应急预案
5. **监控观察**：变更后观察 30 分钟监控指标
6. **分批执行**：多实例环境逐台 reload，观察无异常再下一台

> **行业实践**：把第 6 条进一步平台化——"reload 一台 → 自动比对这台与基准实例的关键指标（错误率、路由命中、RT）→ 无异常自动推进下一台"，即**配置变更的金丝雀发布**。它与第 4 节"混合配置窗口"是配套设计：分批期间集群短暂处于混合版本是可接受的（新旧配置都语义兼容时），这要求变更单里声明"本变更是否容忍混合窗口"，分片规则类变更答案是否为"否"就必须走停写/双写流程而非分批 reload。

# 11. 小结

| 要点 | 结论 |
|------|------|
| 四种变更方式 | 单实例本地文件 + reload、管理端口命令、配置中心推送、HTTP API；集群统一走配置中心 |
| 热生效边界 | 元数据类全部热生效；server/启动级参数需重启；后端 DDL 要 reload 刷列元数据 |
| 最大陷阱 | 分片规则热生效 ≠ 数据迁移完成；reload 前必须理清"配置态"与"数据态"两步 |
| 扩容动线 | backup 状态先挂新分片 → 迁数据 → 校验 → active → reload；能不动 count 就不动 |
| 回滚 | 配置回滚容易，"回滚 + 已写入新分片的数据"要停写倒数据，回滚窗口写进变更单 |
| 安全阀 | 校验失败保持旧配置；审计日志 + 配置中心版本历史是事后定位的双保险 |

一句话：**reload 改变的是 Mycat 的"知识"，不是数据的"位置"**——把这句话贴在每次扩容工单的开头，能避免八成的中间件 P0。下一篇（16 安全）讲这套端口与配置体系在安全面上的边界与加固。
