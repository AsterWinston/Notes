
# 1. Mycat 的历史

Mycat 是国产开源分布式数据库中间件，经历了两个大版本：

```
Mycat 1.6.x (经典版)
  ├── 基于阿里 Cobar 架构演进
  ├── BIO 阻塞 I/O 模型
  ├── MySQL 协议代理 + SQL 解析路由
  ├── 2013-2019 主要维护
  └── 现已停止更新

       ▼ 完全重写

Mycat 2.x (新一代)
  ├── 基于 Vert.x NIO 反应式架构
  ├── 集成 Apache Calcite 查询优化器
  ├── 原生支持分布式事务 XA
  ├── 动态配置热加载
  ├── 支持 MySQL 8.0 完整协议
  └── 2020 至今活跃开发
```

**关键区别**：Mycat2 不是 Mycat1 的升级版，而是**完全重写**。架构、配置格式、内核实现完全不同。

# 2. Mycat2 是什么

Mycat2 是一个**分布式数据库中间件**，作为 MySQL 协议的代理层，对应用透明地将请求路由到后端的多个 MySQL 实例。

```
┌─────────────────────────────────────────────────┐
│                   Application                    │
│         (JDBC/ODBC, 连接 Mycat2 如连接 MySQL)     │
└────────────────────┬────────────────────────────┘
                     │ MySQL Protocol
              ┌──────▼──────┐
              │   Mycat2    │
              │  (Vert.x    │
              │   NIO)      │
              └──┬───┬───┬──┘
                 │   │   │
    ┌────────────┼───┼───┼────────────┐
    ▼            ▼   ▼   ▼            ▼
┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐
│MySQL M │ │MySQL S1│ │MySQL S2│ │MySQL S3│
│(Write) │ │(Read)  │ │(Read)  │ │(Shard) │
└────────┘ └────────┘ └────────┘ └────────┘
```

**核心能力**：

| 能力 | 说明 |
|------|------|
| **读写分离** | 自动路由写请求到 Master，读请求到 Slave |
| **分库分表** | 按分片键水平拆分数据到多个 MySQL 实例 |
| **分布式事务** | 内置 XA 两阶段提交 |
| **SQL 兼容** | 兼容 MySQL 8.0 协议和大部分 SQL 语法 |
| **动态配置** | 在线修改分片规则，无需重启 |
| **全局序列** | Snowflake 等分布式主键生成 |

# 3. Mycat2 vs Mycat1 vs ShardingSphere-Proxy

| 维度 | Mycat 1.6 | Mycat 2.x | ShardingSphere-Proxy |
|------|----------|-----------|---------------------|
| **I/O 模型** | BIO（阻塞） | NIO（Vert.x 反应式） | NIO（Netty） |
| **SQL 解析** | 自研 Druid | Apache Calcite | 自研解析器 |
| **查询优化** | 简单改写 | CBO/RBO 优化器 | 基础改写 |
| **分布式事务** | 弱 XA | 原生 XA | XA/Seata |
| **动态配置** | 需重启 | 热加载 | DistSQL 在线变更 |
| **协议兼容** | MySQL 5.x | MySQL 8.0 完整 | MySQL/PostgreSQL |
| **社区活跃度** | ★☆☆☆☆ | ★★★☆☆ | ★★★★★ |
| **生产成熟度** | 高（存量） | 中（增长中）| 高 |

# 4. 核心设计理念

1. **反应式架构**：基于 Vert.x 事件驱动，单机高并发（数万连接）
2. **协议代理**：完全模拟 MySQL Server 协议，对应用透明
3. **模块化**：Router → Parser → Optimizer → Executor → Merger 管道化处理
4. **Calcite 驱动**：复用 Apache Calcite 的 SQL 解析、校验、优化能力
5. **配置即代码**：JSON 配置文件定义所有逻辑（datasources / schemas / clusters / users）

# 5. 适用场景

- ✓ 单表数据量过大需要分库分表
- ✓ 读写分离（主从架构）
- ✓ 多租户数据隔离
- ✓ 需要透明的分布式数据库访问层
- ✓ 遗留系统无法改造代码但需要拆分数据库
- ✗ 极致的 OLAP 分析场景（考虑 ClickHouse）
- ✗ 需要跨数据库类型的联邦查询（考虑 Presto/Trino）
- ✗ 需要强一致性的金融交易（需额外设计）
