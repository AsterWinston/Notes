
# 1. 什么是MongoDB

MongoDB是一个开源的、跨平台的**面向文档（Document-Oriented）**的NoSQL数据库。它由MongoDB Inc.（前身为10gen公司）开发，使用C++编写，2009年首次发布。MongoDB的名称来源于英文单词"humongous"（巨大的），寓意它能处理海量数据。

MongoDB放弃了传统关系型数据库的表格模型，转而采用类似JSON的BSON（Binary JSON）格式来存储数据。这种设计使得数据的表示更加自然和灵活，特别适合现代应用程序的快速迭代开发。

核心设计理念：
- **面向文档**：数据以类似JSON的文档形式存储，天然支持嵌套结构
- **Schema-less（无模式）**：同一个集合中的文档不需要具有相同的字段结构
- **水平扩展**：通过分片（Sharding）实现数据的横向扩展
- **高性能**：支持内存映射存储引擎（MMAPv1）和WiredTiger存储引擎，提供高性能读写
- **高可用**：通过副本集（Replica Set）提供自动故障转移和数据冗余

# 2. NoSQL概述与分类

NoSQL（Not Only SQL）泛指非关系型数据库，主要解决关系型数据库在以下场景中的局限性：
- 大数据量下的水平扩展困难
- 复杂JOIN操作的性能瓶颈
- 严格的Schema限制导致的数据模型不灵活
- 半结构化/非结构化数据的存储需求

NoSQL数据库的四大分类：

| 分类 | 代表产品 | 数据模型 | 适用场景 |
|------|---------|---------|---------|
| 文档型 | MongoDB、CouchDB | JSON/BSON文档 | 内容管理、用户画像、物联网数据 |
| 键值型 | Redis、Memcached | Key-Value | 缓存、会话存储、排行榜 |
| 列族型 | HBase、Cassandra | 列族存储 | 日志分析、时序数据、大规模写入 |
| 图数据库 | Neo4j、JanusGraph | 节点+关系 | 社交网络、推荐系统、知识图谱 |

## 2.1 文档型数据库的特点

文档型数据库以"文档"为基本数据单元，一个文档相当于关系数据库中的一行记录。文档可以嵌套子文档和数组，形成丰富的层次结构。

```
// MongoDB文档示例
{
    "_id": ObjectId("507f1f77bcf86cd799439011"),
    "name": "张三",
    "age": 28,
    "email": "zhangsan@example.com",
    "address": {
        "city": "北京",
        "street": "长安街",
        "zipcode": "100000"
    },
    "hobbies": ["阅读", "游泳", "编程"],
    "orders": [
        {
            "order_id": "ORD001",
            "amount": 299.00,
            "products": ["书", "笔记本"]
        }
    ]
}
```

# 4. MongoDB核心架构

## 4.1 整体架构层次

```
┌─────────────────────────────────────────┐
│              应用层 (Application)         │
├─────────────────────────────────────────┤
│           驱动层 (Drivers)                │
│   Java/Python/Node.js/C#/Go/...          │
├─────────────────────────────────────────┤
│         查询引擎 (Query Engine)           │
│   查询解析 → 查询优化 → 查询执行            │
├─────────────────────────────────────────┤
│         存储引擎层 (Storage Engine)       │
│      WiredTiger  /  In-Memory            │
├─────────────────────────────────────────┤
│           操作系统 & 文件系统              │
└─────────────────────────────────────────┘
```

## 4.2 核心组件

**mongod（数据库守护进程）**
mongod是MongoDB的核心后台进程，处理所有数据请求、数据访问和执行后台管理操作。它负责：
- 处理客户端的CRUD请求
- 管理数据文件的存储和读取
- 执行索引管理和查询优化
- 参与副本集的选举和数据同步

**mongos（分片路由进程）**
mongos在分片集群中充当查询路由器的角色：
- 接收客户端请求
- 从配置服务器(shard)获取集群元数据
- 将请求路由到正确的分片
- 聚合来自多个分片的结果

**配置服务器（Config Server）**
在分片集群中存储集群的元数据和配置信息：
- 分片键范围与分片的映射关系
- 集群成员的配置信息
- 数据库和集合的分布信息

**mongo（命令行Shell）**
交互式的JavaScript Shell，用于数据库管理和数据操作。MongoDB 6.0之后引入`mongosh`作为新的Shell工具。

# 5. BSON数据格式

## 5.1 什么是BSON

BSON（Binary JSON）是MongoDB用来存储和传输数据的二进制序列化格式。它扩展了JSON的数据类型支持，同时保持了JSON的灵活性。

BSON的设计目标：
- **轻量级**：保持较小的空间开销
- **可遍历**：支持快速扫描和跳过不需要的字段
- **高效**：编解码速度快，适合网络传输和磁盘存储

## 5.2 BSON支持的数据类型

| 类型 | 数字ID | 别名 | 说明 |
|------|--------|------|------|
| Double | 1 | "double" | 64位浮点数 |
| String | 2 | "string" | UTF-8字符串 |
| Object | 3 | "object" | 嵌入文档 |
| Array | 4 | "array" | 数组 |
| Binary data | 5 | "binData" | 二进制数据 |
| ObjectId | 7 | "objectId" | 12字节的文档唯一标识 |
| Boolean | 8 | "bool" | true/false |
| Date | 9 | "date" | UTC时间戳 |

| Regular Expression | 11 | "regex" | 正则表达式 |
| JavaScript | 13 | "javascript" | JavaScript代码 |
| 32-bit Integer | 16 | "int" | 32位整数 |
| Timestamp | 17 | "timestamp" | 内部时间戳，用于oplog |

## 5.3 ObjectId详解

ObjectId是MongoDB默认文档主键，是一个12字节的BSON类型：

```
┌────────────┬───────┬──────┬──────┐
│  4 bytes   │5 bytes│3 bytes│     │
│  timestamp │random │counter│     │
│            │       │       │     │
│  时间戳     │ 随机值 │ 计数器 │     │
└────────────┴───────┴───────┴──────┘
```

- **前4字节**：Unix时间戳（秒级），记录文档创建时间
- **中间5字节**：随机值，由机器标识+进程ID组成
- **后3字节**：自增计数器，初始值为随机数

特性：
- 全局唯一（概率性唯一，非绝对唯一）
- 可以在客户端生成，无需服务端协调
- 天然按创建时间排序
- 适合分片集群（分片键使用_id时分布较均匀）

```
ObjectId生成示例：
507f1f77bcf86cd799439011

解析：
507f1f77 → 时间戳（2012-10-17 20:46:47）
bcf86c  → 机器标识
d79943  → 进程ID
9011    → 计数器
```

# 7. MongoDB的CAP理论与最终一致性

## 7.1 CAP定理

MongoDB在CAP（一致性、可用性、分区容错性）中的定位：

- **单节点**：提供强一致性（C + A，但不具备P）
- **副本集（默认配置）**：采用最终一致性模型，写操作在主节点执行，读可以从从节点读（AP优先）
- **副本集（write concern majority + read concern majority）**：可以配置为强一致性（CP权衡）
- **分片集群**：在分片层面实现数据分区

## 7.2 写关注（Write Concern）

```javascript
// 写关注级别
db.collection.insertOne(
    { name: "test" },
    { writeConcern: { w: "majority", j: true, wtimeout: 5000 } }
)
```

| 值 | 含义 |
|----|------|
| 0 | 不等待任何确认（异步写入，性能最高） |
| 1 | 等待主节点确认（默认） |
| 2 | 等待至少2个节点确认 |
| "majority" | 等待大多数节点确认 |
| \<number\> | 等待指定数量的节点确认 |

## 7.3 读关注（Read Concern）

| 级别 | 说明 |
|------|------|
| "local" | 返回节点最新数据（可能回滚，默认） |
| "available" | 读取节点上可用的数据（分片集群） |
| "majority" | 返回已被大多数节点确认的数据 |
| "linearizable" | 线性读取，保证读到的数据不会回滚 |
| "snapshot" | 快照读（4.0+，用于事务） |

# 8. MongoDB的使用场景

## 8.1 适用场景

- **内容管理系统（CMS）**：灵活的文档模型适合存储文章、评论、多媒体等结构化程度不一的内容
- **用户画像与个性化推荐**：每个用户的标签、行为数据差异大，文档模型天然适配
- **物联网（IoT）与时序数据**：MongoDB 5.0+原生时序集合，支持海量设备数据存储
- **实时分析与日志管理**：聚合框架支持复杂分析和实时数据处理
- **地理位置数据**：内置地理空间索引和查询，适合LBS应用
- **游戏数据**：玩家数据、排行榜、装备信息等嵌套数据
- **电商商品目录**：不同商品属性差异大，灵活的Schema适应多品类管理

## 8.2 不适用场景

- **高度事务性系统**（如银行核心账务）：虽然有ACID事务支持，但性能不如传统关系型数据库
- **复杂多表关联查询**：虽然支持$lookup，但大量JOIN不是文档数据库的优势场景
- **数据之间强关联且关系固定**：如ERP系统，传统RDBMS更合适
- **OLAP分析场景**：大规模数据分析应使用ClickHouse、Doris等OLAP数据库
