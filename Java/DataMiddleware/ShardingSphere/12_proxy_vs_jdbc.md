# 1. 架构差异

两种形态的本质区别在于：**分片逻辑是嵌入业务进程（同进程 SDK），还是独立部署为数据库代理（跨进程网关）**。ShardingSphere-JDBC 本质上是一个"增强版 JDBC 驱动"，它在应用进程内完成 SQL 解析、路由、改写与归并，业务代码拿到的仍然是一个标准的 `DataSource`/`Connection`；ShardingSphere-Proxy 则接管了数据库的前端网络协议（MySQL/PostgreSQL/openGauss 协议），把 ShardingSphere 引擎跑在一个独立的 Netty 进程里，对应用而言它"伪装"成了一个数据库。

```text
ShardingSphere-JDBC                    ShardingSphere-Proxy
┌──────────────────┐                   ┌──────────┐
│   Application    │                   │   App    │  ← 任意语言
│ ┌──────────────┐ │                   └────┬─────┘
│ │ Sharding-JDBC│ │                        │ MySQL Protocol
│ │   (SDK)      │ │                   ┌────▼─────┐
│ └──────┬───────┘ │                   │  Proxy   │
│        │ JDBC    │                   └────┬─────┘
└────────┼─────────┘                        │ JDBC
         ▼                                  ▼
    ┌──────────┐                       ┌──────────┐
    │  MySQL   │                       │  MySQL   │
    └──────────┘                       └──────────┘

网络：0 跳                               网络：+1 跳
```

## 1.1 连接模型

**连接模型是两者最容易被低估的差异**。JDBC 模式下，每个应用实例独立持有物理连接池，逻辑上一个 `Connection` 在路由到 N 个分片时会**同时占用 N 个物理连接**（`max-connections-size-per-query` 控制上限），分片越多连接放大越严重——1000 个应用线程做 4 库查询，理论峰值就是 4000 个物理连接直压数据库。Proxy 模式则是经典的前后端分离模型：前端用 Netty 维护 M 个客户端会话，后端由 Proxy 统一维护 N 个物理连接，**M 个应用共享、收敛到 N**，天然具备连接池治理能力（统一的最大连接数、熔断、限流）。

| 维度 | JDBC | Proxy |
|------|------|-------|
| 物理连接归属 | 各应用独立持有 | Proxy 集中托管 |
| 连接放大 | 线程数 × 路由分片数 | 前端会话与后端连接解耦 |
| 跨应用连接复用 | 无 | 有（多应用共享后端池） |
| 事务中连接行为 | 本地事务逐连接提交；XA 强制一数据源一连接 | 同左，且对客户端表现为单连接 |

## 1.2 执行链路差异

JDBC 的解析、路由、归并全部消耗**应用自己的 JVM 线程和堆内存**：一次跨 8 分片的大结果集查询，归并所需的内存由业务进程买单，OOM 会打爆应用本身。Proxy 把这些开销隔离到独立进程，应用侧只是一个普通 MySQL 客户端，代价是多了**一次协议编解码和一次网络往返**，且 Proxy 自身成为容量与高可用问题（详见第 4 节）。

> **注意**：两种形态共用同一套引擎代码（Parse → Rewrite → Route → Execute → Merge），SQL 支持度、分片算法、改写行为完全一致；选型时不要在"功能"上纠结，纠结点应该放在连接模型、运维模型和语言边界上。

# 2. 功能对比

| 维度 | JDBC | Proxy |
|------|------|------|
| **数据分片** | ✓ | ✓ |
| **读写分离** | ✓ | ✓ |
| **数据加密** | ✓ | ✓ |
| **影子库** | ✓ | ✓ |
| **分布式事务** | ✓（内置） | ✓（内置） |
| **DistSQL** | ✗ | ✓ |
| **治理中心** | 可选（注册中心） | 内置 |
| **可观测性** | Agent 插件 | Agent 插件 |
| **异构语言** | ✗（仅 Java） | ✓ |
| **连接池** | 应用自行管理 | Proxy 统一管理 |

需要澄清两点：第一，**DistSQL 只存在于 Proxy 的接入层**，JDBC 没有协议入口，无法用 `CREATE SHARDING TABLE RULE` 在线改规则，但这不代表 JDBC 看不到 DistSQL 的变更——Cluster 模式下规则集中存储在注册中心，JDBC 实例监听并热加载，**规则的"写入口"与"生效面"是两回事**。第二，Proxy 的前端协议覆盖范围小于 JDBC 的后端数据库范围：Proxy 5.5.x 前端支持 MySQL、PostgreSQL、openGauss 协议，Oracle/SQL Server 只能走 JDBC 接入。

## 2.1 第三种形态：Sidecar（Database Mesh）

在 Kubernetes 场景下还存在第三种部署形态：把 ShardingSphere-Proxy **以 Sidecar 容器的方式注入到每个应用 Pod**，即社区曾孵化的 Database Mesh 方向。Go/Java 混部的 Pod 各自挂着本地 Proxy，形态上像 JDBC 一样"零距离"，能力上又是 Proxy（多语言、协议接入）。

```text
┌────────────── Pod ──────────────┐
│  ┌──────────┐   ┌────────────┐  │
│  │ 应用容器  │──▶│ Proxy 容器  │──┼─▶ MySQL
│  └──────────┘127.0.0.1└────────┘ │
└──────────────────────────────────┘
```

**Sidecar 的本质是用资源换架构统一**：省掉了集中式 Proxy 的单点容量问题和跨节点网络跳数，但每个 Pod 都要为 Proxy 付出 1-2 核 2-4GB 的资源，且 Proxy 版本随镜像大量复制、变更半径失控，运维成本并没有真正消失，只是从"网关运维"变成了"网格运维"。实践中它适合 Proxy 集中部署有明确瓶颈（跨 AZ 延迟、隔离要求高）的团队，不适合作为默认选择。

> **设计争议**：Sidecar 形态在社区始终热度有限，官方长期主推 JDBC + 集中式 Proxy 双形态。反对者的理由很实际：数据库连接的有状态长事务模型与 Sidecar"可随意重启"的云原生假设冲突，一个 Proxy sidecar 重启就可能打断该 Pod 全部在途事务。

# 3. 性能对比

```text
基准测试：4 分片，单表 1000 万行，查询 WHERE shardkey = ?

| 模式               | QPS     | AVG RT | P99 RT |
|--------------------|---------|--------|--------|
| 直连 MySQL（无分片）| 30000   | 3ms    | 8ms    |
| ShardingSphere-JDBC | 28000   | 4ms    | 10ms   |
| ShardingSphere-Proxy| 15000   | 7ms    | 18ms   |

JDBC 模式性能损耗约 7%，Proxy 模式约 50%。
Proxy 额外开销主要来自：网络转发 + MySQL 协议编解码。
```

## 3.1 损耗来源拆解

Proxy 的损耗可以拆成四项：**① 网络多一跳**（同机房 0.2-0.5ms，跨 AZ 可能 1-2ms，对 3ms 级的点查是显著比例）；**② 协议编解码**（MySQL 包协议解析、结果集行列转码，大结果集查询此项被放大）；**③ 内存拷贝与 GC**（Proxy 是 Netty + 堆内缓冲，吞吐高时 GC 压力集中在 Proxy 进程）；**④ 会话串行化**（同一客户端连接上的语句无法像 JDBC 那样并发打散到多物理连接）。JDBC 的损耗则基本只剩**① 解析/路由/归并的 CPU 开销**（官方空规则压测结论是损耗 1%-10%），以及连接模型放大问题。

> **注意**：上表是经验参考值而非绝对结论。真实生产里 Proxy 与 JDBC 的差距往往比压测小——当一次查询要扇出到 8 个分片时，瓶颈在数据库扫描与网络并发，Proxy 的协议开销占比被稀释；反之单分片点查占比高的系统，Proxy 的固定跳数开销就非常刺眼。

## 3.2 两种形态各自的调优抓手

JDBC 侧核心参数：`kernel-executor-size`（归并/执行线程）、`max-connections-size-per-query`（扇出上限）、连接池容量；Proxy 侧核心参数：`proxy-frontend-flush-threshold`、`proxy-frontend-write-high-water-mark`、前后端线程组，以及后端连接池 `maxPoolSize`。**Proxy 还有一个隐藏红利**：它支持 MySQL 二进制协议（prepared statement 透传），配合 `useServerPrepStmts` 对高 QPS 短 SQL 场景比文本协议友好；JDBC 侧则由驱动层控制。

# 4. 运维复杂度对比

| 维度 | JDBC | Proxy |
|------|------|------|
| 部署 | 随应用发布 | 独立部署维护 |
| 配置变更 | 修改 YAML + 重启 | DistSQL 在线变更 |
| 多应用共享 | 各自配置 | 共享 Proxy |
| 连接数管理 | 应用 1:N DB | 应用 M:1 Proxy 1:N DB |
| 升级 | 依赖冲突风险 | 独立平滑升级 |
| 高可用 | 随应用 | 需独立实现（LB + 多实例） |

## 4.1 版本升级路径

**JDBC 的升级成本是一次全量应用回归**。ShardingSphere-JDBC 作为依赖嵌入应用，升级意味着所有引用它的应用都要重新编译、回归、发布，而且它传递依赖 Netty、Guava、Groovy（行表达式引擎）等公共库，**依赖冲突是 Java 团队升级 JDBC 时最常踩的坑**（典型如应用自带旧版 Guava 导致 Groovy 表达式引擎 NoSuchMethodError）。Proxy 升级则是集中式的：多个 Proxy 实例挂在 LB 后面，摘流→滚动重启→回流量，应用完全无感；但要注意 **Proxy 升级会切断客户端连接**，长事务、大结果集拉取中的连接会直接失败，升级窗口需要应用侧具备重连能力。

## 4.2 故障半径与高可用

JDBC 没有"中间层宕机"这个概念——它的可用性等于应用可用性，分片逻辑故障只影响单个应用实例，故障半径最小；Proxy 是多了一层进程，**Proxy 集群就是新的单点**，必须至少 2 实例 + LB，并且注册中心（Cluster 模式）故障时 Proxy 无法扩容和变更规则（存量会话仍可运行）。从 SRE 视角：**JDBC 是"没有新组件"的高可用，Proxy 是"多一个组件要运维"的高可用**，这笔账要和团队运维能力一起算。

> **行业实践**：多数互联网公司的演进路线是先 JDBC（起步快、性能好），当出现异构语言接入、多应用共享一套分片规则、或需要 DBA 用标准 MySQL 客户端直连治理时，再引入 Proxy，最终形成 Java 走 JDBC、其余走 Proxy 的混合格局。

# 5. 混合部署

混合部署指 **Proxy 跑异构应用 + JDBC 跑 Java 应用**，两套形态共享同一个数据分片体系：

```text
┌─────────────────────────────────────────┐
│             混合架构                      │
│                                          │
│  Java 应用 → ShardingSphere-JDBC (直连)   │
│  Go 应用   → ShardingSphere-Proxy → DB   │
│  Python    → ShardingSphere-Proxy → DB   │
│                                          │
│  共享同一套 MySQL 集群和分片规则           │
└─────────────────────────────────────────┘
```

**混合部署注意事项**：
- JDBC 和 Proxy 必须使用相同的分片规则
- Cluster 模式下通过注册中心同步配置
- Proxy 使用 DistSQL 变更 → JDBC 应用重启生效（或动态加载）

补充三点工程纪律。第一，**规则只能有一个写入口**：混合部署时把 DistSQL 变更权限收敛到 Proxy 一侧，JDBC 侧 YAML 只作首次引导（bootstrap），否则两边各改各的，注册中心里的规则与 YAML 迟早漂移。第二，**同一逻辑库名必须对齐**：JDBC 与 Proxy 的 schema 命名不一致时，同一个分片规则会被当成两套配置分别初始化，连接池翻倍。第三，**变更顺序**：先 Proxy 后 JDBC，DistSQL 变更后在任一 Proxy 上 `PREVIEW SQL` 验证路由，再抽一个 JDBC 实例验证热加载是否生效，最后全量确认。

## 5.1 混合模式下的 XA 陷阱

XA 事务在混合部署下有一个隐蔽问题：JDBC 与 Proxy 都各自持有到同一 MySQL 的物理连接，**跨形态的"同一个分布式事务"是不存在的**——一个 Java 服务的事务边界只覆盖它的 JDBC 连接，Go 服务经由 Proxy 的部分由 Proxy 自己的事务管理器接管。因此跨 Java/Go 的业务链路一致性不能指望 ShardingSphere 的 XA，只能靠业务层补偿或 Seata 全局事务，这一点在方案设计阶段就要说清楚。

# 6. 选型决策

```text
是否需要支持非 Java 语言？
  ├── 是 → ShardingSphere-Proxy
  └── 否 → 追求极致性能？
            ├── 是 → ShardingSphere-JDBC
            └── 否 → 需要 DistSQL 在线变更？
                      ├── 是 → ShardingSphere-Proxy
                      └── 否 → 任选
```

决策树的叶子"任选"其实不该随便选，补三条经验规则：**数据库最大连接数紧张**（大量应用实例 × 扇出）→ 选 Proxy 做连接收敛；**团队没有能力运维一个有状态网关**→ 选 JDBC，别为用不上的 DistSQL 背上 Proxy 的运维债；**多应用共享同一套分片规则且变更频繁**（如规则按周迭代的双十一活动配置）→ 选 Proxy 或"JDBC + Cluster 模式"。另外提醒：形态选型与模式选型（Standalone/Cluster）是两个正交决定，JDBC 也可以用 Cluster 模式获得统一规则存储与动态刷新。

# 7. 迁移路径

```text
阶段 1：单库 → ShardingSphere-JDBC 分片（Java 应用）
阶段 2：需要支持其他语言 → 引入 ShardingSphere-Proxy
阶段 3：Proxy 稳定后，逐步将 Java 应用也迁移至 Proxy（统一治理）
```

阶段 1 到阶段 2 是**增量引入**，风险最低：新语言应用先接 Proxy，存量 Java 应用不动。阶段 2 到阶段 3 是**全量切换**，属于架构迁移，执行纪律是：**永远不要在数据迁移的同时切换接入形态**——扩缩容/数据迁移用 ShardingSphere 的 Migration（`MIGRATE TABLE INTO`）或双写方案单独完成，形态切换只改连接串与依赖，一次只动一个变量。切换期间的验证手段：JDBC 实例开 `sql-show`、Proxy 上用 `PREVIEW SQL`，对同一批业务 SQL 比对 Actual SQL 是否一致，一致即认为路由语义对齐，可放心灰度。

> **设计考量**：
> - **默认推荐 JDBC 起步**：零新增组件、性能最优，Java 单体/微服务体系内几乎没有任何理由第一天上 Proxy
> - **Proxy 适合平台化**：当"数据接入治理"成为平台职能（多语言、DBA 直连、连接配额、审计），Proxy 的独立进程形态才体现出不可替代性
> - **Sidecar 谨慎评估**：只有跨 AZ 延迟敏感或强隔离需求明确的 K8s 场景才值得付出每 Pod 的资源税

# 8. 小结

1. **本质区别是连接模型**：JDBC 进程内扇出（线程数×分片数的连接放大），Proxy 前后端解耦做 M:1 连接收敛
2. **性能选 JDBC，语言边界与平台治理选 Proxy**，功能层面两者等价（同一套引擎）
3. **Sidecar 是用资源换架构统一**，默认不建议，跨 AZ 敏感场景再评估
4. **混合部署纪律**：规则单一写入口、schema 对齐、先 Proxy 后 JDBC、变更不叠加数据迁移
5. **升级路径**：JDBC 升级=全量应用回归，Proxy 升级=滚动摘流但会断会话
