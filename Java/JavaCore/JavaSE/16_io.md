第 15 篇讲了 `File`，它只回答了"文件在哪"；真正把数据读进来、写出去的，是 `java.io` 下那套以 `InputStream` / `OutputStream` / `Reader` / `Writer` 为根的**流体系**。本篇先讲清流的分类与继承体系，再逐个讲透字节流、字符流、缓冲流、转换流、序列化流、打印流的用法与坑，重点落在**为什么要有这么多层、每一层解决什么问题**——这四组基类看起来繁琐，但理解了"装饰器叠加"这一个设计思路，整套 API 就变得非常有规律。

# 1. IO 流概述与分类

## 1.1 什么是 IO 流

**IO 流（Input/Output Stream）是程序与外部世界交换数据时的一条"通道"。** 外部世界可能是磁盘文件、网络连接、内存数组、标准输入输出，但对程序来说，它们的抽象都一样：**能不断地往里读、往外写。**

把这个抽象做出来，好处是显而易见的：读文件、读网络、读内存用的是同一套 API，代码在它们之间迁移几乎不用改。Java 里这条"通道"被建模成对象，因此：

1. 用完必须**关闭**（`close()`），否则操作系统资源（文件句柄、socket）会泄漏；
2. 操作可能失败（磁盘满、网络断、权限不足），因此绝大多数方法都抛 `IOException`；
3. 数据是**顺序流动**的，流一旦读过就不能回头（`InputStream` 没有"回到开头"的方法，要重读只能重新打开）。

## 1.2 按流向分类

最粗的一层分类是方向：

| 类别 | 基类 | 含义 | 典型实现 |
|------|------|------|---------|
| **输入流** | `InputStream`（字节）、`Reader`（字符） | 从数据源**读入**程序 | `FileInputStream`、`BufferedReader` |
| **输出流** | `OutputStream`（字节）、`Writer`（字符） | 从程序**写出**到数据目标 | `FileOutputStream`、`BufferedWriter` |

注意"输入 / 输出"是**站在程序的角度**定义的，不是站在文件的角度。从文件读数据进程序叫"输入流"，从程序把数据写到文件叫"输出流"——这个视角一旦搞反，看到 `FileInputStream` 是"读书"会别扭很久。

## 1.3 按数据单位分类：字节流 vs 字符流

第二层分类是**处理的数据单位**，这是整套 IO 中最重要的一个划分：

| 维度 | 字节流 | 字符流 |
|------|--------|--------|
| 基类 | `InputStream` / `OutputStream` | `Reader` / `Writer` |
| 数据单位 | **字节**（8 位，`byte`） | **字符**（`char`，UTF-16 码元） |
| 是否依赖编码 | **不依赖**，原样搬运 | **依赖**，读写时都要按字符集编解码 |
| 能处理的数据 | **任意数据**：文本、图片、音频、压缩包、可执行文件 | **只适合文本** |
| 方法名 | `read()` / `write()` | `read()` / `write()`，另有 `readLine()` / `newLine()` |
| 缓冲区 | 通常无（缓冲流除外） | **自带缓冲区** |

一句话总结：**字节流是万能的，字符流只适合文本，但它替你做掉了编解码。**

```text
   程序内存                    磁盘 / 网络
  ┌────────┐                ┌──────────────┐
  │ String │                │ 一堆 0 和 1   │
  │ "你好" │                │ E4 BD A0 ... │
  └───┬────┘                └──────┬───────┘
      │                            │
      │  字符流：自动编码/解码        │
      │  Reader / Writer ──────────▶│
      │                            │
      │  字节流：原样搬运            │
      │  InputStream / OutputStream │
      └────────────────────────────▶
```

## 1.4 该怎么选

| 场景 | 选择 |
|------|------|
| 读取 / 写入**文本文件** | **字符流**（`FileReader` / `FileWriter`，或 `BufferedReader` / `BufferedWriter`） |
| 复制图片、音频、视频、zip、可执行文件 | **只能用字节流** |
| 网络传输（socket）、序列化 | **字节流**（内容是二进制，字符流会破坏数据） |
| 需要按行读取文本 | **`BufferedReader`** |
| 需要指定字符集读写文本 | **转换流**（`InputStreamReader` / `OutputStreamWriter`）或 `Files.newBufferedReader` |
| 需要把对象存到文件 | 序列化流（`ObjectOutputStream`），见第 10 节 |

> **陷阱**：用字符流去读写图片，会让文件**彻底损坏**。原因是 `Reader` 会把读到的字节按某个字符集**解码**成 `char`，而图片的字节序列很可能不是合法编码，解码时会**用替换字符 `\uFFFD` 顶替非法字节**——信息在这个环节已经丢了，再怎么写回去也恢复不了。判断标准很简单：**能用记事本正常打开看懂的就是文本，否则一律用字节流。**

# 2. IO 流的继承体系

四组基类都是抽象类，都直接继承 `Object`，彼此之间没有继承关系（`Reader` 不是 `InputStream` 的子类）。所有具体流都挂在其中某一个之下：

```text
                              ┌──────────┐
                              │  Object  │
                              └────┬─────┘
        ┌──────────────┬───────────┴───────────┬───────────────┐
        │              │                       │               │
  ┌─────▼─────┐  ┌─────▼──────┐          ┌─────▼─────┐  ┌──────▼─────┐
  │InputStream│  │OutputStream│          │  Reader   │  │   Writer   │
  │ 字节输入   │  │  字节输出   │          │  字符输入  │  │  字符输出   │
  └─────┬─────┘  └─────┬──────┘          └─────┬─────┘  └──────┬─────┘
        │              │                       │               │
        ▼              ▼                       ▼               ▼
  （见下方四个列表）
```

```text
  ┌─────────────────────────────┐   ┌──────────────────────────────┐
  │  InputStream（字节输入）      │   │  OutputStream（字节输出）      │
  ├─────────────────────────────┤   ├──────────────────────────────┤
  │  ├─ FileInputStream         │   │  ├─ FileOutputStream         │
  │  ├─ ByteArrayInputStream    │   │  ├─ ByteArrayOutputStream    │
  │  ├─ ObjectInputStream       │   │  ├─ ObjectOutputStream       │
  │  ├─ DataInputStream         │   │  ├─ DataOutputStream         │
  │  ├─ SequenceInputStream     │   │  ├─ PipedOutputStream        │
  │  ├─ PipedInputStream        │   │  ├─ FilterOutputStream       │
  │  ├─ FilterInputStream       │   │  │     ├─ BufferedOutputStream│
  │  │     ├─ BufferedInputStream│  │  │     ├─ DataOutputStream   │
  │  │     ├─ DataInputStream   │   │  │     └─ PrintStream        │
  │  │     └─ PushbackInputStream│  │  └─ (ZipOutputStream 等)     │
  │  ├─ ZipInputStream          │   │                              │
  │  └─ (抽象，不能直接 new)     │   │  (抽象，不能直接 new)         │
  └─────────────────────────────┘   └──────────────────────────────┘

  ┌─────────────────────────────┐   ┌──────────────────────────────┐
  │  Reader（字符输入）           │   │  Writer（字符输出）            │
  ├─────────────────────────────┤   ├──────────────────────────────┤
  │  ├─ FileReader              │   │  ├─ FileWriter               │
  │  ├─ CharArrayReader         │   │  ├─ CharArrayWriter          │
  │  ├─ StringReader            │   │  ├─ StringWriter             │
  │  ├─ PipedReader             │   │  ├─ PipedWriter              │
  │  ├─ InputStreamReader       │   │  ├─ OutputStreamWriter       │
  │  │     └─ FileReader        │   │  │     └─ FileWriter         │
  │  ├─ BufferedReader          │   │  ├─ BufferedWriter           │
  │  │     └─ LineNumberReader  │   │  ├─ FilterWriter             │
  │  └─ FilterReader            │   │  └─ PrintWriter              │
  └─────────────────────────────┘   └──────────────────────────────┘
```

这套结构里有一个**极易搞错**的点，必须单独讲：

| 常见误解 | 事实 |
|---------|------|
| `BufferedInputStream` 继承 `FileInputStream` | ✗ 它继承 **`FilterInputStream`**，包装的是**任意** `InputStream` |
| `BufferedOutputStream` 继承 `FileOutputStream` | ✗ 同理，继承 `FilterOutputStream` |
| `PrintStream` 继承 `FileOutputStream` | ✗ 它继承 **`FilterOutputStream`**，构造参数是 `OutputStream` |
| `FileReader` 是独立实现 | ✗ 它是 `InputStreamReader` 的**便捷子类**，内部固定用平台默认字符集 |

**为什么会这样？** 因为这批流的设计采用了**装饰器模式**：`FileInputStream` 是"能读文件"的基础流，`BufferedInputStream` 是"能加缓冲"的装饰器。装饰器只认基类 `InputStream`，因此可以套在 `FileInputStream`、`ByteArrayInputStream`、甚至网络流上，**能力可以任意组合**：

```text
   new BufferedReader(                             最外层：提供 readLine()
       new InputStreamReader(                      中间层：字节 → 字符，指定 GBK
           new BufferedInputStream(                内层：给原始读加 8192 缓冲
               new FileInputStream("d.txt")),      最内层：真正打开文件
           "GBK"))
```

**看懂这行嵌套，就看懂了整个 Java IO 的设计哲学**：每一层只做一件事，通过层层包装组合出需要的能力。这也是为什么"读文件要写这么长一串"——不是 Java 啰嗦，而是它把"打开文件""缓冲""解码"这三件独立的事显式表达了出来。

# 3. 字节流：FileOutputStream 与 FileInputStream

## 3.1 FileOutputStream

`FileOutputStream` 负责把字节写到文件。

| 构造方法 | 说明 |
|---------|------|
| `FileOutputStream(String name)` | 按路径打开，**默认覆盖**已有内容 |
| `FileOutputStream(String name, boolean append)` | `append = true` 时**追加**到末尾 |
| `FileOutputStream(File file)` | 用 `File` 对象打开 |
| `FileOutputStream(File file, boolean append)` | `File` + 追加开关 |

关于构造方法有三件事必须记住：

1. **文件不存在会自动创建**，但**父目录必须已存在**，否则抛 `FileNotFoundException`；
2. **不传 `append` 时默认是覆盖**——每次打开都会把文件截断为 0 字节，即使这一行只写一个字。这是初学者最容易丢数据的坑；
3. 打开一个**目录**、或者文件**没有写权限**，都会抛 `FileNotFoundException`（注意不是 `IOException`）。

| 成员方法 | 说明 |
|---------|------|
| `void write(int b)` | 写入 `b` 的**低 8 位**（高 24 位被丢弃） |
| `void write(byte[] b)` | 写入整个字节数组 |
| `void write(byte[] b, int off, int len)` | 从 `off` 开始写 `len` 个字节 |
| `void close()` | 关闭流并释放资源 |
| `void flush()` | 字节流默认无缓冲，此方法几乎是空操作（见第 5 节） |

```java
import java.io.FileOutputStream;
import java.io.IOException;

public class WriteByteDemo {
    public static void main(String[] args) throws IOException {
        // 父目录 D:/data 必须已存在，否则抛 FileNotFoundException
        try (FileOutputStream fos = new FileOutputStream("D:/data/out.txt")) {
            fos.write(97);                              // 97 是 'a' 的 ASCII 码
            fos.write(new byte[]{98, 99, 100});         // 写入 b、c、d
            fos.write("efg".getBytes("UTF-8"));         // 字符串先编码成字节
            fos.write(new byte[]{'h', 'i', 'j'}, 1, 2); // 从下标 1 开始写 2 个：ij
        }
        System.out.println(java.nio.file.Files.readString(java.nio.file.Path.of("D:/data/out.txt")));
    }
}
/* 输出：
abcdefgij
*/
```

> **陷阱**：`write(int b)` 写的是**低 8 位**。写 `fos.write('你')` 不会写出"你"字，而是把 '你'（`\u4F60` = 0x4F60）的低 8 位 `0x60` 写进文件——得到一个乱码字节。**字符流才能写字符，字节流只认字节。**

## 3.2 FileInputStream

| 构造方法 | 说明 |
|---------|------|
| `FileInputStream(File file)` | 用 `File` 打开 |
| `FileInputStream(String name)` | 用路径打开 |

| 成员方法 | 说明 |
|---------|------|
| `int read()` | 读**一个字节**，返回 `0~255`；读到末尾返回 **`-1`** |
| `int read(byte[] b)` | 读数据填入 `b`，返回**实际读到的字节数**；一个都读不到返回 `-1` |
| `int read(byte[] b, int off, int len)` | 从 `off` 开始最多填 `len` 个字节 |
| `int available()` | 剩余可读字节数的**估计值**（不是精确值，不能用来一次性分配） |
| `void close()` | 关闭流 |

`read()` 的返回值语义是**最容易写错**的地方：

| 返回值 | 含义 |
|--------|------|
| `-1` | **读到末尾（EOF）**，唯一表示"结束"的信号 |
| `0 ~ 255` | 读到的那个字节的值 |
| 为什么不是 `byte` 类型？ | 因为 `byte` 是 `-128~127`，装不下"用 `-1` 表示 EOF"这个额外信息 |

```java
import java.io.FileInputStream;
import java.io.IOException;

public class ReadByteDemo {
    public static void main(String[] args) throws IOException {
        // 逐个字节读
        try (FileInputStream fis = new FileInputStream("D:/data/out.txt")) {
            int b;
            StringBuilder sb = new StringBuilder();
            // 注意：必须用 int 接收！用 byte 接收永远不等于 -1，会死循环
            while ((b = fis.read()) != -1) {
                sb.append((char) b);
            }
            System.out.println("逐字节读 = " + sb);
        }

        // 用数组批量读，效率高得多
        try (FileInputStream fis = new FileInputStream("D:/data/out.txt")) {
            byte[] buf = new byte[1024];
            int len;
            StringBuilder sb = new StringBuilder();
            while ((len = fis.read(buf)) != -1) {
                // 关键：用 len 而不是 buf.length！最后一次可能只读到了一部分
                sb.append(new String(buf, 0, len, "UTF-8"));
            }
            System.out.println("按数组读 = " + sb);
        }
    }
}
/* 输出：
逐字节读 = abcdefgij
按数组读 = abcdefgij
*/
```

> **陷阱**：`new String(buf, 0, len, "UTF-8")` 里的 `len` 一定不能用 `buf.length()`。最后一次 `read()` 通常只填了一部分，用 `buf.length()` 会把**上一轮的残留数据**也拼进来，文件末尾出现莫名其妙的重复内容。这个 bug 在文件大小不是缓冲区整数倍时才暴露，非常隐蔽。

## 3.3 完整示例：文件复制

把两边合起来，就是最经典的"字节流复制文件"。这里顺带看看**缓冲带来的巨大差距**：

```java
import java.io.*;

public class CopyDemo {
    public static void main(String[] args) throws IOException {
        // 先造一个 8MB 的测试文件
        byte[] data = new byte[8 * 1024 * 1024];
        for (int i = 0; i < data.length; i++) data[i] = (byte) (i % 251);
        try (FileOutputStream fos = new FileOutputStream("big.dat")) { fos.write(data); }

        // 方式一：无缓冲，一个字节一个字节搬
        long t1 = System.currentTimeMillis();
        try (InputStream in = new FileInputStream("big.dat");
             OutputStream out = new FileOutputStream("copy1.dat")) {
            int b;
            while ((b = in.read()) != -1) out.write(b);
        }
        long t2 = System.currentTimeMillis();

        // 方式二：外面套一层缓冲流，写法完全一样，速度天差地别
        try (InputStream in = new BufferedInputStream(new FileInputStream("big.dat"));
             OutputStream out = new BufferedOutputStream(new FileOutputStream("copy2.dat"))) {
            int b;
            while ((b = in.read()) != -1) out.write(b);
        }
        long t3 = System.currentTimeMillis();

        System.out.println("无缓冲逐字节复制 8MB = " + (t2 - t1) + " ms");
        System.out.println("有缓冲逐字节复制 8MB = " + (t3 - t2) + " ms");
        System.out.println("加速比 ≈ " + ((t2 - t1) / Math.max(1, t3 - t2)) + " 倍");
    }
}
/* 输出（本机实测，具体数字随机器变化，但量级差异稳定）：
无缓冲逐字节复制 8MB = 27344 ms
有缓冲逐字节复制 8MB = 330 ms
加速比 ≈ 82 倍
*/
```

**82 倍**。代码几乎一模一样，只多套了两层。原因在 8.1 节展开——核心是"每一次 `read()` 都是一次系统调用"。

## 3.4 换行符：一个被低估的跨平台问题

写文本时,"换行"这件事在三大平台上并不统一：

| 平台 | 换行符 | 转义写法 |
|------|--------|---------|
| Windows | `CR LF` | `\r\n` |
| Linux / macOS（OS X 之后） | `LF` | `\n` |
| 早期 Mac OS（已淘汰） | `CR` | `\r` |

```java
// ✗ 写死 \n：在 Windows 记事本里打开会显示成一行（旧版记事本不认单独的 \n）
fos.write("第一行\n第二行\n".getBytes("UTF-8"));

// ✓ 正确：用平台无关的换行符
fos.write(("第一行" + System.lineSeparator() + "第二行").getBytes("UTF-8"));

// ✓ 正确：用字符流时交给 BufferedWriter 处理
bw.write("第一行");
bw.newLine();          // 自动写出本平台的换行符
bw.write("第二行");
```

> **最佳实践**：写文本文件一律用 **`System.lineSeparator()`** 或 **`BufferedWriter.newLine()`**，不要写死 `\n`。反过来，**读**文件时不必操心——`BufferedReader.readLine()` 和 `Files.readAllLines()` 会正确识别三种换行符。

# 4. 资源关闭：从 finally 到 try-with-resources

## 4.1 为什么必须关闭

流背后是**操作系统资源**：一个打开的文件对应一个文件句柄（file descriptor）。句柄数量是有限的（Linux 默认单进程 1024，Windows 也有上限），而且**流还持有内存缓冲区，不关闭就可能丢数据**。

```text
  打开流 ──▶ 操作系统分配句柄 + 内核缓冲区
      │
      │  忘记 close()
      ▼
  句柄一直被占用 ──▶ 达到上限后，新的 open() 全部失败
                     报错：Too many open files / 无法打开文件
      │
      └──▶ 缓冲区数据从未 flush ──▶ 写入的内容丢失
```

## 4.2 finally 的写法

JDK6 及以前没有别的办法，只能在 `finally` 里手动关闭：

```java
import java.io.*;

public class FinallyDemo {
    public static void main(String[] args) {
        FileOutputStream fos = null;
        try {
            fos = new FileOutputStream("D:/data/a.txt");
            fos.write("hello".getBytes("UTF-8"));
        } catch (IOException e) {
            e.printStackTrace();
        } finally {
            // finally 里的代码一定会执行，即使 try 里 return 或抛异常
            if (fos != null) {
                try {
                    fos.close();                 // close 本身也会抛 IOException，还要再套一层
                } catch (IOException e) {
                    e.printStackTrace();
                }
            }
        }
    }
}
```

这种写法有三个毛病：

1. **啰嗦**——每个流都要 `null` 判断 + 内层 `try/catch`，五行的业务代码配十几行的关闭代码；
2. **容易漏**——多个流、多级嵌套时，很容易漏关某一个，或者把关闭顺序写反；
3. **有隐藏 bug**——如果 `try` 块里抛了异常，`close()` 又抛了异常，后者会**覆盖**前者，真正的业务异常被吞掉。

## 4.3 JDK7 的 try-with-resources

JDK7 引入 `try-with-resources`（正式名称是"try-with-resources 语句"），只要资源实现了 **`java.lang.AutoCloseable` 接口**（`Closeable` 是它的子接口，所有 IO 流都实现了），就可以直接在 `try` 的括号里声明，**JVM 保证它在退出时自动调用 `close()`**：

```java
try (创建流对象语句) {
    // 使用流
} catch (IOException e) {
    // 异常处理
}
// 退出 try 块时自动调用 close()，不需要写 finally
```

```java
import java.io.*;

public class TwrDemo {
    public static void main(String[] args) {
        // 括号里创建的流会在 try 块结束时自动关闭，顺序是"先开的最后关"
        try (FileOutputStream fos = new FileOutputStream("D:/data/a.txt");
             OutputStreamWriter osw = new OutputStreamWriter(fos, "UTF-8");
             BufferedWriter bw = new BufferedWriter(osw)) {
            bw.write("用 try-with-resources 写数据");
        } catch (IOException e) {
            System.err.println("出错了：" + e.getMessage());
        }
        System.out.println("写完了，三个流都已自动关闭");
    }
}
```

`try-with-resources` 相比 `finally` 的关键改进：

| 维度 | 手动 `finally` | `try-with-resources` |
|------|---------------|---------------------|
| 代码量 | 多 | **一行搞定** |
| 资源泄漏 | 容易漏关 | **编译器保证必关** |
| 多资源关闭顺序 | 手写，易错 | **自动逆序关闭**（先开的最后关） |
| **异常压制** | 后抛的异常**覆盖**先抛的 | **保留主异常**，被压制的挂到 `getSuppressed()` |

最后一条尤其重要。`try-with-resources` 会在关闭出错时，把 `close()` 抛出的异常**附加（suppress）到主异常上**，而不是覆盖它：

```java
import java.io.*;

public class SuppressDemo {
    public static void main(String[] args) {
        try (AutoCloseable r = new AutoCloseable() {
            @Override public void close() throws Exception {
                throw new Exception("关闭时抛出的异常");
            }
        }) {
            throw new Exception("业务主异常");           // 这才是真正要关注的
        } catch (Exception e) {
            System.out.println("主异常：" + e.getMessage());
            for (Throwable s : e.getSuppressed()) {
                System.out.println("被压制的异常：" + s.getMessage());
            }
        }
    }
}
/* 输出：
主异常：业务主异常
被压制的异常：关闭时抛出的异常
*/
```

## 4.4 JDK9 的改进

JDK9 允许把已经在外面创建好的**终态（或事实终态）变量**直接写进 `try` 括号，不再强制要求"在括号里 new"：

```java
// JDK7 写法：流必须在括号里创建
try (FileInputStream fis = new FileInputStream("a.txt")) {
    // ...
}

// JDK9+ 写法：先创建，再直接把变量名放进括号；多个资源用分号隔开
FileInputStream fis = new FileInputStream("a.txt");
FileOutputStream fos = new FileOutputStream("b.txt");
try (fis; fos) {                    // 必须写变量名，不能再声明类型
    // ...
} catch (IOException e) {
    e.printStackTrace();
}
```

> **注意**：JDK9 写法里放进括号的变量**必须是 final 或事实上 final 的**（赋值后不再修改），否则编译报错。此外它只对已有的变量生效，若流是在 `if` 分支里创建的，仍推荐用 JDK7 的写法。

> **最佳实践**：**新代码一律用 `try-with-resources`，不要手写 `finally` 关流。** 这不是风格偏好，而是正确性问题——手动 `finally` 的异常覆盖行为会实实在在地吞掉你的业务异常。IDE 里看到"手动关流"的代码，可以优先怀疑它是从 JDK6 时代抄来的。

# 5. flush 与 close

这两个方法经常被混为一谈，但它们的职责完全不同：

| 方法 | 作用 | 流是否还能继续用 | 何时调用 |
|------|------|----------------|---------|
| `flush()` | **强制把缓冲区里的数据推到底层目标** | **能**，还可以继续写 | 想在 `close()` 之前让数据落盘 / 到达对方时 |
| `close()` | 先 `flush()`，再释放资源（关闭句柄） | **不能**，再写会抛异常 | 用完了必须调 |

关键结论：

1. **`close()` 内部会调用 `flush()`**——所以正常关闭的流不会丢数据；
2. **不 `close()` 就可能丢数据**——`BufferedOutputStream`、`BufferedWriter` 只在缓冲区满（默认 8192 字节）时才真正写出去，没满的内容在你调用 `flush()` / `close()` 之前**一直在内存里**；
3. **`close()` 之后再 `write()` 会抛 `IOException`**（"Stream closed"）；
4. **`flush()` 不能代替 `close()`**——数据落地了，但文件句柄还开着。

```java
import java.io.*;

public class FlushDemo {
    public static void main(String[] args) throws IOException {
        // 反面案例：不 flush 也不 close，数据全部留在缓冲区里，随对象一起被 GC 掉
        try (OutputStream raw = new FileOutputStream("lost.txt")) {
            BufferedOutputStream bos = new BufferedOutputStream(raw);
            bos.write("这 13 个字节被吞进了缓冲区".getBytes("UTF-8"));
            // 故意不调用 bos.flush() / bos.close()
        }
        System.out.println("lost.txt 大小 = " + new File("lost.txt").length() + "   （数据丢了）");

        // 正确案例：try-with-resources 退出时自动 close()，内部先 flush()
        try (BufferedOutputStream bos = new BufferedOutputStream(new FileOutputStream("ok.txt"))) {
            bos.write("这段数据被正确 flush 了".getBytes("UTF-8"));
        }
        System.out.println("ok.txt  大小 = " + new File("ok.txt").length() + "   （数据完整）");
    }
}
/* 输出：
lost.txt 大小 = 0   （数据丢了）
ok.txt  大小 = 31   （数据完整）
*/
```

> **陷阱**：上面 `lost.txt` 的例子在真实代码里非常常见——**外层 `raw` 被 `try-with-resources` 关了，但 `bos` 从来没关过**，它缓冲区里的数据直接消失。正确的做法是**把缓冲流本身放进 `try` 括号**（像 `ok.txt` 那样），让 JVM 帮你关最外层。原则是：**谁是最外层的装饰器，就关谁**；关外层会**逐层向内**关掉它包装的所有流。

> **注意**：`flush()` 只保证"数据交给了操作系统"，**不保证"写到了磁盘"**。断电场景下仍需操作系统自身刷盘。Java 的 `FileOutputStream` 提供 `getFD().sync()` 来强制落盘，但性能代价极大（每次写都是一次物理 IO），只在数据库、日志系统这类场景才用。

# 6. 编码与解码

## 6.1 编码问题的本质

字符流之所以复杂，全因为一个事实：**计算机只存字节，不存字符**。把字符变成字节叫**编码（encode）**，把字节变回字符叫**解码（decode）**，两者必须用**同一套字符集**才能还原。

| 字符集 | 一个汉字占几字节 | 特点 |
|--------|----------------|------|
| ASCII | —— | 只有 128 个英文符号，不支持中文 |
| ISO-8859-1 | 1 | 单字节，只覆盖西欧字符，**永远不会解码失败**（常用于原始字节中转） |
| **GBK / GB2312** | **2** | 中文 Windows 的传统默认字符集 |
| **UTF-8** | **3**（常用汉字） | 变长编码，**互联网事实标准** |
| UTF-16 | 2 或 4 | Java 内部 `char` / `String` 用的编码 |

```text
   "你好，世界"  ── 5 个字符 ──▶ 不同字符集下的字节数
                              ┌──────────────────────────┐
                              ｜ UTF-8 ：15 字节          ｜
                              ｜ GBK   ：10 字节          ｜
                              └──────────────────────────┘

   乱码产生的唯一原因：编码用的字符集 ≠ 解码用的字符集
```

**乱码不是"文件坏了"，而是"解错了"。** 同一个字节序列，用不同字符集解码会得到完全不同的字符。

## 6.2 String 的编码解码方法

| 方法 | 方向 | 说明 |
|------|------|------|
| `byte[] getBytes()` | 编码 | 用**平台默认字符集**，结果随环境变化，**不要用** |
| `byte[] getBytes(String charsetName)` | 编码 | 指定字符集，抛 `UnsupportedEncodingException` |
| `byte[] getBytes(Charset charset)` | 编码 | 指定字符集（**推荐**，类型安全，不抛异常） |
| `String(byte[] bytes)` | 解码 | 用**平台默认字符集**，同样不要用 |
| `String(byte[] bytes, String charsetName)` | 解码 | 指定字符集 |
| `String(byte[] bytes, Charset charset)` | 解码 | 指定字符集（**推荐**） |
| `String(byte[] bytes, int off, int len, Charset)` | 解码 | 指定区间，配合 `read(buf)` 的返回长度使用 |

```java
import java.io.*;
import java.nio.charset.Charset;
import java.nio.charset.StandardCharsets;

public class EncodeDemo {
    public static void main(String[] args) throws IOException {
        String s = "你好，世界";
        System.out.println("平台默认字符集 = " + Charset.defaultCharset());
        System.out.println("UTF-8 编码后 = " + s.getBytes(StandardCharsets.UTF_8).length + " 字节");
        System.out.println("GBK   编码后 = " + s.getBytes("GBK").length + " 字节");

        // 经典乱码实验：用 UTF-8 写，用 GBK 读
        try (Writer w = new OutputStreamWriter(new FileOutputStream("cn.txt"), "UTF-8")) {
            w.write(s);
        }
        try (Reader r = new InputStreamReader(new FileInputStream("cn.txt"), "UTF-8")) {
            char[] buf = new char[16];
            int len = r.read(buf);
            System.out.println("UTF-8 读 -> " + new String(buf, 0, len));       // 正常
        }
        try (Reader r = new InputStreamReader(new FileInputStream("cn.txt"), "GBK")) {
            char[] buf = new char[16];
            int len = r.read(buf);
            System.out.println("GBK   读 -> " + new String(buf, 0, len));       // 乱码
        }
    }
}
/* 输出（JDK17 + 中文 Windows）：
平台默认字符集 = GBK
UTF-8 编码后 = 15 字节
GBK   编码后 = 10 字节
UTF-8 读 -> 你好，世界
GBK   读 -> 浣犲ソ锛屼笘鐣
*/
```

> **注意**：`浣犲ソ锛屼笘鐣` 就是"UTF-8 的字节被当成 GBK 解码"的经典结果——如果你在中文网站上看到这种字，基本可以断定是编码配错，而不是数据损坏。**因为原始字节是完好的，只要用正确的字符集重新解码，内容完全能恢复。** 这也是排查乱码问题的正确思路：先确认写的时候用什么编码，再用同样的编码去读。

> **行业实践**：**永远显式指定字符集，不要依赖平台默认值。** 中文 Windows 上 `Charset.defaultCharset()` 是 `GBK`（JDK18 起 JEP 400 统一为 UTF-8），Linux 服务器上通常是 `UTF-8`——同一份代码在开发机正常、在服务器乱码，十有八九就是这个原因。用 `StandardCharsets.UTF_8` 常量，它既是 `Charset` 类型又是编译期常量，比传字符串 `"UTF-8"` 更安全（不会写错、不会抛异常）。

# 7. 字符流：FileReader 与 FileWriter

## 7.1 FileReader

| 构造方法 | 版本 | 说明 |
|---------|------|------|
| `FileReader(File file)` | JDK1.1 | 用**平台默认字符集** |
| `FileReader(String pathname)` | JDK1.1 | 用**平台默认字符集** |
| `FileReader(File file, Charset charset)` | **JDK11+** | 指定字符集 |
| `FileReader(String fileName, Charset charset)` | **JDK11+** | 指定字符集 |

| 成员方法 | 说明 |
|---------|------|
| `int read()` | 读**一个字符**，返回其 `int` 码点；末尾返回 `-1`。中文字符会返回一个 UTF-16 码元 |
| `int read(char[] cbuf)` | 读多个字符到数组，返回**实际读到**的字符个数；末尾返回 `-1` |
| `void close()` | 关闭流 |

```java
import java.io.FileReader;
import java.io.IOException;
import java.nio.charset.Charset;

public class FileReaderDemo {
    public static void main(String[] args) throws IOException {
        // ✗ 老写法：用平台默认字符集，中文 Windows 上是 GBK，换台机器就乱码
        // try (FileReader fr = new FileReader("D:/data/a.txt")) { ... }

        // ✓ 新写法（JDK11+）：显式指定 UTF-8
        try (FileReader fr = new FileReader("D:/data/a.txt", Charset.forName("UTF-8"))) {
            char[] buf = new char[1024];
            int len;
            StringBuilder sb = new StringBuilder();
            while ((len = fr.read(buf)) != -1) {
                sb.append(buf, 0, len);        // 同样要用 len，不能用 buf.length
            }
            System.out.println(sb);
        }
    }
}
```

> **陷阱**：`FileReader` 在 **JDK11 之前无法指定字符集**，这是它最被诟病的地方——在中文 Windows 上用它读一个 UTF-8 文件必然乱码。JDK11 之前的标准解法是**走转换流**（见第 9 节）。所以看到老代码里 `new InputStreamReader(new FileInputStream(...), "UTF-8")` 这种冗长写法，不要觉得多余，那是在绕开 `FileReader` 的缺陷。

## 7.2 FileWriter

| 构造方法 | 版本 | 说明 |
|---------|------|------|
| `FileWriter(File file)` | JDK1.1 | 默认字符集，**覆盖** |
| `FileWriter(String pathname)` | JDK1.1 | 同上 |
| `FileWriter(File file, boolean append)` | JDK1.1 | 追加开关 |
| `FileWriter(String pathname, boolean append)` | JDK1.1 | 追加开关 |
| `FileWriter(String fileName, Charset charset[, boolean append])` | **JDK11+** | 指定字符集 |
| `FileWriter(File file, Charset charset[, boolean append])` | **JDK11+** | 指定字符集 |

| 成员方法 | 说明 |
|---------|------|
| `void write(int c)` | 写出一个字符，参数应是该字符的 Unicode 码点 |
| `void write(String str)` | 写出整个字符串 |
| `void write(String str, int off, int len)` | 写出字符串的一部分 |
| `void write(char[] cbuf)` | 写出整个字符数组 |
| `void write(char[] cbuf, int off, int len)` | 写出字符数组的一部分 |
| `void flush()` | 刷新缓冲区 |
| `void close()` | 先 `flush()` 再关闭 |

```java
import java.io.FileWriter;
import java.io.IOException;
import java.nio.charset.StandardCharsets;

public class FileWriterDemo {
    public static void main(String[] args) throws IOException {
        // append = true 表示追加，不传或传 false 会覆盖原文件
        try (FileWriter fw = new FileWriter("D:/data/log.txt", StandardCharsets.UTF_8, true)) {
            fw.write('A');                       // 一个字符
            fw.write("一行文本");                 // 整个字符串
            fw.write("完整字符串", 0, 2);         // 只写前两个字："完整"
            fw.write(new char[]{'x', 'y', 'z'}); // 字符数组
            fw.write(new char[]{'p', 'q', 'r'}, 1, 2);  // 从下标 1 写 2 个："qr"
            fw.write("\n");
        }
        System.out.println(java.nio.file.Files.readString(java.nio.file.Path.of("D:/data/log.txt")));
    }
}
/* 输出：
A一行文本完整xyzqr
（末尾一个换行）
*/
```

> **注意**：`FileWriter(File file, boolean append)` 与 `FileWriter(File file, Charset charset)` 是两个不同重载。**只传 `boolean` 是旧签名**，字符集仍是平台默认；要同时指定编码和追加，必须用 JDK11 的 `FileWriter(String, Charset, boolean)`。

## 7.3 字符流的缓冲区：8192

**字符流自带缓冲区，字节流没有**（`FileOutputStream` 是裸的）。这正是 `flush()` 存在意义最直接的地方。

| 流 | 有无缓冲区 | 默认大小 |
|----|-----------|---------|
| `FileInputStream` / `FileOutputStream` | **无**（每次 `write` 直接进内核） | —— |
| `FileReader` / `FileWriter` | **有** | **8192 字符**（16 KB，因为 `char` 是 2 字节） |
| `BufferedInputStream` / `BufferedOutputStream` | **有** | **8192 字节** |
| `BufferedReader` / `BufferedWriter` | **有** | **8192 字符** |

```java
import java.io.FileWriter;
import java.io.IOException;

public class NoFlushDemo {
    public static void main(String[] args) throws IOException {
        FileWriter fw = new FileWriter("D:/data/tmp.txt");
        fw.write("这段文字还在缓冲区里");         // 只写了 10 个字符，远没到 8192
        System.out.println("文件大小 = " + new java.io.File("D:/data/tmp.txt").length());
        // 输出：文件大小 = 0  （磁盘上还什么都没有！）

        fw.flush();                              // 手动刷新
        System.out.println("flush 后大小 = " + new java.io.File("D:/data/tmp.txt").length());
        // 输出：flush 后大小 = 30  （真正的数据出来了）

        fw.close();                              // 关闭，内部还会再 flush 一次
    }
}
```

> **陷阱**：**每次循环都调用 `flush()` 会彻底抵消缓冲带来的性能优势**——缓冲的意义就是"攒一批再写"，每写一次就刷一次等于每次都写。确认数据落盘的 `flush()` 只应出现在"关键节点"，例如 `finally` 之前、长任务结束之前、需要在同一次运行中用别的流去读这个文件之前。

# 8. 缓冲流

## 8.1 为什么需要缓冲

**每一次对底层流（文件、socket）的读写，都要陷入内核态、执行一次系统调用。** 系统调用的开销比普通方法调用高几个数量级，所以"调用次数"而不是"数据量"才是性能的决定因素。

```text
  无缓冲：8 MB 文件，逐字节复制
    程序 ──read(1 字节)──▶ 内核 ──▶ 磁盘        × 8,388,608 次系统调用
    ↑ 每次都是 read 数据 + write 数据 = 1677 万次系统调用，慢得无法接受

  有缓冲：同样的逐字节代码，外面套一层 BufferedInputStream
    程序 ──read()──▶ ┌─────────────────────┐
                     │ BufferedInputStream │     第一次 read() 一次性读入 8192 字节
                     │ 缓冲区 8192 字节      │     之后的 8191 次 read() 全部命中内存
                     └──────────┬──────────┘
                                │ 缓冲区空了才再读 8192 字节
                                ▼
                              内核 ──▶ 磁盘        × 1024 次系统调用

    调用次数降低 8192 倍 ──▶ 实测加速 82 倍（见 3.3 节的复现实验）
```

> **注意**：缓冲还能带来一个额外好处——**读的时候，缓冲区大小为 8192，是磁盘块大小（通常 4 KB）的整数倍**，能减少"读半个块"造成的额外 IO。这也是 8192 这个数字被选中的原因。

## 8.2 BufferedInputStream 与 BufferedOutputStream

| 构造方法 | 说明 |
|---------|------|
| `BufferedInputStream(InputStream is)` | 用默认 8192 缓冲区包装 |
| `BufferedInputStream(InputStream is, int size)` | 指定缓冲区大小 |
| `BufferedOutputStream(OutputStream os)` | 用默认 8192 缓冲区包装 |
| `BufferedOutputStream(OutputStream os, int size)` | 指定缓冲区大小 |

它们的成员方法与对应的基类完全一致（`read()`、`write()`、`close()`、`flush()`），只是实现变成"先操作内存缓冲区"。**用法上唯一要记住的是包装顺序和关闭对象**：

```java
import java.io.*;

public class BufferedCopyDemo {
    /** 用缓冲流复制文件：生产代码里"手写复制文件"的标准写法 */
    public static long copy(String from, String to) throws IOException {
        // 缓冲流放在 try 括号里，JVM 会依次 close（外层先关，内层后关）
        try (BufferedInputStream in  = new BufferedInputStream(new FileInputStream(from));
             BufferedOutputStream out = new BufferedOutputStream(new FileOutputStream(to))) {
            byte[] buf = new byte[8192];          // 即使有缓冲流，用数组批量搬还能再快一点
            int len;
            while ((len = in.read(buf)) != -1) {
                out.write(buf, 0, len);
            }
            return new File(to).length();
        }
    }

    public static void main(String[] args) throws IOException {
        System.out.println("复制字节数 = " + copy("D:/data/big.dat", "D:/data/copy.dat"));
    }
}
```

> **最佳实践**：**用缓冲流 + `byte[]` 数组一起上，速度最快。** 缓冲流解决"系统调用太多"，数组解决"Java 方法调用太多"——两者不冲突，可以叠加。当然，如果只是简单地复制文件，直接用 `Files.copy(src, dst)` 一行就够了，JDK 内部的实现比手写更优。

## 8.3 BufferedReader：`readLine()` 按行读

`BufferedReader` 除了继承来的 `read()`、`read(char[])`，还多了一个**字符流独有的、非常实用的方法**：

| 构造方法 | 说明 |
|---------|------|
| `BufferedReader(Reader r)` | 用默认 8192 缓冲区包装 |
| `BufferedReader(Reader r, int size)` | 指定缓冲区大小 |

| 成员方法 | 说明 |
|---------|------|
| `String readLine()` | 读**一行**（不含行终止符，即 `\r`、`\n`、`\r\n` 都会被丢掉）；**读到末尾返回 `null`** |
| `Stream<String> lines()` | JDK8+，返回按行的 `Stream` |
| `int read()` / `int read(char[])` | 继承自 `Reader` |

```java
import java.io.BufferedReader;
import java.io.FileReader;
import java.io.IOException;
import java.nio.charset.StandardCharsets;

public class ReadLineDemo {
    public static void main(String[] args) throws IOException {
        // 转换流指定 UTF-8，再套一层缓冲流拿到 readLine()
        try (BufferedReader br = new BufferedReader(
                new java.io.InputStreamReader(
                        new java.io.FileInputStream("D:/data/a.txt"), StandardCharsets.UTF_8))) {
            String line;
            int no = 1;
            // readLine() 返回 null 表示文件读完；注意它不含换行符
            while ((line = br.readLine()) != null) {
                System.out.println(no++ + ": " + line);
            }
        }
    }
}
/* 输出：
1: 第一行
2: 第二行
3: 第三行
*/
```

**为什么 `readLine()` 要配合 `newLine()`？** 因为 `readLine()` **把行终止符丢掉了**——它返回的是"一行的内容"，不包括那个 `\n`。所以：

1. 如果只是逐行处理内容，丢了正好，不用管；
2. 如果要**把读到的行再写出去**（比如过滤、转换、改格式），那么每写一行就得自己补一个换行，否则所有行会连成一整行。这时用 `BufferedWriter.newLine()` 补——它写的是**本平台的换行符**，天然跨平台。

> **陷阱**：`readLine()` 返回 `null` 表示末尾，但**空行返回的是 `""` 而不是 `null`**。所以 `while ((line = br.readLine()) != null)` 不会漏掉空行，不要写成 `while (!(line = br.readLine()).isEmpty())`——那样遇到空行就会误判结束，把后面的内容全丢了。

## 8.4 BufferedWriter：`newLine()`

| 构造方法 | 说明 |
|---------|------|
| `BufferedWriter(Writer w)` | 用默认 8192 缓冲区包装 |
| `BufferedWriter(Writer w, int size)` | 指定缓冲区大小 |

| 成员方法 | 说明 |
|---------|------|
| `void newLine()` | 写出**跨平台的换行符**（本平台的行分隔符） |
| `void write(...)` | 继承自 `Writer` 的各重载 |
| `void flush()` / `void close()` | 刷新 / 关闭 |

```java
import java.io.*;
import java.nio.charset.StandardCharsets;

public class LineFilterDemo {
    public static void main(String[] args) throws IOException {
        // 一个实用示例：过滤日志，只保留含 ERROR 的行，再写到新文件
        try (BufferedReader br = new BufferedReader(
                 new InputStreamReader(new FileInputStream("D:/data/app.log"), StandardCharsets.UTF_8));
             BufferedWriter bw = new BufferedWriter(
                 new OutputStreamWriter(new FileOutputStream("D:/data/error.log"), StandardCharsets.UTF_8))) {
            String line;
            int kept = 0;
            while ((line = br.readLine()) != null) {
                if (line.contains("ERROR")) {
                    bw.write(line);
                    // readLine 丢掉了换行符，这里必须补回来，否则所有行会挤成一行
                    bw.newLine();
                    kept++;
                }
            }
            System.out.println("保留了 " + kept + " 行错误日志");
        }
    }
}
/* 输出：
保留了 3 行错误日志
*/
```

# 9. 转换流

## 9.1 转换流存在的唯一意义：指定字符集

**转换流是"字节流"与"字符流"之间的桥。** `InputStreamReader` 把 `InputStream` 包成 `Reader`（字节 → 字符，解码）；`OutputStreamWriter` 把 `OutputStream` 包成 `Writer`（字符 → 字节，编码）。

| 类 | 继承自 | 作用 |
|----|--------|------|
| `InputStreamReader` | `Reader` | 包装一个 `InputStream`，按指定字符集**解码**成字符 |
| `OutputStreamWriter` | `Writer` | 包装一个 `OutputStream`，按指定字符集**编码**成字节 |

| 构造方法 | 说明 |
|---------|------|
| `InputStreamReader(InputStream in)` | 用**平台默认字符集**，几乎不该用 |
| `InputStreamReader(InputStream in, String charsetName)` | 指定字符集名，抛 `UnsupportedEncodingException` |
| `InputStreamReader(InputStream in, Charset charset)` | 指定字符集（**推荐**） |
| `OutputStreamWriter(OutputStream out)` | 用平台默认字符集 |
| `OutputStreamWriter(OutputStream out, String charsetName)` | 指定字符集名 |
| `OutputStreamWriter(OutputStream out, Charset charset)` | 指定字符集（**推荐**） |

它们的成员方法与普通字符流**完全一致**（`read()`、`write()`、`flush()`、`close()`），因为它们本身就是 `Reader` / `Writer`。

```text
  解码方向（读）
  ┌───────────────┐   ┌────────────────────┐   ┌──────────────┐
  │ 文件 / 网络    │──▶│ InputStreamReader   │──▶│ BufferedReader│──▶ 程序
  │ 一堆字节       │   │ 按 UTF-8 或 GBK 解码│   │ readLine()   │
  └───────────────┘   └────────────────────┘   └──────────────┘

  编码方向（写）
  ┌──────────────┐   ┌─────────────────────┐   ┌───────────────┐
  │ 程序 char     │──▶│ OutputStreamWriter  │──▶│ 文件 / 网络    │
  │ String        │   │ 按指定字符集编码      │   │ 一堆字节       │
  └──────────────┘   └─────────────────────┘   └───────────────┘
```

## 9.2 经典场景：GBK 系统上读写 UTF-8 文件

这是转换流最不可替代的用途，也是面试里最常被问到的编码题。

```java
import java.io.*;
import java.nio.charset.Charset;

public class TransferDemo {
    public static void main(String[] args) throws IOException {
        System.out.println("本机平台默认字符集 = " + Charset.defaultCharset());   // GBK

        // 场景：文件是 UTF-8 编码的，但 JVM 默认是 GBK
        // ✗ 用 FileReader（JDK11 之前只能这样，必然乱码）
        // try (FileReader fr = new FileReader("utf8文件.txt")) { ... }

        // ✓ 用转换流显式指定 UTF-8——这就是转换流存在的意义
        try (BufferedReader br = new BufferedReader(
                 new InputStreamReader(new FileInputStream("utf8文件.txt"), "UTF-8"))) {
            String line;
            while ((line = br.readLine()) != null) {
                System.out.println(line);        // 中文正常显示
            }
        }

        // 写方向同理：把 GBK 系统上的内容写成 UTF-8 文件
        try (BufferedWriter bw = new BufferedWriter(
                 new OutputStreamWriter(new FileOutputStream("output.txt"), "UTF-8"))) {
            bw.write("这段中文以 UTF-8 写入磁盘");
            bw.newLine();
        }
        System.out.println("output.txt 的字节数 = " + new File("output.txt").length()
                           + "（UTF-8 下一个汉字 3 字节）");
    }
}
/* 输出：
本机平台默认字符集 = GBK
（UTF-8 文件的中文内容正常打印）
output.txt 的字节数 = 45（UTF-8 下一个汉字 3 字节）
*/
```

## 9.3 转换流还需要用吗？

JDK11 之后，`FileReader` / `FileWriter` 有了带 `Charset` 的构造方法，`Files.newBufferedReader(path, charset)` 也早就能指定编码，所以**"只是给文件指定编码"这个需求已经不需要转换流了**：

| 需求 | JDK7+ 的现代写法 | 转换流的写法 |
|------|-----------------|-------------|
| 按指定编码读文件 | `Files.newBufferedReader(p, UTF_8)` | `new BufferedReader(new InputStreamReader(new FileInputStream(f), "UTF-8"))` |
| 按指定编码写文件 | `Files.newBufferedWriter(p, UTF_8)` | `new BufferedWriter(new OutputStreamWriter(new FileOutputStream(f), "UTF-8"))` |
| 直接读成字符串 | `Files.readString(p, UTF_8)` | 需要自己循环拼接 |
| 直接读成行列表 | `Files.readAllLines(p, UTF_8)` | 需要自己循环拼接 |

**但转换流并不会消失**，因为它的本质是"**字节流与字符流之间的适配器**"，在很多地方仍然不可替代：

| 场景 | 为什么还要用转换流 |
|------|------------------|
| 包装 **网络 socket** 流 | `Socket.getInputStream()` 返回的是 `InputStream`，`Files` 管不到 |
| 包装 **`System.in`**（标准输入） | 它是 `InputStream`，要按行读必须套 `InputStreamReader` |
| 包装 **进程输出** | `Process.getInputStream()` 同样是 `InputStream` |
| 需要**自定义 CharsetDecoder** | 例如设置 `CodingErrorAction.REPLACE` / `REPORT` 控制非法字节的处理方式 |
| 老代码 / 老框架里已有的流 | 上游给的是 `InputStream`，只能靠转换流接成字符流 |

> **最佳实践**：**文件操作优先用 `Files` 的便捷方法**（`newBufferedReader` / `newBufferedWriter` / `readAllLines`），它们在内部就是用转换流实现的，但更简洁、默认 UTF-8、异常信息更清楚。**只有当数据源不是文件**（socket、标准输入、进程输出）时，才需要自己手写转换流。

# 10. 序列化流

## 10.1 什么是序列化

**序列化（Serialization）是把内存中的对象转成字节序列的过程，反序列化（Deserialization）是反过来。** 它的目的是让对象能"离开内存"——存进文件、通过网络传给另一台机器、放进缓存。

| 类 | 作用 | 关键方法 |
|----|------|---------|
| `ObjectOutputStream` | **序列化**：把对象**写**出去 | `writeObject(Object obj)` |
| `ObjectInputStream` | **反序列化**：把对象**读**回来 | `Object readObject()` |

```java
import java.io.*;

public class SerBasicDemo {
    // 要被序列化的类必须实现 Serializable（标记接口，没有任何方法要实现）
    static class User implements Serializable {
        private String name;
        private int age;
        User(String name, int age) { this.name = name; this.age = age; }
        @Override public String toString() { return "User(" + name + ", " + age + ")"; }
    }

    public static void main(String[] args) throws Exception {
        // 序列化：对象 -> 文件
        try (ObjectOutputStream oos = new ObjectOutputStream(new FileOutputStream("user.dat"))) {
            oos.writeObject(new User("张三", 20));
        }

        // 反序列化：文件 -> 对象
        try (ObjectInputStream ois = new ObjectInputStream(new FileInputStream("user.dat"))) {
            User u = (User) ois.readObject();
            System.out.println("反序列化得到 " + u);
        }
    }
}
/* 输出：
反序列化得到 User(张三, 20)
*/
```

## 10.2 Serializable 是标记接口

```java
public interface Serializable {
    // 空的，一个方法都没有
}
```

**`Serializable` 是个空接口（标记接口）**，它的唯一作用是给 JVM 打一个"这个类可以被序列化"的标记。**没实现它的对象调用 `writeObject()` 会抛 `NotSerializableException`。**

几条必须记住的规则：

1. **序列化的是对象的状态（成员变量的值），不是类的行为（方法）**；
2. **成员变量如果是另一个自定义对象，那个类也必须实现 `Serializable`**，否则在遍历到这个字段时抛 `NotSerializableException`——这是最常见的序列化失败原因；
3. **`static` 成员变量不参与序列化**，因为它属于类而不属于对象；
4. **`transient` 修饰的成员变量不参与序列化**；
5. `Serializable` **不能**被子类自动继承——但如果你继承的父类实现了它，子类自动也是可序列化的。

```text
   序列化时，JVM 沿着对象图递归写入：
   ┌──────────────────────────────────────────────────┐
   │  Order implements Serializable                    │
   │   ├─ long id              写入                    │
   │   ├─ User user            写入（User 也必须可序列化）│
   │   ├─ transient String pwd 跳过                    │
   │   └─ static int COUNT     跳过（属于类）           │
   └──────────────────────────────────────────────────┘
              │
              │ 遇到不可序列化的字段
              ▼
   java.io.NotSerializableException: xxx.User
```

## 10.3 serialVersionUID：不写它就会出问题

**这是序列化最重要、也最容易被忽略的一点。**

`serialVersionUID` 是类的"序列化版本号"。反序列化时，JVM 会拿**文件里记录的版本号**和**当前类的版本号**比较，不一致就抛 `InvalidClassException`。

| 情况 | 结果 |
|------|------|
| 显式声明了 `serialVersionUID`，且两版本一致 | 正常反序列化 |
| 显式声明了 `serialVersionUID`，但改了值 | **抛 `InvalidClassException`** |
| **没声明**，JVM 按类的结构**自动计算** | 只要类改动（增删字段、改方法签名等），自动值就可能变 → **反序列化失败** |
| **没声明**，且类从未改动 | 正常反序列化 |

```java
// 正确写法：显式声明，且不要随便改
public class User implements Serializable {
    // 序列化版本号：显式声明后，增删字段不会导致反序列化失败
    private static final long serialVersionUID = 1L;
    private String name;
}
```

下面用实验证明"不写它"的后果——先序列化一个版本，再给类加一个字段后反序列化：

```java
// 第一步：v1/User.java
public class User implements Serializable {       // 没写 serialVersionUID
    private String name;
    public User(String name) { this.name = name; }
}

// 第二步：序列化
try (ObjectOutputStream oos = new ObjectOutputStream(new FileOutputStream("user.dat"))) {
    oos.writeObject(new User("张三"));
}

// 第三步：给类加一个字段（模拟一次普通的业务迭代），重新编译后反序列化
public class User implements Serializable {
    private String name;
    private int age;                              // 新增字段，自动 serialVersionUID 变了
    public User(String name) { this.name = name; }
}

try (ObjectInputStream ois = new ObjectInputStream(new FileInputStream("user.dat"))) {
    System.out.println(ois.readObject());
}
```

```text
Exception in thread "main" java.io.InvalidClassException: User;
    local class incompatible: stream classdesc serialVersionUID = -6210964107539518685,
                              local class serialVersionUID     = -8400882678286859541
```

> **陷阱**：报错信息里的两个数字就是新旧版本号。**只要你在类里加了一个字段、改了一个字段的类型，甚至改了一个方法，自动计算出的版本号就可能变**，之前存下来的所有对象全部作废。而加了 `serialVersionUID = 1L` 之后，同样的改动可以正常反序列化——**新增的字段会是默认值**（`int` 是 0，对象是 `null`）。

> **最佳实践**：**任何实现 `Serializable` 的类，都必须显式声明 `private static final long serialVersionUID`。** 用 IDE 生成（IntelliJ 是 `Alt+Enter` → "Add serialVersionUID field"）或直接写 `1L`。如果这个类会跨服务传输或长期存储在磁盘上，还应当在注释里写清楚"什么时候该修改这个值"。

## 10.4 transient：不参与序列化的字段

给成员变量加上 `transient` 关键字，它就不会被写进文件，**反序列化后会是该类型的默认值**（对象为 `null`，数值为 `0`，`boolean` 为 `false`）。

| 字段类型 | 是否参与序列化 |
|---------|---------------|
| 普通成员变量 | ✓ 参与 |
| `transient` 成员变量 | ✗ 不参与，反序列化后为默认值 |
| `static` 成员变量 | ✗ 不参与（属于类，不属于对象） |
| `static final` 常量 | ✗ 不参与 |
| 父类中非 `transient` 的字段（父类可序列化） | ✓ 参与 |

```java
import java.io.*;

public class TransientDemo {
    static class Account implements Serializable {
        private static final long serialVersionUID = 1L;

        private String username;
        // 密码、密钥、Token 这类敏感字段绝不落盘
        private transient String password;
        private static String bankName = "某银行";     // static 属于类，不参与序列化

        Account(String username, String password, String ignored) {
            this.username = username;
            this.password = password;
        }

        @Override
        public String toString() {
            return "username=" + username + ", password=" + password + ", bank=" + bankName;
        }
    }

    public static void main(String[] args) throws Exception {
        try (ObjectOutputStream oos = new ObjectOutputStream(new FileOutputStream("acc.dat"))) {
            oos.writeObject(new Account("zhangsan", "123456", "x"));
        }
        try (ObjectInputStream ois = new ObjectInputStream(new FileInputStream("acc.dat"))) {
            System.out.println(ois.readObject());
        }
    }
}
/* 输出：
username=zhangsan, password=null, bank=某银行
                ↑ transient 字段变成了 null（static 字段由当前 JVM 的类提供）
*/
```

> **注意**：`transient` 只是"不写进序列化流"，**不是加密，也不是安全措施**。它防的是"密码被写进文件"，防不了"对象在网络上被传输"。真正敏感的字段应该用专门的加密方案，而不是指望 `transient`。

## 10.5 序列化的风险与现代替代

这一节值得所有写业务代码的人读一遍。**Java 原生序列化如今是一个被广泛劝退的技术**：

| 问题 | 说明 |
|------|------|
| **安全漏洞** | 反序列化会**执行类中的 `readObject()`**，攻击者只要构造出恶意的字节流，就能触发任意代码执行。历史上大量 RCE 漏洞（Apache Commons Collections、WebLogic 等）都源于此 |
| **版本脆弱** | 类一改就可能失效（见 10.3），跨服务版本不一致时经常直接报错 |
| **体积大** | 包含大量类描述元数据，比 JSON 大一倍以上 |
| **不可读** | 二进制格式，出问题时无法直接肉眼看 |
| **跨语言不通** | 只有 Java 能读，无法与 Go、Python 服务交互 |
| **性能一般** | 反射开销大，序列化/反序列化都慢 |

**现代的替代方案：**

| 方案 | 格式 | 特点 |
|------|------|------|
| **JSON**（Jackson、Gson、Fastjson2） | 文本 | **最主流**，可读、跨语言、生态好 |
| **Protobuf**（Google） | 二进制 | 体积小、性能高，需要 `.proto` 定义，强类型 |
| **Avro / Thrift** | 二进制 | 大数据生态（Hadoop、Kafka）常用，支持 Schema 演进 |
| **Kryo / Hessian** | 二进制 | Java 生态内的高性能替代，Dubbo 用过 Hessian |

> **行业实践**：**新项目不要用 Java 原生序列化做存储和网络传输。** 存对象用 JSON 或 Protobuf；RPC 用框架自带的协议（Dubbo 用 Hessian2，gRPC 用 Protobuf）；缓存（Redis）里存 JSON。原生序列化只在这些地方还值得用：本地临时缓存（`Serializable` 的 `Map` 存磁盘）、`Swing` 的剪贴板 / 拖放、以及某些强制要求 `Serializable` 的框架 API（如 `Session` 里的对象）。

> **注意**：**接口和框架传参里出现 `Serializable`，不代表要用 `ObjectOutputStream` 去存它。** 很多框架把 `Serializable` 当作"这个对象可以被我持久化"的通用约束（比如 `Session` 序列化用 JSON），跟 Java 原生序列化格式是两回事。

# 11. 打印流

## 11.1 PrintStream

`PrintStream` 是**唯一一个"从不抛 `IOException`"的输出流**，它的设计目标就是"打印"——方便、不打断程序。

| 构造方法 | 说明 |
|---------|------|
| `PrintStream(OutputStream out)` | 包装任意字节输出流 |
| `PrintStream(OutputStream out, boolean autoFlush)` | 加自动刷新开关 |
| `PrintStream(String fileName, Charset charset)` | 直接写文件，指定编码（JDK10+） |
| `PrintStream(OutputStream out, boolean autoFlush, String encoding)` | 指定编码 + 自动刷新 |
| `PrintStream(File file)` / `PrintStream(String fileName)` | 直接写文件 |

| 成员方法 | 说明 |
|---------|------|
| `void write(int b)` / `write(byte[])` | 继承自 `OutputStream`，**不具备打印流的便捷功能**，写的是原始字节 |
| `void print(...)` | 打印任意数据类型，**不换行**。对象会调用 `toString()` |
| `void println(...)` | 打印任意数据类型，**换行** |
| `void printf(String format, Object... args)` | 按格式串打印，**不换行**，遵循 `Formatter` 规范 |
| `boolean checkError()` | **检查内部错误标记**，见下方陷阱 |

```java
import java.io.PrintStream;
import java.nio.charset.StandardCharsets;
import java.io.IOException;

public class PrintStreamDemo {
    public static void main(String[] args) throws IOException {
        try (PrintStream ps = new PrintStream("D:/data/print.txt", StandardCharsets.UTF_8)) {
            ps.print("不换行");
            ps.println("，println 会换行");      // 自动换行
            ps.println(3.14159);                 // 任意类型
            ps.println(new int[]{1, 2, 3});      // 数组打印的是地址形式的 toString，不是内容
            ps.printf("姓名：%s，年龄：%d，得分：%.1f%n", "张三", 20, 95.5);  // %n 是平台换行
            System.out.println("写入完成，checkError = " + ps.checkError());
        }
        System.out.print(java.nio.file.Files.readString(java.nio.file.Path.of("D:/data/print.txt")));
    }
}
/* 输出（文件内容）：
不换行，println 会换行
3.14159
[I@1b6d3586
姓名：张三，年龄：20，得分：95.5
写入完成，checkError = false
*/
```

关于 `autoFlush`，语义需要精确记忆：

| 构造参数 | 触发自动刷新的时机（`PrintStream`） |
|---------|--------------------------------|
| `autoFlush = true` | 写**字节数组**时、调用 **`println`** 系列时、写入**换行符 `\n`** 时 |
| `autoFlush = false`（默认） | 只在缓冲区满或显式 `flush()` / `close()` 时 |

> **陷阱**：`PrintStream` **吞掉所有 `IOException`**！方法签名上不写 `throws`，也不会把异常抛给调用者，而是**把内部错误标记置为 `true`**。也就是说，往一个已经关闭的流里 `println`，程序**一点反应都没有**，数据静默消失。必须用 **`checkError()`** 主动检查：

```java
import java.io.*;

public class CheckErrorDemo {
    public static void main(String[] args) throws Exception {
        PrintStream ps = new PrintStream(new FileOutputStream("out_test.txt"));
        ps.close();
        ps.println("写向已关闭的流");        // 不抛异常，也不报错
        System.out.println("checkError() = " + ps.checkError());   // true —— 唯一能发现错误的方式
    }
}
/* 输出：
checkError() = true
*/
```

> **最佳实践**：用 `PrintStream` / `PrintWriter` 写**重要数据**时，一定要在关流前调用 `checkError()`（或者在 `try-with-resources` 之后检查），否则磁盘满、权限变更这类错误会被完全静默。

## 11.2 PrintWriter

`PrintWriter` 是**字符版**的打印流，继承自 `Writer`，因此**它可以指定字符集**，这一点比 `PrintStream` 好（`PrintStream` 在 JDK10 才有带 `Charset` 的构造方法）。

| 构造方法 | 说明 |
|---------|------|
| `PrintWriter(Writer w)` | 包装字符流 |
| `PrintWriter(Writer w, boolean autoFlush)` | 加自动刷新 |
| `PrintWriter(File file)` / `PrintWriter(String fileName)` | 直接写文件，**平台默认字符集** |
| `PrintWriter(String fileName, Charset charset)` | 直接写文件 + 指定编码（JDK10+） |
| `PrintWriter(OutputStream out)` | 包装字节流 |
| `PrintWriter(OutputStream out, boolean autoFlush, Charset charset)` | 指定编码 + 自动刷新（**最常用的组合**） |

| 成员方法 | 说明 |
|---------|------|
| `void print(...)` / `println(...)` / `printf(...)` | 与 `PrintStream` 完全相同 |
| `void write(...)` | 继承自 `Writer`，写字符 |
| `boolean checkError()` | 同样有错误标记，同样不抛 `IOException` |

`PrintStream` 与 `PrintWriter` 的自动刷新语义有个**细微但重要的差异**：

| | `PrintStream`（字节） | `PrintWriter`（字符） |
|---|---------------------|---------------------|
| `autoFlush = true` 时的刷新时机 | `println` 系列、写字节数组、写入 `\n` | **仅 `println` / `printf` / `format`** |
| 写普通字符串不换行 | 只有出现 `\n` 才刷 | **不刷新** |
| 适合 | 控制台输出、日志 | 文件/网络文本输出 |

```java
import java.io.*;
import java.nio.charset.StandardCharsets;

public class PrintWriterDemo {
    public static void main(String[] args) throws IOException {
        // 用 OutputStream 构造，同时指定编码和自动刷新
        try (PrintWriter pw = new PrintWriter(
                new OutputStreamWriter(new FileOutputStream("D:/data/pw.txt"), StandardCharsets.UTF_8),
                true)) {                        // autoFlush = true
            pw.println("第一行会自动刷新");
            pw.printf("格式化输出：%d + %d = %d%n", 1, 2, 3);
            pw.print("这行没有换行，可能还留在缓冲区");   // print 不触发自动刷新
        }   // close() 时统一 flush，数据仍然完整
        System.out.println(java.nio.file.Files.readString(java.nio.file.Path.of("D:/data/pw.txt")));
    }
}
/* 输出：
第一行会自动刷新
格式化输出：1 + 2 = 3
这行没有换行，可能还留在缓冲区
*/
```

## 11.3 System.out 的本质

`System.out` 就是一个 `PrintStream`，这也是"为什么 `System.out.println` 用起来这么方便"的答案：

```java
import java.io.*;
import java.lang.reflect.Field;

public class SystemOutDemo {
    public static void main(String[] args) throws Exception {
        PrintStream out = System.out;
        System.out.println("System.out 的实际类型 = " + out.getClass().getName());

        // 反射看一眼它的内部结构（需要 --add-opens java.base/java.io=ALL-UNNAMED）
        Field autoFlush = PrintStream.class.getDeclaredField("autoFlush");
        autoFlush.setAccessible(true);
        System.out.println("autoFlush            = " + autoFlush.get(out));

        Field underlying = FilterOutputStream.class.getDeclaredField("out");
        underlying.setAccessible(true);
        System.out.println("它包装的底层流         = " + underlying.get(out).getClass().getName());
    }
}
/* 输出：
System.out 的实际类型 = java.io.PrintStream
autoFlush            = true
它包装的底层流         = java.io.BufferedOutputStream
*/
```

三层结构，正好把本篇讲的东西全串起来了：

```text
  程序
   │  System.out.println("你好")
   ▼
  ┌─────────────────────────────────┐
  │ PrintStream                     │    提供 println / printf，吞异常，autoFlush = true
  │  └─ BufferedOutputStream(8192)  │    提供二进制缓冲，减少系统调用
  │       └─ FileOutputStream(fd=1) │    真正写向"标准输出"，fd = 1 表示 stdout
  └─────────────────────────────────┘
   │
   ▼
  控制台 / 重定向的文件 / 管道
```

由此可以解释几个日常现象：

| 现象 | 原因 |
|------|------|
| `System.out.println` 立即能看到输出（即使后面程序还在跑） | `autoFlush = true` |
| `System.out.print` 有时"没输出" | 没有换行，未触发自动刷新；程序崩溃时才丢失 |
| 更推荐 `System.err` 打日志 | `System.err` 也是 `PrintStream`，且**通常无缓冲**，优先级更高、更及时 |
| 生产环境不该用 `System.out.println` 打日志 | 无法控制级别、无法输出到文件、无时间戳与线程信息、**每次调用都加锁**，高并发下是性能瓶颈。用 SLF4J + Logback |

> **注意**：`System.out` / `System.err` **都是 `PrintStream`，都吞 `IOException`**。在管道被下游关闭（比如 `java App | head -1`）时，写入会失败但程序不会报错，数据静默丢失。这解释了某些"输出重定向后日志缺行"的诡异现象。

# 12. 压缩流与 Zip

`java.util.zip` 提供 ZIP 格式的读写，它们同样是**流**，可以套在别的流上。

| 类 | 作用 |
|----|------|
| `ZipInputStream` | **读** ZIP 文件，逐个取出 `ZipEntry` |
| `ZipOutputStream` | **创建** ZIP 文件，逐个写入 `ZipEntry` |
| `ZipEntry` | 表示 ZIP 里的一个条目（一个文件或一个目录） |

```java
import java.io.*;
import java.nio.charset.StandardCharsets;
import java.util.zip.*;

public class ZipDemo {
    /** 压缩：把若干文件写进一个 zip */
    public static void zip(String zipFile, String[] files) throws IOException {
        try (ZipOutputStream zos = new ZipOutputStream(new FileOutputStream(zipFile))) {
            zos.setEncoding("UTF-8");                 // 文件名含中文时必须设置，否则乱码
            for (String path : files) {
                File f = new File(path);
                // 每个条目要先 putNextEntry 声明，写完必须 closeEntry
                zos.putNextEntry(new ZipEntry(f.getName()));
                try (FileInputStream fis = new FileInputStream(f)) {
                    byte[] buf = new byte[8192];
                    int len;
                    while ((len = fis.read(buf)) != -1) zos.write(buf, 0, len);
                }
                zos.closeEntry();
            }
        }
    }

    /** 解压：读出 zip 里的每个条目 */
    public static void unzip(String zipFile, String outDir) throws IOException {
        new File(outDir).mkdirs();
        try (ZipInputStream zis = new ZipInputStream(
                new FileInputStream(zipFile), StandardCharsets.UTF_8)) {
            ZipEntry entry;
            // getNextEntry() 返回 null 表示没有更多条目
            while ((entry = zis.getNextEntry()) != null) {
                System.out.println("条目：" + entry.getName()
                                   + "（" + entry.getSize() + " 字节）");
                File out = new File(outDir, entry.getName());
                out.getParentFile().mkdirs();
                try (FileOutputStream fos = new FileOutputStream(out)) {
                    byte[] buf = new byte[8192];
                    int len;
                    while ((len = zis.read(buf)) != -1) fos.write(buf, 0, len);
                }
                zis.closeEntry();
            }
        }
    }

    public static void main(String[] args) throws IOException {
        zip("D:/data/test.zip", new String[]{"D:/data/a.txt", "D:/data/b.txt"});
        unzip("D:/data/test.zip", "D:/data/unzip");
    }
}
```

> **陷阱**：`ZipInputStream` 的条目名默认用**平台默认字符集**解析。中文 Windows 上生成的 zip 在 Linux 服务器上解开，文件名就会乱码。**压缩和解压两侧都要显式设置 `UTF-8`**（`zos.setEncoding("UTF-8")` 与 `new ZipInputStream(in, StandardCharsets.UTF_8)`）。

> **注意**：`ZipInputStream` 读 ZIP **只能顺序读**，不支持随机访问（无法直接跳到某个条目）。需要随机访问时用 `ZipFile` 类——它会先读中央目录，因此可以按名字取任意条目，对大 ZIP 尤其重要。

# 13. 第三方工具：Commons IO

Apache Commons IO 是 Apache Commons 组织提供的 IO 工具包，把大量样板代码封装成了一行调用。虽然 `Files` 已经覆盖了大部分场景，但它的这几个工具类和 `IOUtils` 至今仍被广泛使用。

| 工具类 | 主要用途 |
|--------|---------|
| `IOUtils` | 流的复制、读取、关闭、`toString`，**最有用的一个** |
| `FileUtils` | 文件的复制、移动、删除、目录递归操作、读写字符串 |
| `FilenameUtils` | 只对文件名做字符串操作，不访问磁盘 |
| `FileFilterUtils` | 常用文件过滤器的组合 |
| `Tailer` | 监听文件末尾新增内容（实时读日志） |

```java
import org.apache.commons.io.IOUtils;
import org.apache.commons.io.FileUtils;

import java.io.*;
import java.nio.charset.StandardCharsets;
import java.util.List;

public class CommonsIoDemo {
    public static void main(String[] args) throws IOException {
        // IOUtils：所有 close 都不抛异常，null 传入也安全，专治 try-with-resources 的样板代码
        PrintStream sysout = System.out;
        IOUtils.closeQuietly((Closeable) null);           // 绝不抛异常的关闭

        // 一次把流读成字符串
        try (InputStream in = new FileInputStream("D:/data/a.txt")) {
            String content = IOUtils.toString(in, StandardCharsets.UTF_8);
            sysout.println("内容长度 = " + content.length());
        }

        // FileUtils：整目录复制（Files.copy 做不到的事）
        FileUtils.copyDirectory(new File("D:/data/src"), new File("D:/data/dst"));

        // 按行读写，一步到位
        List<String> lines = FileUtils.readLines(new File("D:/data/a.txt"), StandardCharsets.UTF_8);
        FileUtils.writeLines(new File("D:/data/b.txt"), "UTF-8", lines, true);   // true = 追加

        // 递归删除（Files 那边要自己写 walkFileTree）
        FileUtils.deleteDirectory(new File("D:/data/tmp"));

        System.out.println("共 " + lines.size() + " 行");
    }
}
```

```text
Maven 依赖：
<dependency>
    <groupId>commons-io</groupId>
    <artifactId>commons-io</artifactId>
    <version>2.16.1</version>
</dependency>
```

> **行业实践**：**新项目优先用 JDK 自带的 `Files`**，不要无脑引入 Commons IO。它是 JDK7 之前的历史产物，很多方法现在都有官方替代。但 `FileUtils.deleteDirectory`、`FileUtils.copyDirectory`、`IOUtils.closeQuietly` 这几个 JDK 至今没有等价物的方法，仍然值得用。注意 `FileUtils` 内部的很多实现比 `Files` 更"宽容"——比如 `deleteQuietly` 失败也不报错，用之前要确认这正是你想要的。

# 14. Properties：读写配置文件

`Properties` 是 `Hashtable` 的子类（属于 `Map` 体系），**键和值都是 `String`**，专门用来读写 `.properties` 配置文件。

| 方法 | 说明 |
|------|------|
| `void load(InputStream)` | 从**字节流**读取（**ISO-8859-1 编码**，即 Latin-1） |
| `void load(Reader)` | 从**字符流**读取（**可以指定编码，推荐**） |
| `void store(OutputStream, String comments)` | 写到字节流（Latin-1） |
| `void store(Writer, String comments)` | 写到字符流（可指定编码，推荐） |
| `String getProperty(String key)` | 取值，不存在返回 `null` |
| `String getProperty(String key, String defaultValue)` | 取值，不存在返回默认值 |
| `Object setProperty(String key, String value)` | 设值 |
| `Set<String> stringPropertyNames()` | 所有键 |

```text
# app.properties（内容示例）
# 井号或叹号开头的行是注释
app.name=demo
app.port=8080
app.debug=false
```

```java
import java.io.*;
import java.nio.charset.StandardCharsets;
import java.util.Properties;

public class PropertiesDemo {
    public static void main(String[] args) throws IOException {
        Properties props = new Properties();

        // 读：用 Reader 指定编码，避免 ISO-8859-1 带来中文乱码
        try (Reader r = new InputStreamReader(
                new FileInputStream("D:/data/app.properties"), StandardCharsets.UTF_8)) {
            props.load(r);
        }

        System.out.println("app.name  = " + props.getProperty("app.name"));
        System.out.println("app.port  = " + props.getProperty("app.port"));
        System.out.println("不存在    = " + props.getProperty("missing"));              // null
        System.out.println("带默认值  = " + props.getProperty("missing", "默认值"));      // 默认值
        System.out.println("int 转换  = " + (Integer.parseInt(props.getProperty("app.port")) + 1));
    }
}
/* 输出：
app.name  = demo
app.port  = 8080
不存在    = null
带默认值  = 默认值
int 转换  = 8081
*/
```

> **陷阱**：`Properties.load(InputStream)` 使用的是 **ISO-8859-1（Latin-1）** 编码，**中文会直接乱码**。这是 Java 早期的历史包袱。两种解法：用 `load(Reader)` 自己指定 UTF-8；或者保留 `load(InputStream)`，但在 `.properties` 里把中文写成 `\uXXXX` 转义（IDEA 会自动帮你转，`Settings → File Encodings → Transparent native-to-ascii conversion`）。

> **注意**：`Properties` 的键值都是 `String`，取值后要自己转成 `int` / `boolean`；它还是 `Hashtable` 子类，**线程安全但方法加了锁**，作为配置容器无所谓，但不要拿它当高性能缓存用。

# 15. 小结

| 主题 | 一句话要点 |
|------|-----------|
| 流的两层分类 | 按方向分输入 / 输出；按单位分**字节流**（万能）与**字符流**（只适合文本，但替你做编解码） |
| 继承体系 | 四组基类相互独立；`BufferedInputStream` / `PrintStream` 等**继承自 `FilterXxx`**，靠装饰器模式任意叠加能力 |
| 字节流 | 不存在会创建但**父目录必须存在**；不传 `append` **默认覆盖**；`read()` 用 `int` 接收，`-1` 表示末尾 |
| 关流 | **一律用 `try-with-resources`**，它会逆序关闭且不吞掉主异常；手写 `finally` 会被 `close()` 的异常覆盖真实错误 |
| `flush` vs `close` | `close()` 内部会 `flush()`；**不 `close()` 就可能丢数据**，尤其是 `BufferedOutputStream`；`flush()` 之后流还能用 |
| 缓冲流 | 缓冲把"每次一个字节一次系统调用"变成"8192 字节一次"，实测可快 **80 倍以上**；默认缓冲区 **8192** |
| 编码 | 乱码的唯一原因是**编解码字符集不一致**；`getBytes()` / `new String()` 不带参数用平台默认值，**永远显式传 `StandardCharsets.UTF_8`** |
| 字符流 | `FileReader` / `FileWriter` 在 **JDK11 前无法指定编码**；`readLine()` 丢换行，写回去要配 `newLine()` |
| 转换流 | 本质是**字节流与字符流的适配器**；文件操作用 `Files` 即可，**socket / `System.in` / 进程流**仍离不开它 |
| 序列化 | 必须实现 `Serializable`；**必须写 `serialVersionUID`**，不写则改类后反序列化必失败；`transient` / `static` 不参与；**有安全风险，新项目改用 JSON** |
| 打印流 | `System.out` 就是 `PrintStream`（外层 `BufferedOutputStream`，`autoFlush = true`）；**它们吞掉 `IOException`**，重要数据必须 `checkError()` |
| 其他 | ZIP 读写要用 `UTF-8` 设编码；Commons IO 的 `deleteDirectory` / `copyDirectory` 仍值得用；`Properties.load(InputStream)` 是 **Latin-1**，中文会乱码 |
