
# 1. 标记-清除（Mark-Sweep）

```
标记阶段：                      清除阶段：
┌──┬──┬──┬──┬──┐                ┌──┬──┬──┬──┬──┐
│  │✓ │  │✓ │  │   遍历所有    │  │✓ │  │✓ │  │  ← 碎片化
│  │  │  │  │  │  标记存活    │  │  │  │  │  │
└──┴──┴──┴──┴──┘                └──┴──┴──┴──┴──┘
  死 活  死 活  死                 已回收  →  碎片
```

- **过程**：先标记所有存活对象，再统一清除未标记对象。
- **优点**：最简单。
- **缺点**：
  - 效率低（标记和清除都需遍历）
  - 产生大量内存碎片（导致分配大对象时找不到连续空间，触发另一次 GC）

# 2. 标记-复制（Mark-Copy）

```
┌──┬──┬──┬──┬──┐     ┌─────────────┐    ┌───────────────┐
│  │✓ │✓ │  │  │ ──→ │✓│✓│       │    │ (原空间全部清空)│
│  │  │  │  │  │ 复制│  │  │ 空闲  │    │ 成为新的保留区 │
└──┴──┴──┴──┴──┘     └─────────────┘    └───────────────┘
 使用区   保留区         (新的使用区)        (下次的保留区)
```

- **过程**：将内存分成两块，每次用一块。GC 时把存活对象复制到另一块，原空间全部清空。
- **优点**：无碎片，分配快（指针碰撞）。
- **缺点**：浪费一半内存（实际实现中 Eden : Survivor = 8:1:1）。

**HotSpot 的优化——Appel 式回收：**
- Eden + S0 + S1 = 新生代。
- 每次可用 = Eden + 一个 Survivor（90%）。
- 但"浪费"的是 10%（一个 Survivor 区），而不是一半。
- 如果 Survivor 空间不够，由老年代**分配担保**。

# 3. 标记-整理（Mark-Compact）

```
标记阶段：                      整理阶段：
┌──┬──┬──┬──┬──┐                ┌──────────┬──────┐
│  │✓ │  │✓ │  │   将存活对象   │✓ │✓ │    │ 空闲 │
│  │  │  │  │  │   向一端移动   │  │  │    │      │
└──┴──┴──┴──┴──┘                └──────────┴──────┘
```

- **过程**：标记存活对象 → 将它们移向一端 → 清理边界外的空间。
- **优点**：无碎片；不需要两倍空间。
- **缺点**：移动对象需要 STW，且比标记-复制慢（涉及对象引用的更新）。

```
三者对比：
┌──────────┬──────┬──────┬───────┐
│          │ 速度 │ 碎片 │ 开销  │
├──────────┼──────┼──────┼───────┤
│ 标记-清除 │ 中   │ 有   │ 无    │
│ 标记-复制 │ 快   │ 无   │ 空间  │
│ 标记-整理 │ 慢   │ 无   │ CPU   │
└──────────┴──────┴──────┴───────┘
```

# 4. 分代收集（Generational Collection）

这是**所有商用 JVM 的核心策略**，不是独立的算法，而是将前三种算法组合使用。

```
分代组合策略：
┌────────────┬─────────────────────────────┐
│ 新生代      │ 使用 标记-复制 算法          │
│ (对象朝生夕死)│ (Eden + S0 + S1)          │
├────────────┼─────────────────────────────┤
│ 老年代      │ 使用 标记-整理 或 标记-清除   │
│ (对象存活久) │                             │
└────────────┴─────────────────────────────┘
```

# 5. 跨代引用问题

- 新生代中的对象可能被老年代引用。
- Minor GC 时不能只扫描新生代，还需要知道哪些老年代对象引用了新生代对象。
- 朴素方案：Full GC 扫描整个堆 → **太慢**。

**解决方案：记忆集（Remembered Set）**

## 5.1 卡表（Card Table）

HotSpot 使用**卡表**实现记忆集：

```
老年代内存被分割成 512 字节的卡片(Card)：

┌─────┬─────┬─────┬─────┬─────┬─────┬─────┐
│Card0│Card1│Card2│Card3│Card4│Card5│Card6│... 
└─────┴─────┴─────┴─────┴─────┴─────┴─────┘
  ↑                            ↑
  卡表 (Card Table)             脏卡(Dirty Card)

如果 Card3 对应的老年代区域
引用了新生代对象 → Card3 标记为"脏"。

Minor GC 时：
  只需扫描标记为"脏"的卡片的引用，而非整个老年代。
```

- 卡表是一个 byte 数组，每个元素对应一个 Card。
- 当老年代对象引用发生变化时（写操作），通过**写屏障**（Write Barrier）更新卡表。
- 写屏障是 JVM 在引用赋值前后插入的代码逻辑，类似于 AOP 环绕通知。

```c
// 伪代码：写屏障更新卡表
void oop_field_store(oop* field, oop newValue) {
    *field = newValue;      // 引用赋值
    post_write_barrier(field, newValue);
}

void post_write_barrier(oop* field, oop newValue) {
    if (in_old_gen(field)) {    // 如果引用的持有者在老年代
        card_table[card_index(field)] = DIRTY;
    }
}
```

# 6. 分配担保（Handle Promotion）

- Minor GC 时，Survivor 区可能放不下存活对象 → 老年代兜底。
- JVM 在执行 Minor GC 前检查：
  1. 老年代最大可用连续空间 > 新生代所有对象总空间 → 安全
  2. 老年代最大可用连续空间 > 历次晋升老年代对象的平均大小 → 冒险
  3. 不满足 2，则先进行一次 Full GC，再尝试 Minor GC

```bash
# JDK 7+ 默认打开
-XX:+HandlePromotionFailure
```

# 7. 增量收集和并发收集

| 策略 | 说明 | 代表 |
|------|------|------|
| 串行收集 | 单线程 GC，全程 STW | Serial / Serial Old |
| 并行收集 | 多线程 GC，全程 STW | Parallel Scavenge / Parallel Old |
| 并发收集 | 部分阶段与应用线程并发 | CMS, G1, ZGC |
| 增量收集 | 每次只回收一小部分，多次完成 | G1 |

**并发（Concurrent）vs 并行（Parallel）：**
- **并行**：多条 GC 线程一起工作，但用户线程仍然暂停（STW）。
- **并发**：GC 线程和用户线程同时运行（不暂停或极短暂停）。

# 8. 三色标记法（Tri-color Marking）

CMS、G1、ZGC 等并发收集器都使用三色标记：

```
白色 (White)  → 尚未访问的对象（GC 结束后，白色 = 垃圾）
灰色 (Gray)   → 已访问但引用的子对象尚未全部访问
黑色 (Black)  → 已访问且所有子对象都已访问完成
```

**标记过程：**
1. GC Roots 直接引用的对象标记为灰色。
2. 从灰色集合取对象，将其引用的白色对象标记为灰色，自身标为黑色。
3. 重复步骤 2，直到灰色集合为空。
4. 剩余的白色对象即垃圾。

**并发标记的问题——对象消失：**
- 条件：扫描过程中黑色对象新增了对白色对象的引用，且灰色对象删除了对该白色对象的引用。
- 解决方案：**增量更新**（CMS）或 **SATB 原始快照**（G1）。

## 8.1 增量更新（Incremental Update — CMS）

- 黑色对象新增引用到白色对象时，将黑色对象重新标记为灰色。
- 重新扫描。

## 8.2 SATB（Snapshot At The Beginning — G1）

- 在并发标记开始时，对堆做一个逻辑快照。
- 标记过程中删除引用，通过**写屏障**记录到 SATB 队列。
- 最终标记时扫描 SATB 队列，确保快照中的存活对象不被漏标。

# 9. 漏标与多标

| 情况 | 含义 | 后果 |
|------|------|------|
| 漏标 (Missing) | 本应存活的对象被误回收 | 程序崩溃，绝对不能发生 |
| 多标 (Floating Garbage) | 本应回收的对象被保留 | 浮动垃圾，下次 GC 回收，可接受 |

- 漏标是 JVM 的 bug，多标是可以容忍的浪费。
