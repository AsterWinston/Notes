# 1. 标记-清除（Mark-Sweep）

## 1.1 基本过程

### 1.1.1 两阶段流程

```text
标记阶段：                      清除阶段：
┌──┬──┬──┬──┬──┐                ┌──┬──┬──┬──┬──┐
│  │✓ │  │✓ │  │   遍历所有    │  │✓ │  │✓ │  │  ← 碎片化
│  │  │  │  │  │  标记存活    │  │  │  │  │  │
└──┴──┴──┴──┴──┘                └──┴──┴──┴──┴──┘
  死 活  死 活  死                 已回收  →  碎片
```

- **过程**：先标记所有存活对象，再统一清除未标记对象。

### 1.1.2 成本模型：两趟遍历

- 两趟遍历：标记趟 ∝ 存活对象数（10 篇 2.2.2），清除趟 ∝ 扫描范围内的对象/空间数。
- 两趟都不搬移对象 ⇒ 停顿可拆分、清除可并发（这正是 CMS 选它的原因），但空间整理度为零。

## 1.2 优缺点

| 维度 | 评价 |
|------|------|
| 优点 | 最简单；不需要额外空间；不移动对象（引用永不失效，可实现成并发） |
| 缺点 | 效率低（标记和清除都需遍历） |
| 缺点 | 产生大量内存碎片（分配大对象时找不到连续空间 → 触发另一次 GC） |
| 副作用 | 空闲空间退化为 Free List，分配从"指针碰撞"降级为"查表 + 切割"（见 [6_heap](6_heap.md) 2.1.1） |

## 1.3 适用代与代表收集器

| 算法 | 适用代 | 代表实现 |
|------|--------|----------|
| 标记-清除 | 老年代（碎片尚有大块可用、且移动成本高） | **CMS 老年代**（唯一"纯清除"的商用收集器，也因此成为其原罪，见 [12_gc_collectors](12_gc_collectors.md) 第 5 节） |

# 2. 标记-复制（Mark-Copy）

## 2.1 基本过程

### 2.1.1 两块交替流程

```text
┌──┬──┬──┬──┬──┐     ┌─────────────┐    ┌───────────────┐
│  │✓ │✓ │  │  │ ──→ │✓│✓│       │    │ (原空间全部清空)│
│  │  │  │  │  │ 复制│  │  │ 空闲  │    │ 成为新的保留区 │
└──┴──┴──┴──┴──┘     └─────────────┘    └───────────────┘
 使用区   保留区         (新的使用区)        (下次的保留区)
```

- **过程**：将内存分成两块，每次用一块。GC 时把存活对象复制到另一块，原空间全部清空。

### 2.1.2 为什么便宜：成本 ∝ 存活集

- 复制天然完成"标记 + 整理 + 分配（Free List 清零）"三件事，成本只花在**存活对象**上——新生代存活率 <10%，这正是它便宜的原因。
- 反面：垃圾越少越慢（要搬的全是活的），所以老年代绝不用朴素复制。

## 2.2 优缺点

| 维度 | 评价 |
|------|------|
| 优点 | 无碎片；分配快（指针碰撞）；成本 ∝ 存活对象数，垃圾越多越快 |
| 缺点 | 朴素实现浪费一半内存 |
| 缺点 | 存活率高时（老年代）复制量巨大 → 只适合"朝生夕死"的区域 |

## 2.3 HotSpot 的优化——Appel 式回收与损耗公式

### 2.3.1 Appel 式回收要点（Cheney / Appel 变体）

- Eden + S0 + S1 = 新生代。
- 每次可用 = Eden + 一个 Survivor（90%）。
- 但"浪费"的是 10%（一个 Survivor 区），而不是一半。
- 如果 Survivor 空间不够，由老年代**分配担保**（第 6 节）。

### 2.3.2 损耗公式与 8:1:1 的关系

```text
复制损耗模型（R = Eden 与较小 Survivor 之比，SurvivorRatio 参数）：
   可用率 = (Eden + To) / (Eden + From + To) = (R+1)/(R+2)
   R=8  → 可用 9/10 = 90%，损耗 10%
   R=1  → 可用 2/3 ≈ 67%，损耗 33%（朴素对半）
   R→∞  → 损耗→0，但幸存者无处安放 → 频繁晋升 → 老年代遭殃
→ 8:1:1 是"空间损耗"与"幸存者容量"在弱分代假说下的折中（IBM 实测 98% 对象
  活不过第一轮：1/8 的 Survivor 已足够接住幸存者）
推导细节见 [6_heap](6_heap.md) 2.2.3
```

## 2.4 适用代与代表收集器

| 适用代 | 代表实现 |
|--------|----------|
| **新生代**（标配） | Serial、ParNew、Parallel Scavenge 的 Young GC；G1 的 Young/Mixed 复制阶段；ZGC 的 Relocation |
| 特点 | 各收集器差别不在"要不要复制"，而在**并行度、停顿控制、晋升策略**（见 [12_gc_collectors](12_gc_collectors.md)） |

# 3. 标记-整理（Mark-Compact）

## 3.1 基本过程

```text
标记阶段：                      整理阶段：
┌──┬──┬──┬──┬──┐                ┌──────────┬──────┐
│  │✓ │  │✓ │  │   将存活对象   │✓ │✓ │    │ 空闲 │
│  │  │  │  │  │   向一端移动   │  │  │    │      │
└──┴──┴──┴──┴──┘                └──────────┴──────┘
```

- **过程**：标记存活对象 → 将它们移向一端 → 清理边界外的空间。

## 3.2 为什么比复制贵

### 3.2.1 全链路成本拆解

```text
整理 = 标记 + 计算新地址 + 搬移 + 全场引用更新
```

- 复制只需"搬 + 在搬的过程中顺手改引用"（引用者全在待复制集内）；整理的引用者散布全场，更新是独立负担。

### 3.2.2 引用更新的两种做法

```text
  ① 两遍扫描：搬移后全堆扫一遍把所有指向旧地址的引用改掉 → 第二遍 ∝ 全堆
  ②  forwarding pointer：对象头留转发指针，边发现边修正 → 依赖对象头空间
老年代存活率高（>50%）：搬移量 ∝ 存活集 ≈ 大半个堆，复制算法的优势荡然无存，
却仍要付出"引用更新"的代价 → 所以只在"空间真不够"的 Full GC 里使用
```

## 3.3 优缺点与代表收集器

| 维度 | 评价 |
|------|------|
| 优点 | 无碎片；不需要两倍空间 |
| 缺点 | 移动对象需要 STW，且比标记-复制慢（涉及对象引用的更新） |
| 代表 | **Serial Old、Parallel Old**；G1 的 Full GC（JDK 10 起并行化）；本质是"清除了碎片的重型武器" |

## 3.4 三者对比

```text
三者对比：
┌──────────┬──────┬──────┬───────┐
│          │ 速度 │ 碎片 │ 开销  │
├──────────┼──────┼──────┼───────┤
│ 标记-清除 │ 中   │ 有   │ 无    │
│ 标记-复制 │ 快   │ 无   │ 空间  │
│ 标记-整理 │ 慢   │ 无   │ CPU   │
└──────────┴──────┴──────┴───────┘
```

| 算法 | 成本 ∝ | 能否并发化 | 代表代 |
|------|--------|-----------|--------|
| 标记-清除 | 扫描范围大小 | 容易（不移动） | 老年代（CMS） |
| 标记-复制 | 存活对象数 | 移动瞬间必须 STW/读屏障 | 新生代 |
| 标记-整理 | 存活对象数 + 引用更新 | 难（需读屏障，如 ZGC） | 老年代 / Full GC |

# 4. 分代收集（Generational Collection）

这是**所有主流商用 JVM 的核心策略**，不是独立的算法，而是将前三种算法按代"各就各位"。

## 4.1 算法分派图

```text
分代组合策略：
┌────────────┬─────────────────────────────┐
│ 新生代      │ 使用 标记-复制 算法          │
│ (对象朝生夕死)│ (Eden + S0 + S1)          │
├────────────┼─────────────────────────────┤
│ 老年代      │ 使用 标记-整理 或 标记-清除   │
│ (对象存活久) │                             │
└────────────┴─────────────────────────────┘

         弱分代假说 → 新生代小、高频、复制
依据      强分代假说 → 老年代大、低频、标记类
         跨代引用假说 → 记忆集/卡表兜住老→新引用（第 5 节）
```

## 4.2 串行 / 并行 / 并发 / 增量——执行策略维度

分代决定"**收哪里、用什么算法**"；执行策略决定"**GC 线程与用户线程的关系**"：

### 4.2.1 策略矩阵

| 策略 | 说明 | 代表 |
|------|------|------|
| 串行收集 | 单线程 GC，全程 STW | Serial / Serial Old |
| 并行收集 | 多线程 GC，全程 STW | Parallel Scavenge / Parallel Old |
| 并发收集 | 部分阶段与应用线程并发 | CMS, G1, ZGC |
| 增量收集 | 每次只回收一小部分，多次完成 | G1 |

### 4.2.2 并发（Concurrent）vs 并行（Parallel）

- **并行**：多条 GC 线程一起工作，但用户线程仍然暂停（STW）——目的是**缩短单次停顿**；
- **并发**：GC 线程和用户线程同时运行（不暂停或极短暂停）——目的是**消灭停顿**，代价是要处理"边跑边变"的对象图（第 8 节三色标记）+ 抢 CPU。

## 4.3 分代不是必须的

- **Epsilon**（`-XX:+UseEpsilonGC`，JDK 12 实验）：只分配、永不回收，堆满即亡——用于极短命进程与分配开销基准测试。
- **非分代 ZGC**（JDK 15~22 的默认形态）：全堆一个周期统一并发处理，靠读屏障免掉分代；但大堆高分配率下"每次都全堆"成本高 → **分代 ZGC** 于 JDK 21 实验（JEP 439）、JDK 23 起成为 ZGC 默认（JEP 490）——分代在低延迟世界"复活"，机制见 [13_low_latency_gc](13_low_latency_gc.md)。
- 结论：分代是**性能工程选择**（用空间换扫描范围），不是可达性分析的理论要求。

# 5. 跨代引用与记忆集（卡表）

- 新生代中的对象可能被老年代引用。
- Minor GC 时不能只扫描新生代，还需要知道哪些老年代对象引用了新生代对象。

## 5.1 成本算账：朴素方案 vs 记忆集

```text
朴素方案：Minor GC 时把整个老年代当根集扫描 → 成本 ∝ 老年代大小 → 每轮 Young GC
          都退化成全堆遍历，分代失去意义 ❌

记忆集方案：提前把"老年代中持有新生代引用的对象"登记在案
   Young GC 成本 = 栈根 + 新生代 + Σ(脏卡覆盖的老年代局部)
   跨代引用极少（跨代引用假说）→ 脏卡只占老年代很小比例 ✔

登记成本转嫁到哪里？→ 每次"老年代字段写引用"的瞬间（写屏障）——
   把 O(扫描) 摊销成 O(赋值) 的一条指令
```

## 5.2 记忆集的实现粒度

| 粒度 | 含义 | 空间/精度权衡 |
|------|------|---------------|
| 字粒度 | 精确到每个引用字段 | 表最小开销最大？——精确但元数据爆炸，极少商用 |
| 字节/双字粒度 | 几个字段共享一项 | 折中 |
| **卡粒度（512B）** | HotSpot 选择：一"卡"内任意字段变脏则整卡脏 | 表极小（老年代 1GB → 2MB 卡表），扫描脏卡有少量假阳性 |

## 5.3 卡表结构与定位算法

HotSpot 使用**卡表**实现记忆集：

### 5.3.1 卡片划分与脏卡

```text
老年代内存被分割成 512 字节的卡片(Card)：

┌─────┬─────┬─────┬─────┬─────┬─────┬─────┐
│Card0│Card1│Card2│Card3│Card4│Card5│Card6│... 
└─────┴─────┴─────┴─────┴─────┴─────┴─────┘
  ↑                            ↑
  卡表 (Card Table)             脏卡(Dirty Card)

如果 Card3 对应的老年代区域
引用了新生代对象 → Card3 标记为"脏"。

Minor GC 时：
  只需扫描标记为"脏"的卡片的引用，而非整个老年代。
```

- 卡表 = 一个 **byte 数组**，数组第 i 项对应老年代第 i 个 512B 卡片；0=clean，脏卡标记写非零值。

### 5.3.2 地址 → 卡号：移位定位

地址 → 卡号只需移位（512 = 2⁹）：

```c
card_idx = (address_of_field - heap_start) >> 9;   // 一条移位指令
card_table[card_idx] = DIRTY;                       // 一次字节写
```

## 5.4 写屏障（Store Barrier）与置脏

### 5.4.1 写屏障伪代码

- 当老年代对象引用发生变化时（写操作），通过**写屏障**（Write Barrier）更新卡表。
- 写屏障是 JVM 在引用赋值前后插入的代码逻辑，类似于 AOP 环绕通知。

```c
// 伪代码：写屏障更新卡表
void oop_field_store(oop* field, oop newValue) {
    *field = newValue;      // 引用赋值
    post_write_barrier(field, newValue);
}

void post_write_barrier(oop* field, oop newValue) {
    if (in_old_gen(field)) {    // 如果引用的持有者在老年代
        card_table[card_index(field)] = DIRTY;
    }
}
```

### 5.4.2 实现细节

- 实际 HotSpot 实现更进一步：新生代的对象"整代都是扫描对象"，所以只有**老年代对象变脏**才需要记；写屏障里还有"已是脏卡则跳过"的判断，避免重复写。

## 5.5 卡表只记"老 → 新"：被指向与被覆盖

### 5.5.1 四种写操作对照

| 写操作 | 需要标脏吗 | 原因 |
|--------|-----------|------|
| 老.field = 新对象 | **需要** | 制造了"Minor GC 看不见的外部引用者" |
| 新.field = 老对象 | 不需要 | Minor GC 本来全扫新生代；且不影响老年代可达性判定 |
| 老.field = 老对象 | 不需要 | 本次不回收老年代，老→老引用无影响 |
| 老.field = null（断开） | 通常也标脏 | 卡表只有"脏/净"两态，**不区分增删**，保守标脏可接受 |

### 5.5.2 被指向引用 vs 被覆盖引用

| | 被指向引用（老 → 新，新增） | 被覆盖引用（字段旧值被改写） |
|--|------------------------------|-------------------------------|
| 卡表知道什么 | 只知道"这张卡被写过"（位置） | 同样只记位置，**不知道盖掉了谁** |
| GC 时如何补偿 | 扫描脏卡覆盖范围内**所有对象的全部字段**，找出指向新代者 | 被断开的旧引用随整卡扫描自然"不再被发现"，无需额外补偿 |
| 后果 | 保证不漏"新入边" | 旧入边消失不影响正确性，只会让该卡下轮仍可能被白扫一次 |

- 一句话：卡表是"只记**位置**、不记**内容**"的粗粒度信号，写入时先弄脏、扫描时再判精确——这也是它便宜的原因。

## 5.6 Young GC 时根集合的拼图

```text
          Young GC 的"根"
                ▲
   ┌────────────┼─────────────────┐
   │            │                 │
 线程栈帧     全部新生代对象     脏卡覆盖的老年代对象
 (OopMap)   （整体视为扫描面）   （卡表命中 → 临时根）
                                    ▲
                          老年代其余 99%+ 空间：不碰
```

## 5.7 G1 RSet：卡表的精细化

- G1 放弃了"全局单卡表"，给**每个 Region 维护自己的 RSet**（谁引用了我），底层仍按 512B 卡片记录，再配 **Refinement 线程**异步把脏卡消化进 RSet——本质是"按引用目标分组的卡表"，扫描时 O(1) 定位入边，代价是内存开销（可达堆几个百分点）与写屏障变贵。详见 [12_gc_collectors](12_gc_collectors.md) 6.4。

# 6. 分配担保（Handle Promotion）

- Minor GC 时，Survivor 区可能放不下存活对象 → 老年代兜底。

## 6.1 担保规则与版本演进

### 6.1.1 JDK 6 时代的三项检查（帮助理解"担保"思想）

- JVM 在执行 Minor GC 前检查：
  1. 老年代最大可用连续空间 > 新生代所有对象总空间 → 安全
  2. 老年代最大可用连续空间 > 历次晋升老年代对象的平均大小 → 冒险
  3. 不满足 2，则先进行一次 Full GC，再尝试 Minor GC

### 6.1.2 JDK 6u24 / 7u40 之后的简化

```bash
# JDK 7+ 默认打开（且该参数在 JDK 7u40+ 实际已被忽略，策略固定）
-XX:+HandlePromotionFailure
```

- 6u24 之后大幅简化：只查"老年代连续剩余 > 新生代已用"，依赖弱分代假说"幸存者本来就少"（现行规则全文见 [6_heap](6_heap.md) 5.2）。

## 6.2 担保失败路径

```text
Young GC 前：老年代连续剩余 > 新生代已用？ ──否──▶ 先 Full GC
复制时：To 区满 → 存活者直接晋升老年代
晋升失败（老年代碎片/不足）──▶ 退化 Full GC（CMS 场景退化 Serial Old，长 STW）
G1 对应物：to-space exhausted / Evacuation Failure ──▶ 并发标记来不及则 Full GC
完整规则与版本差异见 [6_heap](6_heap.md) 第 5 节
```

# 7. 年轻代触发的 Full GC

"明明是 Young GC，怎么冒出 Full GC？"——绝大多数由**晋升路径堵塞**导致。

## 7.1 触发链条

```text
Eden 满 → Young GC
   ├─ 幸存者多（分配率高/对象寿命错配）
   ▼
To(Survivor) 满 → 剩余存活者"溢出"直接晋升
   ▼
老年代连续空间不足（Parallel 系要求【连续】；CMS 要求够用且碎片可容）
   ▼
分配担保失败 / promotion failed / to-space exhausted
   ▼
Full GC（整堆 + 元空间，串行或并行整理）—— 单次耗时可达 Young GC 的 10 倍以上
```

## 7.2 日志特征

### 7.2.1 Serial / ParNew / CMS 关键词

```text
JDK8 Serial/ParNew:
  [GC (Allocation Failure) ... [Full GC (Allocation Failure)  [Tenured: 5373K->5367K...]  62M->6M]
  (CMS) promotion failed
  (CMS) concurrent mode failure        ← 并发清除赶不上分配
```

### 7.2.2 G1 / ZGC 关键词

```text
G1:
  (G1 Humongous Allocation) pause full   ← 大对象连续空间凑不齐
  to-space exhausted                     ← 复制目标区不足，Evacuation Failure
ZGC:  Allocation Stall                   ← 回收速度跟不上分配，线程被挂起等空间
```

## 7.3 调参思路

| 症状 | 方向 |
|------|------|
| Young GC 后晋升量大、老年代水位快涨 | 查"短命大对象/缓存错放"；加大新生代比例、调整 MaxTenuringThreshold/TargetSurvivorRatio（[6_heap](6_heap.md) 3.2） |
| 老年代够但**连续空间**不够（CMS/PS） | 提高整理频率（CMSFullGCsBeforeCompaction）、换 G1 |
| Humongous 频繁 | 调大 G1HeapRegionSize 或改业务分块 |
| 兜底无效 | 增大堆 / 换并发收集器，流程见 [14_gc_tuning](14_gc_tuning.md) |

# 8. 三色标记法（Tri-color Marking）

CMS、G1、ZGC 等并发收集器都使用三色标记——它是**让"标记阶段"与应用并发**的理论基础。

## 8.1 三色定义与串行过程

### 8.1.1 三色定义与状态转换图

```text
白色 (White)  → 尚未访问的对象（GC 结束后，白色 = 垃圾）
灰色 (Gray)   → 已访问但引用的子对象尚未全部访问
黑色 (Black)  → 已访问且所有子对象都已访问完成

            被灰对象首次指向            其所有出边处理完
  白 ──────────────────────▶ 灰 ──────────────────────▶ 黑
  ▲                          │(灰集: 待处理工作列表)      │
  └── 每轮：取灰 → 扫其字段(白→灰) → 自身转黑 ─────────────┘
  终态：黑集 = 存活，白集 = 垃圾，灰集为空
```

### 8.1.2 串行标记四步

1. GC Roots 直接引用的对象标记为灰色。
2. 从灰色集合取对象，将其引用的白色对象标记为灰色，自身标为黑色。
3. 重复步骤 2，直到灰色集合为空。
4. 剩余的白色对象即垃圾。

## 8.2 并发修改与漏标条件

### 8.2.1 漏标发生的唯一（充要）条件

串行标记时"黑不再被重看"是安全的；应用并发修改引用图后，这条不变量可能被打破。**对象消失（漏标）当且仅当同时发生两件事**：

```text
① 黑对象【新增】了指向白对象 W 的引用   （黑不会再被扫描 → W 的新入边看不见）
② 所有 灰→…→W 的原有路径被【删除】      （灰的保护链断了 → W 再无人扫描）
     ┌───┐ 新增  ┌───┐            两条同时成立 → W 被判死，但它从根可达 → 悬空引用 ❌
     │ 黑 │─────▶│ 白│
     └───┘       └───┘  灰──▶W 被改/删
```

- 两个条件**缺一不可**：只破 ① 或只破 ②，白对象总还挂在某条灰链上等待处理。
- 解法即"砍掉任一条件"：增量更新砍 ①，SATB 砍 ②。

### 8.2.2 强 / 弱三色不变式

| 不变式 | 内容 | 谁遵守 |
|--------|------|--------|
| **强三色不变式** | 禁止黑色直接指向白色（黑对象的出边要么黑要么灰） | 增量更新维持它 |
| **弱三色不变式** | 允许黑→白，但白必须另有一条 灰→…→白 的路径保护 | SATB 维持它 |

## 8.3 解法一：增量更新（Incremental Update — CMS）

### 8.3.1 机制与写后屏障

- 黑色对象新增引用到白色对象时，将黑色对象重新标记为灰色（记录其**新增引用**）。
- 重新扫描。

```c
// CMS 写后屏障（简化伪代码）
void oop_field_store(oop* field, oop new_obj) {
    *field = new_obj;
    if (concurrent_marking && is_black(holder) && !is_null(new_obj))
        mark_grey_dirty(holder);          // 黑退回灰 / 记入 dirty 列表
}
```

### 8.3.2 代价：Remark 抖动

- 特性：改动记在**写后**，Remark（重新标记）STW 阶段把 dirty 对象**重新扫一遍**收敛。
- 并发修改越多 → dirty 集越大 → Remark 越长 → 二次停顿代价；这是 CMS 日志里 remark 时间随流量抖动的根源。

## 8.4 解法二：SATB（Snapshot At The Beginning — G1）

### 8.4.1 机制与写前屏障

- 在并发标记开始时，对堆做一个逻辑快照（此刻灰/黑边界即"快照"）。
- 标记过程中删除引用，通过**写屏障**记录**删除前**的旧引用值到 SATB 队列。
- 最终标记时扫描 SATB 队列，确保快照中的存活对象不被漏标——被断开的对象在快照内仍算存活（宁可浮动垃圾）。

```c
// G1 SATB 写前屏障（简化伪代码）
void oop_field_store(oop* field, oop new_obj) {
    oop old = *field;
    if (concurrent_marking && !is_null(old))
        satb_queue.push(old);            // 记录"被覆盖掉"的旧引用（写【前】）
    *field = new_obj;
}
```

### 8.4.2 代价：浮动垃圾

- 快照成立之后才"死亡"的对象，本周期仍被当作快照内的活对象 → 清除阶段不动它 → 只能等下个周期（浮动垃圾的定义与可容忍性见第 9 节）。

## 8.5 两方案对比

| 维度 | 增量更新 (CMS) | SATB (G1) |
|------|----------------|-----------|
| 屏障记录时机 | 写**后**：黑对象的新入边 | 写**前**：被覆盖的旧引用 |
| 维护的不变式 | 强三色 | 弱三色 |
| 破坏的条件 | ①（黑指白新增） | ②（灰到白路径被删） |
| 并发修改的代价 | Remark 重扫 dirty → **停顿变长** | 队列变大但处理可摊销 → 停顿稳 |
| 副作用 | 基本无浮动（本轮活对象更"真实"） | **浮动垃圾**：快照后被删的对象本周期不回收 |
| 屏障复杂度 | 较低 | 较高（还要配合 RSet 卡表，两道屏障叠加） |

```text
时序：        CMS(增量更新)                     G1(SATB)
并发标记   改引用→记 dirty 对象              改引用→记 旧值 入队
Remark     STW：重扫 dirty，可能再迭代      STW：只排空 SATB 队列(少量再扫)
结果       标记结果贴近"当下"                标记结果贴近"开始时快照"
```

## 8.6 读屏障方案（预告）

- CMS/G1 用**写屏障**保证正确性；ZGC 反过来用**读屏障（Load Barrier）**：访问引用时顺带检查/修正颜色与转发的新地址，把"对象移动"也做成并发 → 停顿只剩固定几处根处理，全程 <1ms。详见 [13_low_latency_gc](13_low_latency_gc.md)。

# 9. 漏标与浮动垃圾

| 情况 | 含义 | 后果 |
|------|------|------|
| 漏标 (Missing) | 本应存活的对象被误回收 | 程序崩溃（悬空引用），绝对不能发生 |
| 多标 (Floating Garbage) | 本应回收的对象被保留 | 浮动垃圾，下次 GC 回收，可接受 |

- 漏标是 JVM 的 bug，多标是可以容忍的浪费。

## 9.1 两类错误的不对称性

```text
漏标 → 活的被删 → 语义错误 → 数据损坏/崩溃        ← 正确性问题，零容忍
假标 → 死的晚删 → 本周期多占内存，下轮回收         ← 容量问题，可容忍
设计准则：一切并发标记方案都是"用可控的多标，堵死任何漏标的可能"
```

## 9.2 CMS 的浮动垃圾与触发阈值

### 9.2.1 为什么必须留余量

- 并发清除期间程序仍在造垃圾，且**清除阶段无法回收标记后才产生的垃圾** → 老年代必须在周期内留出"并发期间的消耗余量"。
- 阈值太激进（默认值随版本/自适应策略在 ~68%~92% 间变化，不可尽信一个数）→ 余量不足 → **Concurrent Mode Failure** 退化 Serial Old。

### 9.2.2 参数对策

- 建议固定阈值留余量：`-XX:CMSInitiatingOccupancyFraction=70~80 -XX:+UseCMSInitiatingOccupancyOnly`；参数逐条见 [12_gc_collectors](12_gc_collectors.md) 第 5 节。

# 10. 屏障技术总表（其他基础优化）

## 10.1 各收集器用了哪种屏障

| 收集器 | 卡表写后屏障 | 三色写后(增量更新) | 三色写前(SATB) | 读屏障 |
|--------|:---:|:---:|:---:|:---:|
| Serial / Serial Old | Young GC 需要（老→新） | ✗（无并发标记） | ✗ | ✗ |
| ParNew / Parallel | 同上 | ✗ | ✗ | ✗ |
| CMS | 需要 | **需要** | ✗ | ✗ |
| G1 | 需要（RSet refinement） | ✗ | **需要** | ✗（JDK 9 起字符串去重等局部除外） |
| ZGC（含分代） | 分代模式有记忆集 | ✗ | 分代模式配合 | **需要**（着色指针 + load barrier） |
| Shenandoah | 有 | ✗ | 需要 | 需要 |

## 10.2 屏障开销：低延迟的账单

### 10.2.1 写屏障税与后台消化线程

- 每条引用赋值多几条指令 → 吞吐典型损失个位数百分比；写屏障还会制造脏卡、队列，带来**后台消化线程**（G1 Refinement、SATB 线程）。

### 10.2.2 读屏障为什么更贵

- 读屏障成本摊在**所有**字段访问上，比写屏障更贵 → 配合**着色指针**（把元数据藏进 64 位指针高位）才可用（[13_low_latency_gc](13_low_latency_gc.md)）。

### 10.2.3 总结：屏障是 STW 的替代品

- 一句话总结 GC 五十年演进：**从"停顿里做正确性"到"用屏障换并发正确性"**——屏障就是 STW 的替代品，也是 10 篇第 9 节安全点模型的镜像（一个防"引用变化看不见"，一个防"引用变化看错时机"）。
