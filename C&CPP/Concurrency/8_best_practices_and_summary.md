前面七篇讲的是"怎么用"：线程、锁、条件变量、原子、future、线程池、调试。这一篇讲"怎么少用"——最好的并发代码，是让需要同步的地方尽可能少。绝大多数并发事故不是 API 用错，而是共享状态设计得太多、锁的责任边界没划清。下面把工程原则收拢成一套可执行的规范。

# 1. 从设计上避免共享

## 1.1 共享可变状态是万恶之源

| 状态类型 | 是否需要同步 | 说明 |
|---------|-------------|------|
| 不可变（`const`/只读） | 否 | 初始化后不再修改 |
| 线程私有（`thread_local`） | 否 | 每个线程一份 |
| 只读快照 | 否 | 拷贝后各自使用 |
| 共享可变 | 是 | 锁、原子或消息传递 |

★ **关键认知**：并发设计的第一步不是"加什么锁"，而是问"**这个数据为什么需要共享**"。能改成线程私有就私有，能改成只读就只读，能拷贝一份就拷贝。每消除一处共享，就消除一整类竞争、死锁和可见性问题。

## 1.2 线程私有数据

```cpp
thread_local std::vector<char> scratch(4096);   // 每个线程独立一份

void process() {
    scratch.clear();               // 无竞争，不需要锁
    fill(scratch);
    send(scratch);
}
```

`thread_local` 适合缓存、临时缓冲区、每线程统计。代价是每个线程一份内存，线程多时总量不小；不要在里面放跨线程共享的句柄。

批量计算也可以先本地累加，最后合并，避免全程争一把锁：

```cpp
long long local_sum = 0;
for (int v : chunk) local_sum += v;
{
    std::lock_guard<std::mutex> lock(mtx);
    total += local_sum;
}
```

## 1.3 不可变与只读快照

配置、路由表、字典这类"读多写极少"的数据，适合"写时复制 + 原子换指针"：

```cpp
std::shared_ptr<const RouteTable> table;

auto snapshot() { return std::atomic_load(&table); }
void update(std::shared_ptr<const RouteTable> next) {
    std::atomic_store(&table, std::move(next));   // 读者看到完整旧表或完整新表
}
```

★ **关键认知**：不可变数据天然线程安全。把"修改"变成"构造一个新版本再整体替换"，读者不需要锁，也不会看到中间状态。这是配置中心、路由、特征开关最常用的模式。

⚠ **关键认知**：`const` 成员函数不等于线程安全。如果类内部有 `mutable` 缓存、惰性计算、或者返回内部数据的引用，读者仍可能竞争。线程安全要单独设计并写进文档，不能靠 `const` 推断。

# 2. 优先消息传递

## 2.1 共享内存 vs 消息传递

| 方式 | 同步方式 | 优点 | 缺点 |
|------|---------|------|------|
| 共享内存 | 锁/原子 | 零拷贝、延迟低 | 竞争、死锁、可见性复杂 |
| 消息传递 | 队列 | 解耦、边界清晰、易扩展 | 拷贝/序列化开销、队列管理 |

消息传递把"两个线程改同一块内存"变成"一个线程发、另一个线程收"。业务状态各自私有，锁的范围被压缩到队列内部：

```cpp
class Worker {
public:
    void send(Message msg) { inbox_.push(std::move(msg)); }
    void run() {
        while (auto msg = inbox_.pop()) handle(*msg);
    }
private:
    BlockingQueue<Message> inbox_;   // 唯一共享点
    State state_;                    // 只有本线程访问
};
```

★ **关键认知**：消息传递的核心价值不是"性能"，而是**把同步点收敛到一处**。队列内部用锁也好、无锁也好，业务代码不再散落 `lock_guard`，可维护性和可验证性都大幅提升。

## 2.2 消息传递的边界

- 消息要**按值传递**，避免发送方修改已被接收方持有的对象。
- 队列要**有界**，否则生产快于消费时同样会 OOM。
- 关闭要有**明确协议**：停止接收、排空、通知消费者退出。
- 大对象考虑 `std::shared_ptr<const T>` 或移动语义，避免深拷贝。
- 不要用消息传递掩盖"本该同步返回"的调用。

⚠ **关键认知**：消息传递不是银弹。它把"数据竞争"换成了"消息顺序、重复投递、队列积压"等新问题，需要幂等、顺序保证和背压设计。

# 3. 锁的使用规范

## 3.1 固定锁顺序

```text
全局锁层级（数字越小越外层）：
  1. 配置锁
  2. 缓存锁
  3. 会话锁
  4. 日志锁

规则：只能从低层级向高层级申请，禁止反向。
```

同时需要多把锁时，用 `std::scoped_lock` 让标准库处理顺序；必须分步申请时，严格按层级：

```cpp
std::scoped_lock lock(config_mtx, cache_mtx, session_mtx);
```

★ **关键认知**：锁顺序是**全局契约**，必须写进文档、在评审中检查。只靠"我记得先锁 A"迟早会出错。

## 3.2 锁粒度：只保护共享内存

```cpp
void handle(Request req) {
    auto result = expensive_compute(req);   // 锁外计算
    write_to_disk(result);                  // 锁外 IO
    std::lock_guard<std::mutex> lock(mtx);
    cache_[req.id] = result;                // 锁内只有内存操作
}
```

| 原则 | 说明 |
|------|------|
| 锁内只碰内存 | 不做 IO、不睡眠、不等待网络 |
| 锁内不调外部代码 | 回调、虚函数、日志 sink 都可能回头加锁 |
| 临界区尽量短 | 但不要为了短而频繁加解锁 |
| 一把锁保护一组不变式 | 不要把强相关的数据拆到两把锁 |

## 3.3 不要在持锁时调用未知代码

```cpp
std::vector<Callback> local;
{
    std::lock_guard<std::mutex> lock(mtx);
    local = callbacks_;            // 锁内只拷贝
}
for (auto& cb : local) {
    cb(event);                     // 锁外调用，避免回调回头加锁
}
```

⚠ **关键认知**：**持锁调用回调是死锁的高发区**。你无法控制回调里做什么，最稳妥的规则是"锁内不调用任何非本类、非标准库的代码"。

# 4. 性能

## 4.1 伪共享

CPU 缓存以缓存行（通常 64 字节）为单位。两个线程分别修改同一缓存行里的不同变量，硬件仍要来回同步整行：

```text
缓存行（64 字节）
┌──────────────────────────────────────────────┐
│  counter_a (8B)  │  counter_b (8B)  │  其他   │
└──────────────────────────────────────────────┘
        ▲                   ▲
    线程 A 写            线程 B 写
```

```cpp
struct Counters {
    alignas(64) std::atomic<long long> a{0};   // 各占一个缓存行
    alignas(64) std::atomic<long long> b{0};
};
```

★ **关键认知**：伪共享（false sharing）不是逻辑错误，TSan 也检测不到，但会让多线程计数、对象池、无锁队列的性能莫名其妙地差。高频写的独立变量，用 `alignas(64)` 或填充字段隔开。

## 4.2 常见开销量级

| 操作 | 大致开销 | 说明 |
|------|---------|------|
| 无竞争 mutex 加解锁 | 十几到几十纳秒 | 比原子操作贵，但可接受 |
| 原子 RMW | 几纳秒到几十纳秒 | 取决于架构和竞争 |
| 上下文切换 | 几微秒 | 线程数超过核数后频繁发生 |
| 线程创建 | 几十微秒 | 线程池要避免每次创建 |

数值只用于建立直觉，具体以目标平台实测为准。

## 4.3 优化顺序

1. **先正确**：用最直白的锁保证没有竞争。
2. **再测量**：用 profiler 找真正的热点，不要凭感觉优化。
3. **再拆分**：分片锁、读写锁、线程私有累加。
4. **最后才考虑无锁**：确认单变量、可回收、有 ABA 防护。

⚠ **关键认知**：**没有测量就没有优化**。把 `mutex` 换成 `atomic` 不一定更快：竞争激烈时 CAS 循环可能比阻塞锁更浪费 CPU；伪共享可能让"无锁"比加锁慢一个数量级。

# 5. 可维护性

## 5.1 把同步封装在类里

```cpp
class Counter {
public:
    void increment() {
        std::lock_guard<std::mutex> lock(mtx_);
        ++value_;
    }
    long long value() const {
        std::lock_guard<std::mutex> lock(mtx_);
        return value_;
    }
private:
    mutable std::mutex mtx_;      // mutable：const 方法也要加锁
    long long value_ = 0;
};
```

★ **关键认知**：**不要把 mutex 暴露给调用方**，也不要返回内部数据的引用让调用方在锁外访问。锁的边界必须和数据边界重合，否则封装形同虚设。

## 5.2 文档化线程安全级别

| 级别 | 含义 | 例子 |
|------|------|------|
| 线程安全 | 多线程调用无需外部同步 | `Counter` |
| 条件线程安全 | 调用方需保证同一对象不被并发访问 | 大多数容器 |
| 非线程安全 | 只能在单线程使用 | `std::string` 的普通用法 |

在类注释或头文件里写清楚，比任何命名都有效：

```cpp
// 线程安全：所有公有方法可并发调用。
// 注意：value() 返回快照，不保证调用后立即反映其他线程的写入。
class Counter { /* ... */ };
```

## 5.3 生命周期与关闭

- 优先 `std::jthread` 或 RAII 包装，避免"析构时仍 joinable"；尽量避免 `detach`，必须 `detach` 时确保线程不访问可能先销毁的对象。
- 关闭顺序固定：停止接收 → 通知 → 排空/取消 → join。

```cpp
class Service {
public:
    Service() : worker_([this](std::stop_token st) { run(st); }) {}
    ~Service() { worker_.request_stop(); }   // jthread 析构时自动 join
private:
    void run(std::stop_token st) {
        while (!st.stop_requested()) do_one_round();
    }
    std::jthread worker_;
};
```

# 6. 上线前检查清单

## 6.1 设计与代码

| 检查项 | 通过标准 |
|--------|---------|
| 共享状态 | 每一处共享可变数据都有明确的同步策略 |
| 线程数量 | 有上限，CPU/IO 类型分别配置 |
| 队列 | 有界，背压策略明确 |
| 关闭 | 有确定协议，能排空或明确丢弃 |
| 错误传播 | 线程内异常有归宿，不静默丢失 |
| 锁 | 全部 RAII，多锁有固定顺序或 `scoped_lock` |
| 临界区 | 不含 IO、睡眠、网络等待，不调用外部代码 |
| 原子 | 复合逻辑用 CAS 或锁，不用 load+store |
| 内存序 | 默认 `seq_cst`，降级有注释说明 |
| 生命周期 | 无线程访问已销毁对象 |

## 6.2 测试

| 检查项 | 通过标准 |
|--------|---------|
| TSan | CI 中以 `-fsanitize=thread` 跑核心用例 |
| ASan | 单独跑内存越界和悬垂指针检查 |
| 压力测试 | 多线程、长时间、边界负载 |
| 关闭测试 | 反复启动/停止，无线程泄漏和挂起 |
| 故障注入 | 任务抛异常、队列满、下游超时 |

⚠ **关键认知**：并发测试**通过不代表没有 bug**，只代表这次的调度没有触发。真正的保障来自"减少共享 + 明确同步契约 + 代码评审"。

# 8. 总结

| 原则 | 一句话 |
|------|--------|
| 避免共享 | 线程私有、不可变、快照优先 |
| 消息传递 | 把同步点收敛到队列一处 |
| 锁顺序 | 全局固定，能用 `scoped_lock` 就不分步 |
| 锁粒度 | 只包共享内存，锁内不碰 IO 和回调 |
| 性能 | 先正确、再测量、最后才无锁 |
| 封装 | 同步细节藏在类里，不暴露 mutex |
| 生命周期 | 不 detach，关闭有协议，析构能 join |
| 验证 | TSan + ASan + 压测 + 评审 |

八篇走下来，主线可以浓缩成三句话：**能不让线程共享就不要共享**（线程私有、不可变、消息传递永远优先于加锁）；**必须共享时把同步写清楚**（一把锁保护一组不变式，锁顺序固定，临界区只碰内存）；**写完要验证**（TSan 找竞争，gdb 看全栈，压测提高复现率，评审兜住设计）。

并发模块到这里结束。接下来可以带着这套原则进入网络编程、服务端框架或性能优化等主题：无论是连接池、事件循环还是异步 IO，底层仍然是"谁拥有数据、谁负责同步、失败了怎么收场"这三个问题。
