走到这一篇，Make 的语法、规则、依赖、并行和排错都已经覆盖。剩下的问题不是"怎么写"，而是"什么时候该用 Make、怎么写得让别人愿意维护、换一台机器还能不能跑"。这一篇从 Make 与 CMake 的取舍谈起，最后给出一份可执行的最佳实践清单。

# 1. Make 与 CMake 的定位

## 1.1 两者不在同一层

```text
┌─────────────────────────────────────┐
│ CMakeLists.txt                      │
│   ↓ 生成                            │
│ build.ninja / Makefile / .sln ...   │
└──────────────┬──────────────────────┘
               ▼
┌─────────────────────────────────────┐
│ 构建执行器：make / ninja / msbuild  │
│   按依赖图调用编译器                │
└─────────────────────────────────────┘
```

CMake 是**构建系统生成器**，负责探测环境、管理目标、生成平台相关的构建文件；Make 是**构建执行器**，负责按依赖图执行命令。二者不是替代关系：CMake 完全可以把 Make 当作后端。

★ **关键认知**：Make 描述的是"**怎么做**"（命令 + 依赖），CMake 描述的是"**要什么**"（目标、源文件、链接库、安装规则）。项目越大、平台越多，"要什么"的抽象收益越明显。

## 1.2 对比

| 维度 | GNU Make | CMake |
|------|----------|-------|
| 抽象层次 | 规则与命令 | 目标与属性 |
| 跨平台 | 依赖 shell 与工具链 | 原生支持多平台生成器 |
| 依赖发现 | 手写 + `-MMD -MP` | `target_link_libraries` 自动传递 |
| 第三方库 | 手写 `-I`/`-l` 或 `pkg-config` | `find_package`、`FetchContent` |
| IDE 集成 | 较弱 | 生成 VS、Xcode、CLion 工程 |
| 学习曲线 | 语法少，但细节多 | 概念多，但结构统一 |
| 构建速度 | 快，直接执行 | 取决于后端（Ninja 通常更快） |
| 安装/导出 | 手写规则 | `install`、`export` 成熟 |
| 额外依赖 | 几乎无 | 需要安装 CMake |
| 典型场景 | 小型项目、嵌入式、教学、单平台 | 中大型项目、多平台、多目标 |

## 1.3 何时选谁

选 Make 的场景：

1. 项目只有几十个文件，构建逻辑简单。
2. 目标平台固定，工具链固定（嵌入式、单一 Linux 发行版）。
3. 需要极少的额外依赖，构建脚本要能"拷过去就能跑"。
4. 维护者熟悉 Make，且项目已经稳定。
5. 作为学习材料，想理解构建系统的底层机制。

选 CMake 的场景：

1. 需要同时支持 Linux、macOS、Windows。
2. 有多个库、多个可执行文件、测试和安装规则。
3. 依赖多个第三方库，希望自动发现和传递编译选项。
4. 团队使用不同 IDE。
5. 需要 `install`、`export`、`CTest`、CPack 等完整生态。

⚠ **关键认知**：不要因为"CMake 更现代"就把一个三十行的 Makefile 迁到 CMake，也不要因为"Make 更底层"就在大型跨平台项目里硬扛。**构建系统的复杂度应该匹配项目的复杂度**，而不是匹配个人偏好。

# 2. 可维护性

## 2.1 变量集中管理

```makefile
# 所有可配置项集中在文件顶部
CXX      ?= g++
CXXFLAGS := -std=c++17 -Wall -Wextra
CPPFLAGS := -Iinclude
LDFLAGS  :=
LDLIBS   :=

SRCDIR   := src
BUILDDIR := build
```

规则部分只引用变量，不出现魔法字符串。这样换编译器、加选项、改目录都只需要动一处。

## 2.2 规则复用而不是复制

```makefile
# 好：一条模式规则覆盖所有源文件
$(OBJDIR)/%.o: $(SRCDIR)/%.cpp | $(OBJDIR)
	$(CXX) $(CPPFLAGS) $(CXXFLAGS) -c $< -o $@
```

```makefile
# 差：每个文件复制一遍，新增文件必漏
main.o: main.cpp
	$(CXX) -c main.cpp -o main.o
util.o: util.cpp
	$(CXX) -c util.cpp -o util.o
```

复制规则不仅冗长，还会让不同目标的编译选项逐渐分叉。

## 2.3 目录与命名约定

| 约定 | 好处 |
|------|------|
| `src/` 放实现、`include/` 放头文件 | 依赖边界清晰 |
| 产物统一进 `build/` | `clean` 简单、仓库干净 |
| 目标名与产物路径一致 | `make build/bin/app` 可预测 |
| 伪目标用动词命名 | `clean`、`test`、`run`、`install` |
| 一个 Makefile 一个职责 | 避免"什么都管"的巨型文件 |

## 2.4 给未来的维护者留线索

```makefile
# 用法：
#   make                 调试构建
#   make MODE=release    发布构建
#   make -j8             并行构建
#   make clean           清理产物
```

Makefile 顶部的三行注释，比任何外部文档都更容易被看到。关键变量、非显然的依赖、平台限制，都应该就近注释。

★ **关键认知**：可维护性不是"写得短"，而是"**改一处不会牵连十处**"。变量集中、规则抽象、目录规范，本质上都是在减少修改时需要同时理解的范围。

# 3. 可移植性

## 3.1 用工具变量而不是硬编码

```makefile
CC       ?= cc
CXX      ?= c++
AR       ?= ar
RM       ?= rm -f
MKDIR_P  ?= mkdir -p
```

| 写法 | 问题 |
|------|------|
| `g++ -c ...` | 换 Clang 或交叉编译时要全文件替换 |
| `$(CXX) -c ...` | 可用 `make CXX=clang++` 覆盖 |
| `/usr/bin/g++` | 换机器直接失效 |

## 3.2 shell 与路径差异

| 差异 | Unix | Windows |
|------|------|---------|
| 默认 shell | `/bin/sh` | `cmd.exe`（无 sh 时） |
| 建目录 | `mkdir -p` | `mkdir`（需逐级） |
| 删除 | `rm -rf` | `rmdir /s /q` |
| 路径分隔 | `/` | `\`（多数工具也接受 `/`） |
| 可执行后缀 | 无 | `.exe` |

可行策略：

1. 在 Windows 上使用 MSYS2/MinGW 提供的 `sh`、`make`，让命令保持 POSIX 风格。
2. 用变量封装平台差异：

```makefile
ifeq ($(OS),Windows_NT)
RM      := del /q
MKDIR_P := mkdir
else
RM      := rm -f
MKDIR_P := mkdir -p
endif
```

3. **路径里不要有空格**。Make 以空格分隔依赖，含空格的路径需要大量转义，几乎没有项目能处理干净。

## 3.3 编译器差异

| 选项 | GCC/Clang | MSVC |
|------|-----------|------|
| 标准 | `-std=c++17` | `/std:c++17` |
| 警告 | `-Wall -Wextra` | `/W4` |
| 优化 | `-O2` | `/O2` |
| 调试 | `-g` | `/Zi` |
| 宏 | `-DFOO` | `/DFOO` |
| 包含路径 | `-Iinclude` | `/Iinclude` |
| 输出 | `-o app` | `/Fe:app` |

如果确实需要同时支持 GCC 和 MSVC，Makefile 里的条件分支会迅速膨胀。这正是 CMake 存在的理由之一。

⚠ **关键认知**：可移植性不等于"所有平台共用一份 Makefile"。更现实的目标是"**每个受支持的平台都有一份经过验证的构建路径**"，并用 CI 持续验证，而不是假设一套命令到处都能跑。

# 4. 最佳实践清单

## 4.1 结构

- 源码与构建产物分离，产物统一进 `build/`。
- `.gitignore` 覆盖 `build/`、`*.o`、`*.d`、`*.a`、`*.so`、可执行文件。
- 不在仓库里提交 `.d`、`.o` 和编译出来的库。
- Makefile 放在项目根目录，路径相对于它书写。

## 4.2 规则

- 命令行一律用 Tab，编辑器显式配置。
- 所有动作型目标加 `.PHONY`。
- 用模式规则或静态模式规则，避免复制粘贴。
- 头文件依赖用 `-MMD -MP` 自动生成，`-include $(DEPS)` 引入。
- 目录依赖用顺序依赖 `|`，不要用普通依赖。
- 一次生成多个文件的规则用 `&:`（GNU Make 4.3+）。
- 启用 `.DELETE_ON_ERROR`，避免残留半成品。
- 递归调用用 `$(MAKE)`，不用裸 `make`。

## 4.3 选项与配置

- `CPPFLAGS`、`CXXFLAGS`、`LDFLAGS`、`LDLIBS` 分开使用。
- 调试与发布使用不同的 `OBJDIR`。
- 默认打开 `-Wall -Wextra`，CI 再考虑 `-Werror`。
- 链接顺序：目标文件在前，库在后；库之间有依赖时注意顺序或用 `--start-group`。
- 第三方库优先用 `pkg-config`，不要手抄 flags。

## 4.4 验证

```bash
make clean && make -j8 -O     # 从零构建
make MODE=release -j8         # 发布配置
make -n                       # 检查命令是否符合预期
```

CI 至少覆盖：

| 检查 | 目的 |
|------|------|
| 干净环境全量构建 | 确认没有依赖本地产物 |
| debug 与 release 各一次 | 确认两种配置都能编译 |
| 并行构建 | 暴露漏写的依赖 |
| 警告检查 | 防止警告累积 |

# 5. 常见反模式

| 反模式 | 后果 | 替代做法 |
|--------|------|----------|
| 每个文件一条显式规则 | 新增文件必漏 | 模式规则 + `wildcard` |
| `clean` 放在文件第一行 | 直接 `make` 就删产物 | 把 `all`/最终目标放最前 |
| 命令行用空格缩进 | `missing separator` | 统一 Tab |
| 目录写成普通依赖 | 每次全量重编 | 顺序依赖 `\|` |
| 不写 `.PHONY` | 同名文件导致目标不执行 | 动作目标全部声明 |
| 递归里写 `make` | 丢 jobserver，`-n` 失效 | `$(MAKE)` |
| 把 `$(shell find ...)` 当万能 | 读取阶段执行、结果可能过期 | 优先 `wildcard`，必要时明确范围 |
| 命令里 `cd` 后接着写下一行 | `cd` 不生效 | `&&` 或 `.ONESHELL` |
| 编译选项变化不清缓存 | 产物与配置不一致 | 分目录或 `make clean` |
| 硬编码编译器绝对路径 | 换机器失败 | `?=` + 工具变量 |

# 6. 系列回顾

| 篇目 | 核心问题 | 一句话答案 |
|------|----------|------------|
| 1 | Make 怎么判断要不要编译 | 比较目标与依赖的时间戳 |
| 2 | 变量值为什么不对 | 区分 `=` 与 `:=` 的展开时机 |
| 3 | 如何避免重复规则 | 用 `%` 模式规则共享词干 |
| 4 | 改头文件为什么不重编 | `-MMD -MP` 生成并引入 `.d` |
| 5 | 并行为什么随机失败 | 依赖图不完整，`-j` 放大问题 |
| 6 | 项目怎么组织 | 源码/产物分离 + 配置分目录 |
| 7 | 出错怎么定位 | `-n`、`--trace`、`-p`、最小复现 |
| 8 | 什么时候不该用 Make | 复杂度上升时考虑 CMake |

```text
Make 的知识结构：

   规则语法 ──→ 依赖图 ──→ 增量构建
      │           │           │
      ▼           ▼           ▼
   变量函数    模式规则    并行/顺序依赖
      │           │           │
      └───────────┴───────────┘
                  ▼
            项目模板与排错
```

# 7. 小结

| 主题 | 要点 |
|------|------|
| Make 与 CMake | 执行器 vs 生成器，按项目复杂度选择 |
| 可维护性 | 变量集中、规则抽象、目录规范 |
| 可移植性 | 工具变量、shell 差异、路径无空格 |
| 依赖 | 自动生成，不手工维护 |
| 并行 | 依赖写全，顺序依赖只用于"存在性" |
| 清理 | 产物集中，`clean` 只删一个目录 |
| 排错 | 先观察再修改，最小复现 |

Make 的价值在于它足够小、足够直接：一份文本文件就能描述整个构建过程，没有黑盒。把依赖关系写对，把变量展开时机搞清，把产物和源码分开，绝大多数构建问题都会在源头消失。下一步如果想处理跨平台、多目标和依赖发现，可以进入 CMake 专题，把这一套底层模型当作理解生成结果的坐标系。
