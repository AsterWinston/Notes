上一篇的规则是"一个目标一条规则"，十个源文件就要写十条几乎一样的规则。模式规则把"文件名"抽象成"形状"，让一条规则覆盖一整类文件。本篇讲清 `%` 的匹配方式、模式规则的优先级、静态模式规则与多目标规则，以及为什么后缀规则应当退出历史舞台。

# 1. 为什么需要模式规则

## 1.1 重复的显式规则

```makefile
main.o: main.cpp
	$(CXX) $(CXXFLAGS) -c $< -o $@

util.o: util.cpp
	$(CXX) $(CXXFLAGS) -c $< -o $@

order.o: order.cpp
	$(CXX) $(CXXFLAGS) -c $< -o $@
```

三条规则除了文件名不同，结构完全一致。每加一个源文件就要复制一遍，漏改一处就出错。

## 1.2 模式规则的基本形式

```makefile
%.o: %.cpp
	$(CXX) $(CXXFLAGS) -c $< -o $@
```

`%` 是**通配符**，可以匹配任意非空字符串。这条规则的含义是：**任何以 `.o` 结尾的目标，都可以由同名 `.cpp` 生成**。

```makefile
CXX      := g++
CXXFLAGS := -std=c++17 -Wall
OBJS     := main.o util.o order.o

app: $(OBJS)
	$(CXX) $^ -o $@

%.o: %.cpp
	$(CXX) $(CXXFLAGS) -c $< -o $@
```

现在无论 `OBJS` 里有多少个文件，都只需要这一条模式规则。

★ **关键认知**：模式规则不是"批量生成规则"的语法糖，而是 Make 的**隐式规则搜索机制**。Make 在处理目标 `util.o` 时发现没有显式规则，才会去模式规则库里找匹配项。这解释了为什么显式规则永远优先于模式规则。

# 2. 模式规则的匹配机制

## 2.1 词干（stem）

匹配 `%.o` 时，`%` 实际吃到的部分叫**词干**，保存在自动变量 `$*` 中。

```makefile
%.o: %.cpp
	@echo "目标=$@ 依赖=$< 词干=$*"
```

执行 `make util.o` 输出：

```text
目标=util.o 依赖=util.cpp 词干=util
```

依赖中的 `%` 会被替换成同一个词干，这是模式规则的核心约束：**目标和依赖共用同一个词干**。

## 2.2 目录前缀的两种写法

这是模式规则最容易搞混的地方。假设目标在 `build/` 目录下，`build/util.o`：

```makefile
# 写法一：模式中不带目录
%.o: %.cpp
	$(CXX) -c $< -o $@
```

此时 `%` 匹配到的是 `build/util`（包含目录），依赖变成 `build/util.cpp`。也就是说，Make 期望源文件也在 `build/` 下。

```makefile
# 写法二：模式中带目录
build/%.o: %.cpp
	$(CXX) -c $< -o $@
```

此时 `%` 只匹配 `util`，依赖是 `util.cpp`，而目标是 `build/util.o`。这是"源码在根目录、产物在 build 目录"时常用的写法。

| 目标 | 模式 | 词干 `$*` | 依赖 |
|------|------|-----------|------|
| `build/util.o` | `%.o` | `build/util` | `build/util.cpp` |
| `build/util.o` | `build/%.o` | `util` | `util.cpp` |

⚠ **关键认知**：模式里的 `/` 是**字面匹配**，不是目录通配。`build/%.o` 只匹配 `build/` 开头的目标，且 `%` 不会跨过这个前缀。想让产物进 `build/`，要么在模式里写死目录，要么用第 6 篇的 `VPATH` 或显式路径拼接。

## 2.3 匹配顺序与优先级

当多条模式规则都能匹配同一个目标时，Make 的选择规则大致是：

1. **显式规则优先**于任何模式规则。
2. 模式规则之间，**词干更短（更具体）的优先**。
3. 词干长度相同时，按 Makefile 中出现的先后顺序。
4. 匹配任意目标的 `%`（无前缀）优先级最低。

可以给 `foo_main.o` 同时写 `foo_%.o: foo_%.cpp` 和 `%.o: %.cpp` 两条规则，命令里用不同的 `echo`，`make -n foo_main.o` 会优先选中词干更短的那条。

## 2.4 内置规则会来抢活

GNU Make 自带一批内置模式规则，例如 `%.o: %.c`、`%.o: %.cc`、`%.o: %.cpp`。如果你没有写规则却也能编译，多半是命中了内置规则。

```bash
make -p -f /dev/null | grep -A2 '^%.o'
```

想完全关掉内置规则，用 `-r`（关规则）和 `-R`（关变量）：

```bash
make -r
```

⚠ **关键认知**：内置规则省事，但也可能选中你并不想要的编译器或选项。工程里通常显式写出自己的模式规则，避免依赖内置行为，这样换机器、换 Make 版本时结果才稳定。

# 3. 自动变量详解

## 3.1 六个核心变量

| 变量 | 含义 | 在 `%.o: %.cpp` 中 |
|------|------|--------------------|
| `$@` | 目标文件名 | `util.o` |
| `$<` | 第一个依赖 | `util.cpp` |
| `$^` | 所有依赖，去重 | `util.cpp` |
| `$+` | 所有依赖，保留重复 | `util.cpp` |
| `$?` | 比目标新的依赖 | 视时间戳而定 |
| `$*` | 词干 | `util` |

## 3.2 为什么链接要用 `$^`

```makefile
app: main.o util.o order.o
	$(CXX) $^ -o $@
```

`$^` 自动展开成 `main.o util.o order.o`，目标名由 `$@` 提供。增删依赖时命令不用改。

## 3.3 `$+` 与重复依赖

静态库链接时，顺序和重复都可能有意义：

```makefile
app: main.o libfoo.a libfoo.a
	$(CXX) $+ -o $@      # 保留两个 libfoo.a
```

`$^` 会去重成一个，可能改变链接结果；`$+` 保留原始列表。

## 3.4 目录与文件名变体

GNU Make 支持在自动变量后加 `D`（目录）或 `F`（文件名）：

```makefile
build/util.o:
	@echo $(@D)   # build
	@echo $(@F)   # util.o
	@echo $(<D)   # 依赖所在目录
	@echo $(<F)   # 依赖的文件名
```

这些变体在做"目标进 build、源码在 src"的项目里非常实用。

# 4. 静态模式规则

## 4.1 语法与动机

静态模式规则（static pattern rule）把"目标列表"和"模式"分开写：

```makefile
OBJS := main.o util.o order.o

$(OBJS): %.o: %.cpp
	$(CXX) $(CXXFLAGS) -c $< -o $@
```

结构是 `目标列表: 目标模式: 依赖模式`。它只对**列出的目标**生效，不会像普通模式规则那样隐式匹配任何文件。

## 4.2 与普通模式规则的取舍

| 维度 | 普通模式规则 | 静态模式规则 |
|------|--------------|--------------|
| 作用范围 | 全局，任何匹配的目标 | 仅列出的目标 |
| 依赖是否必须存在 | 不存在时会继续找别的规则 | 不匹配直接报错 |
| 可读性 | 简洁，但作用域隐晦 | 目标清单明确 |
| 典型场景 | 统一的编译规则 | 只对一组文件套用特定规则 |

★ **关键认知**：静态模式规则的最大价值是**报错更早**。如果 `$(OBJS)` 里有一个文件没有对应的 `.cpp`，静态模式规则会直接告诉你"没有匹配的依赖"，而普通模式规则可能悄悄回退到别的规则，产生难以理解的链接错误。

## 4.3 每个目标独立求值

```makefile
$(OBJS): %.o: %.cpp
	@echo "构建 $@，词干 $*，源文件 $<"
```

对每个目标，`%` 分别匹配出各自的词干，`$@`、`$<`、`$*` 也随之不同。这和普通模式规则一致。

# 5. 多目标规则

## 5.1 独立多目标

```makefile
clean debug release: prep
	@echo "running for $@"
```

这种写法等价于三条独立规则，命令会**分别为每个目标执行一次**，`$@` 是当前目标。

```text
$ make clean debug
running for clean
running for debug
```

## 5.2 分组目标 `&:`

GNU Make 4.3 引入分组目标：一条命令同时生成多个目标，只执行一次。

```makefile
parser.tab.c parser.tab.h &: parser.y
	bison -d parser.y
```

`&:` 告诉 Make：这条命令**同时产出** `parser.tab.c` 和 `parser.tab.h`，两者要么都更新，要么都不更新。

⚠ **关键认知**：用普通的 `:` 写多目标生成文件，会让 Make 误以为每个目标能独立生成。并行构建时同一条 `bison` 可能被执行多次，产生竞争。这类"一次生成多个文件"的场景必须用 `&:`（GNU Make 4.3+），或者用一条规则只声明主目标、其余文件用依赖兜底。

## 5.3 历史行为：模式规则的多目标

```makefile
%.tab.c %.tab.h: %.y
	bison -d $<
```

在**模式规则**中，多目标天生带有"分组"语义：Make 认为一条命令会生成全部目标。这与显式规则的多目标行为不同，是历史遗留的不一致。

# 6. 后缀规则

## 6.1 历史形式

后缀规则是模式规则出现之前的写法：

```makefile
.SUFFIXES: .cpp .o

.cpp.o:
	$(CXX) $(CXXFLAGS) -c $< -o $@
```

`.cpp.o` 表示"从 `.cpp` 生成 `.o`"，依赖的后缀列表由 `.SUFFIXES` 维护。

## 6.2 为什么不再推荐

| 问题 | 说明 |
|------|------|
| 表达力弱 | 只能处理后缀，不能表达目录结构 |
| 依赖全局状态 | 依赖 `.SUFFIXES`，顺序和内容容易出错 |
| 已被取代 | 模式规则语义更清晰、能力更强 |
| 可读性差 | 新读者往往不知道 `.cpp.o` 是什么 |

★ **关键认知**：后缀规则**只应该出现在维护老项目时**。新写的 Makefile 一律用模式规则；如果老项目里两种规则并存，模式规则的优先级更高，调试时要注意这一点。

# 7. 常见错误

| 现象 | 原因 | 修复 |
|------|------|------|
| `No rule to make target 'build/util.o'` | 模式写成 `%.o`，依赖被解析成 `build/util.cpp` | 改成 `build/%.o: %.cpp` |
| 模式规则不生效 | 存在同名显式规则 | 检查是否有显式规则抢先 |
| 并行时同一文件被生成两次 | 多目标用了 `:` | 改用 `&:` 或拆分规则 |
| 链接顺序错误 | 用了 `$^` 去重 | 改用 `$+` |
| 意外用了内置规则 | 没有显式模式规则 | 显式写出规则，必要时 `-r` |
| 静态模式规则报错 | 目标列表里有文件没有对应源文件 | 检查 `OBJS` 拼写 |

# 8. 动手练习

1. 用一条模式规则改写第 1 篇的四条显式规则，要求新增 `order.cpp` 时只改 `OBJS` 变量。用 `make -n` 验证生成的命令。
2. 把产物放到 `build/` 目录，分别用 `%.o: %.cpp` 和 `build/%.o: %.cpp` 两种写法尝试，记录报错差异，并解释词干的变化。
3. 写一个静态模式规则，只对 `main.o util.o` 启用 `-DDEBUG`，其他文件不加；用 `make -n` 确认两条路径的命令不同。

# 9. 小结

| 概念 | 要点 |
|------|------|
| 模式规则 | `%.o: %.cpp`，目标和依赖共享词干 |
| 词干 `$*` | `%` 实际匹配到的部分 |
| 目录前缀 | `build/%.o` 中 `%` 不含 `build/` |
| 优先级 | 显式 > 更短词干 > 定义顺序 |
| 静态模式 | 目标列表 + 模式，作用域明确、报错早 |
| 多目标 | 显式多目标逐个执行，`&:` 分组只执行一次 |
| 后缀规则 | 历史写法，新项目不再使用 |
