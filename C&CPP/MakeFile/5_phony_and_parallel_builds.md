`.PHONY` 看起来只是一个声明，`-j` 看起来只是一个开关，但它们分别对应两个真实问题：目标名撞上同名文件，以及依赖图不完整时并行构建暴露的竞争。本篇把伪目标、并行、顺序依赖、错误处理和 shell 行为一次讲清。

# 1. 伪目标

## 1.1 `clean` 撞上同名文件

```makefile
clean:
	rm -f app *.o
```

如果目录里恰好有一个叫 `clean` 的文件（可能来自某个脚本或误创建），执行 `make clean` 会得到：

```text
make: 'clean' is up to date.
```

因为 `clean` 没有依赖，Make 比较不了时间戳，就认为目标已存在且不需要更新。

## 1.2 `.PHONY` 的两个作用

```makefile
.PHONY: clean

clean:
	rm -f app *.o
```

`.PHONY` 声明 `clean` 是**伪目标**，带来两个效果：

1. 目标永远被视为"过期"，命令每次都执行，不再检查同名文件。
2. Make 跳过对该目标的隐式规则搜索，不会因为存在 `clean.c` 就试图编译它。

★ **关键认知**：所有"动作型"目标都应该声明为 `.PHONY`，包括 `clean`、`all`、`test`、`install`、`run`、`format`。判断标准很简单：**这个目标的名字是否真的会生成同名文件**。不会，就加 `.PHONY`。

## 1.3 `all` 与默认入口

```makefile
.PHONY: all clean test

all: app

app: $(OBJS)
	$(CXX) $^ -o $@

test: app
	./app --test

clean:
	rm -f $(OBJS) $(DEPS) app
```

`all` 通常作为默认目标，把"要构建的东西"聚合在一起，例如 `all: app tools/docs`。

⚠ **关键认知**：`all` 本身不需要命令，它只负责汇总依赖。如果写成 `all:` 却没有任何依赖，它就什么也不做，容易让人误以为构建成功了。检查 `all` 的依赖列表是否完整。

# 2. 并行构建

## 2.1 `-j` 做什么

```bash
make -j4     # 最多同时运行 4 个命令
make -j      # 不限制并发数（谨慎使用）
make -j8 -O  # 并行，并让每个任务的输出成组显示
```

Make 在依赖图允许的范围内同时启动多个命令。对于多个互不依赖的 `.cpp`，编译阶段可以接近线性加速。

| 命令 | 行为 |
|------|------|
| `make` | 串行，一次一个命令 |
| `make -j4` | 最多 4 个并发任务 |
| `make -j` | 不限制，按依赖图尽量并发 |
| `make -O` | 输出同步，避免多任务输出交错 |
| `make -l 2.0` | 负载超过阈值时不再启动新任务 |

## 2.2 依赖图决定并行度

```text
        main.cpp   util.cpp   order.cpp
            │         │          │
            ▼         ▼          ▼
         main.o    util.o     order.o
            │         │          │
            └────┬────┴────┬─────┘
                 ▼         ▼
                app       tests
```

三个 `.o` 之间没有依赖，可以并行；`app` 必须等三个 `.o` 都完成；`app` 和 `tests` 如果互不依赖，也可以并行。

★ **关键认知**：`-j` 不会让 Make 变得更聪明，它只是**把依赖图里本就可以并行的部分真正并行**。如果依赖漏写，串行时可能靠执行顺序"碰巧正确"，一加 `-j` 就暴露成随机失败。并行构建是一面照妖镜，照出的是依赖图的缺陷。

## 2.3 输出交错与 `-O`

并行时多个编译器的输出可能混在一起：

```text
g++ -c main.cpp -o main.og++ -c util.cpp -o util.o
```

GNU Make 4.0 起支持 `-O`（`--output-sync`）：

```bash
make -j8 -O          # 每个任务的输出整体输出
make -j8 -Otarget    # 按目标分组
```

`-O` 不会改变执行顺序，只是让日志可读。CI 环境里建议默认加上。

# 3. 顺序依赖

## 3.1 `|` 语法

有时候某个依赖只需要"先做"，但它的时间戳不应该触发目标重建。这时用**顺序依赖**（order-only prerequisite）：

```makefile
目标: 普通依赖 | 顺序依赖
```

```makefile
$(BUILD)/%.o: %.cpp | $(BUILD)
	$(CXX) $(CXXFLAGS) -c $< -o $@

$(BUILD):
	mkdir -p $@
```

## 3.2 目录必须先存在

如果不用顺序依赖，写成普通依赖：

```makefile
$(BUILD)/%.o: %.cpp $(BUILD)
```

那么每次 `build/` 目录的修改时间变化（比如新增了一个文件），都会让所有 `.o` 被判定为过期，触发全量重编。目录的时间戳几乎总在变，这正是顺序依赖要解决的问题。

| 依赖类型 | 是否要求先完成 | 时间戳变化是否触发重建 |
|----------|----------------|------------------------|
| 普通依赖 | 是 | 是 |
| 顺序依赖 `\|` | 是 | 否 |

★ **关键认知**：顺序依赖的语义是"**存在性依赖**"——我只需要你在，不需要你新。典型用途就是创建目录、生成配置骨架、准备输出路径，而不是真正的输入文件。

## 3.3 与 `.PHONY` 的配合

如果把目录准备写成一个 `dirs` 伪目标并让 `app: dirs`，虽然也能保证目录存在，但 `dirs` 永远"过期"，会导致 `app` 每次都被重建。正确做法还是用顺序依赖指向真实的目录目标。

# 4. 错误处理

## 4.1 默认失败即停

命令行返回非零状态码时，Make 默认停止当前目标并退出：

```makefile
app: main.o
	$(CXX) $^ -o $@
	./app --self-test
```

如果自检失败，链接后的目标不会继续处理后续规则，Make 以非零码退出。

## 4.2 `-k`、`-i` 与命令前缀

| 方式 | 作用 | 适用场景 |
|------|------|----------|
| `make -k` | 尽量继续，构建其他不依赖失败目标的部分 | 一次看到尽可能多的错误 |
| `make -i` | 忽略所有命令错误 | 几乎不推荐 |
| 命令前加 `-` | 忽略该行错误 | 明知可能失败且可接受 |
| 命令前加 `@` | 不回显命令本身 | 减少日志噪音 |
| 命令前加 `+` | 即使 `-n` 也执行 | 递归 make 调用 |

## 4.3 `.DELETE_ON_ERROR`

```makefile
.DELETE_ON_ERROR:
```

如果某条命令在生成目标的过程中失败，Make 会删除已经部分写出的目标文件。否则一个损坏的 `.o` 可能因为时间戳较新，在下次构建时被当成"已完成"，导致更隐蔽的错误。

⚠ **关键认知**：编译中断、磁盘写满、`Ctrl+C` 都可能留下半成品。`.DELETE_ON_ERROR` 是低成本高收益的保护，建议所有生成文件的规则都启用它。

# 5. 命令与 shell

## 5.1 每一行是一个独立 shell

```makefile
demo:
	cd build
	pwd          # 仍然在原来的目录！
```

Make 会为每一行命令启动一个独立的 shell，`cd` 的效果不会保留到下一行。正确写法：

```makefile
demo:
	cd build && pwd
```

或者用 `.ONESHELL` 把整条规则交给一个 shell：

```makefile
.ONESHELL:
demo:
	cd build
	pwd
```

## 5.2 `.ONESHELL` 的注意点

`.ONESHELL` 下所有命令行拼接后交给一个 shell 执行，`cd`、变量、`set -e` 才会跨行生效。但这也意味着错误检查行为发生变化：默认只看最后一条命令的退出码。需要"任一行失败就停"时：

```makefile
.ONESHELL:
.SHELLFLAGS := -ec
```

`-e` 让 shell 在任一命令失败时退出，`-c` 是执行命令字符串所必需的。

## 5.3 `$` 的转义

Make 会先展开 `$`，再把结果交给 shell。想写 shell 变量必须用 `$$`：

```makefile
demo:
	@for f in *.cpp; do \
	    echo "处理 $$f"; \
	done
```

```makefile
# 错误示范：$(f) 会被 Make 当成变量 f，展开为空
demo:
	@for f in *.cpp; do echo $(f); done
```

同理，shell 的位置参数 `$@`、`$?` 在 Makefile 里要写成 `$$@`、`$$?`，否则会被 Make 的自动变量截获。

# 6. 递归 make

## 6.1 用 `$(MAKE)` 而不是 `make`

```makefile
sub:
	$(MAKE) -C lib
```

`$(MAKE)` 会展开成当前 make 的路径，并把 `-j`、`-n`、`-k` 等参数通过 jobserver 传给子 make。直接写 `make` 会丢失这些信息，并行构建时可能退化成串行，或者 `-n` 下意外真正执行。

★ **关键认知**：递归调用必须用 `$(MAKE)`，并且该命令行要带 `+` 前缀（通常 `$(MAKE)` 会自动处理）。这不是风格问题，而是 jobserver 协作的硬性要求。

## 6.2 `-C` 切换目录

```bash
make -C lib          # 等价于在 lib 目录执行 make
make -C lib clean
```

比 `cd lib && make` 更好，因为 `-C` 会被 make 自己处理，目录切换和错误信息都更清晰。

## 6.3 递归的代价

递归 make 会让每个子目录独立解析 Makefile，依赖关系无法跨目录精确表达，容易出现"父目录不知道子目录产物是否最新"的问题。小项目可以接受；大项目通常改用非递归的单体 Makefile，或直接上 CMake/Ninja。

# 7. 常见错误

| 现象 | 原因 | 修复 |
|------|------|------|
| `make clean` 提示 up to date | 存在同名文件且没加 `.PHONY` | 加 `.PHONY: clean` |
| `-j` 下随机失败 | 依赖漏写，任务顺序不确定 | 补全依赖，或临时 `-j1` 定位 |
| 每次全量重编 | 把目录写成普通依赖 | 改成顺序依赖 `\|` |
| `cd` 不生效 | 每行独立 shell | 用 `&&` 或 `.ONESHELL` |
| `-n` 下子 make 仍执行 | 用了 `make` 而非 `$(MAKE)` | 改用 `$(MAKE)` |
| 失败后残留坏目标 | 没有 `.DELETE_ON_ERROR` | 启用该特殊目标 |
| shell 变量为空 | 只写了一个 `$` | 改成 `$$` |

# 8. 动手练习

1. 创建三个互不依赖的源文件，用 `make -j3 -O` 构建，记录耗时；再故意删掉一条依赖，观察 `-j` 下是否出现竞争或错误。
2. 给 `build/` 目录写顺序依赖，验证新增文件到 `build/` 不会触发 `.o` 重编；再把 `|` 去掉，观察行为差异。
3. 写一个包含 `cd`、循环和 shell 变量的规则，先不用 `.ONESHELL` 看错误，再用 `.ONESHELL` 和 `-ec` 修正，解释每一步的原因。

# 9. 小结

| 主题 | 要点 |
|------|------|
| `.PHONY` | 动作型目标必加，避免同名文件干扰 |
| `-j` | 按依赖图并行，暴露漏写的依赖 |
| `-O` | 并行时同步输出，日志可读 |
| 顺序依赖 `\|` | 只保证先完成，不参与时间戳比较 |
| 错误处理 | 默认失败即停，`-k` 继续，`-` 忽略单行 |
| `.DELETE_ON_ERROR` | 失败时删除半成品目标 |
| shell | 每行独立，`$$` 转义，`.ONESHELL` 合并 |
| 递归 | 用 `$(MAKE)` 和 `-C` |
