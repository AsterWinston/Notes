编译一个 `.cpp` 文件时手敲命令还能忍受，文件一多，谁先编译、谁依赖谁、改了一个头文件到底要重编哪些，很快就不受控制。Make 用一套声明式的规则把这些关系写下来，本篇从最小可用的例子讲清目标、依赖、命令三要素，以及 make 判断"要不要重建"的核心模型。

# 1. Make 是什么

## 1.1 从手敲编译命令说起

一个只有三个源文件的小项目，编译命令大概是这样：

```bash
g++ -std=c++17 -Wall -c main.cpp -o main.o
g++ -std=c++17 -Wall -c user.cpp -o user.o
g++ -std=c++17 -Wall -c order.cpp -o order.o
g++ main.o user.o order.o -o app
```

第一次能跑通，但接下来每次改动都会遇到同一组问题：

| 问题 | 具体表现 |
|------|----------|
| 命令太长 | 每次都要重复敲一长串编译选项 |
| 容易漏编 | 改了 `user.cpp` 却忘记重新链接 |
| 顺序靠人记 | 先编译再链接，顺序错了就报错 |
| 无法并行 | 三个 `.cpp` 明明可以同时编译 |
| 难以复用 | 换一台机器、换一个目录就要重写 |

Make 要解决的就是这类"重复且需要判断"的构建工作。

## 1.2 Make 的定位与边界

Make 是一个**构建自动化工具**：它读取名为 `Makefile` 的文本文件，根据其中声明的依赖关系，决定哪些命令需要执行、按什么顺序执行。

它负责的事情很明确：

1. 解析 Makefile 里的规则、变量和函数。
2. 比较目标文件与依赖文件的时间戳。
3. 只执行"过期"的那部分命令。
4. 把互相独立的步骤并行起来（配合 `-j`）。

它**不负责**的事情同样要清楚：Make 不会替你选择编译器，不管理第三方包，也不生成跨平台的工程文件。这些分别属于编译器、包管理器和 CMake 的职责。

★ **关键认知**：Make 本身**不编译任何代码**，它只是一个"依赖驱动的任务调度器"。真正干活的，是规则里写的那条 shell 命令。理解这一点，就不会把构建失败归咎于"Make 有问题"——绝大多数时候是命令写错了，或者依赖关系描述错了。

## 1.3 一个最小 Makefile

在源文件同级目录新建一个名为 `Makefile` 的文件，内容如下：

```makefile
# 目标: 依赖
# 下一行必须以 Tab 开头
app: main.o
	g++ main.o -o app

main.o: main.cpp
	g++ -std=c++17 -Wall -c main.cpp -o main.o
```

执行：

```bash
make
```

输出类似：

```text
g++ -std=c++17 -Wall -c main.cpp -o main.o
g++ main.o -o app
```

这里有两个规则：

| 目标 | 依赖 | 命令 | 含义 |
|------|------|------|------|
| `app` | `main.o` | `g++ main.o -o app` | 链接出可执行文件 |
| `main.o` | `main.cpp` | `g++ ... -c ...` | 编译出目标文件 |

★ **关键认知**：Makefile 是**声明式**的，你写的是"`app` 依赖 `main.o`"这个事实，而不是"先编译再链接"这个步骤。执行顺序由依赖图推导出来，不需要你手工安排。这正是它比一串 shell 脚本更强的地方。

# 2. 规则的三要素

## 2.1 目标、依赖、命令

一条规则的基本形状是：

```makefile
目标: 依赖1 依赖2 ...
	命令1
	命令2
```

三个部分的职责：

| 要素 | 作用 | 例子 |
|------|------|------|
| 目标（target） | 要生成的文件，或要执行的动作名 | `app`、`main.o`、`clean` |
| 依赖（prerequisites） | 目标由哪些文件产生，或必须先完成什么 | `main.cpp`、`main.o` |
| 命令（recipe） | 真正执行的 shell 命令 | `g++ -c main.cpp` |

含义可以读成一句话：**"当依赖比目标新时，执行命令重新生成目标。"**

## 2.2 制表符与命令前缀

命令行的开头必须是**一个 Tab 字符**，不能是空格。这是新手遇到的第一个、也是最常见的错误：

```makefile
# 错误示范：下面这行用四个空格缩进
app: main.o
    g++ main.o -o app
```

上面这段用的是四个空格，执行时会得到：

```text
Makefile:2: *** missing separator.  Stop.
```

⚠ **关键认知**：`missing separator` 有九成是"命令行用了空格而不是 Tab"。不要依赖编辑器自动缩进，把 Makefile 的缩进策略显式设置为"保留 Tab"。在 Vim 中可以执行 `:set noexpandtab`，在 VS Code 中把该文件的缩进改为 Tab。

判断一个位置到底是 Tab 还是空格，可以用：

```bash
# 把 Tab 显示为 ^I，行尾显示为 $
cat -A Makefile
```

## 2.3 规则的几种书写形式

一条规则可以有多个目标和多个依赖：

```makefile
# 多个依赖：main.o 由两个源文件共同决定（少见，但语法合法）
main.o: main.cpp config.h
	g++ -std=c++17 -c main.cpp -o main.o

# 依赖太多时用反斜杠换行
app: main.o \
     user.o \
     order.o
	g++ main.o user.o order.o -o app
```

注意反斜杠后面**不能有空格**，否则会把空格当成依赖名的一部分。

# 3. Make 如何决定要不要重建

## 3.1 时间戳比较模型

Make 的核心判断只有一条：**比较目标与依赖的最后修改时间**。

```text
            依赖比目标新？
                 │
        ┌────────┴────────┐
       是 │                 │ 否
        ▼                 ▼
   执行命令重建        跳过，提示 up to date
```

完整规则分三种情况：

| 情况 | Make 的行为 |
|------|-------------|
| 目标文件不存在 | 一定执行命令 |
| 目标存在，但任一依赖比它新 | 执行命令 |
| 目标存在，且比所有依赖都新 | 跳过，不执行 |

这套模型简单、快速，但也有一个隐含前提：**文件时间戳是可信的**。从压缩包解压、从 Git 切分支、跨时区同步文件，都可能让时间戳失真，从而出现"明明改了却没重编"或"什么都没改却全量重编"。

## 3.2 一个可观察的增量构建例子

假设当前目录有 `main.cpp` 和上面那个 Makefile：

```bash
make            # 第一次：编译 + 链接，两条命令都执行
make            # 第二次：输出 "make: 'app' is up to date."
touch main.cpp  # 只更新时间戳，内容不变
make            # 重新编译 main.o，再重新链接 app
```

★ **关键认知**：`touch main.cpp` 后**两条命令都重新执行**，因为 `main.o` 被重建后时间戳变新，`app` 又依赖于它，于是链接也被触发。这就是**依赖链的传播**：改动从叶子节点一路向上，直到根目标。

## 3.3 依赖链的传播

```text
   main.cpp          user.cpp          order.cpp
      │                 │                  │
      ▼                 ▼                  ▼
   main.o            user.o             order.o
      │                 │                  │
      └────────┬────────┴────────┬─────────┘
               ▼                 ▼
              app（最终目标）
```

依赖图是一张有向无环图（DAG），Make 从最终目标出发，递归地保证每个依赖都是最新的，再决定自己要不要执行。所以哪怕你只改了一个最底层的源文件，整条链路上过期的目标都会被重新生成，而不相关的分支完全不受影响。

# 4. 执行流程

## 4.1 默认目标

直接执行 `make` 而不指定目标时，Make 会选择**第一个规则的目标**作为默认目标。习惯上把 `all` 或最终产物放在文件最前面：

```makefile
all: app

app: main.o
	g++ main.o -o app
```

⚠ **关键认知**：如果第一个规则恰好是 `clean`，那么直接 `make` 就会删掉所有构建产物。不要把清理规则放在文件开头。

另外，以 `.` 开头的特殊目标和模式规则（含 `%` 的规则）不会成为默认目标。

## 4.2 一次 make 的完整步骤

```text
┌─────────────────────────────┐
│ 1. 读取 Makefile             │
│    展开 include、定义变量    │
└──────────────┬──────────────┘
               ▼
┌─────────────────────────────┐
│ 2. 确定目标（默认或命令行）  │
└──────────────┬──────────────┘
               ▼
┌─────────────────────────────┐
│ 3. 递归检查依赖，构建依赖图  │
└──────────────┬──────────────┘
               ▼
┌─────────────────────────────┐
│ 4. 自底向上比较时间戳        │
│    过期则执行命令            │
└──────────────┬──────────────┘
               ▼
┌─────────────────────────────┐
│ 5. 全部最新则输出 up to date │
└─────────────────────────────┘
```

需要区分两个阶段：

| 阶段 | 发生的事情 |
|------|-----------|
| 读取阶段 | 解析 Makefile、展开变量、执行 `$(shell ...)`、处理 `include` |
| 执行阶段 | 按依赖顺序运行命令行里的 shell 命令 |

变量展开到底发生在哪个阶段，是第 2 篇的重点，也是很多"变量值不对"问题的根源。

## 4.3 按需指定目标

在已有 `app` 规则的基础上增加一个 `clean` 目标，就能得到两个独立入口：

```makefile
clean:
	rm -f app main.o
```

```bash
make app      # 只构建 app
make clean    # 只执行清理
```

`make clean` 不会顺带构建 `app`，因为 `clean` 规则没有把 `app` 列为依赖。目标之间是独立的入口，除非你显式建立依赖。

# 5. 常见错误

| 现象 | 原因 | 修复 |
|------|------|------|
| `missing separator` | 命令行用空格缩进 | 改成 Tab |
| `No rule to make target 'xxx'` | 依赖文件不存在，也没有规则能生成它 | 检查文件名拼写，补规则 |
| `command not found` | 编译器不在 PATH 中 | 安装工具链或写绝对路径 |
| 每次都全量重编 | 依赖里写了总在变化的文件，或时间戳异常 | `make -n` 看触发原因 |
| 改了代码却没重编 | 头文件依赖没写进规则 | 见第 4 篇的依赖自动生成 |
| `make: 'app' is up to date.` 但文件是旧的 | 目标文件时间戳比源文件新 | 先 `make clean`，再排查时间戳 |

# 6. 动手练习

1. 在同一目录创建 `main.cpp`、`util.cpp`、`util.h`，写一个 Makefile 生成 `app`；执行两次 `make`，确认第二次不再编译，再用 `touch util.h` 观察哪些目标被重建。
2. 故意把某条命令前的 Tab 换成四个空格，记录完整的报错信息，再用 `cat -A Makefile` 定位问题行。
3. 给 Makefile 增加 `clean` 目标，验证 `make` 与 `make clean` 分别触发了哪些命令，并解释为什么把 `clean` 放在文件开头会带来风险。

# 7. 小结

| 概念 | 要点 |
|------|------|
| Make 的定位 | 依赖驱动的任务调度器，本身不编译 |
| 规则三要素 | 目标、依赖、命令 |
| 命令缩进 | 必须是一个 Tab |
| 重建条件 | 目标不存在，或任一依赖比目标新 |
| 默认目标 | 文件里第一个非特殊规则的目标 |
| 增量传播 | 叶子变化会沿依赖链向上触发重建 |
