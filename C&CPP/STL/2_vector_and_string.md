`vector` 是绝大多数 C++ 程序里出现频率最高的容器，`string` 则是它管理字符的特化版本。两者都用一块连续内存存放数据，都支持随机访问，也都有一类共同的坑——**扩容导致迭代器、指针、引用失效**。本篇把 `size`/`capacity` 的关系、`reserve` 与 `resize` 的区别、失效规则讲清楚，再延伸到 `string` 的短字符串优化和 `string_view` 的生命周期问题。

# 1. vector 的内存模型

## 1.1 size 与 capacity

`vector` 内部至少维护三个东西：指向首元素的指针、当前元素个数 `size`、已分配空间能容纳的元素个数 `capacity`。

```text
vector 对象
┌──────────┬──────────┬──────────────┐
│ data 指针 │  size=4  │ capacity=8   │
└────┬─────┴──────────┴──────────────┘
     ▼
┌───┬───┬───┬───┬───┬───┬───┬───┐
│ 0 │ 1 │ 2 │ 3 │   │   │   │   │
└───┴───┴───┴───┴───┴───┴───┴───┘
  ←── size = 4 ──→
  ←──────── capacity = 8 ────────→
```

- `size()`：真正构造出来的元素个数，可以安全访问。
- `capacity()`：不需要重新分配就能容纳的元素上限。
- `size() <= capacity()` 恒成立，访问 `[size(), capacity())` 是未定义行为。

```cpp
#include <iostream>
#include <vector>

int main() {
    std::vector<int> v;
    std::cout << v.size() << ' ' << v.capacity() << '\n'; // 0 0
    v.push_back(1);
    std::cout << v.size() << ' ' << v.capacity() << '\n'; // 1 1
    v.push_back(2);
    v.push_back(3);
    std::cout << v.size() << ' ' << v.capacity() << '\n'; // 3 4
    return 0;
}
```

★ **关键认知**：`size` 是"用了多少"，`capacity` 是"准备了多少"。`size()` 之内的元素才是有效对象，`capacity()` 只是内存额度。初学者常把两者混为一谈，于是写出"容量是 100 为什么不能访问 `v[99]`"这类错误。

# 2. 扩容机制

## 2.1 扩容时发生了什么

当 `push_back` 发现 `size == capacity` 时，会按以下步骤扩容：

```text
1. 申请一块更大的新内存（通常是原容量的 1.5 或 2 倍）
2. 把旧元素逐个移动（或拷贝）到新内存
3. 销毁旧元素，释放旧内存
4. 更新 data / size / capacity
```

```text
扩容前（capacity = 4，已满）：
┌───┬───┬───┬───┐
│ 1 │ 2 │ 3 │ 4 │
└───┴───┴───┴───┘

扩容后（capacity = 8）：
┌───┬───┬───┬───┬───┬───┬───┬───┐
│ 1 │ 2 │ 3 │ 4 │ 5 │   │   │   │
└───┴───┴───┴───┴───┴───┴───┴───┘
 旧内存已释放，所有旧指针/引用/迭代器全部作废
```

## 2.2 增长因子

标准没有规定增长倍数，只要求 `push_back` 的**均摊**复杂度是 O(1)。主流实现（libstdc++、MSVC）采用约 1.5 倍或 2 倍增长。

为什么是指数增长而不是每次加 1？因为每次扩容都要搬移全部元素：

| 策略 | 插入 n 个元素的总搬移次数 | 均摊每次 |
|------|---------------------------|----------|
| 每次 +1 | 1 + 2 + ... + n ≈ n²/2 | O(n) |
| 每次 ×2 | 1 + 2 + 4 + ... + n ≈ 2n | O(1) |

★ **关键认知**：指数增长是"用空间换时间"的经典取舍。它保证**均摊 O(1)**，但也意味着容量可能比实际需要大不少。理解这一点，你就明白为什么"先 `reserve` 再批量插入"能明显提速——它把多次扩容合并成了零次。

## 2.3 reserve 与 resize

这两个名字很像，行为完全不同：

| 操作 | 改变 size | 改变 capacity | 是否构造元素 |
|------|-----------|---------------|--------------|
| `reserve(n)` | 否（size 不变） | 至少到 n | 否 |
| `resize(n)` | 是（变成 n） | 可能需要扩大 | 是（补默认值） |

```cpp
std::vector<int> v;
v.reserve(100);           // capacity >= 100，size 仍为 0
// v[0] = 1;              // 错误！size 是 0，元素还没构造
v.push_back(1);           // 正确

v.resize(10);             // size 变成 10，多出的 9 个是 0
v.resize(3);              // size 缩到 3，后面 7 个被销毁
```

★ **关键认知**：`reserve` 只动容量，不动元素；`resize` 真正改变元素个数并构造/销毁对象。已知要插入多少元素时，先 `reserve` 是最容易拿到的性能优化之一，尤其在循环里 `push_back` 时效果显著。

⚠ **关键认知**：`reserve` 之后仍然不能用 `operator[]` 访问未构造的元素，即使那块内存已经分配好了。`size` 没变，访问就是未定义行为。需要"先占位再赋值"时应该用 `resize`，而不是 `reserve` 加下标。

# 3. 迭代器失效

## 3.1 哪些操作会失效

`vector` 的失效规则围绕"内存是否被重新分配"和"元素是否被搬移"展开：

| 操作 | 失效范围 |
|------|----------|
| `push_back` 触发扩容 | 全部迭代器、指针、引用 |
| `push_back` 未扩容 | 仅 `end()` |
| `insert` | 插入点及之后的所有迭代器 |
| `erase` | 删除点及之后的所有迭代器 |
| `reserve` 导致扩容 | 全部 |
| `clear` | 全部 |
| `shrink_to_fit` 导致缩容 | 全部 |

★ **关键认知**：任何**可能触发重新分配**的操作都会让所有迭代器、指针、引用失效，因为元素整体搬到了新地址。即使没有扩容，`insert`/`erase` 也会让操作点之后的迭代器失效，因为元素发生了位移。

## 3.2 循环中删除

`erase` 会返回"被删除元素之后那个位置"的新迭代器，循环删除必须用它更新：

```cpp
std::vector<int> v = {1, 2, 3, 4, 5, 6};

// 错误：erase 后 it 已失效，再 ++it 是未定义行为
for (auto it = v.begin(); it != v.end(); ++it)
    if (*it % 2 == 0) v.erase(it);

// 正确：用 erase 的返回值继续
for (auto it = v.begin(); it != v.end(); ) {
    if (*it % 2 == 0) {
        it = v.erase(it);   // 返回下一个有效位置
    } else {
        ++it;               // 没删才前进
    }
}
```

如果只是删除满足条件的元素，更推荐 erase-remove 惯用法，第 4 篇会专门讲：

```cpp
#include <algorithm>

v.erase(std::remove_if(v.begin(), v.end(),
                       [](int x) { return x % 2 == 0; }),
        v.end());
```

## 3.3 引用与指针

迭代器失效的规则同样适用于引用和指针，因为它们本质上也指向元素地址：

```cpp
std::vector<int> v = {1, 2, 3};
int& r = v[0];
v.push_back(4);      // 若发生扩容，r 指向已释放内存
r = 100;             // 未定义行为
```

⚠ **关键认知**：不要保存 `vector` 元素的引用或指针跨越可能扩容的操作。这是最隐蔽的一类 bug，因为程序往往"看起来正常"，直到某次插入恰好触发扩容才崩溃。函数返回 `vector` 元素的引用时尤其危险，调用方一扩容就悬垂。

# 4. string

## 4.1 常用接口

`std::string` 可以看作"专门存 `char` 的 `vector`"，接口更丰富：

```cpp
#include <string>

std::string s = "hello";
s += " world";                    // 追加，可能扩容
std::string sub = s.substr(0, 5); // 返回新字符串（拷贝）
std::size_t pos = s.find("world");// 找不到返回 npos
if (pos == std::string::npos) {
    // 没找到
}
```

## 4.2 短字符串优化（SSO）

`string` 通常会在对象内部留一小块缓冲区，短字符串直接存在栈上的对象里，不申请堆内存。这叫**短字符串优化（Small String Optimization，SSO）**。

```text
短字符串（SSO 生效）：
┌──────────────────────────────┐
│ 内部缓冲区："hello"           │  ← 数据就在对象里，无堆分配
└──────────────────────────────┘

长字符串（超过内部缓冲）：
┌──────────┬──────────┬────────┐
│ 堆指针   │  size    │capacity│──► 堆上的字符数组
└──────────┴──────────┴────────┘
```

不同实现的内部缓冲区大小不同（libstdc++ 通常 15 字符，MSVC 通常 15 或 22），但标准没有规定阈值。

★ **关键认知**：SSO 让短字符串的构造、拷贝、销毁几乎零成本，这也是"传 `std::string` 按值不一定比按引用慢多少"的原因之一。但**不能依赖具体阈值**，跨编译器、跨标准库时长度界限可能不同。

## 4.3 c_str 的生命周期

```cpp
std::string s = "hello";
const char* p = s.c_str();
s += " world";        // 可能扩容，p 可能失效
// std::cout << p;    // 未定义行为
```

⚠ **关键认知**：`c_str()` 返回的指针归 `string` 所有，字符串被修改（可能重新分配）或销毁后立即失效。不要把它存起来、不要返回给调用方、不要跨线程长期持有。需要在 C 接口边界的当下使用完毕。

# 5. string_view

## 5.1 用法

`std::string_view`（C++17）是一个"只读、不拥有"的字符视图，内部只有一个指针加一个长度：

```cpp
#include <string_view>

std::string s = "hello world";
std::string_view sv = s;             // 不拷贝，只记录地址和长度

void print(std::string_view text);   // 参数用视图，接受 string 和字面量
print(s);                            // 从 string 隐式构造
print("literal");                    // 从 const char* 构造
```

| 特性 | `std::string` | `std::string_view` |
|------|---------------|--------------------|
| 拥有数据 | 是 | 否 |
| 拷贝成本 | 可能申请内存 | 只拷贝指针和长度 |
| 能否修改 | 能 | 不能 |
| 是否保证以 `\0` 结尾 | 是 | 否 |
| 生命周期 | 自己管理 | 依赖被观察的数据 |

★ **关键认知**：`string_view` 的价值在于**只读传参**。函数参数写成 `std::string_view`，既能接收 `std::string`，也能接收字符串字面量，还不会为临时字符串付出分配代价。它适合"看一眼就走"的场景。

## 5.2 悬垂陷阱

```cpp
std::string_view bad() {
    std::string local = "temporary";
    return local;          // 错误：local 销毁，视图悬垂
}

std::string_view dangerous = std::string("temp"); // 临时对象立刻销毁
```

⚠ **关键认知**：`string_view` **不延长被观察对象的生命周期**。它最容易出错的地方就是"从临时 `string` 构造视图"——临时对象在语句结束时销毁，视图立刻悬垂。视图只能用于"底层数据确定活得比自己久"的场景。

另外，`string_view` 不保证 `\0` 结尾，所以不能直接传给需要 C 字符串的函数：

```cpp
std::string_view sv = "hello world";
sv = sv.substr(0, 5);         // "hello"，但末尾没有 '\0'
// std::printf("%s", sv.data()); // 危险：会一直读到 '\0' 为止
std::string tmp(sv);          // 需要 C 字符串时先转成 string
```

# 6. 常见坑

| 坑 | 后果 | 修复 |
|----|------|------|
| `reserve` 后用下标访问 | 未定义行为 | 用 `resize` 或 `push_back` |
| `push_back` 前保存元素引用 | 扩容后悬垂 | 用索引，或不跨扩容持有 |
| 循环 `erase` 后 `++it` | 跳过元素或崩溃 | 用 `erase` 的返回值 |
| 返回局部 `string` 的 `string_view` | 悬垂视图 | 返回 `std::string` |
| 保存 `c_str()` 长期使用 | 修改后失效 | 当场用完 |
| 把 `string_view` 传给 `printf("%s")` | 越界读 | 先构造 `std::string` |
| `vector<bool>` 取引用 | 编译失败 | 用 `deque<bool>` |

⚠ **关键认知**：`vector` 和 `string` 的失效规则本质相同——**底层内存一动，所有指向元素的句柄全部作废**。记住这一条，比逐条背表格更可靠。

3. 写一个函数接收 `std::string_view` 并统计元音个数，分别传入 `std::string`、字符串字面量和 `substr` 结果，观察哪些写法安全。

# 8. 小结

| 概念 | 要点 |
|------|------|
| `size` vs `capacity` | 已用元素数 vs 已分配容量 |
| 扩容 | 申请新内存、搬移元素、释放旧内存 |
| 均摊 O(1) | 靠指数增长摊薄搬移成本 |
| `reserve` | 只改容量，不构造元素 |
| `resize` | 改变元素个数，构造/销毁元素 |
| 迭代器失效 | 扩容全失效，插删影响操作点之后 |
| SSO | 短字符串存在对象内部，无堆分配 |
| `c_str` | 修改或销毁后失效 |
| `string_view` | 只读不拥有，警惕悬垂 |
