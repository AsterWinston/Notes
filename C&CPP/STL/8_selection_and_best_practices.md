学完前七篇，容器、算法、迭代器、lambda 各自的机制都清楚了，但真实项目里更常见的问题是"这个场景到底该用哪个"。选错容器不一定报错，却可能让程序慢十倍、内存翻倍，或者在并发下悄悄失效。本篇把选型、性能、内存、异常安全四条线收束成一组可以直接照着做的规范，并用反模式清单帮你避开常见陷阱。

# 1. 选型总表

## 1.1 按操作选

| 你最常做的操作 | 首选 | 理由 |
|----------------|------|------|
| 尾部追加、随机访问 | `vector` | 连续内存，缓存友好 |
| 两端插删 | `deque` | 两端 O(1)，仍可随机访问 |
| 已持有位置的频繁插删 | `list` | 节点独立，插入不搬移 |
| 按键有序遍历 | `map`/`set` | 红黑树天然有序 |
| 范围查询 | `map`/`set` | `lower_bound` 可用 |
| 单键高频查找 | `unordered_map`/`unordered_set` | 平均 O(1) |
| 只在一端进出 | `stack` | 语义清晰，接口受限 |
| 只在两端进出 | `queue` | 语义清晰 |
| 每次取最值 | `priority_queue` | 堆，常数小 |
| 长度编译期固定 | `array` | 无堆分配 |

## 1.2 按场景选

| 场景 | 选择 | 说明 |
|------|------|------|
| 通用业务数据 | `vector` | 默认答案，先用它 |
| 缓存、字典 | `unordered_map` | 查找多、顺序无关 |
| 配置项、排行榜 | `map` | 需要有序输出 |
| 去重 | `unordered_set` | 平均 O(1) |
| 事件队列 | `deque` 或 `queue` | FIFO，两端操作 |
| 撤销栈 | `stack` 或 `vector` | LIFO |
| Top-K | `priority_queue` | 维护大小为 K 的堆 |
| 只读字符串参数 | `string_view` | 不拷贝 |
| 可能没有的值 | `optional` | 显式表达 |

★ **关键认知**：选型的默认答案是 `vector`，只有当你能说清楚"为什么 `vector` 不够"时才换。很多性能问题不是容器选错，而是选了链表却仍在随机访问、选了哈希表却需要有序遍历。先写对，再用 profiler 证明瓶颈，最后才换容器。

# 2. 性能

## 2.1 缓存局部性

现代 CPU 从缓存读数据比从内存快一到两个数量级。容器是否连续，直接决定遍历速度。

```text
vector：元素连续
┌───┬───┬───┬───┬───┬───┐
│ 1 │ 2 │ 3 │ 4 │ 5 │ 6 │   一次缓存行加载多个元素
└───┴───┴───┴───┴───┴───┘

list：节点分散
┌───┐      ┌───┐      ┌───┐
│ 1 │ ───► │ 2 │ ───► │ 3 │   每次跳转都可能缓存未命中
└───┘      └───┘      └───┘
```

★ **关键认知**：即使 `list` 的插入是 O(1)、`vector` 是 O(n)，遍历时 `vector` 往往快得多，因为**缓存未命中的代价远大于一次内存搬移**。这就是"链表在大数据量下常打不过 `vector`"的根本原因。

## 2.2 分配次数

每次堆分配都有固定开销（系统调用、锁、元数据）。减少分配次数往往比换算法更有效：

```cpp
std::vector<int> v;
v.reserve(10000);          // 一次分配，避免多次扩容
for (int i = 0; i < 10000; ++i) {
    v.push_back(i);
}

std::unordered_map<int, int> m;
m.reserve(10000);          // 一次预留，避免多次 rehash
```

| 优化 | 效果 |
|------|------|
| `vector::reserve` | 消除扩容搬移 |
| `unordered_map::reserve` | 消除 rehash |
| `emplace_back` | 原地构造，少一次临时对象 |
| 批量插入用区间版本 | 一次规划，减少重复扩容 |

## 2.3 移动与 noexcept

```cpp
struct Widget {
    Widget(Widget&&) noexcept;              // 移动构造标 noexcept
    Widget& operator=(Widget&&) noexcept;   // 移动赋值同样
};
```

★ **关键认知**：移动构造/赋值必须标 `noexcept`。`vector` 扩容时要在"强异常安全"和"用移动"之间做选择：如果移动可能抛异常，标准库为保证回滚只能退回复制。结果就是"写了移动却感觉没变快"，性能悄悄差一个数量级。

## 2.4 reserve 与 emplace

```cpp
std::vector<std::string> v;
v.reserve(100);
v.emplace_back("hello");          // 直接在容器内存里构造
v.push_back(std::string("hi"));   // 先构造临时对象，再移动进去

std::map<int, std::string> m;
m.try_emplace(1, "one");          // 键存在时不构造值
```

⚠ **关键认知**：`emplace_back` 不一定比 `push_back` 快。它省掉的是临时对象的构造和移动；如果参数本身就是同类型对象，或者构造很便宜，差异可以忽略。更不要为了 `emplace` 牺牲可读性——需要显式类型转换时，`push_back` 反而更清楚。

# 3. 内存

## 3.1 内存布局对比

```text
vector：
┌─────────────────────────┐
│ data → [元素][元素][元素] │  一块连续内存
└─────────────────────────┘

list：
┌──────┬──────┬──────┐
│ prev │ data │ next │ → 每个节点单独分配，额外两个指针
└──────┴──────┴──────┘

map：
┌──────┬─────┬──────┬──────┬─────┐
│ 颜色 │ 键  │ 值   │ 左   │ 右  │  每节点额外存颜色和两个指针
└──────┴─────┴──────┴──────┴─────┘

unordered_map：
桶数组 + 每个节点带 next 指针，还有负载因子预留的空桶
```

| 容器 | 额外内存 | 说明 |
|------|----------|------|
| `vector` | 容量与大小的差 | 可能浪费一部分 |
| `list` | 每节点两个指针 | 小元素时开销占比很高 |
| `map`/`set` | 每节点颜色 + 两个指针 | 节点开销明显 |
| `unordered_*` | 桶数组 + 链表指针 | 空桶也占内存 |

★ **关键认知**：存 `int` 时，`list` 的一个节点可能占 24 字节，是数据本身的 6 倍；`map` 的节点更大。**元素越小，链表/树的相对内存开销越夸张**。这也是小数据量下 `vector` 几乎总是更优的原因之一。

## 3.2 小对象与 SSO

`std::string` 的短字符串优化让短文本不申请堆内存；`std::function` 和 `std::any` 也有类似的小对象内联优化。

```cpp
std::string a = "hi";                    // 很短，通常走 SSO，无堆分配
std::string b(1000, 'x');                // 长字符串，堆分配
```

⚠ **关键认知**：SSO 的阈值由实现决定，不能依赖。把字符串假设成"一定在栈上"或"一定在堆上"都会出错。跨编译器传递 `string` 时，更不要依赖其内部布局。

## 3.3 泄漏与悬垂

```cpp
// 悬垂引用：容器销毁后仍持有元素引用
const std::string& ref = getVector()[0];   // 临时 vector 已销毁

// 迭代器失效：扩容后继续用旧迭代器
auto it = v.begin();
v.push_back(1);
*it;                                        // 未定义行为
```

★ **关键认知**：STL 容器自己不会泄漏元素（析构会释放），但**保存指向元素的指针/引用/迭代器**会制造悬垂。容器负责元素的生命周期，不负责你从它身上借出去的句柄。借出去的东西，必须在容器变动前还回来。

# 4. 异常安全

## 4.1 三个等级

| 等级 | 保证 | 典型实现 |
|------|------|----------|
| 基本保证 | 不泄漏、不变式不破坏 | 大多数操作 |
| 强保证 | 失败时回滚到操作前状态 | 拷贝后交换、`vector::push_back` |
| 不抛保证 | 承诺不抛异常 | `noexcept`、移动构造 |

```cpp
// 强异常安全的经典写法：先构造副本，成功后再交换
void update(const std::vector<int>& data) {
    std::vector<int> tmp = data;   // 可能抛异常，此时原对象未动
    tmp.push_back(42);             // 仍可能抛，原对象仍未动
    data_.swap(tmp);               // swap 不抛，一次性生效
}
```

★ **关键认知**：强异常安全的核心是"**先做可能失败的事，再原子地提交**"。拷贝构造、交换、移动构造（标 `noexcept`）是构建强保证的三块积木。`vector::push_back` 之所以在扩容时倾向移动而非拷贝，正是为了保证强保证。

## 4.2 与容器相关的异常安全

| 操作 | 异常安全 |
|------|----------|
| `vector::push_back` | 强保证（移动不抛时） |
| `vector::insert` | 基本或强保证，视实现 |
| `map::insert` | 强保证 |
| `list::push_back` | 强保证 |
| `sort` | 基本保证（比较器抛异常时） |

⚠ **关键认知**：自定义类型的移动构造不标 `noexcept`，会让 `vector` 在扩容时退回复制，强异常安全仍在，但性能下降。这是"功能正确但慢"的典型来源，排查性能时要看移动操作是否标了 `noexcept`。

# 5. 最佳实践清单

1. **默认用 `vector`**，除非有明确理由换。
2. **已知规模先 `reserve`**，`vector` 和 `unordered_map` 都适用。
3. **遍历只读用 `const auto&`**，避免隐式拷贝。
4. **查询用 `find`/`contains`**，不要用 `operator[]` 探测。
5. **删除用 erase-remove**，或 C++20 的 `std::erase_if`。
6. **比较器用严格弱序**，永远写 `<`，不写 `<=`。
7. **移动构造标 `noexcept`**，否则容器退回复制。
8. **优先算法而非手写循环**，意图更清楚。
9. **lambda 异步场景按值捕获**，避免悬垂引用。
10. **`string_view` 只用于参数**，不存成员、不返回。
11. **自定义键补齐 `<` 或 `hash` + `==`**，缺一个就编译失败。
12. **不要保存元素句柄跨越容器修改**，扩容会全部作废。

# 6. 常见反模式

| 反模式 | 问题 | 正确做法 |
|--------|------|----------|
| 无脑用 `list` | 缓存不友好，内存开销大 | 先试 `vector` |
| 用 `map` 做纯查找 | 多付 O(log n) | `unordered_map` |
| 循环里 `push_back` 不 `reserve` | 多次扩容 | 先 `reserve` |
| `remove` 后不 `erase` | 元素没删 | erase-remove |
| 比较器写 `<=` | `sort` 崩溃 | 写 `<` |
| `string_view` 存成员 | 悬垂 | 存 `std::string` |
| 到处 `std::function` | 间接调用、堆分配 | 模板或 lambda |
| 用 `vector<bool>` 当数组 | 代理引用 | `deque<bool>` |
| 保存 `c_str()` 长期用 | 修改后失效 | 当场用完 |
| 移动构造不标 `noexcept` | 容器退回复制 | 补 `noexcept` |

⚠ **关键认知**：反模式的共同点是"**看起来能用，但在特定数据规模或路径下突然变慢/崩溃**"。它们不会在编译期报错，也很难在单元测试里暴露。真正可靠的做法是理解底层机制，而不是背 API。

# 7. 综合练习

1. 实现一个词频统计程序：读入文本，用 `unordered_map<string, int>` 计数，再按次数排序输出前 10。要求用 `reserve`、`try_emplace` 和 `partial_sort`，并说明为什么不用 `map`。
2. 写一个 `Buffer` 类，内部用 `vector<char>`，提供 `append(string_view)`，并保证 `append` 失败时对象状态不变（强异常安全）。
3. 审视一段你写过的代码，找出至少三处可以改进的地方：是否该 `reserve`、是否用了 `operator[]` 查询、是否有按值遍历大对象、是否保存了可能失效的迭代器。

# 8. 小结

| 主题 | 核心结论 |
|------|----------|
| 选型 | 默认 `vector`，按"是否按键查、是否要顺序"分流 |
| 缓存 | 连续内存通常胜过理论复杂度 |
| 分配 | `reserve` 减少扩容与 rehash |
| 移动 | 标 `noexcept`，否则容器退回复制 |
| 内存 | 链表/树节点开销大，小元素尤其明显 |
| 异常安全 | 先做可能失败的事，再原子提交 |
| 遍历 | 只读用 `const auto&` |
| 句柄 | 不跨容器修改保存指针/引用/迭代器 |
