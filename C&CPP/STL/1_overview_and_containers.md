STL 是 C++ 标准库中最常被使用、也最容易被"用浅了"的部分。很多人会写 `push_back`、会调 `sort`，却说不清为什么默认选 `vector`、`map` 和 `unordered_map` 到底差在哪、容器适配器为什么不能遍历。本篇先建立一张整体地图：STL 由哪些组件构成、容器如何分类、每种容器的复杂度从哪里来，最后给出一张可以直接照着选的决策表。

# 1. STL 的组成

## 1.1 六大组件

STL 并不是"一堆容器"，而是一套互相配合的组件。先用一段代码把六个组件同时请出来：

```cpp
#include <algorithm>   // 算法
#include <iostream>
#include <iterator>    // 迭代器
#include <vector>      // 容器

int main() {
    std::vector<int> v = {3, 1, 4, 1, 5};      // 容器：存放数据
    std::sort(v.begin(), v.end());             // 迭代器划定区间，算法排序
    std::copy(v.begin(), v.end(),              // 算法 + 输出迭代器
              std::ostream_iterator<int>(std::cout, " "));
    // 仿函数/可调用对象：greater<> 决定排序方向
    std::sort(v.begin(), v.end(), std::greater<>{});
    // 适配器：把 vector 包装成栈的语义
    std::vector<int> stackLike;
    stackLike.push_back(42);
    stackLike.pop_back();
    return 0;
}
```

| 组件 | 作用 | 典型代表 |
|------|------|----------|
| 容器 | 管理一组元素的内存与生命周期 | `vector`、`map`、`list` |
| 迭代器 | 以统一方式访问容器中的元素 | `begin()`、`end()`、`back_inserter` |
| 算法 | 对区间做排序、查找、变换等操作 | `sort`、`find`、`transform` |
| 仿函数 | 可像函数一样调用的对象，用于定制行为 | `std::greater<>`、自定义比较器 |
| 适配器 | 在已有组件上包装出新接口 | `stack`、`queue`、`reverse_iterator` |
| 分配器 | 控制内存申请与释放的策略 | `std::allocator` |

★ **关键认知**：STL 的核心设计是**容器与算法解耦**。算法不认识 `vector`，它只认识"一对迭代器划出的区间"。正因为如此，同一个 `std::sort` 才能作用在 `vector`、`deque`、原生数组上。理解这一点，后面所有"为什么算法长这样"的问题都会变得顺理成章。

## 1.2 头文件与命名空间

STL 的头文件按组件拆分，用到什么就包含什么：

```cpp
#include <vector>        // vector
#include <string>        // string
#include <map>           // map、multimap
#include <unordered_map> // unordered_map
#include <algorithm>     // sort、find、transform
#include <numeric>       // accumulate、reduce
#include <functional>    // std::function、greater
#include <iterator>      // 迭代器工具与插入器
```

所有标准库名字都在 `std` 命名空间里。初学阶段为了省事写 `using namespace std;`，在小型练习里问题不大；但在头文件和大型工程里应当避免，因为它会把成百上千个名字倒进全局作用域，制造重名冲突。

⚠ **关键认知**：`<bits/stdc++.h>` 是 GCC 的私有扩展，不是标准头文件。它在竞赛里很方便，但在跨平台工程里会让 MSVC 直接编译失败。正式项目应逐个包含真正用到的头文件。

# 2. 容器的四大分类

## 2.1 序列容器

序列容器按**插入顺序**保存元素，位置由你决定，不自动排序。

| 容器 | 底层结构 | 随机访问 | 尾部插入 | 中间插入 | 典型场景 |
|------|----------|----------|----------|----------|----------|
| `vector` | 连续动态数组 | O(1) | 均摊 O(1) | O(n) | 默认首选 |
| `deque` | 分段连续数组 | O(1) | 均摊 O(1) | O(n) | 两端频繁进出 |
| `list` | 双向链表 | 不支持 | O(1) | O(1) | 已持有位置时频繁插删 |
| `forward_list` | 单向链表 | 不支持 | 无 `push_back` | O(1) | 极致节省内存 |
| `array` | 编译期定长数组 | O(1) | 不支持 | 不支持 | 长度已知且固定 |

```cpp
#include <vector>

std::vector<int> v = {1, 2, 3};
v.push_back(4);        // 尾部追加，均摊 O(1)
v.insert(v.begin(), 0); // 头部插入，需要整体后移，O(n)
```

★ **关键认知**：**默认用 `vector`**。它的元素在一块连续内存里，CPU 缓存命中率高，即使中间插入是 O(n)，实际往往也快过链表。链表只在"已经拿着插入位置的迭代器、并且频繁插删"时才真正占优，而这类场景比初学者想象的少得多。

## 2.2 有序关联容器

有序关联容器按**键的大小**自动排序，底层通常是红黑树，查找、插入、删除都是 O(log n)。

| 容器 | 是否允许重复键 | 说明 |
|------|----------------|------|
| `map` | 否 | 键值对，按键有序 |
| `multimap` | 是 | 允许重复键 |
| `set` | 否 | 只存键，自动去重排序 |
| `multiset` | 是 | 允许重复元素 |

```cpp
#include <map>

std::map<std::string, int> ages;
ages["Tom"] = 18;                 // 不存在则插入
for (const auto& [name, age] : ages) {
    // 遍历顺序按键的字典序，而不是插入顺序
}
```

## 2.3 无序关联容器

无序关联容器用**哈希表**实现，不保证顺序，但平均查找是 O(1)。

| 容器 | 是否允许重复键 | 说明 |
|------|----------------|------|
| `unordered_map` | 否 | 哈希键值对 |
| `unordered_multimap` | 是 | 允许重复键 |
| `unordered_set` | 否 | 哈希去重集合 |
| `unordered_multiset` | 是 | 允许重复元素 |

它们要求键类型提供哈希函数和相等比较，这一点会在第 3 篇展开。

## 2.4 容器适配器

适配器不是容器，而是"在某个容器上包一层受限接口"。它们故意不提供 `begin()`/`end()`，因为对外暴露的语义只有栈顶或队首。

| 适配器 | 默认底层容器 | 语义 | 主要操作 |
|--------|--------------|------|----------|
| `stack` | `deque` | 后进先出（LIFO） | `push`、`pop`、`top` |
| `queue` | `deque` | 先进先出（FIFO） | `push`、`pop`、`front`、`back` |
| `priority_queue` | `vector` + 堆 | 每次取最大（默认） | `push`、`pop`、`top` |

```cpp
#include <stack>

std::stack<int> s;
s.push(1);
s.push(2);
int top = s.top();   // 2，只看不弹
s.pop();             // 弹出 2，注意 pop 不返回值
```

⚠ **关键认知**：`stack::pop()` 和 `queue::pop()` 返回 `void`，不返回被弹出的元素。想拿到值必须先 `top()` 或 `front()` 再 `pop()`。这是标准库为了异常安全做出的设计，初学时经常误写成 `int x = s.pop();`。

## 2.5 定长容器与视图

`std::array` 是编译期定长的数组封装，不涉及堆分配，大小是类型的一部分：

```cpp
#include <array>

std::array<int, 3> a = {1, 2, 3};
static_assert(a.size() == 3);   // 大小在编译期已知
```

`std::string_view`（C++17）和 `std::span`（C++20）则是**视图**：它们不拥有数据，只记录"一块内存 + 长度"。视图的拷贝极廉价，但要求被观察的数据活得足够久。这部分在第 7 篇详细展开。

# 3. 复杂度

## 3.1 常见操作复杂度

| 操作 | `vector` | `deque` | `list` | `map`/`set` | `unordered_map`/`set` |
|------|----------|---------|--------|-------------|------------------------|
| 随机访问 | O(1) | O(1) | O(n) | 不支持 | 不支持 |
| 查找 | O(n) | O(n) | O(n) | O(log n) | 平均 O(1)，最坏 O(n) |
| 头部插入 | O(n) | O(1) | O(1) | — | — |
| 尾部插入 | 均摊 O(1) | 均摊 O(1) | O(1) | — | — |
| 有序遍历 | 需先排序 | 需先排序 | 需先排序 | O(n) | 需先排序 |

## 3.2 复杂度来自哪里

复杂度不是背出来的，而是由底层结构决定的：

```text
vector：一块连续内存
┌───┬───┬───┬───┬───┬───┐
│ 1 │ 2 │ 3 │ 4 │   │   │
└───┴───┴───┴───┴───┴───┘
  ▲ 下标直接算地址 → 随机访问 O(1)
  中间插入要把后面全部后移 → O(n)

map：红黑树（近似平衡的二叉搜索树）
          ┌───┐
          │ 4 │
        ┌─┴───┴─┐
      ┌─┴─┐   ┌─┴─┐
      │ 2 │   │ 6 │
      └───┘   └───┘
  每次比较排除一半 → O(log n)

unordered_map：哈希桶
  bucket[0] → 节点
  bucket[1] → 节点 → 节点
  bucket[2] → 空
  先算哈希定位桶，再在桶内比较 → 平均 O(1)
```

★ **关键认知**：`unordered_map` 的"平均 O(1)"有前提——哈希函数把键**均匀分散**到各个桶。如果所有键都落进同一个桶，它就退化成一条链表，查找变成 O(n)。所以"用了哈希表就一定快"是错的，键的哈希质量才是决定因素。

# 4. 如何选择容器

## 4.1 决策流程

```text
需要按键查找吗？
├─ 不需要，只按位置放 → 序列容器
│   ├─ 默认 → vector
│   ├─ 两端频繁进出 → deque
│   └─ 已持有位置且频繁插删 → list
└─ 需要，键值映射 → 关联容器
    ├─ 需要有序遍历 / 范围查询 → map / set
    └─ 只查单个键，不关心顺序 → unordered_map / unordered_set

只需要一端进出？        → stack
只需要两端进出？        → queue
每次都要取最值？        → priority_queue
长度编译期固定？        → array
```

## 4.2 场景对照表

| 需求 | 首选 | 备选 | 理由 |
|------|------|------|------|
| 通用存一批元素 | `vector` | `deque` | 缓存友好，接口简单 |
| 频繁在头部插入 | `deque` | `list` | O(1) 且仍支持随机访问 |
| 按键有序遍历 | `map` | 排序后的 `vector` | 红黑树天然有序 |
| 纯查找、不关心顺序 | `unordered_map` | `map` | 平均 O(1) |
| 去重 | `unordered_set` | `set` | 平均 O(1) |
| 固定长度 | `array` | `vector` + `reserve` | 无堆分配 |
| 后进先出 | `stack` | `vector` 手动 | 语义清晰 |
| 先进先出 | `queue` | `deque` 手动 | 语义清晰 |
| 每次取最大 | `priority_queue` | `set` | 堆的常数更小 |

# 5. 常见误区

| 误区 | 后果 | 正确做法 |
|------|------|----------|
| 认为链表插入一定比 `vector` 快 | 实际常更慢 | 先测；`vector` 的连续性优势很大 |
| 用 `map` 做纯查找 | 白白多付 O(log n) | 无顺序需求就用 `unordered_map` |
| 把 `stack` 当容器遍历 | 编译失败 | 适配器有意不暴露迭代器 |
| 以为 `unordered_map` 永远 O(1) | 哈希冲突时退化 | 关注哈希质量与负载因子 |
| `vector<bool>` 当普通数组 | 取不到 `bool&` | 需要真布尔数组用 `deque<bool>` |

⚠ **关键认知**：`std::vector<bool>` 是标准库唯一的位压缩特化，`operator[]` 返回的是代理对象而非 `bool&`。`auto& b = v[0];` 会编译失败，取地址也不行。这不是 bug，而是为了按位存储做的取舍，但常常让不知情的人踩坑。

# 6. 动手练习

1. 分别用 `vector`、`list`、`set` 存 10 万个随机整数，统计"插入 + 查找 1 万次"的总耗时，验证连续内存的优势。
2. 用 `map<string, int>` 统计一段文本的词频，再改成 `unordered_map`，对比输出顺序和运行时间。
3. 用 `stack` 判断一个字符串中的括号是否配对，体会适配器"只暴露必要接口"的好处。

# 7. 小结

| 概念 | 要点 |
|------|------|
| STL 组成 | 容器、迭代器、算法、仿函数、适配器、分配器 |
| 解耦核心 | 算法只认迭代器区间，不认具体容器 |
| 序列容器 | 按位置存，默认 `vector` |
| 有序关联 | 红黑树，O(log n)，可有序遍历 |
| 无序关联 | 哈希表，平均 O(1)，顺序不保证 |
| 适配器 | 受限接口，不能遍历 |
| 选型原则 | 先问"要不要按键查"，再问"要不要有序" |
