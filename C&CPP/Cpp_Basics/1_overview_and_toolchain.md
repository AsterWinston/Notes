很多初学者学 C++ 的第一道坎不是语法，而是"我写的这行字，最后怎么就变成了能双击运行的程序"。搞不清编译、链接、标准版本和工具链，后面学类、模板、智能指针时就会一直悬空。本篇先把整条链路打通，让你知道每一步在做什么，以及出了问题该去哪一层找原因。

# 1. C++ 的定位

## 1.1 从 C 到 C++

C++ 常被描述成"带类的 C"，这个说法只对了一小半。它确实兼容了绝大部分 C 语法，可以直接调用 C 库、复用 C 头文件，但它在此之上加了一整套抽象工具：

| 能力 | C 的做法 | C++ 的做法 |
|------|----------|-----------|
| 数据与操作绑定 | 结构体 + 一组自由函数 | 类 + 成员函数 |
| 泛型 | 宏、`void*` | 模板 |
| 资源释放 | 手动 `free`/`close` | 析构函数、RAII |
| 错误传递 | 返回码、`errno` | 异常、`std::optional` |
| 多态 | 函数指针表 | 虚函数 |

★ **关键认知**：C++ 的设计哲学是"**零开销抽象**"——你不用为没使用的特性付出运行时代价，用了的特性其效率应当与手写底层代码相当。理解这一点，才能明白为什么 `std::vector` 能接近裸数组、为什么模板要在编译期展开。

⚠ **关键认知**：不要把 C++ 当成"C 加几个语法糖"。它的对象模型、生命周期规则、类型系统都和 C 有本质差别。用 C 的思维写 C++（到处 `new`、到处裸指针、靠返回码传播错误）会同时失去两边的优点。

## 1.2 标准版本演进

C++ 每三年发布一版，社区习惯用发布年份称呼：

| 版本 | 常用名 | 代表特性 |
|------|--------|----------|
| C++11 | 现代 C++ 起点 | `auto`、`nullptr`、右值引用、移动语义、`unique_ptr` |
| C++14 | 小修补 | 泛型 lambda、变量模板、`std::make_unique` |
| C++17 | 实用大版本 | 结构化绑定、`std::optional`、`std::string_view`、`if constexpr` |
| C++20 | 又一次跃迁 | concepts、ranges、`std::format`、协程、模块 |
| C++23 | 增量完善 | `std::expected`、`std::print`、`mdspan` |

本篇及后续各篇以 **C++17 为主、C++20 为辅**，示例都能在 GCC 9+、Clang 10+、MSVC 2019+ 上编译。

★ **关键认知**：语言版本不是"越新越好用"这么简单，它同时约束了**编译器支持**、**团队工具链**和**依赖库兼容性**。新项目建议至少 C++17；要用 concepts 或 ranges 再上 C++20；上生产前先确认 CI 上的编译器版本。

# 2. 从源码到可执行文件

## 2.1 四个阶段

一个 `.cpp` 文件变成可执行文件，大致经过四步：

```text
main.cpp
   │
   ▼
┌─────────────┐   去掉注释、展开宏、处理 #include
│  预处理      │   → main.i（仍是文本）
└─────────────┘
   │
   ▼
┌─────────────┐   语法分析、语义检查、生成汇编
│  编译        │   → main.s（汇编文本）
└─────────────┘
   │
   ▼
┌─────────────┐   汇编转机器码
│  汇编        │   → main.o（目标文件）
└─────────────┘
   │
   ▼
┌─────────────┐   合并多个 .o、解析符号、链接库
│  链接        │   → app（可执行文件）
└─────────────┘
```

可以直接观察每一步：

```bash
g++ -E main.cpp -o main.i     # 只做预处理，输出展开后的源码
g++ -S main.cpp -o main.s     # 编译到汇编
g++ -c main.cpp -o main.o     # 汇编到目标文件
g++ main.o -o app             # 链接
```

## 2.2 编译与链接的分工

这两个阶段最容易混淆，因为报错风格完全不同：

| 阶段 | 关注点 | 典型错误 |
|------|--------|----------|
| 编译 | 单个翻译单元是否合法 | 语法错误、类型不匹配、找不到头文件 |
| 链接 | 所有符号能否凑齐 | `undefined reference`、重复定义 |

★ **关键认知**：编译器一次只看一个 `.cpp`（称为一个**翻译单元**）。它不需要知道别的 `.cpp` 里函数怎么实现，只要看到声明就放行。真正把所有实现拼起来的是链接器。所以"函数声明了但没定义"在编译期不报错，到链接期才炸。

一个最小例子能看清这点：

```cpp
// math.h：只有声明，告诉编译器"有这么个函数"
int add(int a, int b);

// main.cpp：调用 add，编译能过
#include "math.h"
int main() {
    return add(1, 2); // 编译器相信声明，生成"调用 add"的指令
}

// math.cpp：提供实现
#include "math.h"
int add(int a, int b) {
    return a + b;
}
```

如果编译时漏掉 `math.cpp`，报错是：

```text
undefined reference to `add(int, int)'
```

⚠ **关键认知**：看到 `undefined reference` 不要去改头文件或语法，先检查**有没有把实现文件加进编译列表**、**链接顺序对不对**。看到 `No such file or directory` 才该去查头文件路径。

## 2.3 最小程序逐段拆解

```cpp
#include <iostream>   // 引入输入输出流库的声明

int main() {                        // 程序入口，返回 int
    std::cout << "Hello, C++"       // std::cout 是标准输出流
              << std::endl;         // endl 输出换行并刷新缓冲
    return 0;                       // 0 表示正常退出
}
```

逐段说明：

1. `#include <iostream>` 是预处理指令，把标准库头文件内容原样插进来，本身不是 C++ 语句。
2. `std::cout` 中的 `std::` 是命名空间前缀，表示这个 `cout` 来自标准库，避免和用户自己的名字冲突。
3. `<<` 在这里是**运算符重载**，不是位移，第 6 篇会讲它的原理。
4. `main` 的返回值会传给操作系统，非 0 通常表示异常退出。

编译运行：

```bash
g++ -std=c++17 -Wall -Wextra main.cpp -o app
./app
```

Windows 上可执行文件带 `.exe`，运行写 `.\app.exe`。

★ **关键认知**：`-Wall -Wextra` 不是"打开所有警告"的字面意思，但它们是性价比最高的两个开关。很多未定义行为（未初始化变量、有符号无符号比较、漏写 return）都会在这里提前暴露，比运行时崩溃好查得多。

# 3. 工具链

## 3.1 三大编译器

| 编译器 | 平台 | 命令 | 特点 |
|--------|------|------|------|
| GCC | Linux、Windows(MinGW) | `g++` | 开源、生态成熟、报错较友好 |
| Clang | macOS、Linux、Windows | `clang++` | 基于 LLVM、报错清晰、工具链完善 |
| MSVC | Windows | `cl` | Visual Studio 自带、Windows 集成最好 |

指定标准：

```bash
g++ -std=c++17 main.cpp -o app          # GCC / Clang
cl /std:c++17 main.cpp                  # MSVC
```

★ **关键认知**：三家的**语言语义基本一致**，差异主要在扩展、警告文案、ABI 和标准库实现。跨平台项目要在 CI 上同时用至少两家编译，才能发现"只在某个编译器上能过"的隐式依赖。

## 3.2 配套工具

| 工具 | 作用 | 常用命令 |
|------|------|----------|
| 构建系统 | 管理多文件编译 | CMake、Make |
| 调试器 | 断点、单步、看变量 | `gdb`、`lldb`、Visual Studio 调试器 |
| 静态分析 | 不改代码找隐患 | `clang-tidy`、MSVC `/analyze` |
| 内存检查 | 查越界、泄漏 | AddressSanitizer、Valgrind |
| 格式化 | 统一代码风格 | `clang-format` |

开启运行时检查（开发期强烈建议）：

```bash
g++ -std=c++17 -g -fsanitize=address,undefined main.cpp -o app
```

`-g` 保留调试符号，`-fsanitize` 在运行时插入检查，越界、悬垂指针、有符号溢出都会直接报出位置。

⚠ **关键认知**：`-fsanitize` 系列会显著拖慢程序、增大体积，只用于开发和测试，不要带进发布构建。发布版通常用 `-O2` 或 `-O3` 并关闭 sanitizer。

## 3.3 最小 CMake 工程

当文件超过两三个，手敲编译命令就不现实了。最小 `CMakeLists.txt`：

```cmake
cmake_minimum_required(VERSION 3.20)
project(hello LANGUAGES CXX)

# 要求 C++17，并让编译器在标准不支持时报错
set(CMAKE_CXX_STANDARD 17)
set(CMAKE_CXX_STANDARD_REQUIRED ON)

add_executable(app main.cpp)
```

构建：

```bash
cmake -S . -B build
cmake --build build
```

★ **关键认知**：`-S` 指定源码目录，`-B` 指定构建目录。这种"源码与产物分离"的 **out-of-source 构建**能让你随时删掉 `build/` 重来，而不会污染源码树。构建系统的细节见本板块 CMake 模块。

# 4. 常见坑

| 现象 | 原因 | 处理 |
|------|------|------|
| `g++: command not found` | 未安装或不在 PATH | 安装 MinGW/MSVC，重启终端 |
| `undefined reference` | 实现文件没参与编译 | 把 `.cpp` 加进编译列表 |
| `multiple definition` | 头文件里定义了非 inline 函数 | 头文件只放声明，或加 `inline` |
| `fatal error: xxx.h: No such file` | 头文件路径没给 | 加 `-I路径` |
| 中文输出乱码 | 源文件编码与终端编码不一致 | 统一 UTF-8，Windows 终端用 `chcp 65001` |
| 改了代码没生效 | 编译的是旧产物 | 清理构建目录，确认输出路径 |

⚠ **关键认知**：`multiple definition` 的根源通常是**在头文件里直接写了函数定义**。头文件会被多个 `.cpp` 各包含一次，定义就被复制多份。解决办法是头文件只留声明，定义放 `.cpp`；模板和 `inline` 函数是例外，它们允许在头文件里定义。

# 5. 动手练习

1. 写一个包含 `add` 声明的头文件和两个 `.cpp`，先用一条命令编译全部源文件，再故意漏掉实现文件，观察 `undefined reference` 的完整报错。
2. 用 `g++ -E`、`-S`、`-c` 分别产出 `.i`、`.s`、`.o`，打开看看每一步的差别，找出 `#include <iostream>` 展开后的行数。
3. 写一个未初始化变量参与运算的程序，分别用带 `-Wall -Wextra` 和不带警告开关编译，记录差异；再加 `-fsanitize=undefined` 运行。

# 6. 小结

| 概念 | 要点 |
|------|------|
| C++ 定位 | 兼容 C，提供类、模板、RAII、异常等抽象 |
| 零开销抽象 | 不用的不付费，用了的接近手写 |
| 四个阶段 | 预处理 → 编译 → 汇编 → 链接 |
| 编译错误 | 单个翻译单元的问题 |
| 链接错误 | 符号凑不齐或重复 |
| 标准版本 | 新项目至少 C++17 |
| 工具链 | 编译器 + 构建系统 + 调试 + sanitizer |
