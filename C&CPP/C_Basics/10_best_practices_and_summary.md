学完语法不等于会写 C。真实项目里的问题，大多不是"不知道 `for` 怎么写"，而是边界没检查、内存没释放、类型悄悄转换、警告被忽略。本篇把前九篇的知识串成一张地图，给出可落地的编码规范、防御式编程手法、调试工具链和常见坑清单，作为整个模块的收束。

# 1. 编码规范

## 1.1 命名与格式

| 对象 | 约定 | 示例 |
|------|------|------|
| 变量与函数 | 小写下划线 | `user_count`、`read_line` |
| 宏与常量 | 全大写下划线 | `MAX_BUFFER`、`PI` |
| 类型 | 大驼峰或小写下划线 | `struct point`、`Point` |
| 全局变量 | 加前缀，慎用 | `g_config` |
| 文件名 | 小写下划线 | `file_io.c` |

格式上至少做到：缩进统一、花括号风格统一、每行不超过 100 列、运算符两侧留空格。格式本身不重要，**全项目一致**才重要。

★ **关键认知**：规范的价值不在于"哪种写法更正确"，而在于**降低阅读和 review 成本**。团队统一用一套，比每个人各写"最优风格"更有价值。

## 1.2 一条语句一件事

```c
// 差：多个副作用挤在一行，难以判断执行顺序
a = b++ + ++c;

// 好：拆开，顺序明确
a = b + c + 1;
++b;
++c;
```

⚠ **关键认知**：同一表达式中对同一变量多次修改且没有序列点，属于未定义行为。`i = i++`、`a[i] = i++` 都不是"结果不确定"，而是**编译器可以做任何事**。

## 1.3 头文件与接口

| 规则 | 原因 |
|------|------|
| 头文件只放声明 | 避免多重定义 |
| 每个头文件加包含守卫 | 防止重复包含 |
| 公开接口尽量 `const` | 明确不修改调用方数据 |
| 不在头文件里定义变量 | 多个 `.c` 包含会重复定义 |
| 内部函数加 `static` | 限制链接范围，避免符号冲突 |

# 2. 防御式编程

## 2.1 检查所有外部输入

```c
#include <limits.h>
#include <stdlib.h>

int parse_count(const char *s, int *out) {
    if (s == NULL || out == NULL) {
        return -1;                 // 参数非法
    }

    char *end = NULL;
    long v = strtol(s, &end, 10);
    if (end == s || *end != '\0') {
        return -1;                 // 不是完整数字
    }
    if (v < 0 || v > INT_MAX) {
        return -1;                 // 越界
    }

    *out = (int)v;
    return 0;
}
```

外部输入包括：命令行参数、环境变量、文件内容、网络数据、用户输入。**它们全都不可信**。

★ **关键认知**：防御式编程不是"到处加 `if`"，而是**在信任边界上做校验**。函数内部的数据如果由自己保证，就不必重复检查；跨越模块、跨越进程的数据必须验证。

## 2.2 返回值与错误码

| 风格 | 示例 | 优点 | 缺点 |
|------|------|------|------|
| 返回错误码 | `int f(...)`，0 成功 | 简单、无分配 | 错误信息有限 |
| 返回指针 | 失败返回 `NULL` | 直观 | 无法区分错误原因 |
| 输出参数 | `int f(..., T *out)` | 可带回多个值 | 调用方要判空 |
| `errno` | 全局错误码 | 标准库通用 | 易被覆盖 |

错误处理的三条纪律：

1. 每个可能失败的调用都检查返回值。
2. 失败时释放已申请的资源。
3. 错误向上传递时保留原因，不要吞掉。

## 2.3 资源清理

多资源场景用 `goto cleanup` 统一收尾：

```c
#include <stdio.h>
#include <stdlib.h>

int process(const char *path) {
    int ret = -1;
    FILE *fp = NULL;
    char *buf = NULL;

    fp = fopen(path, "r");
    if (fp == NULL) {
        goto cleanup;
    }

    buf = malloc(4096);
    if (buf == NULL) {
        goto cleanup;
    }

    // 正常处理
    ret = 0;

cleanup:
    free(buf);
    if (fp != NULL) {
        fclose(fp);
    }
    return ret;
}
```

★ **关键认知**：资源清理的核心是**单一出口**。申请的资源越多，分散 `return` 越容易漏掉某一条路径。`goto cleanup` 把释放集中到一处，反而比"结构化"的多层嵌套更可靠。

# 3. 调试工具

## 3.1 编译器警告

```bash
gcc -std=c17 -Wall -Wextra -Wconversion -Wshadow -Werror -g demo.c -o demo
```

| 选项 | 检查内容 |
|------|----------|
| `-Wall -Wextra` | 常用警告集合 |
| `-Wconversion` | 隐式窄化与符号转换 |
| `-Wshadow` | 变量遮蔽外层同名变量 |
| `-Werror` | 警告即错误，强制修复 |
| `-g` | 生成调试信息 |

⚠ **关键认知**：`-Wall` 并不包含"所有警告"，只是"常用的一组"。新项目一开始就打开高警告级别，比后期再补容易得多。

## 3.2 运行时检查

| 工具 | 检测 | 平台 |
|------|------|------|
| AddressSanitizer | 越界、悬空、双重释放、泄漏 | GCC / Clang |
| UndefinedBehaviorSanitizer | 有符号溢出、空指针、对齐 | GCC / Clang |
| Valgrind | 内存错误与泄漏 | Linux |
| gdb / lldb | 断点、单步、调用栈 | 跨平台 |

```bash
gcc -g -fsanitize=address,undefined demo.c -o demo
./demo
```

## 3.3 调试流程

```text
发现问题
   │
   ▼
用最小输入稳定复现
   │
   ▼
打开 -g 与 sanitizer 重新编译
   │
   ▼
看第一处报错，而不是最后一处崩溃
   │
   ▼
修复后回归测试，确认没有引入新问题
```

★ **关键认知**：调试的第一原则是**稳定复现**。不能复现的 bug，先想办法让它变稳定（固定输入、关闭优化、缩小范围），再谈定位。

# 4. 常见坑清单

| 类别 | 坑 | 后果 | 防范 |
|------|----|------|------|
| 类型 | 有符号与无符号混算 | 负数变大 | 统一类型，开 `-Wconversion` |
| 类型 | 整数溢出 | 未定义行为 | 运算前检查边界 |
| 数组 | 下标越界 | 内存破坏 | 用 `< 长度`，ASan 检测 |
| 字符串 | 忘记 `'\0'` | 越界读取 | 预留一字节 |
| 字符串 | `strcpy` 不限长 | 缓冲区溢出 | `snprintf` |
| 指针 | 返回局部变量地址 | 悬空指针 | 用静态或堆内存 |
| 指针 | `free` 后继续使用 | 悬空指针 | 置 `NULL` |
| 内存 | 忘记 `free` | 泄漏 | 明确所有权 |
| 内存 | 双重释放 | 堆损坏 | 置 `NULL` |
| 宏 | 参数不加括号 | 结果错误 | 参数与整体加括号 |
| 宏 | 参数带副作用 | 多次求值 | 改用内联函数 |
| 文件 | `fopen` 不判空 | 空指针崩溃 | 立即检查 |
| 文件 | 文本模式读写二进制 | 数据损坏 | 用 `"rb"` / `"wb"` |
| 流程 | `switch` 漏 `break` | 意外贯穿 | 补 `break` 或注释 |
| 流程 | `if (x = 0)` | 赋值当比较 | 常量放左边或开警告 |

★ **关键认知**：这些坑有共同点——**编译器默认不报错，运行时才爆发**。所以真正有效的防线不是"记住所有坑"，而是建立三道闸门：高警告级别、sanitizer、代码 review。

# 6. 动手练习

1. 给自己写过的任意一个 C 程序加上 `-Wall -Wextra -Wconversion -Werror`，修完所有警告，记录哪类问题最多。
2. 用 AddressSanitizer 重跑一遍涉及数组和 `malloc` 的代码，确认没有隐藏的越界或泄漏。
3. 按照本篇的资源清理模板，重构一个有多处 `return` 的函数，确保每条失败路径都释放资源。
